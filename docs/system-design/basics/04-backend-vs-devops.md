## 1. Два собеса: чем отличаются

| | Бэкенд-собес | DevOps / SRE-собес |
|---|--------------|---------------------|
| Типичные задачи | Сокращатель ссылок, лента, чат, платежи, бронирование, автодополнение | CI/CD на 30 сервисов, HA-приложение, логи на 1 ТБ/сутки, мониторинг, DR, переезд в k8s |
| Что в центре | Данные и API: что храним, как читаем и пишем, согласованность | Жизнь системы в проде: доставка, масштаб, наблюдаемость, отказы, деньги |
| Главный вопрос | «Как хранить и отдавать данные под нагрузкой?» | «Как это катить, мониторить, чинить ночью и восстанавливать?» |
| Deep dive обычно | Генерация id, fan-out, шардирование, кеш, транзакции | Пайплайн, failover БД, буферы, автоскейлинг, бэкапы |
| Чего ждут в оценках | RPS чтения и записи, объём, размер объекта | То же + ёмкость инфраструктуры, хранение логов/метрик, RPO/RTO, стоимость |
| Типичный провал | Нет отказов и эксплуатации: «Kubernetes сам поднимет» | Нет данных: «а что хранится и сколько?» — без этого нет ни мощностей, ни DR |

SRE-собес — вариант DevOps-собеса с упором на SLO, инциденты, отказоустойчивость и
ёмкость. Platform engineering-собес — с упором на самообслуживание разработчиков:
шаблоны, golden path, порталы ([Platform Engineering](/platform/)).

> ⭐ Граница между типами размыта. На бэкенд-собесе senior-кандидата почти всегда спросят
> «как вы это выкатите и что будет при отказе?». На DevOps-собесе — «какие данные храним
> и что можно потерять?». Поэтому в этом курсе **каждая задача** разбирается с двух сторон.

**Как понять, какой у тебя собес:** название этапа в приглашении («system design»,
«infrastructure design», «architecture»), вакансия, вопрос рекрутеру: «Задача будет больше
про данные и API или про инфраструктуру?». Это нормальный вопрос.

## 2. Одна задача глазами двух

**Задача:** «Спроектируйте загрузку фото для соцсети: пользователь загружает фото, получает
три размера (миниатюра, средний, оригинал), фото показываются в ленте».

### Общие требования и оценки

```text:no-line-numbers
 ФУНКЦИИ:   загрузить фото · получить 3 размера · показать по ссылке · удалить
 ВНЕ РАМОК: лента, комментарии, распознавание лиц
 НЕФУНКЦ.:  фото готово через ≤ 30 с после загрузки (99%) · просмотр p99 < 300 мс
            оригинал после «загружено» не теряем · просмотры доступны 99,9%

 ОЦЕНКИ (допущения: 10 млн DAU, 100 000 загрузок/сутки, оригинал 3 МБ,
         50 млн просмотров/сутки, в среднем отдаём 100 КБ)
   загрузки:   10^5 / 86 400 ≈ 1,2/с, пик ×5 ≈ 6/с → ~18 МБ/с входящих в пике
   оригиналы:  10^5 × 3 МБ = 300 ГБ/сутки ≈ 110 ТБ/год            ← хранение растёт быстро
   размеры:    ~150 КБ на фото → 15 ГБ/сутки ≈ 5,5 ТБ/год
   просмотры:  5 × 10^7 / 86 400 ≈ 580 RPS, пик ×3 ≈ 1700 RPS       ← работа для CDN
   отдача:     5 × 10^7 × 100 КБ = 5 ТБ/сутки ≈ 150 ТБ/месяц        ← главная статья расходов
   обработка:  ~1 CPU·с на фото (3 размера) → в пике ~6 ядер + запас
```

Числа одни и те же, но бэкендер и девопс делают из них разные выводы.

### Взгляд бэкендера

```text:no-line-numbers
 клиент ─1─► API: POST /api/photos ──────► PostgreSQL: photos (id, owner, status=pending)
    │              ◄── { photo_id, upload_url } (presigned PUT/POST на 15 мин)
    │
    └─2─► S3: originals/<photo_id> (клиент грузит напрямую, мимо API)
                  │
                  └─3─► событие «объект создан» ──► очередь resize-jobs
                                                         │
                                          воркеры ◄──────┘  (идемпотентны: ключ = photo_id)
                                             │ 4. читают оригинал, делают 3 размера
                                             ├──► S3: thumbs/<photo_id>/{s,m,l}.webp
                                             └──► PostgreSQL: status=ready, urls

 чтение: GET /api/photos/<id> → метаданные и URL → браузер берёт картинку с CDN
```

Решения бэкендера:

- **Загрузка мимо API** через presigned URL: API не гоняет через себя 18 МБ/с, а только
  выдаёт подпись. Лимит размера — через presigned POST с условием `content-length-range`
  или проверку после загрузки.
- **Статусы** `pending → processing → ready | failed`: клиент видит, что фото готовится,
  а не ждёт синхронной обработки.
- **Очередь задач**: обработка асинхронная, пики загрузок сглаживаются.
- **Идемпотентные воркеры**: очередь может доставить задачу дважды (at-least-once) —
  повторная обработка перезаписывает те же ключи, дублей нет
  ([Очереди: 01. Концепции очередей](/queues/01-queues-concepts)).
- **Неизменяемые ключи** объектов (новая версия — новый ключ): CDN кеширует навсегда,
  инвалидация не нужна.

### Взгляд девопса

```text:no-line-numbers
 пользователи ──► CDN (кеш размеров, hit ratio > 95%) ──► S3 thumbs (origin)
                                                            │ lifecycle: оригиналы старше
 API (Deployment ×3, 3 AZ, HPA по CPU/RPS)                  │ 90 дней → холодный класс
    │                                                       │
    ▼                                                  S3 originals ── версионирование +
 PostgreSQL (primary + standby в другой AZ, PITR)            │         репликация в другой регион
                                                             ▼
 очередь (SQS / RabbitMQ) ──► воркеры (Deployment, KEDA: 1…30 реплик по длине очереди)

 наблюдаемость: SLO «готово ≤ 30 с в 99%», возраст старейшей задачи в очереди,
                ошибки обработки, hit ratio CDN, 5xx и p99 API
 стоимость:     отдача (150 ТБ/мес) ≫ хранение ≫ вычисления → CDN, WebP/AVIF, lifecycle
```

Решения девопса:

- **Воркеры масштабируются по длине очереди**, а не по CPU: CPU отстаёт от реальной
  нагрузки, а длина очереди показывает её сразу. KEDA умеет масштабировать по очереди
  и до нуля ([Kubernetes: 18. HPA и автоскейлинг](/kubernetes/18-hpa-autoscaling),
  [FinOps: 03. Автоскейлинг и стоимость](/finops/03-autoscaling-cost)).
- **SLO на пользовательский путь** «фото готово за 30 с», а не на CPU воркеров. Алерт —
  по возрасту самой старой задачи в очереди: он растёт раньше, чем пользователи начнут
  жаловаться ([SRE: 02. SLI, SLO и error budget](/sre/02-sli-slo-error-budget)).
- **Оригиналы — источник правды**: версионирование, репликация в другой регион. Размеры —
  производные данные: их можно пересоздать, отдельно не бэкапим.
- **Главная статья расходов — отдача трафика**, а не серверы: высокий hit ratio CDN,
  современные форматы (WebP/AVIF заметно легче JPEG), правильный `Cache-Control`.
- **Хранение растёт на ~110 ТБ в год**: lifecycle-политики переводят старые оригиналы в
  дешёвый класс хранения ([Облака: 04. S3 и объектное хранилище](/cloud/04-s3-storage)).

### Где взгляды встречаются

| Решение | Почему так бэкендеру | Что это значит для эксплуатации |
|---------|----------------------|----------------------------------|
| Загрузка через presigned URL | API не держит большие тела запросов | Меньше реплик API, но нужны лимиты и проверка содержимого |
| Очередь задач | Асинхронность, статусы | Новая система: мониторинг лага, DLQ, масштабирование по очереди |
| Идемпотентные воркеры | At-least-once доставка | Можно смело ретраить и перезапускать воркеры |
| Неизменяемые ключи | Нет гонок при обновлении | CDN кеширует навсегда, нет инвалидаций, высокий hit ratio |
| Статусы в БД | Клиент видит прогресс | Метрика «сколько фото в processing дольше 30 с» — готовый SLI |
| Размеры — производные | Их можно пересоздать | Не бэкапим 5,5 ТБ/год, DR проще |

> ⭐ Хорошее решение работает в обе стороны: бэкенд-решение упрощает эксплуатацию,
> и наоборот. Когда ты называешь решение, добавь второй взгляд одной фразой: «Ключи
> неизменяемые — значит, CDN кеширует навсегда и инвалидации не нужны».

### 3.1. Развёртывание

**Что сказать:** где крутится каждый компонент (Kubernetes, ВМ, managed-сервис), сколько
реплик и как они распределены по зонам, как выкатывается новая версия без простоя и как
меняется схема БД.

| Компонент | Типовой ответ |
|-----------|---------------|
| Stateless API | Deployment, ≥ 3 реплики, разнесены по AZ (topology spread), readiness/liveness, graceful shutdown, rolling update или canary |
| Воркеры | Отдельный Deployment, свои ресурсы и масштабирование; при выкатке дорабатывают текущую задачу (SIGTERM → закончить и выйти) |
| База данных | Managed или оператор/Patroni вне общего потока выкаток; миграции — отдельной джобой до выкатки |
| Схема БД | Expand/contract: сначала добавить совместимо, потом переключить код, потом удалить старое ([Базы данных: 13. Миграции схемы](/databases/13-schema-migrations)) |
| Конфиг и секреты | Через env и Secret, не в образе; один образ на все окружения |

> ⚠️ Частая ошибка: «выкатываем rolling update» без слова о миграциях. Во время rolling
> update старая и новая версии работают одновременно — схема должна подходить обеим.

Прогрессивная выкатка (canary, анализ метрик, автоматический откат) — в
[Platform: 06. Progressive delivery](/platform/06-progressive-delivery).

### 3.2. Масштабирование

**Что сказать:** что масштабируется горизонтально и по какой метрике, что — только
вертикально, и где **потолок** — что кончится первым.

| Компонент | Метрика масштабирования | Потолок |
|-----------|------------------------|---------|
| Stateless API | HPA по CPU или RPS на под | Соединения к БД: подов × пул ≤ `max_connections` |
| Воркеры очереди | KEDA по длине очереди или лагу потребителей | Партиции Kafka: потребителей в группе не больше партиций; лимиты внешних API |
| Кеш | Шардирование ключей (Redis Cluster) | Горячий ключ живёт на одном шарде |
| Реляционная БД | Вертикально + реплики чтения | Запись в один primary → дальше шардирование |
| Объектное хранилище | Само (managed) | Лимиты запросов на префикс — распределять ключи |

> ⭐ Слово «потолок» — сильный сигнал. «API масштабируется HPA до 40 подов, дальше упрёмся
> в соединения к PostgreSQL — поэтому PgBouncer» лучше, чем «всё масштабируется
> горизонтально».

### 3.3. Наблюдаемость

**Что сказать:** 1–2 SLI на главный пользовательский путь со SLO, метрики сервисов (RED)
и ресурсов (USE), на что алертим и как связываем логи и трейсы.

| Что | Типовой ответ |
|-----|---------------|
| SLI/SLO | Например, для редиректа linkd: «99,95% успешных и 99% быстрее 50 мс за 30 дней» — на пользовательский путь, а не на CPU |
| RED (сервисы) | Rate, Errors, Duration — для API и воркеров |
| USE (ресурсы) | Utilization, Saturation, Errors — для БД, дисков, нод |
| Асинхронность | Длина очереди, возраст старейшего сообщения, DLQ |
| Кеш | Hit ratio, eviction, память |
| Алерты | По burn rate SLO, а не по каждому скачку CPU |
| Трейсы и логи | `trace_id` в каждом логе, трейсы через API → очередь → воркер ([SRE: 03. Трейсинг и OpenTelemetry](/sre/03-tracing-opentelemetry)) |

> ⚠️ Частая ошибка: «поставим Prometheus и Grafana». Это инструменты, а не ответ.
> Ответ — **что** мерим и **когда** будим человека.

### 3.4. Отказы

**Что сказать:** пройти по схеме и для каждого блока ответить «что будет, если он упадёт»:
что увидит пользователь, как система обнаружит и переживёт отказ, что потеряем.

| Блок упал | Типовой ответ |
|-----------|---------------|
| Под или нода | Балансировщик убирает по readiness, реплики в других AZ, PDB при обслуживании |
| Кеш | Чтение идёт в БД — нужен лимит (иначе каскад), прогрев, request coalescing |
| Primary БД | Автоматический failover на standby, приложение ретраит с backoff, запись недоступна секунды–минуты |
| Очередь | Продюсер буферизует или отвечает «попробуйте позже»; после восстановления — разгребание очереди |
| Внешний сервис | Таймаут, circuit breaker, деградация (показать без рекомендаций, отправить позже) |
| Целая AZ | Остальные AZ держат нагрузку — значит, в каждой запас мощности |

Общие инструменты: таймауты на каждый вызов, ретраи с экспоненциальным backoff и jitter,
идемпотентность, circuit breaker, bulkhead, деградация функций
([SRE: 06. Паттерны надёжности](/sre/06-reliability-patterns),
[Распределённые: 01. Заблуждения о сети](/distributed/01-fallacies-basics)).

> ⚠️ «Kubernetes сам всё поднимет» — не ответ. Kubernetes перезапустит под, но не
> переключит базу, не спасёт от retry storm и не вернёт потерянную AZ.

### 3.5. Данные и DR

**Что сказать:** какие данные — источник правды, а какие производные; как их бэкапим и
реплицируем; RPO и RTO для каждого класса данных; что переживаем — потерю диска, AZ, региона,
ошибочный `DELETE`.

| Класс данных | Пример | Защита |
|--------------|--------|--------|
| Источник правды, транзакции | Пользователи, заказы, ссылки | Реплика в другой AZ + бэкап с PITR вне площадки |
| Источник правды, файлы | Оригиналы фото | Версионирование, репликация в другой регион, object lock от шифровальщика |
| Производные | Кеш, миниатюры, поисковый индекс | Не бэкапим — пересоздаём; оцениваем время пересоздания |
| Поток событий | Клики, логи | Буфер (Kafka) с retention, допустима частичная потеря — согласовать с бизнесом |

> ⭐ Реплика — не бэкап: она повторит `DROP TABLE`. И разные данные — разные RPO:
> для заказов минуты, для счётчика просмотров часы
> ([Базы данных: 05. Бэкап и восстановление](/databases/05-backup-restore),
> [Хранилища: 07. Velero и DR](/storage/07-velero-dr)).

Multi-AZ — разумный стандарт. Multi-region — только если требование переживать потерю
региона стоит своей цены: сложность, задержка репликации, стоимость в разы.

### 3.6. Безопасность

**Что сказать:** кто и как получает доступ, где секреты, как защищаемся от злоупотреблений
и что с персональными данными.

| Тема | Типовой ответ |
|------|---------------|
| Аутентификация и авторизация | Токены (OAuth2/OIDC), проверка прав на каждый ресурс, а не только на вход |
| Секреты | Vault или облачный менеджер секретов, короткоживущие учётные данные ([Vault](/vault/)) |
| Сеть | TLS снаружи и по возможности внутри, NetworkPolicy, БД не торчит наружу ([Kubernetes: 13. NetworkPolicy](/kubernetes/13-networkpolicy)) |
| Злоупотребления | Rate limiting по пользователю и IP, лимиты размера, WAF, капча на создание |
| Пользовательский контент | Проверка типа по содержимому, а не по расширению; удаление EXIF (геолокация); защита от «бомб» в картинках и архивах |
| Минимальные права | Сервис может только то, что нужно: воркер читает originals и пишет thumbs, но не удаляет ([Безопасность: 05. IAM](/security/05-iam-access)) |
| Персональные данные | Где хранятся, кто видит, как удаляются по запросу, требования к стране хранения |

### 3.7. Стоимость

**Что сказать:** 2–3 главные статьи расходов, что из них растёт вместе с нагрузкой, и
рычаги экономии.

| Статья | Когда главная | Рычаги |
|--------|---------------|--------|
| Вычисления | CPU-тяжёлая обработка, много сервисов | Rightsizing, автоскейлинг, spot для воркеров ([FinOps: 02. Rightsizing](/finops/02-k8s-rightsizing)) |
| Хранение | Файлы, логи, история | Классы хранения, lifecycle, сжатие, сроки хранения |
| Исходящий трафик | Медиа, большие ответы | CDN, форматы и сжатие, кеширование |
| Managed-сервисы | Managed БД, очереди, поиск | Сравнить с ценой своей эксплуатации (люди, дежурства) |
| Люди | Сложная своя инфраструктура | Managed вместо своего, меньше компонентов |

> ⭐ Стоимость — инженерный параметр, а не вопрос бухгалтерии. Фраза «главная статья —
> исходящий трафик, поэтому CDN и WebP» показывает зрелость лучше любой схемы.

### 3.8. Пример: блок целиком для сервиса фото

| # | Вопрос | Ответ |
|---|--------|-------|
| 1 | Развёртывание | API и воркеры — отдельные Deployment в k8s, по 3 AZ, rolling update; БД — managed PostgreSQL; миграции expand/contract отдельной джобой |
| 2 | Масштабирование | API — HPA по CPU; воркеры — KEDA 1…30 по длине очереди; потолок — соединения к БД (PgBouncer) и лимиты S3 на префикс |
| 3 | Наблюдаемость | SLO «готово ≤ 30 с в 99%», «просмотр p99 < 300 мс»; алерты по burn rate и возрасту старейшей задачи; hit ratio CDN; трейс API → очередь → воркер |
| 4 | Отказы | Воркеры упали — задачи копятся, фото в processing, после восстановления разгребаем; битое фото после 3 попыток — DLQ и status=failed; CDN недоступен — отдаём с origin с лимитом |
| 5 | Данные и DR | Оригиналы: версионирование + репликация в другой регион, RPO минуты; метаданные: PITR; размеры — пересоздаём из оригиналов |
| 6 | Безопасность | Presigned URL на 15 мин, лимит размера, проверка формата по содержимому, удаление EXIF, лимит загрузок на пользователя, приватные фото — подписанные URL CDN |
| 7 | Стоимость | Отдача ≫ хранение ≫ вычисления: hit ratio CDN, WebP/AVIF, lifecycle оригиналов в холодный класс, spot для воркеров |

Этот же формат таблицы ты увидишь в каждой задаче курса — начиная с
[Бэкенд-задачи: 01. Сокращатель ссылок](/system-design/backend-cases/01-url-shortener).

## 4. Минимум для каждого

### Что бэкендер должен уметь сказать про эксплуатацию

| Тема | Минимум |
|------|---------|
| Stateless | Состояние в БД, кеше и S3, а не в памяти пода — иначе нельзя масштабировать и перезапускать |
| Пробы и остановка | Readiness ≠ liveness; по SIGTERM дорабатываем запросы и выходим ([Kubernetes: 09. Пробы и ресурсы](/kubernetes/09-probes-resources)) |
| Миграции | Expand/contract: две версии кода живут одновременно |
| Соединения | Подов × пул ≤ `max_connections`, иначе масштабирование ломает БД |
| Таймауты и ретраи | Таймаут на каждый вызов, ретрай с jitter, только для идемпотентных операций |
| Метрики | RED для своего сервиса, SLO на пользовательский путь |
| Бэкапы | Реплика ≠ бэкап; что можно пересоздать, а что нет |
| Деньги | Что в его дизайне дорого: трафик, хранение, тяжёлые запросы |

### Что девопс должен уметь сказать про данные и API

| Тема | Минимум |
|------|---------|
| API | REST-ресурсы, коды ответов, идемпотентность, пагинация курсором |
| Согласованность | Что значит читать с реплики, read-your-writes ([Распределённые: 02](/distributed/02-consistency-cap)) |
| Индексы и запросы | Почему запрос медленный, что такое seq scan, зачем индекс ([Базы данных: 08. Основы SQL](/databases/08-sql-basics)) |
| Транзакции | ACID, уровни изоляции на уровне «что может пойти не так» |
| Кеш | Cache-aside, TTL, инвалидация, stampede |
| Очереди | At-least-once, идемпотентные потребители, DLQ, порядок в партиции ([Очереди: 02. Kafka](/queues/02-kafka-basics)) |
| Шардирование | Ключ шардирования, горячий ключ, ребалансировка ([Распределённые: 03](/distributed/03-replication-partitioning)) |
| Выбор хранилища | По запросам к данным: SQL, KV, документное, колоночное, объектное |

> 💡 Девопс, который спрашивает «какой у вас RPS записи и что нельзя потерять?», выглядит
> сильнее девопса, который знает 20 операторов Kubernetes, но не знает, что хранит сервис.

## Грабли

| Грабля | Что не так | Правильно |
|--------|-----------|-----------|
| Бэкендер: «Kubernetes сам поднимет» | Отказы БД, AZ и зависимостей не разобраны | Пройти каждый блок: упал — что дальше |
| Девопс: схема без данных | Непонятно, что бэкапить и сколько мощностей | Коротко: что храним, объём, что нельзя потерять |
| Эксплуатация списком инструментов | «Prometheus, Grafana, ArgoCD» — не ответ | Что мерим, когда будим, как катим и откатываем |
| Rolling update без миграций | Две версии кода на одной схеме ломаются | Expand/contract |
| Масштабирование «горизонтально, и всё» | Не назван потолок | Что кончится первым: соединения, запись, горячий ключ |
| Воркеры по CPU | Нагрузка видна с опозданием | По длине очереди или лагу (KEDA) |
| Один RPO на все данные | Дорого или ненадёжно | Классы данных: источник правды, производные, события |
| Бэкап производных данных | Платим за то, что пересоздаётся | Бэкап источника правды, оценка времени пересоздания |
| Стоимость не упомянута | Решение может быть нереалистичным | 2–3 главные статьи и рычаги |
| На бэкенд-собесе 15 минут про k8s | Не хватило времени на данные и API | Эксплуатация 2–3 минуты, глубже — по запросу |

## 💼 Как это на работе

- В реальной команде дизайн почти всегда пишут **вместе**: бэкендер приносит API и данные,
  девопс или SRE — выкатку, наблюдаемость и DR. Блок «⚙️ Эксплуатация» — готовый раздел
  design doc ([05. Design doc и ADR](/system-design/basics/05-design-doc-adr)).
- Перед запуском новой системы часто проводят **production readiness review** — по сути
  те же 7 вопросов: как катим, как растём, что мерим, что ломается, как восстанавливаем,
  кто имеет доступ, сколько стоит.
- Бэкендер, который сам пишет SLO, миграции expand/contract и runbook на отказы, быстрее
  растёт до senior: его сервисы реже будят дежурных.
- Девопс, который понимает модель данных, лучше планирует мощности, бэкапы и DR — и
  его зовут в архитектурные обсуждения раньше, а не «когда уже надо деплоить».
- В этом сайте оба взгляда уже есть: эксплуатация — в базовом DevOps-роадмапе и
  специализациях, данные — в [Базах данных](/databases/) и
  [Распределённых системах](/distributed/). Курс System Design соединяет их на задачах.

## 🧠 Что запомнить

1. Бэкенд-собес — про данные и API под нагрузкой, DevOps-собес — про жизнь системы в проде.
2. ⭐ В хорошем ответе есть оба взгляда, меняется только время на каждый.
3. ⭐ Блок «Эксплуатация» — 7 вопросов в фиксированном порядке, в каждой задаче курса.
4. У масштабирования всегда называй метрику и потолок.
5. SLO ставится на пользовательский путь, а не на CPU.
6. Воркеры очереди масштабируются по длине очереди, а не по CPU.
7. ⭐ Разные данные — разные RPO; производные данные пересоздаются, а не бэкапятся.
8. «Kubernetes сам поднимет» — не ответ на вопрос об отказах.
9. Стоимость — инженерный параметр: назови главные статьи и рычаги.
10. Бэкендеру нужен минимум эксплуатации, девопсу — минимум данных и API.

### Блок A. Теория

**A1.** Чем отличается центр внимания на бэкенд-собесе и на DevOps-собесе?

<details><summary>Ответ</summary>

Бэкенд — данные и API: что храним, как читаем и пишем под нагрузкой, согласованность.
DevOps — жизнь системы в проде: доставка, масштаб, наблюдаемость, отказы, DR, стоимость.

</details>

**A2.** ⭐ Перечисли 7 вопросов блока «Эксплуатация» по порядку.

<details><summary>Ответ</summary>

Развёртывание, масштабирование, наблюдаемость, отказы, данные и DR, безопасность, стоимость.

</details>

**A3.** Почему при rolling update важно говорить о миграциях схемы?

<details><summary>Ответ</summary>

Во время rolling update старая и новая версии кода работают одновременно на одной
схеме. Изменение схемы должно быть совместимо с обеими — отсюда expand/contract.

</details>

**A4.** Что значит «назвать потолок» масштабирования? Приведи пример.

<details><summary>Ответ</summary>

Назвать ресурс, который кончится первым, несмотря на горизонтальное масштабирование.
Пример: поды API растут по HPA, но подов × пул упирается в `max_connections` PostgreSQL —
нужен PgBouncer или меньший пул.

</details>

**A5.** ⭐ Почему воркеры очереди лучше масштабировать по длине очереди, а не по CPU?

<details><summary>Ответ</summary>

Длина очереди (или лаг) показывает нагрузку сразу, а CPU — с опозданием и косвенно;
воркер может ждать внешний API и почти не тратить CPU при растущей очереди. KEDA умеет
масштабировать по очереди и до нуля.

</details>

**A6.** Какой SLI выбрать для асинхронной обработки фото?

<details><summary>Ответ</summary>

Долю фото, ставших готовыми за N секунд после загрузки (например, ≤ 30 с в 99%). Плюс
технический сигнал для алертов — возраст самой старой задачи в очереди.

</details>

**A7.** Чем источник правды отличается от производных данных и как это влияет на DR?

<details><summary>Ответ</summary>

Источник правды нельзя восстановить из другого места — его бэкапят и реплицируют.
Производные (кеш, миниатюры, индекс) можно пересоздать — их не бэкапят, но оценивают
время пересоздания.

</details>

**A8.** Почему фраза «Kubernetes сам всё поднимет» — плохой ответ про отказы?

<details><summary>Ответ</summary>

Kubernetes перезапускает поды и переносит их с упавших нод, но не переключает БД,
не защищает от retry storm и каскадных отказов, не решает потерю AZ без запаса мощности
и не восстанавливает данные.

</details>

**A9.** Что входит в блок «Безопасность» для сервиса с пользовательским контентом?

<details><summary>Ответ</summary>

Аутентификация и проверка прав на ресурс, секреты в Vault, лимиты частоты и размера,
проверка типа по содержимому, удаление EXIF, защита от «бомб», минимальные права сервисов,
персональные данные.

</details>

**A10.** Назови три главные статьи расходов в облаке и по рычагу на каждую.

<details><summary>Ответ</summary>

Вычисления — rightsizing, автоскейлинг, spot. Хранение — классы хранения и lifecycle.
Исходящий трафик — CDN, сжатие, форматы. Плюс managed-сервисы и люди.

</details>

**A11.** Что бэкендер должен знать про соединения к БД?

<details><summary>Ответ</summary>

Что число соединений ограничено (`max_connections`), каждый под держит свой пул,
и при масштабировании подов × пул может превысить лимит — поэтому пул меньше,
PgBouncer и ограничение maxReplicas.

</details>

**A12.** Что девопс должен знать про очереди, чтобы спроектировать воркеры?

<details><summary>Ответ</summary>

Что доставка обычно at-least-once — потребители должны быть идемпотентны; что есть DLQ
для «ядовитых» сообщений; что порядок гарантирован только в партиции, и потребителей
в группе не больше партиций.

</details>

**A13.** Сколько времени давать эксплуатации на бэкенд- и на DevOps-собесе?

<details><summary>Ответ</summary>

На бэкенд-собесе 2–3 минуты по 7 пунктам, глубже — по запросу. На DevOps-собесе
10–15 минут, все 7 вопросов подробно; API и данные сжимаются до 3 минут.

</details>

**A14.** Зачем при загрузке файлов использовать presigned URL? Какой у этого минус?

<details><summary>Ответ</summary>

Клиент грузит прямо в S3, API не держит большие тела запросов — меньше реплик и
памяти. Минус: API не видит содержимое при загрузке — нужны лимиты размера в подписи
(presigned POST с `content-length-range`) и проверка файла после загрузки.

</details>

### Блок B. «Что тут не так»

```
B1.  Бэкенд-собес. Кандидат 20 минут рассказывает про Helm-чарты и ArgoCD,
     на API и модель данных осталось 3 минуты.

B2.  DevOps-собес. «Какие данные хранит сервис — не важно, я отвечаю за инфраструктуру».

B3.  «Наблюдаемость: поставим Prometheus, Grafana и Loki».

B4.  «Масштабирование: всё stateless, масштабируем горизонтально бесконечно».

B5.  «Воркеры обработки видео масштабируем HPA по CPU 70%».

B6.  «Бэкапим всё: БД, Redis, миниатюры, поисковый индекс — RPO 5 минут для всего».

B7.  «Выкатываем rolling update, в той же выкатке переименовываем колонку email в mail».

B8.  «SLO: CPU воркеров ниже 80% в 99,9% времени».

B9.  «Безопасность: у нас HTTPS».

B10. «Стоимость? Облако же, платим по факту, это оптимально».

B11. Сервис фото: «Миниатюры кешируем на CDN на 5 минут, при обновлении фото
     перезаписываем тот же ключ».
```

<details><summary>Ответы</summary>

**B1.** ⚠️ Не тот фокус для бэкенд-собеса. Эксплуатация — 2–3 минуты, центр — данные и API.

**B2.** ⚠️ Без данных нельзя спланировать ни мощности, ни DR. Коротко выяснить: что храним,
объём, что нельзя потерять.

**B3.** ⚠️ Инструменты вместо ответа. Что мерим (SLI/SLO, RED, очередь), когда будим (burn rate).

**B4.** ⚠️ Нет потолка. Назвать, что кончится первым: соединения к БД, запись в primary,
горячий ключ.

**B5.** ⚠️ CPU отражает нагрузку с опозданием и не показывает очередь. Масштабировать по длине
очереди (KEDA).

**B6.** ⚠️ Производные данные (Redis, миниатюры, индекс) пересоздаются — их бэкап — лишние
деньги. Разные RPO для разных классов данных.

**B7.** ⚠️ Старая версия во время rolling update сломается на переименованной колонке.
Expand/contract: добавить `mail`, писать в обе, переключить чтение, потом удалить `email`.

**B8.** ⚠️ SLO на ресурс, а не на пользовательский путь. «Фото готово за 30 с в 99%».

**B9.** ⚠️ Мало. Доступы и права, секреты, лимиты, проверка контента, минимальные права,
персональные данные.

**B10.** ⚠️ Стоимость — часть дизайна. Назвать главные статьи (здесь — трафик) и рычаги.

**B11.** ⚠️ Перезапись того же ключа требует инвалидации CDN и даёт старые версии в кешах.
Неизменяемые ключи (новая версия — новый ключ) и долгий кеш.

</details>

### Блок C. Практика

#### C1. 🔑 Блок «Эксплуатация» для Pastebin
Возьми разбор Pastebin из [03. Фреймворк ответа](/system-design/basics/03-interview-framework),
раздел 14, и заполни таблицу из 7 вопросов подробно — как в разделе 3.8. Уложи устный ответ
в 3 минуты.

<details><summary>Ответ</summary>

Ориентир: API в k8s по 3 AZ, rolling update, expand/contract; HPA по CPU, потолок —
соединения к PG; SLO на чтение 99,9% и p99, hit ratio кеша и CDN; Redis упал — чтение
в PG с лимитом; PG с репликой и PITR, S3 с версионированием, кеш не бэкапим; лимиты на
создание, непредсказуемые id, размер; главные расходы — хранение S3 и трафик.

</details>

#### C2. 🔑 Одна задача — два ответа
Возьми задачу «система уведомлений (push, email, SMS)». Ответь дважды по 15 минут: как
на бэкенд-собесе и как на DevOps-собесе. Сравни, что поменялось.

<details><summary>Ответ</summary>

Бэкенд-ответ: API отправки, шаблоны, предпочтения пользователя, очередь по каналам,
идемпотентность (не отправить дважды), ретраи с учётом лимитов провайдеров. DevOps-ответ:
воркеры по каналам с KEDA, SLO «доставлено за N секунд», алерты на лаг и ошибки провайдера,
DLQ, секреты провайдеров, стоимость SMS как главная статья.

</details>

#### C3. 🔑 Найди потолок
Для схемы «API (HPA до 50 подов, пул 20) → PostgreSQL (`max_connections = 500`) →
Redis (один инстанс)» назови, что кончится первым при росте нагрузки, и чем лечить.

<details><summary>Ответ</summary>

50 × 20 = 1000 > 500 — соединения кончатся раньше CPU. Лечение: PgBouncer, меньший пул,
ограничение maxReplicas. Следующий потолок — один Redis (память и горячий ключ) и запись в
один primary PostgreSQL.

</details>

#### C4. Классы данных
Для интернет-магазина раздели данные на классы (источник правды, производные, события)
и назначь каждому RPO и способ защиты: заказы, корзины, каталог, поисковый индекс,
рекомендации, логи кликов, картинки товаров.

<details><summary>Ответ</summary>

Заказы — источник правды, RPO ≈ 0–минуты: синхронная реплика + PITR. Каталог —
источник правды, PITR. Картинки — источник правды, версионирование и репликация. Корзины —
можно потерять часть (часы) или хранить в Redis с AOF. Поисковый индекс и рекомендации —
производные, пересоздаём. Логи кликов — события, допустима частичная потеря, буфер Kafka.

</details>

#### C5. Минимум для другой стороны
Если ты бэкендер — выпиши своими словами минимум эксплуатации из раздела 4 и объясни
каждый пункт на примере своего сервиса. Если девопс — то же про данные и API.

<details><summary>Ответ</summary>

Проверка: по каждому пункту есть пример из реальной системы («у нас 12 подов по 10
соединений, `max_connections = 200`…»), а не пересказ определения.

</details>

### Блок D. Ситуации

**D1.** Бэкенд-собес, интервьюер-разработчик. Ты начинаешь про выкатку, он перебивает:
«Это неинтересно, давайте про данные».

<details><summary>Ответ</summary>

Сразу перейти к данным. Эксплуатацию в конце дать одной таблицей за минуту — или
пропустить, если интервьюер ясно показал, что не нужно.

</details>

**D2.** DevOps-собес. Задача: «HA для нашего сервиса», а про сервис ничего не сказано.

<details><summary>Ответ</summary>

Задать 3–4 вопроса про данные: что хранит, объём, соотношение чтения и записи, что
недопустимо потерять. Без этого нельзя выбрать ни репликацию, ни RPO, ни мощности.

</details>

**D3.** Интервьюер спрашивает: «Сколько это будет стоить?», а ты не знаешь цен облака.

<details><summary>Ответ</summary>

Не называть выдуманных цифр, а назвать структуру: главные статьи (здесь трафик и
хранение), как они растут с нагрузкой, рычаги. Порядок величин можно прикинуть, если
интервьюер даст цену за ГБ.

</details>

**D4.** На вопрос «что будет, если упадёт Redis?» ты понимаешь, что база не выдержит
весь поток чтений.

<details><summary>Ответ</summary>

Сказать это прямо и предложить защиту: лимит запросов в БД при промахах, request
coalescing, отдача устаревших данных, Redis с репликой и автоматическим failover,
прогрев после восстановления.

</details>

**D5.** Интервьюер-SRE спрашивает: «Как вы узнаете, что пользователям плохо, раньше,
чем они напишут в поддержку?»

<details><summary>Ответ</summary>

SLO на пользовательский путь и алерты по burn rate: быстрый расход бюджета — будим
сразу, медленный — тикет. Плюс синтетические проверки главных сценариев снаружи.

</details>

### Блок E. Вопросы с собеседования

**1.** Чем DevOps-system design отличается от бэкенд-system design?

<details><summary>Ответ</summary>

Бэкенд — данные, API, алгоритмы и согласованность под нагрузкой. DevOps — доставка,
масштабирование, наблюдаемость, отказы, DR, безопасность и стоимость. В хорошем ответе
есть оба взгляда, меняется только время.

</details>

**2.** Как вы выкатываете новую версию без простоя, если меняется схема БД?

<details><summary>Ответ</summary>

Rolling update или canary с readiness и graceful shutdown; схема — expand/contract:
сначала совместимое расширение, потом переключение кода, потом удаление старого.
Миграции — отдельной джобой до выкатки.

</details>

**3.** По какой метрике вы бы масштабировали воркеры, обрабатывающие очередь?

<details><summary>Ответ</summary>

По длине очереди или лагу потребителей (KEDA), с минимумом и максимумом реплик.
Потолок — партиции (для Kafka) и лимиты внешних зависимостей.

</details>

**4.** Какой SLO вы поставите для асинхронной обработки?

<details><summary>Ответ</summary>

Доля задач, выполненных за целевое время от постановки, например 99% за 30 с.
Алерт — по burn rate и по возрасту старейшей задачи.

</details>

**5.** Что вы бэкапите в системе с БД, кешем, файлами и поисковым индексом?

<details><summary>Ответ</summary>

Источник правды: БД (PITR, реплика вне площадки), файлы (версионирование, репликация).
Кеш и индекс — производные, пересоздаются; оцениваю время пересоздания.

</details>

**6.** Где главная статья расходов в сервисе хранения фото и как её сократить?

<details><summary>Ответ</summary>

Обычно исходящий трафик: CDN с высоким hit ratio, современные форматы (WebP/AVIF),
правильные размеры под экран, долгий кеш с неизменяемыми ключами. Затем хранение —
lifecycle в холодный класс.

</details>

**7.** Что будет, если упадёт кеш перед базой?

<details><summary>Ответ</summary>

Весь поток чтения пойдёт в БД — риск каскадного отказа. Защита: лимит на запросы в БД,
request coalescing, реплика кеша с failover, прогрев, деградация (устаревшие данные).

</details>

**8.** Какой минимум про эксплуатацию должен знать бэкенд-разработчик?

<details><summary>Ответ</summary>

Stateless, пробы и graceful shutdown, expand/contract, лимит соединений к БД, таймауты
и ретраи с идемпотентностью, RED-метрики и SLO, реплика ≠ бэкап, что в его дизайне дорого.

</details>

**9.** Какой минимум про данные должен знать девопс?

<details><summary>Ответ</summary>

API и идемпотентность, согласованность при чтении с реплик, индексы и медленные
запросы, транзакции, кеш и инвалидация, семантики очередей, шардирование и горячие ключи,
выбор хранилища по запросам.

</details>

**10.** Как вы проверяете систему перед запуском в прод?

<details><summary>Ответ</summary>

Production readiness review по 7 вопросам: выкатка и откат, масштабирование и нагрузочный
тест, SLO и алерты, отказы и runbook, бэкапы и проверка восстановления, доступы и секреты,
оценка стоимости.

</details>
