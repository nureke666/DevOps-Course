## 1. Зачем ограничивать

| Цель | Пример | Что без лимита |
|------|--------|----------------|
| Защита от перегрузки | Скрипт клиента в цикле зовёт `POST /api/v1/links` | Один клиент съедает ёмкость, остальные получают 5xx |
| Справедливость (noisy neighbor) | Один tenant делает 90% запросов к общему сервису | Остальные платящие клиенты тормозят |
| Контроль стоимости | Эндпоинт ходит в платный внешний API, экспорт грузит БД | Счёт растёт; автоскейлинг раскручивает расходы — «denial of wallet» |
| Злоупотребления | Перебор паролей, скрейпинг, спам-ссылки, перебор кодов | Утечка аккаунтов, чёрные списки домена |

Рядом живут соседние механизмы — их путают:

| Механизм | Что ограничивает | Кто решает | Ответ |
|----------|-----------------|------------|-------|
| **Rate limit** | Скорость запросов от **одного ключа** | Политика по ключу | `429` + `Retry-After` |
| **Квота** | Объём за период (сутки, месяц) | Бизнес, тариф | `429`/`403` с причиной, сброс по расписанию |
| **Concurrency limit** | Число запросов **в обработке** | Ёмкость сервиса или зависимости | Быстрый `503`/`429` |
| **Load shedding** | Часть запросов при **общей** перегрузке, кто бы ни слал | Сервис по своему состоянию | `503` + `Retry-After` |

> ⭐ Лимит на ключ не защищает от суммы: 10 000 клиентов по 100 RPS — это миллион RPS. Поэтому лимитов по
> ключам недостаточно: нужен ещё сброс нагрузки по состоянию самого сервиса (раздел 5).

## 2. По какому ключу

| Ключ | Когда | Ловушки |
|------|-------|---------|
| **IP** | Нет аутентификации: логин, регистрация, публичные эндпоинты | NAT и CGNAT: тысячи людей за одним IPv4 (офис, мобильный оператор). IPv6: у клиента целая сеть `/64`, лимит по одному адресу бесполезен — считай по префиксу. За прокси `$remote_addr` — адрес балансировщика: реальный IP из `X-Forwarded-For` брать только от доверенных прокси ([Безопасность: 03](/security/03-web-edge-security)). Ботнеты и VPN меняют IP |
| **Пользователь** | После аутентификации | Не защищает до логина; тысяча новых аккаунтов обходит лимит |
| **API-ключ** | B2B-клиенты, программный доступ | Ключ утёк — лимит ограничивает ущерб; у клиента может быть много ключей |
| **Tenant / организация** | Справедливость между клиентами, тарифы | Много ключей и пользователей под одним лимитом |
| **Endpoint (маршрут + метод)** | Запросы разной цены | Нужен шаблон маршрута, а не фактический путь |

**Комбинации** — норма: `(tenant, endpoint)` плюс общий лимит на endpoint; IP-лимит **до**
аутентификации (защищает сам механизм входа) и лимит по ключу **после**. Проверки идут от дешёвых к дорогим:
лимитер не должен сам вызывать дорогую работу.

**Цена запроса.** Запросы неравноценны: поиск стоит в 5 раз дороже чтения, экспорт — в 50. Лимитер тратит
**«токены» по весу** запроса (`cost`), а не считает все запросы одинаково (раздел 3.4).

> ⚠️ В `nginx limit_req_zone` **пустой ключ не лимитируется**: запрос без заголовка с API-ключом пройдёт
> без счёта. Делай запасной ключ (IP) через `map` (практика C1).

## 3. Алгоритмы

Все примеры — в памяти одного процесса, чтобы увидеть логику; общий лимитер на Redis — в разделе 4.

### 3.1 Fixed window (счётчик на окно)

```text:no-line-numbers
 лимит 100 в минуту      окно 1 (0–59 с)      │      окно 2 (60–119 с)
 ────────────────────────────────────────────┼────────────────────────────────►  время
                              100 запросов   │   100 запросов
                              ◄─ 55…59 с ────┼──── 60…64 с ─►
              итого 200 запросов за 10 секунд при «лимите 100 в минуту»
```

Ключ окна = `(key, floor(now / window))`, счётчик растёт `INCR`, старые окна удаляются по TTL. Просто и дёшево
(один счётчик), но на стыке окон пропускает **до двух лимитов подряд**.

```python
class FixedWindow:
    def __init__(self, limit, window):
        self.limit, self.window = limit, window
        self.counters = defaultdict(int)                       # (key, номер окна) -> счётчик

    def allow(self, key, now):
        slot = (key, int(now // self.window))
        if self.counters[slot] >= self.limit:
            return False
        self.counters[slot] += 1
        return True                                            # старые слоты нужно чистить
```

### 3.2 Sliding window log (журнал запросов)

Храним **время каждого запроса** за последнее окно: перед проверкой выкидываем всё старше `now − window`, пропускаем,
если записей меньше лимита. Точно — окно скользит за каждым запросом. Но память — **O(limit) на ключ**: лимит
«1 000 000 в сутки» на ключ означает миллион меток. Разумно при малых лимитах (логин: 5 в минуту).

```python
class SlidingLog:
    def __init__(self, limit, window):
        self.limit, self.window, self.log = limit, window, defaultdict(deque)

    def allow(self, key, now):
        q = self.log[key]
        while q and q[0] <= now - self.window:                 # выкидываем протухшие
            q.popleft()
        if len(q) >= self.limit:
            return False
        q.append(now)
        return True
```

В Redis это sorted set: `ZREMRANGEBYSCORE` + `ZCARD` + `ZADD` (атомарно — только в Lua или `MULTI`).

### 3.3 Sliding window counter (взвешенная оценка)

Компромисс: два счётчика — **текущее** и **предыдущее** окно — и взвешенная сумма:

```text:no-line-numbers
 прошлое окно: 80 запросов    текущее: 30 запросов    прошло 25% текущего окна
 оценка за последнюю «минуту» = 80 × (1 − 0,25) + 30 = 90     лимит 100 → ещё можно ~10
```

```python
class SlidingCounter:
    def __init__(self, limit, window):
        self.limit, self.window, self.counters = limit, window, defaultdict(int)

    def allow(self, key, now):
        idx = int(now // self.window)
        elapsed = (now % self.window) / self.window            # какая часть текущего окна прошла
        prev, cur = self.counters[(key, idx - 1)], self.counters[(key, idx)]
        if prev * (1 - elapsed) + cur + 1 > self.limit:
            return False
        self.counters[(key, idx)] += 1
        return True
```

Память — два числа на ключ, всплеска на стыке нет. Цена — **приближение**: оценка предполагает, что запросы
прошлого окна были распределены равномерно. Для массовых лимитов API этого достаточно.

### 3.4 Token bucket (ведро токенов)

```text:no-line-numbers
   пополнение: r токенов в секунду ──►  ┌───────────┐  вместимость B
                                        │ ● ● ● ○ ○ │  запрос забирает cost токенов
                                        └───────────┘  пусто → 429, Retry-After = (нужно − есть) / r
```

Два параметра: **r** — устоявшаяся скорость, **B** (capacity) — допустимый всплеск. Лимит «100 в минуту, всплеск до 20»:
`r = 100/60 ≈ 1,67` токена в секунду, `B = 20`. Состояние — два числа (токены, время последнего пополнения);
токены **досчитываются лениво** при запросе, таймеров не нужно.

```python
class TokenBucket:
    def __init__(self, rate, capacity):
        self.rate, self.capacity, self.state = rate, capacity, {}   # key -> (токены, время)

    def allow(self, key, now, cost=1):
        tokens, ts = self.state.get(key, (self.capacity, now))
        tokens = min(self.capacity, tokens + (now - ts) * self.rate)   # пополнение
        ok = tokens >= cost
        if ok:
            tokens -= cost
        self.state[key] = (tokens, now)
        return ok
```

Разрешает короткий всплеск и держит средний темп — это то, что нужно клиентам API. Поэтому token bucket —
самый частый выбор (его описывают, например, в документации Stripe и AWS API Gateway). Бонус: `Retry-After`
считается точно — «через 0,6 с накопится токен».

### 3.5 Leaky bucket (дырявое ведро)

```text:no-line-numbers
 запросы ──► [ очередь размера Q ] ──► выход ровно r в секунду ──► сервис
                полна → отказ                 (запросы ждут своей очереди)
```

Вариант «как очередь» (shaper): запросы встают в FIFO и обрабатываются **с постоянной скоростью**; сверх `Q` — отказ.
Выход сглажен, всплесков нет — это годится для **хрупкой зависимости** (платный SMS-шлюз, старый API с лимитом 10 RPS).
Цена — добавленная задержка. Именно так работает `limit_req` в nginx без `nodelay` (параметр `burst` — размер очереди).

```python
class LeakyBucketQueue:
    def __init__(self, rate, queue_size):
        self.rate, self.queue_size, self.level, self.ts = rate, queue_size, 0.0, 0.0

    def offer(self, now):
        self.level = max(0.0, self.level - (now - self.ts) * self.rate)   # вытекло
        self.ts = now
        if self.level + 1 > self.queue_size:
            return None                                       # очередь полна — отказ
        self.level += 1
        return self.level / self.rate                         # через сколько секунд запрос «вытечет»
```

### Сравнение

| Алгоритм | Точность на границе окна | Память на ключ | Всплески | Когда брать |
|----------|--------------------------|----------------|----------|-------------|
| Fixed window | До 2 × лимит на стыке | 1 счётчик | Непредсказуемые | Грубые квоты, где важна простота |
| Sliding log | Точно | O(limit) меток | Нет сверх лимита | Малые лимиты: логин, OTP |
| Sliding counter | Приближённо | 2 счётчика | Почти нет | Массовые лимиты API |
| ⭐ Token bucket | Нет окон; всплеск ≤ B | 2 числа | Разрешён до B | Публичные и B2B API по умолчанию |
| Leaky bucket | Выход ровный | Уровень/очередь | Сглаживает, добавляет задержку | Защита хрупкой зависимости |

Эксперимент (практика C2): 10 запросов за 0,1 с до границы окна и 10 сразу после при лимите 10 в секунду →
fixed window пропускает **20**, sliding log и sliding counter — **10**, token bucket — **11** (10 из ведра + один
токен, накопившийся за 0,1 с).

## 4. Распределённый лимитер на Redis

Если у сервиса 30 подов и каждый считает **сам**, реальный лимит — `30 × limit`. Нужно общее состояние. Redis подходит:
быстрый, атомарные команды, ключи с TTL. Дьявол — в деталях.

### Атомарность

| Ловушка | Что происходит | Как правильно |
|---------|---------------|---------------|
| `GET` → проверка → `SET` | Check-then-act: между чтением и записью влезают другие. В эксперименте (практика C4) при лимите 100 прошло **~900** | Одна атомарная команда (`INCR`) или Lua-скрипт |
| `INCR`, затем отдельный `EXPIRE` | Процесс упал между ними — ключ **без TTL**, счётчик вечен, клиент заблокирован навсегда | `SET key 0 EX 60 NX` + `INCR`; или `MULTI` с `INCR` и `EXPIRE key 60 NX` (Redis 7.0+); или Lua |
| `EXPIRE` на **каждый** запрос | Окно «ползёт» за активным клиентом и никогда не заканчивается | TTL ставится один раз — при создании ключа |

Универсальный ответ — **Lua-скрипт**: Redis выполняет его целиком, пока не пустит другие команды. Token bucket:

```lua
-- token_bucket.lua. KEYS[1] — ключ ведра; ARGV: rate (токенов/с), capacity, cost
local rate, capacity, cost = tonumber(ARGV[1]), tonumber(ARGV[2]), tonumber(ARGV[3])

local t   = redis.call('TIME')
local now = t[1] * 1000 + math.floor(t[2] / 1000)             -- мс по часам Redis, не подов

local state  = redis.call('HMGET', KEYS[1], 'tokens', 'ts')
local tokens, ts = tonumber(state[1]), tonumber(state[2])
if tokens == nil then tokens, ts = capacity, now end          -- новый ключ: ведро полное

tokens = math.min(capacity, tokens + (now - ts) / 1000 * rate)  -- пополнение

local allowed, retry_ms = 0, 0
if tokens >= cost then
  tokens, allowed = tokens - cost, 1
else
  retry_ms = math.ceil((cost - tokens) / rate * 1000)         -- когда накопится нужное
end

redis.call('HSET', KEYS[1], 'tokens', tokens, 'ts', now)
redis.call('PEXPIRE', KEYS[1], math.ceil(capacity / rate * 1000) * 2)   -- пустое ведро забываем
return { allowed, math.floor(tokens), retry_ms }
```

```python
import redis

r  = redis.Redis(host="ratelimit-redis", socket_timeout=0.01)   # 10 мс на вызов
tb = r.register_script(open("token_bucket.lua").read())         # EVALSHA; при NOSCRIPT библиотека загрузит скрипт

def allow(api_key, rate_per_s, burst, cost=1):
    try:
        allowed, remaining, retry_ms = tb(keys=[f"rl:tb:{api_key}"], args=[rate_per_s, burst, cost])
    except redis.RedisError:
        return True, None, 0.0                  # fail-open: решение принимается по маршрутам (раздел 9.4)
    return bool(allowed), remaining, retry_ms / 1000
```

Время берём у Redis (`TIME`): часы подов расходятся, а окно должно считаться по одним часам. Для sliding counter
Lua-скрипт принимает два ключа — текущее и прошлое окно.

### Один Redis или кластер

- **Redis Cluster** делит ключи по хешу. Скрипт может трогать только ключи, переданные в `KEYS`, и все они должны быть
  в **одном слоте**: ключи одного клиента помечают общим **hash tag** — `rl:{apikey:42}:170000` и `rl:{apikey:42}:169999`.
- Объём для лимитера обычно мал: у linkd создание — ~200 RPS в пике, это ~200 вызовов скрипта в секунду. Хватит одного
  основного Redis с репликой; кластер нужен, когда не хватает операций или памяти. **Горячий ключ** (один гигантский
  клиент) живёт на одном шарде.
- **Лимитер — не кеш.** Не клади его в Redis с `allkeys-lru`: вытеснение стирает счётчики. Отдельный инстанс с
  `noeviction` или `volatile-ttl` и своей зоной отказа ([03. Кеширование](/system-design/building-blocks/03-caching)).
- Репликация асинхронна: при failover счётчики могут слегка откатиться — для лимитера это допустимо.

### Бюджет задержки

Лимитер на горячем пути — это **ещё один сетевой поход на каждый запрос**: в пределах зоны доступности порядка долей
миллисекунды, но с хвостом, и ещё одна зависимость. Правила: таймаут на вызов — единицы миллисекунд (меньше бюджета
запроса); вокруг вызова — circuit breaker; решение «что делать при ошибке» — заранее (fail-open или fail-closed,
раздел 9.4). У редиректа linkd по задержке такой поход вписывается, но это +20 000 вызовов в секунду в пике и ещё
одна зависимость на горячем пути, а лимит по IP ломает пользователей за NAT и CGNAT — поэтому глобального
лимитера на редиректе нет (раздел 8).

### Локальный pre-limit и синхронизация

Чтобы не ходить в Redis на каждый запрос, лимит **приближают**:

| Подход | Как | Погрешность |
|--------|-----|-------------|
| Лимит на под = глобальный / N | Каждый под считает локально | Верно, только если балансировщик раздаёт запросы поровну; число подов меняется |
| **Аренда токенов** | Под берёт у Redis пачку из K токенов и тратит локально | Лишнее до `N × K`; K подбирают по лимиту |
| Периодическая синхронизация | Локальные счётчики раз в 100 мс–1 с сливаются в Redis | Всплеск за интервал синхронизации |

Локальный лимит также спасает, когда Redis недоступен (раздел 9.4).

## 5. Слои лимитов

```text:no-line-numbers
 клиент
   ▼ CDN / WAF            грубо: IP, ASN, страна, bot-score; L7-атаки; правила на 404 и на пути логина
   ▼ gateway / ingress    по ключу и маршруту: nginx limit_req, Envoy; не знает тарифов
   ▼ приложение           бизнес-лимиты: tenant, тариф, цена запроса, квоты; знает пользователя
   ▼ зависимости          concurrency limit, load shedding, adaptive: защита БД и внешних API
```

| Слой | Ключ | Что хорошо | Чего не умеет |
|------|------|-----------|---------------|
| CDN / WAF | IP, отпечаток клиента | Режет мусор до вашей сети, рассчитан на большие объёмы | Не знает tenant и тариф |
| Gateway / ingress | API-ключ, IP, маршрут | Один набор политик на все сервисы | Сложные бизнес-правила; `local` лимит Envoy считается **на под** ([Platform: 05](/platform/05-gateway-mesh)) |
| Приложение | tenant, пользователь, цена | Знает тариф, считает квоты | Каждая лишняя проверка — после того, как запрос уже принят |
| Зависимости | — (по ресурсу) | Защищает от **медленной** зависимости, а не от «слишком частых» клиентов | — |

Лимит на gateway по API-ключу в nginx (практика C1) — ключ с запасным IP, ответ `429`, `Retry-After` в отдельном
`location`:

```nginx
map $http_x_api_key $limit_key { "" $binary_remote_addr; default $http_x_api_key; }
limit_req_zone $limit_key zone=create:10m rate=100r/m;          # 100 в минуту на ключ
limit_req_zone $binary_remote_addr zone=create_ip:10m rate=300r/m;   # и на IP: ключ можно подделать
limit_req_status 429;

location = /api/v1/links {
    limit_req zone=create burst=20 nodelay;                      # всплеск до 20; без nodelay лишние ждали бы
    limit_req zone=create_ip burst=50 nodelay;                   # несколько limit_req работают вместе
    error_page 429 = @rate_limited;
    proxy_pass http://linkd_api;
}
location @rate_limited {
    default_type application/json;
    add_header Retry-After 1 always;
    return 429 '{"error":"rate_limited"}\n';
}
```

> ⚠️ Ключ из заголовка клиент может подставить любой: каждый новый `X-Api-Key` получает свежее ведро,
> и лимит обходится, а зона забивается мусором. Поэтому рядом всегда лимит по IP, а лучше сначала
> проверить ключ (`auth_request` или gateway) и только потом лимитировать по нему.

⚠️ `limit_req` в nginx не работает в одном `location` с `return`: `return` срабатывает раньше. А `limit_req_dry_run on` позволяет
сначала только считать и писать в лог, не отвечая `429`.

### Защита зависимостей: concurrency limit

**Лимит по RPS не защищает от медленной зависимости.** Если запрос к БД из-за деградации стал в 20 раз дольше, те же
1 000 RPS создают в 20 раз больше одновременных запросов (закон Литтла: параллельность = RPS × задержка).
**Лимит параллельности** самонастраивается: при росте задержки он автоматически уменьшает пропускную способность.

```python
import threading

db_slots = threading.BoundedSemaphore(5)                  # ≤ 5 одновременных походов в БД на под

def get_from_db(code):
    if not db_slots.acquire(blocking=False):
        raise Overloaded()                                # быстрый 503 + Retry-After, не очередь
    try:
        return query_db(code)
    finally:
        db_slots.release()
```

Для linkd (допущения): 30 подов × 5 = **150 одновременных** запросов к БД на всю систему. При p99 запроса 5 мс это до
~30 000 запросов в секунду — больше пика, лимит не мешает. Если БД деградировала до 100 мс, пропускная способность
падает до ~1 500 в секунду, а остальное быстро получает `503` — база жива, поды не копят очереди. Если
перед базой PgBouncer (~60 серверных соединений, [тема 05](/system-design/building-blocks/05-db-scaling)),
потолок задаёт он: 60 / 0,1 с ≈ 600 запросов в секунду при деградации.

- **Load shedding:** при общей перегрузке сервис сам отбрасывает часть запросов — сначала менее важные (фоновые,
  пакетные), потом интерактивные; health-чеки и критичные вызовы — последними. Очередь — это задержка: лучше
  отказать быстро, чем ответить через 30 секунд ([SRE: 06](/sre/06-reliability-patterns)).
- **Adaptive limits:** лимит параллельности сам подстраивается — растёт, пока задержка в норме, и резко падает при
  росте задержки или таймаутах (принцип AIMD, как в TCP). Библиотеки и фильтры есть (например, adaptive concurrency у
  Envoy, concurrency-limits у Netflix) — подробности смотри в их документации.

## 6. Ответ клиенту и поведение клиента

**`429 Too Many Requests`** (RFC 6585) — «ты превысил **свой** лимит». `503` — «сервис перегружен вообще». Не
`403` (клиент решит, что прав нет) и не `500` (SLO-метрики посчитают ошибкой сервера; по умолчанию nginx отвечает `503`,
поэтому нужен `limit_req_status 429`).

```http
HTTP/1.1 429 Too Many Requests
Retry-After: 12
RateLimit-Limit: 100
RateLimit-Remaining: 0
RateLimit-Reset: 12
Content-Type: application/problem+json

{"type": "https://lnk.example/problems/rate-limited", "title": "Too many requests",
 "status": 429, "detail": "Limit 100 per minute per API key", "retry_after": 12}
```

- **`Retry-After`** — число секунд или HTTP-дата (RFC 9110). Это самый переносимый сигнал.
- **Заголовки лимита.** Исторически — `X-RateLimit-Limit/Remaining/Reset` (смысл `Reset` у разных API разный: секунды
  или момент времени — читай документацию). Единый формат описывает черновик IETF (`draft-ietf-httpapi-ratelimit-headers`):
  в ранних ревизиях `RateLimit-Limit/Remaining/Reset`, в поздних — поля `RateLimit` и `RateLimit-Policy`. Это
  **черновик, не RFC**, формат менялся между ревизиями — сверяйся с актуальной. Отдавай заголовки **и в успешных
  ответах**: клиент сам притормозит, не дожидаясь `429`.

**Клиент.** Правильное поведение:

1. Увидел `429` — **ждать не меньше `Retry-After`**, а при его отсутствии — экспоненциальный backoff.
2. **Jitter:** случайная задержка, иначе все клиенты вернутся в одну секунду (thundering herd) — особенно после сброса
   окна «в :00».
3. Ограничить число попыток, держать **retry budget**; повторять `POST` без побочных эффектов можно (`429` значит «не
   обработано»), но для `503` и таймаутов — только с `Idempotency-Key`
   ([SRE: 06](/sre/06-reliability-patterns), [02. Проектирование API](/system-design/building-blocks/02-api-design)).

```python
def post_with_backoff(url, headers, max_attempts=6, base=0.5, cap=30.0):
    for attempt in range(max_attempts):
        resp = requests.post(url, headers=headers, timeout=5)
        if resp.status_code not in (429, 503):
            return resp
        hint = retry_after_seconds(resp)                              # число секунд или HTTP-дата
        backoff = random.uniform(0, min(cap, base * 2 ** attempt))    # full jitter
        time.sleep(max(hint or 0.0, backoff))                         # не раньше, чем просит сервер
    return resp
```

Со стороны сервера точный `Retry-After` отдаёт token bucket («через 0,6 с накопится токен»); fixed window с «подожди
до конца минуты» создаёт стадо клиентов, возвращающихся одновременно.

## 7. Квоты и rate limit — разные вещи

| | Rate limit | Квота |
|---|-----------|-------|
| Зачем | Защита сервиса от перегрузки и злоупотреблений | Тариф, биллинг, договор |
| Окно | Секунды, минуты | Сутки, месяц (календарные или скользящие) |
| Точность | Приблизительно — приемлемо | Точно, с аудитом: это деньги |
| Хранение | Redis, эфемерно | БД (персистентно); счётчик в Redis с периодическим сбросом в БД |
| Ответ | `429` + `Retry-After` в секундах | `429` или `403` с причиной `quota_exceeded`, датой сброса; предупреждение на 80% |
| При потере счётчика | Короткий пропуск лишнего — нормально | Сверка по логам/БД; мягкий перерасход с последующим учётом |

Это **два слоя**: квота «10 000 ссылок в сутки» говорит, *сколько*, а лимит «100 в минуту» — *как быстро*. Клиент может
не исчерпать квоту, но уложить сервис всплеском; и наоборот.

## 8. Пример linkd: где лимиты, а где их нет

linkd ×1000: ~200 RPS записи и ~20 000 RPS чтения в пике, SLO редиректа 99,95% и p99 ≤ 50 мс, создания — 99,9%.

| Что | Ключ | Лимит | Где | Если лимитер недоступен |
|-----|------|-------|-----|--------------------------|
| `POST /api/v1/links` | API-ключ | Token bucket: 100 в минуту, всплеск 20 (значение — допущение из задачи 01) | Gateway + приложение | Fail-open + локальный лимит |
| Создание за сутки | `owner_id` | Квота, например 10 000/сутки; новые аккаунты — в 10 раз меньше первые сутки | Приложение, БД | Читаем квоту из БД |
| `GET /api/v1/links?q=…` (поиск) | API-ключ | Token bucket, `cost = 5` (в 5 раз дороже чтения) | Приложение | Fail-open |
| Ответы `404` на редиректах | IP (IPv6 — по `/64`) | Например 20 404 в минуту, блок на 10 минут | WAF/CDN-правило и локальный счётчик в поде | Fail-open |
| Успешные редиректы | — | **Нет лимита по IP** | — | — |
| Вход в веб-панель (если есть) | IP + имя пользователя | Sliding log: 5 в минуту | Приложение | Строгий локальный лимит |

**Почему нет лимита по IP на редиректах.** Ссылка в рассылке или у блогера (в задаче 01 — 50 000 RPS на один код) открывается
миллионами людей: часть сидит за корпоративным NAT и CGNAT оператора, часть — боты превью (Telegram, Slack, почтовые сканеры),
которые приходят с нескольких IP. Лимит по IP отрежет легитимных пользователей, а ссылка в чужой рассылке «сломается» — это
минус SLO. Цель защиты другая — **не уронить БД** — и достигается иначе: кеш (CDN, L1, Redis), **concurrency limit на
походах в БД** (раздел 5) и быстрый `503` при перегрузке. Лимит на **404** отдельно: он бьёт именно по перебору кодов и не
трогает нормальный трафик ([03. Кеширование](/system-design/building-blocks/03-caching)).

## 9. ⚙️ Эксплуатация

Семь стандартных вопросов из [Основ, тема 04](/system-design/basics/04-backend-vs-devops) — для лимитера.

### 9.1 Развёртывание

- **Где живёт лимитер:** правила CDN/WAF; политики gateway (nginx, Envoy Gateway `BackendTrafficPolicy` — `local` или `global`
  с rate-limit-сервисом на Redis, [Platform: 05](/platform/05-gateway-mesh)); middleware в приложении с Redis;
  отдельный сервис. Чем ниже слой — тем больше он знает о бизнесе и тем дороже его запросы.
- ⭐ **Лимиты — данные, а не код.** Политики по tenant, маршруту и плану лежат в конфиге/таблице с версионированием и
  горячей перезагрузкой; крупному клиенту поднимают лимит правкой данных, а не релизом:

  ```yaml
  # limits.yaml — ConfigMap или таблица в БД; в git, с ревью
  policies:
    - route: "POST /api/v1/links"
      key: api_key
      algorithm: token_bucket
      rate: 100/min
      burst: 20
      overrides:
        - { tenant: bigcorp, rate: 1000/min, burst: 100 }
    - route: "GET /api/v1/links"
      key: api_key
      cost: { with_query: 5, default: 1 }
  ```
- **Выкатка нового лимита:** режим наблюдения (dry run: считаем и логируем «был бы 429») → применение к доле ключей
  (canary по хешу ключа) → полное включение. Рядом — **kill switch** (флаг «лимитер выключен»).
- **Redis лимитера** — отдельный инстанс (не кеш), `noeviction`, реплика и автоматический failover. После рестарта
  скрипты забываются (`NOSCRIPT`): клиент должен перезагружать их сам (`register_script` в redis-py так и делает).

### 9.2 Масштабирование

- **Нагрузка на лимитер** = RPS защищаемых маршрутов × один вызов. У linkd — создание, ~200 вызовов/с в пике: ничего.
  На редиректах (20 000 RPS) это были бы +20 000 вызовов/с и новая зависимость на горячем пути — поэтому там лимитера нет.
- **Потолки:** операции и CPU одного шарда Redis (порядок десятков–сотни тысяч в секунду — измерь на своём), горячий ключ,
  память: ключей × ~100–200 байт (token bucket) — для миллиона активных ключей это сотни мегабайт; sliding log растёт с
  лимитом.
- **Рычаги:** шардирование по хешу ключа, аренда токенов и локальный pre-limit (меньше походов в Redis). Лимит `local` на
  gateway умножается на число реплик gateway — учитывай при расчёте ([Platform: 05](/platform/05-gateway-mesh)).
- Лимитеры и автоскейлинг должны быть согласованы: без лимитов атака раскручивает HPA до `maxReplicas` и счёт; с лимитами —
  упирается в `429`.

### 9.3 Наблюдаемость

- **Метрики по маршрутам и тарифам, но не по ключам:** `ratelimit_decisions_total{route, tier, decision="allowed|limited"}`.
  ⚠️ API-ключ или IP в лейбле — это взрыв кардинальности (как короткий код в
  [задаче 01](/system-design/backend-cases/01-url-shortener)). «Кто больше всех упирается в лимит» — из логов или
  аналитического хранилища, с хешем ключа.
- ⭐ **Алерт на массовые `429`:** доля `429` по маршруту выросла в разы за 5–10 минут — атака, баг клиента (retry storm) или
  **наша ошибка** (лимит по IP за балансировщиком, лимит 0 после релиза). Отдельно — `429` для платящих tier'ов.
- **Здоровье самого лимитера:** задержка и ошибки вызова Redis, счётчик **fail-open-срабатываний**
  (`ratelimit_errors_total{mode}`), `NOSCRIPT`, память и evictions Redis (должны быть 0).
- **SLO.** `429`, выданные по лимиту клиента, — не ошибка доступности; но `429` легитимному трафику из-за неверной
  конфигурации — ошибка, поэтому считай по tier'ам. Следи и за **соблюдением `Retry-After`**: доля клиентов, пришедших
  раньше срока, — признак неправильных клиентов.

### 9.4 Отказы

| Что сломалось | Что видно | Что делаем |
|---------------|-----------|------------|
| Redis лимитера недоступен или медленный | Растёт задержка запросов или ошибки | Короткий таймаут, circuit breaker, **политика по маршрутам** (ниже); запасной локальный лимит |
| Failover Redis | Счётчики откатились — кратковременный пропуск лишнего | Допустимо; следить, чтобы не было шторма |
| Рестарт Redis | Все счётчики обнулены, скрипты забыты | Клиент перезагружает скрипт; локальный лимит — страховка |
| Кривая конфигурация (лимит 0, слишком строгий) | Массовые `429` у легитимных клиентов | Валидация конфига в CI, canary, kill switch, откат |
| Retry storm после массовых `429` | Нагрузка выше исходной | Jitter, `Retry-After`, retry budget в своих клиентах |
| Дрейф часов подов | Разные окна у разных подов | Время брать у Redis; NTP |

⭐ **Fail-open или fail-closed — решение по маршруту, по цене ошибки:**

| Маршрут | При отказе лимитера | Почему |
|---------|---------------------|--------|
| Редиректы (лимит на 404) | **Fail-open** | Лимитер не должен ронять SLO 99,95%; цена пропуска — перебор кодов чуть быстрее, его гасят кеш и CDN |
| Создание ссылки | **Fail-open + локальный лимит** на под | Полная блокировка создания — авария для SLO 99,9%; злоупотребление ограничит локальный лимит |
| Логин, сброс пароля, OTP | **Fail-closed или строгий локальный лимит** | Весь смысл лимита — защита от подбора; но «никто не может войти» тоже авария — поэтому не полное закрытие, а жёсткий лимит на под |
| Платные операции (SMS, внешние API) | **Fail-closed** | Цена пропуска — прямые деньги |

Ответ для редиректов и для логина отличается, потому что отличается **цена ложного пропуска** и **цена ложного отказа**.
Решение записывается в ADR и проверяется на учениях (выключи Redis лимитера и посмотри метрики).

### 9.5 Данные и DR

- **Состояние лимитера эфемерно**: бэкапов нет. Потеря Redis — обнулённые счётчики на минуту, не катастрофа; планируем
  страховку (локальный лимит) и быстрый возврат.
- **Что нужно беречь:** политики (git/БД — вместе с остальным), **квоты** (платёжные: БД, бэкап, аудит), списки блокировок
  (баны живут в БД и кеше, а не только в Redis лимитера).
- **Регионы.** Глобальный лимит между регионами требует синхронизации с задержкой; обычно лимит делят на регионы
  (глобальный / число регионов) и принимают, что распределённый злоумышленник получит «N лимитов».
- RTO лимитера — минуты, и всё это время работает fail-open/локальный лимит; план проверяется на учениях.

### 9.6 Безопасность

- **Доверие к ключу.** `X-Forwarded-For` от недоверенных — подделка и обход лимита: реальный IP брать только от своих прокси
  ([Безопасность: 03](/security/03-web-edge-security)). IPv6 — по префиксу.
- **Блокировка аккаунта — оружие против жертвы:** «5 ошибок — аккаунт заблокирован» позволяет злоумышленнику заблокировать
  любого. Лимит по паре (IP, имя) + прогрессивные задержки и CAPTCHA вместо жёсткого бана.
- **Распределённый подбор** (credential stuffing с десятков тысяч IP) per-IP лимитом не остановить: нужны счётчик неудач
  **по аккаунту**, bot-защита на WAF, проверка утёкших паролей.
- **Rate limit ≠ защита от DDoS.** Объёмные атаки гасит сеть и CDN, распределённые L7 — WAF и bot management; лимитер
  приложения — только последняя линия, и он сам должен быть дёшевым и стоять **до** дорогой работы.
- Лимитер не должен раскрывать лишнего: одинаковый ответ для существующего и несуществующего аккаунта; доступ к Redis
  лимитера — по сети и паролю.
- Ограничивай **неаутентифицированное** отдельно и строже; админские эндпоинты — отдельный лимит.

### 9.7 Стоимость

- **Цена самого лимитера:** Redis (мало), дополнительный сетевой поход на каждый защищаемый запрос — расход бюджета задержки,
  и работа людей на поддержку политик. Поэтому его ставят там, где он окупается, а не на каждый маршрут.
- **Что он экономит:** предел для автоскейлинга («denial of wallet»), платные вызовы внешних API (SMS, e-mail, LLM) — лимит по
  стоимости запроса, нагрузка на БД (не покупаем БД размером под злоупотребления), egress.
- Managed WAF/CDN-правила тарифицируются по числу правил и проверенных запросов — уточни тариф.
- **Цена ложных `429`:** потерянные клиенты и обращения в поддержку — настраивай через dry run и метрики, а не «на глаз».

## Грабли

| Грабля | Что не так | Правильно |
|--------|-----------|-----------|
| `limit_req_zone $binary_remote_addr` за балансировщиком | Все клиенты — один IP балансировщика, общий лимит | `real_ip` только от доверенных прокси |
| `INCR` и отдельный `EXPIRE` | Сбой между ними — ключ без TTL, клиент блокирован навсегда | Lua, `SET … NX EX` или `EXPIRE … NX` в транзакции |
| `GET` → `SET` для счётчика | Гонка: пропускает кратно больше лимита | Атомарная операция, Lua |
| Лимит по IP на редиректах | NAT, CGNAT, боты превью: ломает вирусные ссылки | Кеш, concurrency limit, лимит на 404 |
| Fixed window и всплеск на стыке | До 2 × лимит за короткое время | Token bucket или sliding counter |
| Лимит по RPS вместо параллельности для БД | Медленная БД копит запросы, лимит молчит | Concurrency limit + быстрый `503` |
| Лимитер на горячем пути без таймаута | Тормозит Redis — тормозят все запросы | Таймаут единиц мс, circuit breaker, fail-open |
| Лимитер в одном Redis с кешем `allkeys-lru` | Вытеснение стирает счётчики | Отдельный инстанс, `noeviction` |
| `Retry-After` одинаковый для всех | Стадо клиентов возвращается в одну секунду | Точный `Retry-After` + jitter на клиенте |
| `503` вместо `429` по умолчанию | SLO и дежурные считают это падением | `limit_req_status 429` |
| Лимиты захардкожены в коде | Любое изменение — релиз | Конфиг/данные с горячей перезагрузкой |
| API-ключ или IP в лейбле метрики | Взрыв кардинальности | Метрики по маршруту и tier'у, «топ» — из логов |
| Fail-closed для логина без запасного плана | Падение Redis = никто не входит | Строгий локальный лимит на под |

## 💼 Как это на работе

- **Бэкенд-сторона.** Тебя будут просить «защитить эндпоинт от спама»: выбрать ключ, алгоритм, ответ и поведение клиентов.
  Хороший ответ звучит как «token bucket по API-ключу, 429 с `Retry-After`, `Idempotency-Key` на создание, а на редиректах
  защищаем базу параллельностью, а не по IP».
- **DevOps-сторона.** Лимиты — часть политик gateway и WAF: версионируются в git, включаются через dry run, имеют метрики и
  kill switch. Главные риски — ошибочный лимит у легитимных клиентов и лимитер, который сам становится единой точкой отказа.
- **linkd — твой полигон.** Поставь перед linkd nginx с `limit_req` по `X-Api-Key` (C1), потом Lua token bucket в Redis (C3)
  и проверь, что происходит, когда Redis недоступен. История «выбрал fail-open для создания и объяснил почему» — сильная
  строка в рассказе.
- **Решения записывай:** «почему нет лимита по IP на редиректах», «fail-open для создания» — готовые ADR
  ([Основы: 05](/system-design/basics/05-design-doc-adr)).

## 📌 Шпаргалка

| Хочу | Как |
|------|-----|
| Защитить от перегрузки и злоупотреблений | Rate limit по ключу + concurrency limit и load shedding для зависимостей |
| Выбрать ключ | Нет аутентификации — IP (IPv6 по `/64`); потом пользователь, API-ключ, tenant, маршрут; запасной ключ |
| Алгоритм по умолчанию | Token bucket: `rate` — устоявшийся темп, `capacity` — всплеск |
| Точный лимит при малом числе | Sliding log (логин: 5 в минуту) |
| Дёшево и без стыка окон | Sliding window counter: `prev × (1 − t) + cur` |
| Ровный поток к хрупкой зависимости | Leaky bucket как очередь (`limit_req` без `nodelay`) |
| Атомарность в Redis | Lua; не `GET`→`SET`, не `INCR` + отдельный `EXPIRE` |
| Redis Cluster | Hash tag `{key}` в ключах одного клиента |
| Меньше ходов в Redis | Локальный pre-limit, аренда токенов |
| Ответ при превышении | `429`, `Retry-After`, `RateLimit-*` (черновик IETF), `problem+json` |
| Клиент | Backoff + full jitter, не раньше `Retry-After`, retry budget |
| Квота vs лимит | Квота — «сколько» (БД, деньги), лимит — «как быстро» (Redis) |
| Лимитер недоступен | Редиректы и создание — fail-open, логин — строгий локальный лимит, платное — fail-closed |
| Эксплуатация | Лимиты как данные, dry run, метрики без ключей в лейблах, алерт на массовые `429` |

## 🧠 Что запомнить

1. ⭐ Rate limit защищает от **одного** клиента, load shedding — от **суммы**; нужны оба, плюс квоты для денег.
2. Ключ выбирают по цели: IP — до аутентификации (NAT и IPv6 `/64`), API-ключ и tenant — для справедливости, маршрут и цена запроса — для разного веса.
3. ⭐ Fixed window пропускает до 2 × лимита на стыке окон; sliding log точен, но O(limit) по памяти; sliding counter — дешёвое приближение.
4. ⭐ Token bucket — выбор по умолчанию: `rate` задаёт средний темп, `capacity` — допустимый всплеск, `Retry-After` считается точно.
5. Leaky bucket как очередь сглаживает поток для хрупкой зависимости, ценой задержки.
6. ⭐ В Redis лимитер — это Lua: `GET`→`SET` даёт гонку, `INCR` с отдельным `EXPIRE` — ключи без TTL.
7. Лимитер на горячем пути — зависимость и бюджет задержки: таймаут, circuit breaker, решение fail-open/fail-closed заранее.
8. ⭐ Лимит по параллельности защищает от медленной зависимости (закон Литтла), лимит по RPS — нет.
9. Ответ: `429` + `Retry-After` (+ `RateLimit-*`, черновик IETF); клиент — backoff с jitter, не раньше `Retry-After`.
10. ⭐ У linkd нет лимита по IP на редиректах: вирусные ссылки и NAT; базу защищают кеш, concurrency limit и `503`, а перебор кодов — лимит на 404.

### Блок A. Теория

**A1.** ⭐ Зачем ограничивать запросы и чем rate limit отличается от квоты и load shedding?

<details><summary>Ответ</summary>

Цели: защита от перегрузки, справедливость между клиентами, контроль стоимости, защита от злоупотреблений. Rate limit
ограничивает скорость одного ключа и отвечает `429`; квота — объём за период (деньги, тариф); load shedding отбрасывает часть
запросов при общей перегрузке, независимо от того, кто их шлёт.

</details>

**A2.** ⭐ Какой ключ выбрать для логина, для публичного API с ключами и для B2B с тарифами? Какие у IP ловушки?

<details><summary>Ответ</summary>

Логин — IP и имя пользователя (до аутентификации ключа нет); API с ключами — API-ключ; B2B — tenant (плюс endpoint). Ловушки IP:
NAT и CGNAT (много людей — один адрес), IPv6 (клиенту принадлежит `/64`, считай по префиксу), за прокси нужен реальный
IP только от доверенных прокси, ботнеты меняют адреса.

</details>

**A3.** ⭐ В чём проблема fixed window и как её лечит sliding window counter?

<details><summary>Ответ</summary>

На стыке окон клиент может отправить лимит в конце одного окна и лимит в начале следующего — до 2 × лимит за короткое время.
Sliding counter хранит счётчики текущего и прошлого окна и считает `prev × (1 − elapsed) + cur`: стык сглаживается, память —
два числа на ключ, цена — приближение (запросы прошлого окна считаются распределёнными равномерно).

</details>

**A4.** ⭐ Что означают параметры token bucket? Лимит 100 в минуту с всплеском 20 — каковы `rate` и `capacity` и сколько запросов
пройдёт в первую секунду?

<details><summary>Ответ</summary>

`rate` — устоявшаяся скорость (100/60 ≈ 1,67 токена/с), `capacity` — всплеск (20). Из полного ведра сразу проходят до 20
запросов (в первую секунду — 20 + ~1,7 за счёт пополнения), дальше — в среднем 1,67 в секунду; `Retry-After` — время до накопления
нужного числа токенов.

</details>

**A5.** Чем leaky bucket как очередь отличается от token bucket и где в nginx это видно?

<details><summary>Ответ</summary>

Token bucket допускает всплеск и пропускает его сразу; leaky bucket ставит запросы в очередь и выпускает их с постоянной
скоростью — выход ровный, но есть задержка. В nginx `limit_req` с `burst` без `nodelay` — очередь (leaky bucket), с `nodelay`
лишние запросы обслуживаются сразу, а слоты освобождаются с темпом `rate`.

</details>

**A6.** ⭐ Почему `INCR` + отдельный `EXPIRE` — ловушка, и что не так с `GET` → проверка → `SET`?

<details><summary>Ответ</summary>

Если процесс упал между `INCR` и `EXPIRE`, у ключа нет TTL: счётчик вечен и клиент заблокирован навсегда; `EXPIRE` на каждый запрос
продлевает окно бесконечно. `GET` → `SET` — check-then-act: параллельные запросы читают одно значение и все проходят. Лечение:
Lua-скрипт, `INCR` как атомарная команда, `SET key 0 EX 60 NX`, `EXPIRE … NX` (Redis 7.0+) в `MULTI`.

</details>

**A7.** Как лимитер на Redis работает в Redis Cluster и зачем нужен hash tag?

<details><summary>Ответ</summary>

Ключи делятся по слотам хеша. Скрипт имеет право трогать только ключи из `KEYS` и только из одного слота. Ключи одного клиента
(текущее и прошлое окно) помечают общим `{tag}` — они попадают в один слот. Горячий клиент живёт на одном шарде.

</details>

**A8.** ⭐ Зачем локальный pre-limit и какая у синхронизации с Redis погрешность?

<details><summary>Ответ</summary>

Чтобы не ходить в Redis на каждый запрос (задержка, нагрузка, зависимость) и пережить его отказ. Аренда токенов пачками
по K даёт перерасход до `N × K` (N — число подов); лимит «глобальный / N» неточен при неравномерной раздаче и меняющемся числе
подов; периодическая синхронизация допускает всплеск за интервал.

</details>

**A9.** ⭐ Где ставят лимиты по слоям и что на каждом?

<details><summary>Ответ</summary>

CDN/WAF — грубые лимиты по IP, bot-score, правила на пути логина и на 404; gateway/ingress — по API-ключу и маршруту; приложение —
бизнес-лимиты (tenant, тариф, цена запроса, квоты); зависимости — concurrency limit, bulkhead, load shedding, адаптивные
лимиты.

</details>

**A10.** ⭐ Почему лимит по параллельности защищает от медленной БД, а лимит по RPS — нет?

<details><summary>Ответ</summary>

По закону Литтла параллельность = RPS × задержка: при том же RPS и росте задержки в 20 раз одновременных запросов становится в 20
раз больше, а RPS-лимит этого не видит. Лимит параллельности (например, 5 на под) сам снижает пропускную способность при росте
задержки и быстро отдаёт `503` излишкам вместо очереди.

</details>

**A11.** ⭐ Что вернуть клиенту при превышении и как клиенту себя вести?

<details><summary>Ответ</summary>

`429` (не `403`, не `500`) с `Retry-After` в секундах и, по желанию, `RateLimit-*` (черновик IETF; формат менялся) и телом
`problem+json`. Клиент ждёт не меньше `Retry-After`, иначе экспоненциальный backoff с jitter, ограничивает число попыток и держит
retry budget; `POST` повторяет с `Idempotency-Key`.

</details>

**A12.** Чем квота отличается от rate limit и где хранится каждая?

<details><summary>Ответ</summary>

Rate limit — «как быстро» (секунды, минуты), точность приблизительная, состояние эфемерно в Redis. Квота — «сколько» за
период (сутки, месяц), точная, привязана к тарифу и деньгам, хранится персистентно в БД с аудитом, в Redis — рабочий счётчик.

</details>

### Блок B. «Что тут не так»

```
B1.  nginx за балансировщиком: limit_req_zone $binary_remote_addr zone=api:10m rate=10r/s; real_ip не настроен.

B2.  n = r.incr(key); r.expire(key, 60) — на каждый запрос.

B3.  Для linkd добавили лимит 10 RPS на IP на GET /r/<code>: «защита от скрейпинга».

B4.  В nginx лимит сработал, клиент получает 503; дежурный видит алерт «рост 5xx».

B5.  Retry-After: 60 для всех клиентов, окно сбрасывается ровно в :00.

B6.  Клиент: while resp.status == 429: sleep(0.1); повторить запрос.

B7.  Счётчики лимитера лежат в том же Redis, что и кеш ссылок (maxmemory-policy allkeys-lru).

B8.  Лимитер на Redis упал — библиотека по умолчанию отвечает 503 на все запросы, включая редиректы.

B9.  Sliding log с лимитом «1 000 000 запросов в сутки» на API-ключ.

B10. «После 5 неверных паролей аккаунт блокируется на час».
```

<details><summary>Ответы</summary>

**B1.** ⚠️ `$remote_addr` — адрес балансировщика, все клиенты делят один лимит. Настроить `set_real_ip_from` только для своих
прокси и `real_ip_header`.

**B2.** ⚠️ Сбой между командами оставляет ключ без TTL, а повторный `EXPIRE` продлевает окно вечно. TTL ставится один раз при
создании: Lua или `EXPIRE key 60 NX` в `MULTI`.

**B3.** ⚠️ NAT, CGNAT и боты превью: легитимные пользователи вирусной ссылки получат `429`. Защищать базу кешем и concurrency
limit, перебор кодов — лимитом на 404.

**B4.** ⚠️ `503` — статус по умолчанию. Нужен `limit_req_status 429`, иначе SLO-метрики и дежурный видят падение сервиса.

**B5.** ⚠️ Стадо клиентов вернётся одновременно. Точный `Retry-After` (token bucket) и jitter у клиентов.

**B6.** ⚠️ Игнорирует `Retry-After`, долбит сервер — усиливает проблему. Backoff с jitter, потолок задержки, лимит попыток.

**B7.** ⚠️ `allkeys-lru` вытесняет счётчики, лимиты «забываются». Отдельный инстанс с `noeviction`.

**B8.** ⚠️ Для редиректов лимитер не должен ронять SLO — fail-open. Для логина — строгий локальный лимит, а не полное закрытие.

**B9.** ⚠️ Миллион меток на ключ — память взрывается. Счётчик по окнам (квота в БД) или sliding counter.

**B10.** ⚠️ Злоумышленник блокирует любого пользователя. Лимит по паре (IP, имя), прогрессивные задержки, CAPTCHA.

</details>

### Блок C. Практика

#### C1. 🔑 `limit_req` по API-ключу в nginx

```nginx
# nginx.conf
events {}
http {
    # ⚠️ ключ из заголовка можно подделать — в проде рядом лимит по IP (раздел 5)
    map $http_x_api_key $limit_key { "" $binary_remote_addr; default $http_x_api_key; }
    limit_req_zone $limit_key zone=create:10m rate=2r/s;
    limit_req_status 429;
    limit_req_dry_run off;                      # поставь on — только лог, без 429

    server {
        listen 8080;
        location = /api/v1/links {
            limit_req zone=create burst=5 nodelay;
            error_page 429 = @rate_limited;
            proxy_pass http://127.0.0.1:9000;
        }
        location @rate_limited {
            default_type application/json;
            add_header Retry-After 1 always;
            return 429 '{"error":"rate_limited"}\n';
        }
    }
    server {                                    # «приложение» для лабы
        listen 127.0.0.1:9000;
        location / { return 201 '{"code":"aZ3x9Qk"}\n'; }
    }
}
```

```bash
docker run -d --name ngx -p 8080:8080 -v $PWD/nginx.conf:/etc/nginx/nginx.conf:ro nginx:1.30.5-alpine
for i in $(seq 1 10); do curl -s -o /dev/null -w "%{http_code} " -X POST -H 'X-Api-Key: free_1' localhost:8080/api/v1/links; done; echo
for i in $(seq 1 3);  do curl -s -o /dev/null -w "%{http_code} " -X POST -H 'X-Api-Key: free_2' localhost:8080/api/v1/links; done; echo
curl -si -X POST -H 'X-Api-Key: free_1' localhost:8080/api/v1/links | sed -n '1p;/Retry/p'
docker logs ngx 2>&1 | grep -i limiting | tail -2
```

Что ты увидишь? Почему для `free_2` всё проходит? Убери `nodelay` и сравни время ответа. Сделай `return` прямо в
`location` вместо `proxy_pass` — сработает ли лимит?

<details><summary>Ответ</summary>

Первые 6 запросов — `201` (1 + `burst=5`), остальные — `429`; у `free_2` свой счётчик, он не затронут. В ответе `429` есть
`Retry-After`, в логе — `limiting requests, excess: …`. Без `nodelay` лишние запросы встанут в очередь и будут обслужены с темпом
`rate` (задержка), а не отвергнуты. С `return` в том же `location` лимит **не сработает**: `return` выполняется на более ранней
фазе, чем `limit_req`.

</details>

#### C2. 🔑 Алгоритмы и граница окна

Собери `algos.py` из классов раздела 3 (`FixedWindow`, `SlidingLog`, `SlidingCounter`, `TokenBucket`, `LeakyBucketQueue`;
нужны `from collections import defaultdict, deque`) и добавь:

```python
def burst_at_edge(limiter, t0, n=10):
    ok = 0
    for i in range(n):
        ok += limiter.allow("k", t0 - 0.1 + i * 0.01)        # конец окна
    for i in range(n):
        ok += limiter.allow("k", t0 + 0.001 + i * 0.01)      # начало следующего
    return ok

for cls in (FixedWindow, SlidingLog, SlidingCounter):
    print(cls.__name__, burst_at_edge(cls(10, 1.0), 100.0))
print("TokenBucket", burst_at_edge(TokenBucket(rate=10, capacity=10), 100.0))
lb = LeakyBucketQueue(rate=10, queue_size=5)
print("Leaky delays", [lb.offer(100.0 + i * 0.001) for i in range(8)])
```

Какие числа получились и почему?

<details><summary>Ответ</summary>

`FixedWindow 20`, `SlidingLog 10`, `SlidingCounter 10`, `TokenBucket 11`; у очереди первые 5 запросов получают задержки
~0,1…0,5 с, остальные — `None`. Fixed window на стыке пропускает два лимита; token bucket — 10 из ведра плюс один токен,
накопившийся за 0,1 с; leaky bucket не отвергает всплеск сразу, а растягивает его по времени до размера очереди.

</details>

#### C3. 🔑 Token bucket на Lua в Redis

`rate = 1` токен в секунду, `capacity = 5`. Что вернул каждый вызов (`allowed remaining retry_ms`)? Что будет через 2 секунды?
Какой `PTTL` у ключа и почему? Затем вызови скрипт из Python (`register_script`) с `100/60` и `capacity = 20` 23 раза подряд;
сделай `r.script_flush()` и вызови снова.

<details><summary>Ответ</summary>

Первые 5 вызовов — `1 4 0`, `1 3 0` … `1 0 0` (токены тают), 6-й и 7-й — `0 0 ~700–800` (мс до накопления токена); через 2 секунды
накапливается 2 токена — следующий вызов проходит. `PTTL` ~10 000 мс: TTL ключа — `2 × capacity / rate`, пустое ведро
забывается само. Из 23 вызовов с `100/60` и `capacity 20` пройдут 20, `Retry-After` ≈ 0,6 с. После `script_flush` redis-py сам
перезагрузит скрипт при `NOSCRIPT`.

</details>

#### C4. Гонка и ловушка `EXPIRE`

```python
# race.py
import threading, redis
LIMIT, WORKERS, ATTEMPTS = 100, 20, 50
r = redis.Redis(decode_responses=True)

def naive_allow(key):
    count = int(r.get(key) or 0)
    if count >= LIMIT:
        return False
    r.set(key, count + 1)
    return True

def atomic_allow(key):
    return r.incr(key) <= LIMIT

def run(fn, key):
    r.delete(key); ok = []
    def worker():
        for _ in range(ATTEMPTS):
            if fn(key):
                ok.append(1)
    ts = [threading.Thread(target=worker) for _ in range(WORKERS)]
    [t.start() for t in ts]; [t.join() for t in ts]
    return len(ok)

print("naive :", run(naive_allow, "t:naive"), "при лимите", LIMIT)
print("atomic:", run(atomic_allow, "t:atomic"), "при лимите", LIMIT)
```

```bash
docker exec redis redis-cli INCR k && docker exec redis redis-cli TTL k       # TTL?
docker exec redis redis-cli SET kk 0 && docker exec redis redis-cli EXPIRE kk 60 NX && docker exec redis redis-cli TTL kk
```

Сколько запросов пропустил наивный вариант? Что вернул `TTL k` и чем это опасно? Как ставить TTL только при создании?

<details><summary>Ответ</summary>

Наивный вариант пропустил порядка 800–900 при лимите 100 (число плавает), атомарный — ровно 100. `TTL k` = `-1`: ключ без срока
жизни, при сбое между `INCR` и `EXPIRE` счётчик вечен, клиент заблокирован навсегда. Лечение: Lua, `SET key 0 EX 60 NX` перед `INCR`
или `EXPIRE key 60 NX` (Redis 7.0+; ставит TTL, только если его нет) в транзакции.

</details>

#### C5. Клиент с backoff и jitter

Подними nginx из C1 и запусти клиента:

```python
# client.py
import random, time
from datetime import datetime, timezone
from email.utils import parsedate_to_datetime
import requests

def retry_after_seconds(resp):
    value = resp.headers.get("Retry-After")
    if value is None:
        return None
    if value.isdigit():
        return float(value)
    try:
        return max(0.0, (parsedate_to_datetime(value) - datetime.now(timezone.utc)).total_seconds())
    except (TypeError, ValueError):
        return None

def post_with_backoff(url, headers, max_attempts=6, base=0.5, cap=30.0):
    for attempt in range(max_attempts):
        resp = requests.post(url, headers=headers, timeout=5)
        if resp.status_code not in (429, 503):
            return resp
        delay = max(retry_after_seconds(resp) or 0.0, random.uniform(0, min(cap, base * 2 ** attempt)))
        print(f"попытка {attempt + 1}: {resp.status_code}, ждём {delay:.2f} с")
        time.sleep(delay)
    return resp

if __name__ == "__main__":
    url, h = "http://localhost:8080/api/v1/links", {"X-Api-Key": "free_9"}
    for _ in range(8):
        requests.post(url, headers=h)                       # выбиваем burst
    print("итог:", post_with_backoff(url, h).status_code)
```

Что напечатает клиент? Как поведёт себя, если сервер вообще не шлёт `Retry-After`? Почему `max`, а не только `Retry-After`?

<details><summary>Ответ</summary>

Первая попытка — `429`, клиент ждёт ≥ 1 с (`Retry-After: 1`) и получает `201`. Без `Retry-After` работает только экспоненциальный
backoff с full jitter. `max` гарантирует «не раньше, чем просит сервер» и сохраняет jitter, чтобы клиенты не возвращались синхронно.

</details>

### Блок D. Инциденты

**D1.** После релиза ingress-слоя у всех клиентов `429`. Конфиг лимита не менялся, нагрузка обычная.

<details><summary>Ответ</summary>

Включили лимит по IP, а перед приложением появился балансировщик/CDN: `$remote_addr` стал адресом прокси, все клиенты делят один
лимит. Сейчас: откатить или включить dry run. Потом: `real_ip` только от доверенных прокси, тест лимита за прокси, canary и
метрика доли `429` с алертом на скачок.

</details>

**D2.** Redis лимитера перезапустился. Через минуту все `POST /api/v1/links` возвращают `500`, редиректы тоже тормозят.

<details><summary>Ответ</summary>

Библиотека лимитера по умолчанию fail-closed и без таймаута: ошибка Redis превращается в `500`, медленные вызовы тормозят запросы.
Сейчас: kill switch или fail-open. Потом: таймаут единиц мс, circuit breaker, политика по маршрутам (создание — fail-open +
локальный лимит, логин — строгий локальный), отказ Redis — в учения; скрипты перезагружаются сами (`NOSCRIPT`).

</details>

**D3.** Ссылку запостил популярный блогер. Часть пользователей из офисов получает `429`, SLO редиректа горит.

<details><summary>Ответ</summary>

После прошлого инцидента на редиректы добавили лимит по IP — он бьёт по NAT и CGNAT. Убрать лимит по IP на успешных
редиректах, защищать базу кешем, concurrency limit и быстрым `503`, оставить лимит только на `404`. Урок: лимит по IP — на
неаутентифицированных чувствительных путях, а не на публичной раздаче.

</details>

**D4.** Каждую минуту ровно в :00 всплеск запросов и волна `429`, график пилообразный.

<details><summary>Ответ</summary>

Fixed window с синхронным `Retry-After` «подожди до конца минуты»: клиенты возвращаются в одну секунду. Перейти на token bucket с
точным `Retry-After`, добавить jitter у клиентов, убрать привязку к границе минуты.

</details>

**D5.** Один клиент жалуется: «все запросы дают `429` уже сутки», хотя лимит — 100 в минуту, а шлёт он 5.

<details><summary>Ответ</summary>

Вероятно, ключ счётчика остался без TTL (сбой между `INCR` и `EXPIRE`) и счётчик вечен. Проверить `TTL` ключа (`-1`), удалить ключ,
исправить код на Lua/`EXPIRE … NX`, найти другие ключи без TTL (`SCAN` + `TTL`) и добавить метрику ключей без срока.

</details>

### Блок E. Вопросы с собеседования

**1.** Как бы вы спроектировали rate limiter для API?

<details><summary>Ответ</summary>

Уточнить: что ограничиваем, по какому ключу, какая точность и нагрузка, что делать при отказе. Алгоритм — token bucket; состояние —
Redis с Lua (атомарно), локальный pre-limit; конфиг лимитов как данные; ответ `429` + `Retry-After`; метрики по маршрутам; fail-open
или fail-closed по маршрутам. Эта тема — основа, полный разбор — отдельная задача курса.

</details>

**2.** Сравните fixed window, sliding window и token bucket.

<details><summary>Ответ</summary>

Fixed window — дёшево, но до 2 × лимит на стыке. Sliding log — точно, память O(limit). Sliding counter — два счётчика, приближение.
Token bucket — всплеск до `capacity` и средний темп `rate`, два числа на ключ, точный `Retry-After`; вариант по умолчанию для API.

</details>

**3.** Как сделать лимит корректным в распределённой системе?

<details><summary>Ответ</summary>

Общее состояние в Redis, операции атомарны (Lua), время — по часам Redis, ключи одного клиента в одном слоте (hash tag). Чтобы не
ходить на каждый запрос — локальный pre-limit и аренда токенов с известной погрешностью. Redis отдельный от кеша, `noeviction`,
таймаут и circuit breaker.

</details>

**4.** Где в архитектуре ставят лимиты?

<details><summary>Ответ</summary>

По слоям: CDN/WAF (грубо, IP), gateway (ключ и маршрут), приложение (tenant, тариф, цена запроса, квоты), зависимости (concurrency
limit, load shedding, адаптивные лимиты). Чем глубже — тем больше знает и дороже каждая проверка.

</details>

**5.** Лимитер недоступен: fail-open или fail-closed?

<details><summary>Ответ</summary>

По цене ошибки на маршрут. Редиректы и создание — fail-open (лимитер не должен ронять SLO; создание — плюс локальный лимит).
Логин и OTP — строгий локальный лимит (иначе подбор паролей или «никто не входит»). Платные операции — fail-closed. Решение
в ADR, проверка — учениями.

</details>

**6.** Что вернуть клиенту, который превысил лимит?

<details><summary>Ответ</summary>

`429` с `Retry-After`, при желании `RateLimit-*` (черновик IETF) и `problem+json`; не `403` и не `500`. Клиенту — backoff с jitter,
уважение `Retry-After`, retry budget, `Idempotency-Key` на повторах `POST`.

</details>

**7.** Чем rate limiting отличается от load shedding?

<details><summary>Ответ</summary>

Rate limit — справедливость и защита от конкретного клиента, по ключу и политике. Load shedding — реакция сервиса на общую
перегрузку: быстро отбросить часть запросов (сначала менее важные), чтобы остальные уложились в SLO. Нужны оба; для зависимостей
добавляют concurrency limit.

</details>

**8.** Как хранить и менять лимиты для тысяч tenant'ов?

<details><summary>Ответ</summary>

Как данные: политики по плану с переопределениями по tenant, в git или таблице, с горячей перезагрузкой, валидацией в CI, dry run
и kill switch. Квоты — отдельно, в БД. Метрики — по маршруту и tier'у, а не по ключам.

</details>
