## 1. Как выбрать стиль API

API — **долгоживущий контракт**: клиенты (мобильные приложения, партнёры, соседние команды)
обновляются медленно, а сломать их легко. Поэтому стиль выбирают по потребителю:

| Стиль | Модель | Сильные стороны | Слабые стороны | Где |
|-------|--------|-----------------|----------------|-----|
| REST поверх HTTP/JSON | Ресурсы и методы HTTP | Понятен, кешируется, любые клиенты и инструменты | Лишние или недостающие поля, схема строгая только с OpenAPI | Публичные и внешние API, CRUD |
| gRPC | Вызовы методов, Protobuf, HTTP/2 | Быстрый, строгая схема, стриминг, дедлайны | Браузеру нужен прокси, отладка сложнее, перекос на L4 | Внутренние вызовы сервис–сервис |
| GraphQL | Граф, клиент выбирает поля | Одна точка входа, ровно нужные данные | N+1, стоимость запросов, сложный кеш | Много разных клиентов, BFF |
| SSE | Поток сервер → клиент по HTTP | Просто, автопереподключение | Односторонний, буферизация прокси | Уведомления, прогресс, дашборды |
| WebSocket | Двунаправленный канал | Низкая задержка в обе стороны | Состояние на сервере, балансировка, drain | Чат, игры, совместное редактирование |
| Вебхуки | Сервер вызывает URL клиента | Нет опроса | Доставка, повторы, подпись, SSRF | События для партнёров |

Правило: **внешним — REST, внутренним — gRPC (или тот же REST), разнородным клиентам — GraphQL
или BFF, событиям клиенту — SSE, двусторонним — WebSocket, событиям партнёру — вебхуки**. Один
сервис часто имеет несколько стилей: linkd — REST снаружи, gRPC между сервисами, SSE для живой статистики.

**API linkd.** Список операций — в [задаче 01](/system-design/backend-cases/01-url-shortener), раздел 3:
`POST /api/v1/links` с `Idempotency-Key` (раздел 5), `GET /api/v1/links?cursor=&limit=` с курсорной
пагинацией (раздел 4), `GET` и `DELETE` по `/api/v1/links/{code}` (цель ссылки не редактируется), статистика, вебхук `link.blocked`.
Редирект `GET /{code}` → 302 стоит **вне API**: без аутентификации, версии и gateway
([тема 01](/system-design/building-blocks/01-edge-dns-cdn-lb)). В linkd 2.0 сейчас только
`POST /api/links`, `GET /api/links` и `GET /r/<code>`: без версий, ключей и пагинации.

## 2. REST: ресурсы, методы, коды, ошибки

**Ресурсы — существительные, во множественном числе, вложенность не глубже двух уровней:**
`/api/v1/links`, `/api/v1/links/{code}`, `/api/v1/links/{code}/stats`. Действие, которое не
вписывается в CRUD, — подресурс: `POST /api/v1/links/{code}/block`. Выбери один стиль и держи его
во всём API. Не зеркаль таблицы БД один в один: API — про предметную область.

### Методы: безопасные и идемпотентные

**Безопасный** метод ничего не меняет на сервере. **Идемпотентный** — N одинаковых запросов оставляют
сервер в том же состоянии, что один (RFC 9110).

| Метод | Безопасный | Идемпотентный | Для чего |
|-------|:----------:|:-------------:|----------|
| GET, HEAD | да | да | Чтение |
| PUT | нет | да | Замена ресурса целиком |
| DELETE | нет | да | Удаление (повтор вернёт 404, но состояние то же) |
| PATCH | нет | по умолчанию нет | Частичное изменение |
| POST | нет | **нет** | Создание, действия |

⭐ От идемпотентности зависит, **что можно повторять**: ретраи клиента, балансировщика и браузера
безопасны для GET, PUT, DELETE, но не для POST. Для POST нужен ключ идемпотентности (раздел 5).

**PATCH** лучше делать как JSON Merge Patch (RFC 7396, `application/merge-patch+json`): передаёшь
только изменяемые поля, `null` удаляет поле. **Потерянные обновления** лечит оптимистичная
блокировка: сервер отдаёт `ETag: "v7"`, клиент шлёт `If-Match: "v7"`; версия устарела — `412 Precondition Failed`; заголовка нет, а он обязателен, — `428`.

### Коды ответов

| Код | Когда |
|-----|-------|
| 200 / 201 + `Location` / 204 | Успех с телом / создан ресурс / успех без тела (DELETE) |
| 202 | Принято, обработка позже; в ответе ссылка на статус, например `/api/v1/jobs/{id}` |
| 304 | Условный GET: не изменилось |
| 400 / 422 | Запрос не разобрать / разобрали, но поля невалидны. Многие API (и linkd) отвечают на оба случая 400 — выбери одно правило на всё API |
| 401 / 403 | Не аутентифицирован / аутентифицирован, но прав нет |
| 404 / 410 | Нет ресурса (или не показываем, что есть) / был, но удалён или истёк |
| 409 | Конфликт состояния: алиас занят |
| 412 / 428 | Не совпал `If-Match` / предусловие обязательно |
| 413 / 415 | Тело слишком большое / формат не поддерживается |
| 429 + `Retry-After` | Лимит превышен |
| 500 / 502 / 503 / 504 | Ошибка сервера / ошибка апстрима / перегрузка (+ `Retry-After`) / таймаут |

**4xx — виноват клиент**, повтор без изменений бесполезен; **5xx — сервер**, повтор имеет смысл
(для идемпотентных); 429 и 503 повторяют после `Retry-After`. Чужой ресурс отдают как `404`, а не
`403`: так не раскрывают, что он существует.

### Ошибки: RFC 9457 (Problem Details)

Единый формат ошибок во всех сервисах — `application/problem+json`:

```http
HTTP/1.1 409 Conflict
Content-Type: application/problem+json

{
  "type": "https://api.lnk.example/problems/alias-taken",
  "title": "Алиас уже занят",
  "status": 409,
  "detail": "Алиас promo2027 принадлежит другой ссылке",
  "instance": "/api/v1/links",
  "trace_id": "4bf92f3577b34da6a3ce929d0e0e4736"
}
```

`type` — стабильный идентификатор для кода клиента; `title` и `detail` — для человека, парсить их
нельзя; `trace_id` — расширение, по нему ищут запрос в логах и трейсах. Для валидации добавляют массив
`errors` с указателем на поле. В ошибке не должно быть стектрейса и SQL.

## 3. Версии и совместимость изменений

| Стратегия | Как | Плюсы | Минусы |
|-----------|-----|-------|--------|
| В пути | `/api/v1/links` | Наглядно, маршрутизируется на gateway, кешируется | Версия «вшита» в каждую ссылку |
| В заголовке | `Accept: application/vnd.linkd.v2+json` | Чистые URL | Сложнее отладка, нужен `Vary` |
| По датам | `Linkd-Version: 2026-11-01` | Клиент фиксирует дату, ломающие изменения ему не страшны | Слой преобразований на сервере: дорого |
| Без версий | Только добавление полей, проверка contract tests | Минимум поддержки | Нужна дисциплина, подходит для внутренних API |

⭐ **Рабочая схема:** major в пути (`/v1`), внутри версии — только совместимые изменения. Новая
major — крайняя мера, когда ломается сама модель.

| Совместимо | Ломает клиентов |
|------------|-----------------|
| Новое необязательное поле в ответе | Удалить или переименовать поле |
| Новый эндпоинт или необязательный параметр | Изменить тип или формат (число → строка) |
| Новое значение enum, **если** клиенты это ожидают | Ужесточить валидацию, сделать поле обязательным |
| Ослабить валидацию | Изменить смысл поля, код ответа или сортировку по умолчанию |

**Tolerant reader** (терпимый читатель): клиент игнорирует неизвестные поля и значения enum. Без этого
даже безобидное добавление поля становится «ломающим» — договорись об этом в документации API.

## 4. Пагинация, фильтры и сортировка

«Отдать все 6 млрд ссылок» нельзя, а `GET /api/v1/links` возвращает только ссылки владельца,
постранично. Две схемы.

**Offset** (`?limit=50&offset=100000`): БД читает и выбрасывает 100 000 строк, цена растёт с
номером страницы; между запросами вставки и удаления сдвигают окно — дубли и пропуски. Плюс: можно
прыгнуть на страницу N.

**Keyset (курсор)**: условие на значение последней отданной строки.

```sql
-- индекс под сортировку: владелец, затем время и код как tie-breaker (время может совпасть)
CREATE INDEX links_owner_created ON links (owner_id, created_at DESC, code DESC);

-- первая страница: limit + 1 строка, лишняя означает «есть следующая»
SELECT code, long_url, created_at FROM links
WHERE owner_id = $1
ORDER BY created_at DESC, code DESC
LIMIT 51;

-- следующая: курсор хранит created_at и code последней отданной строки
SELECT code, long_url, created_at FROM links
WHERE owner_id = $1 AND (created_at, code) < ($2, $3)
ORDER BY created_at DESC, code DESC
LIMIT 51;
```

Индекс из [задачи 01](/system-design/backend-cases/01-url-shortener) (`owner_id, created_at DESC`) для
этого расширяется колонкой `code`. План запроса и разница с offset — в лабе C2.

| | Offset | Keyset |
|---|--------|--------|
| Цена на глубокой странице | Растёт с номером | Постоянная, идёт по индексу |
| Вставки и удаления между запросами | Дубли и пропуски | Стабильно |
| Прыжок на страницу N | Да | Нет: только «дальше» и «назад» |
| Общее число | `COUNT(*)` дорог на больших выборках | Не отдаём: `has_more` или оценка |
| Сортировка | Любая | Только по индексированным полям с tie-breaker |

**Курсор — непрозрачная строка** (base64url от JSON с версией), клиент его не разбирает и не строит:

```python
import base64
import json


def encode_cursor(created_at: str, code: str) -> str:
    raw = json.dumps({"v": 1, "t": created_at, "c": code}, separators=(",", ":"))
    return base64.urlsafe_b64encode(raw.encode()).decode().rstrip("=")


def decode_cursor(cursor: str) -> tuple[str, str]:
    data = json.loads(base64.urlsafe_b64decode(cursor + "=" * (-len(cursor) % 4)))
    if data.get("v") != 1:
        raise ValueError("unsupported cursor")
    return data["t"], data["c"]
```

```json
{ "items": [ { "code": "aZ3x9Qk", "long_url": "https://shop.example/catalog" } ],
  "next_cursor": "eyJ2IjoxLCJ0IjoiMjAyNi0xMS0xN1QxMDowMDowMFoiLCJjIjoiYVozeDlRayJ9",
  "has_more": true }
```

⚠️ **Владелец берётся из токена, а не из курсора** — иначе клиент подставит чужой `owner_id`. Курсор
только продолжает запрос, права проверяются при каждом обращении. Версия в курсоре позволяет сменить
формат. По умолчанию `limit=50`, максимум 200 — защита от «дай всё».

**Фильтры и сортировка:** `?status=active&created_after=2026-11-01&sort=-created_at`. Разрешай сортировку
только по индексированным полям (белый список), помни, что каждая пара «фильтр + сортировка» — свой
индекс, и ограничивай набор. Произвольный поиск по подстроке — задача поискового движка
([тема 07](/system-design/building-blocks/07-blobs-search)). Параметры в SQL — только через привязку.

## 5. Идемпотентность POST и bulk

Клиент отправил `POST /api/v1/links`, ответ потерялся по таймауту, клиент повторил — получились две
ссылки (для платежей — двойное списание). Решение — **ключ идемпотентности**:

- клиент генерирует уникальный ключ (UUID) на **логическую операцию** и шлёт тот же при каждом
  повторе, а для новой операции — новый;
- первый запрос выполняется, и сервер запоминает ответ; повтор с тем же ключом и телом возвращает
  **тот же ответ** (статус и тело);
- тот же ключ с **другим телом** — ошибка `422`: клиент перепутал операции;
- ключ живёт сутки и действует **в рамках владельца** `(owner_id, key)`.

Для заголовка `Idempotency-Key` есть черновик IETF; на практике это соглашение, как у платёжных API.

### Хранилище ключей

```sql
CREATE TABLE idempotency_keys (
    owner_id      bigint      NOT NULL,
    key           uuid        NOT NULL,
    request_hash  bytea       NOT NULL,   -- sha256(метод + путь + тело): ловим «тот же ключ, другое тело»
    response_code int         NOT NULL,
    response_body jsonb       NOT NULL,
    created_at    timestamptz NOT NULL DEFAULT now(),
    PRIMARY KEY (owner_id, key)
);
-- чистка записей старше 24 часов: партиции по дню (DROP PARTITION) дешевле, чем DELETE
```

Это расширенная версия таблицы из [задачи 01](/system-design/backend-cases/01-url-shortener). Если вся
работа — в одной БД, всё делает **одна транзакция**:

```sql
BEGIN;
INSERT INTO idempotency_keys (owner_id, key, request_hash, response_code, response_body)
VALUES ($1, $2, $3, 0, '{}') ON CONFLICT (owner_id, key) DO NOTHING;
-- вставлено 0 строк: ключ уже был, читаем сохранённую строку и отвечаем (или 422 при другом request_hash)
-- вставлена 1 строка: мы первые — выполняем работу (INSERT INTO links ...) и фиксируем ответ:
UPDATE idempotency_keys SET response_code = 201, response_body = $4 WHERE owner_id = $1 AND key = $2;
COMMIT;
```

⭐ Ссылка и ключ фиксируются **атомарно**: падение посередине откатывает обе записи, клиент безопасно
повторит. Параллельный дубль на `INSERT … ON CONFLICT` в PostgreSQL ждёт завершения первой
транзакции и затем получает уже сохранённый ответ. Redis с `SET NX` как основное хранилище хуже:
запись ключа не атомарна с бизнес-записью — между ними можно упасть и получить дубль или потерять
операцию.

Если в операции есть внешний вызов (платёжный провайдер) и одной транзакции не хватает, ключ хранят
со статусом `in_progress` и временем аренды: параллельный дубль получает `409` с `Retry-After`,
зависшую операцию подбирают после истечения аренды, итог пишут после завершения.

**Клиент:** ретрай при таймауте, 5xx и 429, с экспоненциальной паузой и jitter, **тем же ключом**;
на 4xx не повторяет. Ключ в рамках владельца ещё и защита: один клиент не получит ответ другого.

### Bulk-эндпоинты

```http
POST /api/v1/links:batch
Idempotency-Key: 8d1f2c3e-7a4b-4b9a-9c55-1e0d6f3a2b71

{ "items": [ { "long_url": "https://shop.example/a" }, { "long_url": "ftp://bad" } ] }
```

```http
HTTP/1.1 200 OK

{ "results": [ { "status": 201, "code": "aZ3x9Qk" },
               { "status": 400, "error": { "type": ".../invalid-url", "detail": "нужен http или https" } } ] }
```

Решения: **атомарно** (всё или ничего, один код ответа) или **частичный успех** (свой статус на каждый
элемент; общий 200 или 207 Multi-Status). Нужны лимиты: до 100 элементов, предел размера тела,
таймаут; ключ ставится на весь пакет, а в лимите запросов пакет считается по числу элементов. Для
10 000 элементов — асинхронно: `202 Accepted` с `Location: /api/v1/jobs/{id}`, опрос статуса или вебхук.

## 6. gRPC

**gRPC** — вызовы методов поверх HTTP/2; контракт в `.proto`, сообщения в бинарном Protobuf, клиенты
и серверы генерируются. Четыре вида вызова: unary, server streaming, client streaming, двунаправленный
поток.

```proto
syntax = "proto3";
package linkd.v1;

service LinkService {
  rpc GetLink(GetLinkRequest) returns (Link);                          // unary
  rpc WatchBlocked(WatchBlockedRequest) returns (stream BlockedEvent); // поток: сбросить L1-кеш в подах
}

message GetLinkRequest { string code = 1; }
message Link {
  string code = 1;
  string long_url = 2;
  reserved 3;                  // поле удалено: номер больше не используем
  reserved "owner";
  int64 expires_at_unix = 4;
}
```

Правила эволюции Protobuf: номер поля — идентификатор в бинарном формате, его **нельзя менять и
переиспользовать** (`reserved`), можно только добавлять поля, нельзя менять тип. Проверка в CI —
`buf breaking --against '.git#branch=main'`.

**Дедлайн.** Клиент задаёт дедлайн вызова; он передаётся по цепочке (заголовок `grpc-timeout`), и
каждый следующий сервис видит оставшееся время. Истёк — `DEADLINE_EXCEEDED`, работа отменяется. Без
дедлайна запрос может висеть вечно. Статусы gRPC близки к HTTP: `INVALID_ARGUMENT`, `NOT_FOUND`,
`ALREADY_EXISTS`, `UNAUTHENTICATED`, `PERMISSION_DENIED`, `RESOURCE_EXHAUSTED` (≈ 429),
`UNAVAILABLE` (повтор безопасен), `DEADLINE_EXCEEDED`.

| | REST/JSON | gRPC |
|---|-----------|------|
| Формат | Текст, читаем глазами | Бинарный, нужен `grpcurl` и схема |
| Схема | Опционально (OpenAPI) | Обязательна, кодогенерация |
| Стриминг | SSE, WebSocket отдельно | Встроен |
| Браузер | Напрямую | Через gRPC-Web или Connect и прокси |
| HTTP-кеш и CDN | Да | Нет |
| Где | Внешние API | Внутренние вызовы, высокая нагрузка, streaming |

### ⚠️ gRPC и L4: перекос нагрузки

gRPC держит **долгое HTTP/2-соединение**, в котором идут тысячи запросов. L4-балансировщик
([тема 01](/system-design/building-blocks/01-edge-dns-cdn-lb)) выбирает бэкенд **один раз при
установке соединения**: все запросы клиента идут на один под. Обычный Service с ClusterIP в
Kubernetes — тоже балансировка по соединениям. Поды после scale-up стоят пустыми, потому что
соединения уже открыты. Решения:

- **L7-балансировщик с HTTP/2** (Envoy, nginx `grpc_pass`, облачный L7 с поддержкой gRPC) — балансирует
  запросы;
- **балансировка на клиенте**: headless Service и политика `round_robin`, или xDS;
- `MAX_CONNECTION_AGE` на сервере: соединение закрывается через заданное время и клиент
  переустанавливает его, перераспределяя нагрузку (особенно после масштабирования);
- service mesh.

Для корректной остановки сервер шлёт `GOAWAY`: новые запросы не принимаются, текущие дорабатывают.
Проверку живости делают протоколом `grpc.health.v1`; в современных Kubernetes есть gRPC-пробы.

## 7. GraphQL

**GraphQL** — одна точка входа (обычно `POST /graphql`), клиент описывает нужные поля, сервер отдаёт
ровно их, схема строго типизирована.

```graphql
query { me { links(first: 20) { code longUrl clicks { total } } } }
```

| Подходит | Не подходит |
|----------|-------------|
| Много разных клиентов (веб, мобильные) с разными данными | Простой CRUD, где хватит REST |
| Глубокий граф связанных данных, BFF-слой | Публичный API для недоверенных клиентов: стоимость запроса трудно ограничить |
| Агрегация из нескольких сервисов | Вызовы между сервисами внутри системы |

Что ломается и как лечат:

- **N+1.** Resolver вызывается для каждого элемента списка: 20 ссылок — 1 запрос ссылок и 20 запросов
  владельцев. Лечит **DataLoader**: собирает ключи за один «тик» и делает один запрос.

```python
# N+1: на каждую ссылку отдельный запрос
for link in links:
    link["owner"] = db.one("SELECT * FROM users WHERE id = %s", link["owner_id"])

# DataLoader: один запрос на пачку
ids = list({link["owner_id"] for link in links})
users = {u["id"]: u for u in db.all("SELECT * FROM users WHERE id = ANY(%s)", [ids])}
```

- **Стоимость запроса.** Клиент пишет `first: 1000000` или вкладывает запросы на 20 уровней. Нужны
  лимит глубины, расчёт сложности, потолок на размер списков, таймаут, а для публичных API —
  **persisted queries** (разрешён только заранее зарегистрированный набор запросов). Лимиты по
  стоимости, а не по числу запросов ([тема 08](/system-design/building-blocks/08-rate-limiting)).
- **Кеширование.** Всё идёт POST на один URL, у каждого клиента своя форма запроса — HTTP-кеш и CDN
  бесполезны. Помогают persisted queries по GET с хешем (для CDN), кеш в resolver'ах и DataLoader
  внутри запроса, Redis ([тема 03](/system-design/building-blocks/03-caching)).
- **Ошибки.** Ответ `200 OK` с массивом `errors`: мониторинг по HTTP-коду ничего не видит. Метрики
  считают по имени операции и доле ответов с `errors`.
- **Авторизация** проверяется на уровне полей, introspection для внешних клиентов выключают, а если
  команд много, схему собирают через federation.

## 8. Real-time: polling, SSE, WebSocket и вебхуки

| Способ | Направление | Как работает | Цена | Минусы | Для чего |
|--------|-------------|--------------|------|--------|----------|
| Short polling | Клиент опрашивает | Запрос раз в N секунд | 1 запрос / N с на клиента, в основном пустой | Задержка до N с, лишняя нагрузка | Редкие обновления |
| Long polling | Клиент опрашивает | Запрос висит до события или 25–30 с | 1 удерживаемое соединение | Запрос на каждое событие, таймауты прокси | Запасной вариант |
| SSE | Сервер → клиент | Одно долгое HTTP-соединение, `text/event-stream` | 1 соединение | Односторонний, буферизация прокси | Уведомления, прогресс, статистика |
| WebSocket | В обе стороны | Полнодуплексный канал после HTTP Upgrade | 1 соединение + память | Состояние, балансировка, drain | Чат, игры, редакторы |
| Вебхук | Сервер → сервер | Сервер вызывает URL подписчика | Нет постоянной связи | Доставка, повторы, подпись | События для партнёров |

**Цена опроса.** Миллион клиентов раз в 10 секунд — это 100 000 RPS почти пустых запросов; те же
клиенты на SSE или WebSocket — миллион удерживаемых соединений и почти нулевой RPS.

### Математика соединений: 1 млн WebSocket

```text:no-line-numbers
1 млн одновременных соединений, heartbeat раз в 30 с
  память:     порядка 20–50 КБ на соединение (буферы сокета, состояние, TLS) → 20–50 ГБ в сумме
              (порядок величины: зависит от рантайма и буферов, замерь на своём коде)
  узлы:       по ~50 000 соединений на узел с запасом → ~20 узлов, а лимит — память, не CPU
  heartbeat:  1 000 000 / 30 с ≈ 33 000 сообщений/с в каждую сторону — для CPU немного
  рассылка:   1 КБ всем = 1 ГБ исходящего трафика за раз; 10 рассылок в секунду — ~10 ГБ/с на кластер
  деплой:     перезапуск одного узла — 50 000 переподключений сразу = 50 000 TLS-рукопожатий
```

Что из этого следует:

- **Порты.** Пара «IP прокси → бэкенд:порт» даёт порядка 64 000 соединений
  ([тема 01](/system-design/building-blocks/01-edge-dns-cdn-lb), раздел про масштабирование): миллион
  требует нескольких бэкендов, портов или адресов прокси. Нужен и `ulimit -n`.
- **Рассылка между узлами** идёт через брокер (Redis pub/sub, NATS, Kafka): клиент на узле A
  должен получить событие, пришедшее на узел B. Присутствие и состояние хранят во внешнем хранилище.
- **Балансировщик:** таймаут простоя должен быть больше heartbeat. Балансировка по соединению; sticky
  нужен, если состояние лежит в памяти узла.
- **Reconnect storm.** После деплоя или обрыва все клиенты возвращаются разом: переподключение с
  экспоненциальной паузой и jitter, плавный слив узла.

**WebSocket на практике.** Upgrade до `101 Switching Protocols`; в nginx нужны `proxy_http_version 1.1`,
заголовки `Upgrade`/`Connection` и увеличенный `proxy_read_timeout`; свой ping/pong. Браузер не шлёт
произвольные заголовки при открытии сокета, поэтому токен передают коротким одноразовым **ticket**
или первым сообщением (токен в URL попадёт в логи). Проверяй `Origin`, иначе возможен cross-site
WebSocket hijacking.

**SSE на практике.** Клиент (`EventSource`) сам переподключается и шлёт `Last-Event-ID` — сервер
досылает пропущенное из недавнего лога (Redis Streams, Kafka); за буфер прокси отвечают
`X-Accel-Buffering: no` или `proxy_buffering off`; для живого соединения шлют комментарий-heartbeat
(`: ping`). В HTTP/1.1 браузер держит не больше 6 соединений на домен, в HTTP/2 этого лимита нет.
Эффект видно в лабе C3.

**Вебхуки.** Подписчик регистрирует URL и секрет. Надёжная доставка:

- **подпись** HMAC-SHA256 над `timestamp.body` в заголовке и допуск ±5 минут против повторной
  отправки (лаба C4);
- доставка **at-least-once**: получатель дедуплицирует по `event_id` и отвечает 2xx быстро, а работу
  делает асинхронно; порядок не гарантируется — в событии время или версия;
- повторы с экспоненциальной паузой до 24–72 часов, затем эндпоинт отключают и уведомляют владельца;
- **защита от SSRF**: перед вызовом проверять, что адрес не из приватных диапазонов (127.0.0.0/8,
  10.0.0.0/8, 169.254.169.254 с метаданными облака), не ходить по редиректам, жёсткий таймаут и лимит
  размера ответа;
- журнал доставок, ручной повтор, отдельный circuit breaker на эндпоинт.

## 9. Надёжность вызова: таймауты, дедлайны, ретраи

- **Таймаут на каждом вызове**, и убывающий вниз по цепочке: клиент 3 с → gateway 2,5 с → сервис 2 с →
  БД 1,5 с. Иначе внутри система трудится над запросом, который клиент давно бросил.
- **Дедлайн передаётся по цепочке** (в gRPC автоматически, в HTTP — заголовком и контекстом в коде): если
  осталось меньше времени, чем нужно, отказывай сразу.
- **Ретраи — только для идемпотентных операций** (GET, PUT, DELETE, POST с ключом) и только на сетевых
  ошибках, 5xx и 429. Экспоненциальная пауза с jitter, бюджет (не больше ~10% дополнительных запросов),
  уважение к `Retry-After`. Ретрай при `DEADLINE_EXCEEDED` осторожно: операция могла уже начаться.
- **Один слой ретраев** (клиент, балансировщик, gateway, mesh — только один), иначе 3 × 3 × 3 × 3 = 81
  запрос на один клиентский ([тема 01](/system-design/building-blocks/01-edge-dns-cdn-lb)).
- Сервис на 1 000 RPS при сбое с тремя попытками получает 3 000 RPS — **retry storm** добивает
  больного. Защита: circuit breaker, bulkhead, ограничение параллельности
  ([SRE: 06. Паттерны надёжности](/sre/06-reliability-patterns),
  [Распределённые системы: 06. Режимы отказов](/distributed/06-failure-modes)).

## 10. Контракты, совместимость и жизненный цикл

**Контракт — в коде**: OpenAPI (REST), `.proto` (gRPC), SDL (GraphQL) лежат в репозитории и проходят
ревью. Spec-first — сначала схема, потом код; code-first — схема генерируется из кода.

**Автопроверки в CI:**

- линтер контракта (например, Spectral для OpenAPI);
- сравнение с версией из `main` на ломающие изменения (например, `oasdiff`, `buf breaking` для
  Protobuf) — сборка падает при breaking;
- **contract tests**: consumer-driven (потребитель публикует ожидания, провайдер их проверяет, например
  Pact) и проверка провайдера по схеме с генерацией запросов (например, Schemathesis).

**Rolling update и два поколения.** Во время выкатки работают версии N и N+1, а клиенты ещё на N−1: изменения
делают по схеме expand/contract — добавить новое, перевести клиентов, убрать старое
([Базы данных: 13. Миграции схемы](/databases/13-schema-migrations) — то же для схемы БД).

| Стадия | Что значит |
|--------|-----------|
| Beta | Может измениться, об этом предупреждаем |
| GA | Совместимость гарантирована |
| Deprecated | Работает, но заменяется: заголовки, документация, письма |
| Sunset | Дата отключения |
| Removed | Эндпоинт возвращает `410 Gone` |

```http
HTTP/1.1 200 OK
Deprecation: @1793491200
Sunset: Thu, 01 Jul 2027 00:00:00 GMT
Link: <https://docs.lnk.example/migrate-v2>; rel="deprecation"
```

`Deprecation` (RFC 9745) и `Sunset` (RFC 8594) говорят клиентам о дате. Но заголовки читают не все:
нужна **телеметрия** «кто ещё ходит на старую версию» (по ключу и версии), письма владельцам и
**brownout** — плановые короткие отключения, которые находят забытых клиентов. Срок поддержки
записывается в политику API.

## 11. ⚙️ Эксплуатация

Семь вопросов из [Основы: 04. Бэкенд-собес и DevOps-собес](/system-design/basics/04-backend-vs-devops)
для API.

### 11.1 Развёртывание

- **Две версии кода живут одновременно** (rolling update): API N и N+1 совместимы, схему БД меняют по
  expand/contract ([Kubernetes: 05. Deployment](/kubernetes/05-deployment)).
- **Версии API** — разные Deployment за gateway (`/v1`, `/v2`), canary по доле трафика и по клиентам
  ([Platform Engineering: 06. Progressive delivery](/platform/06-progressive-delivery)).
- **Контракт в репозитории**, проверка на ломающие изменения в CI, клиенты генерируются в пайплайне.
- **Долгие соединения** (WebSocket, SSE, gRPC-стримы): `terminationGracePeriodSeconds` под самое долгое
  соединение; сервер шлёт `GOAWAY` или close frame (1001/1012), клиент возвращается с jitter; слив —
  не быстрее X% соединений в секунду, чтобы не получить reconnect storm.
- **Таймауты и дедлайны** — конфиг, а не константы в коде.

### 11.2 Масштабирование

| Компонент | Масштабируется | Метрика | Потолок |
|-----------|---------------|---------|---------|
| REST, stateless | HPA | RPS или CPU на под | Соединения к БД: подов × пул ≤ `max_connections` |
| gRPC | HPA + L7 или клиентская балансировка | Параллельные вызовы на под | Перекос на L4, соединения, открытые до scale-up |
| WebSocket, SSE | По числу соединений, не по CPU | Соединения и память на под | Память, порты proxy → backend, `ulimit`, fan-out |
| GraphQL | HPA | Стоимость запросов, а не их число | Тяжёлые запросы, N+1 |
| Bulk, вебхуки | Отдельные воркеры | Очередь, возраст задачи | Лимиты внешних получателей |

Keyset-пагинация держит цену запроса плоской; лимиты на размер страницы и пакета — защита БД.

### 11.3 Наблюдаемость

- **RED по эндпоинтам**: rate, errors, duration — по шаблону маршрута (`/api/v1/links/{code}`), а не по
  фактическому пути: иначе кардинальность лейбла убьёт Prometheus
  ([Мониторинг: 07. Что мониторить](/monitoring/07-what-to-monitor)). У linkd для этого
  `linkd_http_requests_total` и `linkd_request_duration_seconds`. SLO отдельно: редирект 99,95%,
  создание 99,9%.
- **gRPC** — статусы по методам; **GraphQL** — по имени операции и доле ответов с `errors`.
- **WebSocket и SSE**: открытые соединения, скорость подключений и отключений, причины закрытия,
  reconnect rate, сообщения in/out, задержка доставки, размер очереди отправки (медленные клиенты).
- **Вебхуки**: доля успешных доставок, возраст самого старого недоставленного события, глубина очереди
  повторов, число отключённых эндпоинтов.
- **Идемпотентность**: доля повторов (рост — клиенты ловят таймауты), число `422` «ключ с другим
  телом» (баг клиента), число `in_progress`.
- **Дедлайны и ретраи**: доля `DEADLINE_EXCEEDED` и 504, доля запросов с ретраями.
- **Версии**: трафик по версиям и по клиентам — готовый список, кого предупреждать перед Sunset.
- `trace_id` — сквозной ([SRE: 03. Трейсинг и OpenTelemetry](/sre/03-tracing-opentelemetry)).

### 11.4 Отказы

| Что случилось | Что видит клиент | Что делает система |
|---------------|-----------------|--------------------|
| Зависимость стала медленной | `504` по дедлайну | Дедлайн, circuit breaker, деградация; не ждать вечно |
| Шторм ретраев | Растёт задержка | Паузы с jitter и бюджет, ретраи в одном слое, `Retry-After` |
| Хранилище ключей идемпотентности недоступно | `POST` → `503` | **Fail closed**: лучше отказать, чем создать дубль; клиент повторит с тем же ключом |
| Деплой или падение узла с WebSocket | Обрыв соединения | Reconnect с jitter и resume по `Last-Event-ID` или номеру сообщения |
| Reconnect storm | Тысячи TLS-рукопожатий | Backoff с jitter, лимит новых соединений в секунду на LB |
| Получатель вебхука лежит | — | Повторы с паузой, затем отключение эндпоинта и алерт, журнал |
| Частичный сбой в bulk | `200` с ошибками по элементам | Результат на каждый элемент; повторять только упавшие, тем же ключом |
| Перекос gRPC | Одни поды на 100%, другие пусты | L7 или клиентская балансировка, `MAX_CONNECTION_AGE` |

### 11.5 Данные и DR

- **Ключи идемпотентности** — временные (24 часа): потеря даёт риск дубля только внутри окна. Лежат в
  основной БД (бэкап общий), а не в Redis без персистентности.
- **Подписки вебхуков, хеши API-ключей, журнал доставок** — источник правды в БД с PITR.
- **Контракты** (OpenAPI, proto) — в git; опубликованные версии — неизменяемые артефакты.
- **Курсор stateless**: на сервере ничего не хранится, он переживает рестарты и failover. После
  восстановления БД курсор по `(created_at, code)` остаётся валидным — удалённые ссылки просто
  пропадут из страниц.
- **Состояние соединений** эфемерно: источник правды — не память узла, resume — из лога событий
  (Redis Streams, Kafka) с retention минуты–часы. RPO уведомлений согласуй с продуктом.
- Уведомления в интерфейс можно терять (согласуй RPO с продуктом), вебхуки — нельзя: событие хранится до подтверждённой доставки.

### 11.6 Безопасность

- **Аутентификация** (API-ключ, OAuth2, JWT) — на gateway; **авторизация по объекту** — в сервисе:
  BOLA/IDOR — первая в списке OWASP API Security Top 10. Владелец берётся из токена, а не из тела
  или курсора.
- **Mass assignment** — принимай только разрешённые поля; **excessive data exposure** — не отдавай лишнее.
- **Лимиты и валидация по схеме**: размер тела, длина строк, максимум `limit`, глубина и стоимость
  GraphQL; rate limiting по ключу, IP и стоимости ([тема 08](/system-design/building-blocks/08-rate-limiting)).
- **Ключи идемпотентности в рамках владельца**: чужой ответ получить нельзя.
- **WebSocket**: проверка `Origin`, короткоживущий ticket, лимит соединений на пользователя, лимит
  размера сообщения. **Вебхуки**: подпись, защита от SSRF, ротация секрета с перекрытием.
- Ошибки не раскрывают внутренности, CORS — по белому списку, TLS везде; персональные данные и токены не
  в URL и не в логах. **Инвентарь API**: забытые старые версии без защиты — частая дыра
  ([Безопасность: 03](/security/03-web-edge-security)).

### 11.7 Стоимость

| Статья | Почему растёт | Рычаги |
|--------|---------------|--------|
| Исходящий трафик | Большие ответы, лишние поля | Сжатие, выбор полей, максимум `limit`, Protobuf вместо JSON |
| Опрос или push | 1 млн × раз в 10 с = 100 000 RPS пустых запросов (CPU, запросы LB) | SSE и WebSocket: платишь памятью, а не запросами |
| WebSocket-узлы | Память на соединение | Инстансы с памятью, счёт «на 1 000 соединений» |
| Болтливые API | Много мелких запросов между AZ (межзональный трафик) | Batching, gRPC, агрегация на BFF |
| Gateway | У managed платят за запросы | Кеш и bulk уменьшают число вызовов |
| GraphQL | N+1 и тяжёлые запросы — нагрузка на БД | DataLoader, лимиты стоимости |
| Поддержка версий | Каждая живая версия — тесты, деплой, дежурства | Sunset по политике |

| Грабля | Что не так | Правильно |
|--------|-----------|-----------|
| Побочные эффекты в GET | Прокси, краулеры и префетч вызывают его сами | Меняющие запросы — POST/PUT/PATCH/DELETE |

| Версия API без плана отключения | Старые версии живут годами | Deprecation, Sunset, телеметрия, brownout |

## 💼 Как это на работе

- **Бэкенд:** API — продукт со своими потребителями. Опиши контракт в OpenAPI, назначь ему владельца,
  проверяй совместимость в CI и думай об идемпотентности и пагинации до первого клиента — потом это
  стоит дороже.
- **DevOps:** твоя часть — таймауты и лимиты на gateway и LB, балансировка gRPC и долгих соединений,
  drain при выкатке, метрики по эндпоинтам. Вопрос «что будет с WebSocket при деплое?» должен иметь
  ответ до релиза.
- На ревью дизайна API спрашивают: «что будет при повторе запроса?», «как это пагинируется?», «как
  отключать старую версию?», «что с таймаутами?». Подготовь ответы вместе.
- Самое дорогое в API — не код, а ошибки контракта: их исправляют годами, потому что клиентов не
  заставишь обновиться. Поэтому ревью контракта строже ревью реализации.

## 📌 Шпаргалка

| Хочу | Как |
|------|-----|
| Безопасно повторять запрос | Идемпотентный метод или `Idempotency-Key` на POST |
| Формат ошибки | RFC 9457: `application/problem+json`, стабильный `type`, `trace_id` |
| Пагинация больших списков | Keyset: `WHERE (created_at, code) < ($2, $3) ORDER BY … LIMIT n+1`, курсор непрозрачный |
| Потерянные обновления | `ETag` + `If-Match` → `412` |
| Версионирование | `/v1` в пути, внутри — только совместимые изменения |
| Внутренний вызов | gRPC с дедлайном; L7 или клиентская балансировка |
| Много клиентов с разными данными | GraphQL + DataLoader + лимиты стоимости |
| Уведомления в браузер | SSE (`Last-Event-ID`, heartbeat, без буферизации) |
| Двусторонний канал | WebSocket: heartbeat, ticket, drain, брокер между узлами |
| События партнёру | Вебхук: HMAC, at-least-once, повторы, SSRF-защита |
| Узнать, кто ломается при отключении версии | Телеметрия по ключу и версии + `Sunset` + brownout |

## 🧠 Что запомнить

1. API — долгоживущий контракт: клиентов не заставишь обновиться, поэтому только совместимые изменения, а версии отключают по плану (Deprecation, Sunset, телеметрия).
2. ⭐ Идемпотентный метод можно повторять, POST — только с ключом идемпотентности.
3. ⭐ Ключ и бизнес-запись фиксируются в одной транзакции; хранится `(owner_id, key)` и хеш тела.
4. Коды ответов настоящие, ошибки — по RFC 9457; чужой ресурс — `404`, а не `403`.
5. ⭐ Offset дорожает с номером страницы, keyset — нет; курсор непрозрачный, с tie-breaker, а владелец — из токена, не из курсора.
6. ⭐ gRPC за L4 перекашивает нагрузку: нужен L7, клиентская балансировка или `MAX_CONNECTION_AGE`.
7. GraphQL: N+1, лимиты стоимости и кеш — три цены гибкости.
8. ⭐ WebSocket — это состояние: память на соединение, heartbeat, брокер между узлами, плавный drain.
9. Вебхуки — at-least-once: подпись, дедупликация у получателя, повторы и защита от SSRF.
10. ⭐ Дедлайн на каждом вызове, ретраи — в одном слое и только для идемпотентных операций.

### Блок A. Теория

**A1.** Чем безопасный метод отличается от идемпотентного? Приведи примеры и объясни, почему это важно.

<details><summary>Ответ</summary>

Безопасный не меняет состояние (GET, HEAD); идемпотентный — повтор оставляет состояние таким же, как после
одного вызова (GET, PUT, DELETE). От этого зависит, что можно автоматически повторять: ретраи клиента,
LB и прокси безопасны для идемпотентных; POST — нет.

</details>

**A2.** ⭐ Клиент отправил `POST /api/v1/links`, ответ потерялся. Как сделать повтор безопасным?

<details><summary>Ответ</summary>

Клиент шлёт `Idempotency-Key` (UUID на операцию) и повторяет с тем же. Сервер хранит
`(owner_id, key, request_hash, ответ)`: повтор возвращает тот же ответ, другое тело с тем же ключом — `422`.
Ключ и бизнес-запись — в одной транзакции.

</details>

**A3.** ⭐ Различи `401` и `403`, `400` и `422`, `404` и `410`, `409`.

<details><summary>Ответ</summary>

`401` — не аутентифицирован, `403` — прав нет. `400` — запрос не разобрать, `422` — разобрали, но поля
невалидны. `404` — нет ресурса (или не показываем), `410` — был, но удалён или истёк. `409` — конфликт
состояния, например занятый алиас.

</details>

**A4.** ⭐ Почему keyset быстрее offset и что нужно в индексе и сортировке?

<details><summary>Ответ</summary>

Offset читает и выбрасывает все пропущенные строки; keyset сразу идёт по индексу от последней отданной. В
индексе и в `ORDER BY` нужен tie-breaker (`created_at DESC, code DESC`), иначе при одинаковом времени
будут дубли и пропуски.

</details>

**A5.** Что в курсоре, почему он непрозрачный и почему из него нельзя брать `owner_id`?

<details><summary>Ответ</summary>

Значения сортировки последней строки (`created_at`, `code`) и версия. Он непрозрачный, чтобы можно
было менять формат. Владельца берут из токена: курсор приходит от клиента и может быть подделан.

</details>

**A6.** Какие изменения API ломают клиентов, а какие нет? Что такое tolerant reader?

<details><summary>Ответ</summary>

Ломают: удаление и переименование полей, смена типа, обязательность поля, ужесточение валидации,
смена смысла. Не ломают: новое необязательное поле, новый эндпоинт. Tolerant reader — клиент
игнорирует неизвестные поля и значения enum, без этого и добавление поля может сломать.

</details>

**A7.** ⭐ Когда gRPC, а когда REST? Зачем дедлайн?

<details><summary>Ответ</summary>

gRPC — внутренние вызовы, высокая нагрузка, стриминг, строгая схема; REST — публичные API, браузеры,
кеширование. Дедлайн ограничивает время всей цепочки и передаётся вниз: без него запросы могут висеть
вечно и копиться.

</details>

**A8.** ⭐ Почему gRPC через L4 перекашивает нагрузку и как это исправить?

<details><summary>Ответ</summary>

L4 выбирает бэкенд один раз при установке долгого HTTP/2-соединения, и все запросы клиента идут туда;
поды после scale-up стоят пустыми. Решения: L7 с HTTP/2, балансировка на клиенте (headless Service +
`round_robin`), `MAX_CONNECTION_AGE`, mesh.

</details>

**A9.** Что такое N+1 в GraphQL и как это лечится? Почему сложно кешировать?

<details><summary>Ответ</summary>

Resolver вызывается на каждый элемент списка и делает свой запрос: 1 + N запросов. DataLoader собирает
ключи в пачку и делает один запрос. Кешировать сложно: всё идёт POST на один URL, форма запроса у
каждого клиента своя; помогают persisted queries по GET и кеш на уровне resolver'ов.

</details>

**A10.** ⭐ Сравни short polling, long polling, SSE, WebSocket и вебхуки. Когда что брать?

<details><summary>Ответ</summary>

Short polling — просто, но задержка и лишние запросы; long polling — запасной вариант; SSE — односторонний
поток по HTTP с автопереподключением (уведомления, прогресс); WebSocket — двунаправленный канал (чат,
редакторы), но с состоянием; вебхуки — события сервер → сервер для партнёров.

</details>

**A11.** ⭐ 1 млн WebSocket-соединений: что считаешь?

<details><summary>Ответ</summary>

Память (десятки КБ на соединение → десятки ГБ, узлы по ~50 000), heartbeat (~33 000 сообщений/с при
30 с), порты между прокси и бэкендом (~64 000 на пару адресов), `ulimit`, рассылку через брокер,
reconnect storm при деплое. Масштабируют по числу соединений, а не по CPU.

</details>

**A12.** Как надёжно доставлять вебхуки и как принимать?

<details><summary>Ответ</summary>

Отправитель: подпись HMAC с timestamp, повторы с паузой до 24–72 часов, SSRF-защита, журнал и
отключение «мёртвых» эндпоинтов. Получатель: проверка подписи и времени, быстрый 2xx, дедупликация по
`event_id`, обработка асинхронно.

</details>

### Блок B. «Что тут не так»

```
B1.  «Ссылку создаём через GET /api/v1/links/create?url=... — так удобнее тестировать»

B2.  «Все ответы — 200 OK, а в теле {"success": false, "error": "..."}»

B3.  «Пагинация: OFFSET 1000000, а total считаем через COUNT(*) на каждый запрос»

B4.  «Курсор — это owner_id и created_at в открытом виде: клиент может подставить чужой owner_id»

B5.  «Клиент при таймауте повторяет POST /payments — значит, надёжный»

B6.  «Переименовали поле long_url в url — это минорная версия»

B7.  «gRPC-сервис за обычным Service ClusterIP, HPA до 20 подов — нагрузка выровняется»

B8.  «WebSocket через nginx без правок: idle timeout 60 секунд, heartbeat не нужен»

B9.  «Вебхуки принимаем без проверки подписи — URL секретный, его знают только они»
```

<details><summary>Ответы</summary>

**B1.** ⚠️ GET должен быть безопасным: краулеры, префетч и прокси будут создавать ссылки. Создание — POST с
`Idempotency-Key`.

**B2.** ⚠️ Мониторинг, кеши и ретраи слепы. Нужны настоящие коды и Problem Details (RFC 9457).

**B3.** ⚠️ Цена растёт с номером страницы, а `COUNT(*)` дорог на больших выборках. Keyset и `has_more`.

**B4.** ⚠️ Клиент подставит чужой `owner_id`: владелец берётся из токена, курсор только продолжает запрос
(при желании его подписывают).

**B5.** ⚠️ Без ключа идемпотентности повтор списывает деньги дважды. Нужен `Idempotency-Key` и хранилище
ключей.

**B6.** ⚠️ Переименование ломает клиентов. Добавить `url`, оставить `long_url`, объявить deprecation, убрать
по плану.

**B7.** ⚠️ ClusterIP балансирует соединения: старые соединения остаются на старых подах, новые простаивают.
L7, клиентская балансировка или `MAX_CONNECTION_AGE`.

**B8.** ⚠️ Через минуту тишины LB оборвёт соединение. Heartbeat чаще таймаута, `proxy_read_timeout` под
сценарий.

**B9.** ⚠️ URL утекает в логи и конфиги; без подписи любой подделает событие. Нужны HMAC и timestamp.

</details>

### Блок C. Практика

#### C1. 🔑 Идемпотентный `POST /api/v1/links`

Сервер на стандартной библиотеке и SQLite: ключ и ссылка пишутся в одной транзакции, параллельные
дубли выстраиваются в очередь.

```python
# server.py — POST /api/v1/links с Idempotency-Key
import hashlib
import json
import secrets
import sqlite3
import string
from http.server import BaseHTTPRequestHandler, ThreadingHTTPServer

ALPHABET = string.digits + string.ascii_letters
sqlite3.connect("linkd.db").executescript("""
CREATE TABLE IF NOT EXISTS links (code TEXT PRIMARY KEY, long_url TEXT NOT NULL, owner_id INTEGER NOT NULL);
CREATE TABLE IF NOT EXISTS idempotency_keys (
    owner_id INTEGER NOT NULL, key TEXT NOT NULL, request_hash TEXT NOT NULL,
    response_code INTEGER NOT NULL, response_body TEXT NOT NULL, PRIMARY KEY (owner_id, key));
""")


def problem(status, title, detail):
    return status, {"type": "about:blank", "title": title, "status": status, "detail": detail}, "application/problem+json"


def create_link(owner, key, raw):
    req_hash = hashlib.sha256(raw).hexdigest()
    db = sqlite3.connect("linkd.db", timeout=10, isolation_level=None)
    db.execute("BEGIN IMMEDIATE")      # писатели по очереди: аналог блокировки по ключу в PostgreSQL
    row = db.execute("SELECT request_hash, response_code, response_body FROM idempotency_keys "
                     "WHERE owner_id = ? AND key = ?", (owner, key)).fetchone()
    if row:                            # повтор: тот же ответ, а при другом теле — ошибка
        db.execute("COMMIT")
        if row[0] != req_hash:
            return problem(422, "Idempotency-Key reused", "ключ уже использован с другим телом запроса")
        return row[1], json.loads(row[2]), "application/json", True
    code = "".join(secrets.choice(ALPHABET) for _ in range(7))
    body = {"code": code, "long_url": json.loads(raw)["long_url"]}
    db.execute("INSERT INTO links VALUES (?, ?, ?)", (code, body["long_url"], owner))
    db.execute("INSERT INTO idempotency_keys VALUES (?, ?, ?, 201, ?)", (owner, key, req_hash, json.dumps(body)))
    db.execute("COMMIT")               # ссылка и ключ фиксируются вместе
    return 201, body, "application/json", False


class Handler(BaseHTTPRequestHandler):
    def do_POST(self):
        raw = self.rfile.read(int(self.headers.get("Content-Length", 0)))
        key = self.headers.get("Idempotency-Key")
        if self.path != "/api/v1/links":
            result = problem(404, "Not Found", self.path)
        elif not key:
            result = problem(400, "Idempotency-Key required", "добавь заголовок Idempotency-Key")
        else:
            result = create_link(1, key, raw)   # owner_id = 1: аутентификацию пропускаем
        status, body, ctype = result[:3]
        out = (json.dumps(body, ensure_ascii=False) + "\n").encode()
        self.send_response(status)
        self.send_header("Content-Type", ctype)
        if len(result) > 3 and result[3]:
            self.send_header("Idempotency-Replayed", "true")
        self.send_header("Content-Length", str(len(out)))
        self.end_headers()
        self.wfile.write(out)

    def log_message(self, *args):
        pass


ThreadingHTTPServer(("127.0.0.1", 8000), Handler).serve_forever()
```

Объясни результаты. Что изменится, если вставлять ключ и ссылку в двух разных транзакциях? Как
перенести схему на PostgreSQL?

<details><summary>Ответ</summary>

Первый запрос — `201`, повтор — тот же `code` с `Idempotency-Replayed: true`, другое тело — `422`
(Problem Details). 20 параллельных запросов k6 дают один `code` и одну строку в `links`: остальные ждут
транзакцию первого и читают её итог. Если ключ и ссылку писать в разных транзакциях, между ними можно
упасть: ссылка есть, а ключа нет, и повтор создаст дубль; либо наоборот. В PostgreSQL:
`INSERT … ON CONFLICT (owner_id, key) DO NOTHING`, затем работа и `UPDATE` ответа в той же транзакции (раздел 5); параллельный
дубль на `INSERT` ждёт первую транзакцию. Дополнительно — чистка ключей старше суток.

</details>

```bash
EXPLAIN (ANALYZE, BUFFERS)

ORDER BY created_at DESC, code DESC LIMIT 50 OFFSET 90000;

-- 2) keyset: курсор — последняя строка предыдущей страницы
SELECT created_at AS c_at, code AS c_code FROM links
WHERE owner_id = 1 ORDER BY created_at DESC, code DESC OFFSET 89999 LIMIT 1 \gset
EXPLAIN (ANALYZE, BUFFERS)
SELECT code FROM links WHERE owner_id = 1 AND (created_at, code) < (:'c_at', :'c_code')
ORDER BY created_at DESC, code DESC LIMIT 50;
SQL
docker rm -f pg
```

Сравни время выполнения и число строк, которые читает каждый план. Что будет, если удалить колонку
`code` из индекса и из сортировки?

<details><summary>Ответ</summary>

В плане OFFSET видно чтение и сортировку около 90 050 строк (у нас — десятки миллисекунд), в плане keyset —
`Index Cond` по `ROW(created_at, code) < ROW(…)` и 50 строк (доли миллисекунды); числа зависят от
железа, соотношение — нет. Если убрать `code`, при одинаковом `created_at` порядок строк между страницами
не определён: появятся дубли и пропуски — поэтому нужен tie-breaker. Следующий шаг — отдать клиенту курсор
в виде `encode_cursor(created_at, code)` (раздел 4).

</details>

#### C3. SSE через nginx: буферизация и idle timeout

```python
# sse.py — тик каждые gap секунд; ?hb=1 — между тиками шлём heartbeat-комментарий каждую секунду
import time
from http.server import BaseHTTPRequestHandler, ThreadingHTTPServer
from urllib.parse import parse_qs, urlparse


class Handler(BaseHTTPRequestHandler):
    def do_GET(self):
        q = parse_qs(urlparse(self.path).query)
        gap, hb = int(q.get("gap", ["2"])[0]), "hb" in q
        self.send_response(200)
        self.send_header("Content-Type", "text/event-stream")
        self.send_header("Cache-Control", "no-cache")
        self.end_headers()
        try:
            for i in range(1, 9):
                self.wfile.write(f"id: {i}\ndata: tick {i}\n\n".encode())
                self.wfile.flush()
                for _ in range(gap):
                    time.sleep(1)
                    if hb:
                        self.wfile.write(b": ping\n\n")      # комментарий SSE: клиент его игнорирует
                        self.wfile.flush()
        except (BrokenPipeError, ConnectionResetError):
            pass

    def log_message(self, *args):
        pass


ThreadingHTTPServer(("127.0.0.1", 8000), Handler).serve_forever()
```

```nginx
# nginx/default.conf
server {
    listen 8082;
    location / {
        proxy_pass http://127.0.0.1:8000;
        proxy_http_version 1.1;
        proxy_set_header Connection "";
        proxy_read_timeout 5s;      # 5 секунд тишины от бэкенда — nginx закроет соединение
        # proxy_buffering off;      # раскомментируй и перезагрузи nginx
    }
}
```

```bash
python3 sse.py &
docker run -d --rm --name sse-nginx --network host -v "$PWD/nginx:/etc/nginx/conf.d:ro" nginx:1.27-alpine
curl -N localhost:8082/                      # буфер включён: что видишь? (Ctrl+C через 10 секунд)
# раскомментируй proxy_buffering off, затем: docker exec sse-nginx nginx -s reload
curl -N localhost:8082/                      # события идут каждые 2 секунды
curl -N "localhost:8082/?gap=8"              # пауза 8 с > proxy_read_timeout: что происходит?
curl -N "localhost:8082/?gap=8&hb=1"         # то же с heartbeat
docker rm -f sse-nginx
```

<details><summary>Ответ</summary>

С буфером (по умолчанию) nginx копит ответ, пока не наполнится буфер или не закончится поток, и
`curl` ничего не показывает. С `proxy_buffering off` события идут сразу; то же делает заголовок `X-Accel-Buffering: no`
из приложения. При паузе 8 с nginx через 5 с тишины закрывает соединение (`curl` завершается с
кодом 18) — это idle timeout, тот же, что у WebSocket и gRPC-стримов за LB. Heartbeat-комментарий
каждую секунду держит соединение живым: интервал heartbeat меньше таймаута простоя на всех звеньях.

</details>

#### C4. Подпись вебхука

Реализуй подпись `HMAC-SHA256(timestamp.body)` и проверку с окном ±5 минут.

```python
import hashlib
import hmac
import time

SECRET = b"whsec_demo"


def sign(body: bytes, ts: int) -> str:
    return "sha256=" + hmac.new(SECRET, f"{ts}.".encode() + body, hashlib.sha256).hexdigest()


def verify(body: bytes, ts: int, signature: str, now: int, tolerance: int = 300) -> bool:
    if abs(now - ts) > tolerance:                          # защита от повторной отправки старого запроса
        return False
    return hmac.compare_digest(sign(body, ts), signature)  # сравнение за постоянное время


body = b'{"event":"link.blocked","code":"aZ3x9Qk"}'
now = int(time.time())
sig = sign(body, now)
print(verify(body, now, sig, now))          # True
print(verify(body + b" ", now, sig, now))   # ?
print(verify(body, now, sig, now + 3600))   # ?
```

Что вернут два последних вызова и зачем `compare_digest`? Чего не хватает для дедупликации у получателя?

<details><summary>Ответ</summary>

Оба `False`: тело изменено, подпись не сходится; запрос старше 5 минут отклонён как возможный replay.
`compare_digest` сравнивает за постоянное время, а обычное `==` позволяет подбирать подпись по времени
ответа. Для дедупликации нужен `event_id` в событии и таблица обработанных `event_id` у получателя, потому
что доставка — at-least-once.

</details>

### Блок D. Инциденты

**D1.** После сетевого сбоя у клиентов-партнёров появились дубликаты ссылок: у одного партнёра по две
одинаковые ссылки на каждую операцию из последнего часа.

<details><summary>Ответ</summary>

Клиентские ретраи при таймаутах без ключа идемпотентности: ответ потерялся, повтор создал вторую ссылку.
Сейчас: найти и объединить дубли (по `owner_id` и `long_url` за период). Потом: `Idempotency-Key` в
контракте, хранилище ключей, метрика доли повторов, ретраи в SDK только с ключом.

</details>

**D2.** Сервис на gRPC масштабировали с 10 до 20 подов под нагрузку, но старые поды на 100% CPU, новые
почти пусты, p99 растёт.

<details><summary>Ответ</summary>

Балансировка по соединениям (L4 или ClusterIP): клиенты держат долгие HTTP/2-соединения, открытые до
scale-up. Сейчас: перезапустить клиентов или ограничить возраст соединения. Потом: L7 или
клиентская балансировка (headless Service + `round_robin`), `MAX_CONNECTION_AGE` с grace, метрика
запросов по подам.

</details>

**D3.** После каждого деплоя сервиса с WebSocket CPU TLS уходит в 100%, p99 других API растёт, часть
клиентов подключается минутами.

<details><summary>Ответ</summary>

Reconnect storm: узел с 50 000 соединений перезапускается, и все клиенты возвращаются разом. Сейчас:
вернуть узел и сливать соединения постепенно. Потом: поэтапный drain (X% в секунду), jitter и
экспоненциальная пауза в клиенте, лимит новых соединений на LB, больше запас по CPU, resume по
номеру сообщения без полной ресинхронизации.

</details>

**D4.** Сервис B на секунду замедлился, и через минуту он лёг совсем: клиент A ретраит 3 раза, gateway
ретраит ещё 3 раза.

<details><summary>Ответ</summary>

Retry storm: до 9 запросов на один клиентский добивают B. Сейчас: сбросить лишнюю нагрузку (лимит или
503 на входе), временно отключить ретраи. Потом: ретраи в одном слое, бюджет, backoff с jitter,
дедлайн по цепочке, circuit breaker, `Retry-After`.

</details>

### Блок E. Вопросы с собеседования

**1.** Как выбрать между REST, gRPC и GraphQL?

<details><summary>Ответ</summary>

По потребителю: внешним клиентам и браузерам — REST; внутренним вызовам с высокой нагрузкой и стримингом — gRPC;
разным клиентам с разными данными — GraphQL (или BFF). У каждого своя цена: кеш и over-fetching у REST,
перекос на L4 у gRPC, N+1 и стоимость запросов у GraphQL.

</details>

**2.** Как сделать POST идемпотентным и где хранить ключи?

<details><summary>Ответ</summary>

`Idempotency-Key` от клиента; сервер хранит `(owner_id, key, request_hash, ответ)` сутки. В той же БД и
транзакции, что и бизнес-запись; параллельный дубль ждёт или получает `409`. Redis — как ускоритель, но не
источник правды: он не атомарен с бизнес-записью.

</details>

**3.** Как спроектировать пагинацию для списка на миллиард записей?

<details><summary>Ответ</summary>

Keyset: индекс `(owner_id, created_at DESC, code DESC)`, условие по последней строке, `limit + 1` для
`has_more`, непрозрачный курсор с версией, максимум `limit`, без `total`. Права — из токена.

</details>

**4.** Как вести версионирование и отключение старых версий?

<details><summary>Ответ</summary>

Major в пути, внутри — только совместимые изменения; breaking changes ловит CI. Отключение:
deprecation с датой (`Deprecation`, `Sunset`), телеметрия клиентов, письма, brownout, политика срока
поддержки.

</details>

**5.** Как масштабировать WebSocket до миллиона соединений?

<details><summary>Ответ</summary>

Считать память (десятки КБ на соединение), делить по узлам (~50 000), масштабировать по числу
соединений, держать брокер для рассылки между узлами, heartbeat и idle timeout, порты proxy → backend, плавный
drain и reconnect с jitter, состояние — во внешнем хранилище.

</details>

**6.** Как обеспечить надёжность вызовов между сервисами?

<details><summary>Ответ</summary>

Таймаут и дедлайн на каждом вызове с убывающим бюджетом, ретраи только для идемпотентных операций и в одном
слое, паузы с jitter и бюджет ретраев, circuit breaker, bulkhead, деградация, `Retry-After`.

</details>

**7.** Что такое N+1 в GraphQL и как ограничить стоимость запросов?

<details><summary>Ответ</summary>

Запрос на каждый элемент списка; лечит DataLoader (один запрос на пачку). Стоимость ограничивают глубиной,
сложностью, потолком списков, таймаутом, persisted queries и лимитами по стоимости.

</details>

**8.** Как проверить, что релиз не ломает клиентов?

<details><summary>Ответ</summary>

Сравнение контракта (OpenAPI, proto) с версией из `main` в CI, contract tests потребителей (consumer-driven)
и проверка провайдера по схеме, canary с метриками ошибок по клиентам и версиям, поддержка двух поколений
(N и N+1) при rolling update.

</details>
