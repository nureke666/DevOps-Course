## 1. Путь запроса: от клиента до сервиса

У каждого звена своя работа, свой отказ и свои таймауты:

| Звено | Что делает | Что может ответить само | Как выглядит отказ |
|-------|-----------|--------------------------|--------------------|
| DNS | Имя → IP | — | Клиент не нашёл хост: соединения нет вообще |
| CDN / edge | TLS рядом с клиентом, кеш, WAF, защита от DDoS, сжатие | Ответ из кеша, блокировку, редирект | 5xx от edge, таймауты до origin |
| Балансировщик | Раздаёт соединения или запросы по инстансам | `503`, когда нет здоровых | 502 / 503 / 504 |
| API gateway / ingress | Аутентификация, лимиты, маршруты по host и path | 401, 403, 404, 429 | Ошибки 4xx для всех клиентов сразу |
| Сервис | Бизнес-логика | Любой код | 5xx |

Каждое звено — это задержка, точка отказа и ещё один набор таймаутов. Ставь то, что нужно по
требованиям: у MVP это DNS → облачный L7 → приложение, у публичного сервиса добавляются CDN и
ingress, у платформы с внешними клиентами API — gateway, у десятков сервисов — mesh, у пользователей
на нескольких континентах — GeoDNS или anycast.

### Сколько стоит дальний путь

Скорость света в оптоволокне — около 200 км за миллисекунду: клиент за 10 000 км получает минимум
~100 мс RTT. А новое соединение — это несколько RTT до первого байта:

```text:no-line-numbers
Клиент далеко от origin (RTT 100 мс), соединение новое, TLS 1.3:
  TCP-рукопожатие 1 RTT + TLS 1.3 1 RTT + запрос→ответ 1 RTT ≈ 300 мс   (TLS 1.2 — ещё +1 RTT)
  плюс DNS на холодном кеше: десятки мс

Клиент у edge (RTT 10 мс), ответ из кеша edge:
  3 RTT × 10 мс ≈ 30 мс, origin не участвует
  промах: + запрос edge → origin по уже открытому соединению, ещё 1 RTT до origin
```

HTTP/3 (QUIC) объединяет транспортное и TLS-рукопожатие и экономит один RTT. Вывод: ⭐ **edge
рядом с пользователем выигрывает дважды** — короткие рукопожатия идут с ним, а до origin edge
держит тёплые долгоживущие соединения.

### linkd на этой схеме

```text:no-line-numbers
 браузер ─► DNS lnk.example (ALIAS → CDN)
         ─► CDN: TLS, WAF, кеш 302 на s-maxage=60 ─────── часть кликов заканчивается здесь*
         ─► L7-балансировщик (3 AZ) ─► redirect-сервис (~30 подов, по 10 в AZ) ─► Redis ─► PostgreSQL
 клиент API ─► DNS api.lnk.example ─► API gateway (ключ, лимит) ─► api-сервис ─► PostgreSQL primary

 * доля попаданий — допущение, меряй (раздел 3)
```

Redirect идёт **мимо** gateway: аутентификации у него нет, а каждое лишнее звено на горячем пути
(20 000 RPS в пике) — это задержка и ещё один компонент в SLO 99,95%.

## 2. DNS в system design

DNS отдаёт имя → набор IP. В дизайне он нужен для трёх вещей: **точка входа** (имя → edge),
**грубая маршрутизация** (по гео, весу, здоровью) и **service discovery** в кластере. Про сам
резолв и записи — [Сети: 05. DNS](/network/05-dns); здесь только решения.

> ⭐ DNS кеширует всё: резолвер провайдера, ОС, браузер, HTTP-клиент в процессе. Ответ нельзя
> отозвать — только ждать конца TTL, и то не у всех.

### TTL: быстрая смена против дешёвой работы

| TTL | Плюсы | Минусы | Для чего |
|-----|-------|--------|----------|
| 30–60 с | Быстрые failover и перенос трафика | Больше запросов к DNS (платишь и грузишь серверы зоны), чаще холодный резолв, сильнее зависишь от DNS | Записи в failover, ALIAS на CDN и LB |
| 5–15 мин | Компромисс | Ошибку в записи исправляешь минуты | Обычные записи сервисов |
| 1–24 ч | Дёшево, почти не зависишь от DNS «в моменте» | Меняешь медленно, ошибки живут часами | NS, MX, TXT |

**Правило миграции.** TTL — срок годности уже розданных ответов, значит, ждать нужно **старый**
TTL: за сутки до переезда понизь его, переключи, проверь, верни.

⚠️ Не все уважают TTL: часть резолверов держит запись дольше, долгоживущие соединения и пулы не
перерезолвят адрес, рантаймы кешируют DNS по своим правилам (проверь настройки своего
HTTP-клиента). «Failover за 60 секунд» — это «за 60 с для большинства и хвост на минуты».

### Политики маршрутизации

| Политика | Как работает | Для чего | Ограничение |
|----------|--------------|----------|-------------|
| Weighted | Доля ответов по весам | Миграция 1% → 10% → 100% | Доля ответов ≠ доля запросов: за резолвером тысячи пользователей |
| Latency-based | Регион с лучшей измеренной задержкой | Мультирегион | Измерения от резолвера, не от клиента |
| Geolocation / GeoDNS | По стране или континенту | Законы о данных, региональные версии | Базы геолокации ошибаются, VPN |
| Failover | Primary, пока здоров; иначе secondary | Active–passive между регионами | TTL и кеши клиентов |

**Откуда GeoDNS знает клиента.** Сервер зоны видит IP **резолвера**, а не пользователя. EDNS Client
Subnet передаёт часть адреса клиента, но отправляют его не все резолверы. Итог — «примерно верный
континент», а не «точный дата-центр».

### DNS failover и его пределы

```text:no-line-numbers
время до переключения ≈ обнаружение + TTL + хвост «не уважающих» TTL
  проверки каждые 10 с, порог 3 неудачи   30 с
  TTL записи                              60 с
  для большинства клиентов                ~1,5–2 мин,  для части — минуты и больше
```

DNS failover годится для **потери региона**, где важны минуты. Для отказа пода он не годится — это
работа балансировщика (секунды). Проба провайдера идёт из его точек: проверяй путь, близкий к
пользовательскому, а не `/healthz`. Если все пулы нездоровы, многие провайдеры отдают все записи
сразу (fail-open).

### Anycast

Один IP анонсируется по BGP из многих точек, сеть доставляет пакеты в «ближайшую» по BGP-метрике
(не всегда географически). Упала точка — снимается анонс, трафик уходит в соседнюю за секунды,
**без ожидания TTL**. Так работают CDN, публичные DNS (1.1.1.1, 8.8.8.8) и глобальные
балансировщики облаков.

| | GeoDNS / latency-based | Anycast |
|---|------------------------|---------|
| Где решение | В ответе DNS | В маршрутизации сети |
| Failover | TTL + кеши: минуты | Секунды–десятки секунд |
| DDoS | Не помогает | Атака рассеивается по точкам |
| Минусы | Кеши, ошибки гео | Нужен свой ASN или готовый продукт; при смене маршрута может порваться долгое соединение |

### В проде

- ⚠️ **DNS-провайдер — зависимость, которую не починишь сам** (известный пример — атака на Dyn в
  2016 году). Для критичного домена — второй провайдер, зона хранится как код (Terraform,
  octoDNS) и синхронизируется в оба.
- **Регистратор — часть периметра:** 2FA, registry lock, контакты владельца. Угон домена хуже
  любого отказа. **Висячие CNAME** на удалённые облачные ресурсы дают subdomain takeover.
- **Apex-домен** нельзя сделать CNAME: для `lnk.example` нужен ALIAS/ANAME или CNAME flattening
  у провайдера.

## 3. CDN

**CDN** — сеть точек присутствия (PoP) по миру. Запрос приходит в ближайшую точку (anycast или
GeoDNS), которая отвечает из кеша или идёт к **origin** — твоим серверам.

```text:no-line-numbers
 пользователь ─► PoP (edge) ─┬─ ключ в кеше, свежий ─► ответ (HIT)                10–30 мс
                             └─ промах ─► [origin shield — региональный кеш] ─► origin (наши поды)
                                              один запрос вместо сотен
```

### Статика и динамика

| Контент | Пример | Кеш | Как |
|---------|--------|-----|-----|
| Неизменяемая статика | `app.4f9a1c.js`, картинки с хешем в имени | Навсегда | `Cache-Control: public, max-age=31536000, immutable` |
| Редко меняющееся | `index.html`, логотип | Минуты–часы | Короткий TTL + `ETag`, purge при выкладке |
| Публичные GET API | Каталог, редирект linkd | Секунды–минуты | `s-maxage=N`, `stale-while-revalidate` |
| Персональные ответы | Список ссылок владельца, профиль | Нет | `private` или `no-store` |
| Записи | POST, PUT, DELETE | Нет | Проксируются на origin |

**Динамика ускоряется и без кеша**: TLS заканчивается рядом с клиентом, до origin идёт тёплое
соединение из пула, клиенту отдаётся HTTP/2 или HTTP/3, ответ сжимается. По расчёту из раздела 1
это сотни миллисекунд для дальних клиентов.

### Cache-Control: что и кому говорим

Заголовки подробно — [Сети: 06. HTTP](/network/06-http), раздел про кеширование. Для дизайна нужно:

| Директива | Смысл |
|-----------|-------|
| `max-age=N` | Ответ свежий N секунд, для всех кешей |
| `s-maxage=N` | Свой TTL только для общих кешей (CDN), перекрывает `max-age` |
| `private` / `public` | `private`: только кеш браузера, CDN не хранит |
| `no-cache` | Хранить можно, но перед использованием — спросить origin. **Не** «не кешируй» |
| `no-store` | Не хранить нигде |
| `stale-while-revalidate=N`, `stale-if-error=N` | RFC 5861: отдавать устаревшее и обновлять в фоне / отдавать устаревшее, пока origin болен |
| `immutable` | RFC 8246: до истечения не ревалидировать |
| `Vary: Accept-Encoding` | Ответ зависит от заголовка, он входит в ключ кеша |

Для настроек именно CDN есть `CDN-Cache-Control` (RFC 9213) и провайдерские аналоги; поддержка
разная — смотри документацию.

### Cache key: от него зависит hit ratio

Ключ по умолчанию — схема, хост, путь и query. Лишнее в ключе плодит копии одного ответа:
`?utm_source=tg` и `?fbclid=…` дают отдельную запись на каждую метку; `Vary: Cookie` или
`Vary: User-Agent` — копию на пользователя или браузер (hit ratio около нуля); `?a=1&b=2` и
`?b=2&a=1` — две записи. Лечится **нормализацией**: убрать трекинговые параметры, отсортировать
остальные, в `Vary` оставить `Accept-Encoding`. Эффект видно в лабе C1.

### Hit ratio в числах

Нагрузка на origin = `RPS × (1 − hit ratio)`. Для пика linkd 20 000 RPS: при 50% — 10 000 RPS,
при 80% — 4 000, при 95% — 1 000, при 99% — 200.

Для статики 95%+ — норма. Для редиректов linkd **заранее неизвестно**: 6 млрд ссылок, у большинства
единицы кликов, а кеш каждой точки свой и холодный. Вирусные ссылки кешируются отлично, длинный
хвост — нет. Меряй hit ratio отдельно **по запросам** и **по байтам**.

⚠️ Origin должен выдержать пик и **без CDN** — или нужна заранее понятная деградация (лимиты,
статическая страница). Иначе отказ CDN превращается в отказ всего сервиса.

### Purge и инвалидация

| Способ | Для чего | Цена |
|--------|----------|------|
| Версия в URL | Статика | Ничего: новый URL — новый кеш |
| Purge по URL или тегу (surrogate key) | Срочно убрать объект или группу | Доезжает за секунды–минуты, у API есть лимиты |
| Purge всего | Крайний случай | ⚠️ Холодный кеш: весь трафик сразу на origin |

⭐ Для динамики не строй всё на purge: выбери TTL, при котором худший случай **приемлем сам по
себе**, а purge оставь для срочного. У linkd заблокированная ссылка исчезнет примерно за полторы минуты:
до 60 с в CDN (`s-maxage=60`) плюс TTL L1-кеша в подах (до 30 с), а для фишинга ещё вызывается purge по URL.

### Origin shield и схлопывание запросов

Без shield каждая из сотен точек при промахе идёт к origin: холодный объект даёт сотню одинаковых
запросов. **Origin shield** — региональная точка между edge и origin: промахи идут к ней, и на
origin уходит один запрос. Цена — лишний переход на промахе и иногда отдельная плата. Кроме того,
CDN **схлопывают** одновременные промахи одного ключа в один запрос (в nginx это
`proxy_cache_lock`, лаба C1).

### Что НЕ кешировать

| Что | Почему |
|-----|--------|
| Ответы с персональными данными (`Authorization`, cookie сессии) | Один пользователь получит чужой ответ |
| Ответы с `Set-Cookie` | У разных CDN умолчания разные; не полагайся на них |
| Ответы 5xx | Закешируешь сбой на весь TTL (максимум секунды) |
| `404` для кодов, которые могут появиться | Новая ссылка «залипнет» в 404: у linkd `no-store` или ≤ 5–10 с |
| Одноразовые и подписанные URL | Подпись раздувает ключ; для приватного контента — signed URL/cookie самого CDN |

Две атаки на кеш ([Безопасность: 03](/security/03-web-edge-security)): **cache poisoning** — заголовок
влияет на ответ, но не входит в ключ (например, `X-Forwarded-Host`), и в кеш кладут вредный
ответ; **web cache deception** — жертву заставляют открыть `/account/photo.css`, и CDN кеширует
личную страницу как «статику».

### Edge compute — коротко

Код на edge (Workers, Lambda@Edge и аналоги): редиректы, A/B, проверка токена, переписывание
заголовков. Ограничения: миллисекунды CPU, данные далеко, отладка, привязка к вендору. Для linkd
соблазн — держать таблицу ссылок на edge, но это репликация с задержкой и проблемы с блокировкой
фишинга: логику оставляем на origin.

### linkd: 302 за CDN

```http
HTTP/1.1 302 Found
Location: https://shop.example/catalog?utm_source=tg
Cache-Control: max-age=0, s-maxage=60
```

- Браузер не использует ответ повторно (`max-age=0`), CDN держит минуту (`s-maxage=60`).
  Вирусная ссылка на 50 000 RPS даст origin не больше нескольких запросов в минуту на точку.
- ⚠️ 302 без явных заголовков не считается кешируемым, а многие CDN кешируют не все статусы —
  проверь правила провайдера.
- ⭐ **Клики, отданные CDN, до linkd не доходят.** Статистика недосчитается, пока в аналитику не
  грузятся **логи CDN** (стриминг в Kafka). Объём сопоставим с сырыми кликами — десятки ГБ в сутки
  (в [Бэкенд-задаче 01](/system-design/backend-cases/01-url-shortener) — около 70 ГБ). Альтернатива —
  не кешировать, но тогда весь пик идёт на origin.
- Решение «кеш на CDN» фиксируется в ADR с ценой: клики из логов CDN, блокировка через purge
  ([Бэкенд-задача 01](/system-design/backend-cases/01-url-shortener), раздел 6.2).

## 4. L4 и L7 балансировщики

```text:no-line-numbers
 L4:  клиент ══ TCP ═══► [LB: видит IP и порт] ═══ TCP ═══► под      соединение передано целиком
 L7:  клиент ══ TLS ═══► [LB: читает метод, host, path, заголовки] ══ новое соединение ══► под
```

| | L4 (транспортный) | L7 (прикладной) |
|---|-------------------|-----------------|
| Что видит | IP, порты, TCP/UDP | HTTP: host, path, заголовки, куки |
| Балансирует | **Соединения** | **Запросы** |
| TLS | Пропускает насквозь или терминирует | Терминирует и может перешифровать |
| Маршрутизация | По порту | По host, path, заголовку, весу |
| Возможности | Быстро и дёшево, любой TCP: PostgreSQL, MQTT | Ретраи, лимиты, редиректы, сжатие, WAF, canary |
| Цена | Минимум | CPU на разбор, два соединения вместо одного |
| Примеры | Облачные L4 (класс NLB), HAProxy `mode tcp`, nginx `stream` | Облачные L7 (класс ALB), nginx, HAProxy, Envoy, ingress |

Устройство — [Сети: 13. HAProxy и балансировка](/network/13-haproxy-balancing),
[Сети: 12. Nginx](/network/12-nginx), [Сети: 18. Современные прокси](/network/18-modern-proxies).

```nginx
# L4: nginx stream не читает HTTP — просто разносит TCP (например, на PgBouncer)
stream {
    upstream pgbouncer { least_conn; server 10.0.1.11:6432; server 10.0.1.12:6432; }
    server { listen 5432; proxy_pass pgbouncer; }
}
```

> ⭐ L4 балансирует **соединения**, а не запросы: клиент с долгим HTTP/2-соединением (gRPC)
> целиком уходит на один под. Разбор и решения — в
> [теме 02](/system-design/building-blocks/02-api-design).

**TLS: где кончается шифрование.** Termination на LB или CDN — проще всего, сертификаты в одном
месте, дальше обычный HTTP внутри сети. Passthrough (L4) — сквозное шифрование. Re-encrypt/mTLS —
если нужно шифрование внутри периметра. Сертификаты выпускаются и продлеваются автоматически
(ACME), а **срок их жизни — метрика**: протухший сертификат на edge роняет сервис разом.

**IP клиента за прокси** передают `X-Forwarded-For` (или `Forwarded`), между L4 и L7 — PROXY
protocol. Верить можно только своим звеньям:

```nginx
set_real_ip_from 10.0.0.0/8;       # доверяем только своим балансировщикам
real_ip_header   X-Forwarded-For;
real_ip_recursive on;              # берём первый адрес не из доверенных сетей
```

⚠️ Если брать `X-Forwarded-For` как есть, клиент подставит любой IP и обойдёт лимиты. Часто
ставят обе схемы: **L4 с постоянными адресами впереди** (anycast, DDoS) и **флот L7-прокси** за ним.

## 5. Алгоритмы балансировки, health checks и draining

### Алгоритмы

| Алгоритм | Как выбирает | Подходит | Слабое место |
|----------|--------------|----------|--------------|
| Round robin (с весами) | По кругу | Однородные короткие запросы; веса — для canary | Не видит, что под занят долгими запросами |
| Least connections / least request | Тот, у кого меньше активных | Запросы разной длины | Свежий под с нулём соединений получает всё сразу |
| Power of two choices | Два случайных, из них менее загруженный | Много балансировщиков без общего состояния | Нужны счётчики нагрузки |
| Hash по ключу (IP, URI, заголовок) | Один ключ — один под | Кеши на подах, сессии | Горячий ключ перегружает один под |
| EWMA по задержке | Предпочитает быстрых | Разная скорость подов | Сложнее отлаживать |

**Consistent hashing** меняет владельца лишь у ~1/N ключей при добавлении или удалении узла (при
`hash % N` — почти у всех). Теория — [Распределённые системы: 03. Репликация и шардирование](/distributed/03-replication-partitioning),
цифры — в лабе C2.

⭐ **Выбор для linkd.** Хеш по коду дал бы локальность L1-кеша, но вирусная ссылка на 50 000 RPS
целиком упала бы на один под. Поэтому для redirect — least request, а горячие ключи берут на себя
L1 в каждом поде и CDN.

**Sticky sessions** (по cookie или IP) нужны, когда состояние в памяти пода: WebSocket, старые
сессии. Цена: перекос нагрузки, потеря сессий при падении, сложный drain. Лучше stateless и сессии
во внешнем хранилище.

### Health checks

| | Active | Passive (outlier detection) |
|---|--------|-----------------------------|
| Как | LB сам шлёт пробы раз в N секунд | LB наблюдает за реальными ответами: подряд 5xx или таймауты → выкинуть |
| Плюс | Находит падение до трафика | Реагирует на то, что видят пользователи |
| Минус | Проба «здорова», а запросы нет; нагрузка от проб | Нужен трафик, чтобы заметить |
| Пример | HAProxy `check`, target groups облака | nginx `max_fails`, Envoy outlier detection |

Используют вместе. Нюансы:

- **Время обнаружения** = интервал × порог (2 с × 2 = 4 с): пока идёт, запросы летят в мёртвый под.
  Ретраи на LB прикрывают пробел. Порог возврата (`rise`) выше порога выброса, иначе под «мигает».
- **Что проверять.** Для LB достаточно «процесс может принять запрос». Проверка общей БД в
  readiness выбрасывает **все** поды сразу — разбор в
  [Бэкенд-задаче 01](/system-design/backend-cases/01-url-shortener), раздел 8.1. В linkd 2.0
  `/readyz` проверяет базу, а `/healthz` нет: для redirect-сервиса под LB нужен второй.
- **Panic mode.** Когда здоровых подов слишком мало, часть балансировщиков (Envoy — по умолчанию
  при 50%) возвращает в ротацию всех, лишь бы не отдавать 503.

### Connection draining, slow start и ретраи

Под удаляют из ротации не мгновенно: LB узнаёт об этом с задержкой, а запросы, уже выбравшие
под, ещё летят. Порядок остановки:

```text:no-line-numbers
 1. под помечен на удаление → убирается из endpoints, readiness = false
 2. пауза (preStop sleep), пока LB и ingress узнают    ← иначе запросы идут в закрывающийся под
 3. SIGTERM: перестать принимать, дождаться текущих запросов, закрыть idle-соединения
 4. по terminationGracePeriodSeconds — SIGKILL
```

```yaml
spec:
  terminationGracePeriodSeconds: 40
  containers:
    - name: redirect
      lifecycle:
        preStop:
          exec: {command: ["sleep", "10"]}   # нужен sleep в образе; в новых k8s есть встроенное действие
      readinessProbe:
        httpGet: {path: /healthz, port: 8080}
        periodSeconds: 2
        failureThreshold: 2
```

У облачных L7 есть свой **deregistration delay** — время ожидания перед удалением цели; у ряда
продуктов по умолчанию минуты, проверь. Про пробы — [Kubernetes: 09. Проверки (probes) и ресурсы](/kubernetes/09-probes-resources).

**Slow start.** Свежему поду нужен прогрев (JIT, кеши, пул соединений), и полная доля сразу
поднимает p99. Вес растёт от нуля за 30–60 секунд (у HAProxy `slowstart`, у Envoy есть slow start
mode, у nginx параметр только в коммерческой версии). Особенно важно при `least connections`: под
с нулём соединений «выглядит свободным».

**Ретраи и таймауты.**

- Ретрай — **только идемпотентные** запросы: nginx не повторяет POST на другой сервер, если запрос
  уже отправлен, пока явно не включён `non_idempotent`. Ограничивай попытки и общее время
  (`proxy_next_upstream_tries`, `proxy_next_upstream_timeout`), иначе сбой превращается в шторм
  ([SRE: 06. Паттерны надёжности](/sre/06-reliability-patterns)).
- ⚠️ **Гонка keep-alive.** Если бэкенд закрывает простаивающее соединение раньше LB, LB иногда
  пишет в закрытое и получает 502. Правило: **тот, кто переиспользует соединение (LB), закрывает
  простаивающее раньше сервера** — таймаут простоя на бэкенде больше, чем на LB.

## 6. Reverse proxy, ingress, API gateway и service mesh

Пять слов, которые путают. Разведи по тому, **чей трафик** и **какую задачу** решают:

| Что | Трафик | Что решает | Примеры |
|-----|--------|-----------|---------|
| Reverse proxy | Любой входящий | Принять соединение вместо бэкенда: TLS, кеш, сжатие, маршрутизация | nginx, HAProxy, Envoy, Caddy |
| Балансировщик | Входящий | Раздать нагрузку, убрать неживых | Облачные LB, HAProxy |
| Ingress | Внешний → в кластер (north–south) | L7-маршрутизация по host и path на Service | ingress-nginx, Traefik; преемник — Gateway API |
| API gateway | Внешние клиенты API | Ключи и токены, квоты, версии, преобразование, портал | Kong, Envoy Gateway, облачные API gateway |
| Service mesh | Между сервисами (east–west) | mTLS, ретраи, таймауты, canary, метрики без правок кода | Istio, Linkerd, Cilium |

```text:no-line-numbers
 клиент ─► CDN ─► L7 LB ─► [ingress / API gateway] ─► сервис A ◄── mesh: mTLS, ретраи ──► сервис B
   └────────── north–south (снаружи внутрь) ────────────┘      └──── east–west (между сервисами) ────┘
```

Подробности — [Kubernetes: 12. Ingress](/kubernetes/12-ingress) и
[Platform Engineering: 05. Gateway API и service mesh](/platform/05-gateway-mesh); сравнение
прокси — [Сети: 18. Современные прокси](/network/18-modern-proxies).

**Что делает API gateway:**

- **Аутентификация**: API-ключ или подпись JWT (подпись, срок, аудитория), личность — дальше
  заголовком. Сервисы всё равно не доверяют сети слепо: внутренний вход закрыт mTLS и сетевыми
  правилами, а авторизацию по объекту проверяет сервис.
- **Лимиты и квоты** по ключу и плану — алгоритмы в [теме 08](/system-design/building-blocks/08-rate-limiting).
- **Маршруты и версии**: `/v1/*` и `/v2/*` на разные Deployment, взвешенный canary.
- **Валидация** по схеме OpenAPI до того, как запрос дойдёт до кода.
- **BFF (Backend For Frontend)**: один эндпоинт под мобильный клиент собирает ответ из нескольких
  сервисов, чтобы клиент не делал пять походов.

**Антипаттерны:**

| Антипаттерн | Чем плохо |
|-------------|-----------|
| Бизнес-логика в gateway | Новый монолит, который выкатывает отдельная команда |
| Один gateway на 50 команд без владельцев | Все изменения идут через узкое горлышко и ломают друг друга |
| Gateway без HA | Одна точка отказа на всё: ≥ 3 реплики в разных AZ |
| Ретраи в клиенте, на LB, в gateway и в mesh | 3 × 3 × 3 × 3 = 81 запрос на один клиентский: шторм при сбое |
| Gateway на горячем пути без нужды | +1–5 мс и ещё один компонент в SLO |

⭐ **Ретраи — в одном слое**, обычно ближе к вызывающему сервису или в mesh; в остальных
выключены или ограничены. То же с таймаутами: один явный бюджет на запрос.

**Когда что брать.** Маленькая система — CDN + облачный L7 + ingress. Внешние клиенты API,
платные планы, много команд — API gateway. Десятки сервисов и требование mTLS всюду — mesh; сначала
проверь, хватит ли библиотек и ingress.

## 7. Глобальная балансировка и мультирегион на входе

Вход должен отправить пользователя в **нужный и живой** регион. Три способа:

| Способ | Как | Failover | Подходит |
|--------|-----|----------|----------|
| GeoDNS / latency-based | Ответ DNS зависит от клиента | Минуты (TTL, кеши) | Дёшево, грубо, нет жёстких требований к скорости |
| Anycast + глобальный LB | Один IP, трафик к ближайшему региону по сети | Секунды | Строгий SLO, готовый продукт облака |
| CDN с группой origin | CDN выбирает origin по гео или здоровью | Секунды–десятки секунд | Только HTTP, самый простой старт |

- **Запас мощности.** Если регион A упал, B принимает его трафик: в каждом регионе запас на
  соседа (N+1 по регионам), иначе упадут оба.
- **Холодный кеш.** Переехавший трафик приходит к пустым кешам и ломает origin: shield, прогрев,
  плавный перенос весами.
- **Данные важнее входа.** Вход направил клиента в регион B, а запись идёт в primary региона A —
  межрегиональная задержка на каждую запись. Мультирегион для данных, DR и согласованности — в блоке 4
  «Надёжность и эксплуатация».

linkd начинает с **одного региона и трёх AZ** плюс CDN: задержку закрывает CDN. Следующий шаг —
регионы на чтение (redirect + Redis + реплика) за GeoDNS или anycast, запись остаётся в основном.

## 8. linkd: собираем вход

| Звено | Решение | Почему |
|-------|---------|--------|
| DNS | `lnk.example` ALIAS на CDN, TTL 60 с; `api.lnk.example` на gateway, TTL 60 с; второй DNS-провайдер, зона в git | Failover записей нужен быстрый, остальное дёшево |
| CDN | 302 с `max-age=0, s-maxage=60`, нормализация query, `404` без кеша, origin shield, логи CDN → Kafka | Меньше origin и задержка; блокировка за ~1,5 мин (CDN + L1) + purge |
| Балансировщик | Облачный L7 в 3 AZ, least request, active + passive checks на `/healthz`, slow start 30 с, drain 10–30 с | Запросы короткие; быстрый вывод неживых |
| Gateway | Только `/api/v1/*`: ключ, лимит на создание (например, 100/мин на ключ) | Redirect идёт мимо: на звено меньше |
| Ingress | 3+ реплики по AZ, правила `/api/v1/*` и `/{code}` | Ingress — маршруты, gateway — политика |
| Сервисы | redirect: ~30 подов по 10 в AZ; api: 2–6 подов | Потеря AZ: 20 подов держат пик при 1 000 RPS на под (допущение задачи) |

Расчёт запаса при потере AZ — [Бэкенд-задача 01](/system-design/backend-cases/01-url-shortener),
раздел 2. С CDN запас шире, но проектируем **без него**: origin обязан пережить отказ CDN.

## 9. ⚙️ Эксплуатация

Семь вопросов из [Основы: 04. Бэкенд-собес и DevOps-собес](/system-design/basics/04-backend-vs-devops)
для входа в систему.

### 9.1 Развёртывание

- **Всё как код:** DNS-зона, правила CDN и WAF, балансировщик, маршруты — Terraform или octoDNS и
  ревью. Конфиг CDN применяется глобально за минуты: сначала staging-домен, потом часть трафика
  (весами DNS или по заголовку), потом полностью. До применения — `nginx -t`, линтеры, dry-run;
  откат — прошлая версия из git.
- **Ingress и gateway** — Deployment ≥ 3 реплик, `topologySpreadConstraints` по AZ, PDB, rolling
  update с draining и `preStop`, конфиг маршрутов через GitOps
  ([Kubernetes: 05. Deployment](/kubernetes/05-deployment)).
- **Миграция DNS:** TTL вниз за сутки, весами 1% → 10% → 100%, старое оставить до конца TTL.
- **Сертификаты:** выпуск и продление автоматические (ACME), ключи — в менеджере секретов.

### 9.2 Масштабирование

| Компонент | Масштабируется | Метрика | Потолок |
|-----------|---------------|---------|---------|
| CDN | Провайдером | Hit ratio, origin RPS | Origin при промахах и без CDN |
| Облачный LB | Сам, но постепенно | Новые и активные соединения | Скачок ×10 за минуты: заранее предупреди провайдера |
| Ingress / gateway | HPA | RPS и CPU на под | Файловые дескрипторы, порты |
| redirect-сервис | HPA | RPS на под | Соединения к БД и Redis |

⚠️ **Исчерпание портов.** Одна пара «IP LB → IP:порт бэкенда» даёт порядка 64 000 одновременных
соединений (эфемерные порты). Под NAT и для долгих соединений (WebSocket) это потолок: решается
числом адресов и бэкендов.

### 9.3 Наблюдаемость

- **SLI — на пользовательском краю:** доля успешных ответов и задержка **на CDN или LB**, а не
  пинг `/healthz`. SLO редиректа — 99,95% без 5xx и p99 ≤ 50 мс на сервере
  ([SRE: 02. SLI, SLO и error budget](/sre/02-sli-slo-error-budget)).
- **CDN:** hit ratio по запросам и по байтам, origin offload, 5xx от edge отдельно от 5xx origin.
- **LB:** активные и новые соединения, число здоровых целей, 4xx/5xx **от LB** и **от целей**:
  502 — бэкенд оборвал соединение, 503 — нет здоровых целей, 504 — таймаут бэкенда.
- **DNS и сертификаты:** синтетические проверки разрешения из нескольких регионов; дни до
  истечения сертификата и домена (blackbox exporter, `probe_ssl_earliest_cert_expiry`).
- **Трассировка:** `trace_id` создаётся на edge и идёт как `traceparent`, request id — в логах всех
  звеньев ([Мониторинг: 07. Что мониторить](/monitoring/07-what-to-monitor),
  [SRE: 03. Трейсинг и OpenTelemetry](/sre/03-tracing-opentelemetry)).
- **Алерты:** burn rate по SLO, падение hit ratio (ранний признак перегрузки origin), рост 502,
  сертификат < 14 дней.

### 9.4 Отказы

| Что упало | Что видит пользователь | Что делает система |
|-----------|-----------------------|--------------------|
| Под | Ничего | Active/passive check, ретрай идемпотентного запроса, ReplicaSet |
| AZ | Всплеск ошибок на секунды | LB уводит трафик в остальные AZ; запас мощности по AZ |
| Gateway | 5xx на `/api/*`, редиректы живы | ≥ 3 реплик по AZ; redirect идёт мимо gateway |
| Origin медленный | Растёт задержка | CDN отдаёт устаревшее (`stale-if-error`), лимиты на origin, быстрый 503 |
| CDN целиком | Ошибки или лавина на origin | Переключение DNS на прямой путь (origin держит пик, WAF и лимиты на LB) или второй CDN |
| DNS-провайдер | Новые клиенты не находят сервис | Второй провайдер, кеши резолверов держат ответ до TTL |
| Сертификат истёк | У всех ошибка TLS | Автопродление, алерт за 14/7/3 дня, процедура быстрого выпуска |
| Purge всего | Всплеск на origin | Shield, coalescing, прогрев, плавный перенос |

Общие принципы: таймаут на каждом звене, ретраи с jitter только для идемпотентных, ограничение
параллельности, деградация вместо падения
([Распределённые системы: 06. Режимы отказов](/distributed/06-failure-modes)).

### 9.5 Данные и DR

Слой входа почти stateless: «данные» здесь — **конфигурация, ключи и логи**.

- **Зона DNS, правила CDN и WAF, балансировщик, ingress** — в git и Terraform: пересоздаются за
  минуты. Учение: поднять вход с нуля в пустом аккаунте.
- **Сертификаты и ключи** — в менеджере секретов с резервным доступом. **Аккаунты регистратора и
  DNS-провайдера** защищены, есть резервные владельцы и registry lock; RTO смены DNS-провайдера =
  TTL + время синхронизации зоны.
- **Кеш CDN не бэкапят**: он пересоздаётся; вопрос — выдержит ли origin холодный старт.
- **Логи CDN** — источник истины для кликов linkd, отданных с edge: стримим в Kafka с retention;
  потеря = недосчитанная статистика, допустимый RPO — минуты.
- Нужен ли второй регион на входе — решают SLO и стоимость; полный DR — блок 4.

### 9.6 Безопасность

- **Защита origin.** ⭐ Origin принимает трафик **только от CDN**: allowlist адресов CDN, mTLS или
  секретный заголовок. Иначе атакующий обходит WAF и защиту от DDoS, обратившись к IP origin
  напрямую; этот IP не должен утекать через DNS-историю и заголовки.
- **TLS** 1.2+ (лучше 1.3), HSTS, автоматические сертификаты ([Сети: 07](/network/07-tls)).
- **DDoS и WAF** на edge: L3/L4 гасит anycast, L7 — лимиты и правила
  ([Безопасность: 03](/security/03-web-edge-security)); лимиты на API — в
  [теме 08](/system-design/building-blocks/08-rate-limiting). IP клиента — только из
  `X-Forwarded-For` своих прокси.
- **Gateway:** JWT и ключи проверяются на входе, авторизация по объекту — всё равно в сервисе.
- **Периметр сети:** сервисы доступны только с LB (security groups, NetworkPolicy), порты БД не
  торчат наружу ([Облака: 03. Сеть в облаке](/cloud/03-network-vpc)).
- **DNS и кеш:** registry lock, 2FA, зачистка висячих CNAME; не кешировать персональное, следить за
  cache key (poisoning, deception).

### 9.7 Стоимость

| Статья | Почему растёт | Рычаги |
|--------|---------------|--------|
| CDN | Платишь за гигабайты и за запросы (тариф уточняй) | Высокий hit ratio, сжатие, нормализация ключа |
| Трафик с origin | Промахи идут с origin | Origin shield, длиннее TTL, `stale-while-revalidate` |
| Логи CDN | Один запрос — одна строка, десятки ГБ в сутки у linkd | Убрать лишние поля, сжимать, сырьё хранить недолго |
| Балансировщик | Фиксированная часть + объём трафика и новые соединения | Keep-alive, общий ingress вместо LB на каждый сервис |
| Трафик между AZ | Межзональный часто платный | Осознанный выбор cross-zone балансировки |
| DNS | Платишь за запросы к зоне | TTL не ниже нужного |
| Второй DNS-провайдер или CDN | Двойной счёт и сложность | Только если SLO этого требует |

⭐ «CDN или больше подов» считается просто: гигабайты CDN против вычислений и трафика origin.
При hit ratio около 50% и ниже CDN может не окупаться деньгами — остаются задержка и защита.

## Грабли

| Грабля | Что не так | Правильно |
|--------|-----------|-----------|
| TTL 24 ч на записях, которые будешь менять | Миграция и failover идут сутки | 60–300 с на изменяемых, понижать заранее |
| DNS failover как «мгновенное» решение | Кеши и клиенты, игнорирующие TTL | Для региона минуты; для пода — балансировщик |
| `no-cache` считают «не кешировать» | Это «проверяй перед использованием» | `no-store` для запрета, `private` — для персонального |
| `utm_*` и `Vary: Cookie` в ключе кеша | Hit ratio падает, origin перегружен | Нормализуй ключ, в `Vary` только `Accept-Encoding` |

| `/readyz` с проверкой общей БД на LB | Падение БД выкидывает все поды | Readiness — «процесс готов», деградацию обрабатывает код |
| L4 для gRPC и долгих HTTP/2 | Нагрузка по соединениям, а не по запросам | L7 или балансировка на клиенте |
| `least_conn` без slow start | Новый под получает всё | Slow start 30–60 с |
| Ретраи в клиенте, LB, gateway и mesh | Умножение запросов, шторм | Ретрай в одном слое, бюджет |
| `purge all` на пике | Холодный кеш — лавина на origin | Purge по URL или тегу, shield, прогрев |

## 💼 Как это на работе

- **Бэкенд:** `Cache-Control` — часть контракта API, а не «настройка девопсов». Закладывай graceful
  shutdown и идемпотентность, чтобы ретраи на LB были безопасны.
- **DevOps:** держи вход как код и мониторь не только 5xx, но и hit ratio, срок сертификатов и
  здоровье DNS снаружи. На вопрос «что будет, если CDN упадёт?» нужен проверенный ответ.
- На ревью дизайна спросят: «где заканчивается TLS?», «кто ретраит?», «как узнаем, что origin

- Самое дорогое на входе — ошибки конфигурации: протухший сертификат, purge на пике, неверный

## 📌 Шпаргалка

| Хочу | Как |
|------|-----|
| Быстро сменить адрес | Понизить TTL заранее, ждать **старый** TTL |
| Failover между регионами | DNS failover (минуты) или anycast / глобальный LB (секунды) |
| Дальний пользователь | CDN: короткие рукопожатия у edge, тёплые соединения к origin |
| Кеш редиректа на CDN | `Cache-Control: max-age=0, s-maxage=60`, логи CDN в аналитику |
| Не плодить копии кеша | Нормализовать query, `Vary` только `Accept-Encoding` |
| Защитить origin | Принимать только от CDN: allowlist, mTLS, секретный заголовок |
| L4 или L7 | L4 — соединения и любой TCP; L7 — маршруты, ретраи, TLS |
| Запросы разной длины | `least request`, новым подам — slow start |
| Выкатка без 502 | readiness → `preStop sleep` → SIGTERM → дождаться запросов |
| Gateway или ingress | Ingress — маршруты в кластер; gateway — политика API |
| Ретраи | В одном слое, только идемпотентные, с бюджетом |

## 🧠 Что запомнить

1. Путь запроса: DNS → CDN → балансировщик → gateway/ingress → сервис; у каждого звена свой отказ и таймаут.
2. ⭐ Edge рядом с пользователем сокращает рукопожатия, даже когда кешировать нечего.
3. TTL — срок годности розданных ответов: меняешь адрес, жди **старый** TTL.
4. ⭐ DNS failover — минуты и хвост неуважающих TTL; пода он не спасает, это работа балансировщика.
5. ⭐ Cache key решает hit ratio: нормализуй query, держи `Vary` коротким.
6. Не кешируй персональное, 5xx и «ещё не созданное»; `no-cache` ≠ `no-store`.
7. ⭐ Origin принимает только CDN и выдерживает пик без него.
8. L4 балансирует соединения, L7 — запросы; для gRPC нужен L7 или балансировка на клиенте.
9. Health check, draining и slow start — без них выкатка даёт 502.
10. ⭐ Ретраи — в одном слое и только для идемпотентных.

### Блок A. Теория

**A1.** Назови путь запроса от клиента до сервиса и что делает каждое звено.

<details><summary>Ответ</summary>

DNS (имя → IP), CDN/edge (TLS, кеш, WAF, защита от DDoS), балансировщик (раздача по инстансам,
исключение неживых), gateway/ingress (аутентификация, лимиты, маршруты), сервис. У каждого свой
отказ и свои таймауты.

</details>

**A2.** ⭐ Как выбирать TTL и что делать перед миграцией?

<details><summary>Ответ</summary>

Короткий TTL (30–60 с) — быстрый failover, но больше запросов к DNS; длинный — дёшево, но
медленные изменения. Перед миграцией за сутки понизь TTL (ждать надо старый), переключи, проверь,
верни.

</details>

**A3.** ⭐ Посчитай время DNS failover: проверки каждые 10 с, порог 3, TTL 60 с. Чем это отличается
от anycast?

<details><summary>Ответ</summary>

10 × 3 + 60 = ~90 с для большинства, плюс хвост клиентов и резолверов, игнорирующих TTL: DNS
failover — для потери региона, не пода. Anycast переключается в маршрутизации BGP за секунды, TTL не
участвует и атака на одну точку рассеивается.

</details>

**A4.** ⭐ Чем `s-maxage` отличается от `max-age`, а `no-cache` от `no-store`? Что поставить на
редирект linkd?

<details><summary>Ответ</summary>

`s-maxage` — TTL только для общих кешей (CDN), перекрывает `max-age`. `no-cache` — хранить можно, но
перед использованием проверять у origin; `no-store` — не хранить. Для редиректа:
`Cache-Control: max-age=0, s-maxage=60`.

</details>

**A5.** Что такое cache key и как `utm_*` ломает hit ratio? Зачем origin shield?

<details><summary>Ответ</summary>

Ключ — схема, хост, путь, query и заголовки из `Vary`: каждая уникальная метка — новая запись и
промах к origin; лечится нормализацией ключа. Shield — региональный кеш между edge и origin: промахи
сотен точек превращаются в один запрос, цена — лишний переход на промахе.

</details>

**A6.** ⭐ Что нельзя кешировать на CDN?

<details><summary>Ответ</summary>

Персональные ответы (`Authorization`, cookie сессии), 5xx, `404` для значений, которые могут
появиться (новая ссылка), одноразовые URL, записи. Закешированное личное — утечка чужим.

</details>

**A7.** ⭐ Чем L4 отличается от L7 балансировщика и когда какой нужен?

<details><summary>Ответ</summary>

L4 видит IP и порты и балансирует соединения: быстро, любой TCP, TLS насквозь — для БД и сквозного
TLS. L7 читает HTTP: маршруты по host и path, ретраи, терминация TLS, метрики по запросам — для веба
и API. Часто L4 впереди (постоянный IP, DDoS), L7 за ним.

</details>

**A8.** Когда `least connections` лучше round robin, в чём его риск и почему linkd не берёт хеш по
коду?

<details><summary>Ответ</summary>

При запросах разной длины RR не видит занятый под. Риск: свежий под с нулём соединений получает всё
при холодном кеше — нужен slow start. Хеш по коду сохранил бы локальность L1, но вирусная ссылка на
50 000 RPS целиком ушла бы на один под; горячие ключи гасят L1 и CDN.

</details>

**A9.** ⭐ Active и passive health checks: в чём разница и что проверять?

<details><summary>Ответ</summary>

Active — LB сам шлёт пробы; passive — наблюдает за реальными ответами и выбрасывает после серии
ошибок. Используют вместе. Проверять «процесс может принять запрос»; общая БД в readiness выбросит
все поды сразу. Время обнаружения = интервал × порог.

</details>

**A10.** Опиши порядок остановки пода при выкатке без 502.

<details><summary>Ответ</summary>

Под убирается из endpoints и перестаёт быть ready; `preStop sleep` даёт LB узнать об этом; SIGTERM —
прекратить принимать, дождаться текущих запросов, закрыть idle-соединения; по истечении
`terminationGracePeriodSeconds` — SIGKILL.

</details>

**A11.** Чем ingress, API gateway и service mesh отличаются?

<details><summary>Ответ</summary>

Ingress — L7-вход в кластер: маршруты по host и path. API gateway — политика для внешних клиентов
API: ключи, квоты, версии. Mesh — трафик между сервисами: mTLS, ретраи, canary. Брать нужно только
нужные, а ретраи держать в одном слое.

</details>

**A12.** ⭐ Пик 20 000 RPS, hit ratio CDN 95%. Сколько RPS видит origin? А если CDN недоступен?

<details><summary>Ответ</summary>

20 000 × 0,05 = 1 000 RPS. Если CDN недоступен — все 20 000, поэтому origin обязан держать пик без
CDN или иметь понятную деградацию (лимиты, статическая страница).

</details>

### Блок B. «Что тут не так»

```
B1. «Ставим TTL 86400 на всё — меньше запросов к DNS, дешевле»

B2. «Для failover между регионами хватит DNS с TTL 1 час»

B3. «Cache-Control: no-cache — значит, CDN этот ответ не закеширует»

B4. «404 на CDN кешируем на сутки — боты, перебирающие коды, не дойдут до origin»

B5. «У нас CDN с WAF, origin можно оставить открытым — так проще мониторить»

B6. «gRPC раздаём через L4-балансировщик с round robin — нагрузка выровняется»

B7. «readinessProbe у redirect-сервиса: SELECT 1 к PostgreSQL»

B8. «Ретраи: клиент 3 раза, ingress 3 раза, mesh 3 раза — надёжнее»

B9. «Под получил SIGTERM и сразу завершается — балансировщик сам разберётся»
```

<details><summary>Ответы</summary>

**B1.** ⚠️ Изменяемые записи и failover будут меняться сутки. На изменяемых — 60–300 с; длинный TTL —
для NS, MX, TXT.

**B2.** ⚠️ Час на TTL плюс хвост клиентов. Нужен короткий TTL (30–60 с) либо anycast или глобальный LB.

**B3.** ⚠️ `no-cache` разрешает хранить, но требует проверки перед использованием. Запрет —
`no-store`, личное — `private`.

**B4.** ⚠️ Новая ссылка «залипнет» в 404. На CDN `no-store` или секунды; от перебора защищают лимиты
по IP на 404.

**B5.** ⚠️ Атакующий обходит WAF и DDoS-защиту, обратившись к origin напрямую. Принимай трафик только
от CDN: allowlist, mTLS или секретный заголовок.

**B6.** ⚠️ L4 балансирует соединения: долгие HTTP/2-соединения расходятся по подам неравномерно. Нужен
L7 с поддержкой gRPC или клиентская балансировка
([тема 02](/system-design/building-blocks/02-api-design)).

**B7.** ⚠️ Падение БД выбросит все поды сразу, хотя они могли бы отдавать ответы из кеша. Readiness —
«процесс готов принять запрос».

**B8.** ⚠️ 3 × 3 × 3 = 27 запросов на один клиентский: при сбое шторм. Ретраи — в одном слое, с
бюджетом.

**B9.** ⚠️ LB узнаёт об удалении с задержкой, запросы летят в закрывающийся под — 502. Нужны
readiness=false, `preStop sleep`, graceful shutdown.

</details>

### Блок C. Практика

#### C1. 🔑 Балансировщик и мини-CDN на nginx

Один бэкенд-образ для двух ролей: `app` (три реплики за балансировщиком) и `origin` (одна копия за
кеширующим «edge»). Конфиги монтируем **каталогами**: при `sed -i` у файла меняется inode, и
контейнер продолжит видеть старую версию.

```python
# app.py — / отдаёт имя контейнера, /r/<code> — «linkd»: 302 с Cache-Control; ?ms=N — задержка
import socket
import time
from http.server import BaseHTTPRequestHandler, ThreadingHTTPServer
from urllib.parse import parse_qs, urlparse

HOST, hits = socket.gethostname(), 0


class Handler(BaseHTTPRequestHandler):
    protocol_version = "HTTP/1.1"

    def do_GET(self):
        global hits
        url = urlparse(self.path)
        time.sleep(int(parse_qs(url.query).get("ms", ["0"])[0]) / 1000)
        body = b""
        if url.path.startswith("/r/"):
            hits += 1                    # считаем только «редиректы», без healthcheck
            self.send_response(302)
            self.send_header("Location", "https://example.org/" + url.path[3:])
            self.send_header("Cache-Control", "max-age=0, s-maxage=30")
        else:
            self.send_response(200)
            body = f"backend={HOST}\n".encode()
        self.send_header("X-Origin-Hits", str(hits))
        self.send_header("Content-Length", str(len(body)))
        self.end_headers()
        self.wfile.write(body)

    def log_message(self, *args):
        pass


ThreadingHTTPServer(("0.0.0.0", 8000), Handler).serve_forever()
```

for i in $(seq 1 12); do curl -s localhost:8080/; done | sort | uniq -c          # round robin
docker stop "$(docker compose ps -q app | head -1)"                              # отказ бэкенда

docker compose up -d --scale app=3                                               # вернуть бэкенд и подождать ~10 с (fail_timeout)

(curl -s "localhost:8080/?ms=5000" >/dev/null &); sleep 0.5

# Часть 2. Мини-CDN
for u in /r/abc /r/abc "/r/abc?utm_source=tg" "/r/abc?utm_source=mail"; do

Объясни результаты каждого шага. Что изменится без `zone app 64k;`? Какие три настройки настоящего
CDN повторяет `edge`?

<details><summary>Ответ</summary>

**Часть 1.** Round robin раскладывает запросы поровну (4/4/4). Остановленный бэкенд nginx обнаруживает
**пассивно**, по отказу соединения: запрос повторяется на соседа (`proxy_next_upstream error`), клиент
видит 200 с чуть большей задержкой, а на `fail_timeout` бэкенд исключается. Активных проб в открытом
nginx нет (они в коммерческой версии), их умеет HAProxy. С `least_conn` бэкенд, занятый долгим
запросом, не получает ни одного из быстрых; при round robin получил бы треть. Без `zone` у каждого
воркера nginx своё состояние алгоритма и счётчиков `max_fails`, и на коротких сериях распределение
перекошено (в проверочном прогоне первые 5 запросов подряд ушли на один бэкенд). `healthcheck` и
`depends_on` нужны, чтобы nginx не пометил ещё не запущенные бэкенды упавшими.

**Часть 2.** Первый запрос — `MISS`, дальше `HIT` с тем же `X-Origin-Hits`, в том числе для разных
`utm_*` (ключ без query; с `$request_uri` каждая метка дала бы свой `MISS`). Холодный ключ с локом:
1 `MISS` и 49 `HIT`, origin получает один запрос; без лока — 50 `MISS` и 50 запросов (stampede).
Прогретый ключ после истечения `s-maxage` при остановленном origin отдаётся как `STALE`, а
незакешированный — 502. Это три настройки CDN: ключ без лишних параметров, схлопывание запросов,
раздача устаревшего при отказе origin. Для 302 с `max-age=0` в своём CDN поведение проверь отдельно.

</details>

#### C2. Consistent hashing руками

Сравни, сколько ключей меняет владельца при добавлении 11-го пода: `hash % N` и кольцо со 100
виртуальными узлами.

```python
import bisect
import hashlib


def h(s: str) -> int:
    return int.from_bytes(hashlib.md5(s.encode()).digest()[:8], "big")


class Ring:
    def __init__(self, nodes, vnodes=100):
        self.ring = sorted((h(f"{n}#{i}"), n) for n in nodes for i in range(vnodes))
        self.points = [p for p, _ in self.ring]

    def owner(self, key):
        return self.ring[bisect.bisect(self.points, h(key)) % len(self.ring)][1]


keys = [f"code{i}" for i in range(100_000)]
r10, r11 = (Ring([f"pod{i}" for i in range(n)]) for n in (10, 11))
print("hash % N:", sum(h(k) % 10 != h(k) % 11 for k in keys) / len(keys))
print("ring    :", sum(r10.owner(k) != r11.owner(k) for k in keys) / len(keys))
```

<details><summary>Ответ</summary>

Скрипт детерминирован: `hash % N` — сдвинулось ≈ 91% ключей, кольцо — ≈ 9% (≈ 1/11). Для
балансировщика с кешами на подах это разница между «кеш почти не пострадал» и «холодный кеш у всех».
Без виртуальных узлов (`vnodes=1`) сдвиг мал, но нагрузка перекошена в разы. Горячий ключ при любом
хеше остаётся на одном поде — consistent hashing с этим не помогает.

</details>

#### C3. DNS и CDN снаружи: dig и curl

```bash
dig +noall +answer example.com A           # TTL — вторая колонка
sleep 5; dig +noall +answer example.com A  # TTL уменьшился: ответ из кеша резолвера
curl -sI https://cdnjs.cloudflare.com/ajax/libs/jquery/3.7.1/jquery.min.js | \
  grep -iE '^(cache-control|age|vary|cf-cache-status|cf-ray|alt-svc)'
```

Что значит убывающий TTL? Посчитай время failover для записи с TTL 300 с и проверок 15 с × 3 и
скажи, как уложиться в 2 минуты. Объясни `s-maxage`, `immutable`, `age`, `cf-cache-status`, `vary`.

<details><summary>Ответ</summary>

Повторный запрос показывает **остаток** TTL в кеше резолвера — «срок годности» ответа. Failover:
15 × 3 + 300 = 345 с ≈ 5,75 минуты; чтобы уложиться, TTL 60 с и проверки 10 с × 3 (90 с) либо anycast
и глобальный LB, где TTL не участвует. Файл версионирован в URL, поэтому `Cache-Control` стоит на год
с `immutable` и `s-maxage` для CDN; `age` — сколько секунд объект лежит в кеше;
`cf-cache-status: HIT` — ответ из кеша edge; `vary: Accept-Encoding` — сжатая и несжатая версии хранятся отдельно;
`alt-svc` анонсирует HTTP/3; после дефиса в `cf-ray` — код точки присутствия, в которую anycast привёл
тебя. Названия заголовков кеша у разных CDN разные.

</details>

#### C4. Спроектируй вход для linkd на бумаге

Нарисуй путь запроса для `lnk.example/{code}` и `api.lnk.example`. Для каждого звена: решение, TTL

пропуски: «что, если упадёт CDN» и клики из логов CDN.

</details>

### Блок D. Инциденты

**D1.** После каждого деплоя 1–2% запросов получают 502 в течение минуты. Приложение стартует и
останавливается штатно, ошибок в логах нет.

<details><summary>Ответ</summary>

Гонка при остановке: под получает SIGTERM и закрывается, пока LB ещё шлёт ему запросы. Исправить:
readiness=false, `preStop sleep` (10 с), graceful shutdown с ожиданием текущих запросов. Проверить
гонку keep-alive: таймаут простоя на бэкенде больше, чем на LB. Проверка — деплой под нагрузкой с
подсчётом 5xx.

</details>

**D2.** В 03:00 все клиенты получили ошибку TLS. Сервис жив, изнутри отвечает.

<details><summary>Ответ</summary>

Истёк сертификат на edge или LB: автопродление сломалось тихо. Сейчас: выпустить и установить
сертификат вручную, проверить цепочку. Потом: метрика «дней до истечения» с алертами за 14, 7 и 3 дня,
проверка продления по расписанию, процедура быстрого выпуска и владельцы.

</details>

**D3.** Hit ratio CDN упал с 95% до 40% после маркетинговой кампании, origin получает в пять раз
больше запросов, p99 растёт.

<details><summary>Ответ</summary>

Рекламные ссылки пришли с уникальными параметрами (`utm_*`, `fbclid`), каждая комбинация — новый ключ
кеша. Нормализовать ключ, проверить `Vary`. Для срочного снижения нагрузки — увеличить `s-maxage`,
включить origin shield. Потом: hit ratio по путям и алерт на его падение.

</details>

**D4.** WAF и DDoS-защита на CDN ничего не блокируют, а на origin огромный трафик с множества IP,
минуя CDN.

<details><summary>Ответ</summary>

Атакуют IP origin напрямую: он открыт в интернет или «утёк» через DNS-историю или заголовки писем.
Сейчас: закрыть origin для всех, кроме адресов CDN, или включить mTLS/секретный заголовок, при
необходимости сменить IP. Потом: authenticated origin pull как стандарт, security groups только на CDN.

</details>

### Блок E. Вопросы с собеседования

**1.** Что происходит между вводом URL и получением страницы?

<details><summary>Ответ</summary>

Резолв имени (кеши → рекурсивный резолвер → авторитативные серверы), anycast или GeoDNS приводят в
ближайшую точку CDN, TCP и TLS-рукопожатие, запрос на edge: попадание — ответ из кеша, промах — к
origin через LB и gateway. Подробно — [Сети: 14. Путь запроса в браузере](/network/14-url-journey).

</details>

**2.** Как спроектировать быстрое переключение на второй регион?

<details><summary>Ответ</summary>

Anycast или глобальный LB с health checks (секунды) либо GeoDNS/failover с TTL 30–60 с (минуты);
запас мощности на соседа; тёплые кеши и данные второго региона; запись остаётся в основном регионе.
Проверять учениями.

</details>

**3.** Статику и API раздаём через CDN. Как настроить кеширование?

<details><summary>Ответ</summary>

Статика — версия в URL, `public, max-age=31536000, immutable`. Публичные GET API — короткий
`s-maxage` и `stale-while-revalidate`. Персональное — `private` или `no-store`. Нормализовать ключ,
убрать лишнее из `Vary`, purge для срочного, мониторить hit ratio.

</details>

**4.** Как не положить origin после сброса кеша CDN?

<details><summary>Ответ</summary>

Не делать purge all на пике; origin shield и схлопывание запросов; `stale-while-revalidate` и
`stale-if-error`; плавный перенос трафика весами; origin рассчитан на пик без CDN или имеет лимиты и
быстрый 503.

</details>

**5.** L4 или L7 балансировщик для API? А для PostgreSQL?

<details><summary>Ответ</summary>

Для HTTP API — L7: маршруты, ретраи, терминация TLS, метрики по запросам. Для PostgreSQL и PgBouncer —
L4 или клиентская балансировка: протокол не HTTP, важна передача соединений. Часто L4 впереди L7.

</details>

**6.** Как сделать выкатку без потери запросов?

<details><summary>Ответ</summary>

Readiness и проба старта, rolling update с `maxUnavailable: 0`, `preStop sleep`, graceful shutdown с
ожиданием запросов, draining на LB, slow start, canary с автооткатом по SLO.

</details>

**7.** Чем API gateway отличается от ingress и mesh? Нужны ли все три?

<details><summary>Ответ</summary>

Ingress — маршрутизация в кластер, gateway — политика для внешних клиентов API (ключи, квоты,
версии), mesh — трафик между сервисами (mTLS, ретраи). Все три нужны редко: начинают с CDN, L7 и
ingress, остальное добавляют по требованию. Ретраи и таймауты держат в одном слое.

</details>

**8.** Как защитить origin за CDN?

<details><summary>Ответ</summary>

Принимать только трафик CDN: allowlist адресов, mTLS или секретный заголовок, закрытые security
groups; не раскрывать IP origin; WAF и лимиты на CDN и на LB как вторая линия.

</details>
