## 1. Базу масштабируют не «вообще», а против конкретного ресурса

У базы кончаются разные вещи: CPU и диск (плохие запросы), память и IOPS одного сервера,
соединения, ёмкость чтения, возможность обслуживать огромные таблицы, объём и запись. Каждое
лечится по-своему, поэтому первый шаг один — по метрикам выяснить, **что именно** кончилось.

> ⭐ Ступени идут от **дешёвых и обратимых** к **дорогим и необратимым**: каждая следующая
> меняет модель данных или умножает эксплуатацию. На следующую поднимаются, только когда метрика
> показала, что текущая исчерпана, а не «на вырост».

## 2. ⭐ Лестница: сигнал → ступень → цена

| # | Ступень | Сигнал, что пора | Что даёт | Цена |
|---|---------|------------------|----------|------|
| 1 | Запросы и индексы | Топ-запросы в `pg_stat_statements`, `Seq Scan` на больших таблицах | Во много раз быстрее без новых серверов | Индекс тормозит запись и занимает место |
| 2 | Вертикальный рост | После п. 1 CPU, RAM или IOPS стабильно выше ~70% в пике | ×2–4 за часы | Цена растёт быстрее мощности; потолок; перезапуск или failover |
| 3 | Пул соединений | Поды × пул больше `max_connections`; `too many clients` | Сотни клиентов на десятки соединений | Ещё один компонент; ограничения режима transaction |
| 4 | Реплики чтения | Primary занят чтением; нужен standby для HA | Чтение ×N, быстрый failover | Лаг, read-your-writes, копия диска |
| 5 | Кеш | Одни и те же ключи читают снова и снова | Нагрузка на БД делится на 5–10 | Инвалидация, холодный старт |
| 6 | Партиционирование | Таблицы в сотни ГБ, тяжело обслуживать, нужно сбрасывать старое | Дешёвое удаление, меньшие индексы | Ключ партиции входит в PK; запросы без него ходят во все партиции |
| 7 | Разделение по сервисам | Разные SLO и нагрузки в одной БД | Независимый рост, радиус поражения | Нет `JOIN` и транзакций между БД |
| 8 | Шардирование | Запись, объём или restore не помещаются в один сервер, 1–7 исчерпаны | Запись и объём растут линейно | Кросс-шардовые запросы, решардинг, эксплуатация ×N |

Порядок 4 и 5 зависит от данных: для read-heavy сервисов кеш часто дешевле реплик. Но реплика
нужна в любом случае — для HA (у linkd — синхронная реплика в другой AZ).

## 3. Ступени 1–2: запросы, индексы и вертикальный рост

**Сначала запросы, а не железо.** Вместо догадок — статистика самой базы:

```sql
-- нужны расширение pg_stat_statements (shared_preload_libraries + CREATE EXTENSION)
SELECT calls, round(mean_exec_time::numeric, 2) AS mean_ms,
       round(total_exec_time::numeric) AS total_ms, left(query, 70) AS query
FROM pg_stat_statements ORDER BY total_exec_time DESC LIMIT 5;

EXPLAIN (ANALYZE, BUFFERS) SELECT long_url FROM links WHERE code = 'aZ3x9Qk';

-- доля чтений из памяти (для OLTP ниже ~99% — повод разобраться)
SELECT round(100 * sum(blks_hit) / nullif(sum(blks_hit) + sum(blks_read), 0), 2) AS hit_pct
FROM pg_stat_database WHERE datname = current_database();
```

| Находка | Лечение |
|---------|---------|
| `Seq Scan` по таблице в миллионы строк | Индекс по колонкам условия; для «мои ссылки» — `(owner_id, created_at DESC)` |
| N+1: сотня мелких запросов на один HTTP-запрос | Один запрос с `ANY(...)` или `JOIN` |
| Пагинация через `OFFSET 100000` | Keyset: `WHERE (created_at, code) < ($1, $2) ORDER BY created_at DESC, code DESC LIMIT 50` |
| Индексы без чтений (`idx_scan = 0`) | Удалить: каждый лишний индекс тормозит запись |

**Вертикальный рост** — самая простая ступень: больше CPU, памяти, быстрее диск, код не
меняется. Но цена растёт быстрее мощности, потолок конечен, а сервер один: упал — failover и
холодный кеш. Когда следующий размер сервера уже в пределах ×2 от нужного, пора планировать
ступени 3–8, пока есть запас.

## 4. Ступень 3: соединения — жёсткий лимит

В PostgreSQL каждое соединение — процесс ОС, по умолчанию `max_connections = 100`
([Базы данных: 04. postgresql.conf](/databases/04-postgresql-conf)). Тысяча соединений — это
память и переключения контекста, а не тысяча параллельных запросов: по CPU работают десятки.

**Сколько соединений нужно на самом деле** — закон Литтла из
[Основы: 02. Оценки](/system-design/basics/02-estimations): занято = RPS × время запроса.

```text:no-line-numbers
 linkd: после кеша в базу ~2 000 RPS в пике, выборка по PK ~2 мс
   одновременно занято: 2 000 × 0,002 = 4 соединения; запас ×3 на всплески → ~12
 а подов 30, у каждого пул 10:  30 × 10 = 300  >  max_connections = 100
   почти все 300 простаивают, но занимают слоты и память
```

**Решение — PgBouncer:** сотни клиентских соединений мультиплексируются на десятки серверных.

Схема: 30 подов × пул 10 = 300 клиентских → PgBouncer × 2 (Deployment за Service,
`default_pool_size = 30` на каждый) → ~60 серверных соединений к primary с `max_connections = 100`
(остальное — запас: админ, репликация, миграции, мониторинг).

```ini
[pgbouncer]
pool_mode         = transaction   # соединение возвращается в пул после COMMIT/ROLLBACK
max_client_conn   = 1000          # сколько клиентов принимаем
default_pool_size = 30            # серверных соединений на пару (база, пользователь)
reserve_pool_size = 5             # временный запас, если клиенты ждут слишком долго
```

⚠️ В режиме `transaction` соседние транзакции клиента попадают на **разные** серверные
соединения. Ломается всё сессионное: `SET` без `LOCAL`, `LISTEN/NOTIFY`, сессионные
advisory-блокировки, временные таблицы между транзакциями. Prepared statements поддерживает
PgBouncer 1.21+ (`max_prepared_statements`; проверь версию), иначе их отключают в драйвере:
`prepare_threshold=None` в psycopg 3, `statement_cache_size=0` в asyncpg.

И в приложении нужен пул — вместо «нового соединения на каждый запрос», как в linkd 2.0
([Пет-проект: 01. Приложение](/project/01-app)):

```python
# пример для psycopg 3; свой драйвер и версию проверь
from psycopg_pool import ConnectionPool

pool = ConnectionPool(DSN, min_size=2, max_size=10, kwargs={"prepare_threshold": None})

def get_long_url(code: str) -> str | None:
    with pool.connection(timeout=0.2) as conn:      # ждать пул дольше 200 мс бессмысленно: быстрый 503 лучше
        row = conn.execute("SELECT long_url FROM links WHERE code = %s", (code,)).fetchone()
    return row[0] if row else None
```

> ⭐ Лимит соединений — **сквозное неравенство**: `maxReplicas × пул_пода ≤ max_client_conn`
> PgBouncer, а `default_pool_size × число пулов × число PgBouncer ≤ max_connections − запас`.
> Иначе автоскейлинг под нагрузкой сам положит базу
> ([Kubernetes: 18. HPA и автоскейлинг](/kubernetes/18-hpa-autoscaling)).

PgBouncer однопоточный и сам может стать точкой отказа: минимум два экземпляра за Service с
PodDisruptionBudget, следи за его CPU. В managed-базах часто есть встроенный пулер — проверь,
какие режимы он умеет.

## 5. Ступень 4: реплики чтения

Физическая репликация ([Базы данных: 06. Репликация PostgreSQL](/databases/06-replication))
даёт копии, с которых можно читать. Это решает чтение и HA, но **не запись и не объём**: запись
по-прежнему идёт на один primary, а каждая реплика хранит полную копию.

**Лаг и read-your-writes.** Создал ссылку и сразу открыл: запись на primary, чтение с реплики,
до которой WAL не доехал, — 404 (аномалии лага разобраны в
[Распределённые системы: 03. Репликация и шардирование](/distributed/03-replication-partitioning)).
На практике:

| Способ | Как | Цена |
|--------|-----|------|
| Читать своё с primary | После записи пометить сессию на N секунд | Часть чтения возвращается на primary |
| Ждать LSN | После записи запомнить `pg_current_wal_lsn()`; читать с реплики, только если `pg_last_wal_replay_lsn()` не меньше, иначе — primary | Код и метка в cookie или заголовке |
| `synchronous_commit = remote_apply` | Запись ждёт, пока реплика **применит** изменение | Задержка записи; реплика недоступна — запись встаёт |
| Write-through в кеш | Запись сразу кладёт значение в кеш (так в linkd) | Нужен кеш и дисциплина инвалидации |

⚠️ Не делай «автомаршрутизацию по тексту запроса» (`SELECT` → реплика): под `SELECT` бывают
`FOR UPDATE` и функции с побочными эффектами. Лучше явный выбор в коде: два пула, для записи и
для чтения. Отстающую реплику **выводят из пула чтения**: у Patroni для этого есть проверка с
порогом `GET /replica?lag=<порог>` (проверь свою версию).

Для linkd реплики — это HA и запас, а не ёмкость: после кеша на базу ~2 000 RPS, по ~1 000 на
каждую из двух реплик — выборка по PK из памяти почти ничего не стоит.

## 6. Ступень 5: кеш

Подробно — [03. Кеширование](/system-design/building-blocks/03-caching). Для ёмкости БД важна
одна формула:

```text:no-line-numbers
 нагрузка на БД = пик RPS × (1 − hit ratio)
 linkd: 20 000 × (1 − 0,90) = 2 000 RPS;  при hit ratio 99% — 200 RPS
```

⚠️ Кеш **маскирует** слабость базы: пока hit ratio 90%, она видит 10% нагрузки. Redis
перезапустился пустым — база получает 100% и падает. Проектируй так, будто кеша нет: лимит
параллельных походов в БД, быстрый `503` на излишки, прогрев до включения трафика
([Распределённые системы: 06. Режимы отказов](/distributed/06-failure-modes), stampede).

## 7. Ступень 6: партиционирование таблиц

**Партиционирование** — одна логическая таблица физически хранится кусками **на одном сервере**.
Это про обслуживание, а не про ёмкость записи: `DROP` партиции вместо `DELETE` миллиарда строк
(без раздувания и всплеска WAL), меньшие индексы, свой `VACUUM` на партицию, **partition
pruning** (планировщик отбрасывает партиции, не подходящие под `WHERE`), готовая единица для
будущего шардирования. Способы в PostgreSQL: `RANGE` (время; нужно сбрасывать старое),
`HASH` (равномерно, нет естественного диапазона), `LIST` (небольшой набор значений).

```sql
-- ссылки: hash по коду (4 партиции для примера; в проде — 64 и больше)
CREATE TABLE links (
    code       varchar(32) COLLATE "C" PRIMARY KEY,
    long_url   text        NOT NULL,
    owner_id   bigint      NOT NULL,
    created_at timestamptz NOT NULL DEFAULT now()
) PARTITION BY HASH (code);
CREATE TABLE links_p0 PARTITION OF links FOR VALUES WITH (MODULUS 4, REMAINDER 0);
-- … p1, p2, p3

-- события по времени: PARTITION BY RANGE (ts), партиция на месяц (полный пример — упражнение C1);
-- сбросить старый месяц без долгой блокировки. CONCURRENTLY — PostgreSQL 14+, не внутри транзакции
-- и не при наличии DEFAULT-партиции (тогда — обычный DETACH)
ALTER TABLE clicks DETACH PARTITION clicks_2026_08 CONCURRENTLY;
DROP TABLE clicks_2026_08;
```

⭐ **Главное правило:** в `PRIMARY KEY` и любом `UNIQUE` на партиционированной таблице должны
быть **все** колонки ключа партиции. Поэтому `links` нельзя партиционировать по `created_at`,
если нужна уникальность `code`: PostgreSQL ответит `unique constraint on partitioned table must
include all partitioning columns`, а обход `PRIMARY KEY (code, created_at)` потеряет уникальность
кода. Для `links` ключ партиции — сам `code`; для событий и агрегатов, где время и так в ключе, —
`RANGE` по времени.

**Pruning работает, только если в `WHERE` есть ключ партиции.** Запрос по `code` идёт в одну
партицию; «мои ссылки» (`owner_id = 42`) — во все (упражнение C1). Шарды повторят это же, но дороже.

| Нюанс эксплуатации | Что делать |
|--------------------|-----------|
| Партиции на будущее | `pg_partman` или CronJob; **алерт**, если нет партиции на следующий период |
| Данные упали в `DEFAULT` | Партиции на период не было; пока строки не вычищены, создать «правильную» с пересечением нельзя — мониторь размер `DEFAULT` |
| Сколько партиций | Сотни — нормально, тысячи удлиняют планирование (проверь на своей версии) |
| `HASH`: число | Менять модуль дорого (перекладывание данных) — бери с запасом сразу |
| Статистика родителя | Автовакуум не анализирует саму родительскую таблицу — `ANALYZE` по расписанию |
| Миграции | Каждая партиция — своя блокировка: `lock_timeout` ([Миграции схемы](/databases/13-schema-migrations)); `CREATE INDEX CONCURRENTLY` на родителе не поддерживается — на партициях и `ATTACH` (проверь версию) |

> ⚠️ Партиционирование — не шардирование: сервер один, restore копирует весь объём, запись идёт в один primary.

## 8. Ступень 7: разделение по сервисам

**Функциональное разделение** — у каждой роли своя БД. Выделяют то, что отличается по нагрузке,
SLO или типу данных: аналитику кликов (у linkd — ClickHouse, [кейс §6.5](/system-design/backend-cases/01-url-shortener)),
пользователей и API-ключи, тяжёлые отчёты, поиск ([тема 07](/system-design/building-blocks/07-blobs-search)).

Цена: **нет `JOIN` и транзакций между базами**. Связи — через идентификаторы (`owner_id` без
внешнего ключа), согласование — через события и outbox
([06. Асинхронность](/system-design/building-blocks/06-async-messaging)), «собрать ответ из двух
баз» — работа приложения. ⚠️ Не режь по таблицам то, что меняется вместе в одной транзакции:
получишь распределённый монолит.

## 9. Ступень 8: шардирование

**Шардирование** — данные одной таблицы делятся на непересекающиеся части, и каждая часть (шард)
живёт на своём сервере со своим primary и репликами. Теория (hash, range, consistent hashing,
ребалансировка) — в [Распределённые системы: 03](/distributed/03-replication-partitioning); здесь —
как подойти к этому как к дизайну.

### 9.1. Когда пора

Когда ступени 1–7 исчерпаны **и** сработал хотя бы один сигнал:

| Сигнал | Как проверить |
|--------|---------------|
| Restore не укладывается в RTO | Объём на диске ÷ скорость восстановления: десятки минут — норма, часы — нет |
| Запись упёрлась в один primary | После настройки диск и WAL у потолка, `COMMIT` замедляется |
| Объём у потолка | Диск уже на самом большом доступном размере |
| Обслуживание длится сутками | `REINDEX`, `pg_upgrade`, `CREATE INDEX CONCURRENTLY` по всей таблице |
| Рабочее множество не в памяти | Hit ratio падает, а сервер побольше уже не помогает |

> ⚠️ «Чтений стало много» — не сигнал (это ступени 4–5), как и «хотим на вырост». У linkd 200 RPS
> записи в пике: шардируют его **из-за объёма и RTO**, а не из-за RPS.

### 9.2. Ключ шарда: главное решение

Ключ определяет, на какой шард попадёт строка, а значит — какие запросы дешёвые. Исправить его
потом — это перенос **всех** данных.

| Критерий | Вопрос | Плохой ключ |
|----------|--------|-------------|
| Кардинальность | Значений намного больше, чем шардов? | `status`, `country` — 5 значений на 16 шардов |
| Равномерность | Нагрузка и объём делятся поровну? | `created_at` с диапазонами: вся запись в последний шард |
| Локальность | Главные запросы содержат ключ и идут в один шард? | Ключ, которого нет в `WHERE` горячих запросов |
| Неизменность | Ключ не меняется после создания? | `email`, который можно сменить |

Примеры: linkd — `code` (редирект знает его; код случайный → равномерно); B2B SaaS — `tenant_id`
(запросы и `JOIN` клиента в одном шарде); мессенджер — `chat_id`; заказы магазина — `user_id`.

### 9.3. Hash, range или справочник

| | Hash | Range | Directory (справочник) |
|-|------|-------|------------------------|
| Как | `hash(key)` → шард | Диапазон ключей → шард | Таблица «ключ → шард» |
| Плюсы | Равномерно | Диапазонные запросы в 1–2 шарда | Любое размещение; перенос по одному ключу |
| Минусы | Диапазон идёт во все шарды | Горячие диапазоны на монотонных ключах | Справочник — горячий путь и точка отказа (кешируют) |

⭐ **Логические шарды.** Не привязывай ключ к числу серверов. Выбери большое **фиксированное**
число логических шардов (например, 1024) и храни карту «логический шард → сервер». Рост —
перенос целых логических шардов, а отображение «ключ → логический шард» не меняется никогда.
Наивный `hash(key) mod N` при росте с 4 до 5 серверов переселяет ~80% ключей, логические
шарды — ~20% (упражнение C3). Тот же принцип в слотах Redis Cluster и партициях Kafka;
consistent hashing с виртуальными нодами — родственный приём
([Распределённые системы: 03](/distributed/03-replication-partitioning)).

### 9.4. Горячие шарды и «звёзды»

Равномерный хеш не спасает от **горячего ключа**: ссылка из вирусного поста, огромный арендатор.
Одна ссылка с ~30% трафика даёт её серверу ~47% нагрузки (C3). Приёмы: кеш и CDN перед шардом
([тема 03](/system-design/building-blocks/03-caching)); разбить ключ (`key#0 … key#9`, чтение
собирает куски); вынести тяжёлого клиента на свой шард через справочник; перенести соседние
логические шарды на другой сервер. Увидеть перекос помогает метрика «максимум ÷ среднее»
по шардам (QPS, размер, CPU).

### 9.5. Запросы, `JOIN` и транзакции через шарды

| Что | Что происходит | Что делать |
|-----|----------------|-----------|
| Запрос без ключа | **Scatter-gather**: во все шарды и склейка | Не на горячем пути; вторичный индекс (9.6) |
| Доступность | Запрос на 16 шардов при 99,95% на шард: 0,9995¹⁶ ≈ 99,2% | Ответ из доступных шардов с пометкой |
| Хвост задержки | Ждём самый медленный: шанс задеть чей-то p99 = 1 − 0,99¹⁶ ≈ 15% ([Основы: 01](/system-design/basics/01-what-is-system-design)) | Таймаут на шард, hedged-запросы |
| `JOIN` | Строки на разных шардах | Общий ключ у связанных таблиц; справочники копией на каждый шард; денормализация; отчёты — в аналитику |
| Транзакция | Изменение двух шардов не атомарно | Агрегат целиком в одном шарде; иначе сага и outbox ([Распределённые системы: 06](/distributed/06-failure-modes)); 2PC медленный и блокирующий |

### 9.6. Вторичные индексы

Шард по `code`, а нужен список ссылок владельца. Локальный индекс на каждом шарде — это
scatter-gather; **глобальный** — отдельная таблица, шардированная по другому ключу (теория —
[Распределённые системы: 03, §7](/distributed/03-replication-partitioning)). В ручном шардировании
ты строишь её сам (`owner_index`, пример в разделе 12.2): таблица шардирована по `owner_id` и
пишется **асинхронно** через outbox и идемпотентного потребителя — две записи в разные шарды
одной транзакцией не сделать. Значит, индекс **eventually consistent** (только что созданной
ссылки может не быть секунды), а потерянный индекс пересобирают сканом основной таблицы. Готовые
аналоги: lookup vindex в Vitess, GSI в DynamoDB.

### 9.7. Уникальность

Уникальный индекс гарантирует уникальность **внутри шарда**. Глобально:

| Способ | Пример |
|--------|--------|
| Уникальный атрибут — сам ключ шарда | `code` в linkd: коллизия — `ON CONFLICT`, повтор |
| Ключ шарда входит в уникальный индекс | `UNIQUE (tenant_id, slug)` |
| Таблица-справочник по этому атрибуту | `email → user_id`, шардирована по email |
| ID с зашитым шардом | Snowflake-подобные идентификаторы |

⚠️ Ловушка linkd: «один URL — один код у владельца» требует уникальности `(owner_id,
hash(long_url))`, а ссылки шардированы по `code` — проверить можно лишь в таблице, шардированной
по `owner_id`, то есть в `owner_index`.

### 9.8. ID, маршрутизация и карта шардов

**ID** между шардами должен быть уникален и желательно сам говорить, где живёт строка: случайный
(UUIDv4, у linkd — случайный `code`; без координации, но плохая локальность индекса), время +
шард + счётчик (Snowflake, UUIDv7; нужен ID шарда и аккуратность с часами) или диапазоны от
сервиса выдачи (ещё один компонент). Подробнее — в блоке 3 «Данные».

**Маршрутизация** живёт в приложении (библиотека с картой шардов — путь linkd), в прокси
(Vitess `vtgate`) или в самой БД (координатор Citus). Карта шардов — критичный конфиг:
версионируй, выкатывай постепенно и принимай запросы только с актуальной версией карты — иначе
«отставший» клиент запишет не туда.

## 10. Решардинг: перенос данных без простоя

Решардинг неизбежен: растёт объём, появляется горячий шард, меняется ключ. Три подхода:
**перенос логических шардов** (основной: ключ не меняется, добавляем серверы; логическая
репликация), **двойная запись + бэкфилл** (меняется ключ или схема размещения; уход с одной БД на
шарды) и **средства СУБД** (Citus-ребалансировщик, Vitess `MoveTables` и `Reshard`, автоматика CockroachDB).

```text:no-line-numbers
 0. ПОДГОТОВКА    логические шарды, колонка shard в таблице, карта шардов v1
 1. КОПИЯ         снимок + поток изменений (логическая репликация) на новый сервер
 2. ПРОВЕРКА      счётчики и контрольные суммы по логическим шардам; теневое чтение: сравниваем ответы
 3. ПЕРЕКЛЮЧЕНИЕ  запись по переносимым ключам замораживаем на секунды → лаг 0 → карта v2 → размораживаем
 4. ОБРАТНАЯ РЕПЛИКАЦИЯ  держим несколько суток: откат без потери новых записей
 5. УБОРКА        удалить перенесённое с источника пачками; удалить слот и подписку
```

Простой — секунды записи **только** по переносимым ключам; чтение не прерывается.

| Подводный камень | Что делать |
|------------------|-----------|
| Слот репликации держит WAL, пока подписчик стоит | Мониторь лаг слота и диск источника; забытый слот забивает диск primary |
| Фильтр публикации по колонке `shard` | Для `UPDATE` и `DELETE` колонка фильтра должна входить в replica identity (упражнение C4) |
| Последовательности и DDL не реплицируются | Схему создай заранее; миграции на время переноса заморозь |
| Перенос грузит источник | Ограничивай скорость, работай в часы низкой нагрузки |
| Клиент с устаревшей картой | Версия карты в запросе; «не тому» шарду — отказ |
| Решардинг начали при 95% диска | Начинай при 60–70% заполнения |

Двойная запись сложнее: вторая запись может упасть, порядок и конфликты на тебе — пиши
идемпотентно (`ON CONFLICT`), сбои отправляй в очередь повторов, сверяй непрерывно.

## 11. Готовые решения

| Решение | Что это | Что берёт на себя | Цена и ограничения | Когда |
|---------|---------|-------------------|--------------------|-------|
| **Citus** | Расширение PostgreSQL | Распределённые таблицы по ключу, справочные таблицы, ребалансировка, распределённые запросы | Уникальность и внешние ключи привязаны к ключу распределения; запросы без ключа дороги | PostgreSQL-код, мультиарендность по `tenant_id` |
| **Vitess** | Слой шардирования над MySQL | Маршрутизация, vindex'ы (в том числе lookup), `Reshard`, онлайн-миграции | Тяжёлая инфраструктура; это про MySQL | Большой MySQL, много клиентов |
| **CockroachDB, YugabyteDB** | Распределённый SQL: данные режутся на диапазоны, реплики через Raft | Шардирование, ребалансировка, failover, сильная согласованность | Каждая запись — кворум (задержка, особенно между регионами); совместимость с PostgreSQL неполная; лицензии менялись — проверь | Запись в нескольких регионах, не хочется шардировать руками |
| **Managed** | Aurora, Spanner; для ключ-значение — DynamoDB, Cassandra, Scylla | Хранилище, реплики, бэкапы, у части — шардирование | Привязка к провайдеру; в классической конфигурации Aurora запись идёт в один writer | Мало людей на эксплуатацию |
| **Руками в приложении** | Карта шардов и роутер в коде | Полный контроль | Решардинг, миграции, бэкапы, индексы — на тебе | Простая модель `code → url`, готовая команда |

> ⭐ Это обмен: платишь деньгами и привязкой (managed), людьми (самописное) или задержкой записи
> (распределённый SQL). Развилка — сколько людей, какие язык и СУБД уже в проде и нужна ли
> запись в нескольких регионах. Если нет — PostgreSQL + партиции + реплики + кеш закрывают очень многое.

## 12. linkd по лестнице: цифры

Числа из [кейса](/system-design/backend-cases/01-url-shortener): 100 млн новых ссылок в месяц,
200 RPS записи и 20 000 RPS чтения в пике, 6 млрд ссылок за 5 лет, ~3 ТБ.

| Ступень | Что делаем в linkd | Числа |
|---------|-------------------|-------|
| 0. Сейчас | linkd 2.0: новое соединение на каждый запрос, пула нет | Не вытянет и сотню RPS |
| 1. Запросы | Редирект — по PK `code`; список — `(owner_id, created_at DESC)` и keyset; `EXPLAIN` горячих запросов в CI | Редирект — единицы мс |
| 2. Вертикально | Один primary с запасом по RAM | Запас, а не цель |
| 3. PgBouncer | 30 подов × пул 10 = 300 > 100; два PgBouncer, `default_pool_size = 30` | Занято ~4–12 соединений |
| 4. Реплики | Синхронная в другой AZ (RPO ≈ 0) + асинхронные для чтения | ~1 000 RPS на реплику |
| 5. Кеш | L1 + Redis, hit ratio 90–95% | До БД ~2 000 RPS (при 90%) |
| 6. Партиции | `links` по `HASH (code)`, 64 партиции (~47 ГБ данных каждая при 3 ТБ); агрегаты по месяцам с `DROP` | Меньше индексы, `VACUUM` по частям |
| 7. Разделение | Клики — в ClickHouse (уже), пользователи и ключи — отдельная БД | Ссылки не раздуты кликами |
| 8. Шарды | `code` → 1024 логических шарда → ~10 серверов | ~300 ГБ данных на сервер |

### 12.1. Когда шардировать

Данные растут на 50 ГБ в месяц (100 млн × 500 Б), ~0,6 ТБ в год. Индексы дают ×1,5–2, а физический
бэкап копирует всё: кейс оценил restore 3 ТБ в ~4 часа по минимуму, а на диске с индексами это
4,5–6 ТБ и 6–8 часов.

```text:no-line-numbers
 допущение: RTO на восстановление из бэкапа 4 ч (горячие ссылки живут из кеша)
 4 ч × 3 600 с × 200 МБ/с ≈ 2,9 ТБ на диске  →  с индексами ×1,5–2 это ~1,5–2 ТБ данных
 при росте 50 ГБ/мес — это 30–40-й месяц  →  проект шардирования стартует за 6–9 месяцев до порога, со 2-го года
 10 шардов по ~300 ГБ восстанавливаются ПАРАЛЛЕЛЬНО: итог — время самого большого шарда,
 порядка 25–50 минут вместо 6–8 часов
```

Второй сигнал — индексы: на 6 млрд строк они занимают сотни ГБ и целиком в RAM не помещаются;
горячая часть в памяти, а промахи уходят на диск. Это допущения — пересчитай со своим RTO и
измеренной скоростью restore. Запись (200 RPS) триггером не является: важна связка «объём — RTO —
индексы и обслуживание».

### 12.2. «Мои ссылки» после шардирования

```sql
-- шардируется по owner_id; хранит всё нужное для списка, чтобы не ходить по шардам кодов
CREATE TABLE owner_index (
    owner_id bigint NOT NULL, created_at timestamptz NOT NULL,
    code varchar(32) COLLATE "C" NOT NULL, long_url text NOT NULL, status smallint NOT NULL DEFAULT 0,
    PRIMARY KEY (owner_id, created_at, code)
);
```

```text:no-line-numbers
 POST /api/v1/links
   │ code → шард по hash(code)
   ▼ shard(code): BEGIN; INSERT INTO links … ON CONFLICT …; INSERT INTO outbox (LinkCreated); COMMIT
   │ relay → Kafka (ключ = code)
   ▼ потребитель: shard(owner_id): INSERT INTO owner_index … ON CONFLICT DO NOTHING
 GET /api/v1/links?cursor=…  → один шард (owner_id); keyset: (created_at, code) < ($2, $3)
```

Потребитель идемпотентен (`ON CONFLICT DO NOTHING`); удаление и блокировка идут событиями
`LinkDeleted` и `LinkBlocked`, меняющими `status`. Read-your-writes: сразу после создания в
индексе ссылки может не быть — UI добавляет её из ответа на `POST` либо API подмешивает
«недавние» из Redis.

## 13. ⚙️ Эксплуатация

Семь вопросов из [Основы: 04](/system-design/basics/04-backend-vs-devops) — для базы linkd на
всём пути: от одного PostgreSQL с PgBouncer до шардов.

### 13.1. Развёртывание

| Компонент | Как |
|-----------|-----|
| PostgreSQL | Managed или оператор (Patroni, CloudNativePG) вне потока релизов приложения ([Хранилища: 06](/storage/06-db-backup-replication)); primary и реплики в разных AZ |
| PgBouncer | Deployment в 2–3 реплики за Service, PodDisruptionBudget, лимиты CPU; конфиг из ConfigMap и Secret, `RELOAD` без обрыва клиентов |
| Партиции | Создание на период вперёд — `pg_partman` или CronJob; алерт, если не создана |
| Шарды | Каждый — отдельный кластер (primary + 2 реплики) из одного шаблона (Helm или оператор); выкатка по одному |
| Карта шардов | Версионированный конфиг в Git; выкатка постепенно; приложение принимает только известную версию |
| Миграции схемы | Expand/contract ([Миграции схемы](/databases/13-schema-migrations)), `lock_timeout`; на шардах — **по одному**: канарейка, потом остальные, проверка дрейфа схем; код совместим со старой и новой схемой, пока не прошли все шарды |

### 13.2. Масштабирование

| Что | Как | Потолок |
|-----|-----|---------|
| Приложение | HPA | `поды × пул ≤ max_client_conn` |
| PgBouncer | Реплики (один экземпляр однопоточный) | CPU экземпляра; `default_pool_size × пулов ≤ max_connections` |
| Чтение | Реплики, кеш | Лаг, WAL sender'ы на primary; запись не растёт |
| Один сервер | Вертикально, партиции | Самый большой инстанс; restore |
| Запись и объём | Шарды: добавить сервер → перенести логические шарды по runbook из раздела 10 | Запас 1024 логических шардов; заполнение шарда 60–70% |

### 13.3. Наблюдаемость

| Что | Метрика | Алерт |
|-----|---------|-------|
| Пользовательский путь | SLO редиректа; задержка запроса к БД (гистограмма по шарду) | Burn rate ([SRE: 02](/sre/02-sli-slo-error-budget)) |
| Соединения | `pg_stat_activity` по состояниям; PgBouncer `SHOW POOLS`: `cl_waiting`, `maxwait` | Клиенты ждут пул; занято > 80% `max_connections` |
| Лаг реплик | `pg_stat_replication`: байты и секунды | Лаг выше порога; реплика выведена из пула |
| Кеш и запросы | Hit ratio буферов и приложения; `pg_stat_statements` | Падение hit ratio; новый запрос в топе |
| Рост | Размер таблиц и партиций, `predict_linear` по диску | Диск кончится менее чем за 30 суток |
| Партиции | Есть ли партиция на следующий период; размер `DEFAULT` | Нет партиции; `DEFAULT` не пуст |
| Шарды | QPS, размер, CPU по шардам; **перекос** = максимум ÷ среднее | Перекос выше порога |
| Бэкапы | Свежесть WAL-архива и бэкапа **каждого шарда** | У хоть одного шарда архив отстал |
| Решардинг | Лаг слота, диск источника | Лаг растёт; диск источника < 20% |

### 13.4. Отказы

| Что упало | Что видит пользователь | Что делает система |
|-----------|-----------------------|--------------------|
| Primary шарда | Создание ссылок этого шарда — ошибка на десятки секунд; редиректы — из кеша и с реплик | Failover (Patroni, managed); клиент повторяет с `Idempotency-Key` |
| Шард целиком | Недоступна доля кодов 1/N | Радиус поражения мал; кеш прикрывает горячие ссылки |
| PgBouncer | Ошибки подключения | Второй экземпляр, быстрые ретраи |
| Отстающая реплика | Устаревшее чтение | Вывод из пула по лагу; чтение на primary с лимитом |
| Scatter-gather | Частичный список | Ответ из доступных шардов; таймаут на шард |
| Сбой при решардинге | Ничего, пока не переключили | Карта шардов обратно на v1; обратная репликация хранит записи |
| Миграция упала на части шардов | Разная схема у шардов | Код совместим с обеими схемами; повтор на упавших |

### 13.5. Данные и DR

| Данные | RPO | Как |
|--------|-----|-----|
| `links` по шардам | ≈ 0 при потере сервера; минуты при логической ошибке | Синхронная реплика в другой AZ + WAL-архив и base backup **каждого шарда** в S3 другого региона |
| `owner_index` | Производные | Пересобирается; знай время пересборки |
| Карта шардов | Нельзя потерять | В Git и в бэкапе конфигов: без неё непонятно, где какие данные |

- **Общий срез между шардами.** PITR каждого шарда откатывает его на свой момент. Для общей
  точки нужна именованная точка восстановления на всех шардах одновременно
  (`pg_create_restore_point()`; в Citus есть координируемый вариант — проверь версию) либо
  осознанное допущение, что шарды откатятся на чуть разные моменты, а производные данные
  пересоберутся. Для linkd хватит второго: ссылки между собой не связаны.
- **Restore-test по шардам** регулярно, с замером времени; восстановление идёт параллельно —
  время аварии = время самого большого шарда.
- Реплика — не бэкап: `DROP` и ошибочный `DELETE` реплицируются
  ([Базы данных: 05](/databases/05-backup-restore), [Пет-проект: 09](/project/09-backup-dr)).

### 13.6. Безопасность

| Тема | Как |
|------|-----|
| Роли | Приложение — `SELECT, INSERT, UPDATE` на нужные таблицы; миграции — отдельная роль с DDL; репликация — своя; аналитики — только на реплику |
| PgBouncer | `auth_type = scram-sha-256`, учётные данные из Vault или External Secrets ([Vault](/vault/)); TLS клиент → PgBouncer → PostgreSQL |
| Сеть | БД и PgBouncer недоступны снаружи кластера; NetworkPolicy только от нужных подов |
| Данные | `owner_index` и бэкапы содержат те же персональные данные: шифрование дисков и бэкапов, S3 с бэкапами без записи с прод-серверов |
| Шарды | Ротация паролей на всех шардах автоматизирована, иначе «забытый» шард |

### 13.7. Стоимость

| Статья | Почему растёт | Как сдерживать |
|--------|--------------|----------------|
| Запросы и индексы | Самый дешёвый выигрыш | Чистить неиспользуемые индексы |
| Сервер побольше | Цена растёт быстрее мощности | Вовремя перейти к реплике и кешу |
| Реплики | Каждая — полная копия диска и сервер | Столько, сколько нужно для HA и чтения |
| Кеш | RAM под Redis | Держать только горячее |
| Шарды | ×число шардов × (primary + 2 реплики): 10 шардов — 30 инстансов + бэкапы каждого | Меньше реплик на некритичных данных; заполнение 60–70%; не шардировать раньше сигнала |
| Люди | Шардирование — эксплуатация ×N | Managed или Citus вместо самописного, если людей мало |

> ⭐ Главная статья шардирования — не серверы, а **время людей**: миграции ×N, решардинг,
> дежурства. Считай его в стоимости наравне с железом.

| Грабля | Что не так | Правильно |

| Шардирование «на вырост» | ×N эксплуатации без сигнала | Ступени 1–7 и измеренный сигнал |

## 💼 Как это на работе

- **Бэкенд:** перед запросом спрашивай, есть ли в нём ключ партиции или шарда; `JOIN` и
  транзакцию «через всё» сделать просто сейчас и больно ломать потом. Ключ шарда — решение на
  годы: обсуди его до первых данных. Читаешь с реплики — думай про лаг; пул и таймауты — часть кода.
- **DevOps:** твои числа — соединения, лаг, рост диска, время restore; держи неравенство
  поды × пул ≤ лимит в алертах. Шардирование — это в первую очередь процессы: миграции по одному
  шарду, бэкап и restore-test каждого, карта шардов в Git, runbook решардинга.
- Хороший ответ на ревью: «сейчас ступень 5, сигнал на следующую — restore дольше RTO; проект
  шардирования начнём за 6 месяцев до порога». Это сильнее, чем «давайте шардировать».

## 📌 Шпаргалка

| Хочу | Как |
|------|-----|
| Найти, что тормозит | `pg_stat_statements` по `total_exec_time`, `EXPLAIN (ANALYZE, BUFFERS)` |
| Сколько соединений нужно | RPS × время запроса (Литтл), запас ×3 |
| Лимит соединений | `поды × пул ≤ max_client_conn`; пулы PgBouncer `≤ max_connections − запас` |

| Партиции | `HASH` — равномерно, `RANGE` — время и `DROP`, `LIST` — набор значений |
| PK партиционированной таблицы | Обязан включать ключ партиции; pruning только с ним |
| Ключ шарда | Кардинальность, равномерность, локальность запросов, неизменность |

## 🧠 Что запомнить

1. Базу масштабируют против конкретного ресурса: сначала выясни, что кончилось.
2. ⭐ Лестница: запросы и индексы → вертикально → пул соединений → реплики → кеш → партиции →
   разделение по сервисам → шарды. Шаг вверх — только по сигналу из метрик.
3. ⭐ Соединения — жёсткий лимит: поды × пул ≤ лимит; нужное число считается по закону Литтла и
   обычно мало — решение PgBouncer.
4. Реплики дают чтение и HA, но не запись и не объём; платишь лагом. ⭐ Read-your-writes лечится:
   primary на время, ожидание LSN, write-through в кеш.
5. Партиционирование — про обслуживание на одном сервере; PK обязан включать ключ партиции;
   pruning работает только с ним.
6. ⭐ Ключ шарда — главное решение: кардинальность, равномерность, локальность, неизменность.
7. Логические шарды вместо `hash mod N`: рост переносит ~1/N данных, а не ~80%.
8. Кросс-шардовые запросы, `JOIN`, транзакции, индексы и уникальность — теперь твоя забота:
   таблица-индекс через outbox, справочники, агрегат в одном шарде.
9. Горячий ключ не лечится хешем — кеш, CDN, разбиение ключа, перенос логических шардов.
10. ⭐ Шардирование — эксплуатация ×N: миграции по одному шарду, бэкап и restore-test каждого,
    карта шардов в Git, runbook решардинга; начинай при 60–70% заполнения.

### Блок A. Теория

**A1.** ⭐ Назови ступени лестницы роста БД по порядку и сигнал для каждой.

<details><summary>Ответ</summary>

1) Запросы и индексы — топ в `pg_stat_statements`, `Seq Scan`. 2) Вертикально — CPU, RAM, IOPS
выше ~70% после п. 1. 3) Пул соединений — `too many clients`. 4) Реплики — primary занят
чтением, нужен HA. 5) Кеш — те же ключи читают снова и снова. 6) Партиции — большие таблицы,
нужно сбрасывать старое. 7) Разделение по сервисам — разные нагрузки и SLO. 8) Шарды —
запись, объём или restore не помещаются в один сервер.

</details>

**A2.** ⭐ 30 подов с пулом по 10, `max_connections = 100`, после кеша в базу идёт 2 000 RPS
по 3 мс. Что произойдёт, сколько соединений нужно на самом деле и что делать?

<details><summary>Ответ</summary>

30 × 10 = 300 соединений при лимите 100 — новые получат `too many clients`. Нужно же по закону
Литтла 2 000 × 0,003 = 6 занятых, с запасом ×3 — около 18. Поднимать `max_connections` не стоит
(каждое соединение — процесс). Решение — PgBouncer в режиме `transaction`: сотни клиентских
соединений на десятки серверных.

</details>

**A3.** Что ломается в `transaction`-режиме PgBouncer?

<details><summary>Ответ</summary>

Всё сессионное: `SET` без `LOCAL`, `LISTEN/NOTIFY`, сессионные advisory-блокировки, временные
таблицы между транзакциями. Prepared statements — только в PgBouncer 1.21+ с
`max_prepared_statements` (проверь версию), иначе их отключают в драйвере.

</details>

**A4.** ⭐ Что такое проблема read-your-writes на репликах и как её лечат?

<details><summary>Ответ</summary>

Запись прошла на primary, а чтение идёт с реплики, до которой WAL ещё не доехал, — пользователь
не видит своего. Лечат: читать своё с primary N секунд, ждать LSN записи на реплике,
`synchronous_commit = remote_apply` (дорого), write-through в кеш.

</details>

**A5.** ⭐ Почему `links` с `PRIMARY KEY (code)` нельзя партиционировать по `created_at`? Когда
срабатывает pruning?

<details><summary>Ответ</summary>

В `PRIMARY KEY` и `UNIQUE` партиционированной таблицы должны входить все колонки ключа партиции;
с `(code, created_at)` уникальность `code` пропадёт. Поэтому `HASH (code)`. Pruning работает,
только если в `WHERE` есть ключ партиции: `WHERE code = …` читает одну партицию, а
`WHERE owner_id = 42` — все.

</details>

**A6.** Чем партиционирование отличается от шардирования и от реплик?

<details><summary>Ответ</summary>

Партиции — куски таблицы на одном сервере: дешёвое удаление, меньшие индексы, но запись и restore
те же. Реплики — полные копии: растёт чтение и HA, не запись и не объём. Шарды — куски на разных
серверах со своими primary: растут запись и объём, но появляются кросс-шардовые запросы и решардинг.

</details>

**A7.** ⭐ По каким критериям выбирают ключ шарда? Почему `created_at` — плохой ключ?

<details><summary>Ответ</summary>

Высокая кардинальность, равномерность, локальность главных запросов (ключ в `WHERE`),
неизменность. `created_at` с диапазонами монотонен: вся запись идёт в последний шард; при хеше
его нет в горячих запросах.

</details>

**A8.** Hash, range, справочник: по одному плюсу и минусу. Когда справочник?

<details><summary>Ответ</summary>

Hash — равномерно, но диапазон идёт во все шарды. Range — диапазоны в 1–2 шарда, но горячие
диапазоны. Справочник — любое размещение и перенос по одному ключу, но сам становится горячим
путём (его кешируют). Берут, чтобы вынести крупных клиентов на отдельные шарды.

</details>

**A9.** ⭐ Что такое логические шарды и чем плох `hash mod N`?

<details><summary>Ответ</summary>

Фиксированное большое число шардов (1024) и карта «шард → сервер». При росте переносятся целые
логические шарды (~1/N данных), а отображение ключа не меняется. `hash mod N` при 4 → 5
переселяет ~80% ключей.

</details>

**A10.** Как сделать «мои ссылки», если ссылки шардированы по `code`? Какая цена?

<details><summary>Ответ</summary>

Таблица-индекс `owner_index`, шардированная по `owner_id`, заполняется асинхронно через outbox и
идемпотентного потребителя. Цена: eventual consistency (новой ссылки может не быть секунды),
события на удаление и блокировку, возможность пересобрать индекс сканом.

</details>

**A11.** Как получить глобальную уникальность атрибута, который не является ключом шарда?

<details><summary>Ответ</summary>

Сделать атрибут ключом шарда (как `code`); включить ключ шарда в уникальный индекс; завести
таблицу-справочник, шардированную по этому атрибуту (`email → user_id`); использовать ID с
зашитым шардом. Обычный `UNIQUE` проверяет только свой шард.

</details>

**A12.** Опиши решардинг без простоя шагами.

<details><summary>Ответ</summary>

Подготовка (логические шарды, карта v1) → копия снимка и поток изменений на новый сервер →
проверка счётчиков и сумм, теневое чтение → заморозка записи по переносимым ключам на секунды,
лаг 0, карта v2 → обратная репликация на случай отката → уборка источника пачками, удаление слота.

</details>

### Блок B. «Что тут не так»

```
B1.  «Упёрлись в 100 соединений — ставим max_connections = 2000».

B2.  «Читаем „мои ссылки" с реплики сразу после создания — лаг же в миллисекундах».

B3.  CREATE TABLE links (code varchar PRIMARY KEY, …) PARTITION BY RANGE (created_at);

B4.  «Шардируем заказы по status: пять статусов — пять шардов, красиво».

B5.  «Шардируем по месяцу created_at: запись равномерно размажется по времени».

B6.  «Добавим пятый сервер: hash(key) mod 5, переедет около 20% ключей».

B7.  «UNIQUE (email) в каждом шарде — значит, email уникален во всей системе».

B8.  «Создание ссылки пишет в шард кода и шард владельца через 2PC — надёжнее».

B9.  «PgBouncer в transaction-режиме, сервис берёт pg_advisory_lock в начале сессии —
     так и оставим».
```

<details><summary>Ответы</summary>

**B1.** ⚠️ Соединение — процесс: 2000 процессов съедят память и CPU на переключения. PgBouncer и умеренный лимит.

**B2.** ⚠️ Под нагрузкой лаг — секунды, пользователь увидит 404. Primary на время, ожидание LSN или кеш.

**B3.** ⚠️ PostgreSQL не примет PK без ключа партиции. Для ссылок — `HASH (code)`.

**B4.** ⚠️ Низкая кардинальность и перекос, ключа нет в запросе «мои заказы». Ключ — `user_id` или `order_id`.

**B5.** ⚠️ Вся запись идёт в шард текущего месяца — горячий хвост, остальные простаивают.

**B6.** ⚠️ У `mod N` при 4 → 5 переезжает ~80%. Нужны логические шарды и карта.

**B7.** ⚠️ Индекс проверяет только свой шард. Справочник `email → user_id` или шард по email.

**B8.** ⚠️ 2PC блокирующий и медленный. Запись в шард кода плюс outbox и идемпотентный
потребитель, строящий `owner_index`.

**B9.** ⚠️ Сессионная блокировка в `transaction`-режиме не держится: следующий запрос уйдёт на
другое соединение. Нужен `pg_advisory_xact_lock` внутри транзакции.

</details>

#### C1. 🔑 Партиции: pruning и сброс старого

```bash
docker run -d --name pgp -e POSTGRES_PASSWORD=pw -e POSTGRES_DB=linkd -p 55432:5432 postgres:16-alpine
psql -h localhost -p 55432 -U postgres linkd
```

```sql
CREATE TABLE links (
    code varchar(32) COLLATE "C" PRIMARY KEY, long_url text NOT NULL,
    owner_id bigint NOT NULL, created_at timestamptz NOT NULL DEFAULT now()
) PARTITION BY HASH (code);
CREATE TABLE links_p0 PARTITION OF links FOR VALUES WITH (MODULUS 4, REMAINDER 0);
CREATE TABLE links_p1 PARTITION OF links FOR VALUES WITH (MODULUS 4, REMAINDER 1);
CREATE TABLE links_p2 PARTITION OF links FOR VALUES WITH (MODULUS 4, REMAINDER 2);
CREATE TABLE links_p3 PARTITION OF links FOR VALUES WITH (MODULUS 4, REMAINDER 3);
CREATE INDEX links_owner_created ON links (owner_id, created_at DESC);
INSERT INTO links (code, long_url, owner_id)
SELECT substr(md5(g::text), 1, 10), 'https://example.com/' || g, (g % 1000) + 1 FROM generate_series(1, 200000) g;
ANALYZE links;

SELECT code AS c FROM links LIMIT 1 \gset
EXPLAIN (COSTS OFF) SELECT long_url FROM links WHERE code = :'c';
EXPLAIN (COSTS OFF) SELECT code FROM links WHERE owner_id = 42 ORDER BY created_at DESC LIMIT 50;
CREATE TABLE links_bad (code varchar(32) PRIMARY KEY, created_at timestamptz NOT NULL) PARTITION BY RANGE (created_at);

CREATE TABLE clicks (
    event_id bigint GENERATED ALWAYS AS IDENTITY, code varchar(32) NOT NULL, ts timestamptz NOT NULL,
    PRIMARY KEY (event_id, ts)
) PARTITION BY RANGE (ts);
CREATE TABLE clicks_2026_10 PARTITION OF clicks FOR VALUES FROM ('2026-10-01') TO ('2026-11-01');
CREATE TABLE clicks_2026_11 PARTITION OF clicks FOR VALUES FROM ('2026-11-01') TO ('2026-12-01');
CREATE TABLE clicks_default PARTITION OF clicks DEFAULT;
INSERT INTO clicks (code, ts)
SELECT substr(md5((g % 500)::text), 1, 8), timestamptz '2026-10-01' + (g % 45) * interval '1 day' + (g % 86400) * interval '1 second'
FROM generate_series(1, 100000) g;
ANALYZE clicks;
EXPLAIN (COSTS OFF) SELECT count(*) FROM clicks WHERE ts >= '2026-11-10' AND ts < '2026-11-11';
EXPLAIN (COSTS OFF) SELECT count(*) FROM clicks WHERE code = 'abc';
ALTER TABLE clicks DETACH PARTITION clicks_2026_10;
DROP TABLE clicks_2026_10;
```

Сколько партиций читает каждый `EXPLAIN`? Что ответит PostgreSQL на `links_bad`?

<details><summary>Ответ</summary>

По `code` — одна партиция; «мои ссылки» по `owner_id` — все четыре (`Merge Append`). По дню — только
`clicks_2026_11`; по `code` в `clicks` — все, включая `DEFAULT`: ключа времени в условии нет.
`links_bad`: `unique constraint on partitioned table must include all partitioning columns`.
`DETACH` и `DROP` убирают месяц мгновенно, без `DELETE`. Тот же эффект «без ключа — во все» ты увидишь в шардах.

</details>

Что происходит в обоих случаях? Что показывают `cl_active`, `cl_waiting`, `sv_active`?

<details><summary>Ответ</summary>

Напрямую — ошибки `sorry, too many clients already`, как только заняты 100 слотов. Через PgBouncer
300 клиентов работают без ошибок: `sv_active` ≈ 20 (столько, сколько `default_pool_size`),
`cl_waiting` — сотни клиентов стоят в очереди на эти соединения, `cl_active` — те, кому соединение
выдано сейчас. Пул превращает «упали на лимите» в «встали в очередь»; поэтому `cl_waiting` и
`maxwait` — метрики для алерта.

</details>

#### C3. 🔑 Логические шарды, рост 4 → 5 серверов и горячий ключ

```python
# router.py
import hashlib
import random
import string
from collections import Counter

L = 1024                                                      # логических шардов: выбираем один раз
shard_of = lambda code: int.from_bytes(hashlib.blake2b(code.encode(), digest_size=8).digest(), "big") % L
codes = ["".join(random.choices(string.ascii_letters + string.digits, k=7)) for _ in range(200_000)]

m4 = [i % 4 for i in range(L)]                                # карта: логический шард -> сервер
print("ключей на сервер:", sorted(Counter(m4[shard_of(c)] for c in codes).values()))

moved = sum(1 for c in codes if shard_of(c) % 4 != shard_of(c) % 5)
print(f"hash mod N, 4 -> 5: переезжает {moved / len(codes):.0%}")

m5, load = m4[:], Counter(m4)                                 # пятый сервер забирает свою долю шардов
for s in range(L):
    if load[4] >= L // 5:
        break
    if load[m5[s]] > L // 5:
        load[m5[s]] -= 1; load[4] += 1; m5[s] = 4
moved = sum(1 for c in codes if m4[shard_of(c)] != m5[shard_of(c)])
print(f"логические шарды, 4 -> 5: переезжает {moved / len(codes):.0%}; шардов на сервер: {sorted(load.values())}")

traffic = Counter(m4[shard_of(c)] for c in codes[:50_000])    # одна ссылка даёт ~30% трафика
traffic[m4[shard_of(codes[0])]] += 21_000
print("доля трафика:", {s: f"{v / sum(traffic.values()):.0%}" for s, v in sorted(traffic.items())})
```

Запусти `python3 router.py`. Сравни равномерность, долю переезжающих ключей и перекос от горячей
ссылки. Что будет при 16 логических шардах?

<details><summary>Ответ</summary>

По ~50 тыс. ключей на сервер; `hash mod N` переселяет ~80%, логические шарды — ~20% (по 204–205
шардов на сервер); горячая ссылка даёт одному серверу ~47% трафика при ~18% у остальных —
равномерный хеш не спасает от горячего ключа, нужны кеш, CDN или разбиение ключа. При 16
логических шардах 16 не делится на 5 — шарды получатся неравными, а единица переноса — 1/16 данных.
Число логических шардов берут с запасом: 1024 и больше.

</details>

Что нужно сделать дальше для переключения и уборки?

<details><summary>Ответ</summary>

Колонки фильтра публикации (`shard`) нет в replica identity (по умолчанию это PK `code`), поэтому
`UPDATE` и `DELETE` на источнике падают: `Column used in the publication WHERE expression is not
part of the replica identity`. Лечение — уникальный индекс по `(code, shard)` и `REPLICA IDENTITY
USING INDEX` (колонки `NOT NULL`). После этого счётчики и суммы совпадают, лаг слота 0 байт.
Дальше: проверка по всем логическим шардам и теневое чтение; на секунды заморозить запись по
шардам 512–1023, дождаться лага 0, поставить в карту шардов новый сервер, разморозить; держать
обратную репликацию для отката; затем пачками удалить перенесённое на источнике и убрать
подписку, публикацию и слот (иначе WAL копится). Фильтры строк в публикациях — PostgreSQL 15+.

</details>

### Блок D. Инциденты

**D1.** PgBouncer ещё не поставили: поды ходят в PostgreSQL напрямую. После вечернего пика HPA поднял
redirect-сервис до 40 подов. В логах — `sorry, too many clients already`, часть редиректов падает.

<details><summary>Ответ</summary>

Сейчас: уменьшить `maxReplicas` или пул пода, чтобы поды × пул уложились в `max_connections`; смотреть
`pg_stat_activity`. Причина: 40 × 10 = 400 соединений против `max_connections` = 100 — пока трафик был
ниже, пулы не заполнялись до конца, и проблема пряталась. Потом: PgBouncer перед базой (раздел 4),
неравенство поды × пул — в ревью и в алерте, нагрузочный тест на `maxReplicas`.

</details>

**D2.** Ночной бэкфилл дал лаг реплик 40 секунд. Утром: «создал ссылку — открывается 404».

<details><summary>Ответ</summary>

Чтение с отстающих реплик, а write-through в кеш не сработал. Сейчас: вывести отстающие реплики из
пула, читать «свежее» с primary с лимитом. Потом: бэкфиллы пачками с паузами по лагу, health-check
по лагу, ожидание LSN для «своего» чтения, алерт на лаг.

</details>

**D3.** Миграция `ADD COLUMN` на 16 шардах: на 14 прошла, на двух упала по `lock_timeout`;
приложение с новым кодом уже выкачено.

<details><summary>Ответ</summary>

Новый код падает на двух шардах. Сейчас: найти долгую транзакцию, повторить миграцию на упавших
шардах, при необходимости откатить выкатку. Потом: порядок «миграция на всех шардах → проверка
дрейфа → выкатка кода», expand/contract, канарейка на одном шарде.

</details>

**D4.** Во время переноса шарда диск primary заполнен на 98%, место занимает WAL.

<details><summary>Ответ</summary>

Слот репликации держит WAL: подписчик отстал или остановлен, либо слот остался после отмены
переноса. Сейчас: оживить подписчика, чтобы слот продвинулся; если перенос отменён — `DROP
SUBSCRIPTION` и `pg_drop_replication_slot`; при нужде расширить диск. Потом: алерт на лаг слотов
и диск источника, `max_slot_wal_keep_size` как страховка, решардинг при 60–70% диска.

</details>

### Блок E. Вопросы с собеседования

**1.** Как масштабировать базу данных и в каком порядке?

<details><summary>Ответ</summary>

По лестнице, каждая ступень — по сигналу: запросы и индексы, вертикально, пул соединений,
реплики, кеш, партиции, разделение по сервисам, шарды. Сначала выясняю, какой ресурс кончился.

</details>

**2.** Почему нельзя просто поднять `max_connections`?

<details><summary>Ответ</summary>

Соединение — процесс: растут память и переключения контекста, а полезный параллелизм ограничен
ядрами. Нужное число соединений по закону Литтла невелико. Решение — PgBouncer в `transaction`-режиме.

</details>

**3.** Как выбрать ключ шарда?

<details><summary>Ответ</summary>

Кардинальность, равномерность, локальность главных запросов, неизменность. Сокращатель —
`code`, SaaS — `tenant_id`, мессенджер — `chat_id`.

</details>

**4.** Что такое логические шарды и зачем они?

<details><summary>Ответ</summary>

Фиксированное число шардов (например, 1024) и карта «шард → сервер»: рост — перенос целых шардов,
отображение ключа не меняется. `hash mod N` при изменении N переселяет большую часть данных.

</details>

**5.** Как сделать запрос по полю, не являющемуся ключом шарда?

<details><summary>Ответ</summary>

Scatter-gather во все шарды (дорого: хвост задержки и доступность) или глобальный индекс —
таблица, шардированная по этому полю и обновляемая асинхронно через outbox; цена — eventual consistency.

</details>

**6.** Как перейти с одной БД на шарды без простоя?

<details><summary>Ответ</summary>

Логическая репликация или двойная запись плюс бэкфилл, проверка суммами и теневым чтением,
переключение карты шардов с коротким замораживанием записи, обратная репликация для отката, уборка.

</details>

**7.** Когда ты бы не стал шардировать?

<details><summary>Ответ</summary>

Когда не исчерпаны ступени 1–7, нет измеренного сигнала (restore дольше RTO, запись или объём у
потолка), команда мала. Шардирование умножает эксплуатацию на число шардов.

</details>

**8.** Citus, Vitess, CockroachDB или шардировать самим?

<details><summary>Ответ</summary>

От стека и людей: PostgreSQL и мультиарендность — Citus; большой MySQL — Vitess; запись в нескольких
регионах и сильная согласованность — распределённый SQL ценой задержки записи; простая модель
(`code → url`) и готовая команда — шардирование в приложении; мало людей — managed.

</details>
