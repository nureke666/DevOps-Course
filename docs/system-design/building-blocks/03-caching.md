## 1. Зачем кеш и сколько он стоит

**Кеш** — копия данных там, где их быстрее прочитать, чем в источнике. Копия — это предположение
«источник с тех пор не изменился». Пока оно верно, кеш выигрывает; когда нет — кеш **врёт**.

| Цель | Что даёт | Пример в linkd |
|------|----------|----------------|
| Задержка | Ответ из памяти вместо похода в базу | Редирект ~1 мс из Redis вместо ~10 мс из реплики |
| Разгрузка источника | База видит только промахи: `RPS × (1 − hit)` | 20 000 RPS в пике → 2 000 RPS до реплик при hit 90% |
| Буфер при сбое | Горячие данные доступны, пока источник недоступен | Primary PostgreSQL упал — редиректы живут из кеша |

Цена — три вещи, о которых говори вслух:

1. **Устаревание.** Между изменением в источнике и моментом, когда кеш узнает о нём, читатели видят
   старое: консистентность становится *eventual* ([Распределённые системы: 02](/distributed/02-consistency-cap)).
2. **Ещё одна система в эксплуатации:** память, отказы, обновления, дежурства.
3. **Скрытая несущая конструкция.** Если без кеша источник не выдерживает нагрузку, кеш — уже не
   оптимизация, а часть ёмкости, и его отказ — авария (раздел 11).

> ⚠️ Кеш — не лекарство от плохого запроса. Сначала индекс, потом пул соединений (linkd 2.0 открывает
> новое соединение на каждый запрос — это чинится PgBouncer, а не кешем), и только потом кеш
> ([Сокращатель ссылок, раздел 7](/system-design/backend-cases/01-url-shortener)).

**Два вопроса перед любым кешем:** сколько устаревания терпит эта операция (секунды для редиректа,
ноль для баланса)? Что будет, когда кеш пуст или недоступен? Первый задаёт TTL и инвалидацию, второй — план отказа.

## 2. Уровни кеша

```text:no-line-numbers
 браузер ─► CDN/edge ─► gateway / nginx ─► сервис ─► Redis ─────► БД
 private    shared      shared            L1: память  L2: общий    буфер БД +
 cache      cache       cache             пода        для подов    page cache ОС
 ≈ 0 мс     ≈ 10–30 мс  ≈ 1 мс            ≈ мкс       ≈ 0,3–1 мс   ≈ 0,1 мс из памяти,
 (от пользователя)                                    (одна AZ)    1–10 мс с диска
 ↑ порядки величин: меряй на своём железе
```

| Уровень | Что кеширует | Инвалидация | Главный риск |
|---------|-------------|-------------|--------------|
| Браузер | Ответы по `Cache-Control`, `ETag` | Только TTL — до клиента не достучаться | Долгий `max-age` на изменяемом: починить нечем |
| CDN / edge | Статика и (осторожно) ответы API | TTL, purge по URL или тегу | Персональный ответ в общем кеше (раздел 10); подробно — [тема 01](/system-design/building-blocks/01-edge-dns-cdn-lb) |
| Gateway / прокси | Ответы upstream (nginx `proxy_cache`, Varnish) | TTL, purge | Ключ без нужных `Vary` |
| L1 в процессе | Объекты в куче пода (Caffeine, `cachetools`, `lru_cache`) | TTL в секундах; общей инвалидации между подами нет | У каждого пода своя копия: расхождение до TTL |
| L2 распределённый | Redis, Memcached | `DEL`, TTL, версии ключей | Сетевой ход, отказ, память, горячий ключ |
| Буфер БД | Страницы (`shared_buffers` PostgreSQL) и page cache ОС | Автоматически | Данные и индексы не помещаются в RAM — чтение с диска |

**HTTP-кеш.** `max-age` — для всех кешей, `s-maxage` — только для общих (CDN, прокси), `private` —
только браузер, `no-store` — не хранить нигде. ⚠️ `no-cache` не значит «не кешировать»: кеш хранит ответ,
но обязан перепроверить его у источника (`ETag` / `If-None-Match` → `304`). Расширения
`stale-while-revalidate` и `stale-if-error` ([RFC 5861](https://www.rfc-editor.org/rfc/rfc5861))
разрешают отдать устаревшее, пока свежее грузится или источник недоступен.

**Redis или Memcached.** Memcached проще: многопоточный, строки, без репликации и персистентности в
базовой поставке, шардирование на стороне клиента. Redis — ещё структуры данных, TTL на ключ, репликация,
Lua, `SET NX` для блокировок; команды исполняет один поток. Берут почти всегда Redis (или совместимый
форк вроде Valkey — актуальное состояние лицензий проверяй), потому что он пригодится ещё и под лимитеры
и блокировки.

**L1 + L2.** Типичная связка горячего пути: L1 с TTL в секунды (разгружает Redis и горячий ключ) и
Redis с TTL в часы. Цена L1 — после изменения данные устаревают до истечения L1-TTL; для редиректа
linkd это допустимые секунды (разбор, 6.3).

## 3. Паттерны чтения и записи

### 3.1 Cache-aside (lazy loading)

Приложение само ходит и в кеш, и в базу. Самый распространённый паттерн.

```text:no-line-numbers
 приложение                         кеш                       БД
     │── GET key ───────────────────►│                          │
     │◄─ miss ───────────────────────│                          │
     │── SELECT … ─────────────────────────────────────────────►│
     │◄─ строка ───────────────────────────────────────────────│
     │── SET key value EX ttl ──────►│                          │
 запись:  UPDATE ─► COMMIT ─► DEL key        (следующее чтение заполнит кеш само)
```

Плюсы: кеш не обязателен для работы (упал — идём в базу), кешируется только прочитанное. Минусы: первый
запрос всегда промах; логика размазана по вызовам (выноси в одну функцию); есть гонка читателя и писателя
(раздел 5).

### 3.2 Read-through

Приложение говорит только с кеш-слоем, а тот сам грузит данные при промахе.

```text:no-line-numbers
 приложение ── get(key) ──► кеш-слой ── (промах) ── load(key) ──► БД
                               └─ сохранил, вернул ◄──────────────┘
```

Это cache-aside с загрузчиком внутри: `LoadingCache` в Caffeine и Guava, `proxy_cache` в nginx, любой CDN.
Плюс — одно место загрузки и естественное слияние одинаковых промахов (раздел 6).

### 3.3 Write-through

Запись идёт через кеш-слой и синхронно попадает в базу; кеш содержит последнее записанное.

```text:no-line-numbers
 приложение ── write(key, val) ──► кеш-слой ── INSERT/UPDATE ──► БД
      ◄──────────────── OK ───────────┘ положил в кеш  ◄── OK ───┘
```

На практике это «записали в БД, закоммитили, сделали `SET`» — так linkd делает при создании ссылки.
Работает для **неизменяемых** или редко меняющихся данных: код ссылки не меняется, гонки писателей нет.
⚠️ Для изменяемых данных с несколькими писателями `SET` вместо `DEL` опасен: два обновления могут
попасть в кеш в порядке, обратном порядку коммитов. Минус паттерна — запись медленнее, а в кеш попадает то,
что никто не прочитает.

### 3.4 Write-behind (write-back)

Запись сначала попадает в кеш или буфер, в базу уходит позже пачками.

```text:no-line-numbers
 приложение      кеш / буфер                  воркер                БД
     │── write ───►│ принял, ответил OK
     │◄─ OK ───────│──── раз в секунду, пачкой ──►│── INSERT batch ──►│
 ⚠️ кеш или воркер упали до сброса → подтверждённые записи потеряны
```

Плюсы: быстрая запись, схлопывание повторных записей (счётчик вырос 100 раз — в базу одна запись).
Минусы: окно потери, порядок и ретраи — на тебе. Подходит для счётчиков, метрик, событий; **не** для денег
и ссылок. Клики linkd — по сути write-behind: буфер → Kafka → ClickHouse с осознанной потерей до 0,1%.

### 3.5 Write-around

Запись идёт только в базу, мимо кеша; кеш заполняется при чтении. Подходит, когда пишут часто, а читают
редко (логи, загрузки, история): запись не вытесняет нужное. Это cache-aside с `DEL` при записи.

### Что выбрать

| Паттерн | Читает | Пишет | Свежесть | Когда подходит |
|---------|--------|-------|----------|----------------|
| Cache-aside | Приложение: кеш, потом база | В базу, затем `DEL` | Eventual, ограничена TTL | По умолчанию для большинства |
| Read-through | Кеш-слой грузит сам | В базу | Как у cache-aside | Есть библиотека или прокси с загрузчиком |
| Write-through | Из кеша | Кеш-слой и база синхронно | Высокая для записанного | Неизменяемое, нужно «записал — сразу прочитал» |
| Write-behind | Из кеша | В кеш, в базу позже | Кеш новее базы | Счётчики, метрики, события; потеря допустима |
| Write-around | Кеш → база | Только в базу | Eventual | Запись частая, чтение редкое |

> ⭐ Выбор — **на операцию**: чтение редиректа — cache-aside + L1, создание ссылки — write-through в
> Redis, клики — write-behind через очередь. Одним паттерном на сервис не обойтись.

## 4. TTL и джиттер

**TTL** — не «сколько влезет», а **максимальное время, которое пользователь может видеть устаревшее**.

| Данные | Допустимое устаревание | TTL |
|--------|------------------------|-----|
| Цель ссылки linkd (меняется редко, удаление — через `DEL`) | Секунды после удаления | 24 ч в Redis, 5–30 с в L1 |
| Негативный ответ «ссылки нет» | Минута | 30–60 с |
| Курс валют, каталог | Минуты | 1–10 мин |
| Баланс, остатки, права доступа | Ноль или секунды | Не кешируем, либо 1–5 с с событиями |

> ⭐ TTL нужен **даже при активной инвалидации**: любая схема `DEL` когда-нибудь потеряет сообщение
> (Redis недоступен, failover «съел» команду). Без TTL ошибка живёт вечно, с TTL — не дольше TTL.

**Джиттер.** Если миллион ключей прогреть одним батчем с TTL ровно 3600 с, через час они истекут разом и
миллион промахов уйдёт в базу — **cache avalanche**. Лечится разбросом:

```python
import random

def ttl_with_jitter(base: int, spread: float = 0.1) -> int:
    return int(base * random.uniform(1 - spread, 1 + spread))   # 86 400 ± 10%
```

Redis удаляет просроченное **лениво** (при обращении) и **активно** (выборочно проверяет ключи с TTL), поэтому
просроченные ключи какое-то время занимают память, а массовое истечение даёт всплеск CPU.

## 5. Инвалидация

Запись в базу и удаление из кеша — **две операции без общей транзакции**. Между ними (и до них) кто-то
успевает прочитать.

### 5.1 Порядок: удаляем после коммита

| Порядок | Что случается |
|---------|---------------|
| `DEL` → `COMMIT` | Между ними читатель прочитал старое из базы и положил в кеш — старое осталось надолго. ⚠️ |
| `COMMIT` → `DEL` | Окно устаревания — от коммита до `DEL`, миллисекунды. ✅ |
| `SET` до коммита | Откат оставит в кеше значение, которого в базе нет. ⚠️ |

### 5.2 Классическая гонка: старое возвращается в кеш

Даже при правильном порядке читатель мог **прочитать старое до** коммита, «зависнуть» (пауза GC, сеть) и
положить его в кеш **после** `DEL`:

```text:no-line-numbers
 t   читатель A                      писатель B                    кеш      БД
 1   GET key → промах                                              —        v1
 2   SELECT → v1                                                   —        v1
 3                                   UPDATE …; COMMIT               —        v2
 4                                   DEL key                        —        v2
 5   SET key = v1   ◄ «проснулся»                                   v1 ✗     v2
 6   … до конца TTL все читают v1                                   v1       v2
```

**Вариант с репликой** — самый частый на проде. Читатель промахивается и читает с **реплики**, которая
отстаёт на 200 мс: запись и `DEL` на primary уже прошли, реплика отдаёт v1 — и читатель кладёт его в кеш
на весь TTL. Лаг репликации — то же окно гонки, только длиннее.

| Способ закрыть | Как | Цена |
|----------------|-----|------|
| TTL как потолок | Ошибка живёт не дольше TTL | Ничего; но «не дольше TTL» бывает долго |
| Отложенный повторный `DEL` | `DEL` после коммита и ещё раз через время больше лага реплики (например, 1 с) | Хак, но работает; нужен таймер или очередь |
| Версионные ключи | Версия — отдельным ключом (`INCR` при изменении), в ключ данных входит версия: `user:42:v17`. Читатель берёт версию **до** базы, и его запоздалый `SET` попадает в ключ мёртвой версии | Лишний запрос за версией; мусор вытесняется сам |
| Lease / CAS | При промахе читатель получает токен; инвалидация его аннулирует, `SET` по отозванному токену отвергается (так сделано в Memcached в Facebook, статья «Scaling Memcache at Facebook», NSDI 2013). В Redis — токен в ключе + Lua «положить, если токен совпал» | Сложнее код, зато строгая гарантия |
| Читать с primary после записи | Для только что изменённых ключей — запрос в primary ([Распределённые системы: 02, раздел 7](/distributed/02-consistency-cap)) | Нагрузка на primary |

Рабочее правило: **`COMMIT` → `DEL` (`UNLINK` для больших значений) + TTL**, а там, где устаревание больно, —
версионные ключи или lease. Скрипт, воспроизводящий гонку и закрывающий её арендой, — в практике C4.

### 5.3 Откуда берётся сигнал инвалидации

| Источник | Как | Плюсы | Минусы |
|----------|-----|-------|--------|
| Приложение после коммита | `DEL` рядом с `UPDATE` | Просто | Не видит записей мимо кода: ручной `UPDATE`, миграция, другой сервис |
| Outbox | Событие «ключ изменён» пишется в ту же транзакцию, воркер делает `DEL` с ретраями ([тема 06](/system-design/building-blocks/06-async-messaging)) | Не теряется при сбое Redis | Задержка, ещё один компонент |
| CDC | Журнал базы (WAL) → брокер → инвалидатор делает `DEL` | Видит **все** записи; не зависит от кода | Инфраструктура; задержка от сотен мс до секунд |
| Версионирование | Меняем версию в ключе, а не удаляем | Нет гонки удаления | Лишний `GET`, мусор |
| Client-side caching Redis | Сервер сам шлёт клиентам сообщения об изменении ключей (`CLIENT TRACKING`, Redis 6+) | Инвалидация L1 без TTL-хаков | Память сервера; нужна поддержка клиента |

> ⚠️ **Потерянный `DEL`.** Redis недоступен в момент удаления или Sentinel сделал failover на реплику, не
> получившую команду (репликация асинхронная) — удалённая запись «воскреснет». Отсюда ретраи или outbox
> для инвалидации и TTL как последняя защита.

## 6. Stampede, avalanche, penetration

Три разные беды с похожим симптомом — «внезапно все идут в базу».

| Беда | Что происходит | Лекарство |
|------|----------------|-----------|
| **Stampede / dogpile** | Одна горячая запись истекла, тысяча одновременных промахов идёт за ней в базу | Слияние запросов, блокировка, раннее обновление, stale-while-revalidate |
| **Avalanche** | Много записей исчезли разом: одинаковый TTL, рестарт кеша | Джиттер, прогрев, защита базы (раздел 11) |
| **Penetration** | Запрашивают ключи, которых нет нигде (боты, перебор), каждый запрос идёт до базы | Негативный кеш, лимиты, иногда фильтр Блума |

### 6.1 Защита от stampede

**1. Слияние запросов (single-flight).** Внутри пода за ключом в базу идёт один запрос, остальные ждут
его результат. Прокси делают это сами: `proxy_cache_lock on` в nginx, request collapsing на CDN. В Go —
`singleflight`, в Java — `LoadingCache`.

```python
import threading

lock = threading.Lock()
in_flight: dict[str, threading.Event] = {}

def get_singleflight(key, cache, load):
    if key in cache:
        return cache[key]
    with lock:
        if key in cache:                           # пока ждали замок, лидер мог уже загрузить
            return cache[key]
        event = in_flight.get(key)
        leader = event is None
        if leader:
            event = in_flight[key] = threading.Event()
    if leader:
        try:
            cache[key] = load(key)                 # в базу идёт один поток
        finally:
            with lock:
                del in_flight[key]
            event.set()                            # будим ждущих
    else:
        event.wait(timeout=2)                      # ждём лидера, а не идём в базу
    return cache.get(key)
```

Слияние работает **внутри процесса**: 30 подов дадут до 30 запросов за ключом, не 1000 — обычно достаточно.

**2. Блокировка в Redis**, когда и 30 лишние: `SET lock:aZ3x9Qk <токен> NX PX 2000` — `NX` значит «только
если ключа нет», `PX` — автоснятие через 2 с. Получил `OK` — иди в базу, положи значение, сними блокировку
Lua-скриптом «удалить, если токен мой». Получил `nil` — подожди 20–50 мс и перечитай кеш.
⚠️ Без TTL блокировка повиснет навсегда, а чужую снимать нельзя — только по своему токену.

**3. Раннее обновление с вероятностью (XFetch).** Читатель перед истечением с растущей вероятностью сам
обновляет значение, пока оно ещё в кеше. Формула из статьи Vattani и др. (VLDB 2015): обновляем, если
`now − δ · β · ln(rand()) ≥ expiry`, где `δ` — время пересчёта, `β` обычно 1.

**4. Stale-while-revalidate.** В кеше две границы: «мягкая» (значение считается устаревшим) и «жёсткая»
(удаляется). Между ними читатель получает **старое сразу**, а обновление идёт в фоне. Цена — ограниченная
устарелость. В HTTP — `stale-while-revalidate`, в nginx — `proxy_cache_use_stale updating` с
`proxy_cache_background_update`.

### 6.2 Penetration и негативный кеш

**Негативный кеш** — запомнить «ключа нет» (пустое значение или маркер). Правила:

- **Короткий TTL** (30–60 с): длинный сломает только что созданную запись. В linkd это закрывает
  write-through — `SET` при создании перезаписывает маркер (разбор, 6.3).
- **Отличай «нет» от «ошибка».** Таймаут или 5xx базы нельзя класть в кеш как отсутствие данных — короткий
  сбой превратится в 404 на весь TTL.
- **Защита глубже.** Лимит на число 404 с IP ([тема 08](/system-design/building-blocks/08-rate-limiting)).
  Фильтр Блума по всем существующим ключам отсекает несуществующие, но для 6 млрд кодов linkd он весил бы
  около 7 ГБ (≈ 9,6 бита на ключ при 1% ложных срабатываний) и обновлялся бы при каждом создании — пока
  хватает лимитов и негативного кеша, он не нужен.

## 7. Горячие ключи

**Горячий ключ** — один ключ с непропорциональной долей запросов (вирусная ссылка: 50 000 RPS). Redis
исполняет команды одним потоком, ключ живёт на одном шарде — шард упирается в CPU, остальные простаивают.
⚠️ **Redis Cluster не помогает**: ключ — один слот, слот — один шард.

Найти: `redis-cli --hotkeys` (только при LFU-политике), метрики «запросов на ключ» в приложении,
неравномерность CPU по шардам. `MONITOR` — только на минуты: он сам дорог.

| Способ | Как | Цена |
|--------|-----|------|
| L1 в подах | Короткий TTL (5–30 с, как в задаче 01): 30 подов превращают 50 000 RPS по ключу в ≤ 30 запросов к Redis за период TTL | Устаревание до секунд |
| CDN / `s-maxage` | Горячая ссылка отдаётся с edge | Инвалидация — purge ([тема 01](/system-design/building-blocks/01-edge-dns-cdn-lb)) |
| Реплики чтения Redis | Читать горячие ключи с реплик | Реплика отстаёт; нужен клиент, умеющий читать с реплик |
| Разбиение ключа | `link:aZ3#0 … link:aZ3#7`, читаем случайную копию — нагрузка делится по шардам | Запись и инвалидация — во все копии; нужно знать, какие ключи горячие |

> ⭐ Сначала L1: он бесплатен по инфраструктуре и убирает основную долю запросов. Остальное — когда его мало.

## 8. Вытеснение и размер кеша

Когда память кончилась, решаем, **кого выкинуть**: **LRU** выбрасывает давно не тронутое (просто, но один
большой скан вымывает горячее); **LFU** — редко используемое (держит популярное, устойчив к сканам, но
медленно «забывает» прошлых любимцев). В Redis политика — `maxmemory-policy`:

| Значение | Что делает |
|----------|------------|
| `noeviction` | **По умолчанию.** Память кончилась — записи отвергаются: `OOM command not allowed` |
| `allkeys-lru` / `allkeys-lfu` | Выкидывает среди **всех** ключей; для чистого кеша — это оно |
| `volatile-lru` / `volatile-lfu` / `volatile-ttl` | Только ключи **с TTL**; если таких нет — ведёт себя как `noeviction` |
| `allkeys-random` / `volatile-random` | Случайно |

⚠️ По умолчанию `maxmemory` равен `0` (лимита нет — Redis растёт, пока его не убьёт ОС) и политика
`noeviction`. Для кеша нужно задать оба. Redis использует **приближённые** LRU и LFU: берёт несколько
случайных ключей (`maxmemory-samples`, по умолчанию 5) и выкидывает худший. Для read-heavy кеша с
популярным хвостом, как в linkd, — `allkeys-lfu`.

**Размер.** Память ≈ `ключей × (ключ + значение + накладные расходы)`, накладные расходы Redis — десятки
байт на ключ (меряй `MEMORY USAGE`). Для linkd из разбора: ~200 Б на запись, горячий набор — десятки ГБ
(оценка сверху ~35 ГБ). `maxmemory` — не размер машины: нужен запас на буферы клиентов и репликации,
фрагментацию и копирование при снимке, поэтому `maxmemory` — порядка 65–75% памяти инстанса.

**Размер и hit ratio — не линейно.** Запросы подчиняются закону Ципфа: небольшая «голова» ключей получает
основную долю. Симуляция из практики C2 (100 000 ключей, LRU) даёт примерно:

| Кеш, % ключей | s = 0,8 («мягкое») | s = 1,0 | s = 1,2 («крутое») |
|---------------|--------------------|---------|--------------------|
| 1% | ~20% | ~50% | ~80% |
| 10% | ~47% | ~74% | ~92% |
| 50% | ~79% | ~91% | ~97% |

Первые проценты памяти дают больше всего, последние гигабайты — почти ничего. И hit ratio зависит от
**формы распределения**: свой профиль нужно мерить (для linkd — по логам в ClickHouse), а не брать «80/20»
как факт.

## 9. Hit ratio в числах

**Hit ratio** = `hits / (hits + misses)`. Три формулы на каждый случай:

```text:no-line-numbers
 нагрузка на источник                          = RPS × (1 − hit)
 средняя задержка (грубо)                      = hit × t_кеш + (1 − hit) × t_источника
 одновременных запросов к базе (закон Литтла)  = RPS × (1 − hit) × t_источника
```

Точнее, промах платит ещё за проверку кеша и запись в него, но для порядка величин хватает грубой формулы.
Числа linkd: пик 20 000 RPS, `t_кеш` = 1 мс (Redis в той же зоне), `t_БД` = 10 мс (реплика через
PgBouncer), две реплики чтения, допущение — по 3 000 RPS точечных чтений каждая (как «1 000 RPS на под» в
разборе: на работе это замер, не догадка).

| Hit ratio | RPS до реплик | Загрузка двух реплик (из 6 000) | Запросов к БД одновременно | Средняя задержка |
|-----------|--------------|--------------------------------|----------------------------|------------------|
| 0% (кеша нет) | 20 000 | 333% — не выдержим | 200 | 10 мс |
| 80% | 4 000 | 67% | 40 | 2,8 мс |
| 90% | 2 000 | 33% | 20 | 1,9 мс |
| 95% | 1 000 | 17% | 10 | 1,45 мс |
| 99% | 200 | 3% | 2 | 1,09 мс |
| 99,9% | 20 | 0,3% | 0,2 | 1,01 мс |

- ⭐ **Средняя задержка почти не реагирует на hit ratio, а нагрузка на базу — кратно.** С 95% до 99% средняя
  задержка улучшилась на 0,36 мс, а база разгрузилась в 5 раз. Кеш считают **по нагрузке на источник**.
- ⭐ **p99 зависит от промахов.** Если промахов больше 1%, p99 сервиса — это хвост пути через базу. При hit
  95% худший 1% запросов — это 20% худших промахов, то есть p80 пути к базе. Для SLO «p99 ≤ 50 мс» важно, как
  база ведёт себя **под нагрузкой промахов**.
- **Усреднение маскирует провалы.** 97% «за сутки» могут скрывать 20 минут ночью с 40%. Смотри по минутам,
  по слоям и типам ключей.
- **Слои перемножаются.** L1 ловит 50%, Redis — 90% оставшегося: до базы доходит `0,5 × 0,1 = 5%`, общий
  hit 95%. Измеряй каждый слой (`linkd_cache_requests_total` с лейблами слоя и результата — целевая метрика
  из разбора, в linkd 2.0 её пока нет).

**Окупается ли кеш.** Без него база должна держать 20 000 RPS: при 3 000 на реплику — 7–8 реплик вместо двух.
С кешем — две реплики плюс Redis на десятки ГБ RAM с репликой. Кеш выигрывает, когда `RAM под кеш + его
эксплуатация < стоимость реплик, которые он заменяет`, **и** команда готова жить с устареванием. На малой
нагрузке (100 RPS чтения) хватит индекса и пула соединений.

## 10. Что нельзя кешировать (или только с оговорками)

| Что | Чем опасно | Правильно |
|-----|-----------|-----------|
| **Решения авторизации** | Права отозвали, а кеш ещё час разрешает — дыра в безопасности | Не кешировать, либо TTL в секунды + событие «права изменились» → `DEL`; подпись JWT кешировать можно |
| **Деньги и остатки при решениях** | Устаревший баланс → двойное списание, продажа несуществующего | Решения — по источнику правды (с блокировкой или версией); кеш — только для показа |
| **Персональные данные** | Общий кеш отдаёт ответ одного пользователя другому; ПДн в Redis живут дольше нужного | `private` или `no-store`, `Vary`; пользователь в ключе; короткий TTL; удаление по запросу — по всем слоям |
| **Ключи идемпотентности** | Вытеснение или рестарт → операция выполнится дважды | В базе, в одной транзакции с операцией |
| **Ошибки как «данных нет»** | Короткий сбой → долгое 404 | Не кешировать 5xx и таймауты |
| **Данные с «читаю сразу после записи»** | Автор не видит свою правку | Write-through или чтение с primary |
| **Сессии, очереди, счётчики лимитов** | Это состояние, а не кеш: вытеснение = потеря | Отдельный инстанс с `noeviction` и персистентностью (12.5), [тема 08](/system-design/building-blocks/08-rate-limiting) |

> ⚠️ Классический инцидент: `GET /api/me` закеширован на CDN без `Vary` и `private` — пользователи видят
> чужие профили. Ответы с `Set-Cookie` или `Authorization` по умолчанию не должны попадать в общий кеш.

## 11. Холодный старт и отказ кеша

**Холодный старт** — кеш пуст: рестарт Redis, потеря инстанса, `FLUSHALL`, смена формата ключей. Нагрузка,
которую держал кеш, мгновенно уходит в базу.

Пример linkd. Redis перезапустился пустым в пик (20 000 RPS). L1 ловит, допустим, половину (допущение: TTL
5–30 с, 100 тыс. записей на под). Остальные 10 000 RPS идут в базу, две реплики держат 6 000:

```text:no-line-numbers
 без защиты:  10 000 RPS в базу → реплики перегружены → запросы ждут → пул подов исчерпан →
              таймауты, в том числе у запросов, которые мог бы обслужить L1 → каскад
 с защитой:   ограничитель параллельности пускает в базу ≲ 4 500 RPS, ≈ 5 500 RPS получают быстрый 503
              (≈ 27% всех запросов), горячие ключи заполняются, hit ratio растёт, ошибки уходят
```

Ошибки не бесплатны: 5 минут по ~27% — это около 1,4 минуты «полного простоя», ≈ 6% месячного бюджета
99,95% (21,6 мин). Защита базы превращает катастрофу в управляемую деградацию. На средней нагрузке
(4 000 RPS) та же авария проходит почти без ошибок: 2 000 RPS промахов база выдержит. Опасное окно — пик.

**Прогрев:**

- **Органический** — кеш заполняется по промахам. Медленно: ~70 млн ключей горячего набора при ≤ 3 000
  промахов в секунду — часы. Зато «голова» заполняется за первые минуты: hit ratio растёт быстрее памяти.
- **Активный** — скрипт читает топ-N ключей (для linkd — из ClickHouse по кликам за сутки) и заливает в Redis
  конвейером (pipeline) **до** переключения трафика; оценка — десятки минут. Ограничивай скорость, чтобы
  прогрев сам не положил реплики.
- **Постепенное включение** — трафик на новый кеш долями (10% → 50% → 100%).
- **Не очищай кеш без причины.** `FLUSHALL` после деплоя — самодельная авария; для смены формата данных
  используй версию в ключе (12.1).

Проектируй так, чтобы кеш мог исчезнуть в любой момент, а пользователи это пережили (12.4).

## 12. ⚙️ Эксплуатация

Семь стандартных вопросов из
[Основы: 04. Бэкенд-собес и DevOps-собес](/system-design/basics/04-backend-vs-devops) — для кеша на примере
Redis перед linkd.

### 12.1 Развёртывание

| Топология | Что это | Отказоустойчивость | Когда брать |
|-----------|---------|--------------------|-------------|
| Один инстанс | Один процесс | Нет: упал — кеш пуст | Dev, тесты, второстепенный кеш |
| Primary + реплики + Sentinel | Асинхронная репликация; 3 процесса Sentinel (в разных зонах) решают, что primary упал, и повышают реплику | Автоматический failover; по умолчанию Sentinel считает primary упавшим через 30 с (`down-after-milliseconds`) | Данные влезают в одну машину — случай linkd (~35 ГБ) |
| Redis Cluster | 16 384 слота между шардами, у каждого реплики; клиент должен понимать кластер | Failover на уровне шарда; потеря шарда — потеря его доли ключей | Не влезает в одну машину или отказ узла не должен обнулять весь кеш |
| Managed (облачный Redis) | Облако ведёт репликацию, failover, патчи | Мульти-AZ по галочке | Команда маленькая, цена RAM + сервиса приемлема |

В Kubernetes stateful-часть держат оператором или Helm-чартом, либо берут managed: свой Redis в k8s — ещё
один stateful-компонент со своими PVC, PDB и обновлениями.

```text:no-line-numbers
# redis.conf для кеша — отправная точка, не догма
maxmemory 48gb                    # ~70% от 70 ГБ RAM инстанса
maxmemory-policy allkeys-lfu      # без лимита и политики кеш не кеш
maxclients 10000                  # по умолчанию 10000; считай поды × размер пула
save ""                           # снимки выключены: нет fork-пауз, но рестарт = холодный старт
appendonly no
slowlog-log-slower-than 10000     # мкс; в slowlog попадёт всё, что дольше 10 мс
```

**Персистентность — точно.** В Redis 7.x по умолчанию **включены RDB-снимки** по правилам `save`
(`3600 1 300 100 60 10000`: раз в час при ≥ 1 изменении, раз в 5 минут при ≥ 100, раз в минуту при ≥ 10 000;
до 7.0 было `900 1 300 10 60 10000`) и **выключен AOF** (`appendonly no`). В официальном Docker-образе то же
самое — проверяй `CONFIG GET save` и `CONFIG GET appendonly`.

| Режим | Что даёт | Что стоит |
|-------|----------|-----------|
| Без персистентности (`save ""`) | Нет `fork`, нет нагрузки на диск | Рестарт = пустой кеш |
| RDB (по умолчанию) | Рестарт поднимается из последнего снимка, теряем изменения после него (TTL хранится как абсолютное время) | `fork` при снимке: пауза и всплеск памяти за счёт copy-on-write |
| AOF (`appendonly yes`, `appendfsync everysec` по умолчанию) | Потеря до ~секунды записей | Больше записи на диск, перезапись журнала; для кеша обычно избыточно |

Для чистого кеша разумно «ничего» или «RDB раз в час»; AOF — когда Redis хранит данные, которых больше нигде
нет (12.5).

**Выкатка.** Обновление Redis: реплика → failover → старый primary; клиентам нужны ретраи на переподключение.
Конфиг и пароли — через Secret. ⭐ **Формат значений при rolling update.** Старые и новые поды работают
**одновременно** и читают один Redis; если новая версия поменяла формат значения, старые получат мусор.
Решение — **версия формата в префиксе ключа** (`v1:link:…` → `v2:…`): версии живут рядом, старые ключи
вытесняются сами. Миграция кеша — не `FLUSHALL`.

### 12.2 Масштабирование

| Компонент | Как масштабируется | Метрика | Потолок |
|-----------|--------------------|---------|---------|
| L1 | Вместе с подами (HPA) | Память пода, hit ratio L1 | Память × число подов; расхождение копий |
| Redis: чтение | Реплики чтения | CPU и ops/s узла | Реплика отстаёт; клиент должен уметь читать с реплик |
| Redis: объём | Redis Cluster | `used_memory` / `maxmemory` на шард | Чем больше RAM у шарда, тем дольше `fork` и снимок |
| Redis: пропускная способность | Больше шардов | CPU шарда (**один поток**), ops/s | ⚠️ Горячий ключ: шардами не лечится |
| Соединения | Пул в подах | `connected_clients` | Поды × пул ≤ `maxclients`; при автоскейлинге — по `maxReplicas` |

Redis для linkd нужен не из-за RPS: 20 000 GET/с — малая часть возможностей одного узла (порядка сотен тысяч
простых операций в секунду — меряй `redis-benchmark`). Cluster или реплики нужны ради **памяти** и **радиуса
поражения**: потеря одного шарда из шести обнуляет ~1/6 кеша, а не весь.

### 12.3 Наблюдаемость

Метрики Redis (`INFO` → `redis_exporter`; имена сверяй с версией экспортера):

| Что | Где смотреть | Зачем |
|-----|-------------|-------|
| Память | `used_memory`, `maxmemory`, `mem_fragmentation_ratio` | Упёрлись ли в лимит; фрагментация |
| Вытеснение | `evicted_keys` | Растёт при заполненном кеше — нормально; опасно вместе с падением hit ratio |
| Попадания | `keyspace_hits`, `keyspace_misses` | Hit ratio со стороны Redis |
| Нагрузка | `instantaneous_ops_per_sec`, CPU, `connected_clients`, `blocked_clients` | Однопоточность: ядро в 100% — шард насыщен |
| Задержка | `redis-cli --latency`, `SLOWLOG GET`, `LATENCY DOCTOR` | Медленные команды, fork-паузы |
| Снимки и репликация | `rdb_last_bgsave_status`, `latest_fork_usec`, `master_repl_offset` | Упал ли снимок; цена `fork`; лаг реплики |

Из приложения (важнее): hit ratio по слоям и типам ключей, гистограмма задержки вызова Redis, состояние
circuit breaker, число отказов ограничителя базы. **Hit ratio приложения точнее серверного** — он учитывает
L1 и промахи по таймауту.

```yaml
groups:
  - name: cache
    rules:
      - alert: CacheHitRatioLow          # ранний признак будущей перегрузки базы
        expr: |
          sum(rate(linkd_cache_requests_total{layer="redis",result="hit"}[10m]))
            / sum(rate(linkd_cache_requests_total{layer="redis"}[10m])) < 0.90
        for: 10m
        labels: {severity: page}
      - alert: RedisMemoryNearLimit
        expr: redis_memory_used_bytes / redis_memory_max_bytes > 0.95
        for: 15m
        labels: {severity: ticket}
      - alert: RedisDown
        expr: redis_up == 0
        for: 1m
        labels: {severity: page}
```

Hit ratio со стороны Redis: `rate(redis_keyspace_hits_total[5m]) / (rate(redis_keyspace_hits_total[5m]) +
rate(redis_keyspace_misses_total[5m]))`. ⚠️ Не клади короткий код ссылки в лейбл метрики — 6 млрд значений
положат Prometheus; горячие ключи ищут через `--hotkeys` и логи. Отдельного SLO у кеша нет: его качество видно
в SLO редиректа, а hit ratio — **ранний индикатор** перед ним ([SRE: 02](/sre/02-sli-slo-error-budget)).

### 12.4 Отказы

| Что случилось | Что видит пользователь | Что делает система |
|---------------|------------------------|--------------------|
| Redis недоступен | p99 растёт, редиректы работают | Короткий таймаут + circuit breaker, L1, ограничитель базы, быстрый `503` на лишнее |
| Redis «завис» (`fork`, большой ключ, `KEYS`) | Задержка растёт у всех | Таймаут обрезает ожидание, breaker открывается; потом разбор по `SLOWLOG` |
| Failover Sentinel (десятки секунд по умолчанию) | Всплеск задержки или ошибок | Breaker; часть `DEL` могла потеряться — ключи устареют до TTL |
| OOM-kill Redis | Как «недоступен», затем холодный старт | Лимит контейнера выше `maxmemory` с запасом; прогрев |
| Снимок RDB упал (диск полон), `stop-writes-on-bgsave-error yes` | Чтение работает, **записи в Redis отвергаются** | Алерт на `rdb_last_bgsave_status`; для чистого кеша снимки отключить |
| Память кончилась при `noeviction` | Ошибки `OOM command not allowed` | Для кеша — `allkeys-lfu` |
| Релиз сменил формат ключей | Резко упал hit ratio | Версия в ключе; прогрев; откат |

**Soft dependency** — кеш не должен быть причиной недоступности сервиса. Горячий путь целиком:

```python
import random, threading, time
import redis
from redis.backoff import NoBackoff
from redis.retry import Retry

# Таймаут 10 мс и ВЫКЛЮЧЕННЫЕ встроенные ретраи: в свежих redis-py они включены по умолчанию
# (3 повтора с backoff) — запрос с «таймаутом 0,2 с» у меня висел ~6 с. Проверь свою версию.
r = redis.Redis(host="redis", socket_timeout=0.01, socket_connect_timeout=0.01,
                retry=Retry(NoBackoff(), 0))
db_slots = threading.BoundedSemaphore(50)         # не больше 50 одновременных запросов в базу


class Overloaded(Exception):
    """Отвечаем 503 + Retry-After: быстрый отказ лучше очереди до таймаута."""


class Breaker:
    """5 ошибок подряд — кеш пропускаем 5 секунд, потом пробуем снова."""
    def __init__(self, threshold=5, pause=5.0):
        self.fails, self.open_until, self.threshold, self.pause = 0, 0.0, threshold, pause
    def allow(self):  return time.monotonic() >= self.open_until
    def ok(self):     self.fails = 0
    def fail(self):
        self.fails += 1
        if self.fails >= self.threshold:
            self.fails, self.open_until = 0, time.monotonic() + self.pause


breaker = Breaker()


def get_link(code: str):
    key = f"v1:link:{code}"                        # v1 — версия формата значения
    if breaker.allow():
        try:
            cached = r.get(key)
            breaker.ok()
            if cached is not None:
                return cached.decode() or None     # пустая строка — негативный кеш
        except redis.RedisError:
            breaker.fail()                         # кеш недоступен — считаем промахом
    if not db_slots.acquire(blocking=False):
        raise Overloaded()                         # load shedding
    try:
        url = db_get_link(code)                    # SELECT … на реплике
    finally:
        db_slots.release()
    if breaker.allow():
        try:
            ttl = (60 if url is None else 86_400) * random.uniform(0.9, 1.1)
            r.set(key, url or "", ex=int(ttl))     # джиттер ±10%
        except redis.RedisError:
            breaker.fail()
    return url
```

Здесь вместе: таймаут, breaker, ограничитель параллельности (bulkhead + load shedding), негативный кеш,
джиттер и версия формата ([SRE: 06](/sre/06-reliability-patterns)).

> ⚠️ **Readiness не должна зависеть от Redis.** Если `/readyz` пингует кеш, при его отказе балансировщик
> выкинет **все** поды, хотя они могли бы отдавать из L1 и базы. Readiness — про процесс
> ([Kubernetes: 09. Пробы и ресурсы](/kubernetes/09-probes-resources)).

### 12.5 Данные и DR

- **Кеш — производные данные.** Источник правды — база. Redis-кеш не бэкапят: RPO не нужен, **RTO кеша — время
  прогрева**. Проверь на учениях: убей Redis под нагрузкой и замерь, за сколько минут вернулся hit ratio.
- ⭐ **Не смешивай кеш и состояние в одном Redis.** Кеш хочет `allkeys-lfu` и выбрасывает ключи; сессии, очереди
  и счётчики лимитов хотят `noeviction` и персистентности (AOF `everysec` или managed с гарантиями). Один
  инстанс с `allkeys-lru` молча выбросит чужие сессии.
- **Мульти-AZ:** реплика в другой зоне, клиенты — в тех же зонах, что и поды. **Мульти-регион:** кеш обычно
  региональный (свой Redis в каждом, прогрев из общих данных): межрегионная репликация кеша редко стоит
  своей цены.
- **Бэкап** нужен только тем Redis, где лежат не-производные данные: `BGSAVE` + копия `dump.rdb` или AOF
  ([Базы данных: 09](/databases/09-redis-mongo-clickhouse), [Базы данных: 05](/databases/05-backup-restore)).

### 12.6 Безопасность

- **Redis не должен торчать наружу.** Порт `6379` без пароля в интернете — классический инцидент: чтение и
  запись данных, а через `CONFIG SET` — запись файлов на диск (майнеры, SSH-ключи). ⚠️ В официальном образе
  `protected-mode` выключен (проверь `CONFIG GET protected-mode`), поэтому `-p 6379:6379` без пароля публикует
  Redis на все интерфейсы. Внутренняя сеть, `NetworkPolicy`, `bind` на внутренний адрес
  ([Kubernetes: 13. NetworkPolicy](/kubernetes/13-networkpolicy)).
- **ACL (Redis 6+).** Отдельный пользователь сервиса с минимумом команд; `FLUSHALL`, `FLUSHDB`, `KEYS`, `CONFIG`,
  `DEBUG`, `SHUTDOWN` запрещены. TLS внутри сети, если в кеше чувствительное; пароли — из Vault или Secret
  ([Пет-проект: 08](/project/08-secrets-security)).
- **Отравление кеша.** Кто может **писать** в Redis, управляет ответами сервиса: подменив `link:aZ3x9Qk`, он
  направит редирект на фишинг. Запись в Redis — такая же привилегия, как запись в базу.
- **Персональные данные в кеше** — те же правила, что в базе: короткий TTL, удаление по запросу субъекта по
  всем слоям (включая L1 и CDN), снимки на диске — шифруй.

### 12.7 Стоимость

| Статья | Почему растёт | Рычаги |
|--------|--------------|--------|
| ⭐ RAM | Самая дорогая единица ёмкости: за гигабайт RAM обычно платят на порядок больше, чем за гигабайт SSD. Для linkd — десятки ГБ × реплика × запас на `fork` и фрагментацию | Короткие значения (`code → url`); сжатие больших (CPU за память); LFU; TTL по реальной пользе |
| Число копий | Реплика удваивает память; Cluster — реплики на каждый шард | Реплики только там, где нужен failover |
| Трафик между зонами | В облаках межзонный трафик, как правило, платный | Клиент читает из своей зоны; L1 режет обращения |
| Сеть и CPU | Много мелких команд | Pipelining, `MGET`, L1 |
| Люди | Redis — ещё одна система на дежурстве | Managed, если команда маленькая |

Решение «брать ли кеш» — сравнение RAM под кеш с ценой реплик БД, которые он заменяет (раздел 9), плюс люди.
Пока нагрузка помещается в базу, «кеш на всякий случай» только добавляет компонент.

## Грабли

| Грабля | Что не так | Правильно |
|--------|-----------|-----------|
| Кеш без TTL и без `maxmemory` | Память растёт до OOM-kill, ошибки живут вечно | TTL с джиттером, `maxmemory` + `allkeys-lfu` |
| `DEL` перед `COMMIT` | Читатель успевает положить старое | `COMMIT` → `DEL` + TTL |
| Одинаковый TTL у всех ключей | Avalanche | Джиттер ±10–20% |
| Нет защиты от stampede | Вирусный ключ выпал — база под тысячей запросов | Single-flight, блокировка, SWR |
| Таймаут Redis не задан или ретраи клиента «по умолчанию» | Зависший Redis кладёт потоки; встроенные ретраи растягивают 10 мс до секунд | Таймаут 5–10 мс, ретраи выключены, circuit breaker |
| Нет плана на падение кеша | Холодный старт → каскад | Ограничитель базы, L1, прогрев, учения |
| Негативный кеш с длинным TTL | Только что созданная запись «не существует» | TTL ≈ минута, `SET` при создании |
| Кеш персонального ответа на CDN | Пользователи видят чужие данные | `private` / `no-store`, `Vary` |
| Кеш и сессии в одном Redis с LRU | Сессии вытесняются | Раздельные инстансы и политики |
| `KEYS *` и `FLUSHALL` на проде | Блокируют единственный поток; сносят всё | `SCAN`, `UNLINK`, ACL |
| Смена формата значения без версии в ключе | Старые поды при rolling update читают мусор | Версия в префиксе ключа |
| Кеш как источник правды | Вытеснение или рестарт = потеря данных | База — источник, кеш — копия |

## 💼 Как это на работе

- **Бэкенд:** кеш — последний в лестнице (запрос → индекс → пул соединений → кеш). Одна функция доступа с
  TTL, джиттером, слиянием запросов и метриками, а не разбросанные `get/set`. Каждый ключ в дизайне — с
  ответом «сколько устаревания терпим» и «что при промахе».
- **DevOps:** кеш — stateful-компонент: топология, политика вытеснения, лимит памяти, hit ratio, учения «убей
  Redis». Без плана «кеш упал» он появится в 3 часа ночи в виде инцидента.
- **На ревью дизайна** спрашивай: что кешируем, какой TTL и почему, кто инвалидирует, что с базой при пустом
  кеше, какой hit ratio обещаем и чем измеряем.
- Типичные инциденты — «кеш пропал, база не выдержала», «после правки видят старое», «после релиза hit ratio
  упал из-за ключа». Hit ratio падает за минуты до роста p99 и ошибок — он ранний индикатор.

## 📌 Шпаргалка

| Хочу | Как |
|------|-----|
| Паттерн по умолчанию | Cache-aside: кеш → промах → база → `SET` с TTL |
| «Создал — сразу читается» | Write-through (`SET` после `COMMIT`) |
| Счётчики и события | Write-behind через очередь; потеря допустима |
| Порядок при изменении | `COMMIT` → `DEL` (+ TTL как потолок) |
| Гонка «старое вернулось» | Версионные ключи или lease/CAS; отложенный `DEL` как хак |
| Avalanche / stampede / penetration | Джиттер / single-flight, блокировка, SWR / негативный кеш + лимиты |
| Горячий ключ | L1 с TTL в секундах → CDN → реплики → разбиение ключа |
| Вытеснение для кеша | `maxmemory` + `allkeys-lfu` (по умолчанию лимита нет, политика `noeviction`) |
| Нагрузка на базу / задержка | `RPS × (1 − hit)` / `hit × t_кеш + (1 − hit) × t_БД` |
| Persistence Redis 7.x по умолчанию | RDB включён (`save 3600 1 300 100 60 10000`), AOF выключен |
| Отказ кеша | Таймаут 5–10 мс, breaker, ограничитель базы, `503`, L1, прогрев |
| Нельзя кешировать | Решения авторизации, деньги, идемпотентность, ошибки как «нет данных», личное в общем кеше |
| Формат значения меняется | Версия в префиксе ключа |

## 🧠 Что запомнить

1. Кеш — копия с предположением «источник не менялся»; платим устареванием, ещё одной системой и скрытой
   зависимостью.
2. ⭐ Паттерн выбирают **на операцию**: cache-aside для чтения, write-through для неизменяемого, write-behind
   для счётчиков и событий.
3. TTL — максимально допустимое устаревание; он нужен даже при активной инвалидации.
4. ⭐ Удаляем **после** коммита; гонку «старое вернулось» (и лаг реплики как её вариант) закрывают версионные
   ключи или lease, а TTL ограничивает ущерб.
5. Stampede, avalanche и penetration — разные беды: слияние запросов, джиттер, негативный кеш.
6. Горячий ключ не лечится шардированием: сначала L1 с коротким TTL.
7. ⭐ Нагрузка на базу = `RPS × (1 − hit)`; средняя задержка слабо зависит от hit ratio, а нагрузка на базу и
   p99 — сильно. Мерь hit ratio по слоям и по минутам.
8. ⭐ Для кеша в Redis задай `maxmemory` и `allkeys-lfu`: по умолчанию лимита нет, политика `noeviction`.
   Персистентность по умолчанию — RDB-снимки, AOF выключен.
9. ⭐ Кеш — soft dependency: таймаут 5–10 мс, circuit breaker, ограничитель базы, быстрый `503`; readiness от
   Redis не зависит.
10. Авторизацию и деньги по кешу не решают; личное — не в общий кеш; кеш и состояние — в разных инстансах.

### Блок A. Теория

**A1.** Назови уровни кеша на пути запроса. В чём разница между L1 и Redis?

<details><summary>Ответ</summary>

Браузер, CDN, gateway/прокси, L1 в памяти пода, распределённый кеш (Redis, Memcached), буфер БД и page cache
ОС. L1 быстрее на порядки, но у каждого пода своя копия и общей инвалидации нет — TTL в секундах. Redis общий
для подов и больше по объёму, но это сетевой ход и отдельная система в эксплуатации.

</details>

**A2.** Чем cache-aside отличается от read-through?

<details><summary>Ответ</summary>

В cache-aside приложение само ходит в кеш и в базу и кладёт значение в кеш. В read-through приложение говорит
только с кеш-слоем, а тот сам грузит данные при промахе (`LoadingCache`, `proxy_cache`, CDN). Логика почти
та же, но загрузчик в одном месте и слияние промахов получается естественно.

</details>

**A3.** ⭐ Когда write-through, когда write-behind и write-around? Что рискуем?

<details><summary>Ответ</summary>

Write-through — данные нужны сразу после записи и меняются редко (создание ссылки); цена — запись медленнее.
Write-behind — счётчики, метрики, события; цена — окно потери между ответом клиенту и сбросом в базу, деньги и
ссылки сюда нельзя. Write-around — пишут часто, читают редко: запись не вытесняет нужное из кеша.

</details>

**A4.** ⭐ Почему при записи делают `DEL`, а не `SET`, и почему после коммита?

<details><summary>Ответ</summary>

`SET` опасен при конкурентных писателях: порядок записи в кеш может не совпасть с порядком коммитов. `DEL`
проще: следующее чтение возьмёт актуальное. После коммита, потому что `DEL` до коммита даёт читателю шанс
положить старое, а `SET` до коммита при откате оставит в кеше то, чего нет в базе.

</details>

**A5.** ⭐ Опиши гонку, при которой старое значение возвращается в кеш. Два способа закрыть.

<details><summary>Ответ</summary>

Читатель промахнулся и прочитал старое (из базы или с отстающей реплики); писатель закоммитил и сделал `DEL`;
читатель кладёт прочитанное старое в кеш на весь TTL. Закрывают версионными ключами (запоздалый `SET` попадает в
ключ мёртвой версии), lease/CAS (положить можно только по действующему токену), отложенным повторным `DEL`;
потолок — TTL.

</details>

**A6.** ⭐ Чем stampede отличается от avalanche и penetration? Как защититься от stampede?

<details><summary>Ответ</summary>

Stampede — истекла одна горячая запись, и за ней идёт много одновременных промахов. Avalanche — много записей
исчезли разом. Penetration — запросы за ключами, которых нет нигде. От stampede: single-flight, блокировка
`SET lock:key token NX PX`, раннее обновление XFetch, stale-while-revalidate; на практике часто хватает
single-flight и L1.

</details>

**A7.** ⭐ Почему Redis Cluster не лечит горячий ключ? Что лечит?

<details><summary>Ответ</summary>

Ключ принадлежит одному слоту, слот — одному шарду; команды в шарде исполняет один поток, и он упирается в CPU
независимо от числа шардов. Помогают L1 с коротким TTL, кеш на CDN, чтение с реплик, разбиение ключа на копии.

</details>

**A8.** Чем LFU лучше LRU и какая политика нужна кешу в Redis?

<details><summary>Ответ</summary>

LRU вымывается разовым сканом по редким ключам; LFU считает частоту и держит по-настоящему популярное. Для кеша
— `allkeys-lfu` (или `allkeys-lru`) вместе с заданным `maxmemory`; по умолчанию лимита нет, а политика `noeviction`.

</details>

**A9.** ⭐ Пик 20 000 RPS. Hit ratio вырос с 90% до 95%. Как изменились нагрузка на базу и средняя задержка
(`t_кеш` = 1 мс, `t_БД` = 10 мс)?

<details><summary>Ответ</summary>

Нагрузка: 2 000 → 1 000 RPS, вдвое меньше. Средняя задержка: 0,9 × 1 + 0,1 × 10 = 1,9 мс → 0,95 × 1 + 0,05 × 10
= 1,45 мс, на 0,45 мс. Кеш оценивают по разгрузке источника.

</details>

**A10.** Что такое негативный кеш и чем он опасен?

<details><summary>Ответ</summary>

Запоминание «ключа нет». Опасен длинным TTL (только что созданная запись «не существует») и кешированием
ошибок (таймаут базы превращается в 404). Нужны короткий TTL и перезапись при создании.

</details>

**A11.** Что нельзя кешировать без особых мер?

<details><summary>Ответ</summary>

Решения авторизации (отозванное право работает до TTL), деньги и остатки при решениях (двойное списание),
персональные ответы в общем кеше (утечка), ключи идемпотентности (вытеснение → повтор операции), ошибки как
«данных нет».

</details>

**A12.** ⭐ Что в Redis включено по умолчанию: RDB или AOF? Что теряется при рестарте?

<details><summary>Ответ</summary>

В Redis 7.x включены RDB-снимки (`save 3600 1 300 100 60 10000`), AOF выключен. Redis поднимется из последнего
снимка и потеряет изменения после него; без снимков стартует пустым. Для чистого кеша это допустимый холодный
старт.

</details>

### Блок B. «Что тут не так»

```
B1.  maxmemory 0, maxmemory-policy noeviction — «Redis у нас под кеш»

B2.  Обновление профиля:  cache.delete(key); db.update(profile); db.commit()

B3.  Инвалидация по шаблону на проде:  redis-cli KEYS "link:*" | xargs redis-cli DEL

B4.  «Hit ratio за сутки — 97%, значит, ночью с кешем всё было в порядке»

B5.  «Права пользователя кешируем в Redis на час — запросы к IAM дорогие»

B6.  Клиент Redis с настройками по умолчанию, таймаут не задан; Redis ушёл в BGSAVE на 2 секунды

B7.  Один Redis: кеш страниц, сессии и очередь задач; maxmemory-policy allkeys-lru

B8.  /readyz пода делает PING Redis и возвращает 503, если ответа нет

B9.  Cache-Control: public, max-age=3600 на GET /api/me

B10. «Заблокировали фишинговую ссылку: DEL link:aZ3x9Qk в Redis — готово»
```

<details><summary>Ответы</summary>

**B1.** ⚠️ Без лимита Redis растёт до OOM-kill; с лимитом `noeviction` вернёт ошибки записи вместо вытеснения.
Нужны `maxmemory` + `allkeys-lfu`.

**B2.** ⚠️ `DEL` до коммита: читатель между ними положит старое. Порядок: `COMMIT`, затем `DEL`, и TTL как потолок.

**B3.** ⚠️ `KEYS` блокирует единственный поток Redis на весь перебор. `SCAN`, версия в ключе или точечные `UNLINK`.

**B4.** ⚠️ Среднее за сутки прячет провал. Hit ratio — по минутам, по слоям, с алертом на падение.

**B5.** ⚠️ Отозванный доступ работает до часа — дыра. Не кешировать или TTL в секунды + событие «права изменились».

**B6.** ⚠️ Все потоки зависнут на 2 секунды (а встроенные ретраи клиента растянут ожидание). Таймаут 5–10 мс,
ретраи выключены, circuit breaker.

**B7.** ⚠️ `allkeys-lru` вытеснит сессии и задачи вместе с кешем. Разные инстансы: состояние — `noeviction` и
персистентность.

**B8.** ⚠️ Отказ кеша выведет из балансировки все поды, хотя они обслужили бы запросы из L1 и базы. Readiness —
про процесс.

**B9.** ⚠️ Персональный ответ в общем кеше — пользователи увидят чужие профили. `private` или `no-store`.

**B10.** ⚠️ Остались L1 в подах (секунды), копия на CDN (до purge) и возможная гонка с читателем. Нужны
`status` в базе, `DEL` в Redis, purge CDN; L1 истечёт сам.

</details>

#### C2. 🔑 Hit ratio и размер кеша (закон Ципфа)

```python
# zipf_lru.py
import random
from bisect import bisect_left
from collections import OrderedDict
from itertools import accumulate

N, S, REQUESTS = 100_000, 1.0, 2_000_000        # ключей; крутизна «головы»; запросов
cum = list(accumulate(1 / rank ** S for rank in range(1, N + 1)))
random.seed(42)
stream = [bisect_left(cum, random.random() * cum[-1]) for _ in range(REQUESTS)]


def lru_hit_ratio(size: int) -> float:
    cache, hits = OrderedDict(), 0
    for key in stream:
        if key in cache:
            hits += 1
            cache.move_to_end(key)
        else:
            cache[key] = True
            if len(cache) > size:
                cache.popitem(last=False)
    return hits / len(stream)


for percent in (0.1, 1, 5, 10, 20, 50):
    print(f"кеш {percent:>4}% ключей -> hit ratio {lru_hit_ratio(int(N * percent / 100)):.1%}")
```

Запусти с `S = 0.8`, `1.0`, `1.2`. Какие выводы про размер кеша?

<details><summary>Ответ</summary>

Ориентировочно: при `S = 1.0` — 1% ключей ≈ 50%, 10% ≈ 74%, 50% ≈ 91%; при `S = 0,8` — 1% ≈ 20%, 10% ≈ 47%;
при `S = 1,2` — 1% ≈ 80%. Hit ratio растёт быстро, потом выходит на плато — последние гигабайты почти не
помогают; результат зависит от формы распределения, поэтому профиль запросов мерят на реальных данных. Часть
промахов «холодные» (первое обращение к ключу), поэтому на коротких прогонах hit ratio ниже.

</details>

#### C3. 🔑 Stampede: воспроизведи и закрой

Возьми `get_singleflight` из раздела 6.1. Напиши «наивную» версию и прогони обе: 100 потоков просят один ключ,
«база» отвечает 200 мс и считает вызовы.

```python
import threading, time

cache, calls = {}, 0
def load(key):
    global calls
    calls += 1                                     # для точности можно обернуть в Lock
    time.sleep(0.2)
    return f"value-of-{key}"

def get_naive(key, cache, load):
    if key not in cache:
        cache[key] = load(key)                     # каждый поток идёт в базу сам
    return cache[key]

for getter in (get_naive, get_singleflight):
    cache.clear(); calls = 0
    ts = [threading.Thread(target=getter, args=("hot", cache, load)) for _ in range(100)]
    [t.start() for t in ts]; [t.join() for t in ts]
    print(getter.__name__, "запросов в базу:", calls)
```

<details><summary>Ответ</summary>

Без защиты — около 100 запросов в базу, с single-flight — 1; время одинаковое (~0,2 с), но база не получает
100 одновременных запросов. В проде single-flight работает внутри процесса: 30 подов дадут до 30 запросов за
ключом, а не тысячи. Если и этого много — блокировка в Redis или stale-while-revalidate.

</details>

#### C4. 🔑 Гонка «старое вернулось» и lease

```python
# race.py
import threading

db, cache, leases = {"link": "v1"}, {}, {}
next_token = 0

def reader(use_lease, read_done, write_done):
    global next_token
    token = None
    if use_lease:                          # 1. промах: берём аренду на заполнение ключа
        next_token += 1
        token = leases["link"] = next_token
    value = db["link"]                     # 2. читаем из БД: пока v1
    read_done.set()
    write_done.wait()                      # 4. читатель «застрял» (GC, сеть)
    if use_lease and leases.get("link") != token:
        return                             # аренду отозвали — не кладём
    cache["link"] = value                  # 5. без аренды кладём прочитанное давно

def writer(use_lease, read_done, write_done):
    read_done.wait()
    db["link"] = "v2"                      # 3. обновили БД, удалили ключ, отозвали аренду
    cache.pop("link", None)
    if use_lease:
        leases.pop("link", None)
    write_done.set()

for use_lease in (False, True):
    db["link"] = "v1"; cache.clear(); leases.clear()
    ev = (threading.Event(), threading.Event())
    ts = [threading.Thread(target=f, args=(use_lease, *ev)) for f in (reader, writer)]
    [t.start() for t in ts]; [t.join() for t in ts]
    print("с арендой " if use_lease else "без аренды", "| БД:", db["link"], "| кеш:", cache.get("link", "пусто"))
```

Что в кеше в каждом случае? Как это реализовать в Redis?

<details><summary>Ответ</summary>

Без аренды: в БД `v2`, в кеше `v1` — устаревшее живёт до TTL. С арендой: кеш пуст, следующее чтение загрузит
`v2`. В Redis: при промахе `SET lease:key <токен> NX PX 5000`; запись значения — Lua-скрипт «если `GET lease:key`
равен моему токену — `SET key value EX ttl`»; инвалидация — `DEL key` и `DEL lease:key`. Альтернатива —
версионные ключи: читатель берёт версию **до** базы, запоздалый `SET` попадает в ключ уже мёртвой версии.

</details>

#### C5. Redis недоступен: `stop` против `pause`

Возьми `get_link` из раздела 12.4 (заглушка для `db_get_link`, `host`/`port` своего Redis). Замерь время одного
`r.get(...)` при трёх состояниях Redis, потом повтори с настройками клиента по умолчанию.

```bash
docker pause redis-lab     # процесс заморожен: соединение принимается, ответа нет
docker unpause redis-lab
docker stop redis-lab      # соединение отвергается сразу
docker start redis-lab
```

Что покажет замер? Зачем circuit breaker, если уже есть таймаут?

<details><summary>Ответ</summary>

С таймаутом 50 мс и выключенными ретраями: `pause` — `TimeoutError` примерно через 50 мс (ждём весь таймаут),
`stop` — `ConnectionError` за миллисекунды. С умолчаниями в свежих `redis-py` запрос с «таймаутом 0,2 с» занимает
секунды из-за встроенных повторов с backoff (проверь на своей версии). Одного таймаута мало: при зависшем Redis
**каждый** запрос платит эти 50 мс. Breaker после нескольких ошибок перестаёт ходить в Redis на время, а
ограничитель базы защищает её от наплыва.

</details>

### Блок D. Инциденты

**D1.** После выкатки redirect-сервиса растут ошибки десериализации, падает hit ratio — только в первые минуты
выкатки, потом проходит.

<details><summary>Ответ</summary>

Новая версия поменяла формат значения; при rolling update старые и новые поды читают общие ключи и не понимают
друг друга. Сейчас: нечитаемое значение считать промахом. Потом: версия формата в префиксе ключа (`v2:link:…`),
обратная совместимость на время выкатки, тест «смешанной версии» в CI. `FLUSHALL` — не лекарство.

</details>

**D2.** Ночью алерт: ошибки записи в Redis `OOM command not allowed`, hit ratio падает.

<details><summary>Ответ</summary>

Память упёрлась в `maxmemory` при `noeviction` — кеш не принимает новые записи. Сейчас: `CONFIG SET
maxmemory-policy allkeys-lfu`, при необходимости поднять `maxmemory`; искать ключи без TTL и раздутые значения
(`--bigkeys`, `MEMORY USAGE`). Потом: `allkeys-lfu` в конфиге, алерт на память > 95% и на рост `evicted_keys`
вместе с падением hit ratio.

</details>

**D3.** Модерация заблокировала фишинговую ссылку, а 20 минут часть кликов всё ещё уходит по ней; в Redis лежит
старое значение с полным TTL.

<details><summary>Ответ</summary>

Вероятно, гонка: читатель промахнулся на реплике с лагом и положил старое значение после `DEL` (5.2). Проверить
лаг реплик в момент блокировки. Исправить: после блокировки писать в Redis отметку «заблокирована» или использовать версию/lease;
отложенный повторный `DEL` дольше лага; критичное читать с primary сразу после записи. TTL оставить потолком.

</details>

**D4.** Redis убит по лимиту памяти (OOM-kill) днём. Кеш пуст, реплики PostgreSQL на 100% CPU, p99 — секунды.

<details><summary>Ответ</summary>

Лимит контейнера был равен `maxmemory`, а ещё нужна память на буферы, фрагментацию и `fork`. Сейчас: ограничитель
параллельности к базе и быстрый `503` на излишки, больший L1-TTL, прогрев топа ссылок из аналитики, при
необходимости временно добавить реплики. Потом: лимит контейнера заметно выше `maxmemory`, алерт на RSS, план
прогрева в runbook, учения «убей Redis».

</details>

**D5.** Каждый час на 2–3 секунды растёт задержка всех запросов к Redis. Ошибок нет.

<details><summary>Ответ</summary>

Похоже на `fork` при RDB-снимке (`save 3600 1`): на большой памяти `fork` блокирует процесс (смотри
`latest_fork_usec`) плюс всплеск copy-on-write. Для чистого кеша — отключить снимки (`save ""`), для данных —
снимки на реплике, меньше размер шарда. Заодно проверить `SLOWLOG` и большие ключи.

</details>

**D6.** После релиза hit ratio упал с 95% до 70%, ошибок нет, нагрузка на реплики выросла втрое.

<details><summary>Ответ</summary>

Изменили ключ или TTL: в ключ добавили поле с высокой кардинальностью (`user_id`, время, query-параметр), сменили
префикс (новая версия прогревается) или уменьшили TTL. Сравнить ключи (`redis-cli --scan | head`), метрики по
типам ключей. Откатить или исправить построение ключа; на будущее — тест на форму ключа и алерт на hit ratio.

</details>

### Блок E. Вопросы с собеседования

**1.** Как добавить кеш к сервису с тяжёлым чтением? С чего начать?

<details><summary>Ответ</summary>

Проверить, что запрос не лечится индексом и пулом соединений. Уточнить: сколько устаревания терпим, какой hit
ratio ожидаем, что при пустом кеше. Cache-aside с TTL и джиттером, один код доступа, метрики hit ratio. Защита от
stampede и план на отказ кеша — до включения в прод.

</details>

**2.** Cache-aside, write-through, write-behind — когда что?

<details><summary>Ответ</summary>

Cache-aside: читаем кеш, при промахе базу и кладём в кеш; запись — база + `DEL`. Write-through: запись через кеш в
базу синхронно; для неизменяемого и «записал — сразу прочитал». Write-behind: запись в кеш, в базу позже; быстро,
но окно потери — счётчики и события.

</details>

**3.** Как инвалидировать кеш? Что может пойти не так?

<details><summary>Ответ</summary>

`COMMIT` → `DEL`, TTL как потолок, outbox или CDC (для надёжности и записей мимо кода), версионные ключи. Что не
так: потерянный `DEL`; гонка «читатель положил старое после удаления» (в том числе из-за лага реплики); несколько
слоёв (L1, CDN) инвалидируются по-разному.

</details>

**4.** Redis упал. Что произойдёт с сервисом и что вы сделали заранее?

<details><summary>Ответ</summary>

Короткий таймаут и circuit breaker — запросы идут в базу и L1, а не ждут Redis. Ограничитель параллельности к
базе и быстрый `503` вместо очереди. Прогрев после восстановления. Readiness от Redis не зависит. Учения «убей
Redis под нагрузкой» с замером возврата hit ratio.

</details>

**5.** Как найти и разгрузить горячий ключ?

<details><summary>Ответ</summary>

Найти: `redis-cli --hotkeys` (нужен LFU), метрики запросов по ключам, неравномерность CPU по шардам. Разгрузить:
L1 с TTL в секунды, CDN, чтение с реплик, разбиение ключа. Шардирование не лечит — слот один.

</details>

**6.** Как оценить размер кеша и целевой hit ratio?

<details><summary>Ответ</summary>

Размер: рабочий набор × (ключ + значение + накладные расходы) плюс запас на `fork` и буферы (`maxmemory` порядка
70% RAM). Целевой hit ratio — от разгрузки источника: `RPS × (1 − hit)` должно помещаться в ёмкость базы с
запасом. Профиль запросов (Zipf) мерить на живых данных.

</details>

**7.** LRU или LFU? Что в Redis по умолчанию?

<details><summary>Ответ</summary>

LRU — «недавнее», уязвим к сканам; LFU — «популярное», хуже забывает старое. Для read-heavy кеша с популярным
хвостом обычно LFU. По умолчанию в Redis лимита памяти нет, а политика `noeviction` — оба параметра задают.

</details>

**8.** Что нельзя кешировать? Что у Redis по умолчанию с персистентностью, нужен ли бэкап кеша?

<details><summary>Ответ</summary>

Решения авторизации и деньги — без особых мер; персональные ответы — в общем кеше; ключи идемпотентности; ошибки
как «нет данных». У Redis RDB-снимки включены, AOF выключен. Бэкап чистого кеша не нужен: данные восстанавливаются
из источника, RTO — время прогрева; бэкап нужен Redis с не-производными данными.

</details>
