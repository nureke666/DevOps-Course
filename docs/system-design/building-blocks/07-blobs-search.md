## 1. Файлы: почему не в БД и не на диск пода

Загрузка аватарок, документов, видео, выгрузок — в любой системе рано или поздно появляется
«положи файл и отдай его потом». У файла три отличия от строки таблицы: он **большой**
(мегабайты и гигабайты), он **целиком неизменяемый** (заменили — значит, записали новый),
и его отдают **клиентам напрямую** (трафик, а не запросы).

| Куда положить | Что хорошо | Почему не подходит как основное |
|---------------|-----------|----------------------------------|
| Колонка `bytea` в PostgreSQL | Одна транзакция со строкой, один бэкап | Раздувает таблицы, WAL и бэкапы; каждое скачивание держит соединение к БД; кеш БД забит файлами. Лимит поля — 1 ГБ, но проблемы начинаются с мегабайтов |
| Диск пода (`emptyDir`, hostPath) | Быстро и просто | Под умер — файл пропал; второй под не видит файл первого; ломается stateless и масштабирование |
| Сетевая ФС (NFS, RWX-том) | Файл виден всем подам | Одна точка отказа, слабое масштабирование метаданных, нет HTTP, подписанных ссылок и CDN ([Хранилища: 03](/storage/03-nfs-minio)) |
| ⭐ **Объектное хранилище** | HTTP API, почти неограниченный объём, дешёвый гигабайт, высокая сохранность, версионирование, lifecycle, дружба с CDN | Не файловая система: нет частичного изменения, rename и настоящих каталогов; первый байт — десятки миллисекунд |

> ⭐ Правило: **БД хранит метаданные (кто, что, статус), объектное хранилище — байты.**
> Исключение — совсем маленькие файлы (иконка на 20 КБ в строке), когда простота важнее.

В [Основах, тема 04](/system-design/basics/04-backend-vs-devops) API уже выдавал presigned URL, а клиент
грузил фото мимо него. Здесь — как это устроено внутри, где ломается и как эксплуатируется.

## 2. Объектное хранилище: модель

```text:no-line-numbers
 bucket «uploads»
 ├── incoming/7f3a…         ← ключ — просто строка; «/» — соглашение, каталогов нет
 ├── files/7f3a…/original
 └── files/7f3a…/thumb-m-9c41.webp
```

- **Bucket** — контейнер с общими настройками: политика доступа, версионирование, lifecycle,
  шифрование. **Key** — имя объекта внутри бакета. Выборка «по префиксу» (`files/7f3a…/`)
  заменяет каталоги, но это поиск по строке, а не обход дерева.
- **Объект неизменяем.** Байты изменить нельзя: `PUT` с тем же ключом атомарно заменяет
  объект целиком. «Переименовать» = скопировать под новым ключом и удалить старый.
- **Метаданные объекта**: системные (`Content-Type`, `Cache-Control`, `ETag`, размер) и свои
  `x-amz-meta-*` (в AWS — до ~2 КБ). Искать по ним нельзя — поэтому каталог файлов живёт в БД.
  `ETag` — не всегда MD5: у multipart-объекта это хеш от хешей частей с суффиксом `-N`;
  для целостности запрашивай контрольную сумму (SHA-256).
- **Версионирование**: каждый `PUT` создаёт новую версию, `DELETE` ставит delete marker —
  версию можно вернуть. Это защита от ошибок, а не бесплатная опция: старые версии
  занимают место.
- **Консистентность.** Amazon S3 с декабря 2020 даёт строгую согласованность «прочитать
  после записи» для `PUT`/`DELETE` и листинга: записал — сразу видишь. У других
  S3-совместимых хранилищ (MinIO, Ceph RGW, облака РК) модель может отличаться,
  особенно при репликации между зонами — читай документацию своего.
- **Ключи.** Не делай ключом имя файла от пользователя: юникод, `../`, коллизии
  двух «Отчёт.pdf». Ключ — `files/<uuid>/…`, исходное имя — в БД и в заголовке
  `Content-Disposition` при отдаче.
- **Сохранность и защита — разное.** «11 девяток» — про потерю из-за отказа железа, а не про
  твой `delete` ([Основы: 01](/system-design/basics/01-what-is-system-design)).

## 3. Загрузка: напрямую в хранилище

### Почему не через API

Если файл идёт «клиент → API → хранилище», API держит соединение всё время загрузки:
мобильный клиент грузит 3 МБ по плохой сети минуту — минуту занят поток, а пик из Основ, тема 04
в 18 МБ/с идёт через поды. **Presigned URL** убирает API с пути данных: он решает, *можно ли*,
и выдаёт подпись.

```text:no-line-numbers
 клиент                    API                      хранилище
   │  POST /files           │                           │
   │ ─────────────────────► │ проверка прав и лимитов   │
   │                        │ INSERT files(pending)     │
   │                        │ подпись — локально,       │
   │                        │ без похода в хранилище    │
   │ ◄── { file_id, url } ──│                           │
   │  PUT url (байты) ────────────────────────────────► │ проверка подписи
   │ ◄──────────────────────────────────── 200 / 204 ── │
   │  POST /files/id/complete ► │ HEAD объекта ───────► │ (размер, checksum)
```

### Presigned URL: что внутри

URL содержит бакет, ключ, срок жизни и **подпись** (HMAC от секретного ключа сервиса,
SigV4). Хранилище пересчитывает подпись и пускает клиента без собственного аккаунта.
Следствия:

- **Это bearer-токен.** Утёк URL — любой выполнит операцию до истечения срока. Срок — минуты
  (15 минут на загрузку, 1–5 на скачивание); не пиши URL целиком в логи — подпись лежит в
  query-строке.
- Максимум для SigV4 — 7 дней; URL, подписанный временными ключами роли, умирает вместе с
  ключами (поведение AWS; у других реализаций проверь).
- Подпись считается **локально**: API выдаёт URL, даже если хранилище лежит; ошибка появится
  у клиента — ему нужны повторы. Права нужны тому, кто подписывает: роль API — только
  `PutObject` на `incoming/*`.
- Браузер, грузящий напрямую с другого домена, упирается в **CORS** бакета.

### PUT или POST

| | Presigned PUT | Presigned POST (форма с policy) |
|---|---------------|---------------------------------|
| Запрос | `PUT url` с телом файла | `multipart/form-data`: поля policy + файл |
| Ключ | Зашит в URL | Зашит в policy (можно `starts-with` на префикс) |
| Тип | Если подписать заголовок `Content-Type` — другой тип даст `SignatureDoesNotMatch` | Условие `Content-Type` в policy |
| ⭐ Размер | Надёжно ограничить нельзя (зависит от SDK и хранилища) | `content-length-range` — отказ до записи |
| Когда | Внутренние клиенты, доверенные загрузки | Пользовательские файлы с лимитом |

```python
# API: выдаём presigned POST — ключ, тип и размер зафиксированы подписью
post = s3.generate_presigned_post(
    Bucket="uploads", Key=f"incoming/{file_id}",
    Fields={"Content-Type": "image/webp"},
    Conditions=[{"Content-Type": "image/webp"},
                ["content-length-range", 1, 10 * 1024 * 1024]],   # 1 байт … 10 МиБ
    ExpiresIn=900)
# клиенту: post["url"] и post["fields"]; в форме поле file — последним
```

> ⚠️ `Content-Type` в запросе клиент заявляет сам. Настоящий тип проверяет обработчик
> **по содержимому** (magic bytes), а не по расширению или заголовку.

### Multipart: большие файлы

Один `PUT` — до 5 ГиБ (AWS), но гигабайтный файл одним запросом упадёт на любом сбое сети
и начнёт заново. **Multipart upload** режет файл на части:

```text:no-line-numbers
 1. CreateMultipartUpload        → UploadId
 2. UploadPart (1…N)             ← клиент грузит части параллельно, каждую можно повторить;
                                   на каждую — свой presigned URL, в ответе ETag части
 3. CompleteMultipartUpload      ← список (номер, ETag) → хранилище склеивает объект
```

| Параметр (AWS S3) | Значение |
|-------------------|----------|
| Размер части | 5 МиБ … 5 ГиБ (последняя может быть меньше 5 МиБ) |
| Число частей | до 10 000 → размер части = размер файла / 10 000 или больше |
| Объект целиком | до 5 ТиБ |
| Когда включать | ориентир AWS — от ~100 МБ; для нестабильных сетей — раньше |

- **Возобновление.** Клиент запоминает `UploadId`, спрашивает `ListParts` и докачивает
  недостающее. Нужен общий протокол докачки — открытый **tus** (`tusd`); у Google Cloud
  Storage — свои resumable-сессии.
- ⚠️ **Незавершённые загрузки невидимы и платные.** Части брошенного multipart лежат
  в хранилище, не попадают в листинг объектов, но тарифицируются. Лечится lifecycle-правилом
  `AbortIncompleteMultipartUpload` (в AWS нужно явно; у MinIO свой механизм очистки —
  проверь по документации версии).

## 4. Метаданные в БД и объект в хранилище: согласованность

Строка в PostgreSQL и объект в S3 — две системы без общей транзакции. Атомарно «создать оба»
нельзя, поэтому согласие строится на **статусах** и **порядке операций**.

```sql
CREATE TABLE files (
    id            uuid        PRIMARY KEY,
    owner_id      bigint      NOT NULL,
    object_key    text        NOT NULL,            -- incoming/<id>, после проверки — files/<id>/…
    original_name text        NOT NULL,            -- имя от пользователя живёт только здесь
    content_type  text,                            -- заполняем по результату проверки содержимого
    size_bytes    bigint,
    sha256        bytea,
    status        text        NOT NULL DEFAULT 'pending',
    created_at    timestamptz NOT NULL DEFAULT now(),
    updated_at    timestamptz NOT NULL DEFAULT now()
);
CREATE INDEX files_pending ON files (created_at) WHERE status = 'pending';   -- для уборщика
```

```text:no-line-numbers
 pending ──(объект на месте: confirm или событие)──► uploaded ──► processing ──► ready
    │                                                                  └────────► failed
    └──(срок presigned + запас вышел, объекта нет)──► строка удаляется

 ready ──(DELETE)──► deleted ──(через N дней, ≥ окна восстановления БД)──► объект удалён физически
```

**Порядок операций** (идея: строка — источник правды о существовании файла):

| Операция | Правильный порядок | Если процесс упал посередине |
|----------|--------------------|-------------------------------|
| Загрузка | 1) строка `pending` 2) клиент грузит объект 3) проверка и `uploaded` | Строка без объекта — безвредно, уберёт чистильщик |
| Загрузка наоборот | объект, потом строка | Объект-сирота, о котором никто не знает |
| Удаление | 1) в БД `deleted` 2) объект — позже и асинхронно | Объект без строки — мусор, а не битая ссылка |
| Удаление наоборот | объект, потом строка | Строка указывает в пустоту: пользователь видит 404 |

> ⭐ Не доверяй клиенту, что «загрузил». Confirm → API сам делает `HEAD` объекта (размер,
> checksum) и только тогда ставит `uploaded`. Либо опирайся на событие хранилища (раздел 5).

**Уборка** — три слоя, от дешёвого к дорогому:

1. **Lifecycle по префиксу:** всё в `incoming/` старше суток удаляется само.
2. **Чистильщик `pending`:** строки старше `срок presigned + запас` — `HEAD`; объекта нет —
   удалить строку.
3. **Сверка:** листинг бакета (или отчёт инвентаризации, S3 Inventory) против таблицы:
   «объект без строки» и «строка без объекта» — сначала метрика и алерт, удаление — после разбора.

Грузи **недоверенное в одно место, проверенное — в другое**: `incoming/` читает только воркер,
`files/` — только CDN. Непроверенный файл тогда нельзя отдать, даже если ошибся в коде выдачи.

## 5. Обработка загруженного: событие → очередь → воркеры

```text:no-line-numbers
 хранилище ──событие «объект создан»──► очередь ──► воркеры (idempotent)
 (или confirm → outbox → очередь)                     │ 1. проверить тип по содержимому, размер, антивирус
                                                       │ 2. сделать производные (превью, WebP, текст для поиска)
                                                       ├──► объекты files/<id>/thumb-m-<hash>.webp
                                                       └──► БД: status = ready | failed
```

Очереди, DLQ и outbox — в [теме 06](/system-design/building-blocks/06-async-messaging).

- **События хранилища — at-least-once.** Бывают дубли, нет гарантии порядка, редко
  приходят с большой задержкой, редко теряются. Значит: воркер **идемпотентен** (ключи
  производных детерминированы), переход статусов — условный
  `UPDATE files SET status='processing' WHERE id=$1 AND status='uploaded'`, а чистильщик
  досылает задачи для файлов, застрявших в `uploaded` дольше N минут.
- **Источник события** — уведомление хранилища (S3 → SNS/SQS/EventBridge, MinIO → webhook, Kafka,
  AMQP; см. [Хранилища: 03](/storage/03-nfs-minio)) или `confirm` из API через outbox. Второе проще
  тестировать; событие хранилища — страховка от клиента, который не позвонил в `confirm`.
- **Неизменяемые имена производных** (`thumb-m-<hash>.webp`): новая версия — новый ключ, CDN
  кеширует навсегда, инвалидация не нужна.
- **Воркеры читают и пишут потоком**, с лимитами памяти, CPU и таймаутом на файл; защита от «бомб» —
  максимум пикселей, степень сжатия архива, число вложенных файлов. Масштабирование — по длине
  очереди (KEDA); SLI — «время от загрузки до `ready`».

## 6. Отдача файлов: CDN, подписанные ссылки, классы хранения

**Публичные** файлы (превью, статика): бакет остаётся приватным, читать его может только
CDN (origin access control или аналог), пользователи ходят на CDN. **Приватные** файлы:

| Способ | Как | Плюсы | Минусы |
|--------|-----|-------|--------|
| API проверил права → presigned GET | Короткий срок (1–5 минут), клиент качает прямо из хранилища | Просто, нет лишнего компонента | URL уникален — CDN не кеширует; каждое скачивание = запрос к хранилищу |
| ⭐ CDN signed URL | Подпись на пути и сроке проверяет edge | Кеш работает, если подпись не входит в cache key | Ключ подписи на CDN; формат у каждого CDN свой |
| CDN signed cookie | Одна cookie открывает целый префикс | Галереи, сегменты видео: не подписывать каждый URL | Привязка к домену, срок жизни cookie |

Механизм везде один: токен «путь + срок + HMAC» (на nginx его видно руками — `secure_link`, практика C3).
Заголовки при отдаче: `Cache-Control: public, max-age=31536000, immutable` для неизменяемых ключей;
`Content-Disposition` (имя файла, `attachment` для всего, что не картинка); `X-Content-Type-Options: nosniff`.
Пользовательский контент — с **отдельного домена** (`usercontent.example`): загруженный HTML или SVG на
основном домене — это XSS и кража сессии. Range-запросы (видео, докачка) не ломай прокси.

### Классы хранения и lifecycle

| Класс (названия у провайдеров свои) | Доступ | Типичные условия | Для чего |
|--------------------------------------|--------|------------------|----------|
| Горячий (standard) | Мгновенно | Без минимального срока | Свежие файлы |
| Редкий доступ | Мгновенно | Дешевле хранение, но плата за извлечение и минимальный срок (в AWS — 30 дней) | Оригиналы старше N дней |
| Архив | Минуты–часы до первого байта | Минимальный срок до 90–180 дней, платное извлечение | Бэкапы, юридическое хранение |
| Автоматический (intelligent) | Мгновенно | Объект сам «остывает» между классами; есть плата за мониторинг | Когда паттерн доступа неизвестен |

```text:no-line-numbers
 lifecycle-правила бакета (по префиксу и возрасту):
   incoming/   → удалить через 1 день; прервать незавершённый multipart через 1 день
   exports/    → удалить через 7 дней
   files/…/original → через 90 дней в «редкий доступ»
   старые версии (noncurrent) → удалить через 30 дней
```

> ⭐ **Главная статья расходов — исходящий трафик (egress), а не хранение.** В примере из Основ, тема 04
> хранение растёт на ~110 ТБ в год, а отдача — 150 ТБ в месяц. Платишь за гигабайты, уходящие в
> интернет и между регионами, и за запросы (много мелких объектов дороже). Рычаги: CDN и высокий
> hit ratio, современные форматы, `Cache-Control`. Цены у провайдеров разные — считай по тарифам
> ([FinOps: 01](/finops/01-finops-intro)).

## 7. Поиск: зачем он нужен и почему `LIKE` не годится

Пользователю нужно «найти мою ссылку про куртки». Простейшая реализация:

```sql
SELECT * FROM links WHERE title LIKE '%куртк%';
```

Почему это не масштабируется:

- B-tree не работает с шаблоном, начинающимся с `%`: остаётся полный просмотр таблицы — время
  растёт линейно (на 1 млн строк — сотни миллисекунд, на миллиардах — минуты).
- **Нет морфологии** («куртка», «куртки» — разные строки), **нет релевантности** (только
  «подошло/не подошло»), нет опечаток, подсветки и фасетов.

Полнотекстовый поиск строится на **инвертированном индексе**. Но прежде проверь, нужен ли он: в
linkd поиск идёт **внутри одного владельца**, и после фильтра `owner_id` кандидатов могут быть
сотни (раздел 13).

## 8. Инвертированный индекс и анализ текста

Обычный индекс отвечает «документ → слова». Инвертированный — «слово → документы»:

```text:no-line-numbers
 документы                          инвертированный индекс (термин → posting list)
 1: «Каталог зимних курток»         каталог   → [1]      куртк  → [2]
 2: «Распродажа: куртки и ботинки»  курток    → [1]      зимн   → [1, 3]
 3: «Ботинки зимние»                распродаж → [2]      ботинк → [2, 3]

 запрос «зимние ботинки» (AND):  зимн [1, 3] ∩ ботинк [2, 3] = [3]   ← списки отсортированы
```

В posting list хранят номера документов, часто — позиции слов (для поиска фразы)
и частоты (для релевантности). Индекс состоит из неизменяемых сегментов, которые периодически
сливаются.

**Анализатор** превращает текст в термины — и при индексации, и при поиске:

```text:no-line-numbers
 текст → char filter (убрать HTML) → tokenizer (разбить на слова)
       → token filters: нижний регистр → стоп-слова («и», «в») → стемминг/лемматизация → синонимы
```

> ⚠️ Анализатор запроса должен совпадать с анализатором индексации. Иначе документ лежит
> как `куртки`, а запрос превратился в `куртк` — ничего не найдётся.

**Русская морфология.** Слова изменяются по падежам и числам, поэтому нужно приводить их к
основе. **Стеммер** (Snowball) отрезает окончания по правилам: быстро и без словаря, но
ошибается. Реальный результат PostgreSQL (`russian` — Snowball):

```sql
SELECT to_tsvector('russian', 'ссылка ссылки ссылку ссылкой куртки куртка курток');
-- 'куртк':5,6  'курток':7  'ссылк':1,2,3,4
```

Четыре формы «ссылка» склеились, «куртка» и «куртки» — тоже, а родительный падеж множественного
числа «курток» остался отдельным термином: по запросу «куртка» документ «Каталог зимних
курток» не найдётся. **Лемматизатор** (словарный: Hunspell, внешние морфологические
модули) точнее, но тяжелее. Проверь ё/е и свои типичные слова на реальных данных.

Для **казахского** встроенных стеммеров в PostgreSQL и Elasticsearch нет (проверь документацию своей
версии): используют `simple`-анализатор, n-граммы или внешний модуль; смешанные RU/KZ/EN-данные
держат в отдельных полях по языкам. Автодополнение «пока печатаешь» — отдельная задача (префиксные
структуры, ранжирование по популярности): её разберём в
[Бэкенд-задачи: 06](/system-design/backend-cases/) (скоро), здесь не проектируем.

## 9. Релевантность: от TF-IDF к BM25

Совпавших документов бывает тысячи — важен порядок.

- **TF** (term frequency): слово чаще в документе — документ больше о нём. **IDF** (inverse document
  frequency): редкое по коллекции слово важнее частого («и» ничего не значит, «куртка» — значит).
- **TF-IDF** = TF × IDF. Проблемы: сотая «куртка» не делает документ в сто раз релевантнее, а длинный
  документ набирает частоты просто потому, что длинный.
- **BM25** лечит оба: частота «насыщается» (`k1`, по умолчанию ~1,2) и нормируется на длину документа
  относительно средней (`b`, ~0,75):

```text:no-line-numbers
 score(q, d) = Σ по словам запроса:  IDF(t) · tf·(k1 + 1) / (tf + k1·(1 − b + b·|d|/avgdl))
```

В современных версиях Lucene и Elasticsearch BM25 — по умолчанию. Поверх него настраивают вес полей
(`title^3`), затухание по дате, сигналы популярности (`function_score`); оценку разбирает `explain`.
В PostgreSQL `ts_rank` проще — он не использует IDF по коллекции, и для тонкой настройки
релевантности его часто не хватает.

## 10. Elasticsearch / OpenSearch: как устроен кластер

```text:no-line-numbers
 кластер
 ├── нода-1 (data)      ├── нода-2 (data)       ├── нода-3 (data)
 │   links_v2 [S0 primary]  links_v2 [S1 primary]    links_v2 [S0 replica]
 │   links_v2 [S1 replica]  links_v2 [S2 replica]    links_v2 [S2 primary]
 └── ≥ 3 master-eligible ноды (кворум): состояние кластера, размещение шардов

 индекс = N primary-шардов (фиксируется при создании) × (1 + R реплик, меняется на лету)
 шард = полноценный индекс Lucene = набор сегментов
```

- **Шард** — единица деления: документ попадает в шард по `hash(_id) % N`. Число primary-шардов
  после создания не меняется (только `_split`, `_shrink` или переиндексация). **Реплика** —
  копия шарда на другой ноде: переживает потерю ноды и **обслуживает чтения**. Число реплик
  меняют на ходу.
- **Поиск** — scatter-gather: нода-координатор рассылает запрос по одной копии каждого шарда,
  каждый возвращает свой top-N, координатор сливает. Глубокая пагинация (`from + size` больше
  `index.max_result_window`, по умолчанию 10 000) дорога — используй `search_after`.
- **Near-real-time.** Новый документ сначала попадает в буфер и журнал (translog) и **невидим
  для поиска**. Раз в `refresh_interval` (по умолчанию 1 с) буфер превращается в новый
  сегмент — только тогда документ находится. Поэтому «записал и сразу нашёл» не гарантировано;
  шарды, которые 30 секунд никто не искал, refresh пропускают. `refresh=true` на каждую запись
  плодит мелкие сегменты и убивает пропускную способность.
- **Обновление = удалить и вставить**: документ неизменяем, старая версия помечается
  удалённой и исчезает при слиянии сегментов. Частые обновления одних и тех же документов дороги.
- ⚠️ Elasticsearch — **не источник правды.** Нет транзакций; кластер можно потерять и пересобрать.
  Источник правды — БД, индекс — производная копия.

**Размер шардов (ориентиры — сверяй с документацией своей версии).** Elastic советует шарды порядка
10–50 ГБ (для поиска — ближе к нижней границе, для логов — к верхней) и число шардов на ноду
соразмерять с heap: «тысячи мелких шардов» — типовая болезнь (память и работа мастера на каждый шард).
Мало шардов на много данных — нет параллелизма. Heap — не больше половины RAM и ниже ~30 ГБ,
остальное нужно файловому кешу ОС. Пример: индекс 100 ГБ ≈ 4–5 primary-шардов по 20–25 ГБ + одна реплика.

**Mapping** фиксирует типы полей: `text` анализируется (поиск по словам), `keyword` хранится
целиком (точное совпадение, сортировка, агрегации).

```json
PUT links_v1
{
  "settings": { "number_of_shards": 1, "number_of_replicas": 1 },
  "mappings": {
    "dynamic": "strict",
    "properties": {
      "code":       { "type": "keyword" },
      "owner_id":   { "type": "long" },
      "title":      { "type": "text", "analyzer": "russian" },
      "long_url":   { "type": "text", "fields": { "raw": { "type": "keyword", "ignore_above": 2048 } } },
      "created_at": { "type": "date" }
    }
  }
}
```

```json
GET links/_search
{
  "query": { "bool": {
      "must":   [ { "match": { "title": "куртка" } } ],
      "filter": [ { "term": { "owner_id": 42 } } ]
  } },
  "size": 20
}
```

`filter` не влияет на score и кешируется. `dynamic: strict` защищает от «взрыва маппинга»: JSON с
произвольными ключами иначе плодит тысячи полей. OpenSearch — форк Elasticsearch 7.10 (2021, после
смены лицензии); API в основном совместимы, но расходятся с каждой версией — версии и лицензии
проверяй на момент выбора.

## 11. Индекс — копия данных: синхронизация с БД

### Dual write не работает

```text:no-line-numbers
 db.commit()   ✅
 es.index(doc) ❌ таймаут / ES недоступен / процесс убили между двумя строками
 → в БД ссылка есть, в поиске её нет — и никто об этом не знает
 (поменяй местами — получишь в поиске то, чего нет в БД)
```

Распределённой транзакции между PostgreSQL и Elasticsearch нет. Решение — записать **одно**
и доставить остальное надёжно:

| Способ | Как | Плюсы / минусы |
|--------|-----|----------------|
| ⭐ **Outbox + relay** | В транзакции БД — строка и событие в `outbox`; relay публикует в очередь; индексатор пишет в ES | Не теряет события, код приложения знает о событиях ([тема 06](/system-design/building-blocks/06-async-messaging)) |
| **CDC** (Debezium → Kafka) | Читаем WAL PostgreSQL, события строк уходят в Kafka | Приложение не меняется; зависит от схемы таблиц и логической репликации |
| Опрос по `updated_at` | Индексатор раз в N секунд берёт изменённое | Просто; сложности с удалениями (нужен soft delete) и пропусками при равных временах |

**Индексатор:**

- пишет **пачками** через `_bulk` (ориентир — единицы–десятки МБ на запрос);
- идемпотентен: `_id` документа = id строки, повторная запись безвредна;
- защищается от «старого события позже нового» внешней версией: `version_type: external`
  и `version` = номер версии строки или `updated_at` в микросекундах — ES отвергнет устаревшее;
- при `429` от ES (`es_rejected_execution` — очередь записи переполнена) делает backoff,
  а не долбит ещё сильнее ([тема 08](/system-design/building-blocks/08-rate-limiting));
- «ядовитые» документы (ошибка маппинга) уводит в DLQ, а не блокирует поток;
- удаление — тоже событие; запоздавшее событие может «воскресить» документ, поэтому нужна сверка.

```text:no-line-numbers
 POST _bulk
 { "index":  { "_index": "links", "_id": "aZ3x9Qk", "version": 1731850000123456, "version_type": "external" } }
 { "code": "aZ3x9Qk", "owner_id": 42, "title": "Каталог зимних курток", "created_at": "2026-11-17T10:00:00Z" }
 { "delete": { "_index": "links", "_id": "bK81mNa", "version": 1731850000999999, "version_type": "external" } }
```

**Сверка** — страховка: периодически сравнивать БД и индекс диапазонами id (счётчики и
контрольные суммы), расхождения исправлять переиндексацией. **Свежесть** — два слагаемых:
лаг индексатора и `refresh_interval`; для read-your-writes на экране «мои ссылки» берут
данные из БД, а поиск не обещает мгновенность.

### Переиндексация без простоя: alias

Изменился анализатор или mapping? В живом индексе их не поправить — только новый индекс.
Приложение ходит не по имени индекса, а по **alias**:

```text:no-line-numbers
 приложение ──► alias links ──► links_v1   (читает)       alias links_write ──► links_v1 (пишет индексатор)
 1. создать links_v2 с новым mapping/analyzer (replicas = 0, refresh_interval = -1 на время заливки)
 2. залить: _reindex из links_v1 или заново из БД; новые события индексатор пишет в оба индекса
 3. вернуть replicas и refresh_interval; сравнить счётчики и выборочные запросы
 4. атомарно переключить alias одним запросом _aliases
 5. links_v1 оставить на сутки-двое для отката, потом удалить
```

```json
POST _aliases
{ "actions": [
    { "remove": { "index": "links_v1", "alias": "links" } },
    { "add":    { "index": "links_v2", "alias": "links" } },
    { "remove": { "index": "links_v1", "alias": "links_write" } },
    { "add":    { "index": "links_v2", "alias": "links_write" } }
] }
```

Весь `_aliases` применяется атомарно — клиент никогда не видит «ни там, ни там».

## 12. Поиск средствами PostgreSQL: с чего начинать

Для корпуса в миллионы строк PostgreSQL закрывает 80% потребностей **без новой системы в
эксплуатации**. `tsvector` — набор терминов, `tsquery` — запрос, GIN — инвертированный индекс.

```sql
CREATE EXTENSION IF NOT EXISTS pg_trgm;

ALTER TABLE links
  ADD COLUMN search tsvector GENERATED ALWAYS AS (
      setweight(to_tsvector('russian', coalesce(title, '')),    'A') ||
      setweight(to_tsvector('simple',  coalesce(long_url, '')), 'B')
  ) STORED;                                                  -- PG 12+; на большой таблице — перезапись

CREATE INDEX CONCURRENTLY links_search_gin ON links USING gin (search);
CREATE INDEX CONCURRENTLY links_url_trgm   ON links USING gin (long_url gin_trgm_ops);

-- поиск по словам с морфологией, релевантность и подсветка
SELECT code, ts_rank(search, q) AS rank, ts_headline('russian', title, q) AS snippet
  FROM links, websearch_to_tsquery('russian', 'куртки -ботинки') AS q
 WHERE owner_id = 42 AND search @@ q
 ORDER BY rank DESC LIMIT 20;

-- подстрока и опечатки в URL
SELECT code FROM links WHERE owner_id = 42 AND long_url ILIKE '%shop.exam%';
SELECT code FROM links WHERE long_url %> 'shop.exmaple';         -- похожесть фрагмента на часть URL (word_similarity)
```

- **FTS** — слова и морфология (`russian`), веса полей, `ts_rank`; `websearch_to_tsquery` понимает
  синтаксис «как в поисковике» (`-слово`, `"фраза"`, `or`).
- **pg_trgm** — подстроки и опечатки: строка режется на триграммы, GIN ищет по ним; для шаблонов
  короче трёх символов индекс не помогает. URL лучше искать триграммами: парсер FTS разбирает URL на
  хост и путь, но подстроку домена по токенам не найти.
- Порядок величин на 1 млн строк (ноутбук; твои цифры будут другими): подстрока по редкому фрагменту —
  полный просмотр ~230 мс против ~1 мс через триграммный GIN. Измеряй `EXPLAIN (ANALYZE)` на своих данных.

| | PostgreSQL FTS + pg_trgm | Elasticsearch / OpenSearch |
|---|--------------------------|----------------------------|
| Новая система | Нет — те же БД, бэкапы, права | Да: кластер, оператор, мониторинг |
| Согласованность с данными | Транзакционно: индекс = колонка | Асинхронно: outbox, лаг, сверка |
| Релевантность | `ts_rank`, веса — просто | BM25, boosting, function_score, learning-to-rank |
| Фасеты, агрегации по результатам | Неудобно | Сильная сторона |
| Опечатки, синонимы, много языков | Триграммы, словари — ограниченно | Fuzzy, анализаторы, синонимы |
| Масштаб | Реплики для чтения, GIN на одной БД | Шарды и реплики на десятки нод |
| Цена ошибки | Тяжёлый поиск грузит основную БД | Отдельный кластер, отдельные расходы |

> ⭐ **Начинай с PostgreSQL.** Elasticsearch — когда упёрся в конкретное: нужны фасеты и настраиваемая
> релевантность, опечатки и многоязычность, корпус слишком велик для GIN в одной БД, поиск мешает
> основной БД и реплик чтения уже мало. У GIN свои ограничения: вставки идут через pending list, широкие
> запросы с `ts_rank` читают много строк. Для небольших корпусов есть и более лёгкие движки (Meilisearch,
> Typesense). У MongoDB есть текстовые индексы, у ClickHouse — индексы по токенам, но поисковый движок
> с релевантностью они не заменяют ([Базы данных: 09](/databases/09-redis-mongo-clickhouse)). Векторный и
> гибридный поиск — за рамками урока.

## 13. Пример linkd: экспорт ссылок и поиск по своим ссылкам

linkd ×1000: 6 млрд ссылок за 5 лет, но у каждого владельца их немного. Две задачи из этой темы.

**Экспорт «моих ссылок» в CSV — это файл, и он не про горячий путь:**

```text:no-line-numbers
 POST /api/v1/exports ──► 202 {export_id}      строка exports(status=pending) + задача в очередь
 воркер: SELECT по owner_id курсором → CSV.gz потоком → exports/<owner>/<id>.csv.gz → status=ready
 GET /api/v1/exports/<id> → 200 {status, download_url}   ← presigned GET на 15 минут
 lifecycle: exports/ удаляется через 7 дней; сам файл через API не гоняем
```

**Поиск по своим ссылкам** (`GET /api/v1/links?q=куртки`; поле `title` — целевая схема,
в linkd 2.0 его нет). Лестница решений, подниматься только по доказанной нужде:

| Шаг | Решение | Когда достаточно |
|-----|---------|------------------|
| 1 | `owner_id` по индексу `(owner_id, created_at DESC)` + `ILIKE` по найденным строкам | У владельца сотни–тысячи ссылок (почти все) |
| 2 | FTS (`search tsvector` + GIN) и триграммы по URL | У отдельных владельцев — сотни тысяч ссылок, нужна морфология |
| 3 | Elasticsearch | Глобальный поиск, фасеты по доменам, опечатки, нагрузка поиска мешает БД |

Запросы вида «все ссылки на домен evil.example» — не поиск, а фильтр: колонка `host` с обычным
индексом (или аналитика в ClickHouse). Запись в индекс не должна ломать создание ссылки:
индексация — после коммита и вне горячего пути; создание и редирект поиска не ждут.

## 14. ⚙️ Эксплуатация

Семь стандартных вопросов из [Основ, тема 04](/system-design/basics/04-backend-vs-devops) — отдельно
для файлов и для поиска.

### 14.1 Развёртывание

- **Файлы.** Managed S3-совместимое хранилище или self-hosted (MinIO-форк, Ceph RGW — см.
  [Хранилища: 03](/storage/03-nfs-minio), там же про смену статуса MinIO). Бакеты, политики,
  CORS и lifecycle — в IaC (Terraform), не руками. Разделяй бакеты или префиксы по ролям:
  `incoming`, `files`, `exports` — у каждого свои права и lifecycle. Доступ API и воркеров —
  через роль сервисного аккаунта, не статические ключи в образе. Воркеры — отдельный
  Deployment. ⚠️ Схему ключей не «переименуешь»: смена = копирование и dual-read.
- **Поиск.** PG FTS: миграции `CREATE INDEX CONCURRENTLY`; `ADD COLUMN … GENERATED … STORED`
  перезаписывает таблицу — на больших таблицах делай через триггер и пачки
  ([Базы данных: 13](/databases/13-schema-migrations)). Elasticsearch: managed или оператор
  (ECK, OpenSearch operator) на StatefulSet с отдельными пулами нод под роли, anti-affinity
  и распределение по зонам (`awareness`), `vm.max_map_count=262144`, heap по роли ноды.
  Шаблоны индексов, mapping и alias — в git; индексатор — отдельный Deployment;
  обновление — rolling, нода за нодой.

### 14.2 Масштабирование

- **Файлы.** Хранилище масштабируется само; потолки — лимиты запросов на префикс (в AWS
  порядка тысяч в секунду на префикс; у других — иначе), лимиты KMS при шифровании ключом
  KMS, пропускная способность NAT (трафик в хранилище лучше пускать через приватный endpoint).
  Воркеры — по длине очереди, скачивание — CDN.
- **Поиск.** PG — реплики чтения. Elasticsearch — больше data-нод: шарды ребалансируются, но
  **число primary-шардов фиксировано** — планируй заранее или готовь reindex. Реплики
  добавляют пропускную способность чтения; для multi-tenant — `routing` по `owner_id`
  (запрос владельца идёт в один шард; риск — перекос на крупных клиентах). Потолки: heap и число
  шардов, диск и ввод-вывод слияний, пропускная способность `_bulk`.

### 14.3 Наблюдаемость

| | Файлы | Поиск |
|---|-------|-------|
| SLI | Доля загрузок, дошедших до `ready` за N секунд; время «загрузка → ready» (p99 ≤ 30 с, как в Основах, тема 04) | p99 поиска, доля поисков без ошибок |
| Очередь | Длина и возраст старейшей задачи, DLQ | Лаг индексатора (секунды) |
| Хранилище | 4xx/5xx и задержка запросов, объём по префиксам и классам | ES: `green/yellow/red`, unassigned shards, heap, старый GC, отказы в thread pool (`rejected`), диск против watermark |
| Целостность | Число сирот и «строк без объектов» из сверки | Расхождение БД и индекса по сверке |
| Деньги | Egress по дням, hit ratio CDN | Размер индекса и число шардов |

⚠️ Алерт по **лагу индексации** важнее алерта по CPU: кластер может быть «зелёным», а поиск —
недельной давности. Лаг мерь как «возраст самой старой необработанной записи outbox».

### 14.4 Отказы

| Что упало | Что видит пользователь | Что делает система |
|-----------|-----------------------|--------------------|
| Хранилище недоступно | Не грузится и не скачивается; метаданные и API живы | Подпись URL локальна — клиент ретраит; `pending` живёт дольше TTL; CDN отдаёт закешированное |
| Событие потеряно или задвоено | Файл висит в «обрабатывается» | Идемпотентность + чистильщик досылает задачи для застрявших `uploaded` |
| Воркер падает на файле | `failed` для одного файла | Ретраи, затем DLQ; остальные идут дальше |
| CDN | Рост нагрузки на origin | Origin держит ограниченный поток; деградация заранее продумана |
| Elasticsearch `red`, недоступен | Поиск не работает или устарел | Таймаут и circuit breaker; запасной путь — PG по `owner_id`; создание и редирект не затронуты; события копятся в очереди (хватит ли retention?) |
| Диск ES на flood-stage (по умолчанию 95%) | Индекс только для чтения, индексатор получает ошибки | Алерт на 85% (low watermark); освободить диск или добавить ноду |
| Индексатор отстаёт | Новые ссылки не находятся | Масштабировать индексатор, проверить `429` от ES, сверка |

### 14.5 Данные и DR

- **Файлы.** Оригиналы — источник правды: версионирование, репликация в другой регион
  (асинхронная — RPO минуты, не ноль; у AWS есть платная опция с заявленным окном 15 минут),
  object lock против шифровальщика и `rm`, lifecycle для старых версий
  ([Облака: 04](/cloud/04-s3-storage)). Производные (превью) — пересоздаём.
- ⚠️ **Согласованность при восстановлении.** Восстановили БД на момент T: объекты, загруженные
  после T, — сироты (найдёт сверка), а объекты, **физически удалённые** после T, — потеря,
  строки указывают в пустоту. Поэтому физическое удаление откладывают дольше окна PITR
  (или опираются на версионирование).
- **Поиск.** Индекс — производная: бэкап не обязателен, если **время пересборки меньше RTO**.
  Оцени: число документов / скорость bulk на твоём железе (измерь) = часы пересборки. Если
  много — снапшоты в S3 (`_snapshot`, SLM-политика с retention) и **регулярный restore-тест**.
  PG FTS бэкапится вместе с БД: `tsvector` — вычисляемая колонка, GIN пересобирается.

### 14.6 Безопасность

- **Файлы.** Бакет приватный, публичный доступ заблокирован политикой аккаунта; минимальные
  права по ролям (API подписывает `incoming/*`, воркер читает `incoming` и пишет `files`, CDN
  читает `files`, удаляет один чистильщик). Presigned: короткий срок, зафиксированные ключ, тип и
  размер; URL не в логах. Проверка содержимого, антивирус, удаление EXIF, лимиты размера и
  пикселей. Пользовательский контент — с отдельного домена, `nosniff`, `attachment`.
  Шифрование на диске и TLS; аудит доступа (access logs, data events); требования регулятора
  к месту хранения персональных данных.
- **Поиск.** Elasticsearch не торчит наружу; включены аутентификация и TLS (в 8+ по умолчанию);
  клиент **не присылает Query DSL** — сервер строит запрос сам. Фильтр по `owner_id` ставится
  **на сервере в каждом запросе** — иначе чужие данные. Дорогие запросы (wildcard с
  ведущим `*`, огромный `size`) — вектор DoS: ограничивай и лимитируй
  ([тема 08](/system-design/building-blocks/08-rate-limiting)). Удаление по запросу
  пользователя должно дойти до индекса и до снапшотов.

### 14.7 Стоимость

- **Файлы.** egress ≫ хранение ≫ запросы. Рычаги: CDN и hit ratio, форматы и сжатие,
  lifecycle в холодные классы (с учётом минимального срока и платы за извлечение), чистка
  старых версий, хвостов multipart и `incoming/`. Много мелких объектов — дорогие запросы.
  Репликация между регионами удваивает хранение и добавляет трафик. Теги бакетов и
  префиксов — чтобы отчёт показывал, кто платит.
- **Поиск.** PG FTS: «бесплатно», но потребляет CPU и диск основной БД — вынеси чтение на
  реплику. Elasticsearch: RAM и диск × (1 + реплики), минимум три ноды для нормальной
  отказоустойчивости — постоянная база счёта даже для маленького корпуса. Рычаги:
  не индексировать лишние поля (`index: false`), не хранить лишнее в `_source`, холодные
  ноды для старого. Managed против своего — это сравнение со временем людей
  ([FinOps: 01](/finops/01-finops-intro)).

## Грабли

| Грабля | Что не так | Правильно |
|--------|-----------|-----------|
| Файлы через API «для простоты» | API держит соединения, трафик идёт через поды | Presigned POST с `content-length-range`; API выдаёт только подпись |
| Имя файла пользователя — ключ объекта | Коллизии, `../`, юникод | `files/<uuid>`, имя — в БД |
| Верить `Content-Type` клиента | Скрипт под видом картинки | Magic bytes в воркере, nosniff, отдельный домен |
| Удалить объект, потом строку (и наоборот при создании) | Битые ссылки или сироты | Статусы; в БД первой помечаем, объект — позже |
| Нет lifecycle на `incoming/` и multipart | Мусор копится и стоит денег | Правила удаления и `AbortIncompleteMultipartUpload` |
| Подпись в cache key CDN | hit ratio падает, счёт растёт | Подпись не входит в cache key |
| `LIKE '%…%'` на большой таблице | Полный просмотр | FTS + GIN или pg_trgm |
| Запись в БД и в ES подряд | Расхождение без следов | Outbox/CDC + индексатор + сверка |
| `refresh=true` на каждую запись | Тысячи мелких сегментов | Дефолтный refresh, `wait_for` — точечно |
| Тысячи мелких шардов | Память и мастер задыхаются | Шард 10–50 ГБ, меньше индексов |
| Менять mapping/analyzer «на месте» | Старые документы остаются по-старому | Новый индекс + alias |
| Query DSL от клиента в ES | Утечка чужих данных, дорогие запросы | Сервер строит запрос, `owner_id` всегда в фильтре |

## 💼 Как это на работе

- **Бэкенд-сторона.** Загрузка файлов почти всегда — один шаблон: строка в БД со статусом, presigned URL,
  событие, воркер; умение нарисовать его вместе с уборкой сирот и идемпотентностью — заметная часть
  senior-собеса. На «нужен ли тут Elasticsearch?» честный ответ — «померим на PostgreSQL».
- **DevOps-сторона.** Бакеты, политики и lifecycle — код; главные риски — публичный бакет, ключи в образах,
  неотлаженное удаление и счёт за egress. Elasticsearch — самая «тяжёлая» часть: heap, шарды, диск, снапшоты,
  rolling upgrade; без плана переиндексации и мониторинга лага поиск тихо устаревает.
- **linkd — твой полигон.** MinIO и практика C1–C3, экспорт ссылок в S3 и поиск по `title` на PG FTS — это
  история «померил и выбрал», а не «поставил Elasticsearch на всякий случай».
- **Решения записывай:** «почему PG FTS, а не ES», «почему presigned POST» — готовые ADR
  ([Основы: 05](/system-design/basics/05-design-doc-adr)).

## 📌 Шпаргалка

| Хочу | Как |
|------|-----|
| Где хранить файлы | Объектное хранилище; БД — метаданные и статус |
| Загрузка мимо API | Presigned POST (`content-length-range`, тип) / PUT; срок 15 минут |
| Файл больше ~100 МБ | Multipart: части 5 МиБ–5 ГиБ, до 10 000; abort-правило в lifecycle |
| Согласие БД и хранилища | `pending → uploaded → processing → ready`; confirm через HEAD; уборка в 3 слоя |
| Удалить файл | Пометка в БД, объект — позже (дольше окна PITR) |
| Обработка | Событие или confirm → очередь → идемпотентные воркеры, производные с хешем в имени |
| Приватные файлы | CDN signed URL/cookie или presigned GET на минуты |
| Расходы на файлы | egress ≫ хранение: CDN, форматы, lifecycle, классы |
| Поиск по словам | Инвертированный индекс: токены → posting lists |
| Релевантность | BM25: TF с насыщением, IDF, длина документа |
| Elasticsearch | Шарды (фиксированы) × реплики (меняются); refresh 1 с = near-real-time |
| Индекс и БД | Outbox/CDC → индексатор (bulk, external version) + сверка |
| Новый mapping | Новый индекс → заливка → `_aliases` → откат в запасе |
| Начать поиск | PG: `tsvector` + GIN, `pg_trgm` для подстрок |
| Эксплуатация | Права по ролям, lifecycle, лаг индексатора, snapshots в S3, restore-тест |

## 🧠 Что запомнить

1. ⭐ Файлы — в объектное хранилище, метаданные и статусы — в БД; ни диск пода, ни `bytea` не подходят.
2. Объект неизменяем, каталогов нет, ключ — строка; ключом не должно быть имя от пользователя.
3. ⭐ Presigned URL — bearer-токен: короткий срок, зафиксированные ключ/тип/размер (POST policy), не в логах.
4. Multipart: части 5 МиБ–5 ГиБ, до 10 000 частей; брошенные загрузки платные — нужен abort в lifecycle.
5. ⭐ БД и хранилище без общей транзакции: статусы, правильный порядок операций, чистильщик и сверка.
6. События хранилища — at-least-once: воркеры идемпотентны, застрявшие файлы досылает чистильщик.
7. ⭐ Главная статья расходов на файлы — egress: CDN, форматы, lifecycle.
8. ⭐ Инвертированный индекс (слово → документы) + анализатор (токены, нормализация, морфология) — основа полнотекстового поиска; BM25 ранжирует.
9. Elasticsearch: число primary-шардов фиксировано, реплики — нет; refresh даёт near-real-time; это копия, не источник правды.
10. ⭐ Индекс синхронизируют через outbox/CDC, не dual write; новый mapping — новый индекс и alias; начинай поиск с PostgreSQL.

### Блок A. Теория

**A1.** Почему файлы не хранят в БД и на диске пода и чем объектное хранилище отличается от файловой системы?

<details><summary>Ответ</summary>

БД: раздувание таблиц, WAL и бэкапов, соединение занято на время скачивания. Диск пода:
эфемерный и не общий — ломает stateless. Объектное хранилище: плоские ключи вместо дерева,
объект неизменяем (замена целиком), нет rename (копия + удаление), доступ по HTTP, большой
масштаб и сохранность, но больше задержка первого байта. `bytea` допустим для мелких файлов.

</details>

**A2.** ⭐ Что делает presigned URL, как ограничить размер и тип загрузки и в чём риск?

<details><summary>Ответ</summary>

Даёт клиенту временное право на одну операцию над одним объектом: подпись HMAC от секретного
ключа сервиса и срок жизни. Размер и тип ограничивает presigned POST (`content-length-range`,
`Content-Type`); у PUT можно подписать `Content-Type`. Риск — URL это bearer-токен: утёк (например,
в логи) — им воспользуются до истечения. Меры: короткий срок, фиксированный ключ, проверка
содержимого после загрузки.

</details>

**A3.** ⭐ Когда нужен multipart и какие у него ловушки?

<details><summary>Ответ</summary>

Для больших файлов (ориентир ~100 МБ) и плохих сетей: части грузятся параллельно, повторяются по
отдельности, загрузка возобновляется через `ListParts`. Ловушки: часть не меньше 5 МиБ (кроме
последней), не больше 10 000 частей, брошенные части невидимы и платные (нужен
`AbortIncompleteMultipartUpload`), `ETag` составного объекта — не MD5.

</details>

**A4.** ⭐ Опиши процесс «upload → confirm → process» и статусы файла.

<details><summary>Ответ</summary>

API создаёт строку `pending` и выдаёт presigned POST; клиент грузит объект в `incoming/`; confirm
(или событие хранилища) — API делает `HEAD` и ставит `uploaded`; задача в очередь; воркер
проверяет и обрабатывает (`processing`), пишет производные, ставит `ready` или `failed`.

</details>

**A5.** ⭐ Как избежать сирот между БД и хранилищем и в каком порядке удалять?

<details><summary>Ответ</summary>

При создании — строка раньше объекта; при удалении — сначала пометка в БД, затем асинхронно объект.
Уборка: lifecycle на `incoming/`, чистильщик `pending`, периодическая сверка листинга с таблицей
с алертом (не молчаливым удалением).

</details>

**A6.** Почему обработчики событий хранилища должны быть идемпотентными?

<details><summary>Ответ</summary>

Доставка at-least-once: дубли и произвольный порядок неизбежны. Детерминированные ключи производных
и условный переход статуса (`WHERE status='uploaded'`) делают повтор безвредным.

</details>

**A7.** Как отдавать приватные файлы: presigned GET или CDN signed URL?

<details><summary>Ответ</summary>

Presigned GET — просто, но URL уникален, CDN не кеширует, каждый запрос идёт в хранилище. CDN
signed URL/cookie — подпись проверяет edge, кеш работает, если подпись не входит в cache key;
cookie удобна для целого префикса (галерея, сегменты видео).

</details>

**A8.** ⭐ Почему главная статья расходов на файлы — egress? Какие lifecycle-правила нужны почти всегда?

<details><summary>Ответ</summary>

Платишь за гигабайты, уходящие в интернет и между регионами; хранение растёт медленнее отдачи.
Правила: удалять `incoming/` через сутки, прерывать незавершённый multipart, переводить старые
оригиналы в «редкий доступ», удалять старые версии.

</details>

**A9.** ⭐ Почему `LIKE '%x%'` не масштабируется и что даёт инвертированный индекс?

<details><summary>Ответ</summary>

Ведущий `%` не использует B-tree — полный просмотр, время растёт линейно. Инвертированный индекс
хранит «термин → документы»; запрос — пересечение отсортированных списков. Плюс морфология и
релевантность, которых у `LIKE` нет.

</details>

**A10.** Что такое анализатор, почему он одинаков при индексации и поиске и чем BM25 лучше TF-IDF?

<details><summary>Ответ</summary>

Анализатор — цепочка: char filter → tokenizer → фильтры (регистр, стоп-слова, стемминг, синонимы).
Если запрос анализируется иначе, термины не совпадут. BM25 «насыщает» частоту слова и нормирует
на длину документа — длинный текст не выигрывает только за счёт длины.

</details>

**A11.** ⭐ Чем шарды отличаются от реплик, что нельзя менять после создания индекса и откуда near-real-time?

<details><summary>Ответ</summary>

Primary-шард — единица деления данных, их число фиксируется при создании (иначе `_split`,
`_shrink`, reindex); реплика — копия шарда на другой ноде: отказоустойчивость и чтение, число меняется
на ходу. Документ видим после refresh (по умолчанию раз в 1 с) — «записал и сразу нашёл» не
гарантировано; для своих данных читают из БД.

</details>

**A12.** ⭐ Что такое dual write, как синхронизировать индекс с БД и как переиндексировать без простоя?

<details><summary>Ответ</summary>

Dual write — запись в БД и в индекс двумя вызовами: между ними сбой даёт расхождение без следов.
Решение — БД + outbox в транзакции, relay, очередь, идемпотентный индексатор (или CDC) и
периодическая сверка. Переиндексация: новый индекс, заливка, дозапись новых событий в оба,
сверка, атомарный `_aliases`, старый индекс в запасе для отката.

</details>

### Блок B. «Что тут не так»

```
B1.  API принимает файл multipart/form-data и сам заливает в S3 — «так проще». 30 подов, видео по 100 МБ.

B2.  Presigned PUT выдаём на 7 дней: «чтобы не протухал, пока человек соберётся».

B3.  Ключ объекта = имя файла, которое прислал пользователь.

B4.  Тип файла проверяем по расширению и заголовку Content-Type из запроса.

B5.  Удаление файла: сначала DELETE объекта в S3, потом DELETE FROM files.

B6.  «S3 eventually consistent, поэтому после PUT ждём 5 секунд» — про Amazon S3 в 2026 году.

B7.  На таблице в 100 млн строк медленный LIKE '%куртка%'. Решение: добавить B-tree-индекс по title.

B8.  Обработчик: db.commit(); es.index(doc) — «если ES упадёт, повторим в следующий раз».

B9.  Elasticsearch: 1 000 индексов по 50 МБ, у каждого 5 primary-шардов.

B10. Эндпоинт поиска принимает из тела запроса готовый Query DSL и пересылает его в Elasticsearch.
```

<details><summary>Ответы</summary>

**B1.** ⚠️ API держит соединения на всё время загрузки и гонит байты через поды. Presigned POST — API
только выдаёт подпись.

**B2.** ⚠️ Bearer-токен на неделю: утёк — загрузят что угодно. Срок — минуты, при необходимости
выдать новый.

**B3.** ⚠️ Коллизии, `../`, юникод. Ключ — `files/<uuid>`, имя — в БД и в `Content-Disposition`.

**B4.** ⚠️ Оба значения контролирует клиент. Проверять содержимое (magic bytes) в воркере, раздавать с
`nosniff` и с отдельного домена.

**B5.** ⚠️ Упал между шагами — строка ведёт в пустоту, у пользователя 404. Сначала пометка в БД, объект —
позже.

**B6.** ⚠️ С декабря 2020 Amazon S3 строго согласован для `PUT`/`DELETE` и листинга; пауза не нужна. Для
другого S3-совместимого хранилища — смотреть его документацию.

**B7.** ⚠️ B-tree не работает с ведущим `%`. Нужен GIN: FTS (`tsvector`) для слов или `pg_trgm` для подстрок.

**B8.** ⚠️ Dual write: падение между строками — расхождение без следов, «в следующий раз» не наступит.
Outbox/CDC + индексатор + сверка.

**B9.** ⚠️ 5 000 шардов по ~10 МБ — накладные расходы памяти и мастера. Один шард на мелкий индекс или
объединить индексы.

**B10.** ⚠️ Клиент может обойти фильтр по `owner_id` и увидеть чужое или запустить дорогие запросы. Сервер
строит запрос сам и всегда добавляет фильтр владельца.

</details>

</details>

#### C2. 🔑 Multipart на 12 МиБ

```python
# multipart.py — API выдаёт URL частей, «клиент» грузит, API собирает
import boto3, requests
from botocore.client import Config

s3 = boto3.client("s3", endpoint_url="http://127.0.0.1:9000",
                  aws_access_key_id="admin", aws_secret_access_key="admin-secret-123",
                  region_name="us-east-1",
                  config=Config(signature_version="s3v4", s3={"addressing_style": "path"}))
BUCKET, KEY, PART = "uploads", "incoming/big-file", 5 * 1024 * 1024
data = open("bigfile.bin", "rb").read()

upload_id = s3.create_multipart_upload(Bucket=BUCKET, Key=KEY)["UploadId"]
parts = []
for n in range(1, -(-len(data) // PART) + 1):
    url = s3.generate_presigned_url("upload_part", ExpiresIn=3600,
          Params={"Bucket": BUCKET, "Key": KEY, "UploadId": upload_id, "PartNumber": n})
    resp = requests.put(url, data=data[(n - 1) * PART : n * PART])      # это делает клиент
    parts.append({"PartNumber": n, "ETag": resp.headers["ETag"]})

s3.complete_multipart_upload(Bucket=BUCKET, Key=KEY, UploadId=upload_id,
                             MultipartUpload={"Parts": parts})
head = s3.head_object(Bucket=BUCKET, Key=KEY)
print(head["ContentLength"], head["ETag"])
```


`s3.list_multipart_uploads(Bucket="uploads")`; прерви её `abort_multipart_upload`. Что означает
суффикс в `ETag`?

<details><summary>Ответ</summary>

`ETag` вида `"<hash>-3"`: суффикс — число частей, хеш — от хешей частей, а не MD5 файла. Брошенная загрузка

</details>

### Блок D. Инциденты

**D1.** Пользователи пишут: «загрузил фото — висит в статусе "обрабатывается"». В очереди пусто, воркеры здоровы.

<details><summary>Ответ</summary>

Событие потеряно или не создано (клиент не вызвал `confirm`, уведомление хранилища отключено). Сейчас:
найти файлы в `uploaded` старше N минут и отправить задачи заново (обработка идемпотентна). Потом: чистильщик

</details>

**D2.** Счёт за облако вырос вдвое за неделю при том же числе пользователей. Рост — в строке исходящего трафика.

<details><summary>Ответ</summary>

Проверить hit ratio CDN: после перехода на подписанные URL подпись попала в cache key — каждый URL уникален,
кеш не работает, всё идёт с origin. Или hotlinking с чужих сайтов. Исправить cache key, ограничить
`Referer`/подписывать, поставить алерт на egress по дням.

</details>

**D3.** Восстановили БД из бэкапа на утро. Часть документов в интерфейсе не открывается: «объект не найден».

<details><summary>Ответ</summary>

Строки указывают на объекты, физически удалённые после точки восстановления. Если включено версионирование —
вернуть версии. Системно: физическое удаление после мягкого — дольше окна PITR; сверка после каждого
восстановления; учения «БД + хранилище» вместе.

</details>

**D4.** После релиза «куртки» перестало находить старые ссылки, новые находятся.

<details><summary>Ответ</summary>

Анализатор сменили на живом индексе: новые документы проиндексированы по-новому, старые — по-старому.
Анализатор и mapping не меняют «на месте»: новый индекс, заливка, переключение alias. Сейчас — откат
конфигурации и переиндексация; в CI — тест на реальных словах.

</details>

**D5.** Жалоба: «создал ссылку — в поиске её нет уже час». Кластер Elasticsearch зелёный.

<details><summary>Ответ</summary>

Лаг индексации: relay outbox завис, индексатор в crash-loop на «ядовитом» документе или упёрся в `429`.
Смотреть возраст старейшей записи outbox, лаг очереди, DLQ, логи индексатора. Починить поток, сверка добьёт
расхождения. Алерт ставить на лаг, а не на статус кластера.

</details>

### Блок E. Вопросы с собеседования

**1.** Спроектируйте загрузку больших файлов (до 5 ГБ) для веб-приложения.

<details><summary>Ответ</summary>

Клиент просит разрешение у API; API создаёт строку `pending` и выдаёт presigned URL частей multipart; клиент
грузит параллельно и возобновляет; confirm — API проверяет `HEAD`; событие → очередь → воркер. Уборка: lifecycle
на `incoming/` и abort multipart. Отдача — CDN. Эксплуатация: права по ролям, лимиты, egress, мониторинг очереди.

</details>

**2.** Как работает presigned URL и какие у него риски?

<details><summary>Ответ</summary>

Подписанное временное право на операцию над объектом; хранилище проверяет подпись. Риски: bearer-токен (утечка
через логи), слишком долгий срок, отсутствие ограничений размера и типа. Меры: короткий срок, POST policy,
фиксированный ключ, проверка содержимого.

</details>

**3.** Как держать БД и S3 согласованными?

<details><summary>Ответ</summary>

Общей транзакции нет — статусы и порядок операций (строка первой, при удалении помечаем в БД первой),
идемпотентные воркеры, уборка (lifecycle, чистильщик, сверка), мягкое удаление дольше окна PITR.

</details>

**4.** Как устроен полнотекстовый поиск?

<details><summary>Ответ</summary>

Анализатор превращает текст в термины; инвертированный индекс хранит «термин → документы»; запрос
анализируется тем же анализатором, списки пересекаются; результаты ранжирует BM25 (TF с насыщением, IDF,
длина документа).

</details>

**5.** PostgreSQL FTS или Elasticsearch?

<details><summary>Ответ</summary>

Начать с PostgreSQL: нет новой системы, транзакционная согласованность, GIN + pg_trgm. Elasticsearch — при
фасетах, тонкой релевантности, опечатках и многоязычности, большом корпусе или когда поиск мешает основной БД.
Решать по измерениям на своих данных.

</details>

**6.** Как синхронизировать Elasticsearch с БД?

<details><summary>Ответ</summary>

Outbox или CDC → очередь → индексатор с `_bulk`, `_id` = id строки, внешней версией; backoff на `429`; DLQ;
периодическая сверка; мониторинг лага. Dual write не использовать.

</details>

**7.** Как поменять mapping в проде без простоя и сколько шардов делать?

<details><summary>Ответ</summary>

Новый индекс, заливка, дозапись новых событий в оба, сверка, атомарное переключение alias, старый индекс в
запасе. Шарды — по объёму (ориентир 10–50 ГБ на шард, не тысячи мелких); число primary фиксируется при
создании — закладывай рост или готовь reindex; реплик ≥ 1.

</details>

**8.** Как защитить приватные файлы и не разориться на раздаче?

<details><summary>Ответ</summary>

Приватный бакет, доступ только у CDN и подписанных ссылок с коротким сроком; пользовательский контент — с
отдельного домена. Расходы: CDN и hit ratio (подпись вне cache key), современные форматы, lifecycle в холодные
классы, алерты на egress.
