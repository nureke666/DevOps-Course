# 05. Merge conflict: причины, разрешение, профилактика

> Роадмап → 1. Git → 3. Собесы: **«Что такое merge conflict и каковы причины?»** —
> один из трёх вопросов, которые вообще спрашивают про git.
> **После темы ты умеешь:** объяснить, почему возникает конфликт, прочитать маркеры,
> разрешить конфликт руками, откатить неудачное слияние и — главное — конфликтов избегать.

---

## 🗺️ Карта темы

```text:no-line-numbers
  Общий предок (merge base):        timeout: 30
            │
     ┌──────┴───────┐
     ▼              ▼
   main          feature
timeout: 60     timeout: 90      ← ОДНА И ТА ЖЕ строка изменена ПО-РАЗНОМУ
     └──────┬───────┘
            ▼
      git merge feature
            │
            ▼
   CONFLICT (content): Merge conflict in config.yml
   Automatic merge failed; fix conflicts and then commit the result.

   В файле появляется:
   <<<<<<< HEAD              ← моя версия (ветка, в которой я стою)
   timeout: 60
   =======                   ← разделитель
   timeout: 90
   >>>>>>> feature           ← их версия (та, что я сливаю)

   Мой цикл действий:
   1. git status            → какие файлы конфликтуют
   2. открыть файл          → решить, каким должен быть результат
   3. убрать маркеры        → оставить правильный текст
   4. git add <файл>        → «конфликт разрешён»
   5. git commit            → завершить слияние
```

---

## 1. Что такое merge conflict

**Конфликт слияния** — ситуация, когда git не может автоматически объединить изменения,
потому что **один и тот же участок файла изменён по-разному в двух ветках**, и git не имеет
права решать, какая версия правильная.

Важно: git **умеет** сливать изменения одного файла — если они в разных местах. Конфликт
возникает только на пересечении.

```text:no-line-numbers
Ветка A: правит строки 10-12        Ветка B: правит строки 80-85   → слилось автоматически
Ветка A: правит строку  42          Ветка B: правит строку  42     → КОНФЛИКТ
```

Конфликт — **не ошибка и не поломка**. Это запрос к человеку: «реши, как должно быть».

## 2. ⭐ Причины конфликтов (ответ для собеса)

| Причина | Пример |
|---------|--------|
| **Одна строка изменена в двух ветках по-разному** | В `values.yaml` двое поставили разный `replicas` |
| **Соседние строки / один блок** | Оба добавили строку в конец одного списка портов |
| **Файл изменён в одной ветке и удалён в другой** | `modify/delete`: один правил `old-config.yml`, другой его удалил |
| **Файл добавлен в обеих ветках с разным содержимым** | `add/add`: оба создали `README.md` |
| **Переименование против правки** | Один переименовал `deploy.yml` → `deployment.yml`, другой правил старый |
| **Разные окончания строк / автоформатирование** | CRLF vs LF, prettier переформатировал весь файл — «конфликт всего» |
| **Долгоживущая ветка** | Ветка неделю не синхронизировалась, `main` ушёл на 80 коммитов |
| **Сгенерированные файлы в репозитории** | `package-lock.json`, `terraform.lock.hcl`, собранные бандлы, дампы |

**Корневая причина почти всегда одна:** двое параллельно меняли одно и то же место,
и никто не синхронизировался вовремя.

> 🎤 **Формулировка для собеса:** «Merge conflict — это когда git при слиянии видит, что один
> и тот же участок файла изменён по-разному в двух ветках, и не может выбрать версию
> автоматически. Причины: параллельные правки одних и тех же строк, правка против удаления
> файла, добавление одинаковых файлов, переименования, а на практике чаще всего — долгоживущие
> ветки, которые давно не синхронизировались с main. Разрешается вручную: смотрю `git status`,
> правлю файл, убираю маркеры, `git add`, `git commit`. Если понял, что слился не туда, —
> `git merge --abort`.»

## 3. Как выглядит конфликт

```bash
git switch main
git merge feature/timeout
```
```text:no-line-numbers
Auto-merging config.yml
CONFLICT (content): Merge conflict in config.yml
Automatic merge failed; fix conflicts and then commit the result.
```

```bash
git status
```
```text:no-line-numbers
You have unmerged paths.
  (fix conflicts and run "git commit")
  (use "git merge --abort" to abort the merge)

Unmerged paths:
  (use "git add <file>..." to mark resolution)
        both modified:   config.yml
```

Содержимое файла:
```yaml
server:
  host: 0.0.0.0
<<<<<<< HEAD
  timeout: 60
  retries: 3
=======
  timeout: 90
>>>>>>> feature/timeout
  port: 8080
```

| Маркер | Что значит |
|--------|-----------|
| `<<<<<<< HEAD` | Начало «моей» версии — ветки, в которой я стою |
| `=======` | Разделитель |
| `>>>>>>> feature/timeout` | Конец «их» версии — ветки, которую сливаю |

При `git rebase` стороны **меняются местами**: `HEAD` — это то, на что перебазируешься
(обычно `main`), а «их» — твои собственные коммиты. Частая причина путаницы (тема 06).

Более информативный режим (рекомендую включить):
```bash
git config --global merge.conflictStyle zdiff3
```
```yaml
<<<<<<< HEAD
  timeout: 60
||||||| merge base            ← ⭐ ЧТО БЫЛО ИЗНАЧАЛЬНО — видно, кто что менял
  timeout: 30
=======
  timeout: 90
>>>>>>> feature/timeout
```

## 4. Разрешение: пошагово

```bash
git status                       # 1. увидеть список конфликтных файлов
git diff                         # 2. посмотреть конфликты (diff покажет обе стороны)

vim config.yml                   # 3. решить, каким должен быть ИТОГОВЫЙ файл
                                 #    убрать ВСЕ маркеры <<<<<<<, =======, >>>>>>>

git add config.yml               # 4. пометить как разрешённый
git status                       # 5. проверить, не осталось ли unmerged
git commit                       # 6. завершить (сообщение git предложит сам)
```

Решение — **не «выбрать одну из сторон»**, а понять, что должно получиться. Часто правильный
ответ — комбинация:

```yaml
server:
  host: 0.0.0.0
  timeout: 90        # взяли значение из feature
  retries: 3         # но сохранили строку из main
  port: 8080
```

### Быстрые способы выбрать сторону целиком

```bash
git checkout --ours   config.yml     # взять версию текущей ветки (HEAD)
git checkout --theirs config.yml     # взять версию сливаемой ветки
git restore --source=MERGE_HEAD --worktree config.yml   # современный аналог --theirs
git add config.yml
```
⚠️ Это законно для файлов, которые целиком принадлежат одной стороне (например, `package-lock.json`
перегенерируют, а не сливают). Для конфига, где важны обе правки, — руками.

### Полезные команды во время конфликта

```bash
git diff --name-only --diff-filter=U     # список конфликтных файлов (удобно для скриптов)
git diff --ours config.yml               # что изменилось относительно моей стороны
git diff --theirs config.yml             # относительно их стороны
git log --merge -p config.yml            # ⭐ коммиты обеих веток, трогавшие этот файл
git show :1:config.yml                   # версия общего предка
git show :2:config.yml                   # версия HEAD (ours)
git show :3:config.yml                   # версия MERGE_HEAD (theirs)
git mergetool                            # запустить графический инструмент (meld, vimdiff, kdiff3)
```

### Отмена

```bash
git merge --abort           # ⭐ вернуть всё как было ДО merge (самая полезная команда)
git rebase --abort          # то же для rebase
git reset --merge           # альтернатива, если merge уже «завис» в странном состоянии
```

Пока конфликт не разрешён и коммит не сделан, `--abort` возвращает репозиторий в исходное
состояние. Не бойся сливать — всегда можно откатиться.

## 5. Особые типы конфликтов

### modify/delete
```text:no-line-numbers
CONFLICT (modify/delete): old-config.yml deleted in feature and modified in HEAD
```
Git не может решить сам. Решение осознанное:
```bash
git rm old-config.yml          # согласен: файл больше не нужен
# ИЛИ
git add old-config.yml         # нет, файл нужен, оставляем изменённую версию
```

### add/add
```text:no-line-numbers
CONFLICT (add/add): Merge conflict in README.md
```
Оба создали файл с одинаковым именем — правится как обычный контентный конфликт.

### rename/rename и rename/modify
Git сам старается отследить переименования (по схожести содержимого), но при сильных правках
может не справиться. Решение — вручную: оставить одно имя и свести содержимое.

### «Конфликт всего файла»
Причины: разные окончания строк (CRLF/LF), автоформаттер, смена отступов.
Профилактика:
```bash
git config --global core.autocrlf input      # Linux/macOS
# в репозитории:
cat > .gitattributes <<'EOF'
* text=auto eol=lf
*.sh text eol=lf
*.png binary
EOF
```

### Бинарные файлы
```text:no-line-numbers
warning: Cannot merge binary files: logo.png (HEAD vs feature)
```
Сливать нечего — выбирается одна из версий (`--ours`/`--theirs`).

## 6. ⭐ Профилактика — самое ценное в теме

1. **Короткие ветки.** Задача на 1-3 дня, а не на две недели.
2. **Ежедневная синхронизация.** В своей ветке каждый день:
   ```bash
   git fetch origin
   git rebase origin/main        # или git merge origin/main
   ```
   Конфликты разбираются маленькими порциями и на свежую голову.
3. **Договорённость о зонах ответственности.** Двое не правят один файл одновременно —
   это вопрос планирования задач, а не git.
4. **Маленькие MR.** MR на 2000 строк = гарантированный конфликт и бесполезное ревью.
5. **Генерируемое — не в git** (или с явной стратегией). Для локов и снапшотов:
   ```text:no-line-numbers
   package-lock.json merge=ours
   ```
6. **Единый формат файлов**: `.editorconfig`, линтеры, `.gitattributes` с `eol=lf`.
7. **`git rerere`** — git запоминает, как ты разрешил конфликт, и повторяет решение
   при следующей встрече с тем же конфликтом:
   ```bash
   git config --global rerere.enabled true
   ```
   Незаменимо при длинных rebase и регулярных слияниях долгих веток.

## 7. Чего делать НЕ надо

- ❌ Не коммить файл с маркерами `<<<<<<<`. Это классика: конфликт «разрешён»,
  а в проде YAML не парсится. Проверка перед коммитом:
  ```bash
  grep -rn '^<<<<<<<\|^>>>>>>>\|^=======$' . --exclude-dir=.git
  ```
  (в CI это ставят отдельной проверкой, а локально — pre-commit хуком, тема 12).
- ❌ Не брать `--theirs`/`--ours` вслепую, «лишь бы собралось».
- ❌ Не удалять `.git` и не клонировать репозиторий заново «чтобы конфликт пропал» —
  ты просто потеряешь свою работу.
- ❌ Не разрешать чужой конфликт молча: если не понимаешь, чья правка важнее — спроси автора.
- ❌ Не делать `git merge --abort` после того, как ты уже час разруливал конфликт вручную
  (всё пропадёт). Если сомневаешься — сначала сохрани состояние в отдельной ветке.

## 💼 Как это в DevOps

- Самые конфликтные файлы у DevOps: `values.yaml`, `docker-compose.yml`, `.gitlab-ci.yml`,
  `inventory`/`group_vars`, `terraform.tfvars`, `Chart.yaml`. Их правят все и постоянно.
- **Конфликт в `terraform.tfstate` не разрешается руками** — state вообще не должен лежать
  в git (используется remote backend с блокировкой). Если он там — это архитектурная проблема.
- В GitLab у MR есть «Merge conflicts» с веб-редактором: мелкие конфликты (версия образа,
  строка в values) удобно чинить прямо в браузере.
- Хорошая практика команды: перед мержем MR обязателен ребейз/апдейт ветки от `main`
  (в GitLab — «Rebase» кнопкой, настройка «Fast-forward merge»).
- Инцидент из жизни: разрешили конфликт «взяв свою сторону» в `values.yaml` — и откатили
  лимиты памяти, которые коллега поднял днём ранее. Под падает по OOM ночью. Мораль: конфликт
  разрешается **осмысленно**, с пониманием обеих правок.

## 📌 Шпаргалка

| Хочу | Как |
|------|-----|
| Увидеть конфликтные файлы | `git status` / `git diff --name-only --diff-filter=U` |
| Понять, что было изначально | `git config --global merge.conflictStyle zdiff3` |
| Посмотреть три версии файла | `git show :1:file` (база), `:2:` (ours), `:3:` (theirs) |
| Взять свою версию целиком | `git checkout --ours file && git add file` |
| Взять их версию целиком | `git checkout --theirs file && git add file` |
| Посмотреть коммиты вокруг конфликта | `git log --merge -p file` |
| Пометить файл разрешённым | `git add file` |
| Завершить слияние | `git commit` |
| **Всё отменить** | `git merge --abort` (или `git rebase --abort`) |
| Графический инструмент | `git mergetool` |
| Запомнить решение конфликта | `git config --global rerere.enabled true` |
| Проверить, не остались ли маркеры | `grep -rn '^<<<<<<<' . --exclude-dir=.git` |

## 🧠 Что запомнить

1. **Конфликт = один участок изменён по-разному в двух ветках.** Git не имеет права выбрать сам.
2. Изменения в **разных местах файла** git сливает автоматически — конфликта не будет.
3. Причины: параллельные правки одних строк, modify/delete, add/add, переименования,
   форматирование/EOL, генерируемые файлы и — чаще всего — **долгоживущие ветки**.
4. Маркеры: `<<<<<<< HEAD` (моя сторона) / `=======` / `>>>>>>> ветка` (их сторона).
5. При **rebase стороны меняются местами** — `HEAD` это `main`, а «их» — твои коммиты.
6. Алгоритм: `git status` → правка файла → убрать маркеры → `git add` → `git commit`.
7. `git merge --abort` возвращает состояние до слияния — конфликт не страшен.
8. `--ours`/`--theirs` — только для файлов, которые берутся целиком, не «лишь бы собралось».
9. **Никогда не коммить маркеры конфликта** — проверяй grep'ом или хуком.
10. Лучшее лечение — профилактика: короткие ветки, ежедневный `rebase origin/main`,
    маленькие MR, `.gitattributes`, `rerere`.
11. Разрешение конфликта — инженерное решение: понять обе правки, а не выбрать «свою».

### Блок A. Теория

**A1.** ⭐ Что такое merge conflict? Дай определение одним предложением.

<details><summary>Ответ</summary>

Ситуация, когда при слиянии git видит, что один и тот же участок файла изменён
по-разному в двух ветках, и не может выбрать правильный вариант автоматически.

</details>

**A2.** ⭐ Назови шесть причин конфликтов. Какая встречается чаще всего на практике?

<details><summary>Ответ</summary>

(1) Одна строка/блок изменены по-разному; (2) modify/delete — один правил файл,
другой удалил; (3) add/add — оба создали файл с одним именем; (4) переименование против
правки; (5) форматирование/окончания строк (CRLF vs LF, автоформаттер); (6) генерируемые
файлы (`package-lock.json`, локи, бандлы). Чаще всего на практике — следствие долгоживущей
ветки, которая давно не синхронизировалась с `main`.

</details>

**A3.** Почему изменения в разных частях одного файла сливаются автоматически?

<details><summary>Ответ</summary>

Git сливает по «ханкам» (блокам строк с контекстом), опираясь на общего предка:
если изменённые блоки не пересекаются, оба изменения применяются к базовой версии
автоматически.

</details>

**A4.** Что означают маркеры `<<<<<<<`, `=======`, `>>>>>>>`? Где чья сторона?

<details><summary>Ответ</summary>

`<<<<<<< HEAD` — начало версии текущей ветки (ours), `=======` — разделитель,
`>>>>>>> <ветка>` — конец версии вливаемой ветки (theirs).

</details>

**A5.** ⭐ Почему при `rebase` «ours» и «theirs» означают не то, что при `merge`?

<details><summary>Ответ</summary>

При rebase git по очереди применяет **твои** коммиты поверх целевой ветки. Текущим
состоянием (HEAD/ours) в этот момент является ветка, на которую перебазируешься (обычно
`main`), а «theirs» — твой переносимый коммит. Поэтому значения сторон противоположны
интуиции из merge.

</details>

**A6.** Что показывает `merge.conflictStyle zdiff3` дополнительно и зачем это нужно?

<details><summary>Ответ</summary>

Показывает третью секцию `||||||| merge base` — исходный вариант до обеих правок.
Видно, кто что изменил относительно базы, и решение принимается осознанно, а не «на глаз».

</details>

**A7.** Что такое конфликт типа modify/delete? Как его решают?

<details><summary>Ответ</summary>

Файл изменён в одной ветке и удалён в другой. Git спрашивает у человека: либо
`git rm <файл>` (согласиться с удалением), либо `git add <файл>` (оставить изменённую версию).

</details>

**A8.** Как git понимает, что файл переименован, и почему иногда не понимает?

<details><summary>Ответ</summary>

По схожести содержимого (rename detection): если удалённый и добавленный файлы похожи
выше порога (по умолчанию ~50%), git считает это переименованием. При сильной правке
одновременно с переименованием схожесть падает, и git видит «удаление + добавление».

</details>

**A9.** Что происходит, если конфликтует бинарный файл?

<details><summary>Ответ</summary>

Слить содержимое нельзя — git сообщает `Cannot merge binary files` и требует выбрать
одну из версий (`--ours`/`--theirs`) целиком.

</details>

**A10.** Какие шаги нужно выполнить, чтобы завершить слияние после разрешения конфликта?

<details><summary>Ответ</summary>

Разрешить конфликты в файлах, убрать маркеры, `git add` каждый файл (это и есть
пометка «разрешено»), проверить `git status`, затем `git commit` (для merge сообщение
предлагается автоматически; при rebase — `git rebase --continue`).

</details>

**A11.** Что делает `git merge --abort` и до какого момента его можно применять?

<details><summary>Ответ</summary>

Прерывает слияние и возвращает репозиторий в состояние до `git merge`. Применим,
пока merge не завершён коммитом. После коммита откат — уже `git revert`/`git reset` (тема 07).

</details>

**A12.** Что такое `git rerere` и когда оно окупается?

<details><summary>Ответ</summary>

«Reuse recorded resolution»: git запоминает пары «конфликт → твоё решение»
и автоматически применяет его при повторной встрече. Окупается при долгих rebase,
регулярных слияниях длинных веток и повторяющихся конфликтах в одних и тех же файлах.

</details>

**A13.** Почему `terraform.tfstate` в git — это архитектурная проблема, а не проблема конфликтов?

<details><summary>Ответ</summary>

State содержит секреты и должен быть в remote backend с блокировкой (S3+DynamoDB,
GitLab-managed state, Terraform Cloud). Если он в git — конфликт JSON-состояния в принципе
неразрешим корректно, а параллельная работа ломает инфраструктуру. Проблема не в конфликте,
а в том, что state попал в git.

</details>

**A14.** Три меры профилактики конфликтов, которые зависят от процесса, а не от git.

<details><summary>Ответ</summary>

Короткие ветки и маленькие MR; ежедневная синхронизация ветки с `main`;
разделение зон ответственности при планировании (двое не правят один файл одновременно).
Плюс: единый формат (`.editorconfig`, `.gitattributes`), генерируемое — вне git.

</details>

**A15.** Как проверить, что в коммит не попали маркеры конфликта?

<details><summary>Ответ</summary>

`grep -rn '^<<<<<<<\|^>>>>>>>\|^=======$' . --exclude-dir=.git`, pre-commit хук
с той же проверкой, отдельная джоба в CI, линтеры YAML/JSON (сломанный синтаксис тоже поймают).

</details>

**A16.** Что показывают `git show :1:file`, `:2:file`, `:3:file`?

<details><summary>Ответ</summary>

Версии файла в индексе во время конфликта: `:1:` — общий предок (base),
`:2:` — версия текущей ветки (ours), `:3:` — версия сливаемой ветки (theirs).

</details>

### Блок B. «Что делает команда»

Слева — команда, справа (сразу под ней) — что она делает.

```bash
B1.  git status
B2.  git diff --name-only --diff-filter=U
B3.  git checkout --ours values.yaml
B4.  git checkout --theirs package-lock.json
B5.  git restore --source=MERGE_HEAD --worktree config.yml
B6.  git add config.yml
B7.  git commit
B8.  git merge --abort
B9.  git rebase --abort
B10. git log --merge -p config.yml
B11. git show :1:config.yml
B12. git mergetool
B13. git config --global rerere.enabled true
B14. git config --global merge.conflictStyle zdiff3
B15. grep -rn '^<<<<<<<' . --exclude-dir=.git
B16. git merge -X ours feature
```

<details><summary>Ответ</summary>

```text:no-line-numbers
B1.  Показать конфликтные файлы и подсказки (fix conflicts / merge --abort)
B2.  Список только неразрешённых (Unmerged) файлов — удобно для скриптов
B3.  Взять для values.yaml версию текущей ветки целиком
B4.  Взять для package-lock.json версию вливаемой ветки целиком
B5.  Современный аналог --theirs: восстановить файл из MERGE_HEAD в рабочий каталог
B6.  Пометить конфликт в config.yml разрешённым
B7.  Завершить слияние коммитом (сообщение git предложит сам)
B8.  Прервать слияние, вернуть состояние до merge
B9.  Прервать rebase, вернуть ветку в исходное состояние
B10. Показать коммиты обеих сторон, затронувшие config.yml, с диффами
B11. Показать версию config.yml из общего предка
B12. Запустить настроенный графический инструмент разрешения конфликтов
B13. Включить запоминание решений конфликтов (rerere)
B14. Показывать в конфликте и исходную версию (три секции вместо двух)
B15. Найти забытые маркеры конфликта в рабочем каталоге
B16. Слить ветку, при конфликтах автоматически предпочитая свою сторону (⚠️ опасно вслепую)
```

</details>

### Блок C. Практика

#### C1. 🔑 Создай свой первый конфликт
```bash
mkdir -p ~/git-lab/t05 && cd ~/git-lab/t05 && git init
cat > config.yml <<'EOF'
server:
  host: 0.0.0.0
  timeout: 30
  port: 8080
EOF
git add . && git commit -m "init config"

git switch -c feature/timeout
sed -i 's/timeout: 30/timeout: 90/' config.yml
git commit -am "feature: timeout 90"

git switch main
sed -i 's/timeout: 30/timeout: 60/' config.yml
git commit -am "main: timeout 60"

git merge feature/timeout          # ⭐ КОНФЛИКТ
git status
cat config.yml
```
Опиши: какие строки добавил git, где твоя сторона, где чужая.

<details><summary>Ответ</summary>

Git добавил три маркера: под `<<<<<<< HEAD` — `timeout: 60` (версия main, где ты
стоишь), под `=======` и до `>>>>>>> feature/timeout` — `timeout: 90`. Остальные строки
файла слились автоматически.

</details>

#### C2. Разрешаем руками
Продолжая C1:
```bash
vim config.yml         # оставь timeout: 90, УБЕРИ все маркеры
git status             # что советует git?
git add config.yml
git status
git commit             # посмотри предложенное сообщение
git lg
git show HEAD --stat
```

#### C3. `--abort` — кнопка «отмена»
```bash
git switch -c feature/port
sed -i 's/port: 8080/port: 9090/' config.yml
git commit -am "feature: port 9090"
git switch main
sed -i 's/port: 8080/port: 7070/' config.yml
git commit -am "main: port 7070"

git merge feature/port      # конфликт
git status
git merge --abort           # ⭐
git status                  # чисто?
cat config.yml              # какое значение порта осталось?
git lg
```

<details><summary>Ответ</summary>

После `--abort` рабочий каталог чист, `config.yml` содержит `port: 7070` (версия main),
история без merge-коммита — как будто слияния не было.

</details>

#### C4. Автоматическое слияние без конфликта
```bash
git switch -c feature/host
sed -i 's/host: 0.0.0.0/host: 127.0.0.1/' config.yml    # первая строка блока
git commit -am "feature: host"
git switch main
printf "  workers: 4\n" >> config.yml                    # конец файла
git commit -am "main: workers"
git merge feature/host       # ⭐ конфликта НЕТ. Почему?
cat config.yml
```
Сформулируй правило: когда git справляется сам.

<details><summary>Ответ</summary>

Конфликта нет, потому что изменения в разных участках файла: git применил оба ханка
к базовой версии. Правило: **конфликт возникает только при пересечении изменённых участков**
(или при конфликте типов операций: удаление/переименование).

</details>

#### C5. modify/delete
```bash
git switch -c feature/cleanup
git rm config.yml && git commit -m "feature: remove config"
git switch main
echo "  debug: true" >> config.yml && git commit -am "main: debug flag"
git merge feature/cleanup
git status                    # ⭐ прочитай формулировку конфликта
# реши сам: файл нужен или нет
git add config.yml            # оставить
# ИЛИ: git rm config.yml      # удалить
git commit
```

<details><summary>Ответ</summary>

Git печатает `CONFLICT (modify/delete)` и оставляет файл на диске: решение принимает
человек. `git add` = «оставляем файл», `git rm` = «соглашаемся с удалением».

</details>

#### C6. add/add
```bash
git switch main && git switch -c feature/readme
echo "# README из feature" > README.md && git add . && git commit -m "feature readme"
git switch main
echo "# README из main" > README.md && git add . && git commit -m "main readme"
git merge feature/readme
cat README.md
# разреши, объединив оба текста
```

#### C7. zdiff3 — видеть исходное состояние
```bash
git config merge.conflictStyle zdiff3
# повтори сценарий C1 на новом файле и сравни вид конфликта
```
Чем `||||||| merge base` помогает принять решение?

<details><summary>Ответ</summary>

Секция `||||||| merge base` показывает, что было до правок: видно, что одна сторона
изменила значение с 30 на 60, а другая — с 30 на 90. Без базы легко ошибиться, приняв чужое
старое значение за новое.

</details>

#### C8. Выбор стороны целиком
```bash
git switch -c feature/lock
echo '{"lock": "feature"}' > package-lock.json && git add . && git commit -m "lock feature"
git switch main
echo '{"lock": "main"}' > package-lock.json && git add . && git commit -m "lock main"
git merge feature/lock
git checkout --theirs package-lock.json
git add package-lock.json && git commit
cat package-lock.json
```
Когда так делать можно, а когда категорически нельзя?

<details><summary>Ответ</summary>

Можно для файлов, которые целиком принадлежат одной стороне или перегенерируются
(локи, собранные артефакты, бинарники). Нельзя для конфигов и кода, где обе стороны внесли
осмысленные правки, — там нужно объединять вручную.

</details>

#### C9. Три версии файла
Во время любого конфликта выполни:
```bash
git show :1:config.yml     # общий предок
git show :2:config.yml     # ours (HEAD)
git show :3:config.yml     # theirs
git log --merge --oneline -- config.yml
```

#### C10. ⭐ Конфликт при rebase — стороны наоборот
```bash
git switch main && git switch -c feature/rebase-demo
sed -i '1s/.*/# ВЕРСИЯ ИЗ FEATURE/' config.yml 2>/dev/null || echo "# ВЕРСИЯ ИЗ FEATURE" > config.yml
git commit -am "feature: header"
git switch main
echo "# ВЕРСИЯ ИЗ MAIN" > config.yml
git commit -am "main: header"
git switch feature/rebase-demo
git rebase main                 # конфликт
cat config.yml                  # ⭐ что под HEAD? твоя правка или из main?
git rebase --abort
```
Запиши вывод в одну фразу — это частый вопрос на собесе.

<details><summary>Ответ</summary>

Под `<<<<<<< HEAD` при rebase будет версия из **main** (то, на что перебазируешься),
а под `>>>>>>>` — твой коммит из feature. Фраза для собеса: «при rebase ours — это целевая
ветка, theirs — мой переносимый коммит; при merge наоборот».

</details>

#### C11. rerere
```bash
git config rerere.enabled true
# создай конфликт, разреши, сделай merge --abort, повтори merge
# git должен САМ подставить твоё решение: "Resolved 'config.yml' using previous resolution."
```

#### C12. Проверка на маркеры
```bash
printf '<<<<<<< HEAD\na\n=======\nb\n>>>>>>> x\n' > broken.yml
git add broken.yml
grep -rn '^<<<<<<<\|^>>>>>>>\|^=======$' . --exclude-dir=.git
git restore --staged broken.yml && rm broken.yml
```
Придумай, как встроить такую проверку в CI (см. тему 12).

### Блок D. Инциденты

**D1.** `git pull` → конфликт в пяти файлах, ты не понимаешь, что происходит.
Порядок действий с нуля.

<details><summary>Ответ</summary>

`git status` (что конфликтует), `git log --oneline HEAD..origin/main` (что прилетело),
затем по одному файлу: понять обе правки (`git log --merge -p <файл>`), отредактировать,
`git add`. В конце `git status` → `git commit`. Если непонятно вообще — `git merge --abort`
и разобраться спокойно (или спросить автора чужих правок).

</details>

**D2.** Разрешил конфликт, закоммитил, пайплайн упал: `yaml: line 12: could not find expected ':'`.
Что вероятнее всего произошло?

<details><summary>Ответ</summary>

В закоммиченном файле остались маркеры конфликта (`<<<<<<<`, `=======`, `>>>>>>>`) —
YAML перестал быть валидным. Лечение: убрать маркеры, коммит; профилактика — grep-проверка,
pre-commit хук, линтер YAML в CI.

</details>

**D3.** Конфликт в `values.yaml`: ты взял `--ours`, а через сутки прод упал по OOM.
Что было сделано не так?

<details><summary>Ответ</summary>

Сторона выбрана механически: правка коллеги (увеличенные лимиты памяти) была
отброшена. Конфликт нужно разрешать осмысленно — понять обе правки и объединить их,
а при сомнении спросить автора.

</details>

**D4.** Ветка живёт три недели, `git merge main` даёт 40 конфликтных файлов.
Стратегия действий?

<details><summary>Ответ</summary>

Не пытаться разрулить всё одним махом: сначала `git fetch`, затем **поэтапно**
(`git merge main` с разбором по файлам, либо rebase по коммитам, где конфликты мельче),
включить `rerere`, при необходимости разбить ветку на несколько маленьких MR. Вывод на будущее:
синхронизироваться ежедневно.

</details>

**D5.** Конфликт «во всём файле», хотя ты менял одну строку. Первая гипотеза и как проверить?

<details><summary>Ответ</summary>

Скорее всего изменились окончания строк (CRLF↔LF) или прогнался автоформаттер —
git видит «все строки изменены». Проверка: `git diff --stat`, `file config.yml`,
`git config core.autocrlf`, `.gitattributes`. Лечение: `* text=auto eol=lf` в `.gitattributes`
и переформатирование отдельным коммитом.

</details>

**D6.** Ты час разруливал конфликт, случайно нажал `git merge --abort`. Можно ли вернуть работу?

<details><summary>Ответ</summary>

Нет: результат ручного разрешения не был закоммичен, а `--abort` восстанавливает
состояние до merge. Профилактика: коммитить промежуточные результаты (можно во временную
ветку) или делать `git stash`/копию файла перед экспериментами.

</details>

**D7.** Коллега пишет: «У меня конфликт, я просто удалил папку и склонировал заново».
Что он потерял и как надо было?

<details><summary>Ответ</summary>

Он потерял свои незапушенные коммиты и правки (если они были только локально).
Правильно: `git status` → разобрать конфликт → `git add` → `git commit`; при панике —
`git merge --abort`, состояние вернётся к исходному.

</details>

**D8.** В MR GitLab показывает «Merge blocked: merge conflicts». Два способа решить.

<details><summary>Ответ</summary>

(1) Локально: `git switch feature && git fetch && git rebase origin/main`
(или `git merge origin/main`), разрешить конфликты, `git push` (после rebase —
`--force-with-lease` в свою ветку). (2) В веб-интерфейсе GitLab: кнопка «Resolve conflicts»
для простых текстовых конфликтов или «Rebase» при включённой настройке.

</details>

**D9.** Конфликт в `terraform.tfstate` на 8000 строк JSON. Твои действия и что менять
в процессе, чтобы это не повторялось.

<details><summary>Ответ</summary>

Сейчас: взять актуальный state из надёжного источника (бэкап/удалённый backend),
не «сливать» JSON вручную, при необходимости — `terraform state pull/push` после проверки.
В процессе: убрать state из git, перейти на remote backend с блокировкой, добавить
`*.tfstate*` в `.gitignore`.

</details>

**D10.** После разрешения конфликта `git status` пишет `All conflicts fixed but you are still
merging`. Что делать?

<details><summary>Ответ</summary>

Конфликты разрешены и добавлены в индекс, но merge не завершён — нужно `git commit`
(при rebase — `git rebase --continue`).

</details>

### Блок E. Вопросы с собеседования

**1.** ⭐⭐ Что такое merge conflict и каковы его причины?

<details><summary>Ответ</summary>

Конфликт возникает, когда один и тот же участок изменён по-разному в двух ветках и git
не может выбрать автоматически. Причины: параллельные правки одних строк, modify/delete,
add/add, переименования, форматирование/EOL, генерируемые файлы; корневая причина —
долгоживущие несинхронизированные ветки.

</details>

**2.** Как разрешить конфликт? Опиши алгоритм.

<details><summary>Ответ</summary>

`git status` → открыть файл → понять обе правки → оставить верный итоговый текст без
маркеров → `git add <файл>` → `git commit` (при rebase — `git rebase --continue`).

</details>

**3.** Что означают маркеры конфликта в файле?

<details><summary>Ответ</summary>

`<<<<<<< HEAD` — версия текущей ветки; `=======` — разделитель; `>>>>>>> branch` —
версия вливаемой ветки; при `zdiff3` ещё `||||||| merge base` — исходная версия.

</details>

**4.** Как отменить слияние, если что-то пошло не так?

<details><summary>Ответ</summary>

`git merge --abort` (или `git rebase --abort`) до завершения слияния; после коммита —
`git revert` для запушенного, `git reset --hard` для локального.

</details>

**5.** Чем `--ours` отличается от `--theirs`? А при rebase?

<details><summary>Ответ</summary>

`--ours` — сторона текущей ветки, `--theirs` — сторона вливаемой. При rebase они
меняются местами: ours — целевая ветка (main), theirs — переносимые коммиты.

</details>

**6.** Может ли git слить изменения в одном файле без конфликта?

<details><summary>Ответ</summary>

Да, если изменения в непересекающихся участках — git объединит их автоматически.

</details>

**7.** Как избежать конфликтов в команде?

<details><summary>Ответ</summary>

Короткие ветки и маленькие MR, ежедневная синхронизация с main, разделение зон
ответственности, единый формат файлов (`.editorconfig`, `.gitattributes`), генерируемые
файлы вне репозитория, `rerere` для повторяющихся конфликтов.

</details>

**8.** Что такое `git rerere`?

<details><summary>Ответ</summary>

Механизм запоминания разрешённых конфликтов: git сохраняет решение и автоматически
применяет его, когда встречает тот же конфликт снова.

</details>

**9.** Что делать, если конфликтует бинарный файл?

<details><summary>Ответ</summary>

Слить нельзя — выбирается одна из версий целиком (`git checkout --ours/--theirs`),
при необходимости файл пересобирается заново.

</details>

**10.** Почему конфликт — это не ошибка git?

<details><summary>Ответ</summary>

Потому что git намеренно не берёт на себя выбор бизнес-логики: он сообщает о пересечении
правок и передаёт решение человеку. Автоматический выбор молча терял бы чью-то работу.

</details>
