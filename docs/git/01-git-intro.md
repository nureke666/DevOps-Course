# 01. Что такое Git: система контроля версий, распределённость, коммит как снимок

> Роадмап → 1. Git → Примечание: «Все конфиги, пайплайны, манифесты, YAML-файлы — это код.
> Этот код должен где-то храниться, версионироваться и меняться. При этом неважно, GitHub,
> GitLab или BitBucket, потому что все они строятся на git.»
> **После темы ты умеешь:** объяснить, что такое система контроля версий, чем git отличается
> от «папки проект_финал_v2_последний», что физически лежит в `.git` и почему коммит —
> это снимок, а не «дифф».

## 🗺️ Карта темы

```text:no-line-numbers
            ТВОЙ КОМПЬЮТЕР                              ХОСТИНГ (GitHub/GitLab/Bitbucket)
 ┌───────────────────────────────────────┐            ┌──────────────────────────────┐
 │ ~/projects/app/                       │            │  origin (полная копия!)      │
 │   ├── src/         ← working tree     │  push ───► │   ├── все коммиты            │
 │   ├── Dockerfile     (файлы, которые  │            │   ├── все ветки              │
 │   ├── .gitlab-ci.yml  ты видишь)      │  ◄─── pull │   └── все теги               │
 │   └── .git/        ← РЕПОЗИТОРИЙ      │            │  + web-интерфейс, MR, CI     │
 │        objects/  ← все версии всего   │            └──────────────────────────────┘
 │        refs/     ← ветки и теги               «git — распределённый»: у тебя не
 │        HEAD      ← где я сейчас                копия истории, а ПОЛНАЯ история.
 └───────────────────────────────────────┘        Можно работать без интернета.

 Граф коммитов — вот что такое git на самом деле:

   c1 ──► c2 ──► c3 ──► c4   (main)
                   \
                    └► c5 ──► c6   (feature/login)   ← ветка = указатель на коммит
                                ▲
                              HEAD                    ← HEAD = «я сейчас здесь»
```

## 1. Зачем нужна система контроля версий

Знакомая картина без git:

```text:no-line-numbers
конфиг.yml
конфиг_рабочий.yml
конфиг_рабочий_2.yml
конфиг_НЕ_ТРОГАТЬ.yml
конфиг_финал.yml
конфиг_финал_испр_Марат.yml
```

Вопросы, на которые эта «система» не отвечает:
- Что именно поменялось между `финал` и `финал_испр`?
- Почему на проде лежит `конфиг_рабочий_2`, а не `финал`?
- Кто добавил `timeout: 300` и зачем?
- Как вернуться к состоянию, которое работало на прошлой неделе?
- Как двум людям править один файл одновременно?

**Система контроля версий (VCS)** отвечает на все пять. Git хранит не «файлы с разными
именами», а **последовательность состояний проекта** с автором, датой и объяснением.

| Что даёт git | Практический смысл для DevOps |
|--------------|-------------------------------|
| История | «Пайплайн сломался вчера» → `git log` за вчера → видно, какой коммит виноват |
| Откат | Плохой деплой → `git revert` → пайплайн выкатывает предыдущее состояние |
| Авторство | `git blame` по строке конфига → кто и в каком коммите её добавил |
| Ветки | Правишь прод-конфиг и эксперимент одновременно, не мешая друг другу |
| Совместная работа | Пять человек в одном репозитории без «скинь мне свой файл в телеграм» |
| **Триггер для автоматики** | Коммит/тег **запускает** пайплайн; репозиторий = источник правды (GitOps) |

> 💡 Последний пункт — главный. В современном DevOps git не просто хранит код, а **является
> входной точкой всех процессов**: коммит → пайплайн → сборка образа → деплой.
> Нет коммита — не происходит ничего.

## 2. Немного истории и типы VCS (спрашивают редко, понимать полезно)

| Поколение | Примеры | Как устроено | Проблема |
|-----------|---------|--------------|----------|
| Локальные | RCS, SCCS | История в файлах рядом | Только один человек, только одна машина |
| **Централизованные (CVCS)** | SVN, CVS, Perforce, TFS | Единственный сервер с историей, у разработчика — рабочая копия | Сервер лёг → нельзя коммитить; сервер потерян → история потеряна |
| **Распределённые (DVCS)** | **Git**, Mercurial, Bazaar | У **каждого** полная копия репозитория | Порог входа выше (нужно понимать модель) |

**Git создал Линус Торвальдс в 2005 году** для разработки ядра Linux, когда команда потеряла
доступ к проприетарному BitKeeper. Требования были ровно те, за которые его любят сейчас:
скорость, распределённость, надёжная защита от порчи данных (хеши), поддержка нелинейной
разработки (тысячи веток).

### Что такое «распределённый» на практике

```bash
git clone https://gitlab.com/team/infra.git   # ты скачал НЕ файлы, а ВЕСЬ репозиторий
cd infra
git log                                       # вся история — работает без интернета
git checkout v1.2.0                           # версия годовой давности — тоже локально
git commit -m "fix"                           # коммит делается ЛОКАЛЬНО
# интернет нужен только для: clone / fetch / pull / push
```

Отсюда три следствия:
1. **Работа без сети.** В самолёте можно коммитить, ветвиться, смотреть историю.
2. **Скорость.** Всё локально: `git log` по проекту в 100 000 коммитов — мгновенно.
3. **Каждый клон — бэкап.** Упал GitLab — история жива у каждого, кто делал `clone`.

> ⚠️ Важная оговорка для собеса: «у всех полная копия» не значит «бэкап не нужен».
> У разработчиков может не быть свежих веток, нет MR, issues, настроек CI, реестра артефактов.
> Хостинг бэкапят отдельно.

## 3. Git ≠ GitHub ≠ GitLab

Самая частая путаница новичка.

| | Что это |
|---|---|
| **Git** | Программа (`/usr/bin/git`), работающая у тебя локально. Бесплатная, открытая, автор — Линус Торвальдс |
| **GitHub** | Хостинг git-репозиториев + PR, issues, Actions (CI). Принадлежит Microsoft |
| **GitLab** | То же самое + сильный встроенный CI/CD; можно поставить к себе на сервер (self-hosted) |
| **Bitbucket** | То же от Atlassian, тесная интеграция с Jira |
| **Gitea / Forgejo** | Лёгкие self-hosted аналоги, часто поднимают «для себя» |

**Ключ к пониманию роадмапа:** «неважно, GitHub, GitLab или BitBucket, потому что все они
строятся на git». Команды `add/commit/push/pull/branch/merge` **одинаковы везде**.
Различаются только веб-интерфейс, название запроса на слияние (PR vs MR) и CI.

```text:no-line-numbers
   git (протокол и команды)  ← ты учишь ЭТО
        ▲          ▲          ▲
     GitHub     GitLab    Bitbucket   ← это просто «обёртки» с веб-мордой и CI
```

## 4. ⭐ Модель Git: коммит — это снимок

Главное отличие git от SVN и главный источник «магии».

**SVN и подобные** хранят файл + список изменений (дельт) к нему:
```text:no-line-numbers
file.txt  v1 ──(+3 строки)──► v2 ──(-1 строка)──► v3
```

**Git хранит снимок (snapshot) всего проекта на момент коммита:**
```text:no-line-numbers
коммит c1: {README.md → blob A, app.py → blob B}
коммит c2: {README.md → blob A, app.py → blob C}   ← README не менялся: ССЫЛКА на тот же blob A
коммит c3: {README.md → blob D, app.py → blob C}
```

Неизменённые файлы не копируются — на них ставится ссылка на тот же объект.
Поэтому репозиторий не раздувается, а `git checkout` любой версии — это просто «разложить
снимок на диск», без пересчёта цепочки диффов.

### Что такое коммит физически

```text:no-line-numbers
commit a1b2c3d
├── tree     f7e8d9…          ← снимок дерева файлов
├── parent   9x8y7z…          ← ПРЕДЫДУЩИЙ коммит (у merge-коммита их два)
├── author   Nurdaulet <kolbai@sofiasoft.kz>  1757800000 +0500
├── committer Nurdaulet <…>   1757800000 +0500
└── message  "add nginx config"
```

Из наличия `parent` вырастает **граф коммитов** — вся модель git:
- линейная история = цепочка родителей;
- ветка = указатель на коммит;
- merge-коммит = коммит с **двумя** родителями;
- «перенести коммиты» (rebase, cherry-pick) = создать **новые** коммиты с другим родителем.

> 🎤 **Формулировка для собеса:** «Коммит в git — это снимок состояния всего проекта плюс
> ссылка на родительский коммит. История — не набор диффов, а направленный граф снимков.
> Диффы git вычисляет на лету, когда я прошу `git diff` или `git show`.»

## 5. Что лежит в `.git` (и почему это важно понимать)

```bash
cd ~/git-lab/sandbox
ls -a                 # видно .git
ls .git
```

```text:no-line-numbers
.git/
├── HEAD              # ссылка «где я сейчас»: ref: refs/heads/main
├── config            # настройки ЭТОГО репозитория (remote, user.email локальный)
├── description       # для gitweb, не нужен
├── index             # СТАГИНГ: что попадёт в следующий коммит (бинарный файл)
├── hooks/            # скрипты на события (pre-commit, pre-push) — тема 12
├── info/exclude      # локальный .gitignore, не попадающий в репозиторий
├── objects/          # ⭐ ВСЕ ДАННЫЕ: коммиты, деревья, файлы
│   ├── a1/b2c3d…     #   объект с хешем a1b2c3d…
│   └── pack/         #   упакованные объекты (после git gc)
├── refs/
│   ├── heads/main    # ← ветка main = ФАЙЛ с хешем коммита (посмотри cat!)
│   ├── remotes/origin/main
│   └── tags/v1.0.0
└── logs/             # reflog — журнал перемещений HEAD (тема 07)
```

### Четыре типа объектов

| Объект | Что хранит |
|--------|-----------|
| **blob** | Содержимое файла (без имени!) |
| **tree** | Каталог: имена + права + ссылки на blob'ы и вложенные tree |
| **commit** | Ссылка на tree + родитель(и) + автор + сообщение |
| **tag** (annotated) | Ссылка на коммит + автор тега + сообщение |

Всё адресуется **хешем содержимого** (исторически SHA-1, в новых версиях есть SHA-256).
Поменял хоть байт — хеш другой. Отсюда: история git **целостна по построению**,
незаметно подменить старый коммит нельзя — изменятся хеши всех последующих.

### Посмотреть своими глазами (очень рекомендую проделать)

```bash
git log --oneline                       # берём хеш последнего коммита
cat .git/HEAD                           # ref: refs/heads/main
cat .git/refs/heads/main                # ← тот самый хеш. Ветка — это строчка в файле!

git cat-file -t a1b2c3d                 # тип объекта: commit
git cat-file -p a1b2c3d                 # содержимое коммита: tree, parent, author, message
git cat-file -p a1b2c3d^{tree}          # список файлов снимка
git cat-file -p <хеш blob'а>            # содержимое файла

git count-objects -vH                   # сколько объектов и сколько занимают
```

> 💡 После этого упражнения фраза «ветка — это просто указатель» перестаёт быть абстракцией:
> ты буквально увидел файл из 41 байта. Создание ветки в git стоит ноль — поэтому в git
> ветвятся на каждый чих, а в SVN боялись.

## 6. Установка и первичная настройка

```bash
sudo apt update && sudo apt install -y git     # Debian/Ubuntu
sudo dnf install -y git                        # RHEL/Fedora
brew install git                               # macOS
git --version
```

### Обязательный минимум

```bash
git config --global user.name  "Nurdaulet"
git config --global user.email "kolbai@sofiasoft.kz"
```

Имя и почта **вшиваются в каждый коммит**. Забыл — git откажется коммитить или подставит
что-то вроде `nurik@ubuntu-vm.(none)`, и коммиты не привяжутся к твоему профилю на GitHub.

### Три уровня конфига (частый вопрос)

```text:no-line-numbers
system   /etc/gitconfig           git config --system   (на всю машину, нужен root)
   ▼ перекрывается
global   ~/.gitconfig             git config --global   (твой пользователь) ← обычно сюда
   ▼ перекрывается
local    .git/config              git config --local    (конкретный репозиторий) ← приоритет
```

```bash
git config --list --show-origin          # всё и откуда взято
git config user.email                    # какое значение действует ЗДЕСЬ
git config --local user.email "work@company.kz"   # рабочая почта только в этом репозитории
```

Реальный кейс: личные проекты — личная почта в `--global`, рабочие репозитории — корпоративная
в `--local` (или через `includeIf` по каталогу).

### Полезные настройки, которые стоит сделать сразу

```bash
git config --global init.defaultBranch main    # main вместо master в новых репозиториях
git config --global core.editor "vim"          # редактор сообщений коммита
git config --global pull.rebase false          # pull = merge (осознанный выбор, тема 06)
git config --global core.autocrlf input        # Linux/macOS (на Windows: true) — тема 12
git config --global color.ui auto
git config --global alias.lg "log --oneline --graph --all --decorate"
git config --global alias.st "status -sb"
git config --global alias.last "log -1 --stat"
```

## 8. Чем git **не** является

- ❌ **Не бэкап-система.** Он хранит то, что ты закоммитил. Не закоммитил — потерял.
  И `rm -rf project/` уносит `.git` вместе с историей (спасает только `push` на хостинг).
- ❌ **Не хранилище больших бинарников.** Видео, дампы БД, образы дисков раздувают репозиторий
  навсегда (объекты остаются в истории). Для больших файлов — Git LFS или артефакт-хранилище
  (S3, Nexus, registry) — тема 12.
- ❌ **Не место для секретов.** Пароль в коммите остаётся в истории, даже если удалить файл
  следующим коммитом. Секреты — в Vault/CI-переменные/SOPS — темы 12 и Ansible-12.
- ❌ **Не система деплоя.** Git хранит описание, а выкатывает пайплайн или ArgoCD.
- ❌ **Не инструмент только для программистов.** Конспекты, документация, конфиги, статьи —
  всё, что текст, живёт в git прекрасно.

## 💼 Как это в DevOps

- **Git — первый инструмент в списке требований** почти любой вакансии DevOps, и единственный,
  который используется каждый рабочий день без исключений.
- Инфраструктура DevOps-инженера **вся лежит в репозиториях**: `infra-terraform`,
  `infra-ansible`, `k8s-manifests`, `helm-charts`, `ci-templates`, `docs`.
- **Ничего не делается «руками на сервере»** — правится файл в репозитории, открывается MR,
  проходит ревью и CI, только потом применяется. Это и есть культура DevOps: изменение
  инфраструктуры проходит тот же путь, что изменение кода.
- В GitOps-подходе (блок CI/CD, тема 04) репозиторий **буквально является** описанием
  состояния кластера: что в git — то и в проде, автоматически.
- Типичный день: `git pull` → ветка → правка манифеста → `git commit` → `git push` → MR →
  ревью коллеги → merge → пайплайн выкатил. Git участвует в каждом шаге.

## 🧠 Что запомнить

1. **VCS** отвечает на вопросы «что изменилось, кто, когда и зачем» и позволяет вернуться назад.
2. Git — **распределённая** VCS: у каждого полная копия истории, работа офлайн, скорость.
3. **Git ≠ GitHub/GitLab/Bitbucket.** Git — программа, остальное — хостинг поверх неё;
   команды везде одинаковые.
4. **Коммит — снимок всего проекта** + ссылка на родителя, а не набор диффов.
5. Из «ссылки на родителя» вырастает **граф коммитов** — модель, объясняющая merge, rebase,
   конфликты и detached HEAD.
6. Всё лежит в `.git`: `objects/` (blob, tree, commit, tag), `refs/` (ветки и теги — просто
   файлы с хешами), `HEAD`, `index`.
7. Всё адресуется **хешем содержимого** → историю нельзя незаметно подменить.
8. **Ветка — это указатель на коммит**, поэтому создать ветку стоит ноль.
9. `user.name` и `user.email` обязательны; конфиг трёхуровневый: system → global → local.
10. Git — не бэкап, не хранилище бинарников и **не место для секретов**.

### Блок A. Теория

**A1.** Своими словами: что такое система контроля версий и какие пять вопросов она закрывает?

<details><summary>Ответ</summary>

VCS хранит историю изменений проекта. Закрывает: что изменилось, кто изменил,
когда изменил, зачем (сообщение коммита), как вернуться к прошлому состоянию.
Плюс шестое — как нескольким людям менять одно и то же без потери работы.

</details>

**A2.** Чем распределённая VCS отличается от централизованной? Назови по два плюса каждой.

<details><summary>Ответ</summary>

Централизованная (SVN): история только на сервере, у разработчика — рабочая копия.
Плюсы: простая модель, жёсткий контроль доступа к отдельным папкам. Минусы: нет сервера —
нет работы, сервер — единственная точка отказа.
Распределённая (git): полная копия у каждого. Плюсы: офлайн-работа, скорость, каждая копия —
резервная. Минусы: выше порог входа, сложнее ограничить доступ к части репозитория.

</details>

**A3.** ⭐ Git — это GitHub? Объясни разницу так, как объяснил бы стажёру.

<details><summary>Ответ</summary>

Git — программа на твоём компьютере, которая ведёт историю проекта. GitHub — сайт,
где эту историю можно хранить, показывать другим и обсуждать изменения. Аналогия: git —
это текстовый редактор с историей, GitHub — облачный диск и форум для него.
Git без GitHub работает полностью; GitHub без git — просто сайт.

</details>

**A4.** Почему роадмап говорит «неважно, GitHub, GitLab или BitBucket»? Что в них одинаково,
а что различается?

<details><summary>Ответ</summary>

Одинаково: сам git и все его команды (`add`, `commit`, `push`, `pull`, ветки, теги,
merge). Различаются: веб-интерфейс, название запроса на слияние (PR в GitHub, MR в GitLab),
встроенный CI (Actions / GitLab CI / Pipelines), права, интеграции. Выучив git, ты умеешь
работать с любым хостингом; разница осваивается за час.

</details>

**A5.** ⭐ Коммит — это снимок или набор изменений? Как git при этом не раздувается,
если файл не менялся десять коммитов подряд?

<details><summary>Ответ</summary>

Снимок (snapshot) всего дерева проекта. Не раздувается, потому что неизменённые файлы
не копируются: в новом дереве стоит ссылка на **тот же blob-объект** (он адресуется хешем
содержимого — одинаковое содержимое = один объект). Плюс git периодически упаковывает объекты
(`git gc`, packfiles) с дельта-сжатием.

</details>

**A6.** Что физически хранит объект типа `commit`? Перечисли поля.

<details><summary>Ответ</summary>

`tree` (снимок дерева файлов), `parent` (один, два у merge-коммита, ноль у первого),
`author` + дата, `committer` + дата, сообщение. Опционально — GPG-подпись.

</details>

**A7.** Что такое `blob`, `tree`, `commit`, `tag` в терминах объектов git?

<details><summary>Ответ</summary>

`blob` — содержимое файла без имени; `tree` — каталог: имена, права, ссылки на blob'ы
и вложенные tree; `commit` — ссылка на tree + родители + автор + сообщение; annotated `tag` —
ссылка на коммит + автор и сообщение тега.

</details>

**A8.** Что такое ветка с точки зрения файловой системы `.git`? Почему создание ветки «бесплатно»?

<details><summary>Ответ</summary>

Файл в `.git/refs/heads/<имя>`, внутри — 40-символьный хеш коммита. Создать ветку =
записать 41 байт, поэтому это мгновенно и бесплатно (в SVN ветка — копия дерева на сервере).

</details>

**A9.** Что такое `HEAD`?

<details><summary>Ответ</summary>

Указатель «где я сейчас». Обычно содержит `ref: refs/heads/main` — ссылку на текущую
ветку. Если содержит прямо хеш коммита — это detached HEAD (тема 04).

</details>

**A10.** Почему в git нельзя незаметно изменить старый коммит?

<details><summary>Ответ</summary>

Хеш коммита считается от его содержимого, включая хеш родителя. Изменение старого
коммита меняет его хеш → меняются хеши всех потомков → история расходится с той, что у коллег,
и git это явно показывает при `push`/`pull`.

</details>

**A11.** Назови три уровня конфигурации git и порядок их приоритета.

<details><summary>Ответ</summary>

`system` (`/etc/gitconfig`) → `global` (`~/.gitconfig`) → `local` (`.git/config`).
Приоритет возрастает: local перебивает global, global перебивает system.

</details>

**A12.** Зачем git знать `user.email`? Что будет, если его не задать?

<details><summary>Ответ</summary>

Имя и почта вшиваются в каждый коммит и используются хостингом для привязки коммита
к профилю. Без них git либо откажется коммитить, либо подставит `user@hostname.(none)`,
и на GitHub/GitLab коммиты будут «ничьи».

</details>

**A13.** Какие операции в git требуют интернета, а какие нет?

<details><summary>Ответ</summary>

Интернет нужен: `clone`, `fetch`, `pull`, `push`, `ls-remote`. Не нужен: `init`, `add`,
`commit`, `log`, `diff`, `branch`, `checkout/switch`, `merge`, `rebase`, `reset`, `tag`, `stash`.

</details>

**A14.** Верно ли утверждение «git — это бэкап»? Обоснуй.

<details><summary>Ответ</summary>

Нет. Git хранит только закоммиченное; незакоммиченное теряется. Локальный репозиторий
живёт на одном диске — `rm -rf` уносит и `.git`. Бэкапом становится только то, что отправлено
(`push`) на сервер, и сам сервер тоже бэкапят отдельно (MR, issues, настройки CI в git не лежат).

</details>

**A15.** Почему в git нельзя класть пароли, даже если потом удалить файл?

<details><summary>Ответ</summary>

Коммит с секретом остаётся в истории и в объектах репозитория навсегда; удаление файла
новым коммитом лишь убирает его из последнего снимка. Любой, у кого есть клон, может достать
секрет из старого коммита. Правильное действие — считать секрет скомпрометированным, отозвать
и перевыпустить, а историю чистить отдельно (`git filter-repo`, тема 12).

</details>

**A16.** Назови три репозитория, которые заведёт себе DevOps-инженер на новой работе,
и что в них будет лежать.

<details><summary>Ответ</summary>

Например: `infra-terraform` (описание облачных ресурсов), `infra-ansible`
(плейбуки и роли настройки серверов), `k8s-manifests`/`helm-charts` (то, что деплоится
в кластер, тянет ArgoCD), `ci-templates` (общие шаблоны пайплайнов), `docs`/`runbooks`
(документация и инструкции по инцидентам), `dotfiles` (личные конфиги).

</details>

### Блок C. Практика

#### C1. 🔑 Настройка «на всю жизнь»
1. Установи git, проверь версию.
2. Задай `user.name`, `user.email`, `init.defaultBranch`, `core.editor` и алиас `lg`.
3. Выполни `git config --list --show-origin` и найди, в каком файле лежит каждая настройка.
4. Открой `~/.gitconfig` в редакторе — убедись, что это обычный текстовый файл, и что
   его можно править руками.

#### C2. Первый репозиторий
```bash
mkdir -p ~/git-lab/t01 && cd ~/git-lab/t01
git init
ls -a
ls .git
git status
```
Ответь: сколько коммитов в репозитории? Что говорит `git status` про ветку и почему
`git log` сейчас падает с ошибкой?

<details><summary>Ответ</summary>

Коммитов ноль. `git status` пишет `On branch main` и `No commits yet` — ветка
существует как «будущая»: файла `.git/refs/heads/main` ещё нет, он появится после первого
коммита. `git log` падает с `fatal: your current branch 'main' does not have any commits yet`,
потому что показывать нечего.

</details>

#### C3. Первый коммит
```bash
echo "# Мои конспекты по DevOps" > README.md
git add README.md
git commit -m "первый коммит: README"
git log
git lg
```

#### C4. 🔬 Смотрим в кишки
Выполни по шагам и запиши, что увидел:
```bash
cat .git/HEAD
cat .git/refs/heads/main
git log --format=%H -1                  # полный хеш последнего коммита
git cat-file -t <хеш>                   # тип
git cat-file -p <хеш>                   # содержимое коммита
git cat-file -p <хеш>^{tree}            # дерево
git cat-file -p <хеш blob'а README.md>  # содержимое файла
```
Вопрос: в объекте `blob` есть имя файла? Где тогда хранится имя?

<details><summary>Ответ</summary>

В blob'е имени файла нет — только содержимое. Имя (и права) хранится в объекте `tree`,
который ссылается на blob. Поэтому два одинаковых по содержимому файла с разными именами —
это один blob и две записи в дереве.

</details>

#### C5. Снимок, а не дифф
```bash
echo "строка 2" >> README.md
echo "file2" > second.txt
git add . && git commit -m "второй коммит"

git cat-file -p HEAD^{tree}      # дерево второго коммита
git cat-file -p HEAD~1^{tree}    # дерево первого коммита
```
Сравни хеши blob'ов README.md в двух деревьях. Одинаковые или разные? Почему?
Теперь создай третий коммит, добавив только `third.txt`, и сравни хеш blob'а README.md
с предыдущим — совпал?

<details><summary>Ответ</summary>

Во втором коммите хеш blob'а README.md **другой** (файл изменился). В третьем коммите,
где README.md не трогали, хеш blob'а **совпадает** с хешем из второго — тот же объект
переиспользован. Это и есть «снимок без дублирования данных».

</details>

#### C6. Родитель коммита
```bash
git cat-file -p HEAD | head -5
```
Найди строку `parent`. Проверь, что её значение = хеш предыдущего коммита (`git log --format=%H`).
У первого коммита в репозитории есть `parent`? Проверь.

<details><summary>Ответ</summary>

`parent` второго коммита равен полному хешу первого. У самого первого коммита строки
`parent` нет вообще — это корень истории (root commit).

</details>

#### C7. Целостность истории
```bash
git count-objects -vH
git fsck                       # проверка целостности
```
Объясни своими словами, почему git может обнаружить порчу данных.

<details><summary>Ответ</summary>

Имя объекта = хеш его содержимого. При чтении git может пересчитать хеш и сравнить
с именем: не совпало — данные испорчены. `git fsck` делает это для всех объектов и заодно
проверяет связность графа.

</details>

#### C8. Локальный конфиг перебивает глобальный
```bash
git config user.email                        # что действует здесь
git config --local user.email "lab@example.com"
git config user.email                        # изменилось?
git config --global user.email               # а глобальный?
cat .git/config
```
Сделай коммит и посмотри `git log --format="%an <%ae>" -1`. Какая почта попала в коммит?

<details><summary>Ответ</summary>

В коммит попадёт локальная почта `lab@example.com`, потому что local перебивает global.
Глобальная настройка не изменилась. В `.git/config` появилась секция `[user]`.

</details>

#### C9. Работа без интернета
Отключи Wi-Fi/сеть и выполни: `git log`, `git status`, `git commit`, `git branch test`,
`git checkout test`. Что из этого сработало? Какие команды бы упали?

<details><summary>Ответ</summary>

Без сети работает всё перечисленное: `log`, `status`, `commit`, `branch`, `checkout`.
Упали бы `clone`, `fetch`, `pull`, `push` — всё, что общается с удалённым репозиторием.

</details>

#### C10. Git не только для кода
Создай в песочнице `notes/` c тремя `.md`-файлами, закоммить их, поменяй один, закоммить снова,
посмотри `git log -p notes/`. Сформулируй, почему для конспектов git удобнее, чем облачный диск.

<details><summary>Ответ</summary>

У облачного диска есть версии файла, но нет: атомарного «одно изменение = несколько
файлов сразу», сообщения «зачем», веток для экспериментов, diff'а по строкам, поиска по истории
и слияния параллельных правок. Плюс из git конспекты автоматически публикуются и рендерятся
как сайт/README.

</details>

### Блок D. Инциденты

**D1.** Коллега говорит: «У нас же есть Яндекс.Диск с версиями файлов, зачем git?»
Приведи три аргумента, понятных не-программисту.

<details><summary>Ответ</summary>

(1) Видно не только «что» изменилось, но и «зачем» — к каждому изменению приложено
объяснение. (2) Можно вернуться к любому прошлому состоянию **всего проекта целиком**,
а не одного файла. (3) Двое могут править одновременно, и изменения объединятся,
а не перезапишут друг друга («последний сохранивший победил» — типичная потеря работы в облаке).

</details>

**D2.** После `git commit` видишь `Author: root <root@srv-01.(none)>`. Что произошло
и как исправить для будущих коммитов?

<details><summary>Ответ</summary>

Не задан `user.name`/`user.email` (и коммит делался из-под root). Исправить:
`git config --global user.name "…"` и `git config --global user.email "…"`. Уже сделанный
коммит можно поправить `git commit --amend --author="Имя <почта>"` (тема 07),
но переписывать уже отправленную историю — отдельное решение.

</details>

**D3.** Ты сделал `rm -rf ~/projects/app` — папку с репозиторием. Что потеряно,
если ты успел сделать `git push`? А если не успел?

<details><summary>Ответ</summary>

Если `push` был — потеряны только незакоммиченные и неотправленные изменения,
остальное восстанавливается `git clone`. Если `push` не делался — потеряно всё: `.git` лежал
внутри удалённой папки.

</details>

**D4.** В репозиторий залили дамп БД на 900 МБ, потом удалили файл следующим коммитом.
Клонирование всё равно тянет ~900 МБ. Почему?

<details><summary>Ответ</summary>

Объекты остаются в истории: файл присутствует в старых коммитах, а `clone` по умолчанию
тянет всю историю. Лечится либо переписыванием истории (`git filter-repo` + force-push
и повторный клон у всех), либо `clone --depth 1` для CI. Правильнее — не класть такое в git
(LFS или внешнее хранилище) — тема 12.

</details>

**D5.** Разработчик хвастается: «Я поправил старый коммит месячной давности, никто не заметит».
Почему заметят все?

<details><summary>Ответ</summary>

Изменение старого коммита меняет его хеш и хеши всех последующих. У коллег история
останется прежней: при `push` git потребует `--force`, а при `pull` они увидят расхождение
(`divergent branches`). В защищённых ветках force-push обычно запрещён вовсе.

</details>

**D6.** `git status` в домашнем каталоге показывает тысячи файлов как untracked.
Что случилось и как это исправить?

<details><summary>Ответ</summary>

Где-то в домашнем каталоге выполнен `git init` (часто случайно, вместо нужной папки),
и git считает репозиторием весь `$HOME`. Проверить `ls -a ~ | grep .git` и, если репозиторий
не нужен, удалить `rm -rf ~/.git` (убедившись, что там нет нужной истории!).

</details>

**D7.** На рабочем ноутбуке коммиты в личный проект уходят с корпоративной почты.
Как настроить так, чтобы личные — с личной, рабочие — с рабочей?

<details><summary>Ответ</summary>

Убрать `user.email` из `--global` и задавать `--local` в каждом репозитории; либо
использовать условное включение:
```ini
# ~/.gitconfig
[includeIf "gitdir:~/work/"]
    path = ~/.gitconfig-work
```
и в `~/.gitconfig-work` — корпоративные имя и почту.

</details>

**D8.** `fatal: not a git repository (or any of the parent directories): .git`.
Что это значит и три способа получить репозиторий в этой папке?

<details><summary>Ответ</summary>

Текущая папка и её родители — не репозиторий. Варианты: `git init` (создать новый),
`git clone <url>` (скачать существующий), перейти в правильную папку (`cd` туда,
где лежит `.git`).

</details>

### Блок E. Вопросы с собеседования

**1.** Что такое git и зачем он нужен?

<details><summary>Ответ</summary>

Распределённая система контроля версий: хранит историю изменений проекта, позволяет
вернуться к любому состоянию, вести параллельные ветки и работать командой.
Для DevOps — ещё и источник правды и триггер для CI/CD.

</details>

**2.** Чем git отличается от SVN?

<details><summary>Ответ</summary>

Git распределённый (полная история у каждого, офлайн-работа, дешёвые ветки),
SVN централизованный (история на сервере, дорогие ветки, нужна связь для коммита).

</details>

**3.** ⭐ Git и GitHub — это одно и то же?

<details><summary>Ответ</summary>

Нет. Git — программа для контроля версий, GitHub — хостинг репозиториев git с веб-интерфейсом,
PR, issues и CI. Аналоги — GitLab, Bitbucket, self-hosted Gitea.

</details>

**4.** Что такое коммит? Что он хранит?

<details><summary>Ответ</summary>

Снимок состояния проекта на момент сохранения плюс метаданные: ссылка на дерево файлов,
ссылка на родительский коммит, автор, дата, сообщение. Идентифицируется хешем.

</details>

**5.** Что такое ветка в git?

<details><summary>Ответ</summary>

Подвижный указатель на коммит (файл в `.git/refs/heads/`). Новый коммит двигает указатель
вперёд. Поэтому ветки в git дёшевы.

</details>

**6.** Что такое HEAD?

<details><summary>Ответ</summary>

Указатель на текущую позицию — обычно ссылка на активную ветку; определяет, что лежит
в рабочем каталоге и от какого коммита будет создан следующий.

</details>

**7.** Почему git считается «распределённым»?

<details><summary>Ответ</summary>

Потому что `clone` копирует весь репозиторий целиком: все коммиты, ветки и теги. История
есть у каждого, и большинство операций не требует сервера.

</details>

**8.** Что лежит в каталоге `.git`?

<details><summary>Ответ</summary>

`objects/` (все данные: blob, tree, commit, tag), `refs/` (ветки, теги, удалённые ветки),
`HEAD`, `index` (staging), `config`, `hooks/`, `logs/` (reflog).

</details>

**9.** Зачем git хеши SHA?

<details><summary>Ответ</summary>

Для адресации по содержимому (одинаковое содержимое — один объект) и для целостности:
любое изменение данных меняет хеш, поэтому историю нельзя незаметно подменить.

</details>

**10.** Можно ли хранить в git секреты? Почему нет и что делать вместо этого?

<details><summary>Ответ</summary>

Нельзя. Секрет остаётся в истории даже после удаления файла, и попадает ко всем, кто
клонировал репозиторий. Вместо этого — переменные CI/CD, Vault, SOPS/`git-crypt`,
Ansible Vault; в репозитории — только `.env.example` и `.gitignore`.

</details>
