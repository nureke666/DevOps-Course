# 09. Стратегии ветвления: GitFlow, GitHub Flow, GitLab Flow, Trunk-Based

> Роадмап → 1. Git → «Что ещё стоит изучить?» → **GitFlow и другие стратегии ветвления**:
> *GitHub Flow, GitLab Flow, Trunk-Based*.
> Сноска роадмапа: *«Стратегия ветвления — это правила, по которым ведётся разработка в Git:
> там определяется, какие ветки всегда будут жить, как называть переменные, а также как
> и когда можно делать слияние веток.»*
> **После темы ты умеешь:** назвать четыре стратегии, объяснить их различия и обосновать
> выбор для конкретной команды.
> Смежная тема: те же стратегии со стороны пайплайнов и окружений (блок CI/CD).

---

## 🗺️ Карта темы

```text:no-line-numbers
 GitFlow (сложный, релизы версиями)        GitHub Flow (простой, непрерывная поставка)
 main ──────●───────────●── (теги)          main ───●───●───●───●───►  (деплой с каждого merge)
 hotfix      \         /                          ↗   ↗   ↗   ↗
 release      ●───●───●                     feature ветки (1-3 дня)
 develop  ─●───●───●───●───●
 feature   ↗ ↗   ↗

 GitLab Flow (main + ветки окружений)       Trunk-Based (почти без веток)
 main ──●──●──●──●──►                        main ──●─●─●─●─●─●─●──►  (несколько раз в день)
          \      \                                  ↑ ↑ ↑
    pre-prod ●    ●                            очень короткие ветки (часы)
                   \                           + feature flags для незаконченного
       production   ●
```

## 1. Зачем вообще стратегия

Сам git не навязывает процесс: он умеет ветки и слияния, а «как правильно» решает команда.
Стратегия ветвления отвечает на вопросы:

| Вопрос | Пример ответа |
|--------|---------------|
| Какие ветки живут всегда? | Только `main` / `main` + `develop` / + `production` |
| Откуда создаётся ветка задачи? | От `main` (или от `develop`) |
| Как называются ветки? | `feature/*`, `fix/*`, `hotfix/*`, `release/*` |
| Как ветка попадает обратно? | Только через MR с ревью и зелёным CI; merge / squash / rebase |
| Когда происходит деплой? | По merge в `main` / по тегу / по merge в ветку окружения |
| Как делается срочный фикс прода? | Ветка от тега/`production`, отдельный процесс |
| Кто может пушить в `main`? | Никто напрямую — только merge из MR |

Без договорённости получается «кто как привык»: в `main` коммитят напрямую, релиз собирают
из непонятного состояния, а откат превращается в расследование.

## 2. GitFlow

Классика 2010 года (Винсент Дриссен). Пять типов веток:

```text:no-line-numbers
main        ─●─────────────●──────────────●────►   только релизы, каждый помечен тегом
              \           ↗ \            ↗
hotfix/1.0.1   \         ●    \          |
                \       /      \         |
release/1.1      \  ●──●───●     ●───●───●
                  \ ↑          ↗
develop      ─●───●─●──●───●───●───●───►          интеграционная ветка
              ↑ ↗    ↑    ↗
feature/a ────┘      feature/b
```

| Ветка | От чего | Куда вливается | Живёт |
|-------|---------|----------------|-------|
| `main` | — | — | всегда |
| `develop` | `main` | — | всегда |
| `feature/*` | `develop` | `develop` | до готовности задачи |
| `release/*` | `develop` | `main` + `develop` | время стабилизации релиза |
| `hotfix/*` | `main` | `main` + `develop` | часы |

```bash
# фича
git switch develop && git pull
git switch -c feature/payments
# ... работа ...
git switch develop && git merge --no-ff feature/payments

# релиз
git switch -c release/1.2.0 develop
# только багфиксы и бамп версии
git switch main && git merge --no-ff release/1.2.0
git tag -a v1.2.0 -m "release 1.2.0"
git switch develop && git merge --no-ff release/1.2.0

# хотфикс
git switch -c hotfix/1.2.1 main
git switch main && git merge --no-ff hotfix/1.2.1 && git tag -a v1.2.1 -m "hotfix"
git switch develop && git merge --no-ff hotfix/1.2.1
```

**Плюсы:** явные релизные версии, место для стабилизации, понятный процесс хотфиксов,
хорошо для коробочного ПО и релизов «раз в месяц».
**Минусы:** много веток и слияний, долгоживущие ветки → конфликты, медленная поставка,
плохо сочетается с CI/CD и микросервисами. Сам автор в 2020 добавил примечание:
*для непрерывной поставки берите что-то проще*.

## 3. GitHub Flow

Одна вечная ветка — `main`, всё остальное короткоживущее.

```text:no-line-numbers
main ──●────●────●────●────►   main ВСЕГДА деплоится
       ↑    ↑    ↑    ↑
   feature/a  fix/b  feature/c      (ветка 1-3 дня → PR → ревью → CI → merge → деплой)
```

Правила:
1. `main` всегда рабочий и всегда готов к деплою.
2. Любая работа — ветка от `main` с осмысленным именем.
3. Пуш + PR как можно раньше (даже черновиком).
4. Ревью + зелёный CI обязательны.
5. Слияние в `main` → автодеплой.

```bash
git switch main && git pull
git switch -c feature/add-healthcheck
git push -u origin feature/add-healthcheck     # PR открывается сразу
# ... доработка по ревью ...
# merge кнопкой → деплой
```

**Плюсы:** просто, быстро, идеально для веб-сервисов и SaaS, минимум конфликтов.
**Минусы:** нет места для стабилизации, нужен сильный CI и автотесты, сложнее поддерживать
несколько версий одновременно.

## 4. GitLab Flow

GitHub Flow + ветки окружений (или релизные ветки) — компромисс.

```text:no-line-numbers
feature/* → main → pre-production → production
             │           │              │
          авто-деплой   stage          прод (merge = релиз)
```

Вариант с окружениями:
```bash
git switch main && git merge feature/x        # main → авто-деплой на dev
git switch pre-production && git merge main   # → stage
git switch production && git merge pre-production   # → прод
```
Изменения текут **только вперёд** (upstream first): сначала в `main`, потом в окружения.
Хотфикс — исключение: фикс делается в `production`, затем обязательно переносится назад
в `main` (cherry-pick).

Вариант с релизными ветками (для версионируемого ПО):
```text:no-line-numbers
main → release/1.4 → тег v1.4.0, v1.4.1 …
```
Фиксы всегда сначала в `main`, потом cherry-pick в `release/*` (тема 06).

**Плюсы:** видно, что где выкачено; подходит, когда деплой на прод — не автоматический.
**Минусы:** больше веток, чем в GitHub Flow; требует дисциплины «upstream first».

## 5. Trunk-Based Development

Все коммитят в `main` (trunk) несколько раз в день; ветки живут часы.

```text:no-line-numbers
main ─●─●─●─●─●─●─●─●─●──►     незаконченное скрыто за feature flags
       ↑  ↑     ↑
    короткие ветки на несколько часов (или прямой коммит с обязательным ревью)
```

Требования: мощный набор тестов, быстрый CI (минуты), feature flags, культура маленьких
изменений. Релиз — тег с `main` или короткая `release/*`.

**Плюсы:** минимум конфликтов, максимальная скорость поставки, простой граф.
**Минусы:** невозможен без автотестов и флагов; любая ошибка сразу в общей ветке.
Именно так работают крупные инженерные организации (Google, Facebook) и большинство
зрелых DevOps-команд.

## 6. Сравнение и выбор

| | GitFlow | GitHub Flow | GitLab Flow | Trunk-Based |
|---|---------|-------------|-------------|-------------|
| Вечные ветки | `main`, `develop` | `main` | `main` + окружения | `main` |
| Длительность ветки | дни-недели | 1-3 дня | 1-3 дня | часы |
| Релизы | версии, `release/*` | непрерывно | по окружениям/веткам | непрерывно + теги |
| Сложность | высокая | низкая | средняя | низкая (но высокая инженерная планка) |
| Нужны автотесты | желательно | обязательно | обязательно | критично |
| Кому подходит | коробочное ПО, несколько поддерживаемых версий | веб-сервисы, SaaS | команды с ручным деплоем на прод, регулируемые среды | зрелые команды с сильным CI |

**Как выбирать (практическая логика):**
```text:no-line-numbers
Деплой на прод автоматический и часто?           → GitHub Flow / Trunk-Based
Нужно поддерживать несколько версий у клиентов?  → GitFlow или release-ветки GitLab Flow
Есть stage/preprod с ручным «выкатить»?          → GitLab Flow с ветками окружений
Команда 1-3 человека, сервис один?               → GitHub Flow, не усложняй
```

Для **инфраструктурных репозиториев** (ansible, манифесты, terraform) почти всегда
достаточно GitHub Flow: `main` = то, что применено, ветка → MR → ревью → применение.
В GitOps-репозитории добавляют ветки/каталоги окружений (`dev/`, `stage/`, `prod/`) —
это GitLab Flow по сути.

## 7. Что стратегия требует от репозитория

Договорённость работает, только если подкреплена настройками хостинга и CI:

```text:no-line-numbers
✅ Защита main: запрет прямого push и force-push
✅ MR обязателен, минимум 1 approve, зелёный пайплайн
✅ Соглашение об именах веток (проверяется хуком/CI)
✅ Правила слияния: merge --no-ff / squash / fast-forward — одно на команду
✅ Автоудаление ветки после merge
✅ Protected tags: релизный тег ставит не каждый
✅ CODEOWNERS на критичные файлы (тема 11)
```

```yaml
# пример правил в .gitlab-ci.yml под GitLab Flow
deploy-stage:
  rules:
    - if: $CI_COMMIT_BRANCH == "main"
deploy-prod:
  rules:
    - if: $CI_COMMIT_BRANCH == "production"
      when: manual
```

## 💼 Как это в DevOps

- Вопрос «какая у вас стратегия ветвления?» — стандартный на собеседовании **и** первый
  вопрос при выходе на новую работу: он определяет твой ежедневный процесс.
- DevOps-инженер обычно **владелец** этой договорённости: настраивает protected branches,
  правила MR, правила запуска пайплайнов по веткам и тегам.
- Самая частая ошибка молодых команд — «мы делаем GitFlow», а фактически коммитят в `develop`
  напрямую и не понимают, зачем `release/*`. Лучше честный GitHub Flow, чем карго-культ.
- Инфраструктурные репозитории почти всегда живут по простой схеме: короткая ветка → MR →
  merge в `main` → применение. Долгие ветки в инфраструктуре особенно болезненны:
  расхождение между репозиторием и реальным состоянием систем.
- В GitOps-репозитории стратегия = процесс изменения прода. Merge в ветку окружения —
  это и есть «выкатить».

## 📌 Шпаргалка

| Стратегия | Одна фраза |
|-----------|-----------|
| **GitFlow** | `main` + `develop` + `feature/release/hotfix`; релизы версиями, много слияний |
| **GitHub Flow** | Только `main`; короткие ветки → PR → merge → деплой |
| **GitLab Flow** | GitHub Flow + ветки окружений/релизов; изменения текут «вперёд» |
| **Trunk-Based** | Все в `main` несколько раз в день; feature flags вместо долгих веток |

| Хочу | Как |
|------|-----|
| Начать задачу (GitHub Flow) | `git switch main && git pull && git switch -c feature/x` |
| Подтянуть свежий main | `git fetch && git rebase origin/main` |
| Влить задачу в main | MR → ревью → merge (кнопкой, `--no-ff`/squash по правилам) |
| Хотфикс прода | `git switch -c hotfix/1.4.3 v1.4.2` → фикс → тег → cherry-pick в main |
| Посмотреть, что не влито | `git branch --no-merged main` |

## 🧠 Что запомнить

1. **Стратегия ветвления — договорённость команды**, а не функция git: какие ветки живут,
   как называются, как и когда сливаются.
2. **GitFlow**: `main` + `develop` + `feature/release/hotfix`. Для версионируемых релизов;
   тяжёл для непрерывной поставки.
3. **GitHub Flow**: одна вечная ветка `main`, короткие ветки, PR, merge = деплой.
   Дефолт для веб-сервисов и инфраструктурных репозиториев.
4. **GitLab Flow**: main + ветки окружений (или релизные), правило «upstream first».
5. **Trunk-Based**: все в `main`, ветки на часы, незаконченное — за feature flags;
   требует сильного CI.
6. Чем **длиннее живёт ветка**, тем больнее слияние — это общий закон для всех стратегий.
7. Стратегия без **защиты веток, обязательного MR и CI** не работает — остаётся «на словах».
8. Хотфикс всегда делается от того, что на проде (тег/`production`), и обязательно
   возвращается в `main`.
9. Для маленькой команды и одного сервиса GitFlow — почти всегда лишняя сложность.
10. На собесе важно не «назвать все четыре», а **обосновать выбор** для описанной ситуации.

### Блок A. Теория

**A1.** ⭐ Что такое стратегия ветвления? Какие вопросы она закрывает (назови пять)?

<details><summary>Ответ</summary>

Свод правил работы в git для команды. Закрывает: какие ветки существуют постоянно;
откуда и как создаются рабочие ветки; правила именования; как и когда ветка вливается
обратно (merge/squash/rebase, ревью, CI); когда и откуда происходит деплой; как делается
хотфикс; кто имеет право писать в основные ветки.

</details>

**A2.** Перечисли ветки GitFlow и укажи для каждой: откуда создаётся, куда вливается,
сколько живёт.

<details><summary>Ответ</summary>

`main` — вечная, только релизы, теги; `develop` — вечная, интеграция, создаётся
от `main`; `feature/*` — от `develop` в `develop`, живёт до готовности задачи;
`release/*` — от `develop` в `main` и обратно в `develop`, живёт время стабилизации;
`hotfix/*` — от `main` в `main` и `develop`, живёт часы.

</details>

**A3.** Зачем в GitFlow нужна ветка `release/*`, если есть `develop` и `main`?

<details><summary>Ответ</summary>

Чтобы «заморозить» состав релиза: в `release/*` попадают только багфиксы и бамп
версии, а `develop` продолжает принимать новые фичи для следующего релиза. Это место
стабилизации и QA.

</details>

**A4.** ⭐ Опиши GitHub Flow в пяти правилах.

<details><summary>Ответ</summary>

(1) `main` всегда деплоится; (2) любая работа — ветка от `main` с понятным именем;
(3) пуш и PR рано, обсуждение по ходу; (4) обязательны ревью и зелёный CI;
(5) merge в `main` = деплой (и ветка удаляется).

</details>

**A5.** Чем GitLab Flow отличается от GitHub Flow? Что означает принцип «upstream first»?

<details><summary>Ответ</summary>

GitLab Flow добавляет ветки окружений (`pre-production`, `production`) или релизные
ветки. «Upstream first» — изменение сначала попадает в `main`, а затем продвигается
в окружения; обратный порядок допустим только для хотфикса, который потом обязательно
возвращают в `main`.

</details>

**A6.** ⭐ Что такое Trunk-Based Development и без чего он не работает?

<details><summary>Ответ</summary>

Все работают в одной ветке (`main`/trunk), интегрируя изменения несколько раз в день;
ветки живут часы. Не работает без: быстрого и надёжного CI, хорошего покрытия тестами,
feature flags, маленьких изменений и культуры ревью.

</details>

**A7.** Почему автор GitFlow позже рекомендовал его не использовать для веб-сервисов?

<details><summary>Ответ</summary>

Потому что GitFlow создавался под ПО с явными версиями и релизными циклами.
Для веб-сервиса с непрерывной поставкой он избыточен: лишние ветки, долгие слияния,
задержка поставки. Автор рекомендовал GitHub Flow-подобные схемы.

</details>

**A8.** Сравни четыре стратегии по: вечным веткам, длительности веток, модели релиза,
требованиям к тестам.

<details><summary>Ответ</summary>

См. таблицу сравнения выше: вечные ветки (2 / 1 / 1+окружения / 1),
длительность веток (недели / дни / дни / часы), релиз (версии / непрерывно / по окружениям /
непрерывно+теги), тесты (желательно / обязательно / обязательно / критично).

</details>

**A9.** Какую стратегию выберешь для: (а) SaaS с деплоем 5 раз в день; (б) коробочного ПО
с поддержкой трёх версий; (в) инфраструктурного репозитория с манифестами k8s;
(г) команды из двух человек с одним сервисом?

<details><summary>Ответ</summary>

(а) GitHub Flow или Trunk-Based; (б) GitFlow или релизные ветки GitLab Flow;
(в) GitHub Flow (или GitLab Flow с каталогами/ветками окружений при GitOps);
(г) GitHub Flow — минимум церемоний.

</details>

**A10.** Как стратегия связана с правилами запуска пайплайнов?

<details><summary>Ответ</summary>

Правила запуска джоб пишутся по именам веток и тегов (`$CI_COMMIT_BRANCH`,
`$CI_COMMIT_TAG`): деплой на stage с `main`, на прод — по тегу или из `production`,
тесты — везде. Смена стратегии = переписывание `rules:` в пайплайне.

</details>

**A11.** Какие настройки хостинга нужны, чтобы стратегия соблюдалась, а не оставалась
«на словах»? Назови шесть.

<details><summary>Ответ</summary>

Protected `main` (запрет push и force-push), обязательный MR с approve,
обязательный зелёный пайплайн, соглашение об именах веток (проверка в CI/хуке),
единая merge-политика (merge/squash/ff), автоудаление веток после merge,
protected tags, CODEOWNERS.

</details>

**A12.** ⭐ Почему долгоживущие ветки вредны в любой стратегии?

<details><summary>Ответ</summary>

Они расходятся с основной веткой: растёт вероятность конфликтов, конфликты
разрешает автор, уже забывший контекст; изменения долго не проверяются интеграционно;
ревью большого объёма формально. Плюс в инфраструктуре — расхождение репозитория
с реальным состоянием систем.

</details>

**A13.** Где в каждой стратегии делают хотфикс прода?

<details><summary>Ответ</summary>

GitFlow — `hotfix/*` от `main`, обратно в `main` и `develop`;
GitHub Flow — обычная короткая ветка от `main` с приоритетом;
GitLab Flow — в ветке `production` (или в релизной), затем обязательно назад в `main`;
Trunk-Based — фикс в `main` и cherry-pick в релизную ветку, если она есть.

</details>

**A14.** Что такое feature flag и как он заменяет долгую ветку?

<details><summary>Ответ</summary>

Механизм включения/выключения функциональности в рантайме (конфиг, переменная,
сервис флагов). Позволяет вливать незаконченный код в `main` выключенным: интеграция
происходит постоянно, а пользователь ничего не видит до включения флага.

</details>

**A15.** Чем отличается merge-политика: merge-коммит vs squash vs fast-forward?
Что выбрать для чистой линейной истории?

<details><summary>Ответ</summary>

Merge-коммит сохраняет все коммиты ветки и факт слияния; squash превращает ветку
в один коммит в `main`; fast-forward требует предварительного rebase и даёт строго линейную
историю без merge-коммитов. Для чистой линейной истории — squash или ff+rebase.

</details>

**A16.** Как понять, что команда «делает GitFlow» только на словах?

<details><summary>Ответ</summary>

Признаки: коммиты напрямую в `develop`/`main`; `release/*` не создаются
или живут месяцами; хотфиксы не возвращаются в `develop`; ветки называются как попало;
нет защиты веток и обязательных MR.

</details>

```text:no-line-numbers
B11. Сделать pull с rebase по умолчанию (линейная история)
B12. Отправить ветку на сервер и связать с удалённой (дальше открывается MR)
```

</details>

### Блок C. Практика

#### C1. 🔑 Проиграй GitFlow целиком
```bash
mkdir -p ~/git-lab/t09 && cd ~/git-lab/t09 && git init
echo "app v0" > app.txt && git add . && git commit -m "init"
git switch -c develop

git switch -c feature/login develop
echo "login" >> app.txt && git commit -am "feat: login"
git switch develop && git merge --no-ff feature/login -m "merge feature/login"

git switch -c feature/pay develop
echo "pay" >> app.txt && git commit -am "feat: payments"
git switch develop && git merge --no-ff feature/pay -m "merge feature/pay"

git switch -c release/1.0.0 develop
echo "1.0.0" > VERSION && git add . && git commit -m "chore: bump 1.0.0"
git switch main && git merge --no-ff release/1.0.0 -m "release 1.0.0"
git tag -a v1.0.0 -m "release 1.0.0"
git switch develop && git merge --no-ff release/1.0.0 -m "back-merge release 1.0.0"

git switch -c hotfix/1.0.1 main
echo "hotfix" >> app.txt && git commit -am "fix: critical"
git switch main && git merge --no-ff hotfix/1.0.1 -m "hotfix 1.0.1" && git tag -a v1.0.1 -m "hotfix"
git switch develop && git merge --no-ff hotfix/1.0.1 -m "back-merge hotfix"

git lg
```
Посчитай: сколько слияний потребовалось на две фичи и один фикс? Сделай вывод.

<details><summary>Ответ</summary>

На две фичи и один фикс — шесть слияний (`feature×2`, `release` в `main`
и обратно в `develop`, `hotfix` в `main` и в `develop`) плюс два тега. Вывод: церемоний
много; для непрерывной поставки это дорого.

</details>

#### C2. Тот же сценарий в GitHub Flow
```bash

  git switch -c feature/$f main

  git switch main && git merge --no-ff feature/$f -m "merge feature/$f"
  git branch -d feature/$f
done

git switch -c fix/critical main
echo "hotfix" >> app.txt && git commit -am "fix: critical"
git switch main && git merge --no-ff fix/critical -m "merge fix/critical"
git tag -a v1.0.1 -m "release"
git lg
```
Сравни граф и количество действий с C1.

<details><summary>Ответ</summary>

Тот же результат достигается тремя слияниями и одним тегом, граф читается линейно.

</details>

#### C5. Долгая ветка vs короткая

синхронизации те же изменения разбираются маленькими порциями и обычно вообще
не конфликтуют.

</details>

### Блок D. Инциденты

**D1.** Команда «делает GitFlow», но `release/*` живёт три недели, и в неё постоянно
добавляют новые фичи. К чему это приведёт?

<details><summary>Ответ</summary>

Релиз никогда не «замерзает»: стабилизация бесконечна, `develop` и `release`
расходятся, обратные слияния конфликтуют, дата релиза плывёт. Лечение — правило
«в release только фиксы», короткий срок стабилизации.

</details>

**D2.** В GitHub Flow кто-то влил в `main` изменение, которое сломало прод. Что должно было
сработать раньше и что чинить в процессе?

<details><summary>Ответ</summary>

Должны были сработать: ревью MR, обязательный зелёный пайплайн с тестами,
стейджинг-проверка. Чинить: `git revert` в `main` через MR, затем анализ — почему тесты
не поймали; добавить проверку, включить обязательный approve и smoke-тест на stage.

</details>

**D3.** В GitLab Flow фикс сделали в `production` и забыли перенести в `main`.
Что произойдёт при следующем релизе?

<details><summary>Ответ</summary>

Фикс есть на проде, но отсутствует в `main`. При следующем продвижении
`main → production` изменение будет затёрто (регрессия «починили и снова сломалось»),
а в конфликте его легко потерять. Лечение — cherry-pick в `main` сразу же.

</details>

**D4.** Trunk-Based, но тестов почти нет. Что будет происходить каждый день?

<details><summary>Ответ</summary>

Каждая ошибка сразу в общей ветке: частые поломки `main`, блокировка всей команды,
откаты, «страшно коммитить». Trunk-Based без тестов превращается в хаос — нужны тесты,
флаги и быстрый CI, иначе стратегию менять.

</details>

**D5.** В репозитории 60 веток, из них 40 не влиты и старше двух месяцев. Твои действия
как владельца процесса?

<details><summary>Ответ</summary>

Собрать список (`git branch -r --no-merged main`, даты последних коммитов),
написать владельцам, дать срок; влить актуальное, остальное удалить (перед удалением —
тег/архивная ветка при необходимости). Ввести автоудаление веток после merge и правило
«ветка живёт не дольше N дней».

</details>

**D6.** Разработчик просит разрешить прямой push в `main`, «чтобы быстро поправить опечатку».
Твой ответ и альтернатива.

<details><summary>Ответ</summary>

Отказать: правило существует именно для «маленьких» изменений, которые чаще всего
и ломают прод. Альтернатива — ветка + MR с быстрым approve; при необходимости —
ускоренный процесс для hotfix (отдельная метка, дежурный ревьюер), но через MR и CI.

</details>

**D7.** Пайплайн деплоя запускается на каждой ветке и забивает раннеры.
Как это связано со стратегией и что поправить?

<details><summary>Ответ</summary>

Пайплайн не привязан к стратегии: деплой-джобы должны запускаться только
для определённых веток/тегов (`rules: if: $CI_COMMIT_BRANCH == "main"`), для остальных —
только линт и тесты. Плюс `interruptible: true` и `workflow:rules`, чтобы не плодить
лишние пайплайны.

</details>

**D8.** Две команды в одном репозитории: одна хочет GitFlow, другая Trunk-Based.
Как решать?

<details><summary>Ответ</summary>

Стратегия должна быть одна на репозиторий: обсудить требования (частота релизов,
поддержка версий, зрелость тестов) и выбрать компромисс — обычно GitLab Flow.
Если требования принципиально разные, это сигнал, что репозиторий стоит разделить.

</details>

**D9.** После перехода на squash-merge перестали работать `git log --follow` по некоторым
файлам и `git bisect` стал грубее. Объясни причину и что с этим делать.

<details><summary>Ответ</summary>

Squash схлопывает коммиты ветки в один: детализация изменений внутри задачи
теряется, `--follow` хуже отслеживает переименования, `bisect` находит «задачу»,
а не конкретный коммит. Это осознанный компромисс: если нужна точность — merge-коммиты
или мелкие отдельные MR.

</details>

### Блок E. Вопросы с собеседования

**1.** ⭐ Какие стратегии ветвления ты знаешь?

<details><summary>Ответ</summary>

GitFlow, GitHub Flow, GitLab Flow, Trunk-Based Development (плюс вариации с релизными
ветками и форк-модель в open source).

</details>

**2.** ⭐ Расскажи про GitFlow: какие ветки, как связаны?

<details><summary>Ответ</summary>

`main` (релизы, теги) и `develop` (интеграция) живут всегда; `feature/*` растут
из `develop`; `release/*` — от `develop` в `main` и обратно; `hotfix/*` — от `main`
в `main` и `develop`.

</details>

**3.** Чем GitHub Flow отличается от GitFlow?

<details><summary>Ответ</summary>

GitHub Flow проще: одна вечная ветка `main`, короткие ветки, PR, merge = деплой,
нет `develop` и `release/*`. Подходит для непрерывной поставки.

</details>

**4.** Что такое GitLab Flow?

<details><summary>Ответ</summary>

GitHub Flow + ветки окружений (`pre-production`, `production`) или релизные ветки,
с правилом «upstream first»: сначала в `main`, потом дальше по окружениям.

</details>

**5.** Что такое Trunk-Based Development и когда он применим?

<details><summary>Ответ</summary>

Все работают в одной ветке с очень короткими ветками и feature flags; применим,
когда есть сильный CI, тесты и культура маленьких изменений.

</details>

**6.** Какую стратегию выберешь для сервиса с деплоем несколько раз в день?

<details><summary>Ответ</summary>

GitHub Flow (или Trunk-Based, если команда зрелая): минимум церемоний, быстрая поставка,
короткие ветки.

</details>

**7.** Как организовать хотфикс прода?

<details><summary>Ответ</summary>

Ветка от того, что на проде (тег/`production`), минимальный фикс, новый PATCH-тег,
выкат; затем обязательный перенос фикса в основную ветку (cherry-pick/merge).

</details>

**8.** Что такое protected branch и зачем он?

<details><summary>Ответ</summary>

Настройка хостинга, запрещающая прямой push и force-push в ветку и требующая MR
с ревью и зелёным CI; защищает основную ветку от случайных и неотрецензированных изменений.

</details>

**9.** Merge, squash или rebase при вливании MR — что выберешь и почему?

<details><summary>Ответ</summary>

Зависит от соглашения: squash — чистая линейная история и один коммит на задачу;
merge `--no-ff` — видна структура задачи и легко откатить целиком; ff после rebase —
максимально линейная история. Главное — одно правило на всю команду.

</details>

**10.** Какая стратегия использовалась на твоём последнем проекте? (учись отвечать
про свой pet-проект — это нормальный ответ для джуна)

<details><summary>Ответ</summary>

Честный ответ джуна: «В своём pet-проекте с конспектами использую GitHub Flow:
`main` защищён, задачи — короткие ветки, merge через MR, релизы помечаю тегами».

</details>
