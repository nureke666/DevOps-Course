# 07. Отмена изменений: restore, reset, revert, stash, reflog

> Роадмап → 1. Git → Теория → «Что ещё стоит изучить»: команда `git revert`.
> **После темы ты умеешь:** отменить что угодно на любой стадии — от правки в файле
> до запушенного коммита — и вернуть то, что «безвозвратно потеряно», через `git reflog`.

---

## 🗺️ Карта темы: «что я хочу отменить?»

```text:no-line-numbers
┌──────────────────────────────────────────────────────────────────────────────┐
│ Изменил файл, НЕ добавлял в индекс                                           │
│   → git restore <файл>                 (⚠️ правки пропадут навсегда)         │
├──────────────────────────────────────────────────────────────────────────────┤
│ Сделал git add, но НЕ коммитил                                               │
│   → git restore --staged <файл>        (правки остаются в рабочем каталоге)  │
├──────────────────────────────────────────────────────────────────────────────┤
│ Закоммитил, НЕ пушил, хочу поправить последний коммит                        │
│   → git commit --amend                                                       │
├──────────────────────────────────────────────────────────────────────────────┤
│ Закоммитил, НЕ пушил, хочу «отмотать» N коммитов                             │
│   → git reset --soft/--mixed/--hard HEAD~N                                   │
├──────────────────────────────────────────────────────────────────────────────┤
│ Уже ЗАПУШИЛ в общую ветку                                                    │
│   → git revert <хеш>                   ⭐ единственный безопасный способ      │
├──────────────────────────────────────────────────────────────────────────────┤
│ Надо срочно переключиться, работу терять нельзя                              │
│   → git stash                                                                │
├──────────────────────────────────────────────────────────────────────────────┤
│ «Я всё потерял»                                                              │
│   → git reflog                         ⭐ машина времени                      │
└──────────────────────────────────────────────────────────────────────────────┘
```

## 1. `git restore` — отменить правки в файлах

```bash
git restore file.txt                 # ⚠️ вернуть файл к состоянию индекса (правки пропадут)
git restore .                        # ⚠️ все файлы
git restore --staged file.txt        # убрать из индекса, правки оставить
git restore --staged --worktree file.txt   # и то и другое: вернуть к HEAD
git restore --source=HEAD~2 file.txt # взять версию файла из коммита двухдавностного
```

Старый синтаксис (встретится везде):
```bash
git checkout -- file.txt             # = git restore file.txt
git reset HEAD file.txt              # = git restore --staged file.txt
```

> ⚠️ `git restore <файл>` — одна из немногих действительно **необратимых** команд:
> незакоммиченные изменения git нигде не хранит. Сомневаешься — сначала `git stash`.

---

## 2. `git commit --amend` — поправить последний коммит

```bash
git commit --amend                     # изменить сообщение (откроется редактор)
git commit --amend -m "новое сообщение"
git add забытый_файл && git commit --amend --no-edit   # ⭐ дописать файл, сообщение оставить
git commit --amend --author="Имя <mail@example.com>"
```

Amend **не правит** коммит — он создаёт **новый** коммит вместо старого (новый хеш).
Поэтому правило то же, что у rebase: amend'ить можно только **незапушенное** (или свою
личную ветку с `--force-with-lease`).

---

## 3. ⭐ `git reset` — отмотать ветку назад

`reset` двигает указатель ветки на другой коммит. Отличаются три режима — тем, что делают
с индексом и рабочим каталогом:

```text:no-line-numbers
                       ветка/HEAD   индекс    рабочий каталог
git reset --soft  X        →X       не трогает   не трогает     ← изменения остаются в индексе
git reset --mixed X        →X          →X        не трогает     ← (по умолчанию) в рабочем каталоге
git reset --hard  X        →X          →X           →X          ← ⚠️ ВСЁ СТИРАЕТСЯ
```

```bash
git reset --soft HEAD~1        # отменить коммит, всё оставить в индексе (пересобрать коммит)
git reset HEAD~1               # = --mixed: отменить коммит и git add, файлы целы
git reset --hard HEAD~1        # ⚠️ отменить коммит и выбросить все изменения
git reset --hard origin/main   # ⚠️ привести ветку ровно к состоянию сервера
git reset --hard               # ⚠️ выбросить всё незакоммиченное
```

Типовые применения:

```bash
# 1. Разбить последний коммит на два
git reset --soft HEAD~1
git add часть1 && git commit -m "часть 1"
git add часть2 && git commit -m "часть 2"

# 2. Коммитил не в ту ветку (ещё не пушил)
git switch -c feature/right-place     # коммиты уже здесь
git switch main
git reset --hard origin/main          # main вернулся на место

# 3. Убрать из коммита секрет (последний коммит, не пушен)
git reset --soft HEAD~1
git rm --cached .env && echo ".env" >> .gitignore
git commit -m "add config without secrets"
```

> ⚠️ `--hard` — самая опасная команда в git. Незакоммиченные изменения после неё
> не восстанавливаются ничем (коммиты — восстанавливаются через reflog).

## 4. ⭐ `git revert` — отменить коммит новым коммитом

```bash
git revert a1b2c3d              # создать коммит, отменяющий изменения a1b2c3d
git revert HEAD                 # отменить последний коммит
git revert HEAD~2..HEAD         # отменить диапазон
git revert -n a1b2c3d           # применить отмену в индекс, без коммита
git revert -m 1 <merge-хеш>     # ⭐ отменить MERGE-коммит (1 = оставить первую линию)
git revert --abort
```

**Ключевое отличие от reset:** revert **ничего не удаляет из истории** — он добавляет
новый коммит с обратными изменениями. Поэтому это **единственный безопасный способ**
отменить то, что уже опубликовано.

```text:no-line-numbers
reset --hard HEAD~1 :   c1 ─ c2 ─ c3 ─ [c4]     ← c4 исчез из ветки (у коллег остался!)

revert c4           :   c1 ─ c2 ─ c3 ─ c4 ─ c4⁻¹  ← история цела, изменение отменено
```

| | `reset` | `revert` |
|---|---------|----------|
| История | Переписывается | Дополняется |
| Безопасно для общих веток | ❌ | ✅ |
| Нужен force-push | Да | Нет |
| Видно, что откатывали | Нет | Да (в истории) |
| Применение | Локальные, незапушенные коммиты | Прод, `main`, всё опубликованное |

### Revert merge-коммита

У merge-коммита два родителя, поэтому git спрашивает, «какую линию считать основной»:
```bash
git log --oneline --graph
git revert -m 1 <хеш merge-коммита>     # 1 = первый родитель = ветка, в которую сливали (main)
```
Подводный камень: после revert'а merge повторное слияние той же ветки не вернёт изменения
(git считает их уже влитыми) — нужно «отменить отмену» (`git revert <хеш revert-коммита>`)
или сделать новую ветку.

## 5. `git stash` — отложить работу

```bash
git stash                        # спрятать изменения (рабочий каталог станет чистым)
git stash push -m "правки nginx" # с описанием
git stash -u                     # ⭐ включая untracked-файлы
git stash list                   # stash@{0}: On main: правки nginx
git stash show -p stash@{0}      # посмотреть содержимое
git stash pop                    # вернуть последний и удалить из списка
git stash apply stash@{1}        # вернуть, но оставить в списке
git stash drop stash@{0}         # удалить
git stash clear                  # ⚠️ удалить все
git stash branch feature/x       # создать ветку из stash (если контекст ушёл далеко)
```

Когда нужен: «срочно посмотри прод» посреди задачи, переключение веток с грязным каталогом,
`git pull` при незакоммиченных правках.

> 💡 Stash — не «второй git». Не держи там работу неделями: `stash list` на 20 записей —
> способ гарантированно что-то потерять. Лучше сделать коммит в черновой ветке.

## 6. ⭐⭐ `git reflog` — спасательный круг

Reflog — журнал **всех перемещений HEAD и веток** в локальном репозитории: коммиты,
переключения, merge, rebase, reset. Хранится ~90 дней (для недостижимых — 30).

```bash
git reflog                    # история HEAD
git reflog show feature       # история конкретной ветки
git reflog --date=iso
```
```text:no-line-numbers
a1b2c3d HEAD@{0}: reset: moving to HEAD~3
f9e8d7c HEAD@{1}: commit: важная работа            ← вот он, «потерянный» коммит
e5d4c3b HEAD@{2}: commit: ещё работа
```

Восстановление:
```bash
git reset --hard f9e8d7c         # вернуть ветку на тот коммит
git branch rescue f9e8d7c        # или сделать ветку от него
git cherry-pick f9e8d7c          # или взять только этот коммит
git reset --hard HEAD@{1}        # вернуться «на шаг назад» по reflog
```

Что чинится через reflog: неудачный `reset --hard`, «потерянный» rebase, удалённая ветка,
коммиты из detached HEAD, сломанный amend.
Что **не** чинится: незакоммиченные изменения (их git никогда не видел) и то, чего не было
в этом репозитории.

Ещё один спасательный инструмент:
```bash
git fsck --lost-found            # недостижимые объекты (dangling commits)
```

## 7. `git clean` — убрать мусор

```bash
git clean -n                 # ⭐ показать, что будет удалено (ВСЕГДА начинай с этого)
git clean -f                 # удалить untracked-файлы
git clean -fd                # + каталоги
git clean -fdx               # ⚠️ + игнорируемые (.env, venv/, node_modules/)
```
`-x` в проекте с локальными конфигами — частый способ потерять `.env`, который не бэкапится.

## 8. Сводная таблица «как отменить»

| Ситуация | Команда |
|----------|---------|
| Правки в файле не нужны | `git restore <файл>` ⚠️ |
| Убрать файл из индекса | `git restore --staged <файл>` |
| Забыл файл в последнем коммите | `git add <файл>` + `git commit --amend --no-edit` |
| Плохое сообщение последнего коммита | `git commit --amend -m "..."` |
| Отменить последний коммит, оставить изменения | `git reset --soft HEAD~1` |
| Отменить коммит и `git add` | `git reset HEAD~1` |
| Отменить коммит и выбросить изменения | `git reset --hard HEAD~1` ⚠️ |
| Откатить **запушенный** коммит | `git revert <хеш>` ⭐ |
| Откатить запушенный merge | `git revert -m 1 <хеш>` |
| Отложить работу | `git stash -u` → `git stash pop` |
| Вернуть ветку к состоянию сервера | `git reset --hard origin/main` ⚠️ |
| Достать один файл из старого коммита | `git restore --source=<хеш> <файл>` |
| «Я всё потерял» | `git reflog` ⭐ |
| Удалить мусорные файлы | `git clean -n`, затем `-fd` |
| Прервать merge/rebase/cherry-pick | `--abort` у соответствующей команды |

## 💼 Как это в DevOps

- **Откат прода = `git revert`.** В GitOps-репозитории «откатить релиз» буквально означает
  сделать revert коммита с новым тегом образа: ArgoCD применит предыдущее состояние.
  `reset --hard` + force-push в такой ветке — авария, а не откат.
- В GitLab у MR есть кнопка **Revert** — она создаёт ветку с revert-коммитом и новый MR.
  Это штатная процедура отката, проходящая ревью и CI, как обычное изменение.
- `git reflog` — то, что отличает спокойного инженера от паникующего. Первая реакция
  на «я всё сломал» — не клонировать заново, а посмотреть reflog.
- `git stash` — рабочая лошадка дежурного: правил роль, прилетел инцидент, `git stash`,
  разобрался, `git stash pop`.
- Опасные команды, которые стоит выучить как «требующие паузы»: `reset --hard`,
  `clean -fdx`, `push --force`, `branch -D`, `stash clear`, `rm -rf .git`.

## 🧠 Что запомнить

1. Выбор команды зависит от **стадии**: правка → индекс → коммит → запушено.
2. `git restore <файл>` **необратим** — незакоммиченное git не хранит.
3. `--amend` создаёт новый коммит взамен старого: только для незапушенного.
4. ⭐ **`reset --soft` / `--mixed` / `--hard`** отличаются тем, что делают с индексом
   и рабочим каталогом; `--hard` уничтожает незакоммиченные изменения.
5. ⭐⭐ **`revert` — единственный безопасный способ отменить опубликованный коммит**:
   он добавляет обратный коммит, не переписывая историю.
6. `git revert -m 1 <merge>` — откат влитой ветки; помни про «повторно не вольётся».
7. `git stash` — отложить работу на время; не хранилище на месяцы.
8. ⭐ **`git reflog` возвращает почти всё**: reset, rebase, удалённые ветки, detached-коммиты.
9. `git clean -n` перед `git clean -fd`; `-x` удаляет и `.env`.
10. Любую начатую операцию (merge/rebase/cherry-pick/revert) можно прервать `--abort`.
11. Правило команды: в общих ветках — только `revert`; `reset`/`amend`/force — в личных.

### Блок A. Теория

**A1.** Нарисуй схему «что чем отменяется» по стадиям: правка → индекс → коммит → запушено.

<details><summary>Ответ</summary>

Правка в файле → `git restore <файл>`; в индексе → `git restore --staged <файл>`;
последний локальный коммит → `git commit --amend` / `git reset --soft|--mixed|--hard HEAD~1`;
запушенный коммит → `git revert <хеш>`. Плюс `git stash` — отложить, `git reflog` — вернуть
потерянное.

</details>

**A2.** Почему `git restore <файл>` необратим, а `git reset --hard HEAD~1` — почти всегда обратим?

<details><summary>Ответ</summary>

Незакоммиченные изменения никогда не попадали в объекты git — их негде взять.
Коммиты после `reset --hard` остаются объектами и перечислены в reflog, поэтому ветку можно
вернуть на прежний коммит.

</details>

**A3.** ⭐ Чем отличаются `reset --soft`, `--mixed`, `--hard`? Заполни таблицу
(ветка / индекс / рабочий каталог).

<details><summary>Ответ</summary>

| режим | ветка/HEAD | индекс | рабочий каталог |
|---|---|---|---|
| `--soft` | двигает | не трогает | не трогает |
| `--mixed` (по умолчанию) | двигает | сбрасывает | не трогает |
| `--hard` | двигает | сбрасывает | ⚠️ перезаписывает |

</details>

**A4.** Что на самом деле делает `git commit --amend`? Почему его нельзя применять
к запушенному коммиту?

<details><summary>Ответ</summary>

Создаёт новый коммит из текущего индекса, заменяя последний (старый остаётся
недостижимым, виден в reflog). Хеш меняется, поэтому в опубликованной ветке это разойдётся
с историей у коллег и потребует force-push.

</details>

**A5.** ⭐⭐ Чем `revert` отличается от `reset`? Почему в общей ветке допустим только revert?

<details><summary>Ответ</summary>

`reset` двигает указатель, убирая коммиты из ветки (переписывает историю);
`revert` добавляет новый коммит с обратными изменениями, ничего не удаляя. В общей ветке
переписывание истории ломает работу всем, кто её забрал, и требует force-push,
который в защищённых ветках запрещён.

</details>

**A6.** Что такое `git revert -m 1 <merge>` и зачем нужен номер родителя?

<details><summary>Ответ</summary>

Указывает, какого родителя merge-коммита считать «основной линией»: `-m 1` — первый
родитель (ветка, в которую сливали, обычно main), `-m 2` — второй (влитая ветка).
Без этого git не знает, относительно чего строить обратный дифф.

</details>

**A7.** Почему после revert'а merge-коммита повторное слияние ветки «не возвращает» изменения?

<details><summary>Ответ</summary>

С точки зрения графа ветка уже влита: её коммиты — предки текущего. Повторный merge
не даст изменений (`Already up to date` или пустое слияние), потому что отмена жила
в отдельном коммите. Нужно «отменить отмену» (`git revert <revert-коммит>`) или влить
переработанную ветку с новыми коммитами.

</details>

**A8.** ⭐ Что такое `git reflog` и что он может вернуть? Чего он вернуть НЕ может?

<details><summary>Ответ</summary>

Журнал перемещений HEAD и веток в локальном репозитории. Возвращает: коммиты после
`reset --hard`, состояние до неудачного rebase/amend, коммиты удалённой ветки, коммиты
из detached HEAD. Не возвращает: незакоммиченные изменения, содержимое `stash drop`/`clear`
(частично можно через `fsck`), и то, чего в этом репозитории не было.

</details>

**A9.** Сколько времени живут записи reflog по умолчанию?

<details><summary>Ответ</summary>

По умолчанию 90 дней для достижимых записей и 30 дней для недостижимых
(`gc.reflogExpire`, `gc.reflogExpireUnreachable`).

</details>

**A10.** Чем `git stash pop` отличается от `git stash apply`?

<details><summary>Ответ</summary>

`pop` применяет изменения и удаляет запись из списка; `apply` применяет, но запись
остаётся (полезно, если хочешь применить в нескольких ветках или подстраховаться).

</details>

**A11.** Почему `git stash` без `-u` может «не спрятать» твои изменения?

<details><summary>Ответ</summary>

По умолчанию `git stash` прячет только отслеживаемые файлы: новые (untracked)
остаются в рабочем каталоге. Нужен `-u` (или `-a` — ещё и игнорируемые).

</details>

**A12.** Что делает `git clean -fdx` и чем это опасно в рабочем проекте?

<details><summary>Ответ</summary>

Удаляет неотслеживаемые файлы (`-f`), каталоги (`-d`) и игнорируемые файлы (`-x`).
Опасно тем, что под `-x` попадают `.env`, `venv/`, локальные конфиги и кэши, которые нигде
не бэкапятся.

</details>

**A13.** Как достать одну версию файла из старого коммита, не откатывая ветку?

<details><summary>Ответ</summary>

`git restore --source=<хеш> <файл>` (положить в рабочий каталог) либо
`git show <хеш>:<путь>` (просто посмотреть/перенаправить в файл).

</details>

**A14.** Назови шесть команд, перед которыми стоит сделать паузу и подумать.

<details><summary>Ответ</summary>

`git reset --hard`, `git clean -fdx`, `git push --force`, `git branch -D`,
`git stash clear/drop`, `rm -rf .git` (а также `git checkout -- .` в старом синтаксисе).

</details>

**A15.** Ты закоммитил секрет и запушил. Опиши правильный порядок действий
(и почему revert недостаточен).

<details><summary>Ответ</summary>

Сначала **отозвать и перевыпустить секрет** — он уже утёк. Затем убрать его
из истории (`git filter-repo`/BFG), force-push по согласованию с командой, всем сделать
свежий клон, добавить файл в `.gitignore` и подключить сканер секретов в CI.
`revert` недостаточен, потому что он лишь добавляет обратный коммит — старый коммит
с паролем остаётся в истории и у всех, кто клонировал.

</details>

**A16.** Как отменить последний коммит, но сохранить изменения, чтобы пересобрать его иначе?

<details><summary>Ответ</summary>

`git reset --soft HEAD~1` — коммит отменён, все изменения остались в индексе,
можно пересобрать (например, разбить на два коммита или убрать лишний файл).

</details>

#### C1. Отмена по стадиям
```bash
mkdir -p ~/git-lab/t07 && cd ~/git-lab/t07 && git init
echo "v1" > f.txt && git add . && git commit -m "c1"

echo "v2" >> f.txt
git status && git restore f.txt && cat f.txt      # стадия 1

echo "v3" >> f.txt && git add f.txt
git status && git restore --staged f.txt && git status   # стадия 2
git restore f.txt && cat f.txt

echo "v4" >> f.txt && git commit -am "c2"
git reset --soft HEAD~1 && git status             # стадия 3 (что в индексе?)
git commit -m "c2 (пересобран)"
```

#### C2. ⭐ Три режима reset
```bash
for i in 1 2 3; do echo "line$i" >> r.txt; git add .; git commit -m "r$i"; done
git log --oneline

git reset --soft HEAD~1 && git status -s && git log --oneline    # индекс? файлы?
git commit -m "r3 снова"

git reset HEAD~1 && git status -s && cat r.txt                   # --mixed
git add . && git commit -m "r3 снова 2"

git reset --hard HEAD~1 && git status -s && cat r.txt            # ⚠️ --hard
git reflog | head -5                                              # где r3?
```
Заполни таблицу по своим наблюдениям.

<details><summary>Ответ</summary>

`--soft`: коммит исчез, изменения в индексе (`git status -s` показывает `A`/`M`
в левой колонке). `--mixed`: изменения в рабочем каталоге, индекс пуст. `--hard`: файл
вернулся к прежнему содержимому, изменения исчезли; коммит r3 виден в `git reflog`.

</details>

#### C3. `--amend`: забытый файл и плохое сообщение
```bash
echo "код" > code.py && git add . && git commit -m "добавил"
echo "конфиг" > cfg.yml
git add cfg.yml && git commit --amend --no-edit
git show --stat HEAD                    # сколько файлов в коммите?
git commit --amend -m "feat: код и конфиг приложения"
git log --oneline -1
git reflog | head -4                    # ⭐ старые версии коммита видны?
```

<details><summary>Ответ</summary>

После amend в коммите два файла. `git reflog` показывает несколько записей `commit
(amend)` — старые версии коммита доступны по хешам.

</details>

#### C4. 🔑 revert против reset
```bash
echo "плохое изменение" > bad.txt && git add . && git commit -m "bad commit"
git log --oneline
git revert HEAD --no-edit
git log --oneline                       # ⭐ сколько коммитов? исчез ли bad commit?
ls                                       # файл bad.txt есть?
git show HEAD --stat
```
Теперь сравни: `git reset --hard HEAD~2` (сделай в отдельной ветке!) — что с историей?

<details><summary>Ответ</summary>

После `revert` в истории **два** коммита: `bad commit` и коммит отмены; `bad.txt`
удалён из рабочего каталога, но история не переписана. `reset --hard HEAD~2` убрал бы оба
коммита из ветки — для запушенной ветки это неприемлемо.

</details>

#### C5. Revert диапазона
```bash
for i in 1 2 3; do echo "x$i" > x$i.txt; git add .; git commit -m "x$i"; done
git revert --no-edit HEAD~1..HEAD
git log --oneline -5
ls
```

#### C6. ⭐ Revert merge-коммита
```bash
git switch -c feature/revert-demo
echo "фича" > feat.txt && git add . && git commit -m "feature work"
git switch main
git merge --no-ff feature/revert-demo -m "merge feature"
git log --oneline --graph -5
MERGE=$(git log --format=%h --grep="merge feature" -1)
git revert -m 1 $MERGE --no-edit
ls                                      # feat.txt пропал?
git merge feature/revert-demo           # ⭐ что скажет git? изменения вернулись?
```
Объясни результат — это классический подвох.

<details><summary>Ответ</summary>

`feat.txt` пропадает после revert'а merge. Повторный `git merge feature/revert-demo`
скажет `Already up to date` — изменения не вернутся, так как ветка формально уже влита.
Правильно: `git revert <хеш revert-коммита>` (отменить отмену) либо создать новую ветку
с нужными изменениями поверх текущего main.

</details>

#### C7. Stash
```bash
echo "черновик" >> f.txt
echo "новый untracked" > new.txt
git stash                               # ⭐ что произошло с new.txt?
```

</details>

Повтори трюк, но восстанови не через `reset`, а через `git branch rescue <хеш>`.

</details>

### Блок D. Инциденты

**D1.** `git reset --hard` выполнен с незакоммиченными правками за два часа работы.
Что можно вернуть, а что нет?

<details><summary>Ответ</summary>

Незакоммиченные правки не вернуть — их не было в объектах git (остаётся надежда
на Local History в IDE). Коммиты, которые «снёс» reset, восстанавливаются через `git reflog`.

</details>

**D2.** Запушен коммит, который ломает прод. Ветка `main` защищена. Твои действия?

<details><summary>Ответ</summary>

`git revert <хеш>` в отдельной ветке → MR → ревью → CI → merge (в GitLab есть кнопка
Revert, которая делает это за тебя). Никакого `reset --hard` + force-push в защищённую ветку.

</details>

**D3.** Ты сделал `git revert` merge-коммита, а через неделю нужно всё-таки влить ту ветку.
Что произойдёт и как правильно поступить?

<details><summary>Ответ</summary>

Повторный merge не вернёт изменения — ветка считается влитой. Варианты:
`git revert` самого revert-коммита, либо перенести работу новыми коммитами (`cherry-pick`
в новую ветку) и влить её.

</details>

**D4.** `git stash pop` завершился конфликтом. Что со stash — он удалён или нет?

<details><summary>Ответ</summary>

При конфликте `pop` **не удаляет** stash: запись остаётся, пока конфликт не разрешён
и изменения не применены. После разрешения — `git stash drop` вручную (проверь `git stash list`).

</details>

**D5.** В `git stash list` 14 записей полугодовой давности. Как разобрать безопасно?

<details><summary>Ответ</summary>

По одной: `git stash show -p stash@{N}` — посмотреть содержимое; нужное превратить
в ветку `git stash branch tmp/stash-N stash@{N}`; ненужное — `git stash drop`. И договориться
с собой не использовать stash как долговременное хранилище.

</details>

**D6.** Коллега сделал `git commit --amend` и force-push в ветку, которую ты уже тянул.
Что ты увидишь и как синхронизироваться?

<details><summary>Ответ</summary>

Твой `git pull` покажет расхождение (истории разошлись). Если своих коммитов нет:
`git fetch && git reset --hard origin/<ветка>`. Если есть — сначала сохрани их
(`git branch backup`), затем reset и `git cherry-pick`/`rebase` своих коммитов поверх.

</details>

**D7.** После `git clean -fdx` пропал `.env` с локальными настройками стенда.
Восстановим ли он? Как не повторить?

<details><summary>Ответ</summary>

Нет: `.env` не отслеживался и был проигнорирован, git его никогда не видел.
Профилактика: всегда `git clean -n`/`-ndx` перед удалением, хранить шаблон `.env.example`
в репозитории, а реальные значения — в менеджере секретов.

</details>

**D8.** Ты запушил коммит с паролем в `main`. Опиши полный порядок действий.

<details><summary>Ответ</summary>

(1) Немедленно отозвать/сменить пароль — он скомпрометирован; (2) сообщить команде
и безопасникам; (3) удалить секрет из истории (`git filter-repo --path .env --invert-paths`
или BFG); (4) согласовать force-push в защищённую ветку (временно снять защиту);
(5) все делают свежий клон; (6) добавить `.gitignore` и сканер секретов (gitleaks/trufflehog)
в pre-commit и в CI.

</details>

**D9.** `git reflog` пуст (или не содержит нужного). Что ещё можно попробовать?

<details><summary>Ответ</summary>

`git fsck --lost-found` (недостижимые коммиты и blob'ы), поискать копию репозитория
у коллег или на сервере (`git clone` с origin), проверить бэкапы IDE/файловой системы,
`git stash list`, и — в самом простом случае — другие клоны на своих машинах.

</details>

**D10.** Ветка ушла «вперёд» на 3 чужих коммита и «назад» на 2 твоих, ты хочешь ровно
состояние сервера. Команда и её риск.

<details><summary>Ответ</summary>

`git fetch && git reset --hard origin/<ветка>`. Риск: два твоих коммита исчезнут
из ветки (останутся в reflog). Безопаснее сначала `git branch backup-$(date +%F)`.

</details>

**D11.** Ты откатил прод через `git revert`, а релиз-инженер спрашивает: «а почему не reset?».
Сформулируй аргумент в двух предложениях.

<details><summary>Ответ</summary>

«`revert` не переписывает историю: он добавляет коммит, отменяющий изменение,
поэтому проходит обычным путём — MR, ревью, CI — и не ломает репозиторий у остальных.
`reset` потребовал бы force-push в защищённую ветку и уничтожил бы историю, которую
уже забрали все».

</details>

### Блок E. Вопросы с собеседования

**1.** ⭐⭐ Чем `git revert` отличается от `git reset`?

<details><summary>Ответ</summary>

`revert` создаёт новый коммит, отменяющий изменения, и сохраняет историю — безопасен
для опубликованных веток; `reset` двигает указатель ветки, убирая коммиты из истории, —
только для локальных, незапушенных изменений.

</details>

**2.** ⭐ Какие бывают режимы reset и чем отличаются?

<details><summary>Ответ</summary>

`--soft` (двигает ветку, индекс и файлы не трогает), `--mixed` (сбрасывает индекс,
файлы целы), `--hard` (сбрасывает и индекс, и рабочий каталог — изменения теряются).

</details>

**3.** Как отменить последний коммит, если он ещё не запушен?

<details><summary>Ответ</summary>

`git reset --soft HEAD~1` (сохранить изменения), `git reset --hard HEAD~1` (выбросить),
либо `git commit --amend`, если нужно просто поправить.

</details>

**4.** Как отменить коммит, который уже в общей ветке?

<details><summary>Ответ</summary>

`git revert <хеш>` — новым коммитом, через обычный MR.

</details>

**5.** Что делает `git commit --amend`?

<details><summary>Ответ</summary>

Заменяет последний коммит новым: позволяет изменить сообщение или дописать файлы;
хеш при этом меняется, поэтому только для незапушенного.

</details>

**6.** Что такое `git stash` и когда его используют?

<details><summary>Ответ</summary>

Временно откладывает незакоммиченные изменения, очищая рабочий каталог: чтобы
переключиться на срочную задачу, сделать pull или сменить ветку.

</details>

**7.** ⭐ Что такое `git reflog` и зачем он нужен?

<details><summary>Ответ</summary>

Журнал перемещений HEAD и веток; позволяет вернуть коммиты после `reset --hard`,
неудачного rebase, amend или удаления ветки.

</details>

**8.** Можно ли восстановить удалённую ветку?

<details><summary>Ответ</summary>

Да: найти её последний коммит в `git reflog` (или `git fsck`) и создать ветку заново
(`git branch <имя> <хеш>`).

</details>

**9.** Как откатить merge-коммит?

<details><summary>Ответ</summary>

`git revert -m 1 <хеш merge-коммита>`, где 1 — номер основного родителя. Учитывать,
что повторное слияние той же ветки изменения не вернёт.

</details>

**10.** Что нельзя восстановить в git ни при каких условиях?

<details><summary>Ответ</summary>

Незакоммиченные изменения, затёртые `reset --hard`/`restore`/`clean`, и вообще всё,
что никогда не попадало в объекты репозитория.

</details>
