# 11. Командная работа: Pull/Merge Request, ревью, соглашения

> Роадмап → 1. Git → Практика: «Создать репозиторий, пушить конспекты, регулярно коммитить».
> Эта тема — про то, как git выглядит **в команде**: то, чем ты будешь заниматься каждый день
> на работе.
> **После темы ты умеешь:** открыть нормальный MR, пройти ревью, настроить защиту веток
> и CODEOWNERS, писать коммиты по Conventional Commits.

---

## 🗺️ Карта темы

```text:no-line-numbers
 1. git switch -c feature/add-hpa      ← ветка от свежего main
 2. коммиты + git push -u origin …     ← работа
 3. открыть MR/PR  ─────────────────────────────────┐
                                                    ▼
 4.  ┌───────────── MERGE REQUEST ─────────────────────────────┐
     │ Заголовок + описание + ссылка на задачу                 │
     │ ✅ Pipeline passed        (CI: lint, test, build)        │
     │ 👤 Approvals: 1/1         (ревью коллеги)                │
     │ 👮 CODEOWNERS: @devops    (обязательный ревьюер файла)   │
     │ 🔒 main protected         (прямой push запрещён)         │
     └──────────────────────┬──────────────────────────────────┘
                            ▼
 5. Merge (merge-коммит / squash / ff)  →  main  →  пайплайн деплоя
 6. Ветка удаляется автоматически
```

---

## 1. Что такое MR/PR

**Merge Request** (GitLab) = **Pull Request** (GitHub) — запрос «влейте мою ветку
в основную», обёрнутый в процесс: обсуждение, автоматические проверки, аппрув, кнопка merge.

Это **не функция git**, а надстройка хостинга. Технически то же самое делает `git merge`,
но MR добавляет то, ради чего команды и живут в GitHub/GitLab:

| Что даёт MR | Зачем |
|-------------|-------|
| Diff всей ветки | Ревьюер видит ровно то, что изменится (`git diff main...feature`) |
| Комментарии к строкам | Обсуждение конкретного места, а не «там в конфиге что-то не так» |
| Проверки CI | Нельзя влить красный пайплайн |
| Аппрувы | Минимум один человек посмотрел изменение |
| История решений | Через год видно, почему изменение выглядит именно так |
| Кнопка отката | Revert одним действием |

## 2. Жизненный цикл MR

```bash
# 1. свежая ветка
git switch main && git pull
git switch -c feature/add-hpa

# 2. работа, осмысленные коммиты
git add k8s/hpa.yaml
git commit -m "feat(k8s): add HPA for payment service"

# 3. отправка
git push -u origin feature/add-hpa
# git печатает готовую ссылку "Create merge request for feature/add-hpa"

# 4. (по ходу ревью) правки
git commit -m "fix(k8s): lower min replicas to 2"
git push

# 5. актуализация под main перед мержем
git fetch origin && git rebase origin/main
git push --force-with-lease

# 6. merge кнопкой в интерфейсе → ветка удаляется
git switch main && git pull
git branch -d feature/add-hpa
```

### Хорошее описание MR

```markdown
## Что
Добавлен HorizontalPodAutoscaler для payment-service (2-8 реплик, target CPU 70%).

## Зачем
В пиковые часы сервис упирался в CPU, ручное масштабирование не успевало. Closes #431.

## Как проверить
kubectl -n payments get hpa payment-service
# при нагрузке > 70% CPU число реплик растёт

## Риски и откат
При некорректном target возможен «флаппинг» реплик. Откат: revert MR + kubectl delete hpa.

- [x] Манифест проверен `kubeval`
- [x] Проверено на stage
- [ ] Требует обновления дашборда (отдельная задача)
```

**Draft/WIP MR** — открывают сразу, чтобы показать направление работы: ревьюер увидит
подход раньше, чем ты потратишь два дня не туда.

## 3. Ревью: как смотреть и как получать

**Как ревьюер:**
1. Сначала описание и задача — понять **зачем**, а потом уже смотреть код.
2. Смотри на diff целиком (`Changes`), а не только на первые файлы.
3. Комментарий должен быть конкретным: не «плохо», а «здесь стоит вынести таймаут
   в переменную, иначе на stage придётся править вручную».
4. Различай уровни: `blocker` (нельзя вливать), `should` (стоит поправить),
   `nit`/`optional` (вкусовщина).
5. Хвали удачные решения — ревью не только про поиск ошибок.

**Как автор:**
1. MR должен быть **маленьким**: 200-400 строк читаются, 2000 — «LGTM» не глядя.
2. Сам просмотри свой diff перед отправкой (`git diff main...HEAD`) — половина замечаний
   отпадёт.
3. Отвечай на каждый комментарий: исправил / не согласен и почему / вынес в отдельную задачу.
4. Не переписывай историю ветки в середине ревью без предупреждения — комментарии
   «оторвутся» от строк.
5. Не спорь в комментариях дольше двух обменов репликами — созвонись.

**Типичный чек-лист ревью DevOps-изменения:** секреты не в коде; лимиты и реквесты заданы;
есть health-check; изменение обратимо; не сломает другие окружения; документация обновлена.

## 4. Защита веток и CODEOWNERS

Соглашения без настроек не работают. Минимум для `main`:

| Настройка | Что даёт |
|-----------|----------|
| Protected branch | Запрет прямого push |
| Запрет force-push | Нельзя переписать историю общей ветки |
| Обязательный MR + ≥1 approve | Каждое изменение кто-то видел |
| Обязательный зелёный пайплайн | Красный CI не вливается |
| Запрет self-approval | Автор не аппрувит сам себя |
| Автоудаление ветки после merge | Репозиторий не зарастает |
| Protected tags (`v*`) | Релизный тег ставит не каждый |

**CODEOWNERS** — файл, назначающий обязательных ревьюеров по путям:

```text:no-line-numbers
# .github/CODEOWNERS  или  CODEOWNERS / .gitlab/CODEOWNERS
*                       @nurik
/k8s/                   @devops-team
/terraform/             @devops-team @security
/.gitlab-ci.yml         @devops-team
/charts/*/values.yaml   @devops-team
*.tf                    @infra-lead
```

Правило: изменение в `terraform/` нельзя влить без аппрува команды инфраструктуры.
Это и защита от ошибок, и способ распространить знания.

## 5. Conventional Commits

Соглашение о формате сообщений — то, из чего автоматически собирают CHANGELOG
и вычисляют версию.

```text:no-line-numbers
<тип>(<область>): <краткое описание>

[тело: зачем]

[футер: BREAKING CHANGE / Closes #123]
```

| Тип | Когда | Влияет на версию |
|-----|-------|------------------|
| `feat` | новая функциональность | MINOR |
| `fix` | исправление | PATCH |
| `docs` | только документация | — |
| `refactor` | без изменения поведения | — |
| `perf` | производительность | PATCH |
| `test` | тесты | — |
| `build`/`ci` | сборка, пайплайны | — |
| `chore` | рутина (зависимости, версии) | — |
| `BREAKING CHANGE:` в футере или `feat!:` | ломающее изменение | MAJOR |

```text:no-line-numbers
feat(ci): add trivy scan stage

Сканируем образ до пуша в registry, пайплайн падает на HIGH/CRITICAL.

Closes #431
```

Инструменты: `commitlint` в pre-commit и в CI, `semantic-release`/`release-please`
для автоматических версий и CHANGELOG (тема 08).

## 6. Форк-модель (open source и не только)

```text:no-line-numbers
 upstream (оригинал)  ◄── PR ───  origin (твой форк)  ◄── push ──  локально
        │                                                    ▲
        └──────────── git fetch upstream ────────────────────┘
```

```bash
git clone git@github.com:nurik/project.git          # твой форк = origin
git remote add upstream https://github.com/original/project.git
git fetch upstream
git switch -c fix/typo upstream/main
# ... правки ...
git push -u origin fix/typo                          # пуш в СВОЙ форк
# → PR из nurik/project:fix/typo в original/project:main

# поддерживать форк в актуальном состоянии
git fetch upstream && git switch main && git merge upstream/main && git push
```

Используется в open source и в компаниях, где у внешних подрядчиков нет прав на запись.

## 7. Ещё инструменты командной работы

```bash
# шаблон сообщения коммита
git config --global commit.template ~/.gitmessage

# подписывать коммиты (в некоторых компаниях обязательно)
git config --global user.signingkey <KEY_ID>
git config --global commit.gpgsign true
git log --show-signature -1

# кто автор строки и в каком коммите
git blame -L 40,60 values.yaml
git log -S "resources:" -p -- values.yaml
```

Шаблоны MR/issue в репозитории — `.gitlab/merge_request_templates/*.md`,
`.github/PULL_REQUEST_TEMPLATE.md`: единая структура описания для всей команды.

## 💼 Как это в DevOps

- **Инфраструктура меняется только через MR.** «Зашёл на сервер и поправил» — главный
  антипаттерн: изменение не отревьюено, не задокументировано и потеряется при пересоздании
  машины.
- DevOps-инженер обычно **владелец правил репозитория**: protected branches, CODEOWNERS,
  шаблоны MR, обязательные джобы (lint, security scan), автоудаление веток.
- CODEOWNERS на `terraform/`, `k8s/`, `.gitlab-ci.yml` — способ не пропустить изменения,
  которые роняют прод.
- Ревью инфраструктурного MR ≠ ревью кода: смотрят на обратимость, влияние на другие
  окружения, лимиты, секреты, простои при применении.
- В GitOps-репозитории MR — это буквально **заявка на изменение прода**: аппрув = разрешение
  на выкат, merge = выкат.
- На собеседовании часто спрашивают не команды, а процесс: «как у вас проходило изменение
  от задачи до прода» — отвечать нужно именно этой цепочкой.

## 📌 Шпаргалка

| Хочу | Как |
|------|-----|
| Начать задачу | `git switch main && git pull && git switch -c feature/x` |
| Отправить ветку и открыть MR | `git push -u origin feature/x` (ссылка появится в выводе) |
| Посмотреть свой diff как ревьюер | `git diff main...HEAD` |
| Обновить ветку под main | `git fetch && git rebase origin/main` + `--force-with-lease` |
| Довесить правку в старый коммит | `git commit --fixup=<хеш>` + `git rebase -i --autosquash` |
| Понять, кто трогал строку | `git blame -L 10,20 file` |
| Назначить обязательных ревьюеров | файл `CODEOWNERS` |
| Единый формат коммитов | Conventional Commits + `commitlint` в CI |
| Синхронизировать форк | `git fetch upstream && git merge upstream/main` |
| Шаблон описания MR | `.gitlab/merge_request_templates/default.md` |

## 🧠 Что запомнить

1. **MR/PR — надстройка хостинга**, а не команда git; она добавляет ревью, CI и историю решений.
2. Цикл: свежая ветка → коммиты → push → MR → ревью и CI → актуализация под `main` → merge →
   удаление ветки.
3. **Маленький MR** получает настоящее ревью; большой получает «LGTM».
4. Хорошее описание MR отвечает на «что», «зачем», «как проверить», «как откатить».
5. Ревьюер начинает с задачи и описания, а не со строк diff'а; комментарии — конкретные,
   с уровнем важности.
6. Соглашения работают только вместе с настройками: **protected branch, обязательный MR,
   зелёный CI, CODEOWNERS**.
7. **CODEOWNERS** делает ревью критичных путей обязательным (terraform, k8s, CI-файлы).
8. **Conventional Commits** дают автоматические CHANGELOG и версии; `feat`/`fix`/`BREAKING CHANGE`
   отображаются в SemVer.
9. Не переписывай историю ветки в середине ревью без предупреждения.
10. Форк-модель: `origin` — твой форк, `upstream` — оригинал; PR идёт из форка.
11. В DevOps MR — это заявка на изменение инфраструктуры; ручные правки на серверах
    вне git не существуют как процесс.

### Блок A. Теория

**A1.** ⭐ Что такое MR/PR? Является ли это функцией git?

<details><summary>Ответ</summary>

Запрос на слияние ветки, оформленный как процесс с обсуждением, проверками и аппрувом.
Это функция хостинга (GitLab/GitHub/Bitbucket), а не самого git; git знает только `merge`.

</details>

**A2.** Назови шесть вещей, которые даёт MR по сравнению с `git merge` в терминале.

<details><summary>Ответ</summary>

Diff всей ветки относительно точки ветвления; построчные комментарии; обязательные
проверки CI; аппрувы; фиксация обсуждения и причин решения; кнопки merge/revert и автоудаление
ветки; связь с задачей/issue.

</details>

**A3.** Опиши жизненный цикл MR от создания ветки до удаления ветки (шесть шагов).

<details><summary>Ответ</summary>

(1) Ветка от свежего `main`; (2) коммиты; (3) push и открытие MR с описанием;
(4) ревью + зелёный CI, правки по замечаниям; (5) актуализация под `main`
(`rebase origin/main` + `--force-with-lease`); (6) merge и удаление ветки.

</details>

**A4.** Что должно быть в описании MR? Назови четыре обязательных пункта.

<details><summary>Ответ</summary>

Что сделано; зачем (проблема/задача, ссылка на issue); как проверить;
риски и способ отката. Полезное дополнение — чек-лист.

</details>

**A5.** Что такое Draft/WIP MR и зачем открывать его рано?

<details><summary>Ответ</summary>

MR, помеченный как черновик: его нельзя влить, но он виден команде. Открывают рано,
чтобы обсудить подход до того, как написан весь объём работы, и чтобы CI гонялся с первых
коммитов.

</details>

**A6.** ⭐ Почему маленький MR лучше большого? Назови объективный порог.

<details><summary>Ответ</summary>

Маленький MR действительно читают: внимание ревьюера ограничено. Практический
ориентир — до 200-400 изменённых строк; всё, что больше, разбивают на несколько MR
или выделяют механические изменения (переименования, форматирование) в отдельный MR.

</details>

**A7.** Три правила для ревьюера и три для автора MR.

<details><summary>Ответ</summary>

Ревьюер: сначала понять задачу, потом смотреть код; комментарии конкретные
и с указанием важности (blocker/should/nit); не переходить на личности, хвалить удачное.
Автор: маленький MR и самопроверка diff'а; ответ на каждый комментарий; не переписывать
историю в середине ревью без предупреждения.

</details>

**A8.** ⭐ Что такое protected branch и какие настройки в него входят (назови шесть)?

<details><summary>Ответ</summary>

Запрет прямого push; запрет force-push; обязательный MR; минимум N аппрувов;
обязательный успешный пайплайн; запрет self-approval; (часто) автоудаление веток
и ограничение, кто может мержить.

</details>

**A9.** Что такое CODEOWNERS и как он выглядит? Приведи три правила для DevOps-репозитория.

<details><summary>Ответ</summary>

Файл, сопоставляющий пути и обязательных ревьюеров (`/terraform/ @devops-team`).
Для DevOps-репозитория: `/terraform/ @devops-team @security`, `/.gitlab-ci.yml @devops-team`,
`/charts/*/values.yaml @devops-team`.

</details>

**A10.** ⭐ Что такое Conventional Commits? Перечисли основные типы и их влияние на SemVer.

<details><summary>Ответ</summary>

Соглашение о формате сообщений `тип(область): описание`. `feat` → MINOR,
`fix`/`perf` → PATCH, `docs`/`refactor`/`test`/`chore`/`ci`/`build` → версию не меняют,
`BREAKING CHANGE` (или `!` после типа) → MAJOR. Позволяет автоматически считать версию
и собирать CHANGELOG.

</details>

**A11.** Как обозначить ломающее изменение в сообщении коммита?

<details><summary>Ответ</summary>

Восклицательный знак после типа/области (`feat!:`, `fix(api)!:`) либо футер
`BREAKING CHANGE: описание`. Оба варианта поднимают MAJOR.

</details>

**A12.** Что такое форк-модель? Какие remote'ы при этом настроены и зачем?

<details><summary>Ответ</summary>

Работа через собственную копию репозитория: `origin` — твой форк (туда пушишь),
`upstream` — оригинал (оттуда забираешь изменения, туда открываешь PR). Нужна, когда
нет прав на запись в оригинал (open source, внешние подрядчики).

</details>

**A13.** Почему не стоит делать force-push в свою ветку в середине ревью?

<details><summary>Ответ</summary>

Комментарии ревьюера привязаны к конкретным коммитам/строкам: после переписывания
истории они «отрываются», ревьюеру сложно понять, что изменилось с прошлого раза.
Если rebase необходим — предупредить и, по возможности, сделать после аппрува.

</details>

**A14.** Чем ревью инфраструктурного изменения отличается от ревью кода? Назови пять пунктов.

<details><summary>Ответ</summary>

Обратимость изменения; влияние на другие окружения и соседние сервисы; наличие
секретов и прав доступа; ресурсы/лимиты и health-check'и; простой при применении
и план отката; обновлена ли документация/runbook.

</details>

**A15.** Зачем шаблоны MR и где они лежат в GitLab/GitHub?

<details><summary>Ответ</summary>

Чтобы описание MR имело единую структуру и никто не забывал про «как проверить»
и «как откатить». GitLab: `.gitlab/merge_request_templates/*.md`;
GitHub: `.github/PULL_REQUEST_TEMPLATE.md`.

</details>

**A16.** Зачем подписывать коммиты (GPG/SSH) и где это требуют?

<details><summary>Ответ</summary>

Подпись подтверждает авторство коммита (имя и почта в git — это просто текст,
их можно подделать). Требуют в компаниях с повышенными требованиями к безопасности
и в некоторых open source проектах; настраивается через GPG или SSH-ключ.

</details>

### Блок B. «Что делает команда/конструкция»

Слева — команда или конструкция, справа (сразу под ней) — что она делает.

```bash
B1.  git push -u origin feature/add-hpa
B2.  git diff main...HEAD
B3.  git fetch origin && git rebase origin/main
B4.  git push --force-with-lease
B5.  git commit -m "feat(k8s): add HPA for payment service"
B6.  git commit -m "fix!: drop deprecated /api/v1"
B7.  git commit --fixup=9a8b7c6 && git rebase -i --autosquash main
B8.  git blame -L 40,60 values.yaml
B9.  git log -S "resources:" -p -- charts/payment/values.yaml
B10. git remote add upstream https://github.com/original/project.git
B11. git fetch upstream && git switch -c fix/typo upstream/main
B12. git config --global commit.template ~/.gitmessage
B13. git config --global commit.gpgsign true
```

### Блок C. Практика

#### C1. 🔑 Первый MR самому себе
1. В репозитории `devops-notes`: `git switch -c docs/git-block`.
2. Добавь папку `Git/` с конспектами, закоммить по Conventional Commits
   (`docs(git): добавлен блок конспектов по git`).
3. `git push -u origin docs/git-block` — открой ссылку из вывода.
4. Заполни описание MR по шаблону из конспекта (что / зачем / как проверить / откат).
5. Посмотри вкладку Changes — это `git diff main...HEAD`.
6. Влей и убедись, что ветка удалилась.

#### C2. Ревью самому себе
Перед мержем C1 выполни `git diff main...HEAD` в терминале и найди минимум три вещи,
которые стоит поправить (опечатки, забытые файлы, лишние временные файлы).
Исправь отдельными коммитами и запушь.

#### C3. 🔑 Защита main
В настройках репозитория включи:
- protected `main`: запрет прямого push и force-push;
- обязательный MR;
- (если доступно) обязательный зелёный пайплайн;
- автоудаление веток после merge;
- protected tags `v*`.

Проверь: `git switch main && echo x >> README.md && git commit -am "test" && git push` —
что ответит сервер?

<details><summary>Ответ</summary>

Сервер ответит отказом вида `remote: GitLab: You are not allowed to push code
to protected branches on this project` / `protected branch hook declined` — push
в защищённую ветку запрещён, изменение возможно только через MR.

</details>

#### C4. CODEOWNERS
Создай файл `CODEOWNERS` (или `.github/CODEOWNERS`):
```text:no-line-numbers
*                 @<твой-логин>
/Git/             @<твой-логин>
/Kubernetes/      @<твой-логин>
```
Открой MR, меняющий файл в `Kubernetes/`, и проверь, что ревьюер назначился автоматически.

#### C5. Conventional Commits
Перепиши в правильный формат:
```text:no-line-numbers
1. "добавил хпа"
2. "поправил ci"
3. "удалил старый эндпоинт, теперь клиентам надо перейти на v2"
4. "обновил документацию по деплою"
5. "bump alpine"
6. "ускорил сборку образа"
```

<details><summary>Ответ</summary>

1 → `feat(k8s): add HPA for payment service`; 2 → `fix(ci): correct docker build
context`; 3 → `feat(api)!: remove deprecated /api/v1` + футер `BREAKING CHANGE: клиенты
должны перейти на /api/v2`; 4 → `docs(deploy): update deployment guide`;
5 → `chore(deps): bump alpine to 3.20`; 6 → `perf(build): enable docker layer caching`.

</details>

#### C6. commitlint локально
```bash
npm init -y >/dev/null 2>&1
npx --yes @commitlint/cli --version
cat > commitlint.config.js <<'EOF'
module.exports = { extends: ['@commitlint/config-conventional'] };
EOF
echo "плохое сообщение" | npx --yes --package @commitlint/config-conventional --package @commitlint/cli commitlint
echo "feat(ci): add lint stage" | npx --yes --package @commitlint/config-conventional --package @commitlint/cli commitlint
```
Сравни вывод. Как встроить это в CI (тема 12)?

<details><summary>Ответ</summary>

На «плохое сообщение» commitlint выдаст ошибки `subject may not be empty`,
`type may not be empty`; на корректное — пустой вывод (успех). В CI это отдельная джоба,
проверяющая сообщения коммитов MR (или хук `commit-msg` локально).

</details>

#### C7. Шаблон коммита
```bash
cat > ~/.gitmessage <<'EOF'
<тип>(<область>): <что сделано>

# Зачем:
#
# Closes #
EOF
git config --global commit.template ~/.gitmessage
git commit                      # посмотри, что открылось в редакторе
```

#### C8. Шаблон MR
Создай `.gitlab/merge_request_templates/default.md` (или `.github/PULL_REQUEST_TEMPLATE.md`)
с разделами: Что / Зачем / Как проверить / Риски и откат / Чек-лист.
Открой новый MR и убедись, что описание подставилось.

#### C9. Форк-модель
1. Сделай форк любого небольшого публичного репозитория.
2. `git clone` своего форка, `git remote add upstream <оригинал>`.
3. `git fetch upstream && git switch -c docs/typo upstream/main`.
4. Внеси мелкую правку (например, опечатку в README), запушь **в свой форк**.
5. Открой PR в оригинал (можно не отправлять на ревью, если правка выдуманная — закрой его).
6. Синхронизируй форк: `git fetch upstream && git switch main && git merge upstream/main`.

#### C10. blame-расследование
В своём репозитории:
```bash
git blame -L 1,20 Git/00_INDEX.md
git log -S "Trunk-Based" --oneline
git log --follow --oneline -- Git/09_branching_strategies.md
```
Сформулируй, как эти три команды помогают при разборе инцидента.

<details><summary>Ответ</summary>

`blame` показывает, кто и когда внёс конкретную строку (кого звать и что читать);
`log -S` находит коммит, где появилось значение (когда «приехала» проблема);
`log --follow` даёт всю историю файла, включая переименования (контекст изменений).

</details>

#### C11. Комментарии ревью (упражнение на формулировки)
Перепиши грубые комментарии в конструктивные:
```text:no-line-numbers
1. "Это бред, так не делают"
2. "Опять хардкод"
3. "Тут всё надо переписать"
4. "А ты тестировал вообще?"
```

<details><summary>Ответ</summary>

Например: 1 → «Здесь лучше использовать модуль `x`: он уже умеет retry, иначе
мы дублируем логику»; 2 → «Вынеси таймаут в переменную/values — на stage значение другое»;
3 → «Предлагаю разбить на два MR: сначала переименование, потом логика — так проще ревьюить»;
4 → «Как это проверялось? Добавь, пожалуйста, в описание шаги проверки или скрин со stage».

</details>

### Блок D. Инциденты

**D1.** MR висит три дня без ревью. Что делать (три действия) и что менять в процессе?

<details><summary>Ответ</summary>

Напомнить в чате, назначить конкретного ревьюера (а не «команду»), уменьшить MR;
процессно — SLA на ревью (например, 4 часа), дежурный ревьюер дня, автоназначение
через CODEOWNERS.

</details>

**D2.** В MR 47 файлов и 3100 строк. Ревьюер написал «LGTM» через две минуты.
В чём проблема и как её решать?

<details><summary>Ответ</summary>

Такой объём невозможно отревьюить: ревью становится формальностью, ошибки уходят
в прод. Решение — дробить задачи, отделять механические изменения (форматирование,
переименования) в отдельные MR, ограничение по размеру в соглашении команды.

</details>

**D3.** После force-push в ветку MR все комментарии ревьюера «оторвались» от строк.
Как избежать в следующий раз?

<details><summary>Ответ</summary>

Предупреждать и делать rebase до начала ревью или после аппрува; вместо переписывания
истории добавлять новые коммиты (`fixup!`), а схлопывать их squash-мержем при вливании.

</details>

**D4.** Разработчик влил MR с красным пайплайном (была кнопка «merge anyway»).
Что настроить?

<details><summary>Ответ</summary>

Обязательный успешный пайплайн для merge в настройках защиты ветки
(«Pipelines must succeed»), запрет мержа при красном CI и, при необходимости,
ограничение круга тех, кто может мержить.

</details>

**D5.** Изменение в `terraform/` уронило прод; выяснилось, что ревьюер не разбирался
в терраформе. Какая настройка помогла бы?

<details><summary>Ответ</summary>

CODEOWNERS: `/terraform/ @devops-team @security` — обязательный аппрув людей,
которые разбираются в этой части; плюс обязательные проверки (`terraform plan`,
policy-as-code) в пайплайне MR.

</details>

**D6.** В `main` попал коммит с сообщением «фикс» без описания, и через месяц никто
не помнит, зачем он. Что внедрить?

<details><summary>Ответ</summary>

Conventional Commits + `commitlint` в CI, обязательное описание MR по шаблону,
ссылка на задачу в каждом коммите/MR, squash-merge с осмысленным итоговым сообщением.

</details>

**D7.** Ты оставил 12 комментариев в MR коллеги, он обиделся. Что можно было сделать иначе?

<details><summary>Ответ</summary>

Сгруппировать замечания (часть — одним комментарием «общие мелочи»), явно разделить
blocker и nit, начать с плюсов, спорные вещи обсудить голосом, не оставлять оценок личности.
12 комментариев на один MR — сигнал, что MR слишком большой или нужен разговор, а не переписка.

</details>

**D8.** В форке ветка `main` разъехалась с upstream на 200 коммитов, PR показывает
кучу лишних изменений. Как привести в порядок?

<details><summary>Ответ</summary>

Привести `main` форка к upstream: `git fetch upstream && git switch main &&
git reset --hard upstream/main && git push --force-with-lease` (форк — твой, это допустимо),
затем создать ветку заново от `upstream/main` и перенести туда свои коммиты (`cherry-pick`).

</details>

**D9.** Хостинг требует подписанные коммиты, твой push отклонён с `commit not signed`.
Что настроить?

<details><summary>Ответ</summary>

Настроить подпись: сгенерировать GPG (или использовать SSH-ключ),
`git config --global user.signingkey <ID>`, `git config --global commit.gpgsign true`,
добавить публичный ключ в профиль хостинга; проверить `git log --show-signature`.

</details>

**D10.** Правило «MR обязателен» мешает дежурному быстро чинить прод ночью.
Как совместить скорость и контроль?

<details><summary>Ответ</summary>

Отдельный ускоренный путь для hotfix: ветка `hotfix/*` + MR с одним аппрувом
дежурного (или post-merge review), сокращённый набор обязательных проверок (smoke-тесты),
но сохранение самого MR — чтобы изменение осталось в истории и прошло ревью хотя бы постфактум.

</details>

### Блок E. Вопросы с собеседования

**1.** ⭐ Что такое Pull/Merge Request?

<details><summary>Ответ</summary>

Запрос на вливание ветки в основную, оформленный на хостинге: содержит diff, обсуждение,
результаты CI и аппрувы; merge выполняется кнопкой после выполнения правил.

</details>

**2.** Как у вас выглядел процесс от задачи до прода?

<details><summary>Ответ</summary>

Задача → ветка от `main` → коммиты → push → MR с описанием → CI (lint/test/build) →
ревью и аппрув → актуализация под `main` → merge → пайплайн деплоя (stage, затем прод
по тегу/кнопке).

</details>

**3.** Что такое code review и что ты смотришь в чужом MR?

<details><summary>Ответ</summary>

Процесс проверки изменений другим инженером. Смотрю: решает ли изменение задачу,
обратимо ли оно, нет ли секретов, как поведёт себя в других окружениях, есть ли тесты
и обновлена ли документация.

</details>

**4.** Что такое protected branch?

<details><summary>Ответ</summary>

Ветка с ограничениями на хостинге: запрет прямого push и force-push, обязательный MR
с ревью и зелёным пайплайном.

</details>

**5.** Что такое CODEOWNERS?

<details><summary>Ответ</summary>

Файл с сопоставлением путей и обязательных ревьюеров: изменения в указанных каталогах
нельзя влить без аппрува ответственных.

</details>

**6.** Что такое Conventional Commits и зачем они?

<details><summary>Ответ</summary>

Соглашение о формате сообщений (`feat`, `fix`, `docs`, `BREAKING CHANGE` и т. д.),
которое делает историю читаемой и позволяет автоматически считать версию и CHANGELOG.

</details>

**7.** Как обозначается ломающее изменение?

<details><summary>Ответ</summary>

`тип!:` или футер `BREAKING CHANGE: …`; поднимает MAJOR-версию.

</details>

**8.** Что такое форк и когда он нужен?

<details><summary>Ответ</summary>

Собственная копия репозитория на хостинге; нужен, когда нет прав на запись в оригинал:
пушишь в форк и открываешь PR в upstream.

</details>

**9.** Как ты актуализируешь свою ветку перед мержем?

<details><summary>Ответ</summary>

`git fetch origin && git rebase origin/main` (или merge, по соглашению команды),
затем `git push --force-with-lease` для своей ветки.

</details>

**10.** Что делать, если в MR прилетел конфликт?

<details><summary>Ответ</summary>

Забрать свежий `main` в ветку (`rebase`/`merge`), разрешить конфликт локально,
прогнать проверки и запушить; для простых случаев есть веб-редактор конфликтов
в GitLab/GitHub.

</details>
