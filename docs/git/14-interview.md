## 🎯 Часть 1. Три главных вопроса роадмапа

### 1. Как перенести коммиты из одной ветки в другую? ⭐⭐

<details><summary>Ответ</summary>

**Короткий ответ (30 секунд):**
> «Зависит от того, что переносим. Один конкретный коммит — `git cherry-pick <хеш>`;
> всю свою ветку поверх другой — `git rebase <ветка>`; часть ветки — `git rebase --onto`;
> если задача просто "влить готовую ветку" — обычный `git merge`.»

**Развёрнутый ответ:**

| Способ | Команда | Когда |
|--------|---------|-------|
| Один коммит | `git cherry-pick -x <хеш>` | Бэкпорт фикса из `main` в `release/1.4` |
| Диапазон | `git cherry-pick A^..B` | Несколько подряд идущих коммитов |
| Вся ветка на новое основание | `git rebase main` | Актуализировать свою ветку перед MR |
| Часть ветки | `git rebase --onto main develop feature` | Ветка создана не от той ветки |
| Влить целиком | `git merge feature` | Штатное завершение задачи |
| Между репозиториями | `git format-patch` + `git am` | Нет общего remote |
| «Коммитил не в ту ветку» | `git switch -c feature` + `git reset --hard origin/main` | Ещё не пушил |

**Что показать сверх ответа (это и отличает сильного кандидата):**
- cherry-pick и rebase **создают новые коммиты** с новыми хешами — изменение копируется,
  а не «переезжает»;
- флаг `-x` у cherry-pick оставляет ссылку на исходный коммит — важно для релизных веток;
- золотое правило: **не ребейзить опубликованные/общие ветки**; после rebase своей ветки —
  только `git push --force-with-lease`;
- реальный кейс: «фикс сделан в main, на проде живёт release/1.4 → cherry-pick фикса
  в релизную ветку → тег v1.4.3 → выкат».

```bash
# бэкпорт фикса в релизную ветку
git switch release/1.4
git cherry-pick -x a1b2c3d
git tag -a v1.4.3 -m "hotfix 1.4.3" && git push origin release/1.4 v1.4.3
```

</details>

### 2. Что такое merge conflict и каковы причины? ⭐⭐

<details><summary>Ответ</summary>

**Короткий ответ:**
> «Конфликт возникает, когда git при слиянии видит, что **один и тот же участок файла
> изменён по-разному в двух ветках**, и не может выбрать вариант автоматически.
> Он останавливает слияние и просит человека решить.»

**Причины (перечисляй списком — это то, что спрашивают):**
1. Одна и та же строка/блок изменены по-разному в двух ветках.
2. `modify/delete`: в одной ветке файл правили, в другой удалили.
3. `add/add`: в обеих ветках создан файл с одинаковым именем и разным содержимым.
4. Переименование против правки того же файла.
5. Разные окончания строк (CRLF/LF) или автоформаттер — «конфликт всего файла».
6. Генерируемые файлы в репозитории (`package-lock.json`, локи, бандлы).
7. **Корневая причина на практике:** долгоживущая ветка, которая давно не синхронизировалась
   с `main`.

**Как разрешаю:**
```bash
git status                       # какие файлы конфликтуют
# открыть файл: <<<<<<< HEAD — моя сторона, ======= , >>>>>>> ветка — их сторона
# оставить правильный ИТОГОВЫЙ текст, убрать маркеры
git add <файл>
git commit                       # (при rebase: git rebase --continue)
git merge --abort                # если решил откатиться и разобраться
```

**Бонусы, которые стоит упомянуть:**
- при **rebase** стороны меняются местами: `ours` — это целевая ветка (main), `theirs` — твой
  переносимый коммит;
- конфликт — **не ошибка git**: изменения в разных участках файла он сливает сам;
- профилактика: короткие ветки, ежедневный `rebase origin/main`, маленькие MR,
  `.gitattributes` с `eol=lf`, `git rerere`;
- нельзя коммитить файл с маркерами — в CI ставят grep-проверку;
- разрешать нужно **осмысленно**: механический `--ours` откатывает чужую работу
  (реальный кейс: затёрли поднятые лимиты памяти → ночной OOM).

</details>

### 3. Как работает `git pull` (что под капотом)? ⭐⭐

<details><summary>Ответ</summary>

**Короткий ответ:**
> «`git pull` — составная команда: `git fetch` + `git merge`. Fetch скачивает новые объекты
> с сервера и двигает remote-tracking ветку `origin/main`, а merge вливает `origin/main`
> в мою текущую ветку. С флагом `--rebase` вторым шагом выполняется `git rebase`.»

```text:no-line-numbers
git pull
 ├── 1) git fetch origin           → объекты + обновление origin/<ветка>
 └── 2) git merge origin/<ветка>   → fast-forward, merge-коммит или КОНФЛИКТ
        (с --rebase: git rebase origin/<ветка>)
```

**Что добавить, чтобы ответ был «взрослым»:**
- поэтому **pull может создать merge-коммит и вызвать конфликт, а fetch — никогда**;
- `origin/main` — это локальный снимок состояния сервера на момент последнего fetch,
  а не живая ссылка;
- безопасный вариант «посмотреть, что там»:
  ```bash
  git fetch
  git log --oneline main..origin/main     # что прилетит
  git diff main origin/main
  ```
- варианты поведения: `pull.rebase=false` (merge, по умолчанию), `pull.rebase=true` (rebase),
  `pull --ff-only` (только перемотка, иначе ошибка) — в командах часто фиксируют одно
  поведение для всех;
- почему `git push` иногда отклоняется: на сервере есть коммиты, которых нет у тебя, —
  push разрешён только fast-forward, поэтому сначала `pull`.

</details>

## 📚 Часть 2. Дополнительные вопросы

### Основы

**Что такое git и чем он отличается от SVN?**

<details><summary>Ответ</summary>

Распределённая система контроля версий: полная история у каждого, работа офлайн, дешёвые
ветки. SVN централизован: история на сервере, ветка — копия дерева, для коммита нужна связь.

</details>

**Git и GitHub — это одно и то же?**

<details><summary>Ответ</summary>

Нет. Git — программа контроля версий; GitHub/GitLab/Bitbucket — хостинги поверх git
с веб-интерфейсом, PR/MR, issues и CI.

</details>

**Что такое коммит?**

<details><summary>Ответ</summary>

Снимок состояния проекта на момент фиксации плюс метаданные: ссылка на дерево файлов,
родительский коммит (у merge — два), автор, дата, сообщение. Идентифицируется хешем
содержимого.

</details>

**Что такое ветка?**

<details><summary>Ответ</summary>

Подвижный указатель на коммит — физически файл в `.git/refs/heads/` с хешем. Поэтому
создание ветки мгновенно.

</details>

**Что такое HEAD? А detached HEAD?**

<details><summary>Ответ</summary>

HEAD — указатель на текущую позицию, обычно ссылка на активную ветку. Detached HEAD —
когда он указывает прямо на коммит: новые коммиты не привязаны к ветке и легко теряются,
спасает `git switch -c <имя>`.

</details>

**Что лежит в `.git`?**

<details><summary>Ответ</summary>

`objects/` (blob, tree, commit, tag), `refs/` (ветки и теги), `HEAD`, `index` (staging),
`config`, `hooks/`, `logs/` (reflog).

</details>

**Зачем git хеши?**

<details><summary>Ответ</summary>

Адресация по содержимому (одинаковые данные — один объект) и целостность: изменение
любого байта меняет хеш, поэтому историю нельзя подменить незаметно.

</details>

### Ежедневная работа

**Что такое staging area и зачем он нужен?**

<details><summary>Ответ</summary>

Промежуточная область между рабочим каталогом и репозиторием. Позволяет собрать
атомарный коммит из части изменений и проверить `git diff --staged` перед фиксацией.

</details>

**Разница `git diff` и `git diff --staged`?**

<details><summary>Ответ</summary>

Первый — что изменено, но не добавлено в индекс; второй — что уйдёт в коммит.

</details>

**Что делает `git commit -a` и когда не сработает?**

<details><summary>Ответ</summary>

Добавляет изменения отслеживаемых файлов; новые (untracked) файлы не попадут.

</details>

**Как отменить `git add`?**

<details><summary>Ответ</summary>

`git restore --staged <файл>` (раньше — `git reset HEAD <файл>`).

</details>

**Как посмотреть, кто добавил строку?**

<details><summary>Ответ</summary>

`git blame -L 10,20 file`, затем `git show <хеш>`; для поиска появления значения —
`git log -S "строка" -p`.

</details>

**Что такое `.gitignore` и почему он не помогает для уже отслеживаемых файлов?**

<details><summary>Ответ</summary>

Список масок для неотслеживаемых файлов. Уже добавленный в индекс файл продолжает
отслеживаться — нужно `git rm --cached <файл>`.

</details>

### Ветки и слияния

**Fast-forward vs трёхстороннее слияние?**

<details><summary>Ответ</summary>

FF — целевая ветка не двигалась, указатель просто перематывается, merge-коммита нет.
3-way — обе ветки ушли вперёд: берётся общий предок и две вершины, создаётся merge-коммит
с двумя родителями.

</details>

**Зачем `--no-ff`?**

<details><summary>Ответ</summary>

Чтобы в истории остался факт слияния ветки: видно границы задачи, её можно откатить одним
`git revert -m 1`.

</details>

**Чем `merge --squash` отличается от merge?**

<details><summary>Ответ</summary>

Все изменения ветки схлопываются в один коммит с одним родителем; связи с коммитами ветки
не остаётся, git не считает ветку влитой.

</details>

**Что такое `git diff main...feature` (три точки)?**

<details><summary>Ответ</summary>

Разница между общим предком и вершиной ветки — то, что показывает MR. Две точки сравнивают
вершины.

</details>

**Удалятся ли коммиты при удалении ветки?**

<details><summary>Ответ</summary>

Нет: удаляется указатель, коммиты остаются недостижимыми и восстанавливаются через reflog.

</details>

### Откаты и восстановление

**`revert` vs `reset`?**

<details><summary>Ответ</summary>

`revert` добавляет новый коммит с обратными изменениями — безопасен для опубликованных
веток; `reset` двигает указатель и переписывает историю — только для локального.

</details>

**Режимы reset?**

<details><summary>Ответ</summary>

`--soft` (ветка), `--mixed` (ветка + индекс), `--hard` (ветка + индекс + рабочий каталог,
изменения теряются).

</details>

**Что делает `git commit --amend`?**

<details><summary>Ответ</summary>

Создаёт новый коммит взамен последнего (изменить сообщение, дописать файл); хеш меняется —
только для незапушенного.

</details>

**Что такое reflog?**

<details><summary>Ответ</summary>

Журнал перемещений HEAD и веток; возвращает коммиты после `reset --hard`, неудачного rebase,
удаления ветки, из detached HEAD. Хранится ~90 дней.

</details>

**Что нельзя восстановить?**

<details><summary>Ответ</summary>

Незакоммиченные изменения, стёртые `reset --hard`, `restore` или `clean` — git их
никогда не видел.

</details>

**Как откатить merge-коммит?**

<details><summary>Ответ</summary>

`git revert -m 1 <хеш>` (1 — основная линия). Помнить: повторное слияние той же ветки
изменения не вернёт.

</details>

### Удалёнка и командная работа

**Что такое `origin`?**

<details><summary>Ответ</summary>

Имя по умолчанию для удалённого репозитория, из которого сделан клон.

</details>

**Почему push отклоняется и что делать?**

<details><summary>Ответ</summary>

На сервере есть коммиты, которых нет у тебя; push допускается только fast-forward.
Решение: `git pull` (или `--rebase`), разрешить конфликты, запушить снова.

</details>

**Чем опасен `--force`? Что такое `--force-with-lease`?**

<details><summary>Ответ</summary>

Force переписывает серверную ветку и уничтожает чужие коммиты. `--force-with-lease`
отправляет, только если ветка на сервере не двигалась с твоего последнего fetch.

</details>

**Как отправить теги?**

<details><summary>Ответ</summary>

`git push origin <tag>` / `--tags` / `--follow-tags`; обычный push теги не отправляет.

</details>

**Что такое protected branch и CODEOWNERS?**

<details><summary>Ответ</summary>

Защита ветки (запрет push/force-push, обязательный MR, ревью и зелёный CI) и файл,
назначающий обязательных ревьюеров по путям.

</details>

**Что такое MR/PR?**

<details><summary>Ответ</summary>

Запрос на слияние с обсуждением, проверками CI и аппрувами — функция хостинга, а не git.

</details>

### Теги, версии, стратегии

**Тег vs ветка?**

<details><summary>Ответ</summary>

Тег неподвижен и обозначает версию; ветка двигается и обозначает линию разработки.

</details>

**Annotated vs lightweight?**

<details><summary>Ответ</summary>

Annotated — объект с автором, датой, сообщением и подписью (для релизов);
lightweight — просто указатель.

</details>

**Что такое SemVer?**

<details><summary>Ответ</summary>

`MAJOR.MINOR.PATCH`: ломающие изменения / новая совместимая функциональность / исправления.

</details>

**Какие стратегии ветвления знаешь?**

<details><summary>Ответ</summary>

GitFlow, GitHub Flow, GitLab Flow, Trunk-Based. Уметь объяснить различия и обосновать выбор
(см. [тему 09](/git/09-branching-strategies)).

</details>

**Как делается хотфикс прода?**

<details><summary>Ответ</summary>

Ветка от тега прод-версии → минимальный фикс → новый PATCH-тег → выкат → перенос фикса
в `main` (cherry-pick).

</details>

### DevOps-специфика

**Как git используется в CI/CD?**

<details><summary>Ответ</summary>

Коммит/тег — триггер пайплайна; переменные `$CI_COMMIT_SHA`, `$CI_COMMIT_TAG`,
`$CI_COMMIT_BRANCH` определяют правила и теги артефактов; раннер клонирует репозиторий
(обычно shallow).

</details>

**Почему в CI `--depth 1` и когда мешает?**

<details><summary>Ответ</summary>

Ускоряет клон; мешает, когда нужна история (`git describe`, changelog, diff с предыдущим
коммитом) — тогда `GIT_DEPTH: 0` / `fetch-depth: 0`.

</details>

**Что такое deploy key?**

<details><summary>Ответ</summary>

SSH-ключ с доступом к одному репозиторию (обычно read-only) — для серверов, CI и ArgoCD.

</details>

**Что делать, если в репозиторий попал секрет?**

<details><summary>Ответ</summary>

Сначала отозвать и сменить секрет; уведомить команду; при необходимости вычистить историю
(`git filter-repo`) с force-push и переклонированием; добавить сканер секретов
(gitleaks) в pre-commit и CI. `git rm`/`revert` проблему не решают.

</details>

**Что такое GitOps и при чём тут git?**

<details><summary>Ответ</summary>

Репозиторий — источник правды о состоянии кластера; агент (ArgoCD/Flux) приводит кластер
к состоянию ветки. Изменение прода = MR, откат = `git revert`.

</details>

**Как найти коммит, сломавший сборку?**

<details><summary>Ответ</summary>

`git bisect` (бинарный поиск между «хорошим» тегом и «плохим» состоянием),
при скриптуемой проверке — `git bisect run ./check.sh`.

</details>

**Как хранить большие файлы?**

<details><summary>Ответ</summary>

Git LFS или, лучше, вне git: registry, S3, артефакт-хранилище.

</details>

## 🛠️ Часть 3. Практические задания

### Задание A. «Нарисуй, что произойдёт»
Дана история:
```text:no-line-numbers
      c3 ── c4 (feature)
     /
c1 ─ c2 ── c5 (main)
```
Вопросы: что будет после `git merge feature` из `main`? А после `git rebase main`
в `feature`? Какие хеши изменятся? Сколько родителей у результирующего коммита?

<details>
<summary>Ответ</summary>

`git merge feature` из `main`: истории разошлись → трёхстороннее слияние, создаётся
merge-коммит `M` с родителями `c5` и `c4`; хеши существующих коммитов не меняются.

`git rebase main` в `feature`: коммиты `c3`, `c4` пересоздаются поверх `c5` как `c3'`, `c4'`
(новые хеши, один родитель у каждого), история линейная, старые `c3`/`c4` остаются
только в reflog.
</details>

### Задание B. «Разбери ситуацию»
Коллега говорит: «Я сделал rebase своей ветки на main и запушил с `--force`, а теперь
у Пети пропали коммиты». Что произошло и как чинить?

<details>
<summary>Ответ</summary>

Если ветка общая: rebase создал новые коммиты, force-push заменил серверную историю,
и коммиты Пети, лежавшие поверх старой версии, перестали быть достижимыми из ветки.
Чинить: Петя находит свои коммиты в `git reflog`/`git fsck`, создаёт ветку от них
и переносит (`cherry-pick`/`rebase`) поверх новой истории. Профилактика: не ребейзить
общие ветки, `--force-with-lease` вместо `--force`, protected branch с запретом force-push.
</details>

### Задание C. «Секрет в репозитории»
В `main` два дня назад попал `.env` с ключом облака, репозиторий приватный, но у 8 человек
есть клоны. Твои действия по порядку.

<details>
<summary>Ответ</summary>

1. Отозвать и перевыпустить ключ (он скомпрометирован), проверить логи использования.
2. Уведомить команду и безопасность.
3. Решить вопрос истории: `git filter-repo --path .env --invert-paths`, согласованный
   force-push (временно сняв защиту ветки), все делают свежий клон.

## 🗣️ Часть 4. Как себя вести на собесе по git

1. **Отвечай схемой, а не списком команд.** «pull = fetch + merge» звучит лучше, чем
   перечисление флагов.
2. **Рисуй.** Если есть доска или блокнот — граф коммитов до/после мгновенно показывает,
   что ты понимаешь модель, а не заучил команды.
3. **Приводи практику.** «Мы так делали бэкпорт фикса в релизную ветку» весит больше, чем
   формальное определение. Для pet-проекта это тоже работает: «в своём репозитории
   с конспектами…».
4. **Говори про безопасность истории.** Force-push в общую ветку, секреты в истории,
   защита веток — темы, где джун обычно «плывёт», и где легко выделиться.
5. **Не ври про опыт.** «`git rebase --onto` я использовал один раз и гуглил синтаксис,
   но понимаю, что он делает» — нормальный честный ответ.
6. **Если не помнишь команду — объясни идею.** Git-команды гуглятся за 10 секунд,
   понимание модели — нет, и спрашивают именно его.
