# 08. Теги и версионирование: v1.0, v2.0 и SemVer

> Роадмап → 1. Git → Теория → Концепции: **«Теги (tags) — пометки для версий (v1.0, v2.0)»**.
> **После темы ты умеешь:** ставить аннотированные теги, объяснять разницу с ветками
> и lightweight-тегами, читать SemVer и понимать, как тег превращается в релиз и в тег
> docker-образа.
> Смежная тема: версионирование артефактов в CI/CD (блок CI/CD).

---

## 🗺️ Карта темы

```text:no-line-numbers
      ВЕТКА — движется с каждым коммитом      ТЕГ — прибит к одному коммиту навсегда
      ────────────────────────────────►       ▼            ▼           ▼
  c1 ─ c2 ─ c3 ─ c4 ─ c5 ─ c6 ─ c7 ─ c8      v1.0.0      v1.1.0      v2.0.0
                                 (main)

  git tag -a v1.2.0 -m "release 1.2.0"   → объект tag в .git/objects + .git/refs/tags/v1.2.0
  git push origin v1.2.0                 → тег появился на сервере
         │
         ▼
  CI видит тег → собирает образ app:1.2.0 → пушит в registry → деплой на прод
```

---

## 1. Зачем теги

Коммит `a1b2c3d` ничего не говорит человеку. Тег `v1.4.2` говорит всё:
что именно сейчас работает на проде, что откатывать, какую версию упомянуть в инциденте.

| Задача | Как решается тегом |
|--------|--------------------|
| «Что сейчас на проде?» | `v1.4.2` — и это конкретный коммит |
| «Откатись на прошлую версию» | `git checkout v1.4.1` / деплой образа `app:1.4.1` |
| «С какой версии появился баг?» | `git log v1.4.1..v1.4.2` |
| «Собери релиз» | Пайплайн запускается **по тегу** (`rules: if: $CI_COMMIT_TAG`) |
| «Какая версия у этого коммита?» | `git describe --tags` → `v1.4.2-7-gabc1234` |

---

## 2. Тег vs ветка

| | Ветка | Тег |
|---|-------|-----|
| Движется | ✅ при каждом коммите | ❌ прибит к коммиту |
| Назначение | Линия разработки | Метка состояния (версия) |
| Файл | `.git/refs/heads/<имя>` | `.git/refs/tags/<имя>` |
| Уходит при `git push` | Да (при push ветки) | **Нет**, нужен `--tags` |
| Переименовать/подвинуть | Обычно норма | ⚠️ Табу: тег должен быть неизменным |

```bash
cat .git/refs/tags/v1.0.0        # тот же хеш-файл, только в другой папке
```

## 3. ⭐ Lightweight vs annotated

```bash
git tag v1.0.0                              # lightweight: просто указатель на коммит
git tag -a v1.0.0 -m "Первый релиз"         # ⭐ annotated: ОТДЕЛЬНЫЙ объект в базе
```

**Annotated-тег** хранит: автора тега, дату, сообщение, (опционально) GPG-подпись —
и потому пригоден для релизов. **Lightweight** — просто закладка «для себя».

```bash
git cat-file -t v1.0.0        # annotated → tag ; lightweight → commit
git show v1.0.0               # у annotated видно Tagger и сообщение
```

Правило: **для релизов всегда `-a`**. `git describe` по умолчанию видит только
аннотированные теги, а хостинги строят по ним Releases.

## 4. Работа с тегами

```bash
git tag                              # список
git tag -l "v1.*"                    # по маске
git tag -n                           # с сообщениями
git show v1.2.0                      # информация о теге и коммите
git tag -a v1.2.0 -m "release 1.2.0"             # тег на текущий коммит
git tag -a v1.1.0 9a8b7c6 -m "забытый релиз"     # тег на старый коммит
git tag -s v1.2.0 -m "signed"        # подписанный GPG
git tag -v v1.2.0                    # проверить подпись

git push origin v1.2.0               # ⭐ отправить ОДИН тег
git push origin --tags               # отправить все
git push --follow-tags               # push веток + аннотированные теги (удобно)

git tag -d v1.2.0                    # удалить локально
git push origin --delete v1.2.0      # удалить на сервере
git fetch --tags                     # забрать теги с сервера

git checkout v1.2.0                  # ⚠️ detached HEAD — посмотреть состояние релиза
git switch -c hotfix/1.2.1 v1.2.0    # ⭐ ветка от тега — так делают хотфиксы
```

> ⚠️ **Перемещать опубликованный тег нельзя.** У тех, кто уже сделал fetch, останется старый.
> Образ `app:1.2.0`, собранный из старого коммита, разъедется с кодом — классическая
> причина «а у меня работает». Нужна правка — выпускай `v1.2.1`.

## 5. ⭐ SemVer — семантическое версионирование

```text:no-line-numbers
   v  MAJOR . MINOR . PATCH
      │       │       └── исправления, обратно совместимые (v1.4.1 → v1.4.2)
      │       └────────── новая функциональность, совместимая (v1.4.2 → v1.5.0)
      └────────────────── ЛОМАЮЩИЕ изменения (v1.5.0 → v2.0.0)
```

| Изменение | Новая версия |
|-----------|--------------|
| Починили баг в обработке платежей | `1.4.1` → `1.4.2` |
| Добавили эндпоинт `/healthz` | `1.4.2` → `1.5.0` |
| Удалили старый API / сменили формат конфига | `1.5.0` → `2.0.0` |

Дополнительно: предрелизы и метаданные сборки —
`v2.0.0-rc.1`, `v2.0.0-beta.2`, `v1.4.2+build.579`.

**Что считать «ломающим» в инфраструктуре:** несовместимое изменение values Helm-чарта,
удаление переменной окружения, смена формата конфига, миграция БД без обратной совместимости.

### CalVer — альтернатива

`2026.09.1`, `24.04` — версия по дате. Применяют, когда «совместимость» не главный критерий:
Ubuntu, GitLab, внутренние сервисы с непрерывной поставкой.

## 6. `git describe` — версия «на глаз»

```bash
git describe --tags
# v1.4.2-7-gabc1234
#   │     │  └── хеш текущего коммита (g = git)
#   │     └───── 7 коммитов ПОСЛЕ тега
#   └─────────── ближайший аннотированный тег

git describe --tags --always --dirty
# v1.4.2-7-gabc1234-dirty   ← есть незакоммиченные изменения
```

Именно так в CI формируют версии для «не релизных» сборок:
`app:1.4.2-7-gabc1234` — сразу видно, из чего собран образ.

## 7. Теги в CI/CD: от тега до прода

Типичный релизный процесс:

```bash
git switch main && git pull
git tag -a v1.5.0 -m "release 1.5.0: добавлен healthz"
git push origin v1.5.0
```

Дальше работает пайплайн (блок CI/CD):

```yaml
# .gitlab-ci.yml — джоба запускается ТОЛЬКО по тегу
build-release:
  stage: build
  script:
    - docker build -t $CI_REGISTRY_IMAGE:$CI_COMMIT_TAG .
    - docker push   $CI_REGISTRY_IMAGE:$CI_COMMIT_TAG
  rules:
    - if: $CI_COMMIT_TAG

deploy-prod:
  stage: deploy
  script:
    - helm upgrade --install app ./chart --set image.tag=$CI_COMMIT_TAG
  rules:
    - if: $CI_COMMIT_TAG =~ /^v\d+\.\d+\.\d+$/       # только релизные теги, не rc
      when: manual
```

Соответствие «git-тег → тег docker-образа» — базовая практика:
по работающему контейнеру всегда можно найти коммит, из которого он собран.

```text:no-line-numbers
git tag v1.5.0  →  registry/app:1.5.0  →  helm --set image.tag=1.5.0  →  под в кластере
```

⚠️ `latest` как тег образа на проде — антипаттерн: непонятно, что именно запущено,
и откат невозможен.

### GitHub Releases / GitLab Releases

Поверх тега хостинг делает «релиз»: заголовок, changelog, приложенные артефакты.
Генерируют обычно автоматически из сообщений коммитов (Conventional Commits — тема 11):
`semantic-release`, `release-please`, `git-cliff`.

## 8. Как выбрать версию: практическая памятка

```text:no-line-numbers
Изменения только в CI/документации          → тег вообще не нужен
Багфикс, поведение прежнее                  → PATCH  (v1.4.2)
Новая возможность, старое работает          → MINOR  (v1.5.0)
Пользователю/соседнему сервису надо что-то  → MAJOR  (v2.0.0)
менять у себя
Кандидат в релиз перед v2.0.0               → v2.0.0-rc.1
```

Для внутренних инфраструктурных репозиториев (ansible, манифесты) часто хватает
`v<год>.<месяц>.<номер>` или вовсе коммит-хеша — важно, чтобы версия однозначно
указывала на состояние репозитория.

## 💼 Как это в DevOps

- **Тег = единица релиза.** Всё, что уезжает на прод, имеет версию: образ, Helm-чарт
  (`Chart.yaml: version` + `appVersion`), Ansible-роль (`requirements.yml` с версией),
  Terraform-модуль (`?ref=v1.2.0`).
- **Helm-чарт версионируется отдельно от приложения**: `version` — версия чарта,
  `appVersion` — версия приложения. Меняешь только шаблон — бампаешь `version`.
- **Terraform-модули** подключают по тегу: `source = "git::ssh://…//modules/vpc?ref=v1.2.0"` —
  без тега прод может «поехать» при чужом коммите в модуль.
- **Хотфикс прод-версии** делают веткой от тега: `git switch -c hotfix/1.4.3 v1.4.2`,
  фикс → тег `v1.4.3` → релиз, а в `main` изменение приезжает cherry-pick'ом (тема 06).
- Теги защищают (protected tags): право ставить релизные теги есть не у всех —
  это фактически право выкатить прод.
- В инциденте первым делом смотрят: `git describe`, тег образа в кластере
  (`kubectl get deploy -o jsonpath='{..image}'`) и `git log v1.4.1..v1.4.2`.

## 🧠 Что запомнить

1. **Тег — неподвижная метка на коммите**, ветка — подвижный указатель.
2. Для релизов — **annotated (`-a`)**: автор, дата, сообщение, возможна подпись.
3. Теги **не уходят** обычным push: `git push origin <tag>` / `--tags` / `--follow-tags`.
4. **Опубликованный тег не двигают.** Нужна правка — новая версия.
5. **SemVer**: MAJOR — ломающие изменения, MINOR — новая совместимая функциональность,
   PATCH — исправления.
6. `git describe --tags` даёт человекочитаемую версию любого коммита (`v1.4.2-7-gabc1234`).
7. Тег запускает релизный пайплайн: `if: $CI_COMMIT_TAG` → сборка `app:<тег>` → деплой.
8. **Git-тег = тег образа**: по контейнеру на проде всегда находится коммит.
9. `latest` на проде — антипаттерн: нельзя понять, что запущено, и нельзя откатить.
10. Хотфикс делается веткой **от тега**, затем новый PATCH-тег и cherry-pick в `main`.
11. Инфраструктурные зависимости (Terraform-модули, Helm-чарты, Ansible-роли) подключают
    по версии, а не по «последнему состоянию ветки».

### Блок A. Теория

**A1.** ⭐ Чем тег отличается от ветки? Приведи по два сценария использования каждого.

<details><summary>Ответ</summary>

Ветка — подвижный указатель, отмечает линию разработки (`feature/x`, `main`);
тег — неподвижная метка конкретного коммита, отмечает версию (`v1.4.2`).
Ветки: разработка задачи, поддержка релизной линии. Теги: релиз, точка отката,
триггер релизного пайплайна.

</details>

**A2.** ⭐ В чём разница между lightweight и annotated тегом? Какой нужен для релиза и почему?

<details><summary>Ответ</summary>

Lightweight — просто файл-указатель на коммит (как ветка, но неподвижный).
Annotated — полноценный объект в базе git: автор тега, дата, сообщение, возможна GPG-подпись.
Для релизов нужен annotated: он несёт метаданные, виден `git describe` по умолчанию
и на его основе хостинги делают Releases.

</details>

**A3.** Как определить тип существующего тега?

<details><summary>Ответ</summary>

`git cat-file -t <тег>`: `tag` — annotated, `commit` — lightweight.
Ещё признак: у annotated в `git show` есть строки `Tagger`/`tag <имя>`.

</details>

**A4.** Уходят ли теги на сервер при `git push`? Три способа их отправить.

<details><summary>Ответ</summary>

Нет, обычный push отправляет только ветки. Способы: `git push origin <tag>`,
`git push origin --tags`, `git push --follow-tags` (ветки + аннотированные теги).

</details>

**A5.** Почему нельзя двигать опубликованный тег? Что произойдёт в CI/CD?

<details><summary>Ответ</summary>

Потому что у тех, кто уже забрал тег, останется старое значение, а артефакты,
собранные из старого коммита, продолжат называться той же версией: `app:1.4.0` в registry
перестанет соответствовать коду. Возникает классическое «у меня работает», откаты
становятся недостоверными. Правильно — выпустить новую версию.

</details>

**A6.** ⭐ Разбери SemVer: что меняет MAJOR, MINOR, PATCH? Приведи по примеру из мира DevOps.

<details><summary>Ответ</summary>

MAJOR — несовместимые изменения (удалён эндпоинт, изменён формат конфига,
переименована обязательная переменная в Helm values); MINOR — новая функциональность
с сохранением совместимости (добавлен `/healthz`, новый необязательный параметр);
PATCH — исправления без изменения контракта (починили утечку, обновили зависимость).

</details>

**A7.** Что такое предрелизные версии и когда их используют?

<details><summary>Ответ</summary>

`v2.0.0-rc.1`, `-beta.2`, `-alpha.1` — версии для тестирования до релиза.
По SemVer предрелиз «младше» финальной версии. Используют, чтобы выкатить на stage
и проверить перед общим релизом; пайплайн обычно отличает их регуляркой.

</details>

**A8.** Что такое CalVer и в каких проектах он уместнее SemVer?

<details><summary>Ответ</summary>

Календарное версионирование (`2026.09.1`, `24.04`). Уместно там, где важнее дата,
а не совместимость: дистрибутивы, внутренние сервисы с непрерывной поставкой, инфраструктурные
репозитории.

</details>

**A9.** ⭐ Что показывает `git describe --tags` и как читать `v1.4.2-7-gabc1234-dirty`?

<details><summary>Ответ</summary>

Ближайший аннотированный тег + число коммитов после него + сокращённый хеш
текущего коммита. `v1.4.2-7-gabc1234-dirty`: 7 коммитов после `v1.4.2`, коммит `abc1234`,
`-dirty` — в рабочем каталоге есть незакоммиченные изменения.

</details>

**A10.** Как посмотреть, что изменилось между двумя релизами?

<details><summary>Ответ</summary>

`git log --oneline v1.4.1..v1.4.2`, `git diff --stat v1.4.1 v1.4.2`,
`git shortlog v1.4.1..v1.4.2` (по авторам) — основа для CHANGELOG.

</details>

**A11.** Как правильно сделать хотфикс для версии, которая сейчас на проде?

<details><summary>Ответ</summary>

Создать ветку **от тега** прод-версии (`git switch -c hotfix/1.4.3 v1.4.2`),
внести минимальный фикс, поставить тег `v1.4.3`, выкатить; затем перенести фикс в `main`
через cherry-pick или merge, чтобы он не потерялся.

</details>

**A12.** Почему `latest` как тег docker-образа на проде — антипаттерн?

<details><summary>Ответ</summary>

По `latest` невозможно понять, какая версия запущена; рестарт пода может подтянуть
другой образ; нет предсказуемого отката; ломается воспроизводимость инцидента.

</details>

**A13.** Чем `version` отличается от `appVersion` в Helm-чарте?

<details><summary>Ответ</summary>

`version` — версия самого чарта (шаблонов), `appVersion` — версия приложения,
которое чарт разворачивает. Изменил только шаблоны — повышаешь `version`, приложение
осталось прежним.

</details>

**A14.** Зачем Terraform-модули подключают по `?ref=v1.2.0`, а не по ветке?

<details><summary>Ответ</summary>

Чтобы прод зависел от зафиксированного состояния модуля. При `?ref=main`
любой чужой коммит в модуле меняет инфраструктуру при следующем `terraform apply` —
изменение приезжает незаметно и не проходит ревью в твоём репозитории.

</details>

**A15.** Что такое protected tags и зачем они нужны?

<details><summary>Ответ</summary>

Правило хостинга, ограничивающее, кто может создавать/удалять теги по маске
(например, `v*`). Поскольку тег запускает релиз и деплой, право ставить релизный тег —
это фактически право выкатить прод.

</details>

**A16.** Ты поставил тег не на тот коммит и уже запушил. Что делать?

<details><summary>Ответ</summary>

Правильнее выпустить новый тег на верный коммит и не трогать старый.
Если тег только что запушен и никто не успел им воспользоваться (и это согласовано):
`git tag -d v1.4.0`, `git push origin --delete v1.4.0`, создать заново, запушить —
и предупредить команду, чтобы сделали `git fetch --tags --prune-tags`.

</details>

### Блок B. «Что делает команда»

```bash
B1.  git tag

B3.  git tag -n
```

### Блок D. Инциденты

**D1.** Пайплайн релиза не запустился после `git push`. Тег создан локально. Что забыли?

<details><summary>Ответ</summary>

Тег не отправлен на сервер: нужен `git push origin <tag>` (или `--follow-tags`).
CI реагирует на события в удалённом репозитории, локальный тег ему невидим.

</details>

**D2.** Разработчик передвинул тег `v1.4.0` на новый коммит и сделал `push --force`.
Что теперь не так с образом `app:1.4.0` в registry и как это проявится?

<details><summary>Ответ</summary>

В registry уже лежит образ `app:1.4.0`, собранный из старого коммита. Теперь
git-тег указывает на другой код: по одному имени версии существуют два разных состояния.
Проявится как «на проде поведение не то, что в коде», недостоверный откат и невозможность
воспроизвести инцидент.

</details>

**D3.** `git describe` пишет `fatal: No names found, cannot describe anything`. Причины (две).

<details><summary>Ответ</summary>

(1) В репозитории нет аннотированных тегов (или вообще тегов) — лечится `--always`
или созданием тега; (2) клон был shallow/без тегов (`--depth 1`, `--no-tags`) — нужно
`git fetch --tags --unshallow`.

</details>

**D4.** На проде работает `app:latest`. Приложение сломалось, нужен откат. В чём проблема?

<details><summary>Ответ</summary>

Неизвестно, какая версия сейчас работает и на какую откатываться; повторный
`docker pull latest` может дать другой образ. Лечение: тегировать образы версиями,
фиксировать `image.tag` в манифесте/Helm values, откат — на конкретную версию.

</details>

**D5.** В репозитории 200 тегов вида `build-2024-05-13-1`, нужно найти версию,
с которой начался баг. Как искать?

<details><summary>Ответ</summary>

`git log --oneline --decorate --tags`, `git tag --contains <коммит>` и особенно
`git bisect` (тема 12) между «хорошим» и «плохим» тегами: `git bisect start <плохой> <хороший>`.

</details>

**D6.** После `git clone --depth 1` в CI `git describe` не работает. Почему и как чинить?

<details><summary>Ответ</summary>

Shallow-клон не содержит истории и тегов. Решение: `fetch-depth: 0` (GitHub Actions)
/ `GIT_DEPTH: 0` (GitLab), либо `git fetch --tags --unshallow` перед `describe`.

</details>

**D7.** Тег `v2.0.0` стоит на коммите, который не попал в `main` (ветка была удалена).
Чем это опасно?

<details><summary>Ответ</summary>

Коммит достижим только через тег: по `main` его не видно, история релиза непонятна,
а изменения из него отсутствуют в основной линии. Прод может работать на коде, которого
нет в `main` — при следующем релизе фикс «пропадёт».

</details>

**D8.** Хотфикс сделали прямо в `main`, тег `v1.4.3` поставили там же, а на проде
живёт `v1.4.2` + не выпущенные в main изменения. Как выпустить фикс, не выкатывая лишнего?

<details><summary>Ответ</summary>

Нельзя выкатывать `main` целиком: собрать хотфикс от тега прод-версии
(`git switch -c hotfix/1.4.3 v1.4.2`), перенести туда только нужный коммит (`cherry-pick`),
поставить тег `v1.4.3`, выкатить его; фикс уже есть в main.

</details>

**D9.** Два инженера одновременно выпустили `v1.6.0` с разных коммитов.
Что увидит второй при push и как разрулить?

<details><summary>Ответ</summary>

Второй получит отказ при push (`tag already exists` / non-fast-forward для тега).
Разруливается по договорённости: один выпускает `v1.6.0`, второй — `v1.6.1`; двигать
чужой тег нельзя. На будущее — protected tags и релиз через пайплайн, а не вручную.

</details>

**D10.** Terraform-модуль подключён как `?ref=main`. Ночью прод «поехал» без единого
коммита в инфраструктурном репозитории. Объясни, что случилось.

<details><summary>Ответ</summary>

Модуль подключён по ветке: кто-то влил коммит в `main` модуля, и при следующем
`terraform apply` (например, ночным пайплайном) подтянулась новая версия модуля.
Лечение: подключать по тегу `?ref=v1.2.0` и обновлять версию явным коммитом.

</details>

### Блок E. Вопросы с собеседования

**1.** ⭐ Что такое тег в git и чем он отличается от ветки?

<details><summary>Ответ</summary>

Неподвижная метка на конкретном коммите, обозначающая версию; ветка — подвижный
указатель, который двигается с каждым коммитом.

</details>

**2.** Чем annotated тег отличается от lightweight?

<details><summary>Ответ</summary>

Annotated — отдельный объект с автором, датой, сообщением и возможной подписью;
lightweight — просто ссылка на коммит. Для релизов используют annotated.

</details>

**3.** Как отправить теги на сервер?

<details><summary>Ответ</summary>

`git push origin <tag>`, `git push origin --tags` или `git push --follow-tags`;
обычный push теги не отправляет.

</details>

**4.** Что такое SemVer? Расшифруй MAJOR.MINOR.PATCH.

<details><summary>Ответ</summary>

Семантическое версионирование `MAJOR.MINOR.PATCH`: ломающие изменения / новая
совместимая функциональность / исправления.

</details>

**5.** Когда повышают MAJOR?

<details><summary>Ответ</summary>

Когда изменение несовместимо: удалён или изменён контракт (API, формат конфига,
обязательные параметры) и потребителю нужно что-то менять у себя.

</details>

**6.** Что делает `git describe`?

<details><summary>Ответ</summary>

Показывает ближайший аннотированный тег, количество коммитов после него и хеш
текущего коммита — человекочитаемую «версию» любого состояния репозитория.

</details>

**7.** Как сделать хотфикс для релиза, который уже на проде?

<details><summary>Ответ</summary>

Создать ветку от тега прод-версии, внести минимальный фикс, поставить новый PATCH-тег,
выкатить, затем перенести фикс в `main` (cherry-pick/merge).

</details>

**8.** Как связаны git-теги и теги docker-образов?

<details><summary>Ответ</summary>

Git-тег — источник версии для сборки: пайплайн собирает `app:<версия>` и деплоит
именно этот тег, поэтому по контейнеру на проде находится коммит.

</details>

**9.** Можно ли передвинуть тег? Чем это грозит?

<details><summary>Ответ</summary>

Технически можно, практически — нельзя: у забравших останется старое значение,
а артефакты с той же версией будут собраны из другого кода. Нужна новая версия.

</details>

**10.** Как посмотреть изменения между двумя версиями?

<details><summary>Ответ</summary>

`git log v1.0.0..v1.1.0`, `git diff v1.0.0 v1.1.0`, `git shortlog v1.0.0..v1.1.0`.

</details>
