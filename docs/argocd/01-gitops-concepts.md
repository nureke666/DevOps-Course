## 🗺️ Что такое GitOps

```text:no-line-numbers
        ┌──────────────────────────────────────────────────────────┐
        │  GIT = ЕДИНСТВЕННЫЙ ИСТОЧНИК ПРАВДЫ                      │
        │  манифесты, чарты, значения, конфигурация окружений      │
        └───────────────────────────┬──────────────────────────────┘
                                    │ агент постоянно сравнивает
                                    ▼
        ┌──────────────────────────────────────────────────────────┐
        │  КЛАСТЕР                                                 │
        │  фактическое состояние ──► расходится? ──► привести к git│
        └──────────────────────────────────────────────────────────┘

 Изменение инфраструктуры = коммит в git.
 Откат = git revert.
 Аудит = git log.
```

## 1. Четыре принципа GitOps

| Принцип | Смысл |
|---------|-------|
| **1. Декларативность** | Система описана декларативно (YAML-манифесты, чарты), а не скриптами |
| **2. Версионируемость и неизменяемость** | Желаемое состояние хранится в git: история, ревью, откат |
| **3. Автоматическое применение** | Агент сам подтягивает изменения — без ручного `kubectl apply` |
| **4. Непрерывная сверка** | Агент постоянно сравнивает факт и желаемое и устраняет расхождения ⭐ |

Четвёртый принцип — самое важное отличие от «просто CI/CD с `kubectl apply`»:
GitOps не только применяет изменения, но и **постоянно следит**, чтобы кластер
не отклонялся от git.

## 2. ⭐ Push vs Pull

```text:no-line-numbers
 PUSH (классический CI/CD)                 PULL (GitOps)
 ────────────────────────                  ─────────────
 git push → CI собрал → CI применил        git push → CI обновил тег в git
                                            → агент в кластере заметил и применил

 CI хранит kubeconfig/токен прод-кластера   у CI нет доступа к кластеру ⭐
 доступ «снаружи внутрь»                    кластер сам ходит в git «изнутри наружу»
 дрейф не отслеживается                     дрейф обнаруживается и лечится
 откат = снова прогнать пайплайн            откат = git revert
```

| Критерий | Push | Pull (GitOps) |
|----------|------|---------------|
| Доступ к кластеру у CI | Нужен | ⭐ Не нужен |
| Отслеживание дрейфа | Нет | Да, непрерывно |
| Аудит изменений | Логи CI | История git |
| Мультикластер | Сложно (много кредов) | Естественно (агент в каждом кластере) |
| Порог входа | Ниже | Выше (нужен Kubernetes и дисциплина) |
| Подходит для не-k8s | Да | Ограниченно |

## 3. Что даёт GitOps на практике

| Выгода | Как проявляется |
|--------|-----------------|
| Прозрачность | Что в проде — видно в git, а не «надо посмотреть в кластере» |
| Быстрый откат | `git revert` + автоматическая синхронизация |
| Безопасность | Прод-креды не разъезжаются по пайплайнам; доступ к кластеру ограничен |
| Воспроизводимость | Кластер восстанавливается «с нуля» из репозитория |
| Онбординг | Новый инженер читает репозиторий, а не расспрашивает коллег |
| Дисциплина | Все изменения проходят ревью, ручные правки «зарастают» обратно |
| Мультикластер | Один подход для dev/stage/prod и нескольких регионов |

И честно о цене:
```text:no-line-numbers
⚠️ GitOps не бесплатен:
 • нужен Kubernetes (для классического Argo CD/Flux)
 • нужна дисциплина: «поправить руками в кластере» перестаёт работать
 • секреты требуют отдельного решения (SOPS/Sealed Secrets/External Secrets)
 • отладка усложняется: между «нажал» и «применилось» появляется агент
 • ещё один компонент, который надо обновлять и мониторить
```

## 4. Из чего состоит GitOps-процесс

```text:no-line-numbers
 РЕПОЗИТОРИЙ КОДА                    РЕПОЗИТОРИЙ КОНФИГУРАЦИИ (манифесты)
 ────────────────                    ────────────────────────────────────
 src/, Dockerfile                    apps/myapp/{deployment,service}.yaml
 .gitlab-ci.yml                      или Helm-чарт + values-prod.yaml
        │                                        ▲
        │ CI: сборка и тесты                     │ CI обновляет тег образа
        ▼                                        │ (или image updater)
   образ в registry ──────────────────────────────┘
                                                 │
                                                 ▼
                                          Argo CD в кластере
                                           применяет изменения
```

⭐ Практически всегда разделяют **репозиторий приложения** и **репозиторий конфигурации**:
иначе каждый коммит кода будет вызывать деплой, а история конфигурации утонет
в истории разработки.

Как обновляется тег образа:
| Способ | Комментарий |
|--------|-------------|
| CI делает коммит в конфиг-репозиторий | ⭐ Прозрачно, видно в истории |
| Argo CD Image Updater | Сам следит за новыми тегами в registry |
| Обновление values в Helm-чарте | Тот же коммит, но через чарт |

## 5. Инструменты

| | **Argo CD** | **Flux CD** |
|---|-------------|-------------|
| Интерфейс | ⭐ Богатый веб-UI, видно дерево ресурсов и diff | CLI и CRD, UI отдельным проектом |
| Модель | `Application` CRD | Набор контроллеров (source, kustomize, helm) |
| Мультиарендность | Projects, RBAC, SSO | Через namespace и RBAC |
| Управление многими приложениями | App of Apps, ApplicationSet | Kustomization + зависимости |
| Порог входа | Ниже (наглядно) | Чуть выше, но «более kubernetes-native» |
| Популярность | ⭐ Очень высокая | Высокая |

Рядом обычно встречаются: **Argo Rollouts** (canary/blue-green),
**Argo Workflows** (пайплайны в k8s), **Argo Events**.

## 6. GitOps и Terraform: не путать

```text:no-line-numbers
 TERRAFORM ──► создаёт КЛАСТЕР и облачную инфраструктуру (VPC, ноды, managed-БД)
 ARGO CD   ──► управляет тем, что ВНУТРИ кластера (Deployment, Service, Ingress, Helm)

 Типовая схема:
   Terraform: кластер + сеть + БД  →  Argo CD: приложения и платформенные компоненты
```
Существуют попытки управлять облаком из кластера (Crossplane, Terraform-контроллеры),
но базовое разделение именно такое — и его спрашивают на собеседовании.

## 7. Ограничения и типовые заблуждения

| Заблуждение | Реальность |
|-------------|------------|
| «GitOps = CI/CD» | GitOps — про доставку и непрерывную сверку состояния, CI — про сборку и тесты |
| «Теперь не нужен CI» | Нужен: собрать образ, прогнать тесты, обновить тег в конфиге |
| «Секреты тоже просто в git» | Только зашифрованные (SOPS/Sealed Secrets) или через External Secrets |
| «Argo сам всё откатит» | Откат — это коммит в git; автоматический rollback настраивается отдельно |
| «Ручные правки — быстрее» | При `selfHeal` они будут затёрты; при его отсутствии — создадут дрейф |
| «GitOps только для приложений» | Так же управляют платформой: ingress, мониторинг, cert-manager |
| «Достаточно поставить Argo» | Нужны структура репозиториев, процесс ревью и работа с секретами |

---

## 💼 Как это в DevOps

- GitOps — ответ на вопрос «как вы деплоите в Kubernetes» в современных командах;
  Argo CD чаще всего и есть этот ответ.
- Безопасность: прод-креды не раздаются пайплайнам, доступ в кластер сужается
  до агента и людей с ролями — это часто главный аргумент для внедрения.
- Платформенные компоненты (ingress-controller, cert-manager, мониторинг, логирование)
  тоже разворачивают через Argo — тогда кластер целиком описан в git.
- Типичный инцидент: «в кластере что-то поправили руками, и оно откатилось» —
  это не баг, а работающий `selfHeal`.
- На собеседовании достаточно уверенно объяснить pull-модель, источник правды,
  Application, App of Apps и работу с секретами — роадмап прямо говорит,
  что углублённо изучать по желанию.

## 📌 Шпаргалка

| Термин | Одной строкой |
|--------|---------------|
| GitOps | Git — источник правды, агент непрерывно приводит систему к нему |
| Pull-модель | Кластер сам забирает изменения из git |
| Источник правды | Репозиторий с манифестами/чартами |
| Дрейф | Расхождение кластера и git |
| Сверка (reconciliation) | Постоянное сравнение факта и желаемого |
| Repo приложения / repo конфигурации | Код и манифесты разделяют |
| Argo CD | GitOps-агент с UI и CRD `Application` |
| Flux | Альтернативный GitOps-инструмент |
| Argo Rollouts | Canary/blue-green деплой |
| Откат | `git revert` + синхронизация |

## 🧠 Что запомнить

1. GitOps — это декларативность, git как источник правды, автоматическое применение
   и непрерывная сверка.
2. ⭐ Pull-модель: агент внутри кластера сам забирает изменения, у CI нет доступа
   к прод-кластеру.
3. Главное отличие от обычного CI/CD — непрерывное устранение дрейфа, а не разовое
   применение.
4. Репозиторий кода и репозиторий конфигурации разделяют.
5. CI никуда не исчезает: он собирает образ и обновляет тег в конфиг-репозитории.
6. Откат — это `git revert`, а не ручные действия в кластере.
7. Секреты в git кладут только зашифрованными либо подтягивают из внешнего хранилища.
8. Argo CD и Flux решают одну задачу; Argo популярен за счёт UI и `Application`.
9. Terraform создаёт кластер и облачную инфраструктуру, Argo CD управляет содержимым
   кластера.
10. GitOps требует дисциплины: «поправить руками» перестаёт быть допустимым способом
    работы.

### Блок A. Теория

**A1.** Сформулируй четыре принципа GitOps.

<details><summary>Ответ</summary>

Декларативное описание системы; хранение желаемого состояния в git
с версионированием; автоматическое применение изменений; непрерывная сверка
фактического состояния с желаемым.

</details>

**A2.** Какой из принципов сильнее всего отличает GitOps от «CI с `kubectl apply`»?

<details><summary>Ответ</summary>

Четвёртый — непрерывная сверка: обычный CI применяет изменения один раз,
GitOps постоянно следит и устраняет расхождения.

</details>

**A3.** ⭐ Объясни разницу push- и pull-модели деплоя.

<details><summary>Ответ</summary>

В push CI сам подключается к кластеру и применяет изменения. В pull агент
внутри кластера отслеживает git и применяет изменения сам; наружу кластер не открывается.

</details>

**A4.** Почему в pull-модели безопаснее с точки зрения доступа к кластеру?

<details><summary>Ответ</summary>

Не нужно раздавать креды кластера пайплайнам и внешним системам: доступ
инициируется изнутри кластера, поверхность атаки меньше, а права агента ограничены.

</details>

**A5.** Что такое дрейф и как GitOps с ним работает?

<details><summary>Ответ</summary>

Расхождение фактического состояния кластера с описанным в git. GitOps его
обнаруживает (OutOfSync) и, при включённом self-heal, автоматически устраняет.

</details>

**A6.** Почему разделяют репозиторий кода и репозиторий конфигурации?

<details><summary>Ответ</summary>

Чтобы каждый коммит кода не вызывал деплой, чтобы история конфигурации была
читаемой, чтобы права и ревью были разными, и чтобы одну конфигурацию можно было
применять к нескольким окружениям.

</details>

**A7.** Какие есть способы обновления тега образа в конфиг-репозитории?

<details><summary>Ответ</summary>

Коммит из CI в конфиг-репозиторий; Argo CD Image Updater; обновление values
Helm-чарта (тоже коммит).

</details>

**A8.** Исчезает ли CI при переходе на GitOps? Что он делает?

<details><summary>Ответ</summary>

Не исчезает: CI собирает и тестирует образ, публикует его в registry
и обновляет тег в конфигурации. Деплоем занимается агент.

</details>

**A9.** Как выглядит откат в GitOps?

<details><summary>Ответ</summary>

Возврат предыдущего состояния в git (`git revert`) с последующей автоматической
синхронизацией; в Argo есть и кнопка отката на предыдущую синхронизацию.

</details>

**A10.** Назови пять преимуществ GitOps и три его цены.

<details><summary>Ответ</summary>

Плюсы: прозрачность, быстрый откат, безопасность доступа, воспроизводимость,
аудит, дисциплина, удобство мультикластера. Цена: требуется Kubernetes, нужна дисциплина
(нельзя править руками), отдельное решение для секретов, ещё один компонент
в эксплуатации, усложнённая отладка.

</details>

**A11.** Чем Argo CD отличается от Flux?

<details><summary>Ответ</summary>

Argo CD — единый сервис с богатым UI и CRD `Application`, наглядно показывает
diff и здоровье. Flux — набор контроллеров, более «kubernetes-native», UI отдельно.
Обе реализуют GitOps; выбор чаще по удобству команды.

</details>

**A12.** Как соотносятся Terraform и Argo CD?

<details><summary>Ответ</summary>

Terraform создаёт кластер и облачную инфраструктуру, Argo CD управляет
ресурсами внутри кластера.

</details>

**A13.** Можно ли хранить секреты в git при GitOps? Как это делают правильно?

<details><summary>Ответ</summary>

Открытыми — нельзя. Правильно: шифрование в git (SOPS, Sealed Secrets)
или получение секретов из внешнего хранилища через External Secrets Operator
(Vault, облачные сервисы).

</details>

**A14.** Какие компоненты платформы имеет смысл разворачивать через Argo?

<details><summary>Ответ</summary>

Ingress-контроллер, cert-manager, мониторинг и логирование, политики,
операторы, сетевые компоненты — тогда кластер целиком описан в git.

</details>

**A15.** Что такое Argo Rollouts и какую задачу он решает?

<details><summary>Ответ</summary>

Контроллер прогрессивных стратегий деплоя: canary и blue-green
с автоматическим анализом метрик и откатом.

</details>

### Блок C. Практика

#### C1. 🔑 Подготовка стенда
1. Подними kind/minikube.
2. Установи ArgoCD, получи пароль, зайди в UI.
3. Осмотрись: какие объекты появились в namespace `argocd`.

#### C2. Репозиторий конфигурации
Создай git-репозиторий со структурой:
```text:no-line-numbers
apps/
  demo/
    deployment.yaml
    service.yaml
```
и простым nginx-приложением.

#### C3. Push vs pull на практике
1. Задеплой приложение вручную `kubectl apply -f` (push-модель).
2. Удали его и задеплой через ArgoCD (pull-модель, тема 03).
3. Запиши разницу в ощущениях и в том, где хранится «правда».

#### C4. Дрейф своими руками
1. После деплоя через Argo измени число реплик `kubectl scale`.
2. Посмотри статус приложения в UI.
3. Включи self-heal и повтори — что произошло?

<details><summary>Ответ</summary>

Без self-heal приложение останется OutOfSync; с self-heal Argo вернёт число
реплик к значению из git.

</details>

#### C5. Откат через git
1. Внеси изменение в манифест (например, сломай образ), закоммить.
2. Дождись синхронизации и увидь проблему.
3. Сделай `git revert` и проверь, что состояние восстановилось.

<details><summary>Ответ</summary>

После revert Argo синхронизирует состояние обратно — это и есть «откат одной
командой git».

</details>

#### C6. Разделение репозиториев
Разнеси код демо-приложения и манифесты по двум репозиториям.
Опиши, как CI должен обновлять тег образа.

#### C7. Сравнение инструментов
Прочитай документацию Flux (обзорно) и составь таблицу отличий от Argo CD
по пяти критериям. Реши, что выбрал бы для своего проекта и почему.

<details><summary>Ответ</summary>

Полезно зафиксировать, что обе системы решают одну задачу, и выбор
не «технический спор», а вопрос удобства и экспертизы команды.

</details>

#### C8. Границы ответственности
Нарисуй схему: что делает Terraform, что делает CI, что делает Argo CD
на твоём (реальном или воображаемом) проекте.

#### C9. Риски
Выпиши пять вещей, которые сломаются при переходе на GitOps в команде,
которая привыкла править кластер руками. Предложи, как их смягчить.

<details><summary>Ответ</summary>

Типичные болевые точки: привычка `kubectl edit`, отсутствие ревью,
секреты, срочные хотфиксы, недоверие к автоматике.

</details>

### Блок D. Инциденты

**D1.** Инженер поправил ConfigMap в кластере, через минуту изменения исчезли. Почему?

<details><summary>Ответ</summary>

Включён selfHeal: Argo вернул состояние к описанному в git.

</details>

**D2.** Приложение в состоянии OutOfSync уже сутки, никто не заметил. Что настроить?

<details><summary>Ответ</summary>

Мониторинг и алерты на статус приложений (`argocd_app_info`), уведомления
(Argo CD Notifications) в чат, дашборд состояния синхронизаций.

</details>

**D3.** В git закоммитили секрет открытым текстом. Действия?

<details><summary>Ответ</summary>

Считать секрет скомпрометированным: ротировать, удалить из истории,
внедрить SOPS/Sealed Secrets/ESO, добавить проверку секретов в CI (gitleaks).

</details>

**D4.** CI обновил тег образа, но в кластере старая версия. Где искать причину?

<details><summary>Ответ</summary>

Не закоммичен тег (или коммит не в ту ветку/путь), Argo смотрит другой путь/ревизию,
приложение не синхронизировано (нет auto-sync), ошибка рендеринга чарта,
образ не собрался/не запушен, кэш образа и `imagePullPolicy`.

</details>

**D5.** Прод «уехал» относительно git после ручного хотфикса ночью.
Как правильно было поступить?

<details><summary>Ответ</summary>

Внести изменение в git (даже срочное) и дать Argo применить; если правили руками,
то сразу после инцидента отразить изменение в репозитории, иначе оно будет потеряно.

</details>

**D6.** Argo CD упал. Что происходит с приложениями в кластере?

<details><summary>Ответ</summary>

Приложения продолжают работать: Argo нужен для синхронизации, а не для работы
нагрузок. Пока он лежит, не применяются новые изменения и не устраняется дрейф.

</details>

**D7.** Нужно срочно откатить релиз, а git-репозиторий недоступен. Варианты?

<details><summary>Ответ</summary>

Откатить через Argo (история синхронизаций) или применить предыдущие манифесты
вручную, зафиксировав, что после восстановления git состояние надо привести в соответствие.

</details>

**D8.** Команда жалуется: «раньше деплоили за 2 минуты, теперь дольше». Что ответишь?

<details><summary>Ответ</summary>

GitOps добавляет ревью и шаг синхронизации, зато даёт аудит, откат и защиту
от ошибок; скорость решается автоматизацией (auto-sync, корректные интервалы,
webhook вместо опроса).

</details>

**D9.** Разработчики просят доступ к проду «чтобы быстро чинить». Как выстроить процесс?

<details><summary>Ответ</summary>

Доступ на чтение + процесс быстрых MR с ускоренным ревью, отдельные права
для инцидентов («break glass» с обязательным постмортемом), self-service через
шаблоны и ApplicationSet.

</details>

**D10.** После восстановления кластера с нуля часть компонентов отсутствует. Почему
GitOps должен был это предотвратить и что упущено?

<details><summary>Ответ</summary>

Часть компонентов ставилась вручную и не описана в git. Для полной
воспроизводимости всё, включая платформенные компоненты, должно лежать в репозитории.

</details>

### Блок E. Вопросы с собеседования

**1.** Что такое GitOps?

<details><summary>Ответ</summary>

Подход, при котором git — источник правды, а агент непрерывно приводит систему
к описанному состоянию.

</details>

**2.** Чем pull-модель отличается от push?

<details><summary>Ответ</summary>

В pull агент внутри кластера сам забирает изменения; в push внешняя система
применяет их, имея доступ к кластеру.

</details>

**3.** Почему GitOps считают более безопасным?

<details><summary>Ответ</summary>

Потому что кредов кластера нет у внешних систем, доступ инициируется изнутри,
а все изменения проходят через ревью в git.

</details>

**4.** Что такое дрейф и как с ним борется GitOps?

<details><summary>Ответ</summary>

Дрейф — расхождение факта и git; GitOps его обнаруживает и может автоматически
устранять (self-heal).

</details>

**5.** Исчезает ли CI при GitOps?

<details><summary>Ответ</summary>

Нет: CI собирает, тестирует и публикует образ, обновляет тег в конфигурации.

</details>

**6.** Как делается откат?

<details><summary>Ответ</summary>

Через `git revert` (или откат на предыдущую синхронизацию в Argo).

</details>

**7.** Чем Argo CD отличается от Flux?

<details><summary>Ответ</summary>

Argo — сервис с UI и CRD `Application`; Flux — набор контроллеров без встроенного UI.

</details>

**8.** Как хранят секреты при GitOps?

<details><summary>Ответ</summary>

Зашифрованными (SOPS, Sealed Secrets) или через External Secrets из Vault/облака.

</details>

**9.** Как соотносятся Terraform и Argo CD?

<details><summary>Ответ</summary>

Terraform — кластер и облако, Argo CD — содержимое кластера.

</details>

**10.** Какие минусы у GitOps?

<details><summary>Ответ</summary>

Нужен Kubernetes, дисциплина, решение для секретов, дополнительный компонент
и более сложная отладка.

</details>
