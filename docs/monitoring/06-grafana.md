# 06. Grafana: источники, дашборды, переменные

> Роадмап → Мониторинг → *«Grafana (Визуализация, дашборды): источники, дашборды, переменные»*.
>
> **После темы ты умеешь:** подключить источники данных, собрать полезный дашборд,
> сделать его универсальным через переменные и хранить всё в git через provisioning.

---

## 🗺️ Место Grafana в стеке

```text:no-line-numbers
 Prometheus ─┐
 Loki ───────┤
 PostgreSQL ─┼──► GRAFANA ──► дашборды, Explore, алерты, отчёты
 Elastic ────┤     (только читает; своих данных не хранит,
 ClickHouse ─┘      кроме настроек и дашбордов)
```

Grafana **не хранит метрики**. Она умеет ходить в десятки источников и рисовать
результаты их запросов. Собственная база (SQLite/PostgreSQL) нужна ей только для
дашбордов, пользователей и настроек.

## 1. Источники данных (Data sources)

```yaml
# provisioning/datasources/datasources.yml — так делают в проде, а не руками в UI
apiVersion: 1
datasources:
  - name: Prometheus
    type: prometheus
    access: proxy               # Grafana сама ходит в источник (не браузер пользователя)
    url: http://prometheus:9090
    isDefault: true
    jsonData:
      timeInterval: 15s         # == scrape_interval, влияет на $__rate_interval

  - name: Loki
    type: loki
    access: proxy
    url: http://loki:3100

  - name: PostgreSQL
    type: postgres
    url: db:5432
    user: grafana_ro
    secureJsonData:
      password: ${PG_PASSWORD}   # из переменной окружения, не в открытом виде
    jsonData:
      database: shop
      sslmode: require
```

| Режим доступа | Смысл |
|---------------|-------|
| `proxy` | ⭐ Запрос идёт Grafana → источник. Источник не нужно публиковать наружу |
| `direct`/`browser` | Запрос идёт из браузера пользователя. Почти всегда не нужен |

## 2. Дашборд: панели и запросы

```text:no-line-numbers
Дашборд
└── Ряды (rows) — логические блоки: "Обзор", "Приложение", "База"
    └── Панели (panels)
        ├── запросы (A, B, C…) к источнику
        ├── тип визуализации (Time series, Stat, Gauge, Table, Bar, Heatmap, Logs)
        ├── единицы (seconds, bytes, percent) и пороги (thresholds)
        └── легенда, ось, наложения
```

| Тип панели | Когда |
|------------|-------|
| **Time series** | Основной график: динамика метрик |
| **Stat** | Одно число: текущий RPS, аптайм, число подов |
| **Gauge** | Процент с порогами: диск, память |
| **Bar gauge** | Сравнение по категориям: топ инстансов |
| **Table** | Списки: таргеты, топ запросов |
| **Heatmap** | Распределение (гистограммы latency) |
| **Logs** | Логи из Loki рядом с метриками |
| **State timeline** | Состояния во времени (up/down) |

Практические мелочи, которые отличают рабочий дашборд от красивого:
```text:no-line-numbers
• Единицы измерения задают ВСЕГДА (иначе «0.85» вместо «85%» и «1.2e9» вместо «1.2 ГБ»)
• Легенда: {{instance}} вместо полного набора лейблов
• Min/Max по оси Y для процентов: 0..100
• Пороги (thresholds) = те же значения, что в алертах
• $__rate_interval вместо жёсткого [5m] — подстраивается под масштаб графика
```

```text:no-line-numbers
# в панели Grafana
sum by (instance) (rate(node_cpu_seconds_total{mode!="idle", instance=~"$instance"}[$__rate_interval]))
```

Полезные встроенные переменные: `$__rate_interval`, `$__interval`, `$__range`,
`$__from`/`$__to`, `$__timeFilter()` (для SQL-источников).

## 3. Переменные (variables) — главное, что делает дашборд универсальным

```text:no-line-numbers
БЕЗ переменных                        С переменными
20 одинаковых дашбордов               1 дашборд + выпадающие списки
(по одному на сервис)                 [env: prod ▾] [instance: all ▾] [job: api ▾]
```

| Тип переменной | Как задаётся | Пример |
|----------------|--------------|--------|
| **Query** | ⭐ Запрос к источнику | `label_values(up, instance)` |
| **Custom** | Список вручную | `prod,stage,dev` |
| **Constant** | Фиксированное значение | `cluster1` |
| **Interval** | Набор интервалов | `1m,5m,15m,1h` |
| **Data source** | Выбор источника | Переключение между кластерами |
| **Text box** | Ввод руками | Фильтр по пути |
| **Ad hoc filters** | Произвольные фильтры по лейблам | Быстрый дебаг |

```text:no-line-numbers
# типичные query-переменные для Prometheus
label_values(up, job)                                   # список job'ов
label_values(up{job="$job"}, instance)                  # инстансы выбранного job
label_values(node_filesystem_avail_bytes{instance="$instance"}, mountpoint)
query_result(count by (cluster) (up))                   # когда нужен результат запроса
```

Использование в запросах:
```text:no-line-numbers
up{job="$job", instance=~"$instance"}     # для multi-value ОБЯЗАТЕЛЬНО =~ и $instance
```
| Опция переменной | Что даёт |
|------------------|----------|
| `Multi-value` | Можно выбрать несколько значений (в запросе — `=~`) |
| `Include All option` | Пункт «All» (значение `.*` при `=~`) |
| `Refresh: On time range change` | Обновлять список при смене диапазона |
| `Regex` | Отфильтровать значения списка |

**Repeat** — одна панель размножается по значениям переменной:
панель «CPU» с `Repeat by instance` превращается в отдельный график на каждый сервер.

## 4. Provisioning: дашборды как код

```yaml
# provisioning/dashboards/dashboards.yml
apiVersion: 1
providers:
  - name: 'default'
    orgId: 1
    folder: 'Infra'
    type: file
    disableDeletion: true
    updateIntervalSeconds: 30
    allowUiUpdates: false          # ⭐ запрет правок через UI: источник истины — git
    options:
      path: /etc/grafana/dashboards
```
```text:no-line-numbers
grafana/
├── provisioning/
│   ├── datasources/datasources.yml
│   └── dashboards/dashboards.yml
└── dashboards/
    ├── node-exporter.json         ← экспортированный JSON из UI
    ├── postgres.json
    └── app-slo.json
```

Рабочий цикл: собрал дашборд в UI → `Share → Export → Save to file` (с галкой
«Export for sharing externally», чтобы источник стал переменной `${DS_PROMETHEUS}`) →
положил JSON в git → раскатал provisioning'ом.

Готовые дашборды импортируются по ID с grafana.com:
| ID | Дашборд |
|----|---------|
| **1860** | Node Exporter Full ⭐ |
| **193** / **14282** | Docker / cAdvisor |
| **9628** | PostgreSQL |
| **763** | Redis |
| **7362** | MySQL |
| **12006** | Kubernetes cluster |
| **13639** | Loki logs |

## 5. Explore, аннотации и полезные мелочи

- **Explore** — режим «поисследовать»: без сохранения дашборда пишешь PromQL/LogQL
  и сразу видишь результат; идеален во время инцидента. Переключение метрики ↔ логи
  в один клик (если Loki и Prometheus связаны).
- **Аннотации** — вертикальные линии событий на графиках: деплои, миграции, инциденты.
  Добавляются через API из CI:
```bash
curl -X POST -H "Authorization: Bearer $GRAFANA_TOKEN" -H 'Content-Type: application/json' \
  -d '{"text":"deploy api v1.4.2","tags":["deploy"],"time":'"$(date +%s000)"'}' \
  https://grafana.internal/api/annotations
```
  Это мгновенно отвечает на вопрос «а что менялось перед всплеском ошибок».
- **Time range и refresh** — дашборду задают разумный диапазон по умолчанию
  (обычно 6-24 ч) и авто-обновление 30-60 с; секундный refresh только нагружает источник.
- **Snapshot / Share** — поделиться состоянием графиков в постмортеме.

## 7. Как собрать дашборд, которым будут пользоваться

```text:no-line-numbers
 ┌──────────────────────────────────────────────────────────────┐
 │ РЯД 1: ОБЗОР (видно за 5 секунд, «всё ли хорошо»)            │
 │  [Stat: доступность] [Stat: RPS] [Stat: ошибки %] [Stat: p99]│
 ├──────────────────────────────────────────────────────────────┤
 │ РЯД 2: ЗОЛОТЫЕ СИГНАЛЫ приложения                            │
 │  [Traffic] [Errors] [Latency p50/p95/p99] [Saturation]       │
 ├──────────────────────────────────────────────────────────────┤
 │ РЯД 3: РЕСУРСЫ (USE: CPU, RAM, диск, сеть)                   │
 ├──────────────────────────────────────────────────────────────┤
 │ РЯД 4: ЗАВИСИМОСТИ (база, очередь, внешние API)              │
 └──────────────────────────────────────────────────────────────┘
```

| Правило | Почему |
|---------|--------|
| Сверху — симптомы, ниже — причины | Дежурный смотрит сверху вниз |
| Один дашборд = один сервис/слой | «Дашборд обо всём» бесполезен |
| Переменные вместо копий дашборда | Меньше поддержки |
| Пороги совпадают с алертами | График объясняет, почему пришёл алерт |
| Ссылка на рунбук в описании панели | Экономит время ночью |
| Не больше ~15-20 панелей | Иначе никто не читает и всё тормозит |

## 8. Грабли

| Грабля | Симптом | Решение |
|--------|---------|---------|
| Дашборды только в UI | Пропали при переезде, нет истории | Provisioning + git |
| `admin/admin` и доступ наружу | Кто угодно видит внутреннюю кухню | Пароль, OAuth, VPN |
| Жёсткие `[5m]` в запросах | На длинных диапазонах график «ломается» | `$__rate_interval` |
| Нет единиц измерения | «0.85» вместо «85%» | Units в настройках панели |
| Переменная без `=~` при multi-value | Пустой график при выборе нескольких | `=~"$instance"` |
| Тяжёлые запросы на каждой панели | Дашборд грузится 30 секунд | Recording rules, меньше панелей |
| Refresh 5s на 30 панелях | Нагрузка на Prometheus | 30-60 s |
| Дашборд «обо всём» | Никто им не пользуется | Разделить по слоям |

## 💼 Как это в DevOps

- Дашборды и источники раскатываются provisioning'ом из git; правки через UI запрещены
  (`allowUiUpdates: false`) или синхронизируются обратно в репозиторий.
- На каждый сервис — дашборд по схеме «обзор → золотые сигналы → ресурсы → зависимости»,
  и ссылка на него прямо в аннотации алерта.
- Аннотации о деплоях шлёт CI/CD — это самый дешёвый способ связать «выкатили» и «сломалось».
- Explore — основной инструмент во время инцидента: там же переключаешься на логи Loki
  по тем же лейблам.
- В Kubernetes дашборды едут как ConfigMap'ы (sidecar подхватывает их автоматически),
  вместе с kube-prometheus-stack.

## 🧠 Что запомнить

1. Grafana ничего не хранит, кроме своих настроек: она только рисует данные источников.
2. Источники подключают в режиме `proxy` — сами базы и Prometheus наружу не публикуются.
3. ⭐ Переменные превращают 20 копий дашборда в один; для multi-value обязателен `=~`.
4. `label_values(...)` — основной способ наполнить выпадающий список.
5. `$__rate_interval` вместо жёстко заданного окна `rate()`.
6. Дашборды — код: экспорт в JSON, git, provisioning, запрет правок в UI.
7. Готовые дашборды импортируются по ID (1860 — node_exporter, 9628 — PostgreSQL).
8. Структура полезного дашборда: обзор → золотые сигналы → ресурсы → зависимости.
9. Аннотации о деплоях связывают изменения и инциденты.
10. Explore — рабочий инструмент дежурного, особенно в связке метрики + логи.

### Блок A. Теория

**A1.** Хранит ли Grafana метрики? Что она хранит в своей базе?

<details><summary>Ответ</summary>

Нет. В своей базе (SQLite/PostgreSQL/MySQL) она хранит дашборды, источники,
пользователей, права, настройки и — при использовании Grafana Alerting — правила алертов.

</details>

**A2.** Чем режим доступа `proxy` отличается от `browser` и почему обычно выбирают первый?

<details><summary>Ответ</summary>

`proxy` — запрос идёт от сервера Grafana к источнику: источник остаётся во
внутренней сети, работает единая авторизация. `browser` — запрос идёт из браузера
пользователя, требует публичной доступности источника и CORS.

</details>

**A3.** Какие типы панелей знаешь и для чего каждый?

<details><summary>Ответ</summary>

Time series (динамика), Stat (одно число), Gauge (процент с порогами),
Bar gauge (сравнение), Table (списки), Heatmap (распределения), Logs (логи),
State timeline (состояния).

</details>

**A4.** Зачем задавать единицы измерения и пороги в панели?

<details><summary>Ответ</summary>

Без единиц значения нечитаемы (0.85 вместо 85%, 4.3e10 вместо 43 ГБ);
пороги визуально показывают, когда значение близко к алертному.

</details>

**A5.** ⭐ Зачем нужны переменные дашборда? Приведи пример, где они экономят 20 дашбордов.

<details><summary>Ответ</summary>

Чтобы один дашборд обслуживал все окружения/сервисы/хосты: выпадающие списки
вместо копий. Пример: `env` + `job` + `instance` заменяют 20 почти одинаковых дашбордов.

</details>

**A6.** Какие типы переменных бывают? Чем `Query` отличается от `Custom`?

<details><summary>Ответ</summary>

Query (значения из источника), Custom (список руками), Constant, Interval,
Data source, Text box, Ad hoc filters. Query обновляется автоматически, Custom — нет.

</details>

**A7.** Что делает `label_values(up, instance)`?

<details><summary>Ответ</summary>

Возвращает список значений лейбла `instance` у метрики `up` — готовый список
для выпадающего меню.

</details>

**A8.** Почему при multi-value нужно писать `=~"$instance"`, а не `="$instance"`?

<details><summary>Ответ</summary>

При выборе нескольких значений переменная разворачивается в
`value1|value2`, что корректно работает только с regex-оператором `=~`.

</details>

**A9.** Что делает опция Repeat?

<details><summary>Ответ</summary>

Размножает панель (или ряд) по значениям переменной: на каждый инстанс/сервис
своя копия панели.

</details>

**A10.** Что такое `$__rate_interval` и чем он лучше жёсткого `[5m]`?

<details><summary>Ответ</summary>

Это интервал, который Grafana вычисляет из шага графика и `scrape_interval`
источника; он всегда содержит достаточно точек, тогда как жёсткий `[5m]` ломается
на больших диапазонах (или даёт лишнее сглаживание на маленьких).

</details>

**A11.** Что такое provisioning и почему он важнее «накликанных» дашбордов?

<details><summary>Ответ</summary>

Описание источников и дашбордов файлами, которые Grafana подхватывает при старте.
Даёт версионирование, ревью, воспроизводимость и переживание переезда.

</details>

**A12.** Как перенести дашборд из UI в git?

<details><summary>Ответ</summary>

Share → Export → Export for sharing externally → Save to file; JSON кладут
в репозиторий и раскатывают provisioning'ом.

</details>

**A13.** Что такое аннотации и как они помогают в разборе инцидентов?

<details><summary>Ответ</summary>

Отметки событий (деплой, миграция, инцидент) на графиках. Сразу видно
корреляцию «выкатили → сломалось».

</details>

**A14.** Как устроить разграничение доступа между командами?

<details><summary>Ответ</summary>

Папки + команды + роли (Viewer/Editor/Admin), для автоматизации —
service accounts с токенами; вход через OAuth/LDAP.

</details>

**A15.** Как ты организуешь структуру полезного дашборда сервиса?

<details><summary>Ответ</summary>

Ряд обзора (симптомы одним взглядом) → золотые сигналы сервиса →
ресурсы (USE) → зависимости (база, очередь, внешние API).

</details>

### Блок B. «Оцени решение»

```text:no-line-numbers
B1.  Панель CPU: выражение rate(node_cpu_seconds_total[5m]), период графика 30 дней
```

<details><summary>Ответ</summary>

Жёсткий `[5m]` на 30-дневном диапазоне: шаг графика больше окна, график
будет рваным. Нужен `$__rate_interval`.

</details>

```text:no-line-numbers
B2.  Панель "Свободно на диске", единицы не заданы, значения вида 4.3e10
```

<details><summary>Ответ</summary>

Не заданы единицы — читать невозможно.

</details>

```text:no-line-numbers
B3.  Переменная instance (multi-value) используется как up{instance="$instance"}
```

<details><summary>Ответ</summary>

При multi-value нужно `=~"$instance"`, иначе пусто.

</details>

```text:no-line-numbers
B4.  20 дашбордов "API prod", "API stage", "Billing prod", … без переменных
```

<details><summary>Ответ</summary>

Отсутствие переменных: дублирование и тяжёлая поддержка.

</details>

```text:no-line-numbers
B5.  Дашборды создаются только через UI, бэкапов нет
```

<details><summary>Ответ</summary>

Нет источника истины и бэкапа: пересоздание Grafana = потеря всего.

</details>

```text:no-line-numbers
B6.  Grafana доступна из интернета с admin/admin
```

### Блок D. Инциденты

**D1.** После пересоздания контейнера пропали все дашборды. Что было не так?

<details><summary>Ответ</summary>

Дашборды хранились в базе Grafana внутри контейнера без тома и без provisioning.

</details>

**D2.** Дашборд открывается 40 секунд. Что оптимизируешь?

<details><summary>Ответ</summary>

Тяжёлые запросы (вынести в recording rules), слишком много панелей, большой
диапазон по умолчанию, частый refresh, `Max data points` по умолчанию.

</details>

**D3.** При выборе «All» в переменной графики пустые. Причина?

<details><summary>Ответ</summary>

В запросе `="$var"` вместо `=~"$var"`, либо значение All не настроено
(`Include All option` с пустым значением).

</details>

**D4.** На графике «дырки», хотя в Prometheus данные есть. Гипотезы?

<details><summary>Ответ</summary>

Пропуски сбора (`scrape_duration` ≈ `scrape_interval`), рестарты экспортера,
слишком маленькое окно `rate`, `Min interval` панели меньше `scrape_interval`.

</details>

**D5.** Панель показывает 0.85 вместо 85%. Где исправить?

<details><summary>Ответ</summary>

В настройках панели: Standard options → Unit → Percent (0.0-1.0).

</details>

**D6.** Grafana показывает данные, а алерты Prometheus молчат (или наоборот). Как такое возможно?

<details><summary>Ответ</summary>

Grafana может смотреть на другой источник/интервал, у алерта другое выражение
или `for`, алерт заглушен silence, либо правила не загрузились (`/rules`).

</details>

**D7.** Импортированный дашборд пуст: «No data». Что проверишь?

<details><summary>Ответ</summary>

Соответствие имени источника (`${DS_PROMETHEUS}`), наличие нужных экспортеров
и метрик (дашборд может быть под другую версию экспортера), выбранные переменные,
временной диапазон.

</details>

**D8.** Разработчики удалили чужой дашборд. Как предотвратить?

<details><summary>Ответ</summary>

Права: папки + роли, `allowUiUpdates: false`, provisioning из git,
резервное копирование базы Grafana.

</details>

**D9.** В постмортеме нужно показать состояние графиков на момент инцидента. Как?

<details><summary>Ответ</summary>

Snapshot дашборда или экспорт данных панели; плюс ссылка с фиксированным
временным диапазоном (`from`/`to` в URL).

</details>

**D10.** Пароль от источника-базы утёк из репозитория с provisioning. Что делать и как хранить правильно?

<details><summary>Ответ</summary>

Сменить пароль пользователя базы, убрать секрет из истории git, перевести
на переменные окружения/секреты (`${PG_PASSWORD}`, Vault, k8s Secret), проверить доступы.

</details>

### Блок E. Вопросы с собеседования

**1.** Что такое Grafana и хранит ли она данные?

<details><summary>Ответ</summary>

Инструмент визуализации: сама метрики не хранит, ходит в источники, хранит
только собственные настройки и дашборды.

</details>

**2.** Какие источники данных подключал?

<details><summary>Ответ</summary>

Prometheus, Loki, PostgreSQL/MySQL, Elasticsearch, ClickHouse — через плагины источников.

</details>

**3.** Как сделать дашборд универсальным для нескольких серверов?

<details><summary>Ответ</summary>

Переменными (`job`, `instance`, `env`) и опцией Repeat.

</details>

**4.** Что такое переменные дашборда и какие бывают?

<details><summary>Ответ</summary>

Query, Custom, Constant, Interval, Data source, Text box, Ad hoc; Query строится
запросом к источнику (`label_values`).

</details>

**5.** Как дашборды попадают в git?

<details><summary>Ответ</summary>

Экспорт JSON и provisioning из репозитория, правки в UI запрещены.

</details>

**6.** Чем отличается `$__rate_interval` от `[5m]`?

<details><summary>Ответ</summary>

`$__rate_interval` автоматически подстраивается под масштаб графика и `scrape_interval`.

</details>

**7.** Как связать деплои и графики?

<details><summary>Ответ</summary>

Аннотациями из CI/CD через API Grafana.

</details>

**8.** Как ты строишь дашборд для нового сервиса?

<details><summary>Ответ</summary>

Обзор → золотые сигналы (RED) → ресурсы (USE) → зависимости; пороги совпадают с алертами,
в описании — ссылка на рунбук.

</details>

**9.** Как разграничить доступ к дашбордам?

<details><summary>Ответ</summary>

Папки, команды, роли, service accounts; вход через корпоративный SSO.

</details>

**10.** Где алерты лучше держать: в Grafana или в Prometheus?

<details><summary>Ответ</summary>

Для инфраструктуры — Prometheus + Alertmanager (правила в git, независимость от Grafana);
Grafana Alerting — когда источников несколько или алерт естественно рождается из дашборда.

</details>
