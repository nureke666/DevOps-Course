# 01. Основы мониторинга

> Роадмап → 7. Остальное → Мониторинг: *«Мониторинг есть, по крайней мере должен быть
> на любом проекте… Стандарт в девопсерском наборе, знать обязательно.»*
>
> **После темы ты умеешь:** объяснить разницу метрик, логов и трейсов, pull и push,
> мониторинга и алертинга; понимать, что такое SLI/SLO и зачем они нужны девопсу.

## 🗺️ Три источника правды о системе

```text:no-line-numbers
 ┌──────────────┬───────────────────────────┬─────────────────────────────────┐
 │  МЕТРИКИ     │ числа во времени          │ "5xx выросли в 14:03,           │
 │ (Prometheus) │ дёшево хранить, агрегируем│  время ответа 2с вместо 200мс"  │
 │              │ ⇒ ЧТО и КОГДА сломалось   │                                 │
 ├──────────────┼───────────────────────────┼─────────────────────────────────┤
 │  ЛОГИ        │ текстовые события         │ "connection refused to db:5432" │
 │ (Loki/ELK)   │ дорого хранить, ищем      │                                 │
 │              │ ⇒ ПОЧЕМУ сломалось        │                                 │
 ├──────────────┼───────────────────────────┼─────────────────────────────────┤
 │  ТРЕЙСЫ      │ путь запроса по сервисам  │ "из 2с — 1,8с ждали auth-service"│
 │ (Jaeger/Tempo│ ⇒ ГДЕ именно тормозит     │                                 │
 └──────────────┴───────────────────────────┴─────────────────────────────────┘
              вместе это называют observability (наблюдаемость)
```

Порядок внедрения на реальном проекте обычно такой же: сначала метрики и алерты,
потом централизованные логи (раздел «Логирование»), трейсы — когда микросервисов становится много.

---

## 1. Мониторинг ≠ алертинг ≠ наблюдаемость

| Термин | Что это | Вопрос |
|--------|---------|--------|
| **Мониторинг** | Сбор и хранение данных о системе | «Что происходит?» |
| **Алертинг** | Уведомление, когда стало плохо | «Кого будить?» |
| **Дашборды** | Визуализация для человека | «Как это выглядит?» |
| **Наблюдаемость** | Возможность понять состояние системы по её выходным данным, включая ситуации, которых ты не предвидел | «Почему это случилось?» |

Практическая разница: мониторинг отвечает на **заранее заданные** вопросы
(«сколько 5xx?»), наблюдаемость позволяет задавать **новые** вопросы во время инцидента
(«а что с 5xx именно у пользователей из мобильного приложения на версии 3.2?»).

## 2. Pull vs Push

```text:no-line-numbers
        PULL (Prometheus)                      PUSH (Graphite, InfluxDB, StatsD)
 ┌────────────┐   HTTP GET /metrics      ┌────────────┐   метрики летят сами
 │ Prometheus │ ───────────────────────► │  приложение│ ─────────────────────► сервер
 │            │ ◄─── метрики текстом     │            │
 └────────────┘                          └────────────┘

 + видно, что таргет жив (up=0 — это уже алерт)   + работает за NAT и с короткоживущими
 + конфигурация в одном месте                       задачами
 + легко проверить руками: curl /metrics          + не нужен доступ ОТ сервера К цели
 − нужна сетевая доступность до целей             − сложнее понять, «умер или молчит»
 − короткоживущие задачи не успевают быть опрошены − легко «залить» сервер метриками
```

Prometheus — pull. Для короткоживущих job'ов (cron, CI) есть **Pushgateway** —
исключение, а не правило: метрики туда пушат, а Prometheus забирает их оттуда.

> ⭐ Частый вопрос на собесе: *«Как мониторить cron-задачу Prometheus'ом?»*
> Ответ: Pushgateway (или textfile collector у node_exporter) — и обязательно
> метрика вида «время последнего успешного выполнения», по которой строится алерт.

## 3. Модель данных: метрика, лейблы, временной ряд

```text:no-line-numbers
http_requests_total{job="api", instance="10.0.1.7:8080", method="POST", status="500"} 1423
└──────┬──────────┘└──────────────────────────┬───────────────────────────────────┘ └─┬─┘
   имя метрики                             лейблы (метки)                         значение

имя + УНИКАЛЬНЫЙ набор лейблов = отдельный ВРЕМЕННОЙ РЯД (time series)
```

⚠️ **Кардинальность** — главная опасность. Каждое новое значение лейбла создаёт новый ряд:

```text:no-line-numbers
status="500"           → 5 значений        ✅ норма
method="POST"          → 5 значений        ✅ норма
user_id="12345"        → 1 000 000 рядов   💥 Prometheus ляжет
request_id="uuid"      → бесконечность     💥💥
```

Правило: в лейблы кладут только то, у чего **ограниченный набор значений**
(десятки, максимум сотни). Всё остальное — в логи.

## 4. SLI, SLO, SLA и error budget

| Термин | Что это | Пример |
|--------|---------|--------|
| **SLI** (Indicator) | Измеряемый показатель качества | Доля успешных запросов |
| **SLO** (Objective) | Внутренняя цель по SLI | 99,9% успешных за 30 дней |
| **SLA** (Agreement) | Обязательство перед клиентом с санкциями | 99,5%, иначе компенсация |
| **Error budget** | Сколько можно «сломать» и остаться в SLO | 99,9% ⇒ 43 минуты в месяц |

```text:no-line-numbers
SLO 99,9% в месяц = бюджет ошибок 43 мин 12 с
 │
 ├─ бюджет ещё есть  → можно катить релизы, экспериментировать
 └─ бюджет исчерпан  → заморозка фич, всё внимание — надёжности
```

Почему это важно девопсу: SLO превращает спор «надо ли чинить прямо сейчас»
в измеримое решение и задаёт, **на что вообще ставить алерты** (см. тему 07).

## 5. Что такое «хороший алерт»

```text:no-line-numbers
ПЛОХОЙ АЛЕРТ                          ХОРОШИЙ АЛЕРТ
──────────────                        ─────────────
"CPU > 80%"                           "Время ответа API > 1с у 5% запросов, 10 минут"
   │ и что? сервис работает нормально      │ пользователю реально плохо
   │ будят ночью впустую                   │ есть рунбук: что проверить
   │ через месяц его игнорируют            │ есть severity: будить или до утра
```

Критерии хорошего алерта:
1. **Симптом, а не причина** — алертим на то, что чувствует пользователь.
2. **Actionable** — понятно, что делать; есть рунбук.
3. **Срочный** — если действие можно отложить до утра, это не пейджер, а тикет.
4. **С задержкой** (`for: 5m`) — чтобы не ловить одиночные всплески.
5. **Не дублирующий** — один инцидент не должен давать 40 уведомлений.

> ⭐ Alert fatigue (усталость от алертов) — главная болезнь мониторинга.
> Когда алертов много и они шумят, дежурный перестаёт их читать — и пропускает настоящий.
> Лечится удалением алертов, а не привыканием к ним.

## 6. Типовая архитектура мониторинга

```text:no-line-numbers
 ┌──────────┐  ┌──────────┐  ┌──────────┐  ┌────────────┐
 │  сервер  │  │ контейнер│  │ база     │  │ приложение │
 │ node_exp │  │ cAdvisor │  │ pg_exp   │  │ /metrics   │
 └────┬─────┘  └────┬─────┘  └────┬─────┘  └─────┬──────┘
      └─────────────┴─────────────┴──────────────┘
                        │ pull (HTTP GET /metrics каждые 15-30 с)
                        ▼
                ┌───────────────┐   правила алертов (PromQL)
                │  Prometheus   │ ──────────────┐
                │  (TSDB)       │               ▼
                └───────┬───────┘        ┌──────────────┐  группировка,
                        │                │ Alertmanager │  маршрутизация,
                        │ запросы PromQL └──────┬───────┘  silence
                        ▼                       │
                ┌───────────────┐               ▼
                │    Grafana    │        Telegram / почта / PagerDuty
                └───────────────┘
```

Дополнения, которые встречаются рядом:
- **Pushgateway** — для короткоживущих задач;
- **blackbox_exporter** — проверки «снаружи» (HTTP, TCP, ICMP, TLS-сертификаты);
- **VictoriaMetrics / Thanos / Mimir** — долгое хранение и масштабирование Prometheus;
- **Loki** — логи в той же Grafana (раздел «Логирование»).

## 7. Grafana Alerting vs Prometheus Alerting

| | Prometheus + Alertmanager | Grafana Alerting |
|---|---------------------------|------------------|
| Где живут правила | Файлы в git рядом с Prometheus | В базе Grafana (можно provisioning'ом) |
| Источники | Только Prometheus | Любые источники (в т.ч. несколько сразу) |
| Плюс | Стандарт, версионируется, надёжно | Удобный UI, единое место |
| Типовой выбор | ⭐ Прод, инфраструктура | Быстрые алерты по дашбордам, смешанные источники |

Классика в проектах: правила в Prometheus (в git), уведомления — через Alertmanager.

## 💼 Как это в DevOps

- Мониторинг ставится **до** первого инцидента: настроить его «потом» означает
  разбирать первый серьёзный сбой вслепую.
- Стандартный набор для нового сервиса: `up`, время ответа, ошибки, насыщение ресурсов,
  плюс специфичные бизнес-метрики (очередь задач, отправленные письма).
- Конфиги Prometheus, правила и дашборды лежат в git и раскатываются Ansible/Helm —
  «накликано в UI» не переживает переезд и не проходит ревью.
- Дежурство строится вокруг алертов: у каждого есть severity, маршрут и рунбук.
- На собесе спрашивают не «какие кнопки в Grafana», а: pull vs push, типы метрик,
  `rate` vs прямое значение, что такое кардинальность и как ты выбираешь, на что алертить.

## 📌 Шпаргалка

| Термин | Одной строкой |
|--------|---------------|
| Метрика | Число во времени с именем и лейблами |
| Временной ряд | Уникальная комбинация имени и набора лейблов |
| Кардинальность | Сколько рядов порождает метрика; главный риск для Prometheus |
| Pull | Сервер сам ходит за метриками (Prometheus) |
| Push | Источник сам отправляет метрики (StatsD, Pushgateway) |
| Exporter | Мостик: превращает состояние системы в метрики Prometheus |
| Scrape | Один поход Prometheus за метриками |
| SLI / SLO / SLA | Показатель / внутренняя цель / договор с клиентом |
| Error budget | Допустимое время «плохой» работы в рамках SLO |
| Алерт | Правило на PromQL + `for` + маршрут + рунбук |
| Alert fatigue | Дежурный перестал реагировать из-за шума |
| Observability | Возможность отвечать на новые вопросы о системе |

## 🧠 Что запомнить

1. Метрики — «что и когда», логи — «почему», трейсы — «где»; вместе это observability.
2. Prometheus работает по **pull**: сам ходит за `/metrics`, поэтому знает, что таргет жив.
3. Метрика = имя + лейблы; каждая уникальная комбинация — отдельный временной ряд.
4. ⭐ Высокая кардинальность (user_id, uuid в лейблах) убивает Prometheus. Такое — в логи.
5. Для короткоживущих задач есть Pushgateway и textfile collector — это исключение.
6. SLI/SLO/error budget превращают «кажется, всё плохо» в измеримое решение.
7. Хороший алерт: симптом, actionable, срочный, с `for` и рунбуком.
8. Alert fatigue лечится удалением лишних алертов, а не терпением.
9. Типовая связка: exporters → Prometheus → Alertmanager → мессенджер, визуализация — Grafana.
10. Конфиги, правила и дашборды живут в git, а не только в UI.

### Блок A. Теория

**A1.** Чем метрики отличаются от логов и трейсов? На какой вопрос отвечает каждый источник?

<details><summary>Ответ</summary>

Метрики — числовые ряды во времени, дёшевы, агрегируются, отвечают «что и когда».
Логи — текстовые события, дороже в хранении, отвечают «почему». Трейсы — путь запроса
через сервисы, отвечают «где именно тормозит».

</details>

**A2.** Что такое observability и чем она отличается от мониторинга?

<details><summary>Ответ</summary>

Мониторинг — сбор заранее определённых данных и ответы на заранее известные вопросы.
Observability — свойство системы, позволяющее задавать новые вопросы во время инцидента
и получать ответы без выкатки нового кода.

</details>

**A3.** Объясни pull-модель. Назови три плюса и два минуса.

<details><summary>Ответ</summary>

Prometheus сам ходит по HTTP за `/metrics`. Плюсы: видно, жив ли таргет (`up`),
конфигурация централизована, легко проверить вручную `curl`. Минусы: нужна сетевая
доступность до целей, короткоживущие задачи можно не успеть опросить.

</details>

**A4.** Как мониторить короткоживущую задачу (cron, CI-джоба) при pull-модели?

<details><summary>Ответ</summary>

Через Pushgateway (задача пушит метрики, Prometheus забирает их оттуда) или
textfile collector node_exporter'а (задача пишет файл, экспортер его отдаёт).
Алертят обычно по «времени последнего успеха».

</details>

**A5.** Из чего состоит метрика в Prometheus? Что такое временной ряд?

<details><summary>Ответ</summary>

Имя метрики + набор лейблов + значение + временная метка. Уникальная комбинация
имени и лейблов образует отдельный временной ряд.

</details>

**A6.** ⭐ Что такое кардинальность и почему `user_id` в лейблах — это катастрофа?

<details><summary>Ответ</summary>

Число уникальных комбинаций лейблов. `user_id` даёт по ряду на пользователя:
миллион пользователей — миллион рядов, каждый со своей историей в памяти и на диске.
Prometheus упирается в память и деградирует.

</details>

**A7.** Какие данные можно класть в лейблы, а какие нельзя?

<details><summary>Ответ</summary>

Можно: окружение, инстанс, job, метод, код ответа, имя очереди, статус —
то, где значений десятки. Нельзя: идентификаторы запросов, сессий, пользователей,
полные URL с параметрами, метки времени.

</details>

**A8.** Что такое SLI, SLO, SLA? Приведи пример каждого для веб-API.

<details><summary>Ответ</summary>

SLI — доля успешных ответов API; SLO — 99,9% успешных за 30 дней;
SLA — договор с клиентом «99,5%, иначе компенсация».

</details>

**A9.** Что такое error budget? Сколько минут даёт SLO 99,9% в месяц?

<details><summary>Ответ</summary>

Допустимая доля «плохого» времени/запросов в рамках SLO.
99,9% за 30 дней ≈ 43 минуты 12 секунд.

</details>

**A10.** Назови пять критериев хорошего алерта.

<details><summary>Ответ</summary>

Симптом (важен пользователю), actionable (есть что делать), срочный
(иначе это тикет), с `for` (без ложных срабатываний), не дублирующий (группировка).

</details>

**A11.** Что такое alert fatigue и как с ней бороться?

<details><summary>Ответ</summary>

Состояние, когда алертов так много, что дежурный перестаёт на них реагировать.
Лечение: удалять неактуальные, повышать пороги и `for`, группировать в Alertmanager,
разделять severity, писать рунбуки, регулярно пересматривать набор правил.

</details>

**A12.** Почему «CPU > 80%» — обычно плохой алерт, а «время ответа > 1 с» — хороший?

<details><summary>Ответ</summary>

CPU 80% может быть нормой (батч-обработка), а может не влиять на пользователя.
Время ответа — прямой симптом качества сервиса: если оно выросло, пользователю плохо
независимо от причины.

</details>

**A13.** Зачем алерту параметр `for`?

<details><summary>Ответ</summary>

Чтобы алерт срабатывал только если условие держится заданное время —
это отсекает одиночные всплески и «дребезг».

</details>

**A14.** Нарисуй типовую архитектуру мониторинга и назови роль каждого компонента.

<details><summary>Ответ</summary>

Exporters/приложения → Prometheus (сбор, хранение, вычисление правил) →
Alertmanager (группировка, маршрутизация, silence) → каналы уведомлений;
Grafana — визуализация поверх Prometheus.

</details>

**A15.** Когда используют Grafana Alerting, а когда Prometheus + Alertmanager?

<details><summary>Ответ</summary>

Prometheus + Alertmanager — стандарт для инфраструктуры: правила в git,
надёжно, независимо от Grafana. Grafana Alerting удобна, когда источников несколько
или алерт строится по дашборду.

</details>

### Блок B. «Оцени решение»

**B1.** Метрика: `http_requests_total{path="/api/users/12345"}`

<details><summary>Ответ</summary>

Путь с идентификатором в лейбле — взрыв кардинальности. Нужен шаблон пути (`/api/users/:id`).

</details>

**B2.** Метрика: `http_request_duration_seconds{request_id="7f3c-..."}`

<details><summary>Ответ</summary>

`request_id` — бесконечная кардинальность. Это данные для логов/трейсов.

</details>

**B3.** Метрика: `app_queue_size{queue="emails"}`

<details><summary>Ответ</summary>

Хорошая метрика: ограниченный набор очередей.

</details>

**B4.** Алерт: `node_memory_MemAvailable_bytes < 1e9`, `for: 0s`, `severity: critical`

<details><summary>Ответ</summary>

`for: 0s` и critical по абсолютному значению памяти — будет шуметь;
лучше относительный порог и `for: 5-10m`.

</details>

**B5.** Алерт: `up{job="api"} == 0`, `for: 2m`, `severity: critical`

<details><summary>Ответ</summary>

Хороший алерт: простой симптом, разумная задержка.

</details>

**B6.** Алерт: `rate(http_requests_total{status=~"5.."}[5m]) > 0`, `for: 1m`

<details><summary>Ответ</summary>

Любая единичная 5xx поднимет алерт — шум. Нужна доля ошибок от общего числа
запросов и порог.

</details>

**B7.** Алерт: `disk_usage > 90%`, `for: 30m`, `severity: warning` + рунбук

<details><summary>Ответ</summary>

Хороший: заранее, не срочно, с рунбуком; идеально — плюс `predict_linear`.

</details>

**B8.** «Мы храним все метрики 2 года в Prometheus»

<details><summary>Ответ</summary>

Prometheus не предназначен для долгого хранения: нужен Thanos/VictoriaMetrics/Mimir
или downsampling.

</details>

**B9.** «Логи приложения пишем метриками в Prometheus, чтобы всё было в одном месте»

<details><summary>Ответ</summary>

Логи метриками — путь к взрыву кардинальности и потере информации; логи идут
в Loki/ELK, метрики — в Prometheus.

</details>

**B10.** «У нас 200 алертов, дежурный смотрит только критичные»

<details><summary>Ответ</summary>

Симптом alert fatigue: 200 алертов невозможно поддерживать; нужен аудит
и сокращение до значимых.

</details>

**B11.** Приложение само пушит метрики в Prometheus по HTTP POST

<details><summary>Ответ</summary>

Prometheus не принимает push от приложений (кроме remote write и Pushgateway) —
приложение должно отдавать `/metrics`.

</details>

**B12.** cron-задача раз в сутки: метрика последнего успеха уходит в Pushgateway

<details><summary>Ответ</summary>

Правильный приём для cron-задач.

</details>

### Блок C. Практика

#### C1. Первый взгляд на метрики
1. Подними compose-стенд из индекса.
2. `curl -s localhost:9100/metrics | head -40` — разбери формат: имя, лейблы, значение, `# HELP`, `# TYPE`.
3. Найди метрики: `node_cpu_seconds_total`, `node_memory_MemAvailable_bytes`, `node_filesystem_avail_bytes`.

<details><summary>Ответ</summary>

Формат: строка `# HELP`, строка `# TYPE`, затем `имя{лейблы} значение`.

</details>

#### C2. Временные ряды и лейблы
1. В Prometheus выполни `node_cpu_seconds_total` — сколько получилось рядов?
2. Объясни, из-за каких лейблов их столько.
3. Посчитай: `count(node_cpu_seconds_total)`.

<details><summary>Ответ</summary>

Рядов = число CPU × число режимов (`user`, `system`, `idle`, `iowait`, …).

</details>

#### C3. 🔑 Кардинальность на практике
1. Напиши простое приложение (или скрипт), отдающее `/metrics` с метрикой
   `demo_requests_total{user_id="..."}`, где `user_id` случайный.
2. Дай Prometheus собрать это несколько минут.
3. Посмотри `count({__name__=~"demo_.*"})` и `prometheus_tsdb_head_series`.
4. Сделай вывод и перепиши метрику правильно.

<details><summary>Ответ</summary>

`prometheus_tsdb_head_series` покажет рост числа рядов; правильный вариант метрики —
без `user_id`, с ограниченными лейблами (например, `status`).

</details>

#### C4. Pull своими глазами
1. Останови `node-exporter`, посмотри метрику `up{job="node"}` в Prometheus.
2. Запусти обратно. Объясни, чем `up == 0` ценнее, чем «метрики просто перестали приходить».

<details><summary>Ответ</summary>

`up == 0` отличает «цель недоступна» от «цель жива, но метрика не изменилась» —
при push такой разницы нет.

</details>

#### C5. Pushgateway
1. Добавь `pushgateway` в compose, пропиши таргет в Prometheus.
2. Отправь метрику из скрипта:
```bash
echo "backup_last_success_timestamp $(date +%s)" | \
  curl --data-binary @- http://localhost:9091/metrics/job/backup
```
3. Построй выражение «бэкап не делался больше 25 часов».

<details><summary>Ответ</summary>

Алерт: `time() - backup_last_success_timestamp > 25*3600`.

</details>

#### C6. SLI/SLO на бумаге
Возьми любой сервис (свой pet-проект или воображаемый API) и опиши:
2 SLI, SLO для каждого, error budget в минутах, что делаем при его исчерпании.

#### C7. Разбор чужих алертов
Найди в интернете любой готовый набор правил (например, awesome-prometheus-alerts),
выбери 10 правил и для каждого ответь: это симптом или причина? Есть ли действие?
Разбудил бы ты им человека ночью?

<details><summary>Ответ</summary>

Полезно заметить, что значительная часть готовых правил — «причины»
(память, CPU, inode), и им место в предупреждениях, а не в ночном пейджере.

</details>

#### C8. Свой первый алерт
Создай правило `InstanceDown` (`up == 0`, `for: 2m`), проверь его в Prometheus
(состояния pending → firing), выключив экспортер.

<details><summary>Ответ</summary>

В Prometheus правило сначала переходит в состояние `pending` (идёт отсчёт `for`),
потом `firing`.

</details>

#### C9. Логи vs метрики
Для одного инцидента (например, «сервис отдаёт 500») выпиши: какие метрики покажут
проблему, какие логи нужны для причины, что дал бы трейс.

#### C10. Инвентаризация своего проекта
Составь таблицу: что у тебя есть (серверы, контейнеры, базы, приложения),
чем это мониторится сейчас, чего не хватает. Это план работ на блок.

### Блок D. Инциденты

**D1.** Prometheus «съел» 40 ГБ диска за неделю. С чего начнёшь разбор?

<details><summary>Ответ</summary>

Число активных рядов (`prometheus_tsdb_head_series`), топ метрик по кардинальности,
`scrape_interval`, retention, новые экспортеры/релизы, `--storage.tsdb.retention.time`.

</details>

**D2.** Дежурный жалуется: за ночь пришло 300 уведомлений. Что делать?

<details><summary>Ответ</summary>

Собрать статистику: какие алерты дали шум; отключить/поднять пороги, добавить `for`,
настроить группировку и `repeat_interval`, разделить severity, ввести обязательные рунбуки.

</details>

**D3.** Алерт «сервис недоступен» не сработал, хотя сервис лежал 20 минут. Гипотезы?

<details><summary>Ответ</summary>

Алерт не существовал/не загрузился (ошибка в правилах), сам Prometheus был недоступен,
Alertmanager не доставил уведомление, действовал silence, условие некорректно
(например, `absent()` не использовано), `for` слишком большой.

</details>

**D4.** Метрики приложения пропали после релиза, `up` при этом `1`. Что проверишь?

<details><summary>Ответ</summary>

Изменился путь `/metrics` или порт, приложение перестало регистрировать метрики,
поменялись имена метрик, экспортер отдаёт пустой ответ; `up=1` означает лишь успешный HTTP-ответ.

</details>

**D5.** Разработчик добавил метрику с лейблом `session_id`, Prometheus начал тормозить.
Объясни связь и предложи замену.

<details><summary>Ответ</summary>

Каждый `session_id` создаёт новый ряд; память и диск растут, запросы замедляются.
Замена — убрать лейбл, использовать гистограмму/счётчик без идентификаторов,
а детали искать в логах.

</details>

**D6.** Нужно мониторить сервис за NAT, до которого Prometheus не достучится. Варианты?

<details><summary>Ответ</summary>

Pushgateway, remote write от агента (Grafana Agent/VMAgent) на стороне сервиса,
VPN/туннель, отдельный Prometheus внутри периметра с federation/remote write наружу.

</details>

**D7.** После инцидента выяснилось, что данных за нужный период уже нет. Что настроить?

<details><summary>Ответ</summary>

Увеличить retention, поднять долговременное хранилище (VictoriaMetrics/Thanos),
настроить downsampling, а также сохранять ключевые графики/данные в постмортеме.

</details>

**D8.** Бизнес спрашивает: «какая у нас доступность за месяц?» Как ответить цифрой?

<details><summary>Ответ</summary>

Через SLI: доля успешных запросов за период, посчитанная по метрикам;
сопоставить с SLO и остатком error budget.

</details>

**D9.** Алерты приходят, но никто не знает, что с ними делать. Что внедрить?

<details><summary>Ответ</summary>

Рунбуки: на каждый алерт — короткая инструкция (что проверить, какие команды,
когда эскалировать), ссылка в аннотации алерта.

</details>

**D10.** Prometheus упал, и мониторинга нет вообще. Как такое предотвращать?

<details><summary>Ответ</summary>

Мониторить сам Prometheus (второй инстанс, blackbox-проверка, dead man's switch —
алерт, который всегда должен срабатывать), хранить конфиг в git, сделать HA-пару
или использовать внешний сервис проверки.

</details>

### Блок E. Вопросы с собеседования

**1.** Что такое мониторинг и чем он отличается от observability?

<details><summary>Ответ</summary>

Мониторинг — сбор и отображение заранее заданных данных; observability — способность
отвечать на новые вопросы о системе.

</details>

**2.** Чем метрики отличаются от логов?

<details><summary>Ответ</summary>

Метрики — числа во времени, агрегируемые и дешёвые; логи — детальные события,
дороже в хранении.

</details>

**3.** Как работает pull-модель и в чём её плюсы?

<details><summary>Ответ</summary>

Сервер сам опрашивает цели по HTTP; видно доступность цели, конфигурация централизована,
легко отладить `curl`.

</details>

**4.** Что такое кардинальность метрик?

<details><summary>Ответ</summary>

Число уникальных комбинаций лейблов; высокая кардинальность убивает Prometheus.

</details>

**5.** Что такое SLI, SLO, SLA?

<details><summary>Ответ</summary>

Показатель качества, внутренняя цель по нему, внешнее обязательство с санкциями.

</details>

**6.** Что такое error budget?

<details><summary>Ответ</summary>

Допустимый объём отказов в рамках SLO; исчерпан — приоритет надёжности над фичами.

</details>

**7.** Каким должен быть хороший алерт?

<details><summary>Ответ</summary>

Симптом, actionable, срочный, с задержкой `for`, с рунбуком и понятным адресатом.

</details>

**8.** Как мониторить cron-задачи?

<details><summary>Ответ</summary>

Pushgateway или textfile collector + алерт по «времени последнего успеха».

</details>

**9.** Из чего состоит типовой стек мониторинга?

<details><summary>Ответ</summary>

Exporters → Prometheus → Alertmanager → каналы; Grafana для дашбордов; логи отдельно.

</details>

**10.** Как бороться с шумными алертами?

<details><summary>Ответ</summary>

Аудит правил, пороги и `for`, группировка и подавление, severity, рунбуки,
регулярный пересмотр.

</details>
