## 🎯 Часть 1. Семь главных вопросов роадмапа

### 1. Чем отличаются Deployment, StatefulSet, DaemonSet? ⭐

<details><summary>Ответ</summary>

**Короткий ответ (30 секунд):**
> «Deployment — для stateless-приложений: поды взаимозаменяемы, имена случайные,
> обновляются плавно с откатом. StatefulSet — для приложений с состоянием: у подов
> стабильные порядковые имена, персональные DNS-записи и персональные тома через
> `volumeClaimTemplates`, создаются и удаляются строго по порядку. DaemonSet —
> гарантирует по одному поду на каждой подходящей ноде: агенты логов, метрик,
> сетевые плагины, CSI».

**Развёрнуто (если просят подробнее):**
- **Имена.** Deployment: `web-7d8f9c5b4-x2k9` (хеш шаблона + случайный суффикс).
  StatefulSet: `db-0`, `db-1` — имя стабильно и переживает пересоздание.
- **Хранилище.** У StatefulSet `volumeClaimTemplates` создаёт PVC на каждый под;
  при пересоздании под получает **тот же** том.
- **Сеть.** StatefulSet требует headless Service (`clusterIP: None`) и даёт
  каждому поду DNS-имя `db-0.db.ns.svc.cluster.local`.
- **Порядок.** StatefulSet: создание 0→1→2 с ожиданием готовности, удаление
  и обновление — в обратном порядке; `partition` позволяет обновлять частично.
- **DaemonSet.** Нет `replicas`; число подов равно числу подходящих нод; новая нода —
  новый под автоматически; обычно нужны `tolerations` и `hostPath`/`hostNetwork`.

**Сильные дополнения:**
- «StatefulSet **не реплицирует данные** — он даёт только identity, порядок и диски.
  Репликация и failover — задача приложения или оператора».
- «PVC не удаляются ни при уменьшении реплик, ни при удалении StatefulSet —
  это частая причина забытых дисков и счетов в облаке».
- «Для прод-БД я предпочитаю managed-сервис или зрелый оператор,
  а StatefulSet руками — для dev и для приложений, которые умеют кластеризоваться сами».

</details>

### 2. Расскажи про архитектуру Kubernetes ⭐

<details><summary>Ответ</summary>

**Как отвечать:** не списком компонентов, а **путём пода**. Это сразу отличает
понимание от зубрёжки.

**Короткий ответ:**
> «Кластер делится на control plane и рабочие ноды. В control plane: **API server** —
> единственная точка входа и единственный клиент **etcd**, где хранится всё состояние;
> **scheduler** выбирает ноду для новых подов; **controller manager** — набор циклов,
> сверяющих желаемое и фактическое состояние; **cloud-controller-manager** отвечает
> за интеграцию с облаком. На каждой ноде: **kubelet** — агент, запускающий поды
> через CRI, **container runtime** (containerd), **kube-proxy**, программирующий
> правила сети для Service, плюс CNI-плагин. Все компоненты общаются только
> через API server».

**Дальше — путь пода:**
```text:no-line-numbers
kubectl apply → API server (аутентификация → RBAC → admission → валидация) → etcd
  → Deployment-контроллер создаёт ReplicaSet
  → ReplicaSet создаёт поды без nodeName
  → scheduler: фильтрация нод → скоринг → binding (записывает nodeName)
  → kubelet нужной ноды: CNI даёт IP, монтируются тома, CRI тянет образ и запускает
  → probe'ы → под Ready → EndpointSlice → kube-proxy обновляет правила → трафик пошёл
```

**Сильные дополнения:**
- «etcd требует кворума: 3 узла переживают потерю одного, 5 — двух; нечётное число
  обязательно. Снапшот etcd — единственный настоящий бэкап кластера».
- «Падение control plane не останавливает работающие поды и трафик: теряется
  управление, а не обслуживание».
- «Scheduler ноду выбирает, но контейнеры не запускает — это делает kubelet».
- «kube-proxy не пропускает трафик через себя, он только программирует iptables/IPVS».

</details>

### 3. Какие типы сервисов (Service) бывают? ⭐

<details><summary>Ответ</summary>

**Короткий ответ:**
> «**ClusterIP** — по умолчанию, доступ только внутри кластера по виртуальному IP
> и DNS-имени. **NodePort** — открывает порт из диапазона 30000-32767 на каждой ноде.
> **LoadBalancer** — просит облако создать внешний балансировщик; включает в себя
> NodePort и ClusterIP. **ExternalName** — DNS-алиас на внешнее имя без проксирования.
> Отдельно стоит **headless** — ClusterIP со значением `None`: DNS возвращает адреса
> всех подов, нужен для StatefulSet и клиентской балансировки».

**Сильные дополнения:**
- «Service — это не процесс: kube-proxy программирует правила ядра, и ClusterIP
  не существует ни на одном интерфейсе».
- «Связь с подами — через метки; результат виден в EndpointSlice. Первое,
  что я проверяю при "сервис не работает", — `kubectl get endpoints`:
  пусто означает несовпадение меток или неготовые поды».
- «`externalTrafficPolicy: Local` сохраняет реальный IP клиента, но ноды без подов
  перестают отвечать; `Cluster` балансирует ровнее, но применяет SNAT».
- «В проде наружу обычно смотрит один LoadBalancer для Ingress Controller
  (или Gateway), а приложения публикуются через Ingress или HTTPRoute — иначе
  получится счёт за десяток балансировщиков».
- «Service работает на L4: маршрутизации по URL и заголовкам нет — это Ingress».

</details>

### 4. Почему именно под, а не контейнер считается минимальной единицей? ⭐

<details><summary>Ответ</summary>

**Короткий ответ:**
> «Под — это группа из одного или нескольких контейнеров с общими сетевым namespace,
> томами и жизненным циклом. Так сделано, потому что часть задач требует нескольких
> процессов, работающих "как на одной машине": приложение и сборщик логов, приложение
> и прокси service mesh. Класть их в один контейнер неправильно — принцип "один
> контейнер, один процесс"; разносить по разным подам нельзя — они потеряют общий
> localhost и общие файлы. Плюс планировать, перезапускать и адресовать удобнее
> одну неделимую единицу: у пода один IP, и именно под является целью Service».

**Сильные дополнения:**
- «Namespace'ы пода удерживает служебный pause-контейнер, поэтому контейнеры
  приложения можно перезапускать, не теряя IP пода».
- «Под — абстракция самого Kubernetes, не зависящая от конкретного runtime;
  это одна из причин, почему уход от Docker прошёл незаметно для пользователей».
- «На практике 90 % подов содержат один контейнер — под нужен как единица
  абстракции, а не как повод складывать туда несколько процессов».

</details>

### 5. В чём разница между Ingress и Ingress Controller? ⭐

<details><summary>Ответ</summary>

**Короткий ответ:**
> «**Ingress** — объект Kubernetes, набор правил: какой хост и путь ведут к какому
> сервису, где TLS. Сам по себе он ничего не делает. **Ingress Controller** —
> реально работающее в кластере приложение, обычно nginx или Traefik, которое следит
> за объектами Ingress, превращает их в свою конфигурацию и фактически принимает
> и проксирует трафик. Если контроллера нет, объекты Ingress создаются, но не работают:
> у них остаётся пустой ADDRESS».

**Сильные дополнения:**
- «Один контроллер обслуживает десятки Ingress'ов; какой именно — задаётся
  `ingressClassName`».
- «Ingress работает на L7: маршрутизация по хосту и пути, терминация TLS,
  редиректы, лимиты. Service такого не умеет — он L4».
- «Сертификаты в проде выпускает cert-manager по аннотации, продление автоматическое».
- «Ingress Controller — критичный компонент: минимум две реплики, anti-affinity и PDB,
  иначе обновление ноды уронит весь вход в кластер».
- «Ограничения Ingress (аннотации вместо типизированных полей, только HTTP,
  нельзя ссылаться на сервис из другого namespace) решает Gateway API:
  GatewayClass → Gateway → HTTPRoute с разделением ролей между платформой и командами».
- «Актуально на 2026: самый популярный контроллер, ingress-nginx, в EOL
  с 24 марта 2026 — репозиторий в архиве, CVE не чинят. Сам Ingress API
  не deprecated. Новые проекты начинаю с Gateway API, legacy мигрирую через
  ingress2gateway с ручной доработкой аннотаций».

</details>

### 6. Как работает HPA? ⭐

<details><summary>Ответ</summary>

**Короткий ответ:**
> «HorizontalPodAutoscaler примерно раз в 15 секунд забирает метрики из Metrics API,
> считает среднее по готовым подам и вычисляет желаемое число реплик по формуле
> `ceil(текущие × факт / цель)`. Есть зона нечувствительности около 10 %, ограничения
> `minReplicas`/`maxReplicas` и окно стабилизации при уменьшении — по умолчанию
> 5 минут. Утилизация CPU считается **в процентах от `requests`**, поэтому без
> заданных requests HPA не работает вовсе, и нужен установленный metrics-server».

**Пример вслух:** «Три реплики, средняя загрузка 90 %, цель 70 %:
`ceil(3 × 90/70) = ceil(3.86) = 4` реплики».

**Сильные дополнения:**
- «При нескольких метриках считается желаемое число по каждой и берётся максимум».
- «Секция `behavior` управляет скоростью роста и снижения — полезно, когда
  приложение долго стартует или трафик резко скачет».
- «Если в манифесте или чарте оставлен `replicas`, каждый деплой будет перетирать
  решения HPA — это частая ошибка».
- «HPA не масштабирует до нуля — это умеет KEDA; она же скейлит по очередям».
- «HPA добавляет поды, но если на нодах нет места, они встанут в `Pending` —
  нужен Cluster Autoscaler. И скейлинг не лечит узкое место в базе:
  больше подов означает больше нагрузки на неё».

</details>

### 7. Что такое Affinity и Anti-Affinity? ⭐

<details><summary>Ответ</summary>

**Короткий ответ:**
> «Это правила размещения подов. **nodeAffinity** — притяжение пода к нодам
> по их меткам, более гибкая версия `nodeSelector`: поддерживает операторы,
> логическое ИЛИ и мягкие правила с весами. **podAffinity** — разместить под рядом
> с определёнными подами, **podAntiAffinity** — наоборот, не размещать вместе.
> Область "вместе" задаётся `topologyKey`: нода, зона, регион. Чаще всего
> anti-affinity используют, чтобы развести реплики одного приложения по разным
> нодам и зонам — тогда падение ноды не уносит приложение целиком».

**Сильные дополнения:**
- «Правила бывают жёсткие (`requiredDuringScheduling…`) — иначе под `Pending`,
  и мягкие (`preferredDuringScheduling…`) с весами. Суффикс
  `IgnoredDuringExecution` означает, что правила проверяются только при планировании:
  если метки ноды изменились, работающий под не выселяется».
- «Anti-affinity дорого обходится планировщику на больших кластерах, поэтому
  для равномерного распределения чаще берут `topologySpreadConstraints` с `maxSkew`».
- «Важно не путать с taint'ами: affinity описывается в поде и притягивает,
  а taint ставится на ноду и отталкивает. Toleration лишь разрешает попасть
  на ноду с taint, но не притягивает туда — нужен ещё селектор».
- «Anti-affinity без PodDisruptionBudget неполна: реплики разнесены, но `drain`
  может снести их одновременно».

</details>

## 📚 Часть 2. Дополнительные вопросы по темам

### Основы и архитектура

**1. Что такое Kubernetes и какую задачу решает?**

<details><summary>Ответ</summary>

Оркестратор контейнеров: держит фактическое состояние равным описанному — запускает,
перезапускает, распределяет, масштабирует, обновляет, связывает сервисы.

</details>

**2. Что такое reconciliation loop?**

<details><summary>Ответ</summary>

Цикл, в котором контроллер сравнивает `spec` и `status` и устраняет разницу.
Основа всего кубера.

</details>

**3. Чем кубер отличается от docker compose?**

<details><summary>Ответ</summary>

Кластер вместо одного хоста, самовосстановление между нодами, встроенная балансировка,
rolling update с проверками, конфиги и секреты как объекты API.

</details>

**4. Что хранится в etcd?**

<details><summary>Ответ</summary>

Все объекты кластера и их состояние. Пишет туда только API server.

</details>

**5. Что произойдёт, если упадёт API server?**

<details><summary>Ответ</summary>

Потеряется управление: kubectl, создание и пересоздание подов. Работающие поды
и трафик не пострадают.

</details>

**6. Что произойдёт, если упадёт нода?**

<details><summary>Ответ</summary>

Через ~40 секунд `NotReady`, ещё примерно через 5 минут поды вытесняются
и пересоздаются на других нодах (`tolerationSeconds: 300` у taint'ов
`not-ready`/`unreachable`).

</details>

**7. Что делает kubelet?**

<details><summary>Ответ</summary>

Запускает и останавливает поды через CRI, монтирует тома и конфиги, выполняет
probe'ы, отправляет статус, вытесняет поды при нехватке ресурсов, обслуживает
статические поды.

</details>

**8. Что такое статические поды?**

<details><summary>Ответ</summary>

Поды из `/etc/kubernetes/manifests`, которыми управляет kubelet напрямую.
Так запускается control plane.

</details>

**9. Почему кубер «отказался от Docker»?**

<details><summary>Ответ</summary>

Удалён dockershim — прослойка для Docker Engine. Работают runtime с CRI
(containerd, CRI-O); образы и Dockerfile не меняются.

</details>

**10. Что такое admission-контроллеры?**

<details><summary>Ответ</summary>

Компоненты, которые после авторизации изменяют или проверяют объект: квоты,
Pod Security, mutating/validating webhooks.

</details>

### Поды и контроллеры

**11. Какие бывают фазы пода?**

<details><summary>Ответ</summary>

Pending, Running, Succeeded, Failed, Unknown.

</details>

**12. Что такое CrashLoopBackOff?**

<details><summary>Ответ</summary>

Цикл падений и перезапусков с экспоненциально растущей задержкой (до 5 минут).
Разбор — `logs --previous` и `Last State`.

</details>

**13. Что означает Exit Code 137?**

<details><summary>Ответ</summary>

SIGKILL, чаще всего OOMKilled.

</details>

**14. Что происходит при удалении пода?**

<details><summary>Ответ</summary>

Под убирается из Endpoints, выполняется `preStop`, контейнерам приходит SIGTERM,
ждём `terminationGracePeriodSeconds` (30 с), затем SIGKILL.

</details>

**15. Почему при выкатке возможны 502?**

<details><summary>Ответ</summary>

Удаление из Endpoints и остановка идут параллельно, правила на нодах обновляются
с задержкой. Лечение — `preStop`-пауза и корректная обработка SIGTERM.

</details>

**16. Что такое init-контейнер?**

<details><summary>Ответ</summary>

Контейнер, выполняемый до основных, по очереди, до успешного завершения:
ожидание зависимости, миграции, подготовка файлов.

</details>

**17. Что такое sidecar?**

<details><summary>Ответ</summary>

Вспомогательный контейнер рядом с приложением; с 1.29 объявляется как
init-контейнер с `restartPolicy: Always`.

</details>

**18. Почему нельзя запускать голые поды в проде?**

<details><summary>Ответ</summary>

Их некому восстановить: нет контроллера, нет обновлений и масштабирования.

</details>

**19. Что такое ReplicaSet и кто его создаёт?**

<details><summary>Ответ</summary>

Контроллер числа реплик; создаётся Deployment'ом при каждом изменении шаблона пода.

</details>

**20. Что вызывает новую выкатку Deployment?**

<details><summary>Ответ</summary>

Любое изменение `spec.template`. Изменение `replicas` — не вызывает.

</details>

**21. Как работает RollingUpdate?**

<details><summary>Ответ</summary>

Постепенная замена подов с ограничениями `maxSurge` и `maxUnavailable`;
безопасный дефолт — `1/0`.

</details>

**22. Когда нужен Recreate?**

<details><summary>Ответ</summary>

Когда две версии не могут работать одновременно: общий RWO-том, несовместимая
схема БД, лицензия на один экземпляр.

</details>

**23. Как откатить релиз?**

<details><summary>Ответ</summary>

`kubectl rollout undo` — работает благодаря сохранённым ReplicaSet'ам прошлых
ревизий (`revisionHistoryLimit`).

</details>

**24. Чем Job отличается от Deployment?**

<details><summary>Ответ</summary>

Job выполняет задачу до успешного завершения и останавливается.

</details>

**25. Что делают completions и parallelism?**

<details><summary>Ответ</summary>

Сколько успешных завершений нужно и сколько подов работает одновременно.

</details>

**26. Как не копить завершённые поды?**

<details><summary>Ответ</summary>

`ttlSecondsAfterFinished` и `successfulJobsHistoryLimit`.

</details>

**27. Что такое concurrencyPolicy у CronJob?**

<details><summary>Ответ</summary>

`Allow`, `Forbid`, `Replace` — поведение при наложении запусков.

</details>

**28. Как правильно выполнять миграции БД?**

<details><summary>Ответ</summary>

Отдельным Job до обновления образа (или Helm-хуком `pre-upgrade`), с ожиданием
завершения; миграции — обратно совместимые.

</details>

### Конфигурация и ресурсы

**29. Чем ConfigMap отличается от Secret?**

<details><summary>Ответ</summary>

Назначением и обращением: Secret для чувствительных данных, хранится в base64,
скрыт в `describe`, монтируется в память, требует отдельного RBAC.

</details>

**30. Secret зашифрован?**

<details><summary>Ответ</summary>

Нет, это кодирование. Нужны encryption at rest, RBAC и внешние хранилища
(Vault через ESO, SOPS, Sealed Secrets).

</details>

**31. Обновится ли конфиг в работающем поде?**

<details><summary>Ответ</summary>

Переменные окружения — нет; файлы из тома — да (кроме `subPath`), но приложение
должно их перечитать.

</details>

**32. Как заставить поды перечитать конфиг?**

<details><summary>Ответ</summary>

`kubectl rollout restart` или checksum-аннотация в шаблоне пода.

</details>

**33. Чем requests отличается от limits?**

<details><summary>Ответ</summary>

requests — гарантия и основа планирования; limits — потолок потребления.

</details>

**34. Что будет при превышении лимитов?**

<details><summary>Ответ</summary>

CPU — throttling; память — OOMKilled (137).

</details>

**35. Какие бывают QoS-классы?**

<details><summary>Ответ</summary>

Guaranteed (requests == limits), Burstable, BestEffort; вытесняются в обратном
порядке.

</details>

**36. Чем liveness отличается от readiness?**

<details><summary>Ответ</summary>

Liveness перезапускает контейнер, readiness исключает под из Endpoints, не трогая
контейнер.

</details>

**37. Зачем startupProbe?**

<details><summary>Ответ</summary>

Для медленно стартующих приложений: пока она идёт, остальные пробы не выполняются.

</details>

**38. Почему liveness не должна проверять базу?**

<details><summary>Ответ</summary>

Недоступность базы приведёт к рестарту всех реплик и каскадному отказу.

</details>

**39. Что такое LimitRange и ResourceQuota?**

<details><summary>Ответ</summary>

Значения по умолчанию и границы для контейнеров против суммарных ограничений
на namespace.

</details>

### Сеть

**40. Как устроена сеть в кубере?**

<details><summary>Ответ</summary>

Плоская: у каждого пода свой IP, поды общаются без NAT; реализует это CNI-плагин,
кубер задаёт только требования.

</details>

**41. Что такое CNI и какие плагины знаешь?**

<details><summary>Ответ</summary>

Стандарт подключения сети; Calico, Cilium, Flannel, Weave.

</details>

**42. Чем оверлей отличается от маршрутизации?**

<details><summary>Ответ</summary>

Инкапсуляция (работает везде, режет MTU) против обычных маршрутов (быстрее,
нужна поддержка сети).

</details>

**43. Что делает kube-proxy?**

<details><summary>Ответ</summary>

Программирует правила ядра (iptables/IPVS/nftables) для Service; трафик через
него не идёт.

</details>

**44. Что такое EndpointSlice?**

<details><summary>Ответ</summary>

Список адресов за сервисом, разбитый на срезы ради масштабируемости.

</details>

**45. Как работает DNS в кластере?**

<details><summary>Ответ</summary>

CoreDNS резолвит `service.namespace.svc.cluster.local`; адрес DNS прописан
в `resolv.conf` подов.

</details>

**46. Что такое ndots:5?**

<details><summary>Ответ</summary>

Порог, ниже которого имя достраивается суффиксами из `search` — источник
лишних запросов и «медленного DNS».

</details>

**47. Что произойдёт при падении CoreDNS?**

<details><summary>Ответ</summary>

Перестанут резолвиться имена; внешне это выглядит как полный отказ, хотя поды живы.

</details>

**48. Почему сервис может не отвечать?**

<details><summary>Ответ</summary>

Несовпадение меток, неготовые поды, неверный `targetPort`, приложение слушает
`127.0.0.1`, NetworkPolicy, разные namespace.

</details>

**49. Что такое NetworkPolicy и от чего зависит её работа?**

<details><summary>Ответ</summary>

Firewall уровня пода; исполняется CNI-плагином — Flannel её игнорирует.

</details>

**50. Что нужно разрешить сразу после default-deny?**

<details><summary>Ответ</summary>

DNS (порт 53 к CoreDNS), иначе «ломается всё».

</details>

**51. Изолирует ли namespace сеть?**

<details><summary>Ответ</summary>

Нет, только имена, права и квоты.

</details>

**52. Что означают 404/502/503 от ingress-nginx?**

<details><summary>Ответ</summary>

Не совпало правило; бэкенд не отвечает; нет endpoints.

</details>

**53. ingress-nginx ретайрнут — что делать?**

<details><summary>Ответ</summary>

Не паниковать: умер контроллер, а не Ingress API (EOL 24.03.2026, финальный
`controller-v1.15.1`, CVE больше не чинят). Инвентаризация Ingress'ов и аннотаций →
выбор цели (реализация Gateway API, например Envoy Gateway, или поддерживаемый
Ingress-контроллер) → ingress2gateway как черновик → ручной перенос snippets
и аннотаций без аналога → параллельный запуск → переключение DNS → удаление старого.
До конца миграции — сузить поверхность атаки: admission webhook доступен только
API server'у, NetworkPolicy.

</details>

**54. Ingress vs Gateway API?**

<details><summary>Ответ</summary>

Ingress — один объект: HTTP, хост/путь → Service, расширения аннотациями
конкретного контроллера, бэкенд только в своём namespace. Gateway API — роли:
GatewayClass (реализация), Gateway (вход, TLS, кому можно цепляться),
HTTPRoute/GRPCRoute (правила команды); веса, фильтры и заголовки — типизированными
полями, cross-namespace через `allowedRoutes` и ReferenceGrant, у маршрута есть
статус (`Accepted`, `ResolvedRefs`).

</details>

### Хранилище

**55. Что такое PV, PVC, StorageClass?**

<details><summary>Ответ</summary>

Ресурс хранения, заявка приложения и описание того, как создавать тома автоматически.

</details>

**56. Какие бывают access modes?**

<details><summary>Ответ</summary>

RWO (одна нода), ROX (много нод, чтение), RWX (много нод, запись), RWOP (один под).

</details>

**57. Почему три реплики не могут использовать один RWO-том?**

<details><summary>Ответ</summary>

Том монтируется только на одной ноде: остальные поды получат `Multi-Attach error`.

</details>

**58. Как дать каждой реплике свой диск?**

<details><summary>Ответ</summary>

StatefulSet с `volumeClaimTemplates`.

</details>

**59. Что такое reclaimPolicy?**

<details><summary>Ответ</summary>

Что делать с PV после удаления PVC: `Delete` (удалить вместе с данными) или
`Retain` (сохранить).

</details>

**60. Что делает WaitForFirstConsumer?**

<details><summary>Ответ</summary>

Откладывает создание тома до планирования пода, чтобы диск появился в нужной зоне.

</details>

**61. Что произойдёт с PVC при удалении StatefulSet?**

<details><summary>Ответ</summary>

Останутся; удалять вручную.

</details>

**62. Снапшот — это бэкап?**

<details><summary>Ответ</summary>

Нет: он в той же системе хранения и не проверен восстановлением.

</details>

### Helm, доставка, эксплуатация

**63. Что такое Helm?**

<details><summary>Ответ</summary>

Пакетный менеджер: чарт (шаблоны + значения) превращается в релиз с историей
и откатом.

</details>

**64. Чем version отличается от appVersion?**

<details><summary>Ответ</summary>

Версия чарта против версии приложения.

</details>

**65. Какой приоритет у values?**

<details><summary>Ответ</summary>

`values.yaml` → файлы `-f` по порядку → `--set`.

</details>

**66. Как деплоят через Helm в CI?**

<details><summary>Ответ</summary>

`helm upgrade --install` с `-f values-<env>.yaml`, `--set image.tag=$SHA`,
`--atomic` и `--timeout`.

</details>

**67. Где Helm 3 хранит состояние?**

<details><summary>Ответ</summary>

В Secret'ах namespace релиза; Tiller'а нет.

</details>

**68. Что такое GitOps?**

<details><summary>Ответ</summary>

Желаемое состояние в git, агент в кластере приводит кластер к нему; откат —
`git revert`, дрейф виден и исправляется.

</details>

**69. Что такое CRD и оператор?**

<details><summary>Ответ</summary>

Свой тип объекта и контроллер, который кодирует знания администратора о его
эксплуатации.

</details>

**70. Что такое service mesh и когда он нужен?**

<details><summary>Ответ</summary>

Прокси у каждого сервиса: mTLS, L7-маршрутизация, устойчивость, наблюдаемость.
Нужен при большом числе сервисов и соответствующих требованиях; иначе слишком дорог.

</details>

**71. Как бэкапить кластер?**

<details><summary>Ответ</summary>

Снапшот etcd (для самосборного) вне кластера с проверкой восстановления; Velero
для объектов и томов; данные приложений отдельно.

</details>

**72. Что такое RBAC?**

<details><summary>Ответ</summary>

Субъекты, роли и биндинги; по умолчанию запрещено всё, запрещающих правил не бывает.

</details>

**73. Какие комбинации Role/Binding возможны?**

<details><summary>Ответ</summary>

RoleBinding+Role, RoleBinding+ClusterRole (права в одном namespace),
ClusterRoleBinding+ClusterRole; ClusterRoleBinding+Role невозможен.

</details>

**74. Как развернуть кластер?**

<details><summary>Ответ</summary>

kubeadm, kubespray (Ansible поверх kubeadm), managed-сервисы облаков.

</details>

**75. Что делает kubeadm init?**

<details><summary>Ответ</summary>

Проверки, PKI, kubeconfig'и, статические поды control plane, запуск kubelet,
bootstrap-токены, CoreDNS и kube-proxy.

</details>

**76. Как вывести ноду на обслуживание?**

<details><summary>Ответ</summary>

`cordon` + `drain --ignore-daemonsets`, затем `uncordon`; PDB защищает от
одновременного вытеснения всех реплик.

</details>

**77. Что такое PodDisruptionBudget?**

<details><summary>Ответ</summary>

Ограничение числа одновременно недоступных подов при добровольных нарушениях
(drain, обновления); от падения ноды не защищает.

</details>

**78. Как вы обновляете кластер?**

<details><summary>Ответ</summary>

Регулярно и по одной минорной, как проект: changelog, устаревшие API (pluto +
метрика `apiserver_requested_deprecated_apis`), матрица аддонов (Envoy Gateway v1.9
держит на ≤ 1.36), staging; в проде — снапшот etcd вне кластера, control plane →
аддоны → ноды по одной с drain и PDB, post-checks. Даунгрейда нет: откат — снапшот
etcd или blue/green-кластер с переключением трафика (тема 24).

</details>

**79. Что такое version skew policy?**

<details><summary>Ответ</summary>

kubelet не новее apiserver и старше максимум на 3 минорные; controller-manager/scheduler
— не новее и максимум на 1 старше; kubectl — ±1. Отсюда порядок: apiserver →
controller-manager/scheduler → ноды (24).

</details>

**80. Как узнать, кто удалил deployment?**

<details><summary>Ответ</summary>

По аудит-логу apiserver (`audit.k8s.io/v1`): событие `delete` — `user.username`,
`impersonatedUser`, `sourceIPs`, `userAgent`; если это SA ArgoCD — искать коммит
в git. Events не помогут: пользователя в них нет, живут около часа. Аудит включают
до инцидента; секреты — только уровень `Metadata` (24).

</details>

**81. Что изменилось в Helm 4?**

<details><summary>Ответ</summary>

Server-side apply для новых релизов (старые остаются client-side), `--atomic` →
`--rollback-on-failure`, `--force` → `--force-replace`, ожидание по kstatus,
WASM-плагины, post-renderer как плагин, OCI по digest; чарты v2 работают.
Helm 3 получает security-фиксы до 10.02.2027 — CI пора переводить (25).

</details>

## 🛠️ Часть 3. Практические задания на собеседовании

Часто дают доступ к кластеру или просят порассуждать вслух. Типовые задания:

| Задание | Что проверяют | Как действовать |
|---------|---------------|-----------------|
| «Под в CrashLoopBackOff, разберись» | Алгоритм отладки | `describe` → `logs --previous` → Exit Code → причина |
| «Сервис не отвечает» | Понимание сети | `get endpoints` → IP пода → ClusterIP → DNS → политики |
| «Напиши манифест Deployment с probe'ами» | Знание синтаксиса | Генерируй через `--dry-run=client -o yaml`, дополняй руками |
| «Под в Pending, почему?» | Планировщик | `describe pod` → `FailedScheduling` → ресурсы/метки/taint/тома |
| «Опиши, как катится релиз у вас» | Реальный опыт | Пайплайн → образ с тегом коммита → `helm upgrade --install --atomic` → `rollout status` → откат |
| «Нарисуй архитектуру кластера» | База | Control plane + ноды + путь пода |
| «Как обеспечить отказоустойчивость приложения?» | Инженерное мышление | Реплики + anti-affinity/spread + PDB + probe'ы + ресурсы + graceful shutdown |

**Как себя вести:**
1. **Рассуждай вслух.** Ход мысли ценнее готового ответа: «сначала посмотрю события,
   потому что там пишет планировщик…».
2. **Уточняй.** «Кластер managed или свой?», «Приложение stateless?» — уточняющий
   вопрос почти всегда плюс.
3. **Не знаешь — скажи честно и покажи, как найдёшь.** «Наизусть не помню,
   посмотрю в `kubectl explain` / документации» — нормальный ответ.
4. **Приводи примеры из практики.** Даже учебной: «я ломал readiness в своём
   кластере и видел, что под выпадает из Endpoints без рестарта».
5. **Признавай сложность.** «Mesh я бы здесь не брал — дорого в эксплуатации» звучит
   сильнее, чем перечисление модных технологий.
6. **Не спорь с ошибочной формулировкой агрессивно.** «Обычно это описывают так…»
   мягче, чем «вы неправы».
