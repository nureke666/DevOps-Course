## 1. GitOps: ArgoCD и Flux ⭐

**Идея:** желаемое состояние кластера лежит в git, а агент внутри кластера
непрерывно приводит кластер к этому состоянию. Никто не делает `kubectl apply`
руками и даже из пайплайна.

```text:no-line-numbers
  разработчик → MR в git-репозиторий с манифестами/чартом
                        │
                        ▼
              ArgoCD/Flux (в кластере) видит изменение
                        │
                        ▼
              применяет в кластер и следит за дрейфом
                        │
                        ▼
              состояние в кластере == состояние в git
```

| Push (классический CI) | Pull (GitOps) |
|------------------------|---------------|
| Пайплайн ходит в кластер с правами | Агент в кластере сам забирает из git |
| Креды кластера лежат в CI | Кластер наружу не открыт |
| Дрейф не отслеживается | Дрейф виден и автоматически исправляется |
| Откат = повторный деплой | Откат = `git revert` |

### ArgoCD за 10 минут
```bash
kubectl create namespace argocd
kubectl apply -n argocd -f https://raw.githubusercontent.com/argoproj/argo-cd/stable/manifests/install.yaml
kubectl -n argocd get secret argocd-initial-admin-secret \
  -o jsonpath="{.data.password}" | base64 -d; echo
kubectl port-forward svc/argocd-server -n argocd 8080:443
```
```yaml
apiVersion: argoproj.io/v1alpha1
kind: Application
metadata:
  name: myapp
  namespace: argocd
spec:
  project: default
  source:
    repoURL: https://gitlab.com/me/myapp-config.git
    targetRevision: main
    path: chart
    helm:
      valueFiles: [values-prod.yaml]
  destination:
    server: https://kubernetes.default.svc
    namespace: prod
  syncPolicy:
    automated:
      prune: true          # удалять то, чего больше нет в git
      selfHeal: true       # ⭐ возвращать ручные изменения
    syncOptions: [CreateNamespace=true]
```

| | ArgoCD | Flux |
|---|---|---|
| Интерфейс | Богатый веб-UI | CLI и CRD, UI отдельно |
| Модель | Application/ApplicationSet | набор контроллеров (source, kustomize, helm) |
| Порог входа | Ниже, нагляднее | Легче встраивается «в код» |
| Мультикластер | Из одного ArgoCD в несколько кластеров | Обычно по агенту на кластер |

**Обязательный приём:** репозиторий с кодом и репозиторий с конфигурацией
разделяют. Пайплайн собирает образ и делает коммит с новым тегом в config-репозиторий;
дальше работает GitOps-агент.

## 2. Операторы и CRD

**CRD (CustomResourceDefinition)** — способ добавить в кубер свой тип объекта.
**Оператор** — контроллер, который этот тип обслуживает, воспроизводя работу
человека-администратора.

```yaml
apiVersion: apiextensions.k8s.io/v1
kind: CustomResourceDefinition
metadata:
  name: backups.ops.example.com
spec:
  group: ops.example.com
  names: { kind: Backup, plural: backups, singular: backup, shortNames: [bk] }
  scope: Namespaced
  versions:
    - name: v1
      served: true
      storage: true
      schema:
        openAPIV3Schema:
          type: object
          properties:
            spec:
              type: object
              properties:
                schedule: { type: string }
                target:   { type: string }
```
После этого работает `kubectl get backups`, как для встроенных типов.

**Зачем операторы:** сложные системы требуют не только «запустить под», а знания
предметной области: как сделать failover PostgreSQL, как расширить кластер Kafka,
как выполнить обновление без потери данных. Оператор кодирует эти знания.

| Известные операторы | Что делают |
|---------------------|------------|
| CloudNativePG, Zalando postgres-operator | PostgreSQL с репликацией, бэкапами, failover |
| Strimzi | Kafka |
| Prometheus Operator | Prometheus, Alertmanager, ServiceMonitor |
| cert-manager | сертификаты |
| Redis/MongoDB/Elasticsearch операторы | соответствующие СУБД |

**Как писать свои:** Kubebuilder или Operator SDK (Go), kopf (Python),
Shell-operator / Ansible-operator для простых случаев. Начинать стоит с чтения
чужого оператора и с простого контроллера на 100 строк.

> 💡 Первый практический шаг в этом направлении обычно не «написать оператор»,
> а «поставить и настроить чужой» — например, Prometheus Operator
> с `ServiceMonitor` для своего приложения.

## 3. Service Mesh: Istio и Linkerd

**Идея:** рядом с каждым подом (или на ноде) работает прокси, через который идёт
весь трафик между сервисами. Прокси даёт то, чего нет в самом кубере.

| Возможность | Что это даёт |
|-------------|--------------|
| mTLS между сервисами | Шифрование и аутентификация без изменения кода |
| L7-маршрутизация | Деление трафика по версиям, заголовкам, процентам |
| Ретраи, таймауты, circuit breaking | Устойчивость без правок приложения |
| Наблюдаемость | Метрики, трассировки и карта сервисов «из коробки» |
| Политики доступа | Кто с кем может общаться на уровне L7 |

| | Istio | Linkerd |
|---|---|---|
| Мощность | Очень высокая | Достаточная для большинства задач |
| Сложность | Высокая | Низкая, «ставится и работает» |
| Прокси | Envoy | Собственный лёгкий прокси на Rust |
| Режимы | sidecar и ambient (без sidecar) | sidecar |

**Цена:** дополнительный контейнер у каждого пода (или новый слой на ноде),
рост потребления ресурсов и задержек, ещё одна сложная система в эксплуатации
и в отладке инцидентов.

> 🎤 Здравая позиция для собеса: «Mesh даёт mTLS, канареечный трафик и наблюдаемость
> без изменения кода, но это серьёзная сложность. Я бы брал его, когда сервисов
> действительно много и есть требования к mTLS и тонкой маршрутизации;
> для 5-10 сервисов дешевле обойтись Ingress, ретраями в коде и Prometheus».

## 4. Бэкап etcd и disaster recovery ⭐

Единственный настоящий бэкап самосборного кластера — снапшот etcd.

```bash
# снятие снапшота (на control-plane ноде)
ETCDCTL_API=3 etcdctl \
  --endpoints=https://127.0.0.1:2379 \
  --cacert=/etc/kubernetes/pki/etcd/ca.crt \
  --cert=/etc/kubernetes/pki/etcd/server.crt \
  --key=/etc/kubernetes/pki/etcd/server.key \
  snapshot save /backup/etcd-$(date +%F-%H%M).db

etcdctl snapshot status /backup/etcd-*.db --write-out=table
```
```bash
# восстановление (упрощённо)
systemctl stop kubelet                       # останавливаем control plane
etcdctl snapshot restore /backup/etcd.db --data-dir=/var/lib/etcd-restored
mv /var/lib/etcd /var/lib/etcd-old && mv /var/lib/etcd-restored /var/lib/etcd
systemctl start kubelet
```

| Правило | Почему |
|---------|--------|
| Снапшот по расписанию (CronJob или systemd-timer) | Ручной бэкап не делается никогда |
| Хранить **вне кластера** | Кластер умер вместе с бэкапом — не бэкап |
| Проверять восстановлением | Непроверенный бэкап не существует |
| Помнить: etcd не хранит данные приложений | Тома и БД бэкапятся отдельно |

**Velero** — бэкап уровня Kubernetes: сохраняет объекты (манифесты) и снапшоты PV
в объектное хранилище, умеет восстанавливать в другой кластер и мигрировать namespace.

```bash
velero backup create prod-daily --include-namespaces prod
velero restore create --from-backup prod-daily
```

| | Снапшот etcd | Velero |
|---|---|---|
| Что сохраняет | Всё состояние кластера целиком | Выбранные объекты + тома |
| Гранулярность | Только «весь кластер» | Namespace, метки, отдельные ресурсы |
| Восстановление в другой кластер | Нет | Да |
| Managed-кластер | Недоступен | Работает |

## 5. Multi-cluster стратегии

Зачем несколько кластеров: изоляция окружений, разные регионы, отказоустойчивость,
требования регуляторов, разделение по командам, ограничение «радиуса поражения».

| Стратегия | Суть | Сложность |
|-----------|------|-----------|
| Отдельные кластеры, общий GitOps | Один ArgoCD катит во все | ⭐ Низкая, начинать отсюда |
| Active-passive | Второй кластер в горячем резерве | Средняя |
| Active-active | Трафик распределяется глобальным балансировщиком | Высокая |
| Cluster API | Кубер управляет кластерами как объектами | Высокая |
| Karmada / Cluster Federation | Единое управление нагрузками во многих кластерах | Высокая |
| Multi-cluster mesh | Сервисы «видят» друг друга через mesh | Очень высокая |

Что становится трудным: DNS и маршрутизация между кластерами, синхронизация
секретов и конфигураций, реплицированное состояние (БД), наблюдаемость с общей
картиной, стоимость.

**Практичный первый шаг:** два кластера (dev и prod), один GitOps-репозиторий,
разные `values` — и никакой федерации, пока она реально не понадобится.

## 7. Как выбирать направление

```text:no-line-numbers
Ты работаешь в компании, где кубер уже есть?
   └─ да  → спроси, что болит: доставка (GitOps), безопасность (RBAC/политики),
            надёжность (бэкапы, multi-cluster), наблюдаемость.
            Бери то, что нужно команде — это самый быстрый рост.

Ты учишься самостоятельно?
   └─ порядок по практической ценности:
      1. GitOps (ArgoCD) — встречается почти в каждой вакансии
      2. Prometheus + алерты — без наблюдаемости кластер не эксплуатируют
      3. Бэкап etcd / Velero — вопрос на собесе и реальный риск
      4. Операторы (поставить и настроить чужой)
      5. Service mesh — когда есть настоящая потребность
      6. Multi-cluster — в последнюю очередь
```

## 💼 Как это в DevOps

- GitOps — самый востребованный пункт списка: он меняет процесс доставки целиком
  и его спрашивают на собеседованиях чаще, чем mesh и операторы вместе.
- Бэкап etcd — тот случай, когда отсутствие навыка замечают ровно один раз.
  Проверяй восстановление на тестовом кластере, а не на проде.
- Про mesh важно уметь сказать «нет»: осознанный отказ от лишней сложности
  ценится не меньше, чем умение его внедрить.
- Операторы — хороший способ перейти от «пишу YAML» к «пишу софт для кубера»:
  начни с простого контроллера, который следит за своим CRD.
- Мультикластер почти всегда начинается не с федерации, а с дисциплины:
  один способ деплоя, одинаковые чарты, разные values.

## 🧠 Что запомнить

1. Развилка роадмапа: GitOps, операторы, mesh, бэкап etcd, multi-cluster, траблшутинг.
2. ⭐ GitOps — приоритет №1: агент в кластере приводит состояние к описанному в git.
3. ArgoCD `selfHeal` устраняет дрейф, `prune` удаляет лишнее; откат — это `git revert`.
4. Репозиторий кода и репозиторий конфигурации разделяют.
5. CRD добавляет тип объекта, оператор — контроллер, который его обслуживает.
6. Операторы кодируют знания администратора: failover, обновления, бэкапы.
7. Service mesh даёт mTLS, L7-маршрутизацию и наблюдаемость ценой сложности.
8. ⭐ Единственный бэкап самосборного кластера — снапшот etcd; хранить вне кластера
   и проверять восстановлением.
9. etcd не хранит данные приложений: тома и БД бэкапятся отдельно (Velero, дампы).
10. Velero умеет восстанавливать объекты и тома, в том числе в другой кластер.
11. Multi-cluster начинается с одного GitOps-репозитория, а не с федерации.
12. Умение отказаться от лишней сложности — такой же навык, как умение её внедрить.

### Блок A. Теория

**A1.** ⭐ Что такое GitOps и чем отличается от обычного деплоя из пайплайна?

<details><summary>Ответ</summary>

Подход, при котором желаемое состояние системы описано в git,
а агент внутри кластера непрерывно приводит кластер к этому состоянию.
В отличие от деплоя из пайплайна, изменения применяет не CI, а агент,
и расхождение (дрейф) постоянно отслеживается.

</details>

**A2.** Чем push-модель отличается от pull-модели? Плюсы каждой.

<details><summary>Ответ</summary>

Push: пайплайн сам ходит в кластер — проще начать, но нужны креды
кластера в CI и нет контроля дрейфа. Pull: агент забирает состояние из git —
кластер не открыт наружу, дрейф виден и исправляется, но нужен ещё один компонент.

</details>

**A3.** Почему при GitOps не нужно давать CI доступ к кластеру?

<details><summary>Ответ</summary>

Потому что применяет манифесты агент изнутри кластера; CI лишь
коммитит изменения в репозиторий конфигурации.

</details>

**A4.** Что такое дрейф конфигурации и как GitOps с ним борется?

<details><summary>Ответ</summary>

Дрейф — расхождение фактического состояния кластера с описанным в git
(чей-то `kubectl edit`, ручной scale). GitOps его показывает и при `selfHeal`
автоматически возвращает состояние из git.

</details>

**A5.** Что делают `prune` и `selfHeal` в ArgoCD?

<details><summary>Ответ</summary>

`prune` удаляет из кластера объекты, исчезнувшие из git;
`selfHeal` возвращает объекты к состоянию из git при ручных изменениях.

</details>

**A6.** Как выглядит откат релиза в GitOps?

<details><summary>Ответ</summary>

`git revert` нужного коммита: агент увидит изменение и вернёт кластер
к предыдущему состоянию.

</details>

**A7.** Почему репозиторий кода и репозиторий конфигурации разделяют?

<details><summary>Ответ</summary>

Чтобы изменение конфигурации не требовало коммита в код (и наоборот),
чтобы у них были разные права доступа и история, и чтобы автоматический коммит
тега образа не смешивался с историей разработки.

</details>

**A8.** Чем ArgoCD отличается от Flux?

<details><summary>Ответ</summary>

ArgoCD — единое приложение с богатым UI и объектами Application;
Flux — набор контроллеров, более «кодовый» подход, легко встраивается
в автоматизацию. Оба реализуют pull-модель.

</details>

**A9.** ⭐ Что такое CRD и что такое оператор?

<details><summary>Ответ</summary>

CRD — определение собственного типа объекта в API кубера;
оператор — контроллер, который следит за такими объектами и выполняет
действия, приводящие систему к описанному состоянию.

</details>

**A10.** Зачем нужны операторы, если есть Helm?

<details><summary>Ответ</summary>

Helm умеет установить набор манифестов, но не умеет эксплуатировать
систему: делать failover, обновлять кластер БД по шагам, снимать бэкапы,
реагировать на сбои. Это и делает оператор.

</details>

**A11.** Назови четыре известных оператора и что они делают.

<details><summary>Ответ</summary>

CloudNativePG/Zalando postgres-operator (PostgreSQL), Strimzi (Kafka),
Prometheus Operator (мониторинг), cert-manager (сертификаты).

</details>

**A12.** На чём пишут операторы?

<details><summary>Ответ</summary>

Kubebuilder и Operator SDK (Go), kopf (Python), shell-operator
и ansible-operator для простых сценариев.

</details>

**A13.** ⭐ Что такое service mesh и какие задачи он решает?

<details><summary>Ответ</summary>

Слой прокси рядом с каждым сервисом, который берёт на себя mTLS,
L7-маршрутизацию, ретраи и таймауты, наблюдаемость и политики доступа
без изменения кода приложений.

</details>

**A14.** Как mesh даёт mTLS без изменения кода приложения?

<details><summary>Ответ</summary>

Прокси перехватывает весь входящий и исходящий трафик пода
и устанавливает взаимно аутентифицированные TLS-соединения с прокси
других сервисов, используя сертификаты, выпускаемые control plane mesh.

</details>

**A15.** Чем Istio отличается от Linkerd?

<details><summary>Ответ</summary>

Istio мощнее и сложнее (Envoy, множество CRD, режимы sidecar и ambient);
Linkerd проще, легче по ресурсам и быстрее внедряется, но с меньшим набором
возможностей.

</details>

**A16.** Какова цена внедрения mesh?

<details><summary>Ответ</summary>

Дополнительный контейнер (или слой) на каждый под: ресурсы, задержки,
усложнение отладки, ещё одна система, которую нужно обновлять и понимать.

</details>

**A17.** Когда mesh не нужен?

<details><summary>Ответ</summary>

При небольшом числе сервисов, отсутствии требований к mTLS
и сложной маршрутизации: дешевле обойтись Ingress, ретраями в коде,
Prometheus и OpenTelemetry.

</details>

**A18.** ⭐ Как сделать бэкап etcd и что он содержит?

<details><summary>Ответ</summary>

`etcdctl snapshot save` с сертификатами кластера; снапшот содержит
все объекты Kubernetes и их состояние.

</details>

**A19.** Содержит ли снапшот etcd данные приложений из PVC?

<details><summary>Ответ</summary>

Нет: данные приложений лежат в PV/внешних системах и бэкапятся отдельно.

</details>

**A20.** Где нужно хранить снапшоты и почему?

<details><summary>Ответ</summary>

Вне кластера и вне той же ноды: бэкап, погибший вместе с кластером,
бесполезен. Плюс шифрование — в снапшоте есть секреты.

</details>

**A21.** Что такое Velero и чем отличается от снапшота etcd?

<details><summary>Ответ</summary>

Инструмент бэкапа уровня Kubernetes: сохраняет выбранные объекты
и снапшоты томов в объектное хранилище, умеет восстанавливать в другой кластер
и работает в managed-кластерах.

</details>

**A22.** Можно ли сделать снапшот etcd в managed-кластере?

<details><summary>Ответ</summary>

Нет: доступа к etcd там нет. Используются Velero и бэкапы на уровне
провайдера.

</details>

**A23.** Зачем компании несколько кластеров? Назови четыре причины.

<details><summary>Ответ</summary>

Изоляция окружений и «радиуса поражения», разные регионы и задержки,
требования регуляторов и данных, разделение по командам и SLA, отказоустойчивость.

</details>

**A24.** Какие сложности появляются при multi-cluster?

<details><summary>Ответ</summary>

Маршрутизация и DNS между кластерами, синхронизация конфигураций
и секретов, реплицирование состояния, общая наблюдаемость, стоимость
и сложность эксплуатации.

</details>

**A25.** С чего разумно начать мультикластерную стратегию?

<details><summary>Ответ</summary>

С двух независимых кластеров, управляемых одним GitOps-репозиторием
с разными values; федерация — только когда без неё действительно нельзя.

</details>

**A26.** Что такое Cluster API и Karmada?

<details><summary>Ответ</summary>

Cluster API — управление жизненным циклом кластеров через объекты
Kubernetes; Karmada — распределение и управление нагрузками сразу в нескольких
кластерах.

</details>

**A27.** Что такое Argo Rollouts/Flagger и чем отличаются от обычного Deployment?

<details><summary>Ответ</summary>

Контроллеры прогрессивной доставки: канареечные и blue-green релизы
с анализом метрик и автоматическим откатом, чего штатный Deployment не умеет.

</details>

**A28.** Какие направления ты бы выбрал первыми и почему?

<details><summary>Ответ</summary>

Обычно: GitOps, затем наблюдаемость и алерты, затем бэкап и DR;
операторы, mesh и multi-cluster — по реальной потребности.

</details>

### Блок B. «Что произойдёт»

```yaml
# B1
syncPolicy:
  automated:
    selfHeal: true
# кто-то сделал kubectl scale deployment web --replicas=10
```
Вопрос: что произойдёт через минуту?

<details><summary>Ответ</summary>

ArgoCD обнаружит расхождение с git и вернёт число реплик
к описанному в репозитории.

</details>

```yaml
# B2
syncPolicy:
  automated:
    prune: false
# из git удалили манифест Service
```
Вопрос: удалится ли Service из кластера?

<details><summary>Ответ</summary>

Нет: при `prune: false` объекты, исчезнувшие из git, остаются в кластере
(ArgoCD лишь покажет расхождение).

</details>

```bash
# B3
# ArgoCD показывает статус OutOfSync
```
Вопрос: что это означает и какие причины бывают?

<details><summary>Ответ</summary>

Фактическое состояние отличается от описанного: ручные изменения,
мутирующие webhooks, поля, проставляемые кубером, различия в форматировании
или HPA, меняющий реплики.

</details>

```bash
# B4
# снапшот etcd лежит на той же ноде, что и etcd
# нода сгорела
```
Вопрос: что осталось?

<details><summary>Ответ</summary>

Ничего: бэкап нужно хранить вне кластера и вне той же машины.

</details>

```bash
# B5
etcdctl snapshot restore backup.db --data-dir=/var/lib/etcd-new
# при этом control plane не останавливали
```
Вопрос: чем это опасно?

<details><summary>Ответ</summary>

Работающие компоненты продолжают писать в старый каталог данных,
восстановление окажется неконсистентным. Control plane обязательно останавливают.

</details>

```bash
# B6
# восстановили кластер из снапшота недельной давности
```
Вопрос: что вернётся, а что нет?

<details><summary>Ответ</summary>

Вернутся объекты кластера на момент снимка (деплойменты, секреты,
конфиги); не вернутся изменения за неделю и данные приложений в томах —
может возникнуть рассинхронизация между объектами и реальными данными.

</details>

```yaml
# B7
# в кластер внедрили Istio, у каждого пода появился sidecar
```
Вопрос: как это отразится на ресурсах и на отладке?

<details><summary>Ответ</summary>

Вырастет потребление CPU и памяти (на каждый под), немного вырастут
задержки, усложнится отладка: в цепочке появляется дополнительный прокси,
логи и метрики которого тоже нужно смотреть.

</details>

```bash
# B8
# CI делает kubectl apply, а ArgoCD следит за тем же namespace
```
Вопрос: что будет происходить с объектами?

<details><summary>Ответ</summary>

Конфликт: ArgoCD будет возвращать состояние к описанному в git,
а CI — накатывать своё. Нужно выбрать один источник правды (обычно git + ArgoCD).

</details>

### Блок C. Практика

#### C1. 🔑 ArgoCD: установка и первое приложение
1. Установи ArgoCD в kind-кластер.
2. Получи пароль администратора, зайди в UI через `port-forward`.
3. Создай репозиторий (можно публичный на GitLab/GitHub) с чартом из темы 15.
4. Создай `Application` и дождись синхронизации.
5. Проверь, что приложение задеплоилось.

#### C2. 🔑 selfHeal
1. Включи `selfHeal: true`.
2. Сделай `kubectl scale deployment ... --replicas=10`.
3. Наблюдай, что произойдёт.
4. Сформулируй, как это меняет процесс работы команды.

<details><summary>Ответ</summary>

Реплики вернутся к значению из git — ручные изменения перестают быть
рабочим инструментом, всё идёт через MR.

</details>

#### C3. Откат через git
1. Измени тег образа в git — дождись синхронизации.
2. Сделай `git revert` предыдущего коммита.
3. Замерь, за сколько кластер вернулся к старой версии.

#### C4. prune
1. Удали из git один манифест при `prune: false` — проверь кластер.
2. Включи `prune: true` и повтори.

#### C5. Разделение репозиториев (со звёздочкой)
Собери схему: репозиторий приложения (код + Dockerfile + пайплайн) и репозиторий
конфигурации (чарт + values). Пайплайн после сборки образа коммитит новый тег
в config-репозиторий. Опиши шаги; реализуй, если есть возможность.

#### C6. CRD своими руками
1. Создай CRD `Backup` из конспекта.
2. Примени объект этого типа.
3. Проверь `kubectl get backups`, `kubectl describe backup`.
4. Объясни, почему ничего не происходит (нет контроллера).

<details><summary>Ответ</summary>

Объект создаётся и хранится в etcd, но никаких действий не происходит:
CRD добавляет только тип, а поведение обеспечивает контроллер (оператор).

</details>

#### C7. Чужой оператор
Установи Prometheus Operator (kube-prometheus-stack) и:
1. Создай `ServiceMonitor` для своего приложения.
2. Проверь, что метрики появились в Prometheus.
3. Опиши, какие CRD принёс с собой оператор.

#### C8. Оператор БД (со звёздочкой)
Установи CloudNativePG (или другой PostgreSQL-оператор) и создай кластер БД
из трёх узлов. Проверь, что произойдёт при удалении пода-лидера.
Сравни с ручным StatefulSet из темы 06.

#### C9. 🔑 Бэкап etcd
1. Сними снапшот etcd на kind-кластере.
2. Скопируй файл за пределы кластера.
3. Посмотри `etcdctl snapshot status`.
4. Опиши по шагам процедуру восстановления.
5. Если не страшно — создай отдельный кластер и потренируйся восстановить.

<details><summary>Ответ</summary>

Проверь, что файл читается `snapshot status`, и опиши шаги:
остановить control plane, восстановить в новый каталог, подменить каталог данных,
запустить компоненты.

</details>

#### C10. Velero (со звёздочкой)
Установи Velero с MinIO в качестве хранилища, сделай бэкап namespace,
удали namespace и восстанови его. Запиши, что восстановилось, а что нет.

#### C11. Linkerd (со звёздочкой)
Установи Linkerd в kind-кластер, добавь свой namespace в mesh
и посмотри дашборд: карта сервисов, успешность запросов, задержки.
Оцени, сколько ресурсов добавили sidecar'ы.

#### C12. Canary по метрикам (со звёздочкой)
Прочитай документацию Argo Rollouts и опиши, как выглядит автоматический
канареечный релиз с откатом по метрике ошибок.

#### C13. Выбор направления
Напиши в заметку короткий план: какое направление берёшь следующим,
почему, какой первый практический шаг и как поймёшь, что освоил.

### Блок D. Инциденты и обсуждения

**D1.** В компании деплой идёт через `kubectl apply` из пайплайна,
креды прода лежат в CI. Какие риски и что предложишь?

<details><summary>Ответ</summary>

Риски: компрометация CI даёт доступ к проду, нет контроля дрейфа,
права избыточны. Предложить GitOps (агент в кластере) либо, как минимум,
отдельный SA с минимальными правами и защищённые переменные.

</details>

**D2.** После внедрения ArgoCD разработчики жалуются: «мои ручные правки
откатываются». Как объяснить и как выстроить процесс?

<details><summary>Ответ</summary>

Это ожидаемое поведение: источник правды — git. Выстроить процесс так,
чтобы правки шли через MR, а для срочных случаев была процедура
(временное отключение автосинхронизации с последующим приведением git в порядок).

</details>

**D3.** ArgoCD показывает `OutOfSync` постоянно, хотя никто ничего не менял.
Возможные причины?

<details><summary>Ответ</summary>

Мутирующие webhooks и поля, добавляемые кубером; HPA, меняющий реплики;
различия форматирования; `Job`/`CronJob`-объекты; неверно настроенные
`ignoreDifferences`.

</details>

**D4.** Кластер умер, снапшота etcd нет, но все манифесты в git.
Что можно восстановить и что потеряно?

<details><summary>Ответ</summary>

Можно восстановить приложения и конфигурацию, применив манифесты
в новый кластер; потеряны сам кластер, объекты, созданные вручную,
и данные томов, если они не бэкапились отдельно.

</details>

**D5.** Бэкапы etcd делаются год, восстановление никогда не проверялось.
Какой у этого статус на самом деле?

<details><summary>Ответ</summary>

Бэкапов фактически нет: непроверенное восстановление — это гипотеза,
а не процедура. Нужно регулярно восстанавливать на тестовом стенде.

</details>

**D6.** Руководство просит внедрить Istio «потому что микросервисы».
Как построить разговор?

<details><summary>Ответ</summary>

Выяснить конкретные задачи: mTLS, канареечные релизы, наблюдаемость,
политики. Оценить, решаются ли они более дешёвыми средствами; предложить
пилот на части сервисов и честно назвать цену внедрения и эксплуатации.

</details>

**D7.** После внедрения mesh выросли задержки и потребление памяти.
Что показать и какие варианты предложить?

<details><summary>Ответ</summary>

Показать метрики до и после, оценить ресурсы sidecar'ов; варианты:
настройка ресурсов прокси, ambient-режим, переход на более лёгкий mesh,
сужение периметра до сервисов, которым mesh реально нужен.

</details>

**D8.** Компания хочет два кластера в разных регионах для отказоустойчивости.
Какие вопросы задашь до начала работ?

<details><summary>Ответ</summary>

Что именно резервируется (данные, трафик, control plane), какой
допустимый RTO/RPO, как реплицируется состояние, как переключается трафик,
кто и как принимает решение о переключении, как тестируется переключение,
какова стоимость.

</details>

**D9.** Оператор БД удалил PVC при удалении кастомного ресурса.
Как этого избежать в будущем?

<details><summary>Ответ</summary>

Настроить политику сохранения томов в самом операторе,
`reclaimPolicy: Retain` в StorageClass, финализаторы и бэкапы;
проверять поведение оператора на тестовом стенде до прода.

</details>

**D10.** В GitOps-репозитории лежат секреты открытым текстом.
Что предложишь (три варианта)?

<details><summary>Ответ</summary>

SOPS с ключом в KMS/age, Sealed Secrets, External Secrets Operator
поверх Vault или облачного менеджера секретов.

</details>

### Блок E. Вопросы с собеседования

**1.** ⭐ Что такое GitOps? Чем отличается от CI/CD-деплоя?

<details><summary>Ответ</summary>

Описание желаемого состояния в git и агент в кластере, который непрерывно
приводит кластер к нему; в отличие от push-деплоя, есть контроль дрейфа
и не нужны креды кластера в CI.

</details>

**2.** Что такое ArgoCD и как он работает?

<details><summary>Ответ</summary>

Контроллер, следящий за репозиторием и синхронизирующий манифесты/чарты
с кластером; объект Application описывает источник, назначение и политику синхронизации.

</details>

**3.** Что такое дрейф и как его устраняют?

<details><summary>Ответ</summary>

Расхождение кластера с git; устраняется синхронизацией, а при `selfHeal` —
автоматически.

</details>

**4.** ⭐ Что такое оператор и CRD?

<details><summary>Ответ</summary>

CRD — новый тип объекта в API; оператор — контроллер, реализующий
его поведение и кодирующий знания администратора.

</details>

**5.** Зачем нужен оператор, если есть Helm?

<details><summary>Ответ</summary>

Helm устанавливает, оператор эксплуатирует: обновления, failover, бэкапы,
реакция на сбои.

</details>

**6.** Что такое service mesh и когда он нужен?

<details><summary>Ответ</summary>

Слой прокси для межсервисного трафика: mTLS, маршрутизация, устойчивость,
наблюдаемость. Нужен при большом числе сервисов и соответствующих требованиях.

</details>

**7.** Что даёт mTLS в mesh?

<details><summary>Ответ</summary>

Взаимную аутентификацию и шифрование трафика между сервисами
без изменения кода приложений.

</details>

**8.** ⭐ Как бэкапить кластер?

<details><summary>Ответ</summary>

Снапшот etcd для самосборного кластера (вне кластера, с проверкой
восстановления) и Velero для объектов и томов; данные приложений — отдельно.

</details>

**9.** Что содержит снапшот etcd и чего в нём нет?

<details><summary>Ответ</summary>

Все объекты Kubernetes и их состояние; данных из PV и внешних систем в нём нет.

</details>

**10.** Зачем несколько кластеров и какие есть стратегии?

<details><summary>Ответ</summary>

Изоляция, регионы, регуляторы, отказоустойчивость; стратегии —
от независимых кластеров с общим GitOps до active-active и федерации.

</details>
