## 1. Что нужно для работы HPA

| Требование | Почему |
|------------|--------|
| **metrics-server** установлен | HPA берёт метрики из Metrics API |
| У контейнеров заданы **`requests`** | Загрузка CPU считается в процентах **от requests** |
| Приложение **stateless** и масштабируемо | Иначе скейлить бессмысленно |
| В манифесте **нет** фиксированного `replicas` (или он не перетирается) | Иначе деплой откатывает решения HPA |

```bash
kubectl apply -f https://github.com/kubernetes-sigs/metrics-server/releases/latest/download/components.yaml
kubectl top nodes
kubectl top pods
```

## 2. Манифест HPA (autoscaling/v2)

```yaml
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: web
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: web
  minReplicas: 2
  maxReplicas: 20
  metrics:
    - type: Resource
      resource:
        name: cpu
        target:
          type: Utilization
          averageUtilization: 70        # ⭐ 70 % от requests.cpu
    - type: Resource
      resource:
        name: memory
        target:
          type: Utilization
          averageUtilization: 80
  behavior:                              # ⭐ управление скоростью
    scaleUp:
      stabilizationWindowSeconds: 0
      policies:
        - { type: Percent, value: 100, periodSeconds: 30 }   # удваивать не чаще раза в 30 с
        - { type: Pods,    value: 4,   periodSeconds: 30 }
      selectPolicy: Max
    scaleDown:
      stabilizationWindowSeconds: 300    # 5 минут «остывания» перед уменьшением
      policies:
        - { type: Percent, value: 50, periodSeconds: 60 }
```

Быстрый способ:
```bash
kubectl autoscale deployment web --cpu-percent=70 --min=2 --max=10
kubectl get hpa
# NAME  REFERENCE         TARGETS        MINPODS  MAXPODS  REPLICAS
# web   Deployment/web    45%/70%        2        10       3
kubectl describe hpa web
```

## 3. ⭐ Формула (главный вопрос собеса)

```text:no-line-numbers
желаемые_реплики = ceil( текущие_реплики × ( текущая_метрика / целевая_метрика ) )
```

**Пример:** 3 реплики, средняя загрузка 90 %, цель 70 %.
```text:no-line-numbers
ceil(3 × (90 / 70)) = ceil(3.857) = 4 реплики
```

Дополнительные правила:

| Правило | Смысл |
|---------|-------|
| Толерантность 10 % | Если отношение в пределах 0.9-1.1, ничего не делается — чтобы не «дёргать» |
| Период проверки | По умолчанию раз в 15 секунд |
| Неготовые поды | Не учитываются при расчёте (или считаются консервативно) |
| Несколько метрик | Считается по каждой, берётся **максимум** желаемых реплик |
| Границы | Результат ограничивается `minReplicas`/`maxReplicas` |
| Уменьшение | Сглаживается окном стабилизации (по умолчанию 300 секунд) |

> 🎤 Ответ на собесе: «HPA раз в 15 секунд берёт метрики из Metrics API, считает
> среднее по готовым подам и вычисляет желаемое число реплик как текущее,
> умноженное на отношение факта к цели, с округлением вверх; есть зона
> нечувствительности 10 %, ограничения min/max и окно стабилизации при уменьшении.
> Загрузка CPU считается в процентах от `requests`, поэтому без requests HPA не работает».

## 4. Метрики, кроме CPU

| Тип | Откуда | Пример |
|-----|--------|--------|
| `Resource` | metrics-server | CPU, память |
| `Pods` | Custom Metrics API (prometheus-adapter) | среднее число запросов на под |
| `Object` | Custom Metrics API | RPS у Ingress, длина очереди |
| `External` | External Metrics API | глубина очереди в Kafka/SQS, метрика облака |

```yaml
  metrics:
    - type: Pods
      pods:
        metric: { name: http_requests_per_second }
        target: { type: AverageValue, averageValue: "100" }
    - type: External
      external:
        metric:
          name: kafka_consumergroup_lag
          selector: { matchLabels: { topic: orders } }
        target: { type: AverageValue, averageValue: "1000" }
```

Для внешних метрик обычно используют **KEDA** — она умеет скейлить по Kafka, RabbitMQ,
очередям облаков, cron-расписанию и даже **до нуля** (чего HPA не умеет).

> Память как метрика HPA работает плохо: многие рантаймы (JVM, Go) не отдают память
> обратно, и уменьшение реплик не происходит. Масштабируют обычно по CPU
> или по прикладной метрике.

## 5. VPA — вертикальный автоскейлинг

Подбирает `requests`/`limits` вместо числа реплик.

| Режим | Что делает |
|-------|------------|
| `Off` | ⭐ Только рекомендации — самый полезный режим на практике |
| `Initial` | Применяет значения при создании пода |
| `Auto`/`Recreate` | Пересоздаёт поды с новыми значениями |

```bash
kubectl describe vpa web | grep -A8 "Recommendation"
```

> ⚠️ **VPA и HPA по одной метрике (CPU) вместе использовать нельзя** — они будут
> конфликтовать. Рабочее сочетание: HPA по CPU + VPA в режиме рекомендаций
> для памяти. В новых версиях кубера появилась возможность менять ресурсы пода
> без рестарта, что постепенно снимает главное неудобство VPA.

---

## 6. Cluster Autoscaler — автоскейлинг нод

HPA добавил поды, а места на нодах нет → поды `Pending` → **Cluster Autoscaler**
добавляет ноду в облаке.

| Событие | Реакция |
|---------|---------|
| Есть поды `Pending` из-за нехватки ресурсов | Добавить ноду (если group не на максимуме) |
| Нода недогружена ~10 минут и её поды помещаются на другие | Удалить ноду |

Что мешает удалить ноду: поды без контроллера, поды с `hostPath`/локальными томами,
поды с жёстким PDB, поды системных namespace без разрешающей аннотации.

**Karpenter** (AWS и не только) — более быстрая альтернатива: подбирает тип и размер
инстанса под конкретные ожидающие поды, а не масштабирует заранее заданные группы.

## 7. Почему HPA «не работает» — чек-лист

```bash
kubectl get hpa
# TARGETS: <unknown>/70%        ← метрик нет
kubectl describe hpa web
kubectl top pods
kubectl get apiservice v1beta1.metrics.k8s.io
```

| Симптом | Причина |
|---------|---------|
| `TARGETS: <unknown>` | Нет metrics-server, или он не готов, или проблема с сертификатами kubelet |
| `TARGETS: <unknown>` при живом metrics-server | У контейнеров не заданы `requests.cpu` |
| Реплики не растут | Достигнут `maxReplicas`; метрика ниже цели; поды `Pending` из-за ресурсов |
| Реплики не уменьшаются | Окно стабилизации (5 минут); метрика всё ещё высокая; память не освобождается |
| Реплики «пилят» вверх-вниз | Слишком низкая цель или резкий трафик; настрой `behavior` |
| HPA скейлит, деплой возвращает | В манифесте/чарте задан `replicas` — убрать |
| Скейлит, но приложению не легче | Узкое место снаружи (БД, внешний API) — поды не помогут |

## 💼 Как это в DevOps

- HPA — первое, что включают для веб-нагрузок с неравномерным трафиком;
  цель по CPU обычно 60-75 %.
- Обязательное условие — корректные `requests`. Половина «неработающего HPA» —
  это забытые ресурсы в манифесте.
- HPA не спасает от узкого места в БД: рост числа подов только увеличит нагрузку
  на неё. Всегда смотри, где реальное ограничение.
- Связка HPA + Cluster Autoscaler работает только при нормальных `requests`:
  иначе ноды добавляются впустую или не добавляются вовсе.
- Для очередей и событийных нагрузок берут KEDA: она умеет скейлить до нуля
  и по десяткам источников.

| Хочу | Как |

| Подобрать ресурсы | VPA в режиме `Off` (рекомендации) |
| Добавлять ноды автоматически | Cluster Autoscaler / Karpenter |
| Временно отключить HPA | Удалить объект или выставить min=max |

## 🧠 Что запомнить

1. HPA меняет **число реплик**, VPA — **ресурсы пода**, Cluster Autoscaler — **число нод**.
2. ⭐ Формула: `желаемые = ceil(текущие × факт / цель)`; период — около 15 секунд.
3. Загрузка CPU считается **в процентах от `requests`** — без requests HPA не работает.
4. Нужен metrics-server; без него `TARGETS: <unknown>`.
5. Есть зона нечувствительности около 10 % — HPA не реагирует на мелкие колебания.
6. При нескольких метриках берётся максимум из посчитанных значений.
7. Уменьшение сглаживается окном стабилизации (по умолчанию 300 секунд).
8. `behavior` управляет скоростью роста и снижения.
9. Если в манифесте задан `replicas`, деплой будет перетирать решения HPA.
10. Память — плохая метрика для HPA; лучше CPU или прикладные метрики.
11. HPA до нуля не масштабирует — это умеет KEDA.
12. Скейлинг не лечит узкое место в зависимостях: больше подов — больше нагрузка на БД.

## Задачи

> ⭐ Вопрос собеса: *«Как работает HPA?»* — нужно уметь назвать формулу
> и условия работы, а не только «добавляет поды под нагрузкой».

---

### Блок A. Теория

**A1.** ⭐ Что делает HPA? Чем отличается от VPA и Cluster Autoscaler?

<details><summary>Ответ</summary>

HPA изменяет число реплик рабочей нагрузки по метрикам; VPA подбирает
`requests`/`limits` для подов; Cluster Autoscaler добавляет и убирает ноды кластера.

</details>

**A2.** Что нужно установить, чтобы HPA заработал?

<details><summary>Ответ</summary>

metrics-server (для CPU и памяти); для прикладных метрик —
prometheus-adapter или KEDA.

</details>

**A3.** ⭐ Почему без `requests.cpu` HPA не работает?

<details><summary>Ответ</summary>

Утилизация считается как отношение фактического потребления к `requests`.
Без requests база для процента отсутствует, и метрика не вычисляется.

</details>

**A4.** ⭐ Напиши формулу расчёта желаемого числа реплик и разбери на примере.

<details><summary>Ответ</summary>

`желаемые = ceil(текущие × факт / цель)`. Например, 3 реплики при 90 %
и цели 70 %: `ceil(3 × 90/70) = ceil(3.857) = 4`.

</details>

**A5.** Как часто HPA пересчитывает состояние?

<details><summary>Ответ</summary>

Примерно раз в 15 секунд (параметр контроллера).

</details>

**A6.** Что такое зона нечувствительности (толерантность) и зачем она?

<details><summary>Ответ</summary>

Около 10 %: если отношение факта к цели в пределах 0.9-1.1, изменений нет.
Защищает от постоянных мелких пересчётов.

</details>

**A7.** Что произойдёт, если задано несколько метрик?

<details><summary>Ответ</summary>

Для каждой метрики считается желаемое число реплик, применяется максимум.

</details>

**A8.** Учитываются ли неготовые поды при расчёте?

<details><summary>Ответ</summary>

Нет: неготовые и только что созданные поды исключаются из расчёта
(или учитываются консервативно), чтобы не завышать оценку.

</details>

**A9.** Что такое `stabilizationWindowSeconds` и почему оно разное для роста и снижения?

<details><summary>Ответ</summary>

Окно, в течение которого HPA берёт наибольшее из недавних рекомендаций.
Для снижения оно велико (по умолчанию 300 секунд), чтобы не убирать поды
при кратковременных провалах нагрузки; для роста — обычно 0, чтобы реагировать быстро.

</details>

**A10.** Что настраивается в секции `behavior`?

<details><summary>Ответ</summary>

Скорость и шаг изменения: политики (`Pods`, `Percent` за период),
выбор политики (`Max`/`Min`/`Disabled`) и окна стабилизации отдельно
для `scaleUp` и `scaleDown`.

</details>

**A11.** Может ли HPA уменьшить число реплик до нуля?

<details><summary>Ответ</summary>

Нет, минимум — 1 (масштабирование до нуля даёт KEDA).

</details>

**A12.** Какие типы метрик поддерживает `autoscaling/v2`?

<details><summary>Ответ</summary>

`Resource` (CPU/память), `Pods`, `Object`, `External`,
а также `ContainerResource`.

</details>

**A13.** Что такое prometheus-adapter и зачем он нужен?

<details><summary>Ответ</summary>

Компонент, который отдаёт метрики Prometheus через Custom Metrics API,
чтобы HPA мог использовать прикладные показатели.

</details>

**A14.** Что такое KEDA и какие задачи решает лучше HPA?

<details><summary>Ответ</summary>

Надстройка для событийного автоскейлинга: десятки триггеров (Kafka,
RabbitMQ, очереди облаков, cron, Prometheus) и масштабирование до нуля.

</details>

**A15.** Почему память — плохая метрика для автоскейлинга?

<details><summary>Ответ</summary>

Многие рантаймы не возвращают память ОС: потребление не снижается
после спада нагрузки, поэтому реплики не уменьшаются и скейлинг становится
односторонним.

</details>

**A16.** Что такое VPA и какие у неё режимы?

<details><summary>Ответ</summary>

Vertical Pod Autoscaler: подбирает requests/limits.
Режимы `Off` (рекомендации), `Initial` (при создании), `Auto`/`Recreate`
(с пересозданием подов).

</details>

**A17.** ⭐ Почему нельзя использовать VPA и HPA по одной метрике?

<details><summary>Ответ</summary>

Они управляют связанными величинами: VPA меняет requests, от которых
зависит расчёт утилизации в HPA, — получается положительная обратная связь
и нестабильность.

</details>

**A18.** Как работает Cluster Autoscaler? Что запускает добавление ноды?

<details><summary>Ответ</summary>

Следит за подами `Pending`, которые не помещаются на существующие ноды,
и добавляет ноды в группу; при длительной недогрузке ноды и возможности
разместить её поды в другом месте — удаляет.

</details>

**A19.** Что мешает Cluster Autoscaler удалить недогруженную ноду?

<details><summary>Ответ</summary>

Поды без контроллера, поды с локальными томами, жёсткие PDB,
системные поды без аннотации `safe-to-evict`, поды с ограничениями размещения.

</details>

**A20.** Чем Karpenter отличается от Cluster Autoscaler?

<details><summary>Ответ</summary>

Karpenter подбирает конкретные инстансы под ожидающие поды
(тип, размер, зона) без заранее заданных групп, работает быстрее
и лучше утилизирует ресурсы.

</details>

**A21.** ⭐ Что произойдёт, если в манифесте Deployment оставить `replicas` при включённом HPA?

<details><summary>Ответ</summary>

Каждый `apply`/`helm upgrade` будет возвращать число реплик к значению
из манифеста, обнуляя работу HPA, — приложение может резко просесть.

</details>

**A22.** Почему HPA может скейлить, но приложению не становится лучше?

<details><summary>Ответ</summary>

Узкое место не в подах: база данных, внешний API, блокировки,
ограничение по сети или диску. Больше реплик только увеличит нагрузку на это место.

</details>

**A23.** Какое целевое значение по CPU обычно выбирают и почему не 95 %?

<details><summary>Ответ</summary>

Обычно 60-75 %: нужен запас на всплески и на время старта новых подов;
при 95 % приложение уже деградирует, пока реплики поднимаются.

</details>

**A24.** Как временно отключить HPA?

<details><summary>Ответ</summary>

Удалить объект HPA либо задать `minReplicas = maxReplicas`
(или, в новых версиях, приостановить через аннотацию).

</details>

**A25.** Что показывает `TARGETS: <unknown>` и как это чинить?

<details><summary>Ответ</summary>

Метрики недоступны: не установлен или не работает metrics-server,
проблемы с его сертификатами, либо у контейнеров нет `requests`.

</details>

### Блок B. «Что произойдёт»

```text:no-line-numbers
# B1
реплик: 4, средняя загрузка CPU: 85 %, цель: 50 %
```
Вопрос: сколько реплик закажет HPA?

<details><summary>Ответ</summary>

`ceil(4 × 85/50) = ceil(6.8) = 7`.

</details>

```text:no-line-numbers
# B2
реплик: 5, загрузка 68 %, цель 70 %
```
Вопрос: что сделает HPA?

<details><summary>Ответ</summary>

Ничего: отношение 68/70 ≈ 0.97 попадает в зону нечувствительности.

</details>

```text:no-line-numbers
# B3
реплик: 10, загрузка 20 %, цель 70 %, minReplicas: 3
```
Вопрос: сколько реплик получится и как быстро?

<details><summary>Ответ</summary>

`ceil(10 × 20/70) = ceil(2.86) = 3` — ровно `minReplicas`;
снижение начнётся после окна стабилизации (по умолчанию 5 минут).

</details>

### Блок C. Практика

#### C1. Подготовка
1. Убедись, что metrics-server работает: `kubectl top nodes`, `kubectl top pods`.
2. Если нет — установи его (см. карту темы Kubernetes).
3. Проверь, что у твоего Deployment заданы `requests.cpu`.

#### C2. 🔑 Первый HPA
1. Включи автоскейлинг: `kubectl autoscale deploy web --cpu-percent=50 --min=1 --max=10`.
2. Посмотри `kubectl get hpa -w` в одном окне.
3. Во втором создай нагрузку (цикл `wget` из временного пода).
4. Запиши: через сколько секунд появились новые поды и сколько их стало.

<details><summary>Ответ</summary>

Обычно новые поды появляются в течение 15-60 секунд после роста нагрузки,
в зависимости от периода опроса и времени старта приложения.

</details>

#### C3. 🔑 Проверка формулы
1. Зафиксируй число реплик и среднюю загрузку (`kubectl top pods`).
2. Посчитай ожидаемое число реплик по формуле.
3. Сравни с фактическим решением HPA.
4. Повтори на другом уровне нагрузки.

#### C4. Снижение
1. Останови нагрузку.
2. Засеки, через сколько HPA начал уменьшать реплики.
3. Сопоставь с `stabilizationWindowSeconds` по умолчанию.

<details><summary>Ответ</summary>

Снижение начинается примерно через 5 минут после падения нагрузки —
это окно стабилизации по умолчанию.

</details>

#### C5. behavior
1. Поставь `scaleDown.stabilizationWindowSeconds: 30` и повтори эксперимент.
2. Поставь ограничение роста `policies: [{type: Pods, value: 1, periodSeconds: 60}]`
   и посмотри, как изменится скорость.
3. Запиши, в каких случаях нужен медленный рост, а в каких быстрый.

#### C6. Без requests
1. Убери `requests` у контейнера.
2. Посмотри `kubectl get hpa` и `describe hpa`.
3. Верни requests и убедись, что метрики появились.

<details><summary>Ответ</summary>

Без requests HPA показывает `<unknown>` и не принимает решений.

</details>

#### C7. maxReplicas
Поставь `maxReplicas: 3`, создай большую нагрузку и убедись, что HPA упёрся в потолок.
Найди соответствующее условие в `describe hpa`.

#### C8. HPA и Pending
1. Поставь большие `requests` и высокий `maxReplicas`.
2. Создай нагрузку, чтобы HPA заказал больше подов, чем помещается.
3. Посмотри, как часть подов остаётся `Pending`.
4. Сформулируй, зачем нужен Cluster Autoscaler.

#### C9. 🔑 HPA и деплой
1. Дай HPA раскачать приложение до 6 реплик.
2. Примени манифест с `replicas: 2`.
3. Посмотри, что произошло сразу и что через минуту.
4. Убери `replicas` из манифеста и повтори. Запиши правильный подход.

<details><summary>Ответ</summary>

Правильный подход: не указывать `replicas` в манифесте/чарте,
когда включён HPA (или явно исключать это поле из применения).

</details>

#### C10. Несколько метрик
Добавь метрику по памяти и понаблюдай, какая из метрик «выигрывает».
Объясни результат.

#### C11. VPA в режиме рекомендаций (со звёздочкой)
Установи VPA, создай объект с `updateMode: "Off"` и через некоторое время
посмотри рекомендации. Сравни с текущими значениями requests.

#### C12. Своя метрика (со звёздочкой)
Опиши (или настрой, если есть Prometheus) схему масштабирования по RPS:
что нужно установить, какие объекты создать, как выглядит HPA.

#### C13. KEDA (со звёздочкой)
Прочитай документацию KEDA и опиши в заметке: как выглядит ScaledObject,
как работает масштабирование до нуля, какие триггеры доступны.

### Блок D. Инциденты

**D1.** HPA создан, но `TARGETS: <unknown>` вторые сутки. Алгоритм разбора.

<details><summary>Ответ</summary>

Проверить `kubectl top pods` (работает ли Metrics API), состояние
metrics-server и его логи, наличие `requests` у контейнеров,
`kubectl describe hpa` и `kubectl get apiservice v1beta1.metrics.k8s.io`.

</details>

**D2.** Нагрузка выросла, HPA не добавляет поды. Четыре причины.

<details><summary>Ответ</summary>

Достигнут `maxReplicas`; метрика ниже цели (узкое место не в CPU);
метрики недоступны; новые поды `Pending` из-за нехватки ресурсов;
политики `behavior` ограничивают скорость.

</details>

**D3.** Число реплик «пилит» от 2 до 10 и обратно каждые пару минут. Что настроить?

<details><summary>Ответ</summary>

Увеличить окно стабилизации для снижения, ограничить шаг роста политиками,
поднять цель утилизации, увеличить `minReplicas`.

</details>

**D4.** HPA добавил 15 подов, но время ответа не улучшилось. Где искать проблему?

<details><summary>Ответ</summary>

Узкое место вне приложения: база, внешний сервис, сеть, блокировки.
Смотреть метрики зависимостей и профиль запроса, а не только CPU подов.

</details>

**D5.** После каждого деплоя приложение просаживается, а через минуту
восстанавливается. Причина?

<details><summary>Ответ</summary>

В манифесте задан `replicas`, и деплой сбрасывает число реплик,
поднятое HPA.

</details>

**D6.** Реплики не уменьшаются даже ночью при нулевом трафике. Гипотезы?

<details><summary>Ответ</summary>

Метрика не падает (память, фоновые задачи), окно стабилизации,
`minReplicas` установлен высоко, либо приложение держит соединения
и продолжает потреблять CPU.

</details>

**D7.** Cluster Autoscaler не удаляет пустые ноды. Что может мешать?

<details><summary>Ответ</summary>

Поды без контроллеров, локальные тома, PDB, системные поды
без разрешения на вытеснение, ограничение минимального размера группы нод.

</details>

**D8.** HPA скейлит по памяти, и количество реплик только растёт. Объясни.

<details><summary>Ответ</summary>

Приложение не возвращает память ОС: потребление остаётся высоким,
HPA не видит оснований уменьшать реплики. Масштабировать по CPU
или по прикладной метрике.

</details>

**D9.** Приложение скейлится, но база данных начинает отказывать. Что делать?

<details><summary>Ответ</summary>

Ограничить `maxReplicas`, добавить пул соединений и очередь,
масштабировать саму базу (реплики на чтение, кэш), применить backpressure
и ограничение частоты запросов.

</details>

**D10.** После включения VPA в режиме Auto поды постоянно перезапускаются
вместе с HPA. В чём ошибка?

<details><summary>Ответ</summary>

VPA в `Auto` меняет requests, HPA считает утилизацию от requests —
получается взаимное влияние и постоянные пересоздания подов. Использовать
VPA только в режиме рекомендаций либо по другой метрике.

</details>

### Блок E. Вопросы с собеседования

**1.** ⭐ Как работает HPA? *(вопрос роадмапа)*

<details><summary>Ответ</summary>

Контроллер, который раз в 15 секунд сравнивает метрику с целевой и меняет
число реплик по формуле `ceil(текущие × факт/цель)` с учётом зоны
нечувствительности, границ min/max и окон стабилизации.

</details>

**2.** Что нужно, чтобы HPA заработал?

<details><summary>Ответ</summary>

metrics-server (или адаптер прикладных метрик), заданные `requests`,
масштабируемое приложение и отсутствие фиксированного `replicas`.

</details>

**3.** По какой формуле считается число реплик?

<details><summary>Ответ</summary>

`желаемые = ceil(текущие × факт / цель)`.

</details>

**4.** Почему важны requests?

<details><summary>Ответ</summary>

Утилизация считается в процентах от requests; без них метрика не вычисляется.

</details>

**5.** Какие метрики можно использовать?

<details><summary>Ответ</summary>

CPU и память через Metrics API; прикладные через Custom Metrics API;
внешние (очереди, облачные метрики) через External Metrics API или KEDA.

</details>

**6.** Чем HPA отличается от VPA и Cluster Autoscaler?

<details><summary>Ответ</summary>

HPA — число реплик, VPA — ресурсы пода, Cluster Autoscaler — число нод.

</details>

**7.** Можно ли скейлить до нуля?

<details><summary>Ответ</summary>

HPA — нет; KEDA — да.

</details>

**8.** Почему HPA может не уменьшать реплики?

<details><summary>Ответ</summary>

Окно стабилизации, всё ещё высокая метрика (особенно память), `minReplicas`.

</details>

**9.** Что произойдёт, если в манифесте есть replicas?

<details><summary>Ответ</summary>

Каждый деплой будет возвращать это число, перетирая решения HPA.

</details>

**10.** Как масштабироваться по длине очереди?

<details><summary>Ответ</summary>

Через KEDA (ScaledObject с триггером на очередь) или через
External/Object-метрики в HPA с соответствующим адаптером.

</details>
