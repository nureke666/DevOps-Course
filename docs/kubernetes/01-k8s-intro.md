# 01. Зачем нужен Kubernetes

> Роадмап → 6. Kubernetes → вводная: «Самый важный инструмент для DevOps'а сейчас,
> большой и сложный, поэтому идёт только после всех основных технологий».
> **После темы ты умеешь:** объяснить, какую задачу решает оркестратор, чем он отличается
> от `docker compose`, и честно сказать, когда кубер не нужен.

---

## 🗺️ Карта темы

```text:no-line-numbers
Один контейнер на одном сервере              → docker run          (блок Docker)
Несколько контейнеров на одном сервере       → docker compose      (блок Docker)
Сотни контейнеров на десятках серверов       → KUBERNETES          (этот блок)
        │
        ├─ куда поставить контейнер?              → Scheduler
        ├─ что если нода умерла?                  → Controller manager
        ├─ как найти соседа по имени?             → Service + CoreDNS
        ├─ как обновить без даунтайма?            → Deployment / RollingUpdate
        ├─ как дать 10 копий и балансировку?      → ReplicaSet + Service
        └─ как хранить состояние и конфиги?       → PV/PVC, ConfigMap, Secret
```

---

## 1. Проблема, из которой вырос кубер

Ты уже умеешь: собрать образ, запустить контейнер, поднять стек через compose,
раскатать всё это Ansible'ом из пайплайна. Пока серверов 1-2 — этого хватает.
Дальше начинается то, что вручную не решается:

| Вопрос | Руками / compose | Kubernetes |
|--------|------------------|------------|
| Нода упала ночью | Дежурный руками перезапускает на другой | Контроллер сам пересоздаёт поды на живых нодах |
| Куда поставить новый контейнер | Человек смотрит `free -m` и решает | Scheduler считает `requests` и выбирает ноду |
| Приложение зависло, но процесс жив | Мониторинг → алерт → человек | `livenessProbe` → рестарт автоматически |
| Обновить 40 инстансов без даунтайма | Скрипт с циклом и надеждой | `RollingUpdate` + `readinessProbe` |
| Откатить неудачный релиз | Заново катим старый тег | `kubectl rollout undo` — одна команда |
| Нагрузка выросла в 5 раз | Руками добавляем инстансы | HPA добавляет реплики по метрике |
| Приложение ищет базу | IP в конфиге / `/etc/hosts` | DNS-имя сервиса, IP не важен |
| Сертификаты, конфиги, пароли | Разложены по серверам | ConfigMap/Secret, монтируются в под |

> 🎯 **Формулировка в одну строку:** Kubernetes — это система, которая держит
> **фактическое состояние кластера равным описанному в манифестах**, сама разбираясь
> с падениями нод, обновлениями и масштабированием.

## 2. Декларативность и reconciliation loop ⭐

Это главная идея, без неё дальше ничего не поймётся.

```text:no-line-numbers
        ТЫ                              КУБЕР
        │                                  │
kubectl apply -f deploy.yaml               │
        │                                  │
        ▼                                  │
 ┌──────────────────┐                      │
 │ ЖЕЛАЕМОЕ (spec)  │ ──── в etcd ────►    │
 │ replicas: 3      │                      ▼
 └──────────────────┘            ┌────────────────────────┐
                                 │  Контроллер в цикле:   │
 ┌──────────────────┐            │  spec == status ?      │
 │ ФАКТ (status)    │ ◄──────────│  нет → действуй        │
 │ replicas: 2      │            │  да  → ничего не делай │
 └──────────────────┘            └────────────────────────┘
                                          │
                                  создаёт недостающий под
```

**Что из этого следует практически:**

1. `kubectl apply` не «выполняет действие», а **записывает желаемое состояние**.
   Само действие выполнит контроллер, возможно, через несколько секунд.
2. Удалил под руками → он вернётся. Это не баг, это работа ReplicaSet.
3. Чтобы под исчез навсегда — меняй **то, что его порождает** (Deployment), а не под.
4. Если что-то «не применяется», вопрос всегда один: **какой контроллер этим занят
   и что ему мешает** (`kubectl describe`, события, логи контроллера).

Ты это уже видел: в Ansible «пакет должен быть установлен» вместо `apt install`.
Кубер — то же самое, только цикл сверки работает **постоянно**, а не в момент запуска плейбука.

## 3. Чем кубер отличается от docker compose

| | docker compose | Kubernetes |
|---|---|---|
| Масштаб | один хост | кластер из N нод |
| Кто перезапускает | `restart: always` демона Docker | контроллер, в том числе **на другой ноде** |
| Балансировка | нет (или nginx руками) | Service — встроенный L4-балансировщик |
| Обновление | `up -d` пересоздаёт, даунтайм | RollingUpdate с проверками готовности |
| Сеть | bridge на хосте | плоская сеть на весь кластер (CNI) |
| Конфиги | `.env`, bind-mount | ConfigMap/Secret как объекты API |
| Хранилище | volume на этом хосте | PV/PVC, в том числе сетевые |
| Самовосстановление | в пределах хоста | в пределах кластера |
| Кто это описывает | 1 файл `compose.yaml` | 5-10 объектов на приложение (или один chart) |

**Правильная мысль:** compose не «хуже», он про другое. Локальная разработка и маленькие
проекты — compose. Прод с требованием к доступности и масштабу — кубер.

## 4. Когда Kubernetes НЕ нужен (важно для здравого смысла и для собеса)

- **Один сервер, одно приложение, нет требований к доступности.** Кубер добавит
  слой сложности, а взамен не даст ничего. Compose + systemd честнее.
- **Команда без человека, который будет это поддерживать.** Кластер — это отдельный
  объект эксплуатации: обновления, сертификаты, etcd, CNI, мониторинг.
- **Статический сайт / небольшое API с редким трафиком.** Managed-платформа,
  serverless или обычная ВМ решают дешевле.
- **Stateful-нагрузка без опыта**: свою PostgreSQL в кластер тащить можно, но на старте
  правильнее взять managed-БД (это прямо сказано и в практике роадмапа).

> 💬 Хороший ответ на собесе на вопрос «а когда бы вы не взяли кубер?» ценится выше,
> чем восторженный рассказ про микросервисы. Он показывает эксплуатационный опыт.

## 6. Терминология, которую надо принять сразу

| Термин | Что это на самом деле |
|--------|------------------------|
| **Кластер** | Control plane + рабочие ноды, управляемые как одно целое |
| **Нода** | Машина (VM/железо), на которой запускаются поды |
| **Под (Pod)** | Минимальная единица запуска: 1+ контейнеров с общей сетью и namespace'ами |
| **Объект / ресурс** | Запись в API: Pod, Service, Deployment… Хранится в etcd |
| **Манифест** | YAML-файл с описанием объекта |
| **Контроллер** | Цикл, приводящий факт к желаемому для своего типа объектов |
| **Namespace** | Логический «раздел» кластера для группировки объектов |
| **kubectl** | CLI-клиент к API серверу. Ничего не делает сам — только ходит в API |
| **Control plane** | «Мозг» кластера: API, etcd, scheduler, controller manager |
| **Workload** | Общее название для Deployment/StatefulSet/DaemonSet/Job |
| **Label / selector** | Метки на объектах и выборка по ним — так всё связано между собой |

`k8s` = «Kubernetes»: K + 8 букв + s. Произносится «кубер», «кубернетес», «к-восемь-эс».

## 7. Первый взгляд на кластер

```bash
kubectl cluster-info                 # адреса control plane и CoreDNS
kubectl get nodes -o wide            # из чего состоит кластер
kubectl get pods -A                  # ВСЕ поды, включая системные
kubectl get ns                       # разделы кластера
kubectl api-resources | head -30     # какие типы объектов вообще существуют
kubectl version                      # версии клиента и сервера
```

Что увидишь в `kube-system` на свежем kind-кластере и что это такое:

| Под | Роль |
|-----|------|
| `kube-apiserver-*` | точка входа в кластер (тема 02) |
| `etcd-*` | база с состоянием кластера |
| `kube-scheduler-*` | выбирает ноду для новых подов |
| `kube-controller-manager-*` | те самые циклы сверки |
| `kube-proxy-*` (на каждой ноде) | правила для работы Service |
| `coredns-*` | DNS внутри кластера |
| `kindnet-*` / `calico-*` | CNI-плагин, сеть подов |

Уже здесь видно устройство кластера — вся тема 02 стоит перед глазами.

## 8. Первое приложение за 60 секунд

```bash
kubectl create deployment web --image=nginx:1.25 --replicas=3
kubectl get pods -o wide                       # три пода, возможно на разных нодах
kubectl expose deployment web --port=80        # создали Service
kubectl get svc web

# зайти внутрь кластера и постучаться по DNS-имени
kubectl run tmp --rm -it --image=busybox:1.36 --restart=Never -- wget -qO- http://web

# самовосстановление: убиваем под и смотрим
kubectl delete pod -l app=web --wait=false
kubectl get pods -w                            # Ctrl+C, когда насмотришься

kubectl delete deployment web && kubectl delete svc web
```

> ⚠️ Это «императивный» способ (`create`, `expose`) — он хорош для демо и для собеса
> «покажите быстро», но в работе всё живёт в YAML под git. Роадмап в практике прямо
> требует **написать манифесты руками** — этим и займёмся с темы 03.

## 💼 Как это в DevOps

- Кубер — это **слой запуска**. Твоя реальная работа складывается из него плюс уже
  пройденное: образ из блока Docker, доставка из блока CI/CD, ноды и сеть из блока Linux.
- В вакансиях «Kubernetes» почти всегда означает связку: манифесты/Helm + пайплайн +
  мониторинг + разбор инцидентов. Один голый `kubectl apply` не является навыком.
- Первое, что спросят на новом месте: «покажи, как катится релиз». Ответ будет вида
  «пайплайн собрал образ → `helm upgrade --install` в нужный namespace → проверяем
  `rollout status`, при сбое `rollout undo`».
- Managed-кластер (облачный) убирает половину боли (control plane, обновления, LB),
  но не убирает необходимости понимать архитектуру — иначе инциденты не разобрать.

## 🧠 Что запомнить

1. Kubernetes — оркестратор: он решает, **где**, **сколько** и **как долго** работают контейнеры.
2. Главный механизм — **reconciliation loop**: контроллер бесконечно сверяет `spec` и `status`.
3. Ты описываешь **желаемое состояние**, а не последовательность действий (как в Ansible).
4. Удалённый вручную под возвращается — это правильное поведение, а не ошибка.
5. Compose — один хост, кубер — кластер; это разные инструменты, а не «хуже/лучше».
6. Кубер даёт: самовосстановление, планирование, service discovery, скейлинг, rolling update.
7. Кубер стоит сложности: его надо эксплуатировать, и иногда честнее его не брать.
8. Минимальная единица запуска — **под**, а не контейнер (почему — тема 04).
9. Всё в кластере — объекты API, хранятся в etcd, связаны **метками и селекторами**.
10. `kubectl` — просто клиент к API-серверу; он не «делает», а «просит».

### Блок A. Теория

**A1.** Назови пять задач, которые Kubernetes решает, а `docker run` на одном сервере — нет.

<details><summary>Ответ</summary>

Перезапуск пода на **другой** ноде при падении текущей; выбор ноды под ресурсы;
service discovery по имени; rolling update с проверкой готовности и откатом;
горизонтальное масштабирование по метрикам; распределение конфигов и секретов по кластеру.

</details>

**A2.** ⭐ Что такое reconciliation loop? Объясни на примере «хочу 3 реплики, живых 2».

<details><summary>Ответ</summary>

Цикл, в котором контроллер сравнивает желаемое состояние (`spec` в etcd)
с фактическим (`status`) и выполняет действия, устраняющие разницу. «Хочу 3, живых 2» →
ReplicaSet-контроллер видит разницу и создаёт один под; когда станет 3 — ничего не делает.

</details>

**A3.** Почему `kubectl apply` — это не «выполнить команду»?

<details><summary>Ответ</summary>

Он записывает объект в API/etcd. Реальные действия выполняют контроллеры
и kubelet асинхронно; успех `apply` означает «желаемое принято», а не «сделано».

</details>

**A4.** Ты удалил под командой `kubectl delete pod`. Он появился снова. Объясни почему
и как удалить «по-настоящему».

<details><summary>Ответ</summary>

Под создан ReplicaSet'ом, который принадлежит Deployment'у; контроллер видит
нехватку реплики и создаёт новую. Удалять надо владельца: `kubectl delete deployment web`
(или уменьшить `replicas`).

</details>

**A5.** Чем декларативный подход в кубере похож на подход Ansible и чем отличается?

<details><summary>Ответ</summary>

Похожи: описываем состояние, а не шаги; повторное применение безопасно.
Отличие: Ansible сверяет состояние **в момент запуска**, кубер — **непрерывно**,
поэтому чинит дрейф сам.

</details>

**A6.** В чём разница между `docker compose` и Kubernetes по пяти пунктам?

<details><summary>Ответ</summary>

Масштаб (хост vs кластер); самовосстановление в пределах кластера; встроенная
балансировка через Service; rolling update с проверками; сеть/хранилище как объекты API
(плюс конфиги и секреты как ресурсы).

</details>

**A7.** Что такое «нода» и что такое «кластер»?

<details><summary>Ответ</summary>

Нода — машина, где реально запускаются поды (kubelet + runtime + kube-proxy).
Кластер — control plane плюс набор нод, управляемых как одно целое.

</details>

**A8.** Что такое объект (ресурс) Kubernetes и где он хранится?

<details><summary>Ответ</summary>

Запись в API Kubernetes с полями `apiVersion`, `kind`, `metadata`, `spec`, `status`;
хранится в etcd; изменяется только через API-сервер.

</details>

**A9.** Зачем нужны namespace'ы?

<details><summary>Ответ</summary>

Логическое разделение кластера: разные окружения/команды, уникальность имён
внутри namespace, точка приложения квот (ResourceQuota), RBAC и NetworkPolicy.

</details>

**A10.** Что делает `kubectl`? Может ли он что-то изменить в кластере сам, без API-сервера?

<details><summary>Ответ</summary>

`kubectl` формирует HTTP-запросы к API-серверу и печатает ответы. Сам по себе
ничего не меняет: без API-сервера он бесполезен.

</details>

**A11.** Назови три ситуации, когда Kubernetes брать не стоит.

<details><summary>Ответ</summary>

Один сервер и одно простое приложение; нет людей на эксплуатацию кластера;
редкий/предсказуемый трафик, где хватает ВМ или managed-платформы.

</details>

**A12.** Что такое label и selector, и почему без них кубер не работал бы?

<details><summary>Ответ</summary>

Label — пара ключ-значение на объекте; selector — выборка по меткам.
Через них Service находит поды, ReplicaSet — свои реплики, NetworkPolicy — цели правил.
Объекты в кубере связаны не ссылками по ID, а метками.

</details>

**A13.** Почему минимальная единица запуска — под, а не контейнер? (Пока — интуитивно,
подробно в теме 04.)

<details><summary>Ответ</summary>

Потому что часто нужны несколько процессов с общей сетью и файлами (приложение
плюс сайдкар), а планировать и перезапускать удобнее одну неделимую единицу.

</details>

**A14.** Что такое CNI, CSI, CRI — в одну строку каждое.

<details><summary>Ответ</summary>

CRI — интерфейс между kubelet и container runtime; CNI — плагин, дающий подам сеть;
CSI — драйвер, подключающий внешнее хранилище.

</details>

**A15.** Что означает сокращение k8s?

<details><summary>Ответ</summary>

«K» + 8 букв «ubernete» + «s».

</details>

**A16.** Ты пришёл в компанию с managed-кластером. Что облако взяло на себя,
а что осталось тебе?

<details><summary>Ответ</summary>

Облако: control plane (API, etcd, scheduler, controller manager), его обновления
и доступность, интеграция LB и дисков. Тебе: манифесты, версии приложений, ресурсы и лимиты,
autoscaling, сеть-политики, RBAC, мониторинг, стоимость и обновление нод.

</details>

**A17.** Какие компоненты ты увидишь в namespace `kube-system` на любом кластере?

<details><summary>Ответ</summary>

kube-apiserver, etcd, kube-scheduler, kube-controller-manager, kube-proxy (на каждой
ноде), CoreDNS, поды CNI-плагина. В managed-кластере часть control plane не видна.

</details>

**A18.** Чем «оркестрация» отличается от «контейнеризации»?

<details><summary>Ответ</summary>

Контейнеризация — упаковка и изоляция приложения (Docker). Оркестрация — управление
жизненным циклом множества контейнеров на множестве машин.

</details>

**A19.** Приложение падает раз в сутки из-за утечки памяти. Что даст кубер и что не даст?

<details><summary>Ответ</summary>

Кубер перезапустит под (и это скроет симптом), может ограничить память через `limits`
и дать алерт по рестартам. Утечку он не починит — это задача разработчика.

</details>

**A20.** Кубер — это про отказоустойчивость приложения или про отказоустойчивость
инфраструктуры? Ответь аккуратно.

<details><summary>Ответ</summary>

Кубер даёт механизмы: перезапуск, распределение по нодам, проверки, скейлинг.
Но отказоустойчивость приложения зависит от самого приложения (stateless, ретраи,
graceful shutdown) и от внешних зависимостей. Кубер — инструмент, а не гарантия.

</details>

### Блок B. «Что произойдёт»

**B1.**
```bash
kubectl create deployment web --image=nginx --replicas=3
kubectl delete pod <один-из-подов>
kubectl get pods
```
Вопрос: сколько подов будет и почему?

<details><summary>Ответ</summary>

Три: ReplicaSet создаст новый под взамен удалённого.

</details>

**B2.**
```bash
kubectl run solo --image=nginx --restart=Never
kubectl delete pod solo
kubectl get pods
```
Вопрос: чем результат отличается от B1 и почему?

<details><summary>Ответ</summary>

Под исчезнет навсегда: у «голого» пода нет владельца-контроллера, который
сверял бы состояние. Отсюда правило — в проде голых подов не бывает.

</details>

**B3.**
```text:no-line-numbers
kubectl get pods
# No resources found in default namespace.
kubectl get pods -A
# ...30 подов...
```
Вопрос: объясни, что произошло.

<details><summary>Ответ</summary>

`kubectl get pods` без ключа работает в текущем namespace (`default`),
а приложения и системные компоненты живут в других namespace'ах. `-A` — по всем.

</details>

**B4.**
```text:no-line-numbers
kubectl apply -f deploy.yaml
kubectl get deployment web
# READY 0/3
```
Вопрос: назови четыре возможные причины (пока без деталей — на уровне логики).

<details><summary>Ответ</summary>

Образ не скачивается (нет доступа/тега/секрета реестра); подам не хватает ресурсов
и они `Pending`; контейнер падает при старте (`CrashLoopBackOff`); не проходит
`readinessProbe`; ошибка в манифесте (несуществующий ConfigMap/Secret).

</details>

**B5.**
```text:no-line-numbers
kubectl create deployment web --image=nginx --replicas=3
# на ноде node2 внезапно пропало питание
```
Вопрос: что произойдёт с подами, которые были на node2? Мгновенно ли?

<details><summary>Ответ</summary>

Нода перейдёт в `NotReady` примерно через 40 секунд (`node-monitor-grace-period`),
поды получат taint и будут вытеснены и пересозданы на других нодах примерно через
5 минут (`tolerationSeconds` по умолчанию). То есть не мгновенно — это частый вопрос собеса.

</details>

**B6.**
```bash
kubectl scale deployment web --replicas=0
```
Вопрос: удалится ли Deployment? Что произойдёт с подами? Как вернуть?

<details><summary>Ответ</summary>

Deployment остаётся, `replicas` = 0, все поды удаляются. Вернуть — `kubectl scale
deployment web --replicas=3`. Это штатный способ «погасить» приложение без удаления.

</details>

**B7.**
```bash
kubectl explain pod.spec.containers.resources
```
Вопрос: откуда kubectl берёт этот текст?

<details><summary>Ответ</summary>

Из OpenAPI-схемы, которую отдаёт сам API-сервер, — поэтому `explain` всегда
соответствует версии **твоего** кластера.

</details>

#### C5. Масштабирование
```bash
kubectl scale deployment web --replicas=5
kubectl get pods -o wide
kubectl scale deployment web --replicas=1
```
Запиши: какие поды кубер решил оставить и удалить? Есть ли закономерность?

<details><summary>Ответ</summary>

При уменьшении реплик кубер удаляет поды по внутреннему приоритету: сначала
непригодные/непрошедшие readiness и самые «молодые», затем — с нод с большим числом
реплик того же приложения.

</details>

#### C6. Service discovery на пальцах
1. `kubectl expose deployment web --port=80`
2. Из временного пода сходи по имени: `wget -qO- http://web`.
3. Удали все поды приложения и повтори запрос через 20 секунд.
4. Объясни, почему имя продолжило работать, хотя IP подов сменились.

<details><summary>Ответ</summary>

Service имеет стабильные ClusterIP и DNS-имя; при пересоздании подов меняется
только список Endpoints за сервисом, а имя и IP сервиса остаются прежними.

</details>

#### C7. Сравнение с compose
Возьми свой `compose.yaml` из блока Docker и выпиши в таблицу:

`volumes`, `depends_on`, `restart`, `deploy.replicas`). Заполняй по мере изучения тем —
в конце блока сверишься.

#### C8. Убийство ноды (со звёздочкой)
В kind нода — это docker-контейнер.

Типичная картина: `NotReady` через ~40 секунд, пересоздание подов на других нодах
примерно через 5 минут после этого. Объясняет, почему «под переехал не мгновенно».

</details>

#### C9. Документация без интернета
Найди через `kubectl explain`, как называется поле, задающее команду запуска

### Блок D. Инциденты

**D1.** Разработчик говорит: «я удалил под, а он воскрес — у вас кластер сломан».
Что отвечаешь?

<details><summary>Ответ</summary>

Так и должно быть: подами владеет ReplicaSet, он восстанавливает нужное число
реплик. Чтобы приложение остановилось — `scale --replicas=0` или удалить Deployment.

</details>

**D2.** После деплоя приложение доступно по IP пода, но коллега жалуется,
что «завтра IP изменился и всё отвалилось». Что было сделано неправильно?

<details><summary>Ответ</summary>

Обращались к IP пода. IP пода эфемерный — он меняется при каждом пересоздании.
Правильно: обращаться к Service по DNS-имени.

</details>

**D3.** Команда мигрировала с compose на кубер и жалуется, что «стало сложнее,
а пользы ноль»: один сервер, одно приложение, трафика нет. Кто прав?

<details><summary>Ответ</summary>

Правы скептики: на одном сервере без требований к доступности кубер даёт сложность
без выгоды. Разумно вернуться к compose/systemd либо честно назвать другую цель миграции
(например, унификация окружений или подготовка к росту).

</details>

**D4.** Нода выключилась, поды переехали, но приложение всё равно было недоступно 5 минут.
Назови две причины, которые от кубера не зависят.

<details><summary>Ответ</summary>

Долгий старт приложения без `readinessProbe` (трафик пошёл на неготовые поды);
внешняя зависимость (БД, очередь) не переехала; DNS/кэш клиента; отсутствие
PodDisruptionBudget и anti-affinity — все реплики были на одной ноде.

</details>

**D5.** На вопрос «кто у вас перезапускает упавшие контейнеры» новый сотрудник ответил
«Docker с `restart: always`». В чём разница с кубером?

<details><summary>Ответ</summary>

Docker перезапускает контейнер **на том же хосте**; если хост умер — не перезапустит
никто. Кубер пересоздаёт под на другой ноде и учитывает результаты probe'ов.

</details>

**D6.** В кластере 40 подов приложения, но оно всё равно лежит, потому что упала база
на отдельной ВМ. Какой вывод про «кубер = отказоустойчивость»?

<details><summary>Ответ</summary>

Отказоустойчивость системы определяется самым слабым звеном. Кубер повышает
живучесть stateless-части, но единственная БД остаётся единой точкой отказа.

</details>

**D7.** Менеджер просит «перевести всё на кубер за неделю, чтобы было модно».
Как аргументировать риски без конфликта?

<details><summary>Ответ</summary>

Показать стоимость: кластер надо эксплуатировать (обновления, сеть, мониторинг,
дежурства). Предложить этапность: сначала образы и CI/CD, затем staging в managed-кластере,
затем прод. Обосновать бизнес-эффектом (скорость релизов, доступность), а не модой.

</details>

**D8.** После `kubectl scale --replicas=0` разработчик написал «вы удалили мой деплой».
Объясни, что произошло на самом деле.

<details><summary>Ответ</summary>

Deployment на месте, удалены только поды. Приложение остановлено, конфигурация
сохранена; возврат — одной командой `scale`.

</details>

### Блок E. Вопросы с собеседования

**1.** Что такое Kubernetes и какую задачу он решает?

<details><summary>Ответ</summary>

Оркестратор контейнеров: держит фактическое состояние равным описанному —
запускает, перезапускает, распределяет, масштабирует, обновляет и связывает сервисы.

</details>

**2.** Чем кубер отличается от docker compose?

<details><summary>Ответ</summary>

Compose — один хост и простой запуск; кубер — кластер, самовосстановление между нодами,
встроенные балансировка, rolling update, ресурсы и квоты, конфиги как объекты API.

</details>

**3.** ⭐ Что такое декларативный подход и reconciliation loop?

<details><summary>Ответ</summary>

Ты описываешь желаемое состояние; контроллеры в бесконечном цикле сравнивают `spec`
и `status` и устраняют расхождение.

</details>

**4.** Почему под, удалённый вручную, появляется снова?

<details><summary>Ответ</summary>

Его восстанавливает контроллер-владелец (ReplicaSet), потому что желаемое число
реплик не изменилось.

</details>

**5.** Что такое под, нода, кластер, namespace?

<details><summary>Ответ</summary>

Под — минимальная единица запуска (один или несколько контейнеров с общей сетью);
нода — машина с kubelet; кластер — control plane и ноды; namespace — логический раздел
для группировки объектов и разграничения прав и квот.

</details>

**6.** Когда Kubernetes не нужен?

<details><summary>Ответ</summary>

Один сервер, простое приложение, нет команды на эксплуатацию, нет требований
к масштабу и доступности — цена сложности выше выгоды.

</details>

**7.** Что делает kubectl?

<details><summary>Ответ</summary>

CLI-клиент к API-серверу: отправляет запросы и показывает ответы; сам состояние не меняет.

</details>

**8.** Что даёт кубер для отказоустойчивости и чего он не даёт?

<details><summary>Ответ</summary>

Даёт: рестарты, переезд подов, проверки готовности, скейлинг, безопасные обновления.
Не даёт: качества кода, корректной работы с состоянием, живучести внешних зависимостей.

</details>
