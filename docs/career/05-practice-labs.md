## 🧪 Лаба 1. ⭐ Трекер и разбор 10 вакансий

### Что делаем
Заводим трекер откликов, разбираем 10 реальных вакансий на ядро, стек и пожелания и
собираем **таблицу пробелов**: какие навыки требует рынок, что из этого есть у тебя и какой
блок волта закрывает пробел. Это и план подготовки, и материал для резюме.

### Каркас
Трекер — шаблон из [01_job_search.md](/career/01-job-search), раздел 9 (таблица откликов + воронка
по неделям + разборы). Хранить в облачной таблице или отдельной папке вне репозитория.

Разбор одной вакансии:
```markdown
### Вакансия 03 — «маркетплейс-2», DevOps junior+ (Алматы, гибрид)
Тип роли: DevOps в продуктовой команде
| Требование | Группа | Закрываю? | Доказательство / план |
|------------|--------|-----------|-----------------------|
| Linux, bash | ядро | да | блок Linux, 99-incidents |
| GitLab CI | стек | да | 05-conveyor, linkd-platform |
| Kubernetes, Helm | ядро | частично | 07-orbit (не прод) |
| AWS | стек | нет | → Left/04_Cloud |
Флаги: 🟢 вилка указана, 🟢 дежурства с ротацией, 🚩 «широкий круг задач» — уточнить
Решение: откликаюсь, версия резюме — product
```text
Сводная таблица пробелов (главный артефакт):
```markdown
| Навык | В скольких вакансиях из 10 | Мой уровень (0–3) | Доказательство | Блок волта | Приоритет |
|-------|----------------------------|-------------------|----------------|------------|-----------|
| Kubernetes | 9 | 2 | 07-orbit, чарт linkd | [K8s](/kubernetes/) · [собес](/kubernetes/23-interview) | 🔴 |
| Terraform | 6 | 1 | 11-blueprint | [Terraform](/terraform/) | 🟡 |
| AWS / облако | 5 | 0 | — | [Облака](/cloud/) | 🟡 |
| Мониторинг | 7 | 2 | 08-observatory | [Мониторинг](/monitoring/) · [SRE](/sre/) | 🟡 |
| Python/Go | 4 | 2 | бэкенд + 10-toolsmith | [Python](/python/) | 🟢 |
```text
Уровень: 0 — не касался, 1 — читал/стенд, 2 — делал руками в проекте, 3 — в проде на работе.
Приоритет = частота в вакансиях × размер пробела.

### Требования
- [ ] Трекер заведён вне волта: таблица откликов, воронка по неделям, раздел разборов
- [ ] 10 вакансий разобраны по шаблону: тип роли, группы требований, доказательства, флаги, решение
- [ ] Сводная таблица пробелов: 8–12 навыков, частота, уровень, доказательство, ссылка на блок волта
- [ ] Выбраны 2–3 пробела с наивысшим приоритетом и под каждый — действие на 2 недели
- [ ] По итогам разбора обновлены версии резюме (ключевые навыки, первые строки опыта)
- [ ] Минимум 5 откликов отправлены и записаны в день отправки
- [ ] Через неделю посчитана воронка и определён самый ранний проседающий шаг

### Критерии приёмки
```text
career/                         # вне git-волта (или обезличенно)
├── tracker.(xlsx|ods|md)       # отклики + воронка + разборы
├── vacancies/01..10.md         # разбор каждой вакансии
├── skills-gap.md               # сводная таблица пробелов со ссылками на волт
└── resume/product|platform|sre # версии резюме
```text
Проверка себя: открой таблицу пробелов и за 30 секунд скажи, что учишь следующие две недели
и почему именно это.

### Вопросы себе
- Какой навык встречается почти везде, а у тебя на уровне 0–1? Почему он ещё не закрыт?
- Сколько из 10 вакансий — на самом деле не DevOps (сисадмин, поддержка)? Как их отсеивать быстрее?
- Какая версия резюме нужна чаще всего?
- Что в вакансиях повторяется из того, что ты уже делал на текущей работе, но не написал в резюме?

## 🧪 Лаба 2. Питч pet-проекта на 3 минуты и демо на 5

### Что делаем
Готовим и записываем рассказ о `linkd-platform` на 3 минуты и короткое демо на 5 минут —
то, что спрашивают почти на каждом собесе джуна: «расскажи про свой проект» и «покажи».

### Каркас
- Структура рассказа, пример и таблица уточняющих вопросов — в
  [../Project/10_readme_resume.md](/project/10-readme-resume) (шаги 6–7).
- Сценарий демо и предполётная проверка — в
  [../Project/11_demo_and_next.md](/project/11-demo-and-next) (шаги 1–4).
- Запись: диктофон или экран + `asciinema rec` для терминала.

Сжатое демо на 5 минут (для собеса, где нет 15 минут):
```text
0:00  README: схема и два репозитория (30 с)
0:30  граф последнего пайплайна: test → build → scan → push → bump (1 мин)
1:30  Argo CD: дерево приложений, dev и prod Synced/Healthy (1 мин)
2:30  дашборд SLO и последний алерт в Telegram (1 мин)
3:30  лог restore-test и таблица RPO/RTO (1 мин)
4:30  «что бы сделал дальше» и вопросы (30 с)
```text
Если стенд не поднят — запись демо из README и скриншоты вместо живого показа.

### Требования
- [ ] Питч укладывается в 3:00 ± 15 с, проговорён вслух минимум 5 раз с таймером
- [ ] В питче: что и зачем → поток «коммит → прод» → одна своя глубокая история → 2–3 замеренные цифры → ограничения
- [ ] Честно разделено: сервис учебный, платформа — твоя работа
- [ ] Записан ответ на каждый вопрос из таблицы шага 7 Project/10 (по 30–60 с)
- [ ] Демо на 5 минут прогнано на поднятом стенде или по записи
- [ ] Есть вариант питча на английском на 1,5 минуты (для удалёнки)
- [ ] Друг или коллега послушал и пересказал проект своими словами

### Критерии приёмки
```text
career/pitch/
├── pitch-ru.md             # текст-каркас (не для чтения вслух — опорные пункты)
├── pitch-ru-take5.m4a      # последняя запись
├── pitch-en.md
├── qa.md                   # ответы на уточняющие вопросы
└── demo-5min.md            # сценарий + ссылка на запись
```text
Проверка: слушатель после питча отвечает на вопросы «что за проект?», «что сделал сам?»,
«какая самая интересная проблема?».

### Вопросы себе
- Выдержит ли глубокая история пять «почему» подряд?
- Какую цифру спросят «а как вы это замерили?» — и знаешь ли ответ?
- Что ответишь на «а сервис вы писали сами?» спокойно и в свою пользу?
- Как объяснить проект нетехническому рекрутеру за две фразы?

## 🧪 Лаба 3. ⭐ Mock live troubleshooting

### Что делаем
Три сессии поиска поломки **вслух, с таймером и записью**: система сломана, известен только
симптом. Цель — не угадать причину, а натренировать методику из
[02_tech_interview_formats.md](/career/02-tech-interview-formats) (раздел 6): симптом → область →
гипотезы → команды → проверка → фикс → проверка фикса → предотвращение.

### Каркас
**Вариант А: учебные инциденты** (соло или с напарником):
```bash
cd ~/Projects/devops/stands/learn-linux && vagrant snapshot save before_mock
cd ~/Projects/devops/99-incidents && ./sync.sh
cd ~/Projects/devops/stands/learn-linux && vagrant ssh
# на VM:
cd ~/incidents && ./incident.sh list
./incident.sh start NN        # ещё не решённый; соло — выбери наугад
# … диагностика вслух, таймер 30 минут …
./incident.sh check NN
./incident.sh debrief NN      # только после check или по истечении времени
./incident.sh reset NN        # или на хосте: vagrant snapshot restore before_mock
```text
**Вариант Б: напарник ломает** (интервьюер знает причину, ты — только симптом). Напарник
выбирает карточку и ломает VM, пока ты не смотришь. Для nginx-карточек заранее поставь nginx
(`sudo apt install -y nginx`) **до** снапшота:

| Карточка | Как сломать (на VM) | Симптом для кандидата |
|----------|---------------------|-----------------------|
| Порт закрыт | `sudo iptables -I INPUT -p tcp --dport 80 -j DROP` | «Сайт снаружи не открывается, на сервере curl работает» |
| Слушает только localhost | в конфиге nginx `listen 127.0.0.1:80;` + `sudo systemctl reload nginx` | «С соседней машины не открывается» |
| Диск заполнен | `sudo fallocate -l &lt;почти весь свободный объём&gt; /var/tmp/.cache.img` | «Приложение не пишет логи, падает с ошибками» |
| Нет прав на файл | `sudo chmod 000 /var/www/html/index.nginx-debian.html` | «Сайт отдаёт 403» |
| Сервис не стартует после перезагрузки | `sudo systemctl disable nginx && sudo reboot` | «После перезагрузки сайт не работает» |
| Сломан DNS | `echo 'nameserver 10.255.255.1' \| sudo tee /etc/resolv.conf` | «Сервер не может скачать пакеты, apt висит» |
| Процесс съел CPU | `nohup sh -c 'while :; do :; done' >/dev/null 2>&1 &` | «Сервер тормозит» |

Роль интервьюера: отвечать на уточняющие вопросы так, как ответил бы пользователь
(«что менялось?» — «вроде ничего… хотя вчера был ребут»), не подсказывать, записывать
время и шаги. Откат после сессии — `vagrant snapshot restore before_mock`.

**Вариант В: устный** — сценарии из [06_interview.md](/career/06-interview) (часть 2): напарник
читает сценарий и отвечает на команды «выводом», который придумывает по ответу.

Журнал сессий:
```markdown
| # | Дата | Сценарий | Время | Спросил «что менялось?» | Гипотез до решения | Опасные действия | Фикс проверен | Предотвращение | Промахи |
|---|------|----------|-------|-------------------------|--------------------|------------------|---------------|----------------|---------|
```text
### Требования
- [ ] 3 сессии: минимум одна по варианту А и одна по варианту Б или В
- [ ] Каждая сессия записана (звук обязательно, экран — желательно), таймер 30 минут
- [ ] В каждой записи есть: уточнение симптома, «что менялось?», сужение области, гипотеза до команды
- [ ] Ни одного `chmod 777`, `iptables -F`, `setenforce 0` или рестарта «на всякий случай» без объяснения
- [ ] Фикс проверен той же командой, что показала проблему
- [ ] Каждая сессия заканчивается фразой «чтобы не повторилось: …» (алерт, тест, runbook, конфиг в git)
- [ ] Журнал заполнен, промахи повторяющиеся — выписаны отдельно
- [ ] После трёх сессий шпаргалка «первые 60 секунд» воспроизводится по памяти

### Критерии приёмки
```bash
# вариант А: инцидент засчитан движком
./incident.sh check NN            # на VM: успех
# вариант Б: симптом ушёл, проверка тем же способом, что показал проблему
curl -sI http://&lt;ip-vm&gt;/          # с хоста: 200 OK
df -h / ; systemctl is-enabled nginx ; getent hosts archive.ubuntu.com
```text
Плюс журнал сессий с тремя строками и файл повторяющихся промахов.

### Вопросы себе
- На какой минуте появилась первая гипотеза? Была ли она проверена одной командой?
- Где молчал дольше 30 секунд? Что в этот момент стоило сказать вслух?
- Что сделал бы иначе, будь это прод и SEV2 ночью ([../SRE/04_incident_management.md](/sre/04-incident-management))?
- Какая «скучная» проверка (диск, память, логи, время) нашла бы проблему быстрее?

## 🧪 Лаба 4. Два mock system design

### Что делаем
Две сессии по 45 минут по фреймворку из [03_system_design_devops.md](/career/03-system-design-devops):
одна задача из конспекта (без подглядывания), одна — новая из
[06_interview.md](/career/06-interview) (часть 1). Лучше с напарником в роли интервьюера,
соло — с диктофоном и таймером по шагам.

### Каркас
```text
Таймер по шагам (45 мин):
00–07  уточнения — вопросы и допущения записаны на доске
07–11  оценка — RPS, объём, хранение
11–21  схема — 8–12 блоков, путь запроса/кода/данных
21–31  компоненты — 2–3 самых важных блока глубже
31–41  качества — «а если упадёт X?», узкие места, безопасность, стоимость
41–45  trade-offs и «как развивать»
```text
Инструменты: лист А4 или Excalidraw/draw.io. Напарнику — список «что спросят дальше» из
конспекта: задаёт 2–3 вопроса в последние 10 минут и в середине меняет одно условие
(«данные должны остаться в РК», «бюджет в два раза меньше»).

Самооценка по чек-листу (0/1 за пункт):
```text
[ ] Задал 5+ уточняющих вопросов до схемы
[ ] Назвал допущения вслух и записал
[ ] Оценка повлияла на решение («при N RPS хватит …»)
[ ] Схема читается без меня
[ ] Для каждого блока ответил «а если он упадёт?»
[ ] Назвал узкое место и как его снять
[ ] Упомянул безопасность (секреты, доступы, сеть)
[ ] Упомянул стоимость
[ ] Назвал 2+ trade-offs с «когда передумаю»
[ ] Адаптировался к смене условия без паники
```text
### Требования
- [ ] 2 сессии по 45 минут, каждая записана, тайминг по шагам соблюдён ± 5 минут
- [ ] Схемы сохранены (фото или экспорт)
- [ ] Самооценка по чек-листу; во второй сессии — не ниже, чем в первой
- [ ] После первой сессии сравнил с конспектом и выписал, что пропустил
- [ ] Во второй сессии отработал смену условия от напарника (или сам вытянул карточку с условием)
- [ ] Для одной схемы написан короткий ADR на ключевое решение ([../Project/10_readme_resume.md](/project/10-readme-resume), шаг 4)

### Критерии приёмки
```text
career/system-design/
├── 01-&lt;задача&gt;/  schema.png · notes.md (вопросы, допущения, оценки) · selfcheck.md
├── 02-&lt;задача&gt;/  schema.png · notes.md · selfcheck.md · adr.md
└── misses.md     # что пропускаю регулярно
```text
### Вопросы себе
- На каком шаге ушло больше всего времени сверх плана? Почему?
- Какое допущение сильнее всего повлияло на схему?
- Где в схеме я добавил компонент «потому что модно», а не из требований?
- Как бы я объяснил эту схему нетехническому руководителю за минуту?

## 🧪 Лаба 5. Полный mock-собес с разбором

### Что делаем
Генеральная репетиция: 75–90 минут, как настоящий собес — техника и behavioral подряд,
с напарником (лучше — действующим девопсом) или, если никого нет, с записью и вопросами
из банка, вытянутыми наугад.

### Каркас
```text
00–05   знакомство, «расскажи о себе» (../SoftSkills/09_interview.md)
05–10   питч pet-проекта (лаба 2)
10–30   техвопросы по стеку вакансии: 6–8 вопросов из *_interview.md
        (карта — 02_tech_interview_formats.md, раздел 11), ответ слоями
30–50   live troubleshooting: карточка из лабы 3 или сценарий из 06_interview.md
50–65   мини system design (15 мин): «как бы ты задеплоил сервис X в прод?»
65–80   behavioral: 3 вопроса из ../SoftSkills/09_interview.md + «ожидания по зарплате?»
80–90   твои вопросы работодателю; фидбек от напарника
```text
Соло-вариант: `shuf -n 8` по списку вопросов из файлов карты, сценарий troubleshooting —
вариант А лабы 3, вопросы behavioral — наугад; всё записать, фидбек — сам себе через сутки
по записи.

Разбор (шаблон из [02_tech_interview_formats.md](/career/02-tech-interview-formats), раздел 10) +
оценка по блокам:
```markdown
| Блок | 1–5 | Что было хорошо | Что улучшить | Действие (блок волта / лаба) |
|------|-----|-----------------|--------------|------------------------------|
| Рассказ о себе и проект | | | | |
| Теория (слоями, «не знаю, но…») | | | | |
| Live troubleshooting | | | | |
| System design | | | | |
| Behavioral | | | | |
| Деньги и вопросы работодателю | | | | |
```text
### Требования
- [ ] Mock проведён целиком за один раз, без пауз «сейчас подсмотрю»
- [ ] Запись есть; разбор написан в течение суток
- [ ] Оценка по всем шести блокам, у каждой оценки ниже 4 — конкретное действие со ссылкой на волт
- [ ] Ожидания по зарплате названы вилкой с обоснованием ([04_offer_negotiation.md](/career/04-offer-negotiation))
- [ ] Задано 3+ своих вопроса работодателю
- [ ] План подготовки на 2 недели из действий разбора
- [ ] Через 2 недели — повторный mock; оценки сравнены

### Критерии приёмки
```text
career/mock/
├── 2026-10-xx/  recording.* · review.md · plan-2w.md
└── 2026-11-xx/  recording.* · review.md          # повторный, сравнение с первым
```text
### Вопросы себе
- Какой блок провис сильнее всего, и совпадает ли это с отказами в трекере?
- Где я говорил «мы», а нужно было «я»?
- Что в ответах звучало заученно, а что — как опыт?
- Готов ли я к реальному собесу на этой неделе? Если нет — чего конкретно не хватает?

career/                            # вне git-волта

```text
