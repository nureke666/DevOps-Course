# 01. Проблема секретов

> Роадмап → 7. Остальное → Vault: *«На любом зрелом проекте существует,
> все секреты (пароли, ключи, токены) хранятся в нем.»*
>
> **После темы ты умеешь:** объяснить, почему привычные способы хранения секретов
> плохи, сформулировать требования к решению и сравнить доступные варианты.

---

## 🗺️ Где живут секреты на типичном проекте

```text:no-line-numbers
 ┌──────────────────────────────────────────────────────────────────────┐
 │ .env на сервере            пароль БД, ключи API                      │
 │ переменные CI/CD           токены реестра, ключи облака              │
 │ ansible-vault               пароли в репозитории (зашифрованы)        │
 │ Kubernetes Secret          base64 = «не зашифровано»                 │
 │ terraform.tfstate          ⚠️ всё, что создал Terraform, открытым текстом│
 │ личные сообщения и заметки пароли «на время», которые живут годами   │
 │ репозиторий                ключ, закоммиченный три года назад        │
 └──────────────────────────────────────────────────────────────────────┘
             │
             ▼  вопросы, на которые никто не может ответить
   Кто имеет доступ к прод-базе?  Когда последний раз меняли этот пароль?
   Кто им пользовался вчера?      Что делать, если уволился инженер?
```

---

## 1. Чем плохи привычные способы

| Способ | Проблема |
|--------|----------|
| `.env` / конфиг на сервере | Видит любой, кто получил доступ к машине; нет аудита и ротации |
| Переменные CI/CD | Лучше, но секрет всё равно «вечный»; видят все, кто может править пайплайн |
| `ansible-vault` / SOPS | Шифрование есть, но нет аудита, ротации и ролевого доступа; пароль от vault тоже надо где-то хранить |
| Kubernetes Secret | ⚠️ base64 — это кодирование; без шифрования etcd читается напрямую |
| Файлы ключей на дисках | Копируются, забываются, попадают в снапшоты и бэкапы |
| Пароль в мессенджере | Остаётся в истории навсегда, у неизвестного круга людей |
| Секрет в git | Даже после удаления остаётся в истории — считается скомпрометированным |

```text:no-line-numbers
Три вопроса, которые обнажают проблему:
 1. Можешь ли ты за 5 минут сменить пароль от прод-базы во всех местах?
 2. Знаешь ли ты, кто читал этот секрет за последний месяц?
 3. Что произойдёт, если уволится человек, у которого были все пароли?
```

---

## 2. Что вообще считается секретом

| Тип | Примеры |
|-----|---------|
| Учётные данные | Пароли БД, брокеров, админок |
| Токены и ключи API | Registry, облако, платёжные шлюзы, мессенджеры |
| Криптографические ключи | TLS-ключи, ключи подписи, SSH-ключи |
| Строки подключения | С логином и паролем внутри |
| Сессии и cookie-ключи | Секреты приложений (JWT secret, cookie secret) |
| Персональные данные | Формально не секрет, но требует такой же защиты |

⭐ Отдельно: **конфигурация ≠ секрет**. Адрес базы и имя очереди — обычная конфигурация;
пароль к ним — секрет. Смешивание их в одном месте усложняет и то, и другое.

---

## 3. Требования к нормальному решению

```text:no-line-numbers
 1. ЦЕНТРАЛИЗАЦИЯ     один источник правды, а не десять мест
 2. ШИФРОВАНИЕ        данные зашифрованы в покое и при передаче
 3. АУТЕНТИФИКАЦИЯ    каждый (человек, приложение, CI) доказывает, кто он
 4. АВТОРИЗАЦИЯ       политика: кто какие пути может читать и писать ⭐
 5. АУДИТ             журнал: кто, когда, какой секрет получил
 6. TTL И ОТЗЫВ       секреты живут ограниченно и отзываются мгновенно
 7. РОТАЦИЯ           смена секрета без остановки сервисов
 8. ДИНАМИЧЕСКИЕ      временные креды, создаваемые под конкретную задачу ⭐
    СЕКРЕТЫ
 9. ИНТЕГРАЦИИ        k8s, CI/CD, Ansible, Terraform, приложения
10. ОТКАЗОУСТОЙЧИВОСТЬ хранилище секретов не должно быть единой точкой отказа
```

---

## 4. Варианты решений

| Решение | Что даёт | Ограничения |
|---------|----------|-------------|
| **Переменные CI/CD** | Просто, есть маскирование | Нет аудита чтения, ротации, TTL; статические секреты |
| **SOPS / git-crypt** | Секреты в git зашифрованы, работает везде | Нет аудита и TTL; управление ключами на тебе |
| **Sealed Secrets** | Безопасное хранение в git для k8s | Только Kubernetes, ротация сложна |
| **Облачные менеджеры секретов** | Managed, интеграция с IAM облака | Привязка к провайдеру, меньше гибкости |
| **HashiCorp Vault** ⭐ | Всё из списка требований: политики, аудит, TTL, динамические секреты, много интеграций | Сам требует эксплуатации: HA, unseal, бэкапы |
| **OpenBao** | Открытый форк Vault | Молодой проект, экосистема меньше |

```text:no-line-numbers
Практический выбор:
 • маленький проект             → секреты CI + SOPS, дисциплина
 • Kubernetes без Vault         → Sealed Secrets / облачный менеджер + ESO
 • зрелый проект, аудит, ротация→ ⭐ Vault (или облачный менеджер + ESO)
```

## 5. Жизненный цикл секрета

```text:no-line-numbers
 создание ──► выдача ──► использование ──► ротация ──► отзыв ──► удаление
    │           │             │              │           │
    │           │             │              │           └ при увольнении, инциденте
    │           │             │              └ по расписанию или при подозрении
    │           │             └ приложение читает при старте или периодически
    │           └ кому, на какой срок, с какими правами
    └ кто создал, где хранится, кто владелец
```

Каждый этап должен быть **описан процессом**, а не «как получится».
Именно это и даёт Vault: выдача по политике, TTL, отзыв, журнал.

---

## 6. Что делать при утечке секрета ⭐

```text:no-line-numbers
1. РОТАЦИЯ ПЕРВЫМ ДЕЛОМ      сменить сам секрет (пароль, токен, ключ)
2. ОТЗЫВ                     аннулировать старые токены и сессии
3. ОЦЕНКА ДОСТУПА            кто мог им воспользоваться, что доступно
4. ПРОВЕРКА ЖУРНАЛОВ         были ли обращения с чужих адресов
5. ЧИСТКА                    удалить из git/логов/тикетов (после ротации!)
6. ПОСТМОРТЕМ                почему секрет вообще оказался в этом месте
```

⚠️ Частая ошибка — начать с «удалим из git». Пока секрет не сменён, он остаётся
рабочим у всех, кто его уже скопировал.

---

## 7. Гигиена секретов в повседневной работе

| Практика | Смысл |
|----------|-------|
| Секрет не покидает хранилище в открытом виде | Приложение получает его само, а не человек копирует |
| Персональные учётки вместо общих | Понятно, кто что делал |
| Разные секреты для dev/stage/prod | Утечка в dev не открывает прод |
| Минимальные права | Сервис читает только свой путь |
| TTL по умолчанию | Забытый доступ протухает сам |
| Сканеры секретов в CI (`gitleaks`) | Ловят коммит до того, как он попал в историю |
| Регулярный аудит доступов | «Кто ещё может читать прод-секреты?» |
| Секреты не в логах | `no_log`, маскирование, `sensitive` |

---

## 💼 Как это в DevOps

- Управление секретами — одна из первых зон ответственности девопса: именно он
  отвечает за то, чтобы прод-пароли не лежали в чатах и репозиториях.
- Внедрение обычно идёт поэтапно: сначала убрать секреты из git и с серверов
  в CI-переменные, затем поднять хранилище, затем перевести приложения на чтение
  из него, и только потом — динамические секреты.
- Ротация без простоя требует поддержки со стороны приложений (перечитывание секрета,
  два активных ключа на время смены) — это обсуждают с разработчиками заранее.
- На собеседовании вопрос «как вы храните секреты» задают почти всегда; ответ
  «в переменных CI» допустим, но объяснение ограничений и знание Vault выделяет кандидата.

## 🧠 Что запомнить

1. Секреты обычно разбросаны по десятку мест, и никто не знает, кто имеет к ним доступ.
2. `.env`, переменные CI и файлы на серверах не дают аудита, TTL и ротации.
3. Kubernetes Secret в base64 — не защита; нужен шифрованный etcd и строгий RBAC.
4. Секрет, попавший в git, считается скомпрометированным навсегда.
5. ⭐ Требования к решению: централизация, шифрование, аутентификация, политики,
   аудит, TTL, ротация, интеграции.
6. Конфигурация и секреты — разные вещи; их разделяют.
7. Динамические секреты (временная учётка на 30 минут) сильнее любой ротации статических.
8. При утечке первым шагом всегда идёт ротация, а не чистка репозитория.
9. Разные секреты для разных окружений и персональные учётки вместо общих.
10. Сканеры секретов в CI дешевле любого разбора инцидента.

### Блок A. Теория

**A1.** Перечисли семь мест, где на типичном проекте лежат секреты.

<details><summary>Ответ</summary>

`.env` и конфиги на серверах, переменные CI/CD, ansible-vault/SOPS
в репозитории, Kubernetes Secret, terraform-стейт, личные сообщения и заметки,
сам git (включая историю), бэкапы и снапшоты.

</details>

**A2.** Какие три вопроса обнажают проблему с управлением секретами?

<details><summary>Ответ</summary>

Сможешь ли сменить прод-пароль везде за 5 минут? Знаешь ли, кто его читал
за месяц? Что будет, если уволится человек, у которого все пароли?

</details>

**A3.** Что считается секретом? Приведи шесть категорий.

<details><summary>Ответ</summary>

Учётные данные, токены и ключи API, криптографические ключи, строки подключения,
секреты приложений (JWT/cookie), а также персональные данные, требующие такой же защиты.

</details>

**A4.** Чем конфигурация отличается от секрета и почему их разделяют?

<details><summary>Ответ</summary>

Конфигурация описывает «куда и как подключаться» и может лежать в репозитории;
секрет — то, что даёт доступ. Разделение упрощает ревью, версионирование и защиту.

</details>

**A5.** Почему `.env` на сервере — плохое хранилище?

<details><summary>Ответ</summary>

Любой с доступом к серверу читает его; нет журнала обращений, нет TTL,
ротация означает ручной обход всех серверов.

</details>

**A6.** Чем плохи переменные CI как единственное решение?

<details><summary>Ответ</summary>

Секрет статичный и «вечный», доступен всем, кто может править пайплайн;
нет аудита чтения и TTL; сложно организовать разные права для разных сервисов.

</details>

**A7.** ⭐ Почему Kubernetes Secret сам по себе не решает проблему?

<details><summary>Ответ</summary>

Значения хранятся в base64 (кодирование, не шифрование); без шифрования etcd
и строгого RBAC их читает каждый, у кого есть доступ к API/namespace; нет TTL,
ротации и аудита обращений.

</details>

**A8.** Чем `ansible-vault`/SOPS лучше открытого хранения и чего им не хватает?

<details><summary>Ответ</summary>

Даёт шифрование в репозитории и возможность ревью. Не хватает аудита чтения,
TTL, отзыва, ролевого доступа и динамических секретов; ключ шифрования тоже надо хранить.

</details>

**A9.** Сформулируй десять требований к системе управления секретами.

<details><summary>Ответ</summary>

Централизация, шифрование, аутентификация, авторизация по политикам, аудит,
TTL, отзыв, ротация, динамические секреты, интеграции, отказоустойчивость.

</details>

**A10.** Сравни пять решений: CI-переменные, SOPS, Sealed Secrets, облачный менеджер, Vault.

<details><summary>Ответ</summary>

CI-переменные — просто, но статично и без аудита. SOPS — шифрование в git,
универсально, но без TTL и аудита. Sealed Secrets — удобно для k8s, но ограничено им.
Облачный менеджер — managed и интегрирован с IAM, но привязка к провайдеру.
Vault — максимально полно закрывает требования, но требует эксплуатации.

</details>

**A11.** Что такое динамические секреты и чем они принципиально лучше статических?

<details><summary>Ответ</summary>

Секреты, создаваемые по запросу на ограниченное время (например, временный
пользователь в PostgreSQL на 30 минут). Их не нужно ротировать: они истекают сами,
а утечка ограничена коротким окном.

</details>

**A12.** Опиши жизненный цикл секрета.

<details><summary>Ответ</summary>

Создание → выдача (кому, на какой срок, с какими правами) → использование →
ротация → отзыв → удаление; на каждом этапе — журнал и ответственный.

</details>

**A13.** ⭐ Каков правильный порядок действий при утечке секрета?

<details><summary>Ответ</summary>

Ротация секрета → отзыв старых токенов/сессий → оценка возможного доступа →
проверка журналов → чистка из git/логов/тикетов → постмортем.

</details>

**A14.** Почему нельзя начинать с чистки git-истории?

<details><summary>Ответ</summary>

Потому что до смены секрет остаётся рабочим у всех, кто уже успел его
скопировать; чистка истории не отзывает доступ.

</details>

**A15.** Назови восемь практик гигиены секретов.

<details><summary>Ответ</summary>

Секрет не копируется людьми; персональные учётки; разные секреты по окружениям;
минимальные права; TTL по умолчанию; сканеры секретов в CI; регулярный аудит доступов;
запрет секретов в логах.

</details>

### Блок C. Практика

#### C1. 🔑 Аудит своего проекта
Составь таблицу: какой секрет, где лежит, кто имеет доступ, когда менялся,
что произойдёт при утечке. Даже для учебного проекта это упражнение открывает глаза.

#### C2. Поиск секретов в репозитории
```bash
# установи gitleaks и прогони по своему репозиторию (включая историю)
gitleaks git --verbose .
grep -rEn '(password|token|secret|api[_-]?key)\s*[:=]' --include='*.y*ml' .
```
Разбери находки: что действительно секрет, что ложное срабатывание.

#### C3. Проверка Kubernetes Secret

### Блок D. Инциденты

**D1.** Ключ облака закоммичен в публичный репозиторий. Порядок действий.

<details><summary>Ответ</summary>

Немедленно отозвать/пересоздать ключ, проверить журналы облака на чужую
активность, оценить ущерб, удалить из истории репозитория, внедрить сканер секретов,
разобрать причину.

</details>

**D2.** Уволился инженер, знавший все прод-пароли. Что делаешь?

<details><summary>Ответ</summary>

Отозвать персональные доступы (SSO, VPN, SSH, облако, git), ротировать общие
секреты, к которым он имел доступ, проверить журналы, зафиксировать процедуру офбординга.

</details>

**D3.** Разработчик просит пароль от прод-базы в чате. Как поступить?

<details><summary>Ответ</summary>

Не передавать пароль в чате: выдать доступ через хранилище/по процессу,
временный или read-only, с аудитом; при необходимости — помочь выполнить задачу
без выдачи секрета.

</details>

**D4.** Пароль от базы попал в логи приложения. Действия и профилактика.

<details><summary>Ответ</summary>

Ротировать пароль, вычистить логи (и их бэкапы), добавить маскирование
и запрет на логирование секретов, проверить, кто имел доступ к логам.

</details>

**D5.** Подрядчику выдали доступ год назад, проект закончен. Как такое не допускать?

<details><summary>Ответ</summary>

Выдавать доступы с ограниченным сроком (TTL/`VALID UNTIL`), вести реестр
внешних доступов и регулярно его пересматривать.

</details>

**D6.** Один и тот же пароль используется в dev и prod, dev скомпрометирован. Что теперь?

<details><summary>Ответ</summary>

Считать прод скомпрометированным: ротировать пароль, проверить журналы доступа,
развести секреты по окружениям.

</details>

**D7.** Нужно сменить пароль базы без простоя сервиса. Как это делается?

<details><summary>Ответ</summary>

Создать второй набор кредов, перевести сервисы на него (или поддержать
две активные учётки на время), убедиться в отсутствии использования старых,
затем отозвать старые. В Vault это делается динамическими секретами или встроенной ротацией.

</details>

**D8.** Бэкап `terraform.tfstate` лежит в общем бакете. Чем это грозит?

<details><summary>Ответ</summary>

Любой, кто имеет доступ к бакету, читает все секреты инфраструктуры;
нужно шифрование, ограничение доступа и версионирование.

</details>

**D9.** Секреты в Kubernetes читает любой, у кого есть доступ к namespace. Как ограничить?

<details><summary>Ответ</summary>

RBAC по namespace и конкретным секретам, шифрование etcd, отказ от хранения
реальных секретов в k8s (ESO/Vault), аудит обращений к API.

</details>

**D10.** Команда сопротивляется внедрению Vault: «и так работает». Твои аргументы.

<details><summary>Ответ</summary>

Показать риски на конкретных примерах (утечка, увольнение, аудит),
оценить стоимость инцидента, предложить поэтапное внедрение с быстрым результатом
(например, только прод-секреты) и снять страх поддержки, начав с managed/простой схемы.

</details>

### Блок E. Вопросы с собеседования

**1.** Как вы храните секреты?

<details><summary>Ответ</summary>

Централизованное хранилище (Vault/облачный менеджер), приложения получают секреты
сами; в git секретов нет, в CI — только защищённые переменные для доступа к хранилищу.

</details>

**2.** Чем плохо хранить секреты в переменных CI?

<details><summary>Ответ</summary>

Нет аудита чтения, TTL и ротации; доступ есть у всех, кто может править пайплайн.

</details>

**3.** Почему Kubernetes Secret — не полноценная защита?

<details><summary>Ответ</summary>

base64 — не шифрование; нужна связка «шифрование etcd + RBAC», и всё равно нет TTL
и аудита обращений.

</details>

**4.** Что делать, если секрет попал в git?

<details><summary>Ответ</summary>

Ротировать секрет, отозвать сессии, проверить журналы, затем чистить историю
и разобрать причину.

</details>

**5.** Какие требования к системе управления секретами?

<details><summary>Ответ</summary>

Централизация, шифрование, аутентификация и политики, аудит, TTL, отзыв, ротация,
динамические секреты, интеграции, отказоустойчивость.

</details>

**6.** Что такое динамические секреты?

<details><summary>Ответ</summary>

Временные учётные данные, выдаваемые по запросу на короткий срок и автоматически
отзываемые.

</details>

**7.** Как организовать ротацию паролей?

<details><summary>Ответ</summary>

Через хранилище с поддержкой ротации, две активные учётки на время перехода
и приложения, умеющие перечитывать секреты; в идеале — динамические секреты.

</details>

**8.** Как выдаются доступы людям и сервисам?

<details><summary>Ответ</summary>

Людям — по персональным учёткам через SSO и политике на время; сервисам —
через AppRole/Kubernetes-аутентификацию с минимальными правами.

</details>

**9.** Что происходит с доступами при увольнении?

<details><summary>Ответ</summary>

Отзываются персональные доступы и ротируются общие секреты, к которым был доступ.

</details>

**10.** Чем ansible-vault отличается от HashiCorp Vault?

<details><summary>Ответ</summary>

`ansible-vault` шифрует файлы в репозитории Ansible; HashiCorp Vault — отдельный
сервис с аутентификацией, политиками, аудитом, TTL и динамическими секретами.

</details>
