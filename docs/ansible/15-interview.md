## 🎯 Часть 1. Пять главных вопросов роадмапа

### 1. Что такое playbook? ⭐

<details><summary>Ответ</summary>

**Короткий ответ (30 секунд):**
> «Playbook — это YAML-файл, основная единица работы в Ansible. В нём описывается,
> **на каких хостах** и **какие задачи** выполнить, чтобы привести систему в нужное
> состояние. Если ad-hoc команда — это как команда в терминале, то playbook — как
> bash-скрипт, только декларативный и идемпотентный: я описываю состояние, а не шаги,
> и повторный запуск ничего не меняет, если всё уже настроено».

**Развёрнуто (если просят подробнее):**
- Playbook состоит из **play** — связок «группа хостов + задачи».
- Play содержит: `hosts`, `become`, `vars`, `pre_tasks`, `roles`, `tasks`,
  `post_tasks`, `handlers`.
- Порядок: `pre_tasks` → роли → `tasks` → `post_tasks`, handler'ы — после каждого блока.
- Задачи выполняются **сверху вниз** на всех хостах параллельно (по `forks`).
- Несколько play в одном файле дают оркестрацию: сначала БД, потом приложение, потом проверка.
- Перед применением на проде — `--check --diff --limit`, после — контроль `changed=0`.

**Сильное дополнение:** «В реальной работе плейбук у нас тонкий — 15-20 строк со списком
ролей, вся логика в ролях. Запускается из пайплайна, секреты — в vault».

</details>

### 2. Что такое роль? ⭐

<details><summary>Ответ</summary>

**Короткий ответ:**
> «Роль — это способ разбить конфигурацию на переиспользуемые модули: роль для nginx,
> роль для PostgreSQL, роль для мониторинга. У роли стандартная структура каталогов,
> поэтому её можно переиспользовать между проектами, тестировать отдельно и подключать
> к плейбуку одной строкой».

**Структура (называть уверенно — это и есть проверка):**
```text:no-line-numbers
roles/nginx/
├── tasks/main.yml       ← что делать (точка входа)
├── handlers/main.yml    ← реакции на изменения (reload/restart)
├── templates/           ← Jinja2-шаблоны (.j2)
├── files/               ← статические файлы для copy
├── defaults/main.yml    ← переменные по умолчанию (НИЗШИЙ приоритет)
├── vars/main.yml        ← внутренние константы (ВЫСОКИЙ приоритет)
├── meta/main.yml        ← зависимости и метаданные
├── tests/               ← тестовый прогон
└── README.md            ← описание и таблица переменных
```

**Что добавить, чтобы ответ был сильным:**
- «Всё настраиваемое кладём в `defaults` с префиксом имени роли — тогда роль
  переиспользуется без правок, только переменными окружения».
- «Зависимости описываем в `meta/main.yml` — они выполняются перед ролью и один раз».
- «Роль — единица ревью и тестирования: molecule прогоняет её в контейнере
  и проверяет идемпотентность».
- «Скелет создаётся `ansible-galaxy init`, внешние роли фиксируем в `requirements.yml`
  с версиями».

</details>

### 3. Расскажи про приоритеты переменных ⭐⭐

<details><summary>Ответ</summary>

**Короткий ответ (правило, которое всегда работает):**
> «Чем ближе переменная к месту использования — тем выше её приоритет.
> Самый низкий уровень — `defaults` роли, самый высокий — extra vars через `-e`,
> которые побеждают всё».

**Порядок от слабого к сильному (называть по группам, а не зубрить 22 пункта):**
```text:no-line-numbers
1. role defaults/main.yml          ← слабее всех, создано для переопределения
2. переменные инвентаря, group_vars: all → родительская группа → дочерняя
3. host_vars
4. facts (собранные с хоста)
5. play vars, vars_prompt, vars_files
6. role vars/main.yml              ← высокий приоритет, «константы роли»
7. block vars → task vars
8. include_vars
9. set_fact и registered vars
10. параметры роли (- role: x + переменные)
11. extra vars (-e)                ← побеждает ВСЕГДА
```

**Три вещи, которые отличают сильный ответ:**
1. **`defaults` vs `vars` в роли:** «`defaults` — самый низкий приоритет, туда кладут всё,
   что пользователь роли должен настраивать; `vars` — высокий, туда кладут константы,
   которые не должны перебиваться инвентарём».
2. **Внутри групп:** «`group_vars/all` слабее конкретной группы, дочерняя группа сильнее
   родительской, `host_vars` сильнее любой группы. Если хост в двух группах одного уровня —
   решает алфавит или `ansible_group_priority`».
3. **Практика отладки:** «Когда непонятно, откуда значение, смотрю
   `ansible-inventory --host <хост>` и `debug var=` — и иду по списку приоритетов сверху вниз».

</details>

### 4. Что такое handler? ⭐

<details><summary>Ответ</summary>

**Короткий ответ:**
> «Handler — это задача, которая выполняется только по уведомлению `notify`
> и только если уведомившая задача изменила состояние, то есть вернула `changed`.
> Классический пример: изменился конфиг nginx — перезапускаем nginx. Если конфиг
> не менялся, сервис никто не трогает».

**Правила, которые стоит назвать:**
- Выполняется **один раз**, даже если его уведомили десять задач.
- Выполняется **в конце play**, а не сразу после задачи.
- Порядок — **как объявлено в секции `handlers`**, а не как звали.
- При падении play handler'ы по умолчанию **не выполняются** — решается `force_handlers`
  или `meta: flush_handlers`.
- `listen` позволяет одному событию поднять несколько handler'ов (удобно в ролях).

**Зачем он нужен (главная мысль):**
> «Без handler'а пришлось бы писать `state: restarted` в обычной задаче, и сервис
> перезапускался бы при каждом прогоне — это ломает идемпотентность и создаёт
> ненужные обрывы соединений».

</details>

### 5. Что такое идемпотентность? ⭐

<details><summary>Ответ</summary>

**Короткий ответ:**
> «Идемпотентность — это когда повторное применение ничего не меняет: запустил плейбук
> один раз — настроил сервер, запустил второй — ничего не произошло, потому что система
> уже в нужном состоянии. Модуль сначала проверяет текущее состояние и выполняет действие
> только при расхождении. Практический критерий — во втором прогоне `PLAY RECAP`
> показывает `changed=0`».

**Что добавить:**
- «Поэтому упавший плейбук можно спокойно перезапустить: выполненные задачи просто
  отчитаются `ok`».
- «И поэтому `changed` — полезный сигнал: если кто-то поправил конфиг руками,
  прогон вернёт файл к описанному состоянию и покажет `changed`».

**Что ломает идемпотентность (назвать 3-4 примера):**
- `command`/`shell` без `creates`/`removes`/`changed_when` — всегда `changed`;
- `state: latest` у пакетов — `changed` при каждом выходе обновления;
- `service: state=restarted` в обычной задаче вместо handler'а;
- шаблоны с меняющимися данными (дата, случайные значения, несортированный словарь);
- `get_url` без `checksum`, `unarchive` без `creates`, `lineinfile` без `regexp`.

**Пример на доске, если просят:**
```yaml
# ❌ неидемпотентно
- ansible.builtin.shell: echo "127.0.0.1 app.local" >> /etc/hosts

# ✅ идемпотентно
- ansible.builtin.lineinfile:
    path: /etc/hosts
    line: "127.0.0.1 app.local"
    state: present
```

</details>

## 📚 Часть 2. Дополнительные вопросы

### Основы

**6. Что такое Ansible и зачем он нужен?**

<details><summary>Ответ</summary>

Инструмент управления конфигурацией: с одной управляющей машины по SSH приводит целевые
хосты в описанное кодом состояние. Даёт повторяемость, массовость и версионирование настройки.

</details>

**7. Что значит agentless? Что нужно на целевом хосте?**

<details><summary>Ответ</summary>

Агент не ставится. Нужны SSH-доступ, Python 3 и права (обычно sudo).

</details>

**8. Push или pull?**

<details><summary>Ответ</summary>

Push: применение инициирует оператор или CI. Puppet/Chef работают по pull —
агент сам периодически забирает конфигурацию.

</details>

**9. Ansible декларативный или императивный?**

<details><summary>Ответ</summary>

Декларативный на уровне задач (описываем состояние, `state: present`), но порядок
выполнения императивный — задачи идут сверху вниз. Это честный ответ, который ценят.

</details>

**10. Чем Ansible отличается от Terraform?**

<details><summary>Ответ</summary>

Terraform создаёт инфраструктуру (VM, сети, балансировщики) и хранит state;
Ansible настраивает ОС и приложения внутри. Типовая связка: Terraform создал →
динамический inventory → Ansible настроил.

</details>

**11. Чем отличается от Puppet/Chef?**

<details><summary>Ответ</summary>

Agentless vs агент, push vs pull, YAML vs собственный DSL, ниже порог входа,
но нет непрерывного автоисправления дрейфа.

</details>

**12. Как Ansible выполняет модуль на удалённом хосте?**

<details><summary>Ответ</summary>

Копирует python-код модуля по SSH во временный каталог, запускает его там, получает JSON
с результатом, удаляет временные файлы.

</details>

**13. Что такое ad-hoc команды и когда их применяют?**

<details><summary>Ответ</summary>

Разовые команды: <code v-pre>ansible &lt;хосты&gt; -m &lt;модуль&gt; -a "&lt;аргументы&gt;"</code>.
Годятся для диагностики и срочных операций; всё повторяющееся оформляют плейбуком.

</details>

**14. Чем `command` отличается от `shell`?**

<details><summary>Ответ</summary>

`command` выполняется без шелла (нет пайпов, редиректов, переменных), `shell` — через
`/bin/sh -c`. Есть ещё `raw` (без python) и `script` (выполнить локальный скрипт).

</details>

**15. Что такое коллекции и FQCN?**

<details><summary>Ответ</summary>

Коллекция — пакет модулей/ролей/плагинов (`community.docker`, `ansible.posix`).
FQCN — полное имя модуля (`ansible.builtin.copy`), убирает неоднозначность.

</details>

### Inventory и переменные

**16. Что такое inventory?**

<details><summary>Ответ</summary>

Список хостов и групп с переменными; форматы INI и YAML, плюс динамические инвентари.

</details>

**17. Как разделять окружения?**

<details><summary>Ответ</summary>

Отдельными каталогами `inventories/dev` и `inventories/prod` со своими `group_vars`;
плейбук один и тот же, различия — только в переменных.

</details>

**18. Что такое динамический inventory?**

<details><summary>Ответ</summary>

Инвентарь, который формируется из внешнего источника (API облака, теги) плагином
(`aws_ec2`, `gcp_compute`) или скриптом, печатающим JSON по `--list`.

</details>

**19. Что такое facts?**

<details><summary>Ответ</summary>

Данные о хосте, собираемые модулем `setup`: ОС, сеть, железо. Ключевые —
`ansible_os_family`, `ansible_default_ipv4.address`, `ansible_processor_vcpus`.

</details>

**20. Как отключить и как ускорить сбор фактов?**

<details><summary>Ответ</summary>

`gather_facts: false`, `gather_subset`, кэш фактов (`fact_caching = jsonfile/redis`)
с `gathering = smart`.

</details>

**21. Чем `set_fact` отличается от `register`?**

<details><summary>Ответ</summary>

`register` сохраняет результат выполнения задачи; `set_fact` создаёт переменную
из выражения в рантайме. У обоих высокий приоритет.

</details>

**22. Как получить переменную другого хоста?**

<details><summary>Ответ</summary>

<code v-pre>hostvars['db1']['ansible_default_ipv4']['address']</code> — при условии,
что факты этого хоста собраны или закэшированы.

</details>

**23. Как задать значение по умолчанию?**

<details><summary>Ответ</summary>

Фильтром `default()`; для обязательных переменных — `assert` в `pre_tasks`
или фильтр `mandatory`.

</details>

### Плейбуки и выполнение

**24. Что делает `--check`?**

<details><summary>Ответ</summary>

Сухой прогон: модули сообщают, что бы изменили, ничего не меняя. `command`/`shell`
в этом режиме пропускаются. Вместе с `--diff` показывает построчные различия.

</details>

**25. Как запустить плейбук на одном сервере?**

<details><summary>Ответ</summary>

`--limit web1` (а также тегами и `--start-at-task` — по задачам).

</details>

**26. Что такое теги?**

<details><summary>Ответ</summary>

Метки задач для выборочного запуска: `--tags`, `--skip-tags`; специальные `always` и `never`.

</details>

**27. Что происходит, если задача упала на одном из хостов?**

<details><summary>Ответ</summary>

Этот хост выбывает из play, остальные продолжают. Меняется `any_errors_fatal`
и `max_fail_percentage`.

</details>

**28. Как сделать раскатку без даунтайма?**

<details><summary>Ответ</summary>

`serial` (волнами) + вывод/возврат в балансировщик в `pre_tasks`/`post_tasks` +
health-check и `max_fail_percentage`.

</details>

**29. Что такое `block`/`rescue`/`always`?**

<details><summary>Ответ</summary>

Аналог try/catch/finally. Типовое применение — деплой с откатом; после успешного `rescue`
play считается успешным, поэтому в конце `rescue` ставят `fail`.

</details>

**30. Чем `ignore_errors` отличается от `failed_when`?**

<details><summary>Ответ</summary>

`ignore_errors` не считает падение фатальным (задача остаётся ошибкой в отчёте);
`failed_when` переопределяет само условие ошибки — это точнее и честнее.

</details>

**31. Как дождаться готовности сервиса?**

<details><summary>Ответ</summary>

`uri` + `until`/`retries`/`delay` для HTTP, `wait_for` для порта/файла.

</details>

**32. Что делает `delegate_to`? А `run_once`?**

<details><summary>Ответ</summary>

`delegate_to` выполняет задачу на другом хосте (часто `localhost` — API балансировщика,
DNS, уведомления); `run_once` выполняет задачу один раз на весь play.

</details>

### Роли, шаблоны, модули

**33. Чем `import_role` отличается от `include_role`?**

<details><summary>Ответ</summary>

`import_role` — статически при парсинге (виден в `--list-tasks`, теги работают,
но нельзя в цикле); `include_role` — динамически в рантайме (можно `loop` и условия).

</details>

**34. Чем `copy` отличается от `template`?**

<details><summary>Ответ</summary>

`template` рендерит файл через Jinja2 перед копированием; рендер происходит
на управляющей машине.

</details>

**35. Как безопасно менять критичные конфиги?**

<details><summary>Ответ</summary>

`validate:` (проверка до подмены), `backup: true`, handler `reload`,
`--check --diff --limit` перед применением.

</details>

**36. Как сгенерировать конфиг балансировщика из списка серверов?**

<details><summary>Ответ</summary>

Циклом по `groups['web']` в шаблоне с обращением к `hostvars[host]`.

</details>

**37. Что такое Ansible Galaxy?**

<details><summary>Ответ</summary>

Публичный репозиторий ролей и коллекций + CLI (`ansible-galaxy init/install/search`);
зависимости фиксируются в `requirements.yml` с версиями.

</details>

**38. Как сделать роль кроссплатформенной?**

<details><summary>Ответ</summary>

Ветвления по `ansible_os_family`, файлы переменных `vars/Debian.yml`/`vars/RedHat.yml`
с `include_vars`, универсальный модуль `package`.

</details>

### Секреты, эксплуатация, CI/CD

**39. Как хранить секреты?**

<details><summary>Ответ</summary>

`ansible-vault` (файл или `encrypt_string`), пароль — вне репозитория (файл с правами 600,
CI-переменная, менеджер паролей); плюс `no_log: true` и права `0600` на файлах с секретами.

</details>

**40. Достаточно ли vault, чтобы секрет не утёк?**

<details><summary>Ответ</summary>

Нет: без `no_log: true` значение попадёт в лог задачи, а на хосте секрет лежит открытым —
нужны правильные права и владелец.

</details>

**41. Что делать, если секрет попал в git?**

<details><summary>Ответ</summary>

Считать скомпрометированным: сначала ротация самого секрета, потом чистка истории
и уведомление команды.

</details>

**42. Как запускать Ansible из CI/CD?**

<details><summary>Ответ</summary>

Отдельная джоба: установка зависимостей из `requirements.yml`, секреты из CI/CD Variables
(masked + File), `--vault-password-file`, прод — `when: manual` с `environment`
и `resource_group`.

</details>

**43. Как ускорить Ansible?**

<details><summary>Ответ</summary>

`pipelining`, `ControlPersist`, больше `forks`, отключение/сужение сбора фактов, кэш фактов,
`strategy: free`, списки вместо циклов, `async` для долгих задач, меньше `shell`.

</details>

**44. Как тестируют роли?**

<details><summary>Ответ</summary>

`ansible-lint` и `--syntax-check` в CI, `--check --diff` на dev, molecule
(контейнер + шаг `idempotence` + проверки), повторный прогон на staging.

</details>

**45. Как применяете изменения на проде?**

<details><summary>Ответ</summary>

MR → линт в CI → ревью → `--check --diff` на dev/staging → прогон на одном прод-хосте
через `--limit` → остальные волнами с health-check → контрольный прогон на `changed=0`.

</details>

**46. Что такое AWX?**

<details><summary>Ответ</summary>

Веб-платформа поверх Ansible: запуск по кнопке и расписанию, RBAC, хранилище креденшелов,
логи и аудит прогонов. AWX — бесплатный upstream Ansible Automation Platform.

</details>

**47. Какие минусы у Ansible?**

<details><summary>Ответ</summary>

Скорость на больших парках (SSH на каждую задачу), YAML плохо подходит для сложной логики,
нет непрерывного контроля дрейфа (push-модель), отладка приоритетов переменных
и шаблонов бывает болезненной.

</details>

## 🛠️ Часть 3. Практические задания

На джуна/мидла чаще всего просят одно из:

### Задание A. «Напиши плейбук, который настроит веб-сервер»

Что показать:
```yaml
- name: Веб-сервер
  hosts: web
  become: true
  tasks:
    - name: Пакеты
      ansible.builtin.apt: { name: [nginx, curl], state: present, update_cache: true, cache_valid_time: 3600 }
    - name: Конфиг
      ansible.builtin.template:
        src: nginx.conf.j2
        dest: /etc/nginx/nginx.conf
        mode: "0644"
        validate: "nginx -t -c %s"
      notify: reload nginx
    - name: Сервис
      ansible.builtin.service: { name: nginx, state: started, enabled: true }
  handlers:
    - name: reload nginx
      ansible.builtin.service: { name: nginx, state: reloaded }
```
Обязательно проговори вслух: `name` у задач, FQCN, `state: present` (не `latest`),
`validate`, handler вместо `restarted`, `mode` строкой, и «второй прогон даст `changed=0`».

### Задание B. «Найди ошибки в плейбуке»

Типовой набор подсадок:
- `shell` вместо модулей; `mode: 0644` без кавычек; `state: latest`;
- `state: restarted` в задаче; `lineinfile` без `regexp`; пароль открытым текстом;
- отсутствие `name`; <code v-pre>when: {{ var }}</code>; `user` без `append: true`;
- `command` без `changed_when` в задаче-проверке.

### Задание C. «Как разложишь это на роли?»

Отвечай структурой: `common` (база), сервисные роли по одной на сервис,
`app` (деплой), зависимости через `meta`, переменные окружений — в `group_vars`,
секреты — в vault, плейбук — тонкий.

## 🗣️ Как себя вести на собесе по Ansible

1. **Ansible спрашивают неглубоко** (роадмап прав): 5-10 минут, 3-5 вопросов.
   Ошибка — начать теряться на простом вопросе после сложного блока по Kubernetes.
2. **Отвечай определением + примером.** «Handler — это… Например, изменился конфиг nginx —
   перезапускаем nginx» звучит в разы лучше сухого определения.
3. **Говори про идемпотентность** там, где это уместно, — это маркер того, что ты
   реально писал плейбуки, а не читал документацию.
4. **Упоминай практику:** «у нас в репозитории роли, окружения разделены инвентарями,
   в CI прогоняется `ansible-lint` и `--check`». Это сразу поднимает уровень разговора.
5. **Не выдумывай.** Не пользовался molecule — скажи: «не применял, знаю, что это
   фреймворк тестирования ролей с проверкой идемпотентности».
6. **Связывай с другими блоками:** Linux (SSH, sudo, systemd), Docker (деплой контейнеров),
   CI/CD (запуск из пайплайна, секреты). Целостная картина ценится выше зубрёжки.
