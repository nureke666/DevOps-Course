# 01. Что такое Ansible: agentless, декларативность, идемпотентность

> Роадмап → 5. Ansible → 1. Теория → **Фундамент**:
> «Это инструмент для управления конфигурациями. Он позволяет с одной управляющей машины
> выполнять инструкции и задачи на целевых хостах.»
> **После темы ты умеешь:** объяснить, что такое Ansible, чем он отличается от bash-скриптов
> и от Puppet/Chef, и — главное — что такое **идемпотентность**.

---

## 🗺️ Карта темы

```text:no-line-numbers
        УПРАВЛЯЮЩАЯ МАШИНА                      ЦЕЛЕВЫЕ ХОСТЫ
        (control node)                          (managed nodes)
 ┌──────────────────────────┐            ┌───────────────────────┐
 │ ansible / ansible-playbook│           │ web1   sshd + python3 │
 │ inventory (список хостов) │  ──SSH──► │ web2   sshd + python3 │
 │ playbooks + roles         │           │ db1    sshd + python3 │
 │ модули (готовый код)      │           └───────────────────────┘
 └──────────────────────────┘             ⬆ НИЧЕГО не установлено
            ▲                                (agentless)
            │ git
     репозиторий команды

 Как выполняется задача:
 1. ansible берёт модуль (python-код) → 2. копирует его на хост по SSH →
 3. запускает python3 → 4. модуль проверяет состояние → меняет ТОЛЬКО если надо →
 5. возвращает JSON (ok / changed / failed) → 6. удаляет за собой временный файл
```

---

## 1. Зачем вообще нужен Ansible

Представь 20 серверов, на которых нужен одинаковый nginx с одинаковым конфигом.

| Способ | Что не так |
|--------|-----------|
| Руками по SSH | 20 раз одно и то же, опечатки, «а на web7 забыли», через месяц никто не помнит, что там делали |
| Bash-скрипт + цикл по хостам | Не переживает повторный запуск (`useradd` упадёт «уже существует»), падение на середине оставляет половину сервера настроенной, нет отчёта |
| Образ/«золотой образ» | Хорош для новых машин, но не решает «поменять один параметр на живых серверах» |
| **Ansible** | Описал состояние → применил ко всем → повторный запуск безопасен → всё лежит в git |

**Ansible = конфигурация как код (Configuration Management).**
Сервер перестаёт быть «уникальным питомцем, которого настраивали руками» и становится
результатом выполнения кода из репозитория.

> 💡 Главный вопрос, на который отвечает Ansible: **«В каком состоянии должен быть сервер?»**
> а не «какие команды на нём выполнить».

## 2. Agentless — главное архитектурное отличие

**На целевые серверы не нужно ставить ничего.** Требования к хосту:

| Что нужно | Зачем |
|-----------|-------|
| SSH-доступ (обычно по ключу) | Транспорт, по которому доставляются модули |
| Python 3 на целевом хосте | На нём выполняются модули (есть «raw»-модули, работающие без python) |
| Права (обычно `sudo`) | Чтобы ставить пакеты и править `/etc` |

На управляющей машине — только сам Ansible (python-пакет). Управляющей машиной может быть
твой ноутбук, bastion-хост или **раннер CI/CD**.

### Чем это лучше агентной модели (Puppet/Chef/Salt)

| | Ansible (agentless, push) | Puppet/Chef (agent, pull) |
|---|---|---|
| Установка на хосты | ❌ не нужна | ✅ нужен агент + сертификаты |
| Кто инициирует | Ты, командой (push) | Агент сам раз в 30 мин (pull) |
| Порог входа | Низкий: YAML | Выше: свой DSL/Ruby |
| Дрейф конфигурации | Обнаруживается, когда ты запустил | Исправляется автоматически |
| Масштаб 5000+ хостов | Нужны ухищрения (forks, AWX, pull-режим) | Спроектировано под это |
| Сеть | Нужен доступ **к** хостам по SSH | Агент сам ходит **наружу** |

**Вывод для собеса:** agentless = быстрый старт и никакой инфраструктуры на хостах,
но управление — по запросу, а не непрерывное.

> ⚠️ Не путай: agentless — не значит «без ничего». Python на целевом хосте нужен.
> На голых сетевых железках/контейнерах без python используют `raw`, `script`
> или специальные коллекции (`network_cli`, `ansible_connection=docker`).

## 3. Декларативный подход: состояние, а не шаги

```bash
# Императивно (bash) — Я ОПИСЫВАЮ ШАГИ
apt-get update
apt-get install -y nginx
systemctl enable nginx
systemctl start nginx
```

```yaml
# Декларативно (Ansible) — Я ОПИСЫВАЮ СОСТОЯНИЕ
- name: nginx установлен
  ansible.builtin.apt:
    name: nginx
    state: present
    update_cache: true

- name: nginx запущен и в автозагрузке
  ansible.builtin.service:
    name: nginx
    state: started
    enabled: true
```

Разница не в синтаксисе, а в том, **кто отвечает за проверку**:
- в bash — ты (`if ! dpkg -l | grep -q nginx; then ...`);
- в Ansible — модуль. Он сам смотрит текущее состояние и меняет только расхождения.

Ключевые слова состояния: `state: present / absent / started / stopped / restarted /
latest / directory / link / touch`.

> 📝 Честная оговорка: Ansible **декларативен на уровне задачи**, но **императивен
> на уровне порядка** — задачи выполняются сверху вниз в указанном порядке.
> Это не Terraform с графом зависимостей. Хороший ответ на собесе именно такой.

## 4. ⭐ Идемпотентность — слово, ради которого учат раздел

> **Идемпотентность** — свойство операции давать один и тот же результат независимо
> от того, сколько раз её применили: один раз или сто.

```text:no-line-numbers
1-й запуск playbook:   PLAY RECAP  ok=3  changed=3   ← сервер настроен
2-й запуск playbook:   PLAY RECAP  ok=6  changed=0   ← ничего не тронуто, всё уже так
3-й запуск playbook:   PLAY RECAP  ok=6  changed=0   ← и так всегда
```

**Как это работает внутри модуля:**
```text:no-line-numbers
модуль apt: пакет nginx установлен?
   ├─ да  → ничего не делать, вернуть  {"changed": false}   → в отчёте  ok
   └─ нет → apt-get install nginx,     вернуть {"changed": true}  → в отчёте changed
```

### Почему это важно на практике

1. **Безопасный повтор.** Плейбук упал на 7-й задаче из 10? Чини причину и запускай заново —
   первые 6 задач просто отчитаются `ok`.
2. **Дрейф конфигурации.** Кто-то руками поправил `/etc/nginx/nginx.conf` — прогон плейбука
   вернёт файл к описанному состоянию, и ты увидишь `changed` (сигнал: кто-то лазил руками).
3. **`changed` как сигнал.** `changed=0` на втором прогоне = плейбук написан правильно.
   `changed` каждый раз = где-то «шумная» задача, чаще всего `command`/`shell`.
4. **Handler'ы.** Перезапуск сервиса происходит, **только если** конфиг реально изменился.
   Без идемпотентности пришлось бы рестартовать nginx при каждом прогоне.

### Что ломает идемпотентность

| Причина | Пример | Лечение |
|---------|--------|---------|
| `command`/`shell` | `shell: echo "x" >> /etc/hosts` — дописывает каждый раз | `lineinfile`, либо `creates:`/`changed_when:` |
| `state: latest` | «всегда свежая версия» → `changed`, когда вышло обновление | `state: present` + осознанные обновления |
| Генерация файла с меткой времени | шаблон с <code v-pre>{{ ansible_date_time }}</code> | убрать нестабильные данные из шаблона |
| `service: state=restarted` в обычной задаче | рестарт при каждом прогоне | `notify` → handler |
| Скачивание без проверки | `get_url` без `checksum`/`creates` | `checksum:`, `creates:` |

```yaml
# ❌ неидемпотентно: строка добавляется при каждом прогоне
- shell: echo "127.0.0.1 myapp.local" >> /etc/hosts

# ✅ идемпотентно: строка приводится к нужному виду
- ansible.builtin.lineinfile:
    path: /etc/hosts
    line: "127.0.0.1 myapp.local"
    state: present

# ✅ если без shell никак — объясни Ansible, когда это «изменение»
- ansible.builtin.shell: /opt/app/bin/init-db.sh
  args:
    creates: /var/lib/app/.initialized     # не запускать, если файл уже есть
```

> 🎤 **Формулировка для собеса (заучи):** «Идемпотентность — это когда повторный запуск
> плейбука не меняет систему, потому что она уже в нужном состоянии. Модуль сначала
> проверяет текущее состояние и выполняет действие только при расхождении. Практический
> критерий — на втором прогоне в PLAY RECAP `changed=0`.»

## 5. Как Ansible выполняет задачу (важно понимать)

```text:no-line-numbers
[control node]                                   [managed node]
ansible-playbook site.yml
   │
   ├─ читает inventory, playbook, переменные
   ├─ для задачи №1 берёт модуль apt (python-код)
   ├─ подставляет аргументы (name=nginx, state=present)
   ├─ открывает SSH-сессию ───────────────────────►  sshd
   ├─ копирует модуль во временный каталог ───────►  ~/.ansible/tmp/ansible-tmp-.../
   ├─ команда запуска ────────────────────────────►  /usr/bin/python3 AnsiballZ_apt.py
   │                                                        │ проверяет состояние
   │                                                        │ меняет при необходимости
   ◄─────────────────────── JSON {"changed": true, ...} ────┘
   ├─ печатает результат: changed: [web1]
   └─ удаляет временные файлы
```

Из этой схемы следуют важные выводы:
- **на каждую задачу — работа по сети**, поэтому 200 мелких задач на 100 хостов медленные
  (лечится `pipelining`, `forks`, `free`-стратегией — тема 13);
- **модуль — это код на целевой машине**, поэтому нужен python и правильный интерпретатор;
- **вывод модуля — JSON**, отсюда `register`, `changed_when`, `failed_when` (темы 07-08);
- **состояние между задачами не сохраняется в shell** — `cd /tmp` в одной задаче не влияет
  на следующую (у каждой задачи своя сессия).

## 6. Словарь блока (выучить сразу)

| Термин | Что это |
|--------|---------|
| **Control node** | Машина, с которой запускают Ansible (ноут, bastion, CI-раннер) |
| **Managed node** | Целевой хост, которым управляют |
| **Inventory** | Список хостов и групп + их переменные (тема 03) |
| **Module** | Готовая единица работы: `apt`, `copy`, `service`… (тема 05) |
| **Task** | Вызов модуля с аргументами |
| **Play** | Связка «группа хостов + список задач» |
| **Playbook** | YAML-файл с одним или несколькими play (тема 06) |
| **Handler** | Задача, которая выполняется, только если её «позвали» через `notify` (тема 09) |
| **Facts** | Данные, собранные с хоста (ОС, IP, память…) (тема 07) |
| **Role** | Переиспользуемый набор задач/шаблонов/переменных со стандартной структурой (тема 11) |
| **Collection** | Пакет из модулей/ролей/плагинов (`community.docker`, `ansible.posix`) |
| **Idempotency** | См. §4 — главное свойство |
| **AWX / Ansible Automation Platform** | Веб-интерфейс и RBAC поверх Ansible (AWX — бесплатный upstream) |

## 7. `ansible` vs `ansible-core`, версии и FQCN

```bash
pipx install ansible-core     # только ядро: ~70 базовых модулей (ansible.builtin.*)
pipx install ansible          # ядро + ~700 коллекций «в комплекте» ← обычно берут это
```

С версии 2.10 модули разъехались по **коллекциям**, и появилось **FQCN**
(Fully Qualified Collection Name):

```yaml
- ansible.builtin.apt:            # ядро
- ansible.posix.firewalld:        # коллекция ansible.posix
- community.docker.docker_container:   # коллекция community.docker
- community.general.ufw:          # коллекция community.general
```

Короткие имена (`apt:`, `copy:`) всё ещё работают, но **в новом коде пиши FQCN** —
это требование `ansible-lint` и защита от коллизий имён.

```bash
ansible --version                     # версия ansible-core + путь к конфигу
ansible-galaxy collection list        # какие коллекции установлены
ansible-doc -l | wc -l                # сколько модулей доступно
ansible-doc ansible.builtin.copy      # документация по модулю прямо в терминале
```

## 8. Где Ansible применяют в реальности

| Сценарий | Пример |
|----------|--------|
| **Provisioning / базовая настройка** | Новый сервер: пользователи, ключи, sudo, ntp, firewall, мониторинг-агент |
| **Управление конфигурацией** | Конфиги nginx/postgres из шаблонов, единый стандарт на весь парк |
| **Деплой приложения** | Выкатить новую версию: `git`/`docker pull` → перезапуск → health-check |
| **Оркестрация релиза** | Rolling update по 2 хоста (`serial`), вывод из балансировщика, возврат |
| **Разовые операции** | Ad-hoc: обновить пакет безопасности на всех хостах, собрать факты, выгрузить логи |
| **Внутри CI/CD** | Стадия `deploy` в пайплайне запускает `ansible-playbook` (блок CI/CD, тема 03) |
| **Настройка самой инфраструктуры** | Установка docker, k8s-нод (kubespray — это Ansible), GitLab Runner |

### Чем Ansible **не** является

- ❌ **Не замена Terraform.** Terraform создаёт ресурсы (VM, сети, балансировщики),
  Ansible настраивает то, что внутри ОС. Типовая связка: Terraform создал → Ansible настроил.
- ❌ **Не система мониторинга.** Он не следит за состоянием постоянно.
- ❌ **Не замена Docker/Kubernetes.** В k8s-мире конфигурация живёт в манифестах,
  а Ansible остаётся для нод, легаси-VM и вспомогательных задач.
- ❌ **Не язык программирования.** Как только в плейбуке начинается «программирование» —
  скорее всего, задачу решают не тем инструментом.

## 💼 Как это в DevOps

- Ansible — обычно **второй-третий** инструмент в резюме джуна после Linux и Docker,
  и первый, который показывают на практическом задании («настрой сервер плейбуком»).
- В компаниях он живёт в отдельном git-репозитории, куда открывают MR, гоняют
  `ansible-lint` и `--check` в CI и применяют кнопкой из пайплайна.
- Даже там, где всё в Kubernetes, Ansible остаётся: подготовка нод, легаси-VM, bastion-хосты,
  настройка CI-раннеров, разовые массовые операции.
- Типичный рабочий день: «нужно на 30 серверах поменять параметр sysctl» → правишь роль,
  MR, `--check` на одном хосте, применяешь на всех, `changed=30`, готово.

## 🧠 Что запомнить

1. Ansible — **управление конфигурацией**: с одной управляющей машины задаётся состояние
   целевых хостов.
2. **Agentless**: на хостах нужны только SSH, python3 и права; агент не ставится.
3. Модель **push**: ты инициируешь применение, а не агент сам просыпается.
4. Подход **декларативный** на уровне задач (`state: present`), но задачи выполняются
   строго по порядку сверху вниз.
5. **Идемпотентность** — главное понятие: повторный запуск ничего не меняет.
   Критерий — `changed=0` во втором прогоне.
6. Идемпотентность ломают `command`/`shell`, `state: latest` и нестабильные шаблоны.
7. Модуль копируется на хост и выполняется там python'ом; результат — JSON (`ok/changed/failed`).
8. Ansible ≠ Terraform: Terraform создаёт инфраструктуру, Ansible настраивает ОС внутри.
9. `ansible` (с коллекциями) vs `ansible-core` (только ядро); в новом коде — **FQCN**.
10. Ансибл действительно простой — сложность появляется в масштабе (скорость, структура репозитория, секреты).

### Блок A. Теория

**A1.** Своими словами: что такое Ansible и какую задачу он решает?

<details><summary>Ответ</summary>

Инструмент управления конфигурацией: с одной управляющей машины по SSH приводит
целевые хосты в описанное в коде состояние. Решает задачи повторяемости, массовости
и версионирования настройки серверов.

</details>

**A2.** Что означает «agentless»? Что при этом всё-таки должно быть на целевом хосте?

<details><summary>Ответ</summary>

Agentless — на управляемые хосты не ставится постоянный агент. Нужны: доступ по SSH,
Python 3 и достаточные права (обычно sudo).

</details>

**A3.** Чем push-модель отличается от pull-модели? Назови плюс и минус каждой.

<details><summary>Ответ</summary>

Push (Ansible): запуск инициирует оператор/CI — просто, прозрачно, но изменения
применяются только когда запустили. Pull (Puppet/Chef): агент сам регулярно тянет
конфигурацию — автоматически лечит дрейф, но требует агента, сертификатов и инфраструктуры.

</details>

**A4.** Что такое декларативный подход? Приведи пару «императивно → декларативно».

<details><summary>Ответ</summary>

Декларативно = описываю желаемое состояние, модуль сам решает, что делать.
`apt-get install -y nginx` → `apt: name=nginx state=present`;
`systemctl enable --now nginx` → `service: name=nginx state=started enabled=true`.

</details>

**A5.** ⭐ Дай определение идемпотентности и назови практический критерий её проверки.

<details><summary>Ответ</summary>

Повторное применение не меняет систему, потому что она уже в нужном состоянии.
Критерий: второй прогон даёт `changed=0` в PLAY RECAP.

</details>

**A6.** Почему `command`/`shell` считаются «неидемпотентными» модулями?
Как сделать такую задачу идемпотентной (два способа)?

<details><summary>Ответ</summary>

Они просто выполняют команду и не знают, что считать «изменением»: любая команда
объявляется `changed`. Лечение: (1) `args: creates:`/`removes:`, (2) `changed_when:`
с осмысленным условием (или `register` + анализ вывода); лучший вариант — найти
профильный модуль.

</details>

**A7.** Опиши по шагам, что происходит, когда Ansible выполняет одну задачу на одном хосте.

<details><summary>Ответ</summary>

Ansible берёт python-код модуля, подставляет аргументы, по SSH копирует его
во временный каталог на хосте, запускает python3, модуль проверяет состояние и меняет
при необходимости, возвращает JSON, временные файлы удаляются.

</details>

**A8.** Почему `cd /opt && ./script.sh` в одной задаче не влияет на следующую задачу?

<details><summary>Ответ</summary>

У каждой задачи своя SSH-сессия и свой процесс: shell-состояние (рабочий каталог,
переменные окружения) не переносится. Нужен общий контекст — используй `args: chdir:`
или объединяй в одну задачу.

</details>

**A9.** Чем Ansible отличается от Terraform? Могут ли они работать вместе?

<details><summary>Ответ</summary>

Terraform управляет **инфраструктурными ресурсами** (VM, сети, DNS, балансировщики)
и хранит state; Ansible настраивает **ОС внутри** машины. Вместе работают штатно:
Terraform создаёт → отдаёт inventory → Ansible настраивает.

</details>

**A10.** Чем Ansible отличается от Puppet? Назови три отличия.

<details><summary>Ответ</summary>

(1) Agentless vs агент; (2) push vs pull; (3) YAML vs собственный DSL/Ruby;
плюс порог входа и подход к дрейфу конфигурации.

</details>

**A11.** Что такое control node и managed node?

<details><summary>Ответ</summary>

Control node — машина, с которой запускают Ansible (ноутбук, bastion, CI-раннер);
managed node — хост, которым управляют.

</details>

**A12.** Объясни разницу между `ansible` и `ansible-core`.

<details><summary>Ответ</summary>

`ansible-core` — только ядро и базовые модули (`ansible.builtin.*`);
`ansible` — ядро плюс большой набор коллекций сообщества.

</details>

**A13.** Что такое FQCN и зачем он нужен?

<details><summary>Ответ</summary>

Fully Qualified Collection Name — полное имя модуля вместе с коллекцией
(`community.docker.docker_container`). Убирает неоднозначность имён и является требованием
линтеров; короткие имена остаются для совместимости.

</details>

**A14.** Что означают `ok`, `changed`, `failed`, `skipped`, `unreachable` в PLAY RECAP?

<details><summary>Ответ</summary>

`ok` — задача выполнена, изменений не потребовалось; `changed` — состояние изменено;
`failed` — задача упала; `skipped` — пропущена по `when`; `unreachable` — до хоста
не удалось достучаться (проблема связи/SSH, а не задачи).

</details>

**A15.** Назови три сценария, где Ansible применяют в реальных компаниях.

<details><summary>Ответ</summary>

Базовая настройка новых серверов, управление конфигами сервисов (nginx/postgres),
деплой приложений из CI/CD, разовые массовые операции, подготовка нод под Kubernetes.

</details>

**A16.** В каком случае Ansible — **плохой** выбор инструмента?

<details><summary>Ответ</summary>

Когда нужно непрерывное автоисправление дрейфа без запуска (лучше pull-системы);
при управлении тысячами хостов с жёсткими требованиями к скорости; для создания самой
инфраструктуры (там Terraform); внутри Kubernetes, где состояние описывают манифестами.

</details>

### Блок B. «Что делает команда»

```bash
B1.  ansible all -i inventory.ini -m ping
B2.  ansible web -m command -a "uptime"
B3.  ansible all -m setup -a "filter=ansible_distribution*"
B4.  ansible-playbook -i inventory.ini site.yml --check --diff
B5.  ansible-doc ansible.builtin.lineinfile
B6.  ansible-doc -l | wc -l
B7.  ansible --version
B8.  ansible-galaxy collection list
B9.  ansible all -m command -a "id" -b
B10. ansible-playbook site.yml --list-hosts
```

<details><summary>Ответ</summary>

```text:no-line-numbers
B1.  Проверить доступность всех хостов инвентаря (модуль ping = SSH + python работают)
B2.  Выполнить uptime на хостах группы web
B3.  Собрать факты и показать только переменные, начинающиеся на ansible_distribution
B4.  «Сухой прогон» плейбука: показать, что изменилось бы, и различия в файлах
B5.  Показать документацию и примеры по модулю lineinfile
B6.  Посчитать количество доступных модулей
B7.  Показать версию ansible-core, путь к конфигу и к python
B8.  Список установленных коллекций и их версий
B9.  Выполнить id на всех хостах с повышением привилегий (sudo) — должен показать root
B10. Показать, на какие хосты плейбук распространится, ничего не выполняя
```

</details>

Для каждого фрагмента ниже ответь: **идемпотентен он или нет** и **почему**.

```yaml
# B11
- ansible.builtin.shell: adduser deploy
```

<details><summary>Ответ</summary>

❌ Неидемпотентно: второй запуск упадёт (`adduser: The user 'deploy' already exists`).

</details>

```yaml
# B12
- ansible.builtin.user:
    name: deploy
    state: present
```

<details><summary>Ответ</summary>

✅ Идемпотентно: модуль `user` создаст пользователя только при отсутствии.

</details>

```yaml
# B13
- ansible.builtin.apt:
    name: nginx
    state: latest
```

<details><summary>Ответ</summary>

⚠️ Формально идемпотентно (состояние «последняя версия» соблюдается), но
на практике даёт `changed` в момент выхода обновления и приводит к неконтролируемым
апгрейдам на проде. Для предсказуемости — `state: present`.

</details>

```yaml
# B14
- ansible.builtin.shell: echo "net.ipv4.ip_forward=1" >> /etc/sysctl.conf
```

<details><summary>Ответ</summary>

❌ Неидемпотентно: строка дописывается при каждом прогоне. Нужен `lineinfile`
(а для sysctl — модуль `ansible.posix.sysctl`).

</details>

```yaml
# B15
- ansible.builtin.service:
    name: nginx
    state: restarted
```

<details><summary>Ответ</summary>

❌ `restarted` — действие, а не состояние: сервис рестартует при каждом прогоне.
Правильно — `state: started` + `notify` на handler с рестартом.

</details>

```yaml
# B16
- ansible.builtin.get_url:
    url: https://example.com/app.tar.gz
    dest: /opt/app.tar.gz
```

<details><summary>Ответ</summary>

✅ Условно идемпотентно: `get_url` не качает повторно, если файл на месте
(сравнивает по времени/размеру, а с `checksum:` — надёжно). Без `checksum` возможны сюрпризы
при изменении файла на сервере.

</details>

### Блок C. Практика

#### C1. 🔑 Стенд и первый контакт

1. Подними 3 хоста (docker или VM) по инструкции из индекса.
2. Сгенерируй отдельный ключ `~/.ssh/ansible_lab` и разложи публичную часть по хостам.
3. Убедись, что `ssh -i ~/.ssh/ansible_lab devops@<host>` работает **без пароля**.
4. Напиши `inventory.ini` с группами `web` (2 хоста) и `db` (1 хост).
5. Добейся `ansible all -m ping` → три `SUCCESS`.

<details><summary>Ответ</summary>

Типовые грабли: не тот порт (docker-стенд слушает 2201-2203), `ansible_user`
не задан, права на `authorized_keys` (нужно 600, каталог 700), не принят host key
(`ansible_ssh_common_args='-o StrictHostKeyChecking=accept-new'` или `ssh-keyscan`).

</details>

#### C2. Убеждаемся, что агента нет

Зайди на целевой хост и выполни:
```bash
ps aux | grep -i ansible ; ls -la ~/.ansible ; which python3
```
Ответь: остаётся ли на хосте работающий процесс Ansible между запусками? Что остаётся вообще?

<details><summary>Ответ</summary>

Между запусками на хосте не остаётся ни одного процесса Ansible. Остаётся только
каталог `~/.ansible/tmp` (обычно пустой) — временные файлы модулей удаляются после выполнения.

</details>

#### C3. Смотрим, как выполняется модуль

Запусти с максимальной подробностью и найди в выводе временный файл модуля:
```bash
ansible node1 -m ping -vvv 2>&1 | grep -E "AnsiballZ|tmp|SSH: EXEC" | head -20
```
Опиши своими словами три строки, которые ты увидел.

<details><summary>Ответ</summary>

В выводе видно: `SSH: EXEC ssh ...` — установка соединения; `PUT ... TO
/home/devops/.ansible/tmp/ansible-tmp-*/AnsiballZ_ping.py` — копирование модуля;
`EXEC /bin/sh -c '/usr/bin/python3 .../AnsiballZ_ping.py'` — запуск; затем `rm -f -r`.

</details>

#### C4. Идемпотентность на практике

```bash
ansible web -m apt -a "name=nginx state=present" -b          # 1-й раз
ansible web -m apt -a "name=nginx state=present" -b          # 2-й раз
```
Сравни цвет/статус вывода (`CHANGED` vs `SUCCESS`). Объясни разницу.

<details><summary>Ответ</summary>

Первый раз — `CHANGED` (пакет ставится), второй — `SUCCESS`/`ok` (`"changed": false`),
потому что модуль увидел установленный пакет и ничего не делал.

</details>

#### C5. Ломаем идемпотентность руками

```bash
ansible web -m shell -a 'echo "# test" >> /etc/motd' -b      # запусти 3 раза
ansible web -m command -a "tail -5 /etc/motd"
```
Сколько строк добавилось? Перепиши эту операцию идемпотентно через `lineinfile`
и проверь повторным запуском.

<details><summary>Ответ</summary>

Добавится три строки — `shell` просто выполняет команду. Идемпотентный вариант:
`ansible web -m lineinfile -a 'path=/etc/motd line="# test"' -b` — первый раз `changed`,
дальше `ok`.

</details>

#### C6. Дрейф конфигурации

1. Ad-hoc'ом положи файл: `ansible web -m copy -a 'content="hello\n" dest=/tmp/state.txt' -b`
2. Руками на хосте измени его содержимое.
3. Запусти ту же команду ещё раз. Что покажет Ansible и почему это полезно?

<details><summary>Ответ</summary>

Ansible покажет `changed` и вернёт файл к описанному содержимому. Это и есть
борьба с дрейфом: любые ручные правки затираются, а `changed` в отчёте — сигнал,
что кто-то менял файл мимо кода.

</details>

#### C7. Сравнение с bash

Напиши bash-скрипт, который делает то же, что эти три задачи:
установить nginx, положить конфиг, включить сервис — **и корректно переживает повторный
запуск**. Посчитай строки. Сравни с 12 строками YAML.

<details><summary>Ответ</summary>

Честный bash с проверками — это 25-40 строк с `if`, `grep`, `systemctl is-enabled`,
обработкой ошибок и `set -euo pipefail`; и он всё равно не даёт отчёта по хостам,
параллельного выполнения и `--check`.

</details>

#### C8. Python на целевом хосте

Удали/переименуй python3 на одном тестовом хосте (в контейнере не жалко) и запусти `-m ping`.
Какую ошибку ты увидишь? Затем попробуй `ansible node -m raw -a "echo hi"` — почему сработало?

<details><summary>Ответ</summary>

Будет ошибка вида `/bin/sh: 1: /usr/bin/python3: not found` (модуль невозможно
выполнить). `raw` работает, потому что выполняет команду прямо через SSH-шелл,
без доставки python-модуля — им же и ставят python на «голые» хосты.

</details>

#### C9. Замер накладных расходов

```bash
time ansible all -m command -a "echo x"
time ansible all -m command -a "echo x" -f 1
```
Объясни разницу и предположи, что будет на 100 хостах.

<details><summary>Ответ</summary>

По умолчанию `forks = 5` — хосты обрабатываются параллельно; `-f 1` делает
выполнение последовательным и медленнее. На 100 хостах при `forks=5` будет 20 «волн» —
отсюда тюнинг `forks`, `pipelining` и стратегия `free` (тема 13).

</details>

### Блок D. Инциденты

**D1.** `ansible all -m ping` → `UNREACHABLE! ... Permission denied (publickey,password)`.
Перечисли пять причин по порядку проверки.

<details><summary>Ответ</summary>

(1) Неверные пользователь/ключ (`ansible_user`, `ansible_ssh_private_key_file`);
(2) публичный ключ не добавлен в `authorized_keys` на хосте; (3) неправильные права
на `~/.ssh` (700) и `authorized_keys` (600); (4) не тот хост/порт (`ansible_host`,
`ansible_port`); (5) не принят host key / sshd не запущен / фильтруется firewall.
Проверка вручную: `ssh -i key -p port user@host -v`.

</details>

**D2.** `ping` работает, а установка пакета падает с `Permission denied`. Причина?

<details><summary>Ответ</summary>

Не запрошено повышение привилегий: нужен `-b` (`become: true`) — а если sudo просит
пароль, то `-K`/`ansible_become_password`, либо NOPASSWD в sudoers.

</details>

**D3.** Коллега говорит: «Твой плейбук нельзя запускать второй раз, он всё сломает».
Как проверить, прав ли он, ничего не сломав?

<details><summary>Ответ</summary>

Запустить `ansible-playbook site.yml --check --diff` — сухой прогон покажет,
что изменилось бы, ничего не меняя. Если во втором (обычном) прогоне `changed=0` —
плейбук идемпотентен и коллега не прав.

</details>

**D4.** Плейбук каждый раз показывает `changed=12`, хотя на сервере ничего не меняется.
Что это значит и где искать причину?

<details><summary>Ответ</summary>

Есть «шумные» задачи: `command`/`shell` без `changed_when`/`creates`,
`state: latest`, `restarted`, шаблоны с нестабильными данными. Ищем по выводу, какие
именно задачи всегда `changed`, и переписываем.

</details>

**D5.** Плейбук упал на 5-й задаче из 9. Можно ли просто запустить его заново? От чего зависит ответ?

<details><summary>Ответ</summary>

Обычно да, если плейбук идемпотентен: выполненные задачи отчитаются `ok`.
Опасно, если внутри неидемпотентные операции (миграции БД, `shell` с побочными эффектами,
скачивание/распаковка поверх) — тогда сначала разбираемся с состоянием.

</details>

**D6.** `ansible-playbook` выдаёт `ERROR! 'apt' is not a valid attribute for a Play`.
Что произошло со структурой YAML?

<details><summary>Ответ</summary>

Нарушена структура: задача написана на уровне play (в словаре play), а не внутри
списка `tasks:`. Проверяется `ansible-playbook --syntax-check` и отступами.

</details>

**D7.** На хосте нет python3 (минимальный образ). Какие есть варианты решения (три)?

<details><summary>Ответ</summary>

(1) Поставить python `raw`-модулем в отдельном play (`gather_facts: false`);
(2) указать другой интерпретатор через `ansible_python_interpreter`;
(3) использовать образ/дистрибутив с python или другой connection-плагин.

</details>

**D8.** Разработчик предлагает: «Давай вместо Ansible просто положим bash-скрипт в cron
на каждый сервер». Сформулируй три возражения.

<details><summary>Ответ</summary>

(1) Скрипт в cron неуправляем: нет отчёта, что где отработало и с каким результатом;
(2) bash без ручных проверок неидемпотентен — повторный запуск ломает состояние;
(3) нет централизованного применения и отката, обновление скрипта нужно раскладывать
на каждый сервер, а инвентарь и переменные нигде не описаны.

</details>

### Блок E. Вопросы с собеседования

**1.** Что такое Ansible и для чего он нужен?

<details><summary>Ответ</summary>

Инструмент управления конфигурацией: описываешь состояние серверов кодом, Ansible
приводит их к нему по SSH с одной управляющей машины.

</details>

**2.** ⭐ Что такое идемпотентность? Приведи пример неидемпотентной задачи.

<details><summary>Ответ</summary>

Свойство повторяемости: сколько раз ни примени — результат один. Пример неидемпотентной
задачи: `shell: echo ... >> /etc/hosts` (дописывает каждый раз) или `shell: adduser deploy`.

</details>

**3.** Что значит agentless и что требуется на целевом хосте?

<details><summary>Ответ</summary>

Не требуется агент на хостах — нужны SSH, python3 и права sudo.

</details>

**4.** Push или pull? В чём разница с Puppet/Chef?

<details><summary>Ответ</summary>

Push: запуск инициирует оператор или CI. Puppet/Chef — pull: агент сам периодически
забирает и применяет конфигурацию.

</details>

**5.** Чем Ansible отличается от Terraform?

<details><summary>Ответ</summary>

Terraform — создание инфраструктуры (state, граф зависимостей), Ansible — настройка ОС
и приложений внутри. Часто используются вместе.

</details>

**6.** Ansible декларативный или императивный? (вопрос с подвохом)

<details><summary>Ответ</summary>

Декларативный на уровне задач (описываем состояние), но выполнение задач — строго
по порядку, то есть императивная последовательность. Это честный и «взрослый» ответ.

</details>

**7.** Как Ansible выполняет модуль на удалённом хосте?

<details><summary>Ответ</summary>

Копирует python-модуль на хост, запускает его там, получает JSON-результат,
удаляет временные файлы.

</details>

**8.** Что такое control node?

<details><summary>Ответ</summary>

Машина, с которой запускают Ansible.

</details>

**9.** Зачем Ansible, если есть bash-скрипты?

<details><summary>Ответ</summary>

Идемпотентность из коробки, параллельное выполнение на множестве хостов, единый отчёт,
`--check`, переиспользуемые роли, инвентарь и переменные, читаемость для всей команды.

</details>

**10.** Какие минусы у Ansible ты знаешь?

<details><summary>Ответ</summary>

Скорость на больших парках (SSH на каждую задачу), YAML плохо подходит для сложной
логики, нет непрерывного контроля дрейфа, отладка шаблонов и приоритетов переменных
бывает болезненной.

</details>
