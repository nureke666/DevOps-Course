# 01. Основы очередей сообщений

> Роадмап → 7. Остальное → Очереди: *«С очередями сервисы общаются асинхронно:
> положил сообщение → когда-нибудь обработают.»*
>
> **После темы ты умеешь:** объяснить, зачем нужны очереди, какие бывают гарантии
> доставки, что такое идемпотентность, DLQ и backpressure — и когда очередь **не** нужна.

---

## 🗺️ Синхронно и асинхронно

```text:no-line-numbers
СИНХРОННОЕ ВЗАИМОДЕЙСТВИЕ (HTTP/gRPC)
 клиент → order-service ──► payment ──► email ──► analytics
                │  ждёт      ждёт       ждёт      ждёт
                └─ общее время = сумма всех шагов
                   любой упавший сервис ломает весь запрос

АСИНХРОННОЕ (через брокер)
 клиент → order-service ──► [ БРОКЕР ] ──► payment-worker
                │ ответил   │           ──► email-worker
                ▼ сразу     │           ──► analytics-worker
          заказ создан      └─ обработчики работают в своём темпе,
                              падение одного не ломает остальных
```

| Когда нужна очередь | Когда она лишняя |
|---------------------|------------------|
| Долгая обработка (отчёты, видео, рассылки) | Нужен немедленный ответ пользователю |
| Пиковая нагрузка, которую нельзя обработать сразу | Простое CRUD-приложение без интеграций |
| Несколько потребителей одного события | Два сервиса, которым достаточно HTTP |
| Интеграция разнородных систем | Строгая транзакционность в рамках одной БД |
| Надёжная доставка при недоступности получателя | Нет ресурсов эксплуатировать ещё один кластер |

> ⚠️ Очередь — это дополнительный компонент, который надо мониторить, бэкапить
> и чинить в 3 ночи. Ставить её «потому что модно» — плохая идея.

## 1. Словарь

| Термин | Смысл |
|--------|-------|
| **Брокер** | Сервер, который принимает, хранит и отдаёт сообщения |
| **Продюсер (producer)** | Тот, кто отправляет сообщения |
| **Консьюмер (consumer)** | Тот, кто читает и обрабатывает |
| **Сообщение** | Данные + метаданные (заголовки, ключ, время) |
| **Топик / очередь** | Именованный «канал», куда пишут и откуда читают |
| **Партиция** | Часть топика; единица параллелизма и порядка (Kafka) |
| **Оффсет** | Позиция сообщения в партиции (Kafka) |
| **Консьюмер-группа** | Набор потребителей, делящих между собой работу |
| **Ack / commit** | Подтверждение обработки |
| **DLQ** (dead letter queue) | Куда складывают сообщения, которые не удалось обработать |
| **Retention** | Сколько сообщения хранятся |
| **Backpressure** | Ситуация, когда производитель быстрее потребителя |

## 2. Две модели доставки

```text:no-line-numbers
 POINT-TO-POINT (очередь задач)          PUBLISH/SUBSCRIBE (события)
 ──────────────────────────────          ────────────────────────────
 producer → [ queue ] → ОДИН из          producer → [ topic ] → ВСЕ подписчики
             потребителей                             ├──► биллинг
             (конкурирующие потребители)               ├──► почта
                                                       └──► аналитика

 «обработай эту задачу»                   «произошло событие, реагируйте кто хочет»
 RabbitMQ (классика)                      Kafka (классика), RabbitMQ fanout/topic
```

Практическое различие: в первой модели важно **не обработать дважды**,
во второй — **дать всем заинтересованным свою копию**.

## 3. ⭐ Гарантии доставки

```text:no-line-numbers
 AT-MOST-ONCE            AT-LEAST-ONCE                EXACTLY-ONCE
 (не больше одного)      (не меньше одного)           (ровно один)
 ────────────────        ─────────────────            ────────────
 подтвердил ДО           подтвердил ПОСЛЕ             транзакции/дедупликация
 обработки               обработки                    в рамках одной системы
 можно потерять ⚠️        можно обработать дважды ⚠️   сложно и дорого
 логи, метрики           ⭐ дефолт почти везде         платежи (и то обычно
                                                       делают идемпотентность)
```

| Гарантия | Как получается | Цена |
|----------|----------------|------|
| At-most-once | Коммит оффсета/ack сразу при получении | Потеря при падении обработчика |
| **At-least-once** | Коммит после успешной обработки | Дубликаты при падении между обработкой и коммитом |
| Exactly-once | Транзакции брокера + идемпотентный продюсер (Kafka), либо дедупликация на стороне потребителя | Сложность, снижение пропускной способности; «сквозной» exactly-once с внешними системами практически недостижим |

⭐ Вывод, который спрашивают на собесе:
**в реальности работают с at-least-once, а дубликаты обезвреживают идемпотентностью.**

## 4. Идемпотентность — обязательный навык

Идемпотентная операция даёт один и тот же результат при повторном выполнении.

```text:no-line-numbers
НЕ идемпотентно:                      Идемпотентно:
balance = balance + 100               if not processed(msg_id):
                                          balance = balance + 100
повтор → деньги начислены дважды          mark_processed(msg_id)
                                      повтор → ничего не произойдёт
```

Типовые приёмы:
| Приём | Как работает |
|-------|--------------|
| **Идентификатор сообщения** | Хранить обработанные `message_id` и пропускать повторы |
| **Естественный ключ** | `UPSERT` по бизнес-ключу вместо `INSERT` |
| **Условное обновление** | `UPDATE ... WHERE status = 'new'` — повтор ничего не изменит |
| **Версия/номер события** | Применять только более новые версии |
| **Транзакция с дедуп-таблицей** | Запись результата и отметки «обработано» в одной транзакции |

## 5. Ошибки, ретраи и DLQ

```text:no-line-numbers
   сообщение → обработка → ошибка
                   │
                   ├─ повтор 1 (через 1 с)
                   ├─ повтор 2 (через 5 с)     ← экспоненциальная задержка
                   ├─ повтор 3 (через 30 с)
                   ▼
             ⛔ не получилось
                   │
                   ▼
          [ DEAD LETTER QUEUE ]  ← «отстойник» для ручного разбора
```

| Правило | Почему |
|---------|--------|
| Различать временные и постоянные ошибки | БД недоступна — повторим; битый JSON — повторять бессмысленно |
| Ограничивать число повторов | Иначе «ядовитое сообщение» (poison message) блокирует очередь навсегда |
| Делать задержку между повторами | Не добивать упавшую зависимость |
| Складывать неподдающееся в DLQ | Очередь продолжает работать, проблема не теряется |
| ⭐ Мониторить DLQ | Непустая DLQ = кто-то должен посмотреть; алерт обязателен |
| Уметь переотправить из DLQ | После исправления кода сообщения возвращают в основную очередь |

## 6. Порядок сообщений и параллелизм

```text:no-line-numbers
Порядок гарантируется только внутри одной партиции/очереди при одном потребителе.

Kafka: сообщения с одним КЛЮЧОМ попадают в одну партицию → их порядок сохраняется
   key=user-42 → партиция 1 → события этого пользователя строго по порядку
   key=user-77 → партиция 3

Хочешь параллелизм → больше партиций.
Хочешь строгий глобальный порядок → одна партиция → и никакого параллелизма.
```

| Хочу | Как |
|------|-----|
| Параллельная обработка | Больше партиций и потребителей в группе |
| Порядок по сущности | Ключ партиционирования = идентификатор сущности |
| Глобальный порядок | Одна партиция (и смириться с пропускной способностью) |
| Не потерять порядок при ретраях | Обрабатывать сообщение до успеха либо отправлять в DLQ, не «перепрыгивая» |

## 7. Backpressure и накопление

```text:no-line-numbers
продюсер 10 000 msg/s  ──►  [ очередь растёт ]  ──►  консьюмер 2 000 msg/s
                                    │
                        лаг/глубина очереди растёт ⚠️
                                    │
     ┌──────────────────────────────┼──────────────────────────────┐
     ▼                              ▼                              ▼
 добавить потребителей      оптимизировать обработку       ограничить продюсера
 (и партиции в Kafka)       (батчи, индексы, кэш)          (rate limit, sampling)
```

Что произойдёт, если ничего не делать: в RabbitMQ закончится память/диск и брокер
начнёт блокировать продюсеров; в Kafka сообщения начнут удаляться по retention,
и потребитель потеряет данные, до которых не успел дочитать.

⭐ Поэтому **лаг/глубина очереди — главная метрика** этого блока, и на неё ставят алерт.

## 8. Типовые паттерны

| Паттерн | Суть |
|---------|------|
| **Work queue** | Много воркеров разбирают задачи из общей очереди |
| **Pub/Sub (события)** | Событие получают все заинтересованные сервисы |
| **Outbox** | Сообщение пишется в БД в той же транзакции, что и данные, затем отправляется отдельным процессом — гарантия «сохранили и отправили» ⭐ |
| **Saga** | Длинная бизнес-операция как цепочка событий с компенсациями |
| **CDC** | Изменения в БД превращаются в поток событий (Debezium) |
| **Delayed/scheduled** | Отложенная доставка (плагин RabbitMQ, отдельные топики) |
| **Priority queue** | Отдельные очереди под разные приоритеты |

---

## 9. Грабли

| Грабля | Последствие | Решение |
|--------|-------------|---------|
| Обработчик не идемпотентен | Двойные списания и письма | Дедупликация по `message_id`/ключу |
| Нет DLQ | «Ядовитое» сообщение блокирует очередь | DLQ + алерт + возможность переотправки |
| Бесконечные ретраи без задержки | Шторм запросов к упавшей зависимости | Лимит повторов, экспоненциальная задержка |
| Нет мониторинга лага | Узнаёшь о проблеме от бизнеса | Алерт на лаг/глубину очереди |
| Огромные сообщения | Брокер деградирует | Хранить payload в S3, в сообщении — ссылку |
| Очередь как база данных | Неуправляемый рост, потеря данных по retention | Брокер — транспорт, а не хранилище состояния |
| Синхронный запрос через очередь | Латентность и сложность | Для RPC лучше HTTP/gRPC |
| Нет схемы сообщений | Обновление ломает потребителей | Версионирование и schema registry |

## 💼 Как это в DevOps

- Девопс редко пишет продюсеров и консьюмеров, но **эксплуатирует брокер**: поднимает,
  настраивает retention и репликацию, следит за лагом, дисками и памятью, чинит инциденты.
- Первые вопросы к команде при внедрении очереди: какие гарантии нужны, идемпотентны ли
  обработчики, есть ли DLQ, что делать при росте лага, сколько хранить сообщения.
- В мониторинге появляются: лаг консьюмер-групп, глубина очередей, скорость записи/чтения,
  размер DLQ, состояние брокеров и диски.
- Наличие очереди меняет разбор инцидентов: «данные не появились» может означать
  не ошибку, а отставание обработчика — это надо уметь быстро отличать.

## 🧠 Что запомнить

1. Очередь развязывает сервисы во времени, сглаживает пики и повышает надёжность —
   но это ещё один компонент в эксплуатации.
2. Две модели: очередь задач (один получатель) и pub/sub (все подписчики).
3. ⭐ Практическая гарантия — at-least-once; дубликаты неизбежны, поэтому обработчики
   обязаны быть идемпотентными.
4. Exactly-once существует, но дорог и не работает «сквозным» образом с внешними системами.
5. Идемпотентность достигается дедупликацией по `message_id`, upsert'ами и условными
   обновлениями.
6. Ретраи должны быть ограниченными и с задержкой, а неподдающиеся сообщения —
   уходить в DLQ, за которой следят.
7. Порядок гарантируется только внутри партиции/очереди; ключ партиционирования
   сохраняет порядок по сущности.
8. Лаг и глубина очереди — главные метрики; на них ставят алерты.
9. Большие payload'ы хранят в объектном хранилище, в сообщении передают ссылку.
10. Брокер — транспорт, а не база данных и не замена HTTP для синхронных запросов.

### Блок A. Теория

**A1.** Какие три задачи решают очереди сообщений?

<details><summary>Ответ</summary>

Развязка сервисов во времени, сглаживание пиков нагрузки, надёжная доставка
при временной недоступности получателя (плюс удобное добавление новых потребителей).

</details>

**A2.** Когда очередь **не** нужна? Назови три случая.

<details><summary>Ответ</summary>

Когда нужен немедленный ответ пользователю; когда двум сервисам достаточно
HTTP; когда нет ресурсов эксплуатировать ещё один кластер; когда требуется строгая
транзакционность в рамках одной БД.

</details>

**A3.** Чем модель «очередь задач» отличается от pub/sub?

<details><summary>Ответ</summary>

В очереди задач сообщение получает **один** из конкурирующих потребителей;
в pub/sub копию события получают **все** подписчики.

</details>

**A4.** Объясни термины: брокер, продюсер, консьюмер, топик, партиция, оффсет,
консьюмер-группа.

<details><summary>Ответ</summary>

Брокер — сервер сообщений; продюсер отправляет; консьюмер читает; топик —
именованный канал; партиция — часть топика, единица параллелизма и порядка;
оффсет — позиция сообщения в партиции; консьюмер-группа — набор потребителей,
делящих партиции между собой.

</details>

**A5.** ⭐ Что такое at-most-once, at-least-once, exactly-once? Какая гарантия
используется на практике?

<details><summary>Ответ</summary>

At-most-once — подтверждение до обработки (возможна потеря); at-least-once —
подтверждение после обработки (возможны дубликаты); exactly-once — ровно один раз
(транзакции и дедупликация). На практике используют at-least-once.

</details>

**A6.** Почему exactly-once «сквозным образом» практически недостижим?

<details><summary>Ответ</summary>

Потому что обработка обычно затрагивает внешние системы (БД, платёжный шлюз,
почта), и атомарно связать «обработали во внешней системе» и «подтвердили в брокере»
невозможно без распределённых транзакций. Kafka даёт exactly-once внутри своей
экосистемы (read-process-write), но не «до конца мира».

</details>

**A7.** Что такое идемпотентность и почему она обязательна при at-least-once?

<details><summary>Ответ</summary>

Свойство операции давать тот же результат при повторе. При at-least-once
дубликаты неизбежны, и только идемпотентность превращает их в безопасные.

</details>

**A8.** Назови четыре способа сделать обработчик идемпотентным.

<details><summary>Ответ</summary>

Дедупликация по `message_id`; upsert по бизнес-ключу; условное обновление
(`WHERE status='new'`); версии/номера событий с применением только более новых;
запись результата и отметки об обработке в одной транзакции.

</details>

**A9.** Что такое DLQ и зачем она нужна?

<details><summary>Ответ</summary>

Очередь для сообщений, которые не удалось обработать после заданного числа
попыток. Позволяет не блокировать основную очередь и не терять проблемные сообщения.

</details>

**A10.** Что такое poison message и как от него защищаются?

<details><summary>Ответ</summary>

Сообщение, обработка которого всегда падает (битый формат, несовместимые
данные). Защита — ограничение числа повторов и переброс в DLQ.

</details>

**A11.** Как правильно устроены ретраи? Какие ошибки повторять не нужно?

<details><summary>Ответ</summary>

Ограниченное число попыток с экспоненциальной задержкой и джиттером;
повторять имеет смысл временные ошибки (недоступна БД, таймаут), а постоянные
(невалидный формат, нарушение бизнес-правил) — сразу в DLQ.

</details>

**A12.** Где гарантируется порядок сообщений? Как сохранить порядок по пользователю?

<details><summary>Ответ</summary>

Внутри одной партиции (Kafka) или одной очереди с одним потребителем.
Порядок по пользователю — использовать идентификатор пользователя как ключ
партиционирования.

</details>

**A13.** Что такое backpressure и какие есть три стратегии реакции?

<details><summary>Ответ</summary>

Ситуация, когда продюсер быстрее консьюмера. Стратегии: масштабировать
потребителей (и партиции), ускорить обработку, ограничить продюсера
(rate limit, sampling, отбрасывание малозначимых событий).

</details>

**A14.** Что произойдёт, если потребитель отстаёт, а retention истекает?

<details><summary>Ответ</summary>

Сообщения будут удалены по истечении retention до того, как потребитель их
прочитает — это безвозвратная потеря данных. Поэтому лаг мониторят, а retention
выбирают с запасом.

</details>

**A15.** Что такое паттерн outbox и какую проблему он решает?

<details><summary>Ответ</summary>

Событие записывается в таблицу outbox в той же транзакции, что и бизнес-данные,
а отдельный процесс читает outbox и отправляет в брокер. Решает проблему
«данные записались, а событие не ушло» (или наоборот).

</details>

### Блок C. Практика

#### C1. Синхронно vs асинхронно (на бумаге)
Возьми процесс «создание заказа» с четырьмя шагами (оплата, письмо, склад, аналитика).
Нарисуй синхронный и асинхронный варианты, посчитай время ответа пользователю
и оцени, что ломается при отказе каждого шага.

#### C2. Первое сообщение
1. В Kafka создай топик, отправь и прочитай сообщение (CLI из темы 03).
2. В RabbitMQ через UI создай очередь, опубликуй и получи сообщение.
3. Опиши, что произошло с сообщением после чтения в каждом случае.

<details><summary>Ответ</summary>

В Kafka сообщение остаётся в топике после чтения (до истечения retention),
в RabbitMQ удаляется после подтверждения.

</details>

#### C3. 🔑 At-least-once своими руками
1. Напиши консьюмер, который обрабатывает сообщение и коммитит оффсет **после** обработки.
2. Убей процесс между обработкой и коммитом.
3. Запусти заново — увидь повторную обработку.
4. Сделай обработку идемпотентной и повтори эксперимент.

<details><summary>Ответ</summary>

Повторная обработка — ожидаемое поведение at-least-once; после внедрения
дедупликации повтор становится безопасным.

</details>

#### C4. Дедупликация
Реализуй таблицу `processed_messages(message_id, processed_at)` и проверку перед
обработкой. Проверь, что повторы игнорируются.

#### C5. DLQ
1. Отправь заведомо «битое» сообщение.
2. Настрой 3 повтора и переброс в DLQ.
3. Убедись, что основная очередь продолжает работать.
4. Разбери сообщение из DLQ и переотправь его.

#### C6. Порядок и ключи
1. Создай топик с 3 партициями.
2. Отправь события с ключами `user-1` и `user-2`, посмотри, в какие партиции они попали.
3. Проверь, сохраняется ли порядок внутри одного ключа.

<details><summary>Ответ</summary>

Сообщения с одинаковым ключом всегда попадают в одну партицию — это и даёт
порядок по сущности.

</details>

#### C7. Backpressure
1. Разгони продюсера быстрее консьюмера.
2. Наблюдай рост лага/глубины очереди.
3. Добавь второго консьюмера в группу и посмотри, как меняется картина.

<details><summary>Ответ</summary>

Добавление консьюмера помогает только до числа партиций: лишние будут простаивать.

</details>

#### C8. Большие сообщения
Попробуй отправить сообщение на 5 МБ. Посмотри на ограничения брокера и подумай,
как перестроить схему через объектное хранилище.

<details><summary>Ответ</summary>

У Kafka по умолчанию ограничение около 1 МБ на сообщение
(`message.max.bytes`/`max.request.size`); увеличивать его — плохая практика.

</details>

#### C9. Мониторинг
Настрой метрики: лаг консьюмер-группы (Kafka), глубина очереди (RabbitMQ), размер DLQ.
Сделай по одному алерту на каждую.

#### C10. Проектирование
Для своего (реального или выдуманного) проекта опиши: какие события есть,
какие потребители, какие гарантии нужны, где нужна идемпотентность,
что попадает в DLQ и какие алерты ты поставишь.

### Блок D. Инциденты

**D1.** Пользователи получили по три одинаковых письма. Что произошло и как чинить?

<details><summary>Ответ</summary>

At-least-once + неидемпотентный обработчик: сообщение обработалось несколько раз
(ретраи, ребаланс, падение до коммита). Лечение — дедупликация по `message_id`,
идемпотентная отправка писем, проверка на стороне почтового сервиса.

</details>

**D2.** Лаг консьюмер-группы растёт уже час. Алгоритм разбора.

<details><summary>Ответ</summary>

Проверить: жив ли консьюмер и сколько их, сколько партиций, скорость обработки,
ошибки в логах, зависимости (БД, внешние API), не идёт ли постоянный ребаланс,
не растёт ли DLQ; далее — масштабировать или оптимизировать.

</details>

**D3.** Очередь не разбирается: одно сообщение постоянно падает. Что это и что делать?

<details><summary>Ответ</summary>

Poison message. Ограничить повторы, отправить в DLQ, разобрать вручную,
поправить код/данные и переотправить.

</details>

**D4.** После падения консьюмера часть сообщений потерялась. Какая была настройка коммита?

<details><summary>Ответ</summary>

Коммит происходил до обработки (at-most-once) либо использовался автокоммит
с коротким интервалом. Нужно коммитить после успешной обработки.

</details>

**D5.** DLQ содержит 40 000 сообщений за месяц. Что это говорит о системе?

<details><summary>Ответ</summary>

Либо систематическая проблема в данных/коде, либо слишком агрессивные
ретраи и неверная классификация ошибок. В любом случае — это сигнал разбираться,
а не «нормальный фон».

</details>

**D6.** Брокер занял весь диск. Причины и действия.

<details><summary>Ответ</summary>

Слишком большой retention, всплеск трафика, отставший потребитель
(в RabbitMQ очередь не разбирается), отсутствие лимитов, накопленные DLQ.
Действия: увеличить диск/уменьшить retention, ускорить потребителей, разобрать очереди,
поставить алерты.

</details>

**D7.** Добавили 10 консьюмеров, скорость обработки не выросла. Почему?

<details><summary>Ответ</summary>

Консьюмеров в группе больше, чем партиций: лишние простаивают.
Нужно увеличить число партиций.

</details>

**D8.** События приходят в неверном порядке, и это ломает бизнес-логику. Варианты решения.

<details><summary>Ответ</summary>

Использовать ключ партиционирования по сущности, обрабатывать сообщения
одной сущности одним потребителем, не «перепрыгивать» упавшие сообщения,
либо делать обработку устойчивой к порядку (версии, идемпотентность).

</details>

**D9.** Данные записались в БД, но событие в брокер не ушло (упал сервис между операциями).
Как исправить архитектурно?

<details><summary>Ответ</summary>

Паттерн outbox (или CDC через Debezium): событие сохраняется в БД
в одной транзакции с данными и отправляется отдельным процессом.

</details>

**D10.** Новая версия продюсера добавила поле, старые консьюмеры падают. Что сделать?

<details><summary>Ответ</summary>

Соблюдать совместимость схем (добавление необязательных полей),
версионировать сообщения, использовать schema registry, выкатывать сначала
потребителей, потом продюсеров.

</details>

### Блок E. Вопросы с собеседования

**1.** Зачем нужны очереди сообщений?

<details><summary>Ответ</summary>

Развязать сервисы, сгладить пики, надёжно доставить сообщения, дать нескольким
потребителям одни и те же события.

</details>

**2.** Чем асинхронное взаимодействие лучше синхронного и чем хуже?

<details><summary>Ответ</summary>

Лучше устойчивостью и масштабируемостью, хуже — сложностью, задержкой
и необходимостью эксплуатировать брокер.

</details>

**3.** Какие гарантии доставки существуют?

<details><summary>Ответ</summary>

At-most-once, at-least-once, exactly-once; на практике — at-least-once.

</details>

**4.** Что такое идемпотентность и зачем она нужна?

<details><summary>Ответ</summary>

Повторная обработка не меняет результат; необходима, потому что дубликаты неизбежны.

</details>

**5.** Что такое DLQ?

<details><summary>Ответ</summary>

Очередь для сообщений, которые не удалось обработать; её мониторят и разбирают.

</details>

**6.** Как устроены ретраи?

<details><summary>Ответ</summary>

Ограниченное число попыток, экспоненциальная задержка, различение временных
и постоянных ошибок, затем DLQ.

</details>

**7.** Как обеспечить порядок обработки?

<details><summary>Ответ</summary>

Через партиционирование по ключу сущности и обработку одной партиции одним
потребителем.

</details>

**8.** Что такое лаг и почему за ним следят?

<details><summary>Ответ</summary>

Лаг — отставание потребителя; при росте данные могут быть потеряны по retention,
а бизнес-процессы — задержаться.

</details>

**9.** Что такое outbox pattern?

<details><summary>Ответ</summary>

Запись события в таблицу в одной транзакции с данными и последующая отправка
отдельным процессом.

</details>

**10.** Когда очередь не нужна?

<details><summary>Ответ</summary>

Когда нужен синхронный ответ, когда достаточно HTTP между двумя сервисами
и когда некому эксплуатировать брокер.

</details>
