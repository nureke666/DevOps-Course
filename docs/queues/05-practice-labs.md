## 🧪 Лаба 1. Kafka: разобраться руками

### Требования
- [ ] Kafka (KRaft, `apache/kafka`) + Kafka UI (`kafbat/kafka-ui`) подняты в compose
- [ ] Топик `orders` с 3 партициями создан из CLI
- [ ] Отправлены сообщения с ключами и без; видно распределение по партициям
- [ ] Прочитано `--from-beginning` двумя разными группами
- [ ] Проверено, что после чтения сообщения остаются в топике
- [ ] Оффсеты группы сброшены на начало и данные перечитаны
- [ ] Топик с `retention.ms=60000` — сообщения исчезли, сделан вывод
- [ ] Топик с `cleanup.policy=compact` — осталось последнее значение по ключу

### Проверка
```bash
# apache/kafka: скрипты в /opt/kafka/bin внутри контейнера, не в PATH
docker exec kafka /opt/kafka/bin/kafka-topics.sh --bootstrap-server localhost:9092 --describe --topic orders
docker exec kafka /opt/kafka/bin/kafka-consumer-groups.sh --bootstrap-server localhost:9092 --describe --group g1
```

## 🧪 Лаба 2. ⭐ Группы, лаг и ребалансы

### Что делаем
Пишем простые продюсер и консьюмер (Python `confluent-kafka`/`kafka-python` или Go),
чтобы управлять коммитами и увидеть поведение группы.

### Каркас (Python)
```python
# producer.py
from confluent_kafka import Producer
import json, time, random
p = Producer({'bootstrap.servers': 'localhost:9092'})
for i in range(100000):
    user = f"user-{random.randint(1,50)}"
    p.produce('orders', key=user, value=json.dumps({'i': i, 'user': user}))
    if i % 1000 == 0:
        p.flush()
        time.sleep(0.1)
p.flush()
```
```python
# consumer.py
from confluent_kafka import Consumer
import time
c = Consumer({
    'bootstrap.servers': 'localhost:9092',
    'group.id': 'billing',
    'auto.offset.reset': 'earliest',
    'enable.auto.commit': False,          # ⭐ коммитим сами
    'max.poll.interval.ms': 300000,
})
c.subscribe(['orders'])
while True:
    msg = c.poll(1.0)
    if msg is None or msg.error():
        continue
    time.sleep(0.01)                       # имитация обработки
    c.commit(msg)                          # коммит ПОСЛЕ обработки
```

### Требования
- [ ] Продюсер и консьюмер работают, видно чтение по партициям
- [ ] Запущены 1, 2, 3, 4 консьюмера — зафиксировано распределение партиций
- [ ] Убит консьюмер во время работы — увиден ребаланс и повторная обработка
- [ ] Измерен лаг под нагрузкой (`--describe --group`), построен график роста/падения
- [ ] Смоделирован «вечный ребаланс»: обработка дольше `max.poll.interval.ms`
- [ ] Добавлена идемпотентность (дедупликация по ключу сообщения)
- [ ] Проверено поведение при `enable.auto.commit=true` и падении обработчика

### Вопросы себе
- Сколько сообщений обработалось дважды при убийстве консьюмера?
- Что нужно изменить, чтобы дубликаты стали безопасными?

## 🧪 Лаба 3. RabbitMQ: маршрутизация и надёжность

### Требования
- [ ] Topic-exchange `events` и три очереди с разными bindings
- [ ] Проверена маршрутизация по ключам `orders.created`, `orders.paid`, `users.created`
- [ ] Fanout-exchange: одно сообщение приходит во все очереди
- [ ] Потребитель с ручным ack; проверено возвращение сообщения при падении
- [ ] Установлен `prefetch_count`, видно равномерное распределение между воркерами
- [ ] Durable-очередь + persistent-сообщения переживают рестарт брокера
- [ ] Настроена DLQ; «битое» сообщение уходит туда, очередь продолжает работать
- [ ] Реализованы ретраи с задержкой (retry-очередь с TTL + DLX)

### Проверка
```bash
docker exec rabbitmq rabbitmqctl list_queues name messages messages_unacked consumers
docker exec rabbitmq rabbitmqctl list_bindings
```

### Вопросы себе

- Как в RabbitMQ сделать то, что в Kafka делается перемоткой оффсета? (И стоит ли.)

## 🧪 Лаба 4. Мониторинг и разбор инцидентов

### Требования
- [ ] kafka-exporter и метрики RabbitMQ подключены к Prometheus
- [ ] Дашборды: Kafka (7589) и RabbitMQ (10991) + свои панели
- [ ] Алерты: растущий лаг группы, under-replicated партиции, глубина очереди RabbitMQ,
      отсутствие потребителей, размер DLQ
- [ ] Смоделированы и разобраны три инцидента:
      1) потребители остановлены → лаг растёт
      2) «ядовитое» сообщение без DLQ → очередь встала
      3) брокер Kafka остановлен → under-replicated партиции
- [ ] На каждый инцидент написан короткий рунбук

### Сценарий проверки
```text:no-line-numbers
1. Запускаем нагрузку 5 000 msg/s, потребитель обрабатывает 1 000 msg/s
2. Наблюдаем рост лага на дашборде → срабатывает алерт
3. Добавляем потребителей (в пределах числа партиций) → лаг сокращается
4. Фиксируем, за какое время система «догнала» очередь
```

### Вопросы себе
- По какой метрике я первым делом отличу «брокер сломался» от «потребитель не справляется»?
- Какой у меня допустимый лаг и откуда взялась эта цифра?
