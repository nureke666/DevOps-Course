# 04. RabbitMQ

> Роадмап → Очереди → *«RabbitMQ — классический брокер, отличие от кафки —
> сообщение доставлено → удалено»*.
>
> **После темы ты умеешь:** объяснить модель exchange/queue/binding, настроить
> подтверждения и prefetch, сделать DLQ, поднять кластер и сравнить RabbitMQ с Kafka.

---

## 🗺️ Модель RabbitMQ

```text:no-line-numbers
 ПРОДЮСЕР
    │ publish(exchange, routing_key, message)
    ▼
 ┌───────────────┐   binding (routing_key / pattern)   ┌──────────────┐
 │   EXCHANGE    │ ──────────────────────────────────► │   ОЧЕРЕДЬ    │
 │ (маршрутизатор│ ──────────────────────────────────► │   ОЧЕРЕДЬ    │
 │  не хранит!)  │                                     └──────┬───────┘
 └───────────────┘                                            │ deliver
                                                              ▼
                                                        КОНСЬЮМЕР
                                                          │ ack
                                                          ▼
                                              сообщение УДАЛЕНО из очереди ⭐
```

⭐ Ключевое отличие от Kafka: сообщение живёт в очереди до подтверждения обработки,
после чего **удаляется**. Перечитать его нельзя, «истории» нет.

---

## 1. Типы exchange

| Тип | Как маршрутизирует | Пример |
|-----|--------------------|--------|
| **direct** | Точное совпадение routing key | `key=orders.paid` → очередь `billing` |
| **topic** | Шаблон с `*` (одно слово) и `#` (любое число слов) | `orders.*` , `logs.#` |
| **fanout** | Всем связанным очередям, ключ игнорируется | Broadcast-события |
| **headers** | По заголовкам вместо ключа | Редко |
| default (пустое имя) | Direct с routing key = имя очереди | Быстрые тесты |

```text:no-line-numbers
topic-обмен "events"
   orders.created ──┐
   orders.paid ─────┼─► очередь billing   (binding: orders.*)
   users.created ───┼─► очередь analytics (binding: #)
                    └─► очередь audit     (binding: #)
```

## 2. Очереди и их свойства

```bash
# через CLI внутри контейнера
rabbitmqctl list_queues name messages consumers memory
rabbitmqctl list_exchanges
rabbitmqctl list_bindings
rabbitmqctl list_connections
rabbitmqadmin declare queue name=orders durable=true
```

| Свойство | Смысл |
|----------|-------|
| `durable` | Очередь переживает перезапуск брокера ⭐ |
| `persistent` (у сообщения) | Сообщение пишется на диск (иначе живёт в памяти) |
| `exclusive` | Только для одного соединения, удаляется с ним |
| `auto-delete` | Удаляется, когда отключился последний потребитель |
| `x-message-ttl` | Время жизни сообщения |
| `x-max-length` | Максимальная длина очереди (старые вытесняются) |
| `x-dead-letter-exchange` | Куда отправлять «мёртвые» сообщения ⭐ |
| `x-queue-type=quorum` | Отказоустойчивая очередь (современная замена mirrored) |

> ⚠️ `durable` очередь + `persistent` сообщения — обязательная пара, если сообщения
> терять нельзя. Только одно из двух не спасает.

## 3. Подтверждения и prefetch ⭐

```text:no-line-numbers
 БЕЗ ack (auto-ack)                     С ручным ack
 ─────────────────                      ────────────
 брокер удалил сразу после отправки     брокер ждёт подтверждения
 упал потребитель → сообщение потеряно   упал потребитель → сообщение вернётся
                                          в очередь и уйдёт другому (at-least-once)
```

```python
# концептуально (pika)
channel.basic_qos(prefetch_count=10)          # ⭐ не больше 10 неподтверждённых
def handler(ch, method, props, body):
    try:
        process(body)
        ch.basic_ack(method.delivery_tag)                       # успех
    except TemporaryError:
        ch.basic_nack(method.delivery_tag, requeue=True)        # вернуть в очередь
    except PermanentError:
        ch.basic_nack(method.delivery_tag, requeue=False)       # → DLQ
channel.basic_consume(queue='orders', on_message_callback=handler)
```

| Параметр | Зачем |
|----------|-------|
| `prefetch_count` | Ограничивает число неподтверждённых сообщений у потребителя: без него один воркер заберёт всю очередь, а остальные будут простаивать ⭐ |
| `ack` | Подтверждение успешной обработки |
| `nack/reject` + `requeue=false` | Отправить в DLQ вместо бесконечных повторов |
| `publisher confirms` | Подтверждение брокером приёма сообщения от продюсера |
| `mandatory` | Ошибка, если сообщение некуда маршрутизировать |

## 4. Dead Letter Exchange (DLQ)

```text:no-line-numbers
 очередь orders
   x-dead-letter-exchange: dlx
   x-message-ttl: 60000
        │
        │ сообщение отклонено (nack, requeue=false),
        │ истёк TTL или превышена длина очереди
        ▼
    exchange "dlx" ──► очередь orders.dlq  ← разбираем вручную, алерт на размер
```

Классическая схема ретраев с задержкой в RabbitMQ:
```text:no-line-numbers
основная очередь ──(nack)──► retry-очередь с TTL 30s и DLX обратно в основную
                                   │ через 30 секунд сообщение возвращается
                                   ▼
                          после N попыток → окончательная DLQ
```
(Счётчик попыток хранят в заголовке `x-death` или собственном поле.)

## 5. Кластер и отказоустойчивость

| Механизм | Смысл |
|----------|-------|
| **Кластер** | Несколько узлов с общими метаданными; очереди по умолчанию живут на одном узле |
| **Quorum queues** ⭐ | Реплицированные очереди на основе Raft — современный стандарт для надёжности |
| Classic mirrored queues | Старый механизм зеркалирования; в RabbitMQ 4.0 удалён совсем |
| **Streams** | Новый тип «лог-очереди» (ближе к Kafka по модели) |
| Federation / Shovel | Передача сообщений между кластерами/ЦОД |
| HA-прокси/DNS перед кластером | Клиенты подключаются к любому живому узлу |

```bash
rabbitmqctl cluster_status
rabbitmqctl list_queues name type members
```

```text:no-line-numbers
Практика для прода:
 • 3 узла (нечётное число для кворума)
 • очереди типа quorum с durable-сообщениями
 • отдельный диск, мониторинг памяти и диска
 • ⚠️ RabbitMQ блокирует продюсеров при достижении memory/disk watermark —
   это защита, но выглядит как «зависание публикации»
```

## 7. ⭐ RabbitMQ vs Kafka

| Критерий | RabbitMQ | Kafka |
|----------|----------|-------|
| Модель | Очередь: доставил → удалил | Лог: хранит по retention |
| Перечитать историю | Нет | Да (перемотка оффсета) |
| Маршрутизация | Богатая (direct/topic/fanout/headers) | Простая (топик + партиции по ключу) |
| Порядок | В пределах очереди (с одним потребителем) | В пределах партиции |
| Пропускная способность | Десятки тысяч msg/s | Сотни тысяч - миллионы msg/s |
| Задержка | Очень низкая | Низкая (но с батчингом) |
| Приоритеты, отложенная доставка | Есть | Нет из коробки |
| Несколько независимых читателей | Через отдельные очереди и bindings | Естественно (консьюмер-группы) |
| Типовые задачи | Задачи воркерам, RPC, уведомления, сложная маршрутизация | События, аналитика, CDC, интеграционная шина, потоковая обработка |
| Порог входа | Ниже | Выше |

```text:no-line-numbers
Простое правило выбора:
  «Дай задание конкретному обработчику»            → RabbitMQ
  «Опубликуй факт, который многим интересен,
   и пусть его можно будет перечитать»              → Kafka
На больших проектах часто есть оба.
```

## 8. Грабли

| Грабля | Последствие | Решение |
|--------|-------------|---------|
| `auto-ack` | Потеря сообщений при падении потребителя | Ручной ack после обработки |
| Нет `prefetch` | Один воркер забирает всё, остальные простаивают | `basic_qos(prefetch_count=N)` |
| Не durable очередь / не persistent сообщения | Потеря при рестарте брокера | Durable + persistent |
| `requeue=true` в бесконечном цикле | Сообщение крутится вечно, очередь стоит | Лимит попыток → DLQ |
| Нет DLQ | «Ядовитое» сообщение блокирует обработку | DLX + алерт |
| Очередь растёт без контроля | Память/диск, блокировка публикации | Алерт на глубину, `x-max-length`, масштабирование |
| Classic mirrored queues в новом проекте | Проблемный механизм, в RabbitMQ 4.x его уже нет | Quorum queues |
| Один узел в проде | Единая точка отказа | Кластер из 3 узлов |
| Большие сообщения | Деградация брокера | Payload в S3, в сообщении ссылка |

## 💼 Как это в DevOps

- RabbitMQ обычно появляется там, где нужны «задачи воркерам»: письма, отчёты,
  обработка загрузок, интеграции. Он проще Kafka и часто достаточен.
- Девопс отвечает за кластер (3 узла, quorum queues), доступы (vhost, пользователи,
  права), мониторинг глубины очередей и DLQ, память и диски.
- Самые частые инциденты: очередь растёт (нет потребителей/не справляются),
  зависшие unacked-сообщения, блокировка публикации по memory/disk watermark
  и «ядовитые» сообщения без DLQ.
- Vhost'ы используют для изоляции команд и окружений внутри одного кластера.
- В облаке есть managed RabbitMQ — как и с базами, это экономит эксплуатацию.

## 🧠 Что запомнить

1. ⭐ RabbitMQ доставляет и удаляет сообщение; Kafka хранит его по retention.
2. Продюсер пишет в exchange, а не в очередь; маршрут определяют bindings и routing key.
3. Типы exchange: direct, topic, fanout, headers — это главное преимущество RabbitMQ
   в гибкости маршрутизации.
4. Надёжность = durable-очередь + persistent-сообщения + ручной ack.
5. `prefetch_count` обязателен, иначе один потребитель забирает всю очередь.
6. `nack` с `requeue=false` отправляет сообщение в DLQ; бесконечный requeue —
   типовая ошибка.
7. Ретраи с задержкой делают через дополнительную очередь с TTL и DLX.
8. В проде — кластер из трёх узлов и quorum queues; classic mirrored удалены в RabbitMQ 4.0.
9. При достижении memory/disk watermark брокер блокирует публикацию — это выглядит
   как «зависание» и требует алертов на память и диск.
10. Выбор: задачи и сложная маршрутизация — RabbitMQ; события, история и большие
    объёмы — Kafka.

### Блок A. Теория

**A1.** ⭐ В чём главное отличие RabbitMQ от Kafka?

<details><summary>Ответ</summary>

RabbitMQ удаляет сообщение после подтверждения обработки — истории нет.
Kafka хранит сообщения по retention, и их могут читать независимо несколько групп,
в том числе перечитывая заново.

</details>

**A2.** Куда публикует продюсер: в очередь или в exchange? Как сообщение попадает в очередь?

<details><summary>Ответ</summary>

В exchange. Exchange по правилам привязок (bindings) и routing key
направляет сообщение в одну или несколько очередей; сам он ничего не хранит.

</details>

**A3.** Назови типы exchange и приведи сценарий для каждого.

<details><summary>Ответ</summary>

direct — точное совпадение ключа (команды конкретному обработчику);
topic — шаблоны (события `orders.*`); fanout — всем очередям (broadcast);
headers — по заголовкам (редкие сценарии).

</details>

**A4.** Чем `*` отличается от `#` в topic-exchange?

<details><summary>Ответ</summary>

`*` заменяет ровно одно слово, `#` — любое количество слов (включая ноль).

</details>

**A5.** Что такое durable-очередь и persistent-сообщение? Почему нужны оба?

<details><summary>Ответ</summary>

Durable — очередь переживает перезапуск брокера; persistent — сообщение
записывается на диск. Нужны оба: durable-очередь без persistent-сообщений останется
пустой, persistent-сообщения в недолговечной очереди исчезнут вместе с ней.

</details>

**A6.** Что делает auto-ack и чем он опасен?

<details><summary>Ответ</summary>

Брокер считает сообщение доставленным сразу при отправке потребителю;
падение обработчика означает потерю сообщения (at-most-once).

</details>

**A7.** ⭐ Что такое `prefetch_count` и что произойдёт без него?

<details><summary>Ответ</summary>

Ограничение числа неподтверждённых сообщений у одного потребителя.
Без него брокер отправит потребителю всё, что есть, — один воркер будет перегружен,
остальные простаивают, а при его падении вернётся огромная пачка сообщений.

</details>

**A8.** Чем `nack(requeue=true)` отличается от `nack(requeue=false)`?

<details><summary>Ответ</summary>

`requeue=true` возвращает сообщение в очередь для повторной обработки;
`requeue=false` отправляет его в DLX (если настроен) или отбрасывает.

</details>

**A9.** Что такое DLX/DLQ и в каких случаях сообщение туда попадает?

<details><summary>Ответ</summary>

Dead letter exchange/queue — куда попадают сообщения при `nack(requeue=false)`,
истечении TTL или превышении `x-max-length`. Нужны для того, чтобы проблемные сообщения
не блокировали очередь и не терялись.

</details>

**A10.** Как реализовать повтор с задержкой в RabbitMQ?

<details><summary>Ответ</summary>

Отдельная retry-очередь с `x-message-ttl` и `x-dead-letter-exchange`,
указывающим обратно на основную очередь: сообщение «отлёживается» и возвращается;
число попыток считают по заголовку `x-death`.

</details>

**A11.** Что такое quorum queues и чем они лучше classic mirrored?

<details><summary>Ответ</summary>

Quorum queues реплицируются по алгоритму Raft, предсказуемо ведут себя
при отказах и являются рекомендуемым типом. Classic mirrored имеют известные проблемы
с консистентностью и производительностью; в RabbitMQ 4.0 их удалили совсем.

</details>

**A12.** Что происходит при достижении memory/disk watermark?

<details><summary>Ответ</summary>

Брокер приостанавливает (блокирует) публикацию от продюсеров,
чтобы не исчерпать память или диск. Внешне выглядит как «зависшая публикация».

</details>

**A13.** Что такое vhost и зачем он нужен?

<details><summary>Ответ</summary>

Виртуальный хост — логическая изоляция внутри брокера: свои очереди, exchange,
права. Используется для разделения команд, приложений и окружений.

</details>

**A14.** Какие метрики RabbitMQ ты будешь мониторить?

<details><summary>Ответ</summary>

Глубина очередей (`messages_ready`), неподтверждённые (`unacked`),
число потребителей, скорости publish/deliver/ack, размер DLQ, память и диск узлов,
состояние кластера и узлов.

</details>

**A15.** Как выбрать между RabbitMQ и Kafka? Дай простое правило.

<details><summary>Ответ</summary>

«Задание конкретному обработчику, сложная маршрутизация, приоритеты
и отложенная доставка» → RabbitMQ. «Поток событий, который надо хранить, перечитывать
и раздавать многим потребителям при больших объёмах» → Kafka.

</details>

### Блок C. Практика

#### C1. 🔑 Первое сообщение
1. Подними RabbitMQ, зайди в UI (`admin/admin`).
2. Создай очередь `orders` (durable), опубликуй сообщение через UI, получи его.
3. Посмотри `rabbitmqctl list_queues name messages consumers`.

#### C2. Exchange и маршрутизация
1. Создай topic-exchange `events`.
2. Создай очереди `billing` (binding `orders.*`) и `audit` (binding `#`).
3. Опубликуй сообщения с ключами `orders.created`, `orders.paid`, `users.created`.
4. Проверь, куда что попало.

#### C3. Fanout
Создай fanout-exchange и три очереди. Убедись, что каждое сообщение приходит во все три.

#### C4. 🔑 Ack и потеря сообщений
1. Напиши потребителя с auto-ack, который «падает» в середине обработки.
2. Проверь, что сообщение потеряно.
3. Переделай на ручной ack и повтори — сообщение должно вернуться в очередь.

<details><summary>Ответ</summary>

С auto-ack сообщение исчезает; с ручным ack оно возвращается в очередь
после разрыва соединения потребителя.

</details>

#### C5. Prefetch
1. Запусти трёх потребителей без `prefetch`, посмотри распределение (`unacked` в UI).
2. Установи `prefetch_count=1`, повтори.
3. Опиши разницу словами.

<details><summary>Ответ</summary>

Без prefetch в UI видно, что у одного потребителя огромное число `unacked`;
с `prefetch_count=1` нагрузка распределяется равномерно.

</details>

#### C6. Durable и persistent
1. Отправь сообщения в не-durable очередь, перезапусти брокер — что осталось?
2. Повтори с durable-очередью и persistent-сообщениями.

<details><summary>Ответ</summary>

В не-durable очереди сообщения не переживут рестарт; durable + persistent —
переживут.

</details>

#### C7. DLQ
1. Настрой у очереди `x-dead-letter-exchange`.
2. Сделай `nack(requeue=false)` для «битого» сообщения.
3. Убедись, что оно попало в DLQ и основная очередь работает.

#### C8. Ретраи с задержкой
Реализуй схему: основная очередь → retry-очередь с TTL 10 секунд и DLX обратно →
после 3 попыток окончательная DLQ. Проверь работу и посчитай попытки через `x-death`.

<details><summary>Ответ</summary>

Заголовок `x-death` содержит историю «смертей» сообщения — по нему считают попытки.

</details>

#### C9. Кластер и quorum queues
Подними 3 узла в compose, объедини в кластер, создай quorum-очередь,
погаси один узел и проверь, что очередь доступна.

<details><summary>Ответ</summary>

Quorum-очередь остаётся доступной при потере одного узла из трёх.

</details>

#### C10. Мониторинг
Включи плагин `rabbitmq_prometheus`, добавь таргет в Prometheus, импортируй дашборд 10991.
Настрой алерты: глубина очереди, отсутствие потребителей, размер DLQ, память узла.

### Блок D. Инциденты

**D1.** Очередь выросла до 2 млн сообщений. Алгоритм разбора.

<details><summary>Ответ</summary>

Есть ли потребители, сколько их и справляются ли; ошибки обработки;
скорость publish против deliver/ack; не блокирует ли что-то обработку
(зависимости, «ядовитое» сообщение); ресурсы узлов; далее — масштабировать
потребителей или ограничивать продюсеров.

</details>

**D2.** Публикация «зависла», продюсеры не получают подтверждений. Что смотреть?

<details><summary>Ответ</summary>

Memory/disk watermark (брокер заблокировал публикацию), состояние узлов
кластера, свободное место и память, `rabbitmqctl status`, сетевые проблемы,
отсутствие publisher confirms.

</details>

**D3.** `unacked` растёт, `ready` не уменьшается. Что происходит?

<details><summary>Ответ</summary>

Потребители забрали сообщения, но не подтверждают их: зависли, слишком большой
prefetch, долгая обработка или потеря соединения. Смотреть логи потребителей,
`unacked` по каналам, уменьшить prefetch, добавить таймауты.

</details>

**D4.** Одно сообщение бесконечно возвращается в очередь. Как это называется и что делать?

<details><summary>Ответ</summary>

Poison message при `requeue=true` в цикле. Нужно ограничить число попыток
и отправлять в DLQ через `requeue=false`.

</details>

**D5.** После перезапуска брокера часть сообщений исчезла. Что было настроено неверно?

<details><summary>Ответ</summary>

Очередь не durable и/или сообщения не persistent (либо использовался auto-ack).

</details>

**D6.** Один воркер загружен, остальные простаивают. Причина?

<details><summary>Ответ</summary>

Не задан `prefetch_count`: брокер выдал одному потребителю слишком много
сообщений.

</details>

**D7.** DLQ растёт по 500 сообщений в час. Что делаешь?

<details><summary>Ответ</summary>

Разобрать содержимое DLQ (типовые ошибки), исправить причину, при необходимости
переотправить, добавить алерт и мониторинг, пересмотреть классификацию ошибок
и число ретраев.

</details>

**D8.** При падении узла кластера очередь стала недоступна. Почему и как исправить?

<details><summary>Ответ</summary>

Классическая очередь жила на одном узле и не реплицировалась.
Решение — quorum queues и кластер из трёх узлов.

</details>

**D9.** Разработчики просят «перечитать сообщения за вчера». Что ответишь?

<details><summary>Ответ</summary>

RabbitMQ этого не умеет: сообщения удаляются после подтверждения.
Варианты — логировать события в БД/хранилище, использовать RabbitMQ Streams
или Kafka для сценариев с историей.

</details>

**D10.** Нужно передавать файлы по 20 МБ через RabbitMQ. Что предложишь?

<details><summary>Ответ</summary>

Хранить файл в объектном хранилище, а в сообщении передавать ссылку
и метаданные; при необходимости — presigned URL с ограниченным сроком.

</details>

### Блок E. Вопросы с собеседования

**1.** Чем RabbitMQ отличается от Kafka?

<details><summary>Ответ</summary>

RabbitMQ — очередь с удалением после доставки и богатой маршрутизацией;
Kafka — распределённый лог с хранением и перечитыванием.

</details>

**2.** Что такое exchange и какие типы бывают?

<details><summary>Ответ</summary>

Маршрутизатор сообщений: direct, topic, fanout, headers.

</details>

**3.** Как работает подтверждение сообщений?

<details><summary>Ответ</summary>

Потребитель подтверждает (`ack`) после обработки; без подтверждения сообщение
возвращается в очередь.

</details>

**4.** Что такое prefetch и зачем он нужен?

<details><summary>Ответ</summary>

Ограничение неподтверждённых сообщений на потребителя; обеспечивает равномерную
загрузку воркеров.

</details>

**5.** Как обеспечить, чтобы сообщения не потерялись?

<details><summary>Ответ</summary>

Durable-очереди, persistent-сообщения, ручной ack, publisher confirms,
кластер с quorum queues.

</details>

**6.** Что такое DLQ и как её настроить?

<details><summary>Ответ</summary>

Очередь для «мёртвых» сообщений; настраивается через `x-dead-letter-exchange`
у основной очереди.

</details>

**7.** Как сделать повтор с задержкой?

<details><summary>Ответ</summary>

Retry-очередь с TTL и DLX обратно в основную; счётчик попыток — в заголовках.

</details>

**8.** Что такое quorum queues?

<details><summary>Ответ</summary>

Реплицированные очереди на Raft — рекомендуемый способ отказоустойчивости.

</details>

**9.** Что произойдёт, если очередь переполнится?

<details><summary>Ответ</summary>

Сработают `x-max-length`/TTL (вытеснение или DLQ), а при исчерпании памяти/диска
брокер заблокирует публикацию.

</details>

**10.** Когда выберешь RabbitMQ, а когда Kafka?

<details><summary>Ответ</summary>

RabbitMQ — задачи, RPC, сложная маршрутизация, приоритеты; Kafka — события,
большие объёмы, история и много независимых потребителей.

</details>
