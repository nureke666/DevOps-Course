# 01. Инфраструктура как код и место Terraform

> Роадмап → 7. Остальное → Terraform: *«в отличие от Ансибла — позволяет создавать
> сервера (в целом всю облачную инфру)»*.
>
> **После темы ты умеешь:** объяснить, что такое IaC, чем декларативный подход отличается
> от императивного, где заканчивается Terraform и начинается Ansible, и что такое OpenTofu.

---

## 🗺️ Три способа управлять инфраструктурой

```text:no-line-numbers
 1. РУКАМИ (клики в консоли)
    + быстро для одного ресурса
    − не воспроизводимо, нет истории, окружения расходятся, «а кто это создал?»

 2. СКРИПТАМИ (bash + CLI облака)         ИМПЕРАТИВНО: «как делать»
    + автоматизация                        if ! exists; then create; fi
    − надо самому обрабатывать «уже есть», удаление, ошибки, порядок

 3. IaC-ИНСТРУМЕНТОМ (Terraform)          ДЕКЛАРАТИВНО: «что должно быть»
    + описываешь желаемое состояние        resource "vm" "web" { cpu = 2 }
    + инструмент сам считает разницу
    + есть план изменений и история в git
```

| Признак | Императивный подход | Декларативный (Terraform) |
|---------|--------------------|---------------------------|
| Что пишешь | Последовательность действий | Желаемое состояние |
| Повторный запуск | Надо самому проверять «уже создано» | Ничего не делает, если всё совпадает |
| Удаление лишнего | Пишешь руками | Убрал из кода → `apply` удалит |
| Видно ли, что будет | Нет | ⭐ `terraform plan` |
| Пример | bash + `aws ec2 run-instances` | Terraform, CloudFormation, Pulumi |

## 1. Зачем IaC в реальной работе

| Проблема без IaC | Как решает Terraform |
|------------------|----------------------|
| «На стейдже работает, на проде нет» | Одинаковый код с разными переменными |
| Никто не знает, из чего состоит прод | Инфраструктура описана в репозитории |
| Изменения без следов | Git-история, MR, ревью, откат |
| Восстановление после аварии — по памяти | `terraform apply` в новом регионе |
| «Сироты»: ресурсы без владельца | Что не в коде — того быть не должно |
| Онбординг нового инженера | Читает код, а не расспрашивает коллег |
| Аудит и комплаенс | Кто, что и когда менял — видно в git |

```text:no-line-numbers
Побочный, но важный эффект:
инфраструктура становится предметом ревью.
«Почему security group открыта в 0.0.0.0/0?» — вопрос в MR, а не постфактум в отчёте
по безопасности.
```

## 2. ⭐ Terraform vs Ansible

```text:no-line-numbers
 ┌──────────────────────────────┬──────────────────────────────┐
 │ TERRAFORM                    │ ANSIBLE                      │
 │ «СОЗДАЙ инфраструктуру»      │ «НАСТРОЙ то, что уже есть»   │
 ├──────────────────────────────┼──────────────────────────────┤
 │ ВМ, сети, подсети, SG        │ пакеты, пользователи, конфиги│
 │ базы, бакеты, k8s-кластеры   │ systemd-сервисы, деплой      │
 │ DNS, балансировщики, IAM     │ настройка nginx/postgres     │
 ├──────────────────────────────┼──────────────────────────────┤
 │ декларативный, со стейтом    │ процедурный, без стейта      │
 │ знает, что создал            │ приходит и приводит к виду   │
 │ умеет удалять лишнее         │ удаление — отдельная задача  │
 │ работает с API провайдеров   │ работает по SSH/WinRM/API    │
 └──────────────────────────────┴──────────────────────────────┘

 Типовой конвейер:
   Terraform создал ВМ ──► выдал IP ──► Ansible настроил ──► приложение поехало
```

| Вопрос | Ответ |
|--------|-------|
| Можно ли ставить пакеты Terraform'ом? | Технически да (`provisioner`, cloud-init), но это плохая практика |
| Можно ли создавать ВМ Ansible'ом? | Да, есть модули облаков, но нет стейта и плана — управлять жизненным циклом тяжело |
| Что выбрать? | Оба: Terraform для инфраструктуры, Ansible для конфигурации — см. раздел «Ansible» этого курса |

## 3. Экосистема и альтернативы

| Инструмент | Особенности |
|------------|-------------|
| **Terraform** (HashiCorp) | Индустриальный стандарт; с 2023 года лицензия BUSL |
| **OpenTofu** ⭐ | Открытый форк Terraform под фондом Linux Foundation; совместим по коду и командам, активно используется после смены лицензии |
| **Pulumi** | IaC на обычных языках (TypeScript, Python, Go) |
| **CloudFormation / ARM / Deployment Manager** | Нативные инструменты конкретных облаков |
| **Crossplane** | Управление инфраструктурой из Kubernetes |
| **Ansible** | Конфигурация (и ограниченно инфраструктура) |
| **Packer** | Сборка образов ВМ (golden image) — часто идёт в паре с Terraform |
| **Terragrunt** | Обёртка над Terraform: DRY-конфигурации, управление множеством окружений |

> 💡 Практически всё, что написано в этом блоке, одинаково применимо к Terraform
> и OpenTofu: команды, HCL, стейт, провайдеры. В командах можно читать `terraform`
> как `tofu`.

## 4. Что вообще умеет Terraform (через провайдеры)

```text:no-line-numbers
Провайдер = плагин, который умеет говорить с чьим-то API.

ОБЛАКА            Yandex Cloud, VK Cloud, Selectel, AWS, GCP, Azure, Hetzner
ВИРТУАЛИЗАЦИЯ     VMware vSphere, Proxmox, OpenStack
KUBERNETES        kubernetes, helm
БАЗЫ              postgresql (роли, базы), mysql
СЕРВИСЫ           GitLab, GitHub, Grafana, Datadog, Cloudflare, PagerDuty
СЕТЬ/DNS          DNS-провайдеры, TLS-сертификаты
ЛОКАЛЬНОЕ         local, random, null, docker, tls, time, http
```

⭐ Отсюда фраза роадмапа «главное, чтобы был провайдер»: Terraform управляет не только
облаком, но и пользователями GitLab, дашбордами Grafana, DNS-записями и чем угодно,
у чего есть API и провайдер.

## 5. Установка

```bash
# Вариант 1: пакетный менеджер (Ubuntu/Debian, репозиторий HashiCorp)
wget -O- https://apt.releases.hashicorp.com/gpg | \
  sudo gpg --dearmor -o /usr/share/keyrings/hashicorp-archive-keyring.gpg
echo "deb [signed-by=/usr/share/keyrings/hashicorp-archive-keyring.gpg] \
https://apt.releases.hashicorp.com $(lsb_release -cs) main" | \
  sudo tee /etc/apt/sources.list.d/hashicorp.list
sudo apt update && sudo apt install terraform

# Вариант 2: OpenTofu
curl -fsSL https://get.opentofu.org/install-opentofu.sh | sh -s -- --install-method deb

# Вариант 3: tfenv — несколько версий рядом (удобно на проектах с разными версиями)
git clone https://github.com/tfutils/tfenv.git ~/.tfenv
export PATH="$HOME/.tfenv/bin:$PATH"
tfenv install 1.9.0 && tfenv use 1.9.0

terraform -version
terraform -install-autocomplete       # автодополнение в shell
```

## 6. Как выглядит рабочий день с Terraform

```text:no-line-numbers
 1. git pull                        забрал актуальный код
 2. правишь .tf файлы               описал желаемое изменение
 3. terraform fmt && validate       формат и синтаксис
 4. terraform plan                  ⭐ что именно изменится
 5. MR + ревью плана                коллеги смотрят diff и вывод plan
 6. terraform apply                 применение (часто из CI, а не с ноутбука)
 7. проверка                        ресурсы на месте, сервис работает
```

Три файла, которые встречаются в любом проекте:
```text:no-line-numbers
main.tf         ресурсы
variables.tf    входные переменные
outputs.tf      что отдаём наружу (IP, имена, идентификаторы)
versions.tf     версии Terraform и провайдеров
terraform.tfvars значения переменных (⚠️ секреты — не сюда)
```

## 7. Грабли новичка (концептуальные)

| Грабля | Последствие | Как правильно |
|--------|-------------|---------------|
| Правки руками в консоли поверх Terraform | Дрейф: код и реальность расходятся | Все изменения — через код |
| Стейт локально, в одиночку | Команда не может работать, риск потери | Удалённый backend (тема 03) |
| `apply` без чтения `plan` | Случайное удаление прода | Всегда читать план, особенно `destroy` |
| Один гигантский `main.tf` на всё | Долгий plan, страшный apply, конфликты | Разделение по компонентам и окружениям |
| Секреты в `.tf`/`.tfvars` в git | Утечка | Переменные окружения, Vault, секреты CI |
| Не закреплены версии | «Вчера работало» | `required_version`, `version` у провайдеров, lock-файл |
| Terraform как система конфигурации | Хрупкие `provisioner`'ы | Terraform → инфраструктура, Ansible → настройка |

## 💼 Как это в DevOps

- Terraform — стандартный ответ на вопрос «как у вас создаётся инфраструктура».
  Отсутствие IaC на собеседовании читается как незрелость процессов.
- Репозиторий с инфраструктурой живёт рядом с кодом сервисов; изменения идут через MR
  с обязательным просмотром плана.
- Обычный порядок: Terraform создаёт ВМ/сеть/БД → выдаёт outputs (IP, имена) →
  Ansible настраивает → приложение деплоится CI/CD.
- Даже если проект не в облаке, Terraform часто используют для GitLab, DNS, мониторинга
  и Kubernetes-ресурсов — «главное, чтобы был провайдер».
- Переход на OpenTofu — живая тема после смены лицензии; знать о нём полезно.

## 📌 Шпаргалка

| Термин | Одной строкой |
|--------|---------------|
| IaC | Инфраструктура описана кодом в репозитории |
| Декларативный | Описываешь результат, а не шаги |
| Идемпотентность | Повторный `apply` без изменений ничего не делает |
| Провайдер | Плагин к API (облако, k8s, GitLab, DNS…) |
| Ресурс | Единица инфраструктуры (ВМ, сеть, бакет) |
| План | Предпросмотр изменений |
| Стейт | Память Terraform о созданном |
| Дрейф | Расхождение кода и реальности из-за ручных правок |
| OpenTofu | Открытый совместимый форк Terraform |
| Packer | Сборка образов ВМ |
| Terragrunt | Обёртка для множества окружений |

## 🧠 Что запомнить

1. IaC даёт воспроизводимость, историю, ревью и быстрое восстановление.
2. Terraform декларативен: описываешь желаемое состояние, он считает разницу.
3. ⭐ Terraform создаёт инфраструктуру, Ansible настраивает её содержимое — они дополняют
   друг друга.
4. Провайдер — плагин к API; Terraform управляет всем, у чего есть провайдер.
5. OpenTofu — совместимый открытый форк; команды и код те же.
6. Рабочий цикл: `fmt` → `validate` → `plan` → ревью → `apply`.
7. Ручные правки поверх Terraform создают дрейф — это главный источник проблем.
8. Секреты не хранят в `.tf` и `.tfvars`, попадающих в git.
9. Версии Terraform и провайдеров фиксируют явно.
10. `plan` читают всегда, особенно строки об удалении ресурсов.

### Блок A. Теория

**A1.** Что такое инфраструктура как код и какие проблемы она решает?

<details><summary>Ответ</summary>

Подход, при котором инфраструктура описывается кодом в репозитории.
Решает: воспроизводимость окружений, историю и ревью изменений, восстановление после
аварии, прозрачность состава инфраструктуры, борьбу с «сиротами» и ручными правками.

</details>

**A2.** Чем декларативный подход отличается от императивного? Приведи пример каждого.

<details><summary>Ответ</summary>

Императивный описывает шаги («создай, если нет»), декларативный — целевое
состояние («должна быть ВМ с такими параметрами»). Пример: bash + CLI облака против
`resource` в Terraform.

</details>

**A3.** Что произойдёт при повторном запуске Terraform, если ничего не менялось?

<details><summary>Ответ</summary>

Ничего: план будет пустым («No changes»). Это и есть идемпотентность.

</details>

**A4.** ⭐ Чем Terraform отличается от Ansible? Где граница между ними?

<details><summary>Ответ</summary>

Terraform создаёт и удаляет инфраструктурные объекты через API провайдеров,
хранит стейт и умеет показывать план. Ansible приходит на уже существующие машины
и приводит их конфигурацию к описанному виду, стейта не хранит. Граница: «создать ВМ» —
Terraform, «настроить то, что на ВМ» — Ansible.

</details>

**A5.** Можно ли ставить пакеты Terraform'ом? Почему это плохая практика?

<details><summary>Ответ</summary>

Технически можно через `provisioner`/`user_data`, но это хрупко: нет
идемпотентности, ошибки провижининга ломают ресурс, повторно не применяется,
отладка тяжёлая. Для настройки есть Ansible и образы.

</details>

**A6.** Можно ли создавать ВМ Ansible'ом? Чего при этом не хватает?

<details><summary>Ответ</summary>

Да, есть облачные модули, но нет стейта, плана и управления жизненным циклом:
удаление лишнего и отслеживание изменений придётся делать вручную.

</details>

**A7.** Что такое провайдер и почему говорят «главное, чтобы был провайдер»?

<details><summary>Ответ</summary>

Провайдер — плагин, который умеет работать с конкретным API. Terraform сам
по себе ничего не знает об облаках: всё, что он умеет, определяется набором провайдеров,
поэтому управлять можно любым сервисом, у которого провайдер есть.

</details>

**A8.** Приведи пять примеров провайдеров, не связанных с облаками.

<details><summary>Ответ</summary>

kubernetes, helm, gitlab, github, grafana, cloudflare, postgresql, tls, docker,
local, random.

</details>

**A9.** Что такое OpenTofu и почему он появился?

<details><summary>Ответ</summary>

Открытый форк Terraform под эгидой Linux Foundation, созданный после перехода
Terraform на лицензию BUSL. Совместим по коду и командам.

</details>

**A10.** Назови три альтернативы Terraform и их особенности.

<details><summary>Ответ</summary>

Pulumi (IaC на обычных языках), CloudFormation/ARM (нативные инструменты
облаков), Crossplane (управление из Kubernetes), Ansible (конфигурация и ограниченно
инфраструктура).

</details>

**A11.** Зачем нужен Packer и как он сочетается с Terraform?

<details><summary>Ответ</summary>

Packer собирает образы ВМ с предустановленным ПО; Terraform затем создаёт
машины из этих образов — быстрее запуск и меньше шагов настройки.

</details>

**A12.** Что такое дрейф конфигурации и откуда он берётся?

<details><summary>Ответ</summary>

Расхождение между описанным в коде состоянием и фактическим. Возникает
из-за ручных правок в консоли, действий других инструментов и автоматики облака.

</details>

**A13.** Почему `plan` — обязательный шаг, а не «для перестраховки»?

<details><summary>Ответ</summary>

Потому что он показывает точный список изменений, включая удаления. Это
единственная защита от «случайно снесли прод» и основа ревью инфраструктурных изменений.

</details>

**A14.** Какие файлы обычно есть в Terraform-проекте и что в каждом?

<details><summary>Ответ</summary>

`main.tf` (ресурсы), `variables.tf` (входы), `outputs.tf` (выходы),
`versions.tf` (версии), `terraform.tfvars` (значения), `.terraform.lock.hcl`
(зафиксированные версии провайдеров).

</details>

**A15.** Какие файлы и данные ни в коем случае нельзя коммитить?

<details><summary>Ответ</summary>

`*.tfstate` и его резервные копии (там секреты открытым текстом), каталог
`.terraform/`, `.tfvars` с секретами, приватные ключи и пароли в любом виде.

</details>

### Блок B. «Классифицируй и оцени»

Определи, чей это инструмент — Terraform или Ansible (или оба):

```text:no-line-numbers
B1.  Создать ВМ в облаке
B2.  Установить nginx на сервер
B3.  Создать VPC, подсети и security groups
B4.  Настроить конфиг postgresql.conf на сервере
B5.  Создать managed PostgreSQL в облаке
B6.  Раскатить обновление приложения на 20 серверов
B7.  Создать бакет и выдать права сервисному аккаунту
B8.  Завести пользователей и группы в GitLab
B9.  Настроить systemd-сервис
B10. Создать DNS-записи
```

<details><summary>Ответ</summary>

**B1.** Terraform. **B2.** Ansible. **B3.** Terraform. **B4.** Ansible.
**B5.** Terraform. **B6.** Ansible. **B7.** Terraform. **B8.** Terraform (провайдер gitlab).
**B9.** Ansible. **B10.** Terraform.

</details>

Оцени решения:
```text:no-line-numbers
B11. Инфраструктура создаётся кликами, документации нет
B12. terraform apply запускают с ноутбука, стейт лежит локально
B13. В .tf файле прописан пароль от базы
B14. В .gitignore нет *.tfstate
B15. Версии провайдеров не зафиксированы
B16. apply запускают без просмотра plan, "и так понятно"
B17. Один main.tf на 4000 строк со всеми окружениями
B18. Terraform создаёт ВМ и через provisioner ставит docker и конфиги
```

<details><summary>Ответ</summary>

**B11.** Нет воспроизводимости и истории — главная проблема, которую решает IaC.
**B12.** Локальный стейт исключает командную работу и рискует потерей состояния.
**B13.** Секрет в коде = утечка; плюс он попадёт и в стейт.
**B14.** Стейт с секретами уедет в репозиторий.
**B15.** Непредсказуемые изменения при обновлении провайдера.
**B16.** Прямой путь к случайному удалению ресурсов.
**B17.** Долгий plan, высокий риск, конфликты в git; нужно разделение.
**B18.** Провижининг внутри Terraform — антипаттерн; лучше cloud-init/Ansible/образ.

</details>

### Блок C. Практика

#### C1. Установка
Поставь Terraform (или OpenTofu), проверь версию, включи автодополнение.
Если есть возможность — поставь `tfenv` и переключись между двумя версиями.

### Блок D. Инциденты

**D1.** Коллега создал ВМ руками, Terraform её «не видит». Что произойдёт при apply?

<details><summary>Ответ</summary>

Terraform не знает об этой ВМ: в плане её не будет, управлять ею нельзя.
Если такой ресурс конфликтует с описанным (например, занято имя), apply упадёт.
Решение — `terraform import` или пересоздание через код.

</details>

**D2.** В команде два человека одновременно запустили apply с локальным стейтом.
Что случится?

<details><summary>Ответ</summary>

Возможны гонки и порча стейта: два процесса меняют инфраструктуру и записывают
разные версии состояния. Для этого нужен удалённый backend с блокировкой.

</details>

**D3.** Инфраструктура прода существует, но кода нет. С чего начать внедрение Terraform?

<details><summary>Ответ</summary>

Начать с нового окружения/компонента, писать код для новых ресурсов,
существующие постепенно импортировать (`import`), зафиксировать правило «руками больше
не создаём», внедрить удалённый стейт и ревью.

</details>

**D4.** После обновления Terraform код перестал работать. Что было упущено?

<details><summary>Ответ</summary>

Не зафиксированы версии Terraform и провайдеров (`required_version`,
`version`, lock-файл), поэтому подтянулись несовместимые версии.

</details>

**D5.** В репозитории обнаружен файл `terraform.tfstate` с паролями. Действия?

<details><summary>Ответ</summary>

Считать содержащиеся секреты скомпрометированными и ротировать их,
удалить файл из истории репозитория, добавить `.gitignore`, перевести стейт
в удалённый backend с шифрованием и ограниченным доступом.

</details>

**D6.** Разработчик добавил `provisioner "remote-exec"` с установкой пакетов.
Какие аргументы приведёшь против?

<details><summary>Ответ</summary>

Хрупкость, отсутствие идемпотентности, ошибки при повторном применении,
невозможность нормально отлаживать, зависимость от SSH-доступа во время apply.
Альтернативы: cloud-init, образы Packer, Ansible после создания.

</details>

**D7.** `apply` удалил прод-базу: в плане была строка `destroy`, но её не заметили.
Как выстроить процесс, чтобы это стало невозможным?

<details><summary>Ответ</summary>

Обязательный `plan` в MR с публикацией вывода, ревью вторым человеком,
`prevent_destroy` на критичных ресурсах, отдельные стейты для прода, запуск apply
только из CI с ручным подтверждением, права, ограничивающие удаление.

</details>

**D8.** Stage и prod «разъехались», хотя код один. Возможные причины?

<details><summary>Ответ</summary>

Ручные правки в одном из окружений, разные значения переменных, разные версии
провайдеров/модулей, ресурсы, созданные вне Terraform.

</details>

**D9.** Нужно быстро поднять копию инфраструктуры в другом регионе. Насколько это реально
при наличии Terraform и при его отсутствии?

<details><summary>Ответ</summary>

С Terraform — реалистично за часы (сменить регион/переменные и применить,
с поправкой на данные и специфичные ресурсы). Без Terraform — дни ручной работы
с высоким риском расхождений.

</details>

**D10.** Руководство спрашивает: «зачем нам Terraform, если всё уже работает?»
Как аргументируешь?

<details><summary>Ответ</summary>

Через риски и стоимость: восстановление после аварии, воспроизводимость
окружений, ревью и аудит изменений, борьба с «сиротами» и лишними расходами,
скорость onboarding'а, снижение зависимости от «того, кто всё помнит».

</details>

### Блок E. Вопросы с собеседования

**1.** Что такое инфраструктура как код?

<details><summary>Ответ</summary>

Описание инфраструктуры кодом с версионированием, ревью и воспроизводимым применением.

</details>

**2.** Чем декларативный подход отличается от императивного?

<details><summary>Ответ</summary>

Декларативный описывает целевое состояние, императивный — последовательность действий.

</details>

**3.** Чем Terraform отличается от Ansible?

<details><summary>Ответ</summary>

Terraform создаёт инфраструктуру и хранит стейт; Ansible настраивает уже существующие
системы.

</details>

**4.** Что такое провайдер в Terraform?

<details><summary>Ответ</summary>

Плагин, реализующий работу с конкретным API (облако, k8s, GitLab, DNS).

</details>

**5.** Что такое дрейф конфигурации?

<details><summary>Ответ</summary>

Расхождение кода и реальности из-за изменений вне Terraform.

</details>

**6.** Зачем нужен `terraform plan`?

<details><summary>Ответ</summary>

Чтобы заранее увидеть, что будет создано, изменено и удалено.

</details>

**7.** Что такое OpenTofu?

<details><summary>Ответ</summary>

Открытый совместимый форк Terraform под Linux Foundation.

</details>

**8.** Как Terraform сочетается с Packer и Ansible?

<details><summary>Ответ</summary>

Packer готовит образы, Terraform создаёт из них ресурсы, Ansible настраивает
содержимое и деплоит.

</details>

**9.** Что нельзя хранить в git в Terraform-проекте?

<details><summary>Ответ</summary>

Стейт и его бэкапы, каталог `.terraform/`, файлы с секретами, ключи.

</details>

**10.** С чего начать внедрение Terraform на существующем проекте?

<details><summary>Ответ</summary>

С нового компонента и удалённого стейта; существующее импортировать постепенно,
запретив ручное создание ресурсов.

</details>
