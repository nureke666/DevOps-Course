# 07. Практика: 5 лаб по Terraform

> Роадмап → Terraform. Цель — пройти путь от `hello world` до модульной инфраструктуры
> в CI, не разорившись на облаке.

> ⚠️ После каждой облачной лабы — `terraform destroy` и проверка счёта.
>
> ☁️ Облачные лабы (2–5) даны в двух вариантах: **AWS** и **Yandex Cloud** (регион Россия
> или Казахстан `kz1`). Делай в том облаке, где есть аккаунт; сильный вариант — оба,
> с общим контрактом модулей (тема 05, §7).

## 🧪 Лаба 1. Первые ресурсы без облака

### Что делаем
Осваиваем цикл и синтаксис на docker-провайдере — бесплатно и быстро.

### Требования
- [ ] `versions.tf` с фиксированными версиями
- [ ] docker-сеть, образ nginx, два контейнера с разными портами
- [ ] Переменные: имя проекта, список портов, теги
- [ ] `locals` для префикса имён
- [ ] `for_each` по map сервисов
- [ ] `output` с URL всех сервисов
- [ ] Проверены `fmt`, `validate`, `plan`, `apply`, `destroy`
- [ ] Эксперимент: удаление среднего элемента при `count` и при `for_each`

### Проверка
```bash
terraform output
curl -s localhost:8081 | head -3
docker ps --format '{{.Names}}\t{{.Ports}}'
```

### Вопросы себе
- Какие изменения приводят к пересозданию контейнера, а какие — к обновлению?
- Что будет, если удалить контейнер руками и запустить `plan`?

## 🧪 Лаба 2. ⭐ Удалённый стейт и импорт

### Что делаем
Переводим стейт в объектное хранилище и учимся забирать существующие ресурсы
под управление.

### Требования
- [ ] MinIO (или облачный бакет) с включённым версионированием
- [ ] `backend "s3"` настроен, выполнен `init -migrate-state`
- [ ] Локальный стейт удалён, `plan` работает из бакета
- [ ] Проверена блокировка: второй `apply` не проходит
- [ ] Испорчен и восстановлен стейт из предыдущей версии
- [ ] Создан ресурс **вручную** и импортирован (`import` + доведение кода до «No changes»)
- [ ] Выполнен `state mv` при переименовании ресурса без пересоздания
- [ ] `state rm` на одном ресурсе — объяснено, что он остался в реальности

### Проверка
```bash
terraform state list
terraform plan        # No changes после импорта
```

### ☁️ AWS-вариант
- [ ] Бакет стейта — отдельной конфигурацией `bootstrap/`: версионирование, public access block,
      `prevent_destroy` (тема 03, §2.2)
- [ ] `backend "s3"` с `encrypt = true` и `use_lockfile = true` (без DynamoDB); во время
      чужого `apply` виден `*.tflock` рядом со стейтом
- [ ] Импортирован созданный руками `aws_instance` или `aws_s3_bucket`
- [ ] Yandex-вариант: тот же backend на `storage.yandexcloud.net` (или `.kz` для `kz1`)
      со `skip_*` флагами и статическим ключом SA

### Вопросы себе
- Что произойдёт, если два человека применят изменения одновременно?
- Что лежит в стейте из того, что нельзя показывать?

## 🧪 Лаба 3. Инфраструктура в облаке

### Что делаем
Повторяем облачную лабу «сеть + ВМ + бакет» из блока про облака, но кодом.

### Требования
- [ ] VPC, публичная и приватная подсети в двух зонах
- [ ] Security groups «от группы к группе»
- [ ] Bastion с публичным IP, ВМ приложения без публичного IP
- [ ] NAT для приватной подсети
- [ ] Бакет для статики/бэкапов с версионированием
- [ ] Сервисный аккаунт с минимальными правами
- [ ] Образ ОС выбирается через `data`, а не хардкодом
- [ ] cloud-init через `templatefile`
- [ ] `output`: IP bastion, идентификаторы подсетей, имя бакета
- [ ] `prevent_destroy` на бакете
- [ ] `terraform destroy` в конце, счёт проверен

### Проверка
```bash
ssh -J ubuntu@$(terraform output -raw bastion_ip) ubuntu@$(terraform output -raw app_private_ip)
terraform output -json | jq 'keys'
```

### ☁️ AWS-вариант
| Требование | AWS | Yandex Cloud |
|------------|-----|--------------|
| Сеть на 2 зоны | `terraform-aws-modules/vpc/aws ~> 6.7` или свои `aws_vpc`/`aws_subnet` | `yandex_vpc_network`/`subnet`; в `kz1` — одна зона `kz1-a` |
| NAT | `single_nat_gateway = true` (лаба) — платный по часам ⚠️ | `yandex_vpc_gateway` + route table |
| SG «от группы к группе» | `aws_vpc_security_group_ingress_rule` с `referenced_security_group_id` | `security_group_id` в правиле `ingress` |
| Вход на приватную ВМ | bastion **или** SSM Session Manager (роль `AmazonSSMManagedInstanceCore`) | bastion или OS Login |
| Бакет | `aws_s3_bucket` + `aws_s3_bucket_versioning` + public access block | `yandex_storage_bucket` с `versioning` |
| Минимальные права | IAM role + instance profile | сервисный аккаунт + роль на каталог/бакет |
| Образ через `data` | `data "aws_ssm_parameter"` (Canonical Ubuntu 24.04) | `data "yandex_compute_image"` по `family` |

Порядок стоимости AWS-варианта — десятки центов в час (NAT + публичные IPv4): уложись в 2 часа.

### Вопросы себе
- Сколько времени займёт поднять такую же инфраструктуру в другой зоне/регионе?
- Какие ресурсы в плане имеют пометку `forces replacement` при смене параметров?

## 🧪 Лаба 4. Модули и два окружения

### Что делаем
Превращаем лабу 3 в модульную структуру с dev и prod.

### Структура
```text:no-line-numbers
infra/
├── modules/
│   ├── network/     (VPC, подсети, NAT, SG)
│   ├── compute/     (ВМ, bastion, cloud-init)
│   └── storage/     (бакет, права)
└── environments/
    ├── dev/   (1 ВМ, малые ресурсы, retention 7 дней)
    └── prod/  (3 ВМ, две зоны, retention 30 дней, prevent_destroy)
```

### Требования
- [ ] Модули с `variables.tf`, `outputs.tf`, README
- [ ] Модули **не** объявляют `provider`/`backend`
- [ ] Окружения отличаются только значениями переменных
- [ ] Разные ключи стейта для dev и prod
- [ ] Выходы одного модуля передаются во входы другого
- [ ] `for_each` на модуле или внутри него для набора ВМ
- [ ] Перенос ресурса в модуль выполнен через блок `moved` без пересоздания
- [ ] `terraform-docs` (или ручной) README с таблицей переменных

### ☁️ AWS-вариант
- [ ] `modules/network/{aws,yandex}` с одинаковыми `variables.tf`/`outputs.tf` (тема 05, §7)
- [ ] `environments/dev-aws` и (если есть доступ) `environments/dev-kz` вызывают одну и ту же
      форму модулей; отличаются `source`, провайдер и значения переменных
- [ ] `terraform test` с `mock_provider` в обеих реализациях
      ([«Тестирование инфраструктурного кода»](/terraform/09-testing), §4)

### Вопросы себе
- Что нужно изменить, чтобы добавить окружение `stage`? (Должно быть ~10 строк.)
- Где в моей структуре может появиться расхождение dev и prod?

## 🧪 Лаба 5. ⭐ Terraform в CI/CD

### Что делаем
Убираем `apply` с ноутбука.

### Требования
- [ ] Репозиторий в GitLab/GitHub с `.gitignore` для Terraform
- [ ] Пайплайн: `fmt -check` → `validate` → `tflint`/`tfsec` → `plan` (артефакт) →
      `apply` (manual, только main)
- [ ] `plan.txt` виден в MR
- [ ] Разные креды: read-only для plan, расширенные для apply
- [ ] Секреты только в защищённых переменных CI
- [ ] Пайплайн по расписанию: ночной `plan`, уведомление при непустом результате
- [ ] Проверено: изменение ресурса вручную → ночной plan это ловит
- [ ] В репозитории есть `CONTRIBUTING.md` с регламентом изменений

### ☁️ AWS-вариант и тесты
- [ ] AWS: вход CI по OIDC в роли `plan` (read-only) и `apply` — без access keys
      (см. раздел «Security» этого курса); Yandex: workload identity federation
- [ ] В MR дополнительно: `trivy config`, `terraform test` модулей (JUnit), `conftest`
      на `plan.json` ([«Тестирование инфраструктурного кода»](/terraform/09-testing), §7)

### Критерии приёмки
```text:no-line-numbers
1. MR с изменением → в комментариях/артефактах виден план
2. Merge → job apply в статусе manual
3. Нажатие apply → изменения применены, уведомление пришло
4. Ручное изменение в облаке → ночной plan не пустой → алерт
```

### Вопросы себе
- Может ли кто-то применить изменения в обход процесса? Как это закрыть?
- Что произойдёт, если apply упадёт на середине в CI?
