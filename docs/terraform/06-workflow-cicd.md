# 06. Рабочий процесс и CI/CD

> Роадмап → Terraform. Концепции понятны — теперь как с этим живёт команда.
>
> **После темы ты умеешь:** организовать окружения, встроить Terraform в CI/CD,
> безопасно работать с секретами и выстроить процесс ревью инфраструктурных изменений.

---

## 🗺️ Как выглядит зрелый процесс

```text:no-line-numbers
 инженер                 GitLab/GitHub                    облако
   │                          │                              │
   ├─ ветка + правка .tf ────►│                              │
   │                          ├─ CI: fmt, validate, tflint   │
   │                          ├─ CI: terraform plan ─────────┤ (read-only креды)
   │                          ├─ план публикуется в MR ⭐     │
   ├─ ревью коллеги ─────────►│                              │
   ├─ merge ─────────────────►│                              │
   │                          ├─ CI: apply (ручное нажатие) ─┤ (write креды)
   │                          └─ уведомление в чат            │
   ▼
 никто не делает apply с ноутбука
```

## 1. Окружения: три способа

| Способ | Плюсы | Минусы | Когда |
|--------|-------|--------|-------|
| **Каталоги** `environments/{dev,stage,prod}` | Явно, разные backend-ключи, разные переменные, отдельные права | Дублирование вызовов модулей | ⭐ Дефолт |
| **Workspaces** | Один код, несколько стейтов | Легко перепутать текущий workspace, трудно держать различия | Временные и однотипные среды |
| **Terragrunt** | Убирает дублирование, DRY-backend | Ещё один инструмент в стеке | Много окружений/аккаунтов |

```bash
# workspaces (если всё же используешь)
terraform workspace list
terraform workspace new stage
terraform workspace select prod
terraform workspace show          # ⭐ проверяй ПЕРЕД apply
```
```hcl
# различия по окружению без дублирования
locals {
  settings = {
    dev   = { instances = 1, size = "small" }
    stage = { instances = 2, size = "small" }
    prod  = { instances = 5, size = "large" }
  }
  cfg = local.settings[var.env]
}
```

## 2. Terraform в CI/CD (GitLab CI)

```yaml
# .gitlab-ci.yml
image:
  name: hashicorp/terraform:1.9
  entrypoint: [""]

variables:
  TF_ROOT: environments/${ENV}
  TF_IN_AUTOMATION: "true"           # ⭐ убирает лишние подсказки в выводе

cache:
  key: "${ENV}"
  paths: [ "${TF_ROOT}/.terraform" ]

before_script:
  - cd "${TF_ROOT}"
  - terraform init -input=false

stages: [validate, plan, apply]

validate:
  stage: validate
  script:
    - terraform fmt -check -recursive -diff
    - terraform validate

plan:
  stage: plan
  script:
    - terraform plan -input=false -out=tfplan
    - terraform show -no-color tfplan > plan.txt      # ⭐ человекочитаемый план в MR
  artifacts:
    paths: [ "${TF_ROOT}/tfplan", "${TF_ROOT}/plan.txt" ]
    expire_in: 7 days

apply:
  stage: apply
  script:
    - terraform apply -input=false tfplan             # ⭐ ровно тот план, что ревьюили
  when: manual                                        # ⭐ ручное подтверждение
  only: [ main ]
  environment:
    name: ${ENV}
```

| Принцип CI для Terraform | Почему |
|--------------------------|--------|
| `plan` на каждый MR | Ревью видит реальные изменения инфраструктуры |
| `apply` только из `main` и вручную | Нет случайных изменений прода |
| `apply` применяет **сохранённый план** | Между ревью и применением ничего не подменилось |
| Разные креды для plan и apply | Планирование — read-only |
| `TF_IN_AUTOMATION=true`, `-input=false` | Не ждать ввода в пайплайне |
| Артефакт плана с ограниченным сроком | В нём могут быть чувствительные данные ⚠️ |

Полезные инструменты рядом:
```bash
tflint                 # линтер: ошибки, неправильные типы инстансов, best practices
tfsec / trivy config   # ⭐ поиск проблем безопасности (открытые SG, публичные бакеты)
checkov                # политики безопасности и комплаенса
terraform-docs         # генерация README модулей
infracost              # ⭐ оценка стоимости изменений прямо в MR
pre-commit             # fmt/validate/tflint до коммита
```

## 3. Секреты

```text:no-line-numbers
 ❌ НЕЛЬЗЯ                                  ✅ МОЖНО
 пароль в .tf                               переменные окружения TF_VAR_*
 пароль в terraform.tfvars в git            секреты CI/CD (masked, protected)
 стейт в git                                Vault / хранилище секретов облака
 вывод секрета в output без sensitive       генерация пароля random_password + Vault
```

```hcl
# генерация пароля и передача в managed-сервис
resource "random_password" "db" {
  length  = 24
  special = true
}

resource "yandex_mdb_postgresql_user" "app" {
  name     = "app"
  password = random_password.db.result      # ⚠️ попадёт в стейт открытым текстом
}

output "db_password" {
  value     = random_password.db.result
  sensitive = true
}
```

⭐ Помни: что бы ты ни делал, **всё, что Terraform создаёт, попадает в стейт**.
Поэтому стейт шифруется, доступ к нему ограничен, а «настоящие» секреты живут в Vault
(см. раздел «Vault» этого курса) и читаются оттуда — в том числе провайдером Vault.

## 4. Ревью инфраструктурных изменений

Чек-лист ревьюера MR с Terraform:
```text:no-line-numbers
[ ] Есть вывод plan, и он прочитан целиком
[ ] Нет неожиданных destroy / forces replacement
[ ] Изменения соответствуют описанию задачи
[ ] Нет секретов в коде и в tfvars
[ ] Security groups не открыты в 0.0.0.0/0 без обоснования
[ ] Бакеты не публичные, шифрование включено
[ ] Критичные ресурсы защищены prevent_destroy
[ ] Версии модулей и провайдеров зафиксированы
[ ] Изменение сначала применено на dev/stage
[ ] Есть теги/метки владельца и окружения
[ ] Оценена стоимость (если есть infracost)
```

## 5. Практики, которые экономят нервы

| Практика | Смысл |
|----------|-------|
| Небольшие MR | Один компонент — один MR; огромный план невозможно ревьюить |
| Отдельные стейты на компонент | Быстрый plan, ограниченный радиус поражения |
| `prevent_destroy` на данных | Защита от ошибки в плане |
| Регулярный `plan` по расписанию | Раннее обнаружение дрейфа |
| Единые теги (`env`, `owner`, `managed-by=terraform`) | Учёт расходов и поиск «сирот» |
| Одинаковые версии Terraform у всех и в CI | `.terraform-version`/`tfenv`, образ в CI |
| Запрет ручного создания ресурсов | Иначе IaC не работает |
| Документированный runbook на аварии | Что делать при порче стейта, зависшей блокировке |

## 6. Тестирование инфраструктурного кода (обзорно)

| Уровень | Инструмент |
|---------|-----------|
| Статика | `fmt`, `validate`, `tflint`, `tfsec`/`checkov` |
| Юнит-тесты конфигурации | `terraform test` (встроенный, 1.6+) |
| Интеграционные | Terratest (Go): создать → проверить → удалить |
| Политики | OPA/Conftest, Sentinel |
| Стоимость | `infracost diff` |

Подробно — пирамида, моки, политики и Terratest: [«Тестирование инфраструктурного кода»](/terraform/09-testing).
```hcl
# пример встроенного теста: tests/network.tftest.hcl
run "creates_network" {
  command = plan
  assert {
    condition     = yandex_vpc_network.this.name == "prod-net"
    error_message = "Неверное имя сети"
  }
}
```

## 7. Грабли процесса

| Грабля | Последствие | Решение |
|--------|-------------|---------|
| `apply` с ноутбука | Разные версии кода, конфликты, нет следа | Только CI с ручным подтверждением |
| `apply` без сохранённого плана | Применяется не то, что ревьюили | `plan -out` + `apply tfplan` |
| Один стейт и гигантские MR | Невозможно ревьюить, страшно применять | Разделение и мелкие изменения |
| Артефакт плана хранится вечно | Утечка чувствительных данных | Короткий `expire_in`, ограничение доступа |
| Разные версии Terraform у людей | Ошибки состояния и форматирования | Единая версия (tfenv/образ) |
| Нет линтеров и сканеров | Открытые SG и публичные бакеты уезжают в прод | tflint, tfsec, policy-as-code |
| Прод применяет тот же, кто писал | Нет контроля | Обязательное ревью вторым человеком |
| Нет расписания `plan` | Дрейф копится месяцами | Ночной plan + алерт |

## 💼 Как это в DevOps

- «Есть ли у вас Terraform в CI?» — типичный вопрос на собеседовании: он проверяет,
  работал ли человек в команде, а не только на своём ноутбуке.
- Плановая выдача доступа: у CI на plan — read-only роль, на apply — расширенная,
  и apply доступен ограниченному кругу.
- Инфраструктурные MR ревьюят так же серьёзно, как код: половина инцидентов
  безопасности в облаках ловится именно на этом этапе.
- `infracost` в MR превращает разговор «дорого/недорого» в цифры до применения.
- Ночной `plan` с алертом на непустой результат — дешёвый способ узнать о ручных правках
  раньше, чем они станут проблемой.

## 🧠 Что запомнить

1. Зрелый процесс: правка → `plan` в MR → ревью → `apply` из CI вручную.
2. ⭐ Применяют **сохранённый план** (`plan -out` + `apply tfplan`), а не «ещё один apply».
3. Окружения разделяют каталогами и ключами стейта; workspaces — для временных сред.
4. У CI разные креды: read-only для plan, расширенные для apply.
5. Секреты — в переменных окружения, секретах CI и Vault; всё созданное всё равно
   попадает в стейт, поэтому стейт защищают.
6. Артефакт плана содержит чувствительные данные — ограничивай срок хранения и доступ.
7. Линтеры и сканеры безопасности (tflint, tfsec, checkov) ловят открытые SG
   и публичные бакеты до прода.
8. `infracost` показывает стоимость изменений прямо в MR.
9. Регулярный `plan` по расписанию обнаруживает дрейф.
10. Единая версия Terraform у всех и в CI — обязательное условие воспроизводимости.

### Блок A. Теория

**A1.** Опиши зрелый процесс внесения инфраструктурного изменения по шагам.

<details><summary>Ответ</summary>

Ветка → правка кода → локальный `fmt/validate/plan` → MR → CI прогоняет
линтеры и `plan`, публикует его → ревью коллеги → merge → `apply` из CI
с ручным подтверждением → проверка результата и уведомление.

</details>

**A2.** Почему `apply` не делают с ноутбука?

<details><summary>Ответ</summary>

Локально может быть другая версия кода, Terraform и переменных; нет следа,
кто и что применил; обходится ревью; легко применить из «грязной» ветки.

</details>

**A3.** ⭐ Почему в CI применяют сохранённый план, а не запускают `apply` заново?

<details><summary>Ответ</summary>

Между планированием и применением код или состояние могли измениться.
Применение сохранённого плана гарантирует, что выполняется именно то, что проверили.

</details>

**A4.** Три способа разделения окружений — плюсы и минусы каждого.

<details><summary>Ответ</summary>

Каталоги: явное разделение, отдельные стейты и права, но дублирование вызовов.
Workspaces: минимум дублирования, но легко перепутать окружение и трудно выражать
различия. Terragrunt: DRY и удобство при многих окружениях, но дополнительный инструмент.

</details>

**A5.** Чем опасны workspaces и как снизить риск?

<details><summary>Ответ</summary>

Тем, что текущий workspace — состояние терминала: можно применить в прод,
думая, что ты в dev. Снижается проверкой `terraform workspace show` в CI,
явными подтверждениями и разделением прав.

</details>

**A6.** Какие креды должны быть у job `plan` и у job `apply`?

<details><summary>Ответ</summary>

`plan` — read-only роль; `apply` — роль с правами на изменение,
доступная ограниченному кругу и только на защищённых ветках.

</details>

**A7.** Зачем нужны `TF_IN_AUTOMATION` и `-input=false`?

<details><summary>Ответ</summary>

Убирают интерактивные запросы и подсказки, рассчитанные на человека:
пайплайн не должен зависать в ожидании ввода.

</details>

**A8.** Почему артефакт плана нельзя хранить долго и открывать всем?

<details><summary>Ответ</summary>

В нём могут быть чувствительные значения (параметры ресурсов, иногда секреты);
хранение вечно и открытый доступ = утечка.

</details>

**A9.** Какие инструменты запускают рядом с Terraform в CI и что они дают?

<details><summary>Ответ</summary>

`tflint` (ошибки и стиль), `tfsec`/`checkov`/`trivy config` (безопасность),
`terraform-docs` (README), `infracost` (стоимость), `pre-commit` (проверки до коммита),
`terraform test`/Terratest (тесты).

</details>

**A10.** Как правильно работать с секретами в Terraform?

<details><summary>Ответ</summary>

Через переменные окружения `TF_VAR_*`, защищённые переменные CI и хранилища
секретов (Vault, облачные сервисы); не в коде и не в закоммиченных tfvars.

</details>

**A11.** Почему `sensitive` не решает проблему секретов в стейте?

<details><summary>Ответ</summary>

`sensitive` лишь скрывает значение в выводе. В файле состояния значение
хранится открытым текстом, поэтому стейт шифруют и ограничивают доступ к нему.

</details>

**A12.** Составь чек-лист ревьюера инфраструктурного MR (минимум 8 пунктов).

<details><summary>Ответ</summary>

План прочитан; нет неожиданных destroy/replacement; изменения соответствуют
задаче; нет секретов; SG не открыты миру; бакеты приватные и шифрованные;
`prevent_destroy` на критичном; версии зафиксированы; применено сначала на dev/stage;
есть теги владельца; оценена стоимость.

</details>

**A13.** Зачем запускать `plan` по расписанию?

<details><summary>Ответ</summary>

Чтобы обнаруживать дрейф (ручные правки, изменения со стороны платформы)
до того, как он приведёт к инциденту или сломает следующий apply.

</details>

**A14.** Зачем нужны единые теги на ресурсах?

<details><summary>Ответ</summary>

Для учёта расходов, поиска владельца ресурса, автоматизации (уборка «сирот»,
политики) и разделения окружений.

</details>

**A15.** Какие уровни тестирования инфраструктурного кода существуют?

<details><summary>Ответ</summary>

Статический анализ (fmt/validate/линтеры/сканеры), встроенные тесты
(`terraform test`), интеграционные тесты (Terratest), политики (OPA/Conftest/Sentinel),
проверка стоимости.

</details>

### Блок B. «Оцени процесс»

```text:no-line-numbers
B1.  Инженер применяет изменения локально, потом коммитит код
B2.  В CI: fmt → validate → plan (артефакт) → apply (manual, только main)
B3.  apply запускается автоматически при merge в main
B4.  plan и apply используют один и тот же сервисный аккаунт с полными правами
B5.  Артефакт плана хранится 1 год, доступен всем участникам проекта
B6.  Секреты передаются через переменные CI (masked + protected)
B7.  terraform.tfvars с паролями лежит в репозитории
B8.  У всех инженеров разные версии Terraform
B9.  В пайплайне запускаются tflint и tfsec, результаты блокируют merge
B10. MR на 3000 строк изменений инфраструктуры
B11. Ночной pipeline делает plan и шлёт алерт, если он непустой
B12. apply выполняет тот же человек, который писал изменение, без ревью
B13. infracost в MR показывает +$450/мес
B14. Prod и stage используют разные версии модулей и разные версии провайдеров
```

<details><summary>Ответ</summary>

**B1.** Плохо: применение раньше ревью, состояние не соответствует репозиторию.
**B2.** Эталонный пайплайн.
**B3.** Рискованно для прода: изменения применяются без осознанного подтверждения.
**B4.** Нарушение принципа наименьших привилегий: планирование должно быть read-only.
**B5.** Долгое хранение и широкий доступ к плану — риск утечки.
**B6.** Правильная работа с секретами.
**B7.** Утечка секретов в репозитории.
**B8.** Источник трудноуловимых различий; нужна единая версия.
**B9.** Хорошая практика: проблемы безопасности ловятся до прода.
**B10.** Такой MR невозможно ревьюить; нужно дробить.
**B11.** Правильный способ ловить дрейф.
**B12.** Нет контроля: ревью должно быть обязательным.
**B13.** Отличный повод обсудить изменение до применения.
**B14.** Stage перестаёт быть репетицией прода.

</details>

### Блок C. Практика

#### C1. 🔑 Структура репозитория
Собери репозиторий: `modules/`, `environments/{dev,prod}`, `.gitignore`,
`README.md`, `.terraform-version`. Настрой разные ключи стейта для окружений.

#### C2. Пайплайн: validate
Добавь job с `terraform fmt -check` и `terraform validate`. Намеренно сломай формат
и убедись, что пайплайн падает.

#### C3. 🔑 Пайплайн: plan как артефакт
1. Сделай job `plan` с `-out=tfplan` и `terraform show -no-color`.
2. Приложи `plan.txt` артефактом.
3. Проверь, что план виден в MR.

#### C4. Пайплайн: apply вручную
1. Добавь job `apply` с `when: manual` и ограничением по ветке.
2. Примени сохранённый план.
3. Проверь, что apply невозможен из feature-ветки.

<details><summary>Ответ</summary>

Ограничение по ветке и `when: manual` — минимальная защита прода.

</details>

#### C5. Разные креды
Настрой две группы переменных CI: read-only для plan и расширенные для apply
(разные сервисные аккаунты). Проверь, что plan не может создавать ресурсы.

<details><summary>Ответ</summary>

Job `plan` с read-only кредами должен успешно строить план, но падать
при попытке применить.

</details>

#### C6. Линтеры и безопасность
Добавь `tflint` и `tfsec` (или `checkov`). Намеренно открой security group
в `0.0.0.0/0` и убедись, что сканер это ловит.

<details><summary>Ответ</summary>

`tfsec` сообщит о правиле с источником `0.0.0.0/0` — это и есть цель упражнения.

</details>

#### C7. Секреты
1. Убери все секреты из кода.
2. Передай пароль через переменную CI (`TF_VAR_db_password`, masked).
3. Проверь, что он не появляется в логах пайплайна.

#### C8. Дрейф по расписанию
Настрой ночной (или ежечасный на стенде) pipeline с `plan`, который падает/шлёт
уведомление при непустом плане. Проверь, изменив ресурс вручную.

<details><summary>Ответ</summary>

При ручном изменении ресурса ночной `plan` перестанет быть пустым — сигнал дрейфа.

</details>

#### C9. Стоимость
Подключи `infracost` (или посчитай вручную) и выведи изменение стоимости в MR.
Оцени, сколько стоит твой учебный стенд.

#### C10. Регламент
Напиши `CONTRIBUTING.md` для репозитория инфраструктуры: как вносить изменения,
кто ревьюит, когда можно применять на прод, что делать при аварии со стейтом.

### Блок D. Инциденты

**D1.** Кто-то применил изменения локально, CI теперь показывает другой план. Действия?

<details><summary>Ответ</summary>

Выяснить, что именно применили, синхронизировать код с реальностью
(довести до «No changes»), при необходимости импортировать; запретить локальный apply
и ограничить права.

</details>

**D2.** В логах пайплайна обнаружен пароль от базы. Что делать и что изменить?

<details><summary>Ответ</summary>

Считать секрет скомпрометированным и ротировать; пометить переменные masked,
убрать вывод секретов, проверить артефакты и логи, ограничить доступ к ним.

</details>

**D3.** `apply` в CI упал на середине, часть ресурсов создана. Что дальше?

<details><summary>Ответ</summary>

Исправить причину и повторить `apply`: Terraform дойдёт до целевого состояния.
Если ресурс создан, но не попал в стейт — импортировать или удалить вручную.
Проверить, не осталась ли блокировка.

</details>

**D4.** Merge прошёл, apply забыли нажать — изменения не применились неделю. Как поймать?

<details><summary>Ответ</summary>

Уведомления о непримененных изменениях, ночной `plan` (он покажет разницу),
правило «merge без apply не завершает задачу», дашборд состояния окружений.

</details>

**D5.** Ночной plan показывает изменения каждый день, хотя никто ничего не менял. Причины?

<details><summary>Ответ</summary>

Дрейф: ручные правки, автоматические изменения платформы (теги, версии),
поля, которые провайдер всегда показывает изменёнными; лечится исправлением кода
или `ignore_changes` для действительно платформенных полей.

</details>

**D6.** В MR план выглядел безопасно, но apply удалил ресурс. Как это возможно?

<details><summary>Ответ</summary>

Применяли не сохранённый план, а новый `apply` — за время ревью изменился код
или состояние; либо в плане строка destroy была, но её не заметили.

</details>

**D7.** Пайплайн блокируется зависшей блокировкой стейта. Порядок действий.

<details><summary>Ответ</summary>

Проверить, не выполняется ли реально apply (другой пайплайн, коллега),
посмотреть Lock Info, дождаться завершения; если процесс мёртв — `force-unlock`
с указанием ID и последующей проверкой состояния.

</details>

**D8.** Стоимость инфраструктуры выросла на 40% за месяц. Как связать это с изменениями
в репозитории?

<details><summary>Ответ</summary>

Сопоставить период роста с историей MR, использовать теги и отчёты по ним,
подключить `infracost` для будущих изменений, найти «сирот» и неиспользуемые ресурсы.

</details>

**D9.** Junior получил права на apply в prod и удалил стейдж. Как выстроить права?

<details><summary>Ответ</summary>

Разделить права по окружениям: отдельные сервисные аккаунты и защищённые
переменные для prod, доступ к apply в prod — ограниченному кругу, обязательное ревью,
`prevent_destroy` на критичном.

</details>

**D10.** Нужно срочно откатить инфраструктурное изменение. Как это делается на практике?

<details><summary>Ответ</summary>

Откатить коммит/версию модуля в git и применить новый план, внимательно проверив,
что откат не приводит к пересозданию/удалению данных; для части ресурсов может
потребоваться ручное восстановление из бэкапа.

</details>

### Блок E. Вопросы с собеседования

**1.** Как у вас устроен процесс изменений инфраструктуры?

<details><summary>Ответ</summary>

Ветка → MR → CI (`fmt`, `validate`, линтеры, `plan`) → ревью плана → merge →
ручной `apply` из CI → проверка.

</details>

**2.** Где запускается `terraform apply`?

<details><summary>Ответ</summary>

В CI/CD, с ручным подтверждением и на защищённой ветке.

</details>

**3.** Почему применяют сохранённый план?

<details><summary>Ответ</summary>

Чтобы применялось именно то, что было проверено на ревью.

</details>

**4.** Как разделяете окружения?

<details><summary>Ответ</summary>

Отдельные каталоги и ключи стейта (иногда workspaces или Terragrunt),
разные креды и права.

</details>

**5.** Как храните секреты?

<details><summary>Ответ</summary>

В переменных CI (masked/protected), переменных окружения и Vault; стейт шифруется,
доступ ограничен.

</details>

**6.** Что проверяете в CI кроме plan?

<details><summary>Ответ</summary>

Формат, синтаксис, линтеры, сканеры безопасности, тесты, стоимость.

</details>

**7.** Как ревьюят инфраструктурные MR?

<details><summary>Ответ</summary>

По чек-листу: смотреть план, искать destroy/replacement, проверять безопасность,
версии, теги и соответствие задаче.

</details>

**8.** Как обнаруживаете дрейф?

<details><summary>Ответ</summary>

Регулярным `plan` по расписанию с уведомлением о непустом результате.

</details>

**9.** Как контролируете стоимость?

<details><summary>Ответ</summary>

Тегами и отчётами биллинга, `infracost` в MR, регулярной уборкой «сирот».

</details>

**10.** Что делать, если apply упал на середине?

<details><summary>Ответ</summary>

Исправить причину и повторить apply; проверить стейт и блокировку; при частичном
создании — импортировать или удалить ресурсы вручную.

</details>
