# 05. Модули

> Роадмап → Terraform → *«Понимать концепции: … Модуль …»*.
>
> **После темы ты умеешь:** написать свой модуль, вызвать его с разными параметрами,
> подключать модули из реестра и организовать репозиторий инфраструктуры.

---

## 🗺️ Зачем нужны модули

```text:no-line-numbers
 БЕЗ МОДУЛЕЙ                              С МОДУЛЯМИ
 ───────────                              ──────────
 prod/main.tf   400 строк                 module "network" { source = "../modules/network", env = "prod" }
 stage/main.tf  400 строк (копия)         module "network" { source = "../modules/network", env = "stage" }
 dev/main.tf    400 строк (копия)         module "network" { source = "../modules/network", env = "dev" }
      │                                          │
 правку надо внести трижды                правка в одном месте
 окружения незаметно расходятся           окружения одинаковы by design
```

**Модуль** — это просто каталог с `.tf` файлами, у которого есть входы (`variable`)
и выходы (`output`). Любая конфигурация Terraform уже является модулем — корневым
(root module).

---

## 1. Анатомия модуля

```text:no-line-numbers
modules/network/
├── main.tf         ресурсы модуля
├── variables.tf    входы  (что можно настроить)
├── outputs.tf      выходы (что модуль отдаёт наружу)
├── versions.tf     требования к версиям
└── README.md       ⭐ описание: что делает, пример вызова, переменные
```

```hcl
# modules/network/variables.tf
variable "env"       { type = string }
variable "cidr" {
  type    = string
  default = "10.0.0.0/16"
}
variable "zones"     { type = list(string) }
variable "tags" {
  type    = map(string)
  default = {}
}

# modules/network/main.tf
resource "yandex_vpc_network" "this" {
  name   = "${var.env}-net"
  labels = var.tags
}

resource "yandex_vpc_subnet" "this" {
  for_each       = { for idx, z in var.zones : z => idx }
  name           = "${var.env}-subnet-${each.key}"
  zone           = each.key
  network_id     = yandex_vpc_network.this.id
  v4_cidr_blocks = [cidrsubnet(var.cidr, 8, each.value)]
}

# modules/network/outputs.tf
output "network_id" { value = yandex_vpc_network.this.id }
output "subnet_ids" { value = { for k, s in yandex_vpc_subnet.this : k => s.id } }
```

Вызов:
```hcl
# environments/prod/main.tf
module "network" {
  source = "../../modules/network"

  env   = "prod"
  cidr  = "10.10.0.0/16"
  zones = ["ru-central1-a", "ru-central1-b"]
  tags  = local.common_tags
}

module "app" {
  source     = "../../modules/app"
  env        = "prod"
  subnet_ids = module.network.subnet_ids      # ⭐ выход одного модуля → вход другого
  count_web  = 3
}

output "web_ips" { value = module.app.web_ips }
```

⭐ Обращение к выходам: `module.<имя>.<output>`. Ресурсы внутри модуля извне
напрямую недоступны — только через outputs. Это и есть инкапсуляция.

## 2. Источники модулей (`source`)

```hcl
source = "./modules/network"                                   # локальный путь
source = "../../modules/network"
source = "git::https://gitlab.com/org/tf-modules.git//network?ref=v1.4.0"   # ⭐ с версией
source = "git::ssh://git@gitlab.com/org/tf-modules.git//network?ref=main"
source = "terraform-aws-modules/vpc/aws"                       # публичный реестр
  version = "~> 6.7"                                            # сентябрь 2026: 6.7.3
source = "app.terraform.io/org/network/yandex"                 # приватный реестр
```

| Источник | Когда |
|----------|-------|
| Локальный путь | Модули внутри одного репозитория ⭐ старт |
| Git с `?ref=тег` | Общие модули компании — **обязательно с версией** |
| Публичный реестр | Готовые модули (VPC, EKS и т.п.) |
| Приватный реестр | Крупные компании |

⚠️ Модуль из git без `ref` (или с `ref=main`) означает, что завтра `terraform init`
подтянет другой код и план изменится сам собой. Всегда фиксируй версию.

## 3. Мета-аргументы модуля

```hcl
module "app" {
  source   = "./modules/app"
  for_each = var.services          # ⭐ один модуль — много экземпляров
  name     = each.key
  cpu      = each.value.cpu

  providers = {                    # передать альтернативный провайдер
    yandex = yandex.secondary      # Yandex: другой каталог/облако
  }                                # AWS: providers = { aws = aws.eu_west } — другой регион/аккаунт

  depends_on = [module.network]    # явная зависимость (редко нужно)
}
# адрес: module.app["billing"].web_ip
```

## 4. Как проектировать модули

```text:no-line-numbers
ХОРОШИЙ МОДУЛЬ                          ПЛОХОЙ МОДУЛЬ
 • решает одну понятную задачу           • «модуль всей инфраструктуры»
   (сеть, ВМ-группа, база)
 • разумное число входов                 • 60 переменных «на все случаи»
 • осмысленные умолчания                 • ничего не работает без 20 обязательных полей
 • отдаёт нужные outputs                 • ничего не отдаёт, приходится лезть внутрь
 • не содержит провайдеров и backend ⭐   • объявляет provider/backend внутри
 • есть README с примером                • «разберётесь по коду»
 • версионируется тегами                 • main без версий
```

⭐ Важное правило: **модуль не объявляет `provider` и `backend`** — их задаёт корневая
конфигурация. Иначе модуль невозможно переиспользовать в другом окружении/аккаунте.

Когда модуль не нужен:
- ресурс используется один раз и нигде больше;
- обёртка вокруг одного ресурса без добавленной ценности;
- «модуль ради модуля» усложняет чтение и отладку.

## 5. Типовая структура репозитория

```text:no-line-numbers
infra/
├── modules/                       ⭐ переиспользуемые модули
│   ├── network/
│   ├── compute/
│   ├── database/
│   └── k8s/
├── environments/
│   ├── prod/
│   │   ├── main.tf                вызовы модулей
│   │   ├── backend.tf             свой ключ стейта
│   │   ├── variables.tf
│   │   └── terraform.tfvars
│   ├── stage/
│   └── dev/
├── .gitlab-ci.yml
├── .gitignore
└── README.md
```

Альтернатива для больших инсталляций — вынести `modules/` в отдельный репозиторий
и подключать по git с тегами; тогда изменения модулей проходят собственный цикл ревью
и версионирования.

## 6. Рефакторинг: переезд ресурсов в модуль

При переносе ресурса в модуль его адрес меняется
(`yandex_vpc_network.this` → `module.network.yandex_vpc_network.this`),
и Terraform по умолчанию предложит **удалить и создать заново**.

```bash
# вариант 1: команда state mv
terraform state mv yandex_vpc_network.this module.network.yandex_vpc_network.this
```
```hcl
# вариант 2 (Terraform 1.1+): декларативный блок moved ⭐
moved {
  from = yandex_vpc_network.this
  to   = module.network.yandex_vpc_network.this
}
```
Блок `moved` лучше: он попадает в git, проходит ревью и работает у всех,
кто применяет код, а не только у того, кто выполнил команду.

## 7. Один интерфейс — два облака: модуль `network` для AWS и Yandex Cloud

Один модуль, который «сам» работает в обоих облаках, не получится: провайдер и типы ресурсов
разные, а `source` — **литерал**, его нельзя подставить из переменной. Рабочий приём —
**общий контракт** (одинаковые `variables.tf` и `outputs.tf`) и две реализации:

```text:no-line-numbers
modules/network/
├── aws/        main.tf (aws_vpc, aws_subnet, SG)       variables.tf  outputs.tf  versions.tf  tests/
└── yandex/     main.tf (yandex_vpc_*)                  variables.tf  outputs.tf  versions.tf  tests/
                        ▲ разное                        └────── одинаковое (контракт) ──────┘
```

```hcl
# контракт: variables.tf — копия в обеих реализациях
variable "name"  { type = string }
variable "env" {
  type = string
  validation {
    condition     = contains(["dev", "stage", "prod"], var.env)
    error_message = "env: dev, stage или prod."
  }
}
variable "cidr" {
  type    = string
  default = "10.20.0.0/16"
}
variable "zones" { type = list(string) }            # AWS: eu-central-1a…; Yandex: ru-central1-a… / kz1-a
variable "ssh_allowed_cidrs" {
  type    = list(string)
  default = []
  validation {
    condition     = !contains(var.ssh_allowed_cidrs, "0.0.0.0/0")
    error_message = "SSH из 0.0.0.0/0 запрещён."
  }
}

# контракт: outputs.tf — одинаковые имена и форма
output "network_id"   { value = ... }               # aws_vpc.this.id | yandex_vpc_network.this.id
output "subnet_ids"   { value = ... }               # { zone => id }
output "subnet_cidrs" { value = ... }               # { zone => cidr }
output "ssh_sg_id"    { value = ... }
```

```hcl
# modules/network/aws/main.tf
resource "aws_vpc" "this" {
  cidr_block           = var.cidr
  enable_dns_hostnames = true
  tags                 = { Name = "${var.name}-${var.env}", env = var.env }
}
resource "aws_subnet" "this" {
  for_each          = { for idx, z in var.zones : z => idx }
  vpc_id            = aws_vpc.this.id
  availability_zone = each.key
  cidr_block        = cidrsubnet(var.cidr, 8, each.value)
}
resource "aws_security_group" "ssh" {
  name   = "${var.name}-${var.env}-ssh"
  vpc_id = aws_vpc.this.id
}
resource "aws_vpc_security_group_ingress_rule" "ssh" {
  for_each          = toset(var.ssh_allowed_cidrs)
  security_group_id = aws_security_group.ssh.id
  ip_protocol       = "tcp"
  from_port         = 22
  to_port           = 22
  cidr_ipv4         = each.value
}
```
```hcl
# modules/network/yandex/main.tf
resource "yandex_vpc_network" "this" { name = "${var.name}-${var.env}" }
resource "yandex_vpc_subnet" "this" {
  for_each       = { for idx, z in var.zones : z => idx }
  name           = "${var.name}-${each.key}"
  zone           = each.key
  network_id     = yandex_vpc_network.this.id
  v4_cidr_blocks = [cidrsubnet(var.cidr, 8, each.value)]
}
resource "yandex_vpc_security_group" "ssh" {
  name       = "${var.name}-${var.env}-ssh"
  network_id = yandex_vpc_network.this.id
  dynamic "ingress" {
    for_each = length(var.ssh_allowed_cidrs) > 0 ? [1] : []
    content {
      protocol       = "TCP"
      port           = 22
      v4_cidr_blocks = var.ssh_allowed_cidrs
    }
  }
}
```

Вызов — корневая конфигурация окружения выбирает реализацию и провайдер:
```hcl
# environments/prod-aws/main.tf                      # environments/prod-kz/main.tf
module "network" {                                    # module "network" {
  source = "../../modules/network/aws"                #   source = "../../modules/network/yandex"
  name   = "linkd"                                    #   name   = "linkd"
  env    = "prod"                                     #   env    = "prod"
  zones  = ["eu-central-1a", "eu-central-1b"]         #   zones  = ["kz1-a"]   # одна зона в kz1
}                                                     # }
module "app" {
  source     = "../../modules/app/aws"
  subnet_ids = module.network.subnet_ids              # ⭐ потребитель знает только контракт
}
```

| Что унифицировать | Что НЕ унифицировать |
|-------------------|----------------------|
| Имена и типы входов, форма outputs | NAT, таблицы маршрутов, endpoints — у облаков разная модель |
| Валидации (env, запрет SSH из мира) | Экзотические фичи одного облака — отдельные входы реализации |
| Тесты контракта: одинаковые `run`-проверки на обе реализации | Внутренние имена ресурсов |

⭐ Обе реализации проверены `terraform test` с `mock_provider` — без облачных кредов,
[«Тестирование инфраструктурного кода»](/terraform/09-testing), §4. Реализация `aws/` может внутри вызывать публичный
`terraform-aws-modules/vpc/aws` (`~> 6.7`), сохраняя свой контракт; для Yandex обычно свой код.
Казахстанские OpenStack-облака (PS Cloud) — третья реализация на провайдере `openstack`.

## 8. Публичные модули: пользоваться или нет

| За | Против |
|----|--------|
| Быстрый старт, покрыты best practices | Много «лишних» возможностей и абстракций |
| Поддерживаются сообществом | Обновления могут менять поведение |
| Экономят время на типовых задачах | Сложно понять, что реально создаётся |

Практика: смотреть популярные модули как **образец**, брать в работу — с фиксированной
версией и после чтения кода; для Yandex Cloud и локальных облаков, где модулей в registry
мало, чаще пишут свои.

## 9. Грабли

| Грабля | Последствие | Решение |
|--------|-------------|---------|
| `source` из git без `ref` | План меняется «сам» после чужого коммита | Фиксировать тег/коммит |
| `provider`/`backend` внутри модуля | Модуль нельзя переиспользовать | Только в корневой конфигурации |
| Мега-модуль на всё | Не переиспользуется, страшный plan | Делить по зонам ответственности |
| Модуль без outputs | Приходится лезть внутрь, связность растёт | Явный интерфейс |
| Переезд в модуль без `moved`/`state mv` | Пересоздание ресурсов ⚠️ | Блок `moved` |
| Нет README и примера | Никто не может использовать | Документировать интерфейс |
| Глубокая вложенность модулей | Невозможно отладить | Максимум 2-3 уровня |
| Разные версии модуля в окружениях | Stage ≠ prod | Единая версия и осознанное обновление |
| «Универсальный» модуль с `count` на каждый ресурс по флагу `cloud` | Нужны оба провайдера и креды всегда, план нечитаем | Общий контракт + отдельные реализации `aws/`, `yandex/` |
| Реализации контракта разъехались (разные имена outputs) | Потребители ломаются при смене облака | Одинаковые тесты контракта на обе реализации |

## 💼 Как это в DevOps

- Типичный рабочий процесс: общие модули компании лежат в отдельном репозитории
  с тегами; окружения подключают их по версии и отличаются только значениями переменных.
- Обновление модуля — отдельный MR: сначала на dev/stage, потом на prod,
  с просмотром плана на каждом шаге.
- README модуля с таблицей переменных и примером вызова — обязательный артефакт;
  часто генерируется `terraform-docs` автоматически в CI.
- Модули позволяют команде разработки создавать инфраструктуру самостоятельно:
  «вот модуль сервиса, заполните три переменные».
- Рефакторинг с `moved` — то, что отличает аккуратную команду: он не создаёт простоя.
- Гибрид «ПДн в Казахстане, остальное в AWS» — типовой повод для контракта модулей:
  `environments/prod-aws` и `environments/prod-kz` вызывают одинаковые интерфейсы
  с разными реализациями, у каждого свой стейт и пайплайн.
- Модуль компании без тестов — не релиз: `terraform test` с моками в CI на каждый MR
  в репозиторий модулей ([«Тестирование инфраструктурного кода»](/terraform/09-testing)).

## 📌 Шпаргалка

| Хочу | Как |
|------|-----|
| Создать модуль | Каталог с `main.tf`, `variables.tf`, `outputs.tf`, README |
| Вызвать модуль | `module "name" { source = "...", ... }` |
| Получить значение из модуля | `module.name.output_name` |
| Модуль из git с версией | `source = "git::...//path?ref=v1.2.0"` |
| Модуль из реестра | `source = "org/name/provider"` + `version` |
| Много экземпляров модуля | `for_each` у блока `module` |
| Передать другой провайдер | `providers = { aws = aws.secondary }` |
| Перенести ресурс в модуль без пересоздания | блок `moved` (или `state mv`) |
| Обновить модуль | Поднять `ref`/`version`, посмотреть план |
| Документировать | `terraform-docs markdown . > README.md` |
| Один модуль для AWS и Yandex | Контракт (`variables.tf` + `outputs.tf`) и реализации `modules/network/{aws,yandex}` |
| Регион/аккаунт AWS для модуля | `providers = { aws = aws.eu_west }` |

## 🧠 Что запомнить

1. Модуль — каталог с конфигурацией, у которого есть входы и выходы; корневая
   конфигурация тоже модуль.
2. Модули убирают копипасту между окружениями и делают их одинаковыми by design.
3. Наружу модуль отдаёт только `output` — это его интерфейс.
4. ⭐ Модуль не объявляет `provider` и `backend`: это дело корневой конфигурации.
5. Модули из git подключают строго с `?ref=тег`, из реестра — с `version`.
6. `for_each` на блоке `module` создаёт несколько экземпляров одного модуля.
7. Хороший модуль решает одну задачу, имеет разумные умолчания и README.
8. Перенос ресурсов в модуль делают через блок `moved`, иначе будет пересоздание.
9. Глубокая вложенность модулей усложняет отладку — ограничивайся 2-3 уровнями.
10. Публичные модули полезны как образец; в работу берут с фиксированной версией
    и после чтения кода.
11. Для двух облаков делают не «универсальный» модуль, а общий контракт входов/выходов
    и отдельные реализации; `source` — литерал, реализацию выбирает окружение.

### Блок A. Теория

**A1.** Что такое модуль в Terraform? Является ли им корневая конфигурация?

<details><summary>Ответ</summary>

Каталог с конфигурацией Terraform, имеющий входы (`variable`) и выходы (`output`).
Да, корневая конфигурация — это root module.

</details>

**A2.** Какую проблему решают модули?

<details><summary>Ответ</summary>

Дублирование кода между окружениями и компонентами, расхождение окружений,
сложность поддержки и ревью.

</details>

**A3.** Из каких файлов обычно состоит модуль?

<details><summary>Ответ</summary>

`main.tf`, `variables.tf`, `outputs.tf`, `versions.tf` и README
(при необходимости — `locals.tf`, шаблоны).

</details>

**A4.** Как получить значение из модуля? Можно ли обратиться к его ресурсу напрямую?

<details><summary>Ответ</summary>

Через `module.<имя>.<output>`. Напрямую к внутренним ресурсам обращаться нельзя —
модуль инкапсулирует их.

</details>

**A5.** Какие бывают источники модулей (`source`)?

<details><summary>Ответ</summary>

Локальный путь, git (https/ssh) с поддиректорией и `ref`, публичный
Terraform Registry, приватный реестр, архив по URL.

</details>

**A6.** ⭐ Почему модуль из git обязательно подключают с `ref`?

<details><summary>Ответ</summary>

Без `ref` берётся текущее состояние ветки: чужой коммит изменит поведение
твоей инфраструктуры без изменения твоего кода — план станет непредсказуемым.

</details>

**A7.** Почему модуль не должен объявлять `provider` и `backend`?

<details><summary>Ответ</summary>

Провайдеры и backend — свойства корневой конфигурации. Если модуль их объявляет,
его нельзя использовать в другом аккаунте/регионе/окружении и нельзя вызывать
несколько раз с разными провайдерами.

</details>

**A8.** Как создать несколько экземпляров одного модуля?

<details><summary>Ответ</summary>

`for_each` (или `count`) на блоке `module`; адресация —
`module.name["key"].output`.

</details>

**A9.** Как передать модулю альтернативный провайдер и зачем это нужно?

<details><summary>Ответ</summary>

Через `providers = { yandex = yandex.secondary }` (Yandex: другой каталог/облако)
или `providers = { aws = aws.eu_west }` (AWS: другой регион/аккаунт через `alias`
и `assume_role`). Нужно, когда модуль должен создавать ресурсы в другом регионе/аккаунте —
например, реплика бакета бэкапов в соседнем регионе AWS.

</details>

**A10.** Признаки хорошего и плохого модуля — назови по три.

<details><summary>Ответ</summary>

Хороший: одна зона ответственности, понятный интерфейс с умолчаниями,
README и версионирование. Плохой: делает всё сразу, десятки обязательных переменных,
нет outputs, объявляет провайдеры, не версионируется.

</details>

**A11.** Когда модуль не нужен?

<details><summary>Ответ</summary>

Когда ресурс используется один раз, когда модуль — тонкая обёртка вокруг
одного ресурса без добавленной ценности, когда он усложняет чтение.

</details>

**A12.** ⭐ Что произойдёт при переносе ресурса в модуль без дополнительных действий?

<details><summary>Ответ</summary>

Изменится адрес ресурса, и Terraform предложит удалить старый и создать новый —
то есть пересоздание (опасно для данных).

</details>

**A13.** Чем блок `moved` лучше команды `state mv`?

<details><summary>Ответ</summary>

`moved` хранится в коде, проходит ревью и срабатывает у всех, кто применяет
конфигурацию; `state mv` выполняется однократно и вручную конкретным человеком.

</details>

**A14.** Как организовать репозиторий инфраструктуры с окружениями и модулями?

<details><summary>Ответ</summary>

`modules/` с переиспользуемыми модулями и `environments/{dev,stage,prod}`
с вызовами и своими backend-ключами; при росте — модули в отдельном репозитории
с тегами.

</details>

**A15.** Стоит ли использовать публичные модули? При каких условиях?

<details><summary>Ответ</summary>

Да, если зафиксирована версия, код прочитан и модуль реально экономит время.
Как минимум их полезно изучать как образец.

</details>

### Блок B. «Оцени решение»

```hcl
B1.  module "network" { source = "git::https://gitlab.com/org/tf.git//network" }   # без ref
B2.  module "network" { source = "git::https://gitlab.com/org/tf.git//network?ref=v1.4.0" }
B3.  # внутри modules/network/main.tf:
     provider "yandex" { token = var.token }
B4.  # внутри modules/network/backend.tf:
     terraform { backend "s3" { ... } }
B5.  module "everything" { source = "./modules/all-infra" }   # 1 модуль на всю инфраструктуру
B6.  modules/network без outputs, окружение лезет в module.network.yandex_vpc_subnet...
B7.  module "app" { for_each = var.services, source = "./modules/app" }
B8.  moved { from = yandex_vpc_network.this, to = module.network.yandex_vpc_network.this }
B9.  prod использует модуль v1.2.0, stage — v1.7.0
B10. В модуле 60 переменных, 45 из них без default
B11. Модуль есть, README нет
B12. Вложенность модулей: env → platform → service → base → primitives (5 уровней)
```

<details><summary>Ответ</summary>

**B1.** Нет версии — непредсказуемые изменения.
**B2.** Правильный вариант.
**B3.** Провайдер внутри модуля — антипаттерн.
**B4.** Backend внутри модуля — модуль становится непереиспользуемым.
**B5.** Мега-модуль не даёт переиспользования и делает планы рискованными.
**B6.** Нет интерфейса: обращение к внутренним ресурсам ломает инкапсуляцию
(и формально невозможно — потребуется output).
**B7.** Нормальный приём для набора однотипных сервисов.
**B8.** Корректный рефакторинг без пересоздания.
**B9.** Разные версии = разные окружения; stage перестаёт быть репетицией прода.
**B10.** Слишком много обязательных входов — модулем невозможно пользоваться.
**B11.** Без README модуль не используется другими.
**B12.** Чрезмерная вложенность: невозможно отлаживать и читать планы.

</details>

### Блок C. Практика

#### C1. 🔑 Первый модуль
Вынеси код из предыдущих лаб (например, «сеть + контейнер») в модуль:
`modules/web/` с переменными `name`, `image`, `port` и выходом `url`.
Вызови его из корневой конфигурации.

#### C2. Несколько экземпляров
Вызови свой модуль три раза с разными параметрами (три сервиса с разными портами).
Затем перепиши на `for_each` по map и сравни код.

#### C3. Композиция модулей
Сделай два модуля: `network` (создаёт docker-сеть) и `app` (создаёт контейнер в сети).
Передай выход первого во вход второго. Посмотри, как Terraform строит порядок.

#### C4. Интерфейс модуля
1. Добавь в модуль переменные с `description`, типами, умолчаниями и валидацией.
2. Добавь осмысленные `output`.
3. Напиши README с таблицей переменных и примером вызова
   (попробуй `terraform-docs`, если есть).

#### C5. 🔑 Модуль из git
1. Вынеси модуль в отдельный репозиторий, поставь тег `v1.0.0`.
2. Подключи его по `source = "git::...?ref=v1.0.0"`.
3. Внеси изменение, поставь `v1.1.0`, обнови ссылку и посмотри план.
4. Попробуй без `ref` и объясни риск.

<details><summary>Ответ</summary>

Без `ref` `terraform init` подтянет актуальную ветку — поведение может
измениться без изменения твоего кода.

</details>

#### C6. Рефакторинг с `moved`
1. Создай ресурс в корневой конфигурации, примени.
2. Перенеси его в модуль и выполни `plan` — увидь предложение пересоздать.
3. Добавь блок `moved`, снова `plan` — изменений быть не должно.

<details><summary>Ответ</summary>

После добавления `moved` план должен стать пустым.

</details>

#### C7. Окружения
Собери структуру `environments/{dev,stage,prod}`, вызывающую одни и те же модули
с разными переменными и разными ключами стейта. Примени dev.

<details><summary>Ответ</summary>

Разные ключи стейта обязательны: иначе окружения перепишут состояние друг друга.

</details>

#### C8. Передача провайдера
Сделай модуль, который создаёт ресурсы в «другом регионе» через переданный
`providers = { ... }` (или второй docker-хост, если есть).

#### C9. Публичный модуль
Найди в реестре модуль для интересующей тебя задачи, прочитай его входы/выходы
и оцени: взял бы ты его в работу? Почему?

#### C10. Обновление модуля по окружениям
Смоделируй процесс: изменение в модуле → тег → обновление в dev → проверка плана →
обновление stage → prod. Запиши регламент в README репозитория.

<details><summary>Ответ</summary>

Разумный регламент: изменение → тег → dev → stage → prod, с просмотром плана
на каждом шаге и возможностью отката по версии.

</details>

#### C11. 🔑 Контракт `network` для AWS и Yandex Cloud
1. Сделай `modules/network/aws` и `modules/network/yandex` с **одинаковыми**
   `variables.tf` (`name`, `env`, `cidr`, `zones`, `ssh_allowed_cidrs`) и `outputs.tf`
   (`network_id`, `subnet_ids`, `subnet_cidrs`, `ssh_sg_id`) — конспект, §7.
2. Вызови обе реализации из `environments/dev-aws` и `environments/dev-kz` (`zones = ["kz1-a"]`).
3. Напиши один набор `run`-проверок (`tests/contract.tftest.hcl` с `mock_provider`)
   и положи копию в обе реализации — `terraform test` должен проходить без облачных кредов
   ([«Тестирование инфраструктурного кода»](/terraform/09-testing)).
4. Переименуй output в одной реализации — убедись, что тест ловит расхождение контракта.

<details><summary>Ответ</summary>

Реализацию нельзя выбрать переменной (`source` — литерал), поэтому выбор делает
корневая конфигурация окружения. Тест контракта с `mock_provider "aws"` / `mock_provider
"yandex"` проверяет CIDR подсетей (`plan`), отказ при SSH из `0.0.0.0/0`
(`expect_failures = [var.ssh_allowed_cidrs]`) и наличие outputs после мок-`apply`;
переименованный output даёт ошибку `Reference to undeclared output value`.

</details>

#### C12. AWS-вариант C9: публичный модуль VPC
1. Подключи `terraform-aws-modules/vpc/aws` с `version = "~> 6.7"` (2 AZ, `single_nat_gateway`).
2. Выполни `terraform init` и найди в `.terraform/modules/` его код: сколько ресурсов он
   создаёт при твоих входах (`terraform plan | grep "will be created" | wc -l`)?
3. Оберни его в свою реализацию `modules/network/aws` так, чтобы контракт из C11 не изменился.
4. Реши: что лучше для твоей команды — обёртка над публичным модулем или свой код?

<details><summary>Ответ</summary>

Публичный модуль при таких входах создаёт около двух десятков ресурсов (VPC, подсети,
route tables и ассоциации, IGW, EIP, NAT…) — больше, чем кажется по вызову. Обёртка даёт
best practices сообщества и свой стабильный контракт; платишь чтением чужого кода
и мажорными обновлениями (переход 5 → 6 потребовал провайдер aws 6.x — читай CHANGELOG).

</details>

### Блок D. Инциденты

**D1.** После `terraform init` план внезапно показывает изменения, хотя код не менялся.
Причина?

<details><summary>Ответ</summary>

Обновилась версия модуля (нет `ref`/`version`) или провайдера
(не закоммичен lock-файл).

</details>

**D2.** Один и тот же модуль в prod и stage ведёт себя по-разному. Гипотезы?

<details><summary>Ответ</summary>

Разные версии модуля, разные значения переменных, ручные правки в одном
из окружений, разные версии провайдеров.

</details>

**D3.** Модуль пересоздал всю сеть при обновлении версии. Что нужно было сделать?

<details><summary>Ответ</summary>

Изучить план до применения; при переименованиях/переносах добавить блоки `moved`;
обновлять версию сначала на dev/stage.

</details>

**D4.** Невозможно использовать модуль во втором облачном аккаунте. Что в нём не так?

<details><summary>Ответ</summary>

В модуле объявлен `provider` (и, возможно, backend) с захардкоженными
параметрами; нужно вынести их в корневую конфигурацию и принимать провайдер извне.

</details>

**D5.** Разработчики не могут воспользоваться модулем: непонятно, что заполнять.
Что исправить?

<details><summary>Ответ</summary>

Нет README, описаний и умолчаний; добавить документацию, `description`,
разумные `default`, пример вызова.

</details>

**D6.** Переименовали модуль — Terraform предлагает удалить 40 ресурсов. Решение?

<details><summary>Ответ</summary>

Добавить блоки `moved` для всех адресов (или выполнить `state mv`).

</details>

**D7.** Изменение в общем модуле сломало три команды одновременно. Как выстроить процесс?

<details><summary>Ответ</summary>

Версионирование модулей тегами, обновление по окружениям, CHANGELOG,
ревью MR в репозитории модулей, тестовые прогоны плана.

</details>

**D8.** В модуле обнаружили `provider` с захардкоженным регионом. Чем это грозит?

<details><summary>Ответ</summary>

Модуль нельзя использовать в другом регионе/аккаунте; ресурсы могут быть созданы
не там, где ожидается.

</details>

**D9.** План стал очень долгим после перехода на модули. Что проверить?

<details><summary>Ответ</summary>

Слишком много ресурсов в одном стейте, глубокая вложенность модулей,
избыточные `data`-запросы, большое число экземпляров модуля; разделить стейты
и упростить структуру.

</details>

**D10.** Нужно откатить версию модуля после неудачного обновления. Как это сделать
и что проверить?

<details><summary>Ответ</summary>

Вернуть предыдущий `ref`/`version`, выполнить `plan` и внимательно проверить,
что откат не приводит к пересозданию/удалению данных; при необходимости —
частичный откат и ручные шаги.

</details>
