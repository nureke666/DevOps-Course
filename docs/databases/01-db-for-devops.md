# 01. База данных глазами DevOps

> Роадмап → 7. Остальное → Базы: *«DevOps не так часто пишет SQL-запросы. Но DevOps поднимает
> базу, настраивает репликацию, делает бэкапы, восстанавливает после аварии, мониторит производительность.»*
>
> **После темы ты умеешь:** объяснить, какие бывают базы и зачем, что такое транзакция,
> ACID и индекс, где у базы «болит» и за что в ней отвечаешь именно ты.

---

## 🗺️ Идея: где база в архитектуре

```text:no-line-numbers
   пользователи
        │
   ┌────▼────┐   stateless: можно убить и поднять заново
   │  nginx  │   ─────────────────────────────────────────
   └────┬────┘
   ┌────▼────┐  ┌─────────┐  ┌─────────┐   приложение в 10 репликах —
   │  app-1  │  │  app-2  │  │  app-3  │   и это никого не пугает
   └────┬────┘  └────┬────┘  └────┬────┘
        └───────────┬┴────────────┘
                    ▼
            ┌───────────────┐   stateful: ЗДЕСЬ ЛЕЖАТ ДАННЫЕ
            │  PostgreSQL   │   ─────────────────────────────
            │   + диск 💾   │   потеряли → бизнес встал
            └───────────────┘   (и это уже не «перезапустим под»)
```

**Вся разница между приложением и базой — в одном слове: состояние.**
Приложение можно пересоздать из образа. Базу — только из бэкапа.
Отсюда весь список обязанностей девопса: диск, бэкап, реплика, мониторинг.

## 1. Какие бывают базы (и что из этого в стеке проекта)

| Тип | Представитель | Модель данных | Когда берут |
|-----|---------------|---------------|-------------|
| Реляционная (SQL) | **PostgreSQL**, MySQL | Таблицы, строки, связи | Основные данные: пользователи, заказы, деньги |
| Key-value | **Redis** | ключ → значение, в памяти | Кэш, сессии, счётчики, блокировки, простые очереди |
| Документная | **MongoDB** | JSON-документы | Разнородные данные без жёсткой схемы |
| Колоночная | **ClickHouse** | Колонки, сжатие | Аналитика, логи, метрики: «посчитать по 500 млн строк» |
| Time-series | Prometheus TSDB, VictoriaMetrics | метрика+время | Мониторинг (см. раздел «Мониторинг») |
| Поисковая | Elasticsearch | Инвертированный индекс | Поиск и логи (см. раздел «Логирование») |

> 💡 Типовой стек проекта: **PostgreSQL** (данные) + **Redis** (кэш/сессии) +
> иногда **ClickHouse** (аналитика/логи) + **Kafka** (события).
> То есть баз на проекте почти всегда **несколько**, и они решают разные задачи.

### Строчное vs колоночное хранение — почему ClickHouse быстрый

```text:no-line-numbers
Строчное (PostgreSQL)            Колоночное (ClickHouse)
[id=1,name=Иван,city=Алматы]     id:    [1,2,3,...]
[id=2,name=Пётр,city=Астана]     name:  [Иван,Пётр,...]
[id=3,name=Анна,city=Алматы]     city:  [Алматы,Астана,Алматы,...]

«дай мне всю строку по id»       «посчитай count по city по 500 млн строк»
= 1 чтение, очень быстро         = читаем ТОЛЬКО колонку city, она ещё и сжата
```

Не «ClickHouse лучше Postgres», а **разные задачи**: OLTP (много мелких операций)
против OLAP (мало тяжёлых аналитических запросов).

## 2. Транзакция и ACID

**Транзакция** — набор операций, который выполняется целиком или не выполняется вообще.

```sql
BEGIN;
UPDATE accounts SET balance = balance - 100 WHERE id = 1;   -- списали
UPDATE accounts SET balance = balance + 100 WHERE id = 2;   -- зачислили
COMMIT;              -- обе операции зафиксированы
-- ROLLBACK;         -- или обе отменены; «списали, но не зачислили» невозможно
```

| Буква | Что значит | На практике |
|-------|------------|-------------|
| **A** Atomicity | Всё или ничего | Упало посередине → откат |
| **C** Consistency | Данные не нарушают правила | Constraints, foreign keys |
| **I** Isolation | Транзакции не мешают друг другу | Уровни изоляции, блокировки |
| **D** Durability | Зафиксировано = переживёт выключение питания | ⭐ **Это про WAL и `fsync`** |

> ⭐ Девопсу важнее всего **D**. Именно за durability отвечает WAL (журнал),
> и именно его ломают, когда «для скорости» выключают `fsync` или ставят базу
> на сетевой диск с кэшированием. Итог — потеря данных при внезапном ребуте.

### Зачем девопсу знать про блокировки

```text:no-line-numbers
Транзакция A: BEGIN; UPDATE users SET ... WHERE id=1;   ← держит блокировку
Транзакция B: UPDATE users SET ... WHERE id=1;          ← ЖДЁТ
Транзакция A: ...забыла COMMIT (idle in transaction)

Итог: B висит, за ней висят ещё 200 соединений, приложение «тормозит»,
      на графике — рост соединений и время ответа, а база «ничего не делает».
```

Это классический инцидент: причина не в «медленной базе», а в долгой транзакции.
Смотрят в `pg_stat_activity` (тема 07).

## 3. Индексы — минимум, который нужен

**Индекс** — отдельная структура (чаще B-tree), которая позволяет найти строки,
не читая всю таблицу.

```text:no-line-numbers
БЕЗ индекса: Seq Scan            С индексом: Index Scan
прочитать все 10 000 000 строк   спуститься по дереву за ~4 чтения
= 8 секунд                       = 0,2 мс
```

```sql
CREATE INDEX idx_users_email ON users(email);   -- обычный
CREATE UNIQUE INDEX ... ;                        -- плюс уникальность
CREATE INDEX CONCURRENTLY ...;                   -- ⭐ без блокировки таблицы (в проде только так)
```

Что девопсу важно понимать про индексы:

| Факт | Последствие для тебя |
|------|----------------------|
| Индексы занимают **место на диске** | Диск под базой растёт не только от данных |
| Индексы замедляют `INSERT/UPDATE` | «Ускорили чтение» = «замедлили запись» |
| Индексы живут в памяти (кэше) | Нехватка RAM → чтение с диска → тормоза |
| `CREATE INDEX` без `CONCURRENTLY` блокирует запись | Миграция в прайм-тайм = инцидент |
| Неиспользуемые индексы — мусор | Их находят через `pg_stat_user_indexes` |

Смотреть, использовался ли индекс, — `EXPLAIN` (тема 08).

## 4. Как база устроена внутри (уровень «достаточно девопсу»)

```text:no-line-numbers
  клиент (psql/приложение)
        │  TCP 5432
        ▼
 ┌──────────────────────────────────────────────────────────┐
 │ PostgreSQL                                               │
 │  postmaster ──fork──► backend-процесс на КАЖДОЕ соединение│ ← отсюда max_connections
 │                                                          │
 │  ┌──────────────┐   читает/пишет страницы по 8 КБ        │
 │  │shared_buffers│ ◄── кэш данных в RAM                   │
 │  └──────┬───────┘                                        │
 │         │ грязные страницы                               │
 │         ▼                                                │
 │  ┌──────────────┐  сначала пишем В ЖУРНАЛ, потом в данные│
 │  │   WAL (pg_wal)│ ── fsync ──► durability ⭐             │
 │  └──────┬───────┘                                        │
 │         ▼                                                │
 │  checkpointer ──► файлы данных (base/)                   │
 │  autovacuum ────► чистит «мёртвые» версии строк          │
 └──────────────────────────────────────────────────────────┘
                       │
                       ▼ диск 💾 (и его свободное место — твой алерт №1)
```

Три вещи, которые отсюда нужно запомнить:

1. **Соединение = процесс.** Поэтому 1000 соединений от приложения — это боль,
   и поэтому существует PgBouncer.
2. **WAL пишется раньше данных.** Поэтому возможны репликация и PITR (темы 05, 06).
3. **MVCC:** `UPDATE` не меняет строку на месте, а создаёт новую версию, старая помечается
   мёртвой. Убирает мусор autovacuum. Отключил/не справляется → **раздувание (bloat)**
   и «база растёт, хотя данных столько же».

## 5. Жизненный цикл базы: за что отвечаешь ты

```text:no-line-numbers
  [1] поднять ──► [2] дать доступ ──► [3] настроить ──► [4] бэкапить
        ▲                                                    │
        │                                                    ▼
  [7] обновить версию ◄── [6] мониторить ◄── [5] отреплицировать
```

| Шаг | Что делаешь | Тема |
|-----|-------------|------|
| 1 | Ставишь PG, выбираешь версию, диск, ресурсы | 02 |
| 2 | `pg_hba.conf`, роли, пароли, `GRANT` | 03 |
| 3 | `postgresql.conf`: память, соединения, логи, autovacuum | 04 |
| 4 | Бэкап + **тестовое восстановление** + RPO/RTO | 05 ⭐ |
| 5 | Реплика для отказоустойчивости и чтения | 06 |
| 6 | Метрики, дашборд, алерты | 07 |
| 7 | Мажорное обновление (`pg_upgrade`), миграции разработчиков | 02, 05 |

## 6. Где живёт база: VM / Docker / Kubernetes / Managed

| Вариант | Плюсы | Минусы | Когда |
|---------|-------|--------|-------|
| **VM (пакетом)** | Классика, предсказуемо, все гайды про это | Всё руками: бэкап, реплика, апгрейд | Дефолт для прода на своих серверах |
| **Docker** | Быстро поднять, идеально для учёбы/дева | Данные только в volume; в проде спорно | Локалка, dev, тесты |
| **Kubernetes** | Единая платформа, оператор (CloudNativePG, Zalando) | Сложнее, нужен нормальный storage | Зрелые команды с оператором |
| **Managed (облако)** | Бэкапы, реплики, апгрейды — не твоя боль | Дороже, меньше контроля, версии отстают | ⭐ Часто лучший выбор, см. раздел «Облака» |

> 💡 Хороший ответ на собесе: *«Базу в k8s кладут только с оператором и понятным storage.
> Иначе — VM или managed. Данные не любят экспериментов.»*

## 7. Типовые грабли

| Грабля | Что происходит | Как правильно |
|--------|----------------|---------------|
| Бэкап есть, восстановление не проверяли | Авария → дамп битый/неполный | Регулярное тестовое восстановление |
| Реплику считают бэкапом | `DROP TABLE` приехал на реплику за 1 сек | Реплика — про доступность, бэкап — про ошибки |
| Диск кончился | База встала, иногда не стартует | Алерт на 80% и на рост `pg_wal` |
| `max_connections=1000` «на всякий» | 1000 процессов съели RAM → OOM | PgBouncer + разумный лимит |
| `shared_buffers` = вся RAM | Двойное кэширование, своп | ~25% RAM (тема 04) |
| Autovacuum «мешает», отключили | Bloat, транзакционное переполнение | Настраивать, а не отключать |
| Пароль/доступ `0.0.0.0/0 trust` | База в интернете без пароля | `pg_hba.conf` + firewall (тема 03) |
| Мажорный апгрейд «на живую» | Несовместимость форматов, простой | `pg_upgrade`, тест на копии, окно |

## 💼 Как это в DevOps

- **Дежурство:** «приложение тормозит» → первым делом смотришь базу: соединения,
  долгие запросы, `idle in transaction`, место на диске, лаг репликации.
- **Релиз:** миграции разработчиков едут в CI/CD. Твоя задача — чтобы миграция не
  заблокировала таблицу на 10 минут в прайм-тайм и чтобы перед ней был свежий бэкап.
- **Новый сервис:** «нам нужна база» → поднять, выдать креды через Vault
  (см. раздел «Vault»), завести бэкап и мониторинг **сразу**, а не потом.
- **Инцидент «удалили данные»:** порядок — остановить запись → понять момент времени →
  восстановить из бэкапа/PITR → сверить → включить. Это тема 05.
- **Собес:** про базы девопса спрашивают не SQL, а **эксплуатацию**: бэкап, реплика,
  мониторинг, что делать при «база тормозит».

## 📌 Шпаргалка

| Термин | Смысл одной строкой |
|--------|---------------------|
| OLTP | Много коротких операций (обычное приложение) — PostgreSQL |
| OLAP | Аналитика по большим объёмам — ClickHouse |
| Транзакция | Всё или ничего (`BEGIN … COMMIT/ROLLBACK`) |
| ACID | Атомарность, согласованность, изоляция, долговечность |
| WAL | Журнал: сначала пишем туда, потом в данные; основа PITR и репликации |
| MVCC | Версии строк вместо блокировок на чтение |
| Autovacuum | Уборщик мёртвых версий строк |
| Bloat | Раздувание таблиц/индексов от мёртвых версий |
| Индекс | Структура для быстрого поиска; ускоряет чтение, замедляет запись |
| Seq Scan / Index Scan | Полный проход / поиск по индексу (видно в `EXPLAIN`) |
| Репликация | Копия базы, применяющая WAL основной |
| PITR | Восстановление на момент времени (базовая копия + WAL) |
| RPO / RTO | Сколько данных допустимо потерять / за сколько восстановиться |
| Connection pooling | PgBouncer между приложением и базой |

## 🧠 Что запомнить

1. База — единственная по-настоящему **stateful** часть системы; отсюда все обязанности девопса.
2. На проекте почти всегда несколько баз: PostgreSQL для данных, Redis для кэша,
   ClickHouse/Elastic для аналитики и логов.
3. Транзакция — «всё или ничего»; из ACID девопсу важнее всего **D** (durability = WAL + fsync).
4. Долгая транзакция (`idle in transaction`) — типовая причина «база тормозит».
5. Индексы ускоряют чтение, замедляют запись и занимают диск; в проде — `CREATE INDEX CONCURRENTLY`.
6. Соединение в PostgreSQL = отдельный процесс → нужен PgBouncer, а не `max_connections=1000`.
7. MVCC + autovacuum: `UPDATE` создаёт новую версию строки, autovacuum убирает старые.
8. ⭐ Реплика — не бэкап. Бэкап без проверенного восстановления — тоже не бэкап.
9. Базу в Kubernetes кладут только с оператором; иначе VM или managed-сервис.
10. Первый алерт по базе, который надо настроить, — **свободное место на диске**.

### Блок A. Теория

**A1.** Чем база принципиально отличается от приложения с точки зрения эксплуатации?

<details><summary>Ответ</summary>

База — stateful: в ней данные, которые нельзя пересоздать из образа. Приложение
можно убить и поднять заново, базу — только восстановить из бэкапа. Отсюда требования
к диску, бэкапам, репликации и мониторингу.

</details>

**A2.** Назови пять типов баз и по одному представителю каждого. Для чего берут каждый?

<details><summary>Ответ</summary>

Реляционные (PostgreSQL) — основные данные; key-value (Redis) — кэш, сессии,
счётчики; документные (MongoDB) — данные без жёсткой схемы; колоночные (ClickHouse) —
аналитика и логи; time-series (Prometheus/VictoriaMetrics) — метрики;
поисковые (Elasticsearch) — поиск и логи.

</details>

**A3.** Почему ClickHouse быстро считает агрегаты по сотням миллионов строк, а PostgreSQL нет?

<details><summary>Ответ</summary>

Колоночное хранение: для агрегата читается только нужная колонка (а не все строки
целиком), и она хорошо сжимается. PostgreSQL хранит строки целиком — для аналитики
приходится поднимать с диска много лишнего.

</details>

**A4.** Что такое транзакция? Приведи пример, где без неё ломаются данные.

<details><summary>Ответ</summary>

Набор операций, выполняющийся целиком или не выполняющийся вовсе. Пример: перевод
денег — списание и зачисление должны быть атомарны, иначе деньги исчезнут.

</details>

**A5.** Расшифруй ACID. Какая буква важнее всего девопсу и почему?

<details><summary>Ответ</summary>

Atomicity, Consistency, Isolation, Durability. Девопсу важнее **Durability**:
за неё отвечают WAL и `fsync`, и именно её ломают «оптимизациями» и сетевыми дисками
с ненадёжным кэшем.

</details>

**A6.** Что такое WAL и как он связан с durability, репликацией и PITR?

<details><summary>Ответ</summary>

Write-Ahead Log: любое изменение сначала записывается в журнал и сбрасывается на
диск, потом применяется к файлам данных. Даёт восстановление после сбоя (durability),
физическую репликацию (реплика применяет WAL) и PITR (базовая копия + WAL до нужного момента).

</details>

**A7.** Что такое MVCC и зачем при нём нужен autovacuum?

<details><summary>Ответ</summary>

MVCC — многоверсионность: `UPDATE`/`DELETE` не меняют строку на месте, а создают
новую версию, старая помечается мёртвой. Читатели не блокируют писателей. Мёртвые версии
накапливаются — их убирает autovacuum, возвращая место для переиспользования.

</details>

**A8.** Что такое bloat и откуда он берётся?

<details><summary>Ответ</summary>

Раздувание: таблица/индекс занимают намного больше места, чем реальные данные,
из-за накопленных мёртвых версий строк. Причины — не справляющийся autovacuum,
массовые `UPDATE`/`DELETE`, долгие транзакции, удерживающие «горизонт».

</details>

**A9.** Индекс ускоряет чтение. Назови три вещи, которые он при этом ухудшает.

<details><summary>Ответ</summary>

Занимает место на диске; замедляет `INSERT/UPDATE/DELETE` (индекс тоже надо
обновлять); требует памяти под кэш; плюс неиспользуемые индексы — чистый мусор.

</details>

**A10.** Почему в проде индекс создают через `CREATE INDEX CONCURRENTLY`?

<details><summary>Ответ</summary>

Обычный `CREATE INDEX` берёт блокировку, запрещающую запись в таблицу на всё
время построения (на большой таблице — минуты и часы). `CONCURRENTLY` строит индекс
без блокировки записи: дольше, но прод живёт. Минус — не работает внутри транзакции
и может оставить «невалидный» индекс при сбое.

</details>

**A11.** Почему большое `max_connections` в PostgreSQL — плохая идея? Что используют вместо этого?

<details><summary>Ответ</summary>

Каждое соединение — отдельный процесс со своей памятью (плюс `work_mem` на
операцию). Тысячи процессов съедают RAM и CPU на переключения, растёт риск OOM.
Вместо этого ставят пул соединений — PgBouncer — и держат `max_connections` разумным
(обычно 100-500).

</details>

**A12.** ⭐ Почему реплика не является бэкапом? Приведи сценарий, где реплика не спасёт.

<details><summary>Ответ</summary>

Реплика повторяет **всё**, включая ошибки: `DROP TABLE`, `DELETE FROM`, кривую
миграцию, шифровальщика. Через секунду это уже на реплике. Реплика защищает от отказа
сервера, бэкап — от ошибок людей и приложений. Нужны оба.

</details>

**A13.** Сравни варианты размещения базы: VM, Docker, Kubernetes, managed. Когда какой?

<details><summary>Ответ</summary>

VM — предсказуемо, дефолт для своего железа, всё руками. Docker — учёба/dev,
быстро поднять. Kubernetes — только с оператором (CloudNativePG, Zalando) и нормальным
storage, требует зрелости команды. Managed — бэкапы/реплики/апгрейды на стороне облака,
дороже и меньше контроля; часто лучший выбор для небольшой команды.

</details>

**A14.** Что такое RPO и RTO? Придумай значения для интернет-магазина и для внутренней вики.

<details><summary>Ответ</summary>

RPO — сколько данных допустимо потерять (глубина отката), RTO — за сколько нужно
восстановиться. Интернет-магазин: RPO ≈ 5 минут (PITR/WAL-архив), RTO ≈ 1 час.
Внутренняя вики: RPO — сутки (ночной дамп), RTO — рабочий день.

</details>

**A15.** Перечисли семь обязанностей девопса по отношению к базе (жизненный цикл).

<details><summary>Ответ</summary>

Поднять → дать доступ → настроить параметры → бэкапить и проверять восстановление →
реплицировать → мониторить и алертить → обновлять версию и сопровождать миграции.

</details>

### Блок B. «Что тут не так / что это значит»

Оцени каждый фрагмент: что он делает, чем опасен, как правильно.

```text:no-line-numbers
B1.  shared_buffers = 30GB          # на сервере 32 ГБ RAM
B2.  fsync = off                    # "чтобы быстрее писалось"
B3.  max_connections = 2000
B4.  autovacuum = off
B5.  host all all 0.0.0.0/0 trust   # строка в pg_hba.conf
```

<details><summary>Ответ</summary>

**B1.** `shared_buffers` ~= вся RAM: не остаётся памяти под page cache ОС, `work_mem`
и соединения → своп и OOM. Норма — около 25% RAM.

**B2.** `fsync = off` отключает гарантию записи на диск: при отключении питания база может
не подняться и потерять данные. Допустимо только на одноразовых тестовых стендах.

**B3.** 2000 процессов-бэкендов: память и контекст-свитчи. Нужен PgBouncer.

**B4.** Отключённый autovacuum → bloat, деградация, в пределе — угроза transaction ID
wraparound и аварийная остановка базы. Autovacuum настраивают, а не выключают.

**B5.** Пускает кого угодно откуда угодно **без пароля**. Классика «базу нашли в интернете».
Нужны конкретные подсети и `scram-sha-256` (тема 03).

</details>

```sql
B6.  BEGIN;
     UPDATE orders SET status='paid' WHERE id=42;
     -- и соединение осталось открытым на 40 минут

B7.  CREATE INDEX idx_orders_user ON orders(user_id);   -- в 19:00 в пятницу на проде

B8.  DELETE FROM events;            -- вместо TRUNCATE, таблица на 200 млн строк

B9.  SELECT * FROM users;           -- в приложении, таблица 5 млн строк
```

<details><summary>Ответ</summary>

**B6.** Долгая открытая транзакция: держит блокировки, тормозит других, мешает vacuum
очищать мёртвые строки. Лечится таймаутами (`idle_in_transaction_session_timeout`)
и исправлением кода.

**B7.** Блокировка записи в таблицу на всё время построения индекса, в пиковый час.
Нужно `CONCURRENTLY` и окно обслуживания.

**B8.** `DELETE` создаёт мёртвую версию для каждой строки, пишет гигабайты WAL, место не
освобождает и грузит autovacuum. Для полной очистки — `TRUNCATE`.

**B9.** `SELECT *` без `LIMIT` по большой таблице: гонит лишние данные по сети и в память
приложения. В коде так делать нельзя.

</details>

```text:no-line-numbers
B10. Бэкап: cron 0 3 * * * pg_dump mydb > /backup/db.sql   # и больше ничего
B11. "У нас есть реплика, бэкапы не нужны"
B12. База в k8s на hostPath-томе, без оператора
```

<details><summary>Ответ</summary>

**B10.** Один дамп в один и тот же файл: нет истории (вчерашний перезаписан), нет проверки
успешности, нет проверки восстановления, нет выноса на другой хост, нет шифрования.

**B11.** Реплика не защищает от ошибочного/злонамеренного изменения данных — оно
реплицируется. Бэкапы обязательны.

**B12.** `hostPath` привязывает под к конкретной ноде и данные ничем не защищены;
без оператора нет ни failover, ни корректных бэкапов. Для прода не годится.

</details>

### Блок C. Практика

#### C1. Поднять и осмотреться
1. Подними PostgreSQL в докере, зайди через `psql`.
2. Выполни: `SELECT version();`, `\l`, `\du`, `\conninfo`.
3. Найди, где физически лежат данные: `SHOW data_directory;`

<details><summary>Ответ</summary>

`SHOW data_directory;` в официальном образе — `/var/lib/postgresql/data`;
`\l` — список баз, `\du` — роли, `\conninfo` — как именно ты подключён.

</details>

#### C2. 🔑 Транзакция своими руками
```sql
CREATE TABLE accounts(id int primary key, balance int);
INSERT INTO accounts VALUES (1, 1000), (2, 0);
BEGIN;
UPDATE accounts SET balance = balance - 100 WHERE id = 1;
-- посмотри данные ИЗ ДРУГОГО сеанса psql: что видно там?
ROLLBACK;
SELECT * FROM accounts;
```
Опиши, что видел второй сеанс до `ROLLBACK` и почему.

<details><summary>Ответ</summary>

Второй сеанс до `ROLLBACK` видел **старые** значения (изоляция), после `ROLLBACK`
данные вернулись к исходным — атомарность.

</details>

#### C3. Блокировка и `idle in transaction`
1. В сеансе 1: `BEGIN; UPDATE accounts SET balance=1 WHERE id=1;` (не коммить).
2. В сеансе 2: тот же `UPDATE` — он повиснет.
3. В сеансе 3: `SELECT pid, state, wait_event_type, query FROM pg_stat_activity;`
4. Найди виновника и «убей»: `SELECT pg_terminate_backend(<pid>);`
5. Запиши последовательность действий как мини-рунбук.

<details><summary>Ответ</summary>

Сеанс 2 ждёт блокировку (`wait_event_type = Lock`), виновник — сеанс 1 в состоянии
`idle in transaction`. Рунбук: найти в `pg_stat_activity` самые старые транзакции →
`pg_cancel_backend` (мягко) → `pg_terminate_backend` (жёстко) → завести
`idle_in_transaction_session_timeout`.

</details>

#### C4. Seq Scan vs Index Scan
```sql
CREATE TABLE t AS SELECT g AS id, md5(g::text) AS val FROM generate_series(1,1000000) g;
EXPLAIN ANALYZE SELECT * FROM t WHERE val = md5('777');
CREATE INDEX idx_t_val ON t(val);
EXPLAIN ANALYZE SELECT * FROM t WHERE val = md5('777');
```
Сравни план и время до и после. На сколько раз быстрее?

<details><summary>Ответ</summary>

До индекса — `Seq Scan` по 1 млн строк (сотни мс), после — `Index Scan` (доли мс).
Разница обычно в сотни-тысячи раз.

</details>

#### C5. Цена индекса
1. Замерь `\timing` вставку 200 000 строк в таблицу без индексов.
2. Создай 3 индекса, повтори вставку в такую же таблицу.
3. Сравни время и размер: `SELECT pg_size_pretty(pg_total_relation_size('t'));`

<details><summary>Ответ</summary>

Вставка с тремя индексами заметно медленнее (часто в 2-4 раза), общий размер
таблицы с индексами — кратно больше. Это и есть «цена индекса».

</details>

#### C6. MVCC и мёртвые строки
```sql
UPDATE t SET val = val;                       -- обновили ВСЕ строки
SELECT n_live_tup, n_dead_tup FROM pg_stat_user_tables WHERE relname='t';
VACUUM (VERBOSE) t;
```
Объясни, откуда взялись мёртвые строки и что сделал `VACUUM`.

<details><summary>Ответ</summary>

`UPDATE` всех строк создал по новой версии каждой строки, старые стали мёртвыми
(`n_dead_tup` ≈ числу строк). `VACUUM` пометил место как переиспользуемое (файл при этом
обычно не уменьшается — для этого нужен `VACUUM FULL`, он блокирующий).

</details>

#### C7. Размер базы и таблиц
Напиши запросы: размер базы, топ-5 самых больших таблиц, размер индексов таблицы.
Сохрани их себе — пригодятся на дежурстве.

<details><summary>Ответ</summary>

```sql
SELECT pg_size_pretty(pg_database_size(current_database()));
SELECT relname, pg_size_pretty(pg_total_relation_size(relid)) FROM pg_catalog.pg_statio_user_tables
 ORDER BY pg_total_relation_size(relid) DESC LIMIT 5;
SELECT pg_size_pretty(pg_indexes_size('t'));
```

</details>

#### C8. Соединения
1. Открой 10 соединений (`for i in $(seq 10); do psql ... -c 'select pg_sleep(60)' & done`).
2. Посмотри `SELECT count(*) FROM pg_stat_activity;` и `SHOW max_connections;`
3. Прикинь, сколько RAM съедает одно соединение (`ps` по процессам postgres).

<details><summary>Ответ</summary>

Каждое соединение — процесс postgres; в `ps` видно десятки МБ RSS на процесс
(значительная часть — общая память, но накладные расходы реальны).

</details>

#### C9. Данные переживают контейнер
1. Создай таблицу с данными.
2. `docker rm -f pg` и подними контейнер заново **с тем же volume**.
3. Проверь, что данные на месте. Потом повтори **без** volume — и сделай вывод.

<details><summary>Ответ</summary>

С volume данные переживают пересоздание контейнера, без volume — исчезают вместе
с контейнером. Отсюда правило: база в докере только с именованным томом.

</details>

#### C10. Мини-инвентаризация проекта (без стенда)
Возьми любой знакомый проект (или придумай) и выпиши: какие базы нужны, зачем каждая,
где они будут жить (VM/docker/k8s/managed), кто их бэкапит, какие RPO/RTO.

<details><summary>Ответ</summary>

Проверь себя: у каждой базы должен быть ответ на вопросы «кто бэкапит», «куда»,
«как проверяем восстановление», «какие алерты».

</details>

### Блок D. Инциденты

**D1.** «Приложение тормозит». С чего начинаешь смотреть базу? Назови 5 проверок по порядку.

<details><summary>Ответ</summary>

1) место на диске; 2) `pg_stat_activity`: число соединений, долгие запросы,
`idle in transaction`; 3) блокировки (`pg_locks`, `wait_event_type=Lock`);
4) нагрузка CPU/IO на хосте; 5) лаг репликации и ошибки в логе базы.

</details>

**D2.** На сервере с базой кончилось место. Что проверяешь и что можно безопасно удалить?

<details><summary>Ответ</summary>

`du -sh` по `base/`, `pg_wal/`, логам. Логи ротировать/удалять можно; `pg_wal`
удалять руками **нельзя** — разобраться, почему растёт (неактивный слот репликации,
неработающий archive_command). Освободить место можно старыми бэкапами на этом же диске
(их там быть не должно) и `VACUUM`/`TRUNCATE` по договорённости с разработчиками.

</details>

**D3.** База не стартует после внезапного ребута сервера. Куда смотреть?

<details><summary>Ответ</summary>

Логи PostgreSQL (`/var/log/postgresql/` или `docker logs`): чаще всего нет места,
битые права на `data_directory`, повреждён WAL, несовпадение версии данных и бинарей.
Восстановление после сбоя по WAL может занимать время — не убивать процесс.

</details>

**D4.** Разработчик выкатил миграцию `CREATE INDEX` на таблицу в 300 млн строк в прайм-тайм.
Что произошло и что делать?

<details><summary>Ответ</summary>

Индекс без `CONCURRENTLY` заблокировал запись: приложение встало.
Действия: увидеть блокировку в `pg_stat_activity`/`pg_locks`, прервать
(`pg_cancel_backend`), удалить недостроенный индекс, договориться о ночном окне
и `CREATE INDEX CONCURRENTLY`, добавить проверку миграций в CI.

</details>

**D5.** Таблица весит 200 ГБ, хотя «данных там на 20 ГБ». Причина и лечение.

<details><summary>Ответ</summary>

Bloat. Проверить `n_dead_tup`, настройки autovacuum, наличие долгих транзакций
и неактивных слотов репликации (они удерживают горизонт очистки). Лечение:
починить причину, затем `VACUUM`, при необходимости `VACUUM FULL`/`pg_repack`
(первый блокирует, второй — почти нет).

</details>

**D6.** После `DELETE FROM events` место на диске не освободилось. Почему?

<details><summary>Ответ</summary>

`DELETE` только помечает версии строк мёртвыми. Место переиспользуется после
vacuum, но файл не уменьшается. Полное освобождение — `TRUNCATE`, `VACUUM FULL`
или `pg_repack`.

</details>

**D7.** Число соединений упёрлось в `max_connections`, новые клиенты получают ошибку.
Быстрое решение и правильное решение.

<details><summary>Ответ</summary>

Быстро: найти и закрыть зависшие/idle-соединения, при необходимости временно
поднять лимит и перезапустить в окне. Правильно: PgBouncer в режиме transaction,
настроенные таймауты, адекватный пул на стороне приложения.

</details>

**D8.** Разработчик просит поднять `max_connections` до 3000. Твой ответ и аргументы.

<details><summary>Ответ</summary>

Отказать с аргументами: каждое соединение — процесс и память; 3000 процессов
не дадут производительности, а дадут OOM. Предложить PgBouncer и разобраться, почему
приложение открывает столько соединений.

</details>

**D9.** Кто-то выполнил `DROP TABLE users` на проде. Реплика есть. Помогает ли она? Что делать?

<details><summary>Ответ</summary>

Не помогает: `DROP TABLE` реплицируется мгновенно. Нужен бэкап/PITR: восстановить
на момент до `DROP` (см. тему 05), перенести таблицу в прод. Параллельно — ограничить
права, чтобы приложение не могло выполнять DDL.

</details>

**D10.** Предлагают перенести прод-базу в Kubernetes «как остальные сервисы».
Какие вопросы задашь, прежде чем соглашаться?

<details><summary>Ответ</summary>

Какой storage (сетевой, с гарантиями по IOPS)? Какой оператор? Кто и как делает
бэкапы и failover? Как обновлять мажорную версию? Что с производительностью и лимитами?
Пробовали ли managed-вариант? Если ответов нет — база остаётся на VM/managed.

</details>

### Блок E. Вопросы с собеседования

**1.** Какие типы баз данных знаешь и чем они отличаются?

<details><summary>Ответ</summary>

Реляционные, key-value, документные, колоночные, time-series, поисковые — разные
модели данных и разные сценарии (OLTP vs OLAP vs кэш).

</details>

**2.** Что такое транзакция и ACID?

<details><summary>Ответ</summary>

Транзакция — всё или ничего; ACID — атомарность, согласованность, изоляция, долговечность.

</details>

**3.** Что такое WAL в PostgreSQL?

<details><summary>Ответ</summary>

Журнал предзаписи: сначала изменение пишется в WAL, потом в данные; основа восстановления,
репликации и PITR.

</details>

**4.** Что такое MVCC и autovacuum?

<details><summary>Ответ</summary>

MVCC — версии строк вместо блокировок чтения; autovacuum убирает мёртвые версии.

</details>

**5.** Зачем нужны индексы и какова их цена?

<details><summary>Ответ</summary>

Индекс ускоряет поиск, но занимает место, замедляет запись и требует памяти.

</details>

**6.** Чем реплика отличается от бэкапа?

<details><summary>Ответ</summary>

Реплика защищает от отказа сервера, но повторяет ошибки; бэкап защищает от ошибок людей.

</details>

**7.** Что такое RPO и RTO?

<details><summary>Ответ</summary>

RPO — допустимая потеря данных, RTO — время восстановления.

</details>

**8.** За что отвечает девопс в работе с базой?

<details><summary>Ответ</summary>

Установка, доступы, настройка, бэкап и проверка восстановления, репликация,
мониторинг и алерты, обновления и сопровождение миграций.

</details>

**9.** Стоит ли держать базу в Kubernetes?

<details><summary>Ответ</summary>

Только с оператором и нормальным storage; иначе VM или managed.

</details>

**10.** С чего начнёшь разбор «база тормозит»?

<details><summary>Ответ</summary>

Диск → соединения и долгие запросы → блокировки → нагрузка хоста → логи и лаг репликации.

</details>
