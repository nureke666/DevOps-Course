## 🧪 Лаба 1. PostgreSQL с нуля под приложение

### Что делаем
Поднимаем PostgreSQL на VM (не в докере — чтобы увидеть systemd, пути и конфиги),
готовим его под условное приложение и подключаемся к нему с другой машины/контейнера.

### Требования
- [ ] Установка из репозитория PGDG, версия зафиксирована
- [ ] Знаешь и проверил через SQL: `data_directory`, `config_file`, `hba_file`
- [ ] Отдельный диск/каталог под данные (хотя бы отдельный LV или директория с квотой)
- [ ] Роли: `shop_owner` (владелец, миграции) и `shop_app` (только DML)
- [ ] База `shop` с владельцем `shop_owner`
- [ ] `listen_addresses` — конкретный адрес, не `*`
- [ ] `pg_hba.conf`: правило для подсети приложения + `reject` в конце
- [ ] Проверено: с разрешённого хоста пускает, с другого — нет
- [ ] Пароли не в git (переменные окружения / ansible-vault)
- [ ] Логирование включено с информативным `log_line_prefix`
- [ ] Установка оформлена скриптом или ролью Ansible (идемпотентно)

### Критерии приёмки
```bash
pg_isready -h <db-ip> -p 5432                       # accepting connections
psql -h <db-ip> -U shop_app -d shop -c '\conninfo'  # подключается
psql -h <db-ip> -U shop_app -d shop -c 'DROP TABLE test;'   # ⇒ ошибка прав
sudo -u postgres psql -c "SELECT * FROM pg_hba_file_rules;" # без ошибок
```

### Вопросы себе
- Что произойдёт, если я поменяю `listen_addresses` и сделаю `reload`, а не `restart`?
- Почему `shop_app` не может создавать таблицы и почему это хорошо?
- Где в моей схеме хранится пароль и кто имеет к нему доступ?

## 🧪 Лаба 2. Настройка под сервер и замер эффекта

### Что делаем
Приводим конфиг к размеру машины, генерируем нагрузку `pgbench` и **измеряем** разницу.
Цель — научиться обосновывать значения цифрами, а не «так в интернете написано».

### Шаги
```bash
sudo -u postgres pgbench -i -s 50 shop         # данные ~750 МБ
sudo -u postgres pgbench -c 10 -j 2 -T 120 -P 10 shop   # базовый замер
```
- [ ] Записал tps «до»
- [ ] Настроил `shared_buffers`, `effective_cache_size`, `work_mem`, `maintenance_work_mem`
- [ ] Настроил WAL: `max_wal_size`, `checkpoint_timeout`, `checkpoint_completion_target`
- [ ] Поставил `random_page_cost = 1.1` (если SSD)
- [ ] Вынес настройки в `conf.d/*.conf`, основной файл не трогал
- [ ] Повторил замер, записал tps «после»
- [ ] Посмотрел `pg_stat_bgwriter` до и после (соотношение `timed`/`req`)
- [ ] Проверил, какие параметры потребовали рестарта (`pending_restart`)
- [ ] Включил `pg_stat_statements` и нашёл топ-5 запросов pgbench

### Критерии приёмки
- Есть таблица «параметр → было → стало → почему» на 10 строк
- Есть цифры tps до/после и объяснение, почему изменилось (или почему нет)

### Вопросы себе
- Что будет с tps, если поставить `synchronous_commit = off`? Проверь и объясни цену.
- Почему рост `shared_buffers` не всегда даёт рост производительности?

## 🧪 Лаба 3. ⭐ Бэкап и восстановление (главная лаба блока)

### Что делаем
Полный цикл: настроили бэкапы → сломали базу → восстановили → записали рунбук.

### Часть A. Логический бэкап
- [ ] `pg_dump -F c` + `pg_dumpall --globals-only` по расписанию (cron/systemd timer)
- [ ] Имя файла с датой, retention (удаление старше N дней)
- [ ] Скрипт с `set -euo pipefail`, проверкой кода возврата и записью в лог
- [ ] Восстановление в отдельную базу и сверка числа строк

### Часть B. Физический бэкап и PITR
- [ ] `archive_mode = on`, `archive_command` пишет в отдельный каталог/бакет
- [ ] `pg_basebackup` снят и сохранён
- [ ] Проверен `pg_stat_archiver` (нет `failed_count`)
- [ ] Сценарий аварии: вставил данные → запомнил время → `DROP TABLE`
- [ ] Восстановление на момент до аварии (`recovery_target_time` + `recovery.signal`)
- [ ] Проверено: таблица есть, поздние данные отсутствуют

### Часть C. Рунбук
Файл `RUNBOOK_restore.md`:
1. Как понять, что нужен restore (признаки).
2. Кто принимает решение и кого уведомляем.
3. Пошаговые команды (копипастом, с путями).
4. Как проверить результат.
5. Что делать, если промахнулись по времени.
6. Сколько времени занимает (замерить!) — это и есть твой реальный RTO.

### Критерии приёмки
```sql
SELECT pg_is_in_recovery();                    -- f после promote
SELECT count(*) FROM orders;                   -- совпадает с ожиданием
SELECT * FROM pg_stat_archiver;                -- failed_count = 0
```
- [ ] Замерено время полного восстановления
- [ ] Указаны фактические RPO и RTO стенда

### Вопросы себе
- Что бы я потерял, если бы авария случилась через 4 часа после последнего бэкапа?
- Где лежат мои бэкапы и что будет, если умрёт диск с базой?

## 🧪 Лаба 4. Реплика и переключение

### Что делаем
Primary + standby, наблюдаем лаг, делаем promote, возвращаем старый primary.

### Требования
- [ ] Два кластера одной версии (две VM или два контейнера в одной сети)
- [ ] Роль `repl`, правило `replication` в `pg_hba.conf`, слот репликации
- [ ] Реплика поднята через `pg_basebackup -R -S`
- [ ] Проверено: `pg_stat_replication` на primary, `pg_is_in_recovery()` на standby
- [ ] Измерен лаг под нагрузкой `pgbench` (в байтах и секундах)
- [ ] Проведён эксперимент: остановил реплику → посмотрел рост `pg_wal` из-за слота
- [ ] Сделан `pg_promote()`, проверена запись на новом primary
- [ ] Старый primary возвращён репликой (`pg_rewind` или пересоздание)
- [ ] Написан `RUNBOOK_failover.md`

### Дополнительно (со звёздочкой)
- [ ] Синхронная репликация `ANY 1 (s1, s2)` и проверка поведения при падении реплики
- [ ] Patroni + etcd + HAProxy в docker-compose, `patronictl switchover`

### Вопросы себе
- Почему нельзя просто включить старый primary обратно?
- Что мой мониторинг покажет в момент failover и хватит ли этого дежурному?

## 🧪 Лаба 5. Мониторинг базы

### Что делаем
Полный стек наблюдения за своей базой: метрики, дашборд, алерты, рунбуки.

### Требования
- [ ] docker-compose: postgres_exporter + node_exporter + prometheus + grafana + alertmanager
- [ ] Экспортер ходит под ролью с `pg_monitor`
- [ ] Импортирован дашборд 9628 + добавлены свои панели (соединения, TPS, cache hit,
      лаг репликации, мёртвые строки, размер базы, место на диске)
- [ ] Минимум 6 алертов в `rules.yml` с разумными `for` и severity
- [ ] Спровоцированы и проверены как минимум 3 алерта
- [ ] Настроены уведомления в Alertmanager (хотя бы webhook/почта)
- [ ] На каждый алерт — короткий рунбук

### Критерии приёмки
```bash
curl -s localhost:9187/metrics | grep -c '^pg_'      # метрики есть
curl -s localhost:9090/api/v1/rules | jq '.data.groups[].rules[].name'
```
- [ ] Скриншот дашборда в момент искусственной нагрузки
- [ ] Скриншот сработавшего алерта

## 🧪 Лаба 7. Релиз со схемой без простоя

### Что делаем
Берём копию linkd 2.0, выносим схему из кода в миграции и переименовываем колонку
`url` → `target_url` за три релиза (expand/contract из [13. Миграции схемы](/databases/13-schema-migrations))
под постоянной нагрузкой. Доказываем цифрами: ни одной 5xx. Потом нарочно делаем
«как нельзя» и видим разницу.

> Работаем в `~/sandbox` (копия `~/Projects/devops/09-ledger/app`), а не в самом
> практическом репозитории: туда готовые решения не коммитим. API linkd не меняется —
> поле `url` в JSON остаётся, переименовывается только колонка.

### Требования
- [ ] PostgreSQL + 2 и более экземпляра linkd за балансировщиком (compose + nginx/Traefik или kind + Deployment)
- [ ] Схема вынесена в миграции (Flyway или Alembic): V1 = текущая таблица `links`;
      на существующей базе — `flyway baseline` / `alembic stamp`
- [ ] Миграции запускаются отдельным шагом (job в CI или k8s Job-хук) под ролью-владельцем;
      приложение работает под ролью без DDL (см. [03. Доступ и pg_hba.conf](/databases/03-pg-hba-access))
- [ ] Генератор нагрузки: цикл `POST /api/links` + `GET /r/<code>` с логом кодов ответов
- [ ] Релизы A (expand + триггер), B (switch), C (contract) — каждый rolling update под нагрузкой
- [ ] Backfill — отдельным джобом пачками с паузами, во время него смотрим лаг реплики (если есть)
- [ ] Во всех миграциях `lock_timeout`; индекс по `created_at` — `CONCURRENTLY`
- [ ] На каждом шаге проверен откат **кода** без отката схемы
- [ ] Эксперимент «как нельзя»: `RENAME COLUMN` вместе с кодом в одном релизе — посчитать 5xx
- [ ] Эксперимент с очередью блокировок: долгая транзакция + `ALTER` без `lock_timeout`
      → замерить простой; с `lock_timeout` + ретраем → простоя нет
- [ ] CI: миграции на пустой базе и на дампе-образце + линтер (squawk или `atlas migrate lint`)
- [ ] Написан `RUNBOOK_migrations.md`: порядок релизов, таймауты, что делать, если миграция упала

### Критерии приёмки
```bash
# генератор пишет по строке на запрос, первое поле — HTTP-код
for f in load_A.log load_B.log load_C.log; do awk '$1 >= 500' "$f" | wc -l; done   # 0, 0, 0
awk '$1 >= 500' load_rename.log | wc -l                                          # > 0 — «как нельзя»
```
```sql
SELECT version, description, success FROM flyway_schema_history ORDER BY installed_rank;
\d links                                                  -- url нет, target_url NOT NULL
SELECT indexrelid::regclass FROM pg_index WHERE NOT indisvalid;   -- пусто
```
- [ ] Замерено время каждой миграции и backfill
- [ ] В рунбуке указано, после какого релиза откат на предыдущую версию кода невозможен

### Дополнительно (со звёздочкой)
- [ ] То же на MySQL 8.4 (стенд из [12. MySQL](/databases/12-mysql)): `ALGORITHM=INSTANT`,
      `lock_wait_timeout`, большое изменение через gh-ost с наблюдением лага реплики
- [ ] Миграция как ArgoCD `PreSync`-хук, упавший хук разобран по логам

- Что сломалось бы, если бы миграции запускались из каждого пода на старте?
