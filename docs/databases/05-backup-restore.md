# 05. Бэкап и восстановление ⭐

> Роадмап → Базы → PostgreSQL → *«Бэкап и восстановление»*.
>
> **После темы ты умеешь:** снять логический и физический бэкап, восстановить базу
> целиком и одну таблицу, сделать PITR на момент времени и объяснить свою схему
> бэкапов через RPO/RTO.

---

## 🗺️ Главная мысль темы

```text:no-line-numbers
        ┌──────────────────────────────────────────────────────┐
        │  Бэкап, который ни разу не восстанавливали,          │
        │  это НЕ бэкап. Это файл неизвестного содержания.     │
        └──────────────────────────────────────────────────────┘

  Вопрос не «делаем ли мы бэкапы», а:
  ─ где лежат (на другом хосте? в другом регионе?)
  ─ сколько храним (retention)
  ─ сколько данных потеряем (RPO)
  ─ за сколько восстановимся (RTO)
  ─ когда в последний раз ПРОВЕРЯЛИ восстановление
```

| Термин | Определение | Пример |
|--------|-------------|--------|
| **RPO** (Recovery Point Objective) | Сколько данных допустимо потерять | «не больше 5 минут» |
| **RTO** (Recovery Time Objective) | За сколько нужно восстановиться | «не больше 1 часа» |

Ночной `pg_dump` = RPO до 24 часов. Нужен RPO 5 минут → нужен архив WAL и PITR.
Это единственная логика, по которой выбирают схему бэкапов.

## 1. Два вида бэкапа

```text:no-line-numbers
ЛОГИЧЕСКИЙ (pg_dump)                ФИЗИЧЕСКИЙ (pg_basebackup / pgBackRest / WAL-G)
─────────────────────               ─────────────────────────────────────────────
Это SQL/дамп объектов               Это копия файлов PGDATA + WAL
+ переносим между версиями          + быстрый на больших базах
+ можно взять одну таблицу          + основа PITR (точка во времени)
+ маленький на «разреженных» базах   + восстановление = копия целиком
− медленно на больших базах         − только та же мажорная версия и платформа
− нет PITR (только момент снятия)   − нельзя достать одну таблицу
− нагружает базу при снятии         − нужен архив WAL для точности

Малые базы (<50-100 ГБ)             Прод, большие базы, требование RPO минуты
```

В зрелом проекте обычно **оба**: физический с PITR как основной и периодический
логический как «страховка от нечитаемого формата» и удобный источник для дев-стендов.

## 2. `pg_dump` / `pg_dumpall` — логический бэкап

```bash
# форматы
pg_dump -U postgres -d shop -F p -f shop.sql          # plain: обычный SQL
pg_dump -U postgres -d shop -F c -f shop.dump         # ⭐ custom: сжат, выборочное восстановление
pg_dump -U postgres -d shop -F d -j 4 -f shop_dir/    # directory: параллельно в каталог
pg_dump -U postgres -d shop -F t -f shop.tar          # tar

# полезные опции
pg_dump -d shop -F c -Z 6 -f shop.dump                # уровень сжатия
pg_dump -d shop -t orders -F c -f orders.dump         # только таблица
pg_dump -d shop -n billing -F c -f billing.dump       # только схема
pg_dump -d shop --schema-only -f schema.sql           # только структура
pg_dump -d shop --data-only -F c -f data.dump         # только данные
pg_dump -d shop -T 'audit_*' -F c -f shop.dump        # исключить таблицы

# роли, табличные пространства, параметры кластера — их pg_dump НЕ берёт!
pg_dumpall -U postgres --globals-only -f globals.sql  # ⭐ обязательно рядом с дампом
pg_dumpall -U postgres -f all.sql                     # весь кластер (plain, без параллели)
```

> ⚠️ Классическая ошибка: восстановили дамп базы на новый сервер — а ролей и прав нет,
> приложение не может подключиться. `pg_dumpall --globals-only` решает это.

### Восстановление

```bash
# plain (.sql) — просто выполняем psql
createdb -U postgres shop_restored
psql -U postgres -d shop_restored -f shop.sql -v ON_ERROR_STOP=1

# custom/directory — pg_restore
pg_restore -U postgres -d shop_restored -j 4 shop.dump         # параллельно
pg_restore -U postgres -d shop_restored -t orders shop.dump    # ⭐ одна таблица
pg_restore -l shop.dump > toc.list                             # оглавление
pg_restore -L toc.list -d shop_restored shop.dump              # выборочно по списку
pg_restore --clean --if-exists -d shop shop.dump               # перезаписать существующие
```

Особенности, о которые спотыкаются:
- `pg_dump` работает **в одной транзакции со снимком** — дамп консистентен на момент старта,
  но длинный дамп удерживает горизонт и мешает autovacuum.
- Дамп в `plain` не даёт параллельного восстановления и выборочности — в проде берут `-F c`/`-F d`.
- `pg_restore -j` ускоряет в разы, но грузит диск и CPU.
- Восстановление **не** включает пользователей/пароли — это `globals`.

## 3. `pg_basebackup` — физический бэкап

```bash
pg_basebackup -h 10.0.1.5 -U repl -D /backup/base_$(date +%F) \
  -Ft -z -Xs -P -c fast
```
| Флаг | Смысл |
|------|-------|
| `-D` | Куда класть |
| `-Ft -z` | Формат tar + gzip (`-Fp` — «как есть», plain) |
| `-Xs` | Стримить WAL параллельно (бэкап самодостаточен) |
| `-P` | Прогресс |
| `-c fast` | Немедленный checkpoint (не ждать) |
| `-R` | Сразу создать `standby.signal` — готовая реплика (тема 06) |

Требования: роль с атрибутом `REPLICATION` и правило в `pg_hba.conf`:
```text:no-line-numbers
host  replication  repl  10.0.1.0/24  scram-sha-256
```

Восстановление физического бэкапа = «положить PGDATA на место»:
```bash
sudo systemctl stop postgresql@16-main
sudo rm -rf /var/lib/postgresql/16/main/*            # ⚠️ трижды проверь путь
sudo -u postgres tar -xzf /backup/base.tar.gz -C /var/lib/postgresql/16/main/
sudo systemctl start postgresql@16-main
```

## 4. PITR — восстановление на момент времени ⭐

```text:no-line-numbers
   базовая копия              архив WAL (непрерывно)
   (pg_basebackup)   ┌───────────────────────────────────────┐
        │            │ 000000010000000000000023              │
   02:00│            │ 000000010000000000000024  …           │
        ▼            └───────────────────────────────────────┘
  ──────●────────────────────────────────────────────►  время
        02:00                       14:37  ← «удалили таблицу»
                                    ▲
        восстановить базовую копию + доиграть WAL ДО 14:36:59
```

### Настройка архивации (делается заранее, до аварии)

```text:no-line-numbers
# postgresql.conf
wal_level = replica
archive_mode = on                        # требует рестарта
archive_command = 'test ! -f /arch/%f && cp %p /arch/%f'   # учебный вариант
archive_timeout = 300                    # форсить сегмент раз в 5 минут (RPO)
```
```text:no-line-numbers
%p — путь к файлу WAL, %f — имя файла
В проде вместо cp: WAL-G / pgBackRest / barman (сжатие, шифрование, S3, проверка)
```

### Сам PITR

```bash
# 1. остановить базу, сохранить «как было» (для расследования)
sudo systemctl stop postgresql@16-main
sudo mv /var/lib/postgresql/16/main /var/lib/postgresql/16/main.broken

# 2. развернуть базовую копию
sudo -u postgres mkdir -p /var/lib/postgresql/16/main && sudo chmod 700 …
sudo -u postgres tar -xzf /backup/base_2026-09-12.tar.gz -C /var/lib/postgresql/16/main/
```
```text:no-line-numbers
# 3. postgresql.conf (или postgresql.auto.conf) в восстановленном PGDATA
restore_command = 'cp /arch/%f %p'
recovery_target_time = '2026-09-13 14:36:59+05'   # смещение явно: Казахстан с 01.03.2024 — UTC+5
recovery_target_action = 'promote'          # после достижения точки — открыть базу
```
```bash
# 4. сигнальный файл — именно он включает режим восстановления (PG 12+)
sudo -u postgres touch /var/lib/postgresql/16/main/recovery.signal
sudo systemctl start postgresql@16-main
sudo tail -f /var/log/postgresql/postgresql-16-main.log    # смотрим прогресс
```
```sql
SELECT pg_is_in_recovery();       -- t пока идёт восстановление, f после promote
```

| Цель восстановления | Параметр |
|---------------------|----------|
| На момент времени | `recovery_target_time` |
| До конкретной транзакции | `recovery_target_xid` |
| До именованной точки | `recovery_target_name` (создаётся `pg_create_restore_point`) |
| До конца доступного WAL | ничего не указывать |
| До LSN | `recovery_target_lsn` |

> 💡 `recovery_target_time` указывают **на секунду раньше** аварии. Если промахнулись —
> можно повторить восстановление с другой целью, если не удалили базовую копию.
> Поэтому копию не трогают до полной проверки.

## 5. Инструменты прода: WAL-G, pgBackRest, Barman

Руками `cp` в `archive_command` пишут только на учебном стенде. В проде:

| Инструмент | Особенности |
|------------|-------------|
| **WAL-G** | Go-бинарь, S3/GCS/Azure/локально, сжатие, шифрование, дельта-бэкапы. Очень популярен |
| **pgBackRest** | Мощный, параллельный, проверка контрольных сумм, retention, репозиторий бэкапов |
| **Barman** | Питоновский, централизованный сервер бэкапов для нескольких кластеров |

```bash
# WAL-G: типовые команды
export WALG_S3_PREFIX=s3://backups/pg-prod
wal-g backup-push /var/lib/postgresql/16/main    # полный/дельта бэкап
wal-g backup-list                                 # список
wal-g backup-fetch /var/lib/postgresql/16/main LATEST   # развернуть последний
wal-g delete retain FULL 7 --confirm              # retention: хранить 7 полных
```
```text:no-line-numbers
archive_command = 'wal-g wal-push %p'
restore_command = 'wal-g wal-fetch %f %p'
```

## 6. Стратегия бэкапов, которую не стыдно показать

```text:no-line-numbers
Правило 3-2-1:
  3 копии данных · 2 разных носителя/хранилища · 1 копия вне площадки
```

| Элемент | Решение |
|---------|---------|
| Расписание | Полный — ежедневно ночью; WAL — непрерывно |
| Хранение | S3/объектное хранилище другого региона + локальная копия последнего дня |
| Retention | 7 ежедневных, 4 еженедельных, 6 ежемесячных (пример) |
| Шифрование | На стороне инструмента (WAL-G) и/или в хранилище |
| Доступ | Бэкапы недоступны на запись с прод-сервера (защита от шифровальщика) |
| Мониторинг | Алерт «бэкап не сделан за 25 часов», «архивация WAL сломана» |
| ⭐ Проверка | Ежемесячное **тестовое восстановление** на отдельный сервер + прогон проверок |

Проверка архивации WAL:
```sql
SELECT * FROM pg_stat_archiver;    -- last_archived_time, failed_count, last_failed_wal
```
Если `failed_count` растёт — WAL не уезжает, `pg_wal` пухнет, PITR не будет работать.

## 7. Типовые сценарии восстановления

| Сценарий | Что делать |
|----------|-----------|
| Удалили строки в одной таблице | PITR в **отдельный** инстанс → выгрузить таблицу → перенести в прод |
| `DROP TABLE` на проде | То же самое; реплика не поможет |
| Умер сервер | Поднять новый + физический бэкап + WAL, либо promote реплики |
| Повреждение данных (corruption) | Восстановление из бэкапа; `pg_checksums` для диагностики |
| Нужен свежий дев-стенд | `pg_dump` с прода + маскирование персональных данных |
| Миграция на новую версию | `pg_dumpall`/`pg_upgrade` (тема 02) |

> ⭐ Ключевой приём: **восстанавливай не поверх прода, а рядом**. Отдельный сервер/инстанс,
> оттуда достаёшь нужное. Восстановление «поверх» уничтожает улики и шанс на вторую попытку.

## 8. Грабли

| Грабля | Последствие | Правильно |
|--------|-------------|-----------|
| Дамп в тот же файл каждый день | Вчерашний перезаписан свежим (возможно, битым) | Имя с датой + retention |
| Бэкап лежит на том же диске | Умер диск — умерло всё | Другой хост/регион, S3 |
| Нет `pg_dumpall --globals-only` | После restore нет ролей и прав | Снимать globals вместе с дампом |
| Не проверяли восстановление | Узнаёшь о проблеме в момент аварии | Регулярный тест restore |
| Нет мониторинга бэкапов | Бэкапы «не делались» 3 месяца | Алерт на возраст последнего бэкапа |
| `archive_command` молча падает | `pg_wal` растёт, PITR невозможен | Алерт по `pg_stat_archiver.failed_count` |
| Бэкап без шифрования в общем бакете | Утечка всех данных | Шифрование + ограниченный доступ |
| Восстановление «поверх» прода | Потеряли и данные, и улики | Восстанавливать в отдельный инстанс |
| Считают реплику бэкапом | `DROP TABLE` уехал на реплику | Реплика ≠ бэкап |

## 💼 Как это в DevOps

- Бэкапы — это не скрипт, а **сервис**: расписание, хранилище, retention, шифрование,
  мониторинг и регулярная проверка восстановления. На собесе спрашивают именно про это.
- Типовой прод: pgBackRest/WAL-G → S3, полный бэкап ночью, WAL непрерывно,
  retention 7/4/6, ежемесячный test restore на отдельную VM с автоматическими проверками.
- Метрики бэкапов уезжают в Prometheus (возраст последнего бэкапа, размер, статус
  архивации) — раздел мониторинга.
- Перед любой рискованной операцией (миграция, апгрейд, массовый `UPDATE`) —
  убедиться, что свежий бэкап есть и он валиден. Это входит в чек-лист релиза.
- Восстановление — процедура с рунбуком: кто принимает решение, кто выполняет,
  как проверяют результат, как сообщают бизнесу. Пишется **заранее**.

| Только структура / только данные | `--schema-only` / `--data-only` |
| Только одну таблицу | `pg_dump -t orders …` |
| Роли и права кластера | `pg_dumpall --globals-only -f globals.sql` |
| Восстановить дамп | `pg_restore -d shop_new -j 4 shop.dump` |
| Восстановить одну таблицу | `pg_restore -d shop -t orders shop.dump` |
| Посмотреть содержимое дампа | `pg_restore -l shop.dump` |
| Физический бэкап | `pg_basebackup -D /backup -Ft -z -Xs -P` |
| Включить архивацию | `archive_mode=on`, `archive_command='…'` (рестарт) |
| Проверить архивацию | `SELECT * FROM pg_stat_archiver;` |
| PITR на время | `restore_command` + `recovery_target_time` + `recovery.signal` |
| Идёт ли восстановление | `SELECT pg_is_in_recovery();` |
| Точка восстановления | `SELECT pg_create_restore_point('before_migration');` |
| WAL-G: бэкап/список/восстановление | `backup-push` / `backup-list` / `backup-fetch` |
| Размер базы (планирование) | `SELECT pg_size_pretty(pg_database_size('shop'));` |

## 🧠 Что запомнить

1. ⭐ Бэкап без проверенного восстановления не считается бэкапом.
2. Схема бэкапов выводится из RPO/RTO, а не из привычки «делать дамп ночью».
3. Логический (`pg_dump`) — гибкий и переносимый; физический (`pg_basebackup`/WAL-G) —
   быстрый и даёт PITR.
4. `pg_dump` не включает роли и права — рядом обязателен `pg_dumpall --globals-only`.
5. Формат `-F c`/`-F d` даёт параллельное и выборочное восстановление; `plain` — нет.
6. PITR = базовая копия + непрерывный архив WAL; включается `recovery.signal`
   и `recovery_target_time` (PG 12+).
7. Архивация WAL должна мониториться (`pg_stat_archiver`): сломалась — нет PITR и растёт `pg_wal`.
8. Восстанавливай рядом, а не поверх прода: сохраняешь улики и право на вторую попытку.
9. Бэкапы хранятся вне площадки, зашифрованы и недоступны на запись с прод-сервера.
10. Реплика не бэкап; бэкап не отменяет реплику — они закрывают разные риски.

### Блок A. Теория

**A1.** Что такое RPO и RTO? Как из них выводится схема бэкапов?

<details><summary>Ответ</summary>

RPO — допустимый объём потерянных данных (глубина отката), RTO — допустимое время
восстановления. RPO определяет частоту бэкапов и необходимость архива WAL;
RTO — формат бэкапа, параллельность восстановления, наличие горячей реплики.

</details>

**A2.** Чем логический бэкап отличается от физического? Плюсы и минусы каждого.

<details><summary>Ответ</summary>

Логический — дамп объектов и данных (переносим между версиями/платформами,
можно взять одну таблицу, но медленный на больших базах и без PITR). Физический — копия
файлов кластера (быстрый, даёт PITR, но привязан к мажорной версии и платформе,
восстанавливается только целиком).

</details>

**A3.** Какие форматы умеет `pg_dump` и чем `-F c` лучше `-F p` в проде?

<details><summary>Ответ</summary>

`p` (plain SQL), `c` (custom, сжатый), `d` (directory, параллельный), `t` (tar).
`-F c` сжат, позволяет `pg_restore -j` и выборочное восстановление отдельных объектов.

</details>

**A4.** ⭐ Что `pg_dump` **не** сохраняет? Как это добрать?

<details><summary>Ответ</summary>

Роли, пароли, права на уровне кластера, табличные пространства, параметры
(`ALTER SYSTEM`). Добирается `pg_dumpall --globals-only` (плюс отдельно — конфиги сервера).

</details>

**A5.** Как восстановить из дампа только одну таблицу?

<details><summary>Ответ</summary>

`pg_restore -d база -t таблица файл.dump` (из формата c/d/t) либо
восстановить дамп в отдельную базу и перенести таблицу.

</details>

**A6.** Что делает `pg_basebackup` и какие требования к правам и `pg_hba.conf`?

<details><summary>Ответ</summary>

Делает физическую копию PGDATA через протокол репликации. Нужна роль с атрибутом
`REPLICATION` (или суперпользователь) и строка `host replication <роль> <адрес> scram-sha-256`
в `pg_hba.conf`.

</details>

**A7.** Объясни PITR: из чего он состоит и как работает.

<details><summary>Ответ</summary>

Point-In-Time Recovery: берём базовую физическую копию и «доигрываем» на неё
архивные сегменты WAL до указанного момента. Позволяет восстановиться на секунду
перед аварией.

</details>

**A8.** Какие параметры нужно включить **заранее**, чтобы PITR стал возможен?

<details><summary>Ответ</summary>

`wal_level = replica` (или выше), `archive_mode = on`, рабочий `archive_command`,
регулярные базовые копии; желательно `archive_timeout` для ограничения RPO.

</details>

**A9.** Что такое `recovery.signal` и чем он заменил `recovery.conf`?

<details><summary>Ответ</summary>

Пустой файл в PGDATA, наличие которого включает режим восстановления (PG 12+).
Раньше роль включателя играл `recovery.conf`; теперь параметры восстановления живут
в обычном конфиге, а `recovery.signal`/`standby.signal` — только сигналы.

</details>

**A10.** Какие бывают цели восстановления (`recovery_target_*`)?

<details><summary>Ответ</summary>

`recovery_target_time`, `recovery_target_xid`, `recovery_target_lsn`,
`recovery_target_name`, либо восстановление до конца доступного WAL.
Поведение после достижения задаёт `recovery_target_action`.

</details>

**A11.** Как проверить, что архивация WAL работает?

<details><summary>Ответ</summary>

`SELECT * FROM pg_stat_archiver;` — смотреть `last_archived_time`,
`last_archived_wal`, `failed_count`, `last_failed_wal`; плюс наличие файлов в архиве
и алерт в мониторинге.

</details>

**A12.** Что такое правило 3-2-1?

<details><summary>Ответ</summary>

Три копии данных, на двух разных типах носителей/хранилищ, одна — вне площадки.

</details>

**A13.** Почему бэкапы должны быть недоступны на запись с прод-сервера?

<details><summary>Ответ</summary>

Чтобы скомпрометированный или заражённый прод-сервер не смог удалить/зашифровать
бэкапы. Реализуется отдельными учётными данными, write-once (object lock), pull-моделью
бэкапа или отдельным сервером бэкапов.

</details>

**A14.** Почему восстанавливать нужно «рядом», а не поверх прода?

<details><summary>Ответ</summary>

Восстановление поверх уничтожает текущее состояние — исчезают улики и шанс
повторить восстановление с другой целью (например, если промахнулись на минуту).

</details>

**A15.** Назови пять пунктов мониторинга бэкапов.

<details><summary>Ответ</summary>

Возраст последнего успешного бэкапа; статус/код возврата задания; размер бэкапа
(резкое изменение — подозрительно); `pg_stat_archiver.failed_count`; результат последней
проверки восстановления; свободное место в хранилище.

</details>

### Блок B. «Что делает команда / что тут не так»

```bash
B1.  pg_dump -d shop -F c -f shop.dump
B2.  pg_dump -d shop -F d -j 4 -f shop_dir/
B3.  pg_dumpall --globals-only -f globals.sql
B4.  pg_restore -d shop_new -j 4 -t orders shop.dump
B5.  pg_restore -l shop.dump
B6.  pg_basebackup -h db1 -U repl -D /backup/base -Ft -z -Xs -P
B7.  wal-g backup-push /var/lib/postgresql/16/main
B8.  wal-g delete retain FULL 7 --confirm
```

<details><summary>Ответ</summary>

**B1.** Дамп базы в сжатом custom-формате.
**B2.** Параллельный дамп в каталог четырьмя процессами — быстрее на больших базах.
**B3.** Дамп общекластерных объектов: ролей, прав, табличных пространств.
**B4.** Восстановление одной таблицы из дампа (флаг `-j` с `-t` бессмысленен, но не мешает).
**B5.** Печатает оглавление дампа — список объектов, из которого делают выборочное восстановление.
**B6.** Физический бэкап с удалённого сервера в tar.gz со стримингом WAL и прогрессом.
**B7.** WAL-G снимает бэкап кластера в объектное хранилище.
**B8.** Retention: оставить 7 полных бэкапов, остальные удалить.

</details>

Оцени схемы бэкапа:

```bash
B9.   0 3 * * * pg_dump shop > /var/lib/postgresql/backup.sql
B10.  0 3 * * * pg_dump -F c shop -f /backup/shop_$(date +\%F).dump   # /backup — тот же диск
B11.  archive_command = 'cp %p /arch/%f'                              # без test ! -f
B12.  archive_command = 'cp %p /arch/%f || true'
B13.  Бэкапы в S3-бакет, доступ на запись и удаление у прод-сервера
B14.  "Бэкапы делает реплика, значит всё надёжно"
B15.  Последняя проверка восстановления: никогда
```

<details><summary>Ответ</summary>

**B9.** Дамп в plain, перезапись одного файла, хранение на том же сервере (и в каталоге
данных!) — три ошибки сразу.
**B10.** Имя с датой — уже лучше, но бэкап на том же диске: отказ диска уносит всё.
**B11.** Без `test ! -f` команда перезапишет уже заархивированный сегмент — риск порчи архива.
**B12.** `|| true` скрывает ошибки: PostgreSQL считает сегмент заархивированным и удаляет его.
Это гарантированная потеря WAL и неработающий PITR.
**B13.** Прод может удалить бэкапы (шифровальщик, ошибка скрипта). Нужны ограниченные права
и object lock/версионирование.
**B14.** Реплика повторяет ошибочные изменения; бэкап нужен отдельно (снимать его с реплики — хорошо).
**B15.** Главная ошибка темы: схема не проверена, реальное восстановление может не сработать.

</details>

### Блок C. Практика

#### C1. 🔑 Дамп и восстановление
1. Создай базу `shop` с парой таблиц и данными.
2. Сними `pg_dump -F c` и `pg_dumpall --globals-only`.
3. Удали базу (`DROP DATABASE shop;`), восстанови из дампа в новую базу.
4. Сверь количество строк до и после.

<details><summary>Ответ</summary>

Количество строк должно совпасть; если нет — разбираться, что потерялось
(например, дамп снимался при активной записи и часть данных пришла позже — это нормально,
дамп консистентен на момент **старта**).

</details>

#### C2. Выборочное восстановление
1. Восстанови из того же дампа **только одну таблицу** в отдельную базу.
2. Посмотри оглавление `pg_restore -l` и восстанови по списку (`-L`).

#### C3. Роли теряются
1. Создай роль `app` с правами на таблицы.
2. Восстанови дамп на «новый сервер» (второй кластер/контейнер) **без** globals.
3. Убедись, что приложение не может подключиться. Почини, применив `globals.sql`.

<details><summary>Ответ</summary>

Ошибка `role "app" does not exist` (или `permission denied`) до применения globals.

</details>

#### C4. Скорость форматов
Налей таблицу на несколько миллионов строк и сравни время:
`-F p`, `-F c`, `-F d -j 4`; восстановление `psql -f` vs `pg_restore -j 4`.
Запиши цифры — это аргументы в споре «почему не plain».

<details><summary>Ответ</summary>

Обычно `-F d -j 4` в разы быстрее на снятии, `pg_restore -j 4` — в разы быстрее
на восстановлении; plain не параллелится.

</details>

#### C5. 🔑 Физический бэкап
1. Создай роль с `REPLICATION`, добавь строку `replication` в `pg_hba.conf`, сделай reload.
2. Сними `pg_basebackup -Ft -z -Xs`.
3. Разверни его на втором кластере (другой порт) и запусти. Проверь данные.

<details><summary>Ответ</summary>

Второй кластер должен подняться с теми же данными: физическая копия — побайтовая.

</details>

#### C6. Архивация WAL
1. Включи `archive_mode`, `archive_command` (в каталог `/arch`), сделай restart.
2. Сгенерируй нагрузку, посмотри, что файлы появляются в `/arch`.
3. Проверь `SELECT * FROM pg_stat_archiver;`
4. Сломай `archive_command` (укажи несуществующий каталог) и посмотри, что происходит
   с `failed_count` и размером `pg_wal`. Почини.

<details><summary>Ответ</summary>

При сломанном `archive_command` `failed_count` растёт, сегменты остаются в `pg_wal`,
каталог пухнет. После починки PostgreSQL доархивирует накопленное.

</details>

#### C7. 🔑 PITR — полный прогон
1. Сними базовую копию, включи архивацию.
2. Вставь данные, запомни время (`SELECT now();`), вставь ещё, затем «сломай»:
   `DROP TABLE orders;` — запиши точное время аварии.
3. Восстанови кластер на момент **до** `DROP`: базовая копия + `restore_command` +
   `recovery_target_time` + `recovery.signal`.
4. Проверь, что таблица на месте, а более поздние данные отсутствуют.
5. Запиши всю последовательность как рунбук.

<details><summary>Ответ</summary>

Проверка успеха: таблица `orders` на месте; данные, вставленные после
`recovery_target_time`, отсутствуют; `pg_is_in_recovery()` возвращает `f` после promote.

</details>

#### C8. Именованная точка восстановления
`SELECT pg_create_restore_point('before_migration');` — сделай точку, «сломай» данные,
восстановись по `recovery_target_name`.

#### C9. WAL-G (со звёздочкой)
Подними MinIO (S3-совместимое хранилище) в докере, настрой WAL-G:
`backup-push`, `backup-list`, `wal-push` в `archive_command`, затем полное
восстановление `backup-fetch` + `wal-fetch`.

<details><summary>Ответ</summary>

Плюс WAL-G — retention и дельта-бэкапы; restore_command берёт сегменты прямо из S3.

</details>

#### C10. Скрипт проверки бэкапа
Напиши скрипт, который: находит последний бэкап, восстанавливает его во временный
инстанс, выполняет проверки (`SELECT count(*)` по ключевым таблицам, `pg_is_in_recovery`),
пишет результат в лог и возвращает ненулевой код при ошибке. Это заготовка для
регулярной автоматической проверки.

<details><summary>Ответ</summary>

В скрипте важны: `set -euo pipefail`, уникальный временный каталог, проверка
кода возврата `pg_restore`, содержательные проверки данных, уведомление в мониторинг.

</details>

### Блок D. Инциденты

**D1.** Разработчик выполнил `DELETE FROM orders` без `WHERE` 20 минут назад.
Опиши план действий по шагам.

<details><summary>Ответ</summary>

1) остановить запись в затронутую таблицу (выключить сервис/забрать права),
2) зафиксировать точное время инцидента, 3) убедиться, что есть базовая копия и архив WAL,
4) поднять **отдельный** инстанс и сделать PITR на момент до `DELETE`,
5) выгрузить нужные строки (`pg_dump -t`/`COPY`) и перенести в прод,
6) сверить данные, включить запись, 7) написать постмортем и закрыть возможность
выполнять такое без ограничений (права, `statement_timeout`, ревью миграций).

</details>

**D2.** `pg_wal` вырос до 200 ГБ, место кончается. Что проверишь в первую очередь?

<details><summary>Ответ</summary>

Неактивные слоты репликации (`pg_replication_slots.active = false`),
сломанная архивация (`pg_stat_archiver.failed_count`), очень большой
`max_wal_size`/`wal_keep_size`, отставшая реплика. Файлы из `pg_wal` руками не удалять.

</details>

**D3.** Восстановили дамп на новый сервер — приложение получает
`FATAL: role "app" does not exist`. Причина и решение.

<details><summary>Ответ</summary>

Не восстановлены globals. Применить `psql -f globals.sql` (или создать роли руками),
затем проверить права.

</details>

**D4.** PITR не доходит до нужного времени: в логе
`could not receive data … requested WAL segment has already been removed`. Что случилось?

<details><summary>Ответ</summary>

Нужные сегменты WAL удалены из архива (агрессивный retention, ручная чистка,
`|| true` в `archive_command`). Восстановление возможно только до последнего доступного
сегмента. Вывод — retention архива согласуют с глубиной хранения базовых копий.

</details>

**D5.** Бэкапы «делаются», но восстановить не получается: файл 0 байт. Как этого избежать?

<details><summary>Ответ</summary>

Нет проверки кода возврата и размера файла, нет уведомления об ошибке,
нет проверки восстановления. Добавить `set -euo pipefail`, контроль размера, алерт
на возраст/статус, регулярный test restore.

</details>

**D6.** Умер сервер с базой. Есть вчерашний полный бэкап и архив WAL.
Какой RPO получится и как действовать?

<details><summary>Ответ</summary>

RPO = потеря данных с момента последнего успешно заархивированного сегмента WAL
(минуты, если `archive_timeout` настроен). Действия: новый сервер → развернуть базовую
копию → `restore_command` из архива → восстановление до конца WAL → promote → проверить
данные → переключить приложение.

</details>

**D7.** В процессе восстановления выяснилось, что базовая копия старше, чем самый ранний
WAL в архиве. Что это значит?

<details><summary>Ответ</summary>

Разрыв в цепочке WAL: доиграть базовую копию до нужного момента нельзя.
Значит, retention архива короче, чем возраст базовой копии — схема бэкапов настроена
неправильно.

</details>

**D8.** Шифровальщик зашифровал прод и примонтированный каталог с бэкапами.
Что в схеме бэкапов было сделано неправильно?

<details><summary>Ответ</summary>

Бэкапы были доступны на запись с прод-сервера и лежали на той же площадке.
Нужны отдельные креды, pull-модель или immutable-хранилище (object lock, версионирование),
копия вне площадки.

</details>

**D9.** Восстановление тестовой копии прода заняло 9 часов, бизнес ожидал час.
Какие есть варианты сократить RTO?

<details><summary>Ответ</summary>

Параллельное восстановление (`-j`), физический бэкап вместо логического,
дельта-бэкапы, горячая реплика для promote, готовый «тёплый» стенд, более быстрые диски,
регулярные репетиции с замером времени.

</details>

**D10.** Нужно отдать разработчикам копию прода для отладки. Какие риски и как их закрыть?

<details><summary>Ответ</summary>

Персональные данные уезжают из контура. Закрывается маскированием/анонимизацией
при выгрузке, отдельным ограниченным окружением, запретом на выгрузку полного прода,
логированием доступа и согласованием с безопасностью.

</details>

### Блок E. Вопросы с собеседования

**1.** Как ты делаешь бэкапы PostgreSQL?

<details><summary>Ответ</summary>

Физический бэкап (pgBackRest/WAL-G) в объектное хранилище + непрерывная архивация WAL,
логический дамп дополнительно; расписание, retention, шифрование, мониторинг и
регулярное тестовое восстановление.

</details>

**2.** Чем логический бэкап отличается от физического?

<details><summary>Ответ</summary>

Логический — переносимый и выборочный, но медленный и без PITR; физический — быстрый,
с PITR, но привязан к версии и восстанавливается целиком.

</details>

**3.** Что такое PITR и как он работает?

<details><summary>Ответ</summary>

Базовая копия + архив WAL, восстановление доигрыванием журнала до заданного момента.

</details>

**4.** Как восстановить одну таблицу из бэкапа?

<details><summary>Ответ</summary>

`pg_restore -t` из custom/directory-дампа или PITR в отдельный инстанс с последующей выгрузкой.

</details>

**5.** Что `pg_dump` не сохраняет?

<details><summary>Ответ</summary>

Роли, пароли, права кластера, табличные пространства, настройки сервера.

</details>

**6.** Что такое RPO и RTO, какие значения у вас были?

<details><summary>Ответ</summary>

RPO — допустимая потеря данных, RTO — время восстановления; называешь свои реальные
цифры и то, как они обеспечены.

</details>

**7.** Как ты проверяешь, что бэкап рабочий?

<details><summary>Ответ</summary>

Регулярным тестовым восстановлением на отдельный сервер с автоматическими проверками
(число строк, ключевые запросы), а не «файл создался».

</details>

**8.** Что мониторишь по бэкапам?

<details><summary>Ответ</summary>

Возраст и статус последнего бэкапа, размер, ошибки архивации WAL, место в хранилище,
дату последней успешной проверки восстановления.

</details>

**9.** Реплика может заменить бэкап?

<details><summary>Ответ</summary>

Нет: реплика мгновенно повторяет ошибочные операции; она про доступность, а не про откат.

</details>

**10.** Опиши действия при `DROP TABLE` на проде.

<details><summary>Ответ</summary>

Изолировать, зафиксировать время, восстановить в отдельный инстанс через PITR,
перенести таблицу, проверить, включить нагрузку, постмортем и ограничение прав.

</details>
