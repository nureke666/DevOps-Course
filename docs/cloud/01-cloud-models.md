# 01. Модели облаков: IaaS, PaaS, SaaS

> Роадмап → 7. Остальное → Облака: *«Понимать IaaS, PaaS, SaaS»*.
>
> **После темы ты умеешь:** объяснить модели облачных сервисов, разобраться в структуре
> любого провайдера (регионы, зоны, проекты, IAM), понимать зону ответственности
> и то, из чего складывается счёт. Параллельно держишь в голове три семейства:
> **AWS**, **Yandex Cloud** и **облака РК** (провайдеры с ЦОД в Казахстане).

## 🗺️ Три модели одной картинкой

```text:no-line-numbers
            ON-PREM        IaaS          PaaS          SaaS
          (своё железо)  (ВМ в облаке) (платформа)  (готовый сервис)
        ┌──────────────┬─────────────┬─────────────┬──────────────┐
данные  │     ТЫ       │     ТЫ      │     ТЫ      │     ТЫ       │
прилож. │     ТЫ       │     ТЫ      │     ТЫ      │  провайдер   │
рантайм │     ТЫ       │     ТЫ      │  провайдер  │  провайдер   │
ОС      │     ТЫ       │     ТЫ      │  провайдер  │  провайдер   │
вирт-я  │     ТЫ       │  провайдер  │  провайдер  │  провайдер   │
железо  │     ТЫ       │  провайдер  │  провайдер  │  провайдер   │
        └──────────────┴─────────────┴─────────────┴──────────────┘
         максимум          твоя зона ответственности сужается →
         контроля                                    максимум удобства
```

| Модель | Что получаешь | AWS | Yandex Cloud | Облака РК | Твоя работа |
|--------|---------------|-----|--------------|-----------|-------------|
| **IaaS** | ВМ, диски, сеть, балансировщики | EC2, EBS, VPC | Compute Cloud, VPC | Облачные серверы на OpenStack (PS Cloud, Kazteleport), IaaS QazCloud | Ставишь пакеты, настраиваешь всё сам |
| **PaaS** | Платформа под приложение/данные | RDS, EKS, Elastic Beanstalk | Managed PostgreSQL, Managed Kubernetes | Managed Kubernetes (PS Cloud, Kazteleport); managed-БД — сверяй по каталогу | Даёшь приложение/схему, не занимаешься сервером |
| **SaaS** | Готовый продукт | — | — | — | Пользуешься (GitLab.com, Grafana Cloud, почта, CRM) |
| **FaaS/Serverless** | Функция по событию | Lambda | Cloud Functions | обычно нет — проверь | Пишешь функцию, платишь за вызовы |
| **CaaS** | Контейнеры как сервис | ECS/Fargate, EKS | Managed Kubernetes, Serverless Containers | Managed Kubernetes | Даёшь образ |

⭐ Практический критерий для девопса: **где заканчивается твой `ssh`**.
В IaaS ты заходишь на машину; в PaaS — нет, только API и настройки; в SaaS — только UI.

## 1. Из чего состоит любое облако

```text:no-line-numbers
 ОРГАНИЗАЦИЯ / АККАУНТ
 └── ОБЛАКО / ПРОЕКТ / ПОДПИСКА        ← единица биллинга и изоляции
     ├── КАТАЛОГ / РЕСУРС-ГРУППА       ← логическая группировка (prod, stage)
     │   ├── VPC (сеть) → подсети по зонам
     │   ├── ВМ, диски, снапшоты
     │   ├── бакеты объектного хранилища
     │   ├── managed-сервисы (БД, k8s, кэш)
     │   └── сервисные аккаунты и роли (IAM)
     └── биллинг, квоты, лимиты, бюджеты
```

| Понятие | Смысл | Практика |
|---------|-------|----------|
| **Регион** | Географическая область (страна/город) | Выбирается по близости к пользователям и по требованиям к данным |
| **Зона доступности (AZ)** | Отдельный дата-центр внутри региона | ⭐ Прод размазывают минимум по двум зонам (если они есть в регионе!) |
| **Проект/каталог** | Группировка ресурсов и прав | Отдельные каталоги для prod и stage |
| **IAM** | Кто что может делать | Роли пользователям и **сервисным аккаунтам** |
| **Квоты** | Лимиты на число ресурсов | Упираешься в них внезапно — планируй заранее |
| **Теги/метки** | Маркировка ресурсов | Нужны для учёта расходов и автоматизации |

### Те же понятия у трёх семейств

| Понятие | AWS | Yandex Cloud | Облака РК (OpenStack-подобные) |
|---------|-----|--------------|--------------------------------|
| Верх иерархии | AWS Organization → OU → **аккаунт** | Организация → **облако** → **каталог** | Домен/договор → **проект** (tenant) |
| Единица изоляции prod/stage | Отдельный аккаунт на окружение | Отдельный каталог (или облако) | Отдельный проект |
| Регион | `eu-central-1` и т.п.; **в Казахстане региона AWS нет** | `ru-central1` и **`kz1` (Казахстан)** | ЦОД в РК: PS Cloud — зоны Алматы и Астана; Kazteleport — три ЦОД в Алматы; QazCloud — ЦОД под Астаной (Косшы) и в регионах |
| Зона | `eu-central-1a`, `-b`, `-c` | `ru-central1-a/b/d`; в `kz1` **одна зона `kz1-a`** ⚠️ | зависит от провайдера |
| IAM | IAM: пользователи, группы, **роли**, JSON-политики, STS | IAM: роли на облако/каталог/ресурс, **сервисные аккаунты** | Keystone: пользователи, проекты, роли; application credentials |
| CLI | `aws` | `yc` | `openstack` (PS Cloud, Kazteleport) или консоль |
| Terraform-провайдер | `hashicorp/aws` | `yandex-cloud/yandex` | `terraform-provider-openstack/openstack` (PS Cloud и Kazteleport заявляют интеграцию с Terraform) |
| Аудит действий | CloudTrail | Audit Trails (есть и в `kz1`) | уточняй у провайдера |
| Метки | tags | labels | metadata/tags |
| Валюта счёта | USD | в `kz1` — тенге | тенге |

```bash
# AWS: кто я и что вокруг
aws configure                               # access key / secret / регион по умолчанию
aws sts get-caller-identity                 # ⭐ «под кем я работаю» — первая команда
aws ec2 describe-regions --output table
aws ec2 describe-availability-zones --region eu-central-1

# Yandex Cloud: профиль под нужный регион
yc init                                     # регион ru-central1
yc init --region=kz                         # ⭐ отдельный профиль для региона Казахстан
yc config profile list
yc config list                              # облако, каталог, зона по умолчанию
yc compute zone list                        # в kz-профиле будет только kz1-a

# Облака РК на OpenStack: openrc/clouds.yaml из консоли провайдера
openstack token issue                       # проверка авторизации
openstack availability zone list
```

```text:no-line-numbers
Отказоустойчивость по зонам:
  ВМ в zone-a ──┐
                ├── балансировщик ──► приложение переживает падение одного ДЦ
  ВМ в zone-b ──┘
  база: primary в zone-a + реплика в zone-b

⚠️ Если в регионе ОДНА зона (как kz1 у Yandex Cloud) — такой схемы внутри региона
   нет. Остаются: несколько хостов в зоне, бэкапы, план восстановления (DR)
   и, если позволяет закон о данных, второй провайдер/площадка в РК.
```

## 2. Зона ответственности (shared responsibility)

```text:no-line-numbers
 ПРОВАЙДЕР ОТВЕЧАЕТ ЗА ОБЛАКО          ТЫ ОТВЕЧАЕШЬ ЗА ТО, ЧТО В ОБЛАКЕ
 ─────────────────────────────         ─────────────────────────────────
 дата-центр, питание, сеть             настройки доступа (IAM, ключи)
 гипервизор, физическая безопасность   security groups и firewall
 доступность сервисов по SLA           обновления ОС и приложений (в IaaS)
 бэкапы managed-сервисов               ⭐ ПРОВЕРКА восстановления
 шифрование инфраструктуры             шифрование своих данных и ключи
                                       ⭐ ГДЕ лежат данные (регион, бэкапы, логи)
```

Частые заблуждения:
- «В облаке бэкапы делает провайдер» — только для managed-сервисов и только по настроенной
  политике. Данные на диске твоей ВМ — твоя забота.
- «Облако безопасно само по себе» — 95% инцидентов это открытый наружу порт,
  публичный бакет и утёкший ключ, то есть твоя часть.
- «SLA 99,95% — значит не упадёт» — SLA это компенсация, а не гарантия.
- «Провайдер с ЦОД в РК — значит мы соблюдаем закон» — локализация касается и бэкапов,
  и логов, и SaaS-инструментов; разбираться всё равно тебе (с юристом).

## 3. Как устроены деньги

| Что тарифицируется | Нюанс |
|--------------------|-------|
| ВМ (vCPU/RAM) | По времени работы; остановленная ВМ обычно не считается, **диск считается** |
| Диски | Постоянно, независимо от состояния ВМ ⚠️ |
| Снапшоты и образы | По объёму |
| Публичный IP | Часто платный; в AWS с 01.02.2024 платный **каждый** публичный IPv4 (порядок 0,005 $/ч ≈ 3,6 $/мес, проверь) |
| Исходящий трафик | ⭐ Главный «сюрприз» в счетах; входящий обычно бесплатный |
| Объектное хранилище | Объём + количество операций + исходящий трафик |
| Managed-сервисы | Дороже самостоятельного развёртывания, но включают работу |
| Балансировщики, NAT | Почасово + за трафик (AWS NAT Gateway — порядок десятков $/мес только за «включён», проверь в калькуляторе) |

```text:no-line-numbers
Как не разориться на учебном стенде:
1. Бюджет с уведомлением на 10% лимита — сразу после регистрации.
2. Прерываемые (spot/preemptible) ВМ — дешевле в разы, годятся для учёбы.
3. Минимальные конфигурации (2 vCPU / 2 ГБ) и HDD вместо SSD.
4. Убирать за собой: ВМ, диски, снапшоты, IP, балансировщики, бакеты.
5. Смотреть детализацию счёта раз в неделю — это тренирует «облачное мышление».
```

### Бесплатный старт и бюджеты (проверь, сентябрь 2026)

| | AWS | Yandex Cloud | Облака РК |
|--|-----|--------------|-----------|
| Старт | С 15.07.2025 при регистрации выбираешь **Free plan** или **Paid plan**: до 200 $ кредитов (100 $ сразу + до 100 $ за учебные активности); Free plan живёт до 6 месяцев или пока не кончатся кредиты, потом аккаунт закрывается, если не перейти на Paid | Стартовый грант на 60 дней; для резидентов РК — от 38 400 ₸ (личный аккаунт; у бизнес-аккаунта при оплате переводом — 80 000 ₸) | Тестовый период — по запросу у провайдера, условия публично не всегда описаны |
| Бюджет и алерты | AWS Budgets (+ Cost Explorer, Cost Anomaly Detection) | Бюджеты в Billing с уведомлениями | Личный кабинет/договор; уточняй, есть ли алерты |
| Калькулятор | calculator.aws | калькулятор на сайте (`/ru-kz/prices` для РК) | прайс на сайте провайдера, в тенге |

```bash
# AWS: бюджет из CLI (или в консоли Billing → Budgets)
aws budgets create-budget --account-id 123456789012 \
  --budget '{"BudgetName":"study","BudgetLimit":{"Amount":"10","Unit":"USD"},
             "TimeUnit":"MONTHLY","BudgetType":"COST"}' \
  --notifications-with-subscribers '[{"Notification":{"NotificationType":"ACTUAL",
      "ComparisonOperator":"GREATER_THAN","Threshold":20,"ThresholdType":"PERCENTAGE"},
      "Subscribers":[{"SubscriptionType":"EMAIL","Address":"me@example.com"}]}]'
# Yandex Cloud: бюджет удобнее завести в консоли Billing (kz.center.yandex.cloud для РК)
```

Оптимизация в проде: right-sizing (не брать лишнее), автоматическое выключение
dev/stage на ночь, резервирование мощностей со скидкой (committed use / Savings Plans),
spot для батчей, lifecycle-политики в хранилище, контроль трафика.

## 4. Региональная специфика (Казахстан)

```text:no-line-numbers
Роадмап писался для России: AWS и GCP ушли, рынок заняли локальные облака.
В Казахстане выбор шире, и решает не «что доступно», а требования проекта:

 ┌───────────────────┐  ┌──────────────────────┐  ┌─────────────────────────┐
 │ AWS (и GCP/Azure) │  │ Yandex Cloud         │  │ облака РК               │
 │ максимум сервисов │  │ регион kz1 (ЦОД в РК,│  │ PS Cloud, Kazteleport,  │
 │ региона в РК НЕТ  │  │ одна зона kz1-a)     │  │ QazCloud (и VK Cloud KZ)│
 │                   │  │ + ru-central1        │  │ ЦОД в РК, OpenStack-API │
 └───────────────────┘  └──────────────────────┘  └─────────────────────────┘
 Вопросы выбора: где по закону должны лежать данные? как платим? какие сервисы нужны?
 нужна ли мультизонность? есть ли Terraform-провайдер?
```

| Что это значит на практике | Комментарий |
|----------------------------|-------------|
| Концепции те же | VPC, подсети, security groups, S3-совместимое хранилище, managed-базы, IAM |
| ⭐ Локализация данных | Закон РК о персональных данных требует хранить базы с ПДн граждан РК на территории Казахстана — вместе с бэкапами и логами, где эти ПДн есть. Отсюда выбор провайдера и региона для прода |
| AWS для ПДн граждан РК | Региона AWS в Казахстане нет → базы с ПДн там не разместишь; AWS остаётся для проектов без ПДн РК, зарубежных рынков, обезличенных данных, обучения |
| Yandex Cloud `kz1` | Отдельная площадка: своя консоль (`kz.console.yandex.cloud`), свой биллинг в тенге, свои API-адреса (`*.api.yandexcloud.kz`, хранилище `storage.yandexcloud.kz`); данные регионов изолированы. Подключает регион владелец организации. **Одна зона** — мультизонность внутри региона невозможна |
| Облака РК | PS Cloud и Kazteleport — OpenStack API/CLI, заявлены Terraform, S3-хранилище, Managed Kubernetes; QazCloud — IaaS, BaaS/DRaaS, хранилище, исторически ориентирован на госсектор и группу «Самрук-Қазына»; VK Cloud в РК оказывает ТОО «QazCloud» |
| Санкции и оплата | Доступ к сервису и способ оплаты зависят от юрисдикции провайдера, банка и карты, и правила могут меняться. Для важного прода держат план выхода: инфраструктура как код, бэкапы вне аккаунта (с учётом локализации), минимум уникальных сервисов одного провайдера |
| [Terraform](/terraform/) работает | У AWS и Yandex Cloud — свои провайдеры; у OpenStack-облаков — провайдер OpenStack; у небольшого провайдера сначала проверь, что он реально умеет |
| Совместимость с S3 API | Объектные хранилища говорят по протоколу S3 — работают `aws s3`, `s3cmd`, `boto3`, `mc` |
| Набор сервисов разный | У региональных провайдеров он обычно скромнее, чем у глобальных: сверяй по их каталогу то, что реально нужно проекту |
| Документация AWS полезна | Как учебник по понятиям, даже если руками работаешь в другом облаке |

> 💡 Учить стоит понятия, а руками работать там, где есть доступ и бесплатный старт
> (Free plan у AWS, грант у Yandex Cloud, trial у локального провайдера — условия
> меняются, смотри на сайте на момент регистрации). Глубже:

## 5. Публичное, частное, гибридное

| Модель | Что это | Когда |
|--------|---------|-------|
| **Публичное** | Ресурсы провайдера, общие для всех клиентов | Дефолт для новых проектов |
| **Частное** | Облако внутри компании (OpenStack и т.п.) | Требования безопасности, большой масштаб |
| **Гибридное** | Часть в своём ДЦ, часть в облаке | Миграция, чувствительные данные |
| **Мультиклауд** | Несколько провайдеров | Снижение зависимости, но резко растёт сложность |

```text:no-line-numbers
Типичный «казахстанский гибрид»:
  ПДн граждан РК (прод-база, её бэкапы, логи с ПДн)  → облако РК / Yandex kz1
  обезличенная аналитика, CDN, CI, dev-стенды        → AWS или любой другой регион
  между ними — VPN/выделенный канал и строгий контроль, какие данные куда уходят
```

⚠️ Vendor lock-in: чем больше специфичных сервисов провайдера используется, тем дороже
переезд. Смягчают стандартными технологиями (Kubernetes, PostgreSQL, S3-совместимое API)
и инфраструктурой как кодом.

## 7. Грабли

| Грабля | Последствие | Решение |
|--------|-------------|---------|
| Работа из-под root-аккаунта AWS / владельца облака | Утечка ключа = потеря всего | MFA на root, отдельные пользователи/роли, root не используется |
| CLI смотрит «не туда» | Создал ресурсы в чужом регионе/каталоге/аккаунте | `aws sts get-caller-identity`, `yc config list` перед работой |
| Ищешь ресурсы `kz1` в обычной консоли Yandex | «Ничего нет» | У региона Казахстан своя консоль и свой профиль `yc` |
| Считаешь, что в `kz1` есть мультизонность | HA-схема не собирается | Одна зона — планируй DR иначе |
| Бюджет не настроен | Грант/кредиты ушли за выходные | Бюджет и алерты в первый день |
| Free plan AWS закончился | Аккаунт закрыт вместе с ресурсами | Перейти на Paid заранее или выгрузить нужное |
| ПДн граждан РК в зарубежном регионе | Нарушение требований о локализации | Регион/провайдер в РК для таких данных |

## 💼 Как это в DevOps

- Первый вопрос при новом проекте: **какое облако и почему** — от этого зависят
  доступные managed-сервисы, стоимость, инструменты и соответствие закону о ПДн.
- Доступ людей и CI в облако — через IAM-роли и сервисные аккаунты с минимальными
  правами; статические ключи хранятся в [Vault](/vault/),
  а лучше вообще заменяются на OIDC-федерацию из CI.
- Ресурсы создаются Terraform'ом, а не руками в консоли: иначе никто не знает,
  что откуда взялось (и половина остаётся неиспользуемой, но оплачиваемой).
- Теги обязательны: `env`, `project`, `owner`, `managed-by=terraform` — по ним
  считают деньги и находят «сирот».
- Контроль расходов — регулярная задача: отчёт по расходам, поиск неиспользуемых
  дисков, IP и снапшотов.
- В казахстанской компании часто живут **два облака сразу**: локальное (или `kz1`)
  для данных с ПДн и глобальное для всего остального — и девопс отвечает за границу между ними.

## 📌 Шпаргалка

| Термин | Одной строкой |
|--------|---------------|
| IaaS | Виртуальные машины, диски, сеть — остальное твоё |
| PaaS | Управляемая платформа (БД, k8s) — ОС не твоя забота |
| SaaS | Готовый продукт по подписке |
| FaaS | Функция по событию, оплата за вызовы (Lambda, Cloud Functions) |
| Регион | Географическая площадка (`eu-central-1`, `ru-central1`, `kz1`) |
| Зона доступности | Отдельный ДЦ внутри региона; прод — минимум в двух (в `kz1` — одна) |
| Проект/каталог | Группировка ресурсов и прав: аккаунт AWS / каталог Yandex / проект OpenStack |
| IAM | Права пользователей и сервисных аккаунтов (ролей) |
| Квота | Лимит на количество ресурсов |
| Shared responsibility | Провайдер отвечает за облако, ты — за то, что в нём |
| Spot/preemptible | Дешёвые прерываемые ВМ |
| Vendor lock-in | Зависимость от специфичных сервисов провайдера |
| Egress | Исходящий трафик — главный источник неожиданных счетов |
| «Кто я» в CLI | `aws sts get-caller-identity` · `yc config list` · `openstack token issue` |
| Профиль Yandex для РК | `yc init --region=kz` |

## 🧠 Что запомнить

1. IaaS/PaaS/SaaS отличаются тем, где заканчивается твоя зона ответственности.
2. Практический критерий: в IaaS у тебя есть SSH, в PaaS — только API и настройки.
3. Любое облако устроено одинаково: аккаунт → проект → ресурсы, плюс IAM, квоты, биллинг.
   AWS: аккаунт; Yandex: облако → каталог; OpenStack-облака РК: проект.
4. ⭐ Прод размещают минимум в двух зонах доступности одного региона — если зон
   несколько; в Yandex `kz1` зона одна, это надо учитывать в архитектуре.
5. Shared responsibility: провайдер отвечает за инфраструктуру, ты — за доступы,
   настройки, обновления, проверку бэкапов и за то, где лежат данные.
6. Диски, публичные IP и исходящий трафик тарифицируются даже тогда, когда «ничего
   не работает»; в AWS платный каждый публичный IPv4.
7. В Казахстане выбор — AWS (региона в РК нет), Yandex Cloud (`kz1` в РК) или локальный
   провайдер; решают локализация ПДн, оплата и нужный набор сервисов, а понятия везде одни.
8. Объектные хранилища почти везде совместимы с S3 API — инструменты одни и те же.
9. Vendor lock-in уменьшают стандартными технологиями и инфраструктурой как кодом.
10. Учиться правильно в порядке: консоль → CLI → Terraform, а не наоборот; бюджет —
    в первый же день.

### Блок A. Теория

**A1.** Объясни IaaS, PaaS, SaaS через зону ответственности. Приведи по два примера.

<details><summary>Ответ</summary>

IaaS — провайдер даёт железо и виртуализацию (ВМ, диски, сеть), остальное твоё
(EC2 в AWS, Compute Cloud в Yandex Cloud, облачные серверы PS Cloud/Kazteleport).
PaaS — провайдер отвечает и за ОС с рантаймом (RDS / Managed PostgreSQL, EKS / Managed
Kubernetes), ты отвечаешь за приложение и данные. SaaS — готовый продукт
(GitLab.com, Grafana Cloud), ты отвечаешь только за свои данные и доступы.

</details>

**A2.** ⭐ Какой практический критерий отличает IaaS от PaaS для девопса?

<details><summary>Ответ</summary>

Наличие SSH: в IaaS ты заходишь внутрь машины и сам её обслуживаешь,
в PaaS доступа к ОС нет — только API, параметры и логи.

</details>

**A3.** Что такое FaaS/serverless и когда его берут?

<details><summary>Ответ</summary>

Выполнение функции по событию с оплатой за вызовы и время работы.
Берут для редких/эпизодических задач, обработчиков событий, вебхуков, склейки сервисов.

</details>

**A4.** Из каких уровней состоит структура ресурсов облака?

<details><summary>Ответ</summary>

Организация/аккаунт → облако/проект/подписка (биллинг и изоляция) →
каталог/ресурс-группа → сами ресурсы (сети, ВМ, диски, бакеты, managed-сервисы),
плюс сквозные IAM, квоты, теги. В AWS: Organization → OU → аккаунт → ресурсы в регионах;
в Yandex Cloud: организация → облако → каталог; в OpenStack-облаке: проект.

</details>

**A5.** Чем регион отличается от зоны доступности? Зачем нужны несколько зон?

<details><summary>Ответ</summary>

Регион — географическая площадка (город/страна), зона доступности — отдельный
дата-центр внутри региона с независимым питанием и сетью. Несколько зон нужны,
чтобы падение одного ДЦ не уронило сервис.

</details>

**A6.** Что такое IAM и чем сервисный аккаунт отличается от пользователя?

<details><summary>Ответ</summary>

IAM — система прав: кто и какие действия может выполнять с какими ресурсами.
Пользователь — человек, сервисный аккаунт — «робот» для приложений, CI и ВМ;
ему выдают ключ или привязывают к инстансу. В AWS роль «робота» играет **IAM-роль**
(её принимает ВМ через instance profile, под через Pod Identity, CI через OIDC);
в Yandex Cloud — **сервисный аккаунт** с ролями на каталог/облако.

</details>

**A7.** Что такое квоты и почему о них надо помнить заранее?

<details><summary>Ответ</summary>

Лимиты на количество ресурсов (ВМ, ядер, IP, дисков). Они всплывают
в самый неподходящий момент — при масштабировании или аварийном развёртывании;
повышение квоты может занять время.

</details>

**A8.** Что входит в зону ответственности провайдера, а что — в твою?

<details><summary>Ответ</summary>

Провайдер: дата-центр, питание, сеть, гипервизор, физическая безопасность,
доступность сервисов. Ты: доступы и IAM, security groups, обновления ОС и приложений,
свои данные и их бэкапы, шифрование, проверка восстановления, мониторинг.

</details>

**A9.** Верно ли, что «в облаке бэкапы делает провайдер»? Развернуто.

<details><summary>Ответ</summary>

Неверно в общем случае. Для managed-сервисов бэкапы делает провайдер,
но по настроенной тобой политике и с твоей ответственностью за проверку восстановления.
Данные на диске твоей ВМ бэкапишь ты (снапшоты, дампы в объектное хранилище).

</details>

**A10.** Что означает SLA 99,95% и что он гарантирует на практике?

<details><summary>Ответ</summary>

Это обязательство по доступности с компенсацией (обычно в виде скидки)
при нарушении. Он не гарантирует, что сбоя не будет, и не покрывает ваши убытки —
отказоустойчивость всё равно проектируешь сам.

</details>

**A11.** За что в облаке платят, даже когда ВМ выключена?

<details><summary>Ответ</summary>

Диски (в том числе отключённые), снапшоты и образы, зарезервированные публичные
IP, балансировщики, NAT-шлюзы, объектное хранилище, managed-сервисы.

</details>

**A12.** Почему исходящий трафик часто становится сюрпризом в счёте?

<details><summary>Ответ</summary>

Он тарифицируется отдельно и часто дороже вычислений; «тяжёлые» сценарии
(раздача файлов и видео напрямую с ВМ, репликация между регионами, выгрузки данных)
дают счета, которых никто не ожидал.

</details>

**A13.** Назови пять способов сократить расходы на облако.

<details><summary>Ответ</summary>

Right-sizing (не брать лишнее), выключение dev/stage на ночь, spot/прерываемые
ВМ, резервирование со скидкой для стабильной нагрузки, lifecycle-политики в хранилище
и удаление «сирот», CDN/кэширование вместо прямого egress.

</details>

**A14.** В чём региональная специфика облачного рынка для Казахстана и что это меняет для девопса?

<details><summary>Ответ</summary>

Выбор шире, чем в российском роадмапе: доступны AWS/GCP/Azure (но региона AWS
в РК нет), Yandex Cloud с регионом `kz1` в Казахстане, казахстанские провайдеры (PS Cloud,
Kazteleport, QazCloud). Решают требования: закон РК требует хранить персональные данные
граждан в Казахстане (включая бэкапы и логи с ПДн), поэтому прод с ПДн размещают
на территории РК; плюс платёжные и санкционные риски и нужный набор сервисов.
Для девопса меняются названия и часть возможностей, но концепции (VPC, secgroups,
S3-совместимое хранилище, managed-сервисы, Terraform-провайдеры) остаются теми же.

</details>

**A15.** Что такое vendor lock-in и как его уменьшают?

<details><summary>Ответ</summary>

Зависимость от специфичных сервисов провайдера, из-за которой переезд становится
дорогим. Снижают использованием стандартных технологий (Kubernetes, PostgreSQL,
S3 API), инфраструктурой как кодом и явной оценкой «что мы будем делать при переезде».

</details>

**A16.** Сопоставь иерархию ресурсов AWS, Yandex Cloud и OpenStack-облака РК:
что у каждого является «единицей изоляции prod/stage»?

<details><summary>Ответ</summary>

AWS: Organization → OU → **аккаунт** (prod и stage — разные аккаунты, это жёсткая
граница прав и биллинга). Yandex Cloud: организация → облако → **каталог** (prod/stage —
разные каталоги, для строгой изоляции — разные облака). OpenStack-облако РК: **проект**
(tenant) внутри договора. Смысл одинаковый: отдельная единица с правами, квотами и счётом.

</details>

**A17.** 🟦🇰🇿 Чем регион Yandex Cloud `kz1` отличается от `ru-central1` и что это меняет
для отказоустойчивости?

<details><summary>Ответ</summary>

`kz1` — отдельная площадка Yandex Cloud в Казахстане: своя консоль
(`kz.console.yandex.cloud`), биллинг в тенге, свои API-адреса (`*.api.yandexcloud.kz`,
хранилище `storage.yandexcloud.kz`), отдельный профиль `yc init --region=kz`; данные регионов
изолированы. Главное отличие для архитектуры — **одна зона `kz1-a`**: разнести прод по зонам
внутри региона нельзя, отказоустойчивость строится несколькими хостами, бэкапами и планом DR
(проверь, сентябрь 2026 — зоны могут добавить).

</details>

**A18.** 🟧 Как устроен бесплатный старт AWS для новых аккаунтов с июля 2025 года
и что произойдёт, когда он закончится?

<details><summary>Ответ</summary>

С 15.07.2025 новый аккаунт выбирает Free plan или Paid plan. Даётся 100 $ кредитов
и ещё до 100 $ за учебные активности; Free plan действует до 6 месяцев или до исчерпания
кредитов, после чего аккаунт закрывается, если не перейти на Paid (кредиты при переходе
сохраняются). Плюс «always free» лимиты ряда сервисов. Проверь условия на момент регистрации.

</details>

**A19.** 🇰🇿 Почему для базы с персональными данными граждан РК не подходит AWS,
а для CI-раннеров и обезличенной аналитики — подходит?

<details><summary>Ответ</summary>

Закон РК требует хранить базы с ПДн граждан РК на территории Казахстана,
а региона AWS в РК нет — значит, прод-база с ПДн, её бэкапы и логи с ПДн в AWS не живут.
CI-раннеры, сборка образов, обезличенная аналитика, dev-стенды на синтетических данных
ПДн не содержат — для них ограничение не действует (граница должна быть явной и проверяемой).

</details>

### Блок B. «Классифицируй и оцени»

Определи модель (IaaS/PaaS/SaaS/FaaS) и кто за что отвечает:

```text:no-line-numbers
B1.  Виртуальная машина с Ubuntu в облаке
B2.  Managed PostgreSQL
B3.  Managed Kubernetes
B4.  GitLab.com
B5.  Объектное хранилище S3
B6.  Cloud Functions / Lambda
B7.  Grafana Cloud
B8.  Своя Grafana на арендованной ВМ
```

<details><summary>Ответ</summary>

**B1.** IaaS: провайдер даёт ВМ, ОС и всё выше — твоё.
**B2.** PaaS: провайдер обслуживает сервер и СУБД, ты отвечаешь за схему, данные и доступы.
**B3.** PaaS/CaaS: управляемый control plane, ты отвечаешь за рабочие нагрузки и часто за ноды.
**B4.** SaaS.
**B5.** IaaS/PaaS в зависимости от трактовки: управляемый сервис хранения, ты отвечаешь
за содержимое и права доступа.
**B6.** FaaS.
**B7.** SaaS.
**B8.** IaaS + твоё приложение: обслуживание Grafana полностью на тебе.

</details>

Оцени решения:

```text:no-line-numbers
B9.  Прод развёрнут в одной зоне доступности
B10. Ключ сервисного аккаунта лежит в репозитории проекта
B11. Учебный стенд: ВМ остановлена, "денег не тратим"
B12. Бюджет и уведомления не настроены
B13. Ресурсы создаются вручную в веб-консоли, документации нет
B14. Ресурсы без тегов, счёт на 300 позиций
B15. Используются 12 специфичных сервисов одного провайдера
B16. Персональные данные клиентов хранятся в зарубежном регионе
B17. 🟧 Вся команда работает под root-пользователем AWS-аккаунта, MFA нет
B18. 🟦 Прод с ПДн граждан РК в Yandex Cloud kz1, HA «по трём зонам» в плане
B19. 🇰🇿 Прод-база в облаке РК, её дампы — в бакете S3 во Франкфурте «для надёжности»
B20. Terraform-код под AWS «перенесём в облако РК, поменяв провайдера»
```

<details><summary>Ответ</summary>

**B9.** Одна зона — единая точка отказа; прод должен быть минимум в двух.
**B10.** Ключ в репозитории — компрометация всего облака.
**B11.** Диск и зарезервированный IP продолжают тарифицироваться.
**B12.** Без бюджета легко потратить грант или деньги компании незаметно.
**B13.** Ручное создание без документации = невоспроизводимая инфраструктура и «сироты».
**B14.** Без тегов невозможно разобрать счёт и найти владельца ресурса.
**B15.** Сильный lock-in: нужно осознанное решение и оценка стоимости переезда.
**B16.** Возможное нарушение требований к локализации персональных данных
(в Казахстане ПДн граждан РК должны храниться на территории страны).
**B17.** Root-аккаунт с полными правами без MFA — одна утечка пароля или ключа означает
потерю аккаунта; root только для редких операций, работа — через отдельные роли.
**B18.** Локализация соблюдена, но план HA нереален: в `kz1` одна зона. Нужно планировать
несколько хостов в зоне, бэкапы и DR, а не «три зоны».
**B19.** Бэкап с ПДн — тоже ПДн: дампы за рубежом нарушают требование локализации.
Копия для надёжности — в другом ЦОД/у другого провайдера **в РК**.
**B20.** Провайдеры Terraform не взаимозаменяемы: ресурсы и их атрибуты разные
(`aws_instance` против `openstack_compute_instance_v2`). Переносятся архитектура и модули
«по смыслу», код пишется заново.

</details>

### Блок C. Практика

#### C1. 🔑 Первые шаги в аккаунте
1. Зарегистрируйся в доступном облаке, активируй грант.
2. Настрой бюджет и уведомления (порог 10-20% гранта).
3. Изучи структуру: организация → облако/проект → каталог.
4. Найди раздел квот и посмотри лимиты на ВМ, IP, диски.

#### C2. Регионы и зоны
Найди список регионов и зон своего провайдера. Запиши, какие есть, и выбери,
где разместишь стенд. Обоснуй выбор (близость, цена, требования к данным).

#### C3. IAM
1. Создай сервисный аккаунт с ролью «только чтение».
2. Создай второй с правами на создание ВМ.
3. Выпусти ключ для CLI, проверь, что первый не может создать ВМ.
4. Опиши, где ты будешь хранить эти ключи.

<details><summary>Ответ</summary>

Проверка: сервисный аккаунт «только чтение» получит ошибку прав при попытке
создать ВМ — это и есть подтверждение работы IAM.

</details>

#### C4. CLI
Установи CLI своего провайдера, авторизуйся, выполни: список зон, список образов,
список типов ВМ, текущие квоты. Сохрани полезные команды.

#### C5. Деньги

3. Удали ВМ, но оставь диск — посмотри на счёт.

<details><summary>Ответ</summary>

контролю и рискам.

<details><summary>Ответ</summary>

В сравнении обычно побеждает managed для небольших команд: дороже по счёту,
но дешевле по времени девопса и рискам.

</details>

#### C11. 🟧 AWS: безопасный старт аккаунта
1. Зарегистрируйся, выбери Free plan (или Paid — осознанно), включи MFA на root.
2. Создай отдельного администратора (IAM Identity Center или IAM-пользователь) и больше
   не заходи под root.
3. Создай бюджет на 5-10 $ с уведомлением на e-mail (консоль или `aws budgets create-budget`).
4. Выполни `aws sts get-caller-identity`, `aws ec2 describe-availability-zones` для выбранного региона.

<details><summary>Ответ</summary>

После настройки вход под root нужен только для редких задач (биллинг, закрытие
аккаунта). `aws sts get-caller-identity` должен показывать ARN твоего пользователя/роли,
а не `:root`.

</details>

2. Сравни `yc compute zone list` в обоих профилях.
3. Запиши, где у региона `kz1` консоль, биллинг и endpoint объектного хранилища.

<details><summary>Ответ</summary>

В профиле `kz` список зон — только `kz1-a`; ресурсы профилей друг друга не видят.

</details>

### Блок D. Инциденты

**D1.** Счёт за месяц в 5 раз больше ожидаемого. Алгоритм разбора.

<details><summary>Ответ</summary>

Открыть детализацию по сервисам и тегам, сравнить с прошлым месяцем, найти топ
позиций: трафик, диски, managed-сервисы, забытые ресурсы; проверить, не включил ли кто-то
дорогой режим (репликация, резервные копии, большой класс машин).

</details>

**D2.** Ушли в минус из-за трафика: приложение раздавало видео напрямую с ВМ. Что предложишь?

<details><summary>Ответ</summary>

Вынести статику и медиа в объектное хранилище и CDN, включить кэширование
и сжатие, ограничить исходящий трафик, при необходимости — отдельный тариф на трафик.

</details>

**D3.** Не получается создать ещё одну ВМ: ошибка про лимит. Что делать?

<details><summary>Ответ</summary>

Проверить квоты в консоли, запросить повышение у провайдера (может занять
время), временно освободить неиспользуемые ресурсы, заложить квоты в планирование.

</details>

**D4.** Ключ сервисного аккаунта утёк в публичный репозиторий. Порядок действий.

<details><summary>Ответ</summary>

Немедленно отозвать/удалить ключ, выпустить новый, проверить журнал действий
(аудит) на предмет чужой активности, удалить ключ из истории репозитория, перевести
хранение в Vault/CI-секреты, разобрать инцидент.

</details>

**D5.** Дата-центр (зона доступности) стал недоступен, сервис лёг полностью. Что было
сделано неправильно?

<details><summary>Ответ</summary>

Все ресурсы находились в одной зоне доступности; не было резервирования
и балансировщика между зонами, а база — без реплики в другой зоне.

</details>

**D6.** Компания требует, чтобы персональные данные не покидали страну. Как это влияет
на архитектуру?

<details><summary>Ответ</summary>

Выбор региона внутри страны, запрет на репликацию и бэкапы за рубеж,
проверка, где физически находятся managed-сервисы и объектное хранилище,
шифрование и контроль доступа.

</details>

**D7.** Провайдер сообщил об инциденте, SLA нарушен. Что это значит для бизнеса и для тебя?

<details><summary>Ответ</summary>

Для бизнеса — компенсация по SLA (обычно небольшая) и простой;
для тебя — постмортем, оценка архитектуры (пережили бы мы это при мультизонном
размещении), обновление плана аварийного восстановления.

</details>

**D8.** Никто не знает, зачем нужны 14 из 30 работающих ВМ. Как навести порядок?

<details><summary>Ответ</summary>

Инвентаризация: теги и владельцы, сопоставление с Terraform-состоянием,
опрос команд, политика «нет владельца и тегов — гасим по расписанию»,
переход на создание ресурсов только кодом.

</details>

**D9.** Руководство просит «переехать в другое облако за месяц». Какие вопросы задашь?

<details><summary>Ответ</summary>

Что именно требуется перенести (данные, объёмы, время простоя),
какие используются специфичные сервисы, есть ли инфраструктура как код,
где будут храниться данные, каков бюджет и план отката, есть ли сетевые связности
на переходный период.

</details>

**D10.** Разработчики создают ресурсы вручную и забывают удалять. Что внедришь?

<details><summary>Ответ</summary>

Terraform как единственный способ создания ресурсов, ограничение прав в IAM
на ручное создание, обязательные теги, регулярный отчёт «сироты», автогашение
dev-ресурсов по расписанию, бюджеты с уведомлениями.

</details>

**D11.** 🟧 На почту пришло письмо AWS о необычной активности: в аккаунте запущены
десятки GPU-инстансов в регионах, которыми вы не пользуетесь. Порядок действий.

<details><summary>Ответ</summary>

Это компрометация ключа или пароля. Немедленно: деактивировать утёкшие access keys,
сменить пароль root и включить MFA, посмотреть CloudTrail (кто, откуда, какие вызовы),
остановить и удалить чужие ресурсы **во всех регионах** (включая созданных IAM-пользователей
и ключи — злоумышленник оставляет «закладки»), обратиться в поддержку AWS по поводу счёта.
Потом — разбор: откуда утёк ключ, переход на роли и OIDC вместо статических ключей,
SCP-запрет неиспользуемых регионов, бюджеты и Cost Anomaly Detection.

</details>

**D12.** 🇰🇿 Банк переносит прод в облако РК, а мониторинг, логи и трекер ошибок
остаются в зарубежных SaaS. Какие риски и что предложишь?

<details><summary>Ответ</summary>

Логи, APM и трекеры ошибок почти всегда содержат ПДн (e-mail, телефоны, ИИН
в URL и payload), а значит, копируют их за рубеж. Варианты: маскировать ПДн до отправки,
развернуть мониторинг и логирование self-hosted в РК (Prometheus/Loki/Grafana, Sentry
self-hosted), выбрать инструменты с хранением в РК; зафиксировать решение с юристом/DPO.

</details>

### Блок E. Вопросы с собеседования

**1.** Чем IaaS отличается от PaaS и SaaS?

<details><summary>Ответ</summary>

Глубиной ответственности: IaaS — виртуальная инфраструктура, PaaS — управляемая
платформа без доступа к ОС, SaaS — готовый продукт.

</details>

**2.** Что такое регион и зона доступности?

<details><summary>Ответ</summary>

Регион — географическая площадка; зона — независимый ДЦ внутри региона.

</details>

**3.** Как обеспечить отказоустойчивость в облаке?

<details><summary>Ответ</summary>

Размещением в нескольких зонах, балансировщиками, репликами баз, автоматическим
восстановлением и проверенными бэкапами.

</details>

**4.** Что такое shared responsibility model?

<details><summary>Ответ</summary>

Разделение ответственности: провайдер отвечает за инфраструктуру, клиент — за данные,
доступы и настройки.

</details>

**5.** Кто отвечает за бэкапы в облаке?

<details><summary>Ответ</summary>

За бэкапы managed-сервисов — провайдер по заданной политике; за данные на ВМ
и за проверку восстановления — клиент.

</details>

**6.** За что платят в облаке и как оптимизировать расходы?

<details><summary>Ответ</summary>

За вычисления, диски, IP, трафик, хранилище и managed-сервисы; оптимизация —
right-sizing, расписания, spot, резервирование, lifecycle, CDN.

</details>

**7.** Что такое IAM и сервисный аккаунт?

<details><summary>Ответ</summary>

Система прав; сервисный аккаунт — «робот» для приложений и CI с ограниченными ролями.

</details>

**8.** Что такое vendor lock-in и как его снижать?

<details><summary>Ответ</summary>

Зависимость от уникальных сервисов провайдера; снижается стандартными технологиями
и IaC.

</details>

**9.** С какими облаками работал?

<details><summary>Ответ</summary>

Честно назвать, с чем работал (в том числе на учебных стендах), и подчеркнуть,
что концепции переносимы.

</details>

**10.** Как контролировать, кто и что создаёт в облаке?

<details><summary>Ответ</summary>

IAM с минимальными правами, создание ресурсов через Terraform и CI, обязательные
теги, бюджеты и алерты, регулярный аудит (CloudTrail / Audit Trails).

</details>

**11.** Зачем компании в Казахстане локальное облако, если есть AWS?

<details><summary>Ответ</summary>

Из-за закона о ПДн: базы с ПДн граждан РК (и их бэкапы, логи) должны быть в Казахстане,
а региона AWS в РК нет. Плюс оплата в тенге, договор по местному праву, задержки
до пользователей. Глобальное облако при этом часто остаётся для всего без ПДн.

</details>

**12.** Чем структура аккаунтов AWS отличается от облаков и каталогов Yandex Cloud?

<details><summary>Ответ</summary>

В AWS граница изоляции — отдельный аккаунт в Organization (права и биллинг
разделены жёстко, общие правила — SCP); в Yandex Cloud — облако и каталог внутри
одной организации, роли назначаются на облако/каталог и наследуются вниз.

</details>
