## 🗺️ Что берёт на себя провайдер

```text:no-line-numbers
                   СВОЯ ВМ                     MANAGED-СЕРВИС
 установка          ты                          провайдер
 обновления ОС      ты                          провайдер
 версия СУБД/k8s    ты                          провайдер (из списка доступных)
 репликация         ты настраиваешь             включается галочкой
 бэкапы             ты настраиваешь             встроены (расписание, retention)
 failover           ты (Patroni и т.п.)         автоматический
 мониторинг         ты ставишь экспортеры       базовые метрики из коробки
 масштабирование    руками/скриптами            изменение конфигурации
 ────────────────────────────────────────────────────────────────────────
 ТВОЯ ЗОНА:         всё                         доступы, схема, запросы,
                                                 производительность, деньги
```

⭐ Главный размен: **деньги и контроль в обмен на время девопса и снижение рисков.**
Для команды из 1-3 инженеров managed почти всегда выгоднее, чем «сэкономить и держать
Patroni-кластер вручную».

### Каталог: что как называется

| Сервис | AWS | Yandex Cloud (в т.ч. `kz1`) | Облака РК |
|--------|-----|-----------------------------|-----------|
| PostgreSQL / MySQL | RDS, Aurora | Managed Service for PostgreSQL / MySQL (managed-БД есть в `kz1`) | VK Cloud в РК (оператор ТОО «QazCloud») — «Cloud Databases»; у PS Cloud и Kazteleport — сверяй по каталогу |
| Kubernetes | EKS | Managed Service for Kubernetes (есть в `kz1`) | PS Cloud (консоль, Terraform, OpenStack API; Алматы и Астана), Kazteleport Managed Kubernetes, VK Cloud в РК — «Cloud Containers» |
| Redis/Valkey | ElastiCache, MemoryDB | Managed Redis/Valkey | проверь |
| Kafka | MSK | Managed Service for Apache Kafka | проверь |
| ClickHouse | — (через партнёров) | Managed Service for ClickHouse | проверь |
| Секреты и ключи | Secrets Manager, KMS | Lockbox, KMS (есть в `kz1`) | проверь |
| Реестр образов | ECR | Container Registry / Cloud Registry (есть в `kz1`) | проверь |
| Бэкап как сервис | AWS Backup | Cloud Backup (есть в `kz1`) | BaaS / DRaaS у Kazteleport и QazCloud |
| Логи и аудит | CloudWatch Logs, CloudTrail | Cloud Logging, Audit Trails (есть в `kz1`) | проверь |

> Наличие сервиса в регионе Yandex `kz1` — по списку API-endpoint'ов региона
> (`*.api.yandexcloud.kz`); про облака РК — по их публичным страницам. То, чего там нет
> в явном виде, помечено «проверь»: спрашивай провайдера до выбора архитектуры.

## 1. Когда managed, а когда своё

| Бери managed, если | Делай сам, если |
|--------------------|-----------------|
| Команда маленькая, девопсов мало | Есть экспертиза и время на эксплуатацию |
| Нужна отказоустойчивость «вчера» | Нужна экзотическая версия/расширение, которых нет |
| Данные критичны, а опыта с failover нет | Требуется полный контроль над конфигом и ОС |
| Нагрузка типовая | Специфичные требования к производительности |
| Считаешь стоимость часа инженера | Стоимость managed непропорционально велика |
| Нужны бэкапы и PITR без внедрения WAL-G | Есть регуляторные ограничения на managed |
| — | Нужного managed-сервиса **нет у провайдера в РК**, а данные обязаны быть в РК |

```text:no-line-numbers
Честный расчёт (порядок цен, проверь в калькуляторе своего провайдера):
  managed PostgreSQL (2 vCPU, 8 ГБ, HA из 2 хостов)  ≈ 250–400 $/мес  (≈ 130–210 тыс. ₸)
  своя схема: 2 ВМ + диски + Patroni + etcd + бэкапы + ваше время
              ≈ 0.6 от этой суммы + 5-15 часов внедрения + дежурства
Экономия часто съедается первым же ночным инцидентом.
```

## 2. Managed PostgreSQL (типовой представитель)

Что настраивается при создании:
```text:no-line-numbers
класс хоста (vCPU/RAM) · тип и размер диска · версия PostgreSQL
количество хостов и зоны  ← ⭐ HA = минимум 2-3 хоста в разных зонах
сеть (VPC + подсети) и security groups
расписание бэкапов и глубина хранения (PITR)
окно обслуживания (когда провайдер может обновлять)
параметры СУБД (доступное подмножество postgresql.conf)
пользователи и базы
```

**Yandex Cloud:**
```bash
yc managed-postgresql cluster create \
  --name shop-pg \
  --environment production \
  --network-name study \
  --host zone-id=ru-central1-a,subnet-name=db-a \
  --host zone-id=ru-central1-b,subnet-name=db-b \
  --resource-preset s2.micro \
  --disk-type network-ssd --disk-size 20 \
  --postgresql-version 16 \
  --user name=app,password="$PG_PASS" \
  --database name=shop,owner=app \
  --security-group-ids <id sg-db>
# в kz1 — только --host zone-id=kz1-a (одна зона: HA — несколько хостов в одной зоне)
yc managed-postgresql cluster list-hosts shop-pg
```

**AWS (RDS):**
```bash
aws rds create-db-subnet-group --db-subnet-group-name shop-db \
  --db-subnet-group-description "db subnets" --subnet-ids "$DB_A" "$DB_B"
aws rds create-db-instance \
  --db-instance-identifier shop-pg \
  --engine postgres --engine-version 16 \
  --db-instance-class db.t4g.micro \
  --allocated-storage 20 --storage-type gp3 \
  --master-username app --manage-master-user-password \
  --db-subnet-group-name shop-db --vpc-security-group-ids "$SG_DB" \
  --no-publicly-accessible \
  --backup-retention-period 7 \
  --multi-az                                     # ⭐ HA: standby в другой AZ (дороже вдвое)
aws rds describe-db-instances --db-instance-identifier shop-pg \
  --query 'DBInstances[0].[DBInstanceStatus,Endpoint.Address]'
```
`--manage-master-user-password` кладёт пароль в Secrets Manager — пароль не светится
в истории shell.

| Возможность | Комментарий |
|-------------|-------------|
| Автоматический failover | Мастер меняется сам; приложение подключается по «ручке» кластера |
| Реплики для чтения | Отдельный endpoint только для чтения |
| Бэкапы и PITR | Настраиваются в консоли; ⭐ **восстановление всё равно нужно проверять самому** |
| Мониторинг | Базовые графики есть; для своих алертов экспортер подключают к endpoint |
| Обновления версий | Мажорные — по кнопке и в окно обслуживания |
| Ограничения | Нет суперпользователя, ограниченный набор расширений и параметров, нет доступа к ОС и файлам |

| HA и ограничения | AWS RDS | Yandex Managed PostgreSQL |
|------------------|---------|---------------------------|
| HA | Multi-AZ: standby в другой AZ (не читается); Multi-AZ DB cluster — два читаемых standby | хосты в разных зонах, автоматическая смена мастера, реплики читаются |
| Endpoint | DNS-имя инстанса/кластера, порт 5432 | особые FQDN: `c-<id>.rw.mdb.yandexcloud.net` (мастер), `c-<id>.ro...` (реплика); порт 6432 — через встроенный PgBouncer |
| «Почти суперюзер» | роль `rds_superuser` | роль `mdb_admin` |
| Параметры СУБД | parameter group | настройки кластера (`--set` / консоль) |
| Расширения | список поддерживаемых в документации | включаются в настройках БД из разрешённого списка |

```text:no-line-numbers
⚠️ Что нельзя в managed PostgreSQL (типично):
  • superuser и произвольные расширения
  • правка pg_hba.conf напрямую (вместо этого — security groups и настройки сервиса)
  • доступ к файловой системе, WAL-архиву, логам на диске
  • нестандартные версии и патчи
Если проекту это нужно — только своя инсталляция.
```

Подключение:
```bash
# Yandex Cloud: FQDN кластера + корневой сертификат
curl -sSo ~/.postgresql/root.crt https://storage.yandexcloud.net/cloud-certs/CA.pem
psql "host=c-<cluster-id>.rw.mdb.yandexcloud.net port=6432 dbname=shop user=app \
      sslmode=verify-full sslrootcert=$HOME/.postgresql/root.crt"
#   в kz1 домены и сертификат — по документации региона (проверь)

# AWS RDS: endpoint инстанса + CA bundle RDS
curl -sSo global-bundle.pem https://truststore.pki.rds.amazonaws.com/global/global-bundle.pem
psql "host=shop-pg.xxxx.eu-central-1.rds.amazonaws.com port=5432 dbname=postgres user=app \
      sslmode=verify-full sslrootcert=global-bundle.pem"
```
Обрати внимание: у Yandex перед базой уже стоит пул соединений (порт 6432) — это встроенный
PgBouncer, о котором говорилось в [«04. PostgreSQL: конфигурация»](/databases/04-postgresql-conf).
В AWS аналог — отдельный сервис RDS Proxy.

## 3. Managed Kubernetes

```text:no-line-numbers
 ┌────────────────────────────────────────────────────────────────┐
 │ CONTROL PLANE (провайдер)                                      │
 │ api-server, etcd, scheduler, controller-manager                 │
 │ обновления, доступность, бэкап etcd — не твоя забота            │
 ├────────────────────────────────────────────────────────────────┤
 │ WORKER-НОДЫ (твои)                                             │
 │ группы узлов, автоскейлинг, версии kubelet, taints/labels        │
 │ ⚠️ ты платишь за ноды и отвечаешь за нагрузки на них             │
 └────────────────────────────────────────────────────────────────┘
```

| Что даёт | Что остаётся тебе |
|----------|-------------------|
| Готовый и обновляемый control plane | Манифесты, Helm-чарты, мониторинг, логи |
| Интеграция с облаком: LoadBalancer, диски (CSI), IAM | Настройка ingress, сертификатов, autoscaling политик |
| Группы узлов с автомасштабированием | Ресурсы, лимиты, надёжность приложений |
| Обновления версий кластера | Совместимость приложений с новой версией |

| | AWS EKS | Yandex Managed Kubernetes | Облака РК |
|--|---------|---------------------------|-----------|
| Control plane | платный почасово (порядок 0,1 $/ч за кластер на стандартной поддержке, проверь) | платный; зональный мастер дешевле регионального | PS Cloud: мастер-ноды тарифицируются как ресурсы; остальное — проверь |
| Ноды | managed node groups, Karpenter, Fargate | группы узлов (`node-group`) | worker-ноды — ВМ провайдера |
| Права подов в облаке | **EKS Pod Identity** / IRSA | сервисные аккаунты через Workload Identity (проверь) | обычно нет — секреты с ключами |
| Диски (PVC) | EBS CSI | CSI Yandex (диски Compute) | Cinder CSI (PS Cloud заявляет PV через Cinder) |
| `Service type: LoadBalancer` | NLB/CLB через AWS Load Balancer Controller | Network Load Balancer | балансировщик провайдера (PS Cloud — интеграция заявлена) |

Подключение и работа — те же, что в блоке [Kubernetes](/kubernetes/):
```bash
# Yandex Cloud
yc managed-kubernetes cluster get-credentials my-cluster --external
# AWS
aws eks update-kubeconfig --name my-cluster --region eu-central-1
# OpenStack-облако РК: kubeconfig скачивается из консоли провайдера (или через его API)

kubectl get nodes
kubectl get pods -A
```

> 💡 В облаке `Service type: LoadBalancer` создаёт **реальный балансировщик**
> (и он платный), а PVC — реальный диск. Это первое, что удивляет после minikube.
> Глубже по EKS и Pod Identity — [«08. AWS: продвинутые темы»](/cloud/08-aws-deep), по Yandex Managed
> Kubernetes — [«09. Yandex Cloud»](/cloud/09-yandex-cloud).

## 4. Другие типовые managed-сервисы

| Сервис | Что решает | На что смотреть |
|--------|------------|-----------------|
| Managed Redis/Valkey | Кэш и сессии с HA | Режим (sentinel/cluster), persistence, `maxmemory-policy` |
| Managed Kafka | Очереди без эксплуатации кластера | Число брокеров, retention, лаг групп (Queues) |
| Managed ClickHouse | Аналитика и логи | Шардирование, репликация, объём дисков |
| Managed MySQL/MongoDB | Аналогично PostgreSQL | Версии, расширения, бэкапы |
| Объектное хранилище | Файлы, бэкапы, статика | См. [«04. S3-совместимое хранилище»](/cloud/04-s3-storage) |
| Управляемый балансировщик | Вход снаружи | Health-check, TLS |
| Хранилище секретов (Secrets Manager / Lockbox) | Секреты вместо файлов | Сравнение с Vault |
| Реестр образов (ECR / Container Registry) | Свои образы | Сканирование уязвимостей, retention |
| Managed CI/раннеры | Сборка | Стоимость минут, изоляция |
| BaaS / DRaaS | Бэкап и аварийное восстановление как услуга | Где лежат копии (РК?), RTO/RPO по договору, учения |

## 5. Что остаётся девопсу в managed-мире

```text:no-line-numbers
Иллюзия: «взяли managed — работы нет».
Реальность: работа меняется, но не исчезает.
```

| Зона | Что делаешь |
|------|-------------|
| **Доступы** | IAM-роли, сервисные аккаунты, security groups, ротация секретов |
| **Данные** | Схема, миграции, индексы, производительность запросов |
| **Бэкапы** | Настроить политику и ⭐ **регулярно проверять восстановление** |
| **Мониторинг** | Свои дашборды и алерты поверх метрик провайдера |
| **Стоимость** | Right-sizing, отключение лишнего, анализ счёта |
| **Ограничения** | Знать, чего сервис не умеет, и планировать обходные пути |
| **Обновления** | Планировать окна обслуживания и проверять совместимость |
| **Архитектура** | Мультизонность, реплики, деградация при отказе сервиса |
| **Размещение данных** | Где лежат сама база, её бэкапы, логи и реплики (закон о ПДн РК) |

## 6. Риски и ограничения

| Риск | Смягчение |
|------|-----------|
| Vendor lock-in | Стандартные технологии (PostgreSQL, k8s, S3), IaC, план миграции |
| Нет нужного расширения/версии | Проверить **до** выбора; иметь запасной вариант со своей инсталляцией |
| Ограниченный тюнинг | Понимать, какие параметры доступны; тестировать под нагрузкой |
| Стоимость при росте | Считать заранее, следить за трендом расходов |
| Зависимость от SLA провайдера | Проектировать деградацию, иметь бэкапы вне провайдера |
| «Бэкапы делает облако» | Проверять восстановление и держать независимую копию критичных данных |
| Окна обслуживания | Задать удобное время, планировать, что failover будет происходить |
| Нужного managed нет в РК | Своя инсталляция на ВМ провайдера РК (Patroni, Strimzi, операторы в k8s) |
| Регион с одной зоной (`kz1`) | HA из нескольких хостов в зоне + бэкапы + DR-план; держать RTO реалистичным |

⭐ Практическое правило: **критичные данные должны иметь копию вне контура провайдера**
(другой аккаунт, другое хранилище, иногда другая площадка). Для ПДн граждан РК — вне
контура провайдера, но **внутри РК**.

## 7. В облаках РК

- **Yandex Cloud `kz1`**: по списку API-endpoint'ов региона доступны Managed Kubernetes,
  managed-БД (PostgreSQL, MySQL, ClickHouse, Kafka, OpenSearch и др. — через общий
  `mdb.api.yandexcloud.kz`), Lockbox, KMS, Container Registry, Cloud Backup, Audit Trails.
  Команды те же (`yc managed-postgresql`, `yc managed-kubernetes`), но зона одна (`kz1-a`)
  (проверь, сентябрь 2026).
- **PS Cloud**: Kubernetes-кластеры через консоль, Terraform или OpenStack API в зонах
  Алматы и Астана, PV через Cinder, интеграция с балансировщиками; про managed-БД — сверяй
  по актуальному каталогу.
- **Kazteleport**: Managed Kubernetes, BaaS, DRaaS, GPU Cloud на базе OpenStack.
- **QazCloud**: IaaS, BaaS, DRaaS, облачное хранение; VK Cloud в Казахстане (серверы,
  хранилище, контейнеры, базы данных) оказывает ТОО «QazCloud», ЦОД — в Косшы под Астаной.
- Если нужного managed-сервиса нет, выбор честный: своя эксплуатация на ВМ/в k8s провайдера
  РК (и тогда пересчитай людей и дежурства) или вынос **не-ПДн** части в другое облако.
  Подробнее: [«10. Облака Казахстана»](/cloud/10-kz-clouds).

## 8. Грабли

| Грабля | Последствие | Решение |
|--------|-------------|---------|
| HA «на одном хосте» | Managed-база без реплик падает как обычная | Минимум 2-3 хоста в разных зонах |
| Не проверяли восстановление | Бэкапы есть, а восстановиться не смогли | Регулярные учебные восстановления |
| Приложение подключается к конкретному хосту | После failover всё ломается | Подключаться к endpoint кластера |
| Нет учёта окна обслуживания | Неожиданный разрыв соединений | Retry в приложении, известное окно |
| `LoadBalancer` на каждый сервис в k8s | Много платных балансировщиков | Один Ingress-контроллер |
| Managed выбран без проверки расширений | Приложение не работает | Проверять требования заранее |
| Всё в одной зоне | Отказ зоны кладёт кластер | Мультизонное размещение |
| Никто не смотрит счёт | Managed «внезапно» дорогой | Регулярный анализ расходов |
| RDS с `--publicly-accessible` «для отладки» | База в интернете | `--no-publicly-accessible`, доступ через bastion/SSM |
| Удалили RDS без финального снапшота | Данных нет | `--final-db-snapshot-identifier`, deletion protection |
| Забытый EKS-кластер на учебном аккаунте | Control plane + ноды + NAT тикают круглосуточно | Удалять в тот же день, бюджет-алерт |
| Архитектуру под `kz1` рисовали «как в ru-central1» | Хостов в других зонах не создать | Сверять зоны и сервисы региона до проектирования |

## 💼 Как это в DevOps

- Типовой современный стек в облаке: managed Kubernetes для приложений + managed
  PostgreSQL для данных + объектное хранилище для файлов и бэкапов + managed Redis/Kafka
  по необходимости. Всё создаётся Terraform'ом.
- Девопс не «настраивает СУБД», а проектирует доступы, отказоустойчивость, наблюдаемость
  и следит за деньгами — работы меньше не становится, она поднимается на уровень выше.
- Собеседования часто содержат вопрос «managed или своё?» — и правильный ответ это
  не «managed лучше», а список критериев (команда, экспертиза, требования, бюджет, риски,
  **где по закону должны лежать данные и есть ли там этот managed**).
- Даже с managed-сервисами держат независимую копию критичных данных и умеют
  восстанавливаться самостоятельно.

## 📌 Шпаргалка

| Вопрос | Ответ |
|--------|-------|
| Что берёт на себя провайдер | Установку, обновления, HA, встроенные бэкапы, failover |
| Что остаётся тебе | Доступы, схема и запросы, проверка восстановления, мониторинг, деньги, место хранения данных |
| Когда managed | Маленькая команда, типовая нагрузка, нужна надёжность быстро |
| Когда своё | Нужны специфичные версии/расширения/тюнинг, есть экспертиза, managed нет в нужной юрисдикции |
| HA в managed БД | Несколько хостов в разных зонах + endpoint кластера (RDS `--multi-az`, Yandex — `--host` в разных зонах) |
| Подключение к БД | FQDN кластера, TLS `verify-full`; Yandex — встроенный пул на 6432, RDS — 5432 (+ RDS Proxy) |
| Создать PG | `yc managed-postgresql cluster create ...` · `aws rds create-db-instance ...` |
| kubeconfig | `yc managed-kubernetes cluster get-credentials NAME --external` · `aws eks update-kubeconfig --name NAME` |
| Managed k8s | Control plane — провайдера, ноды и нагрузки — твои |
| LoadBalancer в k8s | Создаёт реальный платный балансировщик |
| Главный риск | Иллюзия «бэкапы и надёжность — не моя забота» |
| Обязательная практика | Учебное восстановление из бэкапа по расписанию |
| Защита от lock-in | Стандартные технологии, IaC, план миграции |

## 🧠 Что запомнить

1. Managed-сервис — это обмен денег и контроля на время девопса и снижение рисков.
2. Для небольших команд managed обычно выгоднее, чем самостоятельная эксплуатация HA.
3. ⭐ HA не появляется само: нужно явно выбрать несколько хостов в разных зонах
   (RDS `--multi-az`, Yandex — хосты в разных зонах; в `kz1` зона одна).
4. Приложение подключается к endpoint кластера, а не к конкретному хосту — иначе
   failover ломает сервис.
5. В managed нет суперпользователя (`rds_superuser`, `mdb_admin` — не он), доступа к ОС
   и части расширений — проверяй до выбора.
6. Бэкапы провайдера не отменяют твоей обязанности проверять восстановление.
7. В managed Kubernetes провайдер отвечает за control plane, ты — за ноды и нагрузки;
   control plane EKS и Yandex — платный.
8. `LoadBalancer` и PVC в облачном k8s создают реальные платные ресурсы.
9. Критичные данные должны иметь копию вне контура провайдера (для ПДн РК — в РК).
10. Каталог managed-сервисов у облаков РК беднее: сверяй его до выбора архитектуры;
    работа девопса при переходе на managed не исчезает, а поднимается на уровень
    архитектуры, доступов, наблюдаемости и денег.

### Блок A. Теория

**A1.** Что берёт на себя провайдер в managed-сервисе и что остаётся тебе?

<details><summary>Ответ</summary>

Провайдер: установка, обновления ОС и сервиса, репликация и failover,
встроенные бэкапы, базовый мониторинг, инфраструктура. Ты: доступы и сеть, схема данных
и запросы, производительность, проверка восстановления, свои метрики и алерты,
стоимость и архитектура.

</details>

**A2.** ⭐ Сформулируй главный размен при выборе managed.

<details><summary>Ответ</summary>

Платишь деньгами и частью контроля, получаешь время инженеров и снижение
эксплуатационных рисков.

</details>

**A3.** Назови пять критериев «брать managed» и пять — «делать самому».

<details><summary>Ответ</summary>

Managed: маленькая команда, нет опыта эксплуатации HA, нужна надёжность быстро,
типовая нагрузка, важна скорость запуска. Своё: нужны специфичные версии/расширения,
глубокий тюнинг, регуляторные ограничения, есть экспертиза и дежурство, стоимость
managed непропорциональна.

</details>

**A4.** Как посчитать, что выгоднее: managed или своя инсталляция?

<details><summary>Ответ</summary>

Сравнить полную стоимость владения: счёт за managed против стоимости ВМ,
дисков, хранилища бэкапов, лицензий плюс часы инженеров на внедрение и сопровождение
и стоимость риска простоя.

</details>

**A5.** Что настраивается при создании managed PostgreSQL?

<details><summary>Ответ</summary>

Класс хоста, диск, версия, количество хостов и зоны, сеть и security groups,
расписание и глубина бэкапов, окно обслуживания, доступные параметры СУБД,
пользователи и базы.

</details>

**A6.** Как в managed-базе обеспечивается отказоустойчивость и что нужно указать явно?

<details><summary>Ответ</summary>

Несколькими хостами в разных зонах доступности с автоматическим failover;
это нужно явно выбрать при создании — по умолчанию может быть один хост.

</details>

**A7.** Почему приложение должно подключаться к endpoint кластера, а не к хосту?

<details><summary>Ответ</summary>

При failover роль мастера переходит другому хосту; endpoint кластера всегда
указывает на актуального мастера, а жёстко прописанный хост станет репликой или исчезнет.

</details>

**A8.** Чего обычно нельзя в managed PostgreSQL?

<details><summary>Ответ</summary>

Суперпользователь, произвольные расширения, правка `pg_hba.conf` и файлов
конфигурации напрямую, доступ к ОС и WAL-архиву, нестандартные версии и патчи.

</details>

**A9.** Что означает порт 6432 у многих managed-баз?

<details><summary>Ответ</summary>

Обычно это встроенный пул соединений (PgBouncer) перед базой; на 5432 —
прямое подключение к СУБД.

</details>

**A10.** Как делятся зоны ответственности в managed Kubernetes?

<details><summary>Ответ</summary>

Провайдер отвечает за control plane (api-server, etcd, scheduler) и его
обновления; клиент — за рабочие узлы (их размер, масштабирование, версии) и за всё,
что внутри кластера.

</details>

**A11.** Что происходит, когда в облачном k8s создаёшь `Service type: LoadBalancer`?

<details><summary>Ответ</summary>

Облачный контроллер создаёт реальный сетевой балансировщик с публичным IP —
платный ресурс; поэтому на каждый сервис его не создают.

</details>

**A12.** Почему бэкапы провайдера не снимают с тебя ответственности?

<details><summary>Ответ</summary>

Потому что бэкап без проверенного восстановления не является бэкапом,
а ответственность за данные и RTO остаётся на владельце сервиса.

</details>

**A13.** Какие риски несёт managed и как их смягчают?

<details><summary>Ответ</summary>

Vendor lock-in (стандартные технологии, IaC), ограничения тюнинга (проверять
заранее), стоимость при росте (контроль расходов), зависимость от SLA (архитектура
деградации, копия данных вне провайдера).

</details>

**A14.** Что такое окно обслуживания и как к нему готовиться?

<details><summary>Ответ</summary>

Период, когда провайдер может выполнять обслуживание с возможным переключением
и разрывом соединений. Выбирают время минимальной нагрузки, приложение должно уметь
переподключаться и повторять операции.

</details>

**A15.** Что должно быть у критичных данных помимо бэкапов провайдера?

<details><summary>Ответ</summary>

Независимая копия вне контура провайдера (другой аккаунт/площадка/хранилище)
и проверенный сценарий восстановления собственными силами. Для ПДн граждан РК эта площадка
тоже должна быть в РК.

</details>

**A16.** 🟧🟦 Чем отличаются HA и endpoint'ы у RDS for PostgreSQL и Yandex Managed PostgreSQL?

<details><summary>Ответ</summary>

RDS: Multi-AZ — синхронный standby в другой AZ, который не обслуживает чтение
(в режиме Multi-AZ DB cluster — два читаемых standby); endpoint — DNS-имя инстанса,
порт 5432, при failover имя переезжает на новый primary. Yandex: хосты в разных зонах,
автоматическая смена мастера, реплики доступны на чтение; особые FQDN `c-<id>.rw...`
(всегда мастер) и `c-<id>.ro...` (реплика), порт 6432 через встроенный PgBouncer.

</details>

**A17.** 🟧 Что делает `--manage-master-user-password` при создании RDS и зачем он нужен?

<details><summary>Ответ</summary>

RDS сам генерирует мастер-пароль и хранит его в Secrets Manager (с ротацией).
Пароль не попадает в историю shell, Terraform state и CI-логи; приложение читает его
из Secrets Manager.

</details>

**A18.** 🟦🇰🇿 Какие managed-сервисы доступны в регионе Yandex `kz1` и как это проверить?
Что меняет одна зона для managed-базы?

<details><summary>Ответ</summary>

По списку API-endpoint'ов региона (`*.api.yandexcloud.kz`) в документации
и по консоли `kz.console.yandex.cloud`: там есть Managed Kubernetes, managed-БД
(`mdb.api.yandexcloud.kz` — PostgreSQL, MySQL, ClickHouse, Kafka и др.), Lockbox, KMS,
Container Registry, Cloud Backup (проверь, сентябрь 2026). Одна зона `kz1-a` означает:
хосты кластера — в одной зоне, отказ зоны кладёт всё; защита — бэкапы, реплика на другой
площадке в РК и отработанный DR.

</details>

**A19.** 🇰🇿 Нужного managed-сервиса у провайдера РК нет, а данные с ПДн должны быть в РК.
Какие варианты?

<details><summary>Ответ</summary>

Своя инсталляция на ВМ или в k8s провайдера РК (Patroni, операторы вроде
CloudNativePG, Strimzi) — с честным расчётом людей и дежурств; другой провайдер в РК,
у которого сервис есть; вынос только **не-ПДн** части в облако с нужным сервисом;
пересмотр архитектуры, чтобы сервис был не нужен.

</details>

### Блок B. «Оцени решение»

```text:no-line-numbers
B1.  Managed PostgreSQL из одного хоста в проде
B2.  Managed PostgreSQL: 3 хоста в трёх зонах, endpoint кластера в конфиге приложения
B3.  В конфиге приложения прописан конкретный хост rc1a-xxxx.mdb.example.net
B4.  Бэкапы managed-базы включены, восстановление никогда не проверяли
B5.  Приложению нужен расширение pg_cron; managed его не поддерживает — решили "разберёмся потом"
B6.  Каждый микросервис в k8s имеет Service type: LoadBalancer (их 14)
B7.  В кластере один Ingress-контроллер, сервисы — ClusterIP
B8.  Managed Redis используется как основная очередь задач, persistence отключён
B9.  Managed Kafka: 1 брокер, "для экономии"
B10. Копия критичных данных существует только внутри облака провайдера

B13. 🟧 RDS создан с --publicly-accessible и SG 5432 от 0.0.0.0/0 "для DBeaver"
B14. 🟧 aws rds delete-db-instance --db-instance-identifier shop-pg --skip-final-snapshot
B15. 🟧 Учебный EKS-кластер оставлен "до следующих выходных"
B16. 🟦 Приложение подключается к c-<id>.rw.mdb.yandexcloud.net:6432
B17. 🟦🇰🇿 Managed PostgreSQL в kz1: три хоста в kz1-a, бэкапы, реплика в другом ЦОД в РК через логическую репликацию
B18. 🇰🇿 Для ПДн выбрали облако РК, а Redis с сессиями пользователей — managed в AWS
```

<details><summary>Ответ</summary>

**B1.** Один хост — нет отказоустойчивости; при аварии зоны база недоступна.
**B2.** Правильная конфигурация.
**B3.** Жёсткий хост ломается при failover; нужен endpoint кластера.
**B4.** Классическая ошибка: непроверенный бэкап.
**B5.** Отложенная проблема: если расширение критично, managed не подходит,
и это надо решать до миграции.
**B6.** 14 платных балансировщиков; нужен один Ingress-контроллер.
**B7.** Правильная схема.
**B8.** Очередь без persistence — потеря задач при перезапуске.
**B9.** Один брокер Kafka не даёт отказоустойчивости и репликации.
**B10.** Нет независимой копии: риск при проблемах с аккаунтом или провайдером.
**B11.** Окно обслуживания в пик — гарантированное влияние на пользователей.
**B12.** Приложение обязано переживать переподключения: это норма и в облаке, и без него.
**B13.** База в интернете — критично. Приватная подсеть, `--no-publicly-accessible`,
доступ через bastion/SSM-туннель.
**B14.** `--skip-final-snapshot` — данные уходят безвозвратно (автоматические бэкапы
удаляются вместе с инстансом, если их явно не сохранять). Для прода — финальный снапшот
и deletion protection.
**B15.** Control plane EKS тарифицируется почасово, плюс ноды, NAT, балансировщики —
за неделю набегает заметная сумма. Удалять в тот же день.
**B16.** Правильно: особый FQDN мастера и встроенный пул соединений.
**B17.** Разумно для региона с одной зоной: несколько хостов, бэкапы и копия в другом ЦОД
в РК закрывают отказ хоста и площадки (RTO при отказе зоны — время переключения на копию).
**B18.** Сессии пользователей почти всегда содержат ПДн (идентификаторы, e-mail, IP) —
это вынос ПДн за рубеж; кэш с ПДн тоже должен быть в РК.

</details>

### Блок C. Практика

#### C1. 🔑 Managed PostgreSQL
1. Создай кластер из одного хоста (минимальная конфигурация) в приватной подсети.
2. Настрой security group так, чтобы доступ был только от ВМ приложения.
3. Подключись с ВМ через `psql` с `sslmode=verify-full`.
4. Создай базу, роль, таблицу; проверь, что суперпользователя нет.

<details><summary>Ответ</summary>

В managed обычно создаётся пользователь-владелец базы без прав суперпользователя;
`CREATE EXTENSION` работает только для разрешённого списка.

</details>

#### C2. Отказоустойчивость
1. Пересоздай (или расширь) кластер до 2-3 хостов в разных зонах.
2. Найди endpoint кластера и endpoint для чтения.
3. Инициируй переключение (если провайдер позволяет) и посмотри, что происходит
   с подключением приложения.

#### C3. Бэкапы managed-базы
1. Настрой расписание и глубину хранения.
2. Сделай точку восстановления, «испорти» данные, восстановись в новый кластер.
3. Замерь время восстановления — это твой реальный RTO.

<details><summary>Ответ</summary>

Восстановление в новый кластер — правильный подход: продовый остаётся нетронутым.

</details>

#### C4. Ограничения
Посмотри список доступных расширений и параметров конфигурации.
Выпиши три вещи, которые нельзя сделать в managed, но можно на своей инсталляции.

#### C5. Мониторинг managed-базы
1. Посмотри встроенные метрики и графики.
2. Подключи `postgres_exporter` к endpoint и собери свои метрики в Prometheus.
3. Настрой 3 алерта.

#### C6. 🔑 Managed Kubernetes
1. Создай кластер с одной группой узлов (2 ноды, минимальные).
2. Получи kubeconfig, проверь `kubectl get nodes`.
3. Задеплой приложение и `Service type: LoadBalancer` — посмотри, какой ресурс появился
   в облаке и сколько он стоит.
4. Создай PVC и найди соответствующий диск в консоли облака.

<details><summary>Ответ</summary>

После создания `LoadBalancer` в консоли облака появится балансировщик с IP;
PVC создаст диск, видимый в разделе дисков.

</details>

#### C7. Ingress вместо множества балансировщиков
Поставь ingress-контроллер, переведи сервисы на ClusterIP + Ingress.
Сравни количество платных балансировщиков до и после.

<details><summary>Ответ</summary>

Количество платных балансировщиков должно сократиться до одного.

</details>

#### C8. Автоскейлинг узлов
Включи автомасштабирование группы узлов, создай нагрузку (много подов)
и посмотри, как добавляются ноды. Верни обратно.

#### C9. Сравнение стоимости
Для одной и той же конфигурации посчитай: managed PostgreSQL HA vs две ВМ
с самостоятельной репликацией (ВМ + диски + бэкап-хранилище + твоё время).
Сделай вывод письменно.

<details><summary>Ответ</summary>

Обычно managed дороже по счёту на 30-100%, но дешевле по совокупной стоимости
для маленькой команды.

</details>

#### C10. Уборка
Удали кластеры, ноды, балансировщики, диски и снапшоты. Проверь по счёту,
что ничего не осталось.

#### C11. 🟧 RDS for PostgreSQL
1. Создай DB subnet group из двух приватных подсетей и `db.t4g.micro` с
   `--no-publicly-accessible`, `--manage-master-user-password`.
2. Подключись с ВМ приложения через `psql ... sslmode=verify-full` с CA bundle RDS.
3. Посмотри, какие расширения доступны (`SHOW rds.extensions;`) и что может роль `rds_superuser`.
4. Удали инстанс с финальным снапшотом, затем удали снапшот.

<details><summary>Ответ</summary>

`rds_superuser` может создавать расширения из списка поддерживаемых и управлять
ролями, но не является настоящим superuser (нет доступа к файлам, `COPY ... PROGRAM` и т.п.).
Без финального снапшота удаление требует `--skip-final-snapshot`.

</details>

#### C12. 🟧🟦 Один кластер Kubernetes — два облака
Создай минимальный кластер в EKS (например, `eksctl create cluster` с одной малой нодой)
и в Yandex Managed Kubernetes. Получи kubeconfig обоими CLI, задеплой один и тот же манифест
с `Service type: LoadBalancer`. Сравни: что появилось в консоли, сколько стоит час, как быстро
всё удалилось.

<details><summary>Ответ</summary>

В EKS создастся балансировщик AWS (CLB или NLB, в зависимости от контроллера
и аннотаций), в Yandex — Network Load Balancer. Удалять сначала `Service` (иначе балансировщик
может остаться «сиротой»), потом кластер.

</details>

#### C13. 🇰🇿 Каталог managed в РК
Для своего учебного проекта (PostgreSQL + Redis + k8s + S3) проверь по публичным страницам
Yandex `kz1` и двух провайдеров РК, что есть «как сервис», а что придётся эксплуатировать
самому. Посчитай, сколько часов в месяц это добавит команде.

<details><summary>Ответ</summary>

Типичный вывод: k8s и S3 есть почти везде, managed-PostgreSQL — не у всех,
managed Redis/Kafka — реже; «своими руками» обычно добавляет десятки часов в месяц
плюс дежурства.

</details>

### Блок D. Инциденты

**D1.** Managed-база «переехала» на другой хост ночью, приложение не восстановило
соединение. Что не так с приложением и с конфигурацией?

<details><summary>Ответ</summary>

Приложение не переподключается и/или в конфиге прописан конкретный хост;
нужны endpoint кластера, повторные подключения, таймауты и пул с проверкой соединений.

</details>

**D2.** Приложение не может подключиться к managed-базе после создания. Алгоритм проверки.

<details><summary>Ответ</summary>

Security group базы и подсети, правильный ли FQDN и порт, TLS и корневой
сертификат, существует ли пользователь и база, права пользователя, лимит соединений,
доступность из нужной зоны/подсети.

</details>

**D3.** Бэкап есть, но восстановление заняло 6 часов вместо ожидаемого часа.
Что нужно было сделать заранее?

<details><summary>Ответ</summary>

Провести учебное восстановление и замерить RTO, выбрать подходящий класс дисков
и конфигурацию, заранее определить процедуру и ответственных, рассмотреть готовую
реплику для быстрого переключения.

</details>

**D4.** Нужно расширение PostgreSQL, которого нет в managed. Варианты решения.

<details><summary>Ответ</summary>

Проверить альтернативы (другой провайдер, другая версия сервиса), реализовать
функциональность на стороне приложения, вынести конкретную задачу на отдельную ВМ,
либо полностью перейти на самостоятельную инсталляцию.

</details>

**D5.** Счёт за managed-сервисы вырос втрое. Что смотришь?

<details><summary>Ответ</summary>

Детализацию по сервисам: класс хостов, число реплик, объём дисков и бэкапов,
трафик, добавленные окружения, автоскейлинг узлов, забытые тестовые кластеры.

</details>

**D6.** В k8s появилось 14 внешних IP и балансировщиков. Как исправить?

<details><summary>Ответ</summary>

Перевести сервисы на ClusterIP и использовать один Ingress-контроллер;
проверить, что внешние адреса освободились.

</details>

**D7.** Провайдер объявил окно обслуживания на ближайшую ночь. Что делаешь?

<details><summary>Ответ</summary>

Убедиться, что приложение переживает переподключения, предупредить команду,
при возможности перенести окно, подготовить наблюдение за сервисом на это время,
проверить, что есть свежий бэкап.

</details>

**D8.** Провайдер полностью недоступен несколько часов. Что должно быть готово заранее?

<details><summary>Ответ</summary>

Заранее: копия критичных данных вне провайдера, описанная процедура
восстановления, инфраструктура как код (можно развернуть в другом месте),
понимание допустимого простоя и коммуникация с бизнесом.

</details>

**D9.** Managed Redis потерял данные после обслуживания. Почему это могло произойти?

<details><summary>Ответ</summary>

Persistence был отключён (или режим хранения не гарантирует сохранность);
Redis — не хранилище для данных, которые нельзя потерять, если это не настроено явно.

</details>

**D10.** Руководство просит «уйти от managed, чтобы сэкономить». Как построишь разговор?

<details><summary>Ответ</summary>

Сравнить полную стоимость владения, включая часы инженеров, риски простоя
и стоимость внедрения HA и бэкапов; предложить точечный переход для конкретных
сервисов, где экономия реальна, и зафиксировать, какие обязанности вернутся команде.

</details>

**D11.** 🟧 Счёт AWS за учебный месяц — 180 $, хотя «запускал EKS всего на вечер».
Что тикало?

<details><summary>Ответ</summary>

Ресурсы вокруг кластера не удалились вместе с ним или кластер жил дольше вечера:
control plane (почасово), ноды, NAT Gateway (почасово + трафик), балансировщики
от `Service type: LoadBalancer`, EBS-диски от PVC, публичные IPv4, CloudWatch-логи.
Смотреть Cost Explorer по сервисам и тегам; удалять через `eksctl delete cluster`/Terraform.

</details>

**D12.** 🟦🇰🇿 Прод на Managed PostgreSQL в `kz1` лёг вместе с зоной `kz1-a`.
Что должно было быть готово и как сократить простой в следующий раз?

<details><summary>Ответ</summary>

Заранее: бэкапы и WAL в хранилище на другой площадке в РК, реплика или резервный
кластер у другого провайдера/в другом ЦОД РК, IaC для быстрого развёртывания, отрепетированный
DR с измеренным RTO. Сократить простой — держать тёплый резерв и автоматизировать
переключение DNS/строк подключения; честно зафиксировать с бизнесом RTO для региона с одной зоной.

</details>

### Блок E. Вопросы с собеседования

**1.** Что такое managed-сервис и что он берёт на себя?

<details><summary>Ответ</summary>

Сервис, где провайдер отвечает за установку, обновления, отказоустойчивость
и встроенные бэкапы, а клиент — за данные, доступы и использование.

</details>

**2.** Managed или своё: как выбираешь?

<details><summary>Ответ</summary>

По критериям: размер и экспертиза команды, требования к версиям и тюнингу,
бюджет, риски, скорость запуска.

</details>

**3.** Как обеспечивается отказоустойчивость managed-базы?

<details><summary>Ответ</summary>

Несколькими хостами в разных зонах с автоматическим failover и endpoint'ом кластера.

</details>

**4.** Что нельзя сделать в managed PostgreSQL?

<details><summary>Ответ</summary>

Получить суперпользователя, произвольные расширения, доступ к ОС и файлам конфигурации.

</details>

**5.** Кто отвечает за бэкапы в managed-сервисе?

<details><summary>Ответ</summary>

Провайдер выполняет бэкапы по заданной политике, но ответственность за проверку
восстановления и RTO остаётся на клиенте.

</details>

**6.** Как устроен managed Kubernetes и за что отвечает клиент?

<details><summary>Ответ</summary>

Провайдер управляет control plane; клиент отвечает за ноды, нагрузки, мониторинг
и конфигурацию кластера.

</details>

**7.** Что происходит при создании LoadBalancer-сервиса в облачном k8s?

<details><summary>Ответ</summary>

Создаётся реальный облачный балансировщик с публичным IP — платный ресурс.

</details>

**8.** Какие риски у managed-подхода?

<details><summary>Ответ</summary>

Lock-in, ограничения тюнинга, стоимость, зависимость от SLA, иллюзия «за нас всё сделают».

</details>

**9.** Как снизить vendor lock-in?

<details><summary>Ответ</summary>

Использовать стандартные технологии, описывать инфраструктуру кодом, держать копию
данных вне провайдера, оценивать стоимость переезда заранее.

</details>

**10.** Что ты всё равно делаешь сам, даже используя managed?

<details><summary>Ответ</summary>

Доступы и безопасность, схему и производительность, мониторинг и алерты,
проверку восстановления, архитектуру отказоустойчивости и контроль расходов.

</details>

**11.** Чем RDS Multi-AZ отличается от read replica?

<details><summary>Ответ</summary>

Multi-AZ — синхронный standby для отказоустойчивости: автоматический failover,
но (в классическом варианте) не читается. Read replica — асинхронная копия для
масштабирования чтения, у неё свой endpoint, её можно продвинуть в primary вручную.

</details>

**12.** Как дать поду в EKS доступ к S3 без ключей?

<details><summary>Ответ</summary>

EKS Pod Identity (или IRSA): IAM-роль связывается с Kubernetes ServiceAccount,
под получает временные ключи роли; статические access keys в секретах не нужны.

</details>
