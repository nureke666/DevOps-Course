## 🗺️ Чем объектное хранилище отличается от диска

```text:no-line-numbers
 БЛОЧНОЕ (диск ВМ)        ФАЙЛОВОЕ (NFS)          ОБЪЕКТНОЕ (S3)
 ─────────────────        ──────────────          ──────────────
 /dev/vdb, ФС сверху      общая папка по сети     бакет + ключ объекта
 монтируется к одной ВМ   монтируется к многим    доступ по HTTP API
 быстрый, дорогой         удобно, но узкое место  бесконечный объём, дёшево
 базы, ОС                 общие файлы приложений  бэкапы, статика, медиа,
                                                   логи, артефакты
```

**Объект** = данные + метаданные + уникальный ключ. Файлов и папок там нет:
`images/2026/09/photo.jpg` — это просто длинный ключ, а «папки» рисует интерфейс.

| Свойство | Следствие |
|----------|-----------|
| Доступ только по API (HTTP) | Нельзя примонтировать как диск (костыли вроде s3fs существуют, но медленные) |
| Объект неизменяем | «Изменить» = перезаписать целиком |
| Практически бесконечный объём | Не надо планировать место |
| Оплата за объём + операции + исходящий трафик | Дешёвое хранение, платный выход |
| Высокая надёжность (реплики внутри хранилища) | Но это **не бэкап сам по себе** |

⭐ S3 — это протокол де-факто: почти все облака (в том числе Yandex Cloud и региональные) предоставляют
**S3-совместимый API**, поэтому работают одни и те же инструменты: `aws s3`, `s3cmd`,
`mc` (MinIO client), библиотеки `boto3`, драйверы бэкап-систем.

### Одно хранилище — три семейства

| Понятие | AWS S3 | Yandex Object Storage | Облака РК |
|---------|--------|-----------------------|-----------|
| Endpoint | региональный по умолчанию (`s3.<регион>.amazonaws.com`), `--endpoint-url` не нужен | `https://storage.yandexcloud.net`; регион Казахстан — `https://storage.yandexcloud.kz` | свой у провайдера (из консоли): PS Cloud — S3 и OpenStack Swift; у Kazteleport «Объектное хранилище S3» в каталоге |
| Имя бакета | глобально уникально | уникально в пределах хранилища | по правилам провайдера |
| Классы | `STANDARD`, `STANDARD_IA`, `ONEZONE_IA`, `INTELLIGENT_TIERING`, `GLACIER_IR`, `GLACIER`, `DEEP_ARCHIVE` | `STANDARD`, `COLD`, `ICE`, `INTELLIGENT_TIERING` | проверь у провайдера |
| Кто даёт доступ | IAM-политики + bucket policy (ACL по умолчанию выключены) | роли IAM (`storage.viewer`, `storage.uploader`, `storage.editor`…) + bucket policy + ACL | обычно EC2-совместимые ключи проекта + политики — проверь |
| Ключи для CLI | роль/профиль SSO; access keys — крайний случай | **статический ключ сервисного аккаунта** (`yc iam access-key create`) | ключи из консоли / `openstack ec2 credentials create` |
| Защита от публичности | Block Public Access, **включён по умолчанию** для новых бакетов | бакет приватный, публичный доступ включается в настройках | проверь |
| Версионирование, lifecycle | да | да (через S3 API) | проверь |
| Object Lock (WORM) | да | есть — проверь для своего региона | проверь |
| Шифрование | SSE-S3 по умолчанию, SSE-KMS | ключ KMS на бакет | проверь |
| CDN перед бакетом | CloudFront | Cloud CDN | проверь |

## 1. Основные понятия

```text:no-line-numbers
БАКЕТ  my-project-backups                    ← уникальное имя, регион, класс
 ├── ОБЪЕКТ  db/2026-09-13/dump.sql.gz       ← ключ = «путь»
 │     ├── содержимое
 │     ├── метаданные (Content-Type, кастомные)
 │     ├── версии (если включено версионирование)
 │     └── класс хранения (стандартный / холодный / архив)
 └── НАСТРОЙКИ: политика доступа, шифрование, lifecycle, логирование, CORS
```

| Класс хранения | AWS | Yandex | Когда | Особенность |
|----------------|-----|--------|-------|-------------|
| Стандартный | `STANDARD` | `STANDARD` | Активные данные, статика | Дороже за хранение, дешевле за доступ |
| Холодный | `STANDARD_IA` | `COLD` | Бэкапы, редкий доступ | Дешевле хранение, платный доступ, минимальный срок хранения |
| Ледяной/архивный | `GLACIER`, `DEEP_ARCHIVE` | `ICE` | Долгосрочный архив | Очень дёшево; в AWS Glacier Flexible/Deep Archive извлечение — часы; у Yandex ICE — длинный минимальный срок хранения и дорогой доступ (проверь) |
| Автоматический | `INTELLIGENT_TIERING` | `INTELLIGENT_TIERING` | Непредсказуемый доступ | Хранилище само двигает объекты |

## 2. Работа через CLI

```bash
# ── AWS S3: endpoint не нужен ──
aws configure --profile aws              # или SSO: aws configure sso
aws s3 mb s3://my-project-backups-7f3a --region eu-central-1 --profile aws

# ── Yandex Object Storage: aws-cli со своим endpoint ──
yc iam service-account create --name sa-storage
yc iam access-key create --service-account-name sa-storage     # key_id + secret (показывается один раз!)
aws configure --profile yc               # region: ru-central1
export AWS_PROFILE=yc
ENDPOINT="--endpoint-url=https://storage.yandexcloud.net"      # регион Казахстан: https://storage.yandexcloud.kz
#   в новых версиях aws-cli endpoint можно прописать в ~/.aws/config: endpoint_url = https://...

# бакеты
aws s3 $ENDPOINT mb s3://my-project-backups
aws s3 $ENDPOINT ls

# объекты
aws s3 $ENDPOINT cp dump.sql.gz s3://my-project-backups/db/2026-09-13/
aws s3 $ENDPOINT cp s3://my-project-backups/db/2026-09-13/dump.sql.gz ./
aws s3 $ENDPOINT sync ./static s3://my-site-static --delete     # ⭐ синхронизация каталога
aws s3 $ENDPOINT ls s3://my-project-backups/db/ --recursive --human-readable
aws s3 $ENDPOINT rm s3://my-project-backups/db/old.sql.gz

# размер бакета
aws s3 $ENDPOINT ls s3://my-project-backups --recursive --summarize | tail -3

# временная ссылка (объект приватный, ссылка живёт N секунд) ⭐
aws s3 $ENDPOINT presign s3://my-bucket/report.pdf --expires-in 3600
```
Для AWS те же команды — без `$ENDPOINT`. Для S3 провайдера РК — с его endpoint'ом.

Альтернативные инструменты:
```bash
s3cmd sync ./dir s3://bucket/           # классика
mc alias set cloud https://endpoint KEY SECRET && mc cp file cloud/bucket/   # MinIO client (официальный больше не раздают; у форка pgsty/silo — mcli)
rclone sync /data cloud:bucket          # универсальный, умеет десятки бэкендов
```

## 3. Доступ: ключи, политики, публичность

```text:no-line-numbers
 КТО ОБРАЩАЕТСЯ                     КАК ПРАВИЛЬНО
 ───────────────                    ─────────────
 приложение на ВМ в облаке      →   роль ВМ (AWS) / сервисный аккаунт ВМ (Yandex) ⭐
 CI/CD пайплайн                 →   OIDC-федерация (AWS) / отдельный SA, ключ в секретах CI
 внешняя система                →   отдельный ключ с минимальными правами + ротация
 пользователи (скачать файл)    →   presigned URL с TTL, бакет остаётся приватным
 статика сайта                  →   публичный доступ только на чтение + CDN
```

```json
// пример bucket policy: публичное чтение только для каталога static/
{
  "Version": "2012-10-17",
  "Statement": [{
    "Effect": "Allow",
    "Principal": "*",
    "Action": "s3:GetObject",
    "Resource": "arn:aws:s3:::my-site/static/*"
  }]
}
```
Тот же формат политик понимает Yandex Object Storage (ARN вида `arn:aws:s3:::bucket/*`;
конкретный сервисный аккаунт указывается как `"Principal": {"CanonicalUser": "<id SA>"}`).

```bash
# AWS: в новых бакетах Block Public Access включён — чтобы открыть static/, его надо ослабить
aws s3api put-public-access-block --bucket my-site \
  --public-access-block-configuration BlockPublicAcls=true,IgnorePublicAcls=true,BlockPublicPolicy=false,RestrictPublicBuckets=false
aws s3api put-bucket-policy --bucket my-site --policy file://public-static.json
# для бакетов с данными — всё true и никогда не трогать
aws s3api get-public-access-block --bucket my-project-backups-7f3a

# Yandex: роль на бакеты каталога для сервисного аккаунта
yc resource-manager folder add-access-binding <folder-id> \
  --role storage.uploader --subject serviceAccount:<sa-id>
```

Политика «бэкап-агент пишет, но не удаляет» (AWS):
```json
{
  "Version": "2012-10-17",
  "Statement": [{
    "Effect": "Allow",
    "Action": ["s3:PutObject", "s3:GetObject"],
    "Resource": "arn:aws:s3:::my-project-backups-7f3a/db/*"
  }, {
    "Effect": "Allow",
    "Action": "s3:ListBucket",
    "Resource": "arn:aws:s3:::my-project-backups-7f3a",
    "Condition": {"StringLike": {"s3:prefix": ["db/*"]}}
  }]
}
```
В Yandex аналог — роль `storage.uploader` (загрузка без удаления; перезапись возможна,
поэтому версионирование обязательно).

⚠️ **Публичный бакет — топ-1 причина утечек данных в облаках.** Правила:
1. По умолчанию бакет приватный; публичность включается осознанно и точечно.
2. Публичным делают только каталог со статикой, и только на `GetObject`.
3. Бэкапы, дампы, документы — **никогда** не публичные.
4. Регулярно проверяй, какие бакеты открыты наружу.
5. Логирование доступа к бакету включено для чувствительных данных.

## 4. Версионирование, блокировка и защита от удаления

```text:no-line-numbers
БЕЗ версионирования            С версионированием
──────────────────             ──────────────────
перезаписал файл → старого     каждая перезапись создаёт новую версию
уже нет                        удаление ставит delete marker,
удалил → нет насовсем          старая версия остаётся и восстанавливается ⭐
```

```bash
# одинаково для AWS (без $ENDPOINT) и Yandex (с ним)
aws s3api $ENDPOINT put-bucket-versioning --bucket my-project-backups \
  --versioning-configuration Status=Enabled
aws s3api $ENDPOINT get-bucket-versioning --bucket my-project-backups
aws s3api $ENDPOINT list-object-versions --bucket my-project-backups --prefix db/shop.dump.gz

# «воскресить» удалённый объект = удалить его delete marker
aws s3api $ENDPOINT delete-object --bucket my-project-backups \
  --key db/shop.dump.gz --version-id <VersionId маркера>

# AWS: Object Lock (WORM) — включается на бакете, затем правило по умолчанию
aws s3api create-bucket --bucket my-locked-backups-7f3a \
  --create-bucket-configuration LocationConstraint=eu-central-1 \
  --object-lock-enabled-for-bucket
aws s3api put-object-lock-configuration --bucket my-locked-backups-7f3a \
  --object-lock-configuration '{"ObjectLockEnabled":"Enabled","Rule":{"DefaultRetention":{"Mode":"COMPLIANCE","Days":30}}}'
```

| Механизм | Зачем |
|----------|-------|
| **Versioning** | Откат случайной перезаписи/удаления |
| **Object Lock / WORM** (если есть) | Объект нельзя удалить до истечения срока — защита от шифровальщика ⭐ |
| **Отдельный аккаунт/ключ для удаления** | Прод не имеет прав на удаление бэкапов |
| **Репликация в другой регион** | Защита от потери площадки (⚠️ ПДн РК — только в регион/ЦОД в РК) |
| **Шифрование (SSE)** | Данные шифруются на стороне хранилища или клиента |

> ⭐ Для бэкапов правильная связка: отдельный бакет + версионирование + object lock +
> учётка с правами только на запись (`PutObject`), без `DeleteObject`.
> Тогда взломанный прод-сервер не сможет уничтожить резервные копии.
> ⚠️ `COMPLIANCE`-режим в AWS не снимет даже root до конца срока — на учебном бакете
> ставь маленький срок или `GOVERNANCE`.

## 5. Lifecycle: автоматическое управление данными

```text:no-line-numbers
 объект загружен
      │  30 дней  → перевести в холодный класс
      │  90 дней  → перевести в архив
      │ 365 дней  → удалить
      └ старые версии: удалить через 30 дней
        незавершённые multipart-загрузки: удалить через 7 дней ⭐ (про них забывают,
                                                                  а они занимают место)
```
```json
{
  "Rules": [{
    "ID": "backups-lifecycle",
    "Status": "Enabled",
    "Filter": { "Prefix": "db/" },
    "Transitions": [{ "Days": 30, "StorageClass": "COLD" }],
    "Expiration": { "Days": 365 },
    "NoncurrentVersionExpiration": { "NoncurrentDays": 30 },
    "AbortIncompleteMultipartUpload": { "DaysAfterInitiation": 7 }
  }]
}
```
Это вариант для **Yandex** (`COLD`, `ICE`). Для **AWS** меняются только классы:
```json
"Transitions": [
  { "Days": 30, "StorageClass": "STANDARD_IA" },
  { "Days": 90, "StorageClass": "GLACIER" }
]
```
```bash
aws s3api $ENDPOINT put-bucket-lifecycle-configuration --bucket my-project-backups \
  --lifecycle-configuration file://lifecycle.json
aws s3api $ENDPOINT get-bucket-lifecycle-configuration --bucket my-project-backups
```

## 6. Типовые сценарии девопса

| Сценарий | Как делается |
|----------|--------------|
| **Бэкапы БД** | `pg_dump`/WAL-G пишет прямо в бакет; lifecycle + версионирование + отдельные права (см. [«05. Backup и restore»](/databases/05-backup-restore)) |
| **Статика сайта** | `aws s3 sync ./dist s3://site --delete` из CI + CDN перед бакетом |
| **Артефакты сборки** | CI кладёт архивы/образы; retention через lifecycle |
| **[Terraform](/terraform/) state** | Бакет + блокировка (в AWS — `use_lockfile` в новых версиях Terraform или DynamoDB; у S3-совместимых — проверь) |
| **Логи и аналитика** | Долгое хранение логов, источник для ClickHouse/Loki |
| **Обмен файлами** | presigned URL с ограниченным сроком вместо публичного доступа |
| **Хранилище Loki/Thanos** | Чанки метрик и логов лежат в объектном хранилище |

```bash
# бэкап базы прямо в бакет, с датой в ключе
pg_dump -F c shop | gzip | \
  aws s3 $ENDPOINT cp - s3://my-backups/db/shop-$(date +%F).dump.gz

# выгрузка статики из CI
aws s3 $ENDPOINT sync ./dist s3://my-site --delete --cache-control "max-age=3600"
```

## 7. В облаках РК

- **Yandex Cloud `kz1`**: Object Storage с endpoint'ом `https://storage.yandexcloud.kz` —
  те же `aws s3`/`s3api`-команды, ключи сервисного аккаунта из kz-профиля. Данные регионов
  изолированы: бакет в `kz1` и бакет в `ru-central1` — разные хранилища (проверь, сентябрь 2026).
- **PS Cloud**: объектное хранилище, совместимое с S3 и OpenStack Swift; **Kazteleport** —
  «Объектное хранилище S3» в каталоге услуг. Поддержку версионирования, lifecycle,
  object lock, классов хранения и presigned URL проверяй в их документации до того,
  как строить на этом бэкап-схему.
- ⭐ Бэкапы с ПДн граждан РК — это тоже ПДн: копию «для надёжности» кладут в **другой ЦОД
  или к другому провайдеру в РК**, а не в S3 во Франкфурте.
- Инструменты не меняются: `aws s3 --endpoint-url`, `rclone`, `restic`, WAL-G — со своим
  endpoint'ом. Подробнее: [«10. Облака РК»](/cloud/10-kz-clouds).

## 8. Грабли

| Грабля | Последствие | Решение |
|--------|-------------|---------|
| Публичный бакет с данными | Утечка | Приватный по умолчанию, аудит публичности, Block Public Access |
| Ключи в коде/репозитории | Компрометация аккаунта | Роли/сервисные аккаунты, секреты CI, Vault |
| Нет версионирования на бэкапах | Перезаписали/удалили — всё | Versioning + object lock |
| Прод имеет право удалять бэкапы | Шифровальщик уносит и копии | Раздельные права |
| Нет lifecycle | Бакет растёт и дорожает вечно | Правила перехода и удаления |
| Версионирование без `NoncurrentVersionExpiration` | Старые версии копятся, счёт растёт | Правило для неактуальных версий |
| Забытые multipart-загрузки | Платишь за невидимые данные | `AbortIncompleteMultipartUpload` |
| Раздача файлов напрямую из бакета без CDN | Большой счёт за egress | CDN и кэширование |
| `s3fs` как «диск» для базы | Медленно и ненадёжно | Объектное хранилище — не файловая система |
| Имя бакета как у прода на тесте | Перепутали окружения | Явные префиксы `prod-`/`stage-` |
| Забыли `--endpoint-url` с Yandex-ключами | `InvalidAccessKeyId` от AWS | Профиль с `endpoint_url` или переменная |
| Бакет Yandex создан в `ru-central1`, а данные — ПДн РК | Нарушение локализации | Бакет в `kz1` / у провайдера в РК |
| Холодный класс для часто читаемых данных | Платишь за извлечение и минимальный срок | Класс — по частоте доступа |
| COMPLIANCE object lock на год на тестовом бакете | Нельзя удалить даже админу | На учёбе — GOVERNANCE или 1 день |

## 💼 Как это в DevOps

- Объектное хранилище — «универсальный склад» инфраструктуры: бэкапы, артефакты,
  статика, terraform state, чанки Loki/Thanos, архив логов.
- Доступ выдаётся сервисным аккаунтам/ролям с минимальными правами: CI — запись артефактов,
  бэкап-агент — только `PutObject` в свой префикс, приложение — чтение своих объектов.
- Бэкапы в бакете с версионированием и object lock — это то, что реально спасает
  при шифровальщике; без этого «бэкапы в облаке» дают ложное чувство безопасности.
- Всё создаётся Terraform'ом: бакет, политика, lifecycle, права — чтобы окружения
  были одинаковыми и воспроизводимыми.
- Регулярный аудит: какие бакеты публичны, где нет lifecycle, где лежат старые ключи.
- Совместимость S3 API — главный инструмент против lock-in: переезд хранилища между AWS,
  Yandex и облаком РК — это смена endpoint'а и ключей плюс `rclone sync`.

| Посмотреть содержимое и размер | `aws s3 ls s3://bucket --recursive --summarize` |
| Временная ссылка | `aws s3 presign s3://bucket/key --expires-in 3600` |
| Бэкап базы в бакет | `pg_dump ... \| gzip \| aws s3 cp - s3://bucket/key` |
| Включить версии | `aws s3api put-bucket-versioning --versioning-configuration Status=Enabled` |
| Посмотреть версии | `aws s3api list-object-versions --bucket b --prefix key` |
| Защитить от удаления | Object Lock + права без `DeleteObject` |
| Удалять старое автоматически | `aws s3api put-bucket-lifecycle-configuration --lifecycle-configuration file://...` |
| Закрыть публичность (AWS) | `aws s3api put-public-access-block ... =true` |
| Убрать «невидимый» мусор | `AbortIncompleteMultipartUpload` |
| Раздавать статику | Публичное чтение только на `static/*` + CDN (CloudFront / Cloud CDN) |
| Работать из приложения | Роль ВМ / сервисный аккаунт ВМ, без статических ключей |
| Другой клиент | `s3cmd`, `mc`, `rclone` |
| Endpoint Yandex для РК | `https://storage.yandexcloud.kz` |

## 🧠 Что запомнить

1. Объектное хранилище — не файловая система: бакет, ключ, объект, доступ по HTTP API.
2. S3 — стандарт де-факто: AWS, Yandex и облака РК дают S3-совместимый API и те же
   инструменты; меняются endpoint, ключи и названия классов.
3. Объект неизменяем: «изменение» — это перезапись целиком.
4. ⭐ Публичный бакет — главная причина утечек; по умолчанию всё приватно
   (в AWS — Block Public Access включён для новых бакетов).
5. Для приватной выдачи файлов используют presigned URL с ограниченным сроком.
6. Версионирование спасает от случайной перезаписи и удаления.
7. Бэкапы: отдельный бакет, версии, object lock, права без удаления; ПДн РК — копия в РК.
8. Lifecycle обязателен, иначе бакет растёт и дорожает вечно; не забывай про
   незавершённые multipart-загрузки и старые версии.
9. Приложения ходят в хранилище через роли/сервисные аккаунты, а не статические ключи в коде;
   у Yandex для S3 API нужен статический ключ SA — храни его как секрет.
10. Раздача больших объёмов напрямую из бакета бьёт по счёту — нужен CDN и кэширование.

### Блок A. Теория

**A1.** Чем объектное хранилище отличается от блочного и файлового?

<details><summary>Ответ</summary>

Блочное — «сырой» диск, монтируется к одной машине, поверх него файловая система.
Файловое — сетевая файловая система для многих клиентов. Объектное — хранилище объектов
с доступом по HTTP API, практически безграничное и дешёвое, но без семантики файловой
системы.

</details>

**A2.** Что такое объект, ключ и бакет? Есть ли в S3 папки?

<details><summary>Ответ</summary>

Бакет — контейнер верхнего уровня с уникальным именем; объект — данные плюс
метаданные; ключ — уникальное имя объекта внутри бакета. Папок нет: «каталоги» —
это префиксы в ключе.

</details>

**A3.** Почему объект нельзя «изменить частично»?

<details><summary>Ответ</summary>

Объекты неизменяемы: запись создаёт новый объект (или новую версию) целиком.
Частичное обновление не поддерживается (кроме специальных механизмов вроде multipart
при загрузке).

</details>

**A4.** ⭐ Почему S3 называют стандартом де-факто и что это даёт на практике?

<details><summary>Ответ</summary>

Потому что подавляющее большинство хранилищ реализуют S3 API. Практически это
значит, что инструменты (`aws s3`, `s3cmd`, `mc`, `rclone`), библиотеки и бэкап-системы
работают с любым провайдером, меняется только endpoint.

</details>

**A5.** За что платят в объектном хранилище?

<details><summary>Ответ</summary>

За объём хранения (с учётом класса), за количество операций (PUT/GET/LIST)
и за исходящий трафик; иногда за извлечение из холодных классов.

</details>

**A6.** Какие бывают классы хранения и когда какой выбирать?

<details><summary>Ответ</summary>

Стандартный — активные данные и статика; холодный — бэкапы и редкий доступ;
архивный — долгосрочное хранение с медленным извлечением. Выбор — по частоте обращения.

</details>

**A7.** Как правильно дать доступ приложению на ВМ? А CI? А внешнему пользователю?

<details><summary>Ответ</summary>

Приложению на ВМ — сервисный аккаунт с временными токенами через метаданные;
CI — отдельный сервисный аккаунт, ключ в секретах CI; внешнему пользователю — presigned
URL, бакет остаётся приватным.

</details>

**A8.** Что такое presigned URL и чем он лучше публичного бакета?

<details><summary>Ответ</summary>

Временная подписанная ссылка на приватный объект с ограниченным сроком действия.
Позволяет отдать файл конкретному человеку, не открывая бакет всему интернету.

</details>

**A9.** Что даёт версионирование? Что происходит при удалении объекта?

<details><summary>Ответ</summary>

Хранение всех версий объекта: перезапись создаёт новую версию, удаление ставит
delete marker, а прежние версии остаются и могут быть восстановлены.

</details>

**A10.** Что такое object lock и от какой угрозы он защищает?

<details><summary>Ответ</summary>

Запрет на удаление/перезапись объекта до истечения срока (WORM). Защищает
от шифровальщиков и злонамеренного/ошибочного удаления бэкапов.

</details>

**A11.** Какие права должны быть у учётной записи бэкап-агента и почему?

<details><summary>Ответ</summary>

Только запись в свой префикс (и чтение, если нужно проверять): без права
удаления. Тогда компрометация сервера не приводит к уничтожению резервных копий.

</details>

**A12.** Зачем нужны lifecycle-правила? Приведи три примера.

<details><summary>Ответ</summary>

Автоматическое управление объектами: перевод в холодный класс через N дней,
удаление старых объектов и старых версий, очистка незавершённых multipart-загрузок.

</details>

**A13.** Что такое незавершённые multipart-загрузки и чем они опасны?

<details><summary>Ответ</summary>

Части файлов, загрузка которых началась, но не завершилась. Они не видны
в обычном листинге, но занимают место и тарифицируются; убираются правилом lifecycle.

</details>

**A14.** Почему раздача файлов напрямую из бакета может стоить дорого?

<details><summary>Ответ</summary>

Исходящий трафик тарифицируется отдельно и обычно дороже хранения;
без CDN каждый запрос пользователя = оплаченный egress.

</details>

**A15.** Можно ли хранить базу данных на S3 через s3fs? Почему это плохая идея?

<details><summary>Ответ</summary>

Технически смонтировать можно (s3fs, goofys), но это эмуляция: высокие задержки,
отсутствие нормальной семантики файловой системы и блокировок. Для СУБД категорически
не подходит.

</details>

**A16.** 🟧🟦 Что меняется в командах `aws s3`, когда работаешь не с AWS, а с Yandex
Object Storage? Откуда брать ключи?

<details><summary>Ответ</summary>

Добавляется `--endpoint-url=https://storage.yandexcloud.net` (или `endpoint_url`
в профиле; для Казахстана — `https://storage.yandexcloud.kz`), регион в профиле —
`ru-central1`. Ключи — статический ключ сервисного аккаунта (`yc iam access-key create`),
права — роли `storage.*` на каталог или бакет. В AWS вместо ключей лучше роль/SSO.

</details>

**A17.** 🟧 Что такое Block Public Access и почему «сделать static/ публичным» в новом
бакете AWS требует двух шагов?

<details><summary>Ответ</summary>

Набор из четырёх флагов на уровне бакета и аккаунта, запрещающий публичные ACL
и политики; для новых бакетов включён по умолчанию. Чтобы открыть `static/*`, нужно
сначала разрешить публичные политики (`BlockPublicPolicy=false`,
`RestrictPublicBuckets=false`), а затем добавить bucket policy — иначе политика не применится.

</details>

**A18.** 🟧🟦 Сопоставь классы хранения AWS и Yandex. Почему lifecycle-JSON из одного облака
нельзя применить в другом без правок?

<details><summary>Ответ</summary>

Стандартный: `STANDARD` ↔ `STANDARD`; холодный: `STANDARD_IA` ↔ `COLD`;
архив: `GLACIER`/`DEEP_ARCHIVE` ↔ `ICE`; оба знают `INTELLIGENT_TIERING`. Названия классов
в `Transitions` разные, и хранилище отклонит незнакомый класс — JSON надо адаптировать
(остальные поля — `Expiration`, `NoncurrentVersionExpiration`, `AbortIncompleteMultipartUpload` —
совместимы).

</details>

**A19.** 🇰🇿 Где можно, а где нельзя хранить копию бэкапа базы с ПДн граждан РК?

<details><summary>Ответ</summary>

Бэкап с ПДн — тоже ПДн, требование локализации распространяется на него. Можно —
другой ЦОД того же провайдера в РК, другой провайдер с ЦОД в РК, Yandex `kz1`, своя площадка
в РК. Нельзя — зарубежные регионы (AWS, Yandex `ru-central1` и т.п.). Обезличенные данные —
отдельный разговор с юристом.

</details>

### Блок B. «Что делает команда / что тут не так»

```bash
B1.  aws s3 mb s3://my-backups --endpoint-url=https://storage.example.com
B2.  aws s3 sync ./dist s3://my-site --delete
B3.  aws s3 ls s3://my-backups --recursive --summarize
B4.  aws s3 presign s3://my-bucket/report.pdf --expires-in 3600
B5.  pg_dump -F c shop | gzip | aws s3 cp - s3://backups/db/shop-$(date +%F).dump.gz
B6.  aws s3 rm s3://my-backups --recursive
```

<details><summary>Ответ</summary>

**B1.** Создаёт бакет в S3-совместимом хранилище.
**B2.** Синхронизирует каталог, удаляя в бакете то, чего нет локально (осторожно!).
**B3.** Рекурсивный листинг с итоговым размером.
**B4.** Временная ссылка на час.
**B5.** Потоковый бэкап базы прямо в бакет с датой в ключе.
**B6.** Рекурсивное удаление всего бакета — крайне опасная команда.

</details>

Оцени решения:

```text:no-line-numbers
B7.  Бакет с бэкапами открыт на публичное чтение
B8.  Публичное чтение включено только для префикса static/
B9.  Ключи доступа зашиты в коде приложения
B10. Приложение на ВМ использует сервисный аккаунт и временные токены
B11. Бэкапы пишутся учёткой с полными правами, включая удаление
B12. У бакета с бэкапами включены версионирование и object lock
B13. Lifecycle отсутствует, в бакете 8 ТБ логов за три года
B14. Статика сайта раздаётся напрямую из бакета без CDN, трафик 2 ТБ/мес
B15. Один бакет используется и для прода, и для стейджа
B16. Через s3fs смонтирован бакет под каталог с данными PostgreSQL
B17. 🟧 aws s3api put-bucket-versioning --bucket b --versioning-configuration Status=Enabled
B18. 🟧 aws s3api put-public-access-block --bucket backups --public-access-block-configuration BlockPublicPolicy=false,...
B19. 🟦 aws s3 ls s3://my-bucket   # с ключом сервисного аккаунта Yandex, без --endpoint-url
B20. 🟦 lifecycle для Yandex с "StorageClass": "GLACIER"
B21. 🇰🇿 Дампы прод-базы из облака РК реплицируются в бакет AWS eu-central-1
B22. 🟧 Object Lock COMPLIANCE на 365 дней на учебном бакете
```

<details><summary>Ответ</summary>

**B7.** Публичные бэкапы — критическая утечка.
**B8.** Нормально для статики сайта.
**B9.** Ключи в коде — компрометация при любой утечке репозитория.
**B10.** Правильный подход.
**B11.** Полные права у бэкап-учётки — риск потери копий при компрометации.
**B12.** Правильная защита бэкапов.
**B13.** Без lifecycle расходы растут бесконечно.
**B14.** Дорогой egress; нужен CDN.
**B15.** Смешение окружений — риск перезаписи и утечки; нужны разные бакеты.
**B16.** Недопустимо: s3fs не даёт нужных гарантий и производительности для СУБД.
**B17.** Включает версионирование бакета — правильно для бэкапов (не забудь lifecycle для старых версий).
**B18.** Ослабление защиты от публичности на бакете **с бэкапами** — опасно; делают только
на бакете статики.
**B19.** Без endpoint'а запрос уйдёт в AWS и получит `InvalidAccessKeyId`.
**B20.** Yandex не знает класса `GLACIER` в lifecycle — нужен `ICE` (или `COLD`).
**B21.** Нарушение локализации ПДн: копии — только в РК.
**B22.** Удалить объекты не сможет никто, включая root, — год платить за хранение.
На учёбе — `GOVERNANCE` или срок в 1 день.

</details>

### Блок C. Практика

#### C1. 🔑 Первые операции
1. Создай бакет (или подними MinIO).
2. Загрузи файл, скачай обратно, посмотри список и размер.
3. Синхронизируй каталог с `--delete` и посмотри, что происходит при удалении файла локально.

#### C2. Доступ и ключи
1. Создай сервисный аккаунт с правами только на этот бакет.
2. Выпусти ключ, настрой профиль в `aws configure`.
3. Проверь, что он не может работать с другим бакетом.

#### C3. Публичность
1. Сделай бакет публичным на чтение только для `static/`.
2. Проверь `curl` на объект из `static/` и на объект из `private/`.
3. Верни приватность и проверь ещё раз.

<details><summary>Ответ</summary>

Объект из `private/` должен отдавать `AccessDenied`, из `static/` — содержимое.

</details>

#### C4. Presigned URL
Сгенерируй временную ссылку на приватный объект, открой её в браузере,
подожди истечения срока и убедись, что она перестала работать.

<details><summary>Ответ</summary>

После истечения срока ссылка вернёт ошибку подписи/срока.

</details>

#### C5. 🔑 Бэкап базы в бакет
1. Настрой скрипт: `pg_dump | gzip | aws s3 cp -` с датой в ключе.
2. Проверь восстановление: скачай, разверни в отдельную базу, сверь число строк.
3. Поставь скрипт в cron/systemd-timer и добавь метрику времени последнего успеха
   (textfile collector из [«04. Экспортеры»](/monitoring/04-exporters)).

<details><summary>Ответ</summary>

Ключевой шаг — именно проверка восстановления, а не только успешная загрузка.

</details>

#### C6. Версионирование
1. Включи версионирование.
2. Перезапиши файл дважды, посмотри список версий.
3. Удали объект и восстанови его из предыдущей версии.

<details><summary>Ответ</summary>

После удаления объекта он исчезает из обычного листинга, но доступен
в списке версий; восстановление — копирование нужной версии поверх текущей.

</details>

#### C7. Защита бэкапов
Настрой отдельную учётку с правами только `PutObject`/`GetObject` (без удаления).
Проверь, что удалить объект этой учёткой нельзя.

<details><summary>Ответ</summary>

Попытка удаления должна завершаться `AccessDenied`.

</details>

#### C8. Lifecycle
Настрой правила: перевод в холодный класс через 30 дней, удаление через 365,
удаление старых версий через 30 дней, очистка незавершённых загрузок через 7.
Проверь, что правила применились.

#### C9. Статика сайта
Выгрузи каталог статики, настрой `Content-Type` и `Cache-Control`, проверь отдачу.
Оцени, что изменится при подключении CDN.

#### C10. Учёт и уборка
Посчитай объём бакетов, найди самые большие префиксы, удали ненужное.
Запиши, сколько это стоит в месяц.

<details><summary>Ответ</summary>

Полезно сохранить отчёт по префиксам — он пригодится при разговоре о бюджете.

</details>

#### C11. 🟧 AWS: защита по умолчанию
1. Создай бакет, проверь `get-public-access-block` и шифрование по умолчанию
   (`get-bucket-encryption`).
2. Для `static/` ослабь только `BlockPublicPolicy`/`RestrictPublicBuckets`, добавь bucket policy
   на `static/*`, проверь `curl`.
3. Создай IAM-политику «PutObject/GetObject в `db/*`, без Delete» и проверь её.

<details><summary>Ответ</summary>

Шифрование SSE-S3 в новых бакетах AWS включено по умолчанию; объект из `private/`
отдаёт `403 AccessDenied`. Удаление учёткой без `s3:DeleteObject` — тоже `AccessDenied`.

</details>

#### C12. 🟦 Yandex: ключи и endpoint
1. Создай сервисный аккаунт, выдай роль `storage.uploader`, выпусти статический ключ.
2. Настрой профиль `aws configure --profile yc` и `endpoint_url` в `~/.aws/config`.
3. Проверь, что загрузка работает, а удаление — нет.
4. Если подключён регион Казахстан — повтори с `https://storage.yandexcloud.kz`.

<details><summary>Ответ</summary>

`aws s3 rm` под ключом с ролью `storage.uploader` должен давать `AccessDenied`,
а перезапись — проходить (поэтому нужны версии).

</details>

#### C13. 🟧🟦 Переезд хранилища
Перенеси бакет из одного облака в другое через `rclone sync` (два remote с разными
endpoint'ами). Сверь число объектов и суммарный размер. Что не переехало само
(политики, lifecycle, версии)?

<details><summary>Ответ</summary>

`rclone` переносит объекты и метаданные, но не настройки бакета: политики, lifecycle,
версионирование, CORS, object lock настраиваются заново (лучше — Terraform'ом); старые
версии объектов без специальных флагов не переносятся.

</details>

### Блок D. Инциденты

**D1.** В бакете с бэкапами обнаружен публичный доступ. Порядок действий.

<details><summary>Ответ</summary>

Немедленно закрыть публичный доступ, проверить логи обращений, оценить,
что могло утечь, уведомить ответственных, ротировать всё, что лежало в бэкапах
(пароли, ключи), настроить автоматическую проверку публичности бакетов.

</details>

**D2.** Ключ доступа утёк в публичный репозиторий. Что делать?

<details><summary>Ответ</summary>

Отозвать ключ, выпустить новый, проверить журнал действий на подозрительную
активность, удалить из истории репозитория, перевести доступ на сервисные аккаунты
и секреты CI.

</details>

**D3.** Скрипт бэкапа «работает», но в бакете пусто. Как разбирать?

<details><summary>Ответ</summary>

Проверить код возврата команд и `set -euo pipefail`, права учётки, корректность
endpoint и имени бакета, что pipe действительно передаёт данные (`aws s3 cp -`),
логи cron, наличие свободного места для временных файлов.

</details>

**D4.** Разработчик случайно выполнил `aws s3 rm --recursive` на бакете с бэкапами.
Что спасёт и что надо было настроить заранее?

<details><summary>Ответ</summary>

Спасёт версионирование (объекты восстанавливаются) и object lock.
Заранее нужны: версионирование, права без удаления у рабочих учёток, отдельный аккаунт
для бэкапов, репликация.

</details>

**D5.** Счёт за хранилище вырос вдвое, объём данных не изменился. Возможные причины?

<details><summary>Ответ</summary>

Накопление старых версий (включено версионирование без lifecycle),
незавершённые multipart-загрузки, переход в более дорогой класс, рост числа операций
или трафика, дубли бэкапов.

</details>

**D6.** Приложение получает `AccessDenied` при записи в бакет. Что проверишь?

<details><summary>Ответ</summary>

Роли и политику сервисного аккаунта, политику бакета, правильный ли бакет
и префикс, срок действия ключей/токена, время на машине (подпись чувствительна
к рассинхронизации), сетевой доступ к endpoint.

</details>

**D7.** Пользователи жалуются, что скачивание файлов медленное и дорогое.
Что предложишь?

<details><summary>Ответ</summary>

CDN перед бакетом, корректные `Cache-Control`, сжатие, региональное размещение,
presigned URL вместо проксирования через приложение.

</details>

**D8.** Шифровальщик зашифровал прод-сервер; бэкапы лежали в бакете, к которому
у сервера был полный доступ. Что было сделано неправильно?

<details><summary>Ответ</summary>

У прод-сервера были права на удаление бэкапов и не было версионирования/object
lock. Нужны раздельные учётки, WORM и копия в другом аккаунте/регионе.

</details>

**D9.** В бакете 300 ГБ «невидимых» данных: список объектов показывает меньше. Причина?

<details><summary>Ответ</summary>

Незавершённые multipart-загрузки и/или старые версии объектов; лечится
lifecycle-правилами.

</details>

**D10.** Нужно передать подрядчику один большой файл. Как это сделать правильно?

<details><summary>Ответ</summary>

Presigned URL с ограниченным сроком (и, если нужно, одноразовым префиксом),
без открытия бакета; для больших объёмов — multipart и контроль срока действия ссылки.

</details>

**D11.** 🟦 Скрипт бэкапа с ключами Yandex падает с `InvalidAccessKeyId`, хотя ключ
только что выпущен. Причина?

<details><summary>Ответ</summary>

Не указан `--endpoint-url` (или `endpoint_url` в профиле), запрос ушёл в AWS,
а там такого ключа нет. Второй вариант — ключ из другого региона (kz-профиль против
ru-central1) или неверный профиль в `AWS_PROFILE`.

</details>

**D12.** 🇰🇿 Аудитор спрашивает, где физически лежат все копии базы клиентов.
Как быстро и доказуемо ответить?

<details><summary>Ответ</summary>

Из кода и документации: Terraform-описание бакетов и их регионов/endpoint'ов,
настройки репликации, список мест, куда пишут бэкап-скрипты (WAL-G, pg_dump, snapshot-политики),
логи и SaaS, получающие данные. Хорошо, если это заранее собрано в реестре мест хранения ПДн
и проверяется автоматически (например, политика в CI запрещает бакеты вне разрешённых регионов).

</details>

### Блок E. Вопросы с собеседования

**1.** Что такое объектное хранилище и чем оно отличается от диска?

<details><summary>Ответ</summary>

Хранилище объектов с доступом по HTTP API: бесконечный объём, дёшево,
но не файловая система и не блочный диск.

</details>

**2.** Что такое бакет, объект, ключ?

<details><summary>Ответ</summary>

Бакет — контейнер, объект — данные с метаданными, ключ — уникальное имя объекта.

</details>

**3.** Как дать приложению доступ к бакету без статических ключей?

<details><summary>Ответ</summary>

Через сервисный аккаунт ВМ и временные токены из сервиса метаданных.

</details>

**4.** Что такое presigned URL?

<details><summary>Ответ</summary>

Временная подписанная ссылка на приватный объект.

</details>

**5.** Зачем нужно версионирование?

<details><summary>Ответ</summary>

Для защиты от случайной перезаписи и удаления: хранятся все версии.

</details>

**6.** Как защитить бэкапы от удаления и шифровальщика?

<details><summary>Ответ</summary>

Отдельный бакет, версионирование, object lock, права без удаления, копия
в другом аккаунте/регионе.

</details>

**7.** Что такое lifecycle-политики?

<details><summary>Ответ</summary>

Правила автоматического перевода объектов между классами и их удаления,
включая старые версии и незавершённые загрузки.

</details>

**8.** За что платят в S3?

<details><summary>Ответ</summary>

Объём, операции, исходящий трафик, извлечение из холодных классов.

</details>

**9.** Можно ли примонтировать S3 как диск и стоит ли?

<details><summary>Ответ</summary>

Технически можно, но не стоит: это эмуляция с высокими задержками, для баз — недопустимо.

</details>

**10.** Какие типовые задачи девопса решает объектное хранилище?

<details><summary>Ответ</summary>

Бэкапы, артефакты сборки, статика, terraform state, архив логов,
хранилище для Loki/Thanos, обмен файлами.

</details>

**11.** Чем работа с Yandex Object Storage отличается от AWS S3 для инженера?

<details><summary>Ответ</summary>

API тот же (S3), инструменты те же; отличаются endpoint (`storage.yandexcloud.net`,
для РК — `storage.yandexcloud.kz`), способ получения ключей (статический ключ SA),
модель прав (роли `storage.*` + bucket policy) и названия классов (`COLD`, `ICE`).

</details>

**12.** Как защищены бакеты AWS «из коробки» и что обычно ломают руками?

<details><summary>Ответ</summary>

Block Public Access включён, ACL выключены, SSE-S3 по умолчанию. Ломают руками:
отключают BPA «чтобы работало», раздают `s3:*` на `*`, хранят access keys в коде,
не включают версии и lifecycle.

</details>
