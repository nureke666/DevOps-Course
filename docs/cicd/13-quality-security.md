# 13. Качество и безопасность пайплайна

> Раздел опирается на практику роадмапа («Test: линтер flake8 (Python), eslint (JS) и т.д.»)
> и на топ-1 вопрос собеса «как бы ты построил идеальный пайплайн» — без quality gates
> и работы с секретами ответ будет неполным.
> **После темы ты умеешь:** собрать стадию проверок качества, встроить сканеры безопасности
> и грамотно обращаться с секретами в CI/CD.

---

## 1. Пирамида проверок в пайплайне

```text:no-line-numbers
        ┌──────────────────────────────────────────────┐  дорого, медленно, поздно
        │ e2e / нагрузочные / DAST (по расписанию)     │
        ├──────────────────────────────────────────────┤
        │ интеграционные тесты, контрактные тесты      │
        ├──────────────────────────────────────────────┤
        │ unit-тесты + покрытие                        │
        ├──────────────────────────────────────────────┤
        │ сканы: образ (Trivy), зависимости (SCA), SAST│
        ├──────────────────────────────────────────────┤
        │ линтер, форматтер, типы, детект секретов     │  дёшево, быстро, рано
        └──────────────────────────────────────────────┘
```
**Принцип:** чем дешевле проверка — тем раньше. Ошибка, найденная линтером за 10 секунд,
стоит в сотни раз дешевле той же ошибки, найденной e2e-тестом через 40 минут.

## 2. Линтеры и форматтеры по языкам

| Язык | Линтер | Форматтер | Типы |
|------|--------|-----------|------|
| Python | `flake8` / `ruff` | `black`, `isort` | `mypy` |
| JS/TS | `eslint` | `prettier` | `tsc --noEmit` |
| Go | `golangci-lint` | `gofmt` | встроенно |
| Java | `checkstyle`, `spotbugs` | `spotless` | компилятор |
| Shell | `shellcheck` | `shfmt` | — |
| Dockerfile | `hadolint` | — | — |
| YAML/k8s | `yamllint`, `kubeconform` | — | — |
| Terraform | `tflint`, `tfsec` | `terraform fmt` | `terraform validate` |
| Ansible | `ansible-lint` | — | `--syntax-check` |
| .gitlab-ci.yml | `glab ci lint` | — | Pipeline editor |

```yaml
lint:
  stage: lint
  image: python:3.12-slim
  before_script: ["pip install -q ruff black"]
  script:
    - ruff check app/
    - black --check app/
  rules:
    - if: $CI_PIPELINE_SOURCE == "merge_request_event"
    - if: $CI_COMMIT_BRANCH == $CI_DEFAULT_BRANCH
```

> ⭐ Правильное место линтера — **pre-commit hook у разработчика** + проверка в CI.
> Hook даёт мгновенную обратную связь, CI гарантирует, что его не обошли.

```yaml
# .pre-commit-config.yaml
repos:
  - repo: https://github.com/astral-sh/ruff-pre-commit
    rev: v0.6.9
    hooks: [{id: ruff}, {id: ruff-format}]
  - repo: https://github.com/gitleaks/gitleaks
    rev: v8.21.0
    hooks: [{id: gitleaks}]
```

## 3. Тесты и quality gates

```yaml
unit:
  stage: test
  script:
    - pytest -q --junitxml=report.xml --cov=app --cov-report=xml --cov-report=term
    - coverage report --fail-under=70          # ⭐ gate по покрытию
  coverage: '/TOTAL.+?(\d+\.\d+\%)/'
  artifacts:
    when: always
    expire_in: 1 week
    reports:
      junit: report.xml
      coverage_report:
        coverage_format: cobertura
        path: coverage.xml
```

**Типовые gates и разумные пороги:**

| Gate | Порог | Комментарий |
|------|-------|-------------|
| Линтер | 0 ошибок | Не обсуждается |
| Покрытие | ≥ 60-80%, **без падения** относительно main | Гнаться за 100% вредно |
| Уязвимости образа | 0 Critical | High — предупреждение |
| Секреты в диффе | 0 | Блокирующий |
| Размер образа | Лимит по проекту | Ловит «забыли multi-stage» |
| Время пайплайна | ≤ 10-20 мин | Тоже метрика качества |

**Про флакающие тесты:** не `retry`, а карантин + тикет + срок. Тест, который «иногда
красный», разрушает доверие ко всему пайплайну (тема 01).

## 4. Безопасность: какие сканы бывают

| Тип | Что проверяет | Инструменты |
|-----|---------------|-------------|
| **SAST** | Исходный код на уязвимые паттерны | Semgrep, Bandit (Python), gosec, GitLab SAST |
| **SCA** | Зависимости на известные CVE | Trivy fs, `pip-audit`, `npm audit`, Dependabot/Renovate |
| **Container scanning** | Слои образа и пакеты ОС | Trivy, Grype, GitLab Container Scanning |
| **Secret detection** | Секреты в коде и истории | Gitleaks, TruffleHog, GitLab Secret Detection |
| **IaC scanning** | Ошибки конфигурации | tfsec, Checkov, kube-linter |
| **DAST** | Работающее приложение снаружи | OWASP ZAP, GitLab DAST |
| **Licenses** | Лицензионная чистота зависимостей | Trivy, license-checker |

```yaml
# универсальный Trivy: и файловая система, и образ
scan:deps:
  stage: scan
  image: {name: aquasec/trivy:0.74.0, entrypoint: [""]}
  script:
    - trivy fs --scanners vuln,secret --severity HIGH,CRITICAL --exit-code 0 .
    - trivy fs --scanners vuln --severity CRITICAL --exit-code 1 .
  cache: {paths: [.trivycache/]}

scan:image:
  stage: scan
  needs: [build]
  image: {name: aquasec/trivy:0.74.0, entrypoint: [""]}
  script:
    - trivy image --severity CRITICAL --exit-code 1 "$CI_REGISTRY_IMAGE:$CI_COMMIT_SHORT_SHA"

secrets:
  stage: lint
  image: {name: zricethezav/gitleaks:v8.30.1, entrypoint: [""]}
  script:
    - gitleaks git --redact --exit-code 1 .
```

> ⚠️ **Сканеры тоже пиннятся на версию, а не на `latest`.** 19 марта 2026 через украденные
> токены опубликовали заражённый Trivy 0.69.4 и перевесили теги `trivy-action`. Все, кто тянул
> `latest` или action по тегу, отдали атакующим секреты CI. В проде пинят по digest
> (`aquasec/trivy:0.74.0@sha256:…`), actions — по полному SHA коммита.
>
> `gitleaks git` проверяет историю коммитов, `gitleaks dir` — файлы в каталоге. Старый
> `gitleaks detect --source .` ещё работает, но с v8.19 помечен устаревшим.

В GitLab многие сканы доступны готовыми шаблонами:
```yaml
include:
  - template: Jobs/SAST.gitlab-ci.yml
  - template: Jobs/Secret-Detection.gitlab-ci.yml
  - template: Jobs/Dependency-Scanning.gitlab-ci.yml
  - template: Jobs/Container-Scanning.gitlab-ci.yml
```

> Блокируем только то, что действительно критично (обычно Critical + утёкшие секреты).
> Если пайплайн краснеет от 300 «HIGH» в базовом образе, команда научится игнорировать
> красный цвет — и это хуже, чем отсутствие скана.

## 5. Секреты: полный чек-лист

### Где хранить
```text:no-line-numbers
❌ в репозитории (даже в приватном)       ❌ в логах и артефактах
❌ base64 в манифесте                     ❌ в имени образа/параметрах команды
✅ CI/CD Variables (masked + protected)   ✅ Vault / внешний секрет-менеджер
✅ тип File для ключей и kubeconfig       ✅ OIDC/короткоживущие токены
```

### Правила работы
1. **Маскирование ≠ защита.** Прячет точное совпадение; `base64`, склейка, вывод по частям
   обходят его.
2. Не печатать: никакого `env`, `printenv`, `set -x` рядом с подстановкой,
   `docker login -p`, `curl -u user:pass` (используй `--password-stdin`, заголовки из файла).
3. Ограничивать область: protected-переменные и protected environments (GitLab),
   credentials на уровне папки (Jenkins).
4. **Ротация**: секрет, попавший в лог, считается скомпрометированным навсегда — меняем.
5. Короткоживущее лучше долгоживущего: `$CI_JOB_TOKEN`, OIDC-федерация с облаком
   (пайплайн получает временные креды вместо вечного ключа).
6. Разделять по окружениям: прод-секреты не должны быть доступны dev-пайплайнам.

### Что делать при утечке (порядок)
```text:no-line-numbers
1. Немедленно отозвать/сменить секрет (считаем скомпрометированным)
2. Удалить лог джобы/артефакты; при утечке в git — переписать историю и форс-пуш
3. Проверить, где ещё использовался; проверить логи доступа на предмет использования
4. Найти причину в конфиге (echo, set -x, дамп env) и исправить
5. Добавить автоматическую проверку (gitleaks) в pre-commit и в пайплайн
```

## 6. Supply chain: доверие к тому, что собираем

| Практика | Зачем |
|----------|-------|
| Пин версий базовых образов (по тегу, лучше по digest) | Воспроизводимость, защита от подмены |
| Lock-файлы зависимостей (`poetry.lock`, `package-lock.json`) | Детерминированная сборка |
| Renovate/Dependabot | Регулярные контролируемые обновления |
| SBOM (`trivy sbom`, syft) | Знать, из чего состоит артефакт |
| Подпись образов (cosign) + проверка при деплое | Гарантия, что в проде наш артефакт |
| Минимальные базовые образы (alpine/distroless) | Меньше поверхность атаки и CVE |
| Non-root в контейнере | Ограничение последствий компрометации |
| Защита раннеров (тема 09) | Раннер — точка доступа к инфраструктуре |

```bash
# подпись и проверка (cosign)
cosign sign --key cosign.key registry.example.com/app:$SHA
cosign verify --key cosign.pub registry.example.com/app:$SHA
```

## 7. Стадия проверок целиком (пример)

```yaml
stages: [lint, test, build, scan, deploy]

lint:
  stage: lint
  image: python:3.12-slim
  before_script: ["pip install -q ruff black"]
  script: ["ruff check app/", "black --check app/"]
  needs: []                      # стартует сразу

secrets:
  stage: lint
  image: {name: zricethezav/gitleaks:v8.30.1, entrypoint: [""]}
  script: ["gitleaks git --redact --exit-code 1 ."]
  needs: []

dockerfile:
  stage: lint
  image: {name: hadolint/hadolint:latest-debian, entrypoint: [""]}
  script: ["hadolint Dockerfile"]
  needs: []
  allow_failure: true            # начинаем мягко, потом ужесточаем

unit:
  stage: test
  image: python:3.12-slim
  script:
    - pip install -q -r requirements.txt -r requirements-dev.txt
    - pytest -q --junitxml=report.xml --cov=app --cov-report=xml
    - coverage report --fail-under=70
  artifacts:
    when: always
    reports:
      junit: report.xml
      coverage_report: {coverage_format: cobertura, path: coverage.xml}

scan:image:
  stage: scan
  needs: [build]
  image: {name: aquasec/trivy:0.74.0, entrypoint: [""]}
  script:
    - trivy image --severity HIGH --exit-code 0 "$CI_REGISTRY_IMAGE:$CI_COMMIT_SHORT_SHA"
    - trivy image --severity CRITICAL --exit-code 1 "$CI_REGISTRY_IMAGE:$CI_COMMIT_SHORT_SHA"
```

## 8. Как внедрять проверки, чтобы их не отключили

```text:no-line-numbers
1. Сначала ИНФОРМИРОВАНИЕ: allow_failure: true, отчёт в MR, никто не блокируется
2. Через 2-4 недели — почистили накопленное, договорились о порогах
3. Потом БЛОКИРОВКА: allow_failure убираем, gate становится обязательным
4. Пороги повышаем постепенно (покрытие +5% за квартал), а не «с понедельника 90%»
5. Для легаси — baseline: ловим ТОЛЬКО новые проблемы, старые в техдолге
```
Внедрение блокирующего gate «сразу и на всё» почти всегда заканчивается тем,
что команда находит способ его обойти.

## 💼 Как это в DevOps

- Вопрос «как не пустить уязвимость в прод» на собесе — это про связку
  скан образа + gate по Critical + запрет деплоя без прохождения стадии.
- Реальная работа: договориться о порогах с разработчиками, разобрать ложные
  срабатывания, настроить исключения (`.trivyignore`, baseline) и не сломать поток.
- Утечка секрета — инцидент, а не «ой»: ротация, разбор, автоматическая проверка.
- Обновление зависимостей автоматом (Renovate) экономит больше, чем кажется:
  большинство критичных CVE закрываются простым апдейтом.

## 🧠 Что запомнить

1. Порядок проверок — от дешёвых к дорогим; линтер и детект секретов — в самом начале.
2. Линтер в CI + pre-commit у разработчика: мгновенная обратная связь и гарантия.
3. Quality gate без блокировки — не gate; но внедрять надо поэтапно.
4. Покрытие: важнее «не падает относительно main», чем абсолютная цифра.
5. Флакающие тесты лечатся карантином и починкой, а не `retry`.
6. Виды сканов: SAST (код), SCA (зависимости), container scanning (образ),
   secret detection, IaC, DAST.
7. Блокируй по Critical и утёкшим секретам; остальное — предупреждение, иначе шум.
8. Маскирование секретов — страховка от случайности, а не защита.
9. Любой секрет, попавший в лог или git, считается скомпрометированным → ротация.
10. Protected variables/environments и креды на уровне папки ограничивают радиус поражения.
11. Supply chain: пин базовых образов, lock-файлы, SBOM, подпись образов, non-root.
12. Внедряй проверки постепенно и с baseline для легаси — иначе их обойдут.

### Блок A. Теория

**A1.** В каком порядке ставить проверки в пайплайне и почему?

<details><summary>Ответ</summary>

От дешёвых и быстрых к дорогим и медленным: линтер и детект секретов → unit-тесты →
сборка → сканы образа → интеграционные → деплой → smoke. Так обратная связь приходит
раньше, а дорогие ресурсы не тратятся на заведомо плохой код.

</details>

**A2.** Зачем нужен линтер в CI, если он есть в pre-commit hook у разработчика?

<details><summary>Ответ</summary>

Hook можно обойти (`--no-verify`), он не установлен у всех и не гарантирует
одинаковую версию правил. CI — это гарантия: код, не прошедший проверку, не попадёт в main.
Hook нужен для скорости, CI — для надёжности.

</details>

**A3.** Что такое quality gate? Приведи пять примеров с порогами.

<details><summary>Ответ</summary>

Автоматический порог, блокирующий продвижение. Примеры: 0 ошибок линтера;
покрытие ≥ 70% и не ниже, чем в main; 0 Critical CVE в образе; 0 найденных секретов;
размер образа ≤ 300 МБ; отсутствие падений в smoke после деплоя.

</details>

**A4.** Почему гнаться за 100% покрытием вредно? Какой критерий лучше абсолютной цифры?

<details><summary>Ответ</summary>

Погоня за 100% приводит к бессмысленным тестам на геттеры и хрупким тестам,
проверяющим реализацию, а не поведение. Лучший критерий — **не снижать** покрытие
относительно основной ветки и покрывать критичные пути, а не всё подряд.

</details>

**A5.** Что делать с флакающими тестами и почему `retry` — плохое решение?

<details><summary>Ответ</summary>

Выносить в карантин (отдельный набор, не блокирующий), заводить тикет со сроком
и чинить причину (гонки, таймауты, зависимость от внешних сервисов, общее состояние).
`retry` прячет проблему, удлиняет пайплайн и в какой-то момент скроет настоящий баг.

</details>

**A6.** Объясни разницу SAST, SCA, DAST, container scanning, secret detection.

<details><summary>Ответ</summary>

SAST — статический анализ исходного кода на уязвимые паттерны; SCA — анализ
зависимостей на известные CVE; container scanning — проверка слоёв и пакетов собранного
образа; DAST — динамическое тестирование работающего приложения снаружи;
secret detection — поиск секретов в коде и истории git.

</details>

**A7.** По какому уровню серьёзности стоит блокировать пайплайн и почему не по всем?

<details><summary>Ответ</summary>

Блокировать по Critical (и по найденным секретам): это то, что действительно
нельзя пускать дальше. Если блокировать по всем уровням, пайплайн будет красным
постоянно из-за неустранимых уязвимостей базовых образов, и команда начнёт игнорировать
красный статус — теряется смысл любой блокировки.

</details>

**A8.** Почему маскирование переменных не защищает от утечки?

<details><summary>Ответ</summary>

Оно скрывает только точное совпадение строки в выводе. Любое преобразование
(base64, шифрование, вывод по символам, запись в файл и его публикация артефактом)
обходит маскирование. Это защита от случайного `echo`, а не от намеренной или косвенной утечки.

</details>

**A9.** Перечисли шесть правил работы с секретами в CI/CD.

<details><summary>Ответ</summary>

Хранить в секрет-хранилище (CI/CD Variables masked+protected, Vault); не печатать
и не логировать; использовать тип File для ключей и конфигов; ограничивать область
(protected ветки/окружения, папки); предпочитать короткоживущие токены (OIDC, job token);
регулярно ротировать и разделять по окружениям.

</details>

**A10.** Что делать, если секрет попал в лог джобы? Пять шагов по порядку.

<details><summary>Ответ</summary>

(1) Отозвать/сменить секрет; (2) удалить лог и артефакты (при попадании в git —
переписать историю); (3) проверить, где ещё использовался, и просмотреть журналы
использования; (4) исправить причину в конфиге пайплайна; (5) добавить автоматическую
проверку (gitleaks) в pre-commit и CI, чтобы это не повторилось.

</details>

**A11.** Что такое supply chain security? Назови шесть практик.

<details><summary>Ответ</summary>

Защита цепочки поставки ПО: всё, из чего собирается артефакт, и путь артефакта
до прода. Практики: пин базовых образов (digest), lock-файлы, автоматические
контролируемые обновления, SBOM, подпись артефактов и проверка при деплое,
минимальные образы, non-root, защита раннеров и registry.

</details>

**A12.** Зачем пинить базовый образ по digest, а не по тегу?

<details><summary>Ответ</summary>

Тег — плавающая ссылка: под `python:3.12-slim` со временем оказывается другой
образ, и сборка перестаёт быть воспроизводимой; digest фиксирует конкретное содержимое
и защищает от подмены содержимого тега.

</details>

**A13.** Что такое SBOM и зачем он нужен?

<details><summary>Ответ</summary>

Software Bill of Materials — машиночитаемый перечень компонентов артефакта
(библиотеки, версии, лицензии). Нужен, чтобы за минуты ответить «затронуты ли мы
новой CVE» и для лицензионного контроля.

</details>

**A14.** Зачем подписывать образы и как проверка подписи встраивается в деплой?

<details><summary>Ответ</summary>

Подпись (cosign) доказывает, что образ собран вашим пайплайном и не подменён.
При деплое проверяется подпись (`cosign verify`) или политикой в кластере
(admission controller) — неподписанный образ не запускается.

</details>

**A15.** Как правильно внедрять новую блокирующую проверку в команде?

<details><summary>Ответ</summary>

Поэтапно: сначала информирование (`allow_failure: true`, отчёты в MR),
затем чистка накопленного и согласование порогов, потом блокировка; пороги повышать
постепенно; для легаси — baseline, ловящий только новые проблемы; обязательно объяснить
команде, зачем это и как чинить типичные находки.

</details>

**A16.** Что такое baseline для легаси-проекта и зачем он нужен?

<details><summary>Ответ</summary>

Зафиксированный список уже существующих проблем, который проверка игнорирует:
блокируются только **новые** нарушения. Позволяет включить gate сегодня, а не после
месяцев рефакторинга.

</details>

**A17.** Почему сканирование образа ставят после сборки, а сканирование зависимостей
можно раньше?

<details><summary>Ответ</summary>

Образ существует только после сборки — сканировать раньше нечего; а зависимости
описаны в манифестах (`requirements.txt`, `package-lock.json`) и могут проверяться
на исходниках до сборки, давая более раннюю обратную связь.

</details>

### Блок B. «Что не так»

```yaml
# B1
test:
  script:
    - pytest --cov=app || true
```

<details><summary>Ответ</summary>

`|| true` делает тесты декоративными: джоба зелёная при любых падениях,
покрытие не проверяется. Нужно убрать подавление и добавить порог покрытия.

</details>

```yaml
# B2
scan:
  script:
    - trivy image --exit-code 1 --severity LOW,MEDIUM,HIGH,CRITICAL "$IMAGE"
```

<details><summary>Ответ</summary>

Блокировка по всем уровням, включая LOW/MEDIUM — пайплайн будет красным
практически всегда из-за уязвимостей базовых образов, которые нечем закрыть.
Блокировать стоит по Critical, HIGH — предупреждением.

</details>

```yaml
# B3
deploy:
  script:
    - echo "$KUBECONFIG_CONTENT" > kubeconfig
    - cat kubeconfig
    - kubectl --kubeconfig kubeconfig apply -f k8s/
```

<details><summary>Ответ</summary>

`cat kubeconfig` печатает секрет в лог. Плюс файл остаётся в workspace/артефактах.
Нужно использовать переменную типа File, не печатать содержимое, и подчищать за собой.

</details>

```yaml
# B4
variables:
  DB_PASSWORD: "prod_password_123"
```

<details><summary>Ответ</summary>

Пароль прода в открытом виде в конфиге, который лежит в git. Утечка для всех,
у кого есть доступ к репозиторию, и навсегда в истории. Только CI/CD Variables/Vault.

</details>

```yaml
# B5
build:
  script:
    - docker build -t app .
  # Dockerfile: FROM python:latest
```

<details><summary>Ответ</summary>

`FROM python:latest` — невоспроизводимая сборка: сегодня одна версия, завтра другая;
ломает кэш и делает отладку невозможной. Плюс образ без тега версии тяжелее и содержит
больше CVE. Нужен конкретный тег (лучше digest) и slim/distroless.

</details>

```yaml
# B6
lint:
  script: ["ruff check app/"]
  allow_failure: true
# так уже полгода
```

<details><summary>Ответ</summary>

`allow_failure: true` «временно» на полгода — gate, который ничего не гарантирует.
Нужно либо починить накопленное и сделать блокирующим, либо честно убрать проверку:
вечно жёлтые джобы приучают игнорировать статусы.

</details>

### Блок C. Практика

#### C1. 🔑 Стадия проверок качества (задание из практики роадмапа)

Добавь в пайплайн:
1. `lint` — линтер языка приложения (flake8/ruff/eslint/golangci-lint) с `needs: []`;
2. `format` — проверка форматирования (black --check / prettier --check);
3. `dockerfile` — hadolint (сначала `allow_failure: true`);
4. `secrets` — gitleaks, блокирующий;
5. `unit` — тесты с `junit`-отчётом и порогом покрытия.
Убедись, что отчёты видны во вкладке MR.

<details><summary>Ответ</summary>

Критерий: отчёты (тесты, покрытие) видны в MR; проверки с `needs: []` стартуют
сразу; секреты и линтер блокируют; hadolint пока предупреждает.

</details>

#### C2. Сломай и почини

Намеренно внеси: ошибку стиля, падающий тест, секрет в коде (`AWS_SECRET_ACCESS_KEY=...`
тестовый), уязвимую зависимость. Убедись, что **каждая** проверка поймала своё,
и зафиксируй, как выглядит сообщение.

<details><summary>Ответ</summary>

Ожидаемо: ruff/eslint укажет файл и правило; pytest покажет упавший тест
в отчёте; gitleaks найдёт совпадение по правилу и не покажет само значение (`--redact`);
trivy выдаст CVE с уровнем и версией пакета, в которой оно исправлено.

</details>

#### C3. Пороги покрытия

Настрой `--fail-under` и найди текущее покрытие. Поставь порог на 5% ниже текущего
и объясни, почему так лучше, чем ставить круглое число.

<details><summary>Ответ</summary>

Порог чуть ниже текущего значения фиксирует «не хуже, чем сейчас» и не ломает
работу команды. Круглое число, взятое с потолка, либо ничего не блокирует, либо блокирует
всё и будет отключено.

</details>

#### C4. Сканирование

1. Добавь `trivy fs` для зависимостей и `trivy image` для образа.
2. Сделай так, чтобы HIGH предупреждал, а CRITICAL блокировал.
3. Найди реальную уязвимость (возьми старый базовый образ) и убедись, что пайплайн краснеет.
4. Обнови базовый образ и покажи, что уязвимость ушла.
5. Добавь `.trivyignore` для одного осознанно принятого CVE с комментарием.

<details><summary>Ответ</summary>

Критерий: старый базовый образ даёт красную джобу; после обновления — зелёную;
в `.trivyignore` каждое исключение сопровождается комментарием с причиной и сроком
пересмотра.

</details>

#### C5. pre-commit

Настрой `.pre-commit-config.yaml` с ruff/eslint + gitleaks. Проверь, что коммит
с проблемой не проходит локально. Сравни скорость обратной связи с CI.

<details><summary>Ответ</summary>

Обратная связь от hook — секунды против минут в CI. Вывод: hook для скорости,
CI для гарантии.

</details>

#### C6. Секреты

1. Проверь свой репозиторий историей: `gitleaks git --log-opts="--all" .`.
2. Переведи все секреты в CI/CD Variables (masked + protected).
3. Сделай ключ SSH переменной типа File.
4. Напиши в конспект процедуру действий при утечке — по шагам, с командами.

<details><summary>Ответ</summary>

Критерий: `gitleaks` по всей истории не находит секретов; переменные переведены
в CI/CD Variables; процедура на случай утечки записана и содержит конкретные команды.

</details>

#### C7. Supply chain

1. Запинь базовый образ по digest (`FROM python:3.12-slim@sha256:...`).
2. Сгенерируй SBOM (`trivy sbom --format cyclonedx`) и сохрани артефактом.
3. (со звёздочкой) Подпиши образ cosign и проверь подпись в отдельной джобе.

<details><summary>Ответ</summary>

SBOM сохраняется артефактом и позволяет ответить на вопрос «есть ли у нас
уязвимая библиотека» без пересборки; подпись проверяется отдельной джобой перед деплоем.

</details>

#### C8. Обновления зависимостей

Настрой Renovate (или Dependabot) для своего репозитория — хотя бы конфиг.
Опиши, как выглядит процесс приёмки таких MR и кто их ревьюит.

<details><summary>Ответ</summary>

Ключевое в ответе: обновления приходят регулярными маленькими MR, их ревьюит
владелец сервиса, для патч-версий возможен автомерж при зелёном пайплайне.

</details>

#### C9. План внедрения

Напиши план внедрения блокирующего SAST в команде из 8 разработчиков:
этапы, сроки, пороги, что делать с накопленными проблемами, как сообщить.

<details><summary>Ответ</summary>

Ориентир плана: неделя 1-2 — включить в режиме отчёта; неделя 3 — разобрать
находки, согласовать baseline и пороги; неделя 4 — сделать блокирующим для новых
проблем; далее — квартальное ужесточение. Плюс короткая инструкция «как чинить типичные
находки» и канал для вопросов.

</details>

### Блок D. Инциденты

**D1.** После добавления скана пайплайн краснеет на 250 уязвимостях базового образа.
Команда просит отключить скан. Что делать?

<details><summary>Ответ</summary>

Не отключать, а настроить: блокировать только Critical, остальное — отчётом;
обновить базовый образ на свежий slim/distroless (обычно это убирает большую часть);
добавить исключения с обоснованием и сроком; включить регулярное обновление зависимостей.
Ключевая мысль: полезен тот сигнал, на который реагируют.

</details>

**D2.** Разработчик закоммитил приватный ключ. Коммит уже в main. Полный порядок действий.

<details><summary>Ответ</summary>

Считать ключ скомпрометированным: отозвать и перевыпустить; удалить из истории
(`git filter-repo`/BFG) и форс-пушить с уведомлением команды; проверить, где ключ
использовался, и просмотреть журналы доступа; заменить на секрет в хранилище;
включить gitleaks в pre-commit и CI; при необходимости — уведомить безопасность.

</details>

**D3.** Покрытие «упало» с 78% до 41% после мержа, хотя тестов не удаляли. Причины?

<details><summary>Ответ</summary>

Влит код без тестов (знаменатель вырос), изменилась конфигурация покрытия
(другие пути/исключения), тесты не запустились целиком (упали на импорте), отчёт
собирается не со всех джоб (частичное покрытие при параллельных тестах и отсутствии
объединения отчётов).

</details>

**D4.** Gate по покрытию блокирует хотфикс на проде. Что делать сейчас
и как настроить процесс, чтобы это не повторялось?

<details><summary>Ответ</summary>

Сейчас — воспользоваться заранее предусмотренным исключением для хотфиксов
(отдельный пайплайн с сокращённым набором gate'ов и обязательным последующим тикетом).
На будущее — явная политика: какие проверки обязательны даже для хотфикса (секреты,
Critical CVE, smoke), а какие можно отложить.

</details>

**D5.** В логе джобы деплоя видно содержимое kubeconfig. Как это произошло и что делать?

<details><summary>Ответ</summary>

Скорее всего `cat`, `set -x` или вывод конфигурации при отладке. Действия:
ротация кластерных кредов (kubeconfig = доступ к кластеру), удаление лога, исправление
джобы (тип File, без печати), проверка журналов kube-API на подозрительные действия.

</details>

**D6.** Trivy начал падать на джобе, которая месяц была зелёной, хотя код не менялся.
Почему?

<details><summary>Ответ</summary>

База уязвимостей обновилась: в старых пакетах нашли новую CVE. Это нормальное
поведение сканеров и повод обновить базовый образ/зависимости, а не отключать скан.

</details>

**D7.** В команде решили «не блокировать, чтобы не мешать» — теперь 40 открытых
уязвимостей и никто не смотрит отчёты. Как исправить ситуацию?

<details><summary>Ответ</summary>

Ввести владельца и SLA на устранение по уровням, включить блокировку хотя бы
по Critical и по новым проблемам (baseline), добавить видимость (дашборд, регулярный
обзор), автоматизировать обновления зависимостей.

</details>

**D8.** Образ прошёл скан на сборке, а через месяц в нём нашли критическую уязвимость,
и он всё ещё в проде. Что должно быть в процессе?

<details><summary>Ответ</summary>

Периодический пересканер уже опубликованных/задеплоенных образов (по расписанию),
инвентаризация «что сейчас в проде» (окружения + SBOM), процесс реагирования:
пересборка на свежем базовом образе и выкат, а также автоматические обновления.

</details>

**D9.** SAST выдаёт много ложных срабатываний, разработчики теряют доверие.
Что сделать (три действия)?

<details><summary>Ответ</summary>

Настроить правила под стек (отключить нерелевантные), ввести baseline
для легаси, разбирать находки вместе с разработчиками и документировать принятые
исключения; блокировать только подтверждённые классы проблем.

</details>

**D10.** `pip install` в пайплайне подтянул вредоносный пакет с похожим именем.
Какие практики предотвращают такое?

<details><summary>Ответ</summary>

Пин версий и lock-файлы с хэшами, внутренний прокси-репозиторий пакетов
вместо прямого выхода в публичный, проверка зависимостей (SCA), запрет на установку
из произвольных источников, ревью новых зависимостей, SBOM для отслеживания.

</details>

### Блок E. Вопросы с собеседования

**1.** Какие проверки должны быть в пайплайне и в каком порядке?

<details><summary>Ответ</summary>

lint/format/secret-detection → unit + покрытие → build → сканы образа/зависимостей →
интеграционные → deploy → smoke; порядок по стоимости и зависимости от артефакта.

</details>

**2.** Что такое quality gate и какие пороги ты бы поставил?

<details><summary>Ответ</summary>

Автоматический порог, блокирующий продвижение: 0 ошибок линтера, покрытие не ниже
базового, 0 Critical CVE, 0 секретов, зелёный smoke.

</details>

**3.** Чем отличаются SAST, SCA и DAST?

<details><summary>Ответ</summary>

SAST — статический анализ кода; SCA — зависимости и их CVE; DAST — проверка
работающего приложения снаружи.

</details>

**4.** Как не пустить уязвимый образ в прод?

<details><summary>Ответ</summary>

Скан образа после сборки с блокировкой по Critical, деплой только из пайплайна
и только образов, прошедших скан; плюс периодический пересканер и обновления.

</details>

**5.** Где хранить секреты и как защитить их от утечки в логи?

<details><summary>Ответ</summary>

В CI/CD Variables (masked + protected) или Vault; тип File для ключей; не печатать,
не использовать `-p`/`set -x`, ограничивать область и предпочитать короткоживущие токены.

</details>

**6.** Что делать, если секрет утёк?

<details><summary>Ответ</summary>

Ротация, удаление логов/истории, аудит использования, исправление причины,
автоматическая проверка на будущее.

</details>

**7.** Что такое supply chain security?

<details><summary>Ответ</summary>

Защита цепочки поставки: пин базовых образов, lock-файлы, SBOM, подписи, минимальные
образы, контроль registry и раннеров, регулярные обновления.

</details>

**8.** Как внедрять новые проверки, чтобы команда не саботировала?

<details><summary>Ответ</summary>

Поэтапно: сначала отчёт, потом baseline и договорённость о порогах, затем блокировка;
с объяснением, инструкцией по исправлению и постепенным ужесточением.

</details>

**9.** Что делать с флакающими тестами?

<details><summary>Ответ</summary>

Карантин + тикет + починка причины; `retry` не использовать как решение.

</details>

**10.** Как обеспечить, чтобы в проде был именно наш артефакт?

<details><summary>Ответ</summary>

Иммутабельные теги по SHA, подпись образов и проверка при деплое, деплой только
из пайплайна, фиксация версии в окружении и эндпоинт `/version`.

</details>
