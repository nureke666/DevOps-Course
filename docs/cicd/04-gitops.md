# 04. GitOps

> Роадмап → 4. CI/CD → Теория → Методология: «Что такое GitOps?»
> (в блоке роадмапа отдельное видео «GITOPS ЗА 18 МИНУТ»)
> **После темы ты умеешь:** объяснить GitOps как модель доставки, отличить pull от push,
> назвать инструменты (Argo CD, Flux) и понять, что делать с секретами в git.

---

## 1. Определение

**GitOps** — способ управления инфраструктурой и приложениями, где:

1. **Git — единственный источник правды** о желаемом состоянии системы;
2. желаемое состояние описано **декларативно** (манифесты k8s, Helm-чарты, kustomize);
3. **агент внутри кластера** постоянно сравнивает фактическое состояние с описанным
   в git и **приводит фактическое к желаемому** (reconciliation loop);
4. любое изменение проходит через git (commit → MR → merge), а значит есть ревью,
   история, аудит и откат через `git revert`.

Короткая формулировка для собеса:
> «GitOps — это декларативное описание системы в git плюс агент, который непрерывно
> сверяет кластер с этим описанием и сам устраняет расхождения. Деплой = мерж в git,
> откат = revert коммита».

## 2. Push vs Pull — главное отличие

```text:no-line-numbers
        PUSH (классический CD)                      PULL (GitOps)
 ┌──────────────┐                          ┌──────────────┐
 │  CI-система  │                          │  CI-система  │  собирает образ,
 │ (GitLab CI)  │                          │ (GitLab CI)  │  пушит в registry,
 └──────┬───────┘                          └──────┬───────┘  коммитит новый тег
        │ kubectl apply / helm upgrade            │          в config-репозиторий
        │ (у CI есть креды кластера!)             ▼
        ▼                                  ┌──────────────┐
 ┌──────────────┐                          │ config-repo  │ ← желаемое состояние
 │  Кластер     │                          └──────┬───────┘
 └──────────────┘                                 │ агент САМ забирает (pull)
                                                  ▼
                                          ┌────────────────────────┐
                                          │ Кластер + Argo CD/Flux │
                                          │  сверяет и применяет   │
                                          └────────────────────────┘
```

| | Push | Pull (GitOps) |
|---|---|---|
| Кто применяет изменения | CI-система снаружи | Агент внутри кластера |
| Где лежат креды кластера | В CI (секрет наружу) | Нигде снаружи — агент уже внутри |
| Доступ к кластеру извне | Нужен | Не нужен (важно для закрытых контуров) |
| Дрейф конфигурации | Не замечается | Обнаруживается и чинится автоматически |
| Что в git | Код | Код **и** желаемое состояние окружений |
| Откат | Отдельная процедура | `git revert` |
| Инструменты | GitLab CI, Jenkins, Helm, Ansible | Argo CD, Flux |

## 3. Два репозитория

```text:no-line-numbers
 app-repo (код)                        config-repo (состояние окружений)
 ├── src/                              ├── apps/
 ├── Dockerfile                        │   ├── dev/values.yaml       image.tag: 8f3a91c
 ├── .gitlab-ci.yml  ──► build&push ──►│   ├── staging/values.yaml   image.tag: 7c2b40d
 └── tests/              обновляет тег │   └── prod/values.yaml      image.tag: 1a9ff03
                                       └── infra/ (ingress, secrets refs, policies)
```

**Почему разделяют:**
- изменение конфигурации не запускает пересборку приложения;
- права: кто может менять прод-конфиг ≠ кто может менять код;
- в config-repo видно **историю состояний окружений** («что было в проде 3 недели назад»);
- один config-repo может описывать много сервисов.

**Как обновляется тег:** джоба CI после успешной сборки коммитит новый `image.tag`
в config-repo (через MR или напрямую в ветку окружения), либо это делает
**Image Updater** (Argo CD Image Updater / Flux Image Automation), который сам следит
за появлением новых тегов в registry по заданному правилу.

## 4. Reconciliation loop и дрейф

```text:no-line-numbers
        ┌──────────────► сравнить желаемое (git) и фактическое (кластер)
        │                          │
        │                  расхождение?
        │                    ╱          ╲
        │                 нет            да
        │                  │              │
        └────────ждать ────┘        применить git-состояние
                                   (self-heal) + пометить OutOfSync
```

**Дрейф (drift)** — расхождение между git и реальностью. Возникает, когда кто-то
делает `kubectl edit` руками, когда контроллер меняет объект, когда ресурс удалили.
GitOps-агент это видит (статус `OutOfSync`) и, если включён self-heal, возвращает как в git.

Практический эффект: «правка руками на проде» перестаёт работать — через минуту её
откатит агент. Это и есть цель: единственный способ изменить систему — коммит.

## 5. Инструменты

### Argo CD
Kubernetes-контроллер + веб-UI. Главная сущность — `Application`:

```yaml
apiVersion: argoproj.io/v1alpha1
kind: Application
metadata:
  name: myapp-prod
  namespace: argocd
spec:
  project: default
  source:
    repoURL: https://gitlab.com/org/config-repo.git
    targetRevision: main
    path: apps/prod
    helm:
      valueFiles: [values.yaml]
  destination:
    server: https://kubernetes.default.svc
    namespace: myapp-prod
  syncPolicy:
    automated:
      prune: true        # удалять то, чего больше нет в git
      selfHeal: true     # возвращать ручные правки
    syncOptions:
      - CreateNamespace=true
```

Плюсы: наглядный UI (дерево ресурсов, diff, статус Synced/Healthy), удобные ручные sync
и rollback, ApplicationSet для генерации приложений по шаблону, SSO/RBAC.

### Flux CD
Набор контроллеров (source, kustomize, helm, image-automation), без «тяжёлого» UI —
всё через CRD и git. Хорошо ложится на полностью автоматизированные сценарии
и на управление самим собой («Flux bootstrap»).

| | Argo CD | Flux |
|---|---|---|
| UI | Богатый веб-интерфейс | Минимальный (есть сторонние) |
| Модель | `Application` CRD | Набор CRD (GitRepository, Kustomization, HelmRelease) |
| Мульти-кластер | Из коробки (один Argo → много кластеров) | Обычно агент в каждом кластере |
| Автообновление образов | Image Updater (отдельный компонент) | Image automation в составе |
| Кому заходит | Командам, которым нужен обзор и кнопки | Командам, которым нужен «чистый git-flow» |

## 6. Секреты в GitOps

Главный вопрос темы: **в git нельзя класть секреты, но желаемое состояние — в git.**
Четыре рабочих подхода:

| Подход | Как работает | Нюанс |
|--------|--------------|-------|
| **External Secrets Operator** | В git — ссылка (`ExternalSecret`), значения тянутся из Vault/AWS SM/GCP SM | Дефолт для зрелых команд |
| **Sealed Secrets** | Секрет шифруется публичным ключом кластера, в git лежит зашифрованный | Расшифровать может только этот кластер |
| **SOPS (+ age/KMS)** | Файл секретов зашифрован, ключи — в KMS/age; Flux умеет расшифровывать | Удобно для мультиоблака |
| **Vault Agent / CSI** | Секрет монтируется в под из Vault на лету | В git вообще нет секрета |

Что **нельзя**: base64 в манифесте `Secret` в git. Base64 — это кодирование, а не шифрование.

## 7. Как GitOps сочетается с GitLab CI

GitOps **не заменяет** CI — он заменяет часть CD.

```text:no-line-numbers
GitLab CI отвечает за:              Argo CD / Flux отвечает за:
 • lint, тесты                       • сверку кластера с git
 • сборку образа                     • применение манифестов
 • сканы                             • self-heal и prune
 • публикацию в registry             • статус синхронизации и health
 • обновление тега в config-repo     • rollback на предыдущий коммит
```

Джоба, которая двигает тег (упрощённо):

```yaml
bump:prod:
  stage: deploy
  image: alpine:3.20
  variables:
    GIT_STRATEGY: none
  script:
    - apk add --no-cache git yq
    - git clone https://oauth2:$CONFIG_REPO_TOKEN@gitlab.com/org/config-repo.git
    - cd config-repo
    - yq -i ".image.tag = \"$CI_COMMIT_SHORT_SHA\"" apps/prod/values.yaml
    - git config user.email "ci@example.com" && git config user.name "CI"
    - git commit -am "chore(prod): deploy $CI_COMMIT_SHORT_SHA" && git push
  rules:
    - if: $CI_COMMIT_BRANCH == $CI_DEFAULT_BRANCH
      when: manual
```

Ручное подтверждение здесь — это либо `when: manual` на джобе, либо MR в config-repo,
который кто-то аппрувит. Второй вариант «гитопснее»: подтверждение хранится в истории git.

## 8. Плюсы и ограничения

**Плюсы:**
- полный аудит: кто, когда и что изменил в окружении — в истории git;
- откат = `git revert`, и он одинаков для всех окружений;
- кластеру не нужен внешний доступ, кредов кластера нет в CI;
- дрейф обнаруживается и лечится сам;
- воспроизводимость: новый кластер поднимается из того же репозитория.

**Ограничения и подводные камни:**
- рассчитан на **декларативные** системы (k8s); для «серверов с systemd» приходится
  изобретать (Ansible-pull, периодический apply) — это уже не совсем GitOps;
- секреты требуют отдельного решения (см. §6);
- «два репозитория» усложняют навигацию и требуют дисциплины;
- при автоматическом обновлении тегов легко получить неожиданный выкат — нужны правила;
- диагностика «почему OutOfSync» требует понимания k8s-объектов и webhooks/контроллеров.

## 💼 Как это в DevOps

- В компаниях с Kubernetes GitOps сейчас — фактически стандарт CD. Собеседующий, скорее всего,
  спросит не «умеешь ли», а «как устроен процесс: кто двигает теги и как подтверждается прод».
- Твои типичные задачи: настроить Argo CD и структуру config-repo, развести окружения,
  подключить секреты через External Secrets, объяснить разработчикам, что `kubectl edit`
  на проде больше не работает.
- Частый инцидент: «выкатили руками, через минуту откатилось» — это self-heal, и он прав.
- Для не-k8s инфраструктуры честный ответ: «GitOps-принципы (git как источник правды,
  декларативность, аудит) применимы, но pull-агента нет — используем Ansible из пайплайна».

## 🧠 Что запомнить

1. GitOps = **декларативное состояние в git + агент, который сверяет и применяет**.
2. Ключевое отличие от классического CD — **pull вместо push**.
3. Кредов кластера в CI нет: это главный аргумент безопасности.
4. Деплой — это коммит/мерж; откат — `git revert`; аудит — `git log`.
5. Обычно два репозитория: код и конфигурация окружений.
6. Тег образа в config-repo двигает джоба CI или image updater.
7. Reconciliation loop постоянно чинит дрейф — ручные правки на кластере не выживают.
8. Argo CD — с UI и `Application`; Flux — набор CRD и «чистый git».
9. Секреты в git — только зашифрованные или по ссылке (External Secrets/Vault/SOPS/Sealed).
10. GitOps не отменяет CI: сборка, тесты и сканы остаются в GitLab CI/Jenkins.
11. Prune и self-heal — мощно и опасно: включай осознанно, начиная с неавтоматического sync.
12. Для серверов без k8s GitOps в чистом виде не применяется — но принципы переносимы.

### Блок A. Теория

**A1.** Дай определение GitOps через четыре составляющие.

<details><summary>Ответ</summary>

(1) Git — единственный источник правды о желаемом состоянии; (2) состояние описано
декларативно; (3) агент в кластере непрерывно сверяет фактическое состояние с желаемым
и устраняет расхождения; (4) любое изменение проходит через git, поэтому есть ревью,
история, аудит и откат.

</details>

**A2.** Что означает «декларативное описание» и чем оно отличается от императивного?
Приведи по примеру.

<details><summary>Ответ</summary>

Декларативное — «что должно быть» (`replicas: 3`, манифест Deployment);
императивное — «что сделать» (`kubectl scale --replicas=3`, скрипт с шагами).
Декларативное можно применить повторно и сверить с реальностью, императивное — нет.

</details>

**A3.** Нарисуй словами разницу push- и pull-модели доставки.

<details><summary>Ответ</summary>

Push: внешняя CI-система имеет доступ в кластер и сама применяет изменения
(`kubectl apply`, `helm upgrade`). Pull: агент внутри кластера периодически забирает
состояние из git и применяет его сам; извне в кластер никто не ходит.

</details>

**A4.** Почему pull-модель считается более безопасной? Где в push-модели лежат креды кластера?

<details><summary>Ответ</summary>

В push-модели kubeconfig/токен кластера хранится в CI — то есть креды продового
кластера лежат во внешней системе, доступной многим. В pull-модели этих кредов снаружи нет
вообще: агент уже внутри и работает с локальным API, а наружу ему нужен только доступ
к git и registry.

</details>

**A5.** Что такое reconciliation loop?

<details><summary>Ответ</summary>

Цикл: прочитать желаемое состояние из git → получить фактическое из кластера →
сравнить → при расхождении применить желаемое → повторить. Работает постоянно,
а не только в момент деплоя.

</details>

**A6.** Что такое дрейф конфигурации? Назови три причины его появления.

<details><summary>Ответ</summary>

Дрейф — расхождение фактического состояния с описанным в git. Причины: ручные правки
(`kubectl edit/scale/patch`), изменения, внесённые другими контроллерами/операторами,
удаление или порча объектов, внешние автоматизации (автоскейлер), а также применение
изменений мимо GitOps.

</details>

**A7.** Что делают опции `prune` и `selfHeal` в Argo CD? Чем они опасны?

<details><summary>Ответ</summary>

`prune` удаляет из кластера ресурсы, которых больше нет в git; `selfHeal` возвращает
ресурсы к git-состоянию при ручных изменениях. Опасность: неверный путь/фильтр в git или
ошибочный коммит приведёт к удалению нужных объектов, а selfHeal помешает временным
аварийным правкам. Включать осознанно, начиная с ручного sync.

</details>

**A8.** Зачем разделять репозиторий кода и репозиторий конфигурации? Четыре аргумента.

<details><summary>Ответ</summary>

(1) Изменение конфигурации не должно триггерить пересборку кода; (2) разные права
на код и на прод-конфиг; (3) история окружений видна отдельно («что было в проде месяц
назад»); (4) один config-repo описывает много сервисов и окружений; плюс исключается
цикл «CI меняет свой же репозиторий → снова запускается CI».

</details>

**A9.** Кто и как обновляет тег образа в config-repo? Два способа.

<details><summary>Ответ</summary>

Либо джоба CI после успешной сборки коммитит новый тег в config-repo (напрямую
в ветку окружения или через MR), либо image updater (Argo CD Image Updater / Flux image
automation) сам отслеживает новые теги в registry по правилу и делает коммит.

</details>

**A10.** Как в GitOps выглядит откат на предыдущую версию?

<details><summary>Ответ</summary>

`git revert` коммита в config-repo (или переход `targetRevision` на предыдущий
коммит/тег). Агент увидит расхождение и вернёт кластер к предыдущему состоянию.
Фактически откат = обычное изменение состояния через git, поэтому у него та же процедура,
что и у выката.

</details>

**A11.** Как в GitOps организовать ручное подтверждение выката в прод? Два варианта.

<details><summary>Ответ</summary>

(1) Ручной sync в Argo CD (автоматический sync выключен для прод-приложения);
(2) MR в config-repo, который аппрувит ответственный, — тогда решение остаётся в истории git.
Второй вариант предпочтительнее с точки зрения аудита.

</details>

**A12.** Сравни Argo CD и Flux: модель, UI, мульти-кластер, автообновление образов.

<details><summary>Ответ</summary>

Argo CD: модель `Application` (+ ApplicationSet), богатый UI с diff и кнопками,
удобное управление многими кластерами из одной инсталляции, image updater — отдельный
компонент. Flux: набор CRD (GitRepository, Kustomization, HelmRelease, ImagePolicy),
без тяжёлого UI, image automation встроена, обычно по агенту на кластер.

</details>

**A13.** Почему нельзя класть k8s `Secret` с base64 в git? Назови четыре корректных подхода
к секретам в GitOps.

<details><summary>Ответ</summary>

Base64 — кодирование, а не шифрование: любой, у кого есть доступ к репозиторию,
читает секрет. Корректно: External Secrets Operator (в git — ссылка, значения из Vault/
облачного менеджера), Sealed Secrets (шифрование ключом кластера), SOPS с age/KMS,
Vault Agent/CSI (секрет монтируется в под и в git его нет).

</details>

**A14.** GitOps заменяет CI? Что остаётся на стороне GitLab CI/Jenkins?

<details><summary>Ответ</summary>

Не заменяет. CI остаётся: линтеры, тесты, сборка образа, сканы, публикация
в registry и обновление тега в config-repo. GitOps-агент отвечает только за приведение
кластера к описанному состоянию.

</details>

**A15.** Где GitOps применим плохо и почему?

<details><summary>Ответ</summary>

Там, где нет декларативного API и агента, который может применять состояние:
классические серверы с systemd, сетевое оборудование, ручные процедуры. Принципы (git как
источник правды, ревью, аудит) переносимы, но реализуется это обычно push-моделью
(Ansible из пайплайна) или ansible-pull, что уже не полноценный GitOps.

</details>

**A16.** Что такое «окружения» в config-repo? Как обычно организованы каталоги/ветки?

<details><summary>Ответ</summary>

Каталоги на окружение (`apps/dev`, `apps/staging`, `apps/prod`) с overlay'ами
kustomize или отдельными values для Helm; реже — ветки на окружение. Каталоги обычно
удобнее: видно diff между окружениями и нет «долгоживущих» веток.

</details>

**A17.** Чем `ApplicationSet` полезен при большом числе сервисов/окружений?

<details><summary>Ответ</summary>

`ApplicationSet` генерирует множество `Application` по шаблону (по списку,
по каталогам в репозитории, по кластерам). Это убирает копипасту при десятках сервисов
и окружений и делает добавление нового сервиса изменением одной строки.

</details>

**A18.** Как в GitOps узнать, что именно сейчас в проде и когда это туда попало?

<details><summary>Ответ</summary>

По истории config-repo (`git log` файла окружения — когда и кем изменён тег),
по статусу приложения в Argo CD (какой ревизии соответствует текущее состояние)
и по метке/эндпоинту версии самого приложения.

</details>

### Блок B. «Что произойдёт»

**B1.** Разработчик выполнил `kubectl scale deploy/app --replicas=10` на проде.
В git указано `replicas: 3`, `selfHeal: true`. Что будет через минуту?

<details><summary>Ответ</summary>

Через один цикл сверки (обычно ~1-3 минуты или сразу по webhook) агент вернёт
`replicas: 3`, потому что в git указано именно столько. Ручное масштабирование не выживет.

</details>

**B2.** Кто-то удалил Service руками. `prune: true`, `selfHeal: true`. Что произойдёт?

<details><summary>Ответ</summary>

Service будет создан заново — selfHeal восстанавливает то, что описано в git.
(`prune` работает в обратную сторону: удаляет лишнее, чего в git нет.)

</details>

**B3.** В config-repo сделали revert коммита, поднявшего тег образа. Что сделает Argo CD?

<details><summary>Ответ</summary>

Увидит новое желаемое состояние (старый тег), пометит приложение OutOfSync
и — при автоматическом sync — выкатит предыдущий образ. Это и есть штатный откат.

</details>

**B4.** Argo CD показывает статус OutOfSync, но Healthy. Что это значит?

<details><summary>Ответ</summary>

Фактическое состояние отличается от git (кто-то изменил ресурс или новый коммит
ещё не применён), но приложение работает и проходит health-проверки.

</details>

**B5.** Argo CD показывает Synced, но Degraded. Что это значит?

<details><summary>Ответ</summary>

Состояние соответствует git, но приложение нездорово: например, поды не стартуют
из-за несуществующего тега образа, CrashLoopBackOff, не проходит readiness.
То есть «мы применили ровно то, что написано, и написанное не работает».

</details>

**B6.** В config-repo удалили целый каталог приложения при `prune: true`.

<details><summary>Ответ</summary>

Все ресурсы этого приложения будут удалены из кластера. Именно поэтому prune
включают осознанно и защищают критичные ресурсы (аннотации предотвращения удаления,
отдельные политики для PVC).

</details>

**B7.** Image Updater настроен на регулярку тегов `^v\d+\.\d+\.\d+$` и находит `v2.0.0`.
Что произойдёт и что это значит для прода?

<details><summary>Ответ</summary>

Updater закоммитит новый тег в config-repo, агент выкатит v2.0.0 автоматически.
Для прода это означает выкат без участия человека — допустимо только при зрелом
процессе (smoke, canary, автооткат); иначе правило должно быть ограничено (только
dev/staging, только патч-версии).

</details>

**B8.** CI запушил образ в registry, но не обновил config-repo. Что увидит пользователь?

<details><summary>Ответ</summary>

Ничего не изменится: кластер синхронизирован с git, а в git по-прежнему старый тег.
Классическая ситуация «собрали, но не выкатили» — и это ожидаемое поведение GitOps.

</details>

### Блок C. Практика

#### C1. 🔑 Спроектируй GitOps-процесс для своего приложения (на бумаге)

Опиши в `docs/gitops.md`:
1. Структуру config-repo (каталоги окружений, что лежит в каждом).
2. Что делает пайплайн приложения и где заканчивается его ответственность.
3. Кто и как двигает теги для dev/staging/prod.
4. Как подтверждается прод и где остаётся след этого решения.
5. Как хранятся секреты.
6. Как выглядит откат — по шагам, с командами.
7. Что делать, если Argo показывает OutOfSync после чужой ручной правки.

<details><summary>Ответ</summary>

Критерий качества документа: явно написано, **где заканчивается CI и начинается
агент**, кто имеет право менять прод-каталог config-repo и как выглядит откат в командах.

</details>

#### C2. Структура config-repo
Нарисуй дерево каталогов для трёх окружений и двух сервисов. Отметь, что дублируется,
а что выносится в общий base (kustomize overlays или Helm values по окружениям).

<details><summary>Ответ</summary>

Типичная структура:
```text:no-line-numbers
config-repo/
├── base/myapp/            # общие манифесты/чарт
├── overlays/dev/          # values/kustomization: реплики, ресурсы, домены, tag
├── overlays/staging/
└── overlays/prod/
```
Дублируется только то, что реально различается: теги, реплики, ресурсы, домены, секрет-ссылки.

</details>

#### C3. Джоба bump'а тега
Напиши джобу GitLab CI, которая после успешной сборки клонирует config-repo,
меняет `image.tag` на `$CI_COMMIT_SHORT_SHA`, коммитит и пушит. Ответь:
- под каким пользователем/токеном она ходит в config-repo и какие права ему нужны;
- почему для прода лучше создавать MR, а не пушить в ветку напрямую;
- как не зациклить пайплайны (коммит CI не должен вызывать бесконечный цикл).

<details><summary>Ответ</summary>

Токен — отдельный deploy-token/технический пользователь с правом записи **только**
в config-repo (не в код). Для прода лучше MR: остаётся след решения и работает ревью.
Зацикливание предотвращается тем, что это **другой** репозиторий, а в самом config-repo
пайплайна либо нет, либо он игнорирует коммиты от CI (`$CI_COMMIT_AUTHOR`, `[skip ci]`).

</details>

#### C4. (если есть k8s) Развернуть Argo CD
```bash
kind create cluster --name gitops
kubectl create namespace argocd
kubectl apply -n argocd -f https://raw.githubusercontent.com/argoproj/argo-cd/stable/manifests/install.yaml
kubectl -n argocd get pods -w
kubectl -n argocd get secret argocd-initial-admin-secret -o jsonpath='{.data.password}' | base64 -d
kubectl -n argocd port-forward svc/argocd-server 8080:443
```
Создай `Application`, указывающее на свой config-repo, и добейся статуса Synced/Healthy.

#### C5. (если есть k8s) Проверь self-heal
Измени число реплик через `kubectl scale`, наблюдай за статусом приложения и тем,
как Argo возвращает состояние. Замерь, сколько времени это заняло.

#### C6. (если есть k8s) Откат через git
Сделай коммит с заведомо нерабочим образом (несуществующий тег), дождись Degraded,
откати `git revert` и убедись, что кластер вернулся. Запиши время всей процедуры.

<details><summary>Ответ (C4-C6)</summary>

Ориентиры: Synced/Healthy достигается за 1-2 минуты; self-heal возвращает
ручные изменения за один интервал сверки; полный откат через `git revert` занимает
столько же, сколько обычный выкат, — это и есть главный плюс подхода.

</details>

#### C7. Секреты
Выбери один подход (External Secrets / Sealed Secrets / SOPS) и опиши,
что конкретно окажется в git, где будет храниться ключ/хранилище и кто имеет к нему доступ.

<details><summary>Ответ</summary>

Например, External Secrets: в git лежит `ExternalSecret` со ссылкой на путь
в Vault; значения хранятся в Vault; доступ к Vault — по ServiceAccount кластера;
люди в git видят только имя ключа, но не значение.

</details>

### Блок D. Инциденты

**D1.** Дежурный вручную поднял реплики на проде во время нагрузки. Через минуту всё
вернулось обратно, сервис снова лёг. Объясни механику и скажи, как правильно было поступить.

<details><summary>Ответ</summary>

Сработал selfHeal: желаемое состояние в git не менялось, поэтому агент вернул
реплики обратно. Правильно: закоммитить изменение в config-repo (даже в инциденте —
это 1 минута), либо временно отключить автосинк для приложения, зафиксировав это решение.

</details>

**D2.** В config-repo кто-то закоммитил `Secret` с base64-паролем. Что делать по шагам?

<details><summary>Ответ</summary>

Считать секрет скомпрометированным: сменить пароль/токен в источнике; удалить
значение из репозитория и из истории (rewrite/purge), заменить на корректный механизм
(External Secrets/SOPS/Sealed); проверить, кто имел доступ к репозиторию и логам;
добавить в пайплайн проверку на секреты, чтобы это не повторилось.

</details>

**D3.** Argo CD висит в OutOfSync, diff показывает разницу в поле, которое никто не менял
(например, `replicas` или аннотации). Какие причины бывают?

<details><summary>Ответ</summary>

Поля, которые проставляют другие контроллеры (HPA меняет `replicas`, service mesh
и операторы добавляют аннотации/sidecar), дефолты, добавляемые API-сервером,
различия форматов (кавычки/типы), а также несовпадение версии чарта. Лечится игнорированием
конкретных полей (`ignoreDifferences`) и тем, что управляемое HPA поле не описывают в git.

</details>

**D4.** После включения `prune: true` исчез PersistentVolumeClaim с данными.
Почему и как было избежать?

<details><summary>Ответ</summary>

PVC был описан в git, а потом его описание удалили (или он попал под удалённый
каталог) — prune удалил ресурс вместе с данными. Избежать: защищать stateful-ресурсы
(исключение из prune/аннотации), хранить PVC отдельно от быстро меняющихся манифестов,
делать бэкапы и проверять diff перед мержем.

</details>

**D5.** Image Updater автоматически выкатил в прод новый тег ночью, и утром обнаружили
регресс. Что поменять в процессе?

<details><summary>Ответ</summary>

Ограничить автообновление: только dev/staging, только определённые шаблоны версий;
для прода — MR с ревью или ручной sync; добавить smoke-тесты и автооткат;
выкатывать canary. Автоматика без страховки в проде — это Continuous Deployment
без выполненных условий (см. тему 01).

</details>

**D6.** CI успешно собрал образ, но в кластере старая версия. Куда смотреть по шагам?

<details><summary>Ответ</summary>

По шагам: (1) появился ли образ в registry с ожидаемым тегом; (2) обновился ли тег
в config-repo (git log нужного файла); (3) видит ли агент новый коммит (ревизия приложения,
webhook/интервал); (4) статус приложения: Synced/OutOfSync, Healthy/Degraded;
(5) события подов (`kubectl describe`, `ImagePullBackOff`, права на registry).

</details>

**D7.** Config-repo доступен на запись всей команде. Чем это опасно и как ограничить?

<details><summary>Ответ</summary>

Запись в config-repo = право менять прод. Ограничить: protected-ветки, обязательные
MR и аппрувы для каталогов прода (CODEOWNERS), отдельные права на dev/staging и prod,
технический пользователь CI с минимальными правами.

</details>

**D8.** Кластер в закрытом контуре, доступа из интернета нет. Как всё-таки доставлять
изменения и почему pull-модель здесь выигрывает?

<details><summary>Ответ</summary>

Агент внутри контура сам ходит наружу (или во внутренний git/registry) и тянет
состояние, поэтому входящий доступ в кластер не нужен вовсе. В push-модели пришлось бы
открывать доступ к kube-API снаружи или держать раннер внутри контура с кредами кластера.

</details>

### Блок E. Вопросы с собеседования

**1.** Что такое GitOps?

<details><summary>Ответ</summary>

Модель доставки: git — источник правды, состояние декларативно, агент в кластере
постоянно сверяет и приводит систему к описанному состоянию; изменения — через git.

</details>

**2.** Чем pull-модель отличается от push-модели?

<details><summary>Ответ</summary>

В push CI сам применяет изменения в кластер (и хранит его креды); в pull агент
внутри кластера забирает состояние из git и применяет сам.

</details>

**3.** Какие инструменты GitOps знаешь и чем отличаются?

<details><summary>Ответ</summary>

Argo CD (Application/ApplicationSet, UI, мульти-кластер) и Flux (набор CRD,
встроенная автоматизация образов, без тяжёлого UI).

</details>

**4.** Как в GitOps выглядит деплой и откат?

<details><summary>Ответ</summary>

Деплой — коммит/мерж в config-repo (+ sync); откат — `git revert` или переключение
на предыдущую ревизию, агент возвращает состояние.

</details>

**5.** Как хранить секреты при GitOps-подходе?

<details><summary>Ответ</summary>

External Secrets, Sealed Secrets, SOPS, Vault CSI — в git только ссылки или шифротекст.

</details>

**6.** Что такое дрейф конфигурации и как с ним борются?

<details><summary>Ответ</summary>

Дрейф — расхождение кластера с git; борются постоянной сверкой и selfHeal,
а также запретом ручных изменений.

</details>

**7.** Зачем нужен отдельный репозиторий конфигурации?

<details><summary>Ответ</summary>

Разделение ответственности и прав, отсутствие лишних пересборок, отдельная история
окружений, переиспользование для многих сервисов.

</details>

**8.** Как сделать ручное подтверждение выката в прод?

<details><summary>Ответ</summary>

Ручной sync в Argo CD либо MR с аппрувом в config-repo (предпочтительно — остаётся
след в истории).

</details>

**9.** Заменяет ли GitOps GitLab CI?

<details><summary>Ответ</summary>

Нет: CI по-прежнему делает сборку, тесты, сканы и публикацию артефакта.

</details>

**10.** Где GitOps не подходит?

<details><summary>Ответ</summary>

Там, где нет декларативного состояния и агента: классические серверы, сетевое
оборудование, ручные процессы.

</details>
