## 🗺️ Зачем DevOps-инженеру стратегия ветвления

Модель ветвления **определяет пайплайн**: какие ветки есть, тем и триггеры;
куда деплоится каждая ветка; где ставится ручное подтверждение; как считается версия.

```text:no-line-numbers
 модель ветвления ──► какие ветки существуют ──► rules в .gitlab-ci.yml
                                              ──► какое окружение для какой ветки
                                              ──► где manual, где protected
                                              ──► как формируется тег/версия артефакта
```

Спрашивают не «расскажи GitFlow наизусть», а **«какую бы ты выбрал и почему»**.

---

## 1. GitFlow

Классика 2010 года (Vincent Driessen). Максимально формальная модель.

```text:no-line-numbers
main      ──●────────────────────●────────────●──────►  только релизы, каждый = тег
             ╲                  ╱            ╱
hotfix        ╲            ●───╱            ╱           срочные фиксы прода
               ╲          ╱                ╱
release         ╲   ●────╯────────────────╯             стабилизация релиза
                 ╲ ╱
develop   ──●─────●──────●──────●──────●───────────►    интеграционная ветка
             ╲   ╱        ╲    ╱
feature       ●─╯          ●──╯                         фичи
```

| Ветка | Откуда | Куда мержится | Живёт |
|-------|--------|---------------|-------|
| `main`/`master` | — | — | вечно, только прод-релизы |
| `develop` | main | — | вечно, интеграция |
| `feature/*` | develop | develop | дни-недели |
| `release/*` | develop | main + develop | дни |
| `hotfix/*` | main | main + develop | часы |

**Плюсы:** формализован, понятен ролям (QA тестирует `release/*`), поддерживает
несколько версий продукта одновременно, хорош для коробочного софта с версиями.

**Минусы (почему от него уходят):** долгоживущие ветки → та самая *integration hell*,
против которой создавали CI; много мержей и конфликтов; медленный цикл релиза;
избыточен для веб-сервиса, который катится несколько раз в день.

**Как выглядит пайплайн при GitFlow:**
```text:no-line-numbers
feature/*  → lint + unit + build (без деплоя или на общий dev)
develop    → полный CI + авто-деплой на dev
release/*  → полный CI + деплой на staging, тут гоняют e2e и приёмку
main       → сборка релизного артефакта + тег + деплой на prod (manual)
hotfix/*   → ускоренный пайплайн + деплой на prod (manual)
```

> 💬 Хороший ответ на собесе: «GitFlow оправдан, когда есть релизные циклы, поддержка
> нескольких версий и отдельная приёмка QA. Для сервиса, который катится ежедневно,
> он избыточен и противоречит идее непрерывной интеграции».

## 2. GitHub Flow

Максимально простая модель: одна вечная ветка + короткие фича-ветки.

```text:no-line-numbers
main ──●─────●─────●─────●─────●──►   всегда деплоится, всегда рабочая
        ╲   ╱ ╲   ╱ ╲   ╱
         ●─╯   ●─╯   ●─╯              feature/* живут часы-дни, мержатся через PR/MR
```

Правила: `main` всегда деплоима; любая работа — короткая ветка от `main`; изменения
попадают в `main` через pull/merge request с обязательным зелёным пайплайном и ревью;
после мержа — сразу деплой.

**Плюсы:** просто, быстро, идеально ложится на Continuous Deployment.
**Минусы:** нет места для стабилизации релиза и одновременной поддержки нескольких версий;
требует хороших автотестов и feature flags.

---

## 3. GitLab Flow

Компромисс: короткие фича-ветки + **ветки окружений** (или релизные ветки).

```text:no-line-numbers
feature ──●──┐
              ▼
main    ──────●─────────●──────────────►   интеграция, деплой на staging
               ╲         ╲
pre-prod        ●─────────●───────────►    (опционально)
                 ╲         ╲
production        ●─────────●─────────►    что реально в проде
```

Идея: код движется **только вперёд** по цепочке `main → pre-production → production`.
Деплой = мерж в ветку окружения. История ветки `production` — история продовых релизов.

Второй вариант — **release branches**: `main` + `1-5-stable`, `1-6-stable` для версий;
фиксы сначала в `main`, потом cherry-pick в стабильные ветки (upstream first).

**Плюсы:** проще GitFlow, но есть контроль над продом; наглядно видно, что в проде.
**Минусы:** ветки окружений легко превращаются в «долгоживущие», если нарушать
правило «только вперёд» и мержить в обход.

---

## 4. Trunk-Based Development

Самая «CI-шная» модель: все коммитят в один trunk (`main`), ветки живут **часы**.

```text:no-line-numbers
main ──●─●─●─●─●─●─●─●─●─●──►   много мелких коммитов/MR в день
        │   ╲ ╱
        │    ●          короткие ветки на несколько часов
        ▼
   release/1.2 (опционально, для версионных релизов и hotfix)
```

Обязательные условия: быстрый и надёжный CI, обязательные code review (или парное
программирование), **feature flags** для незаконченной функциональности, дисциплина
«не ломать trunk».

**Плюсы:** минимум конфликтов, максимальная скорость, честный CI по определению.
**Минусы:** требует зрелой команды и тестов; без feature flags в trunk попадает
недоделанная функциональность.

> 📊 Исследования DORA стабильно связывают trunk-based с элитной производительностью
> доставки. Это хороший аргумент на собесе, если спросят «что лучше».

## 5. Сравнение

| | GitFlow | GitHub Flow | GitLab Flow | Trunk-Based |
|---|---|---|---|---|
| Вечных веток | 2 (main, develop) | 1 (main) | 1 + ветки окружений | 1 (+release при нужде) |
| Жизнь фича-ветки | дни-недели | часы-дни | часы-дни | часы |
| Релизный цикл | Длинный, по расписанию | Непрерывный | Непрерывный/управляемый | Непрерывный |
| Поддержка старых версий | ✅ отлично | ❌ нет | ✅ через release branches | ⚠️ через release branches |
| Сложность | Высокая | Низкая | Средняя | Низкая (но дисциплина!) |
| Под что | Коробочный софт, версии, регламент | SaaS, простые сервисы | Сервисы с явным контролем прода | Зрелые команды, высокий темп |
| Нужны feature flags | Нет | Желательно | Желательно | Обязательно |

**Как отвечать на «какую выбрать»:** от процесса релиза, а не от вкуса.
Есть регламент и приёмка QA → GitFlow/GitLab Flow с release-ветками.
Катимся часто и сами владеем продом → GitHub Flow / Trunk-Based.

## 6. Merge, rebase, squash — что попадает в историю

| Стратегия | Что получается | Когда |
|-----------|----------------|-------|
| **Merge commit** | Сохраняется вся история ветки + коммит слияния | Релизные ветки, аудит |
| **Squash** | Вся ветка → один коммит в main | Дефолт для фича-веток: чистая история, легко откатывать |
| **Rebase / fast-forward** | Линейная история без merge-коммитов | Когда важна линейность (`git log --oneline` читается) |

```bash
git fetch origin
git rebase origin/main          # перенести свою ветку поверх свежего main
git push --force-with-lease     # ⚠️ только в СВОЮ ветку, не в общую!
```

> ⚠️ `--force` в общую ветку — классика катастроф. Используй `--force-with-lease`
> и только в ветках, где работаешь один. Общие ветки (`main`, `develop`) — protected.

## 7. Защита веток (то, чем это включается в реальности)

**GitLab:** Settings → Repository → Protected branches / Protected tags.
- `main`: Allowed to push — **No one**, Allowed to merge — Maintainers/Developers;
- обязательный MR, обязательный зелёный пайплайн («Pipelines must succeed»),
  обязательные approvals, запрет force-push;
- Protected variables доступны **только** джобам из защищённых веток/тегов — так
  прод-секреты не утекут в пайплайн из случайной фича-ветки.

**GitHub:** Branch protection rules / Rulesets — required status checks, required reviews,
linear history, запрет force-push.

Без защиты веток вся модель ветвления держится на честном слове.

## 8. Версионирование артефактов

### SemVer — `MAJOR.MINOR.PATCH`
```text:no-line-numbers
1.4.2
│ │ └── PATCH: исправления, обратно совместимо
│ └──── MINOR: новая функциональность, обратно совместимо
└────── MAJOR: несовместимые изменения API
```
Плюс пре-релизы: `2.0.0-rc.1`, `1.5.0-beta.2`.

### Что использовать как тег Docker-образа
```text:no-line-numbers
myapp:8f3a91c              # ⭐ commit SHA — иммутабельный, однозначный, для деплоя
myapp:1.4.2                # релизная версия (SemVer), для людей и changelog
myapp:1.4                  # плавающий указатель на последний патч
myapp:main                 # последняя сборка ветки — для dev-стендов
myapp:latest               # ❌ в деплое не использовать: неоднозначно и невоспроизводимо
```
Практика: **деплоим по SHA**, человекочитаемые теги — это алиасы. Тогда «что сейчас в проде»
и «откатиться на предыдущее» — точные операции.

### CalVer
`2026.09.1` — календарное версионирование, удобно для сервисов, у которых нет
публичного API и «мажорность» ничего не значит.

### Откуда берётся версия в CI
```bash
# из git-тега (если пайплайн запущен по тегу)
VERSION=${CI_COMMIT_TAG:-0.0.0-dev}

# автоматически из истории тегов
git describe --tags --always --dirty      # v1.4.2-3-g8f3a91c

# всегда доступно в GitLab CI
$CI_COMMIT_SHORT_SHA   # 8f3a91c
$CI_COMMIT_REF_NAME    # имя ветки или тега
$CI_PIPELINE_IID       # порядковый номер пайплайна в проекте
```

## 9. Conventional Commits (и зачем это CI)

```text:no-line-numbers
feat: добавить экспорт в CSV
fix(auth): не падать при пустом токене
chore(ci): ускорить кэш зависимостей
feat!: убрать поле legacy_id из API     ← ! = breaking change
```
Формат `type(scope): описание` даёт машиночитаемую историю: по ней автоматически
считается следующая версия (`feat` → MINOR, `fix` → PATCH, `!` → MAJOR) и генерируется
changelog (semantic-release, release-please, cz). Это связывает ветвление с пайплайном:
версия перестаёт быть предметом ручного решения.

## 💼 Как это в DevOps

- Модель ветвления приходит к тебе **как требование**: под неё ты пишешь `rules`,
  окружения и правила деплоя. Если разработчики меняют модель — меняется пайплайн.
- Частый запрос: «почему деплой на staging не запустился?» — ответ обычно в `rules`
  и в том, что человек работал в ветке, которую пайплайн не обслуживает.
- Ты — тот, кто настраивает **protected branches, protected tags и protected variables**.
  Это граница безопасности между фича-веткой и продом.
- Тебя спросят: «как понять, что сейчас в проде?» Правильный ответ — тег образа = SHA
  коммита + запись в окружении (Environments в GitLab), а не «Петя помнит».

## 📌 Шпаргалка

| Модель | Вечные ветки | Фича-ветка живёт | Сигнатура |
|--------|--------------|------------------|-----------|
| GitFlow | main + develop | дни-недели | release/* и hotfix/* |
| GitHub Flow | main | часы-дни | деплой сразу после мержа |
| GitLab Flow | main + окружения | часы-дни | код движется только вперёд |
| Trunk-Based | main | часы | feature flags обязательны |

| Задача | Как |
|--------|-----|
| Актуализировать ветку | `git fetch origin && git rebase origin/main` |
| Безопасный force | `git push --force-with-lease` (только своя ветка) |
| Чистая история main | Squash при мерже MR |
| Точная версия в проде | Тег образа = `$CI_COMMIT_SHORT_SHA` |
| Релизная версия | SemVer из git-тега (`$CI_COMMIT_TAG`) |
| Запретить push в main | Protected branches + обязательный MR + зелёный пайплайн |
| Прод-секреты только для прода | Protected variables + protected branches/tags |

## 🧠 Что запомнить

1. Стратегия ветвления диктует устройство пайплайна: ветки → триггеры → окружения.
2. **GitFlow** — про релизные циклы и поддержку версий; для ежедневных релизов избыточен.
3. **GitHub Flow** — одна ветка `main`, всё остальное короткое; идеален под Continuous Deployment.
4. **GitLab Flow** — ветки окружений, код движется только вперёд; компромиссный вариант.
5. **Trunk-Based** — самый «непрерывный», требует feature flags и зрелых тестов.
6. Долгоживущие ветки — главный враг CI в любой модели.
7. Squash-мерж даёт чистую историю main и простой откат одного изменения.
8. `--force-with-lease` вместо `--force`, и никогда в общие ветки.
9. Protected branches/tags/variables — техническая граница между разработкой и продом.
10. Деплой по **SHA**, а не по `latest`: воспроизводимость и честный откат.
11. SemVer — для релизов и людей; SHA — для машин и деплоя; можно и то, и другое.
12. Conventional Commits позволяют считать версию и changelog автоматически.

### Блок A. Теория

**A1.** Почему DevOps-инженеру вообще важна стратегия ветвления? Назови три вещи в пайплайне,
которые от неё напрямую зависят.

<details><summary>Ответ</summary>

Модель определяет: (1) какие ветки существуют → триггеры и `rules` в пайплайне;
(2) соответствие «ветка → окружение» → куда деплоить; (3) где стоят ручные подтверждения
и защищённые переменные; дополнительно — как считается версия артефакта.

</details>

**A2.** Перечисли ветки GitFlow и скажи, откуда каждая создаётся и куда мержится.

<details><summary>Ответ</summary>

`main` — только релизы (ни от кого не создаётся, живёт вечно);
`develop` — от `main`, интеграционная, живёт вечно;
`feature/*` — от `develop` → в `develop`;
`release/*` — от `develop` → в `main` **и** обратно в `develop`;
`hotfix/*` — от `main` → в `main` **и** в `develop`.

</details>

**A3.** Зачем в GitFlow нужна ветка `release/*`, если есть `develop` и `main`?

<details><summary>Ответ</summary>

Чтобы заморозить состав релиза и стабилизировать его (баг-фиксы, QA-приёмка),
пока в `develop` уже идёт работа над следующим релизом. Это разделяет «то, что выпускаем»
и «то, что разрабатываем».

</details>

**A4.** Почему hotfix в GitFlow мержится в две ветки?

<details><summary>Ответ</summary>

В `main` — чтобы фикс попал в прод; в `develop` — чтобы он не потерялся и не
вернулся регрессом в следующем релизе (иначе следующий релиз перезапишет исправление).

</details>

**A5.** Главный недостаток GitFlow с точки зрения идеи CI. Объясни через «долгоживущие ветки».

<details><summary>Ответ</summary>

GitFlow поощряет долгоживущие `feature/*` и `release/*`: интеграция происходит редко
и большими кусками, конфликты копятся, тесты долго не видят совместный код. Это ровно то
состояние, ради устранения которого придумали непрерывную интеграцию.

</details>

**A6.** Опиши GitHub Flow в трёх правилах. Что обязательно должно быть в проекте,
чтобы он работал безопасно?

<details><summary>Ответ</summary>

(1) `main` всегда рабочая и деплоима; (2) любая работа — короткая ветка от `main`;
(3) попадание в `main` только через MR/PR с зелёным пайплайном и ревью, после мержа — деплой.
Нужны: надёжные автотесты, защита ветки, обязательный пайплайн на MR, желательно feature flags.

</details>

**A7.** Что такое ветки окружений в GitLab Flow и что означает правило «код движется только вперёд»?

<details><summary>Ответ</summary>

Ветки, соответствующие окружениям (`main` → staging, `production` → прод). Деплой
происходит при мерже в такую ветку. «Только вперёд» — изменения всегда идут по цепочке
`main → pre-prod → production` и никогда не вносятся напрямую в ветку окружения, иначе
окружения расходятся и теряется воспроизводимость.

</details>

**A8.** Что такое upstream first при работе с release-ветками?

<details><summary>Ответ</summary>

Правило: исправление сначала попадает в основную ветку (upstream), и только потом
переносится (cherry-pick) в стабильные/релизные ветки. Иначе фикс живёт только в старой
версии и возвращается регрессом в новой.

</details>

**A9.** Что такое Trunk-Based Development? Почему без feature flags он опасен?

<details><summary>Ответ</summary>

Все работают в одной ветке `main`, ветки живут часы, интеграция происходит постоянно.
Без feature flags в `main` неизбежно попадает незаконченная функциональность — а `main`
по определению может быть выкачена в любой момент.

</details>

**A10.** Какая модель подойдёт: (а) банковскому монолиту с релизом раз в месяц и приёмкой QA;
(б) SaaS, который катится 10 раз в день; (в) библиотеке, у которой поддерживаются версии 1.x и 2.x?

<details><summary>Ответ</summary>

(а) GitFlow или GitLab Flow с release-ветками — есть регламент, приёмка, окно релиза;
(б) GitHub Flow или Trunk-Based — короткие ветки, непрерывный выкат; (в) release-ветки
(`1-x-stable`, `2-x-stable`) + upstream first, так как надо поддерживать обе версии.

</details>

**A11.** Чем отличаются merge commit, squash и rebase при вливании ветки? Что выбрать
для фича-веток и почему?

<details><summary>Ответ</summary>

Merge commit сохраняет всю историю ветки и факт слияния; squash схлопывает ветку
в один коммит; rebase переносит коммиты поверх целевой ветки, давая линейную историю.
Для фича-веток обычно squash: читаемая история `main`, один коммит = одно изменение,
простой `revert` при откате.

</details>

**A12.** Почему `git push --force` в общую ветку — катастрофа, а `--force-with-lease`
в свою ветку — норма?

<details><summary>Ответ</summary>

`--force` перезаписывает удалённую ветку вашим состоянием, уничтожая чужие коммиты,
которые вы не видели. `--force-with-lease` откажется пушить, если на сервере появились
изменения, которых у вас нет. В своей ветке перезапись истории после rebase — нормальная
практика; в общей — потеря работы команды.

</details>

**A13.** Что дают protected branches? Какие настройки включают в GitLab для `main`?

<details><summary>Ответ</summary>

Запрещают прямой push и force-push, требуют MR, зелёный пайплайн, approvals.
Для `main` в GitLab: Allowed to push — No one; Allowed to merge — Maintainers (или Developers);
включить «Pipelines must succeed», «All threads must be resolved», запретить force-push;
отдельно защитить теги релизов.

</details>

**A14.** Что такое protected variables и как они связаны со стратегией ветвления?

<details><summary>Ответ</summary>

Protected variables отдаются только джобам, запущенным из защищённых веток и тегов.
Это значит, что прод-секреты физически недоступны пайплайну из произвольной фича-ветки —
защита от «сделаю MR, в котором джоба выведет токен».

</details>

**A15.** Объясни SemVer. Что меняется в версии при исправлении бага, при новой обратно
совместимой ручке API, при удалении поля из ответа?

<details><summary>Ответ</summary>

`MAJOR.MINOR.PATCH`: исправление бага → PATCH (`1.4.2` → `1.4.3`); обратно совместимая
новая функциональность → MINOR (`1.4.2` → `1.5.0`); удаление поля из ответа — несовместимое
изменение → MAJOR (`1.4.2` → `2.0.0`).

</details>

**A16.** Почему деплоить по тегу `latest` — плохая идея? Какой тег использовать вместо него?

<details><summary>Ответ</summary>

`latest` — плавающая ссылка: в разные моменты времени это разные образы, поэтому
«перезапуск» может незаметно подменить версию, откат невозможен, а расследование инцидента
теряет опору. Вместо него — иммутабельный тег, равный SHA коммита (плюс SemVer для релизов).

</details>

**A17.** Зачем нужны Conventional Commits с точки зрения автоматизации?

<details><summary>Ответ</summary>

Формат `type(scope): описание` делает историю машиночитаемой: инструменты
(semantic-release, release-please) автоматически вычисляют следующую версию (`fix`→PATCH,
`feat`→MINOR, `!`/`BREAKING CHANGE`→MAJOR) и генерируют changelog — версия перестаёт быть
предметом ручного решения и споров.

</details>

**A18.** Как из пайплайна узнать имя текущей ветки, короткий SHA и тег?

<details><summary>Ответ</summary>

В GitLab CI: `$CI_COMMIT_BRANCH` (или `$CI_COMMIT_REF_NAME` — ветка или тег),
`$CI_COMMIT_SHORT_SHA`, `$CI_COMMIT_TAG` (пусто, если пайплайн не по тегу),
`$CI_DEFAULT_BRANCH` — имя ветки по умолчанию.

</details>

### Блок B. «Что делает команда»

```bash
B1.  git switch -c feature/export main
B2.  git fetch origin && git rebase origin/main
B3.  git merge --no-ff release/1.4
B4.  git push --force-with-lease
B5.  git tag -a v1.4.2 -m "release 1.4.2" && git push origin v1.4.2
B6.  git describe --tags --always --dirty
B7.  git log --oneline --graph --all --decorate
B8.  git cherry-pick 8f3a91c
B9.  git switch -c hotfix/critical-auth main
B10. git branch -r --merged origin/main
B11. git revert 8f3a91c
B12. git reset --hard origin/main
```

<details><summary>Ответ</summary>

```text:no-line-numbers
B1.  Создать ветку feature/export от main и переключиться на неё
B2.  Забрать изменения с сервера и перенести свои коммиты поверх свежего main
B3.  Слить release/1.4 с обязательным merge-коммитом (сохранить факт слияния)
B4.  Перезаписать свою ветку на сервере, но только если на ней нет чужих новых коммитов
B5.  Создать аннотированный тег версии и отправить его в origin (часто = триггер релизного пайплайна)
B6.  Показать ближайший тег + число коммитов после него + SHA (+ dirty, если есть незакоммиченное)
B7.  Показать граф истории всех веток одной строкой на коммит
B8.  Перенести один конкретный коммит в текущую ветку (типично: фикс в release-ветку)
B9.  Создать hotfix-ветку от main (то есть от того, что сейчас в проде)
B10. Показать удалённые ветки, уже слитые в origin/main (кандидаты на удаление)
B11. Создать новый коммит, отменяющий изменения указанного — безопасно для общей истории
B12. Жёстко сбросить локальную ветку на состояние origin/main, потеряв локальные изменения
```

</details>

**B13.** Чем `git revert` принципиально отличается от `git reset --hard` для ветки,
которую уже запушили?

<details><summary>Ответ</summary>

`revert` создаёт новый коммит с обратными изменениями — история не переписывается,
все, кто уже забрал ветку, не пострадают. `reset --hard` переписывает историю и в общей
ветке потребует force-push, ломая работу остальных. В опубликованных ветках — только `revert`.

</details>

### Блок C. Практика

#### C1. 🔑 Смоделируй GitFlow на игрушечном репозитории

```bash
mkdir -p ~/cicd-lab/02 && cd ~/cicd-lab/02 && git init -b main
echo "v0" > app.txt && git add . && git commit -m "init"
git switch -c develop
```
Выполни полный цикл:
1. две ветки `feature/a` и `feature/b` от `develop`, по коммиту в каждой, мерж в `develop`;
2. `release/1.0` от `develop`, один «фикс стабилизации», мерж в `main` + тег `v1.0.0`,
   обратный мерж в `develop`;
3. `hotfix/1.0.1` от `main`, фикс, мерж в `main` + тег `v1.0.1` и мерж в `develop`.

Посмотри результат: `git log --oneline --graph --all --decorate`.
Запиши, **сколько мержей** тебе понадобилось на одну фичу и один хотфикс.

<details><summary>Ответ</summary>

Ожидаемый результат: на одну фичу — 1 мерж (`feature` → `develop`), на релиз — 2
(`release` → `main`, `release` → `develop`), на хотфикс — 2 (`hotfix` → `main`,
`hotfix` → `develop`). Итого много синхронизаций, и каждая — потенциальный конфликт.
Именно этот счётчик — главный аргумент против GitFlow для быстрых релизов.

</details>

#### C2. Тот же сценарий в GitHub Flow
В новом репозитории повтори ту же функциональность (две фичи + срочный фикс),
но по правилам GitHub Flow. Сравни число веток, мержей и шагов с C1 — выпиши разницу.

<details><summary>Ответ</summary>

В GitHub Flow: одна ветка на фичу, один мерж в `main`, деплой сразу; хотфикс —
такая же короткая ветка от `main`. Никаких обратных мержей и release-веток. Меньше шагов,
но вся ответственность переносится на автотесты и защиту ветки.

</details>

#### C3. Ветки окружений (GitLab Flow)
Заведи `main`, `staging`, `production`. Проведи изменение по цепочке
`feature → main → staging → production` только мержами вперёд.
Затем попробуй внести правку **сразу в production** и опиши, какую проблему это создаёт
и как её обнаружить автоматически.

<details><summary>Ответ</summary>

Проблема правки напрямую в `production`: изменение есть в проде, но его нет в `main`,
и следующий мерж вперёд его затрёт (регресс). Обнаруживается автоматически: джоба, которая
проверяет, что `production` не содержит коммитов, отсутствующих в `main`
(`git log --oneline main..production` должен быть пуст) — иначе пайплайн красный.

</details>

#### C4. Rebase против merge
Создай ветку, сделай в ней 3 коммита, параллельно измени `main`. Слей ветку двумя способами
(в двух копиях репозитория): `merge --no-ff` и `rebase`. Сравни `git log --graph`.
Какой вариант тебе проще читать и почему?

<details><summary>Ответ</summary>

`merge --no-ff` даёт «ветвистый» граф, где видно, какие коммиты пришли из ветки;
`rebase` — линейную историю, которую проще читать и бисектить (`git bisect`).
Практика многих команд: rebase внутри ветки для актуализации + squash при мерже.

</details>

#### C5. Защита ветки (в GitLab)
В своём проекте на gitlab.com:
1. сделай `main` protected: push — No one, merge — Maintainers;
2. включи «Pipelines must succeed» и «All threads must be resolved»;
3. попробуй запушить прямо в `main` — зафиксируй текст ошибки;
4. создай protected-переменную `PROD_TOKEN` и убедись, что в джобе из обычной ветки
   она **пустая**, а из `main` — доступна.

<details><summary>Ответ</summary>

Push в защищённый `main` вернёт что-то вида
`remote: GitLab: You are not allowed to push code to protected branches on this project`.
Protected-переменная в джобе из обычной ветки не будет определена (пустая строка) —
это и есть механизм разделения прод- и не-прод-секретов.

</details>

#### C6. Версионирование образа
Настрой (пока на бумаге или в черновом `.gitlab-ci.yml`) схему тегов:
- каждая сборка → `app:$CI_COMMIT_SHORT_SHA`;
- сборка из `main` → дополнительно `app:main`;
- сборка по git-тегу `vX.Y.Z` → дополнительно `app:X.Y.Z` и `app:X.Y`.
Напиши, какой тег будет использоваться в деплое на прод и почему.

<details><summary>Ответ</summary>

Деплой на прод — по `app:$CI_COMMIT_SHORT_SHA` (иммутабельный тег); `app:1.4`
и `app:main` — человекочитаемые указатели для навигации и dev-стендов. При откате
достаточно задеплоить предыдущий SHA — образ уже в registry, пересборка не нужна.

</details>

#### C7. Conventional Commits
Переоформи 5 своих последних коммитов в формате Conventional Commits и определи,
какой номер версии получился бы автоматически, если предыдущая версия — `1.3.0`.

<details><summary>Ответ</summary>

Пример: если среди коммитов есть `fix:` и `feat:` без breaking change, следующая
версия после `1.3.0` — `1.4.0` (MINOR за `feat`). Если бы был `feat!:` или
`BREAKING CHANGE:` — `2.0.0`. Только `fix:`/`chore:` → `1.3.1`.

</details>

### Блок D. Инциденты

**D1.** Разработчик сделал `git push --force` в `develop`, потерялись коммиты двух коллег.
Что делать сейчас и что настроить, чтобы это стало невозможно?

<details><summary>Ответ</summary>

Сейчас: найти потерянные коммиты через `git reflog` у того, у кого есть локальная
копия (или в веб-интерфейсе/событиях GitLab), восстановить ветку и запушить.
Настроить: protected branch с запретом force-push и прямого push, обязательные MR.

</details>

**D2.** Хотфикс выкатили в прод из ветки `hotfix/*`, но через неделю баг вернулся.
Что забыли сделать?

<details><summary>Ответ</summary>

Не сделали обратный мерж `hotfix` → `develop` (или `main` → `develop`): исправление
осталось только в проде, а следующий релиз из `develop` принёс старый код обратно.

</details>

**D3.** В проекте GitFlow. Ветка `develop` зелёная, `release/2.0` — красная,
причём падают тесты, которых в `develop` нет. Как такое возможно?

<details><summary>Ответ</summary>

`release/2.0` была создана раньше и содержит код, который в `develop` уже изменён/
удалён (или наоборот, в `develop` тесты были поправлены/отключены, а в release-ветку это
не перенесли). Классика долгоживущих веток: две истории разошлись. Лечение — upstream first
и регулярная синхронизация release-ветки.

</details>

**D4.** Деплой на прод делают из тега `latest`. Дежурный «перезапустил под» — и в проде
оказалась версия на 4 коммита новее, чем ожидалось. Объясни механику и исправление.

<details><summary>Ответ</summary>

`latest` указывал на более новый образ, и при перезапуске нода скачала его
(или `imagePullPolicy: Always`). Исправление: деплоить по иммутабельному тегу (SHA/версия),
запретить `latest` в манифестах, фиксировать digest.

</details>

**D5.** Пайплайн для `staging` не запускается у одного из разработчиков. Он работает
в ветке `feat/SAVE-123`. В `rules` написано `- if: $CI_COMMIT_BRANCH == "develop"`.
Где ошибка мышления?

<details><summary>Ответ</summary>

`rules` описывают только ветку `develop`, поэтому фича-ветки не деплоятся на staging —
и это, как правило, **правильное** поведение. Ошибка мышления в ожидании: staging-деплой
привязан к модели ветвления, а не к «моей ветке». Если нужны стенды на ветку — это отдельный
механизм (dynamic environments/review apps).

</details>

**D6.** MR висит две недели, в нём 87 файлов. Ревьюер отказывается смотреть.
Какие практики нарушены и что предложить команде?

<details><summary>Ответ</summary>

Нарушены короткие ветки и маленькие изменения, частая интеграция, ревью «по кусочку».
Предложить: дробить работу на серию MR, мержить за фича-флагом, ставить лимит на размер MR,
ревьюить ежедневно.

</details>

**D7.** После перехода на squash-мерж перестала работать автогенерация changelog
по Conventional Commits. Почему и как чинить?

<details><summary>Ответ</summary>

При squash в `main` попадает **один** коммит с заголовком MR — если его заголовок
не оформлен по Conventional Commits, инструмент ничего не находит. Чинится настройкой
шаблона заголовка MR и проверкой заголовка линтером (`commitlint`) в пайплайне MR.

</details>

**D8.** В проде нашли баг. Чтобы понять, какой коммит виноват, нужно знать, что там
за версия. В контейнере тег `app:release`. Что поменять в схеме тегирования?

<details><summary>Ответ</summary>

`release` — плавающий тег, по нему нельзя восстановить коммит. Нужно тегировать
образ SHA (и/или SemVer), прокидывать версию внутрь образа (label + переменная `APP_VERSION`,
эндпоинт `/version`), чтобы прод сам отвечал, какая в нём сборка.

</details>

### Блок E. Вопросы с собеседования

**1.** Какие стратегии ветвления знаешь?

<details><summary>Ответ</summary>

GitFlow, GitHub Flow, GitLab Flow, Trunk-Based Development (плюс форк-модель для OSS).

</details>

**2.** Расскажи GitFlow: ветки и их назначение.

<details><summary>Ответ</summary>

См. A2 — ветки, их источники и точки слияния, теги на `main`.

</details>

**3.** Почему многие уходят от GitFlow?

<details><summary>Ответ</summary>

Долгоживущие ветки, много обязательных мержей, медленный цикл релиза; для сервисов
с частыми выкатами избыточен и мешает непрерывной интеграции.

</details>

**4.** Что такое trunk-based development и что для него нужно?

<details><summary>Ответ</summary>

Разработка в одной основной ветке, ветки живут часы, обязательные быстрые проверки,
feature flags для незавершённого, дисциплина не ломать trunk.

</details>

**5.** Как выбрать модель ветвления для проекта?

<details><summary>Ответ</summary>

От процесса релиза и требований: регламентированные релизы и поддержка версий →
GitFlow/release-ветки; частые выкаты и владение продом → GitHub Flow/Trunk-Based.

</details>

**6.** Как модель ветвления влияет на CI/CD пайплайн?

<details><summary>Ответ</summary>

Определяет триггеры (`rules`), соответствие веток окружениям, точки ручного подтверждения,
работу защищённых переменных и схему версионирования.

</details>

**7.** Чем rebase отличается от merge? Что использовать в команде?

<details><summary>Ответ</summary>

Merge сохраняет историю и создаёт коммит слияния; rebase переписывает историю, давая
линейность. В команде: rebase/squash для своих веток, merge — для релизных слияний;
переписывать опубликованную общую историю нельзя.

</details>

**8.** Как защитить main-ветку?

<details><summary>Ответ</summary>

Protected branches: запрет push и force-push, только MR, обязательный зелёный пайплайн,
approvals; плюс protected tags и protected variables.

</details>

**9.** Как версионировать артефакты? Что использовать как тег Docker-образа?

<details><summary>Ответ</summary>

SemVer для релизов, иммутабельный тег по SHA для деплоя, дополнительные плавающие
алиасы (`1.4`, `main`) для удобства. Артефакты хранятся в registry, не в git.

</details>

**10.** Как понять, какая версия сейчас в проде?

<details><summary>Ответ</summary>

По тегу образа, равному SHA, по записи в Environments (GitLab показывает текущий деплой)
и по эндпоинту `/version` самого приложения, куда версия зашита при сборке.

</details>
