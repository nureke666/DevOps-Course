# 01. CI, CD и CD — концепции

> Роадмап → 4. CI/CD → Теория → Методология

> CI/CD процесс?»

> на примере, назвать принципы, по которым строится процесс, и метрики, которыми его измеряют.

---

## 🗺️ Схема: путь коммита до прода

```text:no-line-numbers
 разработчик            CI (Continuous Integration)             CD
 ──────────             ────────────────────────────            ──────────────────────
 git push  ──►  ┌──────────────────────────────────┐
                │ 1. сборка (build)                │
                │ 2. статический анализ (lint)     │   ← «интеграция»: код всех
                │ 3. unit-тесты                    │     разработчиков собирается
                │ 4. сборка артефакта (образ/пакет)│     и проверяется ВМЕСТЕ, часто
                │ 5. публикация в registry         │
                └───────────────┬──────────────────┘
                                │ артефакт (один и тот же!)
                                ▼
                ┌──────────────────────────────────┐
                │ dev      — авто                  │
                │ staging  — авто                  │  Continuous DELIVERY:
                │ prod     — 🔘 кнопка (manual)    │  всё готово, релиз по кнопке
                └──────────────────────────────────┘
                                или
                ┌──────────────────────────────────┐
                │ prod     — авто, без кнопки      │  Continuous DEPLOYMENT:
                └──────────────────────────────────┘  зелёный пайплайн = прод
```

**Одна фраза, которая закрывает половину собеса:**
разница Delivery и Deployment — **ровно одна кнопка ручного подтверждения перед продом**.

## 1. Continuous Integration (CI) — непрерывная интеграция

**Определение:** практика, при которой разработчики **часто** (минимум раз в день) вливают
свои изменения в общую ветку, и каждое вливание **автоматически** проверяется сборкой и тестами.

**Какую боль лечит.** До CI команда неделями работала в своих ветках, а потом наступал
«день интеграции»: конфликты, сломанная сборка, чужой код, который не собирается, и неделя
разбора, кто что сломал. Это называли *integration hell*. CI переворачивает подход:
интегрируемся постоянно и маленькими кусками, поэтому поломка всегда свежая и маленькая.

**Что входит в CI:**

| Шаг | Зачем |
|-----|-------|
| Сборка из чистого состояния | Проверить, что собирается не только «на машине Васи» |
| Линтеры/форматтеры | Единый стиль, ловля мусора до ревью |
| Unit-тесты | Быстрая обратная связь: 1-5 минут |
| Сборка артефакта (образ, jar, бинарь) | Получить то, что поедет дальше |
| Публикация артефакта в registry | Артефакт versioned и доступен следующим стадиям |

**Признаки, что CI у вас есть по-настоящему:**
1. Сборка запускается **автоматически** на каждый push/MR, а не «когда нажмём».
2. Она **быстрая** (обратная связь ≤ 10 минут), иначе её начнут игнорировать.
3. Красная сборка в основной ветке — **инцидент номер один**, чинится раньше новых фич.
4. Мерж в основную ветку **невозможен** при красном пайплайне (защищённая ветка).
5. Все ветки живут **недолго** (часы/дни, не месяцы) — иначе это не интеграция.

> ❗ Частая путаница на собесе: «У нас Jenkins — значит, есть CI». Нет. Jenkins — инструмент.
> CI — это практика коротких веток + частых мержей + автоматической проверки.
> Можно иметь Jenkins и не иметь CI (ветки живут по 3 месяца), и наоборот.

## 2. Continuous Delivery (CD) — непрерывная поставка

**Определение:** каждое изменение, прошедшее CI, **автоматически доводится до состояния,
готового к релизу**, и может быть выкачено в прод в любой момент — **решение о выкате
принимает человек**.

Ключевое слово — **готовность**. Артефакт собран, протестирован на staging, миграции проверены,
процедура деплоя автоматизирована и отрепетирована. Остаётся нажать кнопку.

```text:no-line-numbers
build → test → публикация артефакта → авто-деплой dev → авто-деплой staging → 🔘 prod (manual)
```

**Зачем кнопка.** Бизнес-причины (релиз привязан к маркетингу), регуляторика (нужна подпись
релиз-менеджера), риск (миграция БД на 300 ГБ), окна обслуживания. Технически прод мог бы
выкатываться сам — но организация решила иначе.

---

## 3. Continuous Deployment (CD) — непрерывное развёртывание

**Определение:** то же самое, **но без кнопки**. Каждый коммит, прошедший все проверки,
автоматически едет в прод.

```text:no-line-numbers
build → test → публикация → dev → staging → prod   (всё авто, человек не участвует)
```

**Что обязательно должно быть, иначе это не «зрелость», а рулетка:**
- высокое доверие к тестам (покрытие, интеграционные, smoke после деплоя);
- **автоматический откат** по метрикам/healthcheck;
- feature flags — код в проде, фича выключена, включается отдельно от деплоя;
- canary/blue-green — выкат на часть трафика раньше, чем на всех;
- мониторинг и алерты, которые заметят деградацию быстрее пользователей.

| | Continuous Delivery | Continuous Deployment |
|---|---|---|
| Прод-деплой | По кнопке (manual) | Автоматически |
| Кто решает | Человек | Пайплайн |
| Требования к тестам | Высокие | Очень высокие |
| Типично для | Банки, энтерпрайз, B2B | Продуктовые компании, SaaS |
| В GitLab CI | <code v-pre>when: manual</code> на джобе прода | Обычная джоба без <code v-pre>when</code> |

> 🎯 На собесе аббревиатуру «CD» нужно **разворачивать самому**: «CD — это два разных термина;
> под CD чаще имеют в виду Delivery; разница с Deployment в ручном подтверждении прода».
> Этот ответ — топ-2 вопрос раздела в роадмапе.

## 4. Принципы, по которым строят CI/CD процесс

Это ядро ответа на топ-1 вопрос собеса («как бы ты построил идеальный пайплайн»).

### 1. Единый источник правды — git
Код, конфиги пайплайна, инфраструктура (IaC), манифесты деплоя — всё в репозитории.
Ничего не настраивается «руками в UI», иначе знание живёт в голове одного человека.

### 2. Build once, deploy many ⭐
Артефакт собирается **ровно один раз** и **один и тот же** проходит dev → staging → prod.
Пересборка перед продом = вы тестировали один артефакт, а выкатили другой
(другая версия зависимости, другой base-image, другой коммит). Различия окружений —
**только через переменные и конфиги**, не через пересборку.

### 3. Быстрая обратная связь
Быстрое — раньше: линтер (10 сек) → unit (2 мин) → интеграционные (10 мин) → e2e (30 мин).
Ломается — падаем сразу, не тратим 40 минут, чтобы узнать про опечатку.

### 4. Fail fast, fail loud
Красный пайплайн виден всем, уведомление приходит автору, мерж заблокирован.
Пайплайн, который «иногда красный и это норм», бесполезен: люди перестают смотреть.

### 5. Идемпотентность и воспроизводимость
Запуск дважды даёт тот же результат. Никаких `latest` у base-образов и зависимостей,
никакого состояния, унаследованного от прошлой сборки (кроме явного кэша).

### 6. Изоляция и чистое окружение
Каждая джоба — в чистом контейнере. Shell-executor на сервере, где остались файлы от прошлой
сборки, — классический источник «у меня локально работает, в CI нет» и наоборот.

### 7. Секреты — вне репозитория
CI/CD Variables (masked + protected), Vault, внешние секрет-менеджеры. Никогда — в YAML,
никогда — в `echo` в логе.

### 8. Автоматизировать, в том числе откат
«Как откатиться» — часть пайплайна, а не устное знание. Откат должен занимать минуты
и не требовать пересборки (см. принцип 2).

### 9. Прод-подобные окружения
Staging максимально похож на прод (та же версия БД, та же схема сети). Иначе staging зелёный,
а прод падает.

### 10. Всё измеряется
Время пайплайна, доля падений, частота релизов, время восстановления (см. DORA ниже).

## 5. Метрики DORA — чем измеряют зрелость процесса

| Метрика | Что значит | Элитный уровень |
|---------|------------|-----------------|
| **Deployment Frequency** | Как часто выкатываете в прод | По требованию, несколько раз в день |
| **Lead Time for Changes** | От коммита до прода | < 1 дня |
| **Change Failure Rate** | Доля релизов, вызвавших инцидент | 0-15% |
| **MTTR / Failed Deployment Recovery** | Время восстановления после сбоя | < 1 часа |

Полезно ввернуть на собесе: «Улучшение пайплайна я бы оценивал по DORA — например, срезать
lead time с 2 дней до 2 часов и держать change failure rate ниже 15%».

## 6. Пирамида тестов в пайплайне

```text:no-line-numbers
              ▲   e2e / UI — мало, медленно, хрупко (ночью или перед релизом)
             ╱ ╲
            ╱   ╲  интеграционные — с БД, очередями, соседними сервисами
           ╱     ╲
          ╱       ╲ unit — много, быстро, на каждый коммит
         ╱_________╲
          статический анализ: линтер, типы, форматтер, секрет-скан (секунды)
```

Правило: чем выше по пирамиде, тем дороже и позже в пайплайне.
Если e2e-тесты гоняются на каждый коммит и занимают 40 минут — разработчики начинают
пушить «на всякий случай без тестов» и процесс разваливается.

---

## 7. Термины, которые надо произносить правильно

| Термин | Смысл |
|--------|-------|
| **Pipeline** | Весь процесс от коммита до деплоя (набор стадий) |
| **Stage** | Этап пайплайна (build, test, deploy); стадии идут последовательно |
| **Job** | Конкретная задача внутри стадии; джобы одной стадии — параллельно |
| **Runner / Agent / Executor** | Машина (или контейнер), которая выполняет джобу |
| **Artifact** | Результат сборки: образ, jar, бинарь, отчёт |
| **Registry** | Хранилище артефактов (Docker Registry, Nexus, Artifactory) |
| **Environment** | Окружение деплоя: dev / staging / prod |
| **Promotion** | Продвижение одного и того же артефакта на следующее окружение |
| **Rollback** | Возврат на предыдущую известную рабочую версию |
| **Quality gate** | Порог, ниже которого пайплайн не пускает дальше (покрытие, уязвимости) |
| **Trunk** | Основная ветка (main/master), от которой живёт продукт |

---

## 8. Стратегии выката (кратко — подробно в теме 03)

| Стратегия | Суть | Цена |
|-----------|------|------|
| **Recreate** | Погасили старое, подняли новое | Простой, но есть downtime |
| **Rolling** | Обновляем по одному инстансу | Без downtime, но две версии одновременно |
| **Blue-Green** | Два одинаковых окружения, переключаем трафик | Мгновенный откат, x2 ресурсов |
| **Canary** | 5% трафика на новую версию, смотрим метрики | Безопасно, нужен хороший мониторинг |
| **Feature flags** | Деплой ≠ релиз, фича включается флагом | Гибко, но растёт сложность кода |

## 💼 Как это в DevOps

- **Ты не «пишешь ямлы», ты владеешь процессом доставки.** Разработчики приходят с вопросом
  «почему мой код не в проде» — ответ должен быть в пайплайне, а не в переписке.
- **Пайплайн — продукт для разработчиков.** Медленный, флакающий (то красный, то зелёный)
  пайплайн так же вреден, как его отсутствие: ему перестают доверять.
- **Типичные задачи на работе:** ускорить пайплайн (кэш, needs, параллель), внедрить проверку
  безопасности, развести окружения, дать командам общий шаблон, разобрать ночное падение.
- **Что чаще всего разваливает процесс:** долгоживущие ветки, ручные шаги «только Петя умеет»,
  секреты в репозитории, пересборка артефакта перед продом, отсутствие отката.

## 📌 Шпаргалка

| Вопрос | Короткий ответ |
|--------|----------------|
| Что такое CI? | Частая интеграция изменений в общую ветку + автоматическая сборка и тесты |
| Что такое CD (Delivery)? | Артефакт всегда готов к релизу, выкат в прод — по решению человека |
| Что такое CD (Deployment)? | То же, но выкат в прод автоматический |
| В чём разница Delivery/Deployment? | В ручном подтверждении прод-деплоя |
| Главный принцип артефакта | Build once, deploy many — один артефакт на все окружения |
| Чем измеряют процесс? | DORA: частота релизов, lead time, change failure rate, MTTR |
| Что должно быть в git? | Код, пайплайн, IaC, манифесты — всё, кроме секретов |
| Где секреты? | CI/CD Variables (masked/protected), Vault — не в репозитории |
| Порядок стадий | Быстрое и дешёвое раньше: lint → unit → build → integration → deploy |
| Признак зрелости | Откат автоматизирован и занимает минуты |

## 🧠 Что запомнить

1. **CI** — про частую интеграцию и автопроверку, а не про наличие Jenkins.
2. **CD** — два разных термина; разворачивай оба и говори про **кнопку** как про разницу.
3. **Build once, deploy many** — топовый принцип; пересборка перед продом ломает всю логику.
4. Различия окружений — **через переменные и конфиги**, не через отдельные сборки.
5. Быстрое раньше медленного: обратная связь ≤ 10 минут, иначе пайплайн начнут игнорировать.
6. Красная основная ветка — инцидент №1; мерж при красном пайплайне должен быть заблокирован.
7. Долгоживущие ветки убивают CI: интеграция раз в месяц — это не continuous.
8. Continuous Deployment без автооткатов, canary и мониторинга — не зрелость, а риск.
9. Секреты — только в хранилище секретов; в логах — маскирование.
10. Откат — часть пайплайна, а не героизм дежурного.
11. DORA-метрики — язык, на котором про CI/CD говорят с менеджментом.
12. Пайплайн, который никто не может объяснить построчно, рано или поздно станет неподдерживаемым.

### Блок A. Теория

**A1.** Что такое Continuous Integration? Назови три обязательных признака, что CI реально есть,
а не просто «стоит Jenkins».

<details><summary>Ответ</summary>

CI — практика частого (минимум ежедневного) вливания изменений в общую ветку с
автоматической сборкой и тестированием каждого вливания. Признаки настоящего CI:
(1) сборка запускается автоматически на каждый push/MR; (2) она быстрая — обратная связь
за минуты; (3) красная основная ветка чинится в приоритете, а мерж при красном пайплайне
заблокирован; плюс короткоживущие ветки.

</details>

**A2.** Какую проблему исторически решил CI? Как называлось то, что было до него?

<details><summary>Ответ</summary>

До CI изменения копились в ветках неделями, и интеграция превращалась в многодневный
разбор конфликтов и поломок — *integration hell*. CI делает интеграцию частой и маленькой,
поэтому поломка всегда свежая, локальная и дешёвая в починке.

</details>

**A3.** Что такое Continuous Delivery? Что значит «артефакт готов к релизу»?

<details><summary>Ответ</summary>

Continuous Delivery — каждое прошедшее проверки изменение автоматически доводится до
состояния «готово к релизу»: артефакт собран, опубликован, выкачен на прод-подобное окружение,
процедура деплоя автоматизирована и отрепетирована. Готовность = чтобы выкатить, нужно только
решение человека, а не работа инженера.

</details>

**A4.** Что такое Continuous Deployment и чем он отличается от Delivery **одним предложением**?

<details><summary>Ответ</summary>

В Continuous Deployment нет ручного подтверждения: прошедший проверки коммит
выкатывается в прод автоматически.

</details>

**A5.** Какие технические и организационные условия должны быть выполнены, чтобы включать
Continuous Deployment было не безрассудно?

<details><summary>Ответ</summary>

Надёжные и не флакающие тесты (unit + интеграционные + smoke после деплоя),
автоматический откат по healthcheck/метрикам, canary или blue-green, feature flags,
мониторинг и алерты, культура «чиним прод сразу», а также отсутствие регуляторных требований
на ручную приёмку релиза.

</details>

**A6.** Объясни принцип **build once, deploy many**. Что конкретно ломается, если пересобирать
артефакт перед продом?

<details><summary>Ответ</summary>

Артефакт собирается один раз и продвигается по окружениям неизменным. При пересборке
перед продом вы выкатываете **другой** артефакт, чем тестировали: могли подтянуться другие
версии зависимостей/базового образа, измениться порядок слоёв, попасть другой коммит.
Все проверки на staging обесцениваются, а расследование инцидента усложняется — нет
однозначного соответствия «версия в проде ↔ то, что тестировали».

</details>

**A7.** Если артефакт один на все окружения, как тогда отличаются dev и prod?

<details><summary>Ответ</summary>

Переменными окружения, конфиг-файлами, секретами из хранилища, параметрами деплоя
(реплики, лимиты, домены). Образ/бинарь — один и тот же, отличается только то, что подаётся
снаружи в момент запуска.

</details>

**A8.** Почему быстрые проверки ставят в начало пайплайна? Что происходит, если пайплайн идёт 50 минут?

<details><summary>Ответ</summary>

Чтобы падать как можно раньше и дешевле: незачем тратить 40 минут e2e, если линтер
за 10 секунд уже видит ошибку. Долгий пайплайн разрушает дисциплину: разработчики перестают
ждать результат, начинают мержить «на веру», накапливают изменения (большие коммиты),
и обратная связь окончательно ломается.

</details>

**A9.** Нарисуй (словами) пирамиду тестов и скажи, что на каком этапе пайплайна гонять.

<details><summary>Ответ</summary>

Основание — статический анализ (линтер, типы, секрет-скан, секунды) и unit-тесты
(минуты) — на каждый коммит. Середина — интеграционные тесты с реальными БД/очередями —
на MR и в main. Вершина — e2e/UI, их мало, они медленные и хрупкие — по расписанию (ночью)
или перед релизом/на staging.

</details>

**A10.** Назови метрики DORA и объясни, что говорит о команде высокий change failure rate
при высокой частоте релизов.

<details><summary>Ответ</summary>

Deployment Frequency, Lead Time for Changes, Change Failure Rate, MTTR (время
восстановления). Частые релизы при высоком change failure rate означают, что скорость
получена за счёт качества: не хватает тестов, quality gates, canary — команда быстро
доставляет в том числе поломки.

</details>

**A11.** Чем отличаются pipeline, stage, job? Что выполняется параллельно, а что последовательно?

<details><summary>Ответ</summary>

Pipeline — весь процесс; stage — этап пайплайна, стадии выполняются последовательно
(следующая начинается после успеха предыдущей); job — задача внутри стадии, джобы одной стадии
выполняются параллельно (в пределах доступных раннеров). В GitLab порядок можно менять через
`needs` (DAG).

</details>

**A12.** Что такое артефакт и чем он отличается от кэша?

<details><summary>Ответ</summary>

Артефакт — **результат** работы, который нужен дальше по пайплайну или для релиза
(образ, бинарь, отчёт); он версионируется, хранится и может быть выкачен. Кэш — **ускоритель**
(зависимости, npm/pip), его потеря ничего не ломает, только замедляет; на корректность
результата кэш влиять не должен.

</details>

**A13.** Что такое quality gate? Приведи три примера порогов.

<details><summary>Ответ</summary>

Порог, который пайплайн не пропускает дальше. Примеры: покрытие тестами не ниже 70%;
ни одной уязвимости уровня Critical в образе; ноль ошибок линтера; отсутствие секретов
в диффе; размер образа не больше 300 МБ.

</details>

**A14.** Почему долгоживущие ветки противоречат самой идее CI?

<details><summary>Ответ</summary>

Потому что «continuous» — это про постоянную интеграцию. Ветка, живущая месяц,
интегрируется один раз в месяц: конфликты копятся, тесты проверяют код, который давно
разошёлся с main, а поломка вскрывается разом и большим куском.

</details>

**A15.** Что такое feature flag и как он меняет смысл слова «релиз»?

<details><summary>Ответ</summary>

Feature flag — переключатель, отделяющий выкат кода от включения функциональности.
Код едет в прод выключенным, включается конфигом для части пользователей. «Релиз» перестаёт
быть синонимом «деплоя»: деплой — техническое событие, релиз — бизнес-решение.

</details>

**A16.** Перечисли пять стратегий выката и назови главный минус каждой.

<details><summary>Ответ</summary>

Recreate (простой сервиса), Rolling (какое-то время работают две версии — нужна
совместимость API и схемы БД), Blue-Green (двойные ресурсы, сложность с состоянием и БД),
Canary (нужен качественный мониторинг и маршрутизация трафика), Feature flags (растёт
сложность кода и число комбинаций, флаги надо удалять).

</details>

**A17.** Почему откат должен быть частью пайплайна, а не ручной процедурой?

<details><summary>Ответ</summary>

Потому что откат нужен в худший момент — в инциденте, ночью, под давлением.
Ручная процедура в этот момент выполняется с ошибками и медленно. Автоматизированный откат
(перезапуск предыдущего образа/тега, переключение трафика) выполняется за минуты и одинаково
любым дежурным.

</details>

**A18.** Что должно лежать в git, а что не должно никогда?

<details><summary>Ответ</summary>

В git: код, тесты, конфигурация пайплайна, IaC (Terraform/Ansible), манифесты
деплоя, шаблоны конфигов, документация, `.env.example`. Никогда: пароли, токены, приватные
ключи, дампы с персональными данными, большие бинарные артефакты (им место в registry).

</details>

### Блок B. «Классифицируй ситуацию»

Для каждой ситуации скажи: это **CI**, **Continuous Delivery**, **Continuous Deployment**
или **ничего из перечисленного** — и почему.

**B1.** На каждый push запускается сборка и unit-тесты, мерж при красном запрещён.
Деплой на прод — вручную по SSH раз в две недели.

<details><summary>Ответ</summary>

CI есть (автосборка, тесты, защита ветки), CD нет: деплой ручной и нерегулярный —
это «CI без CD».

</details>

**B2.** Пайплайн собирает образ, деплоит на dev и staging автоматически;
на прод — джоба с <code v-pre>when: manual</code>, которую нажимает тимлид.

<details><summary>Ответ</summary>

Continuous Delivery: до прода всё автоматизировано, прод — по кнопке.

</details>

**B3.** Любой мерж в main через 12 минут оказывается в проде без участия человека.

<details><summary>Ответ</summary>

Continuous Deployment.

</details>

**B4.** Раз в месяц собирается релизная ветка, QA тестирует неделю, потом релиз.
Сборка запускается по кнопке в Jenkins.

<details><summary>Ответ</summary>

Ничего из перечисленного: сборка по кнопке, интеграция раз в месяц, релизный цикл
неделями. Наличие Jenkins не делает это CI.

</details>

**B5.** Джобы в пайплайне есть, но сборка падает уже три дня, и все просто мержат мимо неё.

<details><summary>Ответ</summary>

Ничего: формально пайплайн есть, но нарушен главный принцип — красная сборка не
является стоп-сигналом. Это «CI-театр».

</details>

**B6.** Есть автотесты и автодеплой, но перед продом образ пересобирается из main заново.

<details><summary>Ответ</summary>

CI + автоматизация деплоя, но принцип build once, deploy many нарушен: в прод едет
не тот артефакт, который тестировали.

</details>

### Блок C. Практика (на бумаге и в git)

#### C1. 🔑 Спроектируй «идеальный пайплайн» (главное задание темы)

Возьми приложение из блока Docker. Напиши (в файле `pipeline-design.md` в этом же репо):

1. Список стадий с обоснованием каждой: **зачем она, что падает, сколько идёт**.
2. Что именно является артефактом и где он хранится.
3. Какие окружения есть, как на них попадает код, кто и чем подтверждает прод.
4. Где хранятся секреты.
5. Как выглядит откат: команда/кнопка, время, что откатывается (код, схема БД, конфиг).
6. Какие quality gates и с какими порогами.
7. Что произойдёт, если тесты флакают (иногда красные).

Это дословно топ-1 вопрос с собеса. Ответ должен занимать **2-3 минуты речи**.

<details><summary>Ответ</summary>

Каркас образцового ответа:

```text:no-line-numbers
1. Триггер: push в ветку и merge request. Для main — отдельные правила.
2. Стадии:
   - lint (10-30 с): форматтер, статический анализ, детект секретов.
   - test (2-5 мин): unit + покрытие; quality gate по покрытию.
   - build (2-4 мин): сборка Docker-образа, тег = commit SHA (иммутабельный),
     пуш в registry. Собирается ОДИН РАЗ.
   - scan (1-3 мин): скан образа (Trivy) и зависимостей (SCA), gate по Critical.
   - integration (5-10 мин): поднять сервис + БД, прогнать интеграционные тесты.
   - deploy:dev (авто, по пушу в любую ветку или в dev).
   - deploy:staging (авто, по мержу в main) + smoke-тесты.
   - deploy:prod (manual, только с main, только защищённые переменные)
     + smoke + автооткат при неуспехе.
3. Артефакт: Docker-образ registry.example.com/app:<git-sha>,
   дополнительно тег :staging/:prod как указатель. Никаких latest в деплое.
4. Окружения: dev/staging/prod; отличаются ТОЛЬКО переменными и секретами.
5. Секреты: CI/CD Variables (masked + protected) или Vault; прод-секреты доступны
   только защищённым веткам/окружениям.
6. Quality gates: покрытие >= X%, 0 Critical CVE, линтер без ошибок.
7. Флакающие тесты: карантин (отдельный набор) + заведённый баг, а не retry навсегда.
8. Откат: деплой предыдущего SHA (образ уже в registry) — 2-3 минуты, кнопкой.
9. Наблюдаемость: уведомление о падении в чат, ссылка на лог, дашборд по DORA.
```

</details>

#### C2. Измерь свой текущий процесс
Для любого своего проекта (или воображаемого) прикинь четыре DORA-метрики и напиши,
какую из них ты улучшал бы первой и какими техническими действиями.

<details><summary>Ответ</summary>

Пример рассуждения: если lead time = 3 дня, самая дешёвая победа обычно —
убрать ручные шаги и ожидание согласований на пути к staging, ускорить пайплайн (кэш,
параллель, `needs`) и разрешить мелкие MR. Если высок change failure rate — сначала тесты,
quality gates и canary, а не скорость.

</details>

#### C3. Раздели «деплой» и «релиз»
Опиши сценарий, в котором код выкатывается в прод в понедельник, а фича включается в четверг.
Что для этого нужно в коде, в конфиге и в процессе?

<details><summary>Ответ</summary>

Нужны: feature flag в коде (проверка флага в точке ветвления), хранилище флагов
(конфиг/БД/сервис флагов), возможность менять флаг без деплоя, договорённость в команде,
что незавершённая фича мержится выключенной, и процедура удаления флага после релиза.

</details>

#### C4. Найди ручные шаги
Выпиши список всего, что в знакомом тебе (или гипотетическом) процессе делается руками:
правка конфига на сервере, перезапуск сервиса, миграция БД, обновление сертификата.
Для каждого — как автоматизировать и что мешает.

<details><summary>Ответ</summary>

Типичный список: правка `.env` на сервере, `systemctl restart`, ручные миграции,
ручное обновление сертификатов, ручная чистка диска, ручное создание пользователей.
Автоматизируется через IaC/Ansible, пайплайн деплоя, миграции как шаг пайплайна,
certbot/cert-manager, cron/ротацию.

</details>

#### C5. Короткие ветки на практике
```bash
git switch -c feature/small-change
# изменение на 10 строк
git commit -am "small change" && git push -u origin HEAD
```
Сделай **три** таких маленьких изменения вместо одного большого и опиши,
чем это лучше с точки зрения CI (три аргумента).

<details><summary>Ответ</summary>

(1) Каждое изменение проверяется отдельно — при падении сразу ясно, что сломало;
(2) конфликты почти невозможны, ревью быстрое; (3) откатывается маленький кусок,
а не трёхнедельная работа целиком.

</details>

### Блок D. Инциденты

**D1.** Пайплайн идёт 47 минут. Разработчики жалуются, что «CI мешает работать», и просят
разрешить мерж без прохождения тестов. Что ты предложишь вместо этого? (Минимум пять действий.)

<details><summary>Ответ</summary>

Не ослаблять gate, а чинить время: распараллелить джобы; вынести медленные e2e
в nightly/по расписанию; кэшировать зависимости; использовать `needs` (DAG) вместо
строгой очерёдности стадий; собирать образ с кэшем слоёв; добавить раннеров/увеличить
`concurrent`; разделить пайплайн на MR-пайплайн (быстрый) и main-пайплайн (полный);
запускать тяжёлые проверки только при изменении соответствующих путей (`rules: changes`).

</details>

**D2.** На staging всё зелёное, на проде приложение падает при старте. Артефакт тот же.
Три вероятные причины и как их устранить на уровне процесса.

<details><summary>Ответ</summary>

(1) Различия окружений, зашитые не в переменные, а в сам стенд (версия БД, ядро,
сеть, права) — лечится прод-подобным staging и IaC; (2) секреты/переменные прода
отличаются по формату или отсутствуют — лечится проверкой обязательных переменных на старте
и одинаковым способом их подачи; (3) данные: на проде реальные объёмы и «грязные» записи —
лечится миграциями с проверкой на копии прод-данных и smoke-тестами после деплоя.

</details>

**D3.** Тест `test_payment_timeout` падает примерно в одном запуске из пяти. Команда добавила
`retry: 3`. Чем это плохо и что делать правильно?

<details><summary>Ответ</summary>

`retry` прячет проблему: тест продолжает быть недетерминированным, а пайплайн
начинает «иногда» пропускать реальный баг и тратить время на повторы. Правильно — найти
причину (таймауты, гонки, зависимость от внешнего сервиса, общее состояние между тестами),
до починки — вынести тест в карантинный набор с заведённым тикетом и сроком.

</details>

**D4.** После релиза выросло число ошибок 5xx. Дежурный не знает, как откатиться:
«надо пересобрать предыдущий коммит, это 30 минут». Что не так с процессом?

<details><summary>Ответ</summary>

Нарушен build once, deploy many: предыдущий артефакт должен уже лежать в registry
и выкатываться одной кнопкой по тегу/SHA. Также нет отрепетированной процедуры отката и,
судя по всему, нет автоматического отката по метрикам. Откат обязан быть операцией на минуты,
не требующей сборки.

</details>

**D5.** Разработчик слил в main ветку, которую вёл три недели. Мерж-конфликты разбирали два дня,
после мержа упали интеграционные тесты. Какая практика CI нарушена и как это предотвратить?

<details><summary>Ответ</summary>

Нарушен базовый принцип CI — частая интеграция маленькими кусками. Предотвращение:
короткоживущие ветки (< 1-2 дней), регулярный `rebase`/`merge` main в ветку, MR небольшого
размера, feature flags для незавершённых фич, обязательный прогон интеграционных тестов
на MR-пайплайне.

</details>

**D6.** В логе джобы виден пароль от продовой БД. Что сделать немедленно (по шагам)
и что поменять в процессе, чтобы это не повторилось?

<details><summary>Ответ</summary>

Немедленно: отозвать и сменить учётные данные (считаем скомпрометированными),
удалить лог джобы, проверить, кто имел доступ к логу, поискать утечку в других местах.
В процессе: переменную сделать masked + protected, не выводить окружение (`set -x`,
`env`, `printenv`) в логах, использовать файл-переменные вместо инлайна, ограничить
доступ к прод-секретам защищёнными ветками, добавить в пайплайн скан на секреты.

</details>

**D7.** Команда включила Continuous Deployment. Через неделю прод лёг на 40 минут после
«безобидного» коммита. Чего не хватало в процессе?

<details><summary>Ответ</summary>

Не хватало страховочного контура: smoke-тестов после деплоя, canary/поэтапного
выката, автоматического отката по ошибкам/метрикам, алертов, feature flags. Continuous
Deployment — следствие зрелости тестов и наблюдаемости, а не переключатель в настройках.

</details>

**D8.** Прод и staging «одинаковые», но на проде PostgreSQL 13, а на staging — 16.
Какие классы багов это создаёт и как с этим бороться?

<details><summary>Ответ</summary>

Разное поведение SQL и планировщика, разные дефолты и типы, разное поведение
миграций и блокировок, фичи, которых нет в 13. Бороться: одинаковые версии из одного
источника (IaC/образы с пином версии), проверка миграций на копии прод-схемы,
запрет ручных различий и регулярная сверка конфигураций.

</details>

### Блок E. Вопросы с собеседования

**1.** Что такое CI/CD своими словами?

<details><summary>Ответ</summary>

Практика автоматической сборки, проверки и доставки изменений: CI — часто интегрировать
и автоматически проверять; CD — держать результат всегда готовым к выкату и выкатывать
автоматизированно.

</details>

**2.** В чём разница Continuous Integration, Continuous Delivery и Continuous Deployment?

<details><summary>Ответ</summary>

CI — интеграция и автопроверки; Delivery — всё готово к релизу, прод по решению человека;
Deployment — прод автоматически. Разница Delivery/Deployment — ручное подтверждение.

</details>

**3.** Как бы ты построил идеальный пайплайн?

<details><summary>Ответ</summary>

См. каркас в C1: триггеры → быстрые проверки → сборка одного артефакта → сканы →
интеграционные → окружения по возрастанию риска → прод по кнопке → smoke + откат.

</details>

**4.** Почему артефакт нужно собирать один раз?

<details><summary>Ответ</summary>

Чтобы в прод попадало ровно то, что тестировали; иначе проверки не дают гарантий,
а инциденты трудно расследовать.

</details>

**5.** Как в вашем процессе отличаются окружения, если артефакт один?

<details><summary>Ответ</summary>

Только конфигурацией: переменные окружения, секреты из хранилища, параметры деплоя.

</details>

**6.** Что делать, если пайплайн стал слишком долгим?

<details><summary>Ответ</summary>

Профилировать джобы, параллелить, кэшировать, применять `needs`, дробить на быстрый
MR-пайплайн и полный main-пайплайн, выносить медленное в расписание, запускать по
изменённым путям, добавлять мощность раннеров.

</details>

**7.** Как измерить, что CI/CD работает хорошо?

<details><summary>Ответ</summary>

DORA-метрики + операционные: длительность пайплайна, доля флаки-падений, время от
мержа до staging, доля успешных деплоев.

</details>

**8.** Где хранить секреты в CI/CD?

<details><summary>Ответ</summary>

В CI/CD Variables (masked, protected), в Vault/внешнем секрет-менеджере; в репозитории —
только `.env.example`; в логах — маскирование; доступ к прод-секретам — только защищённым
веткам/окружениям.

</details>

**9.** Как организовать откат?

<details><summary>Ответ</summary>

Хранить артефакты иммутабельно (тег = SHA), деплой предыдущей версии — отдельная быстрая
операция/кнопка; миграции — обратимые или совместимые вперёд; проверять откат регулярно.

</details>

**10.** Что такое quality gate и какие пороги ты бы поставил?

<details><summary>Ответ</summary>

Порог, блокирующий продвижение: покрытие, уязвимости, линтер, размер образа, результаты
smoke-тестов.

</details>

**11.** Чем деплой отличается от релиза?

<details><summary>Ответ</summary>

Деплой — техническое размещение кода в окружении; релиз — момент, когда функциональность
становится доступна пользователям. Feature flags разводят их во времени.

</details>

**12.** Какие стратегии выката знаешь и когда какую выбрать?

<details><summary>Ответ</summary>

Recreate — для внутренних сервисов, где допустим простой; Rolling — дефолт для
stateless-сервисов в кластере; Blue-Green — когда нужен мгновенный откат и есть ресурсы;
Canary — для рискованных изменений при хорошем мониторинге; Feature flags — для
постепенного включения функциональности и A/B.

</details>
