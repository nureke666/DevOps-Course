## 🗺️ Референсный пайплайн (тот самый «идеальный»)

```text:no-line-numbers
 push / MR
    │
    ▼
┌─────────┐  10-30 с   быстро и дёшево, падаем первыми
│ 1 lint  │  формат, статический анализ, secret-scan, lint Dockerfile/YAML
└────┬────┘
     ▼
┌─────────┐  1-5 мин
│ 2 test  │  unit-тесты + покрытие (quality gate)
└────┬────┘
     ▼
┌─────────┐  2-5 мин   ⭐ АРТЕФАКТ СОБИРАЕТСЯ ОДИН РАЗ
│ 3 build │  docker build → tag :$SHA → push в registry
└────┬────┘
     ▼
┌─────────┐  1-3 мин
│ 4 scan  │  Trivy (образ), SCA (зависимости), SAST — gate по Critical
└────┬────┘
     ▼
┌─────────────┐  5-15 мин
│ 5 integrate │  поднять сервис + БД (services) → интеграционные/контрактные тесты
└────┬────────┘
     ▼
┌──────────────┐   авто          ┌──────────────┐  авто по main    ┌──────────────┐ 🔘 manual
│ 6 deploy dev │ ──────────────► │ 7 deploy stg │ ───────────────► │ 8 deploy prod│
└──────────────┘                 └──────┬───────┘                  └──────┬───────┘
                                        ▼                                 ▼
                                   smoke-тесты                    smoke + мониторинг
                                                                   └─► ❌ → авто-откат
```

Тот же артефакт (`app:$SHA`) проходит все окружения. Меняются **только переменные**.

---

## 1. Стадии: что и зачем

| Стадия | Что делает | Почему здесь | Типичное время |
|--------|-----------|--------------|----------------|
| **lint** | Форматтер, статанализ, детект секретов, lint YAML/Dockerfile | Дешевле всего; ловит мусор до людей | секунды |
| **test** | Unit-тесты, покрытие | Быстрая проверка логики | 1-5 мин |
| **build** | Сборка образа/пакета, публикация в registry | Один раз на весь путь | 2-5 мин |
| **scan** | Уязвимости образа и зависимостей, лицензии | После сборки — есть что сканировать | 1-3 мин |
| **integration** | Тесты с реальной БД/очередью, контрактные | Дороже unit, но до деплоя | 5-15 мин |
| **deploy:dev** | Автодеплой ветки/develop | Ранняя проверка «вживую» | 1-3 мин |
| **deploy:staging** | Автодеплой main + smoke | Прод-подобная проверка | 1-3 мин |
| **deploy:prod** | Manual, только из main/тега | Контроль риска | 1-5 мин |
| **post-deploy** | Smoke, прогрев, миграции, уведомления | Подтвердить, что живое | секунды-минуты |

**Правила порядка:** быстрое раньше медленного; всё, что может упасть, — до сборки, если
не требует артефакта; всё, что требует артефакта, — после сборки; деплой — только после
всех проверок.

## 2. Окружения

| Окружение | Кто пользуется | Данные | Деплой | Секреты |
|-----------|----------------|--------|--------|---------|
| **dev** | Разработчики | Синтетические | Авто на каждый push | Тестовые |
| **staging / pre-prod** | QA, демо | Копия структуры прода, обезличенные | Авто по мержу в main | Отдельные, не прод |
| **prod** | Пользователи | Реальные | Manual (или авто при CD) | Protected, только из main |

**Review apps / динамические окружения** — стенд на каждый MR, удаляется при закрытии.
Отличная практика, но требует ресурсов (и аккуратности с данными).

**Главное требование к staging:** быть похожим на прод в том, что влияет на поведение —
версии БД и рантайма, схема сети, конфигурация балансировщика, объём данных (хотя бы порядок).

## 3. Артефакты: что версионируем и где храним

```text:no-line-numbers
Docker-образ  → Docker Registry (GitLab Registry, Harbor, ECR, Nexus)
jar/war/whl   → Nexus / Artifactory / GitLab Package Registry
бинарь Go     → Package Registry / объектное хранилище
отчёты        → артефакты джобы (coverage, junit, trivy) — с expire_in
```

Правила:
1. Тег = **SHA коммита** → однозначность и иммутабельность.
2. Никаких `latest` в деплое.
3. Артефакт **не пересобирается** между окружениями (build once, deploy many).
4. Ретеншн: старое чистим, релизное храним (политика очистки registry).
5. Артефакт должен быть **самодостаточным**: внутри всё, кроме конфигурации и секретов.

## 4. Как в пайплайн встраивается Docker

Три роли докера в CI/CD — на собесе полезно разделять:

**1) Docker как среда выполнения джобы.** Раннер запускает джобу внутри контейнера
(`image: python:3.12-slim`) — чистое, воспроизводимое окружение без «мусора» с прошлых сборок.

**2) Docker как объект сборки.** Джоба `build` собирает образ приложения и пушит в registry.
Способы сборки внутри CI:

| Способ | Как | Плюсы/минусы |
|--------|-----|--------------|
| **Docker-in-Docker (dind)** | `services: docker:dind`, привилегированный режим | Полный докер; ⚠️ `privileged` = риск, нужен свой раннер |
| **Docker socket binding** | Проброс `/var/run/docker.sock` | Быстро; ⚠️ фактически root на хосте раннера |
| **Rootless BuildKit** | `moby/buildkit:rootless` + `buildctl-daemonless.sh` | Без докер-демона и privileged (но с послаблением seccomp/AppArmor), кэш в registry — ⭐ основной выбор для k8s/shared-раннеров |
| **Buildah** | `quay.io/buildah/stable`, `buildah build` + `buildah push` | Daemonless, Dockerfile как есть — вторая опция без privileged |
| **BuildKit (`docker buildx`)** | Современный билдер поверх dind, кэш в registry | Быстро, хорошая работа с кэшем; но нужен dind → privileged |
| **Kaniko (legacy)** | `/kaniko/executor` | Upstream архивирован в 2025, жив только форк Chainguard (security-фиксы) — не для новых пайплайнов |

**3) Docker как способ доставки.** На сервере/в кластере разворачивается тот самый образ:
`docker compose pull && docker compose up -d`, `docker service update`, `kubectl set image`.

> Подробности, рабочие примеры и подводные камни — тема [07. GitLab CI + Docker](/cicd/07-gitlab-ci-docker).

## 5. Как в пайплайн встраивается Ansible

Ansible в CI/CD решает две задачи:

**1) Подготовка инфраструктуры (provisioning).** Плейбуки ставят docker, настраивают
пользователей, firewall, nginx, сертификаты. Запускается отдельным пайплайном
в infra-репозитории (или по расписанию/вручную).

**2) Деплой приложения.** Джоба `deploy` вызывает плейбук, который на целевых хостах
логинится в registry, тянет образ по тегу и перезапускает сервис.

```yaml
# .gitlab-ci.yml — фрагмент
deploy:prod:
  stage: deploy
  image: alpine:3.20
  before_script:
    - apk add --no-cache ansible openssh-client
    - mkdir -p ~/.ssh && echo "$SSH_PRIVATE_KEY" > ~/.ssh/id_ed25519
    - chmod 600 ~/.ssh/id_ed25519
    - ssh-keyscan -H "$PROD_HOST" >> ~/.ssh/known_hosts     # не отключаем host key checking!
  script:
    - ansible-playbook -i inventory/prod.ini deploy.yml
        -e "app_image=$CI_REGISTRY_IMAGE:$CI_COMMIT_SHORT_SHA"
  environment:
    name: production
    url: https://app.example.com
  rules:
    - if: $CI_COMMIT_BRANCH == $CI_DEFAULT_BRANCH
      when: manual
```

```yaml
# deploy.yml
- hosts: app
  become: true
  tasks:
    - name: Login to registry
      community.docker.docker_login:
        registry_url: "{{ registry_url }}"
        username: "{{ registry_user }}"
        password: "{{ registry_password }}"

    - name: Deploy container
      community.docker.docker_container:
        name: app
        image: "{{ app_image }}"        # ⬅️ конкретный SHA, не latest
        state: started
        recreate: true
        restart_policy: unless-stopped
        published_ports: ["127.0.0.1:8000:8000"]
        env:
          APP_ENV: production
        healthcheck:
          test: ["CMD", "curl", "-fsS", "http://localhost:8000/health"]
          interval: 10s
          retries: 5
```

**Почему Ansible, а не `ssh "docker run ..."`:** идемпотентность (повтор не ломает),
inventory (один плейбук на 1 и на 50 серверов), роли и переменные окружений,
понятный вывод изменений, `--check` для сухого прогона.

**Типовые связки инструментов в пайплайне:**

| Инструмент | Роль в CI/CD |
|------------|--------------|
| Docker / BuildKit / Buildah | Сборка и упаковка |
| Registry (GitLab/Harbor/ECR) | Хранение артефактов |
| Ansible | Конфигурация серверов и деплой не-k8s |
| Terraform | Создание инфраструктуры (обычно отдельный пайплайн + план/apply) |
| Helm / kubectl / Argo CD | Деплой в Kubernetes |
| SonarQube | Качество кода, quality gate |
| Trivy / Grype | Сканирование образов и зависимостей |
| Vault / External Secrets | Секреты |
| Prometheus / Grafana | Проверка после деплоя, автооткат по метрикам |

## 6. Миграции БД — место, где пайплайны ломаются

```text:no-line-numbers
❌ Плохо:  деплой новой версии кода и «ALTER TABLE DROP COLUMN» в одном шаге
✅ Хорошо: expand → deploy → contract (три шага, часто три релиза)
```

**Expand/Contract (расширение и сжатие):**
1. **Expand:** добавить новую колонку/таблицу, ничего не удалять. Старый код работает.
2. **Deploy:** выкатить код, умеющий писать и читать по-новому (и читать старое).
3. **Backfill:** перенести данные фоном.
4. **Contract:** в следующем релизе удалить старое, когда старый код больше не работает.

Правила:
- миграции **отдельным шагом** пайплайна, до или после деплоя — но явно;
- миграции должны быть **совместимы вперёд** (rolling обновление = две версии кода одновременно);
- откат кода не должен требовать отката схемы (иначе rollback невозможен);
- долгие блокирующие миграции — вне пайплайна, отдельной процедурой с окном.

## 7. Стратегии выката

```text:no-line-numbers
Recreate        [v1][v1]  →  [   ][   ]  →  [v2][v2]      простой, есть downtime
Rolling         [v1][v1]  →  [v2][v1]   →  [v2][v2]      без downtime, две версии
Blue-Green      blue[v1] ← трафик ;  green[v2] готов  →  переключили трафик
Canary          95% → v1 , 5% → v2  → смотрим метрики → 100% v2  (или откат)
```

| Стратегия | Когда | Требует |
|-----------|-------|---------|
| Recreate | Внутренние сервисы, допустим простой | Ничего |
| Rolling | Дефолт для stateless в кластере | Healthcheck, совместимость версий |
| Blue-Green | Нужен мгновенный откат | x2 ресурсов, управление трафиком |
| Canary | Рискованные изменения | Маршрутизация трафика + мониторинг |
| Feature flags | Разделить деплой и релиз | Поддержку флагов в коде |

**Smoke-тесты после деплоя** — обязательный шаг: 3-10 запросов, проверяющих, что сервис
поднялся, отвечает и видит зависимости. Без них «деплой прошёл успешно» ничего не значит.

## 8. Откат

Три уровня, от простого к сложному:

1. **Повторный деплой предыдущего артефакта** (`app:<предыдущий SHA>`) — 1-3 минуты,
   ничего не собираем. Это база, она должна работать всегда.
2. **Переключение трафика** (blue-green, canary) — секунды.
3. **Revert коммита + новый пайплайн** — медленно, но честно фиксирует историю.

Что должно быть готово заранее: предыдущий образ в registry (не удалён политикой очистки),
кнопка/джоба отката в пайплайне, совместимая схема БД, знание, кто и когда имеет право откатывать.

```yaml
rollback:prod:
  stage: deploy
  script:
    - ansible-playbook -i inventory/prod.ini deploy.yml -e "app_image=$CI_REGISTRY_IMAGE:$ROLLBACK_TAG"
  when: manual
  environment:
    name: production
    action: start
  rules:
    - if: $CI_COMMIT_BRANCH == $CI_DEFAULT_BRANCH
```

## 9. Скорость пайплайна

| Приём | Эффект |
|-------|--------|
| Кэш зависимостей (`cache`) | Минус минуты на каждой сборке |
| Кэш слоёв Docker (BuildKit + `--cache-from`) | Пересборка только изменившихся слоёв |
| `needs:` (DAG) | Джобы стартуют, не дожидаясь всей стадии |
| Параллельные джобы / `parallel:matrix` | Тесты в N потоков |
| `rules: changes` | Не гонять фронт-тесты при правке бэкенда |
| Разделение MR-пайплайна и main-пайплайна | Быстрая обратная связь в MR |
| Nightly для медленного (e2e, нагрузка) | Пайплайн не растёт до часа |
| `interruptible: true` + auto-cancel | Новый пуш отменяет старый пайплайн |
| Больше раннеров / `concurrent` | Очередь не растёт |

**Целевые ориентиры:** MR-пайплайн ≤ 10 минут, полный пайплайн до staging ≤ 20 минут.

## 10. Антипаттерны (что сразу видно на собесе)

| Антипаттерн | Чем плох |
|-------------|----------|
| Пересборка образа перед продом | Выкатываем не то, что тестировали |
| `latest` в деплое | Невоспроизводимо, откат невозможен |
| Секреты в `.gitlab-ci.yml` / в логах | Утечка, ротация всех ключей |
| Ручные шаги «Петя зайдёт и поправит» | Не масштабируется, не повторяемо |
| Один гигантский job на 300 строк | Не кэшируется, не параллелится, не отлаживается |
| Тесты, которые можно пропустить | Gate перестаёт быть gate'ом |
| Красный main как норма | CI перестаёт быть сигналом |
| Деплой = `scp` файлов на сервер | Нет версионирования и отката |
| Разные Dockerfile для dev и prod | Тестируем не то, что катим (лучше multi-stage target) |
| Нет smoke после деплоя | «Успешный деплой» ничего не гарантирует |

## 💼 Как это в DevOps

- «Спроектируй пайплайн» — самая частая **рабочая** задача: новый сервис в компании,
  нужно завести ему процесс доставки по общему стандарту.
- 80% времени уходит не на YAML, а на вопросы: где секреты, как мигрируем БД,
  как откатываемся, кто нажимает прод, что считаем quality gate.
- Хороший инженер начинает не с `image:`, а с рисунка стадий и списка окружений.
- Пайплайн — тоже продукт: его метрики (длительность, доля падений) стоит собирать
  и улучшать так же, как метрики сервиса.

## 📌 Шпаргалка

| Вопрос проекта | Решение по умолчанию |
|----------------|----------------------|
| Порядок стадий | lint → test → build → scan → integration → deploy → smoke |
| Тег артефакта | `$CI_COMMIT_SHORT_SHA` (+ SemVer на релизах) |
| Сборка образа в CI | Rootless BuildKit/buildah; dind (+buildx) — если есть свой privileged-раннер; kaniko — только legacy (архивирован в 2025) |
| Разница окружений | Переменные и секреты, не пересборка |
| Прод | `when: manual` + protected branch + protected variables |
| Деплой на сервер | Ansible-плейбук с образом по SHA |
| Деплой в k8s | Helm/kubectl или GitOps (Argo CD) |
| Миграции | Отдельный шаг, expand → deploy → contract |
| Откат | Повторный деплой предыдущего SHA, кнопкой |
| После деплоя | Smoke-тесты + уведомление + метрики |
| Ускорение | cache, needs, parallel, rules: changes, interruptible |

## 🧠 Что запомнить

1. Проектирование начинается со **стадий и окружений**, а не с синтаксиса.
2. Артефакт собирается один раз, тегируется SHA и продвигается неизменным.
3. Окружения отличаются **только конфигурацией**; staging должен быть прод-подобным.
4. Docker в пайплайне играет три роли: среда джобы, объект сборки, способ доставки.
5. Ansible даёт идемпотентный деплой и конфигурацию серверов; образ в плейбук передаётся
   параметром (по SHA).
6. Миграции БД — отдельный шаг и expand/contract; откат кода не должен требовать отката схемы.
7. Smoke-тесты после деплоя обязательны: без них «успешно» — это только «команда не упала».
8. Откат = повторный деплой предыдущего артефакта, минуты, без сборки.
9. Ускорение пайплайна — кэш, `needs`, параллель, `rules: changes`, разделение пайплайнов.
10. Прод всегда защищён: protected branch + protected variables + ручное подтверждение.
11. Любой ручной шаг — это будущий инцидент; выписывай их и автоматизируй.
12. Список антипаттернов из §10 — готовый скелет для ответа «что бы ты улучшил в нашем CI».

### Блок A. Теория

**A1.** Назови стадии референсного пайплайна по порядку и обоснуй порядок двумя правилами.

<details><summary>Ответ</summary>

lint → test → build → scan → integration → deploy(dev→staging→prod) → smoke.
Правила: (1) дешёвое и быстрое раньше дорогого и долгого; (2) всё, что требует артефакта,
идёт после сборки, а сборка — ровно одна.

</details>

**A2.** Почему сканирование образа стоит после сборки, а не до?

<details><summary>Ответ</summary>

Сканировать нужно **то, что поедет в прод**: собранный образ со всеми слоями,
базовым образом и установленными пакетами. До сборки можно проверить только исходники
и зависимости (SCA), но не итоговый образ.

</details>

**A3.** Что делает стадия `integration` и чем она отличается от `test`?

<details><summary>Ответ</summary>

`test` — быстрые unit-тесты без внешних зависимостей (моки). `integration` поднимает
реальные зависимости (БД, кэш, очередь — в GitLab через `services`) и проверяет работу
компонентов вместе: SQL, миграции, сериализацию, контракт с соседними сервисами.

</details>

**A4.** Чем dev, staging и prod отличаются друг от друга (данные, деплой, секреты, доступ)?

<details><summary>Ответ</summary>

dev — синтетические данные, автодеплой на каждый push, тестовые секреты, доступ
у всех разработчиков. staging — прод-подобная структура и обезличенные данные, автодеплой
по мержу в main, свои (не прод) секреты, доступ у команды и QA. prod — реальные данные,
ручное подтверждение, protected-секреты, доступ ограничен.

</details>

**A5.** Что такое review app / динамическое окружение? Плюсы и риски.

<details><summary>Ответ</summary>

Временное окружение, поднимаемое на каждый MR и удаляемое при его закрытии
(`environment.on_stop`, `auto_stop_in`). Плюсы: ревьюер видит фичу вживую, тесты на изоляции.
Риски: расход ресурсов, «забытые» стенды, утечка данных, если в них копируют прод-данные.

</details>

**A6.** В чём именно staging должен быть похож на прод? Назови пять параметров.

<details><summary>Ответ</summary>

Версия и конфигурация БД; версия рантайма/базового образа; топология сети и
балансировщик (TLS, таймауты); переменные и способ их подачи; порядок величины данных
и нагрузки; ОС/ядро и лимиты ресурсов.

</details>

**A7.** Перечисли три роли Docker в CI/CD и объясни каждую одним предложением.

<details><summary>Ответ</summary>

(1) Среда выполнения джобы — чистый контейнер на каждый запуск; (2) объект сборки —
пайплайн собирает и пушит образ приложения; (3) способ доставки — на сервере запускается
тот же образ.

</details>

**A8.** Сравни dind, проброс docker.sock и сборку без демона (rootless BuildKit/buildah;
что стало с kaniko): как работают, чем рискованны, что выбрать для раннера в Kubernetes.

<details><summary>Ответ</summary>

dind — внутри джобы поднимается отдельный докер-демон (`services: docker:dind`),
нужен privileged-режим, подходит для своих раннеров. Проброс `docker.sock` — джоба работает
с демоном хоста: быстро, но это фактически root-доступ к хосту и соседним сборкам.
Сборка без демона — rootless BuildKit (`buildctl-daemonless.sh`) или buildah: без privileged
(хотя rootless-режиму нужны послабленные seccomp/AppArmor), дефолт для Kubernetes-раннеров
и shared-инфраструктуры. Kaniko работал так же, но upstream архивирован в 2025 (жив только
форк Chainguard с security-фиксами) — это legacy.

</details>

**A9.** Какие две задачи решает Ansible в CI/CD? Как передать в плейбук версию образа?

<details><summary>Ответ</summary>

Подготовка серверов (provisioning: пакеты, пользователи, firewall, nginx, сертификаты)
и деплой приложения. Версия образа передаётся extra-var: `-e "app_image=$CI_REGISTRY_IMAGE:$CI_COMMIT_SHORT_SHA"`.

</details>

**A10.** Почему Ansible лучше, чем `ssh user@host "docker run ..."`? Три аргумента.

<details><summary>Ответ</summary>

(1) Идемпотентность — повторный запуск не ломает состояние и показывает,
что реально изменилось; (2) масштаб — inventory позволяет применить то же самое к 50 хостам;
(3) структура — роли, переменные окружений, шаблоны конфигов, `--check` для сухого прогона,
и всё это версионируется в git.

</details>

**A11.** Объясни подход expand/contract для миграций БД на примере переименования колонки.

<details><summary>Ответ</summary>

Expand: добавить новую колонку `username`, писать в обе. Deploy: код пишет в обе
и читает из новой (с fallback на старую). Backfill: перенести данные фоном.
Contract: следующим релизом убрать запись в старую колонку и удалить её.
Каждый шаг обратим и не ломает предыдущую версию кода.

</details>

**A12.** Почему при rolling-обновлении миграция обязана быть совместимой вперёд?

<details><summary>Ответ</summary>

При rolling какое-то время одновременно работают старая и новая версия кода на одной
БД. Если миграция удаляет/переименовывает то, что использует старый код, — часть запросов
падает. Поэтому схема должна поддерживать обе версии.

</details>

**A13.** Опиши четыре стратегии выката и скажи, что нужно для canary.

<details><summary>Ответ</summary>

Recreate (гасим старое, поднимаем новое — даунтайм), Rolling (по одному инстансу —
нужны healthcheck и совместимость), Blue-Green (два окружения, переключение трафика —
нужны двойные ресурсы и управление трафиком), Canary (часть трафика на новую версию —
нужны маршрутизация по весам и мониторинг с понятными метриками отката).

</details>

**A14.** Что такое smoke-тест после деплоя? Приведи три конкретные проверки для веб-сервиса.

<details><summary>Ответ</summary>

Минимальная проверка, что задеплоенное реально живо: (1) `GET /health` = 200;
(2) `GET /version` возвращает ожидаемый SHA; (3) ключевой пользовательский сценарий
(например, `GET /api/items` = 200 и непустой ответ, или запись в БД проходит).

</details>

**A15.** Опиши три способа отката. Какой должен работать всегда и за сколько минут?

<details><summary>Ответ</summary>

(1) Повторный деплой предыдущего артефакта — должен работать всегда, 1-3 минуты;
(2) переключение трафика (blue-green/canary) — секунды; (3) revert коммита и новый пайплайн —
минуты-десятки минут, зато чинит историю.

</details>

**A16.** Почему политика очистки registry напрямую влияет на возможность отката?

<details><summary>Ответ</summary>

Откат — это деплой **предыдущего** образа. Если политика очистки удалила его
из registry, откатываться нечем: придётся пересобирать (медленно и не гарантирует
идентичность). Поэтому продовые теги исключают из очистки/хранят дольше.

</details>

**A17.** Назови семь способов ускорить пайплайн.

<details><summary>Ответ</summary>

Кэш зависимостей; кэш слоёв Docker; `needs`/DAG; параллельные джобы и `parallel:matrix`;
`rules: changes`; разделение MR-пайплайна и полного пайплайна; вынос медленного в nightly;
`interruptible` + auto-cancel; больше раннеров/`concurrent`.

</details>

**A18.** Что такое quality gate? Что произойдёт с процессом, если gate можно «пропустить кнопкой»?

<details><summary>Ответ</summary>

Автоматический порог, блокирующий продвижение (покрытие, уязвимости, ошибки линтера).
Если gate можно обойти кнопкой без последствий, он перестаёт быть гарантией: сначала обходят
«в виде исключения», потом всегда, и качество возвращается к состоянию «до».

</details>

**A19.** Перечисли пять антипаттернов пайплайна и объясни вред каждого.

<details><summary>Ответ</summary>

Пересборка перед продом (катим не то, что тестировали); `latest` в деплое
(невоспроизводимость, нет отката); секреты в репозитории/логах (утечка); ручные шаги
(не повторяемо, зависит от человека); тесты, которые можно пропустить (gate не работает);
красный main как норма (CI не сигнал); деплой через `scp` (нет версий и отката).

</details>

### Блок B. «Что не так с этим фрагментом»

**B1.**
```yaml
deploy:prod:
  script:
    - docker build -t myapp:latest .
    - docker push myapp:latest
    - ssh root@prod "docker pull myapp:latest && docker restart app"
```

<details><summary>Ответ</summary>

Сразу несколько проблем: сборка происходит **в джобе деплоя** (нарушен build once);
тег `latest` (невоспроизводимо, откат невозможен); `ssh root@` (работа под root, вероятно
с паролем/ключом без ограничений); `docker restart` не подтянет новый образ корректно
(нужно пересоздание контейнера); нет проверки после деплоя. Правильно: собрать в `build`,
тегировать SHA, деплоить плейбуком/скриптом с конкретным тегом, добавить smoke.

</details>

**B2.**
```yaml
deploy:
  script:
    - echo "DB_PASSWORD=SuperSecret123" >> .env
    - scp .env prod:/opt/app/.env
```

<details><summary>Ответ</summary>

Секрет в открытом виде в конфиге пайплайна (в git!) — это утечка. Плюс `.env`
складывается в артефакт джобы. Правильно: переменная в CI/CD Variables (masked + protected),
подстановка на целевом хосте шаблоном Ansible с правами 600, а лучше — из Vault.

</details>

**B3.**
```yaml
test:
  script:
    - pytest || true
```

<details><summary>Ответ</summary>

`|| true` превращает тесты в декорацию: джоба зелёная при любых падениях.
Если тесты нестабильны — чинить тесты, а не прятать результат. Временный компромисс —
`allow_failure: true` (видно, что джоба красная, но пайплайн продолжается), но с тикетом и сроком.

</details>

**B4.**
```yaml
build:
  script:
    - docker build -f Dockerfile.dev -t app:dev .    # для dev
    - docker build -f Dockerfile.prod -t app:prod .  # для prod
```

<details><summary>Ответ</summary>

Два разных Dockerfile означают, что тестируется один образ, а в прод едет другой.
Правильно — один Dockerfile с multi-stage и разными `target`, либо один и тот же
прод-образ, а dev-удобства подключать через compose/переменные.

</details>

**B5.**
```yaml
migrate:
  script:
    - alembic upgrade head
    - kubectl set image deploy/app app=registry/app:$CI_COMMIT_SHORT_SHA
  # (миграция удаляет старую колонку)
```

<details><summary>Ответ</summary>

Деструктивная миграция (удаление колонки) применяется одновременно с выкатом:
при rolling старый код сломается, а откат кода станет невозможен (схема уже новая).
Нужно expand/contract и отдельный шаг миграции.

</details>

**B6.**
```yaml
deploy:staging:
  script:
    - ansible-playbook deploy.yml
  variables:
    ANSIBLE_HOST_KEY_CHECKING: "False"
```

<details><summary>Ответ</summary>

Отключение проверки ключа хоста открывает путь к MITM: джоба подключится к
подменённому хосту и передаст ему секреты. Правильно — `ssh-keyscan` при первичной настройке
и хранение `known_hosts` в переменной/репозитории.

</details>

### Блок C. Практика

#### C1. 🔑 Спроектируй пайплайн для своего приложения (главное задание)

Файл `docs/pipeline.md` в репозитории приложения. Обязательные разделы:

1. **Схема** стадий (ASCII или диаграмма) с временем каждой.
2. **Триггеры:** что запускается на MR, что на push в main, что по тегу, что по расписанию.
3. **Артефакт:** что собираем, как тегируем, где храним, сколько храним.
4. **Окружения:** таблица dev/staging/prod (деплой, данные, секреты, кто имеет доступ).
5. **Quality gates** с конкретными порогами.
6. **Миграции БД:** где в пайплайне, как откатываются.
7. **Откат:** процедура, время, кто нажимает.
8. **Уведомления:** куда падает алерт о красном пайплайне.
9. **Что специально НЕ делаем** и почему (например, e2e на каждый коммит).

<details><summary>Ответ</summary>

Ориентир для самопроверки: в документе есть **конкретные цифры** (время, пороги,
сроки хранения) и явно описан откат. Если раздел «Откат» звучит как «пересоберём предыдущий
коммит» — проект ещё не спроектирован.

</details>

#### C2. Посчитай бюджет времени
Расставь целевое время каждой стадии так, чтобы MR-пайплайн укладывался в 10 минут.
Что вынесешь из MR-пайплайна в main/nightly?

<details><summary>Ответ</summary>

Типовой бюджет MR-пайплайна: lint 0:30, unit 3:00, build 3:00, scan 1:30,
integration 2:00 (только быстрые) ≈ 10 минут. В main/nightly выносятся: полные
интеграционные, e2e, нагрузочные, скан с полной базой CVE, сборка multi-arch.

</details>

#### C3. Впиши Docker
Опиши (или напиши черновик джобы) сборку образа тремя способами — dind, rootless BuildKit (или buildah), buildx —
и выбери один для своего стенда с обоснованием.

<details><summary>Ответ</summary>

Ориентир выбора: свой раннер на VM и нужен полный докер → dind (`privileged`)
или buildx; раннер в Kubernetes/общая инфраструктура → rootless BuildKit или buildah
(без privileged; kaniko архивирован в 2025);
нужна максимальная скорость и внешний кэш → buildx с `--cache-to/--cache-from` в registry.

</details>

#### C4. Впиши Ansible
Напиши плейбук `deploy.yml`, который:
- логинится в registry,
- запускает контейнер по тегу из переменной `app_image`,
- пробрасывает порт только на 127.0.0.1,
- задаёт healthcheck и `restart_policy`,
- и джобу, которая его вызывает, передавая `$CI_COMMIT_SHORT_SHA`.
Проверь идемпотентность: второй прогон не должен ничего менять.

<details><summary>Ответ</summary>

Критерий приёмки — второй прогон плейбука выводит `changed=0`. Если контейнер
пересоздаётся каждый раз при неизменном образе, значит использован `recreate: true`
безусловно — стоит управлять этим через сравнение образа/тега.

</details>

#### C5. Миграция без даунтайма
Задача: переименовать колонку `user_name` → `username` в работающем сервисе.
Распиши по релизам (expand → deploy → backfill → contract), что происходит в каждом
и что будет, если откатить код между шагами.

<details><summary>Ответ</summary>

Expand: добавили `username`, код пишет в обе колонки, читает `user_name`.
Deploy: код читает `username` с fallback. Backfill: скопировали данные. Contract: убрали
`user_name`. Откат безопасен на всех шагах, кроме периода после contract — поэтому contract
делают, когда уверены, что старый код больше не вернётся.

</details>

#### C6. Smoke-тесты
Напиши скрипт `smoke.sh`, который после деплоя проверяет: `/health` = 200,
`/version` возвращает ожидаемый SHA, главная страница отдаёт 200 за < 1 с.
Скрипт должен возвращать ненулевой код при любой неудаче.

<details><summary>Ответ</summary>

Ключевое: `set -e`, проверка HTTP-кода (`curl -fsS -o /dev/null -w '%{http_code}'`),
сравнение версии с `$CI_COMMIT_SHORT_SHA`, таймаут и ретраи на старт сервиса,
ненулевой exit при любой неудаче — иначе джоба останется зелёной.

</details>

#### C7. Процедура отката
Опиши и, если есть стенд, выполни откат: узнать текущую версию в проде,
найти предыдущий тег, задеплоить его, проверить smoke. Засеки время.

<details><summary>Ответ</summary>

Хороший результат — меньше 5 минут от решения до подтверждённого отката,
и ни одной команды сборки в процедуре.

</details>

#### C8. Найди узкое место
Возьми любой существующий пайплайн (свой или пример из интернета) и выпиши три самых
долгих шага + что с ними сделать.

<details><summary>Ответ</summary>

Типичные узкие места: установка зависимостей без кэша, сборка образа без кэша слоёв,
последовательные стадии там, где подошёл бы `needs`, e2e в каждом MR.

</details>

### Блок D. Инциденты

**D1.** Деплой прошёл «успешно», но пользователи видят 502. Пайплайн зелёный.
Чего не хватает в пайплайне и как это добавить?

<details><summary>Ответ</summary>

Нет проверки после деплоя: нужны smoke-тесты в отдельной джобе (health, версия,
ключевой сценарий), а также проверка готовности (readiness) и автоматический откат
при неуспехе. «Команда деплоя завершилась без ошибки» ≠ «сервис работает».

</details>

**D2.** Прод упал после релиза. В registry нет предыдущего образа — политика очистки удалила
всё старше 7 дней. Как откатываться сейчас и что менять в политике?

<details><summary>Ответ</summary>

Сейчас — пересобрать предыдущий коммит (медленно, без гарантии идентичности)
либо откатиться на образ, который остался на самом сервере (если не удалён).
Менять: исключить из очистки теги, задеплоенные на прод/staging, хранить последние N
релизных образов и все образы, на которые ссылаются окружения.

</details>

**D3.** Rolling-обновление: половина подов на v2, половина на v1. Пользователи получают
случайные ошибки 500 при записи. Что произошло с точки зрения миграций?

<details><summary>Ответ</summary>

Миграция была несовместима вперёд/назад: новая схема ломает старый код (или наоборот).
При rolling обе версии работают одновременно, поэтому изменения схемы обязаны быть
аддитивными (expand), а удаление — отдельным поздним шагом.

</details>

**D4.** Джоба деплоя иногда падает с `Host key verification failed`.
Коллега предлагает `ANSIBLE_HOST_KEY_CHECKING=False`. Почему это плохо и как правильно?

<details><summary>Ответ</summary>

Отключение проверки ключа = разрешение подключаться к любому хосту, включая
подменённый (MITM) — а джоба несёт с собой секреты. Правильно: один раз собрать
`ssh-keyscan -H $HOST` и хранить `known_hosts` в переменной/репо, обновлять при смене хоста.

</details>

**D5.** На staging всё работает, на проде приложение стартует и сразу падает
с `KeyError: 'REDIS_URL'`. Что не так в проектировании окружений?

<details><summary>Ответ</summary>

Окружения расходятся по набору переменных: staging имеет `REDIS_URL`, прод — нет.
Нужно: единый список обязательных переменных, проверка их наличия на старте приложения
(fail fast с понятным сообщением), одинаковый способ подачи переменных во всех окружениях,
и джоба, валидирующая конфигурацию перед деплоем.

</details>

**D6.** Пайплайн вырос до 42 минут, разработчики просят отключить integration-тесты.
Составь план оптимизации на 5 пунктов, не удаляя проверки.

<details><summary>Ответ</summary>

(1) Профилировать джобы и найти три самых долгих; (2) кэш зависимостей и слоёв;
(3) `needs` вместо строгих стадий; (4) распараллелить тесты (`parallel`/matrix);
(5) вынести e2e и полный скан в nightly, в MR оставить быстрое подмножество;
(6) `interruptible` + auto-cancel устаревших пайплайнов; (7) добавить раннеров.

</details>

**D7.** Два MR одновременно задеплоились на один dev-стенд и перетёрли друг друга.
Как решать (два механизма GitLab CI)?

<details><summary>Ответ</summary>

`resource_group` (сериализация джоб деплоя на одно окружение) и
`environment` + отмена устаревших деплоев; дополнительно — динамические окружения
на каждый MR, чтобы стенды не пересекались.

</details>

**D8.** После неудачного прод-деплоя выяснилось, что миграция уже применилась,
а код откатили. Приложение не стартует. Как надо было спроектировать?

<details><summary>Ответ</summary>

Нужно было разделить миграцию и деплой, делать только совместимые (expand) миграции
и держать правило «откат кода не требует отката схемы». Вариант для необратимых случаев —
отдельный релиз contract, выполняемый только после подтверждения стабильности.

</details>

**D9.** Джоба сборки образа занимает 9 минут, потому что каждый раз ставит зависимости
заново. Что проверить в Dockerfile и что настроить в CI?

<details><summary>Ответ</summary>

В Dockerfile: зависимости должны ставиться в отдельном слое **до** копирования кода
(`COPY requirements.txt` → `pip install` → `COPY . .`), иначе кэш инвалидируется на каждом
коммите; использовать multi-stage и `.dockerignore`. В CI: BuildKit с `--cache-from`
на предыдущий образ из registry или кэш билдера.

</details>

**D10.** Команда хочет деплоить на прод из любой ветки «чтобы быстрее чинить».
Какие риски и что предложить взамен?

<details><summary>Ответ</summary>

Риски: обход ревью и проверок, доступ прод-секретов из любой ветки, деплой кода,
которого нет в main, невоспроизводимость. Взамен: быстрый hotfix-процесс (короткая ветка
от main → ускоренный пайплайн → manual-деплой), protected-переменные, право нажимать
кнопку у дежурного, и отрепетированный откат как основной способ «чинить быстро».

</details>

### Блок E. Вопросы с собеседования

**1.** Как бы ты построил идеальный пайплайн? (топ-1 вопрос раздела)

<details><summary>Ответ</summary>

См. каркас в конспекте §«Референсный пайплайн» + окружения, секреты, миграции, откат,
smoke, уведомления. Структура ответа: триггеры → стадии → артефакт → окружения →
gates → деплой → проверка → откат → метрики.

</details>

**2.** Какие стадии обязательны и почему именно в таком порядке?

<details><summary>Ответ</summary>

lint/test/build/scan/integration/deploy/smoke; порядок задаётся стоимостью проверки
и зависимостью от артефакта.

</details>

**3.** Как в пайплайн интегрируется Docker?

<details><summary>Ответ</summary>

Как среда выполнения джоб, как объект сборки (dind/buildx или rootless BuildKit/buildah + push в registry)
и как способ доставки (тот же образ запускается в окружении).

</details>

**4.** Как в пайплайн интегрируется Ansible?

<details><summary>Ответ</summary>

Provisioning серверов и деплой приложения; вызывается джобой, версия образа передаётся
параметром; даёт идемпотентность, inventory и роли.

</details>

**5.** Как выкатывать миграции БД без даунтайма?

<details><summary>Ответ</summary>

Expand/contract, отдельный шаг миграции, совместимость вперёд, backfill фоном,
долгие блокирующие операции — вне пайплайна, в окно.

</details>

**6.** Какие стратегии деплоя знаешь и когда какую применять?

<details><summary>Ответ</summary>

Recreate/Rolling/Blue-Green/Canary (+ feature flags); выбор по допустимому даунтайму,
ресурсам, качеству мониторинга и риску изменения.

</details>

**7.** Как устроен откат в твоём процессе?

<details><summary>Ответ</summary>

Повторный деплой предыдущего иммутабельного тега кнопкой; артефакты хранятся;
схема БД совместима; после отката — smoke; всё занимает минуты.

</details>

**8.** Чем отличаются окружения, если артефакт один?

<details><summary>Ответ</summary>

Только конфигурацией: переменные, секреты, параметры деплоя, домены и ресурсы.

</details>

**9.** Как ускорить длинный пайплайн?

<details><summary>Ответ</summary>

Кэш, параллель, `needs`, `rules: changes`, разделение пайплайнов, nightly для медленного,
больше раннеров, отмена устаревших пайплайнов.

</details>

**10.** Какие антипаттерны в CI/CD видел и как их исправлял?

<details><summary>Ответ</summary>

Примеры из §10 конспекта: пересборка перед продом, `latest`, секреты в репо,
ручные шаги, гигантские джобы, отсутствие smoke и отката.

</details>
