# 10. Jenkins: архитектура и основы

> Роадмап → 4. CI/CD → Инструменты → Jenkins → **Минимум**:
> «Понимать архитектуру: Jenkins Master + Agent. Запустить shell-команду, посмотреть логи.
> Понять что такое build trigger (ручной, по webhook, по расписанию)».
> **После темы ты умеешь:** поднять Jenkins, объяснить controller/agent, создать джобу,
> настроить триггеры и прочитать лог сборки.

---

## 1. Почему Jenkins вообще нужно знать

Из роадмапа: *«Jenkins чаще можно встретить в старых проектах, либо в закрытых
инфраструктурах, свойственно для банков»*.

| | Jenkins | GitLab CI |
|---|---|---|
| Возраст/зрелость | 2011 (форк Hudson, 2004) | 2015 |
| Модель | Отдельный сервер + плагины (1800+) | Встроен в GitLab, конфиг в репозитории |
| Конфигурация | UI + `Jenkinsfile` (Groovy DSL) | `.gitlab-ci.yml` (YAML) |
| Порог входа | Выше: плагины, Groovy, обслуживание | Ниже |
| Гибкость | Практически безграничная | Достаточная для 95% задач |
| Обслуживание | Ты админишь сервер, плагины, агентов | Обслуживает GitLab |
| Где встретишь | Банки, телеком, энтерпрайз, легаси | Новые проекты, стартапы, почти всё новое |

**Вывод для собеса:** Jenkins — не «устаревший хлам», а инструмент с другой нишей:
максимальная гибкость и независимость от системы контроля версий (он умеет работать
с любым Git, SVN, чем угодно), ценой обслуживания.

## 2. Архитектура: Controller + Agent

```text:no-line-numbers
        ┌──────────────────────────────────────────────┐
        │           Jenkins CONTROLLER (master)        │
        │  • веб-интерфейс и REST API                  │
        │  • хранит конфигурацию джоб и историю сборок │
        │  • планирует сборки, распределяет по агентам │
        │  • плагины, учётные данные (credentials)     │
        │  • JENKINS_HOME — всё состояние здесь        │
        └───────────┬───────────────┬──────────────────┘
                    │               │   (JNLP/inbound или SSH)
        ┌───────────▼──────┐ ┌──────▼───────────┐
        │   AGENT linux-1  │ │  AGENT windows-1 │  ← здесь реально выполняются шаги
        │   label: linux   │ │  label: windows  │
        │   executors: 4   │ │  executors: 2    │
        └──────────────────┘ └──────────────────┘
```

| Термин | Что это |
|--------|---------|
| **Controller** | Мозг: UI, планировщик, конфигурация, история. Терминология обновлена: раньше «master» |
| **Agent (node)** | Машина, выполняющая сборки. Подключается по SSH (outbound с контроллера) или JNLP (inbound от агента) |
| **Executor** | Слот параллельного выполнения на агенте: 4 executor'а = 4 сборки одновременно |
| **Label** | Метка агента — аналог тегов раннера в GitLab (`agent { label 'linux && docker' }`) |
| **Workspace** | Рабочий каталог сборки на агенте (**переиспользуется** между сборками!) |
| **JENKINS_HOME** | Каталог со всем состоянием контроллера: джобы, плагины, креды, история |

> ⚠️ Главное отличие от GitLab Runner: workspace **не чистится автоматически**.
> Между сборками остаются файлы — источник «загадочных» успехов и падений.
> Поэтому в пайплайнах пишут `cleanWs()` или используют docker-агентов.

**Best practice:** на контроллере сборки **не запускают** (executors = 0) —
он занимается только координацией. Это и вопрос безопасности, и стабильности.

## 3. Установка (учебный стенд — в Docker)

```bash
docker run -d --name jenkins --restart unless-stopped \
  -p 8080:8080 -p 50000:50000 \
  -v jenkins_home:/var/jenkins_home \
  jenkins/jenkins:lts-jdk17

# пароль первичной настройки
docker exec jenkins cat /var/jenkins_home/secrets/initialAdminPassword
```
- `8080` — веб-интерфейс, `50000` — порт для inbound-агентов (JNLP).
- Том `jenkins_home` — **всё** состояние; без него потеряешь конфигурацию.
- Дальше: Install suggested plugins → создать администратора.

Продакшен-варианты: пакет на VM (`apt install jenkins`), Helm-чарт в Kubernetes,
конфигурация через **JCasC** (Jenkins Configuration as Code, YAML) вместо кликов в UI.

```bash
# бэкап — это просто бэкап JENKINS_HOME
docker run --rm -v jenkins_home:/data -v $PWD:/backup alpine \
  tar czf /backup/jenkins-$(date +%F).tar.gz -C /data .
```

## 4. Типы джоб

| Тип | Когда использовать |
|-----|--------------------|
| **Freestyle project** | Простые задачи, «кликом»; легаси, но встречается часто |
| **Pipeline** | ⭐ Основной современный тип: `Jenkinsfile` в репозитории |
| **Multibranch Pipeline** | Автоматически заводит пайплайн для каждой ветки/PR (тема 12) |
| **Folder** | Группировка джоб, разграничение прав |
| **Organization Folder** | Сканирует все репозитории организации (GitHub/GitLab) |

**Правило:** новое пишем как Pipeline с `Jenkinsfile` в репозитории —
это «pipeline as code», аналог `.gitlab-ci.yml`. Freestyle нужно уметь читать,
потому что в старых проектах его много.

## 5. Первая джоба: shell-команда и логи

**Freestyle:**
1. New Item → Freestyle project → имя.
2. Build Steps → Execute shell:
```bash
echo "Сборка #$BUILD_NUMBER на $NODE_NAME"
echo "Ветка: $GIT_BRANCH"
uname -a
whoami && pwd && ls -la
```
3. Save → Build Now.
4. Логи: клик на номер сборки → **Console Output**.

**Pipeline (то же самое, но как код):**
```groovy
pipeline {
    agent any
    stages {
        stage('Hello') {
            steps {
                sh '''
                    echo "Сборка #${BUILD_NUMBER} на ${NODE_NAME}"
                    uname -a
                    whoami && pwd
                '''
            }
        }
    }
}
```

### Как читать лог
```text:no-line-numbers
Started by user admin                          ← кто/что запустило
Running on agent-1 in /home/jenkins/workspace/myjob   ← где и в каком workspace
[Pipeline] stage / [Pipeline] sh               ← шаги пайплайна
+ echo Сборка #12                              ← команды с префиксом "+" (set -x)
...
Finished: SUCCESS | FAILURE | UNSTABLE | ABORTED
```

| Статус | Значение |
|--------|----------|
| `SUCCESS` | Всё прошло |
| `FAILURE` | Шаг вернул ненулевой код / упал этап |
| `UNSTABLE` | Сборка прошла, но есть проблемы (например, упавшие тесты, `unstable()`) |
| `ABORTED` | Отменена вручную или по таймауту |
| `NOT_BUILT` | Этап пропущен |

## 6. Build triggers — чем запускается сборка

| Триггер | Где настраивается | Смысл |
|---------|-------------------|-------|
| **Вручную** | Кнопка Build Now | Разовый запуск |
| **По расписанию** | `Build periodically` | Cron-синтаксис Jenkins |
| **Опрос SCM** | `Poll SCM` | Jenkins сам проверяет, не появились ли коммиты |
| **Webhook от Git** | `GitHub hook trigger` / GitLab plugin | ⭐ Правильный способ: git сам сообщает о пуше |
| **После другой джобы** | `Build after other projects are built` | Цепочки джоб |
| **Через API/токен** | Remote trigger с токеном | Внешние системы |
| **Upstream/downstream** | `build job: 'other'` в пайплайне | Из кода пайплайна |

### Cron-синтаксис Jenkins
```text:no-line-numbers
MINUTE HOUR DOM MONTH DOW

H/15 * * * *      # каждые 15 минут (H = «размазать» нагрузку по хэшу джобы)
H 2 * * *         # раз в сутки около 02:00
H 9 * * 1-5       # по будням утром
@daily            # алиасы: @hourly, @daily, @weekly, @monthly
```
> ⭐ **`H` вместо конкретной минуты** — важная деталь Jenkins: иначе все джобы стартуют
> ровно в 00:00 и кладут контроллер. `H` даёт стабильное, но распределённое время.

### Webhook vs Poll SCM
```text:no-line-numbers
Poll SCM:   Jenkins ──каждую минуту──► Git «есть новое?»   ❌ нагрузка, задержка
Webhook:    Git ──push событие──► Jenkins «обнови»          ✅ мгновенно, без опросов
```
Webhook требует, чтобы Jenkins был доступен для GitLab/GitHub (или использовался
плагин с исходящим подключением). В закрытых контурах иногда остаётся Poll SCM —
это одна из причин, по которой его всё ещё встречают.

## 7. Подключение агента (кратко)

**По SSH (outbound с контроллера):**
Manage Jenkins → Nodes → New Node → Permanent Agent:
- Remote root directory: `/home/jenkins`
- Labels: `linux docker`
- Launch method: *Launch agents via SSH* + хост и credentials (SSH-ключ).

**Inbound (JNLP, агент сам подключается — удобно за NAT):**
```bash
docker run -d --restart always --name jenkins-agent \
  -e JENKINS_URL=http://jenkins:8080 \
  -e JENKINS_AGENT_NAME=agent-1 \
  -e JENKINS_SECRET=<секрет из UI> \
  -e JENKINS_AGENT_WORKDIR=/home/jenkins/agent \
  jenkins/inbound-agent:latest
```

**Docker-агенты:** плагин Docker/Kubernetes поднимает контейнер (или под) на каждую сборку —
это ближе всего к модели GitLab docker-executor и решает проблему грязного workspace
(тема 12).

## 8. Плагины — и сила, и боль Jenkins

Типовой минимум: Git, Pipeline (workflow-aggregator), Credentials Binding, Docker Pipeline,
Blue Ocean (устаревает), Configuration as Code (JCasC), Timestamper, Workspace Cleanup,
AnsiColor, Slack/Telegram Notification, Role-based Authorization Strategy.

Риски:
- обновление плагина ломает пайплайны (нет строгого версионирования совместимости);
- уязвимости в плагинах — частый источник CVE;
- «плагин на каждый чих» превращает контроллер в неподдерживаемый.

**Практика:** ставить минимум необходимого, фиксировать версии, держать конфигурацию
в JCasC, обновлять планово и с бэкапом `JENKINS_HOME`.

---

## 9. Безопасность (минимум, который спрашивают)

1. Контроллер не должен выполнять сборки (executors = 0).
2. Матрица прав / Role-based Authorization: разработчики не должны иметь `Administer`
   и доступ к Script Console.
3. **Script Console** (`/script`) = выполнение Groovy на контроллере = полный доступ.
4. Креды — только в **Credentials**, никогда в тексте джобы.
5. CSRF protection включён, агенты подключаются по защищённым каналам.
6. Регулярные обновления ядра и плагинов, бэкап `JENKINS_HOME`.

## 💼 Как это в DevOps

- Jenkins в компании — это **сервер, который кто-то админит**: обновления, плагины,
  бэкапы, агенты, диск. В GitLab CI этой работы нет — её делает сам GitLab.
- Типичная задача на работе: «перевести легаси freestyle-джобы в `Jenkinsfile`»
  и «поднять агентов в докере вместо статических машин».
- На собесе в банк спросят именно про архитектуру (controller/agent), credentials,
  `Jenkinsfile` и shared libraries — см. темы 11-12.
- Частый инцидент: закончилось место в `JENKINS_HOME` (старые сборки и артефакты) —
  лечится политикой хранения сборок (`buildDiscarder`).

## 📌 Шпаргалка

| Понятие | Jenkins | Аналог в GitLab CI |
|---------|---------|--------------------|
| Сервер | Controller | GitLab |
| Исполнитель | Agent + executors | Runner + concurrent |
| Метка исполнителя | Label | Tag |
| Конфиг пайплайна | `Jenkinsfile` | `.gitlab-ci.yml` |
| Секреты | Credentials | CI/CD Variables |
| Этап | `stage` | `stage` |
| Шаг | `steps { sh '...' }` | `script:` |
| Ручной шаг | `input` | `when: manual` |
| Рабочий каталог | Workspace (переиспользуется!) | Чистая копия на каждую джобу |
| Хранилище состояния | `JENKINS_HOME` | — |

```groovy
// минимальный Jenkinsfile
pipeline {
    agent any
    triggers { cron('H 2 * * *') }
    stages {
        stage('Build') { steps { sh 'make build' } }
    }
    post { always { cleanWs() } }
}
```

## 🧠 Что запомнить

1. Jenkins = Controller (координация, UI, состояние) + Agents (выполнение сборок).
2. На контроллере сборки не запускают: executors = 0.
3. `JENKINS_HOME` — всё состояние; бэкап Jenkins = бэкап этого каталога.
4. Workspace на агенте **переиспользуется** — отсюда `cleanWs()` и docker-агенты.
5. Label в Jenkins = tag в GitLab: так выбирается, где выполнять.
6. Новое пишем как Pipeline с `Jenkinsfile` в репозитории, freestyle — только читать.
7. Триггеры: вручную, cron, Poll SCM, webhook, по другой джобе, по API.
8. В cron Jenkins используй `H` — иначе все джобы стартуют одновременно.
9. Webhook лучше Poll SCM: мгновенно и без лишней нагрузки.
10. Плагины — главная сила и главный риск: минимум, фиксация версий, бэкап перед обновлением.
11. Script Console — полный доступ к контроллеру: права выдавать аккуратно.
12. Статусы: SUCCESS / FAILURE / UNSTABLE / ABORTED — UNSTABLE это «прошло, но с проблемами».

### Блок A. Теория

**A1.** Из чего состоит архитектура Jenkins? Что делает контроллер, а что агент?

<details><summary>Ответ</summary>

Контроллер: веб-интерфейс и API, хранение конфигурации джоб и истории сборок,
планирование, распределение задач по агентам, плагины, credentials. Агент: машина
(VM/контейнер/под), на которой реально выполняются шаги сборки.

</details>

**A2.** Что такое executor и label? Как они соотносятся с понятиями GitLab Runner?

<details><summary>Ответ</summary>

Executor — слот параллельного выполнения на агенте (сколько сборок агент тянет
одновременно); label — метка агента для выбора, где выполнять (`agent { label 'linux' }`).
В GitLab это `concurrent`/`limit` у раннера и теги соответственно.

</details>

**A3.** Что лежит в `JENKINS_HOME` и почему это самый важный каталог?

<details><summary>Ответ</summary>

Конфигурация всех джоб (`jobs/`), плагины (`plugins/`), учётные данные,
история сборок и артефакты, настройки безопасности, ключи агентов. Потеря каталога =
потеря Jenkins; бэкап Jenkins = бэкап `JENKINS_HOME`.

</details>

**A4.** Почему на контроллере рекомендуется ставить 0 executors?

<details><summary>Ответ</summary>

Безопасность (сборка на контроллере имеет доступ к `JENKINS_HOME`, кредам и
конфигурации) и стабильность (тяжёлая сборка не должна ронять UI и планировщик).

</details>

**A5.** Как агент подключается к контроллеру? Два способа и когда какой применяют.

<details><summary>Ответ</summary>

SSH (контроллер сам подключается к агенту — удобно для управляемых VM)
и inbound/JNLP (агент подключается к контроллеру — удобно за NAT и для динамических
контейнеров).

</details>

**A6.** Чем workspace Jenkins принципиально отличается от рабочего каталога джобы GitLab CI?
К каким багам это приводит?

<details><summary>Ответ</summary>

В Jenkins workspace переиспользуется между сборками на том же агенте: остаются
файлы, кэши, изменения. Это даёт «сборка прошла, потому что файл остался с прошлого раза»
и обратные случаи. В GitLab CI каждая джоба стартует с чистой копии. Лечится `cleanWs()`,
`deleteDir()` и docker/k8s-агентами.

</details>

**A7.** Перечисли типы джоб и скажи, какой тип использовать для нового проекта.

<details><summary>Ответ</summary>

Freestyle, Pipeline, Multibranch Pipeline, Folder, Organization Folder.
Для нового проекта — Pipeline (лучше Multibranch) с `Jenkinsfile` в репозитории.

</details>

**A8.** Чем freestyle отличается от pipeline? Почему freestyle всё ещё встречается?

<details><summary>Ответ</summary>

Freestyle настраивается кликами в UI и хранится только в Jenkins; pipeline
описывается кодом (`Jenkinsfile`) и живёт в репозитории, поддерживает ветвление, параллель,
post-обработку. Freestyle встречается, потому что исторически его создавали годами
и переписывание требует времени.

</details>

**A9.** Перечисли шесть способов запустить сборку.

<details><summary>Ответ</summary>

Вручную (Build Now), по расписанию (cron), опросом SCM, webhook от Git,
после другой джобы (upstream), через REST API с токеном; плюс запуск из другого
пайплайна (`build job: '...'`).

</details>

**A10.** Что означает `H` в cron-выражении Jenkins и зачем он нужен?

<details><summary>Ответ</summary>

`H` — хэш-функция от имени джобы, дающая стабильное, но «размазанное» время
запуска внутри интервала. Нужен, чтобы все джобы не стартовали одновременно и не создавали
пик нагрузки.

</details>

**A11.** Чем webhook лучше Poll SCM? В каком случае Poll SCM всё-таки остаётся?

<details><summary>Ответ</summary>

Webhook срабатывает мгновенно по событию пуша и не создаёт постоянной нагрузки
опросами. Poll SCM остаётся там, где Jenkins недоступен извне (закрытый контур,
нет возможности настроить вебхук в системе контроля версий).

</details>

**A12.** Какие статусы сборки бывают? Что означает UNSTABLE?

<details><summary>Ответ</summary>

SUCCESS, FAILURE, UNSTABLE, ABORTED, NOT_BUILT. UNSTABLE — сборка выполнилась,
но есть проблемы: обычно упавшие тесты, найденные предупреждения статического анализа
или явный вызов `unstable('...')`.

</details>

**A13.** Что такое Script Console и почему доступ к ней критичен?

<details><summary>Ответ</summary>

Консоль выполнения Groovy на контроллере (`/script`). Через неё можно прочитать
и расшифровать креды, изменить конфигурацию, выполнить любой код — фактически это
полный административный доступ.

</details>

**A14.** Почему плагины — это одновременно сила и риск Jenkins?

<details><summary>Ответ</summary>

Плагины дают интеграцию почти с чем угодно (1800+), но они же — источник
несовместимостей при обновлении, уязвимостей и неподдерживаемых конфигураций.
Минимизируй набор, фиксируй версии, обновляй планово с бэкапом.

</details>

**A15.** Что такое JCasC и зачем он нужен?

<details><summary>Ответ</summary>

Jenkins Configuration as Code: описание настроек контроллера (безопасность,
агенты, креды-провайдеры, инструменты, джобы) в YAML, хранящемся в git. Делает Jenkins
воспроизводимым и убирает «настроено кликами, никто не помнит как».

</details>

**A16.** Сравни Jenkins и GitLab CI по пяти параметрам. Когда выберешь Jenkins?

<details><summary>Ответ</summary>

Возраст/экосистема, модель конфигурации (UI+Groovy vs YAML в репо), обслуживание
(свой сервер vs встроен), гибкость (плагины vs достаточный набор), интеграция с VCS
(любая vs GitLab), порог входа. Jenkins выбирают, когда: он уже есть и в него вложено много,
нужна независимость от VCS, закрытый контур, специфические интеграции/железо,
сложные нестандартные сценарии.

</details>

**A17.** Как сделать бэкап Jenkins и что именно бэкапится?

<details><summary>Ответ</summary>

Остановить (или воспользоваться моментом низкой нагрузки), заархивировать
`JENKINS_HOME` (конфигурация, джобы, плагины, креды, история), хранить архив вне сервера,
регулярно проверять восстановление. Дополнительно — держать конфигурацию в JCasC и git.

</details>

### Блок C. Практика

#### C1. 🔑 Подними Jenkins и сделай первую сборку (задание «Минимум» из роадмапа)

1. Запусти Jenkins в докере с томом `jenkins_home`.
2. Разблокируй, поставь suggested plugins, создай администратора.
3. Создай Freestyle-джобу с shell-шагом: версия ОС, `whoami`, `pwd`, `ls -la`,
   `echo $BUILD_NUMBER`.
4. Запусти и найди Console Output. Скопируй в конспект первые и последние 5 строк лога.
5. Повтори то же самое через Pipeline-джобу (`pipeline { ... }` в поле Script).

<details><summary>Ответ</summary>

Ожидаемо: в Console Output видно «Started by user», агент/workspace, команды
с префиксом `+`, и финальную строку `Finished: SUCCESS`.

</details>

#### C2. Workspace не чистится
В pipeline-джобе создай файл `touch artifact-$BUILD_NUMBER.txt`, запусти сборку трижды
и выведи `ls -la`. Убедись, что файлы копятся. Добавь `post { always { cleanWs() } }`
и проверь разницу.

<details><summary>Ответ</summary>

Без очистки файлы копятся от сборки к сборке — это и есть источник «грязного»
workspace. `cleanWs()` в `post { always { ... } }` решает проблему.

</details>

#### C3. Статусы сборки
Сделай три джобы, завершающиеся SUCCESS, FAILURE и UNSTABLE
(подсказка: `currentBuild.result = 'UNSTABLE'` или `unstable('причина')`).
Посмотри, как они отображаются в UI и в истории.

<details><summary>Ответ</summary>

`unstable('tests failed')` даёт жёлтый статус; в истории видно, что сборка
завершилась, но помечена нестабильной.

</details>

#### C4. Триггеры
1. Настрой запуск по расписанию `H/5 * * * *`, дождись автозапуска.
2. Настрой запуск по webhook из GitLab (или GitHub). Если Jenkins недоступен извне —
   опиши, что бы ты настроил, и вместо этого включи Poll SCM `H/2 * * * *`.
3. Сделай цепочку: джоба B запускается после успеха джобы A.
4. Запусти джобу через API с токеном (`curl -X POST .../build?token=...`).

<details><summary>Ответ</summary>

Ожидаемо: cron с `H/5` стартует раз в ~5 минут; webhook требует доступности
Jenkins и настроенного секрета; цепочка настраивается в Build Triggers («Build after
other projects are built»); API-запуск — <code v-pre>curl -X POST -u user:token
"http://host:8080/job/&lt;name&gt;/build"</code> (и CSRF-крамб, если включён).

</details>

#### C5. Агент
Подними inbound-агента в докере, назначь ему label `linux`, поставь на контроллере
executors = 0. Убедись, что сборка идёт на агенте (`echo $NODE_NAME`).
Что произойдёт, если агент остановить?

<details><summary>Ответ</summary>

После остановки агента сборки встают в очередь: «Waiting for next available
executor». Это ровно тот же класс проблем, что «stuck» в GitLab.

</details>

#### C6. Параллельные сборки
Поставь агенту 2 executor'а и запусти три сборки подряд. Опиши, что происходит с третьей.

<details><summary>Ответ</summary>

Третья сборка ждёт освобождения executor'а; при `disableConcurrentBuilds()`
она ждала бы завершения предыдущей сборки этой же джобы.

</details>

#### C7. Хранение сборок
Настрой `buildDiscarder` (Discard old builds): хранить 10 последних сборок.
Проверь, что старые удаляются. Объясни, зачем это нужно.

<details><summary>Ответ</summary>

`buildDiscarder(logRotator(numToKeepStr: '10'))` — иначе история и артефакты
съедают диск контроллера; это одна из самых частых причин аварий Jenkins.

</details>

#### C8. Бэкап
Сделай бэкап `jenkins_home`, удали контейнер, восстанови из архива и убедись,
что джобы и история на месте.

<details><summary>Ответ</summary>

Критерий: после восстановления тома все джобы, история и плагины на месте —
значит, стратегия бэкапа верная.

</details>

#### C9. Сравнение с GitLab CI
Составь таблицу: как одна и та же задача (собрать, протестировать, задеплоить)
решается в Jenkins и в GitLab CI. Минимум восемь строк.

<details><summary>Ответ</summary>

Ориентир для таблицы: конфиг (Jenkinsfile/`.gitlab-ci.yml`), исполнители
(agent/runner), метки (label/tags), секреты (Credentials/CI/CD Variables), артефакты
(`archiveArtifacts`/`artifacts`), ручной шаг (`input`/`when: manual`), условия
(`when`/`rules`), переиспользование (Shared Library/`include`+`extends`),
окружения (плагины/`environment`), уведомления (плагины/интеграции).

</details>

### Блок D. Инциденты

**D1.** Сборка падает с ошибкой, которой нет в коде, а на локальной машине всё хорошо.
Подозрение на workspace. Как проверить и как лечить системно?

<details><summary>Ответ</summary>

Проверить: `ls -la` в начале сборки, наличие файлов от прошлых запусков,
кэши сборщика. Лечение: `cleanWs()`/`deleteDir()`, сборка в docker-агенте, отдельный
workspace на сборку, воспроизведение сборки «с нуля» на чистом агенте.

</details>

**D2.** Все ночные джобы стартуют ровно в 00:00, контроллер перегружен. Что поменять?

<details><summary>Ответ</summary>

Использовать `H` в cron (`H 0 * * *`) — Jenkins распределит запуски внутри часа;
дополнительно разнести тяжёлые джобы по времени и ограничить параллелизм.

</details>

**D3.** Джоба висит с сообщением «Waiting for next available executor». Что проверять?

<details><summary>Ответ</summary>

Онлайн ли агенты с нужной меткой, сколько executor'ов, не заняты ли они,
нет ли `disableConcurrentBuilds`, не залочен ли ресурс (`lock`), хватает ли места
на агенте, не в офлайне ли нода из-за низкого диска (Jenkins сам уводит агента в offline).

</details>

**D4.** После обновления плагинов половина пайплайнов упала. Что делать сейчас
и что надо было сделать заранее?

<details><summary>Ответ</summary>

Сейчас: откатить плагины из бэкапа `JENKINS_HOME` (или через Plugin Manager →
downgrade), проверить логи контроллера. Заранее: тестовый Jenkins, фиксация версий,
бэкап перед обновлением, чтение changelog, поэтапное обновление.

</details>

**D5.** На диске контроллера кончилось место. Что занимает место в `JENKINS_HOME`
и что чистить?

<details><summary>Ответ</summary>

История сборок и архивированные артефакты, логи, workspace на контроллере,
старые плагины и их бэкапы, кэш инструментов. Чистить: настроить `buildDiscarder`,
удалить старые артефакты, вынести сборки на агентов, ограничить хранение логов.

</details>

**D6.** Разработчик получил доступ к Script Console и «посмотрел» креды.
Что произошло с точки зрения безопасности и как это предотвратить?

<details><summary>Ответ</summary>

Script Console даёт исполнение Groovy на контроллере с полным доступом,
включая расшифровку credentials. Предотвращение: Role-based Authorization,
отсутствие `Administer`/`RunScripts` у разработчиков, аудит, вынос секретов во внешний
менеджер (Vault) и короткоживущие токены.

</details>

**D7.** Webhook от GitLab не приходит: пуш есть, сборки нет. Пять причин.

<details><summary>Ответ</summary>

(1) Jenkins недоступен извне (сеть/файрвол); (2) неверный URL вебхука;
(3) не включён нужный триггер в джобе; (4) неверный секрет/токен вебхука;
(5) плагин интеграции не установлен/не настроен; (6) события вебхука не того типа
(push vs merge request); (7) фильтр по веткам отсекает событие.

</details>

**D8.** Агент отвалился посреди сборки, статус ABORTED. Что настроить, чтобы это
не ломало релизы?

<details><summary>Ответ</summary>

Настроить повторные попытки для инфраструктурных сбоев (`retry`), таймауты,
стабильных агентов (или docker/k8s-агентов, поднимающихся на сборку), уведомления,
а релизные операции сделать идемпотентными, чтобы повтор был безопасен.

</details>

**D9.** Jenkins поднят без тома: после `docker rm` пропали все джобы. Как жить дальше
и что сделать сразу?

<details><summary>Ответ</summary>

Всё состояние было в контейнере и удалено вместе с ним. Сразу: поднять заново
с томом (`-v jenkins_home:/var/jenkins_home`), настроить регулярный бэкап и перевести
конфигурацию в JCasC + `Jenkinsfile` в репозиториях, чтобы восстановление было
воспроизводимым.

</details>

**D10.** Джоба выполняется на контроллере, хотя есть агенты. Почему это плохо
и как запретить?

<details><summary>Ответ</summary>

Сборка на контроллере имеет доступ к `JENKINS_HOME` и кредам, а тяжёлая сборка
роняет UI. Запретить: выставить 0 executors на контроллере и указывать в пайплайнах
конкретные метки агентов (`agent { label '...' }` вместо `agent any` там, где это важно).

</details>

### Блок E. Вопросы с собеседования

**1.** Расскажи архитектуру Jenkins.

<details><summary>Ответ</summary>

Controller (UI, конфигурация, планирование, история, плагины, креды) + агенты
(выполнение сборок), связь по SSH или JNLP, метки и executors для распределения.

</details>

**2.** Что такое агент, executor, label?

<details><summary>Ответ</summary>

Агент — машина для сборок; executor — слот параллельного выполнения на агенте;
label — метка для выбора агента.

</details>

**3.** Где Jenkins хранит состояние и как его бэкапить?

<details><summary>Ответ</summary>

В `JENKINS_HOME`; бэкапится архивированием этого каталога (плюс JCasC и Jenkinsfile
в git для воспроизводимости).

</details>

**4.** Какие типы джоб бывают и что использовать сейчас?

<details><summary>Ответ</summary>

Freestyle, Pipeline, Multibranch, Folder, Organization Folder; сейчас —
Pipeline/Multibranch с `Jenkinsfile`.

</details>

**5.** Какие триггеры сборки знаешь?

<details><summary>Ответ</summary>

Ручной запуск, cron, Poll SCM, webhook, upstream-джоба, REST API, запуск из другого
пайплайна.

</details>

**6.** Чем webhook лучше опроса SCM?

<details><summary>Ответ</summary>

Мгновенная реакция и отсутствие постоянной нагрузки опросами; опрос оставляют,
если Jenkins недоступен извне.

</details>

**7.** Что такое UNSTABLE и когда он возникает?

<details><summary>Ответ</summary>

Сборка выполнилась, но с проблемами — чаще всего упавшие тесты или предупреждения
анализаторов; задаётся плагинами или `unstable()`.

</details>

**8.** Чем Jenkins отличается от GitLab CI? Когда выберешь Jenkins?

<details><summary>Ответ</summary>

Jenkins — отдельный сервер с плагинами и Groovy, независим от VCS, требует
администрирования; GitLab CI — встроен, YAML в репозитории, проще. Jenkins выбирают
при существующей инвестиции, закрытом контуре, нестандартных интеграциях.

</details>

**9.** Какие риски несут плагины?

<details><summary>Ответ</summary>

Несовместимости при обновлении, уязвимости, рост сложности и неподдерживаемость.

</details>

**10.** Как обеспечить безопасность Jenkins?

<details><summary>Ответ</summary>

0 executors на контроллере, ролевая модель прав, ограничение Script Console,
креды только в Credentials/Vault, CSRF, обновления, бэкапы, изоляция агентов.

</details>
