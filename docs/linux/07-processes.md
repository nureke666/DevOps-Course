# 07. Processes — процессы, сигналы, приоритеты

> Источник: `07_processes.txt` (Grasshopper, 11 уроков)
> **После темы ты умеешь:** находить процессы, понимать их состояния, корректно завершать,
> управлять приоритетами и работать с фоновыми задачами.

---

## 🗺️ Схема: жизнь процесса

```text:no-line-numbers
                 ┌──────────────────────────────────────────────┐
                 │  PID 1  (systemd) — предок всех процессов     │
                 └──────────────────┬───────────────────────────┘
                                    │ fork()  → копия себя
                                    ▼
                        ┌───────────────────────┐
                        │  Дочерний процесс     │
                        │  (та же программа)    │
                        └───────────┬───────────┘
                                    │ exec()  → заменить код на нужную программу
                                    ▼
      ┌─────────────────────────────────────────────────────────────┐
      │  Работающий процесс: PID, PPID, UID, состояние, память, fd  │
      └───────────┬──────────────────────────────┬──────────────────┘
                  │ exit(code)                   │ сигнал (TERM/KILL/…)
                  ▼                              ▼
      ┌────────────────────────┐     ┌────────────────────────────┐
      │ ZOMBIE (Z)             │     │ завершение                 │
      │ ждёт, пока родитель    │────▶│ родитель делает wait()     │
      │ заберёт код возврата   │     │ запись из таблицы исчезает │
      └────────────────────────┘     └────────────────────────────┘
```

**Процесс** — запущенный экземпляр программы. Программа на диске — мёртвый файл; процесс — живой,
со своей памятью, дескрипторами, правами и состоянием.

## 1. ps — снимок процессов

У `ps` три несовместимых синтаксиса (UNIX с дефисом, BSD без дефиса, GNU с двумя дефисами).
На практике выучи две комбинации:

```bash
ps aux              # BSD-стиль: ВСЕ процессы, с юзерами   ← самая частая
ps -ef              # UNIX-стиль: то же, с PPID            ← вторая по частоте
ps -eo pid,ppid,user,%cpu,%mem,stat,start,cmd --sort=-%cpu | head
```

Читаем `ps aux`:

```text:no-line-numbers
USER   PID %CPU %MEM    VSZ   RSS TTY   STAT START   TIME COMMAND
www-d  842  0.0  0.5 141892 11024 ?     S    10:30   0:02 nginx: worker process
 │      │    │    │     │     │    │     │     │       │      │
 │      │    │    │     │     │    │     │     │       │      └─ команда
 │      │    │    │     │     │    │     │     │       └─ суммарное время CPU
 │      │    │    │     │     │    │     │     └─ когда запущен
 │      │    │    │     │     │    │     └─ СОСТОЯНИЕ (см. ниже)
 │      │    │    │     │     │    └─ терминал (? = нет терминала = демон)
 │      │    │    │     │     └─ RSS: РЕАЛЬНАЯ физическая память, КБ ← смотри сюда
 │      │    │    │     └─ VSZ: виртуальная память (часто огромная, почти бесполезна)
 │      │    │    └─ % памяти
 │      │    └─ % CPU (среднее за время жизни, не «сейчас»!)
 │      └─ PID
 └─ пользователь
```

Полезные варианты:

```bash
ps aux --sort=-%mem | head -11         # топ по памяти
ps aux --sort=-%cpu | head -11         # топ по CPU
ps -ef --forest                        # дерево процессов
pstree -p                              # дерево нагляднее
pstree -p 1234                         # поддерево конкретного процесса
ps -u nurik                            # процессы пользователя
ps -C nginx                            # по имени команды
ps -p 1234 -o pid,ppid,user,cmd        # конкретный PID
ps -eLf                                # с ПОТОКАМИ (threads)
```

Поиск процессов:

```bash
pgrep nginx                 # только PID
pgrep -a nginx              # PID + командная строка
pgrep -u www-data           # по пользователю
pgrep -f "python app.py"    # по ПОЛНОЙ командной строке ← важно для скриптов
pidof nginx
ps aux | grep [n]ginx       # трюк со скобками: grep не находит сам себя
```

## 2. Controlling Terminal

Колонка `TTY`:

| Значение | Смысл |
|----------|-------|
| `?` | Нет управляющего терминала — **демон** |
| `pts/0` | Псевдотерминал (SSH-сессия, эмулятор терминала) |
| `tty1` | Физическая консоль |

Зачем это знать: процесс, привязанный к терминалу, получает `SIGHUP` при закрытии сессии и умирает.
Именно поэтому:

```bash
nohup ./long_task.sh &          # игнорировать SIGHUP, вывод в nohup.out
setsid ./long_task.sh           # запустить в новой сессии, без терминала
screen / tmux                   # ПРАВИЛЬНЫЙ способ: сессия переживает разрыв SSH
systemd-run --user ./task.sh    # или отдать systemd
```

💡 `tmux` — обязательный инструмент девопса: запустил долгую миграцию, отвалился интернет,
переподключился — процесс жив. Базово: `tmux new -s work`, `Ctrl+b d` (detach), `tmux attach -t work`.

### tmux — минимум на каждый день

Главное правило: **сначала `Ctrl+b`, отпустил, потом клавиша** (префикс).

| Что | Хоткей / команда |
|-----|------------------|
| Новая сессия / список / вернуться | `tmux new -s work` · `tmux ls` · `tmux attach -t work` |
| Отцепиться (всё продолжит работать) | `Ctrl+b d` |
| Переключить сессию изнутри | `Ctrl+b s` |
| Убить сессию | `tmux kill-session -t work` |
| Новое окно (вкладка) / по номеру / переименовать | `Ctrl+b c` · `Ctrl+b 1..9` · `Ctrl+b ,` |
| Следующее / предыдущее окно, меню всех окон | `Ctrl+b n` / `Ctrl+b p` · `Ctrl+b w` |
| Разделить: лево-право / верх-низ | `Ctrl+b %` · `Ctrl+b "` |
| Панель на весь экран и обратно (zoom) | `Ctrl+b z` |
| Перебрать раскладки / панель в отдельное окно | `Ctrl+b Пробел` · `Ctrl+b !` |
| Закрыть панель / окно | `Ctrl+b x` (или `exit`) · `Ctrl+b &` |
| Прокрутка и поиск по истории | `Ctrl+b [` → `/error` → `n` → `q` |

Минимальный `~/.tmux.conf` (локально; на чужих серверах работай с дефолтом):

```bash
cat > ~/.tmux.conf << 'EOF'
set -g mouse on                   # клик по панели, ресайз мышью, скролл колесом
set -g history-limit 50000        # длинная история вывода
bind -n M-Left  select-pane -L    # Alt+стрелки — переход между панелями без префикса
bind -n M-Right select-pane -R
bind -n M-Up    select-pane -U
bind -n M-Down  select-pane -D
EOF
tmux source-file ~/.tmux.conf     # применить без перезапуска
```

## 3. Process Details — что есть у процесса

| Атрибут | Что это |
|---------|---------|
| **PID** | Уникальный номер процесса |
| **PPID** | PID родителя |
| **UID/GID** | От кого работает (реальный и эффективный) |
| **CWD** | Текущий рабочий каталог |
| **Файловые дескрипторы** | Открытые файлы, сокеты, пайпы |
| **Окружение** | Переменные, унаследованные от родителя |
| **Приоритет (NI/PR)** | Как часто получает CPU |
| **Состояние** | R, S, D, T, Z |
| **Namespaces / cgroups** | Изоляция и лимиты (основа контейнеров) |

```bash
ls -l /proc/1234/cwd        # рабочий каталог
ls -l /proc/1234/exe        # путь к бинарнику
ls -l /proc/1234/fd/        # открытые дескрипторы ← бесценно при отладке
cat /proc/1234/cmdline | tr '\0' ' '; echo
cat /proc/1234/environ | tr '\0' '\n'
cat /proc/1234/status       # человекочитаемая сводка
cat /proc/1234/limits       # лимиты (ulimit) конкретного процесса
cat /proc/1234/cgroup       # в каком cgroup (какой контейнер/юнит)
```

## 4. Process Creation — fork и exec

```text:no-line-numbers
fork()  → создаёт КОПИЮ процесса (новый PID, копия памяти через copy-on-write)
exec()  → заменяет код текущего процесса новой программой (PID сохраняется)
wait()  → родитель ждёт завершения ребёнка и забирает его код возврата
```

Когда ты в bash пишешь `ls`, происходит: bash делает `fork()` → ребёнок делает `exec("/bin/ls")` →
bash делает `wait()`. Именно так устроен запуск **всего** в UNIX.

**PID 1** — первый процесс (systemd), запускается ядром и усыновляет всех сирот.
В контейнере PID 1 — твоё приложение, и это важно: оно обязано корректно обрабатывать сигналы и
подбирать зомби, иначе получишь `docker stop` по 10-секундному таймауту и накопление зомби.
Отсюда `--init` в Docker и `tini`.

## 5-6. Termination и Signals

**Сигнал** — асинхронное уведомление процессу от ядра или другого процесса.

| № | Имя | Что делает | Можно перехватить? |
|---|-----|-----------|--------------------|
| 1 | **SIGHUP** | Терминал закрыт; у демонов — **перечитать конфиг** | Да |
| 2 | **SIGINT** | Ctrl+C, прерывание | Да |
| 3 | SIGQUIT | Ctrl+\, выход с core dump | Да |
| 9 | **SIGKILL** | Убить немедленно | 🔴 **НЕТ** |
| 11 | SIGSEGV | Обращение к чужой памяти (сегфолт) | Да |
| 13 | SIGPIPE | Запись в закрытый пайп | Да |
| 15 | **SIGTERM** | Вежливая просьба завершиться (**по умолчанию**) | Да |
| 17 | SIGCHLD | Дочерний процесс завершился | Да |
| 18 | SIGCONT | Продолжить приостановленный | — |
| 19 | **SIGSTOP** | Приостановить | 🔴 **НЕТ** |
| 20 | SIGTSTP | Ctrl+Z, приостановить (мягко) | Да |

```bash
kill -l          # список всех сигналов
man 7 signal     # подробности
```

🔑 **SIGTERM vs SIGKILL — вопрос №1 на собеседовании:**

```text:no-line-numbers
SIGTERM (15)                          SIGKILL (9)
├─ процесс ПОЛУЧАЕТ сигнал            ├─ процесс НЕ получает ничего
├─ может закрыть файлы, БД, сокеты    ├─ ядро просто убивает
├─ дописать буферы на диск            ├─ несохранённые данные ТЕРЯЮТСЯ
├─ корректно завершить транзакции     ├─ временные файлы/локи остаются
└─ graceful shutdown                  └─ возможно повреждение данных
```

**Правило: всегда сначала `kill` (TERM), подождать, и только потом `kill -9`.**
`kill -9` как первая реакция — красный флаг на собеседовании и причина инцидентов в проде
(повреждённая БД, «залипший» lock-файл, потерянные транзакции).

⚠️ `kill -9` **не поможет** процессу в состоянии `D` (uninterruptible sleep) — он не отреагирует,
потому что застрял в ядре на I/O. Лечится устранением причины (зависший NFS, сбойный диск) или ребутом.

## 7. kill и друзья

```bash
kill 1234                  # SIGTERM (по умолчанию)
kill -15 1234              # то же явно
kill -TERM 1234            # то же именем
kill -9 1234               # SIGKILL — последнее средство
kill -HUP 1234             # перечитать конфиг (nginx, sshd, rsyslog)
kill -0 1234               # НЕ убивает: проверка "процесс жив?" ← для скриптов

killall nginx              # по ИМЕНИ (все процессы с таким именем)
killall -9 -u nurik        # все процессы пользователя

pkill nginx                # по имени, гибче killall
pkill -f "python app.py"   # по полной командной строке
pkill -u nurik             # по пользователю
pkill -HUP nginx           # сигнал по имени

# Корректный паттерн для скриптов
kill -TERM "$PID"
for i in {1..10}; do kill -0 "$PID" 2>/dev/null || break; sleep 1; done
kill -0 "$PID" 2>/dev/null && kill -9 "$PID"
```

⚠️ `pkill -f` очень мощная и очень опасная: `pkill -f python` убьёт **все** python-процессы, включая
системные. Сначала всегда `pgrep -af python`.

## 8. Niceness — приоритеты

```text:no-line-numbers
NI (nice):  -20 ────────── 0 ────────── +19
            │              │             │
      наивысший       обычный      наинизший
      приоритет      приоритет     приоритет
      («злой»,      (по умолч.)   («вежливый»,
   забирает CPU)                 уступает всем)
```

```bash
nice -n 10 ./backup.sh          # запустить с пониженным приоритетом
nice -n -5 ./critical.sh        # повысить (нужен root!)
renice -n 15 -p 1234            # изменить у работающего процесса
renice -n 5 -u nurik            # для всех процессов пользователя
ps -eo pid,ni,cmd | head
```

Правила: понижать приоритет (увеличивать nice) может любой; **повышать — только root**.
Обычному пользователю нельзя «отобрать» CPU у других.

💡 На практике важнее **ionice** — приоритет дискового ввода-вывода:
```bash
ionice -c3 -p 1234              # idle-класс: работает только когда диск свободен
ionice -c2 -n7 ./backup.sh      # best-effort, низший приоритет
nice -n19 ionice -c3 ./backup.sh   # классическая связка для бэкапов
```

В systemd то же самое задаётся директивами `Nice=`, `IOSchedulingClass=`, `CPUWeight=`, `CPUQuota=`.

## 9. Process States — состояния

| Код | Состояние | Смысл | Норма? |
|-----|-----------|-------|--------|
| **R** | Running / Runnable | Выполняется или готов | ✅ |
| **S** | Interruptible Sleep | Ждёт события (сеть, ввод) — **большинство процессов** | ✅ |
| **D** | Uninterruptible Sleep | Ждёт I/O, **не реагирует даже на SIGKILL** | 🔴 тревога |
| **T** | Stopped | Приостановлен (Ctrl+Z или SIGSTOP) | ⚠️ |
| **Z** | Zombie | Завершился, родитель не забрал код возврата | ⚠️ |
| **I** | Idle | Простаивающий поток ядра | ✅ |

Дополнительные флаги в `ps aux` (колонка STAT):

| Флаг | Значение |
|------|----------|
| `<` | Высокий приоритет (nice < 0) |
| `N` | Низкий приоритет (nice > 0) |
| `s` | Лидер сессии |
| `l` | Многопоточный |
| `+` | В foreground-группе терминала |

**Зомби (Z):**
- сам по себе не ест ресурсы, но занимает запись в таблице процессов;
- **нельзя убить** — он уже мёртв; нужно чинить **родителя** (`ps -o ppid= -p PID`);
- если родитель умер — сироту усыновляет PID 1 и корректно подбирает;
- сотни зомби = баг в приложении (не вызывает `wait()`), частая проблема в контейнерах без init.

**D-состояние:**
- зависший NFS/сетевой диск, сбойный HDD, перегруженное хранилище;
- процессы в `D` **входят в load average** — отсюда «load 50, а CPU простаивает»;
- диагностика: `ps -eo pid,stat,wchan:30,cmd | awk '$2 ~ /D/'`, `dmesg | tail`, `iostat -x 1`.

## 10. /proc — файловая система процессов

`/proc` — виртуальная ФС: файлов на диске нет, ядро генерирует содержимое на лету.
Это прямое воплощение принципа «всё есть файл».

```bash
# Информация о системе
cat /proc/cpuinfo           # процессоры
cat /proc/meminfo           # память в деталях
cat /proc/loadavg           # load average + число процессов
cat /proc/uptime
cat /proc/version           # версия ядра
cat /proc/mounts            # смонтированные ФС
cat /proc/net/tcp           # TCP-соединения (в hex)

# Информация о процессе
ls /proc/1234/
cat /proc/1234/status | grep -E 'Name|State|Pid|PPid|VmRSS|Threads'
cat /proc/1234/limits
ls -l /proc/1234/fd | wc -l       # сколько открытых дескрипторов
cat /proc/1234/io                 # сколько прочитал/записал байт

# Настройки ядра (см. тему 12)
cat /proc/sys/net/ipv4/ip_forward
sudo sysctl -w net.ipv4.ip_forward=1
```

🔥 **Трюк: восстановить удалённый, но открытый файл.**
Процесс держит файл открытым → данные ещё есть, хотя `rm` уже отработал:
```bash
lsof | grep deleted
cp /proc/<PID>/fd/<N> /tmp/restored.log
```
Отсюда же правило: удаление огромного лога **не освобождает место**, пока процесс держит дескриптор.
Нужно `truncate -s 0 /var/log/app.log` или рестарт/сигнал сервису.

## 11. Job Control — фоновые задачи

```bash
./long_task.sh &        # запустить в фоне
Ctrl+Z                  # приостановить текущую задачу (SIGTSTP)
jobs                    # список задач текущего шелла
jobs -l                 # с PID
bg                      # продолжить последнюю в ФОНЕ
bg %1                   # продолжить задачу №1 в фоне
fg                      # вернуть последнюю на передний план
fg %2                   # вернуть задачу №2
kill %1                 # убить задачу по номеру
wait                    # ждать завершения всех фоновых задач
disown -h %1            # открепить от шелла (переживёт выход)
```

```text:no-line-numbers
┌─────────────┐   Ctrl+Z    ┌──────────────┐    bg     ┌──────────────┐
│ FOREGROUND  │────────────▶│  STOPPED (T) │──────────▶│  BACKGROUND  │
│ (занимает   │◀────────────│              │◀──────────│   (работает) │
│  терминал)  │     fg      └──────────────┘    fg     └──────────────┘
└─────────────┘
```

⚠️ Фоновая задача — **не демон**: при выходе из шелла она получит SIGHUP.
Для долгих задач: `tmux`/`screen`, `nohup ... &`, `setsid`, или systemd-юнит.

## 💼 Как это в DevOps

- «Сервис не отвечает» → `ps aux | grep app`, `pgrep -af app`, `systemctl status`, состояние процесса.
- **Graceful shutdown**: `docker stop` шлёт SIGTERM, ждёт 10 с, потом SIGKILL. Kubernetes — то же самое
  через `terminationGracePeriodSeconds` и `preStop`-хук. Понимание сигналов = корректные деплои без 5xx.
- Код выхода **137** в k8s = 128+9 = SIGKILL (обычно OOMKilled), **143** = 128+15 = SIGTERM.
- `kill -HUP` для перечитывания конфига без даунтайма (`nginx -s reload` делает именно это).
- Зомби и PID 1 в контейнерах → `tini` / `docker run --init`.
- `nice`/`ionice` для бэкапов, чтобы не убить прод I/O.
- `/proc/<pid>/` — швейцарский нож при расследовании: что открыто, какие лимиты, сколько памяти.

## 🧪 Мини-лаба

```bash
vagrant ssh

# 1. Разведка
ps aux | head
ps aux --sort=-%mem | head -5
ps -ef --forest | head -30
pstree -p | head -20

# 2. Свой процесс для экспериментов
sleep 600 &
PID=$!
echo "PID=$PID"
ps -p $PID -o pid,ppid,user,stat,ni,cmd

# 3. Job control
jobs
Ctrl+Z   # если процесс в foreground
jobs -l
bg %1
fg %1    # затем Ctrl+Z ещё раз

# 4. Сигналы
kill -STOP $PID; ps -p $PID -o pid,stat      # T
kill -CONT $PID; ps -p $PID -o pid,stat      # S
kill -TERM $PID; ps -p $PID -o pid,stat      # процесса нет

# 5. TERM vs KILL — увидеть разницу
cat > /tmp/trap_demo.sh <<'EOS'
```

## 📌 Шпаргалка

| Команда | Действие |
|---------|----------|
| `ps aux` / `ps -ef` | Все процессы (BSD / UNIX стиль) |
| `ps aux --sort=-%mem \| head` | Топ по памяти |
| `ps -eo pid,ppid,stat,ni,cmd` | Свои колонки |
| `pstree -p` | Дерево процессов |
| `pgrep -af шаблон` | Найти PID по имени/строке запуска |
| `kill PID` / `kill -9 PID` | TERM / KILL |
| `kill -HUP PID` | Перечитать конфиг |
| `kill -0 PID` | Проверить, жив ли (ничего не шлёт) |
| `pkill -f "строка"` | Убить по командной строке (осторожно!) |
| `nice -n 10 cmd` / `renice -n 5 -p PID` | Приоритет CPU |
| `ionice -c3 cmd` | Приоритет диска |
| `jobs` / `bg` / `fg` / `disown` | Управление задачами шелла |
| `nohup cmd &` / `tmux` | Пережить закрытие терминала |
| `/proc/PID/{status,fd,limits,cgroup}` | Всё о процессе |

**Состояния:** R (работает), S (спит — норма), **D (I/O, не убивается)**, T (остановлен), **Z (зомби)**.

## 🧠 Что запомнить

1. `fork()` + `exec()` — так запускается всё. PID 1 усыновляет сирот.
2. **Сначала SIGTERM, потом (если не помогло) SIGKILL.** `kill -9` первым — плохая практика.
3. SIGKILL и SIGSTOP **нельзя перехватить**. Процесс в `D` не убивается вообще.
4. Зомби убивать бессмысленно — чини родителя.
5. RSS — реальная память, VSZ — виртуальная (обычно не показатель).
6. `kill -HUP` — перечитать конфиг без рестарта.
7. Exit code 137 = 128+9 (SIGKILL/OOM), 143 = 128+15 (SIGTERM).
8. Фоновая задача умирает вместе с SSH-сессией → tmux/nohup/systemd.
9. Удаление открытого файла не освобождает место — нужен `truncate` или рестарт сервиса.
10. `nice` понижать может каждый, повышать — только root.

### Блок A. Теория

**A1.** Что такое процесс и чем он отличается от программы?

<details><summary>Ответ</summary>

Программа — исполняемый файл на диске (пассивные данные). Процесс — запущенный экземпляр
программы: собственное адресное пространство, дескрипторы, права, состояние, PID. Из одной
программы можно запустить множество процессов.

</details>

**A2.** Объясни `fork()` и `exec()`. Что происходит, когда ты вводишь `ls` в bash?

<details><summary>Ответ</summary>

`fork()` создаёт копию текущего процесса (новый PID, память через copy-on-write);
`exec()` заменяет образ процесса на другую программу, сохраняя PID. Ввод `ls`: bash делает `fork()`,
ребёнок вызывает `exec("/bin/ls")`, родитель ждёт через `wait()` и получает код возврата.

</details>

**A3.** Что такое PID 1? Почему это важно в контейнерах?

<details><summary>Ответ</summary>

PID 1 — первый процесс, запускаемый ядром (systemd/init). Он усыновляет осиротевшие процессы
и обязан подбирать зомби через `wait()`. В контейнере PID 1 — само приложение; если оно не умеет
обрабатывать сигналы и подбирать детей, `docker stop` будет ждать таймаут и убивать жёстко, а зомби
накапливаться. Решения: `docker run --init`, `tini`, корректная обработка сигналов в приложении.

</details>

**A4.** Чем PID отличается от PPID? Что произойдёт с дочерним процессом, если родитель умрёт?

<details><summary>Ответ</summary>

PID — идентификатор процесса, PPID — идентификатор родителя. Если родитель умирает,
процесс становится сиротой и его усыновляет PID 1 (или ближайший subreaper), PPID меняется на 1.

</details>

**A5.** Разница между SIGTERM и SIGKILL — подробно, с точки зрения приложения и данных.

<details><summary>Ответ</summary>

SIGTERM доставляется приложению, которое может выполнить обработчик: закрыть соединения,
сбросить буферы, завершить транзакции, снять локи, дождаться завершения текущих запросов.
SIGKILL обрабатывается ядром, процесс не получает управления: несохранённые данные теряются,
временные файлы и lock-файлы остаются, БД может остаться в несогласованном состоянии.

</details>

**A6.** Какие два сигнала невозможно перехватить и почему так сделано?

<details><summary>Ответ</summary>

SIGKILL (9) и SIGSTOP (19). Иначе процесс мог бы сделать себя неубиваемым и неостанавливаемым,
и администратор потерял бы контроль над системой.

</details>

**A7.** Что означает состояние `D`? Почему `kill -9` на него не действует и что с этим делать?

<details><summary>Ответ</summary>

`D` — uninterruptible sleep: процесс ждёт завершения операции ввода-вывода внутри ядра и
не может обрабатывать сигналы вообще (состояние гарантирует целостность операции). `kill -9`
доставится только после выхода из этого состояния. Лечение — устранить причину: зависший NFS,
сбойный диск, перегруженное хранилище; в крайнем случае перезагрузка.

</details>

**A8.** Что такое зомби-процесс? Ест ли он ресурсы? Как от него избавиться?

<details><summary>Ответ</summary>

Процесс, который завершился, но его код возврата ещё не забран родителем через `wait()`.
Ресурсов (память, CPU) не потребляет, но занимает запись в таблице процессов — при массовом
накоплении исчерпывается лимит PID. Убить нельзя (он уже мёртв): нужно либо чинить/перезапускать
родителя, либо, если родитель умрёт, зомби подберёт PID 1.

</details>

**A9.** Чем VSZ отличается от RSS? На какой показатель смотреть при поиске утечки памяти?

<details><summary>Ответ</summary>

VSZ — весь виртуальный адресный размер (включая замапленные, но не занятые страницы,
разделяемые библиотеки) — обычно сильно завышен. RSS — реально занятая физическая память.
При поиске утечки смотрят на **RSS** в динамике (и точнее — `PSS` из `/proc/PID/smaps_rollup`).

</details>

**A10.** Что делает `kill -HUP` для nginx и почему это лучше рестарта?

<details><summary>Ответ</summary>

Для nginx SIGHUP = graceful reload: мастер перечитывает конфиг, поднимает новых воркеров,
старым даёт доработать текущие запросы. Обрывов соединений нет, в отличие от рестарта.

</details>

**A11.** Диапазон значений nice? Кто может повышать приоритет, а кто понижать?

<details><summary>Ответ</summary>

От -20 (наивысший приоритет) до +19 (наинизший), по умолчанию 0. Любой пользователь может
только **понижать** приоритет своих процессов (увеличивать nice); повышение (отрицательные значения)
требует root или `CAP_SYS_NICE`.

</details>

**A12.** Почему фоновая задача (`&`) умирает при закрытии SSH? Три способа этого избежать.

<details><summary>Ответ</summary>

При закрытии терминала процессам сессии рассылается SIGHUP, и по умолчанию он завершает процесс.
Способы: (1) `tmux`/`screen` — лучший, позволяет вернуться к сессии; (2) `nohup cmd &` или `setsid`;
(3) оформить как systemd-юнит / `systemd-run --scope`. Для интерактивной работы лучший — tmux,
для регулярных задач — systemd.

</details>

**A13.** Почему `rm huge.log` не освободил место на диске, хотя файл удалён?

<details><summary>Ответ</summary>

Место освобождается, когда обнулится счётчик ссылок И закроются все открытые дескрипторы.
Пока процесс держит файл открытым, данные остаются на диске (`lsof +L1` покажет такие файлы).
Решение: `truncate -s 0 /path/log` (не `rm`), рестарт или сигнал сервису, `logrotate` с `copytruncate`.

</details>

**A14.** Что означают коды выхода 137 и 143 в Kubernetes?

<details><summary>Ответ</summary>

137 = 128 + 9 → процесс убит SIGKILL, чаще всего OOMKilled (превышен `limits.memory`).
143 = 128 + 15 → SIGTERM, обычно нормальное завершение при обновлении/масштабировании.

</details>

### Блок D. Инциденты

**D1.** Приложение не отвечает. `systemctl restart app` висит 90 секунд и падает по таймауту.

<details><summary>Ответ</summary>

Процесс застрял в непрерываемом I/O — сигналы (в т.ч. от systemd) не доставляются, поэтому
`restart` ждёт `TimeoutStopSec` и переходит к SIGKILL, который тоже не срабатывает.
Проверять: `ps -eo pid,stat,wchan:30,cmd | awk '$2~/D/'`, `dmesg -T | tail -50` (ошибки диска,
таймауты NFS), `iostat -x 1`, `mount | grep nfs`, состояние хранилища. Пока причина не устранена,
поможет только устранение I/O-проблемы или перезагрузка.

</details>

**D2.** В `ps aux` — 400 зомби-процессов с именем `<defunct>`, родитель у всех один и тот же PID.
Что делать прямо сейчас и как чинить по-настоящему?

<details><summary>Ответ</summary>

Зомби убить нельзя. Сейчас: найти родителя `ps -o ppid= -p <PID зомби>`, посмотреть, что
это за процесс, и перезапустить его (`systemctl restart <unit>`) — после его завершения зомби
подберёт PID 1. По-настоящему: исправить приложение (вызывать `wait()`/`waitpid()` или установить
`SIGCHLD` в `SIG_IGN`), в контейнере — добавить init-процесс (`tini`, `--init`, `shareProcessNamespace`).

</details>

**D3.** После деплоя в Kubernetes поды рестартуют с кодом 137. Что это значит и куда смотреть?

<details><summary>Ответ</summary>

137 = SIGKILL. Почти всегда OOMKilled: контейнер превысил `resources.limits.memory`.
Смотреть: `kubectl describe pod` (Last State: OOMKilled), `kubectl top pod`, метрики
`container_memory_working_set_bytes`, логи приложения перед падением, `dmesg` на ноде.
Возможна и вторая причина — `liveness probe` убивает контейнер (тогда в событиях будет `Unhealthy`).

</details>

**D4.** Коллега пишет: «перезапустил nginx через `kill -9`, теперь он не стартует: порт занят».
Объясни, что произошло, и как правильно.

<details><summary>Ответ</summary>

`kill -9` не дал nginx корректно закрыть слушающие сокеты и убрать pid-файл; часть воркеров
могла остаться жить и держать порт. Проверить: `ss -tulpn | grep :80`, `pgrep -af nginx`,
убрать оставшиеся процессы, удалить `/run/nginx.pid`, затем `systemctl start nginx`.
Правильно было: `nginx -s reload` / `systemctl reload nginx` для конфига,
`systemctl restart nginx` для перезапуска.

</details>

**D5.** Ночной бэкап «кладёт» прод: приложение отвечает по 5 секунд, `top` показывает низкий CPU,
но высокий `wa`. Как смягчить проблему, не меняя код бэкапа?

<details><summary>Ответ</summary>

Высокий `wa` = процессы ждут диск. Запускать бэкап с пониженным приоритетом ввода-вывода:
`nice -n 19 ionice -c3 /opt/backup.sh`; в systemd-юните — `Nice=19`, `IOSchedulingClass=idle`,
`IOWeight=10`, при необходимости `IOReadBandwidthMax`. Также помогает ограничение скорости самого
инструмента (`rsync --bwlimit`, `pg_dump | pv -L`) и перенос окна бэкапа на менее нагруженное время.

</details>

**D6.** Запустил долгую миграцию через SSH, интернет отвалился, миграция прервалась на середине.
Как сделать так, чтобы это больше не повторилось (3 способа, какой лучший и почему)?

<details><summary>Ответ</summary>

(1) `tmux`/`screen` — сессия живёт на сервере, можно вернуться и видеть вывод — **лучший**
для интерактивных разовых операций. (2) `nohup cmd > log 2>&1 &` — переживёт разрыв, но нельзя
интерактивно вмешаться. (3) `systemd-run --unit=migration --collect /path/cmd` — задача под
управлением systemd с логами в journald, лучше всего для повторяемых/важных операций.

</details>

**D7.** В `top` load average = 25 при 2 CPU, но `%CPU` всех процессов около нуля.
Как такое возможно и как найти причину?

<details><summary>Ответ</summary>

В load average учитываются процессы не только в `R`, но и в `D` (ожидание I/O).
Значит, десятки процессов ждут диск или сеть. Искать: `ps -eo stat,cmd | grep '^D'`,
`iostat -x 1 5` (`%util`, `await`), `vmstat 1` (колонка `b` и `wa`), `dmesg` на предмет ошибок
хранилища, проверить NFS-маунты (`mount | grep nfs`, `nfsstat`).

</details>

### Блок E. Вопросы с собеседования

**1.** Чем `kill -9` отличается от `kill -15`? Когда использовать каждый?

<details><summary>Ответ</summary>

`-15` (SIGTERM) — вежливое завершение: приложение закрывает ресурсы. `-9` (SIGKILL) — жёсткое
убийство ядром, данные могут потеряться. Порядок: TERM → подождать → KILL.

</details>

**2.** Что такое зомби-процесс и как его убрать?

<details><summary>Ответ</summary>

Процесс, завершившийся, но не «подобранный» родителем. Убрать: перезапустить/починить родителя;
сам зомби убить нельзя.

</details>

**3.** Как найти процесс, занимающий порт 8080?

<details><summary>Ответ</summary>

`ss -tulpn | grep :8080` или `sudo lsof -i :8080` / `fuser -n tcp 8080`.

</details>

**4.** Что означает состояние D и почему оно опасно?

<details><summary>Ответ</summary>

Непрерываемый сон в ожидании I/O: процесс не реагирует на сигналы, входит в load average,
часто указывает на проблему с диском или сетевой ФС.

</details>

**5.** Как запустить процесс, чтобы он пережил закрытие SSH?

<details><summary>Ответ</summary>

`tmux`/`screen`, `nohup cmd &`, `setsid`, либо оформить как systemd-сервис.

</details>

**6.** Как посмотреть, какие файлы открыты процессом?

<details><summary>Ответ</summary>

`lsof -p PID` или `ls -l /proc/PID/fd`.

</details>

**7.** Что такое nice и когда ты его использовал?

<details><summary>Ответ</summary>

Значение приоритета CPU (-20…19). Использую для фоновых задач — бэкапы, архивация, индексация —
обычно вместе с `ionice -c3`, чтобы не мешать продовой нагрузке.

</details>

**8.** Как перезагрузить конфигурацию сервиса без даунтайма?

<details><summary>Ответ</summary>

`systemctl reload <unit>` или `kill -HUP <pid>` — мастер перечитывает конфиг без разрыва
соединений (для nginx — `nginx -s reload`).

</details>

**9.** Что происходит при `docker stop`?

<details><summary>Ответ</summary>

Docker шлёт SIGTERM процессу PID 1 в контейнере, ждёт `--time` (по умолчанию 10 с),
затем шлёт SIGKILL. Поэтому приложение обязано обрабатывать SIGTERM, иначе каждый деплой —
жёсткое убийство и возможные 5xx.

</details>
