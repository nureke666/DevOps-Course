> Источник: `01_getting_started.txt` (Linux Journey → Grasshopper)

> и понимать, почему в проде почти всегда Ubuntu LTS / Debian / RHEL-совместимые.

## 🗺️ Схема: из чего состоит «Linux»

```text:no-line-numbers
        ┌─────────────────────────────────────────────────────────┐
        │  USER SPACE (пользовательское пространство)             │
        │  nginx, python, bash, systemd, ваш код, apt, ssh...     │
        └───────────────────────┬─────────────────────────────────┘
                                │  system calls (open, read, write, fork…)
        ┌───────────────────────▼─────────────────────────────────┐
        │  KERNEL (ядро Linux)                                    │
        │  планировщик CPU · память · файловые системы · сеть ·   │
        │  драйверы устройств · безопасность                      │
        └───────────────────────┬─────────────────────────────────┘
                                │  драйверы
        ┌───────────────────────▼─────────────────────────────────┐
        │  HARDWARE: CPU, RAM, диски, сетевые карты               │
        └─────────────────────────────────────────────────────────┘
```

**Главная мысль:** «Linux» в строгом смысле — это **только ядро**. Всё, что ты трогаешь руками
(`ls`, `bash`, `systemd`, `apt`) — это отдельные проекты (в основном GNU и другие), собранные вместе.
Такой комплект «ядро + утилиты + пакетный менеджер + установщик» называется **дистрибутивом**.

Отсюда и спор «Linux vs GNU/Linux»: технически корректно — GNU/Linux, в жизни все говорят Linux.

## 1. История: зачем это знать

Не ради дат, а чтобы понимать **почему система устроена именно так**.

```text:no-line-numbers
1969  UNIX (Ken Thompson, Dennis Ritchie, Bell Labs)
        └─ переписан на C → стал ПОРТИРУЕМЫМ → расползся по всем железкам
1983  GNU Project (Richard Stallman): "GNU's Not UNIX"
        └─ сделали компилятор gcc, bash, coreutils, лицензию GPL
        └─ НО своё ядро (GNU Hurd) так и не довели до прода
1991  Linus Torvalds (студент из Хельсинки) пишет ядро как хобби
1992  Ядро выходит под GPL → GNU-утилиты + ядро Linux = полноценная ОС
```

**Что реально важно из истории:**

| Факт | Почему важно тебе как DevOps |
|------|------------------------------|
| UNIX переписали на C | Отсюда «всё есть файл», пайпы, простые утилиты — философия UNIX, на которой держится вся работа в терминале |
| GPL (copyleft) | Изменил код — обязан открыть изменения. Поэтому вендоры не могут «закрыть» ядро |
| У GNU не было ядра | Linux заполнил ровно эту дыру — поэтому связка и взлетела |
| Ядро — менеджер ресурсов | Когда «сервер тормозит», ты дебажишь именно распределение CPU/RAM/IO ядром |

**Философия UNIX** (запомни — она объясняет 90% решений в Linux):
1. Каждая программа делает **одну вещь** хорошо.
2. Программы соединяются через **текстовые потоки** (пайпы).
3. **Всё есть файл** — диск, сокет, процесс, даже настройки ядра.

Именно поэтому `cat access.log | grep 500 | wc -l` работает, а не требует специального «лог-анализатора».

## 2. Дистрибутив: что это на самом деле

Дистрибутив = **ядро** + **набор утилит** + **пакетный менеджер** + **политика релизов** + **поддержка**.

```text:no-line-numbers
Дистрибутив
├── Ядро Linux (одно и то же везде, отличается версией/патчами)
├── libc (обычно glibc; в Alpine — musl!)
├── coreutils (ls, cp, cat…)
├── init-система (сейчас почти везде systemd)
├── Пакетный менеджер ← ГЛАВНОЕ ОТЛИЧИЕ НА ПРАКТИКЕ
│     ├── apt/dpkg  → Debian, Ubuntu
│     ├── dnf/rpm   → Fedora, RHEL, Rocky, AlmaLinux
│     ├── zypper    → openSUSE
│     ├── pacman    → Arch
│     └── portage   → Gentoo (сборка из исходников)
└── Модель релизов
      ├── fixed / point release → Debian, Ubuntu, RHEL  (стабильно, редко обновляется)
      └── rolling release       → Arch, openSUSE Tumbleweed (всегда свежее, чаще ломается)
```

### Два мира пакетов — знай оба

| | Debian-семья | RHEL-семья |
|---|---|---|
| Пакет | `.deb` | `.rpm` |
| Низкий уровень | `dpkg` | `rpm` |
| Высокий уровень (с зависимостями) | `apt` | `dnf` (раньше `yum`) |
| Список репозиториев | `/etc/apt/sources.list`, `/etc/apt/sources.list.d/` | `/etc/yum.repos.d/*.repo` |
| Установить | `apt install nginx` | `dnf install nginx` |
| Обновить всё | `apt update && apt upgrade` | `dnf upgrade` |
| Найти | `apt search nginx` | `dnf search nginx` |
| Где живут веб-файлы | `/var/www/html` | `/usr/share/nginx/html` |
| Юзер веб-сервера | `www-data` | `nginx` / `apache` |

👉 Работодатели делятся ровно так же: банки/энтерпрайз — RHEL/Rocky, стартапы/облака — Ubuntu/Debian.
Ты должен уметь работать в обоих. Основная база — Ubuntu (у тебя в Vagrant она), но `dnf` тоже потрогай.

## 3. Разбор дистрибутивов (как в курсе, но с DevOps-оптикой)

### Debian
- Праматерь Ubuntu и ещё сотни дистрибутивов.
- Ветки: **stable** (старый, но кремень) → **testing** → **unstable (sid)**.
- Полностью community-driven, никакой компании сверху.
- **Где встретишь:** базовые Docker-образы (`FROM debian:12-slim`), «серьёзные» серверы, где важна стабильность.

### Ubuntu
- Основана на Debian, компания **Canonical**.
- Релизы каждые 6 месяцев (`YY.MM`: 24.04, 24.10), **LTS раз в 2 года** — поддержка 5 лет (+ESM до 10).
- **Правило прода: только LTS.** `22.04`, `24.04` — да. `23.10` — нет.
- **Где встретишь:** дефолт в AWS/GCP/Azure, CI-раннеры, 90% туториалов.

### Red Hat Enterprise Linux (RHEL)
- Платная подписка = поддержка + сертификация + долгий жизненный цикл (10 лет).
- Бесплатные клоны 1:1: **Rocky Linux**, **AlmaLinux** (после того, как CentOS превратился в CentOS Stream — «бету» RHEL).
- **Где встретишь:** банки, телеком, госсектор, OpenShift.

### Fedora
- «Полигон» Red Hat: свежайшие технологии, релиз каждые ~6 месяцев, поддержка ~13 месяцев.
- Что взлетело в Fedora → через годы приезжает в RHEL.
- **Для сервера не берут** (слишком короткая поддержка), для рабочей станции девопса — отличный выбор.

### Linux Mint
- Ubuntu-based, дружелюбный десктоп (Cinnamon), классический вид.
- Для серверов не используют. Хороший «первый Linux» для десктопа.

### Gentoo
- Всё собирается из исходников (`portage`, `emerge`), максимальный контроль и оптимизация.
- Долго, сложно. **Ценность для тебя:** заставляет понять, как ПО реально собирается (флаги, зависимости, USE-флаги).

### Arch Linux
- Rolling release, ставишь голую систему и собираешь вручную. `pacman` + AUR.
- Легендарная **Arch Wiki** — лучшая документация по Linux вообще, пользуйся ей даже сидя на Ubuntu.
- Для прода — нет (rolling = непредсказуемые обновления).

### openSUSE
- **Leap** (стабильный, привязан к SUSE Linux Enterprise) и **Tumbleweed** (rolling).
- Фишка — **YaST** (мощный центр настройки) и `zypper`. Популярен в Европе, особенно в Германии.

### Linux для кибербезопасности
- **Kali Linux** (Debian-based) — пентест, куча инструментов из коробки.
- **Parrot OS** — то же + приватность.
- **Tails** — амнезийная система с флешки, всё через Tor.
- Как повседневная/серверная ОС не используются, это «чемодан с инструментами».

### 🎯 Шпаргалка «что выбрать»

| Задача | Выбор |
|--------|-------|
| Прод-сервер, облако | Ubuntu **LTS** или Debian stable |
| Энтерпрайз с поддержкой/комплаенсом | RHEL (или Rocky/Alma бесплатно) |
| Рабочий ноут девопса | Ubuntu LTS / Fedora / (Arch если любишь боль и контроль) |
| Контейнер | `debian-slim`, `ubuntu`, `alpine` (musl — осторожно!), `distroless` |
| Учиться внутренностям | Gentoo / Arch / LFS |
| Пентест | Kali / Parrot |

⚠️ **Про Alpine:** он крошечный (5 МБ), но использует **musl** вместо glibc. Скомпилированные под glibc
бинарники и некоторые Python-колёса там ломаются. Классические грабли новичка в Docker.

## 4. Как понять, на чём ты сейчас сидишь

```bash
# Универсально (есть на всех современных дистрибутивах)
cat /etc/os-release
# NAME="Ubuntu"
# VERSION="22.04.3 LTS (Jammy Jellyfish)"
# ID=ubuntu
# ID_LIKE=debian          ← вот это главное для скриптов!
# VERSION_ID="22.04"

lsb_release -a          # если установлен пакет lsb-release
hostnamectl             # хост + ОС + версия ядра + виртуализация

uname -a                # всё о ядре
# Linux learn-linux 5.15.0-91-generic #101-Ubuntu SMP x86_64 GNU/Linux
#   │        │           │                              │
#   ядро   hostname   версия ядра                   архитектура

uname -r                # только версия ядра  → 5.15.0-91-generic
uname -m                # архитектура          → x86_64 (или aarch64 на ARM)
arch                    # то же самое
```

💡 **В скриптах** определяй семейство через `ID_LIKE`, а не через красивое имя:

```bash
. /etc/os-release
case "$ID_LIKE $ID" in
  *debian*) PKG="apt-get -y install" ;;
  *rhel*|*fedora*) PKG="dnf -y install" ;;
  *) echo "unsupported distro: $ID" >&2; exit 1 ;;
esac
$PKG curl
```

Разбор версии ядра `5.15.0-91-generic`:
- `5` — major, `15` — minor, `0` — patch
- `-91` — сборка дистрибутива (Ubuntu бэкпортит патчи, не меняя основную версию)
- `generic` — вариант сборки (бывают `-aws`, `-kvm`, `-lowlatency`)

## 5. Where to get help (даже до изучения `man`)

```bash
man ls              # полная документация (q — выход, /слово — поиск)
ls --help           # короткая справка, обычно достаточно
info coreutils      # GNU-шный формат, подробнее man
whatis ls           # одна строка: что это такое
apropos "list dir"  # поиск команды по описанию, когда не знаешь имени
```

Порядок действий, когда застрял:
1. `--help` → 2. `man` → 3. **Arch Wiki** (даже на Ubuntu) → 4. официальная docs дистрибутива →
5. Stack Overflow / ServerFault → 6. исходники/issue-трекер.

⚠️ Правило безопасности: **никогда не копируй команду с `sudo` из интернета, не поняв её.**
Классика жанра — `sudo rm -rf /` и «удали ~/.config чтобы починить» на проде.

## 💼 Как это в DevOps

- **Dockerfile:** `FROM ubuntu:22.04` — ты выбираешь дистрибутив каждый раз, когда пишешь образ.
  Размер образа, наличие пакетов, дефолтный юзер — всё отсюда.
- **Terraform/AMI:** выбирая образ ВМ в облаке, ты выбираешь дистрибутив + версию ядра.
- **Ansible:** роли пишут с `when: ansible_os_family == "Debian"` — это то же семейство.
- **CVE и обновления:** «ядро 5.15 уязвимо» → надо знать `uname -r` и как накатить обновление.
- **LTS-мышление:** в проде ценится предсказуемость, а не свежесть. Rolling release в проде — красный флаг.

## 🧠 Что запомнить (must-know)

1. **Linux = ядро.** Дистрибутив = ядро + userspace + пакетный менеджер + модель релизов.
2. Два мира: **deb/apt** (Debian, Ubuntu) и **rpm/dnf** (RHEL, Fedora, Rocky). Уметь надо оба.
3. **В прод — только LTS/stable.** Rolling release (Arch, Tumbleweed) — для рабочей станции, не для сервера.
4. `/etc/os-release` — универсальный способ определить систему; `ID_LIKE` — для скриптов.
5. Ядро управляет CPU, памятью, устройствами и сетью. Любой перформанс-дебаг упирается в него.
6. Философия UNIX (одна утилита = одна задача + пайпы + всё есть файл) объясняет, почему терминал так силён.

### Блок A. Теория (ответь письменно, 1-3 предложения)

**A1.** Что такое ядро Linux и чем оно отличается от дистрибутива?

<details><summary>Ответ</summary>

Ядро — это программа-посредник между железом и остальным ПО: распределяет CPU, память,
доступ к дискам и сети, предоставляет системные вызовы. Дистрибутив — готовый комплект: ядро +
системные утилиты + libc + init + пакетный менеджер + политика релизов и поддержки.

</details>

**A2.** Почему связка «GNU + Linux» вообще сложилась? Чего не хватало каждой стороне?

<details><summary>Ответ</summary>

У проекта GNU были все утилиты и компилятор, но не было рабочего ядра (Hurd так и не дошёл до
продакшена). У Торвальдса было ядро, но не было пользовательских программ. Сложив их под GPL,
получили полноценную свободную ОС.

</details>

**A3.** Почему переписывание UNIX на C в 1970-х оказалось поворотным моментом?

<details><summary>Ответ</summary>

C — переносимый язык: система перестала быть привязанной к одной архитектуре. UNIX смог
работать на разном железе, что и обеспечило распространение и появление множества потомков.

</details>

**A4.** Чем отличается **fixed release** от **rolling release**? Приведи по 2 примера и скажи, что выберешь для прод-сервера и почему.

<details><summary>Ответ</summary>

Fixed release — фиксированный набор версий пакетов, обновляется большими релизами
(Debian stable, Ubuntu LTS, RHEL): предсказуемо, только security-патчи. Rolling — пакеты обновляются
непрерывно (Arch, openSUSE Tumbleweed): всегда свежее, но обновление может сломать прод в любой
момент и сложно воспроизвести окружение. **Для прода — fixed**, потому что важнее предсказуемость и
возможность повторить ту же конфигурацию через год.

</details>

**A5.** Ubuntu 24.04 и Ubuntu 24.10 — в чём принципиальная разница? Какую поставишь на боевой сервер?

<details><summary>Ответ</summary>

`24.04` — LTS: поддержка 5 лет (до 10 с ESM). `24.10` — промежуточный релиз, поддержка 9 месяцев,
после чего надо срочно мигрировать. На боевой сервер — **24.04 LTS**.

</details>

**A6.** Что случилось с CentOS и чем его заменяют сейчас?

<details><summary>Ответ</summary>

Red Hat превратил CentOS Linux (стабильный клон RHEL) в **CentOS Stream** — ветку *перед* RHEL,
то есть по сути его тестовую версию. Сообщество ответило форками: **Rocky Linux** и **AlmaLinux**,
они бинарно совместимы с RHEL и бесплатны.

</details>

**A7.** У тебя есть Docker-образ приложения на Python с C-расширениями, собранный под Debian. Почему при переезде на `alpine` он может сломаться?

<details><summary>Ответ</summary>

Alpine использует libc-реализацию **musl**, а не **glibc**. Бинарники и Python-колёса (wheels),
собранные под glibc, там не запустятся или будут падать; плюс отличаются пути, отсутствуют привычные
пакеты, другой шелл (`ash`, не `bash`). Лечится сборкой под musl или переходом на `*-slim` (Debian).

</details>

**A8.** Назови три принципа философии UNIX и покажи на примере одной команды, как они работают вместе.

<details><summary>Ответ</summary>

(1) Одна программа — одна задача; (2) программы соединяются текстовыми потоками; (3) всё есть файл.
Пример: `cat /var/log/syslog | grep error | wc -l` — `cat` только читает файл, `grep` только фильтрует,
`wc` только считает; данные текстом текут через пайпы; лог — обычный файл, как и всё остальное.

</details>

### Блок B. «Что делает команда / что выведет»

Не запуская — скажи, что делает каждая команда и зачем она нужна. Потом проверь на стенде.

```bash
B1.  uname -r
B2.  uname -m
B3.  cat /etc/os-release
B4.  hostnamectl
B5.  nproc && free -h
B6.  grep '^ID_LIKE=' /etc/os-release
B7.  apropos "change password"
B8.  whatis uname
```

<details><summary>Ответ</summary>

- **B1.** Версия ядра, например `5.15.0-91-generic`.
- **B2.** Архитектура машины: `x86_64` (Intel/AMD 64-bit) или `aarch64` (ARM).
- **B3.** Файл с описанием дистрибутива в формате `KEY=value`: `NAME`, `VERSION`, `ID`, `ID_LIKE`, `VERSION_ID`. Универсальный способ определить систему.
- **B4.** Сводка от systemd: hostname, Machine ID, Boot ID, тип виртуализации, ОС, версия ядра, архитектура.
- **B5.** `nproc` — количество доступных процессорных ядер; `free -h` — использование RAM и swap в удобных единицах (Gi/Mi).
- **B6.** Выведет строку `ID_LIKE=debian` — семейство дистрибутива. Якорь `^` нужен, чтобы не поймать другие строки.
- **B7.** Поиск по описаниям man-страниц: найдёт `passwd`, `chpasswd`, `gpasswd` и т.п. Нужна, когда знаешь *что* хочешь, но не знаешь *как называется*.
- **B8.** Одна строка с описанием: `uname (1) - print system information`.

</details>

**B9.** Чем отличается вывод `uname -a` от `hostnamectl`? Что есть в одном и нет в другом?

<details><summary>Ответ</summary>

`uname -a` — про ядро: имя ядра, hostname, версия/сборка, дата сборки, архитектура.
`hostnamectl` — про систему целиком: hostname, Machine/Boot ID, **тип виртуализации** (`kvm` — важно!),
название и версию **ОС**, ядро, архитектуру. Названия дистрибутива в `uname` нет, а типа виртуализации нет в `uname`.

</details>

**B10.** В версии ядра `5.15.0-91-generic` — что означает каждая часть?

<details><summary>Ответ</summary>

`5` — major, `15` — minor, `0` — patchlevel (upstream-версия ядра),
`-91` — номер сборки дистрибутива (Ubuntu бэкпортит исправления, не меняя upstream-версию),
`generic` — вариант сборки (бывают `aws`, `kvm`, `lowlatency`).

</details>

**C6.** Открой `man man`. Найди, что означают цифры-секции (1, 5, 8). Затем открой страницу

<details><summary>Ответ</summary>

</details>

### Блок D. Разбор инцидента (как на работе)

**D1.** Коллега прислал инструкцию по установке:
```bash
sudo yum install -y nginx
```
Ты выполняешь её на своём стенде — команда не находится. Что произошло и какие два варианта решения (правильный и костыльный)?

<details><summary>Ответ</summary>

`yum` — пакетный менеджер RHEL-семейства, а твой стенд на Ubuntu (Debian-семейство), там `apt`.
**Правильно:** перевести инструкцию — `sudo apt update && sudo apt install -y nginx`.
**Костыльно:** поставить транслятор вроде `alien`/эмуляцию — так не делают, ломает систему пакетов.
Вывод для работы: любая инструкция бесполезна без указания дистрибутива и версии.

</details>

**D2.** В CI упала сборка с ошибкой `E: Unable to locate package python3.11`.
В `Dockerfile` написано `FROM ubuntu:20.04`. Какая гипотеза первая и как проверишь?

<details><summary>Ответ</summary>

Гипотеза: в репозиториях Ubuntu 20.04 (focal) просто нет пакета `python3.11` — там `python3.8`.
Проверка: `docker run --rm ubuntu:20.04 bash -c 'apt update && apt-cache policy python3.11'`.
Решения: взять `ubuntu:22.04`/`24.04`, подключить PPA `deadsnakes`, или использовать официальный
образ `python:3.11-slim`. Последний вариант — предпочтительный.

</details>

**D3.** Тимлид говорит: «Ставим на прод Arch, там всё свежее и быстрее». Сформулируй 3 аргумента против
на языке рисков (не «мне не нравится»).

<details><summary>Ответ</summary>

(1) **Непредсказуемость обновлений** — rolling может привезти мажорную версию библиотеки в любой
день, воспроизвести старое окружение нельзя. (2) **Нет длинной поддержки и security-политики** —
никто не гарантирует бэкпорт патчей в старую версию, только «обнови всё». (3) **Экосистема**:
вендорские агенты (мониторинг, бэкап, драйверы), Ansible-роли и документация пишутся под LTS-дистрибутивы —
вырастет стоимость поддержки, а найм и онбординг усложнятся.

</details>

### Блок E. Вопросы с собеседования

**1.** Чем Linux отличается от Unix?

<details><summary>Ответ</summary>

UNIX — оригинальная проприетарная ОС (и стандарт POSIX), Linux — свободное ядро, написанное с нуля,
UNIX-подобное по интерфейсу, но не содержащее его кода.

</details>

**2.** Что такое дистрибутив? Назови 3 из разных семейств и их пакетные менеджеры.

<details><summary>Ответ</summary>

Дистрибутив — комплект «ядро + userspace + пакетный менеджер + политика поддержки».
Ubuntu/Debian → `apt`, RHEL/Rocky/Fedora → `dnf`, Arch → `pacman`.

</details>

**3.** Что значит LTS и почему это важно для прода?

<details><summary>Ответ</summary>

LTS — Long Term Support, релиз с длительной поддержкой (Ubuntu — 5 лет). Для прода важно,
чтобы security-патчи приходили годами без мажорной миграции.

</details>

**4.** Как узнать версию ОС и ядра на незнакомом сервере?

<details><summary>Ответ</summary>

`cat /etc/os-release`, `hostnamectl`, `uname -r`.

</details>

**5.** Чем `apt` отличается от `dpkg`?

<details><summary>Ответ</summary>

`dpkg` ставит конкретный `.deb` и **не умеет** разрешать зависимости; `apt` работает с репозиториями,
тянет зависимости, обновляет систему. `apt` — надстройка над `dpkg`.

</details>

**6.** Что такое GPL и чем она отличается от MIT-лицензии в двух словах?

<details><summary>Ответ</summary>

GPL — copyleft: производные работы должны распространяться под той же лицензией с открытым кодом.
MIT — permissive: можно закрыть код и использовать в проприетарном продукте, сохранив упоминание авторства.

</details>

**7.** Почему в контейнерах часто используют slim/alpine образы и какие с этим проблемы?

<details><summary>Ответ</summary>

Меньше образ → быстрее выкатка, меньше поверхность атаки и меньше CVE. Проблемы: нет привычных
утилит для отладки, Alpine на musl ломает glibc-бинарники, часть пакетов отсутствует.

</details>
