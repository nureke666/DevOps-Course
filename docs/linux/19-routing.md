## 🗺️ Схема: как пакет находит дорогу

```text:no-line-numbers
  Хост 10.0.1.5 хочет отправить пакет на 93.184.216.34
                        │
                        ▼
        ┌───────────────────────────────────────┐
        │ Смотрю СВОЮ таблицу маршрутизации      │
        │ Адрес назначения в моей подсети?       │
        └───────────┬───────────────┬───────────┘
                 ДА │               │ НЕТ
                    ▼               ▼
         ┌────────────────┐   ┌──────────────────────────┐
         │ ARP → MAC      │   │ Найти самый ТОЧНЫЙ        │
         │ отправить      │   │ подходящий маршрут        │
         │ напрямую       │   │ (longest prefix match)    │
         └────────────────┘   │ → обычно default gateway  │
                              └───────────┬──────────────┘
                                          ▼
                              ARP на MAC ШЛЮЗА, отправка ему
                                          │
                          ┌───────────────▼────────────────┐
                          │ Роутер: TTL−1, смена MAC,       │
                          │ поиск в СВОЕЙ таблице,          │
                          │ передача следующему хопу        │
                          └───────────────┬────────────────┘
                                          ▼
                                   … и так до цели
```

🔑 **Ключевой факт:** на каждом хопе меняется **MAC** (L2), а **IP** источника и назначения
остаются прежними (L3). Исключение — NAT.

## 1. What is a router — что делает маршрутизатор

Маршрутизатор соединяет **разные сети** и решает, куда передать пакет дальше:
1. Принимает пакет.
2. Смотрит IP назначения.
3. Ищет в таблице маршрутизации самое точное совпадение.
4. Уменьшает TTL на 1 (если TTL = 0 — отбрасывает и шлёт ICMP `Time Exceeded` — на этом
   основан `traceroute`).
5. Пересобирает L2-заголовок (новый MAC) и отправляет дальше.

| Устройство | Уровень | Что делает |
|-----------|---------|-----------|
| **Hub** | L1 | Повторяет сигнал на все порты (устарел) |
| **Switch** | L2 | Коммутирует по MAC внутри одной сети |
| **Router** | L3 | Маршрутизирует между сетями по IP |
| **L3-switch** | L2+L3 | Коммутация + маршрутизация |
| **Firewall** | L3-L7 | Фильтрация трафика |
| **Load balancer** | L4/L7 | Распределение нагрузки |

В Linux любой хост может стать маршрутизатором:
```bash
sudo sysctl -w net.ipv4.ip_forward=1
echo 'net.ipv4.ip_forward=1' | sudo tee /etc/sysctl.d/99-router.conf
```
Именно это включают Docker и Kubernetes на каждой ноде.

## 2. Routing Table — таблица маршрутизации

```bash
ip route                     # ⭐ основная команда
ip -6 route
ip route show table all
route -n                     # устаревшая (net-tools)
netstat -rn                  # устаревшая
```

Типичный вывод:
```text:no-line-numbers
default via 10.0.2.2 dev eth0 proto dhcp metric 100
10.0.2.0/24 dev eth0 proto kernel scope link src 10.0.2.15 metric 100
192.168.56.0/24 dev eth1 proto kernel scope link src 192.168.56.10
172.17.0.0/16 dev docker0 proto kernel scope link src 172.17.0.1 linkdown
```

Как читать:

| Часть | Смысл |
|-------|-------|
| `default` | Маршрут по умолчанию (= `0.0.0.0/0`) — куда всё, что не подошло |
| `via 10.0.2.2` | Через какой шлюз (next hop) |
| `dev eth0` | Через какой интерфейс |
| `proto kernel/dhcp/static` | Кто добавил маршрут |
| `scope link` | Сеть подключена напрямую, шлюз не нужен |
| `src 10.0.2.15` | Какой адрес источника использовать |
| `metric 100` | Приоритет: **чем меньше, тем предпочтительнее** |

### 🔑 Longest prefix match — главное правило

Если подходит несколько маршрутов, выбирается **самый специфичный** (с самым длинным префиксом):

```text:no-line-numbers
Пакет на 10.0.5.20
  0.0.0.0/0      → default           ← подходит (префикс 0)
  10.0.0.0/8     → via 192.168.1.1   ← подходит (префикс 8)
  10.0.5.0/24    → via 192.168.1.2   ← подходит (префикс 24)  ✅ ВЫБРАН
```

Проверить решение ядра для конкретного адреса:
```bash
ip route get 8.8.8.8
# 8.8.8.8 via 10.0.2.2 dev eth0 src 10.0.2.15 uid 1000
ip route get 192.168.56.11
```
💡 `ip route get` — самая недооценённая команда: она показывает **реальное решение ядра**,
а не заставляет тебя читать таблицу глазами.

### Управление маршрутами

```bash
# Добавить
sudo ip route add 10.10.0.0/16 via 192.168.56.1 dev eth1
sudo ip route add default via 192.168.1.1
sudo ip route add 192.168.99.0/24 dev eth1          # напрямую, без шлюза

# Изменить / удалить
sudo ip route replace 10.10.0.0/16 via 192.168.56.2
sudo ip route del 10.10.0.0/16

# Заблокировать направление
sudo ip route add blackhole 10.20.0.0/16
```
⚠️ Эти изменения **не переживут перезагрузку**. Постоянно — через netplan / NetworkManager /
`/etc/network/interfaces` (тема [20. Network Config](/linux/20-network-config)).

**Политики маршрутизации** (несколько таблиц — например, разный выход для разных источников):
```bash
ip rule show
ip route show table 100
sudo ip rule add from 192.168.56.0/24 table 100
```

## 3. Path of a Packet — путь пакета

```text:no-line-numbers
Браузер на 10.0.1.5 → https://example.com (93.184.216.34)

1. DNS: example.com → 93.184.216.34                 (тема 22)
2. Хост: 93.184.216.34 в моей подсети 10.0.1.0/24?  → нет
3. Ищу маршрут → default via 10.0.1.1
4. ARP: кто такой 10.0.1.1? → MAC шлюза             (тема 17)
5. Кадр: src MAC=мой, dst MAC=шлюз | IP src=10.0.1.5, dst=93.184.216.34
6. Шлюз: TTL 64→63, ищет маршрут, меняет MAC, шлёт провайдеру
7. …десяток хопов, на каждом TTL−1 и новый MAC…
8. Возможен NAT: src IP 10.0.1.5 → 203.0.113.7
9. Сервер получает пакет, отвечает — обратный путь может быть ДРУГИМ
```

**TTL** (Time To Live) — защита от петель: на каждом хопе −1; при 0 пакет отбрасывается,
отправителю уходит ICMP `Time Exceeded`. На этом построен `traceroute`.

Начальные значения TTL помогают угадать ОС: Linux — 64, Windows — 128, сетевое оборудование — 255.

```bash
traceroute -n 8.8.8.8         # путь до цели (UDP по умолчанию)
traceroute -I -n 8.8.8.8      # через ICMP
tracepath 8.8.8.8             # + определение MTU, без root
mtr -n 8.8.8.8                # ⭐ traceroute + ping в реальном времени — лучший инструмент
ping -t 5 8.8.8.8             # ограничить TTL
```

⚠️ **Асимметричная маршрутизация** — нормальное явление в интернете: пакеты туда и обратно могут
идти разными путями. Поэтому `traceroute` показывает только путь «туда», а звёздочки `* * *`
означают лишь то, что хоп не отвечает на ICMP — не обязательно проблему.

## 4. Routing Protocols — классификация

```text:no-line-numbers
                    ПРОТОКОЛЫ МАРШРУТИЗАЦИИ
                             │
          ┌──────────────────┴──────────────────┐
      IGP (внутри автономной системы)      EGP (между AS)
          │                                     │
   ┌──────┴───────┐                           BGP
   ▼              ▼
Distance Vector   Link State
(RIP, EIGRP)      (OSPF, IS-IS)
```

**Статическая маршрутизация** — маршруты прописаны вручную: предсказуемо, но не адаптируется
к авариям; подходит для маленьких и стабильных сетей (и для серверов).
**Динамическая** — маршрутизаторы обмениваются информацией и сами перестраивают пути.

**Метрика** — по какому критерию выбирается лучший путь: число хопов (RIP), пропускная
способность (OSPF), задержка, стоимость, политика (BGP).

**AS (Autonomous System)** — сеть под единым административным управлением со своим номером ASN.
Интернет — это ~75 000 AS, связанных между собой через BGP.

## 5. Distance Vector — «по слухам от соседей»

Каждый маршрутизатор сообщает соседям **свою таблицу** («до сети X мне N хопов»),
соседи прибавляют 1 и выбирают лучший вариант.

- **RIP**: метрика — число хопов, максимум 15 (16 = недостижимо), обновления каждые 30 с.
- Плюсы: простота, мало ресурсов.
- Минусы: медленная сходимость, **count-to-infinity**, не масштабируется.
- Защиты: split horizon (не объявлять маршрут обратно тому, от кого узнал), route poisoning,
  hold-down таймеры.

Сегодня RIP — практически музей, но принцип «каждый знает только со слов соседа» важен
для понимания BGP (который тоже path-vector, то есть развитие идеи).

---

## 6. Link State — «у каждого своя карта»

Каждый маршрутизатор рассылает информацию **о своих линках** (LSA) всем в области;
все строят одинаковую карту сети и считают кратчайшие пути алгоритмом **Дейкстры**.

- **OSPF** (Open Shortest Path First) — стандарт IGP в корпоративных сетях; метрика — cost,
  обратно пропорциональный полосе; иерархия областей (area 0 — магистраль).
- **IS-IS** — похож, популярен у операторов связи.
- Плюсы: быстрая сходимость, масштабируемость, точный выбор пути.
- Минусы: требовательнее к CPU/памяти, сложнее в настройке.

| | Distance Vector | Link State |
|---|-----------------|------------|
| Что рассылают | свою таблицу маршрутов | состояние своих линков |
| Знание сети | только «через соседа» | полная карта области |
| Алгоритм | Беллмана-Форда | Дейкстры |
| Сходимость | медленная | быстрая |
| Примеры | RIP, EIGRP (гибрид) | OSPF, IS-IS |

## 7. BGP — протокол, на котором держится интернет

**BGP** (Border Gateway Protocol, текущая версия BGP-4) — **path-vector** протокол между
автономными системами. Работает поверх TCP, порт **179**.

- **eBGP** — между разными AS (провайдеры, точки обмена трафиком).
- **iBGP** — внутри одной AS.
- Выбор маршрута определяется **политиками** (LOCAL_PREF, AS_PATH, MED, communities),
  а не только «кратчайшим путём»: это протокол бизнес-отношений, а не математики.
- Хранит `AS_PATH` — список AS, через которые прошёл анонс (защита от петель и основа фильтрации).

**Почему это важно знать девопсу:**
- **BGP hijacking** — чужая AS анонсирует твои префиксы, трафик уходит не туда.
  Защита: RPKI, IRR-фильтры, мониторинг анонсов.
- Крупные аварии интернета (Facebook 2021, Cloudflare, Rostelecom leaks) — это BGP.
- **Anycast** (один адрес анонсируется из многих точек) — основа CDN и публичных DNS
  (`1.1.1.1`, `8.8.8.8`).
- В дата-центрах: **BGP в ClosFabric** и `MetalLB` в BGP-режиме для Kubernetes on-prem.
- Провайдеры распределяют нагрузку и переключают трафик при авариях именно политиками BGP.

```bash
whois -h whois.radb.net 8.8.8.8 | head -20
mtr -n --report --report-cycles 5 1.1.1.1
# посмотреть AS-путь: сервисы вроде bgp.he.net, RIPEstat, looking glass провайдеров
```

## 🧪 Мини-лаба (нужен стенд из двух ВМ, см. тему 17)

```bash
vagrant ssh web

# 1. Чтение таблицы
ip route
ip -br addr
ip route get 8.8.8.8
ip route get 192.168.56.11
ip route get 127.0.0.1

# 2. Longest prefix match на практике
sudo ip route add 8.8.8.0/24 via 192.168.56.11 dev eth1
ip route get 8.8.8.8              # теперь через 192.168.56.11, а не через default!
sudo ip route del 8.8.8.0/24
ip route get 8.8.8.8              # вернулось к default

# 3. Добавление, замена, удаление маршрута
sudo ip route add 10.99.0.0/16 via 192.168.56.11 dev eth1
ip route | grep 10.99
sudo ip route replace 10.99.0.0/16 dev eth1
ip route | grep 10.99
sudo ip route del 10.99.0.0/16

# 4. Blackhole
sudo ip route add blackhole 10.88.0.0/16
ip route get 10.88.0.1            # покажет blackhole
ping -c1 -W1 10.88.0.1 || echo "заблокировано (как и ожидалось)"
sudo ip route del blackhole 10.88.0.0/16

# 5. TTL и traceroute
sudo apt install -y traceroute mtr-tiny
ping -c1 -t 1 8.8.8.8 || true     # TTL 1 → Time exceeded от первого роутера
traceroute -n 8.8.8.8
tracepath 8.8.8.8
mtr -n --report --report-cycles 3 8.8.8.8

# 6. Сделать из web маршрутизатор для app (учебно)
# на web:
sudo sysctl -w net.ipv4.ip_forward=1
sudo iptables -t nat -A POSTROUTING -s 192.168.56.0/24 -o eth0 -j MASQUERADE
# на app:
sudo ip route add 1.1.1.1/32 via 192.168.56.10 dev eth1
ip route get 1.1.1.1
ping -c2 1.1.1.1
traceroute -n 1.1.1.1 | head -3   # первый хоп — 192.168.56.10
# уборка на app:
sudo ip route del 1.1.1.1/32
# уборка на web:
sudo iptables -t nat -D POSTROUTING -s 192.168.56.0/24 -o eth0 -j MASQUERADE
sudo sysctl -w net.ipv4.ip_forward=0

# 7. Маршруты Docker (если установлен)
ip route | grep docker || echo "docker не установлен"

# 8. Policy routing
ip rule show
```

## 🧠 Что запомнить

1. Маршрутизатор работает на **L3**: смотрит IP, уменьшает TTL, меняет MAC, отправляет дальше.
2. **Longest prefix match** — побеждает самый точный маршрут, не первый попавшийся.
3. `default` (`0.0.0.0/0`) — куда уходит всё, что не подошло ни под один маршрут.
4. `ip route get <IP>` показывает **реальное решение ядра** — используй вместо чтения таблицы глазами.
5. `ip route add` не переживает перезагрузку → закрепляй в netplan/NetworkManager.
6. MAC меняется на каждом хопе, IP — нет (кроме NAT). TTL уменьшается на каждом хопе.
7. Distance vector (RIP) — «со слов соседа»; link state (OSPF) — «полная карта и Дейкстра».
8. BGP — между автономными системами, поверх TCP/179, решения принимаются **политиками**.
   На нём держится интернет, и с ним же связаны крупнейшие аварии.
9. Асимметричная маршрутизация — норма; `traceroute` показывает только путь «туда»,
   а `* * *` означает лишь молчание хопа на ICMP.

### Блок A. Теория

**A1.** Что делает маршрутизатор с пакетом? Перечисли 5 шагов.

<details><summary>Ответ</summary>

(1) Принимает кадр и извлекает IP-пакет. (2) Смотрит адрес назначения.
(3) Ищет в таблице маршрутизации наиболее точное совпадение. (4) Уменьшает TTL на 1 (при 0 —
отбрасывает и шлёт ICMP Time Exceeded). (5) Формирует новый L2-заголовок (MAC следующего хопа)
и отправляет в нужный интерфейс.

</details>

**A2.** Что меняется в пакете на каждом хопе, а что остаётся неизменным?

<details><summary>Ответ</summary>

Меняются: MAC источника и назначения (каждый хоп), TTL (−1), контрольная сумма заголовка.
Остаются: IP источника и назначения, порты, данные — **кроме случая NAT**, где адрес/порт
источника (SNAT) или назначения (DNAT) подменяются.

</details>

**A3.** Чем switch отличается от router? На каких уровнях они работают?

<details><summary>Ответ</summary>

Switch работает на L2: коммутирует кадры по MAC-адресам внутри одного
широковещательного домена. Router работает на L3: соединяет **разные** сети, принимает решения
по IP-адресам и таблице маршрутизации, изолирует широковещательные домены.

</details>

**A4.** Что такое таблица маршрутизации? Разбери по полям строку:
```text:no-line-numbers
default via 10.0.2.2 dev eth0 proto dhcp metric 100
```

<details><summary>Ответ</summary>

`default` — префикс `0.0.0.0/0` (всё остальное); `via 10.0.2.2` — следующий хоп;
`dev eth0` — исходящий интерфейс; `proto dhcp` — маршрут получен по DHCP;
`metric 100` — приоритет (меньше = предпочтительнее).

</details>

**A5.** Что означает `scope link` в выводе `ip route`?

<details><summary>Ответ</summary>

Сеть подключена напрямую к интерфейсу: для доставки не нужен шлюз, достаточно ARP
и отправки кадра в этот интерфейс.

</details>

**A6.** 🔑 Объясни правило **longest prefix match**. Какой маршрут выберется для `10.0.5.20`,
если в таблице есть `0.0.0.0/0`, `10.0.0.0/8` и `10.0.5.0/24`?

<details><summary>Ответ</summary>

Из всех подходящих маршрутов ядро выбирает тот, у которого **самая длинная маска**
(самое точное описание назначения). Для `10.0.5.20` подходят все три, выберется
`10.0.5.0/24` как наиболее специфичный.

</details>

**A7.** Что такое метрика маршрута? Какой маршрут предпочтительнее — с метрикой 100 или 600?

<details><summary>Ответ</summary>

Метрика — «стоимость» маршрута; при наличии нескольких маршрутов к одной сети
выбирается маршрут с **меньшей** метрикой. То есть 100 предпочтительнее 600.

</details>

**A8.** Что такое TTL и зачем он нужен? Как на нём построен `traceroute`?

<details><summary>Ответ</summary>

Time To Live — счётчик хопов, защищающий от бесконечных петель маршрутизации.
Каждый маршрутизатор уменьшает его на 1; при обнулении пакет отбрасывается и отправителю
уходит ICMP `Time Exceeded`. `traceroute` отправляет пакеты с TTL 1, 2, 3… и по адресам
источников этих ICMP-ответов восстанавливает путь.

</details>

**A9.** Почему `traceroute` может показывать `* * *` и означает ли это проблему?

<details><summary>Ответ</summary>

Хоп не отвечает на ICMP/UDP-зонды (фильтрация, rate limiting, политика провайдера),
либо ответы блокируются firewall. Это **не обязательно** проблема: если конечный хост
отвечает и сервис работает, звёздочки в середине маршрута нормальны.

</details>

**A10.** Что такое асимметричная маршрутизация? Почему она мешает диагностике?

<details><summary>Ответ</summary>

Пакеты «туда» и «обратно» идут разными путями. Мешает диагностике, потому что
`traceroute` показывает только прямой путь, а проблема (потери, фильтрация) может быть
на обратном; также ломает stateful-firewall и балансировщики, если трафик приходит
не через тот же узел.

</details>

**A11.** Чем distance vector отличается от link state? Приведи по протоколу на каждый тип.

<details><summary>Ответ</summary>

Distance vector рассылает соседям свою **таблицу маршрутов** («до сети X — N хопов»),
знание сети косвенное, сходимость медленная (RIP, EIGRP — гибрид). Link state рассылает
состояние **своих линков** всем в области, каждый строит полную карту и считает пути
алгоритмом Дейкстры, сходимость быстрая (OSPF, IS-IS).

</details>

**A12.** Что такое автономная система (AS) и BGP? Почему BGP называют «протоколом политик»?

<details><summary>Ответ</summary>

AS — сеть под единым административным управлением с собственным номером ASN.
BGP — протокол маршрутизации **между** AS, работающий поверх TCP/179. Он называется протоколом
политик, потому что лучший маршрут выбирается не по «кратчайшему пути», а по административным
правилам (LOCAL_PREF, AS_PATH, MED, communities), отражающим коммерческие отношения операторов.

</details>

**A13.** Что такое BGP hijacking и какие есть механизмы защиты?

<details><summary>Ответ</summary>

Анонс чужих префиксов из своей AS: трафик к ним начинает приходить злоумышленнику
(перехват, блокировка или подмена). Защита: RPKI/ROA (криптографическая проверка права
анонсировать префикс), фильтры на основе IRR, максимальные лимиты префиксов от пиров,
мониторинг анонсов (BGPStream, RIPE RIS, внешние сервисы алертинга).

</details>

**A14.** Что такое Anycast и где он применяется?

<details><summary>Ответ</summary>

Один и тот же IP-адрес анонсируется из многих географически разных точек, и маршрутизация
приводит клиента к ближайшей. Применяется в CDN, публичных DNS (`1.1.1.1`, `8.8.8.8`),
защите от DDoS и глобальных балансировщиках.

</details>

### Блок D. Инциденты

**D1.** Сервер не выходит в интернет. `ping 8.8.8.8` — «Network is unreachable».
Какие три вещи проверишь первыми и в каком порядке?

<details><summary>Ответ</summary>

(1) Есть ли адрес и поднят ли интерфейс: `ip -br addr`, `ip link`.
(2) Есть ли маршрут по умолчанию: `ip route | grep default` — «Network is unreachable»
почти всегда означает его отсутствие. (3) Доступен ли шлюз: `ping <gw>`, `ip neigh`
(резолвится ли MAC). Далее — firewall и NAT на стороне гипервизора/провайдера.

</details>

**D2.** `ping 8.8.8.8` работает, `ping google.com` — нет. Где проблема?
(Подсказка: это уже не маршрутизация.)

<details><summary>Ответ</summary>

Маршрутизация исправна (IP доступен), проблема в **разрешении имён** — DNS:
проверить `/etc/resolv.conf`, `resolvectl status`, `dig @1.1.1.1 google.com`,
доступность DNS-серверов и порт 53. Подробно — тема [22. DNS](/linux/22-dns).

</details>

**D3.** После добавления второго сетевого интерфейса сервер потерял связь с интернетом.
Что произошло с маршрутами и как чинить?

<details><summary>Ответ</summary>

Новый интерфейс (часто по DHCP) добавил **второй маршрут по умолчанию**, возможно
с меньшей метрикой, и трафик пошёл в сеть без выхода в интернет. Проверить `ip route`,
убрать лишний default (`ip route del default dev ethX`), задать метрики явно, а в netplan
отключить `dhcp4-overrides: use-routes: false` или `default-route: false` для второго интерфейса.

</details>

**D4.** Два маршрута до одной сети с одинаковой метрикой. Какой выберется?
Как гарантированно задать приоритет?

<details><summary>Ответ</summary>

При равных метриках поведение зависит от порядка добавления и наличия ECMP:
ядро может балансировать (multipath) или использовать первый подходящий — результат
непредсказуем для администратора. Гарантированно задать приоритет — разными **метриками**
(`ip route add ... metric 100` и `metric 200`) либо policy routing через `ip rule`.

</details>

**D5.** Приложение на сервере с двумя интерфейсами отвечает клиентам не с того адреса,
и соединения рвутся. Что происходит и как лечится?

<details><summary>Ответ</summary>

Ядро выбирает src-адрес по исходящему маршруту, а не по адресу, на который пришёл запрос;
при асимметрии ответ уходит с «неправильного» интерфейса и отбрасывается stateful-firewall
(или `rp_filter`). Решения: policy routing (отдельная таблица и `ip rule from <ip> table N`
для каждого интерфейса), явное указание `src` в маршруте, привязка приложения к конкретному
адресу (`bind`), настройка `rp_filter=2` (loose) при необходимости.

</details>

**D6.** `traceroute` до сервера обрывается на 5-м хопе звёздочками, но сайт при этом открывается.
Что это значит?

<details><summary>Ответ</summary>

Промежуточные маршрутизаторы не отвечают на зонды traceroute (фильтруют ICMP/UDP
или ограничивают частоту), но **транзитный трафик передают**. Раз сайт открывается, путь рабочий.
Для проверки лучше `mtr` (покажет потери именно на конечном хопе) и `tracepath`/`traceroute -T`
(TCP-зонды на порт 443 обычно проходят).

</details>

**D7.** После перезагрузки сервера пропал маршрут к партнёрской сети, который вчера добавляли
командой. Почему и как надо было?

<details><summary>Ответ</summary>

`ip route add` изменяет только работающее ядро и теряется при перезагрузке.
Постоянно маршрут задаётся в конфигурации сети: netplan (`routes:`), NetworkManager
(`nmcli connection modify ... +ipv4.routes`), `/etc/network/interfaces` или через
конфиг-менеджмент (Ansible). После правки — `netplan apply` и обязательная проверка.

</details>

**D8.** В Kubernetes поды на одной ноде общаются, а между нодами — нет.
Какие настройки маршрутизации/ядра проверишь?

<details><summary>Ответ</summary>

Проверить: `net.ipv4.ip_forward=1` на всех нодах; загруженные модули `br_netfilter`
и sysctl `net.bridge.bridge-nf-call-iptables=1`; маршруты к pod-CIDR соседних нод
(`ip route | grep <podCIDR>`); работает ли CNI-агент (`kubectl -n kube-system get pods`);
не блокирует ли трафик firewall/Security Group (VXLAN UDP 8472 для flannel, 4789, IP-in-IP
для Calico); не пересекаются ли Pod CIDR с сетью нод.

</details>

### Блок E. Вопросы с собеседования

**1.** Как пакет находит путь до сервера в интернете?

<details><summary>Ответ</summary>

Хост проверяет, находится ли адрес назначения в его подсети; если нет — выбирает маршрут
по longest prefix match (обычно default gateway), определяет MAC шлюза через ARP и отправляет
кадр. Каждый маршрутизатор уменьшает TTL, меняет MAC и передаёт дальше, пока пакет
не достигнет цели; возможен NAT.

</details>

**2.** Что такое таблица маршрутизации и как её посмотреть?

<details><summary>Ответ</summary>

Набор правил, по которым ядро выбирает исходящий интерфейс и следующий хоп; смотреть
`ip route` (и `ip route get <IP>` для конкретного решения).

</details>

**3.** Что такое default gateway?

<details><summary>Ответ</summary>

Маршрут `0.0.0.0/0` — куда отправлять пакеты, для которых нет более точного маршрута.

</details>

**4.** Как работает longest prefix match?

<details><summary>Ответ</summary>

Из подходящих маршрутов выбирается с самой длинной маской (наиболее специфичный),
а при равенстве — с меньшей метрикой.

</details>

**5.** Что такое TTL и как работает traceroute?

<details><summary>Ответ</summary>

TTL — счётчик хопов, уменьшающийся на каждом маршрутизаторе; при 0 пакет отбрасывается
с ICMP Time Exceeded. traceroute шлёт пакеты с растущим TTL и собирает адреса ответивших.

</details>

**6.** Чем OSPF отличается от BGP?

<details><summary>Ответ</summary>

OSPF — IGP внутри автономной системы, link-state, выбор пути по метрике (cost).
BGP — EGP между автономными системами, path-vector, выбор пути по административным политикам.

</details>

**7.** Что такое BGP и почему он важен?

<details><summary>Ответ</summary>

Протокол обмена маршрутной информацией между провайдерами; он определяет, как трафик
ходит по интернету. Ошибки и злонамеренные анонсы в BGP приводят к глобальным авариям
и перехвату трафика.

</details>

**8.** Как добавить постоянный статический маршрут?

<details><summary>Ответ</summary>

Через конфигурацию сети: netplan `routes:` + `netplan apply`, NetworkManager `nmcli`,
`/etc/network/interfaces` — а не разовой командой `ip route add`.

</details>
