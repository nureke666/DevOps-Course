## 🗺️ Схема: что bash делает со строкой перед запуском

```text:no-line-numbers
   echo "user: $USER" /var/log/*.log
                 │
                 ▼
   ┌─────────────────────────────────────────────────────────────┐
   │ 1. Разбор на слова по пробелам/табам (по IFS)               │
   │ 2. Раскрытие скобок      {a,b}   → a b                      │
   │ 3. Тильда                 ~      → /home/vagrant            │
   │ 4. Параметры и переменные $USER  → vagrant                  │
   │ 5. Подстановка команд     $(cmd) → вывод команды            │
   │ 6. Арифметика             $((1+2))→ 3                       │
   │ 7. ⚠️ WORD SPLITTING результата подстановок (по IFS)        │  ← 90% багов
   │ 8. Globbing               *.log  → app.log err.log          │  ← остальные 10%
   │ 9. Удаление кавычек                                         │
   │10. Запуск команды с готовым списком аргументов              │
   └─────────────────────────────────────────────────────────────┘
```

**Главный вывод из схемы:** шаги 7 и 8 применяются к тому, что *вернула* подстановка.
Кавычки `"$var"` их отключают. Поэтому правило: **переменные всегда в двойных кавычках.**

## 1. Какой shell и чем они отличаются

```bash
echo "$SHELL"        # shell пользователя из /etc/passwd
echo "$0"            # какой shell выполняет прямо сейчас
readlink -f /bin/sh  # ⚠️ на Ubuntu/Debian → /bin/dash, НЕ bash!
bash --version
cat /etc/shells
```

| Shell | Где встречается | Особенность |
|-------|-----------------|-------------|
| `bash` | Ubuntu/Debian/RHEL — интерактивный, скрипты | Массивы, `[[ ]]`, `${var/…}` — всё, что ниже |
| `dash` | `/bin/sh` в Debian/Ubuntu | Быстрый, **POSIX-минимум**: нет `[[ ]]`, массивов, `+=` |
| `sh` в Alpine (busybox) | Docker-образы | Ещё беднее dash ← частая боль в контейнерах |
| `zsh` | macOS по умолчанию | Для интерактива, для прод-скриптов не берут |

⚠️ **Классическая ошибка:** скрипт написан с `[[ ]]` и массивами, но запускается как `sh script.sh`
или лежит в alpine-контейнере → `[[: not found`, `Syntax error: "(" unexpected`.
Либо пишешь на POSIX sh, либо ставишь bash в образ и следишь за shebang.

## 2. Первый скрипт: shebang и запуск

```bash
cat > hello.sh <<'EOS'
#!/usr/bin/env bash
echo "Привет, $USER! Сегодня $(date +%F)"
EOS

chmod +x hello.sh     # без этого будет Permission denied
./hello.sh            # ← запуск: shebang решает, чем выполнять
```

**Shebang** — первая строка `#!интерпретатор`. Ядро читает первые 2 байта файла; если это `#!`,
то запускает указанный интерпретатор и передаёт ему файл.

| Вариант | Плюс | Минус |
|---------|------|-------|
| `#!/bin/bash` | Явный путь, не зависит от `PATH` | На BSD/macOS bash может лежать не там |
| `#!/usr/bin/env bash` | Возьмёт bash из `PATH` (например, свежий из brew) | Зависит от `PATH`, нельзя передать опции переносимо |
| `#!/bin/sh` | POSIX, есть везде | Это dash: без массивов и `[[ ]]` |

⚠️ Типичные поломки shebang: файл сохранён с **CRLF** (Windows) → `bad interpreter: /bin/bash^M`,
лечится `dos2unix` или `sed -i 's/\r$//'`; перед `#!` есть пробел или пустая строка → скрипт
выполняется текущим shell'ом, а не указанным.

### Четыре способа запустить — и разница между ними

```bash
./script.sh          # нужен +x и shebang. Запускается в ДОЧЕРНЕМ процессе
bash script.sh       # +x не нужен, shebang игнорируется. Тоже дочерний процесс
source script.sh     # выполняется в ТЕКУЩЕМ shell: переменные и cd остаются!
. script.sh          # то же самое, POSIX-форма
```

⭐ Отсюда классический вопрос с собеса: «почему `cd` внутри скрипта не меняет каталог в терминале?»
Потому что скрипт — отдельный процесс, а `cd` меняет каталог только у него.
Нужно менять у себя — `source`.

```bash
# Где лежит сам скрипт (нужно постоянно — рядом лежат конфиги и библиотеки)
SCRIPT_DIR="$(cd -- "$(dirname -- "${BASH_SOURCE[0]}")" && pwd)"
```

## 3. Переменные

```bash
name="nginx"          # ⚠️ БЕЗ пробелов вокруг '='  (name = "nginx" → command not found)
count=5
path="/var/log/$name" # подстановка внутри двойных кавычек работает
echo "${name}_backup" # фигурные скобки — где кончается имя переменной

readonly VERSION="1.2.3"     # константа, изменить нельзя
unset count                  # удалить

# Локальные (shell) vs экспортированные (окружение)
MY_VAR="local"
export MY_VAR               # теперь видна дочерним процессам
env | grep MY_VAR
bash -c 'echo "$MY_VAR"'    # без export было бы пусто
```

**Правило именования:** `UPPER_CASE` — окружение и «глобальные» константы скрипта,
`lower_case` — локальные переменные. Не переопределяй `PATH`, `HOME`, `USER`, `IFS` без нужды.

### Раскрытие параметров (parameter expansion) — учить наизусть

| Выражение | Что делает |
|-----------|------------|
| `${var:-def}` | Значение, а если пусто/не задано — `def` (саму переменную не меняет) |
| `${var:=def}` | То же, но **и присвоить** переменной |
| `${var:?сообщение}` | Упасть с ошибкой, если пусто ← ⭐ проверка обязательных параметров |
| `${var:+alt}` | `alt`, если переменная **не** пуста (иначе пусто) |
| `${#var}` | Длина строки |
| `${var:2:5}` | Подстрока: с 2-го символа, длиной 5 |
| `${var#шаблон}` / `${var##шаблон}` | Срезать с начала: минимально / максимально |
| `${var%шаблон}` / `${var%%шаблон}` | Срезать с конца: минимально / максимально |
| `${var/old/new}` / `${var//old/new}` | Заменить первое / все вхождения |
| `${var^^}` / `${var,,}` | В верхний / нижний регистр |

```bash
f="/var/log/nginx/access.log.gz"
echo "${f##*/}"        # access.log.gz   ← basename без вызова процесса
echo "${f%/*}"         # /var/log/nginx  ← dirname
echo "${f%.gz}"        # /var/log/nginx/access.log
echo "${f##*.}"        # gz              ← расширение

: "${ENVIRONMENT:=staging}"           # дефолт, если не задано снаружи
: "${DB_PASSWORD:?нужно задать DB_PASSWORD}"   # скрипт упадёт с понятным текстом
```

## 4. Кавычки — главная тема всего bash

```bash
name="world"
echo "Hello $name"     # Hello world      ← двойные: подстановка работает
echo 'Hello $name'     # Hello $name      ← одинарные: буквально всё
echo "Path: ${HOME}"   # Path: /home/vagrant
echo "Стоит \$5"       # Стоит $5         ← экранирование
```

### Почему `"$var"` обязательно

```bash
file="my report.txt"
rm $file        # ⚠️ УДАЛИТ ДВА ФАЙЛА: 'my' и 'report.txt'
rm "$file"      # ✅ удалит один файл с пробелом в имени

empty=""
[ -n $empty ] && echo yes    # ⚠️ синтаксическая каша: [ -n ] → истина!
[ -n "$empty" ] && echo yes  # ✅ ничего не выведет

files="*"
echo $files     # раскроется в список файлов каталога
echo "$files"   # напечатает звёздочку
```

### `"$@"` против `"$*"` — вопрос с собеседования

```bash
# скрипт вызван: ./s.sh "один два" три
"$@"   → "один два" "три"     ← ✅ сохраняет границы аргументов. ВСЕГДА используй это
"$*"   → "один два три"       ← склеит всё в одну строку через первый символ IFS
$@     → "один" "два" "три"   ← ❌ порвёт аргумент с пробелом
```

## 5. Подстановка команд

```bash
today=$(date +%F)                  # ✅ современная форма, вкладывается
files=$(ls /etc | wc -l)
kernel=`uname -r`                  # ❌ устаревшие backticks: не вложить, экранирование ада

# Вложенность — ради неё и придумали $( )
echo "Свободно: $(df -h "$(dirname "$PWD")" | awk 'NR==2 {print $4}')"

content=$(<file.txt)               # быстрее, чем $(cat file.txt) — без запуска процесса
count=$(grep -c ERROR app.log)
```

⚠️ Подстановка команд **съедает завершающие переводы строк** — это обычно удобно, но
многострочный вывод нужно брать в кавычки: `echo "$(cmd)"`, иначе всё слипнется в одну строку.

## 6. Аргументы скрипта

| Переменная | Значение |
|------------|----------|
| `$0` | Имя самого скрипта |
| `$1 … $9`, `${10}` | Позиционные аргументы |
| `$#` | Сколько аргументов передано |
| `"$@"` | Все аргументы как отдельные слова ← рабочая форма |
| `"$*"` | Все аргументы одной строкой |
| `$?` | Код возврата последней команды |
| `$$` | PID текущего скрипта |
| `$!` | PID последнего фонового процесса |

```bash
#!/usr/bin/env bash
if [ "$#" -lt 2 ]; then
  echo "Использование: $0 <хост> <порт>" >&2      # ⭐ подсказка — в stderr
  exit 1
fi
host="$1"
port="$2"
shift 2                       # сдвинуть: теперь "$@" — только оставшиеся аргументы
echo "Проверяю $host:$port, доп. опции: $*"
```

## 7. Коды возврата — как скрипт разговаривает с миром

```bash
ls /etc >/dev/null; echo "$?"       # 0  — успех
ls /нет   2>/dev/null; echo "$?"    # 2  — ошибка
grep -q root /etc/passwd; echo "$?" # 0 — нашёл; 1 — не нашёл (это НЕ ошибка)

cmd1 && cmd2      # cmd2 выполнится, только если cmd1 успешна
cmd1 || cmd2      # cmd2 выполнится, только если cmd1 упала
cmd1 ; cmd2       # выполнится в любом случае
systemctl is-active --quiet nginx || systemctl start nginx     # боевой однострочник
```

| Код | Значение |
|-----|----------|
| `0` | Успех — **единственный** код успеха |
| `1` | Общая ошибка |
| `2` | Ошибка использования (неверные аргументы) |
| `126` | Файл найден, но не исполняемый (забыл `chmod +x`) |
| `127` | Команда не найдена (опечатка, нет в `PATH`) |
| `128+N` | Убит сигналом N: `130` = Ctrl+C (SIGINT), `137` = SIGKILL, `143` = SIGTERM |

```bash
exit 0     # успех
exit 1     # ошибка
# exit без аргумента = код последней команды
```

⭐ Это не формальность: по коду выхода принимают решение cron, systemd (`Restart=on-failure`),
CI-пайплайн (упал job или нет), Kubernetes-проба и мониторинг. Скрипт, который всегда
возвращает 0, для автоматики бесполезен.

## 8. Ввод и вывод

```bash
echo "текст"                  # просто и привычно
echo -n "без перевода строки"
printf '%s\n' "$var"          # ⭐ предсказуемее echo: не ломается на '-n', '\t' и т.п.
printf '%-20s %5d %6.2f%%\n' "cpu" 42 87.5      # форматированные таблицы

read -r -p "Имя сервиса: " svc          # -r обязательно: не съедать обратные слэши
read -r -s -p "Пароль: " pass; echo     # -s — не показывать ввод
read -r -t 10 -p "Ответ (10 сек): " ans || echo "таймаут"

# Перенаправления (подробно — тема 03)
cmd >out.log 2>err.log
cmd >all.log 2>&1            # ⚠️ порядок важен: 2>&1 ПОСЛЕ >
cmd &>all.log                # bash-сокращение
exec >>/var/log/my.log 2>&1  # ⭐ перенаправить ВЕСЬ вывод скрипта с этого места

# Heredoc и herestring
cat <<EOF > /etc/myapp.conf
host=$HOSTNAME        # подстановки работают
EOF
cat <<'EOF' > script.sh
echo "$PATH"          # кавычки у метки → всё буквально, ничего не подставляется
EOF
grep -q root <<< "$line"      # herestring: строка на stdin
```

## 9. Арифметика

```bash
a=7 b=2
echo $(( a + b ))            # 9   ← $ перед именами внутри (( )) не нужен
echo $(( a * b ))            # 14
echo $(( a / b ))            # 3   ⚠️ ТОЛЬКО целые числа
echo $(( a % b ))            # 1
(( count++ ))                # инкремент
(( disk_used > 80 )) && echo "мало места"

# Дробная арифметика — внешними инструментами
echo "scale=2; $a / $b" | bc          # 3.50
awk "BEGIN {printf \"%.2f\n\", $a/$b}"

# Частый расчёт в мониторинге
used=$(df --output=pcent / | tr -dc '0-9')
(( used > 85 )) && echo "ALERT: диск занят на ${used}%"
```

⚠️ `(( ))` возвращает код **1**, если результат равен нулю: `(( 0 ))` → «ложь».
В связке с `set -e` это роняет скрипт на `(( count++ ))`, когда count был 0 — пиши `count=$((count+1))`.

## ⚠️ Грабли новичка (проверь себя)

| Ошибка | Что происходит | Правильно |
|--------|----------------|-----------|
| `var = 5` | `var: command not found` | `var=5` |
| `rm $file` | Ломается на пробелах в имени | `rm "$file"` |
| `if [ $x = "y" ]` | Падает, если `$x` пуста | `if [ "$x" = "y" ]` |
| `cd /tmp` в скрипте | Каталог в терминале не меняется | `source script.sh` |
| `#!/bin/sh` + массивы | `Syntax error` | `#!/usr/bin/env bash` |
| `echo $(cat f)` | Многострочный вывод слипся | `echo "$(cat f)"` |
| Скрипт всегда `exit 0` | Мониторинг и CI не видят ошибок | Осмысленные коды |
| Пароль в аргументах | Виден всем в `ps aux` | Через переменную окружения или файл |

## 💼 Как это в DevOps

- **Скрипт — самый дешёвый способ автоматизации.** Раньше Ansible, Python и CI придёт bash:
  подготовить сервер, собрать артефакт, проверить сервис, снять бэкап.
- `entrypoint.sh` есть почти в каждом Docker-образе: подставить конфиг из переменных окружения,
  дождаться БД, запустить приложение через `exec "$@"`.
- Каждый job в GitLab CI/Jenkins — это bash-строки. Кавычки и коды выхода там работают так же.
- Health-check, бэкапы, ротации, выгрузки — cron или systemd-таймер запускает bash-скрипт
  и смотрит на код выхода.
- Умение читать чужой скрипт (в репозитории, в Dockerfile, в `/etc/init.d/`) важнее умения
  писать красивый свой.

## 🧪 Мини-лаба

```bash
vagrant ssh
mkdir -p ~/lab23 && cd ~/lab23

# 1. Скрипт и shebang
cat > info.sh <<'EOS'
#!/usr/bin/env bash
echo "Скрипт : $0"
echo "PID    : $$"
echo "Юзер   : $USER"
echo "Аргум. : $# штук -> $*"
echo "Аптайм : $(uptime -p)"
EOS
bash info.sh a b c          # работает без +x
./info.sh a b c             # Permission denied
chmod +x info.sh && ./info.sh "один два" три

# 2. Разница source и ./
cat > cdtest.sh <<'EOS'
#!/usr/bin/env bash
cd /tmp && echo "внутри скрипта: $PWD"
EOS
chmod +x cdtest.sh
./cdtest.sh; echo "после ./   : $PWD"
source cdtest.sh; echo "после src : $PWD"; cd ~/lab23

# 3. Кавычки на практике
touch "my report.txt"
file="my report.txt"
ls -l $file          # два несуществующих файла
ls -l "$file"        # один реальный
for w in $file;   do echo "без кавычек: [$w]"; done
for w in "$file"; do echo "с кавычками: [$w]"; done

# 4. Parameter expansion
p="/var/log/nginx/access.log.gz"
echo "basename : ${p##*/}"
echo "dirname  : ${p%/*}"
echo "без .gz  : ${p%.gz}"
echo "длина    : ${#p}"
unset ENVIRON; echo "дефолт   : ${ENVIRON:-staging}"
( set -u; echo "${MISSING:?переменная обязательна}" ) || echo "упало, как и задумано"

# 5. Коды возврата
grep -q root /etc/passwd; echo "нашёл root  -> $?"
grep -q zzzz /etc/passwd; echo "не нашёл    -> $?"
ls /нет 2>/dev/null;      echo "нет каталога-> $?"
bash -c 'опечатка';       echo "нет команды -> $?"
cat > exitcode.sh <<'EOS'
#!/usr/bin/env bash
[ "$#" -eq 1 ] || { echo "нужен ровно 1 аргумент" >&2; exit 2; }
[ -f "$1" ] || { echo "файла нет: $1" >&2; exit 1; }
echo "ок: $1"; exit 0
EOS
chmod +x exitcode.sh
./exitcode.sh; echo "-> $?"
./exitcode.sh /нет/такого; echo "-> $?"
./exitcode.sh /etc/hostname; echo "-> $?"

# 6. printf вместо echo
printf '%-12s %8s %6s\n' СЕРВИС СТАТУС АВТО
for s in ssh cron systemd-journald; do
  printf '%-12s %8s %6s\n' "$s" "$(systemctl is-active "$s")" "$(systemctl is-enabled "$s" 2>/dev/null)"
done

# 7. Арифметика и реальный порог
used=$(df --output=pcent / | tr -dc '0-9')
echo "занято ${used}%"
(( used > 85 )) && echo "ALERT" || echo "норма"

# 8. Уборка
cd ~ && rm -rf ~/lab23
```

## 📌 Шпаргалка

| Конструкция | Смысл |
|-------------|-------|
| `#!/usr/bin/env bash` | Shebang — чем выполнять |
| `chmod +x s.sh` → `./s.sh` | Запуск в дочернем процессе |
| `source s.sh` / `. s.sh` | Выполнить в текущем shell (переменные останутся) |
| `var=значение` | Присвоение (без пробелов!) |
| `export VAR` | Отдать переменную дочерним процессам |
| `"$var"` | ⭐ Всегда так. Без кавычек — word splitting и globbing |
| `${var:-def}` / `${var:?err}` | Значение по умолчанию / обязательный параметр |
| `${f##*/}` / `${f%/*}` | basename / dirname без запуска процессов |
| `$(cmd)` | Подстановка команды |
| `$#`, `"$@"`, `$1`, `shift` | Аргументы скрипта |
| `$?` | Код возврата последней команды |
| `exit N` | Завершить скрипт с кодом |
| `cmd1 && cmd2` / `\|\|` | Выполнить при успехе / при ошибке |
| `printf '%s\n' "$v"` | Предсказуемый вывод |
| `read -r -p "текст" var` | Чтение ввода |
| `$(( a + b ))` | Целочисленная арифметика |
| `exec >>log 2>&1` | Весь дальнейший вывод скрипта — в файл |

## 🧠 Что запомнить

1. Shebang определяет интерпретатор; `/bin/sh` в Debian/Ubuntu — это **dash**, а не bash.
2. `./script.sh` — дочерний процесс, `source script.sh` — текущий shell. Отсюда поведение `cd`.
3. **Переменные всегда в двойных кавычках** — это половина всех багов в bash.
4. `"$@"` сохраняет границы аргументов, `$@` и `"$*"` — нет.
5. `${var:-def}`, `${var:?err}`, `${f##*/}` заменяют кучу внешних команд и проверок.
6. Код возврата `0` — успех; по нему судят cron, systemd, CI, Kubernetes и мониторинг.
7. `$(( ))` — только целые числа; дроби — через `bc`/`awk`.
8. `printf` предсказуемее `echo`, `$(<file)` быстрее `$(cat file)`.
9. Секреты не передают аргументами — их видно в `ps aux`.
10. Ошибка в bash часто не в логике, а в раскрытии: помни порядок из схемы наверху.

Дальше — [24. Control Flow](/linux/24-bash-control-flow).

### Блок A. Теория

**A1.** Что такое shebang и как ядро его обрабатывает? Чем `#!/bin/bash` отличается от
`#!/usr/bin/env bash`?

<details><summary>Ответ</summary>

Shebang — первые два байта `#!` и путь к интерпретатору. Ядро видит их при `execve`,
запускает указанный интерпретатор и передаёт ему путь к скрипту.
`#!/bin/bash` — жёсткий путь (надёжно на Linux, но bash может лежать иначе на других ОС);
`#!/usr/bin/env bash` — ищет bash в `PATH` (переносимо, берёт «свой» bash, но зависит от `PATH`
и не позволяет переносимо передавать опции интерпретатора).

</details>

**A2.** Почему `/bin/sh` на Ubuntu — это не bash, и к каким ошибкам это приводит?

<details><summary>Ответ</summary>

В Debian/Ubuntu `/bin/sh` — симлинк на **dash**, минимальный POSIX-шелл: нет `[[ ]]`,
массивов, `${var^^}`, `+=`, `local` с особенностями. Скрипт, написанный для bash и запущенный
как `sh script.sh`, падает с `Syntax error` или `[[: not found`. В alpine-контейнерах `sh` —
это busybox, ещё беднее.

</details>

**A3.** Три способа запустить скрипт (`./s.sh`, `bash s.sh`, `source s.sh`). Чем отличаются?

<details><summary>Ответ</summary>

`./s.sh` — новый процесс, нужен `+x` и shebang. `bash s.sh` — новый процесс, `+x` не нужен,
shebang игнорируется. `source s.sh` (`. s.sh`) — выполняется в текущем shell: переменные,
функции, `cd` и `export` остаются в сессии.

</details>

**A4.** Почему `cd` внутри скрипта не меняет каталог в терминале, из которого его запустили?

<details><summary>Ответ</summary>

Скрипт выполняется отдельным процессом; `cd` меняет рабочий каталог только у него.
Родительский shell об этом не знает. Нужно изменить каталог в текущей сессии — `source`.

</details>

**A5.** Что такое word splitting и globbing? На каком шаге обработки строки они происходят и
как их отключить?

<details><summary>Ответ</summary>

Word splitting — разбиение результата подстановки на слова по символам из `IFS`
(по умолчанию пробел, таб, перевод строки). Globbing — раскрытие `*`, `?`, `[…]` в имена файлов.
Оба выполняются **после** подстановки переменных и команд, и оба отключаются двойными кавычками.

</details>

**A6.** В чём разница `'одинарных'` и `"двойных"` кавычек?

<details><summary>Ответ</summary>

В одинарных всё буквально, подстановок нет вообще. В двойных работают `$переменные`,
`$(команды)`, `$((арифметика))` и экранирование `\`, но отключены word splitting и globbing.

</details>

**A7.** Чем `"$@"` отличается от `"$*"` и от `$@`? Приведи пример, где разница видна.

<details><summary>Ответ</summary>

`"$@"` разворачивается в отдельные слова, сохраняя границы аргументов — единственно
верная форма для передачи аргументов дальше. `"$*"` склеивает всё в одну строку через первый
символ `IFS`. `$@` без кавычек рвёт аргументы с пробелами. Пример: `./s.sh "два слова" x` —
с `"$@"` будет 2 аргумента, с `$@` — 3.

</details>

**A8.** Что делают `${var:-def}`, `${var:=def}`, `${var:?msg}`, `${var:+alt}`?

<details><summary>Ответ</summary>

`${var:-def}` — подставить `def`, если переменная пуста/не задана (не меняя её);
`${var:=def}` — то же и присвоить; `${var:?msg}` — завершить скрипт с ошибкой и текстом `msg`,
если пусто; `${var:+alt}` — подставить `alt`, только если переменная **не** пуста.

</details>

**A9.** Как получить basename и dirname из пути **без** вызова внешних команд?

<details><summary>Ответ</summary>

`${path##*/}` — basename (срезать максимально длинный префикс до последнего `/`);
`${path%/*}` — dirname (срезать минимальный суффикс с последнего `/`).

</details>

**A10.** Что означают коды выхода 0, 1, 2, 126, 127, 130, 137, 143?

<details><summary>Ответ</summary>

0 — успех; 1 — общая ошибка; 2 — неверное использование; 126 — файл не исполняемый;
127 — команда не найдена; 130 = 128+2 — прерван SIGINT (Ctrl+C); 137 = 128+9 — убит SIGKILL
(часто OOM-killer или `docker kill`); 143 = 128+15 — получил SIGTERM.

</details>

**A11.** Чем `cmd1 && cmd2` отличается от `cmd1 ; cmd2` и от `cmd1 || cmd2`?

<details><summary>Ответ</summary>

`&&` — выполнить вторую команду, только если первая вернула 0; `||` — только если
первая вернула не 0; `;` — выполнить в любом случае.

</details>

**A12.** Почему `printf` предпочтительнее `echo` в скриптах?

<details><summary>Ответ</summary>

Поведение `echo` различается между shell'ами и реализациями: обработка `-n`, `-e`,
управляющих последовательностей, строк, начинающихся с дефиса. `printf '%s\n' "$var"` ведёт
себя одинаково везде и умеет форматирование.

</details>

**A13.** Что делает `exec >>/var/log/app.log 2>&1` в начале скрипта?

<details><summary>Ответ</summary>

Перенаправляет stdout и stderr **самого скрипта** (и всех запущенных им команд)
в файл с дозаписью — удобный способ логировать всё разом, без `>> log 2>&1` у каждой команды.

</details>

**A14.** Почему нельзя передавать пароль аргументом командной строки?

<details><summary>Ответ</summary>

Аргументы видны в `ps aux`, `/proc/<pid>/cmdline` любому пользователю системы,
попадают в историю shell и в логи аудита. Передают через переменные окружения, файл с
правами 600, stdin или секрет-хранилище.

</details>

**A15.** Что вернёт `$(( 10 / 3 ))` и как получить дробный результат?

<details><summary>Ответ</summary>

`3` — bash умеет только целочисленную арифметику. Дробь: `echo "scale=2; 10/3" | bc`
или `awk 'BEGIN{printf "%.2f\n", 10/3}'`.

</details>

**B17.** Скрипт содержит `cd /tmp && rm -rf *`. Чем это опасно и как переписать безопасно?

<details><summary>Ответ</summary>

Если `cd /tmp` не сработает (нет каталога, нет прав), `rm -rf *` выполнится **в текущем
каталоге**. Безопасно: `cd /tmp || exit 1` (или `set -e`), а лучше — не использовать `*`,
а удалять по явному пути с проверкой: `rm -rf -- "${dir:?dir не задан}"/…`.

</details>

printf '%-12s: %s%%\n' "Диск /"    "$disk_pct"

**D1.** Скрипт запускается вручную, но из cron падает с `command not found`. Причина?

Что произошло и как защититься?

`rm -rf /*` — удаление от корня (в пределах прав пользователя). Защита:

**D4.** Скрипт очистки удалил не то: в каталоге был файл с пробелом в имени, а в скрипте
`for f in $(ls)`. Объясни и предложи правильный вариант.

<details><summary>Ответ</summary>

`$(ls)` отдаёт текст, который затем режется word splitting'ом по пробелам, поэтому
`my report.txt` превращается в два «файла». Правильно — глоб и кавычки:
`for f in ./*; do … "$f" …; done`, а для рекурсии — `find … -print0 | xargs -0`.

</details>

**D5.** Джоба в CI «зелёная», хотя внутри скрипт явно писал ошибки в лог. Почему?

<details><summary>Ответ</summary>

Скрипт не проверял коды возврата: последняя команда (например, `echo`) вернула 0,
и job стал зелёным. Лечение: `set -euo pipefail` в начале, явные проверки
`cmd || { echo ...; exit 1; }`, осмысленный `exit`.

</details>

**D6.** `./deploy.sh` → `Permission denied`, при этом `bash deploy.sh` работает. Диагноз?

<details><summary>Ответ</summary>

Нет бита выполнения (`chmod +x`) — либо каталог смонтирован с `noexec`
(проверить `mount | grep noexec`), либо скрипт на файловой системе без прав выполнения.
`bash script.sh` работает, потому что исполняется bash, а скрипт читается как текст.

</details>

**D7.** Разработчик жалуется: `VERSION = 1.2` в скрипте даёт `VERSION: command not found`.

<details><summary>Ответ</summary>

В bash присваивание не терпит пробелов вокруг `=`; строка разобрана как команда
`VERSION` с аргументами `=` и `1.2`. Правильно: `VERSION=1.2`.

</details>

**D8.** Скрипт читает пароль из `$1`. Безопасник прислал претензию. Чем он недоволен
и какие есть варианты?

<details><summary>Ответ</summary>

Аргументы видны в `ps aux` и `/proc/<pid>/cmdline` всем пользователям машины.
Варианты: переменная окружения (лучше — только для конкретной команды), файл с правами 600,
чтение из stdin, `--password-stdin` (как у `docker login`), Vault/CI-секреты.

</details>

### Блок E. Вопросы с собеседования

**1.** Что такое shebang? Что будет, если его не написать?

<details><summary>Ответ</summary>

Строка `#!/путь/к/интерпретатору` в начале файла. Без неё скрипт будет выполнен текущим
shell'ом (при `./script` — `sh` или bash в зависимости от системы), что ломает bash-синтаксис.

</details>

**2.** Чем `source script.sh` отличается от `./script.sh`?

<details><summary>Ответ</summary>

`source` выполняет скрипт в текущем shell (переменные и `cd` сохраняются), `./script.sh` —
в дочернем процессе.

</details>

**3.** Разница одинарных и двойных кавычек.

<details><summary>Ответ</summary>

В одинарных — всё буквально; в двойных работают подстановки переменных и команд.

</details>

**4.** Зачем брать переменные в кавычки?

<details><summary>Ответ</summary>

Чтобы отключить word splitting и globbing: иначе значения с пробелами, пустые значения и
спецсимволы ломают команду.

</details>

**5.** `"$@"` vs `"$*"`.

<details><summary>Ответ</summary>

`"$@"` — отдельные аргументы с сохранением границ; `"$*"` — одна строка через первый символ IFS.

</details>

**6.** Как задать значение переменной по умолчанию?

<details><summary>Ответ</summary>

`${VAR:-значение}` (разово) или `: "${VAR:=значение}"` (с присваиванием).

</details>

**7.** Что такое код возврата, где он используется?

<details><summary>Ответ</summary>

Число 0-255, которое процесс возвращает при завершении; по нему судят `&&`/`||`, cron,
systemd (`Restart=`), CI-пайплайны, Kubernetes-пробы и мониторинг.

</details>

**8.** Что означает код 127? А 130?

<details><summary>Ответ</summary>

127 — команда не найдена; 130 — процесс прерван Ctrl+C (128+SIGINT).

</details>

**9.** Как получить вывод команды в переменную?

<details><summary>Ответ</summary>

`var=$(команда)`; для файла быстрее `var=$(<file)`.

</details>

**10.** Как проверить, что скрипт запущен с нужным количеством аргументов?

<details><summary>Ответ</summary>

`[ "$#" -ne N ] && { echo "usage: $0 …" >&2; exit 2; }` — и обязательно вывод в stderr.

</details>
