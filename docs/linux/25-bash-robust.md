# 25. Bash Scripting — надёжный скрипт: set -euo pipefail, trap, логи, CLI

> Конспект №3 модуля bash. Предыдущий: [24. Условия и циклы](/linux/24-bash-control-flow)
> **После темы ты умеешь:** писать скрипты, которые падают громко и в нужном месте, убирают
> за собой, пишут внятный лог, не запускаются дважды и имеют человеческий интерфейс.
> ⭐ Именно это отличает «скриптик на коленке» от того, что не стыдно положить в прод и в CI.

## 🗺️ Схема: почему скрипт «сработал», но всё сломал

```text:no-line-numbers
   Скрипт без защиты:
   ┌─────────────────────────────────────────────────────────┐
   │ cd /opt/app          ← каталога нет, ошибка в stderr     │
   │ rm -rf ./*           ← ВЫПОЛНИЛОСЬ В ТЕКУЩЕМ КАТАЛОГЕ    │
   │ tar -xzf app.tar.gz  ← архив не скачался, но идём дальше │
   │ systemctl restart app│                                    │
   │ exit 0               ← CI зелёный, мониторинг молчит      │
   └─────────────────────────────────────────────────────────┘
                     │
                     ▼  set -euo pipefail
   ┌─────────────────────────────────────────────────────────┐
   │ cd /opt/app  → скрипт падает здесь, с кодом ≠ 0          │
   │ trap          → убирает временные файлы                  │
   │ лог           → видно, на какой строке и почему          │
   └─────────────────────────────────────────────────────────┘
```

**По умолчанию bash после ошибки идёт дальше.** Это поведение 1970-х, и оно убивает прод.

## 1. Строгий режим: `set -euo pipefail`

```bash
#!/usr/bin/env bash
set -euo pipefail
IFS=$'\n\t'      # опционально: сузить разделители (пробел перестаёт резать слова)
```

| Опция | Что делает |
|-------|------------|
| `set -e` (`errexit`) | Завершить скрипт, если любая команда вернула ≠ 0 |
| `set -u` (`nounset`) | Падать при обращении к необъявленной переменной ← ловит опечатки |
| `set -o pipefail` | Код пайпа = код **первой упавшей** команды, а не последней |
| `set -x` (`xtrace`) | Печатать каждую команду перед выполнением ← отладка |
| `set -n` | Только проверить синтаксис, не выполнять |

```bash
# Зачем pipefail
curl -sf http://nowhere/data.json | jq .name
echo $?      # без pipefail: 0 (код jq), с pipefail: код curl → ошибка видна
```

### ⚠️ `set -e` — не серебряная пуля. Где он НЕ срабатывает

```bash
set -e
false && echo "нет"          # часть && — скрипт НЕ упадёт
if false; then :; fi         # условие — НЕ упадёт
false || true                # явно погашено — НЕ упадёт
my_func                      # если внутри функции false в условии — тонкости
count=$(grep -c X file)      # присваивание из подстановки: код теряется
local x=$(cmd)               # ⚠️ local/declare ВСЕГДА возвращают 0 — ошибка cmd проглочена
```

```bash
# Правильно: объявление и присваивание — отдельно
local x
x=$(cmd)          # теперь set -e увидит ошибку cmd

# Явная проверка там, где важно
cmd || die "не смог сделать X"
if ! cmd; then die "не смог сделать X"; fi
```

**Вывод:** `set -euo pipefail` ставим всегда, но критичные места проверяем явно.
Там, где ошибка ожидаема, гасим её сознательно: `grep -q x f || true`.

## 2. Логирование и сообщения об ошибках

```bash
readonly SCRIPT_NAME="${0##*/}"

log()  { printf '%s [INFO]  %s\n'  "$(date '+%F %T')" "$*"; }
warn() { printf '%s [WARN]  %s\n'  "$(date '+%F %T')" "$*" >&2; }
error(){ printf '%s [ERROR] %s\n'  "$(date '+%F %T')" "$*" >&2; }
die()  { error "$*"; exit 1; }
```

Правила, за которые скажут спасибо в 3 часа ночи:

| Правило | Почему |
|---------|--------|
| Ошибки — в **stderr** (`>&2`) | Чтобы `script > out.txt` не проглотил ошибки |
| Метка времени в каждой строке | Иначе невозможно сопоставить с инцидентом |
| Пишем «что делаем», а не «ок» | `log "копирую $src → $dst"` полезнее, чем `log "шаг 3"` |
| Никаких секретов в логе | Логи уезжают в Loki/ELK и живут годами |
| `logger` для системных скриптов | Сообщение попадёт в journald/syslog: `logger -t backup "started"` |

```bash
# Весь вывод скрипта — и в файл, и на экран
exec > >(tee -a "/var/log/${SCRIPT_NAME%.sh}.log") 2>&1
# Или просто в файл (для cron)
exec >>"/var/log/${SCRIPT_NAME%.sh}.log" 2>&1
```

## 3. `trap` — уборка и реакция на сигналы

```bash
tmpdir=$(mktemp -d)                       # ⭐ никогда не /tmp/myfile.$$
trap 'rm -rf "$tmpdir"' EXIT              # сработает при ЛЮБОМ выходе

trap 'error "прервано пользователем"; exit 130' INT
trap 'error "получен TERM"; exit 143' TERM
trap 'error "ошибка на строке $LINENO: $BASH_COMMAND"' ERR
```

| Сигнал/событие | Когда срабатывает |
|----------------|-------------------|
| `EXIT` | Любое завершение скрипта — **главный крючок для уборки** |
| `ERR` | Любая команда вернула ≠ 0 (вместе с `set -e`) |
| `INT` | Ctrl+C (SIGINT) |
| `TERM` | `kill`, `systemctl stop`, `docker stop` |
| `HUP` | Обрыв сессии/терминала |

```bash
cleanup() {
  local rc=$?                       # ⭐ сохранить код ДО любых команд
  rm -rf "$tmpdir"
  [[ -n ${lockfd:-} ]] && flock -u "$lockfd" 2>/dev/null
  (( rc == 0 )) && log "завершено успешно" || error "завершено с кодом $rc"
  exit "$rc"
}
trap cleanup EXIT
```

⚠️ Ловушка `EXIT` не сработает при `kill -9` — от SIGKILL защиты нет в принципе.

## 4. Временные файлы

```bash
tmpfile=$(mktemp)                       # /tmp/tmp.AbC123 с правами 600
tmpdir=$(mktemp -d)
tmpfile=$(mktemp -t myapp.XXXXXX)       # со своим префиксом
trap 'rm -f "$tmpfile"; rm -rf "$tmpdir"' EXIT
```

Почему не `/tmp/backup.$$`: PID предсказуем → чужой пользователь может заранее создать симлинк
`/tmp/backup.1234 → /etc/shadow` и твой скрипт от root перезапишет системный файл
(классическая symlink-атака). `mktemp` создаёт файл атомарно с безопасными правами.

## 5. Защита от параллельного запуска — `flock`

```bash
# Вариант 1: обернуть весь скрипт (удобно в crontab)
# * * * * * /usr/bin/flock -n /var/lock/backup.lock /opt/scripts/backup.sh

# Вариант 2: внутри скрипта
readonly LOCKFILE="/var/lock/${SCRIPT_NAME}.lock"
exec 9>"$LOCKFILE"
flock -n 9 || die "уже выполняется (lock: $LOCKFILE)"
# ... блокировка снимается автоматически при завершении процесса
```

⚠️ Самодельные локи (`[[ -f lock ]] && exit; touch lock`) ломаются: между проверкой и созданием
есть гонка, а после `kill -9` файл остаётся навсегда и скрипт больше не запускается никогда.
`flock` держит блокировку **на дескрипторе** — ядро освободит её само при смерти процесса.

## 6. Человеческий CLI: usage, getopts, dry-run

```bash
usage() {
  cat <<EOF
Использование: $SCRIPT_NAME [опции] <источник>

Опции:
  -d, --dest КАТАЛОГ   куда складывать (по умолчанию /backup)
  -k, --keep N         сколько копий хранить (по умолчанию 7)
  -n, --dry-run        только показать, что будет сделано
  -v, --verbose        подробный вывод
  -h, --help           эта справка

Примеры:
  $SCRIPT_NAME /etc
  $SCRIPT_NAME -d /mnt/backup -k 14 --dry-run /var/www
EOF
}
```

```bash
# Разбор длинных и коротких опций без getopts
dest="/backup"; keep=7; dry_run=0; verbose=0
while [[ $# -gt 0 ]]; do
  case "$1" in
    -d|--dest)    dest="${2:?нужен каталог}"; shift 2 ;;
    -k|--keep)    keep="${2:?нужно число}";   shift 2 ;;
    -n|--dry-run) dry_run=1; shift ;;
    -v|--verbose) verbose=1; shift ;;
    -h|--help)    usage; exit 0 ;;
    --)           shift; break ;;
    -*)           usage >&2; die "неизвестная опция: $1" ;;
    *)            break ;;
  esac
done
src="${1:?нужно указать источник (см. --help)}"
```

```bash
# Классический getopts — короткие опции, POSIX-совместимо
while getopts ":d:k:nvh" opt; do
  case "$opt" in
    d) dest="$OPTARG" ;;
    k) keep="$OPTARG" ;;
    n) dry_run=1 ;;
    v) verbose=1 ;;
    h) usage; exit 0 ;;
    :) die "опции -$OPTARG нужен аргумент" ;;
    \?) die "неизвестная опция: -$OPTARG" ;;
  esac
done
shift $((OPTIND - 1))
```

### `--dry-run` — обязательная опция для всего, что удаляет и деплоит

```bash
run() {
  if (( dry_run )); then
    printf '[dry-run] %s\n' "$*"
  else
    "$@"
  fi
}
run rm -rf -- "$old_backup"
run systemctl restart myapp
```

## 7. Безопасность скрипта

```bash
# Обязательные предусловия
[[ $EUID -eq 0 ]] || die "нужен root"
command -v jq >/dev/null || die "нужен jq"
[[ -d $src ]] || die "нет каталога: $src"

# Опасные удаления
rm -rf -- "${target:?target не задан}"/*      # :? не даст выполнить при пустой переменной
rm -rf -- "$dir"                              # -- защищает от имён, начинающихся с дефиса

# eval — почти всегда признак плохого решения
eval "$user_input"        # ❌ выполнение произвольного кода
"${cmd_array[@]}"         # ✅ массив вместо строки с командой

# Секреты
export PGPASSWORD="$DB_PASS"      # ок, но видно в /proc/PID/environ у root
psql -h db -U app < query.sql     # лучше: ~/.pgpass с правами 600
set +x                            # выключить трассировку вокруг секрета
  curl -H "Authorization: Bearer $TOKEN" ...
set -x

umask 077                         # создаваемые файлы — только владельцу
```

| Опасность | Защита |
|-----------|--------|
| `rm -rf $VAR/*` с пустой `$VAR` | `set -u` + `${VAR:?}` + проверка `[[ -d ]]` |
| Имя файла с дефисом трактуется как опция | `--` перед аргументами, `./*` вместо `*` |
| Символическая атака в `/tmp` | `mktemp` |
| Пароль в аргументах → `ps aux` | Переменная окружения, файл 600, stdin |
| Пароль в логе при `set -x` | `set +x` вокруг блока |
| `eval` с внешними данными | Массивы, `printf %q`, отказ от eval |
| Скрипт из интернета `curl \| bash` | Скачать, прочитать, потом выполнить |

## 8. Отладка

```bash
bash -n script.sh          # проверка синтаксиса без выполнения
bash -x script.sh          # трассировка
set -x ... set +x          # трассировка куска
PS4='+ ${BASH_SOURCE}:${LINENO}:${FUNCNAME[0]:-main}: '   # ⭐ полезный префикс трассировки
trap 'echo "строка $LINENO: $BASH_COMMAND" >&2' ERR
BASH_XTRACEFD=3; exec 3>/tmp/trace.log    # трассировку — в отдельный файл, не в вывод
```

### shellcheck — обязателен

```bash
sudo apt install -y shellcheck
shellcheck script.sh
shellcheck -S error *.sh          # только ошибки
# в CI:  shellcheck -x -e SC1091 scripts/*.sh
```

Он ловит ровно те ошибки, что были в темах 23-24: некавыченные переменные, `$(ls)`,
`[ $x = y ]`, `cd` без проверки, `local x=$(cmd)`. Отключать правило — только осознанно,
комментарием `# shellcheck disable=SC2086` с объяснением.

**Тесты:** для скриптов, от которых зависит прод, есть `bats` (bats-core) —
юнит-тесты на bash: `@test "returns 2 on bad args" { run ./s.sh; [ "$status" -eq 2 ]; }`.

## 9. ⭐ Шаблон боевого скрипта (забрать себе)

```bash
#!/usr/bin/env bash
#
# backup.sh — бэкап каталога с ротацией.
# Использование: backup.sh [-d dest] [-k keep] [-n] <источник>
#
set -euo pipefail

readonly SCRIPT_NAME="${0##*/}"
readonly SCRIPT_DIR="$(cd -- "$(dirname -- "${BASH_SOURCE[0]}")" && pwd)"
readonly LOCKFILE="/var/lock/${SCRIPT_NAME}.lock"

dest="/backup"; keep=7; dry_run=0
tmpdir=""

log()  { printf '%s [INFO]  %s\n' "$(date '+%F %T')" "$*"; }
error(){ printf '%s [ERROR] %s\n' "$(date '+%F %T')" "$*" >&2; }
die()  { error "$*"; exit 1; }

usage() { sed -n '2,5p' "$0" | sed 's/^# \{0,1\}//'; }

cleanup() {
  local rc=$?
  [[ -n $tmpdir && -d $tmpdir ]] && rm -rf -- "$tmpdir"
  (( rc == 0 )) && log "готово" || error "завершено с кодом $rc"
  exit "$rc"
}

run() { (( dry_run )) && printf '[dry-run] %s\n' "$*" || "$@"; }

parse_args() {
  while [[ $# -gt 0 ]]; do
    case "$1" in
      -d|--dest)    dest="${2:?}"; shift 2 ;;
      -k|--keep)    keep="${2:?}"; shift 2 ;;
      -n|--dry-run) dry_run=1; shift ;;
      -h|--help)    usage; exit 0 ;;
      -*)           usage >&2; die "неизвестная опция: $1" ;;
      *)            break ;;
    esac
  done
  src="${1:?нужно указать источник (см. --help)}"
}

main() {
  parse_args "$@"
  trap cleanup EXIT
  trap 'error "прервано"; exit 130' INT TERM

  exec 9>"$LOCKFILE"; flock -n 9 || die "уже выполняется"

  [[ -d $src ]]  || die "нет каталога: $src"
  [[ -d $dest ]] || run mkdir -p -- "$dest"
  command -v tar >/dev/null || die "нужен tar"

  tmpdir=$(mktemp -d)
  local name="${src##*/}-$(date +%F_%H%M).tar.gz"

  log "архивирую $src → $dest/$name"
  run tar -czf "$tmpdir/$name" -C "$(dirname -- "$src")" "${src##*/}"
  run mv -- "$tmpdir/$name" "$dest/$name"

  log "ротация: оставляю последние $keep копий"
  local old
  while IFS= read -r old; do
    log "удаляю старую копию: $old"
    run rm -f -- "$old"
  done < <(ls -1t "$dest"/*.tar.gz 2>/dev/null | tail -n +$(( keep + 1 )))

  log "текущие копии: $(ls -1 "$dest"/*.tar.gz 2>/dev/null | wc -l)"
}

main "$@"
```

## 10. Коды выхода как интерфейс

```bash
exit 0    # успех
exit 1    # общая ошибка
exit 2    # неверные аргументы
exit 3    # не выполнены предусловия (нет утилиты, нет прав)
```

Если скрипт используется как проверка мониторинга (Nagios/Zabbix/Prometheus textfile):
`0 = OK`, `1 = WARNING`, `2 = CRITICAL`, `3 = UNKNOWN` — стандарт, которого ждёт система.
Для Kubernetes-проб и `Restart=on-failure` важен сам факт «0 или не 0».

## 💼 Как это в DevOps

- `set -euo pipefail` — первая строка любого скрипта в CI. Без него «зелёный» пайплайн
  может выкатить сломанный артефакт.
- `trap … EXIT` убирает временные каталоги в раннерах, иначе диск раннера кончится за неделю.
- `flock` в crontab — стандартная защита от наложения бэкапов, из-за которого падает БД.
- `--dry-run` в деплой-скрипте — то, что просят ревьюеры перед выкаткой на прод.
- `shellcheck` в pre-commit и в CI — дешевле любого код-ревью.
- Коды выхода и логи в stderr — это то, как скрипт разговаривает с systemd, cron, CI и мониторингом.

## 🧪 Мини-лаба

```bash
vagrant ssh
mkdir -p ~/lab25 && cd ~/lab25

# 1. Скрипт без защиты — видим проблему
cat > bad.sh <<'EOS'
#!/usr/bin/env bash
cd /opt/notexist
echo "продолжаю работать в: $PWD"
echo "и даже выхожу успешно"
EOS
chmod +x bad.sh; ./bad.sh; echo "код: $?"     # 0 (!)

# 2. Тот же скрипт со строгим режимом
cat > good.sh <<'EOS'
#!/usr/bin/env bash
set -euo pipefail
cd /opt/notexist
echo "сюда не дойдём"
EOS
chmod +x good.sh; ./good.sh; echo "код: $?"   # ≠ 0

# 3. pipefail
set +e
curl -sf http://localhost:9999/x | wc -l; echo "без pipefail: $?"
set -o pipefail
curl -sf http://localhost:9999/x | wc -l; echo "с pipefail:   $?"
set +o pipefail

# 4. nounset ловит опечатку
( set -u; NAME="прод"; echo "деплой в ${NAMЕ:-}" ) 2>&1 | head -2 || true

# 5. trap и уборка
cat > tmp.sh <<'EOS'
#!/usr/bin/env bash
set -euo pipefail
tmpdir=$(mktemp -d)
trap 'echo "убираю $tmpdir"; rm -rf "$tmpdir"' EXIT
echo "работаю в $tmpdir"
touch "$tmpdir/file"
[[ ${1:-} == fail ]] && { echo "падаю"; exit 1; }
echo "успешно"
EOS
chmod +x tmp.sh
./tmp.sh; ./tmp.sh fail; echo "код: $?"
ls /tmp | grep -c '^tmp\.' || echo "мусора не осталось"

# 6. trap ERR с номером строки
cat > errline.sh <<'EOS'
#!/usr/bin/env bash
set -euo pipefail
trap 'echo "ОШИБКА на строке $LINENO: $BASH_COMMAND" >&2' ERR
echo "шаг 1"
ls /нет/такого/каталога
echo "шаг 3"
EOS
chmod +x errline.sh; ./errline.sh; echo "код: $?"

# 7. flock — второй запуск не стартует
cat > locked.sh <<'EOS'
#!/usr/bin/env bash
set -euo pipefail
exec 9>/tmp/locked.lock
flock -n 9 || { echo "уже выполняется" >&2; exit 1; }
echo "начал, pid=$$"; sleep 10; echo "закончил"
EOS
chmod +x locked.sh
./locked.sh & sleep 1; ./locked.sh; echo "код второго: $?"; wait

# 8. Опции и dry-run
cat > cli.sh <<'EOS'
#!/usr/bin/env bash
set -euo pipefail
dest=/backup; dry=0
usage(){ echo "usage: $0 [-d dest] [-n] <src>"; }
while [[ $# -gt 0 ]]; do
  case "$1" in
    -d) dest="${2:?}"; shift 2 ;;
    -n) dry=1; shift ;;
    -h) usage; exit 0 ;;
    -*) usage >&2; exit 2 ;;
    *) break ;;
  esac
done
src="${1:?нужен источник}"
run(){ (( dry )) && echo "[dry-run] $*" || "$@"; }
run cp -a "$src" "$dest/"
EOS
chmod +x cli.sh
./cli.sh -h; ./cli.sh; echo "код: $?"; ./cli.sh -n -d /tmp /etc/hostname

# 9. mktemp vs предсказуемое имя
ls -l "$(mktemp)"        # права 600, случайное имя

# 10. shellcheck
sudo apt-get install -y shellcheck >/dev/null 2>&1
cat > dirty.sh <<'EOS'
#!/bin/bash
FILES=$(ls /tmp)
for f in $FILES; do
  if [ $f = "test" ]; then
    rm -rf $f/*
  fi
done
EOS
shellcheck dirty.sh || true      # прочитай КАЖДОЕ замечание — это темы 23-24

# 11. Уборка
cd ~ && rm -rf ~/lab25 /tmp/locked.lock
```

## 📌 Шпаргалка

| Конструкция | Смысл |
|-------------|-------|
| `set -euo pipefail` | Строгий режим — первая строка скрипта |
| `set -x` / `bash -x s.sh` | Трассировка выполнения |
| `bash -n s.sh` | Проверка синтаксиса |
| `PS4='+ ${LINENO}: '` | Информативная трассировка |
| `trap cleanup EXIT` | Уборка при любом выходе |
| `trap '…' ERR INT TERM` | Реакция на ошибку/Ctrl+C/kill |
| `$LINENO`, `$BASH_COMMAND` | Где и на чём упало |
| `tmp=$(mktemp -d)` | Безопасный временный каталог |
| `exec 9>lock; flock -n 9` | Защита от параллельного запуска |
| `${VAR:?сообщение}` | Обязательный параметр |
| `rm -rf -- "${dir:?}"/*` | Удаление с защитой от пустой переменной |
| `cmd \|\| die "текст"` | Явная проверка критичного шага |
| `run() { (( dry )) && echo … \|\| "$@"; }` | Реализация `--dry-run` |
| `getopts ":d:nh" opt` | Разбор коротких опций |
| `exec >>log 2>&1` | Весь вывод скрипта в лог |
| `logger -t имя "текст"` | Сообщение в journald/syslog |
| `shellcheck s.sh` | Статический анализ — обязательно |

## 🧠 Что запомнить

1. Без `set -euo pipefail` скрипт молча продолжает работу после ошибки — так и теряют данные.
2. `set -e` не ловит всё: `local x=$(cmd)`, `cmd || true`, условия. Критичное проверяй явно.
3. `pipefail` обязателен везде, где есть пайпы: иначе код берётся от последней команды.
4. `trap cleanup EXIT` — единственный надёжный способ убрать временные файлы.
5. В `cleanup` первым делом сохрани `rc=$?`, иначе потеряешь исходный код выхода.
6. Временные файлы — только через `mktemp`; `/tmp/file.$$` — дыра в безопасности.
7. `flock` вместо самодельных lock-файлов: ядро снимает блокировку само.
8. `--dry-run`, `--help` и осмысленные коды выхода — это интерфейс, а не украшение.
9. Секреты не в аргументах, не в логах, `set +x` вокруг чувствительных команд.
10. `shellcheck` прогоняй всегда — он находит ошибки, которые «работали» годами.
11. От `kill -9` не защищает ничего: делай скрипты идемпотентными, чтобы повторный запуск чинил.

### Блок A. Теория

**A1.** Что делает каждая из опций `set -e`, `set -u`, `set -o pipefail`, `set -x`?

<details><summary>Ответ</summary>

`-e` — завершать скрипт при ненулевом коде любой команды; `-u` — падать при обращении
к неинициализированной переменной; `-o pipefail` — код конвейера равен коду первой упавшей
команды; `-x` — печатать команды перед выполнением (трассировка).

</details>

**A2.** Приведи 4 ситуации, в которых `set -e` **не** остановит скрипт.

<details><summary>Ответ</summary>

(1) Команда — часть `&&`/`||`; (2) команда в условии `if`/`while`/`until`;
(3) команда перед `!`; (4) присваивание из подстановки (`x=$(cmd)` в форме `local x=$(cmd)`,
где код берётся от `local`). Также `set -e` не действует внутри подстановки команд в некоторых
конструкциях и гасится явным `|| true`.

</details>

**A3.** Почему `local x=$(cmd)` опасно при `set -e` и как писать правильно?

<details><summary>Ответ</summary>

`local`/`declare`/`export` — сами по себе команды, возвращающие 0, поэтому код `cmd`
теряется и `set -e` не сработает. Правильно: сначала `local x`, затем отдельной строкой `x=$(cmd)`.

</details>

**A4.** Зачем нужен `pipefail`? Покажи на примере `curl … | jq …`.

<details><summary>Ответ</summary>

Без `pipefail` код конвейера — это код последней команды: `curl` упал, но `jq` вернул 0,
и скрипт считает, что всё хорошо (а дальше работает с пустыми данными). С `pipefail` вернётся
код `curl`.

</details>

**A5.** Что такое `trap`? Какие события чаще всего перехватывают и зачем?

<details><summary>Ответ</summary>

`trap 'команда' СИГНАЛ…` — выполнить команду при событии. Чаще всего: `EXIT` — уборка
временных файлов и снятие блокировок; `ERR` — диагностика с `$LINENO`; `INT`/`TERM` — корректное
завершение при Ctrl+C и `kill`/`systemctl stop`.

</details>

**A6.** Почему в функции `cleanup` первой строкой пишут `local rc=$?`?

<details><summary>Ответ</summary>

`$?` меняется после **любой** следующей команды. Сохранив код первым действием,
можно и убрать за собой, и выйти с исходным кодом (`exit "$rc"`).

</details>

**A7.** От какого сигнала `trap` не спасает и что из этого следует для дизайна скрипта?

<details><summary>Ответ</summary>

От `SIGKILL` (`kill -9`) — процесс уничтожается ядром немедленно. Значит, скрипт должен
быть идемпотентным и переживать «грязный» перезапуск: проверять состояние, не полагаться
на то, что уборка обязательно случится.

</details>

**A8.** Чем `mktemp` лучше, чем `/tmp/myscript.$$`? Опиши symlink-атаку.

<details><summary>Ответ</summary>

`mktemp` создаёт файл атомарно, с непредсказуемым именем и правами 600.
`/tmp/script.$$` предсказуем: атакующий заранее создаёт симлинк с таким именем на `/etc/shadow`,
и скрипт, запущенный от root, пишет в системный файл (или раскрывает его содержимое).

</details>

**A9.** Почему `flock` надёжнее самодельного lock-файла?

<details><summary>Ответ</summary>

`flock` держит блокировку на файловом дескрипторе: ядро освобождает её автоматически
при завершении процесса, включая `kill -9` и падение. Самодельная схема «проверил — создал»
имеет гонку между проверкой и созданием и оставляет «вечный» lock после аварийного завершения.

</details>

**A10.** Что такое идемпотентность скрипта и почему это важно для cron и CI?

<details><summary>Ответ</summary>

Идемпотентность — повторный запуск даёт тот же результат и не ломает уже сделанное.
Нужна потому, что cron/CI/Ansible могут запустить скрипт повторно после сбоя, таймаута
или ретрая, и это не должно приводить к дублям, ошибкам и порче данных.

</details>

**A11.** Зачем нужен `--dry-run` и как его реализуют?

<details><summary>Ответ</summary>

`--dry-run` показывает, что скрипт **сделал бы**, ничего не меняя: обязательная опция
для удаления, миграций и деплоя. Реализация — обёртка `run() { (( dry )) && echo "[dry-run] $*" || "$@"; }`,
через которую проходят все изменяющие команды.

</details>

**A12.** Как безопасно передать пароль в скрипт? Перечисли 3 способа и их минусы.

<details><summary>Ответ</summary>

(1) Переменная окружения — не видна в `ps`, но видна root'у в `/proc/PID/environ`
и утекает в дочерние процессы; (2) файл с правами 600 (`~/.pgpass`, `~/.netrc`) — надо следить
за правами и бэкапами; (3) stdin (`--password-stdin`) — самый безопасный, но поддерживается
не всеми утилитами. Идеал — секрет-менеджер (Vault, CI-секреты) с коротким TTL.

</details>

**A13.** Что делает `rm -rf -- "${dir:?}"/*` и от каких двух бед защищает?

<details><summary>Ответ</summary>

Удаляет содержимое каталога. `${dir:?}` не даст выполнить команду при пустой или
незаданной переменной (защита от `rm -rf /*`), а `--` запрещает трактовать имя, начинающееся
с дефиса, как опцию.

</details>

**A14.** Почему `eval` считают плохой практикой и чем его заменяют?

<details><summary>Ответ</summary>

`eval` выполняет строку как код: любые внешние данные (аргументы, вывод команды, JSON
из API) становятся исполняемым кодом — это инъекция. Заменяют массивами (`cmd=(tar -czf "$f");
"${cmd[@]}"`), функциями, `case`, а при необходимости — `printf %q`.

</details>

**A15.** Что такое shellcheck и почему его ставят в CI?

<details><summary>Ответ</summary>

Статический анализатор shell-скриптов: находит некавыченные переменные, `$(ls)`,
`cd` без проверки, ошибки в `[ ]`, недостижимый код. В CI он ловит эти ошибки до прода
и стоит секунды.

</details>

**A16.** Какие коды выхода ждёт от скрипта система мониторинга (Nagios-совместимая)?

<details><summary>Ответ</summary>

0 — OK, 1 — WARNING, 2 — CRITICAL, 3 — UNKNOWN. Такой контракт понимают Nagios/Icinga/Zabbix
и многие обёртки; для systemd и Kubernetes важно только «0 или не 0».

</details>

### Блок B. «Что произойдёт»

```bash
B1.  set -e; false; echo "дошли сюда"
B2.  set -e; false || true; echo "дошли сюда"
B3.  set -e; if false; then echo a; fi; echo "дошли сюда"
B4.  set -e; f() { false; echo "в функции"; }; f; echo "после функции"
B5.  set -u; echo "${UNDEFINED}"
B6.  set -u; echo "${UNDEFINED:-дефолт}"
B7.  set -o pipefail; false | true; echo $?
B8.  set +o pipefail; false | true; echo $?
B9.  trap 'echo прощай' EXIT; echo привет
B10. trap 'echo ошибка на $LINENO' ERR; set -e; ls /нет
B11. t=$(mktemp); trap 'rm -f "$t"' EXIT; ls -l "$t"
B12. set -e; c=0; (( c++ )); echo "дошли сюда"
B13. exec 9>/tmp/a.lock; flock -n 9; echo $?
B14. dir=""; rm -rf "${dir:?dir пуст}"/*
B15. bash -n <<< 'if true; then echo a'
```

- **B1.** Ничего не выведет — скрипт завершится на `false`.
- **B2.** `дошли сюда` — ошибка погашена `|| true`.
- **B3.** `дошли сюда` — команда в условии `if` не роняет скрипт.
- **B4.** Ничего — `false` в теле функции при `set -e` завершает скрипт (функция вызвана
  не в условии).
- **B5.** Ошибка `UNDEFINED: unbound variable`, код 1 (в скрипте — завершение).
- **B6.** Пустая строка… точнее `дефолт`: значение по умолчанию снимает действие `-u`.
- **B7.** `1` — код первой упавшей команды.
- **B8.** `0` — код последней команды (`true`).
- **B9.** `привет`, затем `прощай`.
- **B10.** Сообщение `ошибка на <номер строки>` (плюс ошибка `ls`), затем выход.
- **B11.** Файл вида `/tmp/tmp.XXXXXXXX` с правами `-rw-------`.
- **B12.** Ничего — `(( c++ ))` вернуло 1 (старое значение 0), и `set -e` завершил скрипт.
- **B13.** `0` — блокировка получена (при повторном запуске из другого процесса будет 1).
- **B14.** Команда не выполнится: bash напечатает `dir: dir пуст` и завершит скрипт.
- **B15.** Синтаксическая ошибка: `unexpected end of file` — не хватает `fi`.

**B16.** Что выведет и почему:
```bash
set -euo pipefail
count=$(grep -c "НЕТ_ТАКОЙ_СТРОКИ" /etc/passwd)
echo "count=$count"
```

<details><summary>Ответ</summary>

Скрипт упадёт на строке с `grep`: при отсутствии совпадений `grep -c` возвращает 1,
а `set -e` это ловит (переменная `count` даже не будет напечатана). Правильно:
`count=$(grep -c "…" /etc/passwd || true)` или `count=$(grep -c … || echo 0)`.

</details>

### Блок D. Инциденты

**D1.** Ночной бэкап «успешно» отработал 30 раз подряд, а при восстановлении архивы оказались
пустыми. Скрипт всегда возвращал 0. Что было не так и как это предотвратить?

<details><summary>Ответ</summary>

Скрипт не проверял код `tar`/`pg_dump` (нет `set -e`, нет `pipefail`, нет `|| die`),
а `exit 0` стоял в конце безусловно. Нужно: строгий режим, явные проверки, проверка размера
и целостности архива (`tar -tzf`, `gzip -t`), а главное — регулярная **тестовая проверка
восстановления**: бэкап, который не восстанавливали, не существует.

</details>

**D2.** Скрипт деплоя упал на середине: старая версия удалена, новая не распакована,
сервис лежит. Какие два приёма из темы это предотвращают?

<details><summary>Ответ</summary>

(1) Атомарность: сначала подготовить новое в отдельном каталоге, затем переключить
симлинк/`mv` — а не удалять старое первым. (2) `trap` + откат к предыдущей версии и
`set -euo pipefail`, чтобы падение произошло до разрушающего шага. Плюс `--dry-run`
и проверка предусловий (артефакт скачан и валиден) до остановки сервиса.

</details>

**D3.** Раннер GitLab CI за неделю забил диск: `/tmp` полон каталогов `tmp.XXXX`. Причина?

<details><summary>Ответ</summary>

Скрипты создают `mktemp -d`, но не ставят `trap 'rm -rf "$tmpdir"' EXIT`,
а job падает/отменяется до строки уборки. Чинится trap'ом и периодической очисткой раннера.

</details>

**D4.** Бэкап базы стал запускаться параллельно сам с собой и положил прод по I/O.
В crontab он раз в 10 минут, а идёт 15. Решение?

<details><summary>Ответ</summary>

Обернуть запуск в `flock -n` в crontab (или перейти на systemd-таймер, который сам
не запускает второй экземпляр сервиса). Заодно пересмотреть частоту и добавить ограничение
I/O (`ionice -c3`, `nice`).

</details>

**D5.** После `kill -9` скрипт больше не запускается: «уже выполняется». Что за реализация
блокировки и как переделать?

<details><summary>Ответ</summary>

Реализация через файл-флаг: `[[ -f /tmp/x.lock ]] && exit; touch /tmp/x.lock` с удалением
в конце. После `kill -9` файл остался. Переделать на `flock` (дескриптор освобождается ядром)
или, если очень нужен файл, хранить в нём PID и проверять `kill -0 "$pid"`.

</details>

**D6.** В логах CI обнаружили токен доступа в открытом виде. В скрипте стоял `set -x`.
Как надо было?

<details><summary>Ответ</summary>

Трассировка печатает команды целиком, вместе со значениями переменных. Нужно:
`set +x` перед работой с секретом и `set -x` после; либо `BASH_XTRACEFD` в файл, не попадающий
в артефакты; передавать секрет через stdin/файл; в GitLab CI — использовать masked-переменные
(и помнить, что маскирование не работает для многострочных и «нестандартных» значений).

</details>

**D7.** Скрипт с `set -e` внезапно завершается на строке `(( counter++ ))`, хотя ошибки нет.
Объясни.

<details><summary>Ответ</summary>

`(( expr ))` возвращает 1, если результат выражения равен 0. При `counter=0`
постфиксный `counter++` возвращает старое значение 0 → код 1 → `set -e` завершает скрипт.
Пишут `(( ++counter ))`, `counter=$((counter+1))` или `(( counter++ )) || true`.

</details>

**D8.** `cleanup` в `trap EXIT` отрабатывает, но скрипт всегда возвращает 0, даже когда упал.
Что забыли?

<details><summary>Ответ</summary>

В `cleanup` не сохранили и не вернули исходный код: последняя команда в обработчике
(например, `echo`) вернула 0, и он стал кодом выхода скрипта. Нужно `local rc=$?` в начале
и `exit "$rc"` в конце обработчика.

</details>

**D9.** Скрипт удалил содержимое корня файловой системы на тестовом сервере.
В коде было `rm -rf $DATA_DIR/`. Разбери цепочку и напиши три защиты.

<details><summary>Ответ</summary>

Цепочка: переменная не была задана (опечатка/не тот конфиг) → `set -u` отсутствовал →
`rm -rf /` выполнился от root. Защиты: (1) `set -u` и `${DATA_DIR:?}`; (2) проверка
`[[ -d $DATA_DIR && $DATA_DIR == /data/* ]]`; (3) чёрный список путей (`/`, `/home`, `$HOME`)
и `--dry-run` по умолчанию с явным `--force` для реального удаления. Плюс запуск не от root,
где это возможно.

</details>

### Блок E. Вопросы с собеседования

**1.** Что такое `set -euo pipefail` и зачем каждая из опций?

<details><summary>Ответ</summary>

Строгий режим: падать при ошибке (`-e`), при обращении к необъявленной переменной (`-u`),
учитывать код упавшей команды в конвейере (`pipefail`).

</details>

**2.** Где `set -e` не сработает?

<details><summary>Ответ</summary>

В условиях `if`/`while`, в `&&`/`||`, после `!`, при `local x=$(cmd)` и при явном `|| true`.

</details>

**3.** Как гарантированно удалить временные файлы при любом завершении скрипта?

<details><summary>Ответ</summary>

`trap cleanup EXIT` — сработает при нормальном выходе, ошибке и сигналах (кроме SIGKILL).

</details>

**4.** Как защитить скрипт от параллельного запуска?

<details><summary>Ответ</summary>

`flock` на файле блокировки (в crontab — `flock -n /var/lock/x.lock script.sh`).

</details>

**5.** Как передать секрет в скрипт и почему не аргументом?

<details><summary>Ответ</summary>

Через stdin, файл с правами 600 или переменную окружения — но не аргументом, потому что
аргументы видны в `ps aux` и истории.

</details>

**6.** Что такое идемпотентность и зачем она в автоматизации?

<details><summary>Ответ</summary>

Повторный запуск не меняет результат и не ломает систему; нужна, потому что ретраи
и повторные запуски в cron/CI/Ansible неизбежны.

</details>

**7.** Как отлаживать bash-скрипт?

<details><summary>Ответ</summary>

`bash -n` (синтаксис), `bash -x`/`set -x` с информативным `PS4`, `trap … ERR` с `$LINENO`
и `$BASH_COMMAND`, логирование, shellcheck, при необходимости — тесты на bats.

</details>

**8.** Что такое shellcheck?

<details><summary>Ответ</summary>

Статический анализатор shell-скриптов, ловит типовые ошибки (кавычки, `ls`, `[ ]`, `cd`).

</details>

**9.** Какие коды выхода использует твой скрипт и почему?

<details><summary>Ответ</summary>

0 — успех, 1 — ошибка выполнения, 2 — неверные аргументы, 3 — не выполнены предусловия;
для мониторинга — 0/1/2/3 в Nagios-смысле.

</details>

**10.** Как бы ты сделал деплой-скрипт безопасным для прода?

<details><summary>Ответ</summary>

`set -euo pipefail`, `--dry-run` по умолчанию для разрушающих операций, проверка предусловий,
атомарное переключение версий, блокировка от параллельного запуска, логирование с метками
времени, идемпотентность, понятные коды выхода, shellcheck в CI и ревью.

</details>
