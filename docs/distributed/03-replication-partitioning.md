## 1. Зачем копировать и зачем резать

| | Репликация | Шардирование (партиционирование) |
|-|-----------|----------------------------------|
| Что делает | Держит **одни и те же** данные на нескольких узлах | Делит данные на **непересекающиеся** куски по узлам |
| Решает | Отказ узла, масштаб чтения, задержку до пользователя | Объём больше одной машины, масштаб записи |
| Не решает | Запись упирается в одного лидера; объём = одна машина | Отказ узла теряет его кусок (если без реплик) |
| Главная сложность | Согласованность копий и лаг (тема [02_consistency_cap.md](/distributed/02-consistency-cap)) | Выбор ключа, перекосы, ребалансировка, запросы по нескольким шардам |

В реальных системах они почти всегда вместе:

```text
 Kafka-топик orders, 3 партиции, RF 3:        Ceph-пул, PG 1.a, size 3:
   P0: лидер b1, фолловеры b2 b3                объект → hash → PG 1.a → CRUSH → [osd.3, osd.7, osd.1]
   P1: лидер b2, фолловеры b3 b1                первый OSD в наборе — primary для этой PG
   P2: лидер b3, фолловеры b1 b2
 лидеры разнесены: каждый брокер — лидер для части партиций и фолловер для остальных
```text

## 2. Single-leader: один пишет, остальные повторяют

```text
 клиенты-писатели ──► ЛИДЕР (primary) ──поток изменений (WAL, лог)──► фолловер 1
                            │                                     └──► фолловер 2
 клиенты-читатели ──────────┴──── могут читать и с фолловеров (с лагом!)
```text
Так устроены PostgreSQL, MySQL, Redis (master/replica), MongoDB (replica set), Kafka (лидер
партиции), etcd (лидер Raft — тема [04_consensus_quorum.md](/distributed/04-consensus-quorum)).

### Когда лидер отвечает «записано»

| Режим | Лидер ждёт | Потеря при падении лидера | Цена | Где в волте |
|-------|-----------|---------------------------|------|-------------|
| **Асинхронный** | Только себя | Последние транзакции, не доехавшие до реплик | Минимальная задержка | PG по умолчанию, Redis, MySQL по умолчанию |
| **Синхронный** | Подтверждения реплики(-к) | Почти ноль | +RTT на запись; реплика недоступна — запись встаёт | PG `synchronous_standby_names`, `synchronous_commit` |
| **Semi-sync** | Что хотя бы одна реплика **получила** (не применила) | Мала | +RTT; в MySQL по таймауту **молча уходит в async** | MySQL `rpl_semi_sync_*`; аналог в PG — `remote_write` |
| **Кворумный** | Любые k из n реплик | Нет, пока жив кворум | +RTT до k-й по скорости | PG `ANY 1 (s1, s2)`, Kafka ISR + `acks=all`, Raft |

**Kafka ISR** — удобный пример «гибкого синхронного набора»: при `acks=all` лидер ждёт
все реплики из ISR, но фолловер, отставший дольше `replica.lag.time.max.ms` (по умолчанию
30 с), выкидывается из ISR — и ждать его перестают. Чтобы набор не сжался до одного
лидера, есть `min.insync.replicas`: меньше — запись отклоняется.

### Failover — где single-leader становится опасным

```text
 1. Лидер упал (или кажется упавшим — тема 01: таймаут не отличает мёртвого от медленного)
 2. Выбрать нового: реплику с самым свежим логом (наименьшим лагом)
 3. Переключить клиентов: DNS, VIP, HAProxy + Patroni, Sentinel, метаданные Kafka
 4. Старый лидер вернулся — он обязан стать репликой, а не продолжить писать
```text
| Что может пойти не так | Пример |
|------------------------|--------|
| Асинхронная реплика не получила последние записи | Подтверждённые клиенту транзакции потеряны (RPO > 0) |
| Потерянные записи уже «видели» другие системы | Кэш или Kafka хранят ID, которых в новой базе нет, — ID выдаются повторно |
| Два лидера | Сеть моргнула, старый лидер жив и пишет → split brain (темы 04, 06) |
| Неверный таймаут | Короткий — лишние failover'ы; длинный — долгий простой (тема 01) |

## 3. Аномалии лага

Лаг асинхронной реплики в норме — миллисекунды, под нагрузкой — секунды и минуты. Три
аномалии, которые он порождает:

| Аномалия | Что видит пользователь | Лечение |
|----------|------------------------|---------|
| **Нет read-your-writes** | «Создал ссылку — её нет» | Своё с primary, ожидание LSN, `remote_apply` (тема 02, §7) |
| **Нет monotonic reads** | Данные «появляются и исчезают» при обновлении страницы | Sticky к одной реплике, максимальный увиденный LSN |
| **Нет consistent prefix** | Следствие видно раньше причины | Связанные записи — в одну партицию/шард; causal-упорядочивание |

Consistent prefix — особенно коварна в **шардированных** системах: у каждого шарда свой лаг,
и порядок между шардами никто не гарантирует.

```text
 Kafka-топик chat без ключа (или ключ = id сообщения):
   P0 ← «Алия: сервер упал?»          (лаг потребителя P0: 5 с)
   P1 ← «Бекзат: уже поднял»          (лаг потребителя P1: 0 с)
 читатель видит ответ за 5 секунд до вопроса ❌

 лечение: ключ = id чата → оба сообщения в одной партиции → порядок сохранён
 (порядок в Kafka гарантирован только ВНУТРИ партиции)
```text

## 4. Multi-leader: пишут несколько

Несколько узлов принимают записи и обмениваются изменениями. Зачем:

| Сценарий | Почему single-leader плох |
|----------|---------------------------|
| Несколько ДЦ или регионов | Каждая запись ехала бы в чужой регион (+100 мс), и регион с лидером — точка отказа |
| Офлайн-клиенты (мобильное приложение, календарь) | Устройство — «лидер» своей копии, синхронизируется, когда появится сеть |
| Совместное редактирование (Google Docs, Figma) | Каждый редактор пишет локально, изменения сливаются |

Цена — **конфликты записи**: два лидера одновременно изменили одно и то же.

```text
 регион Алматы:     UPDATE links SET url='https://a.kz'  WHERE code='x'  ─┐
 регион Франкфурт:  UPDATE links SET url='https://b.de'  WHERE code='x'  ─┤ оба «успешны»
                                                                          ▼
                            обменялись изменениями — какое значение правильное?
```text
| Стратегия | Как | Минусы |
|-----------|-----|--------|
| **Избегать** | У каждой записи «домашний» лидер: пользователь из KZ пишет только в Алматы | Перенос «дома» при отказе региона — снова конфликты |
| **LWW** (last writer wins) | Побеждает запись с большей меткой времени (или ID узла) | **Тихо теряет** данные; метки времени зависят от часов (тема [05_time_ordering.md](/distributed/05-time-ordering)); так S3 разрешает одновременные PUT, Cassandra — записи ячеек |
| **Слить в приложении** | Хранить обе версии (siblings), разрешить при чтении или записи | Логика слияния в коде; корзина Amazon в Dynamo: удалённые товары «воскресали» |
| **CRDT** | Типы данных, которые сливаются автоматически и без конфликтов (Shapiro и др., 2011) | Не всё выражается CRDT; растут метаданные |

**CRDT на пальцах:** счётчик кликов, который считают два региона.

```text
 G-Counter: у каждого узла свой счётчик, значение = сумма
   Алматы:    {alm: 5, fra: 0}    Франкфурт: {alm: 0, fra: 3}
   слияние = максимум по каждой позиции → {alm: 5, fra: 3} → 8 кликов
   порядок и повторы обмена не важны: max коммутативен, ассоциативен и идемпотентен
 похожим образом устроены множества (OR-Set), регистры, тексты (Automerge, Yjs)
```text
> ⚠️ Multi-leader для **реляционной** базы (BDR, логическая репликация «туда-обратно», MySQL
> multi-primary) — рискованный выбор: `UNIQUE`, автоинкременты, внешние ключи и триггеры
> плохо дружат с конфликтами. Для linkd уникальность кода требует одного места выдачи
> (тема 02, §6).

## 5. Leaderless: кворумы N, W, R

Лидера нет: клиент (или координатор) пишет на **все** N реплик и ждёт W подтверждений,
читает с R реплик и берёт самую свежую версию. Так устроены Dynamo (Amazon, SOSP 2007),
Cassandra, Riak, ScyllaDB.

```text
 N = 3, W = 2, R = 2  →  R + W = 4 > 3: множества записи и чтения обязательно пересекаются

       запись v2 ──► [A ✓ v2]  [B ✓ v2]  [C ✗ недоступна, осталась v1]      W = 2 ✓
       чтение    ──►            [B v2]    [C v1]                             R = 2
                                  └── хотя бы одна реплика в пересечении видела v2 → вернём v2
                                      и заодно допишем v2 на C (read repair)
```text
| N | W | R | R+W>N? | Переживает недоступность | Для чего |
|---|---|---|--------|--------------------------|----------|
| 3 | 2 | 2 | ✅ | 1 узла на чтение и запись | Типовая конфигурация Dynamo (3, 2, 2) |
| 3 | 3 | 1 | ✅ | Запись — ни одного, чтение — 2 | Быстрые чтения, редкие записи |
| 3 | 1 | 3 | ✅ | Запись — 2, чтение — ни одного | Быстрые записи, редкие чтения |
| 3 | 1 | 1 | ❌ | 2 узлов | Максимум доступности, чтение может быть устаревшим |
| 5 | 3 | 3 | ✅ | 2 узлов | Больше запаса |

В Cassandra это уровни согласованности на запрос: `ONE`, `QUORUM`, `ALL`, `LOCAL_QUORUM`
(кворум внутри своего ДЦ — чтобы не платить межрегиональный RTT, тема 01 §7).

### Как реплики догоняют друг друга

| Механизм | Как | Когда |
|----------|-----|-------|
| **Read repair** | При чтении заметили устаревшую реплику — дописали ей свежую версию | На горячих данных |
| **Anti-entropy** | Фоновое сравнение реплик по деревьям хешей (Merkle trees), досылка разницы | На всём, включая редко читаемое (`nodetool repair` в Cassandra) |
| **Hinted handoff** | Реплика недоступна → запись временно хранит сосед с «подсказкой», потом передаёт | Короткие отказы; в Cassandra подсказки копятся до `max_hint_window` (3 ч) |
| **Sloppy quorum** | Нужные N узлов недоступны → пишем на **любые** W живых (не из «своих» N) | Ради доступности записи; R + W > N после этого **не гарантирует** пересечения |

### ⭐ Кворум ≠ линеаризуемость

R + W > N кажется гарантией «всегда прочитаю последнее», но это не так:

| Почему | Что происходит |
|--------|---------------|
| Sloppy quorum | W подтверждений получено не от «своих» N — чтение по своим R их не увидит |
| Запись в процессе | Запись дошла до одной реплики из трёх: читатель 1 (попал на неё) видит новое, читатель 2 позже — старое |
| Запись не набрала W | Клиенту — ошибка, но на части реплик новое значение осталось и может «всплыть» при чтении |
| Параллельные записи + LWW | Побеждает бо́льшая метка времени, а не «последняя» в реальном времени; часы расходятся |

Для линеаризуемости поверх кворумов нужен консенсус (в Cassandra — легковесные транзакции
на Paxos, `IF NOT EXISTS`) — и это уже тема [04_consensus_quorum.md](/distributed/04-consensus-quorum).

## 6. Шардирование: как резать

| | По диапазону ключа (range) | По хешу ключа (hash) |
|-|---------------------------|----------------------|
| Как | Ключи `a–f` на шард 1, `g–p` на шард 2… | `shard = hash(key) mod число_партиций` |
| Плюсы | Запросы по диапазону (`WHERE ts BETWEEN`) идут в один-два шарда | Равномерное распределение |
| Минусы | Горячие диапазоны: ключ = время → вся текущая запись в одном шарде | Диапазонный запрос — во **все** шарды |
| Где | HBase, Bigtable, MongoDB (range-шардинг), TiKV, CockroachDB | Kafka (ключ → партиция), Redis Cluster, Cassandra, Elasticsearch |

### Горячие ключи и перекос

Даже идеальный хеш не спасёт, если **один ключ** горячий: аккаунт знаменитости, ссылка из
вирусного поста в linkd, одна «большая» партиция Kafka по ключу `tenant=main`.

| Приём | Как | Цена |
|-------|-----|------|
| Кэш перед шардом | Горячий редирект отдаётся из кэша/CDN | Eventual (тема 02) |
| Разбить ключ | `link:x` → `link:x#0 … link:x#9` (случайный суффикс на запись) | Чтение собирает 10 кусков |
| Составной ключ | `tenant + user` вместо `tenant` | Порядок только внутри нового ключа |
| Отдельный шард под «тяжёлого» клиента | Выделенная партиция/кластер | Ручное управление |

### Почему не `hash mod N`

```text
 4 узла → 5 узлов:  ключ остаётся на месте, только если hash mod 4 == hash mod 5
                    это 4 значения из 20 → ПЕРЕЕЗЖАЮТ ~80% ключей
 при каждом изменении числа узлов — почти полная перетасовка данных по сети (тема 01: полоса не бесконечна)
```text
Два решения, которые встретишь везде:

**1. Consistent hashing** (Каргер и др., 1997). Узлы и ключи хешируются на одно кольцо;
ключ принадлежит первому узлу по часовой стрелке. Добавили узел — он забирает только
кусок у соседа: переезжает ~1/N ключей.

```text
                 0
          ●N1  ·    · ●N2            ● — точки узлов на кольце
        ·               ·            ключ k → ближайшая точка по часовой стрелке
       ·    k1 → N2       ·
       ·                  ●N3        проблема: 3 точки делят кольцо неровно
        ·   k2 → N1     ·            решение — ВИРТУАЛЬНЫЕ НОДЫ: у каждого узла много точек
          ·   ●N4    ·               (Cassandra num_tokens: 16 по умолчанию с 4.0, раньше 256)
                                     → ровнее нагрузка; упал узел — его кусок делят МНОГИЕ соседи
```text
**2. Фиксированное число партиций больше числа узлов.** Данные режут на P кусков раз и
навсегда, а узлам раздают **целые куски**. Добавили узел — ему переезжает часть кусков, а
отображение «ключ → кусок» не меняется.

| Система | Кусок | Сколько | Ключ → кусок |
|---------|-------|---------|--------------|
| Redis Cluster | Hash slot | 16384 | `CRC16(key) mod 16384`; hash tag `{user:42}` — в хеш идёт только часть в фигурных скобках |
| Ceph | Placement group | `pg_num` на пул (autoscaler, ~100 PG на OSD) | `hash(имя объекта) mod pg_num`, дальше CRUSH → OSD |
| Elasticsearch | Primary shard | Задаётся при создании индекса | `hash(_routing) mod число_primary` (`_routing` по умолчанию = `_id`) |
| Kafka | Партиция | Задаётся при создании топика, можно только **увеличить** | `hash(key) mod число_партиций` — поэтому добавление партиций **ломает** соответствие ключей |

### Ребалансировка

| Вопрос | Правильный ответ |
|--------|-----------------|
| Автоматически или руками? | Перенос данных — тяжёлая операция; автоматический перенос при ложном «узел умер» (тема 01) может добить кластер. Многие системы предлагают план, а запускает человек (Kafka `kafka-reassign-partitions`, Redis `--cluster rebalance`) |
| Как не положить прод? | Ограничивать скорость: `--throttle` у переназначения Kafka, `osd_max_backfills` и recovery-лимиты в Ceph |
| Что с клиентами во время переноса? | Они должны уметь «переспросить»: `MOVED`/`ASK` в Redis Cluster, обновление метаданных в Kafka, новая карта OSD в Ceph |
| Когда начинать? | Заранее: при 70–80% заполнения, а не когда диск полон (эмпирическое правило) |

## 7. Вторичные индексы в шардированной базе

Поиск по первичному ключу идёт в один шард. А «все ссылки пользователя 42», если шардируем
по коду ссылки?

```text
 ЛОКАЛЬНЫЙ индекс (по документу)                ГЛОБАЛЬНЫЙ индекс (по значению)
 каждый шард индексирует свои документы         индекс сам шардирован по значению поля
 шард 1: owner=42 → [x1]                        индекс-шард A (owner 0–49): owner=42 → [x1, y7, z3]
 шард 2: owner=42 → [y7]                        индекс-шард B (owner 50–99): …
 шард 3: owner=42 → [z3]
 запрос «owner=42» → во ВСЕ шарды               запрос «owner=42» → в ОДИН индекс-шард
 (scatter/gather: хвост латентности = самый     но запись документа трогает ДРУГОЙ шард индекса →
  медленный шард, тема 01 §7)                   индекс обновляется асинхронно = eventual
 Elasticsearch, MongoDB, Cassandra (2i)          DynamoDB GSI (всегда eventually consistent)
```text
Практический вывод: ключ шардирования выбирают под **самый частый** запрос; для остальных —
либо scatter/gather с его хвостом, либо глобальный индекс с его задержкой, либо отдельное
хранилище (поиск в Elasticsearch рядом с основной базой).

## 8. Всё вместе: как это устроено в твоих системах

| Система | Шардирование | Репликация | Что при отказе | Где подробно |
|---------|--------------|------------|----------------|--------------|
| **PostgreSQL** | Нет из коробки (Citus, шардинг в приложении) | Single-leader, async / sync / кворумный | Failover через Patroni; async — возможна потеря | [../Left/01_Databases/06_replication.md](/databases/06-replication) |
| **Kafka** | Партиции по `hash(key)` | Лидер партиции + фолловеры, ISR | Новый лидер из ISR; `unclean` — из кого угодно | [../Left/05_Queues/03_kafka_ops.md](/queues/03-kafka-ops) |
| **Redis Cluster** | 16384 слота, CRC16, hash tags | Master + реплики на слот-группу, **асинхронно** | Реплика повышается голосованием мастеров; подтверждённые записи могут пропасть; меньшинство перестаёт писать через `NODE_TIMEOUT` | [../Left/01_Databases/09_redis_mongo_clickhouse.md](/databases/09-redis-mongo-clickhouse) |
| **Ceph** | Объект → PG → CRUSH | `size` копий или EC; primary OSD PG координирует запись | `min_size` не набран — PG inactive, I/O стоит | [../Storage/04_ceph.md](/storage/04-ceph) |
| **Elasticsearch** | Primary shards (число — при создании, split/shrink — через новый индекс) | Replica shards, никогда на одном узле со своим primary | Реплика повышается до primary; статус yellow/red | [../Left/03_Logging/02_elk_stack.md](/logging/02-elk-stack) |
| **Cassandra** | Consistent hashing, vnodes | Leaderless, N реплик, кворумы на запрос | Hinted handoff, read repair, `nodetool repair` | — |
| **etcd** | Нет: все данные на каждом участнике | Raft (кворумный single-leader) | Потеря кворума — запись стоит | [04_consensus_quorum.md](/distributed/04-consensus-quorum) |

> 💡 Заметь, что Kafka, Redis Cluster, Ceph и Elasticsearch сами по себе не выбирают лидеров
> «на глазок» — это делает кворум: контроллеры KRaft, голосование мастеров Redis Cluster,
> MON'ы Ceph на Paxos, master-узлы ES. Как именно — следующая тема.

## 9. Мини-лаба: асинхронная репликация Redis теряет подтверждённую запись

Цель: увидеть лаг и чтение «прошлого» с реплики, узнать, что `WAIT` не откатывает запись,
как `min-replicas-to-write` выбирает C вместо A, и как failover теряет подтверждённое.

```bash
mkdir -p ~/labs/distributed/03 && cd ~/labs/distributed/03
cat > compose.yaml <<'EOF'
services:
  master:
    image: redis:8                         # проверь тег (или valkey/valkey:8)
  replica:
    image: redis:8
    command: redis-server --replicaof master 6379
EOF
docker compose up -d
M="docker compose exec -T master redis-cli"
S="docker compose exec -T replica redis-cli"
until $S INFO replication | grep -q master_link_status:up; do sleep 1; done   # ждём первичную синхронизацию
$M INFO replication | grep -E 'role|connected_slaves|master_repl_offset'
$S INFO replication | grep -E 'role|master_link_status|slave_repl_offset'
$M SET k1 v1 && $S GET k1                        # "v1" — в норме лаг незаметен
```text
```bash
# 1. Режем связь: реплика «отстаёт навсегда», но продолжает отвечать
NET=$(docker inspect -f '&#123;&#123;range $k,$v := .NetworkSettings.Networks&#125;&#125;&#123;&#123;$k&#125;&#125;&#123;&#123;end&#125;&#125;' $(docker compose ps -q replica))
docker network disconnect "$NET" $(docker compose ps -q replica)
$M SET k2 new                                     # OK — master подтвердил
$S GET k2                                         # (nil) — реплика отдаёт прошлое (replica-serve-stale-data yes)
$S INFO replication | grep master_link_status     # может ещё показывать up: обрыв заметят по repl-timeout (60 с)

# 2. WAIT: «дождись 1 реплику, но не дольше 2 с». WAIT ждёт записи СВОЕГО соединения,
#    поэтому SET и WAIT — в одном redis-cli (отдельный вызов WAIT сразу вернёт «успех»)
printf 'SET k3 v3\nWAIT 1 2000\n' | $M             # OK, затем 0 — ни одна реплика не подтвердила
$M GET k3                                         # "v3" — запись НЕ откатилась: WAIT только сообщает

# 3. Выбор C вместо A: не принимать записи без свежей реплики
$M CONFIG SET min-replicas-to-write 1
$M CONFIG SET min-replicas-max-lag 10
sleep 11; $M SET k4 v4                            # (error) NOREPLICAS Not enough good replicas to write.
$M CONFIG SET min-replicas-to-write 0             # вернуть доступность

# 4. Связь вернулась — реплика догоняет (частичная ресинхронизация по offset)
docker network connect --alias replica "$NET" $(docker compose ps -q replica)
$S CLIENT KILL TYPE master                        # не ждать repl-timeout: переподключиться сразу
sleep 3; $S GET k2; $S GET k3                     # "new", "v3" — eventual: сошлось
docker compose logs replica | grep -i 'partial resynchronization' | tail -2   # Successful partial resynchronization
```text
```bash
# 5. ⭐ Потеря подтверждённой записи при failover
docker network disconnect "$NET" $(docker compose ps -q replica)
$M SET order:42 paid                              # OK — клиент уверен, что записано
docker compose stop master                        # master «умер» до репликации
$S REPLICAOF NO ONE                               # повышаем реплику (так сделал бы Sentinel)
$S GET order:42                                   # (nil) — подтверждённой записи НЕТ
docker compose down

# 6. Бонус — слоты Redis Cluster и hash tags (пустой узел в режиме кластера)
docker run --rm -d --name slot redis:8 redis-server --cluster-enabled yes
docker exec slot redis-cli CLUSTER KEYSLOT user:42          # один слот
docker exec slot redis-cli CLUSTER KEYSLOT cart:user:42     # скорее всего другой
docker exec slot redis-cli CLUSTER KEYSLOT '{user:42}:cart' # = слоту строки "user:42"
docker exec slot redis-cli CLUSTER KEYSLOT '{user:42}:profile'   # тот же → MULTI/MGET по ним возможен
docker rm -f slot
```text
Что записать себе: чем шаг 2 (`WAIT` вернул 0, а запись осталась) похож на отмену ожидания
синхронной репликации в PostgreSQL из темы 02; сколько подтверждённых записей потеряно в
шаге 5 и что ограничило бы окно потери; зачем нужны hash tags и чем грозит один «гигантский»
тег `{all}` для всех ключей.

## 10. Грабли

| Грабля | Последствие | Правильно |
|--------|-------------|-----------|
| Асинхронная реплика + автоматический failover без оценки RPO | Подтверждённые транзакции теряются, ID выдаются повторно | Осознанный RPO, кворумная/синхронная реплика для критичного |
| Одна синхронная реплика | Реплика упала — запись встала | Кворумный режим `ANY 1 (s1, s2)` |
| Semi-sync MySQL «гарантирует» | По таймауту молча переходит в async | Алерт на статус semi-sync |
| Multi-leader для реляционной базы «ради доступности» | Конфликты `UNIQUE`, дубли, тихие потери LWW | Single-leader + «домашний» регион, или CRDT для подходящих данных |
| LWW по времени серверов | Потеря записей при расхождении часов | Логические версии, CRDT, fencing (тема 05) |
| Верить, что R + W > N = «всегда свежее» | Устаревшие и «всплывающие» значения | Понимать sloppy quorum и частичные записи; для строгих операций — консенсус |
| Шардирование по времени | Горячий шард текущего дня | Хеш или составной ключ |
| `hash mod N` для кэша/шардов | Добавили узел — промах кэша на ~80% ключей | Consistent hashing или фиксированные слоты |
| Добавили партиции в Kafka-топик с ключами | Ключи переехали, порядок по ключу нарушен | Планировать число партиций заранее; миграция в новый топик |
| Ребалансировка без throttle | Сеть и диски забиты, прод тормозит | `--throttle`, лимиты recovery/backfill, окно работ |
| Hash tag на всё (`{app}:...`) | Все ключи в одном слоте — один узел греется | Теги только для реально связанных ключей |
| `WAIT` отдельным соединением или через пул | Всегда «подтверждено»: WAIT ждёт записи только своего соединения | `SET` и `WAIT` в одном соединении (или `MULTI`/pipeline) |
| Сообщения одной сущности без ключа | Нарушение consistent prefix | Ключ = id сущности |

## 💼 Как это в DevOps

- Девопс выбирает **режим репликации** (async/sync/кворум), **RPO** и что делать при failover —
  и объясняет бизнесу, сколько транзакций можно потерять. Это не «настройка базы», это решение.
- Мониторинг репликации: лаг в секундах и байтах (PG `replay_lag`), размер ISR и
  `UnderReplicatedPartitions` (Kafka), `master_link_status` и offset (Redis), PG `degraded`
  (Ceph), статус yellow (Elasticsearch). Каждый — «копий меньше, чем обещано».
- Число партиций Kafka, шардов Elasticsearch и PG Ceph задают при создании — это
  capacity planning на годы вперёд; менять потом дорого.
- Ребалансировку планируют как изменение: окно, throttle, мониторинг сети и дисков, план
  отката. «Добавили ноду в пятницу — ребаланс положил кластер» — классика постмортемов.
- На собесе: «синхронная vs асинхронная репликация», «что такое кворум», «как шардировать»,
  «что такое consistent hashing», «почему пользователь не видит свою запись».

## 🧠 Что запомнить

1. Репликация — копии одних данных, шардирование — куски разных; в жизни почти всегда вместе.
2. ⭐ Асинхронная репликация быстра, но теряет подтверждённое при failover; синхронная с одной
   репликой останавливает запись; кворумная (`ANY k`, ISR, Raft) — рабочий компромисс.
3. Лаг порождает три аномалии: нет read-your-writes, monotonic reads и consistent prefix.
4. Multi-leader нужен для регионов и офлайна, но платит конфликтами; LWW тихо теряет данные,
   CRDT сливают без конфликтов, но подходят не для всего.
5. ⭐ Leaderless: R + W > N даёт пересечение кворумов, но не линеаризуемость — из-за sloppy
   quorum, частичных записей и LWW.
6. Read repair, anti-entropy и hinted handoff — как реплики без лидера догоняют друг друга.
7. Range-шардирование даёт диапазонные запросы и горячие точки, hash — равномерность и scatter.
8. ⭐ `hash mod N` перетасовывает почти всё при изменении N; consistent hashing с виртуальными
   нодами и фиксированное число партиций переносят только часть.
9. Redis Cluster — 16384 слота по CRC16 и hash tags; Kafka — партиции по `hash(key)`, добавление
   партиций ломает порядок по ключу; Ceph — PG и CRUSH; Elasticsearch — primary shards при создании.
10. Ребалансировка — изменение с throttle и окном, а автоматический перенос при ложном отказе
    может добить кластер.

### Блок A. Теория


**A1.** Чем репликация отличается от шардирования? Что решает каждая и чего не решает?

<details><summary>Ответ</summary>

Репликация — копии одних данных (отказ узла, масштаб чтения, близость к пользователю;
не решает масштаб записи и объём). Шардирование — непересекающиеся куски (объём и масштаб
записи; без реплик отказ узла теряет его кусок, сложны межшардовые запросы).

</details>

**A2.** ⭐ Сравни асинхронную, синхронную, semi-sync и кворумную репликацию: чего ждёт лидер,
что теряется при его падении, где в волте каждая встречается.

<details><summary>Ответ</summary>

Async — лидер ждёт только себя, при падении теряются недоехавшие транзакции (PG и
MySQL по умолчанию, Redis). Sync — ждёт подтверждения реплики, потери почти нет, +RTT, реплика
недоступна — запись встаёт (PG `synchronous_standby_names`). Semi-sync — ждёт, что реплика
получила, в MySQL по таймауту уходит в async. Кворумная — ждёт любые k из n (PG `ANY 1 (s1, s2)`,
Kafka ISR + `acks=all`, Raft).

</details>

**A3.** Что такое ISR в Kafka и чем он похож на кворумную репликацию? Зачем `min.insync.replicas`?

<details><summary>Ответ</summary>

ISR — реплики, отстающие не больше `replica.lag.time.max.ms` (30 с). С `acks=all` лидер
ждёт всех из ISR, а медленные выпадают из набора — ждут «достаточно синхронные». Без
`min.insync.replicas` ISR может сжаться до лидера, и `acks=all` станет `acks=1`; с ним запись
отклоняется, если реплик в ISR меньше порога.

</details>

**A4.** Перечисли, что может пойти не так при failover single-leader системы.

<details><summary>Ответ</summary>

Потеря неуспевших асинхронных транзакций; повторная выдача ID, которые уже видели другие
системы; два лидера (split brain) при ложном отказе; неправильный таймаут (лишние или поздние
failover'ы); клиенты не переключились (кэш DNS, старые соединения); старый лидер вернулся и
продолжил писать.

</details>

**A5.** ⭐ Назови три аномалии лага реплик и лечение каждой. Почему consistent prefix особенно
легко нарушить в шардированной системе?

<details><summary>Ответ</summary>

Нет read-your-writes (своё с primary, LSN), нет monotonic reads (sticky, максимальный LSN),
нет consistent prefix (связанные записи в одну партицию, causal). У каждого шарда свой лаг и
нет порядка между шардами, поэтому причина и следствие в разных шардах легко меняются местами.

</details>

**A6.** Зачем нужна multi-leader репликация? Приведи три сценария.

<details><summary>Ответ</summary>

Несколько регионов (писать локально, не зависеть от одного региона), офлайн-клиенты
(устройство пишет в свою копию), совместное редактирование.

</details>

**A7.** ⭐ Какие есть стратегии разрешения конфликтов записи? Почему LWW опасен?

<details><summary>Ответ</summary>

Избегать (у записи «домашний» лидер), LWW, слияние в приложении (siblings), CRDT. LWW
тихо выбрасывает одну из записей, а «последняя» определяется метками времени, которые зависят
от часов узлов — выиграть может запись, сделанная раньше в реальном времени.

</details>

**A8.** Что такое CRDT? Объясни G-Counter: как хранится, как сливается, почему порядок обмена
не важен.

<details><summary>Ответ</summary>

Типы данных, реплики которых сливаются автоматически без конфликтов. G-Counter — вектор
счётчиков по узлам; каждый узел увеличивает только свою позицию; слияние — максимум по позициям,
значение — сумма. Max коммутативен, ассоциативен и идемпотентен, поэтому порядок и повторы обмена
не влияют на результат.

</details>

**A9.** ⭐ Как работает leaderless-репликация? Что значат N, W, R и условие R + W > N?

<details><summary>Ответ</summary>

Клиент/координатор пишет на все N реплик и ждёт W подтверждений, читает с R и берёт
самую свежую версию. При R + W > N множества записи и чтения пересекаются хотя бы в одной
реплике, видевшей последнюю успешную запись.

</details>

**A10.** Какие конфигурации (N, W, R) для N = 3 ты знаешь и для чего каждая?

<details><summary>Ответ</summary>

(3, 2, 2) — типовая, переживает 1 недоступный узел на чтение и запись; (3, 3, 1) — быстрые
чтения, запись не переживает отказ; (3, 1, 3) — быстрые записи, чтение не переживает отказ;
(3, 1, 1) — максимум доступности, чтения могут быть устаревшими.

</details>

**A11.** Что такое read repair, anti-entropy, hinted handoff и sloppy quorum?

<details><summary>Ответ</summary>

Read repair — при чтении дописать свежую версию отставшей реплике. Anti-entropy — фоновое
сравнение реплик по деревьям хешей (Merkle) и досылка разницы. Hinted handoff — сосед временно
хранит запись для недоступной реплики и передаёт её потом. Sloppy quorum — если «свои» узлы
недоступны, W подтверждений берут с любых живых.

</details>

**A12.** ⭐ Почему R + W > N ещё не даёт линеаризуемости? Приведи три причины.

<details><summary>Ответ</summary>

Sloppy quorum (подтверждения не от «своих» N — чтение их не увидит); запись в процессе
(разные читатели попадают на реплики с новым и старым значением — второй видит «прошлое» после
первого); неуспешная запись оставляет значение на части реплик; параллельные записи + LWW по
часам.

</details>

**A13.** Сравни шардирование по диапазону и по хешу. Где каждое применяется?

<details><summary>Ответ</summary>

Range — ключи по диапазонам: эффективные диапазонные запросы, но горячие диапазоны
(время); HBase, Bigtable, MongoDB range, CockroachDB, TiKV. Hash — равномерно, но диапазонный
запрос идёт во все шарды; Kafka, Redis Cluster, Cassandra, Elasticsearch.

</details>

**A14.** Что такое горячий ключ? Четыре способа с ним бороться.

<details><summary>Ответ</summary>

Один ключ получает непропорционально много запросов (вирусная ссылка, крупный tenant).
Кэш/CDN перед шардом, разбиение ключа на под-ключи со случайным суффиксом, составной ключ,
выделенный шард под тяжёлого клиента.

</details>

**A15.** ⭐ Почему `hash mod N` плох при изменении числа узлов? Посчитай долю переезжающих
ключей при переходе с 4 на 5 узлов.

<details><summary>Ответ</summary>

При смене N почти у всех ключей меняется `hash mod N` — перетасовка данных и промах
кэша. С 4 на 5: ключ остаётся, если `h mod 4 == h mod 5`; на периоде 20 это 4 значения
(0, 1, 2, 3) → остаётся 20%, переезжает ~80%.

</details>

**A16.** Как работает consistent hashing и зачем виртуальные ноды?

<details><summary>Ответ</summary>

Узлы и ключи хешируются на кольцо, ключ принадлежит ближайшему узлу по часовой стрелке;
новый узел забирает только участок у соседа (~1/N ключей). Виртуальные ноды (много точек на
узел) выравнивают нагрузку и распределяют кусок упавшего узла по многим соседям.

</details>

**A17.** Что такое «фиксированное число партиций»? Приведи четыре системы и как в них ключ
попадает в кусок.

<details><summary>Ответ</summary>

Данные режутся на P кусков раз и навсегда (P ≫ узлов), узлам раздают целые куски.
Redis Cluster — 16384 слота, `CRC16(key) mod 16384`; Ceph — PG, `hash(объект) mod pg_num` и CRUSH;
Elasticsearch — primary shards, `hash(_routing) mod число_primary`; Kafka — партиции,
`hash(key) mod число_партиций`.

</details>

**A18.** ⭐ Как Redis Cluster распределяет ключи? Что такое hash tag и `MOVED`/`ASK`?

<details><summary>Ответ</summary>

16384 слота, слот = `CRC16(key) mod 16384`, каждый master обслуживает часть слотов.
Hash tag: если в ключе есть `{…}` с непустым содержимым, хешируется только оно — связанные
ключи попадают в один слот (нужно для многоключевых команд). `MOVED` — слот живёт на другом
узле постоянно (клиент обновляет карту); `ASK` — слот в процессе переноса, этот запрос
отправь туда один раз.

</details>

**A19.** Чем локальный вторичный индекс отличается от глобального в шардированной базе?

<details><summary>Ответ</summary>

Локальный: каждый шард индексирует свои документы, запрос по полю идёт во все шарды
(scatter/gather, хвост латентности). Глобальный: индекс шардирован по значению поля, запрос
идёт в один шард индекса, но запись трогает другой шард — индекс обновляется асинхронно
(eventual, как GSI DynamoDB).

</details>

**A20.** Почему добавление партиций в Kafka-топик с ключами опасно?

<details><summary>Ответ</summary>

Партиция = `hash(key) mod число_партиций`: при изменении числа партиций ключи переезжают,
новые события сущности идут в другую партицию, а старые ещё не обработаны — порядок по ключу
нарушается.

</details>

### C1. 🔑 Лаг и WAIT
**1.** Разорви связь реплики (как в мини-лабе), сделай `SET` и `WAIT 1 1000` **в одном соединении**
   (`printf 'SET a 1\nWAIT 1 1000\n' | $M`), а потом `WAIT 1 1000` отдельным вызовом. Почему ответы разные?

<details><summary>Ответ</summary>

`WAIT 1 1000` в том же соединении вернул 0 — ни одна реплика не подтвердила за секунду;
offset реплики отстаёт от master. Отдельный вызов `WAIT` сразу вернул 1: WAIT ждёт offset
последней записи **своего** соединения, а у нового соединения записей не было — через пул
соединений так легко получить ложное «подтверждено». `WAIT` лишь ждёт и сообщает, сколько реплик подтвердили, — запись на master уже
применена и не откатывается. После восстановления связи offset'ы сравнялись (частичная ресинхронизация).

</details>

**2.** Сравни `master_repl_offset` на master и `slave_repl_offset` на реплике.

<details><summary>Ответ</summary>

`NOREPLICAS` пошли примерно через `min-replicas-max-lag` (5 с) после последнего ACK реплики
(ACK — раз в секунду). Подтверждённые до этого инкременты (~5) не дошли до реплики и потеряются
при её повышении. Настройка ограничивает окно потери, но не убирает его.

</details>

**3.** Восстанови связь и убедись, что offset сравнялся. Что показало `WAIT` и почему запись не откатилась?

<details><summary>Ответ</summary>

Ориентиры: `hash mod N` — переезд ~80%, распределение ровное; кольцо без vnodes — переезд
~20%, но перекос в разы (max/min 2–5); 100 vnodes — переезд ~20%, перекос единицы процентов.
```python
import hashlib, bisect
h = lambda s: int(hashlib.md5(s.encode()).hexdigest(), 16)
def ring(nodes, v):
    pts = sorted((h(f"{n}#{i}"), n) for n in nodes for i in range(v))
    keys = [p for p, _ in pts]
    return lambda k: pts[bisect.bisect(keys, h(k)) % len(pts)][1]
keys = [f"k{i}" for i in range(100_000)]
for v in (1, 100):
    a, b = ring(["n1","n2","n3","n4"], v), ring(["n1","n2","n3","n4","n5"], v)
    print(v, sum(a(k) != b(k) for k in keys) / len(keys))
print("mod", sum(h(k) % 4 != h(k) % 5 for k in keys) / len(keys))
```text
</details>

### Блок D. Инциденты


**D1.** После автоматического failover PostgreSQL в заказах появились дубли номеров: новые

**D2.** После добавления узла в кэш-кластер нагрузка на базу выросла в 5 раз на полчаса.

<details><summary>Ответ</summary>

Выбор узла `hash mod N`: добавление узла перетасовало ~80% ключей — массовые промахи кэша.
Consistent hashing, прогрев, добавление узлов вне пика.

</details>

**D3.** В Kafka после увеличения числа партиций события одного заказа начали обрабатываться

**D4.** В Redis Cluster один узел загружен на 95% CPU, остальные — на 10%.

**D5.** После сетевого разделения в Cassandra удалённые записи «воскресли».

<details><summary>Ответ</summary>

Удаление в leaderless — это надгробие (tombstone); если реплика была недоступна дольше

недоступных узлов.

</details>

**D6.** Ребалансировка после добавления брокера Kafka на 3 часа подняла латентность всех топиков.

### Блок E. Вопросы с собеседования


**1.** Чем синхронная репликация отличается от асинхронной? Что выберешь для платежей?

<details><summary>Ответ</summary>

Синхронная ждёт подтверждения реплики (почти нет потерь, +RTT, риск остановки записи),
   асинхронная — нет (быстро, теряет последнее при failover). Для платежей — кворумная синхронная
   (`ANY 1 (s1, s2)`), чтобы не терять и не зависеть от одной реплики.

</details>

**2.** Что такое кворум? Как выбрать N, W, R?

<details><summary>Ответ</summary>

Минимальное число узлов, чьё согласие нужно для операции; для пересечения — R + W > N; выбор
   по профилю: много чтений — большой W и малый R, и наоборот; большинство (2f+1) — для консенсуса.

</details>

**3.** Что такое шардирование и как выбрать ключ?

<details><summary>Ответ</summary>

Разбиение данных по узлам по ключу; ключ — под самый частый запрос, с высокой кардинальностью
   и без горячих значений; range — для диапазонов, hash — для равномерности.

</details>

**4.** Что такое consistent hashing?

<details><summary>Ответ</summary>

Узлы и ключи на кольце хешей, ключ — ближайшему узлу по часовой; при добавлении узла
   переезжает ~1/N ключей; виртуальные ноды выравнивают распределение.

</details>

**5.** Как устроен Redis Cluster?

<details><summary>Ответ</summary>

16384 слота по `CRC16(key) mod 16384`, слоты распределены между master'ами, у каждого —
   асинхронные реплики; клиенты ходят напрямую и обрабатывают `MOVED`/`ASK`; hash tags для связанных
   ключей; при разделении возможна потеря подтверждённых записей.

</details>

**6.** Какие проблемы у multi-master репликации?

<details><summary>Ответ</summary>

Конфликты параллельных записей, выбор стратегии (LWW теряет данные), уникальные ограничения
   и автоинкременты, сложность отладки и порядок применения изменений.

</details>

**7.** Почему пользователь может не увидеть свою запись и как это исправить?

<details><summary>Ответ</summary>

Чтение с асинхронной реплики или кэша после записи; своё — с primary, ожидание LSN,
   `remote_apply`, sticky + LSN.

</details>

**8.** Как Kafka обеспечивает надёжность и порядок?

<details><summary>Ответ</summary>

Партиции с лидером и фолловерами, ISR, `acks=all` + `min.insync.replicas`, `unclean` выключен;
   порядок — только внутри партиции, поэтому ключ = id сущности.

</details>

**9.** Что такое hot partition / hot key и что с ним делать?

<details><summary>Ответ</summary>

Ключ или партиция, получающие непропорциональную нагрузку. Кэш, разбиение ключа суффиксами,
   составной ключ, выделенный шард, смена ключа партиционирования.

</details>

**10.** Как добавить узел в шардированный кластер, не положив прод?

<details><summary>Ответ</summary>

Заранее (не на 95% диска), в окно работ, с throttle переноса, мониторингом сети/дисков/лага,
    по шагам; убедиться, что клиенты обновляют карту; иметь план отката.

---

</details>
