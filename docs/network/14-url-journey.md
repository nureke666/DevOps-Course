# 14. Что происходит, когда вводишь адрес в браузере

> Роадмап → 2.5 Сети → Собесы: *«Что происходит, когда вы вводите адрес сайта в браузере
> и нажимаете Enter?»* — **вопрос №1 всех собеседований**.
> Это сквозная тема: она связывает всё, что было в блоке, в одну историю.

---

## 🗺️ Полный путь запроса

```text:no-line-numbers
 ① Браузер разбирает URL            https://shop.example.com/cart?id=5
                                    схема │ хост              │ путь │ параметры
 ② HSTS / кеш браузера              — может сразу переписать http→https
 ③ DNS-резолв                       hosts → кеш → резолвер → корень → TLD → NS зоны
 ④ ARP                              узнать MAC шлюза (или адресата в своей сети)
 ⑤ TCP-хендшейк                     SYN → SYN-ACK → ACK   (3 пакета, 1 RTT)
 ⑥ TLS-хендшейк                     ClientHello (SNI, ALPN) → сертификат → сеансовый ключ
 ⑦ HTTP-запрос                      GET /cart?id=5 HTTP/2, Host, Cookie, Authorization
 ⑧ Путь до приложения               файрвол → балансировщик (L4/L7) → nginx/Ingress → бэкенд
 ⑨ Бэкенд                           БД, кеш, внешние API → формирует ответ
 ⑩ HTTP-ответ                       200 OK + заголовки + тело
 ⑪ Рендеринг                        HTML → подзапросы (CSS, JS, картинки) по тем же шагам
 ⑫ Закрытие/переиспользование       keep-alive, затем FIN/ACK и TIME_WAIT
```

---

## Шаг за шагом — что сказать на собеседовании

### ① Разбор URL и решение браузера

Браузер выделяет схему, хост, порт (по умолчанию 443/80), путь и query.
Если домен есть в **HSTS-списке** или в кеше HSTS, `http://` немедленно переписывается
на `https://` — до всякой сети. Проверяются кеш страницы, service worker и прокси-настройки.

### ② DNS (см. [05. DNS](/network/05-dns))

```text:no-line-numbers
/etc/hosts → кеш ОС/браузера → рекурсивный резолвер →
  корень (.) → TLD (.com) → авторитетный NS зоны → A/AAAA-запись
```
Ответ кешируется на TTL. Ошибки: NXDOMAIN (имени нет), SERVFAIL (не смог узнать).

### ③ ARP и маршрутизация (см. [02. L2/Ethernet/ARP](/network/02-l2-ethernet-arp), [03. L3/IP/ICMP](/network/03-l3-ip-icmp))

Хост смотрит таблицу маршрутизации: адрес не в нашей подсети → ARP-запрос про **шлюз**.
Пакет уходит с dst IP сервера и dst MAC шлюза. На каждом маршрутизаторе MAC переписывается,
TTL уменьшается, IP остаётся прежним (если нет NAT).

### ④ TCP (см. [04. L4: TCP/UDP](/network/04-l4-tcp-udp))

```text:no-line-numbers
SYN (seq=x) → SYN-ACK (seq=y, ack=x+1) → ACK (ack=y+1)
```
Клиент берёт эфемерный порт; соединение однозначно определяется пятёркой.
Возможные исходы: RST (порт закрыт), тишина (файрвол DROP).

### ⑤ TLS (см. [07. TLS](/network/07-tls))

ClientHello (версии, шифры, **SNI**, ALPN) → ServerHello + сертификат → проверка цепочки,
срока и SAN → общий сеансовый ключ по ECDHE. TLS 1.3 — 1 RTT. Дальше всё шифруется симметрично.

### ⑥ HTTP-запрос (см. [06. HTTP](/network/06-http))

```text:no-line-numbers
GET /cart?id=5 HTTP/2
Host: shop.example.com          ← по нему выбирается виртуальный хост
Cookie: session=...             ← «состояние» stateless-протокола
Accept-Encoding: gzip, br
```

### ⑦ Путь внутри инфраструктуры (см. [11. Файрвол](/network/11-firewall-iptables), [12. Nginx](/network/12-nginx), [13. HAProxy](/network/13-haproxy-balancing))

```text:no-line-numbers
интернет → firewall/security group → балансировщик (L4) → nginx/Ingress (L7)
        → выбор upstream по health-check → бэкенд (под/контейнер/VM)
        → БД, кеш, очередь, внешние API
```
Здесь добавляются `X-Forwarded-For`/`X-Forwarded-Proto`, применяются rate limit,
кеш и маршрутизация по пути.

### ⑧ Ответ и рендеринг

Сервер отдаёт код и заголовки (`Content-Type`, `Cache-Control`, `Set-Cookie`),
браузер парсит HTML и запускает десятки подзапросов — каждый со своими DNS/TCP/TLS
(или мультиплексированием в HTTP/2 по одному соединению).

### ⑨ Завершение

Keep-alive оставляет соединение для следующих запросов; при закрытии — FIN/ACK с обеих сторон,
инициатор уходит в TIME_WAIT на ~60 секунд.

## 🎤 Ответ за 60 секунд (заучить)

> Браузер разбирает URL и проверяет HSTS и кеш. Дальше резолвит имя: смотрит `/etc/hosts`,
> свой кеш, потом идёт к рекурсивному резолверу, который при промахе проходит цепочку
> от корневых серверов к серверам зоны и возвращает адрес, кешируя его на TTL.
> Зная IP, ядро выбирает маршрут; если адрес не в локальной сети, ARP-запросом узнаётся
> MAC шлюза, и пакет уходит туда — IP на всём пути не меняется, MAC переписывается на каждом
> хопе, TTL уменьшается. Затем устанавливается TCP-соединение тремя рукопожатиями,
> поверх него — TLS: клиент отправляет ClientHello с SNI и списком шифров, сервер отвечает
> сертификатом, клиент проверяет цепочку и имя, стороны вырабатывают сеансовый ключ.
> Внутри шифрованного канала уходит HTTP-запрос с заголовком Host. На той стороне он проходит
> файрвол, балансировщик, который по health-check выбирает живой бэкенд, reverse proxy
> добавляет X-Forwarded-For и проксирует на приложение; оно ходит в базу и кеш и возвращает
> ответ. Браузер получает HTML и повторяет процесс для статики — обычно уже по
> переиспользованному соединению.

## 🔧 Обратная задача: «сайт не открывается» по тем же шагам

| Шаг | Что проверить | Команда |
|-----|---------------|---------|
| DNS | Резолвится ли имя, тот ли адрес | `getent hosts site`, `dig site`, `dig @8.8.8.8 site` |
| Маршрут | Есть ли путь | `ip route get IP`, `mtr -n IP` |
| TCP | Открыт ли порт | `nc -zv site 443` |
| TLS | Валиден ли сертификат | `openssl s_client -connect site:443 -servername site` |
| HTTP | Какой код и сколько времени | `curl -v`, `curl -w` с таймингами |
| Балансировщик | Живы ли бэкенды | stats HAProxy, `error.log` nginx |
| Бэкенд | Отвечает ли напрямую | `curl --resolve site:443:IP`, `curl http://backend:8080/health` |
| Приложение | Что в логах | `journalctl -u app`, логи контейнера/пода |

⭐ **Практический приём:** `curl -w` сразу показывает, на каком этапе теряется время:
`time_namelookup` (DNS), `time_connect` (TCP), `time_appconnect` (TLS),
`time_starttransfer` (бэкенд), `time_total`.

## 🧪 Мини-лаба: увидеть все шаги для одного запроса

```bash
vagrant ssh web

# 0. Чистим кеши, чтобы увидеть полный путь
sudo resolvectl flush-caches; sudo ip neigh flush all

# 1. DNS
dig +trace example.com | tail -6
getent hosts example.com

# 2. ARP (шлюз, а не сервер!)
ping -c1 example.com >/dev/null; ip neigh

# 3. Маршрут
ip route get "$(dig +short example.com | head -1)"

# 4-5. TCP и TLS в одном дампе
sudo tcpdump -i any -nn -c 14 'host example.com and (port 80 or port 443)' &
curl -s https://example.com >/dev/null; wait
# увидишь [S], [S.], [.], затем Application Data (TLS)

# 6. TLS-подробности
openssl s_client -connect example.com:443 -servername example.com </dev/null 2>/dev/null \
  | grep -E 'Protocol|Cipher|Verify return code'

# 7. HTTP-обмен
curl -sv https://example.com 2>&1 | grep -E '^[<>]' | head -20

# 8. Где теряется время
curl -s -o /dev/null -w \
 'dns=%{time_namelookup}\nconnect=%{time_connect}\ntls=%{time_appconnect}\nttfb=%{time_starttransfer}\ntotal=%{time_total}\n' \
 https://example.com

# 9. Второй запрос — из кешей (сравни цифры)
curl -s -o /dev/null -w 'повторно: dns=%{time_namelookup} total=%{time_total}\n' https://example.com

# 10. Закрытие соединения
ss -tan state time-wait | wc -l
```

## 🧠 Что запомнить

1. Порядок: URL → HSTS/кеш → DNS → маршрут/ARP → TCP → TLS → HTTP → инфраструктура →
   бэкенд → ответ → рендеринг → закрытие.
2. DNS-ответ кешируется на TTL — отсюда «поменял запись, а трафик идёт по-старому».
3. ARP спрашивают про шлюз, если адрес не в своей подсети.
4. IP не меняется на пути, MAC меняется на каждом хопе, TTL уменьшается.
5. TCP — три рукопожатия; TLS 1.3 — ещё один RTT; поэтому первый запрос всегда дороже.
6. SNI и `Host` — два разных механизма выбора сайта: первый в TLS, второй в HTTP.
7. Внутри инфраструктуры запрос проходит файрвол, балансировщик и reverse proxy,
   каждый из которых может стать точкой отказа.
8. Обратный разбор «не открывается» идёт по тем же шагам сверху вниз.
9. `curl -w` с таймингами локализует этап за одну команду.
10. Этот рассказ — способ показать, что ты понимаешь сеть целиком, а не набор команд.

балансировщик и health-check, X-Forwarded-For, ответ и подзапросы.

</details>

**A2.** Теперь за 15 секунд (короткая версия для «быстрого» собеседующего).

<details><summary>Ответ</summary>

«Браузер резолвит имя через DNS, открывает TCP-соединение, устанавливает TLS,
отправляет HTTP-запрос с заголовком Host; на той стороне балансировщик выбирает живой бэкенд,
тот формирует ответ; браузер рендерит HTML и догружает статику по тому же соединению».

</details>

**A3.** Расскажи путь для запроса **внутри** Kubernetes: под → Service → под другого сервиса.

<details><summary>Ответ</summary>

Под резолвит имя сервиса через CoreDNS (`svc.namespace.svc.cluster.local`) и получает
ClusterIP. Пакет уходит на этот виртуальный адрес, где kube-proxy (iptables/IPVS) делает DNAT
на IP конкретного пода из списка Endpoints (только готовые по readiness). Дальше — обычный
TCP/HTTP до контейнера, возможно через CNI-оверлей (VXLAN) между нодами.

</details>

**A4.** Расскажи, что изменится, если сайт за CDN.

<details><summary>Ответ</summary>

DNS вернёт адрес ближайшего узла CDN (GeoDNS/anycast). TLS терминируется на нём,
статика отдаётся из кеша; при промахе CDN идёт к origin (часто по отдельному каналу).
Клиент видит меньший RTT; появляются заголовки CDN (`X-Cache`, `CF-Ray`), а реальный IP
клиента передаётся заголовком.

</details>

**A5.** Расскажи путь для `http://` (без TLS) и объясни, что именно исчезает из схемы.

<details><summary>Ответ</summary>

Исчезает шаг TLS-хендшейка (ClientHello/сертификат/ключи): экономится RTT,
но трафик идёт открытым — видно URL, заголовки, куки и тело. Сегодня это допустимо
только внутри доверенной сети (например, от прокси к бэкенду).

</details>

**A6.** На каком шаге участвуют: ARP, TTL, SNI, Host, X-Forwarded-For, health-check?

<details><summary>Ответ</summary>

ARP — перед отправкой первого пакета (L2); TTL — в каждом IP-пакете, уменьшается
маршрутизаторами; SNI — в ClientHello (TLS); Host — в HTTP-запросе; X-Forwarded-For —
добавляется прокси/балансировщиком; health-check — постоянно, фоном, до попадания запроса
на бэкенд.

</details>

**A7.** Сколько RTT занимает первый запрос по HTTPS (DNS + TCP + TLS 1.3 + HTTP)?
А повторный по keep-alive?

<details><summary>Ответ</summary>

Примерно: DNS 1 RTT (при промахе кеша — больше), TCP 1 RTT, TLS 1.3 1 RTT,
HTTP-запрос/ответ 1 RTT → ~4 RTT. Повторный по keep-alive — 1 RTT (только запрос/ответ),
поэтому переиспользование соединений так сильно ускоряет сайты.

</details>

**A8.** Где в этой цепочке кеши? Назови минимум пять.

<details><summary>Ответ</summary>

Кеш браузера (страницы, DNS, HSTS), кеш ОС/резолвера, кеш рекурсивного резолвера,
ARP-кеш, кеш CDN, кеш reverse proxy (`proxy_cache`), кеш приложения (Redis), кеш БД.

</details>

### Блок B. «На каком шаге ломается»

Для каждого симптома укажи шаг и команду проверки:

```text:no-line-numbers
B1.  ERR_NAME_NOT_RESOLVED
B2.  ERR_CONNECTION_TIMED_OUT
B3.  ERR_CONNECTION_REFUSED
B4.  ERR_CERT_AUTHORITY_INVALID
B5.  ERR_CERT_DATE_INVALID
B6.  502 Bad Gateway
B7.  504 Gateway Timeout
B8.  404 Not Found
B9.  ERR_TOO_MANY_REDIRECTS
B10. Страница открылась, но картинки не грузятся
B11. Сайт открывается у тебя, но не у коллеги
B12. Сайт открывается по IP, но не по имени
```

<details><summary>Ответ</summary>

- **B1.** Шаг DNS. `getent hosts`, `dig`, `dig @8.8.8.8`, `/etc/resolv.conf`.
- **B2.** L3/L4: пакеты дропаются (файрвол/security group/маршрут). `nc -zv`, `mtr`, `tcpdump`.
- **B3.** L4: хост доступен, порт закрыт (RST). `ss -tlnp` на сервере.
- **B4.** TLS: неполная цепочка или неизвестный CA. `openssl s_client -showcerts`.
- **B5.** TLS: истёк сертификат (или неверное время у клиента). `openssl x509 -noout -dates`.
- **B6.** Reverse proxy не достучался до бэкенда. `error.log`, `ss -tlnp` на бэкенде.
- **B7.** Бэкенд не ответил вовремя. `upstream_response_time`, метрики приложения и БД.
- **B8.** Приложение/маршрутизация: сеть в порядке, проблема в пути или конфиге прокси
  (`proxy_pass` со слешем).
- **B9.** Редирект-петля: приложение не видит `X-Forwarded-Proto` и редиректит на https.
- **B10.** Отдельные подзапросы: путь к статике, CORS, mixed content (http-ресурсы на
  https-странице), права на файлы.
- **B11.** Разный DNS/кеш, геобалансировка, кеш браузера, региональная блокировка,
  разные версии клиента.
- **B12.** DNS или SNI/`Host`: имя не резолвится, либо сервер не отдаёт нужный
  виртуальный хост/сертификат.

</details>

**C4. Тайминги.** Сравни `curl -w` для: локального сервиса, сайта в другой стране,
сайта за CDN, повторного запроса с keep-alive. Объясни разницу по этапам.

<details><summary>Ответ</summary>

Локальный сервис — все этапы близки к нулю; удалённый сайт — заметные connect и TLS
(зависят от RTT); CDN — маленькие connect/TLS, но возможен больший TTFB при промахе кеша;
повторный запрос с keep-alive — нулевые dns/connect/tls.

</details>

**C5. Скрипт «где болит».** Напиши `where.sh <url>`, который последовательно проверяет
DNS, TCP, TLS, HTTP и печатает вердикт вида «DNS ok (12 ms) → TCP ok → TLS ok (срок 45 дней)
→ HTTP 502 ← проблема здесь».

<details><summary>Ответ</summary>

```bash
#!/usr/bin/env bash
set -uo pipefail
url="${1:?нужен url}"; host="${url#*://}"; host="${host%%/*}"; port=443
[[ $url == http://* ]] && port=80
t0=$(date +%s%3N); getent hosts "$host" >/dev/null || { echo "DNS: не резолвится ← проблема здесь"; exit 1; }
echo "DNS ok ($(( $(date +%s%3N) - t0 )) ms)"
nc -z -w3 "$host" "$port" || { echo "TCP: порт $port недоступен ← проблема здесь"; exit 1; }
echo "TCP ok"
if [[ $port == 443 ]]; then
  end=$(echo | openssl s_client -connect "$host:443" -servername "$host" 2>/dev/null \
        | openssl x509 -noout -enddate | cut -d= -f2) || { echo "TLS: ошибка ← проблема здесь"; exit 1; }
  echo "TLS ok (срок: $(( ( $(date -d "$end" +%s) - $(date +%s) ) / 86400 )) дней)"
fi
read -r code t < <(curl -s -o /dev/null -w '%{http_code} %{time_total}' --max-time 10 "$url")
echo "HTTP $code за ${t}s"
[[ $code == 2* || $code == 3* ]] || { echo "← проблема здесь"; exit 1; }
```

</details>

**C6. HTTP/2 vs HTTP/1.1.** Загрузи страницу с 20 картинками по обоим протоколам
и сравни число TCP-соединений (`ss`) и общее время.

<details><summary>Ответ</summary>

По HTTP/1.1 браузер откроет до 6 соединений на домен (видно в `ss -tan`),
по HTTP/2 — одно с мультиплексированием. На странице с множеством мелких ресурсов
HTTP/2 обычно заметно быстрее.

</details>

### Блок D. Инциденты

**D1.** «У нас всё лежит». Какие пять команд ты выполнишь первыми и почему именно эти?

<details><summary>Ответ</summary>

(1) `curl -sI` к сервису — есть ли ответ и какой код; (2) `dig`/`getent hosts` —
резолвится ли имя; (3) `nc -zv host 443` — открыт ли порт; (4) состояние балансировщика
(stats/`error.log`) — живы ли бэкенды; (5) `systemctl status`/логи приложения на бэкенде.
Эти пять команд закрывают все слои сверху вниз и отвечают, «где именно» сломалось.

</details>

**D2.** Сайт открывается через раз. Как локализовать, какое звено даёт сбой?

<details><summary>Ответ</summary>

Повторять запросы в цикле, фиксируя код и тайминги; смотреть, разные ли бэкенды
отвечают (`X-Upstream`/`Set-Cookie`/заголовок с именем хоста), `mtr` длительно,
stats балансировщика. «Через раз» почти всегда означает, что один из бэкендов больной
или один из DNS-ответов ведёт не туда.

</details>

**D3.** После переезда на новый сервер часть пользователей видит старый сайт. Причина?

<details><summary>Ответ</summary>

Кеш DNS: старая запись ещё жива у части резолверов и клиентов (не понизили TTL
заранее). Дополнительно — кеш браузера и CDN.

</details>

**D4.** Мобильные пользователи получают ошибку сертификата, десктопные — нет.

<details><summary>Ответ</summary>

Неполная цепочка сертификатов: браузеры достраивают её сами, мобильные клиенты — нет.
Проверить `openssl s_client -showcerts`, перейти на `fullchain.pem`.

</details>

**D5.** Страница грузится 8 секунд: DNS 3 с, TLS 0.2 с, TTFB 0.3 с, остальное — загрузка
ресурсов. Где чинить?

<details><summary>Ответ</summary>

Проблема в DNS-резолве (3 секунды): проверить резолверы, `ndots`/search-домены,
доступность и latency DNS-серверов, включить локальный кеш. Бэкенд и TLS здесь ни при чём;
оставшееся время — загрузка ресурсов (сжатие, кеш, HTTP/2).

</details>

### Блок E. Вопросы с собеседования

**1.** Что происходит, когда вы вводите адрес сайта и нажимаете Enter?

<details><summary>Ответ</summary>

См. эталонный ответ в конспекте («Ответ за 60 секунд»).

</details>

**2.** На каком этапе используется ARP?

<details><summary>Ответ</summary>

Перед отправкой первого пакета: чтобы узнать MAC следующего узла (обычно шлюза).

</details>

**3.** Когда браузер решает, что нужен HTTPS?

<details><summary>Ответ</summary>

По схеме `https://` в URL, по HSTS-заголовку/preload-списку или по редиректу сервера.

</details>

**4.** Как выбирается сертификат, если на одном IP много сайтов?

<details><summary>Ответ</summary>

По SNI в ClientHello — имя передаётся открытым текстом до шифрования.

</details>

**5.** Как сервер понимает, какой сайт запрашивают?

<details><summary>Ответ</summary>

По заголовку `Host` в HTTP-запросе (виртуальные хосты).

</details>

**6.** Что произойдёт, если DNS вернёт неверный адрес?

<details><summary>Ответ</summary>

Клиент пойдёт на чужой сервер: ошибка соединения, чужой сертификат или чужой сайт;
при MITM-подмене — потенциальная утечка данных.

</details>

**7.** Сколько соединений открывает браузер и зачем?

<details><summary>Ответ</summary>

По HTTP/1.1 — до 6 на домен для параллельной загрузки; по HTTP/2 — одно
с мультиплексированием потоков.

</details>
