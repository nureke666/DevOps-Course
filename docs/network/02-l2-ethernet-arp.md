# 02. L2 — Ethernet, MAC, ARP, VLAN

> Роадмап → 2.5 Сети → протоколы: **ARP**.
> **После темы ты умеешь:** объяснить, зачем нужен MAC при наличии IP, прочитать ARP-таблицу,
> найти дубликат IP в сети и понять, что такое broadcast-домен (он же — «почему кластер
> в одной подсети, а трафик ходит странно»).

---

## 🗺️ Схема: как пакет находит соседа

```text:no-line-numbers
   Хост A (192.168.56.10)                    Хост B (192.168.56.11)
   MAC aa:aa:aa:aa:aa:aa                     MAC bb:bb:bb:bb:bb:bb
        │                                            ▲
        │ 1. «Мне нужен 192.168.56.11.                │
        │     Кто-нибудь знает его MAC?»              │
        │     ARP Request → BROADCAST ff:ff:ff:ff:ff:ff│
        ▼                                            │
   ┌──────────────────────────────────────────────────┴──┐
   │                    СВИТЧ (L2)                        │
   │  рассылает broadcast во ВСЕ порты сегмента           │
   └──────────────────────────────────────────────────┬──┘
        ▲                                            │
        │ 2. ARP Reply (unicast): «Это я, мой MAC —  │
        │    bb:bb:bb:bb:bb:bb»                       │
        │                                            │
   3. A кеширует связку IP↔MAC в ARP-таблице (ip neigh)
   4. Только теперь отправляется реальный пакет (ping, TCP SYN…)
```

⭐ **Вывод для собеса:** IP-адрес — «куда», MAC — «кому конкретно на этом проводе».
Пакет не может быть отправлен, пока не известен MAC следующего узла.

---

## 1. MAC-адрес

```text:no-line-numbers
   a4:bb:6d : 3f:2e:01
   └──┬───┘   └──┬───┘
   OUI (вендор)  серийная часть
```

- 48 бит, 6 байт, обычно в hex через `:`.
- Уникален в пределах **broadcast-домена** (глобальная уникальность — в теории).
- Широковещательный адрес: `ff:ff:ff:ff:ff:ff`.
- **Не маршрутизируется**: живёт только внутри одного L2-сегмента.

```bash
ip link show                       # link/ether — свой MAC
ip -brief link
cat /sys/class/net/eth0/address
sudo ip link set eth0 address 02:11:22:33:44:55   # смена MAC (на время)
```

⚠️ В облаках и виртуализации MAC часто **привязан к политике безопасности порта**
(anti-spoofing): сменил MAC — трафик перестал ходить.

---

## 2. Как решает свитч (L2) и как — роутер (L3)

```text:no-line-numbers
Свитч (L2):                             Роутер (L3):
  ведёт MAC-таблицу «MAC ↔ порт»          ведёт таблицу маршрутов «сеть ↔ next hop»
  не знает про IP                         принимает решения по IP
  broadcast рассылает всем                broadcast НЕ пропускает между сетями
  один broadcast-домен = один сегмент     граница broadcast-домена
```

**Broadcast-домен** — множество узлов, до которых долетает широковещательный кадр.
Слишком большой домен = «широковещательный шторм» и деградация сети; поэтому сети режут
на VLAN'ы и подсети.

---

## 3. ARP — Address Resolution Protocol

Задача: по известному IP получить MAC. Работает **только внутри своей подсети**.

```bash
ip neigh                            # современная команда (ARP + NDP для IPv6)
ip neigh show dev eth1
arp -n                              # устаревшая (net-tools)

sudo ip neigh flush all             # очистить кеш
sudo ip neigh del 192.168.56.11 dev eth1
sudo ip neigh add 192.168.56.11 lladdr bb:bb:bb:bb:bb:bb dev eth1 nud permanent  # статическая запись
```

**Состояния записи (важно для отладки):**

| Состояние | Значение |
|-----------|----------|
| `REACHABLE` | Подтверждена, сосед отвечает |
| `STALE` | Есть в кеше, но давно не подтверждалась (используется, потом перепроверится) |
| `DELAY` / `PROBE` | Идёт проверка |
| `FAILED` | ⭐ Сосед не ответил на ARP — его нет в сегменте или он выключен |
| `PERMANENT` | Задана вручную |

```bash
sudo tcpdump -i eth1 -n arp          # увидеть запрос и ответ своими глазами
sudo arping -I eth1 192.168.56.11    # прямой ARP-запрос
```

### Если IP не в нашей подсети

Хост смотрит в таблицу маршрутизации, видит, что адрес чужой, и спрашивает ARP **не про
адресата, а про шлюз**. Дальше кадр уходит на MAC шлюза, а IP-назначения остаётся прежним.

```text:no-line-numbers
Пакет: src IP 192.168.56.10 → dst IP 8.8.8.8      (IP не меняется)
Кадр:  src MAC мой          → dst MAC шлюза       (MAC меняется на КАЖДОМ хопе)
```

⭐ Это любимый вопрос: **IP-адреса в пакете неизменны от источника до получателя
(если нет NAT), а MAC переписывается на каждом маршрутизаторе.**

## 4. Проблемы, с которыми столкнёшься

| Проблема | Симптом | Диагностика |
|----------|---------|-------------|
| Дубликат IP | Связь «то есть, то нет», ARP-запись скачет между MAC | `arping -D`, `ip neigh` (меняющийся lladdr), логи ядра |
| ARP-запись `FAILED` | Сосед в той же сети не пингуется | `tcpdump -n arp`: уходит ли запрос, есть ли ответ |
| Неверная маска | Хост считает соседа «чужим» и шлёт всё на шлюз | `ip addr`, посчитать подсеть |
| ARP spoofing | Трафик уходит «не туда», MITM | Статические записи, `arpwatch`, DAI на свитче |
| Proxy ARP | Шлюз отвечает за чужие адреса — «магическая» связность | `sysctl net.ipv4.conf.all.proxy_arp` |
| Gratuitous ARP | Переезд VIP: новый узел рассылает «теперь этот IP мой» | keepalived, failover (тема [13](/network/13-haproxy-balancing)) |

```bash
# Проверить дубликат IP перед назначением
sudo arping -D -I eth1 -c 2 192.168.56.50 && echo "адрес свободен" || echo "ЗАНЯТ!"
```

## 5. VLAN — логическое разделение одной физической сети

```text:no-line-numbers
   Один физический свитч:
   ┌───────────────────────────────────────────┐
   │  VLAN 10 (прод)   │  VLAN 20 (разработка) │  ← разные broadcast-домены,
   │  порты 1-8        │  порты 9-16           │     между собой — только через L3
   └───────────────────────────────────────────┘
   Транк-порт несёт несколько VLAN с тегами 802.1Q (+4 байта в кадре)
```

```bash
# VLAN-интерфейс в Linux
sudo ip link add link eth1 name eth1.10 type vlan id 10
sudo ip addr add 10.0.10.5/24 dev eth1.10
sudo ip link set eth1.10 up
ip -d link show eth1.10 | grep vlan
```

DevOps встречает VLAN'ы в двух местах: on-premise-серверы (тег от сетевиков) и
виртуализация/облако (VPC и подсети — логически то же самое разделение).

## 6. L2 в мире контейнеров

```text:no-line-numbers
   docker0 / br-xxxx — это программный СВИТЧ (linux bridge)
   veth-пара          — «виртуальный патч-корд» между namespace контейнера и бриджем

   [контейнер eth0] ──veth── [br-xxxx] ──veth── [контейнер eth0]
                                 │
                              (NAT) ──► eth0 хоста
```

```bash
ip link show type bridge          # бриджи
bridge link                       # что подключено
bridge fdb show                   # ⭐ MAC-таблица бриджа (тот самый L2)
ip -d link show veth...           # увидеть veth и её пару
```

Именно поэтому контейнеры в одной docker-сети видят друг друга напрямую: они в одном
broadcast-домене программного свитча. Подробнее — в блоке Docker (сети).

---

## 💼 Как это в DevOps

- `ip neigh` — первое, что смотрят, когда «сервер в той же подсети не пингуется».
- Дубликат IP при ручной раздаче адресов — классическая авария в on-prem; `arping -D` перед
  назначением адреса спасает.
- Gratuitous ARP — механизм переезда VIP в keepalived/HA-кластерах: понимать обязательно.
- Docker/Kubernetes-сети — это linux bridge + veth, то есть обычный L2 внутри хоста.
- MAC-фильтрация и port security в облаках ломают самодельные bridge/VIP-схемы.

## 🧪 Мини-лаба

```bash
vagrant ssh web

# 1. Свои адреса L2
ip -brief link
ip link show eth1 | grep ether

# 2. ARP: до и после
sudo ip neigh flush all
ip neigh                                  # пусто
ping -c1 192.168.56.11 >/dev/null
ip neigh                                  # появилась запись REACHABLE

# 3. Поймать ARP-обмен глазами
sudo tcpdump -i eth1 -n arp -c 4 &
sudo ip neigh flush all; ping -c1 192.168.56.11 >/dev/null; wait
# увидишь: "Request who-has 192.168.56.11 tell 192.168.56.10"
#          "Reply 192.168.56.11 is-at bb:bb:..."

# 4. Состояния записей
ip neigh show
sleep 60; ip neigh show                   # REACHABLE → STALE

# 5. Что происходит при обращении наружу
sudo ip neigh flush all
ping -c1 8.8.8.8 >/dev/null
ip neigh                                  # ⭐ в кеше MAC ШЛЮЗА, а не 8.8.8.8

# 6. MAC меняется, IP — нет
sudo tcpdump -i eth0 -n -e -c 2 icmp &
ping -c1 8.8.8.8 >/dev/null; wait          # dst MAC = MAC шлюза, dst IP = 8.8.8.8

# 7. Проверка дубликата IP
sudo arping -D -I eth1 -c 2 192.168.56.99 && echo "свободен" || echo "занят"
sudo arping -D -I eth1 -c 2 192.168.56.11 && echo "свободен" || echo "занят"

# 8. Ломаем ARP статической неверной записью
sudo ip neigh add 192.168.56.11 lladdr 00:11:22:33:44:55 dev eth1 nud permanent
ping -c2 -W1 192.168.56.11; echo "код: $?"     # не ходит — кадры уходят «в никуда»
ip neigh show 192.168.56.11
sudo ip neigh del 192.168.56.11 dev eth1
ping -c1 192.168.56.11 && echo "починилось"

# 9. Бридж как свитч (если есть docker)
docker network create labnet >/dev/null 2>&1
ip link show type bridge
bridge fdb show | head
docker network rm labnet >/dev/null 2>&1

# 10. VLAN-интерфейс
sudo ip link add link eth1 name eth1.10 type vlan id 10
ip -d link show eth1.10 | grep -o 'vlan protocol.*id 10'
sudo ip link del eth1.10
```

| Команда | Действие |
|---------|----------|
| `ip link show` | Интерфейсы и MAC |
| `ip neigh` | ⭐ ARP/NDP-таблица |

| `arping -I eth1 IP` | Прямой ARP-запрос |

| `ip link add link eth1 name eth1.10 type vlan id 10` | VLAN-интерфейс |

## 🧠 Что запомнить

1. MAC — адрес внутри одного сегмента, IP — адрес в масштабе сети. Нужны оба.
2. ARP переводит IP → MAC: запрос broadcast'ом, ответ unicast'ом, результат кешируется.
3. ⭐ IP в пакете не меняется на всём пути, MAC переписывается на каждом маршрутизаторе.
4. Если адрес не в своей подсети — ARP спрашивают **про шлюз**.
5. `FAILED` в `ip neigh` = соседа нет в сегменте (выключен, не та VLAN/маска).
6. Свитч работает на L2 и ведёт MAC-таблицу; роутер — граница broadcast-домена.
7. Дубликат IP ловится `arping -D`; симптом — «связь через раз» и скачущий MAC.
8. Gratuitous ARP — как VIP переезжает между узлами в HA-схемах.
9. VLAN (802.1Q) режет один физический свитч на независимые broadcast-домены.
10. Docker-сеть = linux bridge (свитч) + veth-пары: тот же L2, только программный.

### Блок A. Теория

**A1.** Что такое MAC-адрес, из чего состоит и в каких пределах уникален?

<details><summary>Ответ</summary>

48-битный адрес сетевого интерфейса: первые 3 байта — OUI производителя, последние 3 —
номер устройства. Уникален в пределах broadcast-домена (и, в идеале, глобально).

</details>

**A2.** Зачем нужен MAC, если уже есть IP?

<details><summary>Ответ</summary>

IP работает на L3 и нужен для маршрутизации между сетями, но физическая доставка кадра
внутри сегмента идёт по MAC. Сетевая карта принимает кадр, только если dst MAC — её или broadcast.
Кроме того, IP может меняться (DHCP, переезд), а доставка в сегменте должна работать здесь и сейчас.

</details>

**A3.** Как работает ARP? Опиши обмен по шагам, укажи, какой кадр broadcast, какой unicast.

<details><summary>Ответ</summary>

(1) Хост проверяет ARP-кеш; (2) если пусто — шлёт ARP Request широковещательно
(`ff:ff:ff:ff:ff:ff`): «кто имеет IP X, ответьте»; (3) владелец IP отвечает ARP Reply
**unicast**'ом со своим MAC; (4) запись кладётся в кеш на несколько минут; (5) только после
этого уходит исходный пакет.

</details>

**A4.** Что происходит с MAC и IP при прохождении пакета через маршрутизатор?

<details><summary>Ответ</summary>

IP-адреса источника и назначения не меняются (если нет NAT), а MAC-адреса переписываются
на каждом хопе: dst MAC всегда равен MAC следующего узла (шлюза), src MAC — MAC исходящего
интерфейса маршрутизатора.

</details>

**A5.** Что делает хост, если адрес назначения **не** в его подсети?

<details><summary>Ответ</summary>

Смотрит таблицу маршрутизации, выбирает next hop (обычно default gateway) и делает
ARP-запрос **про шлюз**, а не про конечный адрес.

</details>

**A6.** Что такое broadcast-домен? Что его ограничивает?

<details><summary>Ответ</summary>

Множество узлов, до которых доходит широковещательный кадр. Ограничивается
маршрутизатором (L3) или границей VLAN.

</details>

**A7.** Назови состояния записей в `ip neigh` и что означает `FAILED`.

<details><summary>Ответ</summary>

`REACHABLE` — подтверждена; `STALE` — устарела, но используется; `DELAY`/`PROBE` —
идёт перепроверка; `FAILED` — сосед не ответил на ARP; `PERMANENT` — статическая запись.

</details>

**A8.** Что такое gratuitous ARP и где он используется в инфраструктуре?

<details><summary>Ответ</summary>

Это ARP-ответ, который узел рассылает без запроса, объявляя «IP X теперь за моим MAC».
Используется при переезде VIP (keepalived, HA-кластеры, миграция ВМ) и для проверки дубликатов —
чтобы соседи и свитчи быстро обновили кеши.

</details>

**A9.** Что такое ARP spoofing и как от него защищаются?

<details><summary>Ответ</summary>

Атакующий шлёт ложные ARP-ответы и перехватывает трафик (MITM). Защита: Dynamic ARP
Inspection и port security на свитчах, статические ARP-записи для критичных узлов, `arpwatch`,
сегментация сети, шифрование (TLS) — чтобы перехват не давал данных.

</details>

**A10.** Что такое VLAN и чем тегированный порт отличается от нетегированного?

<details><summary>Ответ</summary>

VLAN — логическое разделение одного физического коммутатора на независимые
broadcast-домены (тег 802.1Q, +4 байта в кадре). Нетегированный (access) порт принадлежит
одному VLAN и тегов не видит; тегированный (trunk) несёт несколько VLAN с метками.

</details>

**A11.** Чем свитч отличается от роутера с точки зрения модели OSI?

<details><summary>Ответ</summary>

Свитч — L2: коммутирует кадры по MAC-таблице внутри сегмента. Роутер — L3: принимает
решения по IP, соединяет разные сети и не пропускает broadcast.

</details>

**A12.** Как устроена сеть Docker на уровне L2?

<details><summary>Ответ</summary>

`docker0`/`br-xxx` — это linux bridge (программный свитч), контейнеры подключены
к нему veth-парами; внутри сети контейнеры находятся в одном broadcast-домене, наружу трафик
уходит через NAT (`MASQUERADE`).

</details>

### Блок B. «Что делает команда»

```bash
B1.  ip -brief link
B2.  ip neigh show dev eth1
B3.  sudo ip neigh flush all
B4.  sudo arping -I eth1 -c 2 192.168.56.11
B5.  sudo arping -D -I eth1 -c 2 192.168.56.50
B6.  sudo tcpdump -i eth1 -n -e arp
B7.  bridge fdb show
B8.  ip -d link show eth1.10
B9.  sudo ip neigh add 10.0.0.5 lladdr 00:11:22:33:44:55 dev eth1 nud permanent
B10. cat /sys/class/net/eth0/address
```

<details><summary>Ответ</summary>

```text:no-line-numbers
B1.  Краткий список интерфейсов с состоянием и MAC.
B2.  ARP-записи, выученные на интерфейсе eth1.
B3.  Очищает ARP/NDP-кеш — следующий запрос вызовет новый ARP-обмен.
B4.  Отправляет 2 ARP-запроса к соседу и печатает ответы с MAC и временем.
B5.  Duplicate Address Detection: проверяет, не занят ли адрес (код 1 — занят).
B6.  Показывает ARP-трафик с MAC-адресами в реальном времени.
B7.  MAC-таблица linux bridge: какой MAC за каким портом.
B8.  Подробности VLAN-интерфейса (протокол 802.1Q и id).
B9.  Добавляет статическую ARP-запись, которая не устаревает.
B10. Печатает MAC интерфейса из sysfs.
```

</details>

**B11.** Что ты увидишь в `ip neigh` после `ping 8.8.8.8` и почему именно это?

<details><summary>Ответ</summary>

В кеше появится запись для **шлюза** (например, 192.168.56.1 или 10.0.2.2),
а не для 8.8.8.8: адрес назначения не в нашей подсети, поэтому MAC нужен только для next hop.

</details>

### Блок C. Практика

**C1. ARP своими глазами.** Очисти ARP-кеш, запусти tcpdump на ARP и пингани соседа.
Приведи расшифровку обоих кадров: кто кого спрашивает, кто отвечает, какие MAC в заголовках.

<details><summary>Ответ</summary>

```bash
sudo ip neigh flush all
sudo tcpdump -i eth1 -n -e arp -c 2 &
ping -c1 192.168.56.11 >/dev/null; wait
```
Первый кадр: src MAC — наш, dst MAC `ff:ff:ff:ff:ff:ff`, «Request who-has 192.168.56.11
tell 192.168.56.10». Второй: unicast от соседа к нам, «Reply 192.168.56.11 is-at bb:bb:…».

</details>

**C2. MAC vs IP.** Сними дамп с `-e` при пинге соседа по локальной сети и при пинге 8.8.8.8.
Покажи, чем отличаются MAC назначения, и объясни почему.

<details><summary>Ответ</summary>

При пинге соседа dst MAC — MAC соседа; при пинге 8.8.8.8 dst MAC — MAC шлюза,
а dst IP остаётся 8.8.8.8. Причина: MAC всегда адресует следующий узел, IP — конечного получателя.

</details>

**C3. Сломай и почини.** Добавь неверную статическую ARP-запись для соседа.
Зафиксируй симптом (какая ошибка, что в tcpdump), затем почини. Опиши, чем этот симптом
отличается от «сосед выключен».

<details><summary>Ответ</summary>

С неверной статической записью кадры уходят на несуществующий MAC: ping даёт
100% потерь, в tcpdump видно только исходящие ICMP без ответов, ARP-обмена нет вовсе
(запись `PERMANENT`). Если сосед просто выключен — в tcpdump будут видны **ARP-запросы без
ответов**, а `ip neigh` покажет `FAILED`.

</details>

**C4. Поиск дубликата IP.** Назначь второй ВМ адрес, который уже занят первой.
Что покажут `arping -D`, `ip neigh`, `dmesg`? Как ведёт себя ping?

<details><summary>Ответ</summary>

`arping -D` вернёт код 1 и покажет MAC владельца; `ip neigh` может показывать
меняющийся lladdr; ядро пишет в dmesg что-то вроде `IPv4: duplicate address detected`.
Ping идёт нестабильно: ответы приходят то от одного, то от другого хоста.

</details>

**C5. Скрипт инвентаризации сегмента.** Напиши `l2scan.sh`, который пингует весь диапазон
`192.168.56.1-20` (параллельно), затем выводит таблицу «IP / MAC / вендор (OUI)» из `ip neigh`.

<details><summary>Ответ</summary>

```bash
#!/usr/bin/env bash
set -uo pipefail
net=192.168.56
for i in $(seq 1 20); do ping -c1 -W1 "$net.$i" >/dev/null 2>&1 & done; wait
printf '%-16s %-20s %s\n' IP MAC СОСТОЯНИЕ
ip neigh | awk '/lladdr/ {printf "%-16s %-20s %s\n", $1, $5, $NF}'
```

</details>

**C6. Маска и «чужой» сосед.** Поставь на интерфейсе маску /26 вместо /24 и попробуй
достучаться до адреса, который теперь оказался вне подсети. Объясни, куда уходит трафик.

<details><summary>Ответ</summary>

С маской /26 адрес 192.168.56.11 остаётся в той же подсети (0-63), поэтому для
эксперимента нужен адрес из другого блока (например, .100 при /26). Хост посчитает его чужим
и отправит трафик на шлюз; если шлюза в этой сети нет — `Network is unreachable`
или молчание, при этом ARP-запроса к самому адресу не будет.

</details>

**C7. Bridge как свитч.** Создай docker-сеть, подними два контейнера, найди их MAC,
посмотри `bridge fdb show` и покажи, что они в одном L2-сегменте (ARP между ними ходит).

<details><summary>Ответ</summary>

```bash
docker network create labnet
docker run -d --name c1 --network labnet alpine sleep 600
docker run -d --name c2 --network labnet alpine sleep 600
docker exec c1 ip link show eth0 | grep ether
docker exec c1 ping -c1 c2
docker exec c1 arp -n 2>/dev/null || docker exec c1 ip neigh
bridge fdb show | grep -c .
docker rm -f c1 c2; docker network rm labnet
```

</details>

### Блок D. Инциденты

**D1.** Сервер в той же подсети не пингуется, `ip neigh` показывает `FAILED`.
Три вероятные причины и порядок проверки.

<details><summary>Ответ</summary>

(1) Хост выключен или его интерфейс down; (2) он в другой VLAN/подсети (неверная маска
или тег порта); (3) фильтрация на свитче/гипервизоре (port security, MAC-фильтр).
Порядок: `tcpdump -n arp` — уходит ли запрос и приходит ли ответ; проверить маску и адрес
(`ip addr`), затем конфигурацию порта/VLAN и наличие дубликата IP.

</details>

**D2.** После добавления нового сервера в стойку часть старых серверов стала «мигать»:
связь пропадает на 10-20 секунд и возвращается. Что проверить в первую очередь?

<details><summary>Ответ</summary>

Дубликат IP: новый сервер получил адрес, уже занятый другим. ARP-таблицы у соседей
и свитча начинают «скакать» между MAC. Проверка — `arping -D`, `ip neigh` (меняющийся lladdr),
логи ядра, а на свитче — flapping MAC между портами.

</details>

**D3.** Виртуалка переехала на другой хост, IP остался тот же, но клиенты минуту ходили
на старый адрес. Какой механизм должен был это решить?

<details><summary>Ответ</summary>

Gratuitous ARP: после переезда узел должен разослать безвозмездный ARP, чтобы соседи
и свитчи обновили кеши. Если он не отправлен (или отфильтрован), клиенты будут слать трафик
на старый MAC до истечения ARP-кеша.

</details>

**D4.** В облаке подняли VIP на ВМ через `ip addr add`, но трафик на него не идёт,
хотя внутри ВМ всё настроено. Почему (подсказка: port security)?

<details><summary>Ответ</summary>

В облаке на порту ВМ включён anti-spoofing: разрешены только те MAC/IP, что выданы
платформе. Дополнительный IP нужно разрешить явно (allowed address pairs / secondary IP),
иначе гипервизор отбрасывает кадры с «чужим» адресом.

</details>

**D5.** Контейнеры в одной docker-сети видят друг друга, а после `--network host`
перестали резолвиться по именам. Как это связано с L2?

<details><summary>Ответ</summary>

`--network host` убирает контейнер из bridge-сети: нет отдельного namespace, нет veth
и нет встроенного DNS Docker, который резолвит имена контейнеров в этой сети. Контейнер
оказывается прямо в L2/L3 хоста.

</details>

### Блок E. Вопросы с собеседования

**1.** Что такое ARP и зачем он нужен?

<details><summary>Ответ</summary>

Протокол разрешения IP→MAC внутри одного сегмента: без MAC кадр физически некуда отправить.

</details>

**2.** Зачем MAC, если есть IP?

<details><summary>Ответ</summary>

IP адресует хост в масштабе интернета, MAC — интерфейс в пределах провода/сегмента.

</details>

**3.** Меняется ли IP-адрес при прохождении через роутер? А MAC?

<details><summary>Ответ</summary>

IP не меняется (без NAT), MAC переписывается на каждом маршрутизаторе.

</details>

**4.** Что такое broadcast-домен?

<details><summary>Ответ</summary>

Область, куда доходит широковещательный кадр; ограничивается роутером или VLAN.

</details>

**5.** Что такое VLAN?

<details><summary>Ответ</summary>

Логическое деление свитча на изолированные L2-сегменты с тегом 802.1Q.

</details>

**6.** Как найти дубликат IP в сети?

<details><summary>Ответ</summary>

`arping -D`, наблюдение за ARP-таблицей (скачущий MAC), логи ядра, flapping на свитче.

</details>

**7.** Чем свитч отличается от роутера?

<details><summary>Ответ</summary>

Свитч коммутирует по MAC (L2), роутер маршрутизирует по IP (L3) и делит broadcast-домены.

</details>
