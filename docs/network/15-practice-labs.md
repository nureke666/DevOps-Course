# 15. Практические лабы — сеть целиком

> Семь сквозных лаб на стенде из двух ВМ. Каждая закрывает несколько тем блока
> и даёт артефакт (конфиг, дамп, скрипт), который можно показать на собеседовании.
>
> Стенд: `web` 192.168.56.10, `app` 192.168.56.11.
> Перед каждой лабой: `vagrant snapshot save before_lab<N>`.

---

## 🧪 Лаба 1. Диагностический полигон (темы 01-04, 09, 10)

**Цель:** научиться за 5 минут определять уровень проблемы.

**Задание.** Напарник (или скрипт) ломает одно звено, ты находишь его, не зная заранее что.

```bash
# Скрипт-«ломатель» (запусти на app, выбери случайный сценарий)
cat > /tmp/break.sh <<'EOS'
#!/usr/bin/env bash
case $((RANDOM % 6 + 1)) in
  1) sudo ip link set eth1 down ;;                                     # L1/L2
  2) sudo ip neigh add 192.168.56.10 lladdr 00:11:22:33:44:55 dev eth1 nud permanent ;;  # L2
  3) sudo ip route del default ;;                                      # L3
  4) sudo iptables -A INPUT -p tcp --dport 80 -j DROP ;;               # L4 (таймаут)
  5) sudo iptables -A INPUT -p tcp --dport 80 -j REJECT ;;             # L4 (refused)
  6) echo "nameserver 192.0.2.1" | sudo tee /etc/resolv.conf ;;        # DNS
esac
echo "сломано, чини"
EOS
chmod +x /tmp/break.sh
```

**Что сдать:**
- журнал диагностики: какие команды выполнял и что они показали;
- вывод, на каком уровне была проблема;
- команда починки.

**Критерии:** находишь причину не более чем за 6 команд и объясняешь, почему симптом
выглядел именно так.

## 🧪 Лаба 2. Свой DNS и разбор резолвинга (тема 05)

**Цель:** понять резолвинг изнутри.

1. Подними `dnsmasq` на `web`, заведи зону `lab.local`:
   `web.lab.local → 192.168.56.10`, `app.lab.local → 192.168.56.11`, wildcard `*.lab.local`.
2. Переключи `app` на этот DNS, проверь `dig`, `getent hosts`, `ping`.
3. Сними дамп `udp port 53` и разбери запрос и ответ.
4. Поставь TTL 30 секунд, смени запись и замерь, через сколько клиент увидит новое значение.
5. Добавь запись в `/etc/hosts` на `app` и покажи расхождение `dig` и `getent`.
6. Сломай резолвинг тремя способами (неверный nameserver, DROP на 53, закешированный NXDOMAIN)
   и опиши симптом каждого.

**Артефакт:** конфиг dnsmasq + скрипт `dnscheck.sh` из задач [темы 05](/network/05-dns).

## 🧪 Лаба 3. HTTPS-сайт от нуля (темы 06, 07, 12)

**Цель:** собрать боевую конфигурацию веб-сервиса.

1. Свой CA и сертификат для `shop.lab.local` (SAN: DNS + IP).
2. nginx: редирект 80 → 443, TLS 1.2/1.3, `fullchain`, HSTS.
3. Два «бэкенда» на `app` (разные ответы), upstream с `least_conn`, keepalive и
   `max_fails`/`fail_timeout`.
4. Полный набор `X-Forwarded-*`, `log_format` с `$request_time` и `$upstream_response_time`.
5. Отдача статики с кешем (`expires`, ETag), `client_max_body_size`, rate limit на `/api/`.
6. Проверки: `openssl s_client`, `curl -w` с таймингами, 200 → 304 на статике,
   429 при превышении лимита.
7. Сломай бэкенды и покажи 502; сделай медленный — покажи 504; найди обе записи в `error.log`.

**Артефакт:** `nginx.conf` + `ca.crt` + отчёт с кодами и таймингами.

## 🧪 Лаба 4. Балансировка и отказоустойчивость (темы 12, 13)

**Цель:** сравнить nginx и HAProxy на одинаковом сценарии.

1. Три бэкенда (можно контейнерами) с эндпоинтом `/health` и «версией» в ответе.
2. Вариант А: nginx с upstream и пассивными проверками.
   Вариант Б: HAProxy с активными проверками, stats и runtime API.
3. Для каждого варианта: запусти непрерывный `curl`-цикл, останови один бэкенд
   и посчитай, **сколько запросов получили ошибку** до исключения из ротации.
4. Сделай rolling deploy: в HAProxy через `disable/enable server`, в nginx — через
   изменение конфига и `reload`. Сравни, сколько ошибок увидели пользователи.
5. Проверь липкость: `ip_hash` в nginx и cookie в HAProxy.
6. Испорти `/health` (пусть зависит от «БД», которую ты остановишь) и покажи,
   как из ротации выпадают все живые бэкенды.

**Артефакт:** таблица сравнения (обнаружение падения, ошибки при деплое, наблюдаемость)
и оба конфига.

## 🧪 Лаба 5. Файрвол и NAT-шлюз (тема 11)

**Цель:** закрыть сервер и не потерять доступ.

1. `iptables-save` в бэкап и отложенный откат через `at`.
2. На `app`: базовый набор (lo, ESTABLISHED, SSH только из 192.168.56.0/24, 80/443,
   ICMP с лимитом, LOG + `-P INPUT DROP`).
3. Проверь с `web`: SSH работает, 80 работает, любой другой порт — таймаут;
   сравни поведение DROP и REJECT.
4. Сделай из `web` NAT-шлюз: `app` выходит в интернет через него (`MASQUERADE`),
   проверь `curl ifconfig.me` и найди запись в `conntrack`.
5. Пробрось порт: 8080 на `web` → 80 на `app` (DNAT + FORWARD).
6. Подними docker-контейнер с `-p` на `app` и покажи, что INPUT его не закрывает;
   закрой через `DOCKER-USER`.
7. Сохрани правила через `netfilter-persistent`, перезагрузи ВМ, проверь.
8. Собери эквивалент на `nftables`.

**Артефакт:** `rules.v4` + `nftables.conf` + короткий README «что открыто и почему».

## 🧪 Лаба 6. Сквозной путь запроса (тема 14 + всё остальное)

**Цель:** собрать всю цепочку и проследить запрос от начала до конца.

```text:no-line-numbers
клиент → DNS (dnsmasq) → HAProxy (:443, TLS) → nginx (:8080, L7-маршрутизация)
       → бэкенд app-1/app-2 → «БД» (nc-заглушка)
```

1. Собери цепочку целиком на двух ВМ.
2. Сделай один запрос и сними дампы **на каждом звене** одновременно.
3. Составь таблицу: звено → что видно в дампе → какие заголовки добавились.
4. Замерь `curl -w` и распиши, сколько времени ушло на каждый этап.
5. Проверь, что бэкенд видит реальный IP клиента (X-Forwarded-For через два прокси).
6. Сломай по очереди каждое звено и зафиксируй, что видит клиент и где это видно в логах.
7. Напиши `where.sh`, который по URL говорит, на каком этапе проблема.

**Артефакт:** схема цепочки (нарисованная от руки или в ASCII), таблица дампов,
скрипт `where.sh`, отчёт по шести поломкам.

## 🧪 Лаба 7. Site-to-site WireGuard между ВМ (темы 03, 11, 17)

**Цель:** связать две «площадки» туннелем так, как связывают офис с облаком или два ДЦ.

```text:no-line-numbers
 офис A 10.10.0.0/16                                        офис B 10.20.0.0/16
 cli 10.10.1.10 ── web (шлюз) ══ wg0 10.99.0.0/24, UDP 51820 ══ app (шлюз) ── srv 10.20.1.10
 (netns)          192.168.56.10                     192.168.56.11          (netns)
```

1. Собери «офисы»: на `web` и `app` — dummy-интерфейсы и netns-хосты за шлюзами
   (как в мини-лабе [17. VPN](/network/17-vpn)); у хостов default gateway — свой шлюз.
2. Подними WireGuard: ключи генерируются на узлах, в конфигах — сети за пирами в `AllowedIPs`,
   автозапуск `wg-quick@wg0`, `ip_forward` в `/etc/sysctl.d/`, netns и dummy — в `PostUp`.
3. Проверь LAN-to-LAN: `cli` ↔ `srv` — ping, TCP (`nc`), HTTP (`python3 -m http.server` в netns).
4. Файрвол (тема 11): на шлюзах `FORWARD` по умолчанию DROP, разрешено только `wg0 ↔ LAN`;
   UDP 51820 принимается только от второго шлюза. Покажи, что прочий трафик режется.
5. MTU: запрети исходящий ICMP `fragmentation-needed`, воспроизведи зависание передачи 5 МБ
   `cli → srv`, почини MSS clamping; сними дампы до и после (видно MSS в SYN).
6. Живучесть: перезагрузи обе ВМ — туннель и маршруты поднимаются сами; `wg-check.sh`
   (задача C10 [темы 17](/network/17-vpn)) по cron пишет алерт, если handshake старше 3 минут.
7. Поломки от напарника (или скрипта): неверный ключ, выключенный `ip_forward`, урезанный
   `AllowedIPs`, закрытый порт, MTU. Каждую находишь по чек-листу темы 17 §10.
8. Бонус: то же на strongSwan (`swanctl.conf`), сравни объём конфига, время установления
   туннеля и то, что видно в tcpdump (UDP 51820 против ESP / UDP 4500).

**Артефакт:** `wg0.conf` обеих сторон (без приватных ключей), правила iptables, дампы
до/после MSS clamping, `wg-check.sh`, README со схемой адресации.

**Критерии:** стенд переживает перезагрузку; 5 МБ по TCP проходят `cli → srv`; лишний трафик
режется; любую из пяти поломок находишь не более чем за 5 минут.
