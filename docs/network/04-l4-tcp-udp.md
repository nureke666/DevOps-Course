# 04. L4 — TCP и UDP: хендшейк, состояния, порты

> Роадмап → 2.5 Сети → **особое внимание уровню 4**, протоколы **TCP/UDP**.
> Вопрос с собеса: *«В чём отличие TCP от UDP?»* — входит в топ-3 самых частых.
> **После темы ты умеешь:** нарисовать три рукопожатия, объяснить TIME_WAIT,
> читать `ss -tan` и понимать, почему «порт занят» и «соединения копятся».

## 🗺️ Схема: жизнь TCP-соединения

```text:no-line-numbers
   КЛИЕНТ                                              СЕРВЕР
      │                                                   │ LISTEN
      │──────────────── SYN (seq=x) ─────────────────────►│
      │                                            SYN_RECV│
      │◄────────── SYN+ACK (seq=y, ack=x+1) ──────────────│
 SYN_SENT                                                  │
      │──────────────── ACK (ack=y+1) ───────────────────►│
 ESTABLISHED                                      ESTABLISHED
      │                                                   │
      │◄═══════════ обмен данными (seq/ack) ═════════════►│
      │                                                   │
      │──────────────── FIN ─────────────────────────────►│
 FIN_WAIT_1                                       CLOSE_WAIT
      │◄──────────────── ACK ─────────────────────────────│
 FIN_WAIT_2                                                │
      │◄──────────────── FIN ─────────────────────────────│ LAST_ACK
      │──────────────── ACK ─────────────────────────────►│
  TIME_WAIT  (2×MSL, обычно 60 сек)                    CLOSED
      │
   CLOSED
```

⭐ **Кто закрыл первым — тот и держит TIME_WAIT.** Отсюда практический вывод: десятки тысяч
TIME_WAIT на сервере означают, что соединения закрывает он (типично для прокси без keep-alive).

## 1. TCP vs UDP — ответ за 30 секунд

> TCP — соединение с гарантией: три рукопожатия, нумерация байтов, подтверждения,
> повторная отправка потерянного, контроль перегрузки и порядок доставки. Платим за это
> задержкой и накладными расходами. UDP — просто «выстрелил и забыл»: никакого соединения,
> подтверждений и порядка, зато минимальная задержка и накладные расходы.
> TCP — там, где важна целостность (HTTP, SSH, БД), UDP — где важна скорость и допустимы
> потери (DNS-запросы, VoIP, видео, метрики, VXLAN).

| | TCP | UDP |
|---|-----|-----|
| Соединение | Да (3-way handshake) | Нет |
| Гарантия доставки | Да (ACK + ретрансмиссия) | Нет |
| Порядок | Сохраняется | Не гарантирован |
| Контроль перегрузки | Да (congestion control) | Нет |
| Заголовок | 20+ байт | 8 байт |
| Скорость/задержка | Ниже | Выше |
| Broadcast/multicast | Нет | Да |
| Примеры | HTTP, HTTPS, SSH, SMTP, PostgreSQL | DNS, DHCP, NTP, syslog, VoIP, QUIC/HTTP-3, VXLAN |

⚠️ Частая ошибка на собесе: «UDP ненадёжен, поэтому его почти не используют».
На самом деле весь DNS, все метрики (statsd), весь VXLAN в k8s и HTTP/3 — это UDP.

## 2. Флаги TCP

| Флаг | Значение | Где увидишь |
|------|----------|-------------|
| `SYN` | Запрос на установку соединения | Начало каждого соединения |
| `ACK` | Подтверждение | Почти в каждом пакете после handshake |
| `FIN` | Корректное закрытие | Нормальное завершение |
| `RST` | ⭐ Резкий сброс | **Порт закрыт** (Connection refused), сброс приложением, разрыв по таймауту |
| `PSH` | Отдать данные приложению немедленно | Интерактивный трафик |
| `URG` | Срочные данные | Почти не используется |

```bash
sudo tcpdump -i any -n 'tcp[tcpflags] & tcp-syn != 0'   # только SYN
sudo tcpdump -i any -n 'tcp[tcpflags] & tcp-rst != 0'   # ⭐ ловим RST — «кто рвёт соединения»
```

**Три главных исхода попытки подключения:**

| Ответ | Что вернулось | Диагноз |
|-------|---------------|---------|
| SYN-ACK | Соединение установлено | Порт открыт |
| RST | Хост есть, порт закрыт | `Connection refused` — сервис не слушает |
| Ничего (таймаут) | Пакеты дропаются | Файрвол `DROP`, security group, нет маршрута |

## 3. Состояния соединений — `ss` и что они значат

```bash
ss -tan                       # TCP, все состояния, без резолва
ss -tlnp                      # ⭐ кто слушает (порт + процесс)
ss -tanp state established
ss -tan state time-wait | wc -l
ss -ti                        # ⭐ детали: RTT, cwnd, ретрансмиссии
ss -s                         # сводка по всем сокетам
ss -tan '( dport = :443 or sport = :443 )'
```

| Состояние | Значение | Много таких = |
|-----------|----------|---------------|
| `LISTEN` | Сервис ждёт подключений | Норма |
| `ESTAB` | Активное соединение | Норма |
| `SYN-SENT` | Клиент отправил SYN и ждёт | Сервер недоступен/фильтруется |
| `SYN-RECV` | Сервер получил SYN, ждёт ACK | ⚠️ SYN-флуд или потери |
| `TIME-WAIT` | Ждём «хвост» после закрытия (60 с) | Много коротких соединений — обычно норма |
| `CLOSE-WAIT` | ⭐ Другая сторона закрыла, **наше приложение — нет** | **Баг в приложении**: не закрывает сокеты |
| `FIN-WAIT-1/2` | Мы закрыли, ждём ответа | Другая сторона не отвечает |

⭐ Разница, которую спрашивают: `TIME_WAIT` — нормальное состояние ядра (само пройдёт),
`CLOSE_WAIT` — почти всегда утечка файловых дескрипторов в коде приложения.

## 4. Порты, bind и «Address already in use»

```bash
ss -tlnp | grep :8080                 # кто занял порт
sudo lsof -i :8080
sudo fuser -k 8080/tcp                # убить того, кто держит (осторожно)
```

| Слушает на | Значение |
|------------|----------|
| `127.0.0.1:5432` | Только локально ← классика «из контейнера БД не видна» |
| `0.0.0.0:5432` | На всех IPv4-интерфейсах |
| `[::]:5432` | На всех IPv6 (часто и IPv4 через dual-stack) |

**`SO_REUSEADDR`** позволяет перезапустить сервис, не дожидаясь окончания TIME_WAIT
на его порту; без него после рестарта возможна ошибка «Address already in use».

```bash
sysctl net.ipv4.ip_local_port_range     # диапазон эфемерных портов (32768-60999)
sysctl net.ipv4.tcp_fin_timeout
sysctl net.core.somaxconn               # ⭐ максимальная очередь accept
sysctl net.ipv4.tcp_max_syn_backlog     # очередь полуоткрытых соединений
```

⚠️ **Исчерпание эфемерных портов** — реальная авария на прокси и в CI: ~28 000 портов,
каждый TIME_WAIT держит пару «src port ↔ dst» 60 секунд. Симптом: `cannot assign requested
address`. Лечение: keep-alive (переиспользовать соединения), `tcp_tw_reuse=1`, расширить
диапазон портов, несколько исходящих IP.

## 5. Надёжность: seq/ack, окно, ретрансмиссии

```text:no-line-numbers
Отправитель                      Получатель
   seq=1000, 500 байт ──────────►
                      ◄────────── ack=1500, win=64240
   seq=1500, 500 байт ──────────►   (потерян)
   ...таймаут или 3 дубликата ACK...
   seq=1500 ПОВТОР ─────────────►
```

- **Sequence/Acknowledgement** — нумерация байтов и подтверждение полученного.
- **Окно (window)** — сколько байт можно отправить без подтверждения; масштабируется
  опцией window scaling.
- **Ретрансмиссия** — повтор потерянного сегмента: по таймауту (RTO) или по трём
  дублирующим ACK (fast retransmit).
- **Контроль перегрузки** (cubic, BBR) — снижает скорость при потерях.

```bash
netstat -s | grep -i retrans           # ретрансмиссии по системе
ss -ti | grep -E 'rtt|retrans|cwnd'    # по конкретным соединениям
sysctl net.ipv4.tcp_congestion_control
```

⭐ Ретрансмиссии — объективный признак потерь в сети. «Тормозит» + растут retransmits =
проблема в канале, а не в приложении.

## 6. Keep-alive: два разных зверя

| | TCP keepalive | HTTP keep-alive |
|---|---------------|-----------------|
| Уровень | L4 (ядро) | L7 (заголовок `Connection`) |
| Зачем | Проверять, жив ли пир, и не дать NAT «забыть» соединение | Переиспользовать TCP-соединение для нескольких запросов |
| Настройка | `net.ipv4.tcp_keepalive_time` (по умолчанию 7200 с!) | `keepalive_timeout` в nginx, пул соединений в клиенте |

⚠️ Дефолтные 2 часа TCP keepalive — причина «зависших» соединений через NAT/облачный LB,
который выбрасывает сессию через 5-15 минут молчания. В инфраструктуре обычно ставят 300 с.

---

## 💼 Как это в DevOps

- `ss -tlnp` — первая команда при «сервис не отвечает»: слушает ли он и на каком адресе.
- `CLOSE_WAIT` в большом количестве — готовый аргумент разработчикам, что утечка в коде.
- Исчерпание эфемерных портов и переполнение `somaxconn` — типичные проблемы под нагрузкой.
- Ретрансмиссии и RTT из `ss -ti` отличают «сеть плохая» от «приложение медленное».
- Балансировщики L4 работают именно здесь: они видят только порты и адреса.
- Health-check в мониторинге корректнее делать TCP-коннектом, а не пингом.

## 🧪 Мини-лаба

```bash
vagrant ssh web

# 1. Три рукопожатия глазами
sudo tcpdump -i any -n -c 10 'tcp port 22 and host 192.168.56.11' &
ssh -o StrictHostKeyChecking=no 192.168.56.11 true 2>/dev/null; wait
# увидишь: Flags [S], Flags [S.], Flags [.] — SYN, SYN-ACK, ACK

# 2. Три исхода подключения
nc -zv 192.168.56.11 22    ; echo "открыт      -> $?"
nc -zv 192.168.56.11 9999  ; echo "закрыт(RST) -> $?"
nc -zv -w 3 10.255.255.1 80; echo "таймаут     -> $?"

# 3. RST своими глазами
sudo tcpdump -i any -n -c 4 'tcp[tcpflags] & tcp-rst != 0' &
nc -z 192.168.56.11 9999; wait

# 4. Состояния соединений
ss -s
ss -tlnp | head
ss -tan state established | head
ss -tan state time-wait | wc -l

# 5. Сделать TIME_WAIT много
for i in $(seq 1 50); do curl -s -o /dev/null http://192.168.56.11/ 2>/dev/null; done
ss -tan state time-wait | wc -l        # кто закрывает первым — у того и TIME_WAIT

# 6. Слушать только на localhost — и понять симптом
python3 -m http.server 8080 --bind 127.0.0.1 >/dev/null 2>&1 &
ss -tlnp | grep 8080                   # 127.0.0.1:8080
curl -s -o /dev/null -w '%{http_code}\n' http://127.0.0.1:8080/
# с соседней ВМ: nc -zv 192.168.56.10 8080  → Connection refused
kill %1

# 7. Занятый порт
python3 -m http.server 8080 >/dev/null 2>&1 &
python3 -m http.server 8080            # Address already in use
sudo lsof -i :8080 | head -3
kill %1

# 8. Эфемерные порты и параметры ядра
sysctl net.ipv4.ip_local_port_range net.core.somaxconn net.ipv4.tcp_keepalive_time
curl -s -o /dev/null example.com & sleep 0.2; ss -tan | grep -m1 :80

# 9. Качество соединения
ss -ti 2>/dev/null | grep -A1 ESTAB | head -6
netstat -s | grep -iE 'retransmit|segments' | head -5

# 10. UDP
sudo tcpdump -i any -n -c 2 'udp port 53' &
dig +short example.com >/dev/null; wait
ss -uln | head
```

## 🧠 Что запомнить

1. TCP: 3-way handshake (SYN → SYN-ACK → ACK), гарантия доставки и порядка, контроль перегрузки.
2. UDP: без соединения и гарантий, 8 байт заголовка — DNS, DHCP, NTP, VXLAN, QUIC/HTTP-3.
3. Закрытие — четыре пакета (FIN/ACK × 2); инициатор закрытия остаётся в `TIME_WAIT` ~60 с.
4. `RST` = порт закрыт или соединение сброшено; тишина = пакеты дропаются файрволом.
5. `CLOSE_WAIT` в количестве — баг приложения (не закрывает сокеты), `TIME_WAIT` — норма ядра.
6. `0.0.0.0` vs `127.0.0.1` в `ss -tlnp` объясняет половину «сервис недоступен снаружи».
7. Эфемерных портов ~28 000: под нагрузкой они кончаются — спасает keep-alive и пул соединений.
8. `somaxconn`/`tcp_max_syn_backlog` — очереди соединений; при переполнении клиенты получают отказы.
9. Ретрансмиссии и RTT (`ss -ti`) отличают проблему сети от проблемы приложения.
10. TCP keepalive (L4, 2 часа по умолчанию) ≠ HTTP keep-alive (L7, переиспользование соединения).

> которые задают почти на каждом собеседовании. Ответы должны отскакивать.

---

### Блок A. Теория

**A1.** Опиши три рукопожатия TCP по шагам с флагами и номерами.

<details><summary>Ответ</summary>

(1) Клиент → SYN с начальным seq=x; (2) сервер → SYN+ACK со своим seq=y и ack=x+1;
(3) клиент → ACK с ack=y+1. После этого обе стороны в состоянии ESTABLISHED.
Смысл: согласовать начальные номера последовательности и подтвердить двустороннюю связь.

</details>

**A2.** Как TCP закрывает соединение? Почему пакетов четыре, а не два?

<details><summary>Ответ</summary>

Закрытие полудуплексное: каждая сторона закрывает свою половину. Инициатор шлёт FIN,
получает ACK (его направление закрыто), затем вторая сторона шлёт свой FIN и получает ACK.
Отсюда четыре пакета (иногда три — при объединении FIN и ACK).

</details>

**A3.** Что такое TIME_WAIT, зачем он нужен и сколько длится? У какой стороны он возникает?

<details><summary>Ответ</summary>

Состояние инициатора закрытия длительностью 2×MSL (в Linux ~60 с). Нужно, чтобы
«опоздавшие» пакеты старого соединения не попали в новое с той же парой портов и чтобы
гарантированно дошёл последний ACK.

</details>

**A4.** Чем TIME_WAIT отличается от CLOSE_WAIT? О чём говорит большое количество каждого?

<details><summary>Ответ</summary>

TIME_WAIT — у того, кто закрыл первым, нормальное состояние ядра, проходит само.
CLOSE_WAIT — мы получили FIN, но наше приложение не вызвало `close()`: сокет висит,
пока процесс жив. Много TIME_WAIT — много коротких соединений (обычно ок, иногда исчерпание
портов); много CLOSE_WAIT — утечка дескрипторов в коде.

</details>

**A5.** В чём отличие TCP от UDP? Назови по 4 протокола поверх каждого.

<details><summary>Ответ</summary>

TCP — с установкой соединения, подтверждениями, порядком и контролем перегрузки
(HTTP, HTTPS, SSH, SMTP, PostgreSQL, MySQL). UDP — без соединения и гарантий, минимум
накладных расходов (DNS, DHCP, NTP, syslog, VoIP, VXLAN, QUIC/HTTP-3).

</details>

**A6.** Назови флаги TCP и что означает каждый.

<details><summary>Ответ</summary>

SYN — установка; ACK — подтверждение; FIN — корректное закрытие; RST — сброс;
PSH — «передать приложению немедленно»; URG — срочные данные (практически не используется).

</details>

**A7.** Три возможных исхода TCP-подключения и что каждый означает для диагностики.

<details><summary>Ответ</summary>

SYN-ACK → порт открыт; RST → хост доступен, но порт закрыт (`Connection refused`);
тишина → пакеты отбрасываются (файрвол DROP, security group, нет маршрута) — `timed out`.

</details>

**A8.** Что такое sequence/acknowledgement number и окно (window)?

<details><summary>Ответ</summary>

seq — номер первого байта в сегменте, ack — номер следующего ожидаемого байта.
Window — сколько байт получатель готов принять без подтверждения (управление потоком).

</details>

**A9.** Что такое ретрансмиссия и по каким двум признакам она запускается?

<details><summary>Ответ</summary>

Повторная отправка неподтверждённого сегмента: по истечении таймера RTO или
по трём дублирующим ACK (fast retransmit).

</details>

**A10.** Что такое эфемерные порты? Что происходит при их исчерпании и как это лечится?

<details><summary>Ответ</summary>

Порты 32768-60999, которые ядро выдаёт исходящим соединениям. При исчерпании —
`cannot assign requested address`. Лечение: keep-alive и пулы соединений, `tcp_tw_reuse=1`,
расширение диапазона, несколько исходящих адресов, уменьшение числа коротких соединений.

</details>

**A11.** Чем `0.0.0.0:80` отличается от `127.0.0.1:80`?

<details><summary>Ответ</summary>

`0.0.0.0:80` — слушает на всех интерфейсах (доступен снаружи);
`127.0.0.1:80` — только для локальных процессов, снаружи будет `Connection refused`.

</details>

**A12.** Что такое `somaxconn` и `tcp_max_syn_backlog`?

<details><summary>Ответ</summary>

`somaxconn` — максимальная длина очереди установленных соединений, ожидающих
`accept()`; `tcp_max_syn_backlog` — очередь полуоткрытых (SYN_RECV). Переполнение приводит
к отбрасыванию SYN и таймаутам у клиентов.

</details>

**A13.** Чем TCP keepalive отличается от HTTP keep-alive?

<details><summary>Ответ</summary>

TCP keepalive — механизм ядра (L4), проверяющий живость простаивающего соединения
(по умолчанию через 2 часа). HTTP keep-alive — переиспользование одного TCP-соединения
для нескольких HTTP-запросов (L7, заголовок `Connection`).

</details>

**A14.** Что такое SYN-флуд и как от него защищаются?

<details><summary>Ответ</summary>

Атака потоком SYN без завершения handshake: заполняется очередь полуоткрытых
соединений. Защита: SYN cookies (`net.ipv4.tcp_syncookies=1`), увеличение backlog,
rate limiting, защита на периметре/у провайдера.

</details>

### Блок B. «Что делает команда / что означает вывод»

```bash
B1.  ss -tlnp
B2.  ss -tan state time-wait | wc -l
B3.  ss -tanp state close-wait
B4.  ss -ti
B5.  ss -s
B6.  nc -zv 10.0.0.5 5432
B7.  lsof -i :8080
B8.  tcpdump -n 'tcp[tcpflags] & tcp-syn != 0'
B9.  netstat -s | grep -i retrans
B10. sysctl net.ipv4.ip_local_port_range
```

<details><summary>Ответ</summary>

```text:no-line-numbers
B1.  Слушающие TCP-сокеты с процессами и адресами привязки.
B2.  Количество соединений в TIME_WAIT.
B3.  Соединения в CLOSE_WAIT с именами процессов — прямое указание на утечку.
B4.  Внутренняя статистика соединений: RTT, cwnd, ретрансмиссии.
B5.  Сводка: сколько сокетов каких типов и состояний.
B6.  Проверка TCP-порта без передачи данных.
B7.  Процессы, использующие порт 8080.
B8.  Захват только SYN-пакетов — видно, кто и куда инициирует соединения.
B9.  Число ретрансмиссий — индикатор потерь.
B10. Диапазон эфемерных портов.
```

</details>

**B11.** Что означает каждая строка:
```text:no-line-numbers
LISTEN  0  4096   127.0.0.1:5432   0.0.0.0:*
LISTEN  0  511      0.0.0.0:80     0.0.0.0:*
ESTAB   0  0    192.168.56.10:22   192.168.56.11:51234
```

<details><summary>Ответ</summary>

Первая строка: PostgreSQL слушает только локально (снаружи недоступен),
очередь accept 4096. Вторая: веб-сервер слушает на всех интерфейсах, backlog 511.
Третья: установленное SSH-соединение с соседом, очереди пусты.

</details>

**B12.** Клиент видит `Connection refused` мгновенно. Что произошло на уровне пакетов?
А если он видит `Connection timed out` через 2 минуты?

<details><summary>Ответ</summary>

Мгновенный refused — в ответ на SYN пришёл RST: хост доступен, порт закрыт
(или REJECT на файрволе). Таймаут — ответа нет вовсе: SYN теряется (DROP на файрволе,
нет маршрута, хост выключен), клиент повторяет SYN несколько раз и сдаётся.

</details>

### Блок C. Практика

**C1. Хендшейк в дампе.** Поймай tcpdump'ом установку и закрытие TCP-соединения
(например, `curl http://сосед/`). Выпиши последовательность флагов и объясни каждый пакет.

<details><summary>Ответ</summary>

Последовательность: `Flags [S]` (SYN), `Flags [S.]` (SYN-ACK), `Flags [.]` (ACK),
затем `Flags [P.]` с данными, `Flags [F.]` (FIN) и финальные ACK. Точка означает ACK.

</details>

**C2. Три исхода.** Воспроизведи на стенде все три случая: открытый порт, закрытый порт (RST),
отфильтрованный порт (таймаут — через `iptables -j DROP`). Для каждого приведи вывод `nc -zv`,
время реакции и что видно в tcpdump.

<details><summary>Ответ</summary>

```bash
nc -zv 192.168.56.11 22                  # succeeded
nc -zv 192.168.56.11 9999                # Connection refused (мгновенно, RST)
# на соседе: sudo iptables -A INPUT -p tcp --dport 8081 -j DROP
nc -zv -w 5 192.168.56.11 8081           # timed out (тишина)
# на соседе: sudo iptables -D INPUT -p tcp --dport 8081 -j DROP
```

</details>

**C3. TIME_WAIT.** Сделай 200 коротких HTTP-запросов к соседу и посчитай TIME_WAIT
на обеих сторонах. Объясни, почему они оказались именно там. Затем повтори с keep-alive
(`curl --keepalive-time` / один `curl` с несколькими URL) и сравни.

<details><summary>Ответ</summary>

TIME_WAIT будет там, кто закрыл соединение первым: при обычном `curl` без keep-alive
это клиент. С переиспользованием соединения количество TIME_WAIT резко падает — это и есть
практический аргумент за keep-alive/пул соединений.

</details>

**C4. CLOSE_WAIT.** Напиши программу/скрипт, который принимает соединение и **не закрывает**
его после того, как клиент отключился. Покажи растущий CLOSE_WAIT и объясни,
почему это баг приложения, а не сети.

<details><summary>Ответ</summary>

Например, `nc -l 9000` без чтения и закрытия, либо скрипт, принимающий соединение
и уходящий в `sleep`. После отключения клиента сокет остаётся в CLOSE_WAIT: ядро своё сделало
(получило FIN), а `close()` должно вызвать приложение — потому это баг кода.

</details>

**C5. Занятый порт.** Воспроизведи `Address already in use`, найди виновника тремя способами
(`ss`, `lsof`, `fuser`) и освободи порт.

<details><summary>Ответ</summary>

`ss -tlnp | grep :8080`, `lsof -i :8080`, `fuser 8080/tcp`; освободить —
завершить процесс (`kill`) или `fuser -k 8080/tcp`.

</details>

**C6. Bind-адрес.** Подними сервис на `127.0.0.1` и покажи, что с соседней ВМ он недоступен,
а локально работает. Затем перебинди на `0.0.0.0`. Это симптом, который встречается постоянно —
опиши его своими словами.

<details><summary>Ответ</summary>

Симптом: «локально curl работает, снаружи connection refused, файрвол ни при чём».
Проверка — `ss -tlnp`: если в колонке адреса `127.0.0.1`, сервис слушает только петлю.
Лечение — bind на `0.0.0.0` (или на конкретный адрес) в конфиге приложения.

</details>

**C7. Очередь соединений.** Уменьши `somaxconn` до 1, создай 50 одновременных подключений
и посмотри, что будет. Верни значение обратно.

<details><summary>Ответ</summary>

При `somaxconn=1` часть соединений будет отбрасываться или ждать: клиенты получают
таймауты/сбросы под всплеском нагрузки. Возврат: `sudo sysctl -w net.core.somaxconn=4096`.
Важно: значение применяется при `listen()`, поэтому сервис надо перезапустить.

</details>

**C8. Качество канала.** Через `iperf3` между ВМ измерь пропускную способность TCP и UDP,
затем добавь искусственные потери (`tc qdisc add dev eth1 root netem loss 5%`)
и сравни поведение TCP и UDP. Убери правило.

<details><summary>Ответ</summary>

TCP при 5% потерь резко теряет пропускную способность (срабатывает контроль
перегрузки), UDP продолжает слать с той же скоростью, но часть датаграмм теряется —
`iperf3 -u` покажет процент потерь. Убрать: `sudo tc qdisc del dev eth1 root`.

</details>

**C9. UDP на практике.** Организуй обмен по UDP через `nc -u` между ВМ. Покажи, что
для UDP нет соединения: сервер не знает об «отключении» клиента.

<details><summary>Ответ</summary>

`nc -u -l 9999` на одной ВМ и `nc -u 192.168.56.10 9999` на другой: текст доходит,
но ни одна сторона не узнаёт о «разрыве» — соединения нет, `ss -uln` показывает лишь сокет.

</details>

**C10. Скрипт проверки портов.** `portcheck.sh host port1 port2 …` — параллельно проверяет
список портов, различает refused/timeout/open, выводит таблицу и возвращает ненулевой код,
если хоть один обязательный порт закрыт.

<details><summary>Ответ</summary>

```bash
#!/usr/bin/env bash
set -uo pipefail
host="${1:?}"; shift
rc=0
for p in "$@"; do
  if timeout 3 bash -c "exec 3<>/dev/tcp/$host/$p" 2>/dev/null; then
    printf '%-6s %s\n' "$p" "открыт"
  elif nc -z -w1 "$host" "$p" 2>&1 | grep -q refused; then
    printf '%-6s %s\n' "$p" "refused (сервис не слушает)"; rc=1
  else
    printf '%-6s %s\n' "$p" "таймаут (фильтруется)"; rc=1
  fi
done
exit "$rc"
```

</details>

### Блок D. Инциденты

**D1.** На проде 40 000 соединений в TIME_WAIT, новые исходящие подключения падают
с `cannot assign requested address`. Причина и три способа лечения.

<details><summary>Ответ</summary>

Исчерпание эфемерных портов из-за множества коротких исходящих соединений.
Лечение: (1) keep-alive/пул соединений в приложении; (2) `net.ipv4.tcp_tw_reuse=1`
и расширение `ip_local_port_range`; (3) несколько исходящих IP или локальный прокси
с пулом. (`tcp_tw_recycle` не использовать — он удалён и ломал NAT.)

</details>

**D2.** У приложения растёт число открытых файловых дескрипторов, `ss` показывает тысячи
CLOSE_WAIT. Кто виноват и что сказать разработчикам?

<details><summary>Ответ</summary>

Приложение не закрывает сокеты после того, как клиент разорвал соединение:
утечка дескрипторов, рано или поздно `Too many open files`. Аргумент разработчикам:
`ss -tanp state close-wait` с именем их процесса и растущим счётчиком
`ls /proc/<pid>/fd | wc -l`.

</details>

**D3.** Сервис «иногда не отвечает» под нагрузкой, в логах клиента — таймауты подключения,
на сервере всё «зелёное». Какие очереди и метрики проверить?

<details><summary>Ответ</summary>

Очереди: `somaxconn`/backlog приложения (`ss -tln` колонка Send-Q у LISTEN),
`tcp_max_syn_backlog`, счётчики `netstat -s | grep -iE 'listen|overflow'`
(`listen queue overflows`), лимиты воркеров приложения, conntrack на пути.

</details>

**D4.** После переезда за облачный балансировщик долгоживущие соединения к БД рвутся
каждые 10 минут. Почему и что настроить?

<details><summary>Ответ</summary>

Балансировщик/NAT выбрасывает простаивающие сессии по idle timeout, а TCP keepalive
по умолчанию срабатывает через 2 часа. Настроить `net.ipv4.tcp_keepalive_time=300`
(или keepalive в драйвере БД/пуле соединений), чтобы трафик шёл чаще idle-таймаута.

</details>

**D5.** Мониторинг пингует хосты и говорит «всё ок», но пользователи видят ошибки.
Как перестроить проверки?

<details><summary>Ответ</summary>

Проверять сам сервис: TCP-connect на порт и HTTP-запрос к `/health` с проверкой кода
и времени ответа (blackbox_exporter), а ICMP оставить как вспомогательную метрику.

</details>

**D6.** Приложение в контейнере не может подключиться к PostgreSQL на хосте:
`Connection refused`, хотя БД работает. Первое, что проверить?

<details><summary>Ответ</summary>

На что забиндена БД: скорее всего `listen_addresses='localhost'`, поэтому из сети
контейнера порт закрыт. Проверить `ss -tlnp | grep 5432`, затем `pg_hba.conf` и файрвол.

</details>

**D7.** Скорость передачи между двумя ЦОД в 10 раз ниже ожидаемой, потерь нет,
RTT 80 мс. Что смотреть (подсказка: окно и BDP)?

<details><summary>Ответ</summary>

Окно и BDP: при RTT 80 мс нужно большое окно (bandwidth-delay product).
Смотреть window scaling (`ss -ti`, `sysctl net.ipv4.tcp_window_scaling`), буферы
(`net.ipv4.tcp_rmem/wmem`), алгоритм перегрузки (BBR вместо cubic), а также
промежуточное оборудование, режущее опции TCP.

</details>

### Блок E. Вопросы с собеседования

**1.** В чём отличие TCP от UDP?

<details><summary>Ответ</summary>

TCP — с установлением соединения, гарантией доставки, порядком и контролем перегрузки;
UDP — без соединения и гарантий, но быстрее и легче.

</details>

**2.** Как происходит установка TCP-соединения?

<details><summary>Ответ</summary>

SYN → SYN-ACK → ACK.

</details>

**3.** Как TCP закрывает соединение?

<details><summary>Ответ</summary>

FIN → ACK → FIN → ACK; инициатор остаётся в TIME_WAIT.

</details>

**4.** Что такое TIME_WAIT и почему их много?

<details><summary>Ответ</summary>

Состояние закрывшей стороны ~60 с, защищает от «старых» пакетов; много их — много
коротких соединений.

</details>

**5.** Что такое CLOSE_WAIT и о чём он говорит?

<details><summary>Ответ</summary>

Мы получили FIN, но приложение не закрыло сокет — утечка дескрипторов в коде.

</details>

**6.** Что такое RST?

<details><summary>Ответ</summary>

Флаг резкого сброса соединения: чаще всего «порт закрыт» или сброс приложением.

</details>

**7.** Почему `Connection refused` — это хорошая новость для диагностики?

<details><summary>Ответ</summary>

Потому что RST доказывает: сеть, маршрут и файрвол до хоста работают — проблема в сервисе.

</details>

**8.** Что такое эфемерные порты?

<details><summary>Ответ</summary>

Динамические порты для исходящих соединений (обычно 32768-60999).

</details>

**9.** Как проверить, слушает ли сервис порт?

<details><summary>Ответ</summary>

`ss -tlnp | grep <порт>` (и обратить внимание на адрес привязки).

</details>

**10.** Какие протоколы работают поверх UDP?

<details><summary>Ответ</summary>

DNS, DHCP, NTP, syslog, VoIP/RTP, VXLAN, QUIC (HTTP/3).

</details>
