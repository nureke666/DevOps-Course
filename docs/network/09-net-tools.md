# 09. Утилиты диагностики — ping, mtr, ss, nc, curl, nmap, iftop

> Роадмап → 2.5 Сети → «Утилиты траблшутинга в контексте линукса»:
> `ping`, `traceroute`/`mtr`, `netstat`/`ss`, `telnet`/`curl`, `nc`, `nmap`, `tcpdump`,
> `wireshark`, `iftop`, `iptables`.
> tcpdump/Wireshark — отдельная тема [10](/network/10-tcpdump-wireshark), iptables — [11](/network/11-firewall-iptables).
> **После темы ты умеешь:** за 5 минут локализовать сетевую проблему нужным инструментом.

---

## 🗺️ Схема: какой инструмент на каком уровне

```text:no-line-numbers
  L7  приложение    │ curl, wget, dig, openssl s_client
  ────────────────  │
  L4  порт/сессия   │ ss, netstat, nc (netcat), telnet, nmap
  ────────────────  │
  L3  IP/маршрут    │ ping, traceroute, mtr, tracepath, ip route
  ────────────────  │
  L2  MAC/ARP       │ ip neigh, arping, bridge
  ────────────────  │
  L1  линк          │ ip link, ethtool
  ────────────────  │
  Трафик/нагрузка   │ iftop, nload, iperf3, tcpdump, nethogs
```

**Алгоритм «ничего не работает» за 5 минут:**

```text:no-line-numbers
ip link          → линк есть?
ip addr / route  → адрес и маршрут есть?
ping шлюз        → L2/L3 внутри сети
ping 8.8.8.8     → IP-связность наружу
dig example.com  → DNS
nc -zv host port → порт открыт?
curl -v URL      → приложение отвечает?
mtr -n host      → где теряются пакеты (если «иногда тормозит»)
```

## 1. ping — L3-связность

```bash
ping -c4 8.8.8.8              # 4 пакета и выход (без -c будет бесконечно)
ping -c4 -W1 host             # таймаут 1 с на ответ
ping -c4 -i 0.2 host          # интервал
ping -c4 -I eth1 host         # с конкретного интерфейса
ping -c4 -s 1472 -M do host   # ⭐ проверка MTU
ping -c100 -q host            # только итоговая статистика
```

Читаем вывод:

```text:no-line-numbers
64 bytes from 8.8.8.8: icmp_seq=1 ttl=115 time=12.3 ms
                                    │           └─ RTT: задержка
                                    └─ сколько хопов осталось (по нему видно ОС и длину пути)
--- statistics ---
4 packets transmitted, 4 received, 0% packet loss, time 3005ms
rtt min/avg/max/mdev = 11.8/12.4/13.1/0.5 ms
                                      └─ mdev (джиттер): большой разброс = нестабильный канал
```

⚠️ `ping` проверяет только ICMP. «Пингуется» ≠ «работает», «не пингуется» ≠ «недоступен».

## 2. traceroute / tracepath / mtr — где рвётся путь

```bash
traceroute -n 8.8.8.8         # -n без DNS — быстрее
traceroute -n -T -p 443 host  # ⭐ TCP-трейс (когда ICMP закрыт)
traceroute -n -I host         # ICMP вместо UDP
tracepath -n host             # + определение Path MTU, без root
mtr -n host                   # интерактивно
mtr -n -r -c 100 host         # ⭐ отчёт по 100 пакетам — то, что прикладывают к тикету
```

`mtr` = traceroute + ping в реальном времени: показывает **потери на каждом хопе**.

```text:no-line-numbers
HOST                 Loss%   Snt   Last   Avg  Best  Wrst StDev
1. 192.168.1.1        0.0%   100    1.2   1.3   1.0   2.1   0.2
2. 10.10.0.1         12.0%   100   15.3  16.1  14.8  38.2   3.1   ← потери начинаются здесь
3. 8.8.8.8            0.0%   100   12.1  12.4  11.9  13.5   0.3   ← а тут их нет!
```

⭐ **Ключевое правило чтения mtr:** потери на промежуточном хопе, которых нет дальше, —
это **не проблема**: маршрутизаторы ограничивают генерацию ICMP для себя (rate limit).
Реальны только потери, которые сохраняются **до конца** маршрута.

## 3. ss / netstat — сокеты и соединения

`netstat` устарел (пакет net-tools), но встречается в старых мануалах. Учить — `ss`.

```bash
ss -tlnp                 # ⭐ TCP listening + процессы (самая частая команда)
ss -ulnp                 # UDP listening
ss -tanp                 # все TCP с процессами
ss -s                    # сводка
ss -ti                   # RTT, cwnd, ретрансмиссии
ss -tan state established '( dport = :443 )'
ss -tp dst 10.0.0.5      # соединения с конкретным хостом
ss -K dst 10.0.0.5       # ⭐ принудительно закрыть соединения (нужен root)

# Соответствие netstat → ss
netstat -tulpn  →  ss -tulpn
netstat -an     →  ss -an
netstat -s      →  nstat / ss -s
netstat -rn     →  ip route
netstat -i      →  ip -s link
```

## 4. nc (netcat) — швейцарский нож

```bash
nc -zv host 22                    # ⭐ проверка порта
nc -zv host 20-25                 # диапазон
nc -zvu host 53                   # UDP (результат условный: нет ответа ≠ закрыт)
nc -zv -w 3 host 443              # таймаут

nc -l 9000                        # слушать (простой сервер)
echo "hello" | nc host 9000       # отправить
nc host 9000 < file.txt           # передать файл
nc -l 9000 > received.txt         # принять файл

# Мини-HTTP-сервер для отладки балансировщика
while true; do printf 'HTTP/1.1 200 OK\r\nContent-Length: 2\r\n\r\nok' | nc -l -p 8080 -q0; done

# Посмотреть, что реально шлёт клиент (сырой запрос)
nc -l 8080
```

⚠️ Есть два несовместимых netcat: OpenBSD (`-w`, без `-p` в режиме listen) и traditional.
Проверить: `nc -h 2>&1 | head -1`.

## 5. telnet и curl — проверка прикладного уровня

```bash
telnet host 25                    # ручной диалог с SMTP/HTTP-сервером
# HTTP вручную:
printf 'GET / HTTP/1.1\r\nHost: example.com\r\nConnection: close\r\n\r\n' | nc example.com 80

curl -v https://host/path         # весь обмен
curl -sI https://host             # только заголовки
curl -s -o /dev/null -w '%{http_code} %{time_total}\n' URL
curl --resolve host:443:10.0.0.5 https://host/     # ⭐ проверить конкретный бэкенд
curl -x socks5h://127.0.0.1:1080 URL               # через SOCKS (см. SSH -D)
```

`telnet` как клиент почти вытеснен `nc`/`curl`, но как быстрый способ «поговорить руками»
с текстовым протоколом — жив.

## 6. nmap — что открыто (⚠️ только на своих системах)

```bash
nmap -sT -p 22,80,443 192.168.56.11      # TCP connect scan
nmap -sS -p- 192.168.56.11               # SYN-скан всех портов (нужен root)
nmap -sU -p 53,123 192.168.56.11         # UDP (медленно)
nmap -sV -p 22,80 192.168.56.11          # ⭐ определить версии сервисов
nmap -sn 192.168.56.0/24                 # ping-скан: кто живой в подсети
nmap -A 192.168.56.11                    # всё сразу: ОС, версии, скрипты
nmap --script ssl-cert -p443 example.com # сертификат
```

⚠️ Сканирование чужих сетей без письменного разрешения — нарушение закона и политики
безопасности. На работе — только по согласованию, на учебном стенде — сколько угодно.
Практическое применение DevOps: проверить, что после настройки файрвола снаружи видны
**только** нужные порты.

## 7. iftop / nload / nethogs / iperf3 — нагрузка на сеть

```bash
sudo iftop -i eth0                # ⭐ кто и с кем говорит прямо сейчас (по хостам)
sudo iftop -i eth0 -P             # с портами
sudo nethogs eth0                 # ⭐ трафик по ПРОЦЕССАМ
nload eth0                        # общая загрузка интерфейса
ip -s link show eth0              # счётчики: пакеты, ошибки, дропы
vnstat -l                         # объёмы за период (если установлен)

# Замер пропускной способности между хостами
iperf3 -s                         # на одной машине
iperf3 -c 192.168.56.10 -t 10     # на другой
iperf3 -c host -u -b 100M         # UDP с заданной скоростью (покажет потери и джиттер)
iperf3 -c host -P 4               # 4 параллельных потока
```

⭐ `ip -s link` — быстрый способ увидеть ошибки и дропы на интерфейсе: растущие `errors`/`dropped`
означают проблему с железом, драйвером или переполнение буферов.

## 8. Диагностические сценарии

| Симптом | Последовательность |
|---------|--------------------|
| «Сервис недоступен» | `ping` → `nc -zv` → `curl -v` → логи сервиса |
| «Иногда тормозит» | `mtr -n -r -c 200` → `ss -ti` (retrans) → `iftop` (не забит ли канал) |
| «После деплоя 502» | `ss -tlnp` на бэкенде → `curl` напрямую к бэкенду → логи nginx |
| «Медленно качается» | `iperf3` (канал) → `ip -s link` (ошибки) → MTU |
| «Кто-то ест трафик» | `iftop -P` → `nethogs` → `ss -tanp` |
| «Что открыто наружу» | `ss -tlnp` изнутри → `nmap` снаружи |

---

## 💼 Как это в DevOps

- 90% инцидентов закрываются связкой `ss -tlnp` + `curl -v` + `mtr`.
- `nc -zv` — стандартная проверка доступности порта в скриптах и init-контейнерах.
- `iperf3` — единственный честный ответ на «у нас медленная сеть».
- `nmap` после настройки файрвола/security group — проверка, что закрыли именно то, что хотели.
- Вывод `mtr -r -c 100` — то, что прикладывают в тикет провайдеру или сетевикам.

## 🧪 Мини-лаба

```bash
vagrant ssh web
sudo apt install -y iputils-ping traceroute mtr-tiny netcat-openbsd nmap iftop iperf3 net-tools

# 1. ping и чтение статистики
ping -c5 192.168.56.11
ping -c20 -q -i 0.2 8.8.8.8 | tail -3      # обрати внимание на mdev

# 2. traceroute/mtr
traceroute -n -q1 -m 12 8.8.8.8
mtr -n -r -c 20 8.8.8.8

# 3. TCP-трейс, когда ICMP закрыт
sudo traceroute -n -T -p 443 -m 12 example.com | tail -5

# 4. ss — всё о сокетах
ss -tlnp
ss -s
ss -tan state established | head
ss -ti | head -6

# 5. nc: проверка портов
nc -zv 192.168.56.11 22
nc -zv 192.168.56.11 9999
nc -zv -w2 192.168.56.11 20-25

# 6. nc: свой сервер и клиент
nc -l 9000 > /tmp/received.txt &
echo "привет через netcat" | nc -q0 127.0.0.1 9000
cat /tmp/received.txt

# 7. Мини-HTTP-сервер на nc и запрос к нему
(printf 'HTTP/1.1 200 OK\r\nContent-Length: 2\r\n\r\nok' | nc -l -p 8081 -q0 >/dev/null) &
sleep 1; curl -s -o /dev/null -w 'nc-сервер: %{http_code}\n' http://127.0.0.1:8081/

# 8. HTTP руками
printf 'GET / HTTP/1.1\r\nHost: example.com\r\nConnection: close\r\n\r\n' | nc example.com 80 | head -8

# 9. nmap по СВОЕМУ стенду
nmap -sn 192.168.56.0/24
nmap -sT -p 1-1000 192.168.56.11
nmap -sV -p 22 192.168.56.11

# 10. Пропускная способность
# на app:  iperf3 -s
iperf3 -c 192.168.56.11 -t 5 2>/dev/null || echo "запусти на app: iperf3 -s"
iperf3 -c 192.168.56.11 -u -b 50M -t 5 2>/dev/null | tail -4

# 11. Кто ест трафик
sudo timeout 10 iftop -i eth1 -t -s 10 2>/dev/null | head -15
ip -s link show eth1

# 12. Полный алгоритм одной строкой (сохрани себе)
cat > ~/netdiag.sh <<'EOS'
#!/usr/bin/env bash
h="${1:?хост}"; p="${2:-80}"
echo "== link ==";  ip -brief link
echo "== route =="; ip route get "$h" 2>&1 | head -1
echo "== icmp ==";  ping -c2 -W1 "$h" | tail -2
echo "== dns ==";   getent hosts "$h" || echo "имя не резолвится"
echo "== port ==";  nc -zv -w2 "$h" "$p" 2>&1
echo "== http ==";  curl -s -o /dev/null -w 'code=%{http_code} time=%{time_total}\n' "http://$h:$p/" || true
echo "== path ==";  mtr -n -r -c 10 "$h" 2>/dev/null | tail -5
EOS
chmod +x ~/netdiag.sh && ~/netdiag.sh 192.168.56.11 22
```

## 📌 Шпаргалка

| Задача | Команда |
|--------|---------|
| L3-связность | `ping -c4 -W1 host` |
| Проверка MTU | `ping -M do -s 1472 host` |
| Путь пакета | `traceroute -n host` / `mtr -n -r -c 100 host` |
| Трейс при закрытом ICMP | `traceroute -n -T -p 443 host` |
| Кто слушает | ⭐ `ss -tlnp` |
| Все соединения | `ss -tanp` |
| Качество TCP | `ss -ti` (retrans, rtt) |
| Закрыть соединения | `ss -K dst IP` |
| Проверка порта | `nc -zv host port` |
| Передать файл | `nc -l 9000 > f` / `nc host 9000 < f` |
| HTTP-проверка | `curl -sI URL`, `curl -v URL` |
| Конкретный бэкенд | `curl --resolve host:443:IP https://host/` |
| Что открыто | `nmap -sT -p- host` (только свои!) |
| Кто живой в сети | `nmap -sn 192.168.56.0/24` |
| Кто ест трафик | `iftop -i eth0 -P`, `nethogs` |
| Пропускная способность | `iperf3 -s` / `iperf3 -c host` |
| Ошибки интерфейса | `ip -s link show eth0` |

## 🧠 Что запомнить

1. Инструмент выбирается по уровню: ping — L3, ss/nc — L4, curl — L7.
2. `ss -tlnp` — самая частая команда: слушает ли сервис и на каком адресе.
3. `netstat` устарел: `-tulpn` → `ss -tulpn`, `-rn` → `ip route`.
4. `nc -zv` различает refused (порт закрыт) и таймаут (фильтруется).
5. `mtr` показывает потери по хопам; потери только на промежуточном хопе — обычно артефакт
   rate limit, а не проблема.
6. Когда ICMP закрыт — `traceroute -T -p 443` по TCP.
7. `curl --resolve` проверяет конкретный бэкенд в обход DNS и балансировщика.
8. `nmap` — только по своим системам и по согласованию; полезен для проверки файрвола снаружи.
9. `iperf3` отвечает на «медленная ли сеть», `iftop`/`nethogs` — «кто её ест».
10. `ip -s link` показывает ошибки и дропы на интерфейсе — то, что часто упускают.

## Задачи

> ⚠️ `nmap` — только по своему стенду. Сканирование чужих сетей = инцидент безопасности.

---

### Блок A. Теория

**A1.** Какой инструмент соответствует каждому уровню (L1-L7)? Приведи по одному.

<details><summary>Ответ</summary>

L1 — `ip link`/`ethtool`; L2 — `ip neigh`/`arping`; L3 — `ping`/`traceroute`/`ip route`;
L4 — `ss`/`nc`/`nmap`; L7 — `curl`/`dig`/`openssl s_client`.

</details>

**A2.** Напиши алгоритм «ничего не работает» из 7 шагов по порядку.

<details><summary>Ответ</summary>

`ip link` → `ip addr`/`ip route` → ping шлюза → ping внешнего IP → DNS (`dig`/`getent`)
→ проверка порта (`nc -zv`) → запрос приложением (`curl -v`); при «иногда» — `mtr` длительно.

</details>

**A3.** Что показывают поля вывода ping: `ttl`, `time`, `mdev`, `packet loss`?

<details><summary>Ответ</summary>

`ttl` — сколько хопов осталось (косвенно указывает на ОС и длину пути);
`time` — RTT; `mdev` — среднее отклонение (джиттер); `packet loss` — доля потерянных пакетов.

</details>

**A4.** Почему «пингуется» не значит «работает», а «не пингуется» — не значит «недоступен»?

<details><summary>Ответ</summary>

ICMP может быть закрыт политикой при полностью рабочем сервисе; и наоборот —
хост отвечает на ICMP, а приложение упало или слушает не тот адрес.

</details>

**A5.** Чем `mtr` лучше `traceroute`? Как правильно читать потери по хопам?

<details><summary>Ответ</summary>

`mtr` непрерывно шлёт пакеты и показывает потери и задержку **по каждому хопу**
в динамике. Правило чтения: значимы потери, которые сохраняются до конечного хопа;
потери только на промежуточном узле обычно означают rate limit ICMP на нём.

</details>

**A6.** Когда traceroute нужно запускать в режиме `-T`?

<details><summary>Ответ</summary>

Когда ICMP и UDP-пробы фильтруются: `-T` использует TCP SYN на нужный порт,
и путь строится по тому же протоколу, что и реальный трафик.

</details>

**A7.** Соответствие команд `netstat` и `ss` (минимум 5 пар).

<details><summary>Ответ</summary>

`netstat -tulpn` → `ss -tulpn`; `netstat -an` → `ss -an`; `netstat -rn` → `ip route`;
`netstat -i` → `ip -s link`; `netstat -s` → `nstat`; `netstat -g` → `ip maddr`.

</details>

**A8.** Чем отличаются `nc -zv` для TCP и для UDP? Почему UDP-результат ненадёжен?

<details><summary>Ответ</summary>

Для TCP результат достоверен: SYN-ACK (открыт) или RST (закрыт). Для UDP ответа
обычно нет вовсе: «нет ответа» может значить и «открыт, но молчит», и «отфильтрован».
Достоверный ответ даёт только ICMP port unreachable (закрыт).

</details>

**A9.** Что делает `ss -K` и когда это применяют?

<details><summary>Ответ</summary>

Принудительно закрывает (убивает) найденные сокеты. Применяют, когда нужно
разорвать зависшие соединения без перезапуска сервиса — например, после смены firewall-правил
или при переключении на новый бэкенд.

</details>

**A10.** Что показывает `ss -ti` и как по нему понять, что проблема в сети?

<details><summary>Ответ</summary>

RTT, cwnd, размер окна, число ретрансмиссий по каждому соединению. Растущие
`retrans` при нормальном приложении указывают на потери в сети, а не на медленный бэкенд.

</details>

**A11.** Зачем нужен `curl --resolve`?

<details><summary>Ответ</summary>

Чтобы обратиться по имени (SNI, Host, сертификат корректны), но к конкретному IP —
проверить отдельный бэкенд за балансировщиком или новый сервер до переключения DNS.

</details>

**A12.** Чем `iftop` отличается от `nethogs` и от `iperf3`?

<details><summary>Ответ</summary>

`iftop` — трафик по парам хостов/портов в реальном времени; `nethogs` — трафик
по процессам; `iperf3` — активное измерение максимальной пропускной способности
(сам генерирует нагрузку).

</details>

**A13.** Что показывает `ip -s link` и на что там смотреть?

<details><summary>Ответ</summary>

Счётчики интерфейса: переданные/принятые байты и пакеты, `errors`, `dropped`,
`overrun`, `carrier`. Рост errors/carrier — физика/драйвер; dropped/overrun — переполнение
буферов, нехватка CPU или слишком маленькая очередь.

</details>

**A14.** Какие типы сканирования nmap ты знаешь и чем `-sS` отличается от `-sT`?

<details><summary>Ответ</summary>

`-sT` — полное TCP-соединение (без root, заметнее в логах); `-sS` — SYN-скан
(полуоткрытый, быстрее, нужен root); `-sU` — UDP; `-sn` — только обнаружение хостов;
`-sV` — определение версий; `-A` — агрессивный набор.

</details>

### Блок C. Практика

**C1. Полный алгоритм.** Напиши и проверь `netdiag.sh <host> <port>`, который последовательно
проходит уровни (link → route → icmp → dns → port → http → path) и печатает отчёт,
пригодный для вставки в тикет.

<details><summary>Ответ</summary>

Готовый вариант — в мини-лабе конспекта (`netdiag.sh`). Важно: вывод должен содержать
конкретику (коды, времена, номера хопов), чтобы тикет не требовал уточнений.

</details>

**C2. Три исхода порта.** На стенде добейся трёх результатов и зафиксируй вывод и время:
открытый порт, закрытый порт, порт под `DROP`. Чем отличается диагностика в каждом случае?

<details><summary>Ответ</summary>

Открыт: `nc -zv` → `succeeded`, мгновенно. Закрыт: `Connection refused`, мгновенно
(в tcpdump — RST). DROP: `nc -zv -w2` молчит до таймаута, в tcpdump видно только исходящие SYN.

</details>

**C3. mtr при потерях.** Добавь искусственные потери (`tc qdisc add dev eth1 root netem loss 10%`)
и сравни вывод `ping` и `mtr` до и после. Убери правило.

<details><summary>Ответ</summary>

`sudo tc qdisc add dev eth1 root netem loss 10%` — ping покажет ~10% потерь,
mtr — потери на последнем хопе (значит, они реальны). Убрать: `sudo tc qdisc del dev eth1 root`.

</details>

**C4. Искусственная задержка.** Добавь `netem delay 200ms`, посмотри, как меняются RTT,
время `curl`, скорость `iperf3`. Объясни связь задержки и пропускной способности.

<details><summary>Ответ</summary>

`netem delay 200ms` увеличивает RTT, `curl` растёт на величину нескольких RTT
(TCP+TLS-хендшейк), `iperf3` в один поток резко падает: пропускная способность ограничена
окном/RTT (BDP). Несколько потоков (`-P 4`) частично компенсируют.

</details>

**C5. netcat-лаборатория.** Реализуй: (1) передачу файла между ВМ; (2) простейший чат;
(3) mini-HTTP-сервер, отвечающий 200; (4) «слушалку», показывающую сырой HTTP-запрос,
который шлёт curl.

<details><summary>Ответ</summary>

(1) `nc -l 9000 > file` / `nc host 9000 < file`; (2) `nc -l 9000` на одной и
`nc host 9000` на другой — двусторонний обмен; (3) цикл с `printf 'HTTP/1.1 200 OK…' | nc -l -p 8080 -q0`;
(4) `nc -l 8080`, затем `curl http://host:8080/` — в терминале появится сырой запрос
со всеми заголовками.

</details>

**C6. HTTP руками.** Через `nc` отправь корректный HTTP/1.1-запрос с заголовком Host
и прочитай ответ. Затем отправь запрос **без** Host и объясни результат.

<details><summary>Ответ</summary>

Без `Host` сервер HTTP/1.1 обязан ответить `400 Bad Request`: заголовок обязателен,
иначе непонятно, какой виртуальный хост запрашивается.

</details>

**C7. nmap по стенду.** Просканируй соседнюю ВМ: какие порты открыты, какие версии сервисов,
какая ОС определяется. Затем закрой один порт файрволом и покажи, как изменился результат
(`filtered` vs `closed`).

<details><summary>Ответ</summary>

`nmap -sT -p-` покажет open-порты; после `iptables -A INPUT -p tcp --dport 8080 -j DROP`
порт станет `filtered` (нет ответа), а при `-j REJECT` — `closed` (RST). Это ровно та же
разница, что между таймаутом и refused.

</details>

**C8. Пропускная способность.** Измерь `iperf3` между ВМ: TCP в один поток, TCP в 4 потока,
UDP на 50 Мбит и на 500 Мбит. Объясни разницу и появление потерь.

<details><summary>Ответ</summary>

Один TCP-поток может не выбрать канал из-за окна и потерь; 4 потока дают больше.
UDP на 50 Мбит пройдёт без потерь, на 500 Мбит (если канал уже) появятся потери —
UDP не снижает скорость сам, в отличие от TCP.

</details>

**C9. Кто ест трафик.** Запусти фоновую загрузку (`curl -o /dev/null` большого файла или
`iperf3`) и найди её через `iftop -P` и `nethogs`. Сопоставь с `ss -tanp`.

<details><summary>Ответ</summary>

`iftop -P` покажет пару хостов и порты с максимальной скоростью; `nethogs` —
процесс (`curl`/`iperf3`); `ss -tanp` свяжет соединение с PID и портом.

</details>

**C10. Ошибки интерфейса.** Найди счётчики ошибок и дропов, объясни, что означает каждый,
и как отличить проблему физики от переполнения буферов.

<details><summary>Ответ</summary>

`RX errors` — битые кадры (кабель, SFP, помехи); `RX dropped` — пакеты отброшены
ядром/драйвером (переполнение очереди, нет буферов, нет обработчика); `overrun` — не успели
вычитать из кольцевого буфера (нагрузка на CPU). Физика — errors/carrier, нагрузка —
dropped/overrun.

</details>

**C11. Сравнение инструментов.** Для одной и той же проблемы («сервис не отвечает на порту
8080») составь таблицу: инструмент → что он показал → какой вывод сделан.

<details><summary>Ответ</summary>

Пример: `ss -tlnp` (никто не слушает 8080 → вывод «сервис не запущен»);
`nc -zv` (refused подтверждает); `curl -v` (connection refused);
`journalctl -u service` (причина падения). Итог: проблема не сетевая.

</details>

### Блок D. Инциденты

**D1.** Пользователи жалуются на «рывки» видеозвонков. `ping` показывает 0% потерь и 20 мс.
Что ещё измерить и какой инструмент?

<details><summary>Ответ</summary>

Для голоса/видео важны джиттер и потери, а не средний RTT: `mtr -n -r -c 500`
(потери), `ping -i 0.2` с анализом `mdev`, `iperf3 -u` (джиттер и потери UDP),
загрузка канала (`iftop`), очереди/QoS на оборудовании.

</details>

**D2.** Сервис недоступен снаружи, но `curl localhost:8080` изнутри работает.
Последовательность проверок?

<details><summary>Ответ</summary>

`ss -tlnp` (на каком адресе слушает — 127.0.0.1 или 0.0.0.0) → правила файрвола
(`iptables -L -n`, security group) → `nc -zv` снаружи (refused или таймаут) →
маршрут/NAT → `tcpdump` на сервере: доходят ли SYN.

</details>

**D3.** `mtr` показывает 40% потерь на третьем хопе, но до цели 0%. Нужно ли эскалировать провайдеру?

<details><summary>Ответ</summary>

Нет: потери на промежуточном хопе, отсутствующие на конечном, — это ICMP rate limit.
Эскалируют, когда потери держатся до целевого хопа и подтверждаются TCP-трейсом/ретрансмиссиями.

</details>

**D4.** Копирование файла между ЦОД идёт 10 Мбит/с, хотя канал 1 Гбит/с, потерь нет.
Чем измерять и что проверять?

<details><summary>Ответ</summary>

`iperf3` в несколько потоков (честная пропускная способность), проверка MTU,
`ss -ti` (retrans, cwnd, окно), `ip -s link` (ошибки), настройки TCP-буферов и алгоритма
перегрузки; при большом RTT — типичная проблема BDP.

</details>

**D5.** После настройки файрвола коллеги говорят «всё закрыто», а ты уверен, что открыл 443.
Как проверить снаружи и изнутри?

<details><summary>Ответ</summary>

Изнутри: `ss -tlnp` (слушает ли), `iptables -L -n -v` (правила и счётчики).
Снаружи: `nc -zv host 443` и `nmap -Pn -p 443 host` с другой машины/сети.
Разница filtered/closed сразу покажет, файрвол это или отсутствующий сервис.

</details>

**D6.** Сервер периодически «пропадает» из мониторинга на 10-20 секунд. Какие три инструмента
запустишь одновременно, чтобы поймать момент?

<details><summary>Ответ</summary>

Одновременно: `mtr -n` (потери в момент сбоя), `tcpdump` с фильтром на хост
(долетают ли пакеты) и `ip -s link`/`dmesg` (флап интерфейса, ошибки). Плюс логи
коммутатора/гипервизора, если доступны.

</details>

**D7.** Из контейнера не работает подключение к внешнему API, с хоста — работает.
Порядок диагностики внутри контейнера (с учётом того, что там нет привычных утилит)?

<details><summary>Ответ</summary>

Внутри контейнера обычно нет утилит: использовать `docker exec` с временным
образом (`nicolaka/netshoot`), `nsenter` в namespace контейнера с хоста, либо проверить
`/etc/resolv.conf`, переменные прокси и `wget`/`curl` (если есть). Дальше — обычный алгоритм:
DNS → маршрут → порт → HTTP.

</details>

### Блок E. Вопросы с собеседования

**1.** Какими утилитами ты диагностируешь сетевые проблемы?

<details><summary>Ответ</summary>

ping, traceroute/mtr, ss, nc, curl, dig, tcpdump, nmap, iftop/nethogs, iperf3 — по уровням.

</details>

**2.** Чем `ss` лучше `netstat`?

<details><summary>Ответ</summary>

`ss` быстрее (читает netlink, а не `/proc`), поддерживает мощные фильтры по состояниям
и адресам, показывает внутренние метрики TCP.

</details>

**3.** Как проверить, открыт ли порт, не имея telnet?

<details><summary>Ответ</summary>

`nc -zv host port`, `curl -v telnet://host:port`, `timeout 2 bash -c '</dev/tcp/host/port'`,
`nmap -p port host`.

</details>

**4.** Как понять, где теряются пакеты?

<details><summary>Ответ</summary>

`mtr` длительно с большим числом пакетов; значимы потери, доходящие до конечного хопа;
подтверждение — ретрансмиссии в `ss -ti` и счётчики интерфейсов.

</details>

**5.** Чем ping отличается от traceroute и mtr?

<details><summary>Ответ</summary>

ping проверяет достижимость и RTT; traceroute показывает путь; mtr совмещает оба
и даёт статистику по хопам.

</details>

**6.** Как измерить реальную пропускную способность канала?

<details><summary>Ответ</summary>

`iperf3` между двумя точками (TCP и UDP, один и несколько потоков).

</details>

**7.** Как узнать, какой процесс занимает порт?

<details><summary>Ответ</summary>

`ss -tlnp | grep :порт` или `lsof -i :порт` / `fuser порт/tcp`.

</details>

**8.** Как узнать, кто расходует трафик на сервере?

<details><summary>Ответ</summary>

`iftop -P` (по хостам и портам), `nethogs` (по процессам), `ss -tanp` (по соединениям).

</details>
