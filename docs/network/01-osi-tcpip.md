# 01. OSI и TCP/IP — каркас, к которому сводится всё остальное

> Роадмап → 2.5 Сети → «Модель OSI: все 7 уровней, протоколы на них,
> **особое внимание уровням 3, 4, 7**».
> **После темы ты умеешь:** назвать все уровни, объяснить инкапсуляцию и — главное —
> по симптому определить, **на каком уровне искать проблему**.

---

## 🗺️ Схема: инкапсуляция — что происходит с твоими данными

```text:no-line-numbers
   Ты:  curl https://example.com/api
   │
   ▼
┌─────────────────────────────────────────────────────────────────┐
│ L7 Приложение   HTTP-запрос: GET /api HTTP/1.1 + заголовки      │  ДАННЫЕ
├─────────────────────────────────────────────────────────────────┤
│ L6 Представление  TLS-шифрование, сжатие, кодировка             │
├─────────────────────────────────────────────────────────────────┤
│ L5 Сеанс          установка/поддержание сессии                  │
├─────────────────────────────────────────────────────────────────┤
│ L4 Транспорт    + TCP-заголовок (порт источника/назначения,     │  СЕГМЕНТ
│                   seq, ack, флаги)                              │
├─────────────────────────────────────────────────────────────────┤
│ L3 Сетевой      + IP-заголовок (src IP, dst IP, TTL, protocol)  │  ПАКЕТ
├─────────────────────────────────────────────────────────────────┤
│ L2 Канальный    + Ethernet-заголовок (src MAC, dst MAC) + FCS   │  КАДР (frame)
├─────────────────────────────────────────────────────────────────┤
│ L1 Физический     биты: электричество / свет / радио            │  БИТЫ
└─────────────────────────────────────────────────────────────────┘
   │
   ▼  провод / Wi-Fi
   На той стороне всё разворачивается в обратном порядке (декапсуляция)
```

⭐ **Главное свойство модели:** каждый уровень общается «со своим» уровнем на другой стороне
и не знает, что происходит ниже. Поэтому HTTP работает одинаково поверх Wi-Fi, оптики и VPN.

## 1. Семь уровней — что на каждом

| № | Уровень | Единица | Что делает | Протоколы | Устройства |
|---|---------|---------|------------|-----------|------------|
| 7 | Application | Данные | Прикладные протоколы | HTTP, DNS, SSH, SMTP, FTP, gRPC | ⭐ L7-балансировщик (nginx) |
| 6 | Presentation | Данные | Шифрование, сжатие, форматы | TLS/SSL, JPEG, ASCII | — |
| 5 | Session | Данные | Сессии, их поддержание и восстановление | NetBIOS, RPC, SOCKS | — |
| 4 | Transport | Сегмент | Порты, надёжность, порядок | ⭐ **TCP**, **UDP**, QUIC | L4-балансировщик, NAT |
| 3 | Network | Пакет | Адресация и маршрутизация между сетями | ⭐ **IP**, ICMP, IPsec | Маршрутизатор (роутер) |
| 2 | Data Link | Кадр | Доставка в пределах одного сегмента | Ethernet, ARP*, VLAN, PPP | Свитч, сетевая карта |
| 1 | Physical | Бит | Передача сигнала | 100BASE-TX, Wi-Fi, оптика | Кабель, хаб, трансивер |

\* ARP формально между L2 и L3 — он преобразует IP в MAC (подробно в теме [02](/network/02-l2-ethernet-arp)).

**Мнемоника:** «**П**ожалуйста **К**оля **С**делай **Т**ак **С**естре **П**ринёс **П**ирог» —
Физический, Канальный, Сетевой, Транспортный, Сеансовый, Представления, Прикладной (снизу вверх).

## 2. Модель TCP/IP — то, что работает на самом деле

OSI — учебная модель. Реальный стек — TCP/IP из 4 уровней:

```text:no-line-numbers
   OSI                      TCP/IP (реальность)         Пример
┌──────────────┐         ┌───────────────────────┐
│ 7 Прикладной │         │                       │   HTTP, DNS, SSH
│ 6 Представл. │────────►│  Application          │   TLS живёт здесь
│ 5 Сеансовый  │         │                       │
├──────────────┤         ├───────────────────────┤
│ 4 Транспорт  │────────►│  Transport            │   TCP, UDP
├──────────────┤         ├───────────────────────┤
│ 3 Сетевой    │────────►│  Internet             │   IP, ICMP
├──────────────┤         ├───────────────────────┤
│ 2 Канальный  │         │                       │   Ethernet, ARP
│ 1 Физический │────────►│  Network Access       │   Wi-Fi, оптика
└──────────────┘         └───────────────────────┘
```

На собесе спрашивают OSI (потому что это классика), а работаешь ты с TCP/IP.
Правильный ответ: «Формально 7 уровней OSI, практически — четырёхуровневый стек TCP/IP,
где 5-7 схлопнуты в прикладной, а TLS живёт между транспортом и приложением».

## 3. ⭐ Диагностика по уровням — за что тут любят этот блок

Это не теория ради теории: модель нужна, чтобы **не гадать, а искать по порядку**.

```text:no-line-numbers
Симптом                                   Уровень  Чем проверять
──────────────────────────────────────────────────────────────────────────────
Линк не поднят, «кабель не подключён»       L1     ip link, ethtool eth0
Есть IP, но не пингуется сосед по сети      L2     ip neigh (ARP), tcpdump arp
Пингуется сосед, но не пингуется интернет   L3     ip route, ping 8.8.8.8, traceroute
Пингуется IP, но порт не отвечает           L4     ss -tlnp, nc -zv host port, iptables
Имя не резолвится, а по IP работает         L7/DNS dig, /etc/resolv.conf, getent hosts
Соединение есть, но 502/403/404             L7     curl -v, логи nginx и приложения
Работает по HTTP, не работает по HTTPS      L6/7   openssl s_client, срок сертификата
──────────────────────────────────────────────────────────────────────────────
```

**Правило троблшутинга:** идти снизу вверх (L1 → L7). Проверка занимает секунды,
а «давай перезапустим приложение» при оборванном кабеле — это потерянный час.

## 4. Порты и сокеты — стык L4 и L7

```text:no-line-numbers
Соединение однозначно определяется пятёркой (5-tuple):
   протокол + src IP + src port + dst IP + dst port

   192.168.1.5:54321  ──TCP──►  93.184.216.34:443
   ↑ клиент, эфемерный порт      ↑ сервер, well-known порт
```

| Диапазон | Название | Кто использует |
|----------|----------|----------------|
| 0-1023 | Well-known | Системные сервисы, требуют root для bind |
| 1024-49151 | Registered | Приложения (PostgreSQL 5432, Redis 6379) |
| 49152-65535 | Ephemeral (динамические) | Исходящие соединения клиентов |

**Порты, которые надо знать наизусть:**

| Порт | Сервис | Порт | Сервис |
|------|--------|------|--------|
| 20/21 | FTP | 443 | HTTPS |
| 22 | ⭐ SSH | 465/587 | SMTPS |
| 25 | SMTP | 3306 | MySQL |
| 53 | ⭐ DNS (UDP и TCP) | 5432 | ⭐ PostgreSQL |
| 67/68 | DHCP | 6379 | Redis |
| 80 | ⭐ HTTP | 9090 | Prometheus |
| 123 | NTP | 9200 | Elasticsearch |
| 161 | SNMP | 6443 | ⭐ Kubernetes API |
| 389/636 | LDAP/LDAPS | 2379/2380 | etcd |

```bash
cat /etc/services | grep -w 5432      # справочник портов прямо в системе
ss -tlnp                               # кто слушает на этой машине
```

## 5. Где в DevOps проходит граница L4 и L7

Это **самый практичный вывод** из всей модели:

| | L4-балансировка | L7-балансировка |
|---|---|---|
| Что видит | IP и порт | HTTP-запрос целиком: URL, заголовки, куки |
| Может ли роутить по `/api` | ❌ | ✅ |
| Терминирует TLS | Обычно нет (проксирует как есть) | ✅ да |
| Производительность | Выше, задержка меньше | Ниже (нужно разобрать запрос) |
| Примеры | HAProxy в `mode tcp`, AWS NLB, `Service type=LoadBalancer` | nginx, HAProxy `mode http`, ALB, Ingress |

В Kubernetes это ровно граница между **Service** (L4) и **Ingress** (L7) —
см. Service и Ingress в блоке Kubernetes.

---

## 💼 Как это в DevOps

- Модель — это **язык общения** с сетевиками и разработчиками: «проблема на L4, порт закрыт»
  понятнее, чем «что-то не работает».
- Любой troubleshooting начинается с вопроса «на каком уровне рвётся» — и это экономит часы.
- Балансировщики, Service/Ingress в k8s, security groups в облаке, правила файрвола —
  всё описывается в терминах уровней.
- На собесе «назови уровни OSI» — это разминочный вопрос. Провалить его = сразу минус.

## 🧪 Мини-лаба

```bash
vagrant ssh web

# L1 — физика и линк
ip link show                       # state UP / DOWN
ethtool eth0 2>/dev/null | head -20 # скорость, дуплекс, есть ли линк

# L2 — MAC и ARP
ip link show eth1 | grep ether     # свой MAC
ip neigh                           # ARP-таблица: IP ↔ MAC
ping -c1 192.168.56.11 >/dev/null && ip neigh | grep 192.168.56.11

# L3 — IP и маршруты
ip -brief addr
ip route
ping -c2 8.8.8.8                   # L3 наружу
traceroute -n 8.8.8.8 | head -5

# L4 — порты и соединения
ss -tlnp                           # кто слушает
ss -tan state established          # активные TCP-соединения
nc -zv 192.168.56.11 22            # проверить конкретный порт

# L7 — прикладной уровень
curl -sI http://example.com | head -5
dig +short example.com

# Увидеть инкапсуляцию своими глазами (тема 10)
sudo tcpdump -i any -n -c 5 -e icmp &   # -e покажет MAC-адреса (L2)
ping -c2 8.8.8.8; wait
# В выводе видно: MAC → IP → ICMP, то есть L2 → L3 → L4/7 в одной строке

# Диагностика по уровням: сломаем и починим
sudo ip link set eth1 down         # L1/L2
ping -c1 -W1 192.168.56.11; echo "код: $?"
ip link show eth1 | head -1        # state DOWN ← вот и ответ
sudo ip link set eth1 up
```

## 📌 Шпаргалка

| Уровень | Единица | Ключевые протоколы | Команда для проверки |
|---------|---------|--------------------|----------------------|
| L7 Application | Данные | HTTP, DNS, SSH | `curl -v`, `dig` |
| L6 Presentation | Данные | TLS | `openssl s_client` |
| L5 Session | Данные | RPC, SOCKS | — |
| L4 Transport | Сегмент | TCP, UDP | `ss -tulnp`, `nc -zv` |
| L3 Network | Пакет | IP, ICMP | `ip route`, `ping`, `traceroute` |
| L2 Data Link | Кадр | Ethernet, ARP | `ip neigh`, `ip link` |
| L1 Physical | Бит | — | `ip link`, `ethtool` |

## 🧠 Что запомнить

1. 7 уровней OSI: Физический, Канальный, Сетевой, Транспортный, Сеансовый, Представления,
   Прикладной. Реально работает 4-уровневый TCP/IP.
2. Инкапсуляция: каждый уровень **добавляет свой заголовок** к данным верхнего уровня.
3. Единицы: биты → кадр → пакет → сегмент → данные.
4. L3 — это IP и маршрутизация «между сетями», L2 — доставка «внутри сети» по MAC.
5. L4 — порты: одно приложение на хосте отличается от другого именно портом.
6. Соединение однозначно определяется пятёркой: протокол + два IP + два порта.
7. Диагностику ведут **снизу вверх**: линк → MAC → IP → порт → приложение.
8. L4-балансировка знает только IP:порт, L7 — видит URL и заголовки. В k8s это Service vs Ingress.
9. Порты 0-1023 требуют root; исходящие соединения берут эфемерный порт.
10. Знать наизусть: 22, 53, 80, 443, 5432, 6379, 3306, 6443.

### Блок A. Теория

**A1.** Назови все 7 уровней OSI снизу вверх и единицу данных на каждом.

<details><summary>Ответ</summary>

L1 Физический (биты), L2 Канальный (кадры), L3 Сетевой (пакеты), L4 Транспортный
(сегменты), L5 Сеансовый, L6 Представления, L7 Прикладной (данные).

</details>

**A2.** Что такое инкапсуляция? Опиши путь HTTP-запроса вниз по стеку.

<details><summary>Ответ</summary>

Каждый уровень добавляет свой заголовок к данным верхнего: HTTP-запрос → TCP-сегмент
(порты, seq/ack) → IP-пакет (src/dst IP, TTL) → Ethernet-кадр (src/dst MAC, FCS) → биты в среде.
На приёмной стороне заголовки снимаются в обратном порядке (декапсуляция).

</details>

**A3.** Чем модель TCP/IP отличается от OSI? Какие уровни OSI схлопнуты?

<details><summary>Ответ</summary>

TCP/IP — 4 уровня: Network Access (L1+L2), Internet (L3), Transport (L4),
Application (L5+L6+L7). Это реально реализованный стек; OSI — эталонная модель для описания.

</details>

**A4.** На каком уровне работают: HTTP, TCP, IP, Ethernet, ARP, TLS, DNS, ICMP, SSH?

<details><summary>Ответ</summary>

HTTP — L7; TCP — L4; IP — L3; Ethernet — L2; ARP — между L2 и L3 (обычно относят к L2);
TLS — L6 (практически «между L4 и L7»); DNS — L7 (поверх UDP/TCP 53); ICMP — L3; SSH — L7.

</details>

**A5.** Какие устройства работают на L2, L3 и L7?

<details><summary>Ответ</summary>

L2 — свитч, сетевая карта, мост (bridge в Docker); L3 — маршрутизатор, L3-свитч,
firewall с маршрутизацией; L7 — reverse proxy и балансировщик (nginx, HAProxy в mode http),
WAF, API gateway, Ingress-контроллер.

</details>

**A6.** Что такое 5-tuple и зачем он нужен?

<details><summary>Ответ</summary>

Пятёрка «протокол + IP источника + порт источника + IP назначения + порт назначения»
однозначно идентифицирует соединение. Благодаря ей на один серверный порт можно открыть
тысячи соединений от разных клиентов, а NAT и conntrack умеют разводить трафик обратно.

</details>

**A7.** Чем отличаются диапазоны портов 0-1023, 1024-49151, 49152-65535?

<details><summary>Ответ</summary>

0-1023 — well-known, за ними закреплены стандартные сервисы и нужны привилегии;
1024-49151 — зарегистрированные за приложениями; 49152-65535 — эфемерные, выдаются ядром
для исходящих соединений.

</details>

**A8.** Почему для запуска на порту 80 нужен root, а на 8080 — нет? Как это обходят?

<details><summary>Ответ</summary>

Исторически привязка к портам < 1024 требует `CAP_NET_BIND_SERVICE` (обычно у root) —
чтобы обычный пользователь не подменил системный сервис. Обходы: запуск под root с
последующим `drop privileges` (так делает nginx), `setcap cap_net_bind_service=+ep /path/bin`,
проброс порта через iptables/`authbind`, `sysctl net.ipv4.ip_unprivileged_port_start`.

</details>

**A9.** В чём разница L4- и L7-балансировки? Приведи по два примера.

<details><summary>Ответ</summary>

L4 видит только IP и порт, просто проксирует поток TCP/UDP — быстро, но без знания
о содержимом (HAProxy `mode tcp`, AWS NLB, IPVS). L7 разбирает HTTP: маршрутизация по пути
и заголовкам, терминация TLS, ретраи, кеш (nginx, HAProxy `mode http`, ALB, Ingress).

</details>

**A10.** Что в Kubernetes соответствует L4-, а что L7-балансировке?

<details><summary>Ответ</summary>

Service (ClusterIP/NodePort/LoadBalancer) — L4; Ingress/Gateway API — L7.

</details>

**A11.** Назови порты: SSH, DNS, HTTP, HTTPS, PostgreSQL, Redis, MySQL, Kubernetes API, etcd.

<details><summary>Ответ</summary>

SSH 22, DNS 53, HTTP 80, HTTPS 443, PostgreSQL 5432, Redis 6379, MySQL 3306,
Kubernetes API 6443, etcd 2379 (клиент) и 2380 (peer).

</details>

**A12.** Почему диагностику ведут снизу вверх, а не наоборот?

<details><summary>Ответ</summary>

Нижние уровни проверяются за секунды и являются условием работы верхних:
бессмысленно дебажить HTTP, если нет линка или маршрута. Так исключаются целые классы причин.

</details>

### Блок B. «Определи уровень»

Для каждого симптома скажи, на каком уровне проблема и какой командой проверять:

**B1.** `ip link` показывает `state DOWN`

<details><summary>Ответ</summary>

L1/L2 — нет линка или интерфейс выключен: `ip link set eth1 up`, проверить кабель/vSwitch.

</details>

**B2.** `ping 192.168.56.11` → `Destination Host Unreachable`, сосед в той же подсети

<details><summary>Ответ</summary>

L2/L3 — ARP не резолвится: `ip neigh`, `tcpdump -n arp`, проверить маску и VLAN.

</details>

**B3.** `ping 8.8.8.8` работает, `ping google.com` — нет

<details><summary>Ответ</summary>

L7/DNS — резолвинг: `dig`, `/etc/resolv.conf`, `systemd-resolved`.

</details>

**B4.** `telnet host 5432` → `Connection refused`

<details><summary>Ответ</summary>

L4 — порт закрыт, на нём никто не слушает: `ss -tlnp` на сервере (RST в ответ).

</details>

**B5.** `telnet host 5432` → висит и отваливается по таймауту

<details><summary>Ответ</summary>

L3/L4 — пакеты не доходят: файрвол/security group с DROP, неверный маршрут.

</details>

**B6.** `curl https://site` → `SSL certificate problem: certificate has expired`

<details><summary>Ответ</summary>

L6/L7 — TLS: истёк сертификат, неверное время на клиенте или неполная цепочка.

</details>

**B7.** `curl http://site` → `502 Bad Gateway`

<details><summary>Ответ</summary>

L7 — прокси не смог достучаться до бэкенда: смотреть upstream и логи nginx.

</details>

**B8.** `curl http://site` → `404 Not Found`

<details><summary>Ответ</summary>

L7 — приложение ответило: сеть в порядке, проблема в маршруте/конфиге приложения.

</details>

**B9.** ping идёт, ssh подключается, а большой файл по scp зависает на 20%

<details><summary>Ответ</summary>

L3 — MTU/фрагментация (Path MTU Discovery заблокирован ICMP): классика VPN и туннелей.

</details>

**B10.** `ip neigh` показывает `FAILED` для соседа

<details><summary>Ответ</summary>

L2 — сосед не отвечает на ARP: выключен, не в той сети, неверная маска, порт свитча.

</details>

**B11.** Чем отличаются «Connection refused» и «Connection timed out» с точки зрения уровней
и что каждая ошибка говорит о причине?

<details><summary>Ответ</summary>

«Connection refused» — TCP RST от **хоста**: пакеты дошли (L3 и L4 работают),
но на порту никто не слушает или порт явно отвергается (`REJECT`). «Connection timed out» —
ответа нет вообще: пакеты теряются по пути или тихо отбрасываются (`DROP` на файрволе,
неверный маршрут, security group). Первое — проблема сервиса, второе — сети/фильтрации.

</details>

### Блок C. Практика

**C1. Инкапсуляция глазами.** Запусти `sudo tcpdump -i any -n -e -c 5 icmp` и одновременно
пингани соседа. Разбери одну строку вывода: где MAC, где IP, где тип ICMP.

<details><summary>Ответ</summary>

В строке `tcpdump -e` видно: `aa:bb:cc... > dd:ee:ff...` — MAC источника и назначения (L2),
`ethertype IPv4` — тип вложенного протокола, `192.168.56.10 > 192.168.56.11` — IP (L3),
`ICMP echo request, id …, seq …` — L3-полезная нагрузка (ICMP).

</details>

**C2. Карта своей машины по уровням.** Напиши скрипт `netinfo.sh`, который печатает отчёт:
L1/L2 (интерфейсы, состояние, MAC), L3 (адреса, маршруты, шлюз), L4 (слушающие порты),
L7 (DNS-серверы, доступность 8.8.8.8 и example.com).

<details><summary>Ответ</summary>

```bash
#!/usr/bin/env bash
set -euo pipefail
echo "=== L1/L2 ==="; ip -brief link
echo "--- ARP ---";   ip neigh
echo "=== L3 ==="; ip -brief addr; ip route
echo "=== L4 ==="; ss -tlnp 2>/dev/null | head -20
echo "=== L7 ==="; grep -H nameserver /etc/resolv.conf
ping -c1 -W1 8.8.8.8 >/dev/null && echo "IP-связность: ok" || echo "IP-связность: НЕТ"
getent hosts example.com >/dev/null && echo "DNS: ok" || echo "DNS: НЕТ"
```

</details>

**C3. Порты.** Найди в системе: все слушающие TCP-порты с именами процессов,
все установленные соединения, все UDP-сокеты. Определи, какой процесс занял порт 22.

<details><summary>Ответ</summary>

`ss -tlnp` (слушающие TCP), `ss -tan state established`, `ss -ulnp` (UDP),
`ss -tlnp 'sport = :22'` или `lsof -i :22` — процесс на 22-м порту.

</details>

**C4. Эфемерные порты.** Посмотри диапазон (`sysctl net.ipv4.ip_local_port_range`),
открой соединение (`curl example.com`) и поймай в `ss` исходящий порт.

<details><summary>Ответ</summary>

`sysctl net.ipv4.ip_local_port_range` → обычно `32768 60999`.
`curl -s example.com >/dev/null & ss -tan | grep :80` покажет локальный порт из этого диапазона.

</details>

**C5. Привилегированные порты.** Попробуй от обычного пользователя поднять
`python3 -m http.server 80`, посмотри ошибку. Затем подними на 8080 и пробрось 80→8080
через iptables (тема 11) или `CAP_NET_BIND_SERVICE`.

<details><summary>Ответ</summary>

Ошибка `Permission denied` (bind к привилегированному порту).
Варианты: `sudo setcap 'cap_net_bind_service=+ep' $(which python3)` (осторожно — на интерпретатор
так делать не стоит), проброс `iptables -t nat -A PREROUTING -p tcp --dport 80 -j REDIRECT --to-port 8080`,
`sysctl -w net.ipv4.ip_unprivileged_port_start=80` или запуск за nginx.

</details>

**C6. Диагностика по уровням.** По очереди «ломай» и восстанавливай, каждый раз фиксируя,
как симптом выглядит и на каком шаге алгоритма ловится:
1. `ip link set eth1 down`;
2. удалить маршрут по умолчанию;
3. вписать нерабочий DNS в `/etc/resolv.conf`;
4. остановить nginx, оставив порт закрытым.

<details><summary>Ответ</summary>

Симптомы: (1) `ip link` → DOWN, пинг соседа не идёт вообще; (2) `ping 8.8.8.8` →
Network is unreachable, локальная сеть работает; (3) `ping google.com` → Temporary failure
in name resolution, при этом `ping 8.8.8.8` идёт; (4) `nc -zv host 80` → Connection refused,
пинг идёт. Каждый симптом однозначно указывает на свой уровень.

</details>

### Блок D. Инциденты

**D1.** Приложение в контейнере не может достучаться до БД. `ping db` идёт, `nc -zv db 5432`
даёт Connection refused. Какой уровень и что проверять дальше?

<details><summary>Ответ</summary>

L4: ICMP проходит (L3 в порядке), но TCP-порт отвечает RST — значит, БД не слушает
на этом адресе (слушает только 127.0.0.1), не запущена, или порт не тот. Проверить
`ss -tlnp` в контейнере БД, `listen_addresses` в postgresql.conf, сеть Docker/Compose.

</details>

**D2.** Пользователи жалуются: сайт «то открывается, то нет». `ping` до сервера — 0% потерь,
`curl` иногда висит. С чего начать и почему?

<details><summary>Ответ</summary>

Перемежающаяся проблема — смотреть не «работает/не работает», а статистику:
потери и джиттер (`mtr -n host` длительно), ретрансмиссии TCP (`ss -ti`, `netstat -s | grep
retrans`), загрузку канала (`iftop`), а также балансировщик: возможно, один из бэкендов мёртв,
и «не открывается» — это попадание на него.

</details>

**D3.** После смены провайдера перестали ходить большие ответы от API, маленькие работают.
Какой уровень и какая классическая причина?

<details><summary>Ответ</summary>

L3, MTU: путь стал с меньшим MTU (PPPoE/VPN/туннель), а ICMP «Fragmentation needed»
блокируется — Path MTU Discovery ломается, большие пакеты пропадают. Лечится уменьшением MTU,
`tcp_mss_clamp` на шлюзе или разрешением нужных ICMP.

</details>

**D4.** Сетевик говорит «у нас всё работает, проблема на вашей стороне». Какие три факта
с разных уровней ты соберёшь, чтобы разговор стал предметным?

<details><summary>Ответ</summary>

(1) L3: `mtr -rwc 100` с потерями по хопам и их местом; (2) L4: `nc -zv`/`ss` — порт
открыт или RST/таймаут, и `tcpdump` с обеих сторон (ушёл ли SYN, пришёл ли ответ);
(3) L7: `curl -v` с кодом ответа и временем, плюс логи сервиса. Конкретика превращает
«не работает» в «SYN уходит, SYN-ACK не возвращается — потери на хопе X».

</details>

### Блок E. Вопросы с собеседования

**1.** Назови все уровни модели OSI.

<details><summary>Ответ</summary>

Физический, канальный, сетевой, транспортный, сеансовый, представления, прикладной.

</details>

**2.** На каком уровне работает HTTP? А TLS? А ARP?

<details><summary>Ответ</summary>

HTTP — L7; TLS — L6 (между транспортом и приложением); ARP — L2 (на стыке с L3).

</details>

**3.** Что такое инкапсуляция?

<details><summary>Ответ</summary>

Добавление собственного заголовка каждым уровнем при движении данных вниз по стеку.

</details>

**4.** Чем OSI отличается от TCP/IP?

<details><summary>Ответ</summary>

OSI — эталонная 7-уровневая модель, TCP/IP — реальный 4-уровневый стек.

</details>

**5.** Что такое порт и зачем он нужен?

<details><summary>Ответ</summary>

Число, идентифицирующее приложение на хосте; вместе с IP и протоколом задаёт сокет.

</details>

**6.** Чем L4-балансировка отличается от L7?

<details><summary>Ответ</summary>

L4 работает с IP и портами (быстро, «не понимает» HTTP), L7 разбирает запрос и умеет
роутить по URL/заголовкам, терминировать TLS, кешировать.

</details>

**7.** Как понять, на каком уровне проблема?

<details><summary>Ответ</summary>

Проверять снизу вверх: линк → ARP → IP/маршрут → порт → DNS → приложение.

</details>

**8.** Какие порты ты знаешь наизусть?

<details><summary>Ответ</summary>

22, 53, 80, 443, 3306, 5432, 6379, 6443, 9090, 2379.

</details>
