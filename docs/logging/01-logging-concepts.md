## 🗺️ Путь лога от приложения до инженера

```text:no-line-numbers
 ┌────────────┐   пишет      ┌──────────────┐   читает   ┌───────────────┐
 │ приложение │─────────────►│ stdout /файл │───────────►│  СБОРЩИК      │
 │            │  строку лога │ /journald    │  tail      │ Alloy /       │
 └────────────┘              └──────────────┘            │ Fluent Bit /  │
                                                         │ Filebeat      │
                                                         └───────┬───────┘
                                       парсинг, лейблы, буферизация│
                                                                  ▼
                                                    ┌──────────────────────┐
                                                    │ ХРАНИЛИЩЕ            │
                                                    │ Loki / Elasticsearch │
                                                    └──────────┬───────────┘
                                                               ▼
                                                  ┌────────────────────────┐
                                                  │ ИНТЕРФЕЙС: Grafana /   │
                                                  │ Kibana → поиск, алерты │
                                                  └────────────────────────┘
```

Четыре части, которые надо различать: **источник → сборщик → хранилище → интерфейс**.
Почти любой вопрос «почему логов нет» решается движением по этой цепочке слева направо.

## 1. Уровни логирования

| Уровень | Когда пишут | Включён в проде? |
|---------|-------------|------------------|
| `TRACE` | Пошаговая детализация, дампы | Нет |
| `DEBUG` | Отладочные детали разработчика | Нет (временно — при разборе) |
| `INFO` | Штатные события: старт, конфиг, обработанный запрос | Да |
| `WARN` | Странно, но работаем: ретрай, деградация, устаревший API | Да |
| `ERROR` | Операция не выполнена, нужен разбор | Да |
| `FATAL`/`PANIC` | Сервис не может продолжать работу | Да |

```text:no-line-numbers
DEBUG в проде = ×10-100 к объёму логов и к счёту за хранение.
Правильный приём: уровень задаётся переменной окружения (LOG_LEVEL) и меняется
без пересборки — чтобы можно было временно включить DEBUG на одном поде.
```

## 2. Текстовые vs структурированные логи

```text:no-line-numbers
ТЕКСТОВЫЙ (человекочитаемый)
2026-09-13 14:03:22 ERROR Failed to process order 12345 for user ivan: timeout after 30s

СТРУКТУРНЫЙ (JSON) ⭐
{"ts":"2026-09-13T14:03:22Z","level":"error","msg":"failed to process order",
 "order_id":12345,"user":"ivan","error":"timeout","duration_ms":30000,
 "service":"billing","trace_id":"7f3c9a1b","env":"prod"}
```

| | Текстовый | Структурный |
|---|-----------|-------------|
| Читать глазами | ✅ | Хуже (но Grafana/Kibana разворачивают в таблицу) |
| Поиск по полю | Регулярками, больно | ✅ `order_id=12345` |
| Агрегация («сколько таймаутов за час») | Почти невозможно | ✅ |
| Парсинг сборщиком | Нужны regex/grok | ✅ Уже разобран |

Правило: **приложение пишет JSON в stdout**, а красивое человекочитаемое представление
делает интерфейс (Grafana/Kibana) или локальный вывод в dev-режиме.

Обязательные поля хорошего лога:
```text:no-line-numbers
ts (ISO8601, UTC) · level · msg · service · env · version
+ контекст: request_id / trace_id, user_id (если допустимо), duration, коды ошибок
```

⭐ `trace_id` — то, что связывает записи одного запроса через десяток сервисов.
Без него в микросервисах разбор инцидента превращается в археологию.

## 3. Что логировать — и что категорически нельзя

| Логировать | Не логировать ⚠️ |
|------------|------------------|
| Старт/остановку, версию, применённый конфиг (без секретов) | Пароли, токены, ключи, cookie/сессии |
| Входящие запросы: метод, путь-шаблон, код, длительность | Полные тела запросов с персональными данными |
| Ошибки со стектрейсом и контекстом | Номера карт, CVV, паспортные данные |
| Обращения к внешним системам: адрес, код, время | Содержимое писем, сообщений, документов |
| Бизнес-события: заказ создан, платёж проведён | Персональные данные без юридического основания |
| Изменения доступа и админ-действия (аудит) | «Логи ради логов» в цикле на каждый шаг |

```text:no-line-numbers
Секрет, попавший в лог, считается скомпрометированным.
Порядок действий тот же, что при утечке: ротация секрета → чистка хранилища → разбор.
Профилактика: маскирование на стороне приложения + правила фильтрации в сборщике.
```

## 4. Объём, retention и деньги

```text:no-line-numbers
Оценка «на салфетке»:
  100 запросов/с × 1 лог-строка × 500 байт = 50 КБ/с ≈ 4 ГБ/сутки ≈ 130 ГБ/месяц
  DEBUG вместо INFO → ×10 → 1,3 ТБ/месяц
  Elasticsearch с индексами и репликой → ×2-3 к сырому объёму
```

| Приём | Эффект |
|-------|--------|
| Уровень INFO в проде | Основная экономия |
| Структурные логи без дублирования | Меньше «воды» в строке |
| Sampling (писать 1 из N успешных запросов) | Сильно режет объём при сохранении картины |
| Разный retention по типам | Аудит — 1 год, прикладные — 14-30 дней, debug — 3 дня |
| Сжатие и «холодное» хранилище (S3) | Дёшево хранить долго |
| Метрики вместо логов для счётного | «Сколько ошибок» — это метрика, а не 10 млн строк |

Типовой retention: **7-30 дней «горячих»** логов для поиска + архив в объектном
хранилище на 90-365 дней (аудит и безопасность — по требованиям регуляторов).

## 5. Ротация локальных файлов (то, что ломает диск)

```bash
# logrotate — классика для файлов приложений
cat /etc/logrotate.d/myapp
```
```text:no-line-numbers
/var/log/myapp/*.log {
    daily
    rotate 7
    compress
    delaycompress
    missingok
    notifempty
    copytruncate        # если приложение не умеет переоткрывать файл
}
```
```json
// docker: ограничение размера логов контейнеров — /etc/docker/daemon.json
{
  "log-driver": "json-file",
  "log-opts": { "max-size": "100m", "max-file": "3" }
}
```
> ⚠️ Без этих настроек логи докера растут бесконечно и однажды забивают диск —
> один из самых частых инцидентов у начинающих команд.

## 6. Корреляция: как связать логи, метрики и трейсы

```text:no-line-numbers
Алерт: доля 5xx выросла в 14:03           (метрика)
  │
  ├─► открыл логи с фильтром по времени и сервису   (логи)
  │     нашёл: "connection refused to db:5432"
  │
  ├─► взял trace_id из строки                       (трейс)
  │     увидел: билинг ждал базу 30 секунд
  │
  └─► посмотрел аннотацию деплоя                    (Grafana annotation)
        в 14:01 выкатили миграцию
```

Чтобы это работало, нужны три вещи:
1. **Единые лейблы**: `service`, `env`, `instance` одинаково называются в метриках и логах.
2. **`trace_id` в каждой строке** (пробрасывается через заголовки между сервисами).
3. **Одно окно для просмотра**: Grafana с источниками Prometheus + Loki (+ Tempo).

## 7. Типовые проблемы

| Проблема | Причина | Решение |
|----------|---------|---------|
| Логи есть, найти ничего нельзя | Неструктурированный текст без полей | JSON + обязательные поля |
| Логи потерялись при падении пода | Читали файл внутри контейнера | stdout + сборщик на ноде |
| Диск забит логами | Нет ротации/лимитов драйвера | logrotate, `max-size`, retention |
| Стектрейс разорван на 30 строк | Не настроен multiline | Правила multiline в сборщике |
| Логи приходят с задержкой в часы | Буфер/бэкпрешер в сборщике | Настройка буферов, масштабирование хранилища |
| Секреты в логах | Нет маскирования | Фильтры в приложении и сборщике |
| Время в логах «плавает» | Локальные таймзоны, нет NTP | UTC + ISO8601 + синхронизация времени |
| Хранилище съело весь бюджет | Нет retention и sampling | Уровни, ILM, архив в S3 |

## 💼 Как это в DevOps

- Девопс отвечает за **конвейер**: сбор, доставку, хранение, доступ и retention;
  за содержимое строк — разработчики, но требования к формату задаёт девопс.
- Первое требование к новому сервису: логи в **stdout**, в **JSON**, с полями
  `service`, `env`, `level`, `trace_id`. Это дешевле внедрить сразу, чем переделывать.
- Доступ к логам дают разработчикам через Grafana/Kibana, а не по SSH на прод —
  это одновременно удобство и безопасность.
- Контроль расходов — часть работы: объём логов растёт быстрее всего остального,
  и именно он внезапно превращается в счёт.
- На собесе спрашивают не «как поднять Elasticsearch», а: чем отличаются стек ELK и Loki,
  откуда берутся логи в k8s, что нельзя логировать, как связать логи с метриками.

## 📌 Шпаргалка

| Термин | Одной строкой |
|--------|---------------|
| Уровни | TRACE/DEBUG/INFO/WARN/ERROR/FATAL; в проде — с INFO |
| Структурные логи | JSON с полями вместо свободного текста |
| Обязательные поля | ts, level, msg, service, env, version, trace_id |
| trace_id | Связывает записи одного запроса между сервисами |
| Сборщик | Alloy, Fluent Bit, Filebeat, Fluentd, Vector (Promtail — EOL с 02.03.2026) |
| Хранилище | Loki (лейблы) или Elasticsearch (полнотекст) |
| Retention | Горячие 7-30 дней + архив 90-365 дней |
| Sampling | Писать часть однотипных успешных событий |
| Multiline | Склейка стектрейсов в одну запись |
| Ротация | logrotate, `max-size`/`max-file` у docker |
| Маскирование | Удаление секретов и ПДн до отправки |
| Корреляция | Единые лейблы + trace_id + общий интерфейс |

## 🧠 Что запомнить

1. Цепочка «источник → сборщик → хранилище → интерфейс» объясняет почти все проблемы с логами.
2. Уровень логирования в проде — INFO; DEBUG включают точечно и временно.
3. ⭐ Структурные логи (JSON) в stdout — единственный формат, с которым удобно работать
   в централизованной системе.
4. Обязательные поля: время в UTC, уровень, сообщение, сервис, окружение, версия, trace_id.
5. Секреты и персональные данные в логи не попадают никогда; попавший секрет — скомпрометирован.
6. Объём логов — это деньги: retention, уровни, sampling и архив в объектном хранилище.
7. Без ротации (`logrotate`, `max-size` докера) логи забивают диск — классический инцидент.
8. Стектрейсы требуют настройки multiline, иначе разваливаются на десятки записей.
9. Счётные вещи («сколько ошибок») — это метрики, а не поиск по логам.
10. Логи ценны вместе с метриками и трейсами: единые лейблы и `trace_id` связывают картину.

### Блок A. Теория

**A1.** Нарисуй цепочку «от строки лога до инженера» и назови каждое звено.

<details><summary>Ответ</summary>

Источник (приложение → stdout/файл/journald) → сборщик (Alloy, Fluent Bit,
Filebeat) → хранилище (Loki, Elasticsearch) → интерфейс (Grafana, Kibana) с поиском
и алертами.

</details>

**A2.** Перечисли уровни логирования и скажи, какие включены в проде.

<details><summary>Ответ</summary>

TRACE, DEBUG, INFO, WARN, ERROR, FATAL. В проде — от INFO и выше.

</details>

**A3.** Почему DEBUG в проде — дорогое удовольствие? Как включить его временно и правильно?

<details><summary>Ответ</summary>

Объём растёт в 10-100 раз: диск, трафик, стоимость хранения и индексации, плюс
замедление самого приложения. Правильно — уровень через переменную окружения
(`LOG_LEVEL`), включать точечно на одном инстансе и на ограниченное время.

</details>

**A4.** ⭐ Чем структурированные логи лучше текстовых? Назови четыре преимущества.

<details><summary>Ответ</summary>

Поиск по конкретным полям; агрегация и подсчёты; не нужен хрупкий парсинг
регулярками; единый формат для всех сервисов и удобные фильтры в интерфейсе.

</details>

**A5.** Какие поля обязаны быть в каждой строке лога?

<details><summary>Ответ</summary>

Время (UTC, ISO8601), уровень, сообщение, сервис, окружение, версия, идентификатор
запроса/трейса; плюс контекст события.

</details>

**A6.** Что такое `trace_id` и зачем он в микросервисах?

<details><summary>Ответ</summary>

Идентификатор запроса, который пробрасывается через все сервисы в заголовках.
Позволяет собрать все записи одного пользовательского запроса из десятка сервисов.

</details>

**A7.** Назови шесть вещей, которые нельзя писать в логи.

<details><summary>Ответ</summary>

Пароли, токены и ключи, cookie/сессии, номера карт и CVV, персональные данные
без основания, содержимое пользовательских сообщений и документов.

</details>

**A8.** Что делать, если пароль попал в лог?

<details><summary>Ответ</summary>

Считать секрет скомпрометированным: ротация секрета, затем чистка/ограничение
доступа к хранилищу логов, проверка, кто мог видеть, добавление маскирования, разбор
инцидента.

</details>

**A9.** Посчитай объём логов: 200 запросов/с, одна строка 600 байт. Сколько в сутки и в месяц?

<details><summary>Ответ</summary>

200 × 600 Б = 120 КБ/с ≈ 10 ГБ/сутки ≈ 300 ГБ/месяц сырых; с индексами
Elasticsearch — в 2-3 раза больше.

</details>

**A10.** Какие есть способы уменьшить объём логов без потери пользы?

<details><summary>Ответ</summary>

Уровень INFO, sampling однотипных успешных событий, отказ от «логов ради логов»,
перенос счётных данных в метрики, компактный формат, разный retention, сжатие и архив в S3.

</details>

**A11.** Какой retention считается типовым и почему он разный для разных типов логов?

<details><summary>Ответ</summary>

Горячие 7-30 дней для поиска, архив 90-365 дней; аудит и безопасность хранят
дольше по требованиям, отладочные — совсем недолго, потому что они самые объёмные.

</details>

**A12.** Зачем нужен logrotate, если есть централизованное логирование?

<details><summary>Ответ</summary>

Потому что локальные файлы всё равно существуют (до отправки, при недоступности
хранилища, для системных сервисов) и без ротации забивают диск.

</details>

**A13.** Что будет с диском, если не настроить `max-size` у docker-драйвера логов?

<details><summary>Ответ</summary>

Файлы `*-json.log` растут неограниченно и заполняют диск ноды; контейнеры
и сам docker начинают падать.

</details>

**A14.** Что такое multiline и почему без него стектрейсы бесполезны?

<details><summary>Ответ</summary>

Склейка многострочных сообщений (стектрейсов) в одну запись. Без неё каждая
строка трейса — отдельное событие без контекста, поиск и алерты по ним бесполезны.

</details>

**A15.** Что нужно, чтобы связать метрику, лог и трейс одного инцидента?

<details><summary>Ответ</summary>

Единые лейблы (`service`, `env`, `instance`), `trace_id` в каждой строке,
единый интерфейс (Grafana с Prometheus + Loki + Tempo) и синхронизированное время.

</details>

### Блок B. «Оцени строку/решение»

```text:no-line-numbers
B1.  2026-09-13 14:03:22 ERROR something went wrong
```

<details><summary>Ответ</summary>

Бесполезная строка: нет сервиса, контекста, идентификаторов, непонятно что произошло.

</details>

```text:no-line-numbers
B2.  {"ts":"2026-09-13T14:03:22Z","level":"error","msg":"db timeout",
      "service":"billing","env":"prod","trace_id":"7f3c","duration_ms":30000}
```

<details><summary>Ответ</summary>

Эталон: структурно, есть сервис, окружение, трейс и длительность.

</details>

```text:no-line-numbers
B3.  {"level":"info","msg":"user login","password":"qwerty123"}
```

<details><summary>Ответ</summary>

⚠️ Пароль в логе — инцидент безопасности.

</details>

```text:no-line-numbers
B4.  {"level":"debug","msg":"loop iteration","i":45231}
```

<details><summary>Ответ</summary>

Лог в цикле: колоссальный объём без пользы; такое место для метрики или DEBUG.

</details>

```text:no-line-numbers
B5.  logger.info(f"Request body: {request.json}")      # платёжный сервис
```

<details><summary>Ответ</summary>

⚠️ Тело запроса платёжного сервиса содержит ПДн и платёжные данные.

</details>

```text:no-line-numbers
B6.  Приложение пишет логи в /app/logs/app.log внутри контейнера
```

<details><summary>Ответ</summary>

Логи внутри контейнера исчезнут вместе с ним; нужно писать в stdout.

</details>

```text:no-line-numbers
B7.  LOG_LEVEL=DEBUG на проде «чтобы было удобнее»
```

<details><summary>Ответ</summary>

DEBUG на проде постоянно — рост объёма и риск утечки деталей; допустим временно
и точечно.

</details>

```text:no-line-numbers
B8.  Логи приложения только на русском, без кодов ошибок
```

<details><summary>Ответ</summary>

Логи без кодов ошибок и на одном языке хуже поддаются автоматической обработке
и поиску; сообщения лучше делать машинно-стабильными (код + поля), а текст — пояснением.

</details>

```text:no-line-numbers
B9.  Время в логах в локальной таймзоне сервера
```

<details><summary>Ответ</summary>

Локальные таймзоны ломают сопоставление событий между серверами; нужен UTC.

</details>

```text:no-line-numbers
B10. Retention: всё хранится вечно «на всякий случай»
```

<details><summary>Ответ</summary>

«Хранить всё вечно» — прямой рост затрат и юридические риски по ПДн.

</details>

```text:no-line-numbers
B11. Docker без log-opts, приложение пишет 5 ГБ логов в сутки
```

<details><summary>Ответ</summary>

Диск забьётся; нужны `max-size`/`max-file` или другой драйвер.

</details>

```text:no-line-numbers
B12. Метрика «число ошибок» считается ежедневным grep по логам
```

<details><summary>Ответ</summary>

Счётные показатели должны быть метриками: grep по логам дорог, медленен
и не даёт алертов в реальном времени.

</details>

### Блок C. Практика

#### C1. Уровни на практике
1. Запусти приложение (или скрипт), пишущее логи разных уровней.
2. Сравни объём вывода при `LOG_LEVEL=INFO` и `DEBUG` за минуту.
3. Сделай уровень настраиваемым через переменную окружения.

#### C2. 🔑 Структурный лог
Напиши скрипт, который пишет в stdout JSON-логи с полями
`ts, level, msg, service, env, version, trace_id, duration_ms`.
Прогони через `jq` и научись фильтровать: `jq 'select(.level=="error")'`.

<details><summary>Ответ</summary>

`jq 'select(.level=="error") | {ts, msg, trace_id}'` — типичный рабочий фильтр.

</details>

#### C3. Ротация файлов
1. Настрой logrotate для файла приложения: 7 дней, сжатие, `copytruncate`.
2. Запусти принудительно (`logrotate -f`) и проверь результат.
3. Объясни разницу `copytruncate` и обычной ротации.

<details><summary>Ответ</summary>

`copytruncate` копирует файл и обрезает исходный — нужен, если приложение
держит файл открытым и не умеет переоткрывать его по сигналу; минус — возможна потеря
нескольких строк в момент ротации.

</details>

#### C4. Ограничение логов докера
1. Посмотри размер `/var/lib/docker/containers/*/*-json.log`.
2. Настрой `max-size` и `max-file` в `daemon.json`, перезапусти докер.
3. Проверь, что ротация работает (нагенерируй логов).

#### C5. Секреты в логах
1. Намеренно залогируй «токен» в тестовом приложении.
2. Напиши фильтр (в приложении или через `sed` в конвейере), который маскирует его.
3. Опиши порядок действий, если такой лог уже уехал в хранилище.

<details><summary>Ответ</summary>

Маскирование лучше делать в приложении (до записи), фильтр в сборщике —
вторая линия защиты.

</details>

#### C6. Объём и деньги
Посчитай для своего стенда: строк в секунду, средний размер строки, объём за сутки,
за месяц, с учётом ×2 на индексы. Запиши, какой retention ты бы выбрал.

#### C7. Multiline
1. Сгенерируй Python/Java-стектрейс в логах.
2. Посмотри, как он выглядит построчно в `docker logs`.
3. Сформулируй правило склейки (например, строки, начинающиеся с пробела —
   продолжение предыдущей).

<details><summary>Ответ</summary>

Правило multiline обычно опирается на признак начала новой записи
(дата в начале строки или `{`), всё остальное считается продолжением.

</details>

#### C8. Корреляция руками
Добавь `trace_id` в логи двух «сервисов» (двух скриптов, вызывающих друг друга),
прокинь его через заголовок и найди обе строки по одному идентификатору.

#### C9. Метрики вместо логов
Возьми задачу «сколько ошибок было за час» и реализуй её двумя способами:
grep по логам и counter в Prometheus. Сравни удобство и стоимость.

<details><summary>Ответ</summary>

Метрика отвечает мгновенно и даёт алерты; grep по логам требует хранения
и сканирования больших объёмов.

</details>

#### C10. Требования к логированию
Напиши памятку для разработчиков на одну страницу: формат, обязательные поля,
уровни, что нельзя логировать, как называть сервисы. Это реальный рабочий артефакт девопса.

### Блок D. Инциденты

**D1.** Диск на 90% занят логами. Что проверишь и что настроишь?

<details><summary>Ответ</summary>

`du -sh /var/log/*`, размер логов докера, ротация и `max-size`, размеры файлов
приложений, уровень логирования; настроить logrotate и лимиты драйвера, при
необходимости уменьшить retention.

</details>

**D2.** Под упал, логи причины пропали. Почему и как исправить архитектурно?

<details><summary>Ответ</summary>

Логи писались в файл внутри контейнера и удалились вместе с ним. Правильно —
stdout + сборщик на ноде (или sidecar), который отправляет логи в централизованное
хранилище сразу.

</details>

**D3.** Стектрейс в Kibana разбит на 40 отдельных записей. Что настроить?

<details><summary>Ответ</summary>

Multiline в сборщике (Alloy `stage.multiline`, Fluent Bit `multiline.parser`,
Filebeat `multiline`), либо писать стектрейс одним JSON-полем из приложения.

</details>

**D4.** В логах прода найден токен доступа. Порядок действий.

<details><summary>Ответ</summary>

Ротация токена, проверка использования, ограничение доступа к логам,
удаление/маскирование записей там, где это возможно, добавление фильтров,
уведомление ответственных, постмортем.

</details>

**D5.** Логи приходят с задержкой в 2 часа. Где искать причину?

<details><summary>Ответ</summary>

Бэкпрешер: перегружено хранилище (Loki/ES), забиты буферы сборщика, сеть,
недостаточно ресурсов у ingester'ов, слишком большие пачки; смотреть метрики сборщика
и хранилища.

</details>

**D6.** Разработчик просит включить DEBUG на проде на неделю. Твой ответ и компромисс.

<details><summary>Ответ</summary>

Неделя DEBUG на проде — рост объёма и риск ПДн. Компромисс: DEBUG на одном
инстансе/поде, на несколько часов, с ограничением по модулю, либо добавить нужные
INFO-поля в код.

</details>

**D7.** Счёт за хранение логов вырос в 5 раз за месяц. Что смотришь?

<details><summary>Ответ</summary>

Рост трафика, включённый DEBUG, новый сервис с болтливыми логами, потеря
retention/ILM, дублирование логов двумя сборщиками, отсутствие sampling.

</details>

**D8.** По логам невозможно понять, какой сервис их написал. Что не так с форматом?

<details><summary>Ответ</summary>

Нет поля `service` (и `env`): логи разных сервисов неразличимы. Это требование
к формату, которое задаёт девопс.

</details>

**D9.** Время инцидента в метриках и в логах различается на 3 часа. Причина?

<details><summary>Ответ</summary>

Локальная таймзона вместо UTC или несинхронизированное время (нет NTP/chrony).

</details>

**D10.** Разработчикам нужен доступ к логам прода. Как организуешь?

<details><summary>Ответ</summary>

Доступ через Grafana/Kibana с разграничением по папкам/индексам и SSO,
без выдачи SSH на прод; чувствительные поля маскируются на этапе сбора.

</details>

### Блок E. Вопросы с собеседования

**1.** Зачем нужно централизованное логирование?

<details><summary>Ответ</summary>

Чтобы искать по всем сервисам в одном месте, не терять логи вместе с контейнерами,
давать доступ разработчикам без прода и хранить логи дольше жизни инстанса.

</details>

**2.** Чем логи отличаются от метрик?

<details><summary>Ответ</summary>

Метрики — агрегированные числа во времени (что и когда), логи — детальные события
(почему); логи дороже в хранении.

</details>

**3.** Какие уровни логирования знаешь и какой ставишь в проде?

<details><summary>Ответ</summary>

TRACE/DEBUG/INFO/WARN/ERROR/FATAL; в проде — INFO и выше.

</details>

**4.** Что такое структурированные логи и зачем они?

<details><summary>Ответ</summary>

Логи в машиночитаемом формате (JSON) с полями: удобны для поиска, фильтрации
и агрегации.

</details>

**5.** Какие поля должны быть в логе?

<details><summary>Ответ</summary>

Время в UTC, уровень, сообщение, сервис, окружение, версия, trace_id и контекст.

</details>

**6.** Что нельзя писать в логи?

<details><summary>Ответ</summary>

Секреты, ПДн, платёжные данные, содержимое пользовательского контента.

</details>

**7.** Как считать объём логов и управлять retention?

<details><summary>Ответ</summary>

Считать по строкам/секунду и размеру строки, умножать на индексы и репликацию;
управлять уровнями, sampling, retention, архивом.

</details>

**8.** Что такое multiline и зачем он нужен?

<details><summary>Ответ</summary>

Склейка многострочных сообщений (стектрейсов) в одну запись сборщиком.

</details>

**9.** Как связать лог с конкретным запросом пользователя?

<details><summary>Ответ</summary>

Через `trace_id`/`request_id`, пробрасываемый между сервисами.

</details>

**10.** Как не дать логам забить диск?

<details><summary>Ответ</summary>

Ротация (logrotate, `max-size`/`max-file`), лимиты, retention, отправка логов
в централизованное хранилище и алерт на заполнение диска.

</details>
