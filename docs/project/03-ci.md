# 03. CI: от коммита до образа в registry и коммита в gitops

> **Цель этапа:** пайплайн из 05-conveyor начинает работать по-настоящему на gitlab.com:
> каждый MR проверяется, каждый коммит в `main` превращается в просканированный образ
> с тегом по SHA и коммит с этим тегом в `linkd-gitops`.
>
> **После этапа у тебя есть:** `.gitlab-ci.yml` и `ci/templates/` в `linkd-platform`,
> образы в GitLab Container Registry, job доставки в gitops-репо вместо «деплоев» из
> проекта, проверки для всего содержимого репо (а не только кода), раздел «CI/CD» в README.
>
> **~время:** 4–6 часов (после проекта).

## 🎯 Цель

В 05-conveyor пайплайн проверялся локально валидатором, а «деплои» были упражнением на
`environment` и `rules`. В портфолио он должен **реально** собирать и публиковать образ
и **реально** доставлять его — через git, а не командой в кластер.

Три принципа, которые здесь становятся видны:

1. **Build once** — образ собирается один раз и дальше только перетегируется.
2. **Тег = SHA коммита** — по любому поду понятно, какой код в нём работает.
3. **CI не ходит в кластер** — он только пишет новый тег в `linkd-gitops`, деплоит
   Argo CD (этап 06). У CI нет kubeconfig, и утечка CI-переменных не даёт доступа к кластеру.

---

## 🗺️ Что получится

```text
 MR           test ─► tools-test ─► build ─► smoke(+PostgreSQL) ─► scan     (ничего не публикуем)
 main         … ─► build ─► smoke ─► scan ─► push :&lt;sha&gt; ─► bump-dev ──► linkd-gitops
                                                                          envs/dev
 тег vX.Y.Z   retag :&lt;sha&gt; → :X.Y.Z ─► bump-prod (manual, через MR) ────────────► envs/prod
 по изменённым путям:  helm-lint · terraform-validate · promtool-test · gitleaks
```text
| Событие | Что запускается | Что публикуется |
|---------|----------------|-----------------|
| MR | тесты, сборка, smoke с PostgreSQL, скан, проверки изменённых каталогов | ничего |
| push в `main` | + push, bump-dev | `:&lt;sha&gt;`, коммит в `envs/dev/values.yaml` |
| тег `vX.Y.Z` | retag, bump-prod (кнопка) | `:X.Y.Z` с тем же digest, MR в `envs/prod` |
| ветка без MR | ничего — экономим минуты | — |

## 🪜 Шаги

### 1. Проект зелёный

```bash
cd ~/Projects/devops/05-conveyor && ./check.sh
```text
### 2. Перенос

`.gitlab-ci.yml`, `ci/templates/` и `tests/` → `linkd-platform`. Пути под новую раскладку:
Dockerfile в `docker/`, код в `app/`, свои тесты в `tools/`.

Тесты из 05-conveyor написаны для linkd 1.x. API 2.0 совместим, а SQLite остаётся
режимом по умолчанию, поэтому они должны пройти и на 2.0 — проверь; если что-то упало,
это запись в журнал, а не повод править тесты наугад. Поверх проекта — интеграционный
job: собранный образ + PostgreSQL в `services`, по HTTP прогоняется smoke-сценарий из
этапа 02. Так CI проверяет режим, в котором linkd реально работает.

### 3. Настройка GitLab

1. Проекты `linkd-platform` и `linkd-gitops` публичные (кластер вытянет образ без
   `imagePullSecret`, Argo прочитает репо без кредов; приватные — см. грабли).
2. **Protected branches:** в `main` пушить напрямую нельзя, только merge.
   **Protected tags:** `v*`.
3. В `linkd-gitops` — project access token с правом записи в репозиторий и сроком
   действия; в `linkd-platform` — CI/CD-переменная с этим токеном, **protected + masked**.
4. Runner: свой из 05-conveyor или shared. Если shared runners требуют верификации
   аккаунта — свой runner снимает вопрос и заодно даёт историю для собеса.

### 4. «Деплои» из проекта → доставка через git

`deploy-dev/staging/prod` из 05-conveyor заменяются job'ами, которые **коммитят**, а не
катят. Что делает bump-job — по шагам, словами:

1. клонирует `linkd-gitops` по токену из protected-переменной;
2. меняет `image.tag` в `envs/&lt;env&gt;/values.yaml` (например, `yq`);
3. коммитит с сообщением, в котором есть SHA и ссылка на пайплайн;
4. пушит; при конфликте — `pull --rebase` и повтор, а два пайплайна не пушат одновременно
   (`resource_group`);
5. для prod — не пуш в `main`, а ветка + MR в gitops-репо: прод меняется только после ревью.

Staging из проекта: либо третье окружение в gitops, либо осознанно убран — реши
и запиши в ADR.

### 5. Что добавить поверх проекта

- **Скан образа** (Trivy) между build и push: пайплайн падает на HIGH/CRITICAL, для которых
  есть исправление; исключения — в `.trivyignore`, у каждого комментарий «почему».
  Образ сканируется **до** публикации (артефакт `image.tar` или временный репозиторий).
- **Релиз перетегированием:** на теге образ не пересобирается — берётся `:&lt;sha&gt;` этого
  коммита и получает тег версии. Проверка — digest совпадает.
- **Метки образа:** build-аргументы из этапа 02 получают SHA и версию из переменных CI.
- **Проверки всего репо**, по `rules: changes` соответствующих каталогов: тесты `tools/`,
  `helm lint`/`helm template` чарта, `terraform fmt -check` и `validate`, `promtool test rules`
  (последние два job'а появятся на этапах 04 и 07).
- **gitleaks** по истории — секрет не должен пройти даже в MR.

### 6. CI для linkd-gitops

Короткий пайплайн на каждый MR: для dev и prod — `helm template` чарта с values
окружения и проверка схемы манифестов; gitleaks. Если на этапе 06 чарт останется в
`linkd-platform`, этот job берёт его той версии, что указана в Application.

Бот коммитит в `main` — поэтому этот пайплайн не должен сам ничего коммитить
(иначе бесконечный цикл).

### 7. Проверка, что конвейер фильтрует

- ветка со сломанным тестом → MR красный, build не запускался, в registry ничего нового;
- базовый образ со старой уязвимой версией → scan красный, push не запустился;
- MR из ветки не видит protected-переменную с токеном (проверь по логу job'а, не печатая её).

### 8. Замеры и README

- время первого пайплайна и повторного (кэш зависимостей и слоёв) — в README;
- раздел «CI/CD»: схема из «Что получится», таблица событий, бейдж статуса пайплайна;
- скриншоты: зелёный граф `main` и красный пайплайн, остановленный сканом.

Соответствие для GitHub Actions — одной таблицей, без второго пайплайна:

| GitLab CI | GitHub Actions |
|-----------|----------------|
| `stages` + `needs` | `jobs` + `needs` |
| `services` | `services` |
| `CI_REGISTRY_*` | `GITHUB_TOKEN` + `permissions: packages: write` |
| protected variables | environment secrets с правилами защиты |
| `resource_group` | `concurrency` |

### 9. Коммит

```bash
git add .gitlab-ci.yml ci .trivyignore README.md
git commit -m "ci: build, scan, publish and bump image tag in linkd-gitops"
```text

## ✅ Критерии приёмки

- [ ] MR прогоняет тесты, сборку и скан и **ничего не публикует**
- [ ] Сломанный тест или скан останавливает пайплайн до push
- [ ] Коммит в `main` → образ `:&lt;короткий sha&gt;` в registry → коммит в `linkd-gitops/envs/dev/values.yaml`
- [ ] Тег `vX.Y.Z` создаёт `:X.Y.Z` с тем же digest, что `:&lt;sha&gt;`; prod меняется только через MR
- [ ] Токен для gitops — protected + masked, с ограниченным сроком; в логах секретов нет
- [ ] Job'ы для `tools/`, чарта, Terraform и правил запускаются только при изменении своих каталогов
- [ ] Повторный пайплайн быстрее первого, цифры записаны
- [ ] У CI нет kubeconfig и прав на кластер

## 🪤 Грабли

- **`docker:dind` без privileged-runner'а** — `Cannot connect to the Docker daemon`.
  Настройка своего runner'а — как в 05-conveyor.
- **`latest` в деплое.** Невозможно понять, что работает, и откат превращается в угадайку.
  В gitops — только SHA или semver.
- **`rules: changes` на тегах и первом пайплайне новой ветки** считается истинным —
  на теге запустятся все «условные» job'ы. Для тегов правила пишутся отдельно.
- **Кэш и артефакты путают.** Cache — ускорение, может пропасть. Artifact — результат,
  который гарантированно получит следующий job (`image.tar`).
- **Trivy качает базу каждый раз** — медленно и упирается в лимиты. Кэш базы между пайплайнами.
- **Приватный проект** → кластеру нужен `imagePullSecret` (deploy token на чтение registry),
  Argo — креды к репо. Оба секрета не коммитятся (этап 08).
- **Бот не может пушить в защищённый `main` gitops-репо** — либо права токена, либо
  схема «ветка + MR», как для prod.
- **Токен истёк** — пайплайн красный в день демо. Срок токена записан в календарь и в README.
- **Бесконечный цикл:** gitops-репо со своим CI, который тоже что-то коммитит.
