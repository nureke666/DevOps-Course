## 🎯 Цель

Технически сильный репозиторий с пустым README выглядит как «что-то скачано и не
доделано». Средний — с хорошим README, схемой и ADR — выглядит как работа инженера.
Оформление — не косметика: это навык документировать, который на работе нужен каждый
день (runbook'и, постмортемы, описания MR).

## 🪜 Шаги

### 1. README витрины

````markdown
# linkd-platform — платформа доставки и эксплуатации для сервиса коротких ссылок

> Pet-проект: учебный сервис linkd (Python, PostgreSQL) проходит полный путь до
> «продакшена»: GitLab CI → registry → Argo CD → Kubernetes, мониторинг по SLO,
> секреты в Vault, проверенное восстановление из бэкапа. Сервис — учебный;
> платформа вокруг него и утилиты в tools/ — моя работа.

![pipeline](https://gitlab.com/&lt;you&gt;/linkd-platform/badges/main/pipeline.svg)

## Архитектура
&lt;схема Mermaid&gt; + 3–5 предложений о пути «коммит → прод».

## Стек
| Слой | Инструменты |
|------|-------------|
| Сервис и утилиты | linkd 2.0 (Python, PostgreSQL), свои утилиты на Python |
| Сборка и CI | Docker, GitLab CI, Trivy, gitleaks |
| Инфраструктура | Terraform (docker provider, state в MinIO), Ansible, Vagrant, kind |
| Доставка | Helm, Argo CD (app-of-apps) |
| Наблюдаемость | Prometheus, Alertmanager → Telegram, Grafana, Loki, Alloy, Tempo, k6 |
| Секреты и безопасность | Vault, External Secrets, ansible-vault, NetworkPolicy, PSA restricted |

## Что реализовано
- [x] Образ собирается один раз, продвижение dev → prod перетегированием
- [x] Кластер поднимается из git за N минут
- [x] SLO …%, burn-rate алерты с тестами, runbook'и
- [x] Бэкап вне кластера, еженедельная автоматическая проверка восстановления
- [ ] В планах: …

## Быстрый старт
Локально: make up && make smoke
Кластер с нуля: make cluster, затем bootstrap (3–5 команд)

## CI/CD · Инфраструктура · Kubernetes · Наблюдаемость · Безопасность · Бэкапы и DR
&lt;по короткому разделу из этапов 02–09, длинное — ссылкой в docs/&gt;

## Архитектурные решения
- `ADR-001: Два репозитория и pull-модель`
- …

## Ограничения и что дальше
Честно: dev-режим Vault, одна реплика БД, dev и prod в одном kind-кластере, всё на одном хосте.
````

Правила хорошего README:
- **первый экран** отвечает на «что это и зачем» — без прокрутки;
- **быстрый старт** работает с нуля (проверь в чистом клоне и новом кластере);
- **честный раздел ограничений** вызывает больше доверия, чем «всё идеально»;
- длинное — в `docs/`, README ссылается.

### 2. Схема

ASCII из [00_INDEX.md](/project/) хороша для Obsidian; в GitLab/GitHub удобнее
Mermaid — он рендерится прямо в README:

```mermaid
flowchart LR
  dev([Разработчик]) -->|merge request| app[linkd-platform]
  app --> ci[GitLab CI: test, build, Trivy]
  ci -->|push :sha| reg[(Container Registry)]
  ci -->|commit image.tag| gitops[linkd-gitops]
  gitops -->|pull| argo[Argo CD]
  subgraph cluster [kind]
    argo --> svc[linkd 2.0]
    svc --> pg[(PostgreSQL)]
    prom[Prometheus] -->|scrape| svc
    prom --> am[Alertmanager]
    prom --> graf[Grafana]
    loki[Loki] --> graf
    tempo[Tempo] --> graf
    vault[(Vault)] --> eso[External Secrets]
    eso --> svc
  end
  reg -->|pull image| svc
  am --> tg([Telegram])
  pg -->|backup| minio[(MinIO вне кластера)]
```text

### 4. ADR

Короткий документ на одно решение: контекст → варианты → решение → последствия.

```markdown
# ADR-001: Два репозитория и pull-модель доставки

- Статус: принято
- Дата: ГГГГ-ММ-ДД

## Контекст
Нужно доставлять linkd в kind-кластер так, чтобы у CI не было доступа к кластеру,
а история выкаток была видна и откатывалась.

## Варианты
1. Один репозиторий, CI делает helm upgrade в кластер.
2. Один репозиторий, Argo CD Image Updater сам обновляет тег.
3. linkd-platform (код, CI) + linkd-gitops (желаемое состояние), CI коммитит тег.

## Решение
Вариант 3.

## Последствия
+ У CI нет kubeconfig; утечка CI-переменных не даёт доступа к кластеру.
+ git log linkd-gitops = история выкаток, откат = git revert.
− Токен на запись в gitops-репо в CI, возможны гонки коммитов (resource_group + retry).
− Два репозитория нужно держать согласованными (версия чарта, имена).
```text
Темы ADR, которые уже есть в портфолио:

| № | Решение | Главный аргумент |
|---|---------|------------------|
| 001 | Два репозитория и pull-модель | у CI нет доступа к кластеру, история деплоев = git |
| 002 | Способ связи чарта и values (копия / multi-source / OCI) | этап 06 |
| 003 | CI коммитит тег, а не Image Updater | явность при одном сервисе |
| 004 | PostgreSQL вместо SQLite в linkd 2.0 | несколько реплик, вывод из 04-shipyard |
| 005 | PostgreSQL в своём StatefulSet, а не оператор | прозрачность для обучения, план перехода |
| 006 | Terraform с docker provider вместо облака | деньги и воспроизводимость, путь в облако |
| 007 | Режим Vault + ESO | секреты вне git при разумной сложности |
| 008 | SLO и multiwindow burn rate | алерты на симптом, а не на CPU |
| 009 | Бэкапы в MinIO вне кластера | переживают потерю кластера |

### 5. Строки для резюме

Раздел **«Проекты»** (не «Опыт работы»), с пометкой «pet-проект» и ссылкой. Под
конкретную вакансию — 4–6 строк, безличными формами:

- Построение платформы доставки и эксплуатации для учебного сервиса на Python + PostgreSQL: GitLab CI → Container Registry → Argo CD → Kubernetes.
- Контейнеризация сервиса: multi-stage образ меньше 100 МБ, non-root, healthcheck; локальный стенд в Docker Compose (nginx, две реплики, PostgreSQL).
- Настройка CI в GitLab: шаблоны через include, правила для MR/веток/тегов, скан образов Trivy, публикация с тегом по SHA, релизы перетегированием, доставка через коммит в gitops-репозиторий.
- Описание инфраструктуры как кода: модули Terraform с remote state в S3-совместимом хранилище (MinIO), окружения dev/prod, import и обнаружение drift; Ansible-роли с двумя окружениями, ansible-vault и идемпотентными прогонами.
- Разработка Helm-чарта: пробы liveness/readiness, requests/limits, PDB, NetworkPolicy; окружения dev/prod через Argo CD app-of-apps с self-heal и откатом через git.
- Настройка наблюдаемости: Prometheus, Grafana, Loki, Tempo; SLO с multiwindow burn-rate алертами, покрытыми promtool-тестами, доставка в Telegram, нагрузочные сценарии k6.
- Управление секретами через HashiCorp Vault (AppRole, Kubernetes auth, External Secrets Operator), Pod Security «restricted», проверки gitleaks и `trivy config` в CI.
- Резервное копирование PostgreSQL в S3-совместимое хранилище вне кластера с автоматической проверкой восстановления; runbook и DR-учения с замером RTO.
- Разработка утилит автоматизации на Python с тестами: CLI к API сервиса, анализатор логов, Prometheus-exporter, бэкап в S3.

Цифры — **только замеренные**: «образ уменьшен с X до Y МБ», «кластер разворачивается
из git за N минут», «RTO при потере кластера — N минут».

Чего не писать:
- «Коммерческий опыт с Kubernetes» — это pet-проект, так и называется;
- «Разработка сервиса сокращения ссылок» — сервис учебный, не твой;
- инструменты, которые только установлены, но не разобраны;
- «высоконагруженная система», «микросервисная архитектура» — один сервис, честно.

### 6. Рассказ за 3 минуты

| Время | Блок | Что сказать |
|-------|------|-------------|
| 0:00–0:20 | Что и зачем | одна фраза: учебный сервис, на котором отработан путь кода до прода |
| 0:20–1:20 | Архитектура по потоку | MR → CI → registry → gitops → Argo → кластер → метрики/алерты. Рисуется за минуту |
| 1:20–2:20 | Одна глубокая история | проблема → как искалась причина → решение → что вынесено. Из журнала |
| 2:20–3:00 | Результат и планы | 2–3 цифры, честные ограничения, следующий шаг |

Пример (настоящее время и безличные формы — рассказ звучит спокойнее и короче):

> «Это pet-проект: учебный сервис коротких ссылок, вокруг которого построена платформа
> доставки и эксплуатации. Код и сборка — в одном репозитории, желаемое состояние
> кластера — в другом. На каждый merge request GitLab CI гоняет тесты, собирает образ и
> сканирует его; после merge образ с тегом по SHA уходит в registry, а CI коммитит новый
> тег в gitops-репозиторий. Argo CD замечает коммит и раскатывает dev; прод обновляется
> через merge request с ревью.
>
> Для сервиса записан SLO, алерты по скорости сгорания бюджета ошибок покрыты тестами
> и приходят в Telegram, от алерта можно дойти до логов и трейса. Секреты — в Vault,
> в кластер их доставляет External Secrets. База бэкапится в хранилище вне кластера,
> и раз в неделю отдельная джоба проверяет восстановление.
>
> Самая показательная проблема — унаследованный скрипт бэкапа, который иногда давал
> битую базу. Причина нашлась чтением кода: копировался живой файл посреди записи.
> Решение — консистентный снимок средствами самой СУБД, проверка целостности после
> каждого бэкапа и регулярное восстановление; разбор лежит в репозитории как постмортем.
>
> Кластер поднимается из git за N минут, восстановление после потери кластера — N минут.
> Ограничения — всё на одном хосте и Vault в dev-режиме; следующий шаг — …»

История в середине должна быть **своей** — из журнала поломок. Выдуманная рассыпается
на втором уточняющем вопросе.

### 7. Уточняющие вопросы и опоры для ответа

| Вопрос | На что опереться |
|--------|------------------|
| Сервис вы писали сами? | Нет, он учебный; моя работа — платформа, утилиты в `tools/`, решения в ADR |
| Почему два репозитория? | ADR-001: у CI нет доступа к кластеру; история деплоев = git log gitops-репо |
| Что будет, если упадёт Argo CD? | Приложения работают; остановятся синхронизация и self-heal |
| Как откатить прод? | `git revert` в gitops-репо; аварийно — rollback в Argo с отключением auto-sync |
| Почему не `latest`? | Воспроизводимость, понятно, что работает, откат на конкретный SHA |
| Как секрет попадает в под? | Vault → ESO (Kubernetes auth, роль на namespace) → Secret → env |
| Как деплой проходит без простоя? | readiness на `/readyz`, стратегия обновления, корректный SIGTERM, PDB |
| Как масштабировать ×10? | реплики linkd — легко; узкое место — PostgreSQL: linkd открывает подключение на каждый запрос, пула нет → PgBouncer, затем реплики на чтение |
| Почему именно эти алерты? | симптомы для пользователя + «ослепли» + данные не защищены |
| Какой RPO/RTO и как проверено? | цифры из учений, еженедельный restore-test |
| Terraform или Ansible? | оба: ресурсы, ОС, кластер — три слоя, видно по каталогам |
| Как тестируется инфраструктурный код? | `terraform validate/plan`, второй прогон Ansible, `helm lint`, promtool, учения |
| Чего не хватает до настоящего прода? | отдельные кластеры dev/prod, HA, постоянный Vault, SSO в Argo, off-site бэкапы, PITR |

## 🪤 Грабли

- **Преувеличение.** «Внедрение Kubernetes в компании» для pet-проекта — прямой путь
  к неловкой паузе. Формулировки — про то, что есть в репозитории.
- **Сервис выдан за свой.** Первый вопрос про его код — и доверие к остальному падает.
- **Список из 30 инструментов** без понимания. Лучше 10, про каждый из которых можно
  говорить 5 минут.
- **README-простыня.** Витрина + `docs/`.
- **Быстрый старт, который не работает** (забыт шаг с Vault или bootstrap) — первое,
  что проверит внимательный интервьюер.
- **Выдуманные цифры** проверяются вопросом «а как замерялось?».
- **Рассказ-перечисление** («там Docker, там Kubernetes») вместо потока «коммит → прод»
  и одной глубокой истории.
- **Секреты на скриншотах** и в истории git перечёркивают раздел «Безопасность».
- **Незаконченные этапы в README как сделанные.** Им место в «Ограничениях и планах».
